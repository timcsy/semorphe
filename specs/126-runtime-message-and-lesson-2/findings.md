# 走第二課撞到的坑

> 2026-08-15。**這份清單是 spec `126` US3 真正的產出**。
> ⚠️ 走的人是作者——按第一課的教訓，這份清單**會低估卡點**，
> 而「因為知道答案而跳過的地方」另外標。

---

## 🔴 一、課文走不通——它從頭到尾沒叫學生按「程式碼→積木」

**實測**：

```
只按「執行」            輸出區 = ""                  🔴 什麼都沒有
先按「程式碼→積木」再執行  輸出區 = "分數是 90\n程式執行完畢"  ✅
```

**卡在哪一步**：每一步。
**卡的是說明還是工具**：**兩者都是**。

- **說明錯了**：第一課在第二步教過那個鈕，而我寫第二課時**假設它會被記住**
- ⚠️ **而工具的行為更值得記**：按了「執行」，**畫面上什麼都沒發生**
  ——沒有錯誤、沒有提示、輸出區空白

> **一個什麼都不做的按鈕，與一個壞掉的按鈕，在使用者眼裡是同一件事。**

🔴 **而這條是「因為知道答案而跳過」的直接後果**：我寫課文時心裡跑的是
`e2e` 的步驟（那裡每次都按了那個鈕），**而課文裡沒有**。

**處置**：課文六處補上「先按『程式碼→積木』，再按『執行』」，
並在開場加一段解釋**為什麼**（只按執行跑的是改之前的東西）。

⚠️ **而工具那一半沒有修**——「按執行卻靜默無事」是 UX 缺陷，不在本 spec 範圍。
**記在這裡，不要讓它消失。**

---

## 🟢 二、第三步的教學設計成立了

課文刻意讓學生把 `score` 打成 `Score`，然後用系統的回覆教「宣告」：

```
變數 'Score' 尚未宣告
```

**而那句話在今天早上還是**：

```
RUNTIME_ERR_UNDECLARED_VAR: {"%1":"Score"}
```

> 🔴 **同一個教學設計，在修訊息之前根本寫不出來。**
> 課文只能寫「你會看到一串代號」——**那等於把缺陷寫進教材**。

⚠️ 而它有一個副作用值得記：**現在課文依賴那句話的逐字內容**。
訊息改了，課文就在說謊——`e2e/lesson-02.spec.ts` 因此逐字釘住它，
而失敗訊息說的是「**先問訊息這樣改對嗎，再考慮改課文**」。

---

## 🔴 三、一個不在範圍內的缺陷，記下來不修

```
score = 90;        ← 沒有 int
cout << score;
→ ✅ 跑完，輸出 "90"
```

**C++ 拒絕這段程式**（assignment to undeclared identifier），
而我們的直譯器**默默把那個變數創出來**。

⚠️ 它與使用者原話「**寫錯還能順利執行就是不合理的**」同一族，
而它**不是語法錯誤**（tree-sitter 解得出來）——與 `Cout`／`<` 同一個地盤。

🔴 **而它直接威脅第二課的教學**：這一課花了兩段講「`int` 不能省」，
而**系統本身允許省**。所以課文**避開了這個寫法**——
⚠️ 那是一個繞道，不是解決。

> **當工具的行為與課文教的規則相反時，課文只能繞路——
> 而繞路的地方就是下一個功能的規格。**

---

## ⚠️ 四、「INDEX_OUT_OF_RANGE 的參數被靜靜丟掉」

修訊息時查到的：那個文案是「陣列索引超出範圍」，**沒有佔位符**，
而有拋出點傳了 `%1`（就是那個索引值）。

```
使用者看到   陣列索引超出範圍
資訊還在     索引是 7，而它沒有被印出來
```

**沒有修**——理由是同一個身分有的拋出點傳參數、有的不傳，
把佔位符加進文案會讓**不傳的那些**在畫面上留下一個 `%1`。
🔴 而那正是第四十四條護欄第三支注入釘住的東西。

> **修法不是「把佔位符加進去」，是「讓同一個身分的參數形狀一致」
> ——而那要動拋出點，不在本輪。**

---

## ⚠️ 五、`TYPE_MISMATCH` 的參數值是**一堆不同的東西**

```
'array'                              一個型別名
`${name} 不是容器`                    一句話
'這個東西不能被指定值（它不是一個位置）'  一整句話
```

文案原本是「型別不符：預期 %1，但得到 %2」，而 **32 個拋出點沒有一個傳 `%2`**。

**處置**：改文案成「型別不符：%1」（便宜、不改行為），**不動 32 個拋出點**。
⚠️ **而那讓句子在有些情況下讀起來很怪**（「型別不符：array」）。
**訊息品質是另一件事**，本 spec 明確排除。

# FR-011 的答案：每加一課要不要手寫一支走查？

## 🔴 答案：**要，而且成本比想像低**

```
lesson-01.spec.ts   109 行   2 支測試
lesson-02.spec.ts    95 行   2 支測試
共用的               fresh() 6 行 ＋ run() 7 行   ← 第二支才長出來
```

**每課約 90–110 行，寫一次約 20 分鐘。**

## 而「要不要導出」現在有答案了：**不要**

第一課與第二課的走查**斷言的東西完全不同**：

```
第一課   積木【型別清單】=== [cpp_print, cpp_literal_string, cpp_endl]
         「骨架那一步積木數 = 0」        ← 講的是投影
第二課   輸出 === "分數是 90" / goal.txt
         錯誤訊息【逐字】=== "變數 'Score' 尚未宣告"   ← 講的是回饋
```

> **兩支的共同點只有「開瀏覽器、設程式碼、按兩個鈕」，
> 而那已經是 13 行的兩個函式了。剩下的全是這一課特有的。**

🔴 **導出一個「課程走查框架」會把那 13 行變成一個要學的東西，
而它省不下那 90 行。**

⚠️ **重看條件**：**第四課**。三課還看不出模式（兩課的斷言毫無交集），
而如果第三、四課的斷言開始長得像，那時抽出**共同的斷言**（不是共同的流程）。

> **兩個樣本看起來不像，可能是樣本太少；而三個還不像，就是它們真的不像。**

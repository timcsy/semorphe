# 151 — 兩條產出路徑的一致性，要被量出來而不是被踩到

**日期**：2026-08-20 · **上游**：spec `150` 的病歷（第二次踩同一個坑）

## 出發點：一句寫在案發現場的警告，擋不住三天後的自己

`src/components/cpp/program/generate.ts:70` 逐字（**寫於 2026-08-17**）：

> 「⚠️ `cpp:program` 有【兩條產出路徑】：這一條（有鷹架，**UI 走的**）
> 與下面的 legacy（**測試走的**）。本輪第一版只改了 legacy，
> **`c-style-parity` 10/10 而瀏覽器上仍然產出 `<iostream>`**。」
>
> 「**一份只走得到其中一條路徑的測試，會讓另一條路徑的缺陷全綠通過。**」

**而 2026-08-19 的 spec 150，我在同一個檔案裡編輯時又踩了一次**
（標頭替換只寫在 legacy 那條，單元測試全綠、瀏覽器裡完全沒作用）。

> **一句寫在案發現場的警告是【讀】的，而陷阱是【寫】的時候踩到的。**

## 量出來的規模

```
946 支測試／139 檔（全套 20%）   走 legacy 路徑（把它改成拋錯，實測 2026-08-20）
2 支測試                        裝了鷹架
產品                            app.ts:188 無條件裝鷹架；兩個宿主都走 App；沒有 CLI
```

## 🔴 而「兩條路的產出要一模一樣」是【錯的】判準

鷹架多做 preamble（`using namespace std;`）、進入點外殼、pinned items
——**那正是它存在的理由**。要求全文相同等於要求鷹架什麼都不做。

**對的判準**：**兩條路都實作的那些轉換，效果必須一致。**

今天有三個這樣的轉換：

| | 轉換 | 鷹架那條 | legacy 那條 |
|---|---|---|---|
| ① | C 方言的標頭改名 | `cHeaderLine(...)` | `toCHeader` ／ `cIoHeaderFor` |
| ② | 板子的標頭替換 | `aliasIncludeLine(...)` | 節點層的 `aliasHeader` |
| ③ | C 目標的 `bool` → `<stdbool.h>` | 直接 `code +=` | `buildInclude(C_BOOL_HEADER)` |

🔴 **每一個都是「同一件事寫兩次」**——而那正是 ① 與 ② 各出過一次事的原因。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 🔴 一個轉換只修了一條路，護欄要紅 (Priority: P1)

**驗收**：把 spec 150 的鷹架端替換拿掉 → 護欄紅；把 legacy 端拿掉 → 護欄也紅。
**兩個方向都要**——否則它只守得住其中一條。

### User Story 2 - 🔴 對照要照產品的方式配置 (Priority: P1)

⚠️ 2026-08-20 的第一次探針量出「Arduino 兩條路差很多」——
**而那是探針沒設 `entryShell`，不是產品缺陷**。

**驗收**：每個目標的鷹架配置逐項照 `app.ts` 來
（`setEntryShell(target.entryShell ?? 'main')`、`scaffoldDepth`、`headerAliases`），
而**這件事要寫在測試檔頭上**。

### Edge Cases

- **鷹架獨有的產出**（preamble／進入點）→ 不在比對範圍，而**要說出來**
- **未來新增第四個共用轉換** → 護欄要跟著加一格，⚠️ **而沒有機械方式強制**
  → 判準寫在檔頭：**「在兩條路各寫一次的東西，這裡就要有一格。」**

## Requirements *(mandatory)*

- **FR-001**：對三個共用轉換 MUST 各有一組「兩條路效果一致」的斷言
- **FR-002**：對照的鷹架配置 MUST 逐項照產品
- **FR-003**：🔴 護欄 MUST 兩個方向都會紅（改壞任一條路徑）
- **FR-004**：鷹架獨有的產出 MUST 明確排除並寫出理由

## Success Criteria

- **SC-001**：三個轉換 × 兩個方向 ＝ 六種注入，逐一驗過會紅
- **SC-002**：全套測試綠、e2e 綠

## 明確排除

- **遷移那 946 支測試**——那不是一刀，是一個專案
- **刪掉 legacy 路徑**——要不要刪由這支護欄的結果決定，**不是先決定**
- **「兩條路產出全文相同」**——錯的判準（見上）

## 已知的坑

1. 🔴 **探針自己配置錯 → 量出假差異**（2026-08-20 已踩過一次）
2. **`setProgramScaffold` 沒有「清掉」的介面**——測試要 cast，⚠️ 而那是**測試的權宜**，
   不要為了它改產品介面
3. **這支護欄防的是「同一件事寫兩次」的後果，不是那個成因**
   —— ⚠️ 成因（兩條路徑）仍然在，而**護欄不該假裝它治好了根因**

# Feature Specification: 符合性清償——函式族的參數不再靜默消失

**Feature Branch**: `105-conformance-params`

**Created**: 2026-08-10

**Status**: Draft

**Input**: 六顆元件宣告了 `params` 接點，而它們的積木形態表達不出來——走一次 render → extract 參數就靜默消失。這是第二十九條護欄（符合性）第一次跑抓到的 7 筆裡的 6 筆。

---

## 問題（實測，不是推想）

```
[](int a, int b) { return a + b; }   →   []() { return a + b; }
C(int a) {}                          →   C() {}
```

**使用者看得到**：任何一次工作區重新序列化（切語言、切風格、存檔重載）都會走
render → extract，於是參數消失，而**產出的仍然是合法的 C++**——
所以沒有任何錯誤訊息，程式只是**不再是使用者寫的那一段**。

### 為什麼 `func_def` 沒事而這六顆有事

| | `params` 接點 | 積木形態怎麼表達 | 結果 |
|---|---|---|---|
| `cpp:func_def` | ✅ lift 產出 `param_decl` 子節點 | `renderMapping.dynamicRules` → 動態欄位 `TYPE_{i}`／`PARAM_{i}` | ✅ 走得過 |
| 其餘六顆 | ✅ 同上 | **沒有任何對應**——只映射 `CAPTURE`／`BODY` | 🔴 掉 |

六顆是：`cpp:lambda`、`cpp:constructor`、`cpp:method_virtual`、
`cpp:method_virtual_pure`、`cpp:method_override`、`cpp:template_function`。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 寫了參數的函式，換個視角回來參數還在 (Priority: P1)

學生在程式碼視圖寫 `[](int a, int b) { return a + b; }`，切到積木視圖看它長什麼樣，
再切回程式碼——參數必須還在。今天不在。

**Why this priority**: 這是**靜默的資料遺失**。產出仍是合法程式，所以沒有任何訊號；
而 lambda 與建構子是課程裡真的會教的東西。

**Independent Test**：對每一顆元件跑「原始碼 → 語義樹 → 積木 → 語義樹 → 原始碼」，
結果與原始碼**逐字相同**。

**Acceptance Scenarios**:

1. **Given** `[](int a, int b) { return a + b; }`，**When** 走完一次投影來回，
   **Then** 產出與輸入逐字相同。
2. **Given** `C(int a) {}`，**When** 走完一次投影來回，**Then** 產出與輸入逐字相同。
3. **Given** 一個**沒有參數**的同族元件（`[](){...}`），**When** 走完來回，
   **Then** 產出沒有多出空的參數表示（不得變成 `[]( )` 或 `[](void)`）。
4. **Given** 使用者在積木上編輯參數文字，**When** 切回程式碼，
   **Then** 程式碼反映編輯後的參數。

---

### User Story 2 - 加第七顆同族元件時，不必再改一次共用檔 (Priority: P2)

未來新增一顆有參數的元件（另一種方法修飾詞、Python 的函式…），
應該只需要**在它自己的宣告裡多寫一行**，不必去動投影引擎。

**Why this priority**: 這一階段治的病就是「加一顆元件要編輯 N 個既有共用檔」。
六顆各寫一份 82 行的 Blockly 動態積木是**把病規模化**。

**Independent Test**：合成一顆全新的、宣告了 `params` 接點的元件，
只加宣告不改任何引擎程式碼，它的參數必須走得過來回。

**Acceptance Scenarios**:

1. **Given** 一顆新元件的宣告裡有那一行映射，**When** 走投影來回，
   **Then** 參數保住，且**沒有任何共用檔被修改**。
2. **Given** 一顆有 `params` 接點但**沒寫**那一行映射的元件，
   **When** 符合性護欄執行，**Then** 它被報為違規（沉默不算通過）。

---

### User Story 3 - 護欄的數字要真的下降，而且不是靠改量測 (Priority: P3)

**Why this priority**: `history/018` 的教訓——用宣告刷數字看起來會像進步。

**Independent Test**：符合性護欄的「確定違規」從 7 降到 1，
且**護欄的判準一個字都沒有改**。

**Acceptance Scenarios**:

1. **Given** 修改完成，**When** 符合性護欄執行，**Then** 確定違規 = 1
   （只剩 `cpp:vector_declare`），且「無法確定」不上升。
2. **Given** 有人把某一顆的映射拿掉，**When** 護欄執行，**Then** 它變紅並指名那一顆。

---

### Edge Cases

- **零個參數**：不得產出空的參數表示，也不得把「沒有參數」與「沒宣告」搞混。
- **參數只有型別沒有名字**（`void f(int)`）：要嘛保住、要嘛明確不支援並記進缺陷帳，
  不得靜默補一個名字。
- **參數含逗號的型別**（`map<int,int> m`）：分隔符的選擇不得讓它拆錯。
  這一條**必須有測試**——它是這個方向最明顯的失敗模式。
- **參數含預設值**（`int a = 3`）：今天 lift 產不產出？產不出的話要明確不支援。
- **使用者在積木上打了不合法的參數文字**：不得讓整棵樹壞掉；
  最差情況是那一顆元件的參數維持原樣或清空，而不是拋例外中斷同步。
- **`method_virtual_pure` 沒有 body**：它只有 `params` 一個接點，
  修好之後不得因為缺 body 而走不過渲染。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓宣告了 `params` 接點的元件，其參數在「語義樹 → 積木形態 → 語義樹」
  之後**保持結構化**（每個參數的型別與名字各自可取得），而不只是保住一段文字。
- **FR-002**: 上述能力 MUST 由**一個共用機制**提供，六顆元件各自**只加宣告**；
  不得為每顆元件複製一份行為程式碼。
- **FR-003**: 一顆有 `params` 接點卻**沒有**宣告該映射的元件，MUST 被符合性護欄報為違規
  ——**沉默不得等於通過**。
- **FR-004**: 參數為零時，系統 MUST 產出與「原本就沒有參數」完全相同的結果。
- **FR-005**: 參數的文字表示 MUST 能承載型別中含分隔符的情形（例如 `map<int,int>`），
  或**明確宣告不支援**並讓該情形被護欄看見。
- **FR-006**: 使用者在積木上輸入無法解析的參數文字時，系統 MUST NOT 中斷同步或拋出未處理的例外。
- **FR-007**: 本次改動 MUST NOT 改變任何元件身分，因此 MUST NOT 需要存檔遷移；
  且 MUST 有測試釘住這一點。
- **FR-008**: 六顆元件的**既有積木外觀 MUST 維持**（使用者今天在哪裡打參數，之後還在那裡）。

### Key Entities

- **參數**：一顆函式族元件的形式參數。語義樹裡是結構化的子節點（型別 ＋ 名字）；
  積木形態上是使用者看得到、編輯得到的表示。
- **形態映射**：把語義的接點與積木上的表示接起來的**宣告**。
  這次新增的那一種，是六顆元件唯一要寫的東西。

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 符合性護欄的「確定違規」**7 → 1**，且護欄判準未修改。
- **SC-002**: 六顆元件各至少一個**有參數**與一個**無參數**的來回樣本，
  產出與輸入**逐字相同**（0 筆差異）。
- **SC-003**: 型別含分隔符的樣本（`map<int,int>`）**有測試**，
  且結果是「保住」或「明確不支援且被護欄看見」二者之一。
- **SC-004**: 新增一顆合成的同族元件只需**加宣告**，**0 個共用檔**被修改。
- **SC-005**: 全套測試在每一顆元件修完時都是綠的（紅燈步數 = 0）。
- **SC-006**: 存檔版本不變，且有測試釘住「本次改動不需要遷移」。
- **SC-007**: **瀏覽器實測**：六顆元件在真實編輯器裡，參數在切語言前後一致。

## Assumptions

- **參數的積木表示沿用既有的單一文字欄位**（`PARAMS`），不改成
  `func_def` 那種每參數一組下拉＋輸入框。理由：那六顆**今天就長這樣**，
  使用者已經在那裡打字；把「修資料遺失」與「改積木外觀」綁在一起會讓
  紅燈無法歸因，而後者是獨立的 UX 決定。
  ⚠️ **這是取捨不是結論**——升級的判準寫在下面。
- **語義樹保持結構化**。文字只是**形態**；`param_decl` 子節點不變。
  這一點與既有教訓「需要 parse 回結構才能用的字串，就不該是字串」的張力，
  處置是：**字串只存在於形態層，語義層永遠是結構化的**，且來回轉換有機械檢查。
- **不修 `cpp:vector_declare`**——它的接點是**變長列表**，形狀不同。
- **不修 `cpp:func_def` 的宣告錯誤**（`params` 寫成屬性而 lift 產出接點）——
  那是另一個方向的問題，見下。
- **lift 側不動**：`param_decl` 已經產得出來（實測過）。

### ⚠️ 什麼時候該把參數升級成結構化插槽

三個訊號，**任一個出現就該升級**，不要等三個都到：

1. 使用者在參數欄位裡打錯字造成的缺陷**出現第二次**
2. 需要對參數做**逐項操作**（重排、單獨刪一個、型別下拉選單）
3. 型別含分隔符的情形從「測試裡的邊界案例」變成**課程裡真的會教的東西**

---

## Out of Scope

- `cpp:vector_declare` 的變長初始值（形狀不同，要動態積木）
- 那 3 筆「無法確定」（`cpp:program`／`cpp:if_else`／`cpp:comma_expr`）
- 把六顆的積木改成 `func_def` 那種每參數一組欄位的外觀
- **符合性護欄的反方向**：它從**宣告**合成節點，所以「宣告漏了一個接點」看不見
  ——`cpp:func_def` 正是這樣逃掉的（宣告把 `params` 寫成屬性，而 lift 產出接點）。
  反方向是「**lift 實際產出的接點，宣告裡有嗎**」，要另外開一條。
- `cpp:func_def` 宣告與實作不一致的修正（會被上面那條護欄抓到，一起做比較合理）

# Contract：存檔 v2 → v3

## 為什麼一定要有

P8「不做向後相容」的**範圍**不含語義詞彙本身（`knowledge/history/026`）：
P8 推導自「投影可重建」，而 componentId 改名動的是**真實**，沒有東西可以重建它。
→ 這類變更 **MUST** 附一次性轉換。

**這是那條釐清的第二次使用**（第一次是 B 項的六對合併，v1→v2）。

## 契約

| 輸入 | 輸出 |
|---|---|
| `version: 2` 的存檔 | 語義樹的 `conceptId` 全部改寫為新格式，`version: 3` |
| `version: 3` 的存檔 | 不觸發轉換 |
| 樹中已是新格式的身分 | 原樣通過（冪等） |
| 轉換表認不得的身分 | **原樣保留**，該節點不丟棄 |
| `blocklyState` 裡的積木型別 | **完全不動** |

## 驗收

- 同一份存檔遷移前後，產出的程式碼**逐字相同**
- `storage-version.test.ts` 既有的「從 1 到 `CURRENT_VERSION` 的每一步都必須有註冊」
  那支測試必須仍然通過（調高版本卻忘了寫升級函式，它會紅）

## 不做的事

- 不轉積木型別。B 項已定加法式保留（`c_increment_expr` 仍有效，只是對應到 `cpp_increment`）
  ——**不必要的轉換是額外的風險面**

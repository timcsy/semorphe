# Feature Specification: 能力介面——語意能力由可抽換的提供者給，核心只認能力

**Feature Branch**: `179-capability-interface`

**Created**: 2026-10-31

**Status**: Draft

**Input**: 重構階段 1（vision〈重構：語意交給 Cella〉）。使用者 2026-10-31 定的方向：「降級路徑應該是有系統的，且不混雜的，方便未來深嵌入完成之後替換過去」；
核心只認四種能力（判決、型別查詢、執行與除錯、步數），提供者各自宣告做得到哪些，有序登錄表決定用誰，每個結果帶出處與少了什麼；核心不准 import 提供者。
設計：`knowledge/draft/2026-10-31-重構的設計-能力介面與降級路徑.md`。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 學生照常執行、除錯、判題，什麼都沒變（Priority: P1）

學生打開任一堂課（C++、Python、Arduino），按執行、逐步、設中斷點、看變數、改變數、輸入資料、提交答案——行為與今天逐字相同。
這一刀換的是「誰在背後給答案」的接法，不是答案本身。

**Why this priority**: 這一刀之後到切換到 Cella 之間還有好幾個月，學生每天在用；任何退步都是直接的傷害。

**Independent Test**: 全部 e2e 與課文判題測試在改動前後結果相同。

**Acceptance Scenarios**:

1. **Given** 一堂會讀輸入的 C++ 課，**When** 學生執行並在提示時輸入，**Then** 輸出與今天相同。
2. **Given** 設了中斷點的程式，**When** 學生以除錯模式執行，**Then** 停在同一顆積木、變數面板顯示同樣的值，改變數後續跑結果相同。
3. **Given** 一份課文的參考解答，**When** 系統判題，**Then** 判定與今天相同。

---

### User Story 2 - 換一個提供者不必改核心（Priority: P1）

開發者要接上另一個能給「執行與除錯」的提供者（之後是 Cella，或外接的 debugger）：寫一個提供者、宣告它的能力、在組裝點登記，核心與介面零修改。

**Why this priority**: 這是整個重構的目的——深嵌入完成時，替換是刪一個提供者、加一個提供者，不是在核心裡到處改。

**Independent Test**: 用一個只宣告部分能力的測試用提供者登記在前面，確認核心改用它的那幾項、其餘照舊落到原本的提供者，而核心沒有任何一行知道它的名字。

**Acceptance Scenarios**:

1. **Given** 登錄表裡有兩個提供者，前面那個只宣告「執行與除錯」，**When** 系統要執行，**Then** 用前面那個；**When** 系統要判題，**Then** 落到宣告了判題（或其退回路徑）的那個。
2. **Given** 核心與介面的原始碼，**When** 自動檢查 import，**Then** 沒有任何一處直接引用某個提供者。

---

### User Story 3 - 降級看得見（Priority: P3）

當某項能力沒有提供者、或提供者給的比較少（例如沒有步數），學生與老師在畫面上看得到「這是誰給的、少了什麼」，而不是悄悄換成比較弱的答案。

**Why this priority**: 誠實降級（P6）的「必須可見」。⚠️ 本階段判決與型別兩項能力**還沒有任何介面消費者**（判題今天是比執行的輸出、型別篩選今天是既有的 slot-check，兩者到階段 5～6 才換），
所以本階段只立「結果帶出處與缺項」的形狀；畫面上的說明隨階段 5 的第一個消費者一起做。

**Independent Test**: 向登錄表要一項沒有提供者的能力，確認回來的結果帶著 `missing` 與出處，而不是 undefined 或例外。

**Acceptance Scenarios**:

1. **Given** 沒有任何提供者宣告型別查詢，**When** 向登錄表要型別查詢，**Then** 得到「缺這項能力」的結果，說得出缺的是哪一項。
2. **Given** 一次執行，**When** 執行結束，**Then** 結果說得出是哪個提供者跑的。

### Edge Cases

- 兩個提供者都宣告同一項能力：取登錄表裡前面那個，不並跑比對（設計 draft 第五節第 3 條）。
- 提供者在執行中途失敗：照今天的錯誤呈現，並標出處；不自動改用下一個提供者（避免一次執行混用兩份語意）。
- 單獨運作（沒有 Cella）：判題退回「跑一次比輸出」，型別查詢不篩不標（第 3 題）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 以四項能力描述語意：判決、型別查詢、執行與除錯、步數；每項有固定的輸入與輸出形狀，形狀照 Cella 的判決／型別查詢／除錯工作階段（不另發明）。
- **FR-002**: 每個提供者 MUST 宣告它支援哪幾項能力，以及執行與除錯的細節：停點粒度（敘述或節點）、能否改輸入、能否改變數、給不給步數。
- **FR-003**: 系統 MUST 依一張有序的登錄表，為每項能力挑第一個宣告了它的提供者。
- **FR-004**: 每個能力的結果 MUST 帶出處（哪個提供者）與缺項（哪些能力或細節沒有）。
- **FR-005**: 核心與介面層 MUST NOT 直接引用任何提供者；只有組裝點可以登記提供者。此條 MUST 有自動檢查。
- **FR-006**: 今天的 JS 直譯器 MUST 包成第一個提供者，只宣告它真的有的能力（執行與除錯、步數）；MUST NOT 宣告判決或型別查詢。
- **FR-007**: 本階段判題照舊用執行能力跑、比輸出（行為不變）；判題改成「優先用判決、沒有才退回跑一次比輸出」在階段 5 做（設計 draft 第五節第 1 條）。
- **FR-008**: 某項能力沒有提供者時，登錄表 MUST 回一個帶缺項的結果，不得回 undefined 或靜默略過；介面上的說明隨階段 5 的第一個消費者一起做。
- **FR-009**: 各元件的執行實作 MUST 原封不動（重構階段 6 才拆）。

### Key Entities

- **能力（Capability）**：判決、型別查詢、執行與除錯、步數四者之一。
- **提供者（Provider）**：一個能給出某些能力的實作，帶身分與能力宣告。
- **能力宣告（Capability declaration）**：提供者支援哪些能力，以及執行與除錯的細節。
- **登錄表（Registry）**：有序的提供者清單；決定每項能力用誰。
- **帶出處的結果（Result with provenance）**：能力的答案，加上「誰給的、少了什麼」。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 改動前後，全部 e2e 與課文判題的結果 100% 相同。
- **SC-002**: 核心與介面層對任何提供者的直接引用數為 0，且由自動檢查守住（注入一個違規會紅）。
- **SC-003**: 加一個新的提供者只需要新增它自己的檔案與組裝點的一行登記；核心與介面的修改行數為 0（由一支測試用提供者示範）。
- **SC-004**: 每一個能力結果都帶出處；向登錄表要一項沒有提供者的能力時，100% 得到帶缺項的結果（0 個 undefined）。

## Assumptions

- 形狀照抄 Cella 已公開的判決 JSON、型別查詢與除錯工作階段（`cella-lang/dap` 的宿主層 Cella 承諾不變）。
- 提供者住在與核心、語言套件、介面平級的目錄（設計 draft 第五節第 2 條的推薦）。
- 階段 1 期間只有一個實際提供者（JS 直譯器）；Cella 提供者在階段 5 加入。
- 執行狀態的廣播沿用既有的匯流排事件（`execution:*`），事件形狀不改。

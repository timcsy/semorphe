# Feature Specification: 四條護欄——碎裂、殼與缺陷帳的基線與棘輪

**Feature Branch**: `049-audit-guardrails`

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "階段 6.5 的 P0：為 Semorphe 建立四條護欄測試，量出碎裂、殼、條件性正確的基線並用棘輪擋住惡化。純加法、不修任何既有違規、不搬任何檔案。"

---

## 為什麼做這個

專案有三條寫下來的規範，**沒有任何一條有機械化的檢查**：

| 規範（逐字） | 現況 |
|---|---|
| P2「缺任一條路徑 = coverage gap = 架構缺陷（**0 容忍**）」 | 無檢查 |
| P9「**語言獨立性**：拔掉 C++…無 `languages/cpp/` import」 | 無檢查 |
| P3「歧義**在註冊時仲裁，不在執行時碰運氣**」 | 無檢查 |

外加使用者連續糾正三次的「**零 todo 為目標**」——已寫進四支 skill，同樣無檢查。

沒有執行機構的規範就是裝飾（見 `knowledge/concepts/執行機構.md`）。**本功能不新增任何規範，只讓這四條第一次真的被檢查。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 中立性護欄：知道語言獨立性離成立有多遠 (Priority: P1)

維護者想知道「拔掉 C++ 之後系統還能不能跑」。目前唯一的方法是真的去寫第二個語言套件，成本是一整個階段。

護欄用一條測試回答同一個問題：核心與呈現層裡有幾個檔案認得 C++ 專屬的元件身分。數字是幾，就是離語言獨立性還有多遠。

**Why this priority**：路線圖階段 7（Python）的核心目的就是驗證語言無關性。這條護欄用一條測試提前給出答案，且它是四條裡**唯一能改變路線圖決策**的。

**Independent Test**：單獨實作這條就有完整價值——跑一次就得到違規清單，可據以排後續清償順序，其餘三條護欄不存在也不影響。

**Acceptance Scenarios**：

1. **Given** 核心／呈現層目前有若干檔案硬編了特定語言的元件身分，**When** 執行中立性護欄，**Then** 報表列出每個違規檔案與它提到的元件身分，並輸出違規檔案總數
2. **Given** 已記錄的違規清單，**When** 有人在核心層新增一處對特定語言元件身分的引用，**Then** 護欄失敗並指出新增的那一處
3. **Given** 已記錄的違規清單，**When** 有人清掉其中一處違規，**Then** 護欄通過，且維護者可將基線下調到新數字

---

### User Story 2 - 完備性護欄：分辨「做完了」與「看起來做完了」 (Priority: P1)

維護者想知道哪些元件是真的實作完成、哪些只是**殼**——該有的東西在該在的位置，但它是空的或只會退化。

目前無法分辨：一個空的實作檔和一個真的實作檔，在檔案清單上長得一樣；一個永遠退化成原始碼片段的辨識路徑，和一個真的能辨識的路徑，在註冊表上長得一樣。

護欄實際**執行**每個元件的五條路徑，看它吐出什麼，然後分成三類：真的實作了／是殼／根本沒有。輸出是一張補完地圖。

**Why this priority**：這是專案宣稱「0 容忍」卻從未檢查的那條，也是使用者最擔心的問題——「很容易以為已經做完了，因為看起來有 code，但其實只有殼」。

**Independent Test**：單獨實作就得到完整的補完地圖，可直接當作後續補完工作的清單，不依賴其他三條護欄。

**Acceptance Scenarios**：

1. **Given** 註冊表中的每一個元件，**When** 執行完備性護欄，**Then** 每個元件在五條路徑上各得到一個分類（實作／殼／缺），並輸出彙總數字
2. **Given** 一個元件的執行路徑是空操作但沒有顯式宣告「本元件本來就不執行」，**When** 執行護欄，**Then** 該路徑被判為**殼**而非實作
3. **Given** 一個元件的執行路徑是空操作且**已顯式宣告**「本元件本來就不執行」，**When** 執行護欄，**Then** 該路徑被判為**實作**
4. **Given** 護欄在兩種載入組態下各跑一次，**When** 兩次的分類結果不同，**Then** 報表明確標出差異元件——這代表測試環境與實際使用環境走不同路徑
5. **Given** 已記錄的殼與缺總數，**When** 任一數字上升，**Then** 護欄失敗

---

### User Story 3 - 缺陷帳護欄：讓被歸檔的缺陷重新可見並排出優先序 (Priority: P2)

維護者想知道那些被停用的測試代表什麼。目前它們混成一團：有些是**已否決決定的正確後果**（該保留）、有些是**真缺陷**（該修）、有些是**已修好卻沒開回來**（白白損失覆蓋）、有些**一個字的理由都沒寫**。

更糟的是缺陷被記在「被它擋住的那個元件」上，而不是「有問題的那個元件」上——所以稽核有問題的那個會通過。

護欄要求每個被停用的測試標明分類，缺陷類還要標明**阻斷者是哪個元件**。有了阻斷者，就能看出「修一個 A 可以解鎖十個測試」這種優先序。

**Why this priority**：使用者已連續三次要求「發現 bug 就修、不能只留待辦」，這條護欄是那條要求的執行機構。優先序低於 P1 是因為它治的是**存量**，而 P1 兩條治的是**架構性質**。

**Independent Test**：單獨實作就能把停用測試分類、產出阻斷者統計，直接得到清償順序。

**Acceptance Scenarios**：

1. **Given** 測試套件中所有被停用的測試，**When** 執行缺陷帳護欄，**Then** 每一個都必須帶有分類標記，未標記者使護欄失敗
2. **Given** 一個被標為「缺陷」的停用測試，**When** 它沒有標明阻斷者元件，**Then** 護欄失敗
3. **Given** 一個被標為「已否決決定的後果」的停用測試，**When** 它沒有連到對應的決策記錄，**Then** 護欄失敗
4. **Given** 已記錄的停用測試總數，**When** 總數上升，**Then** 護欄失敗
5. **Given** 全部停用測試已分類，**When** 產出報表，**Then** 報表按阻斷者彙總，例如「元件 X 擋住 N 個測試」

---

### User Story 4 - 就近性護欄：量出「加一個元件要動幾個檔」 (Priority: P3)

維護者想知道新增一個元件的實際成本。專案宣稱可以在不修改既有程式碼的前提下加入新概念，但實際上一個元件的實作散在十幾個檔案。

護欄對每個元件數它出現在幾個原始檔、幾個目錄，作為碎裂程度的量化指標。

**Why this priority**：碎裂是**看得出來**的病，痛感最低；而且它的清償主要發生在後續期別的搬移，護欄本身只提供進度計。P1／P2 三條治的是看不出來的病，價值更高。

**Independent Test**：單獨實作就得到每元件的擴散度排名，可用來排搬移順序。

**Acceptance Scenarios**：

1. **Given** 註冊表中的每一個元件，**When** 執行就近性護欄，**Then** 輸出每個元件的檔案數與目錄數，以及最擴散的前幾名
2. **Given** 已記錄的每元件檔案數上限，**When** 任一元件的檔案數上升，**Then** 護欄失敗並指出是哪個元件
3. **Given** 某元件的實作被收攏，**When** 重跑護欄，**Then** 該元件的數字下降且維護者可下調其上限

---

### Edge Cases

- **元件身分字串出現在無關的上下文**（註解、字串字面、測試資料）——中立性與就近性都靠「檔案提到某個元件身分」判定，必須定義什麼算「提到」，避免誤報使護欄失去可信度
- **一個元件本來就不該有某條路徑**（宣告性元件不執行、無視覺形態的元件不渲染）——若無法與「缺失」區分，完備性護欄會產生大量假陽性
- **最小樣本本身不具代表性**——完備性護欄跑的那個樣本可能恰好是會通過的簡單情形，導致一個「淺的情形對、深的情形錯」的元件被判為實作
- **停用測試以區塊為單位停用**（整組一次停用）——單一標記可能覆蓋多個測試，計數與分類需定義以什麼為單位
- **基線調整被濫用**——若下調基線太容易，棘輪形同虛設；若太難，正當的清償無法反映
- **護欄本身跑很久**——完備性護欄要執行每個元件的五條路徑，可能顯著拖慢既有的測試迴圈

## Requirements *(mandatory)*

### Functional Requirements

**通用**

- **FR-001**: 四條護欄 MUST 在既有測試流程中被執行，且各自能獨立執行
- **FR-002**: 每條護欄 MUST 輸出**人類可讀的報表**（違規或分類的明細），而不只是通過／失敗
- **FR-003**: 每條護欄 MUST 以**已記錄的基線**為門檻：數字持平或下降則通過，上升則失敗
- **FR-004**: 基線 MUST 以可版本控制的形式記錄，且調整基線 MUST 是一個顯式的、可在版本歷史中看見的動作
- **FR-005**: 護欄失敗時 MUST 指出**是哪一項使數字上升**，而不只是報告總數變了
- **FR-006**: 四條護欄 MUST NOT 修改任何既有程式碼的行為；既有測試全數維持通過

**① 中立性**

- **FR-010**: 護欄 MUST 檢查核心與呈現層的原始檔是否提及任何特定語言的元件身分
- **FR-011**: 護欄 MUST 輸出違規檔案清單，含每個檔案提及的元件身分
- **FR-012**: 護欄 MUST 定義並記錄「提及」的判定方式，且該方式 MUST 排除顯而易見的誤報

**② 完備性**

- **FR-020**: 護欄 MUST 對註冊表中每個元件**實際執行**五條路徑的最小樣本，而非僅檢查路徑是否註冊
- **FR-021**: 護欄 MUST 將每條路徑分類為「實作」、「殼」或「缺」，並定義**殼**的判定條件（路徑存在但輸出退化）
- **FR-022**: 「一個元件本來就不需要某條路徑」MUST 由該元件**顯式宣告**，未宣告的空實作 MUST 判為殼
- **FR-023**: 護欄 MUST 在至少兩種載入組態下執行，並在分類結果不一致時明確標出差異
- **FR-024**: 護欄 MUST 輸出補完地圖：每個元件 × 五條路徑的分類矩陣
- **FR-025**: 護欄的報表 MUST 明確聲明它**不檢測「條件性正確」**（單獨測通過、組合時失敗的情形），避免通過被誤讀為完備

**③ 缺陷帳**

- **FR-030**: 每一個被停用的測試 MUST 帶有分類標記，分類至少涵蓋：已否決決定的正確後果／缺陷／已修復未啟用
- **FR-031**: 標為「缺陷」者 MUST 標明阻斷它的元件身分
- **FR-032**: 標為「已否決決定的後果」者 MUST 連到對應的決策記錄
- **FR-033**: 未帶分類標記的停用測試 MUST 使護欄失敗
- **FR-034**: 護欄 MUST 產出按阻斷者彙總的統計，使「修一個解鎖多個」的優先序可見
- **FR-035**: 護欄 MUST 同時涵蓋單一測試的停用與測試區塊的整組停用

**④ 就近性**

- **FR-040**: 護欄 MUST 對註冊表中每個元件計算它出現在幾個原始檔與幾個目錄
- **FR-041**: 護欄 MUST 輸出擴散度排名，並支援每元件各自的上限
- **FR-042**: 護欄 MUST 定義並記錄「出現」的判定方式（與 FR-012 一致）

### Key Entities

- **護欄（Guardrail）**：一項可重複執行的檢查，包含一個量測、一份人類可讀報表、一個記錄下來的基線，以及「數字只准下降」的門檻規則
- **基線（Baseline）**：某條護欄在某個時間點量到的數字與明細清單；是棘輪的比較對象，調整需顯式進行
- **路徑分類（Path Classification）**：某個元件在某條路徑上的狀態——實作／殼／缺
- **補完地圖（Completion Map）**：元件 × 路徑的分類矩陣，後續補完工作的清單
- **缺陷帳目（Defect Entry）**：一個被停用的測試，帶分類、阻斷者（若為缺陷）或決策連結（若為已否決決定的後果）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 四條護欄全部進入既有測試流程，各自輸出**非零的基線數字**——沒有數字等於沒做
- **SC-002**: 任一護欄的數字上升時，測試流程失敗；維護者能在報表中直接看到是哪一項造成的
- **SC-003**: 完備性護欄產出涵蓋註冊表中**全部**元件的補完地圖，無元件被靜默略過
- **SC-004**: 100% 的被停用測試帶有分類標記；標為缺陷者 100% 標明阻斷者；標為已否決決定後果者 100% 連到決策記錄
- **SC-005**: 缺陷帳報表能回答「修哪一個元件可以解鎖最多測試」——目前完全無法回答
- **SC-006**: 既有測試全數維持通過，且本功能**零行為改動**——除新增護欄外，不改變任何既有輸出
- **SC-007**: 四條護欄的總執行時間不使既有測試迴圈的體感變差，維持在維護者願意每次都跑的範圍內
- **SC-008**: 維護者在不閱讀任何實作程式碼的情況下，能從報表判斷「這個元件到底做完了沒」

## Assumptions

- **既有測試套件是可信的安全網**：本功能純加法、零行為改動，既有測試維持全綠即代表沒有破壞
- **基線第一天不會是零**：所有護欄的初始數字都是正數（已知有違規、殼與停用測試存量），因此護欄的形式是**報表加棘輪**而非通過／失敗；要求第一天就綠是不切實際的
- **元件註冊表是元件的權威清單**：護欄以註冊表為遍歷來源，未註冊的東西不在本功能的檢查範圍
- **「顯式宣告不需要某條路徑」這個機制目前不存在**：完備性護欄需要它才能區分「正確的空」與「缺失的空」，因此本功能包含引入該宣告，但**不包含**為既有元件補上宣告——那是後續清償工作
- **停用測試的分類標記需要人工補上**：護欄能檢查標記是否存在，但無法自動判斷某個停用測試屬於哪一類；本功能包含為現有存量補標記
- **報表格式以維護者閱讀為準**，不需要對外或圖形化呈現
- **本功能只治 C++ 現況**：其他語言尚未有實質內容，護欄設計需語言中立，但驗證只在 C++ 上進行

## Out of Scope（明確排除）

以下**明確不在本功能範圍**，列出以防範圍蔓延：

- ❌ **修任何一個違規、殼或停用測試**——本功能只**量**，不**修**
- ❌ **消除多套平行機制的仲裁協定**（後續期別）
- ❌ **目錄結構重整、元件膠囊格式、任何檔案搬移**
- ❌ **改動核心型別、詞彙改名、序列化格式**
- ❌ **碰觸最大的雙重真相來源檔**——它是後續期別的目標，本功能只在報表中記錄它
- ❌ **檢測「條件性正確」**（單獨測通過、組合時失敗）——完備性護欄明確不做這件事，該類問題靠既有的組合式測試發現

## Risks & Mitigations

| 風險 | 緩解 |
|---|---|
| **完備性護欄的綠燈製造安全感**——它抓不到「淺的情形對、深的情形錯」 | FR-025 要求報表明說它不檢測條件性正確 |
| **護欄本身變成殼**——只產報表沒人看，數字上升也沒人擋 | FR-003 要求棘輪卡在測試流程中（上升即失敗），不只是報表 |
| **誤報侵蝕可信度**——判定方式太寬鬆會產生大量假陽性，維護者最後直接忽略 | FR-012／FR-042 要求判定方式被定義並記錄；邊界情形已列入 Edge Cases |
| **基線調整被濫用**，棘輪形同虛設 | FR-004 要求調整是顯式且在版本歷史中可見的動作 |
| **執行時間拖垮迴圈** | SC-007 設為成功標準；必要時完備性護欄可與其他護欄分開執行頻率 |
| **為存量補分類標記的工作量被低估** | 假設中已載明這是人工工作；它是本功能的一部分，不是副作用 |

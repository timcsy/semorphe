# Feature Specification: 目標（target）——把三個既有機制綁成一個具名組合

**Feature Branch**: `134-target-named-combination`
**Created**: 2026-08-17
**Status**: Draft
**路線圖位置**: 階段 6.10

## User Scenarios & Testing *(mandatory)*

一位老師要教 C（不是 C++）。今天他要**分三個地方各選一次**：

```
選一個【課程清單】     決定哪些積木看得到
選一個【風格】         決定產出 printf 還是 cout
心裡記著【用什麼編譯器驗】  而系統不知道這件事
```

⚠️ **三次選擇必須一致，而沒有任何東西保證它們一致。** 選錯一個，
學生會看到一顆他的編譯器編不出來的積木——**而系統不會說任何話**。

> **三個機制各自都對，而沒有東西保證它們指向同一個世界。**

### User Story 1 - 選一次，而不是三次 (Priority: P1)

老師選一個**具名的目標**（例如「C 語言教學」），
而可見範圍、產出風格**一起跟著變**。

**Why this priority**: 這是整個功能的存在理由。不一致今天**已經可能發生**
——有一個課程清單有自己的層級樹而**沒有自己的風格**。

**Independent Test**: 切換目標，看可見範圍與產出是否一起變。

**Acceptance Scenarios**:

1. **Given** 一個具名目標，**When** 選它，**Then** 可見範圍與產出風格**一起**生效
2. **Given** 兩個目標，**When** 來回切換，
   **Then** 🔴 **語義樹逐節點相同**——目標是投影參數，不是真相
3. **Given** 沒有選目標（今天的使用者），**When** 開啟系統，
   **Then** 行為與今天**完全相同**

### User Story 2 - 而它不是一個新的抽象層 (Priority: P1)

目標**綁的全是既有欄位**，它自己不帶任何新機制。

**Why this priority**: 🔴 **這是設計脈絡的核心主張**，而它很容易在實作時
被違反——一個「順手多加一個欄位」就會讓它從**組合**變成**新層**。

⚠️ 而這個專案有前例：「機制有了沒人接上」發生過**五次**。
**一個新層會帶來第六次。**

**Independent Test**: 列出目標的每一個欄位，逐個指出它今天住在哪裡。

**Acceptance Scenarios**:

1. **Given** 目標的定義，**When** 檢查它的每一個欄位，
   **Then** **每一個都對應到一個今天已經存在的東西**
2. **Given** 實作，**When** 檢查有沒有新增機制，
   **Then** 🔴 **沒有**——⚠️ 新增任何一個就違反本故事

### User Story 3 - 而 C 的產出真的編得過 (Priority: P1)

選「C 語言教學」之後，產出的程式碼**用 C 編譯器編得過**。

**Why this priority**: 🔴 **這是唯一能證明目標「有生效」的驗收**。
沒有它，目標可以是一個什麼都不做的下拉選單。

⚠️ 而它今天是 **6/10** ——缺口**已經量過**，正好兩種：
一個關鍵字要一份不同的標頭、一種型別宣告要一個標籤。

**Independent Test**: 同一批程式，選 C 目標產出，餵給 C 編譯器。

**Acceptance Scenarios**:

1. **Given** 中性語料（不含任何一邊專屬寫法），**When** 用 C 目標產出並編譯，
   **Then** **10/10 編得過**（今天 6/10）
2. **Given** 同一批程式，**When** 用 C++ 目標產出，
   **Then** 仍然全部編得過——⚠️ **不得為了修 C 而弄壞 C++**
3. **Given** C 目標的產出，**When** 檢查內容，
   **Then** 🟢 **零**個 C++ 專屬的輸出寫法（今天已經成立，**不得退步**）

### Edge Cases

- 🔴 **一個目標指向一個不存在的課程清單** → 必須說出來，不得靜默用預設值
- **標頭名對映漏了一筆** → ⚠️ 那一筆會產出**對方世界的名字**，而它**編得過嗎**？
  （某些編譯器兩種都吃）——**編得過的漏網最危險，因為測不出來**
- **同一個程式同時用到兩種只有一邊有的東西** → 那不是中性語料，**不該進分母**
- 🔴 **切換目標之後又切回來** → 產出必須與第一次**逐字相同**
- **既有使用者沒有選過目標** → 必須有一個預設，而**那個預設要與今天等價**

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供**具名的目標**，每一個綁定「可見範圍」與「產出風格」。
- **FR-002**: 🔴 目標的每一個欄位 MUST 對應到一個**今天已經存在**的機制，
  MUST NOT 新增任何機制。
- **FR-003**: 切換目標 MUST NOT 改變語義樹——**逐節點相同**。
- **FR-004**: MUST 至少有兩個目標：今天的預設，以及 C。
- **FR-005**: 沒有選目標時的行為 MUST 與今天**完全相同**。
- **FR-006**: C 目標的產出 MUST 用 C 編譯器**全數編得過**（今天 6/10）。
- **FR-007**: C++ 目標的產出 MUST NOT 因本功能而退步。
- **FR-008**: 一個關鍵字所需的**標頭名在兩個世界不同**時，
  系統 MUST 產出**該目標世界的名字**。⚠️ 而那是**一整族**，不是特例。
- **FR-009**: 一種型別宣告在其中一個世界需要額外標籤時，系統 MUST 加上它。
- **FR-010**: 目標指向不存在的可見範圍時 MUST 說出來，MUST NOT 靜默退回預設。
- **FR-011**: 撞到的坑 MUST 逐條記下，含「因為知道答案而跳過的」。

### Key Entities

- **目標**：一個名字 ＋ 一組**指向既有東西的引用**。
  🔴 **它不擁有任何資料**——那正是「不是新抽象層」的意思。
- **可見範圍**：哪些概念看得到。今天存在，由課程清單提供。
- **產出風格**：產出什麼形狀的程式碼。今天存在。
- **標頭名對映**：同一個東西在兩個世界的名字。
  🔴 ~~今天不存在~~ **已經存在，而且是 19 筆**（research Q5）——
  本功能只是用它的**反向**。**新增的資料 = 0。**

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 老師選擇的次數從 **3 次降到 1 次**。
- **SC-002**: 🔴 C 目標的產出編得過的比例 **6/10 → 10/10**。
- **SC-003**: C++ 目標編得過的比例**不下降**。
- **SC-004**: 切換目標前後，語義樹的**節點差異數 = 0**。
- **SC-005**: 🔴 **新增的機制數 = 0**。
  ⚠️ 判準：目標的每一個欄位都說得出「它今天住在哪裡」——
  說不出來的即為新機制。
- **SC-006**: 核心對語言的耦合數**仍為 0**——目標是語言那一側的東西。
- **SC-007**: 既有的自動化驗證全數通過，既有量測基線**一個數字都不變**。
- **SC-008**: 坑清單**存在**，且分得出「說明的缺陷」與「工具做不到的事」。

## Assumptions

- **第一個目標用 C 而不是硬體**，理由是 C 的差異**已經量過**（6/10，缺口兩種），
  而硬體要先有執行模型才看得到任何東西。
  > **一個機制的第一個消費者，該選【已經量過差異】的那個，
  > 而不是【最想要】的那個。**
- **「驗證用什麼編譯器」這一格不在本輪**——目標的設計有四格，
  本輪只做兩格（可見範圍、產出風格）。⚠️ 而**那個限定要寫下來**，
  否則下一個人會以為目標已經完整。
- ~~標頭名對映約 10 筆~~ ✅ **數出來了：5 筆**（research Q2）——而 18 種標頭裡
  **13 種在 C 裡根本不存在**，那是可見範圍的責任，不是對映表的。
- **不動任何課程清單的內容**——只是讓目標指得到它們。

## Out of Scope

- 硬體／Arduino 目標（那是下一個消費者）
- 「用什麼編譯器驗證」這一格
- 「這個目標提供什麼能力」與「這顆概念需要什麼」的求解
- 既有兩套詞彙的命名收斂
- 修改課程清單的內容或層級樹

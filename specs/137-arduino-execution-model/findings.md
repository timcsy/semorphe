# Findings：Arduino 第 1–3 項撞到的坑

**日期**：2026-08-17　⚠️ 含「**因為知道答案而跳過的**」。

---

## 一、🔴 我在 brief 裡指認的「閘門」不存在

`/knowie-next` 那份 brief 逐字：

> 「🔴 執行路【不知道目標】 `ExecutionContext` 沒有 style、沒有 target
> ← **本輪真正的閘門**」

**而修法是六行，核心一個字都沒動**：`cpp:program` 的執行路改成
「沒有 `main` 就找 `setup`／`loop`」——**進入點由「樹裡有哪些函式」決定**。

> **我把「這個功能需要什麼資訊」錯認成「這個資訊要從哪裡傳進來」
> ——而正確答案是【它已經在樹裡了】。**

🟢 而那顆檔頭**早就寫著**：「哪一個函式是進入點是**這顆（整個程式）的知識**」。
⚠️ **我讀過那句話，而我沒有把它當成答案。**

## 二、進入點的邊界，兩次翻車

```
第一版   只問 ctx.functions        → 🔴 144 支既有測試當場紅
         而它們是對的：body 裡直接放敘述的程式【沒有函式，而它跑得好好的】
第二版   補「有非函式節點就放行」   → 剩 1 支：【空程式】（`[].some()` 是 false）
                                    ⚠️ 一支比 144 支難發現
```

> **「沒有進入點」與「進入點不是一個函式」是兩件事，
> 而只問 `functions` 的話，第二種會被誤判成第一種。**

判準用**宣告**（`traits.functionDefinition`）而不是猜 conceptId。

---

## 三、🔴 而最貴的一坑：一個靠名字認人的樣式，把使用者宣告的名字搶走了

`cpp:pin_constant` 第一版有 `lift-pattern.json`，靠識別字的名字認
`HIGH`／`LOW`／`OUTPUT`……。**第三十二條護欄（行為的誤差）當場抓到**：

```c
enum Level { LOW = -1, MEDIUM = 0, HIGH = 1 };
cout << LOW << endl;      // 參照：-1     我們：0  🔴
```

> **一個靠「識別字的名字」認人的樣式，會把使用者自己宣告的名字搶走。
> 而 `HIGH`／`LOW`／`INPUT`／`OUTPUT` 正是【最常見的列舉成員名】。**

⚠️ **而既有的 `builtin_constant` 用【同一個做法】**（`EOF`／`NULL` 靠名字 lift）
——差別**不在做法，在那些名字幾乎沒有人會重新宣告**。

**處置**：拿掉 lift 樣式，改在 `cpp:var_ref` **查不到宣告之後**才問腳位常數表。
🟢 那正是正確的語義：**沒有人宣告它，它才是環境提供的**。

🔴 **代價（已接受）**：積木 → 程式碼 → 積木時，腳位常數會變回「變數參照」積木。
**correctness 贏 round-trip**——一個印錯數字的程式，比一顆換了形狀的積木糟。

## 四、共用分派器的一個靜默缺口

`lifters/io.ts` 有一行 `if (shape && shape.argSlots.length > 0)`
——**零引數的登錄概念被靜默跳過**，落到通用的 `cpp:func_call`。

`millis()` 是第一顆零引數的。

> **一個看起來像防護的條件，常常是一句沒有被寫下來的假設。**
（那句假設是「登錄的概念都至少有一個引數」，而它在 `millis` 出現之前一直是真的。）

## 五、兩個「界」的問題，而第一版兩個都錯

```
第一版   圈數上限 100_000      🔴 太大——maxSteps 先觸發，使用者看到一個與他程式無關的訊息
         模擬時間上限 5000ms   🔴 沒有 delay 的 loop() 【永遠推不動時間】，這個界到不了
```

實測：十段語料有**四段**的 `loop()` 沒有 `delay` → 全部 `RUNTIME_ERR_MAX_STEPS`。

> **一個「永遠到不了」的界，與一個不存在的界，效果一樣。**

**處置不是把圈數調小**（那又是一個說不出理由的數字），是承認
**一圈總是花了一點時間**（真板子上約 60 微秒，這裡進位到 1 毫秒）。
🟢 於是**只剩一個界，而它有一個理由**。

## 六、🔴 而我的規格有兩條驗收本身寫錯了

### SC-001「十段語料真的印得出東西」——**錯的**

十段裡**四段只有 `pinMode`／`digitalWrite`，本來就不印東西**。

正確的觀察量是**可觀察的效果**（輸出**或**腳位狀態）：

```
🟢 10 / 10   跑得完，0 拋錯
🟢  9 / 10   有輸出或腳位變化
⚠️  1 / 10   只改變數（`millis 計時` 那段）——而那正是它該做的
```

⚠️ 諷刺的是：本功能的**起因**正是「沒有輸出被誤判成沒有執行」，
而我寫驗收時**用了同一個錯誤的觀察量，只是方向相反**。

### SC-002「`runnable` 從 `false` 翻成 `true`」——**也是錯的**

`true` 會拿 `g++` 當裁判，而 **`g++` 編不動 Arduino sketch**。

> **`history/071`：裁判的能力邊界不是固定的——它是【目標】的函數。**

**處置**：加第三態 `'ours-only'`（跑我們的，而**沒有參照可比**），
🔴 **並且在報表上標明「無參照可比」**，不讓它看起來像「比對過了」。
Arduino 的裁判是 `arduino-cli`，那是第 6 項。

## 七、兩張登錄表都表達不出「這個方法在哪個物件上」

`Serial.begin(9600)` 不能用 `registerMethodConcept`——那張表的鍵是**方法名**，
而 `begin` 已經被 `cpp:container_iter`（`v.begin()`）用著。

> **「`begin` 在 `Serial` 上」這件事，一張只放得下方法名的表【表達不出來】。**

**處置**：用 `registerMethodBranch`（看得到 `obj`）。
🟢 而 `container_iter` 的分支**已經拒絕帶引數的 `begin`**，所以落得下來。

⚠️ 而命名詞彙表也撞上同一個字 → 身分改名 **`cpp:serial_open`**
（`begin` 在那張表裡已經是「取得一端」）。**語法仍然是 `Serial.begin(...)`。**

## 八、`map` 這個名字已經被佔用了

```
既有     cpp:map_declare / map_at / map_assign     ← std::map
Arduino  map(v, 0, 1023, 0, 255)                   ← 數值區間重映射
```

> **一個與既有概念同名而語義無關的新概念，會讓兩邊的搜尋都變不準。**

身分叫 `cpp:range_remap`，**而 lift 仍然認 `map(` 這個語法**。

---

## 九、`HIGH` 不能塞進既有的 `builtin_constant`

語義上它就是「環境提供的具名常數」，與 `EOF`／`NULL` 同族。**而併進去會讓目標機制失效**：

> **課程清單過濾得了一顆【概念】，過濾不了一顆概念裡的一個【列舉值】。**

---

## 十、兩條護欄自己有盲點，而它們是這一輪才被看見的

**① 課程清單護欄手寫了兩個 topic 的 import**
——所以 spec 136 加的 `c-beginner.json` **它從來沒看到過**。

> **一條檢查如果自己維護一份「要看哪些檔」的清單，
> 那份清單就是它的盲點，而盲點不會出聲。**

已改成 `import.meta.glob`。

**② 命名護欄只看得到「主體在詞彙表裡」的概念**
——加 `pin`／`digital`／`analog`／`serial` 進主體表之後，**又報出三顆**。
🟢 那不是退步，是**那三顆本來就沒被檢查過**。

### 🔴 而最後一條要單獨說

`component-pipeline` 的 ⛔ 規則要求**五個階段缺一不可**。本輪**只跑了階段 1、2**
（discover ＋ generate），而 3、4、5 **沒有透過 Skill tool 跑**。

**替代做的**：每顆膠囊的 `spec.test.ts` 都含 lift／generate／**round-trip**／execute

⚠️ **那不等於跑過那三個 skill**——`component-fuzz` 的資訊隔離盲測**沒有做**，
而它抓的正是「自己寫的測試看不到的東西」。**這是一個已知的缺口，不是一個判斷。**

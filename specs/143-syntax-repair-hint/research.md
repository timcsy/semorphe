# Phase 0 研究：語法錯誤的修復提示

**日期**：2026-08-19 · **規格**：[spec.md](spec.md)

> 🔴 規格本身已經被一次實測翻過一次（見它的「出發點」）。
> 這裡是**第二輪**：那個事實要怎麼流到使用者眼前。

---

## R1｜🔴 MISSING 的 token **沒有語義節點**，所以 `nodeId` 定位不了它

`Diagnostic.nodeId` 的檔頭逐字：

> 「語義節點的 id——**唯一真實那一側**。各視圖自己把它投影成自己看得懂的位置。」

而 Monaco 今天的做法是 `mappingFor(d.nodeId)` → 拿到**行範圍** → 波浪畫**整行**
（`startColumn: 1` 到 `getLineMaxColumn`）。

🔴 **一個 MISSING 的 `;` 不在語義樹裡**——它是「本來該有而沒有的東西」。
沒有節點，就沒有 `nodeId` 指得到它。

> **一個「不存在的東西」的位置，只能用它【該出現的地方】來表達
> ——而在一棵樹裡，那不是一個節點，是一個【縫】。**

**決定**：`Diagnostic` 多一格**選用**的 `at?: { line: number; column: number }`
——**原始碼座標**，而它只在「缺的東西沒有節點」時出現。

⚠️ **這不是把程式碼投影的概念塞進核心**：缺口的位置**就是**那個事實本身
（「這裡少了一個 `;`」的「這裡」）。拿掉它，事實就只剩「某處少了一個 `;`」。

**被否決的替代方案**

| 方案 | 為什麼不 |
|---|---|
| 塞進 `params` | `params` 是給**訊息插值**用的。位置是**錨點**不是措辭，混在一起之後「誰負責畫波浪」講不清楚 |
| 用最近的父節點的 `nodeId` | 波浪會畫**整個父節點**——`int x = 1` 少分號會標整行甚至整個函式，**比不標更糟** |
| 只給行不給欄 | 規格 FR-003 要的就是欄；而 tree-sitter 給得出來，少給是自己丟資訊 |

## R2｜`AstNode` 缺 `isMissing`，而補它的理由與 `hasError` 逐字相同

`AstNode` 已經有 `startPosition`、`hasError`。而檔頭替 `hasError` 寫的理由**一字不差地適用**：

> 「這兩個原本不在介面裡，而 lifters 需要它們——於是那幾處寫成 `any`。
> **`any` 藏住的是「這個抽象不完整」，不是「型別難寫」。**」

**決定**：`AstNode` 多一格 `isMissing?: boolean`（選用，理由同 `hasError`：
測試裡的假樹省略它，而它們描述的正是**沒有缺口**的樹）。

## R3｜提示在**哪一層**產生：lift，而不是 `diagnosticsFromTree`

```
diagnosticsFromTree(tree)   吃【語義樹】——而 MISSING 不在樹裡 ❌
lift（走 AST）              看得到 MISSING 節點                ✅
```

**決定**：lift 走到有錯誤的節點時，把找到的 MISSING 缺口**記進該節點的 metadata**，
`diagnosticsFromTree` 照舊只讀 metadata。

🟢 **這讓既有的分工一格不變**——`diagnosticsFromTree` 的檔頭寫著它「吃樹」，
而那句話仍然成立。

⚠️ **而它有一個要小心的地方**：一個節點底下可能有**多個** MISSING。
規格的邊界案例說「每一個都報，**不合併**」——所以 metadata 裝的是**陣列**。

---

## R4｜措辭留在面板，核心只給事實

既有設計（`Diagnostic.rule` 的檔頭）逐字：

> 「**是哪一條規則**——身分，不是訊息。舊欄位叫 `message` 而裝的是一個 i18n key，
> 於是**兩個面板只能查同一張表 → 說同一句話**。」

**決定**：核心給 `{ 缺什麼, 行, 欄 }`；

```
程式碼側   波浪縮到那一欄，hover 說「這裡少了 `;`」
積木側     tooltip 說「少了 `;`（第 2 行）」——⚠️ 它沒有「欄」的概念
```

**那個不對稱是刻意的，不是還沒做完。**

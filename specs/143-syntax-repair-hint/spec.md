# Feature Specification：語法錯誤說得出「少了什麼、在哪裡」

**Feature Branch**: `143-syntax-repair-hint`
**Created**: 2026-08-19
**Status**: Draft
**路線圖位置**: vision 階段 6.7（唯一 🟡 進行中）的**第三個缺口**
**設計脈絡**: `knowledge/draft/2026-08-05-語義診斷系統.md`（**in-flight**）

---

## 🔴 出發點：一個實測，而它把原本的構想【反過來】了

原本的構想是「**打錯的關鍵字**要說得出『你是不是要打 `while`？』」
——與執行期那半（`interpreter/near-miss.ts`，「你是不是要打 `Score`？」）同一個機制。

**而寫規格之前先量了一次 tree-sitter 實際給什麼**：

```
void f() { whlie (x < 10) {…} }   ERROR 節點【不含】"whlie"  只報 ;(MISSING)
void f() { retrun 0; }            ERROR="0"，不是 "retrun"
void f() { int x = 1 }            MISSING「;」@ 第 2 行第 12 欄   🟢
void f() { @@@ ### }              ERROR="@@@ ### "
```

🔴 **打錯的關鍵字拿不到**——`whlie` 是一個合法的識別字，
所以 tree-sitter 把它當運算式的開頭，報的是**後面少了分號**。
要說「你是不是要打 while」，得**自己去猜哪一個 token 是他打錯的**——那是猜測。

🟢 **而我原本要「明確排除」的少分號，才是有確定位置的事實**：
`MISSING「;」` 帶著**行與欄**，四種常見形狀全中（宣告、輸出、巢狀區塊、for 的第一個分號）。

> **在寫規格之前量一次工具實際給什麼——
> 而這一次量出來的結果，把「該做的」與「該排除的」整個對調。**

⚠️ 這與這個專案反覆記過的那條同族：
「**一個判準如果是照著手上那個實例寫的，它只會涵蓋那個實例**」
——`whlie` 那個例子是我腦中想的，不是量出來的。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 學生少打一個分號，看得到少在哪 (Priority: P1)

一位學生寫 `int x = 1`（忘了分號），積木那側少了一塊。
今天他只看到「這一段的語法不完整」；**他要看到的是「這裡少了一個 `;`」，而且游標指得到那個位置**。

**Why this priority**: 這是 tree-sitter **確定知道**的唯一一類修復建議。
其餘的（打錯的關鍵字、括號不對稱）都要猜。

**Independent Test**: 貼一段少分號的程式碼，看診斷說什麼、指哪裡。

**Acceptance Scenarios**:

1. **Given** `void f() {\n  int x = 1\n  int y = 2;\n}`，**When** 轉成積木，
   **Then** 診斷說得出「少了 `;`」，且位置是**第 2 行第 12 欄**（不是「第 2 行」而已）
2. **Given** `void f() {\n  cout << "hi"\n}`，**Then** 同上（第 3 行第 2 欄）
3. **Given** 巢狀區塊裡少分號，**Then** 位置指在**最內層**那一行，不是函式的開頭

---

### User Story 2 - 🔴 不亂報（Priority: P1）

一位學生寫的程式**完全正確**，或者他貼進來的是一段**真的認不得**的東西
（`@@@ ###`）。前者**一個診斷都不該有**；後者只說「語法不完整」，
**不得編一個修復建議出來**。

**Why this priority**: 與 US1 同級，而它**比 US1 重要**。
`near-miss.ts` 檔頭逐字：

> 「`experience`：**一個指錯地方的錯誤訊息，比沒有訊息更糟。**
> 所以判準寧可漏，不可錯——**找不到就完全不提，訊息與今天逐字相同**。」

**Acceptance Scenarios**:

1. **Given** 一段正確的程式，**Then** 語法診斷**數量為 0**
2. **Given** `void f() { @@@ ### }`，**Then** 有語法診斷，**而它不含任何「少了 X」的建議**，
   訊息與今天**逐字相同**
3. **Given** 打錯的關鍵字（`whlie`），**Then** 🔴 **不得**說「你是不是要打 `while`」
   ——那個詞我們拿不到，說了就是猜的

---

### Edge Cases

- **一行少兩個東西**：只報 tree-sitter 給的那些，不推論
- **MISSING 不是 `;`**（例如少 `)`）：⚠️ 同一個機制**自然涵蓋**，
  而訊息要說出**是哪一個符號**，不是一律講「少了分號」
- **一個檔案少很多分號**：每一個都報，⚠️ 而**不合併**——合併會讓「哪裡」消失
- **既有的執行期建議**：一個字都不變

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：語法診斷 MUST 能帶一個**修復提示**，而它只在 tree-sitter
  **明確指出缺了什麼**時出現。
- **FR-002**：提示 MUST 說出**缺的是哪一個符號**（`;`／`)`／…），不得一律講分號。
- **FR-003**：提示 MUST 帶**行與欄**，而不只是行。
- **FR-004**：🔴 找不到明確缺口時 MUST **完全不提**——訊息與今天**逐字相同**。
- **FR-005**：🔴 MUST NOT 對「打錯的識別字／關鍵字」提出建議
  ——實測顯示那個 token 拿不到（見出發點）。
- **FR-006**：一段**正確**的程式 MUST 產生**零**語法診斷。
- **FR-007**：兩個面板都拿得到這個提示，⚠️ **而它們可以顯示得不一樣**
  ——那是既有的刻意不對稱（程式碼側有波浪指位置，積木側沒有）。
- **FR-008**：既有的執行期建議（`UNDECLARED_VAR_SUGGEST`）MUST 一個字不變。

### Key Entities

- **修復提示（repair hint）**：`{ 缺什麼, 行, 欄 }`。
  ⚠️ **它是一個事實不是一句話**——措辭由各面板自己組（同 `Diagnostic.rule` 的既有設計：
  「`rule` 是**身分不是訊息**……舊欄位叫 `message` 而裝的是 i18n key，
  於是**兩個面板只能查同一張表 → 說同一句話**」）。

---

## Success Criteria *(mandatory)*

- **SC-001**：四種常見的少分號形狀（宣告、輸出、巢狀區塊、`for` 的第一個分號）
  **4/4** 說得出位置。
- **SC-002**：一段正確的程式，語法診斷**0** 個。
- **SC-003**：無法辨識的輸入，修復提示**0** 個（而語法診斷仍在）。
- **SC-004**：學生看到提示之後，**不需要再讀一次整段程式**就知道游標該放哪
  ——判準是提示帶得出**行與欄**。
- **SC-005**：既有的執行期建議測試**一支都不變**。

---

## 明確排除（防蔓延）

- 🔴 **「你是不是要打 `while`」**——原構想的主體，**實測否決**：那個 token 拿不到。
  ⚠️ **重開的條件是「有辦法確定哪一個 token 是打錯的」**，不是「又想到它了」。
- **括號不對稱的推論**——`int f( {` 給的是 ERROR 不是 MISSING，指不出「少在哪」。
- **委派編譯器（clangd）**——draft 裡的另一條線，成本完全不同。
- **6.7 ①「ERROR 節點的身分」**——2026-08-19 判為待論證（P6 要的「可見」「區分原因」
  兩條都已成立，「有身分」買到什麼還沒人說得出來）。
- **改寫既有訊息的措辭**——`spec 119` 記過：加強錯誤訊息做了六十年而沒有共識
  （Becker 等 2019 回顧 107 篇）。**這一刀加的是事實，不是修辭。**

---

## Assumptions

- **tree-sitter 的 MISSING 節點是可信的**——實測四種形狀全中，而
  ⚠️ 驗收要**逐形狀**斷言，不從一個推論其他（`experience.md`
  「一叢違規不一定同一個根因」）。
- **缺的符號種類不預先列舉**——直接用 MISSING 節點的型別，
  `experience.md`：「**列舉已知的，等於保證下一個會被漏掉**」。

---

## 已知的坑（本專案的經驗，不要重踩）

1. **診斷是全集取代**——`params` 多一格不可以讓既有的兩個面板少顯示東西。
2. **提示是事實不是句子**——措辭留給面板，否則兩個面板又只能說同一句話。
3. **位置的錨點**：既有的 `Diagnostic` 用 `nodeId`（「唯一真實那一側」），
   ⚠️ 而 MISSING 的位置是**原始碼座標**。兩者怎麼共存要在 plan 論證，
   **不得默默塞一個 `line` 欄位進去**。

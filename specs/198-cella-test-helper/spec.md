# Feature Specification: 測試用的共用 Cella 判決入口（重構 6c-1）

**Feature Branch**: `222-cella-test-helper`

**Created**: 2026-11-02

**Status**: Draft

**Input**: User description: "重構 6c-1：測試用的共用 Cella 判決 helper——6c 要把 127 個「拿 JS 直譯器當執行判準」的測試檔改成對 Cella 驗，而那之前要先有一個共用入口。"

## 背景

重構階段 6c 要拆掉 JS 直譯器。依賴它的測試檔有 168 個，其中 127 個（B 類）是「把一段程式 lift 起來、用直譯器跑、斷言輸出」——換成 Cella 之後，同一條斷言守的是「formalize 有沒有把那段程式翻對、Cella 有沒有判對」。
（盤點：`knowledge/draft/2026-11-02-6c測試盤點.md` 總表與 B 類。）

盤點列了兩個不先解決就會讓整個遷移失敗的風險：

- **風險 1：時間**。每個測試檔各自編一次 Cella（C 家族約 12 秒），127 個檔以並行 2 計，全套多出 13 分鐘以上——最可能的結局是「改成 Cella 之後，這批被加上跳過條件」。
- **風險 2：判不出來被當成跳過**。Cella 對還沒建模的構造一律回 unknown。如果共用入口把 unknown 當成「這支跳過」或「輸出是空字串」，還沒支援的那幾族會**靜靜變綠**。

這一刀只做共用入口與示範，不做大批遷移。

## User Scenarios & Testing *(mandatory)*

這一刀的使用者是**寫與維護測試的人**（開發者、之後做 6c-2 遷移的人）。

### User Story 1 - 用一行呼叫拿到 Cella 的判決（Priority: P1）

寫測試的人給一段 C++ 程式碼與輸入，拿到 Cella 的判決、輸出與問題清單，走的是產品同一條路（lift → formalize → 判決），不必自己組判決器、讀模組檔、處理 formalize。

**Why this priority**: 127 個檔都要用它；沒有它，6c-2 的每一個檔都要各自寫一遍這段，而且各寫各的就會各錯各的。

**Independent Test**: 拿一段印出固定字串的程式呼叫它，得到判決 accept、輸出是那個字串。

**Acceptance Scenarios**:

1. **Given** 一段合法、輸出確定的 C++ 程式與它的輸入，**When** 呼叫共用入口，**Then** 判決是 accept、輸出與真的編譯器相同。
2. **Given** 同一個測試行程裡呼叫二十次，**When** 量總時間，**Then** Cella 的模組只準備一次（第二次起不再付編譯的成本）。

---

### User Story 2 - 判不出來、翻不出來、判定有錯，都會紅並說清楚為什麼（Priority: P1）

寫測試的人斷言「這段程式印出 X」時，如果 Cella 判 unknown、invalid、reject，或 formalize 翻不出，測試**失敗**，訊息說得出是哪一種、原因是什麼、指到原始碼的哪一段。

**Why this priority**: 這是風險 2。一個把「判不出來」當成「通過」或「跳過」的入口，會讓遷移看起來完成、而實際上什麼都沒驗（P6 誠實降級：降級必須可見、必須區分原因）。

**Independent Test**: 兩支注入測試——一段 Cella 必定判 unknown 的程式（依定義不會被支援的構造，例如步數用盡的無窮迴圈）、一段必定判 reject 的程式（讀未初始化的變數），兩支都必須讓「斷言輸出」那個呼叫失敗，且失敗訊息含有判決種類與原因。

**Acceptance Scenarios**:

1. **Given** 一段會被判 unknown 的程式，**When** 測試斷言它的輸出，**Then** 測試失敗，訊息含「unknown」、問題種類、原因與指到的原始碼片段。
2. **Given** 一段會被判 reject 的程式，**When** 測試斷言它的輸出，**Then** 測試失敗，訊息含「reject」與原因。
3. **Given** 一段 formalize 翻不出的程式，**When** 呼叫共用入口，**Then** 失敗並列出翻不出的構造名稱。
4. **Given** 一個測試**刻意**要驗「這段會被判 reject」（例如未定義行為的偵測），**When** 它用共用入口取得判決，**Then** 它拿得到完整的判決物件自己斷言，不會被入口先擋掉。

---

### User Story 3 - 三支既有的測試換判準之後照樣成立（Priority: P2）

把三支難度低的 B 類測試檔改用共用入口（一支容器輸出、一支初始化串列、一支膠囊自證測），它們原本的斷言在 Cella 底下照樣成立；若有不成立的，逐支判斷誰對並記下。

**Why this priority**: 證明共用入口在真實的測試上能用，並量出「一支測試檔多花幾秒」——那是 6c-2 能不能照這個方式做下去的依據。

**Independent Test**: 三個檔各自單獨跑，全綠；記錄每個檔改前與改後的執行時間。

**Acceptance Scenarios**:

1. **Given** `tests/integration/execution-cpp-containers.test.ts`、`tests/integration/vector-initializer-list.test.ts`、`src/components/cpp/range_max/spec.test.ts`，**When** 執行判準改成 Cella，**Then** 原本的輸出斷言全部成立，或不成立的每一條都附判斷（誰對、依據）。
2. **Given** 改寫完成，**When** 量時間，**Then** 報告每個檔多花的秒數。

---

### Edge Cases

- 程式要讀輸入但沒給：輸入當成空的，判決照 Cella 的規則（讀到檔尾）。
- 程式跑不完：步數上限用盡 → unknown（fuel），算失敗，訊息說是步數用盡、上限是多少。
- 一段 Arduino 草稿：本入口只處理 C／C++ 的一般程式；Arduino 的時間軸與腳位不在這一刀（6c-4）。
- 同一支測試檔裡同時有 C 與 C++ 的程式：兩個家族都要能判。
- Cella 判 accept 但帶了假設（例如「依 libstdc++」、「依 gcc 的 VLA」）：仍然算 accept，假設要在結果裡拿得到。
- 模組快取不存在（新的機器、清掉了快取）：第一次自己準備並寫入快取，之後重用；不得因為沒有快取就跳過。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供一個給測試用的共用入口：輸入一段程式碼與輸入字串，回傳判決（accept／reject／unknown／invalid）、標準輸出、問題清單與判決帶的假設。
- **FR-002**: 共用入口 MUST 走產品同一條路徑——同一個 lift、同一個 formalize、同一個 Cella 判決——不得另寫一份簡化版。
- **FR-003**: 在同一個測試行程裡，Cella 的判決模組 MUST 只準備一次；MUST 優先讀建置時已經編好的模組（第 210 刀的快取），沒有時自己準備並寫回。
- **FR-004**: 共用入口 MUST 提供「斷言輸出」的用法：判決不是 accept 時直接失敗，訊息包含判決種類、每一筆問題的種類與原因、問題指到的原始碼片段（對回語義樹節點、再對回原始碼位置）。
- **FR-005**: formalize 翻不出時，共用入口 MUST 失敗並列出翻不出的構造與原因；MUST NOT 把它當成輸出為空。
- **FR-006**: 共用入口 MUST 同時提供「拿完整判決」的用法，給刻意驗 reject／unknown 的測試自己斷言。
- **FR-007**: 系統 MUST 有兩條注入測試，分別證明 unknown 與 reject 會讓「斷言輸出」失敗；兩條都要先有正向錨點（一段 accept 的程式通過），證明量到了東西。
- **FR-008**: 三支示範的 B 類測試檔 MUST 改用共用入口，且 MUST 不再引用 JS 直譯器。
- **FR-009**: 改寫時若有斷言在 Cella 底下不成立，MUST 逐條判斷誰對（Cella 依標準、原期望值的來源），依判斷修期望值或回報 Cella，並記在提交訊息與 spec 的紀錄裡；MUST NOT 整批以新輸出覆蓋。
- **FR-010**: 系統 MUST 量出並記錄：共用入口第一次準備模組的時間、之後每次判決的時間、三支示範檔改前改後的執行時間。

### Key Entities

- **判決結果**：判決種類、標準輸出、問題清單（每筆：種類、原因、指到的節點）、假設清單。
- **問題的原始碼位置**：從問題指到的語義樹節點，對回原始碼的一段文字與行號，用在失敗訊息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 寫一條「這段程式印出 X」的測試只需要一個呼叫；三支示範檔改寫後，檔內不再有任何對 JS 直譯器的引用。
- **SC-002**: 判不出來、翻不出來、判定有錯三種情況，各有一條注入測試證明測試會失敗，且失敗訊息包含判決種類、原因與原始碼片段。
- **SC-003**: 同一個測試行程裡，第二次起的判決不再付模組準備的成本；量到的「一支測試檔多花的秒數」記錄下來，作為 6c-2 是否照這個方式遷移的依據。
- **SC-004**: 全套測試綠，沒有任何一支是因為新加的跳過條件而綠。

## Assumptions

- 第 210 刀的建置會把編好的 Cella 模組放在 Node 的快取目錄；測試環境可以讀它。
- 這一刀只處理 C／C++ 的一般程式（cfamily）；Python 與 Arduino 的時間軸留給後續（盤點的風險 4、6）。
- 6c-2 的大批遷移、6c-3 的產品端切換、6c-4 的刪除都不在這一刀。
- Cella 目前的版本已帶資源上限；它還有兩個誤判 reject 已修好、下一版發布（迭代器的箭頭、巢狀大括號的元素）——示範檔若碰到，依 FR-009 判斷並記錄。

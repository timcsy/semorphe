# 契約

**Feature**: 050-repay-top-blockers

本功能改動兩個既有契約、新增一個標記。

## 契約 1：`array_declare` 的語義形狀（擴充）

```
array_declare
  properties: { type, name }
  children:
    size:    [節點]              既有
    values:  [節點, ...]         新增，可選
```

| 情形 | `values` |
|---|---|
| 無初始值 | 欄位不存在 |
| 空初始值列表 | `[]` |
| 有初始值 | 逐個節點 |
| 多維 | 巢狀節點，層次不壓平 |

**相容性**：`values` 為可選欄位，既有不帶初始值的陣列宣告**形狀完全不變**（FR-006）。

## 契約 2：缺陷帳基線（擴充）

```json
{
  "_meta": { ... },
  "total": 85,
  "withBody": 21,
  "titleOnly": 64,
  "byBlocker": { }
}
```

- `total` **保留**，與舊基線可比較
- `withBody` / `titleOnly` 新增，**各自**是只准下降的棘輪
- `byBlocker` 語義收窄為**只統計有測試本體的項目**

**為什麼 `byBlocker` 要收窄**：它的用途是回答「修一個解鎖多少」。只有名字的項目修好缺口也不會「解鎖」任何東西——它們需要重新產生測試。把它們算進去會讓優先序失真，而優先序是這份彙總存在的唯一理由。

## 契約 3：停用測試標記（新增一種）

```
[UNVERIFIED]   逐筆註解未寫明真正原因，先前標記來自檔案層級推測，不可信
```

既有四種不變：`[BLOCKED:<id>]`／`[UNSUPPORTED:<描述>]`／`[TOMBSTONE:<ref>]`／`[DEADSKIP]`。

**為什麼需要它**：沒有它，「不知道為什麼停用」只有兩條路——留空（會被判為未分類而失敗）或編一個阻斷者（把不確定偽裝成確定）。兩條都比誠實地說「還沒查」差。

**驗證規則**：`[UNVERIFIED]` 無額外必填欄位；但它的**數量本身是一個棘輪**——只准下降，避免它變成新的垃圾桶。

# Quickstart：驗證本功能

**Feature**: 050-repay-top-blockers ｜ **Date**: 2026-08-06

## 前置

```bash
npm test    # 基準：既有測試全綠
```

## 情境 1：陣列初始值被保留（US1，SC-001）

準備一段帶初始值的陣列宣告，走「辨識 → 產生程式碼」一圈。

**預期**：初始值在語義結構中完整存在；產生回去的程式碼與原始等價。
數值、字元、字串、多維皆然，且多維的層次沒有被壓平。

**現況對照**（修改前）：初始值完全不存在，且該節點標著最高信心。

## 情境 2：做不到的時候會出聲（US1，SC-002）★ 本功能的核心

找一個系統無法完整保留初始值的寫法（例如指定初始化）。

**預期**：該節點的信心等級**低於最高**，且帶有降級原因。

**這條比情境 1 更重要。** 情境 1 驗的是「做得到的時候有沒有做對」，情境 2 驗的是「做不到的時候有沒有承認」。現況的病是後者——**沒做卻說做到了**。

## 情境 3：三態可區分（US1，FR-005）

比較三種寫法的語義結構：無初始值／空初始值列表／有初始值。

**預期**：三者可區分——第一種沒有該欄位，第二種是空的，第三種有內容。

## 情境 4：輸出身分不保被釘住（US2，SC-003）

```bash
npx vitest run tests/integration/roundtrip-concept-identity.test.ts
```

**預期**：測試**通過**（因為它用 `it.fails` 斷言「這件事目前是壞的」），且每次跑都在 console 印出診斷：`概念身分：print → cpp_printf`。

> **實作偏離 spec 的一處**：原訂交付「一支刻意紅的測試」。實作時改用 `it.fails`——**一支永遠紅的測試會讓「全套綠」失去意義**，而本專案四條護欄的價值全建立在那個訊號上；紅久了還會被無視，那正是「護欄自己變成殼」。
>
> `it.fails` 兩者兼得：套件保持綠、現象保持可見（console 每次印）、而且**修好時它會自己變紅**提醒拔釘子。

## 情境 5：缺陷帳分得出兩類（US3，SC-004）

```bash
npx vitest run tests/integration/audit-defect-ledger.test.ts
```

**預期**：報表分別呈現「有測試本體」與「只有名字」兩個數字；阻斷者彙總**只統計有本體的**；只有名字的那些被標示為需要「重新產生測試」。

**驗收的關鍵問題**：報表能不能回答「修哪個元件可以解鎖最多**已存在的**測試」？
修改前它答錯——把 64 個不存在的測試算了進去。

## 情境 6：歸因與註解一致（US4，SC-005）

抽查幾筆停用項目，比對其標記與逐筆註解。

**預期**：註解寫明原因的，標記與之一致；註解沒寫明的，標為「歸因待確認」而非沿用舊標記。

**反例**（修改前）：`fuzz-cpp-string.test.ts` 的 10 筆全標同一個阻斷者，但逐筆註解寫的是四種不同的原因。

## 情境 7：零回歸（SC-006）

```bash
npm test
```

**預期**：既有測試全數通過；四項量測的數字皆未上升。

## 常見誤判

| 現象 | 不是 bug |
|---|---|
| 情境 4 的測試「通過」了 | **正常**。`it.fails` 斷言「目前是壞的」——它變紅才代表缺陷被修好了 |
| 缺陷帳 `total` 沒下降 | 本功能不修任何阻斷者的缺口——它改的是**量測的正確性**與**一個無聲丟值的 bug**。`total` 下降是後續功能的事 |
| 完備性報表對陣列宣告仍是綠的 | 它只跑最小樣本，而最小樣本不帶初始值。這是它自己聲明過的能力邊界 |

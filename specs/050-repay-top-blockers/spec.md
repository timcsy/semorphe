# Feature Specification: 清償缺陷帳前兩名——補回黃金測試網 47% 的破口

**Feature Branch**: `050-repay-top-blockers`

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "清償缺陷帳前兩名：修好 print 與 array_declare 的 lift，把 40 筆被它們擋住的停用測試開回來。"

---

## 為什麼做這個

上一個功能（`049-audit-guardrails`）量出了三個數字，其中一個推翻了整個階段 6.5 的可行性論據：

> 遷移計畫立論於「roundtrip 與 fuzz 是格式無關的黃金測試，**可在測試全綠下抽換機器**」。
> 實測：**85 筆停用測試，100% 落在 roundtrip／fuzz 檔**。

**「測試全綠」是綠的，因為失敗的那些被關掉了。** 那張要保護 17 次模組搬移的網，破口全在它自己身上，而且正好落在隨機測試找到問題的地方。專案有一道現成的疤——曾經一次重構弄丟功能，得專開一個規格救回來。帶著 85 個洞去搬 17 個模組，就是把那道疤放大。

前兩名佔了 **47%**：

| 阻斷者 | 擋住幾筆 |
|---|---|
| 輸出構造（`print`） | 21 |
| 陣列宣告（`array_declare`） | 19 |
| **合計** | **40 / 85** |

還有一個理由：上一個功能的計畫裡自己記過的風險是「**護欄本身變成殼——只產報表沒人看**」。缺陷帳的全部價值就是告訴你先修哪個。**現在不照它做，那四條護欄就成了裝飾。**

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 深層運算元的輸出可以被辨識 (Priority: P1)

學生寫 `cout << s.substr(0, 3) << endl;`——把一個方法呼叫的結果印出來，是最平常不過的寫法。

目前系統認不出這是「輸出」這個概念：簡單值可以（`cout << x << endl`），一旦運算元是方法呼叫或函式呼叫就失敗。後果是這段程式碼**無法投影成積木**，而且 21 個涵蓋真實程式的隨機測試因此被停用。

**Why this priority**：它擋住的測試最多（21 筆），而且**兩支獨立的量測儀器都指向它**——缺陷帳說它擋住 21 筆，完備性審計說它的辨識路徑連最小樣本都過不了。兩支儀器同時指向同一處，代表這是真缺口不是量測誤差。

**Independent Test**：單獨修這一項就能讓 21 筆測試恢復，其餘缺口不動也不影響。

**Acceptance Scenarios**：

1. **Given** 一段把方法呼叫結果輸出的程式碼，**When** 系統辨識它，**Then** 產生「輸出」概念，且該方法呼叫成為它的運算元（不是降級成原始碼片段）
2. **Given** 同一段程式碼，**When** 走完「辨識 → 產生程式碼」一圈，**Then** 產出的程式碼與原始語義等價
3. **Given** 混合深度的輸出鏈（簡單值 ＋ 方法呼叫 ＋ 換行），**When** 系統辨識它，**Then** 每個運算元都以正確的概念出現在同一個輸出節點下
4. **Given** 原本就能辨識的簡單輸出，**When** 本次改動後重跑，**Then** 行為完全不變（含另一種輸出風格與換行的各種組合）

---

### User Story 2 - 陣列的初始值不再無聲消失 (Priority: P1)

學生寫 `int arr[3] = {1, 2, 3};`——宣告陣列並給初始值。

目前系統辨識出「陣列宣告」，**但初始值整組消失**：沒有錯誤、沒有警告、沒有降級標記。語義樹拿到一個看起來完全正常的陣列宣告，只是值不見了。從使用者角度是「程式就是跑錯了」，而系統毫無提示。這擋住 19 筆測試。

**Why this priority**：與 US1 並列最高，因為它不只是功能缺失，是**無聲的資料遺失**——比報錯更危險。而且它只有缺陷帳抓得到；完備性審計對它是綠的（最小樣本不帶初始值）。

**Independent Test**：單獨修這一項就能讓 19 筆測試恢復，與 US1 互不依賴。

**Acceptance Scenarios**：

1. **Given** 帶初始值的陣列宣告，**When** 系統辨識它，**Then** 每一個初始值都保留在語義結構中
2. **Given** 同一段程式碼，**When** 走完「辨識 → 產生程式碼」一圈，**Then** 初始值原樣還在
3. **Given** 字元陣列、字串陣列與多維陣列的初始值，**When** 系統辨識它們，**Then** 值同樣被保留
4. **Given** 一個系統**無法**完整保留初始值的情形，**When** 系統辨識它，**Then** 產生**可見的降級標記**——不得回傳一個看起來正常但值已遺失的結構

> 場景 4 是本故事的核心，不是邊界情形：**允許做不到，不允許無聲做不到。**

---

### User Story 3 - 被擋住的測試真的恢復，而不是被繞過 (Priority: P1)

維護者要能確定那 40 筆測試是**真的通過**，不是被改成跳過、也不是斷言被放寬到必然通過。

**Why this priority**：與前兩者並列，因為它是前兩者價值的**唯一驗證方式**。修好了但測試沒開回來，等於沒修；開回來但放寬了斷言，比沒修更糟——那會把假的安全感寫進基線。

**Independent Test**：對照修改前後的測試檔，確認被啟用的測試其斷言未被削弱。

**Acceptance Scenarios**：

1. **Given** 40 筆原本停用的測試，**When** 本功能完成，**Then** 全部處於啟用狀態且通過
2. **Given** 這 40 筆測試，**When** 比對修改前後，**Then** 每一筆的斷言與修改前**完全相同**（僅移除停用標記與分類標籤）
3. **Given** 缺陷帳的統計，**When** 重新量測，**Then** 阻斷者清單中不再有這兩個項目
4. **Given** 其餘三項量測，**When** 重新量測，**Then** 數字**皆未上升**

---

### Edge Cases

- **輸出鏈中出現系統尚不支援的運算元**——修好深層辨識後，鏈中可能出現其他還沒支援的構造；此時應降級且**降級必須可見**，不得讓整條鏈靜默退化
- **初始值數量與宣告大小不符**（`int a[5] = {1,2}`）——C++ 合法（其餘補零），保留機制不得因此丟棄
- **空的初始值列表**（`int a[3] = {}`）——與「沒有初始值」是不同的兩件事，不得混為一談
- **巢狀初始值**（多維陣列）——保留機制必須能表達層次，不能壓成一維
- **開回來的測試本身就有問題**——某些測試可能因為**別的**阻斷者而仍然失敗；此時應改標為該阻斷者，而非退回停用
- **兩個修法互相影響**——輸出鏈中出現帶初始值的陣列時，兩者同時參與

## Requirements *(mandatory)*

### Functional Requirements

**輸出構造的辨識深度（US1）**

- **FR-001**: 系統 MUST 能辨識輸出鏈中的方法呼叫與函式呼叫運算元，產生正確的輸出概念
- **FR-002**: 辨識結果 MUST 保留每個運算元各自的概念身分，而非把整條鏈壓成單一原始碼片段
- **FR-003**: 本改動 MUST NOT 改變任何原本已能正確辨識的輸出構造的行為，**包含另一種輸出風格與換行的各種組合**
- **FR-004**: 對於鏈中仍無法辨識的運算元，降級 MUST 可見（符合既有的誠實降級要求）

**陣列初始值的保留（US2）**

- **FR-010**: 系統 MUST 在辨識帶初始值的陣列宣告時保留全部初始值
- **FR-011**: 保留機制 MUST 涵蓋數值、字元、字串與多維陣列的初始值
- **FR-012**: 走完一圈「辨識 → 產生程式碼」後，初始值 MUST 與原始碼等價
- **FR-013**: 當系統**無法**完整保留初始值時，MUST 產生可見的降級標記；**MUST NOT 回傳一個看起來正常但值已遺失的結構**
- **FR-014**: 保留機制 MUST 區分「沒有初始值」與「空的初始值列表」

**測試恢復的誠實性（US3）**

- **FR-020**: 被本功能解鎖的停用測試 MUST 全部啟用並通過
- **FR-021**: 啟用時 MUST NOT 修改原有斷言——僅得移除停用標記與其分類標籤
- **FR-022**: 若某筆測試因**其他**阻斷者仍然失敗，MUST 改標為該阻斷者並保持停用，且在完成報告中列出
- **FR-023**: 量測基線的下調 MUST 是一次顯式且獨立的紀錄，訊息說明下調原因

**回歸保護（全域）**

- **FR-030**: 四項量測的數字 MUST 皆未上升
- **FR-031**: 既有測試 MUST 全數維持通過

### Key Entities

- **阻斷者（Blocker）**：一個元件，它的缺口導致若干測試無法啟用；缺陷帳按它彙總，使「修一個解鎖多個」可見
- **輸出鏈**：由連續輸出運算子串起的一組運算元，整體對應單一「輸出」概念
- **初始值列表**：陣列宣告時給定的一組值，屬於該宣告的語義內容而非附屬資訊
- **可見降級**：系統承認「此處超出當前解析能力」的顯式標記，與「無聲丟失」相對

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 停用測試從 **85 筆降至 45 筆或更少**，且阻斷者彙總中不再出現這兩個項目
- **SC-002**: 完備性量測中，輸出構造的辨識路徑從「殼」變為「實作」
- **SC-003**: **40 筆**被解鎖的測試全部啟用且通過，斷言與啟用前逐字相同
- **SC-004**: 其餘三項量測的數字皆未上升
- **SC-005**: 既有測試全數維持通過
- **SC-006**: 學生寫 `cout << s.substr(0,3) << endl;` 與 `int arr[3] = {1,2,3};` 時，都能得到正確的積木投影與正確的執行結果——**這是本功能對使用者的實際意義**
- **SC-007**: 任何無法完整處理的情形都留下可見標記，**零無聲資料遺失**

## Assumptions

- **那 40 筆測試的斷言本身是對的**：它們由隨機測試產生器產出、經驗證後才寫入，斷言反映的是真實 C++ 行為。修法要讓它們通過，而不是讓它們變得容易通過。
- **兩個修法互不依賴**：可各自獨立完成與交付。實作順序先做輸出構造再做陣列，只為了讓「修一個帶出另一個」時能分辨是誰造成的。
- **四項量測是可信的回歸基準**：它們在上一個功能中已建立並驗證過棘輪行為。
- **部分測試可能有第二個阻斷者**：解鎖後仍失敗的，改標為真正的阻斷者，不視為本功能失敗（FR-022）。
- **不引入新的相依**：兩處都是既有辨識機制的深度不足，補深度即可。

## Out of Scope（明確排除）

- ❌ **其餘 45 筆停用測試**（第三名以下的阻斷者）——分開排，避免一次動太多而分不清是誰壞的
- ❌ **後續期別的工作**：仲裁協定、檔案搬移、格式定案、目錄重整
- ❌ **那筆已否決決定所導致的停用測試**——它是**正確的後果，不該修**
- ❌ **負載敏感的間歇性失敗**——已歸因為與本功能無關的既有問題
- ❌ **其餘三項量測所發現的問題**（跨層耦合、其他的殼、擴散度）——各自屬於後續期別

## Risks & Mitigations

| 風險 | 緩解 |
|---|---|
| **改動輸出辨識會影響所有輸出構造**——它是全域共用的規則 | FR-003 明訂行為不變，且**必須涵蓋另一種輸出風格與換行的組合**——這是專案既有的已知坑 |
| **修陣列時退回「填一個空值就算了」** | FR-013 明訂：做不到必須可見。既有教訓記載過同型病例——多層 fallback 都用同一個預設值，互相掩蓋，讓真正的遺失點無法定位 |
| **測試「看起來綠」但斷言被放寬** | FR-021 要求斷言逐字相同；SC-003 要求可對照驗證。棘輪擋得住改回停用，但擋不住改斷言，所以這條必須靠驗收 |
| **修一個帶出另一個** | 兩者各自獨立交付，順序固定，量測數字全程當回歸基準 |
| **解鎖後才發現還有第二個阻斷者** | FR-022 已定義處理方式：改標、保持停用、列入報告——不視為失敗 |

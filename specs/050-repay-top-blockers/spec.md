# Feature Specification: 補回無聲丟失的資料，並讓缺陷帳量對

**Feature Branch**: `050-repay-top-blockers`

**Created**: 2026-08-06

**Status**: Draft（2026-08-06 依 Phase 0 研究修正前提——見「研究推翻的前提」）

**Input**: User description: "清償缺陷帳前兩名：修好 print 與 array_declare 的 lift，把 40 筆被它們擋住的停用測試開回來。"

---

## 為什麼做這個

上一個功能（`049-audit-guardrails`）量出了三個數字，其中一個推翻了整個階段 6.5 的可行性論據：

> 遷移計畫立論於「roundtrip 與 fuzz 是格式無關的黃金測試，**可在測試全綠下抽換機器**」。
> 實測：**85 筆停用測試，100% 落在 roundtrip／fuzz 檔**。

**「測試全綠」是綠的，因為失敗的那些被關掉了。** 那張要保護 17 次模組搬移的網，破口全在它自己身上，而且正好落在隨機測試找到問題的地方。專案有一道現成的疤——曾經一次重構弄丟功能，得專開一個規格救回來。帶著 85 個洞去搬 17 個模組，就是把那道疤放大。

上一個功能的計畫裡自己記過的風險是「**護欄本身變成殼——只產報表沒人看**」。缺陷帳的全部價值就是告訴你先修哪個。**現在不照它做，那四條護欄就成了裝飾。**

於是本功能開始時的計畫是「修掉排名前兩位的阻斷者」。**照著護欄行動的第一步，就發現護欄自己量錯了**——見下方「研究推翻的前提」。這不是意外，是那條紀律的必然：**量測工具的錯，有一類只有在你照它行動時才會現形。**

---

## ⚠️ 研究推翻的前提（2026-08-06）

Phase 0 對兩個目標缺口做了實證探測，**推翻了本 spec 初稿的兩個前提**。完整證據見 `research.md`，摘要：

| 初稿主張 | 實測 | 處置 |
|---|---|---|
| `print` 的辨識吃不下深層運算元 | **`cout << s.substr(0,3) << endl` 現在認得出來**，運算元概念身分完整保留。檔頭記載的阻斷條件**已過期** | **改寫 US1** |
| 40 筆停用測試可以「開回來」 | **85 筆裡有 64 筆沒有測試本體**——`it.todo('標題')` 只是一個名字，測試程式從未存在 | **改寫 US3** |
| 「修 `print` 解鎖 21 個測試」 | 那 21 個不存在；且逐筆註解顯示根因各異（條件中的賦值、const 遺失、vector 初始化列表、未支援的字串函式），**與檔頭宣稱的「全部因為 cout」矛盾** | **新增 US4** |

**但研究也確認了一個更強的缺口，並找到一個真的 `print` 問題：**

- `int a[3] = {1,2,3}` 的初始值**確實無聲消失**，而且該節點的信心標記是 **`high`**——系統不只丟了值，還宣稱自己有高信心
- `print` 走一圈確實壞掉，**但原因不同**：預設風格下產生 `printf(...)`，而 `printf(...)` 辨識回來是**另一個概念**。**概念身分沒有守住**

> **這一輪本身就是本專案那條紀律的實例**：量測工具的錯，有一類**只有在你照它行動時才會現形**。缺陷帳的數字對、分類對，只有「停用測試」這個詞把兩種需要完全不同工作量的東西包在一起。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 陣列的初始值不再無聲消失 (Priority: P1)

學生寫 `int arr[3] = {1, 2, 3};`——宣告陣列並給初始值。

系統辨識出「陣列宣告」，**但初始值整組消失**：沒有錯誤、沒有警告、沒有降級標記，而且該節點的信心標記是**最高等級**。語義樹拿到一個看起來完全正常的陣列宣告，只是值不見了。從使用者角度是「程式就是跑錯了」，而系統宣稱自己很有把握。

**Why this priority**：這是研究階段**唯一被實證強化**的缺口（初稿低估了它——不只丟值，還標高信心）。它不是功能缺失，是**無聲的資料遺失加上錯誤的自信**，比報錯危險得多。

**Independent Test**：單獨修這一項即可驗證，與其餘故事無依賴。

**Acceptance Scenarios**：

1. **Given** 帶初始值的陣列宣告，**When** 系統辨識它，**Then** 每一個初始值都保留在語義結構中
2. **Given** 同一段程式碼，**When** 走完「辨識 → 產生程式碼」一圈，**Then** 初始值原樣還在
3. **Given** 字元陣列、字串陣列與多維陣列的初始值，**When** 系統辨識它們，**Then** 值同樣被保留，且多維的層次不被壓平
4. **Given** 一個系統**無法**完整保留初始值的情形，**When** 系統辨識它，**Then** 產生**可見的降級標記**（信心等級下降並記錄原因）——**不得**回傳一個標著高信心、值卻已遺失的結構
5. **Given** 沒有初始值的陣列宣告（`int a[3];`），**When** 系統辨識它，**Then** 與「空初始值列表」（`int a[3] = {};`）可區分

> 場景 4 是本故事的核心，不是邊界情形：**允許做不到，不允許無聲做不到。** 現況的錯不只是「沒做」，是「沒做卻說做到了」。

### User Story 2 - 輸出構造走一圈之後還是同一個概念 (Priority: P1)

維護者要能確定：一個概念經過「產生程式碼 → 重新辨識」之後，**還是原來那個概念**。

目前「輸出」不是。它在預設風格下產生一種輸出寫法，而那種寫法被辨識回來時變成**另一個概念**。輸出字串合法、執行結果也對，**只有身分變了**——而專案的既有紀律明訂「round-trip 必須驗證概念身分，不能只驗輸出字串」。

**Why this priority**：這是研究階段找到的**真缺口**（初稿把它記成了別的原因）。它是可逆性最根本的那一條：如果概念身分守不住，所有以「語義是唯一真實」為前提的機制都站不住。

**Independent Test**：一個測試即可釘住現象，與其餘故事無依賴。

**Acceptance Scenarios**：

1. **Given** 一個「輸出」概念的最小節點，**When** 走完「產生程式碼 → 重新辨識」一圈，**Then** 回來的概念身分**與原本相同**
2. **Given** 現況做不到場景 1，**When** 本功能完成，**Then** 這個現象被一個**具名測試釘住**，且該測試的失敗訊息說明「概念身分從 A 變成 B」而非只說「不相等」
3. **Given** 缺陷帳，**When** 重新量測，**Then** 這個現象的歸因是**正確的**（身分不保），而非初稿記載的錯誤原因

> **本故事刻意不含修法。** 要讓身分守住有兩條路，兩條都會動到跨風格的既有行為，而「跨風格測試」是專案明列的已知坑——那個決定不該被塞進本功能的規模。**先把現象釘住、歸因改對，修法另排。**

### User Story 3 - 缺陷帳要分辨「被關掉的測試」與「只有名字的測試」 (Priority: P1)

維護者看缺陷帳是為了回答「**先修哪個**」。目前它答錯了，因為它把兩種東西當成同一種在數：

| | 數量 | 恢復它要做什麼 |
|---|---|---|
| 真的測試，被關掉了 | **21** | 修好缺口 → 移除停用標記 |
| **只有名字**，測試程式從未存在 | **64** | **重新產生測試程式** |

「修 X 解鎖 N 個測試」這句話，對第二類是假的——那些測試不存在。而優先序正是缺陷帳存在的唯一理由。

**Why this priority**：它是**引導後續所有工作的儀器**。儀器量錯，後面每一步都會照著錯的優先序走。這也是本專案剛記下的那條教訓的第三個實例——**量測工具的錯，有一類只有在你照它行動時才會現形**。

**Independent Test**：重新量測後對照兩個數字，與其餘故事無依賴。

**Acceptance Scenarios**：

1. **Given** 全部停用項目，**When** 量測，**Then** 報表分別呈現「有測試本體」與「只有名字」兩個數字
2. **Given** 阻斷者彙總，**When** 量測，**Then** 它**只統計有測試本體的項目**——因為只有那些「修好就能解鎖」
3. **Given** 只有名字的項目，**When** 量測，**Then** 報表明確標示它們需要的是**重新產生測試**，不是修缺口
4. **Given** 既有的棘輪行為，**When** 本改動完成，**Then** 兩個新數字**各自**都是只准下降的棘輪

---

### User Story 4 - 阻斷者歸因改對 (Priority: P2)

上一個功能為 85 筆停用項目補分類時，有一批是**照檔案開頭的宣稱**歸因的。研究發現**那個宣稱本身是錯的**——同一個檔案裡，逐筆註解寫的根因各不相同（條件中的賦值、const 修飾遺失、vector 初始化列表、未支援的字串函式）。

**Why this priority**：低於前三者，因為它改的是標籤不是行為。但它必須做，否則缺陷帳指著錯的方向——而 US3 才剛讓它量對，歸因錯會讓那個修正白費。

**Independent Test**：對照逐筆註解與標記，確認一致。

**Acceptance Scenarios**：

1. **Given** 逐筆註解已寫明真正原因的項目，**When** 重新歸因，**Then** 標記與註解一致
2. **Given** 註解未寫明原因的項目，**When** 重新歸因，**Then** 標為「歸因待確認」而非沿用可疑的舊標記
3. **Given** 重新歸因後的阻斷者彙總，**When** 檢視，**Then** 不再有任何阻斷者的數量是來自檔案層級的推測

### Edge Cases

- **初始值數量與宣告大小不符**（`int a[5] = {1,2}`）——C++ 合法（其餘補零），保留機制不得因此丟棄
- **空的初始值列表**（`int a[3] = {}`）——與「沒有初始值」是不同的兩件事，不得混為一談
- **巢狀初始值**（多維陣列）——保留機制必須能表達層次，不能壓成一維
- **指定初始化**（`int a[3] = {[0]=1}`，C 風格）——若無法處理，必須走可見降級而非丟棄
- **初始值中含運算式**（`int a[2] = {x+1, f()}`）——值不是常數時同樣要保留
- **同一個項目有兩個以上的根因**——歸因只能標一個；此時標最直接的那個，其餘寫進註解
- **逐筆註解與檔頭宣稱衝突**——以逐筆註解為準（研究已證實檔頭會錯）

## Requirements *(mandatory)*

### Functional Requirements

**陣列初始值的保留（US1）**

- **FR-001**: 系統 MUST 在辨識帶初始值的陣列宣告時保留全部初始值
- **FR-002**: 保留機制 MUST 涵蓋數值、字元、字串與多維陣列的初始值，且多維的層次 MUST NOT 被壓平
- **FR-003**: 走完一圈「辨識 → 產生程式碼」後，初始值 MUST 與原始碼等價
- **FR-004**: 當系統**無法**完整保留初始值時，MUST 降低該節點的信心等級並記錄降級原因；**MUST NOT 回傳一個標著最高信心、值卻已遺失的結構**
- **FR-005**: 保留機制 MUST 區分「沒有初始值」與「空的初始值列表」
- **FR-006**: 本改動 MUST NOT 改變無初始值的陣列宣告的既有行為

**輸出構造的身分守恆（US2）**

- **FR-010**: MUST 有一個具名測試釘住「輸出概念走一圈後身分改變」這個現象
- **FR-011**: 該測試失敗時 MUST 指出**身分從哪個變成哪個**，而非只報告不相等
- **FR-012**: 本故事 MUST NOT 修改任何輸出構造的產生或辨識行為——**只記錄，不修法**

**缺陷帳的分類正確性（US3）**

- **FR-020**: 停用項目的量測 MUST 分別呈現「有測試本體」與「只有名字」兩個數字
- **FR-021**: 阻斷者彙總 MUST 只統計**有測試本體**的項目
- **FR-022**: 報表 MUST 標示「只有名字」的項目需要的是**重新產生測試**，而非修缺口
- **FR-023**: 兩個新數字 MUST 各自成為只准下降的棘輪
- **FR-024**: 量測基線的調整 MUST 是一次顯式且獨立的紀錄，訊息說明原因

**阻斷者歸因（US4）**

- **FR-030**: 逐筆註解已寫明真正原因的項目，其標記 MUST 與該註解一致
- **FR-031**: 註解未寫明原因的項目 MUST 標為「歸因待確認」，MUST NOT 沿用來自檔案層級推測的標記
- **FR-032**: 重新歸因 MUST NOT 改變停用項目的總數——它只改標籤，不改狀態

**回歸保護（全域）**

- **FR-040**: 四項量測的數字 MUST 皆未上升（缺陷帳的新分項除外——那是新增的量測）
- **FR-041**: 既有測試 MUST 全數維持通過

### Key Entities

- **初始值列表**：陣列宣告時給定的一組值，屬於該宣告的**語義內容**而非附屬資訊——這是本功能的核心主張
- **可見降級**：系統承認「此處超出當前解析能力」的顯式標記（信心等級 ＋ 原因），與「無聲丟失」相對
- **阻斷者（Blocker）**：一個元件，它的缺口導致若干**已存在的**測試無法啟用
- **只有名字的項目**：一個記下了標題、但測試程式從未存在的停用項目——它需要的是重新產生，不是修缺口
- **身分守恆**：一個概念走完「產生 → 重新辨識」後仍是同一個概念；與「輸出字串正確」是兩件事

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 帶初始值的陣列宣告，其初始值在語義結構中**100% 保留**——數值、字元、字串、多維皆然
- **SC-002**: **零無聲資料遺失**：任何無法完整保留的情形都留下可見的降級標記，不再出現「標著最高信心但值已消失」的節點
- **SC-003**: 「輸出概念走一圈後身分改變」這個現象有具名測試釘住，且失敗訊息說得出身分是從哪個變成哪個
- **SC-004**: 缺陷帳能回答「修哪個元件可以解鎖最多**已存在的**測試」——目前它答錯，因為把 64 個不存在的測試算了進去
- **SC-005**: 100% 的停用項目分類與其逐筆註解一致，或明確標為「歸因待確認」
- **SC-006**: 其餘三項量測的數字皆未上升，既有測試全數維持通過
- **SC-007**: 學生寫 `int arr[3] = {1,2,3};` 時能得到正確的積木投影與正確的執行結果——**這是本功能對使用者的實際意義**

## Assumptions

- **逐筆註解比檔案開頭的宣稱可信**：註解是隨機測試當時的一手記錄，檔頭是事後的概括——研究已證實檔頭是錯的（US4 的依據）。
- **「只有名字」的項目仍是有效的缺口記錄**：它們不該被刪除。它們記下了「這裡曾經失敗過」，只是恢復它們需要重新產生測試程式——那屬於後續功能。
- **信心等級與降級原因是既有機制**：本功能使用它們表達可見降級，不發明新的標記方式。
- **四項量測是可信的回歸基準**：它們在上一個功能中已建立並驗證過棘輪行為。
- **不引入新的相依**。

---

## Out of Scope（明確排除）

- ❌ **修「輸出構造」的身分不保**——US2 刻意只記錄不修法：兩條可能的修法都會動到跨風格的既有行為，那是專案明列的已知坑，不該塞進本功能的規模
- ❌ **重新產生那 64 筆「只有名字」的測試**——需要重跑隨機測試產生器，屬後續功能
- ❌ **其餘阻斷者的缺口**（第三名以下）——分開排，避免一次動太多而分不清是誰壞的
- ❌ **後續期別的工作**：仲裁協定、檔案搬移、格式定案、目錄重整
- ❌ **那筆已否決決定所導致的停用測試**——它是**正確的後果，不該修**
- ❌ **負載敏感的間歇性失敗**——已歸因為與本功能無關的既有問題
- ❌ **其餘三項量測所發現的問題**（跨層耦合、其他的殼、擴散度）——各自屬於後續期別

## Risks & Mitigations

| 風險 | 緩解 |
|---|---|
| **修陣列時退回「填一個空值就算了」** | FR-004 明訂：做不到必須降信心並記原因。既有教訓記載過同型病例——多層 fallback 都用同一個預設值，互相掩蓋，讓真正的遺失點無法定位 |
| **保留了初始值，但產生程式碼時又丟掉** | FR-003 要求走完一圈等價，不只驗辨識那一半 |
| **US2 的「只記錄不修法」被實作階段擅自擴大** | FR-012 明訂禁止改動產生或辨識行為。這條是規模控制，不是保守——擴大它會把跨風格的已知坑吞進來 |

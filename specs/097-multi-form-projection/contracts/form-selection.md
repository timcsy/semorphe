# 契約：形態選擇

## 這份契約管什麼

**投影方向**（語義 → 積木）在有多個形態時，怎麼選出正確的那一個。

## 契約

```
選形態(conceptId, node, 呈現位置) → blockType
```

### C-1 選擇必須是**全函數**

任何輸入都要回傳一個 blockType，**不得回傳 undefined 讓呼叫端自己想辦法**。

- 軸值取不到 → 回 `default`
- 軸值取到但沒有對應形態 → 回 `default`，**且出聲**

> 理由：`靜默降級是 bug 的藏身之處`。而回傳 undefined 會讓呼叫端各自發明退路，那是碎裂。

### C-2 選擇規則的來源是**宣告**

實作 MUST NOT 出現以 conceptId 或 blockType 為對象的分支。

**可機械檢查**：中立性護欄——核心層不得出現具體元件身分。這條契約破了，那條護欄會叫。

### C-3 所有形態產出**相同的碼與相同的行為**

同一個 conceptId 的任兩個形態：

- 產生的程式碼字串相同
- 執行結果相同
- 執行器是**同一份**（執行器重複註冊護欄維持 0）

> 這是「形態是投影、行為是真實」的可執行版本。

### C-4 反向唯一

```
反推(blockType) → conceptId
```

任一形態反推都得到同一個 conceptId。

**目前免費成立**（extractSpecs 以 blockType 為鍵），但必須釘住——免費的性質最容易被改壞而沒人發現。

### C-5 選擇不得依賴節點以外的東西

只能讀 `node`（屬性與子節點）與**呈現位置**。不得走樹、不得查全域狀態。

> 理由：投影是逐節點的。破了這條，投影就依賴脈絡，而脈絡在存檔往返時不保證還在。

## 已知的兩個實例

| 軸 | 例子 | 形態 |
|---|---|---|
| `role` | `c_increment` / `c_increment_expr` | 依呈現位置 |
| `container_kind` | `cpp_container_push` 於 stack／queue | 依節點屬性 |

## 反例（必須被擋下）

| | 為什麼不合法 |
|---|---|
| 兩個 conceptId 共用同一個 blockType | 破 C-4，反推不出來 |
| 某個形態的產出與另一個不同 | 破 C-3——那代表它們是**兩個概念**，不是兩個形態 |
| 選擇函式裡出現 `if (conceptId === 'cpp_container_push')` | 破 C-2 |

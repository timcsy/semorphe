# 契約：使用者拿得到

## 這份契約管什麼

**一顆元件做出來了，使用者能不能選到它。**

既有的十八條護欄全部在量「做得出來」——五路完備、就近性、中立性、身分健檢。
**沒有一條在量「拿得到」。** 這份契約補那一格。

## 契約

### R-1 每顆積木都拿得到

有積木投影的元件，其積木型別必須出現在某個工具箱分類的產出裡。

**例外只有一種**：明確宣告的排除（`excludeTypes` 或形態是中性版）。
**「忘了加進清單」不是例外**——那正是這條契約要抓的東西。

### R-2 不得指向幽靈

工具箱產出的每一個積木型別，必須在登錄表裡存在。
刪掉一顆元件而忘了清理清單 → 使用者拖出一顆壞掉的積木。

### R-3 加一顆元件不必編輯清單

新增元件（概念定義＋積木投影）之後，**不編輯任何清單**，它就出現在工具箱。

**可機械驗證**：合成一顆元件宣告，斷言它出現在產出裡。

### R-4 教學設計不得被導出覆蓋

分類的順序、標題、以及帶 `extraState` 的入口，必須仍是宣告的資料。

**反例**：用字母序排分類、用登錄表順序決定積木排列——那是讓演算法決定教學設計。

### R-5 課程收錄是策展

課程清單的成員**不導出**。未收錄要**報出**，但不是違規。

## 反例（必須被擋下）

| | 為什麼不合法 |
|---|---|
| 一顆有積木的元件不在任何分類裡，且沒有明確排除 | 破 R-1——使用者拿不到它 |
| 工具箱列出一個登錄表裡沒有的積木型別 | 破 R-2 |
| 加元件之後要去某個清單登記 | 破 R-3——那只是把手寫換個地方 |
| 分類順序由程式算出來 | 破 R-4 |
| 為了讓護欄綠而把新元件塞進課程 | 破 R-5 的用意 |

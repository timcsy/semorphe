## User Scenarios & Testing *(mandatory)*

### User Story 1 - 看得到板子做了什麼（Priority: P1）

學生寫了一支閃燈程式（板子目標）。底部多一個「硬體」分頁：每支用到的腳一條時間軸，亮的那段塗滿、暗的那段空著，
橫軸是模擬的時間（毫秒）；下面列出結束時每支腳的狀態、伺服馬達的角度、LCD 上的字。

**Why this priority**: 板子上的程式「不當機，只是行為不對」（課文 01 的原話）——忘了 `pinMode`、`delay` 寫錯，主控台什麼都看不到。
沒有這一格，學生只能猜。

**Independent Test**: 閃燈程式 → 硬體分頁看得到 13 號腳在約 0、1、2、3 秒交替亮暗。

**Acceptance Scenarios**:

1. **Given** 板子目標上的閃燈程式、判斷功能已就緒，**When** 程式改完（判決跑完），**Then** 硬體分頁畫出 13 號腳的時間軸，切換點在約 1、1001、2002 ms
2. **Given** 程式改成亮 0.1 秒、暗 0.9 秒，**When** 判決跑完，**Then** 時間軸跟著變
3. **Given** 腳位變化超過記錄上限，**When** 判決跑完，**Then** 時間軸畫得出前面的部分，並說明「後面還有，沒有記下來」
4. **Given** 不是板子的目標（C++、C），**Then** 沒有硬體分頁（或分頁說明「這個目標沒有板子」）

---

### User Story 2 - 課文檢查腳位（Priority: P1）

Arduino 課文的題目可以寫「腳位要這樣變」：只寫關鍵事件（哪支腳、變成什麼、大約什麼時候），帶容許誤差。
學生跑完，裁判照這幾個事件判對錯——在此之前閃燈題的檢查是「沒有輸出」，任何一支不印東西的程式都會通過。

**Why this priority**: 第 18 題已定「要」；課文 01 的「跟著做」今天等於沒有裁判。

**Independent Test**: 閃燈課「跟著做」：照課文寫 → 通過；把 `delay(1000)` 改成 `delay(500)` → 不通過，說得出哪一個事件對不上。

**Acceptance Scenarios**:

1. **Given** 題目宣告了腳位事件，**When** 學生的程式在容許誤差內做到每一個事件（照順序），**Then** 通過
2. **Given** 某個事件時間差超過容許誤差、或腳位／值不對、或缺了，**Then** 不通過，訊息說出是哪一個事件、期望什麼、實際是什麼
3. **Given** 判斷功能還沒就緒或無法使用，**Then** 裁判誠實說「要判腳位需要 Cella」，不判通過也不判錯
4. **Given** 題目沒有宣告腳位，**Then** 裁判照舊（只比輸出）

---

### Edge Cases

- 腳位用名字（`LED_BUILTIN`）與用號碼（`13`）是同一支腳——比對以板子上的號碼為準
- PWM（`analogWrite`）的值是工作週期，不是 0／1——時間軸畫成高度，事件比對照值
- 程式沒有讓任何腳變化——分頁說「這次沒有腳位變化」，不是一片空白
- 判決是 reject／unknown（程式有錯或還判不出來）——時間軸照判決給的畫到停下為止，並標出停在哪

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 板子目標上的判決結果 MUST 帶出腳位變化（`{t, pin, value}`）、是否截斷、結束時的硬體狀態，交給畫面
- **FR-002**: 「硬體」MUST 是一份面板宣告（照面板協定），在「狀態」層，排在主控台與變數之後
- **FR-003**: 時間軸 MUST 每支用到的腳一條，橫軸是模擬時間；截斷時 MUST 說明
- **FR-004**: 結束時的狀態 MUST 列出每支腳的模式與值、伺服馬達角度、LCD 的字
- **FR-005**: 課文任務的 check MUST 可選地宣告腳位事件（腳、值、時間、容許誤差，預設誤差 50 ms），照順序比對
- **FR-006**: 腳位事件不符 MUST 說出是哪一個事件、期望與實際
- **FR-007**: 判不了腳位（沒有提供者、未就緒）MUST 誠實說明，不判通過（P6）
- **FR-008**: 閃燈課（arduino/01）的「跟著做」MUST 改用腳位事件當裁判

### Key Entities

- **腳位事件**：腳（板子上的號碼）、值（0／1 或工作週期）、時間（毫秒）、容許誤差
- **硬體狀態**：時鐘、圈數、每支腳的模式／電位／PWM／音調、伺服、LCD、EEPROM

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 閃燈程式的時間軸切換點與 Cella 判決的 `pins` 逐筆一致
- **SC-002**: 閃燈課「跟著做」：照課文的程式通過，`delay(500)` 的版本不通過且訊息指出第一個對不上的事件
- **SC-003**: 既有的 Arduino 課文 e2e 零支因這一段變紅

## Assumptions

- 資料來源是 5a 已經在跑的判決（板子程式的步數給到 50,000,000——模擬到 5 秒）；不另外執行一次
- 範圍外：暫停時的即時板子狀態（DAP 的 `env`）、改感測器輸入（`setInput`）——那是除錯工作階段在板子上的延伸，下一段
- 範圍外：VSCode 擴充（與 5a、5b 同：webview 還沒有 Cella）

# Quickstart：驗證本功能

**Feature**: 051-lift-claim-arbitration ｜ **Date**: 2026-08-06

## 情境 1：歧義被列出來（US1，SC-001／SC-002）

```bash
npx vitest run tests/integration/audit-lift-ambiguity.test.ts
```

**預期**：報表列出每個「同語法同優先權」的群組，含規則清單、目前勝出者、以及**勝出原因是「優先權較高」還是「只是登記得早」**。

## 情境 2：已知的那組必然出現（US3，SC-005）★ 護欄的自我驗證

在報表中找 `declaration` 那一組（8 條規則）。

**預期**：它出現在「**確定會撞**」裡。

> **報不出來就是護欄壞了**，不是那組沒問題。這條有專門的測試釘住（FR-022）——一條抓不到已知案例的護欄，比沒有護欄更危險。

## 情境 3：不會誤報最常用的那一對（US2，FR-010）

在報表中找 `binary_expression @priority=105` 的 `print` 與 `input`。

**預期**：分類為「**不會撞**」。

> 它們的判別式住在 `chain` 的運算子與根文字（`<<`/`cout` vs `>>`/`cin`），**不在限定條件裡**。只看限定條件的話兩者都是空的 → 會誤報成「確定會撞」，而那是專案最常用的兩條規則——誤報它足以讓維護者立刻學會忽略整個護欄。

## 情境 4：三分類分得開，且「無法確定」不算安全（US2，SC-003）

**預期**：報表分別呈現三個數字，且「無法確定」**自成一類**——不被併入「不會撞」，也不被併入「確定會撞」。

## 情境 5：棘輪擋得住新增的歧義（SC-004）

在任一辨識規則設定中新增一條與既有規則同語法同優先權的規則。

**預期**：護欄失敗，並**指名新增的是哪一條、與誰衝突**。還原後通過。

## 情境 6：重複登記被區分出來（FR-013）

在報表中找 `pointer_expression`。

**預期**：`cpp_address_of` 與 `cpp_pointer_deref` 被標為**重複登記**（同一概念在同一語法上出現兩次），而不是被當成兩組獨立的優先權設計。

## 情境 7：零行為改動（SC-006）

```bash
npm test
```

**預期**：既有測試全數通過；前四項量測數字**皆未上升**——尤其完備性（每元件每路徑的分類矩陣），它對匹配結果的任何變化都極敏感。

## 常見誤判

| 現象 | 不是 bug |
|---|---|
| 「無法確定」的數字不小 | **預期**。判不出來就說判不出來，比猜一個答案有用。它是棘輪，會被推著下降 |
| 同優先權組數 ≠ 確定會撞的數量 | **預期且是資訊**。差集有兩個方向：「同優先權但不會撞」＝優先權設了沒作用；「不同優先權但會撞」＝優先權在做隱形仲裁，**後者更危險** |
| 護欄沒抓到某個實際發生過的錯配 | 可能落在它聲明不檢測的範圍（跨語法節點的間接競爭、手寫辨識層、執行期才成立的條件） |

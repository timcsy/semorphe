# Phase 0 研究：腳位的界由板子決定

**日期**：2026-08-19 · **規格**：[spec.md](spec.md)

> 規格本身已經被一次實測翻過（「三塊板子的腳位下拉不同」指著一個**不存在的下拉**）。
> 這裡查的是：**板子模型要住在哪、怎麼流到執行期**。

---

## R1｜🔴 那格不放 `Target.provides`

規格的坑 #2 要求論證。**結論：另立一格。**

```
provides   ['touch', 'ledc-pwm']       「有沒有這個能力」——布林性質的集合
腳位模型   { maxPin: 39, constants }   「這塊板子的數值是多少」
```

**兩者的問法不同**：`targetProvides()` 回一個布林；腳位模型要回**一個值**。

> **一個宣告如果同時裝「有沒有」與「是多少」，
> 那麼讀它的每一個消費者都要先分辨自己拿到的是哪一種
> ——而那個分辨會在每個消費點各寫一次。**

**決定**：`Target.board?: BoardPinModel`，與 `provides` 並列。

⚠️ 而**非硬體目標省略它**——省略 ＝ 「這個目標沒有板子」，
腳位那條路本來就不會被走到（`cpp`／`c`／競程不會執行 `pinMode`）。

## R2｜怎麼流到執行期：`SemanticInterpreter` 的組態

```
src/ui/execution-controller.ts:293/387/627   new SemanticInterpreter({ maxSteps: 10_000_000 })
```

🟢 **已經有一個組態物件**——加一格 `board` 即可，不必新開通道。

而 `MAX_PIN`／`PIN_CONSTANT_VALUES` 在 `arduino-pins.ts` **之外零個消費者**
（grep 全 `src/` 確認），所以整個模型**收在那一個檔裡**，改動面很小。

⚠️ **這一次的「零消費者」我 grep 了 `tests/`**——spec 144 就是漏掉護欄
而被 `npm test` 接住的（`experience.md`：「『零消費者』要 grep 到護欄」）。

## R3｜ESP32 的界取多少——**查證，不要猜**

```
ESP32 的 GPIO 編號 0–39     而 34–39 只能輸入（沒有輸出驅動器）
```

**決定**：`maxPin: 39`。⚠️ **「只能輸入」那一層不做**——沒有當前需求（憲法 I），
而它需要的是一個「方向能力」的模型，那是另一件事。

🔴 **而這條假設要能被否證**：規格的 Assumptions 寫了「要查證」，
而驗收只驗**界**不驗方向——**所以如果 34–39 的輸出後來被發現要擋，
那是一條新的需求，不是這一刀的 bug。**

## R4｜ESP32 沒有 `A0`——而「查不到」與「回錯的值」差很多

`PIN_CONSTANT_VALUES` 今天是一張模組層級的表，`A0: 14`（Uno 的）。
ESP32 的類比腳位不叫 `A0`。

**決定**：常數表**由板子提供**，而板子沒有的名字**查不到**。

🟢 那條路已經是對的：`cpp:var_ref` 在**查不到宣告之後**才問這張表
（見 `arduino-pins.ts` 的檔頭「**一個名字的意思由誰宣告它決定**」）。
查不到 → 走既有的「未宣告變數」診斷，**而那條路已經會說「你是不是要打 X」**。

> **一個不存在的名字，最好的處置是讓它【看起來就是不存在】
> ——而不是給它一個別的板子的值。**

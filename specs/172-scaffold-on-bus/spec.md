# Feature Specification: 骨架在積木那側上匯流排

**Feature Branch**: `172-scaffold-on-bus`
**Created**: 2026-09-06
**Status**: Draft
**Input**: vision「🧾 未清的債」最老的一筆 🆕（2026-08-30 交付時留下）。
`src/core/view-host.ts:104` 自己逐字寫著這筆債：

> 「⚠️ **積木那一側今天還走組裝點直接呼叫**（`markScaffoldBlocks`）
> ——搬過來是一筆債，不是這一刀。」

---

## 這一刀在解什麼

一個「哪幾顆是骨架」的事實，今天有**兩條路**送到兩個視圖：

```
流程視圖   真相 → semantic:update 事件（帶著 scaffold 告示） → 面板自己決定怎麼畫    ✅
積木視圖   真相 → 組裝點算好 → 組裝點【直接呼叫】面板的方法，順便決定用哪一種模式   🔴
```

而第二條路上，**組裝點替視圖做了兩個決定**：算出哪幾顆是骨架（可以），
以及**這個深度該用 ghost 還是 editable**（不可以——那是視圖的事）。

> **一個模式如果在某個視圖上與另一個模式長得一樣，那個視圖就沒有實作它
> ——而選單仍然讓人選得到。**
> （[history/191](../../knowledge/history/191-骨架在流程視圖上是一句謊話.md)）

這一刀讓兩條路合成一條。它不改任何使用者看得到的東西——
**這是它最重要的驗收條件**。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 三段鷹架看起來一模一樣 (Priority: P1)

學生打開一堂 `ghost` 的課，`#include` 與 `using namespace` 那幾塊是**淡的、拖不動**；
換到一堂 `editable` 的課，同樣那幾塊是**實心的、拖得動**；換到 `hidden`，它們不在畫布上。

**Why this priority**: 這一刀是內部重構，而重構的驗收就是「外面看不出來」。
這條不過，其餘全部沒有意義。

**Independent Test**: 三堂課各開一次，比對積木的透明度、可拖曳性、數量。

**Acceptance Scenarios**:

1. **Given** 一堂 `scaffoldMode: ghost` 的課，**When** 打開它，
   **Then** 骨架積木是淡的且拖不動，而非骨架積木拖得動
2. **Given** 一堂 `editable` 的課，**When** 打開它，
   **Then** 每一塊積木都是實心的且拖得動
3. **Given** 一堂 `hidden` 的課，**When** 打開它，
   **Then** 畫布上沒有骨架積木
4. **Given** 任何一堂課，**When** 在課程中途切換鷹架深度，
   **Then** 積木的外觀當場跟著變（而不是要等下一次編輯）

### User Story 2 - 拖曳沒有被這一刀弄壞 (Priority: P1)

學生在畫布上拖一塊非骨架積木，它跟著滑鼠走、接得上、放得下。

**Why this priority**: ⚠️ **已知的雷**。`src/ui/app.ts:1757` 記著
`markScaffoldBlocks` 會 `setDragStrategy` ＋ `setEditable(false)`，
而那條註解說它踩過時序的雷。改成事件驅動**會換掉呼叫時機**。

**Independent Test**: 拖一塊積木到另一個位置，確認它真的動了。

**Acceptance Scenarios**:

1. **Given** 一堂 `ghost` 的課，**When** 拖一塊非骨架積木，
   **Then** 它跟著移動
2. **Given** 同一堂課，**When** 拖一塊骨架積木，
   **Then** 它**不動**（而那是正確的）

### User Story 3 - 組裝點不再替視圖決定它該畫什麼 (Priority: P2)

任何人（或任何 AI）想在組裝點加一行「順便叫視圖畫成這樣」，會被護欄擋下來。

**Why this priority**: 沒有這一條，這一刀會在下一次「順手加一行」時被還原，
而**還原不會有人發現**——今天就是這樣來的。

**Independent Test**: 在組裝點注入一行直接呼叫，護欄要紅並指出是哪一行。

**Acceptance Scenarios**:

1. **Given** 現在的程式碼，**When** 跑護欄，**Then** 綠
2. **Given** 在組裝點注入一行 `blocklyPanel.markScaffoldBlocks(...)`，
   **When** 跑護欄，**Then** 紅，而訊息說得出是哪一個檔案哪一行

### Edge Cases

- **面板還沒建好就收到事件**：積木面板可能在第一個 `semantic:update` 之前
  還沒完成初始化 → 收到的告示要能在初始化完成後補用，
  或者初始化本身就會觸發一次同步
- **一次更新裡骨架沒有變**：不得因此跳過（今天的 `remarkScaffold` 是
  「換目標的途中只重蓋鷹架那一層」——那條路要保住）
- **`hidden` 模式**：骨架根本不在樹裡（`scaffoldNodeIds` 是空的），
  而那與「有骨架但要淡化」是兩件事，不得混為一談
- **切換鷹架深度**：那不是一次語義更新（樹沒變），
  ⚠️ **而它今天靠 `remarkScaffold` 直接呼叫**——事件那條路要有辦法表達它

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 積木視圖 MUST 從語義更新事件的骨架告示取得「哪幾顆是骨架」與「用哪一種模式」
- **FR-002**: 組裝點 MUST NOT 直接呼叫積木視圖的骨架標記方法
- **FR-003**: 鷹架深度改變時，積木視圖 MUST 在使用者下一個動作之前就更新外觀
  （⚠️ 那不是一次語義更新——樹沒有變）
- **FR-004**: 系統 MUST 有一條護欄擋住「組裝點直接呼叫視圖的骨架標記」，
  而該護欄 MUST 有注入測試（注入一筆 → 紅；沒有 → 綠）
- **FR-005**: 三段鷹架模式（`hidden` / `ghost` / `editable`）在積木上的外觀
  MUST 與這一刀之前逐字相同
- **FR-006**: 骨架積木 MUST 保持不可拖曳、不可編輯；非骨架積木 MUST 保持可拖曳

### Key Entities

- **骨架告示**：一次語義更新裡附帶的「哪幾顆節點是骨架 ＋ 使用者想看到多少」。
  它已經存在（`SemanticUpdateEvent.scaffold`），流程視圖已經在讀
- **積木視圖**：告示的第二個消費者。它自己決定「淡的」長什麼樣

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 組裝點對積木視圖骨架標記方法的呼叫數 = **0**（硬性零）
- **SC-002**: 「四項獨立性」量表的**組裝點呼叫視圖**（`compositionRootViewCalls`）
  **下降**（至少 1）——實測 **72 → 71** ✅

  🔴 **這一條在實作中修正過**（憲章 IV：改要留下為什麼）。
  原本寫的是「方法呼叫數下降」，而跑下去它**上升**了（2969 → 2971）。
  查證之後：那一格是 `assertCorpus`（**輸入量**），不是耦合指標
  ——加了一支方法、加了一條護欄，它本來就會漲。

  ⚠️ 而真正該錨的那一格 2026-08-26 就被分出去了，理由逐字是：

  > 「`directViewCalls` 五天內被**上調四次**，而每一次的理由都是
  > 『組裝點把兩端接起來』——**一個正確的動作**。」
  > **一個每次做對事情都要上調的數字，量的是兩件事。**

  > **一個驗收標準如果錨在「總量」上，它會在【做對事情】的時候也動
  > ——而那時沒有人知道該慶祝還是該修。**
- **SC-003**: 三段鷹架的既有端對端測試**一條不改**而全數通過
- **SC-004**: 積木的拖曳在三段模式下都與這一刀之前相同
- **SC-005**: 護欄的注入測試：注入一筆 → 紅並指出檔案與行號

## Assumptions

- **A-001**: 積木面板收到事件之後**仍呼叫自己內部的**標記邏輯
  （把它從對外可見改成內部），而不是把那 200 行搬進事件處理器。
  🔴 **理由**：那段邏輯與拖曳策略耦合，搬家會把「這一刀」與「重構那段」
  合成一件事，**而它們的風險不同**——前者可以用「外觀逐字不變」驗，
  後者不行。
- **A-002**: 「切換鷹架深度」這條路（樹沒變而外觀要變）**在事件那一側處理**
  ——由真相那一側發一次帶著新告示的更新，而不是讓視圖多開一個入口。
  🔴 理由：多開一個入口就是把今天這條債換一個名字留下來。
- **A-003**: 流程視圖那一側**一行都不改**（它已經在事件那條路上）

  ⚠️ **而它收到的東西變了**（實作中發現，誠實記下）：告示原本只從真相那棵樹算，
  現在是**兩棵樹的聯集**（真相 ∪ 顯示樹）。
  🔴 那不是順手改的——**單問任何一棵都會壞掉一半**：

  ```
  只問真相那棵     增強器補的 #include／using 認不出來
                   → 「兩顆實心的積木站在一堆淡的裡面」（2026-09-02 使用者報過）
  只問顯示樹       hidden 模式下骨架【已經被剝掉了】，於是告示是空的
                   → 流程視圖不知道要隱藏誰（實測 e2e 當場紅）
  ```

  🟢 淨效果是流程視圖**變好了**：它現在也認得增強器補上去的那兩顆。

## Out of Scope

- 骨架的**判定**（哪些節點算骨架）——`core/scaffold-nodes.ts` 的
  `scaffoldNodeIds` 一行都沒動。
  ⚠️ **而餵給它的樹變了**（見 A-003）——判定的函式沒動，判定的**輸入**動了。
  > **「這支函式沒動」與「這個判定沒變」是兩句不同的話。**
- 三段模式的**語義**（`hidden` / `ghost` / `editable` 各自表示什麼）
- 流程視圖那一側（2026-08-30 已完成）
- `markScaffoldBlocks` 那 200 行內部邏輯的重構
- 「超出範圍」的標記（`markOutOfScopeBlocks`）——它是另一件事，
  而 2026-09-02 刻意把兩者分開過

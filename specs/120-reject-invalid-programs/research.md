## Q1（plan 的第一個問題）：拒絕放在哪一層

### 今天的執行入口

```
src/ui/app.ts:231          new ExecutionController(...)
src/ui/execution-controller.ts:340／:679   await this.interpreter.execute(tree)
```

**兩個呼叫點，同一個控制器。** 而積木側與程式碼側**共用同一棵樹**
——`execute(tree)` 不知道那棵樹是從積木來的還是從程式碼來的。

### 決策 1：閘門在 `ExecutionController`，不在直譯器

- **Rationale**：閘門要問的是「**使用者現在要求執行**」，而那是 UI 的事件。
  直譯器不知道「按了執行」這件事——它只知道有人給了它一棵樹。
  ⚠️ 而 spec 的 FR-004（**編輯時不拒絕**）正是一個關於**時機**的要求，
  所以它必須放在知道時機的那一層。
- **Alternatives considered**：
  - **直譯器自己拒絕** ❌ 它沒有「按執行」的概念，而且**測試也走它**
    ——那會讓一堆既有測試的樹全部被擋
  - **lift 拒絕產樹** ❌ 打破殘差通道（`unsupported` 也活不了），
    而且積木側會一起死
  - **`unknownConceptHandler` 的 `'abort'`** ❌ 那是「跑到一半遇到不認得的概念」，
    語法錯誤要在**跑之前**就攔住

⚠️ **而積木側的問題自動解決**：積木永遠不會有 `syntax_error` 標記
（積木是拖出來的），所以同一個閘門對積木側**天然無作用**——
**不需要為它寫一條例外**。

> **一個判準如果對某一側天然無作用，就不要為那一側寫例外
> ——例外會變成一個沒有人維護的分支。**

## Q2：US4 的「方法屬於哪些型別」宣告在哪

### 🔴 查證結果：那個宣告【一筆都不存在】，而且缺的不只是宣告

```
容器方法元件   25 顆（string 16／vector 3／map 2／queue 2／set 1／stack 1）
宣告了接收者型別的：0 顆
```

而更根本的兩件事：

```
cpp:container_push  properties: [{ name: 'obj', kind: 'identifier' }]
                    🔴 接收者是一個【字串屬性】，不是接點
cpp:method_call     properties: [{ obj: literal }, { method: literal }]
                    🔴 同上，而且方法名也是字串
```

**而 `v.push_back(x)` lift 成的是 `cpp:container_push`——一顆刻意
【型別無關】的元件。** 所以就算給那 25 顆容器方法加上宣告，
**使用者原話裡的那個例子也不會被涵蓋**。

### 而核心裡沒有任何「變數 → 宣告型別」的表

`grep declaredType|symbolTable|varTypes` → 零命中。

所以 US4 需要**三件事**，而不是一件：

| | 要什麼 | 今天 |
|---|---|---|
| ① | 元件宣告「我的接收者要是什麼型別」 | 0 / 25 |
| ② | 一張「變數 → 宣告型別」的表 | 不存在 |
| ③ | 接收者從**字串**變成**可解析的引用** | 🔴 它是 `kind: 'identifier'` 的字串 |

⚠️ ③ 是一筆**已知的架構債**——`concepts/概念代數` 的「屬性的結構化邊界」逐字：

> 「判定準則：如果一個屬性值在管線中需要被拆分或**解析**，它就不該是字串。」

而 `history/057` 已經把「表達式被存成字串屬性」列為 **A 類**（要動積木形態）。

⚠️ 而 ② 還有一個已知的坑——`experience`「一個作用域少了，
症狀不是『變數不見』而是『變數活太久』」：一張扁平的名字表**是錯的**。

### 🔴 決策 2：**US4 移出本 spec**

- **Rationale**：它不是「中等成本」，是**三個子問題，其中一個是既有架構債**。
  硬做的話會產出一個只涵蓋 25 顆具名容器方法、而**漏掉使用者原本舉的例子**
  的版本——那比不做更糟，因為它看起來像做了。
- ⚠️ **而 spec 自己的 SC-002 就要求這件事**：US1 量完之後，
  「程式不合法」那一欄的內容可能根本不是型別錯誤
  ——**先量再決定 US4 長什麼樣**。
- **落點**：`knowledge/draft/2026-08-05-語義診斷系統.md` §七 的 ③ 保留，
  而它的三個前置寫進去。

> **descope 不是退讓，是照 spec 自己寫的邏輯走。**

## Q3：US1 的分類判準

### 參照工具的失敗資訊拿得到

`tests/helpers/run-cpp.ts:50` 的 `runCppDetailed` 回 `{ ok, stage, message }`。

### 而反方向的分類【已經存在】，照抄

`tests/integration/audit-behavior-error.test.ts:119` 逐字：

> 「參照跑得動而直譯器跑不動的那些——**功能缺口**，與 `mismatch`（誤差）意義相反。」

它的形狀是 `gaps: { gapCount, byStage, details }`。
而 `onlyInterpreterRuns`（`:114`）**只有一個數字**。

### 決策 3：分類判準——而它要在已知答案的樣本上驗過

```
工具跑不動    找不到標頭（fatal error: 'x.h' file not found）、環境問題
程式不合法    編譯器【看懂了而且拒絕】——語法錯誤、未宣告、型別不符
```

⚠️ `build-guardrail` 第 6 步：「靜態判斷不能下結論，只能排順序……
要用靜態判斷，**先在已知答案的樣本上驗過**」。

→ 判準要**先餵兩個合成樣本**（一段缺標頭的、一段真的不合法的），
確認分得開，才拿去跑那 27 段。

⚠️ **判不出來的要歸「無法確定」，而且不計入任一類**（第 5 步）
——為了讓數字好看而樂觀歸類，比沒有分類更糟。

## 決策彙總

1. **閘門在 `ExecutionController`**——它是唯一知道「按了執行」的那一層
2. **積木側不寫例外**——積木天然沒有 `syntax_error` 標記
3. 🔴 **US4 移出本 spec**——它需要三件事，其中一件是既有架構債
4. **分類判準先在合成樣本上驗過**，判不出來歸第三類
5. **拒絕訊息抄 `refusal-message` 的形狀**：為什麼 ＋ 你的東西還在

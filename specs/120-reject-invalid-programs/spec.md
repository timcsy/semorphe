# Feature Specification: 寫錯的程式不該跑得起來——先量再擋

**Feature Branch**: `120-reject-invalid-programs`

**Created**: 2026-08-14

**Status**: Draft

**Input**: 使用者逐字：「我是希望學生在文字區域打程式的時候也會知道哪裡寫錯，
**而不是寫錯還能順利執行**。例如沒有分號還能執行就是不合理的。
另外型別錯了然後還使用其他型別的方法也是不合理的。」

設計脈絡見 `knowledge/draft/2026-08-05-語義診斷系統.md` §七。

---

## 為什麼是現在

前面幾輪都在讓**錯誤訊息更好**。而這一則指出更前面的一件事：

```
少一個分號  →  系統認得出來（有標記）
            →  訊息顯示得出來（紅色波浪，上一輪剛做）
            →  🔴 而程式【照樣跑得起來】
```

那個標記是**附註**，不是**閘門** —— 沒有任何東西讀它來決定「要不要執行」。

> **我們不小心做出了一個比 C++ 寬鬆的語言，而學生以為他在學 C++。**
>
> **一個會執行的錯誤程式，教的不是「這裡有錯」，是「這裡沒有錯」。**

⚠️ 這比「還沒做」更嚴重：外部研究量到結構化編輯器讓語法問題少 4.6 倍，
**而學生轉到一般文字編輯器後語法錯誤多 4 倍**——那是「擋掉而沒教會」。
**我們是主動教了相反的事。**

## ⚠️ 而第一步不是修，是量

系統裡已經有一個數字可能正在量這件事：**27 段程式「只有我們跑得動，
參照的編譯器跑不動」**。而那 27 段**只有一個總數，沒有明細**——
它把「編譯器缺標頭」和「這程式根本不合法」算在同一欄。

> **一個把「工具跑不動」與「程式不合法」算在同一欄的量測，
> 正好看不見我們最該擔心的那一格。**

**所以①先做，而它可能推翻②③的前提**（見 SC-002）。

⚠️ 而這個專案已經走過同一條路：另一個機制的註解逐字寫著
「**不在註冊時報錯**……這裡只讓它可見，逐一消除排在後面
（加嚴之前先回答『被拒絕的東西去哪了』，**而這裡的答案目前是「不知道」**）」。
**先可見、後加嚴。**

## 🔴 T012 檢查點的結論（2026-08-14，量完之後補）

> SC-002 要求「若『程式不合法』那一欄是 0，US2／US4 的前提要重看並記錄」。
> **量出來不是 0（25/27），而它的【內容】不是我們假設的東西。**

### 那 27 段量不出這個病——而理由是第三次出現的那一條

```
19  use of undeclared identifier 'cout'    語料片段缺 #include——而那正是 auto-include 刻意處理的
 3  no template named 'vector' / string    同上
 2  __gcd                                  macOS clang 沒有它（已知，環境）
 1  main cannot be declared as global      🔴 唯一未知的
 2  unclassified
```

**22/25 是語料片段缺標頭，不是「使用者寫了不合法的程式」。**

⚠️ [history/057](../../knowledge/history/057-缺陷清單只包含被記下來的缺陷.md) 第三次咬人：
語料來自**我們自己的測試檔**，它量不出使用者會寫的東西。

### 所以直接量使用者說的那件事

```
少分號（下一行 cout）    標記 1  →  丟錯，而訊息是「變數 x 未宣告」🔴 完全誤導
少分號（下一行 return）  標記 0  →  跑完，輸出 ""          無聲成功
大括號沒關               標記 0  →  跑完，輸出 "1"         無聲成功
亂碼 @@@                 標記 1  →  跑完，輸出 "1"         無聲成功
正常（對照）             標記 0  →  跑完，輸出 "1"
```

**四種寫錯的程式，三種順利跑完，一種給出誤導性的錯誤。**
使用者的觀察**完全成立**，而且比他說的更嚴重。

⚠️ 那個誤導的最糟：學生少了分號，系統說「變數 x 未宣告」
——他會去找變數宣告的問題，而真正的錯在**上一行**。

### 🔴 而這改變了 US2 的預期效果，必須寫下來

```
擋執行只擋得住【有標記的】。而四種裡只有兩種有標記。
```

**US2 仍然要做**（使用者直接點名、成本低、而且擋得住的那兩種是真的），
⚠️ **但它不會兌現「寫錯就不能跑」這個承諾**——瓶頸在**辨識層**
（[history/063](../../knowledge/history/063-通道接好了而辨識那一層只認得某些形狀.md)
的第一個缺口），不在閘門。

> **一個閘門只擋得住它看得見的東西。而我們今天看見的比想像少。**

→ **交付時不得宣稱「寫錯的程式不能跑了」**，只能說
「**被辨識出來的語法錯誤不能跑了**」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 先知道這個病有多大（Priority: P1）

沒有人知道「編譯器拒絕而我們照跑」今天發生幾次。有一個總數 27，
而它混了兩件事。本故事把那 27 段**各自的原因說出來**。

**Why this priority**: 🔴 **它可能推翻 US2／US3 的前提。**
如果「程式不合法」那一欄是 0，代表問題不在這裡，而後兩個故事在修一個不存在的病。

**Independent Test**: 看那份報表能不能對每一段說出「參照為什麼跑不動」。

**Acceptance Scenarios**:

1. **Given** 那批「只有我們跑得動」的程式，**When** 產出報表，
   **Then** 每一段都說得出參照失敗的**階段與原因**
2. **Given** 同一份報表，**When** 讀分類，
   **Then**「程式不合法」與「工具跑不動」是**兩個分開的數字**

---

### User Story 2 - 少一個分號，按執行時被擋下來（Priority: P1）

學生在程式碼區打字，漏了分號。今天他按執行 → **程式跑了**，
而輸出可能誤導他以為程式是對的。

本故事讓那件事變成：**按執行 → 被擋下來**，而且說得出為什麼。

**Why this priority**: 這是使用者原話裡點名的例子，而它是**第一週最常撞到**的。

**Independent Test**: 打一段少分號的程式，按執行，看它跑不跑。

**Acceptance Scenarios**:

1. **Given** 一段有語法錯誤的程式，**When** 按執行，
   **Then** 它**不執行**，而畫面說得出**為什麼**
2. **Given** 同一個情境，**When** 讀那則訊息，
   **Then** 它同時說出「**你的程式還在**」——不是只說「失敗」
3. **Given** 一段沒有語法錯誤的程式，**When** 按執行，**Then** 正常執行

---

### User Story 3 - 打字打到一半不會被打斷（Priority: P1）

**編輯中的程式，大部分時間都是不合法的。** 一個每次按鍵就跳出「語法錯誤、
無法執行」的工具沒有人用得下去。

**Why this priority**: 🔴 **這是 US2 最大的風險。** 沒有這個故事，
US2 的「擋住」會擋到學生連字都打不完。

**Independent Test**: 在程式碼區打字（中間必然經過不合法狀態），確認沒有東西阻止你。

**Acceptance Scenarios**:

1. **Given** 使用者正在打字而程式暫時不合法，**When** 沒有按執行，
   **Then** **不出現任何拒絕**（波浪提示可以有，那是上一輪的事）
2. **Given** 同一段不合法的程式，**When** 按下執行，**Then** 這時才拒絕

---

### User Story 4 - 用錯型別的方法會被指出來（Priority: P2）

`int x;` 之後寫 `x.push_back(1)` ——那是 C++ 會拒絕的程式，
而我們今天會試著跑它。

**Why this priority**: 使用者點名的第二個例子。⚠️ 而它比 US2 貴且更容易誤報，
所以排在後面。

**Independent Test**: 寫一個對整數呼叫容器方法的程式，看有沒有診斷。

**Acceptance Scenarios**:

1. **Given** 一個變數宣告為某型別，而程式對它呼叫**不屬於該型別**的方法，
   **When** 診斷跑完，**Then** 出現一則診斷，來源標記為「元件宣告」
2. **Given** 一個合法的方法呼叫，**When** 診斷跑完，**Then** **不報**

---

### Edge Cases

- **語法錯誤發生在一段永遠不會被執行到的程式碼裡**：仍然擋
  ——⚠️ 我們無法在執行前知道哪裡會被執行到，而 C++ 也是全檔拒絕。
- **同時有語法錯誤與型別錯誤**：語法錯誤優先擋；型別錯誤是診斷不是閘門。
- **積木側**：⚠️ **積木永遠不會有語法錯誤**（它們是拖出來的）——
  拒絕只發生在程式碼那一側，積木側的執行不受影響。
- **一個我們還不認得的寫法**（而程式是合法的）：🔴 **不得擋**
  ——那是我們的問題不是使用者的，它走的是另一條通道。
- **US4 的接收者型別推不出來**（例如來自函式回傳值）：判不出來就**不報**
  ——寧可漏報，不可誤報。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 對於「只有本系統跑得動、參照工具跑不動」的每一段程式，
  系統 MUST 說得出**參照失敗的階段與原因**。
- **FR-002**: 那些原因 MUST 被分成至少兩類：**工具本身跑不動**
  （缺少標頭、環境問題）與**程式不合法**（工具明確拒絕它）。
  兩類 MUST 是**分開的數字**。
- **FR-003**: 當程式帶有**使用者造成的語法錯誤**時，執行 MUST 被拒絕。
- **FR-004**: 拒絕 MUST 只發生在**使用者主動要求執行**的時候，
  MUST NOT 發生在編輯過程中。
- **FR-005**: 拒絕的訊息 MUST 同時說出**為什麼**與**使用者的程式還在**。
- **FR-006**: 「我們還不認得的寫法」與「非標準但合法的寫法」
  MUST NOT 觸發拒絕——它們不是使用者的錯。
- **FR-007**: 對一個變數呼叫**不屬於其宣告型別**的方法時，系統 MUST 產出一則診斷，
  且該診斷的來源 MUST 標記為「元件宣告」。
- **FR-008**: FR-007 判不出接收者型別時 MUST **不報**——寧可漏報，不可誤報。
- **FR-009**: 合法程式被 FR-007 誤報的數量 MUST 被量測並且**只准下降**。

### Key Entities

- **參照工具的失敗**：一次「編譯器沒跑起來」的紀錄。
  屬性：哪一段程式、失敗在哪個階段、原因是什麼、**屬於哪一類**。
  ⚠️ 分類是本功能新增的；今天只有一個總數。
- **執行前的閘門**：一次「要不要讓它跑」的判定。
  今天不存在——今天的判定只影響**顯示**。
- **接收者型別**：一個方法呼叫的對象被宣告成什麼型別。
  ⚠️ 已經在語義樹上，只是沒有人拿它跟方法比對。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 那 27 段中的**每一段**都有分類，沒有一段落在「不知道」。
- **SC-002**: 🔴 **「程式不合法」那一類的數量是一個明確的數字**，
  ⚠️ **而如果它是 0，US2／US4 的前提要重看並記錄**
  ——這條讓整個功能可否證。
- **SC-003**: 一段少了分號的程式，按執行後**不產生任何執行輸出**。
- **SC-004**: 同一段程式，在**沒有按執行**的情況下編輯，**不出現任何拒絕**
  ——🔴 這條是防止工具變得不能用的那道閘。
- **SC-005**: 一段含有「我們還不認得的寫法」但合法的程式，
  按執行**仍然正常執行**。
- **SC-006**: `int x; x.push_back(1)` 這類程式產出一則診斷；
  而合法程式的誤報數是一個**只准下降**的數字。
- **SC-007**: 既有測試全數通過（現況 4138 支），43 條護欄基線**一個都不動**，
  端對端驗證全數通過。

## Out of Scope（明確排除）

- 🔴 **委派編譯器**——它一次解掉 US2／US4 的所有剩餘（型別、模板、未宣告…），
  而它卡在「離線可用」與「體積」兩個未答的問題上。**那是一個獨立的決定。**
- **不改變「什麼算語法錯誤」**——本功能只改變那個判定的**後果**。
- **不做完整型別檢查**——US4 只做「這個方法屬於哪些型別」，
  不做型別推導、不做模板、不做繼承。
- **積木側不擋執行**——積木不會有語法錯誤。
- **不做涵蓋率／假警報的整體量測**（那是另一條驗收）。
- **不改變殘差通道**——「我們還沒長到」那些一行不動。

---

## Assumptions

- **拒絕的時機是「按執行」**。⚠️ 這是本功能最重要的預設，
  而它直接來自 US3：編輯中的程式大部分時間都是不合法的。
- **「參照工具跑不動」與「程式不合法」可以從工具的失敗訊息分辨**
  ——失敗階段與訊息今天都拿得到。
- **接收者型別只從「宣告」取得**，不從推導。所以只涵蓋
  「宣告過型別的變數」上的方法呼叫，其餘一律不報。
- **積木側的執行路徑不變**。
- **既有的端對端驗證檔案可以被擴充**，不需要新建。

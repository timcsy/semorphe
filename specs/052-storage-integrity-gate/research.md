# Phase 0 研究：存檔完整性

**日期**：2026-08-06 ｜ **方法**：跑真的程式碼，不推論

---

## F1：欄位遺失的機制（實測確認）

```
src/ui/app.ts:546-552   buildSaveState() 回傳完整 SavedState，含 blockStyleId 與 locale
src/core/storage.ts:31-41  merged 物件逐欄位列舉，沒有這兩個欄位
```

實測：存 `blockStyleId:'zelos'`／`locale:'en'` → 載回來 `undefined`／`undefined`。

**根因不是打錯字，是形式選錯了**：`merged` 用**逐欄位列舉**組合物件。列舉表與型別宣告是兩份東西，而兩個欄位是選填的，所以編譯器不會發現它們沒被列舉。

> 這正是 `concepts/執行機構.md` 的第一條判準——「沉默的正確和沉默的缺失撞在一起」。`blockStyleId: undefined` 可能是「使用者沒設過」（正確），也可能是「被丟了」（缺失），兩者長得一模一樣。

## F2：三條讀取路徑，三種不同的鬆緊度（實測）

| 路徑 | 檢查什麼 | 實測 |
|---|---|---|
| `load()`（每次開頁面自動跑） | **什麼都不檢查**，`JSON.parse` 完直接回傳 | `{hello:'world'}` 原樣回傳；`version:99` 接受 |
| `importFromJSON()`（使用者匯入檔案） | `version` 與 `lastModified` **存在**即可 | `version:99` 通過 |
| — | — | — |

**最鬆的那條是自動跑的那條。** vision.md:210 描述的「`version` 只檢查存在不檢查值」講的是 `importFromJSON`；`load()` 比它更糟。

**決策**：兩條路徑共用同一個判定函式。不是「各自加檢查」——那會製造第三種鬆緊度。

## F3：拒絕會變成刪除（推理鏈已逐環查證）

```
src/core/storage.ts:30    save() 第一件事是 const existing = this.load()
src/core/storage.ts:33-39 merged 用 state.x ?? existing?.x ?? 預設值
src/ui/app.ts:559-560     restoreState(): const state = load(); if (!state) return
src/ui/app.ts:517         每次積木變動 → runBlockDiagnostics(); autoSave()
```

若 `load()` 因版本不符回傳 `null`：

1. `restoreState()` 的 `if (!state) return` —— **分不出「沒有存檔」與「存檔被拒絕」**
2. 使用者以為是新的一頁，開始操作
3. 第一次積木變動觸發 `autoSave()`
4. `save()` 呼叫 `load()`，又拿到 `null`，於是 `existing?.x` 全部落到預設值
5. **寫回去，原存檔被空白狀態覆蓋**

**「拒絕載入」在四步之內變成「永久刪除」。** 這就是 spec 的 US3 存在的理由——它不是防禦性的補充，是這個功能不會反過來害人的**必要條件**。

**決策：拒絕時先把原始內容搬到備份鍵，再讓正常存檔繼續。**

考慮過的三種做法：

| 做法 | 問題 |
|---|---|
| 拒絕後禁止一切存檔 | 使用者當次的**新工作**全部存不了，換一種資料遺失 |
| 拒絕後照常運作 | 就是 F3 描述的那條路，四步變刪除 |
| **拒絕後搬到備份鍵，再照常運作** ✅ | 原資料保住、新工作也存得了。代價是多一個鍵 |

備份**只留一份**（覆蓋式）。留多份需要一套淘汰策略，而那是憑空猜測——目前沒有任何證據說得出該留幾份。

## F4：欄位清單能不能不手寫（實測 TypeScript 行為）

FR-002 要求欄位清單不得手寫成第二份真相。但 TypeScript 的介面在執行期是**不存在的**，測試沒辦法列舉 `keyof SavedState`。

實測 `satisfies`：

```ts
export const FIELDS = { version:1, ..., blockStyleId:1 /* 故意漏 locale */ }
  satisfies Record<keyof Required<SavedState>, 1>
```

```
error TS1360: Property 'locale' is missing in type '{...}'
  but required in type 'Record<keyof SavedState, 1>'.
```

**編譯器抓到了。** 多寫一個不存在的欄位同樣會錯。

**決策**：用 `satisfies` 釘住的常數當作執行期的欄位清單。

**誠實地說**：這個常數**是手寫的**。它滿足 FR-002 的**意圖**（不會與型別無聲地不一致），但不滿足字面（「不手寫」）。差別在於——**它不可能漂移**，因為漂移會讓專案編不起來。這是把「推斷」改成「宣告」的同一招：缺失從沉默變成可偵測。

考慮過但否決的替代：

- **從 JSON Schema 產生型別**——需要新的建置步驟與相依，為了一個 11 欄位的介面不划算
- **執行期反射**——TypeScript 沒有
- **測試裡直接寫欄位陣列**——這才是真正的第二份真相，會無聲漂移，正是要避免的

## F5：合併方式——偵測不如消除

修 F1 有兩條路：

| | 做法 | 性質 |
|---|---|---|
| A | 保留逐欄位列舉，加測試抓漏 | **偵測**——下次還會漏，只是會被抓到 |
| B | 改用展開合併 `{...預設, ...既有, ...傳入}` | **消除**——結構上不可能漏欄位 |

**選 B，並且仍然保留 A 的測試。**

理由：B 讓這個 bug 不可能再發生；A 的測試仍然需要，因為它守的是**別的**東西——有人日後把 B 改回列舉、或在合併後又做了會丟欄位的處理。B 是修法，A 是執行機構，兩者不互相取代。

B 的一個細節：傳入值中 `undefined` 的欄位不得覆蓋既有值（否則「這次沒提供」會抹掉「上次存的」）。展開會保留 `undefined`，所以要先濾掉。

## F6：升級路徑註冊表——過 over-justify 但理由要說對

`/over-justify` 的判準：抽象要嘛**多解釋**、要嘛**多預測**、要嘛**壓縮**；三個都不中就是裝飾。

「未來 P5／P6 會用到」是**預測**，但那是最弱的一種理由——預測可能落空。

**真正撐得住的理由是它讓當下的行為正確**：

沒有註冊表，「版本低於當前」只剩一條路——拒絕。而目前所有既有存檔都是版本 1；當 `CURRENT_VERSION` 第一次調成 2 的那天，那條路等於**拒絕掉每一位既有使用者的存檔**。那比現況更糟。

所以註冊表不是為未來預留的，是這道閘門**自身正確性的一部分**。

**範圍因此嚴格限縮**：一張「版本 → 升級函式」的表，加上 FR-016 的檢查（調高版本卻沒註冊路徑 → 測試變紅）。**不做**遷移框架、不做鏈式升級的通用機制、不寫任何升級函式。

## 自我否證：這份研究若在什麼情況下是錯的

- **F3 的四步鏈是推理，不是實測**——每一環都查證了程式碼，但沒有實際跑一次「拒絕 → 自動存檔 → 原資料消失」。**實作的第一件事就是把它跑出來**，跑不出來代表這條鏈有一環我讀錯了，US3 的設計要重來。
- **F5 的「結構上不可能漏欄位」只在合併是唯一寫入路徑時成立**。若有第二處組裝 `SavedState` 再寫入，B 保護不到它。實作時要確認寫入路徑只有一條。

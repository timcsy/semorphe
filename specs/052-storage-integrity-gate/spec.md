# Feature Specification: 存檔層的無聲遺失——欄位守恆與版本閘門

**Feature Branch**: `052-storage-integrity-gate`

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "存檔層的無聲遺失：版本閘門 + 欄位守恆。階段 6.5 列為 P5 的阻斷前置，也是「同一個形狀出現五次」表裡唯一還沒補執行機構的那一列。"

---

## 為什麼做這個

使用者切換積木風格、切換介面語言，重新整理之後**全部復原**。這兩個選擇**從來沒有被保存過**。

不是設定沒接上——是存檔層把它們丟了。介面宣告了這兩個欄位、呼叫端確實傳了進來、存檔函式組合新狀態時**沒有把它們放進去**。因為兩個欄位在型別上是選填的，編譯器不會抱怨。

實測（2026-08-06，跑真的存檔服務，不是讀程式碼推的）：

| 做了什麼 | 得到什麼 |
|---|---|
| 存 `blockStyleId: 'zelos'` → 載回來 | **`undefined`** |
| 存 `locale: 'en'` → 載回來 | **`undefined`** |
| 塞一份「版本 99」的存檔 → 自動載入 | **接受了** |
| 塞 `{hello:'world'}` → 自動載入 | **原樣回傳，當成合法存檔** |

而專案的既有教訓正好點名這個形狀：

> **靜默降級是 bug 的藏身之處。**

以及：

> `version` 欄位存在、名字對、看起來就是版本控制，**但沒有任何東西 branch on 它**。

那句話寫在概念檔的「同一個形狀出現五次」表裡，是**五列中唯一還沒補上檢查的一列**。其餘四列都在前兩輪補完了。

**為什麼是現在**：規劃中的核心型別改名會改變存檔的形狀。在版本閘門存在之前做那件事，等於在沒有安全帶的情況下改格式——舊存檔會被當成相容的載進來，使用者的作品會壞掉而且**不會有任何提示**。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 選了的東西下次還在 (Priority: P1)

使用者切換積木外觀、切換介面語言，關掉分頁再打開——這兩個選擇應該還在。

目前它們每次都復原成預設值。使用者會以為是自己沒存到，或是這個功能壞了。

**Why this priority**：**這是四個缺陷裡唯一使用者現在就看得到的**。其餘三個是「未來改格式時會壞」，這一個是**現在就壞著**。

**Independent Test**：存一份帶有全部欄位的狀態、讀回來、逐欄位比對。其餘故事不存在也能單獨驗。

**Acceptance Scenarios**：

1. **Given** 使用者選了非預設的積木外觀，**When** 重新載入，**Then** 該外觀仍然生效
2. **Given** 使用者選了非預設的介面語言，**When** 重新載入，**Then** 該語言仍然生效
3. **Given** 一份包含存檔格式**所有**欄位的狀態，**When** 存入再讀出，**Then** 每一個欄位都與存入時相同
4. **Given** 有人在存檔格式中新增一個欄位卻忘記把它接進儲存流程，**When** 執行測試，**Then** 測試失敗並**指名是哪個欄位**

---

### User Story 2 - 不相容的存檔會出聲，不會被默默接受 (Priority: P1)

存檔帶有版本號。目前自動載入那條路徑**完全不看它**——不管版本是多少，甚至根本不是存檔，都會被原樣接受。

使用者可能在另一台裝置用了較新的版本，或是手上有一份很舊的檔案。三種情況（較新／較舊／相同）現在**得到完全一樣的待遇**。

**Why this priority**：與 US1 並列。它是核心型別改名的阻斷前置——**沒有它，那件事會無聲毀掉使用者的作品**。

**Independent Test**：分別餵入較新、較舊、相同版本的存檔，確認三種行為不同且都不是靜默接受。

**Acceptance Scenarios**：

1. **Given** 一份版本**高於**系統當前版本的存檔，**When** 載入，**Then** 拒絕載入並讓使用者看得到原因，**且原有資料未被覆寫**
2. **Given** 一份版本**低於**當前的存檔且有對應的升級路徑，**When** 載入，**Then** 升級後正常載入
3. **Given** 一份版本**低於**當前但**沒有**升級路徑的存檔，**When** 載入，**Then** 拒絕並讓使用者看得到原因，**且原有資料未被覆寫**
4. **Given** 一份版本與當前相同的存檔，**When** 載入，**Then** 正常載入，行為與現況完全相同
5. **Given** 一筆根本不是存檔形狀的資料，**When** 載入，**Then** 不被當成存檔回傳
6. **Given** 匯入檔案這條路徑，**When** 餵入以上任一情況，**Then** 判定結果與自動載入完全一致

---

### User Story 3 - 拒絕不等於丟掉 (Priority: P1)

閘門變嚴之後出現一個新風險：**判錯的代價是使用者的作品**。

一份被拒絕的存檔必須**原封不動留在原地**。系統不得因為「載入失敗」就繼續正常運作、然後在下一次自動存檔時把空白狀態寫上去——那會把「拒絕載入」變成「永久刪除」。

**Why this priority**：與 US1／US2 並列，因為**它是前兩者的安全條件**。少了它，這個功能會從「防止資料無聲遺失」變成「造成資料明確遺失」。

**Independent Test**：放一份會被拒絕的存檔，觸發一次載入失敗，再觸發一次自動存檔，確認原資料仍在。

**Acceptance Scenarios**：

1. **Given** 一份被拒絕的存檔，**When** 載入失敗後系統繼續運作並自動存檔，**Then** 原本那份資料仍然完整存在
2. **Given** 一份被拒絕的存檔，**When** 使用者查看，**Then** 能得知「有一份存檔沒有載入」以及原因，而不是只在開發者工具裡有一行訊息

---

### User Story 4 - 這件事以後不會再悄悄退步 (Priority: P2)

前三個故事修的是**現在**。這個故事管的是**以後**。

存檔完整性需要一條護欄：量出當前的違規數量、進基線、只准下降；並且**護欄自己要說得出它在什麼情況下是壞的**。

**Why this priority**：低於前三者，因為它不改變任何當下的行為。但沒有它，前三者會在下一次有人改存檔格式時退步，而且**退步是沉默的**——那正是這個功能一開始要治的病。

**Independent Test**：單獨跑護欄即得報表與基線。

**Acceptance Scenarios**：

1. **Given** 護欄的報表，**When** 檢視，**Then** 開頭有明確的失效樣態聲明——「如果結果長成 ○○，代表工具壞了」
2. **Given** 護欄的報表，**When** 檢視，**Then** 它聲明自己**不檢測**什麼
3. **Given** 已記錄的基線，**When** 有人讓存檔完整性退步，**Then** 護欄失敗並**指名是哪一項**
4. **Given** 一個已知必然會被報出來的違規，**When** 執行護欄，**Then** 它必須被報出來，**且報出的理由必須正確**——理由錯了也算工具壞了

---

### Edge Cases

- **版本號本身缺失或不是數字**——歸入「不是存檔形狀」，不得猜一個預設版本
- **存檔在寫入途中被中斷**（內容截斷）——歸入「不是存檔形狀」
- **升級路徑本身失敗**——不得產出半升級的狀態；視同拒絕，原資料保留
- **同一份存檔被連續拒絕多次**——不得每次都重複打擾使用者到無法工作的程度
- **存檔中有系統不認得的額外欄位**（來自較新版本但版本號相同）——**不得因為多了欄位就拒絕**；未知欄位保留原樣，避免跨版本往返時被抹掉
- **欄位守恆檢查自己漏掉新欄位**——檢查用的欄位清單不得手寫，否則它會和儲存流程變成第二處雙重真相

## Requirements *(mandatory)*

### Functional Requirements

**欄位守恆（US1）**

- **FR-001**: 存檔格式宣告的**每一個欄位**，存入後 MUST 能原值讀回
- **FR-002**: 欄位守恆的檢查 MUST 涵蓋全部欄位，且欄位清單 **MUST NOT 手寫**——必須從單一來源導出
- **FR-003**: 新增欄位而未接進儲存流程時，檢查 MUST 失敗並**指名是哪個欄位**
- **FR-004**: 選填欄位若呼叫端未提供，MUST 與「提供了但值為空」可區分

**版本閘門（US2）**

- **FR-010**: 自動載入與匯入檔案**兩條路徑** MUST 都依版本號的**值**分支，且判定結果一致
- **FR-011**: 版本高於當前 MUST 拒絕，並產生使用者可見的原因
- **FR-012**: 版本低於當前 MUST 嘗試升級；無對應升級路徑 MUST 拒絕，並產生使用者可見的原因
- **FR-013**: 版本等於當前 MUST 正常載入，**行為與現況完全相同**
- **FR-014**: 不符合存檔形狀的資料 MUST NOT 被當成存檔回傳
- **FR-015**: 系統 MUST 有一處註冊升級路徑的地方；本功能 **MUST NOT 撰寫任何實際的升級函式**（目前沒有需要升級的版本）
- **FR-016**: 「當前版本被調高但沒有註冊對應升級路徑」MUST 讓測試失敗——否則調版本號的人會無聲地拒絕掉所有既有使用者
- **FR-017**: 存檔中系統不認得的額外欄位 MUST 被保留，MUST NOT 成為拒絕的理由

**拒絕的安全性（US3）**

- **FR-020**: 被拒絕的存檔 MUST 保持原樣，MUST NOT 被覆寫或清除
- **FR-021**: 載入失敗後的後續自動存檔 MUST NOT 把原資料蓋掉
- **FR-022**: 拒絕 MUST 讓使用者看得到，不得只出現在開發者工具

**護欄（US4）**

- **FR-030**: MUST 產出報表與基線，形式與既有五條護欄同形（基線 + 只准下降的棘輪）
- **FR-031**: 報表 MUST 在開頭聲明失效樣態
- **FR-032**: 報表 MUST 聲明本護欄**不檢測**什麼
- **FR-033**: MUST 有自我驗證測試釘住一個已知違規，且**釘住的是理由不只是結果**——因為錯誤的理由也能得到正確的結果，那種護欄看起來與健康的完全一樣

**回歸保護（全域）**

- **FR-040**: 既有測試 MUST 全數維持通過
- **FR-041**: 既有五項量測的數字 MUST 皆未上升
- **FR-042**: 版本相同這條主要路徑的行為 MUST NOT 改變

### Key Entities

- **存檔**：使用者作品與偏好設定的持久化快照；帶有版本號
- **版本號**：存檔格式的世代標記。**它的價值在於被比較，不在於存在**——只存在不比較的版本號是本功能要修的病本身
- **升級路徑**：把舊世代存檔轉成當前世代的方法；目前一條都不需要，但**沒有這個概念的話，版本閘門只能是「不同就拒絕」，那比現況更糟**
- **欄位守恆**：存入的每個欄位都讀得回來；違反時是**無聲**的，所以需要機械化檢查
- **拒絕**：明確的、可見的、**不破壞原資料**的載入失敗

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者切換積木外觀與介面語言後重新載入，兩個選擇都還在——目前 0% 保留，目標 100%
- **SC-002**: 存檔格式的每一個欄位都通過守恆檢查；新增欄位忘記接上時**必定**失敗並指名該欄位
- **SC-003**: 版本較新／較舊／相同三種情況產生**三種不同**且都非靜默的結果——目前三種結果相同
- **SC-004**: 不是存檔形狀的資料 100% 不被當成存檔載入——目前 0%
- **SC-005**: 存檔被拒絕之後，原資料 100% 仍然存在且完整
- **SC-006**: 使用者能得知「有一份存檔沒載入」與原因，不需要打開開發者工具
- **SC-007**: 調高當前版本卻沒註冊升級路徑時，測試**必定**失敗
- **SC-008**: 既有測試全數維持通過，五項量測數字皆未上升，版本相同的主要路徑行為零改動

## Assumptions

- **目前所有既有存檔都是版本 1**。因此「版本較舊」這條路徑現在無法被真實觸發，只能用合成資料驗證。這是接受的——**閘門的價值在於它在版本改變的那一天已經在位**。
- **升級路徑註冊表通過了「這個抽象賺不賺得起位置」的檢驗，但理由不是「未來會用到」**。理由是：沒有它，「版本較舊」只剩拒絕一條路，而當前版本首次調高的那天，那等於拒絕掉每一位既有使用者的存檔——**比現況更糟**。它是這道閘門自身正確性的一部分。範圍因此限縮為一張註冊表，不做框架。
- **「使用者看得見」的最低標準是應用程式介面內的訊息**，不是開發者工具的輸出。具體形式交由實作決定。
- **不引入新的相依**。
- **不改動儲存後端**——仍是瀏覽器本地儲存。

---

## Out of Scope（明確排除）

- ❌ **核心型別改名本身**——那是本功能解鎖的下一件事，不是本功能
- ❌ **膠囊格式**
- ❌ **瀏覽器本地儲存以外的後端**
- ❌ **撰寫任何實際的升級函式**——沒有需要升級的版本，寫了就是憑空猜測
- ❌ **改掉「存檔前先讀舊檔再合併」這個設計**——它會讓壞資料傳播，但改它會變動既有行為。本功能只用測試把現況**釘住讓它可見**，修法另外排

## Dependencies

- **前置**：既有五條護欄作為回歸基準與形式範本
- **知識地基**：專案原則的「誠實降級」；教訓「靜默降級是 bug 的藏身之處」與「量測工具的第一版會安靜地量錯」（三個觸發點）；概念檔「執行機構」的「同一個形狀出現五次」表第五列，以及它的第一條判準——**沉默的正確與沉默的缺失撞在一起時，讓正確的那個說話**
- **解鎖**：階段 6.5 的核心型別改名（P5）與膠囊格式（P6）

## Risks & Mitigations

| 風險 | 緩解 |
|---|---|
| **閘門判錯，代價是使用者的作品** | US3 整個故事在管這件事：FR-020～FR-022 要求拒絕不得破壞原資料。**這是本功能唯一會讓事情變得比現況更糟的方式** |
| **調高版本號的人無聲拒絕掉所有既有使用者** | FR-016 要求那件事讓測試變紅 |
| **欄位守恆檢查自己漏欄位** | FR-002 禁止手寫欄位清單——否則它與儲存流程構成第二處雙重真相，而雙重真相正是階段 6.5 要殺的東西之一 |
| **護欄自己安靜地量錯** | FR-031／FR-033。今天已經是第四次：上一輪的護欄報出「4 條死規則」，自我驗證測試**通過了**，但實測全部推翻——因為那支測試只釘「必須被報出來」，沒釘「必須因為正確的理由被報出來」。FR-033 就是為了堵這個 |
| **「未知欄位」與「壞掉的存檔」判反** | FR-017 明訂多出欄位不構成拒絕理由；只有形狀不符才拒絕。判嚴的代價（拒絕合法存檔）遠大於判鬆 |

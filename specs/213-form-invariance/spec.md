# Feature Specification: 換形態，判決不變（第一層）

**Feature Branch**: `262-form-invariance`
**Created**: 2026-11-04
**Status**: Draft
**Input**: vision〈換形態，判決不變（第一層）〉；三方會議第三輪的不變式 ①（history/334 後記）。

## 背景

semorphe 的承諾是「唯一真實，各式投影」：同一棵語意樹可以畫成程式碼、積木、流程圖，學生在任何一種形態上改，意思都不變。
6c 之後「意思」由 Cella 判——所以這個承諾在機器上可以檢查：**同一棵樹換一種形態再轉回來，交給 Cella 的程式要一模一樣**。

一個宣告今天量四個面向（①產出的程式碼 ②語義的不動點 ③載得進工作區 ④走一趟積木回來），這一刀補第五個：⑤**翻給 Cella 的程式**。
前四個都是「形狀」，第五個是「意思」——形狀全對而意思被換掉（例如走一趟積木回來，型別從 `long long` 變成 `int`）只有它看得到。

⚠️ 一個量到的事實界定了範圍：I/O 風格的切換（`cout` ↔ `printf`）會**換掉語意樹本身**（不同的元件），翻給 Cella 的程式本來就不同。那一類比的是**判決與輸出相同**（判決層），不是程式相同。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 學生在積木與程式碼之間切換，程式的意思不變（Priority: P1）

學生把一段程式碼轉成積木、拖一拖、再轉回程式碼。他沒有改任何東西時，semorphe 交給判斷功能的程式要和原來一模一樣——否則「我什麼都沒改，執行結果卻變了」。

**Why this priority**: 這是產品的核心承諾；破掉時學生無從察覺，只會看到莫名其妙的結果。

**Independent Test**: 拿課文的每一支參考解答，走「轉成積木 → 抽回語意樹」，比兩次交給判斷功能的程式。

**Acceptance Scenarios**:

1. **Given** 課文語料的每一支程式，**When** 走一趟積木再回來，**Then** 交給判斷功能的程式與原來相同（節點編號不算）；不同的每一筆有附理由的釘子，並指出是哪一段（轉積木、抽回、或翻譯）的缺陷。
2. **Given** 一支走一趟積木就會變意思的程式（注入），**When** 跑檢查，**Then** 紅，並指名那一支與差在哪個欄位。

---

### User Story 2 - 程式碼來回與只改格式的風格切換，意思不變（Priority: P1）

學生換縮排、換「using namespace」或「std::」的寫法、換標頭的寫法，或只是讓 semorphe 重新產生一次程式碼——意思都不能變。

**Why this priority**: 風格切換是一個按鈕；它換掉意思而學生不知道，比積木那一路更隱形。

**Independent Test**: 每一支程式：產碼再讀回；以及換成每一種只改格式的風格產碼再讀回；比交給判斷功能的程式。

**Acceptance Scenarios**:

1. **Given** 課文語料，**When** 用同一個風格產碼再讀回，**Then** 交給判斷功能的程式相同。
2. **Given** 課文語料，**When** 換成只改格式的另一個風格產碼再讀回，**Then** 交給判斷功能的程式相同。
3. **Given** 換了 I/O 風格（`cout` ↔ `printf`），**When** 比較，**Then** 比的是判斷功能的判決與輸出相同（程式本來就不同，不算不一致）。

---

### User Story 3 - 學生自己寫的程式也量過（Priority: P2）

課文是我們寫的；學生的程式寫法更雜。用真實學生語料（218 支）跑同一套檢查，把數字寫下來，量到的缺陷要修。

**Why this priority**: 課文全綠不代表學生的寫法也安全；但學生語料是別人的 repo，不能常駐在全套裡。

**Independent Test**: 開環境變數跑探針，報出三種轉換各自的不一致數與歸因。

**Acceptance Scenarios**:

1. **Given** 學生語料，**When** 跑探針，**Then** 報出三種轉換的「相同／不同／翻不出」數字，每一筆不同指出差在哪個欄位；數字寫進 history。

### Edge Cases

- 語意樹本身翻不出（判斷功能還不支援的寫法）：兩邊都翻不出算一致；一邊翻得出一邊翻不出算不一致。
- 節點編號：每次讀回都會換新的編號；比較前依出現順序重新編號，其餘欄位逐字相同。
- 程式碼來回時被正規化的寫法（例如 `i++` 與 `i += 1` 在樹上本來就同一顆）：只要交給判斷功能的程式相同就算一致，程式碼文字不同不算。
- 板子程式（Arduino）：形態轉換一樣適用；它的程式帶板子資訊，比較時一併比。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 對課文語料的每一支，量三種轉換：(a) 同風格產碼再讀回 (b) 只改格式的風格切換後讀回 (c) 轉積木再抽回；比交給判斷功能的程式（節點編號正規化）。
- **FR-002**: I/O 風格切換那一類比判決與輸出（判決層），不比程式。
- **FR-003**: 檢查常駐在全套裡，硬性零或附理由的釘子；每一根釘子說得出是哪一段的缺陷，修好時會紅。
- **FR-004**: 一個注入測試證明比較真的會紅（不是空轉），並指名差在哪個欄位。
- **FR-005**: 量到的真缺陷在這一刀修掉；修不了的（例如判斷功能那側）以釘子留下並回報。
- **FR-006**: 學生語料走全套之外的探針（環境變數開），數字寫進 history。
- **FR-007**: 「宣告的五個面向」在 CLAUDE.md 與元件 skill 的表裡補上第五個。

### Key Entities

- **正規化的程式**：交給判斷功能的程式，節點編號依出現順序重新編號後的樣子；兩份相同 ⟺ 意思相同。
- **轉換**：同風格來回、格式風格切換、積木來回；I/O 風格切換另歸判決層。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 課文語料三種轉換的不一致數：零，或每一筆都有附理由的釘子。
- **SC-002**: 注入一個會換意思的轉換，檢查會紅並指名。
- **SC-003**: 學生語料 218 支跑過三種轉換，數字與歸因寫進 history。
- **SC-004**: 量到的缺陷修好後，相關的既有檢查（四個面向）照樣全綠。

## Assumptions

- 判斷功能（Cella）的程式是語意樹的單向投影，翻譯由 semorphe 負責；兩份程式相同 ⟹ 判決相同，所以比程式比判決更嚴、也更便宜。
- 「只改格式」的風格切換：縮排、命名空間寫法、標頭寫法；I/O 風格不在此列。
- 沿用既有的積木載入／抽回架子與課文語料，不另造一套。

# Feature Specification: 讓「刻意不執行」說得出話——而不是替沒實作的東西發宣告

**Feature Branch**: `053-declare-noop-execute`

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "階段 6.5 P2 前半：execute 路徑的語言專屬身分搬出核心層。實測發現真正的問題不是搬檔案。"

---

## 為什麼做這個

核心直譯器裡有一份**寫死的清單**，列著 34 個「沒有執行行為」的概念：

```
src/interpreter/interpreter.ts:117-132
  const noop = async () => {}
  for (const c of ['cpp_include', 'cpp_class_def', 'cpp_lambda', … 34 個]) reg(c, noop)
```

而上一輪已經為這件事建好了宣告欄位，理由寫在概念檔裡：

> **沉默的正確和沉默的缺失撞在一起時，讓正確的那個說話。**
>
> ```
> execute: "noop"     ← 顯式宣告：這個概念本來就不執行
> （缺這個欄位）       ← 缺失
> ```

**那個欄位加好之後，一個概念都沒有用過。**

實測（2026-08-06）：

| 量到什麼 | 數字 |
|---|---|
| 核心直譯器的寫死清單 | **34** 個概念 |
| 宣告了「刻意不執行」的概念 | **0** 個 |
| 完備性報表判為「execute 是殼」的 | 54 個 |
| 其中**其實在那份寫死清單裡**的 | **31** 個 |

**92 個殼裡有 31 個（34%）不是沒實作，是沒宣告。**

一個為了讓「刻意的空」出聲而建的機制，自己從沒被接上——概念檔裡正好有一節叫「**執行機構自己也可能是殼**」。

### Phase 0 追加：那份清單不只是文件，**它在關掉能用的東西**

研究階段追出一件 spec 第一版沒想到的事：執行器註冊表是「後註冊的贏」，而那份清單**在所有真實作之後**才跑。

**四個轉型概念有能用的實作，被清單無聲覆蓋**——`static_cast`、`dynamic_cast`、`reinterpret_cast`、`const_cast`。

實測 `static_cast<int>(3.9)` **輸出 0**：程式跑完、印出一個數字、而它是錯的。**不是沒實作，是實作被關掉了。**

這讓本功能多了一個性質：它**不只是重新分類**，其中一部分是真的把壞掉的東西修好。

### 但這個功能最危險的地方，正是它看起來最划算的地方

**把 31 個概念宣告成「刻意不執行」，會讓兩個護欄的數字同時下降，而不改變任何一行執行行為。**

如果那 34 個裡混著「其實是還沒實作、只是做成空的、看起來像刻意的」，這個功能就是在**把缺陷洗成宣告**——而且洗完之後，護欄會替它背書。

`comment`、`cpp_include`、`cpp_define` 顯然是真的不執行。
`cpp_constructor`、`cpp_destructor`、`cpp_lambda`、`cpp_class_def`、`cpp_virtual_method` **顯然可疑**——直譯器不支援物件導向，把它做成空的，執行結果會靜靜地錯。

**所以這個功能的主要工作不是宣告，是判斷哪些不配得到宣告。**

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每一個「刻意不執行」都說得出理由，說不出的不准宣告 (Priority: P1)

維護者要能回答：「這 34 個概念，哪些是真的不需要執行，哪些是我們還沒做？」

目前**兩者長得一模一樣**——都是那份清單裡的一行。

**Why this priority**：這是整個功能的地基。先做這個判斷，後面的宣告才不是替缺陷背書。**判斷錯的代價比不做更大**：一旦宣告下去，護欄會替它背書，而且以後沒人會再檢查。

**Independent Test**：把 34 個逐一分類，每一類都有可執行的判準，不是意見。

**Acceptance Scenarios**：

1. **Given** 那 34 個概念，**When** 逐一判定，**Then** 每一個都落入「真的不執行」或「還沒實作」，且**兩者都要寫出理由**
2. **Given** 一個被判為「真的不執行」的概念，**When** 檢查理由，**Then** 理由必須是**可驗證的**（例如：它在執行期沒有任何可觀察效果），不得只是「目前沒做」
3. **Given** 一個被判為「還沒實作」的概念，**When** 執行完備性報表，**Then** 它**仍然被算成殼**，且進入缺陷帳
4. **Given** 一個「還沒實作」卻被做成空操作的概念，**When** 使用者的程式用到它，**Then** 系統**出聲**而不是靜靜地給出錯的結果

---

### User Story 1b - 被清單關掉的四個轉型運算恢復正確 (Priority: P1)

使用者寫 `static_cast<int>(3.9)`，應該得到 3。目前得到 **0**——而且沒有任何錯誤訊息。

那四個轉型概念**本來就有能用的實作**，只是被那份清單覆蓋掉。

**Why this priority**：與 US1 並列。它是整個功能裡**唯一讓使用者現在就受益**的部分，其餘都是「以後不會出事」。而且它證明了 US1 的判斷值得做——清單裡確實藏著壞東西。

**Independent Test**：跑四個轉型的最小程式，比對輸出。

**Acceptance Scenarios**：

1. **Given** `static_cast<int>(3.9)`，**When** 執行，**Then** 得到 3（目前是 0）
2. **Given** 四個轉型概念，**When** 檢查註冊處，**Then** 每個**只有一處**註冊
3. **Given** 任一概念，**When** 被註冊超過一次，**Then** 有東西會出聲——**執行器註冊表目前沒有任何東西在看重複註冊**

---

### User Story 2 - 「刻意不執行」從程式碼裡的清單變成概念自己的宣告 (Priority: P1)

那份清單住在核心層，這違反「核心層不得認識語言專屬概念」。而且同一個事實有兩處記載——概念檔案裡的宣告欄位，和核心層的清單——**兩處從來沒有一致過**（宣告那邊是 0 個）。

**Why this priority**：與 US1 並列。US1 決定**誰**該被宣告，US2 決定宣告**放在哪**。

**Independent Test**：核心層的清單消失後，被宣告的概念仍然正常執行（不報未知概念）。

**Acceptance Scenarios**：

1. **Given** 一個宣告了「刻意不執行」的概念，**When** 執行到它，**Then** 跳過且不報錯，行為與現況完全相同
2. **Given** 核心層，**When** 搜尋語言專屬的概念身分，**Then** 那份 34 個的清單**不存在**
3. **Given** 一個**沒有**宣告也**沒有**執行器的概念，**When** 執行到它，**Then** 回報未知概念（現況行為，不得改變）
4. **Given** 同一個事實（這個概念不執行），**When** 檢查有幾處記載，**Then** **只有一處**

---

### User Story 3 - 除錯步驟的概念清單改由概念自己宣告 (Priority: P2)

核心層還有第二份寫死清單：判斷「哪些概念算一個除錯步驟」的 12 個概念名。

那是**視圖層的關心**（除錯器要在哪裡停），卻用語言專屬的清單寫在核心裡。專案已有既定做法——語義標註（annotations），而且概念型別上已經有這個欄位。

**Why this priority**：低於前兩者。它的數量較小，而且不像 US1 有「宣告錯了會替缺陷背書」的風險。

**Independent Test**：除錯時停下來的位置與現況完全相同。

**Acceptance Scenarios**：

1. **Given** 一個標註為「算一個步驟」的概念，**When** 除錯執行，**Then** 停在該處，與現況相同
2. **Given** 核心層，**When** 搜尋那 12 個概念名，**Then** 清單不存在
3. **Given** 一個沒有該標註的概念，**When** 除錯執行，**Then** 不停（現況行為）

---

### User Story 4 - 這件事以後不會再退回寫死清單 (Priority: P2)

**Why this priority**：不改變當下行為，但沒有它，下一個人加概念時還是會往核心層那份清單裡加一行——因為那是最省事的做法。

**Acceptance Scenarios**：

1. **Given** 有人在核心層新增一個語言專屬概念身分，**When** 執行既有的中立性護欄，**Then** 失敗並指名是哪一筆
2. **Given** 一個宣告了「刻意不執行」的概念，**When** 執行護欄，**Then** 報表列出**它的理由**，讓宣告可被複查而不是一次性的
3. **Given** 完備性報表，**When** 檢視，**Then** 「已宣告刻意不提供」與「真的有實作」**分開呈現**，不得混為同一個數字

---

### Edge Cases

- **一個概念在某些情況要執行、某些情況不用**——那它不是「刻意不執行」，不得宣告
- **宣告了刻意不執行，卻仍註冊了執行器**——矛盾，必須被偵測出來
- **概念同時屬於多個語言**（`comment` 這類通用概念）——宣告該放在通用層而非語言套件
- **判為「還沒實作」的概念，使用者現在就在用**——不得因為改成報錯而讓原本能跑的程式跑不了；需要一條可見的降級路徑
- **完備性的數字因為宣告而下降**——報表必須讓「因為宣告而下降」與「因為實作而下降」**分得出來**，否則下一個人會用宣告來刷數字

## Requirements *(mandatory)*

### Functional Requirements

**判斷（US1）**

- **FR-001**: 那 34 個概念 MUST 全部被逐一分類，**沒有一個可以略過**
- **FR-002**: 每一個分類 MUST 附可驗證的理由；「目前沒做」MUST NOT 構成「刻意不執行」的理由
- **FR-003**: 被判為「還沒實作」的概念 MUST NOT 取得宣告，且 MUST 仍被完備性報表算成殼
- **FR-004**: 被判為「還沒實作」且會產生**錯誤執行結果**的概念，MUST 在執行到它時出聲，不得靜靜地給出錯的答案
- **FR-005**: 判斷結果 MUST 記錄在可複查的地方，而非只存在於這次的討論裡

**宣告（US2）**

- **FR-010**: 「刻意不執行」MUST 由概念自己宣告，MUST NOT 由核心層的清單決定
- **FR-011**: 核心執行引擎 MUST 讀取該宣告；同一事實 MUST 只有一處記載
- **FR-012**: 宣告了「刻意不執行」卻同時註冊執行器 MUST 被偵測為矛盾
- **FR-013**: 既無宣告也無執行器的概念 MUST 維持現況——回報未知概念
- **FR-014**: 已宣告概念的執行行為 MUST 與現況完全相同

**重複註冊（US1b）**

- **FR-015**: 被清單覆蓋掉的四個轉型概念 MUST 恢復正確運作
- **FR-016**: 每個概念在執行器註冊表中 MUST 只有一處註冊
- **FR-017**: 重複註冊 MUST 可被偵測——目前執行器註冊表**沒有任何東西在看**這件事

**除錯步驟（US3）**

- **FR-020**: 「算一個除錯步驟」MUST 由概念的語義標註決定，MUST NOT 由核心層的清單決定
- **FR-021**: 除錯時停下來的位置 MUST 與現況完全相同

**防退步（US4）**

- **FR-030**: 中立性護欄的數字 MUST 下降，且下降幅度 MUST 可歸因到具體項目
- **FR-031**: 完備性報表 MUST 把「已宣告刻意不提供」與「有實作」分開呈現
- **FR-032**: 護欄報表 MUST 列出每個宣告的**理由**，讓宣告可被複查

**回歸保護（全域）**

- **FR-040**: 既有測試 MUST 全數維持通過
- **FR-041**: 六項既有量測中，中立性與完備性 MUST 下降，其餘 MUST NOT 上升
- **FR-042**: 任何使用者現在跑得起來的程式 MUST 仍然跑得起來，或**明確出聲說明為什麼不行**

### Key Entities

- **刻意不執行**：一個概念在執行期**沒有任何可觀察效果**。這是關於概念本質的陳述，不是關於實作進度的陳述
- **還沒實作**：一個概念**應該**有執行效果，但目前沒有。做成空操作會讓它與上一者無法區分——這正是要治的病
- **宣告**：概念自己說出「我不執行」。它取代推斷
- **理由**：宣告必須附帶的東西。沒有理由的宣告是**把缺陷洗成設計**

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 34 個概念 100% 被分類，每個都有可複查的理由
- **SC-002**: 核心層的兩份寫死清單（34 個 + 12 個）**歸零**
- **SC-003**: 中立性違規 **216 筆 → ≤170 筆**，且 `interpreter.ts` 從 61 筆降到 **≤15 筆**（餘量留給無法在本功能處理的）
  > **實測 174 筆、`interpreter.ts` 33 筆——後者沒達標。** 剩下的 33 筆是 15 條已知缺口清單 + 18 個 inline 執行器（`cpp_rand` 那類）。清掉它們要把執行器搬進語言套件，那是 P2，本功能的 Out of Scope 明確排除。**訂目標時沒把這兩塊算進去，是估錯了，不是做少了。**
- **SC-004**: 完備性的 execute 殼下降，且報表**分得出**多少是因為宣告、多少是因為實作——目前完全分不出
- **SC-005**: 被判為「還沒實作」的概念**沒有**取得宣告，且它們出現在缺陷帳裡
- **SC-006**: 既有測試全數通過；使用者現在跑得起來的程式仍然跑得起來
- **SC-007**: 有人再往核心層加一筆語言專屬概念身分時，CI 失敗並指名該筆
- **SC-008**: `static_cast<int>(3.9)` 得到 3——目前得到 0 且無任何提示
- **SC-009**: 執行器的重複註冊數被量出來並進棘輪；目前**完全沒有被看過**

## Assumptions

- **`skipPaths` 這個既有欄位是正確的落點**，不需要新的欄位。它目前被註記為「不影響執行期行為」，本功能**改變那句註記**——讓它成為機制而非文件。這正是「宣告取代推斷」。
- **語義標註（annotations）是除錯步驟清單的正確落點**——概念型別上已有該欄位，且專案已規劃過這個契約。
- **34 個裡會有一部分不配得到宣告**。若最後判定 34 個全部都是真的不執行，那**反而要懷疑判準太鬆**——這是本功能的自我否證提示。
- **不引入新的相依。**

---

## Out of Scope（明確排除）

- ❌ **實作那些「還沒實作」的概念**——本功能只讓它們**停止假裝已完成**
- ❌ **lift 路徑的搬移**（需要先消 `any`）
- ❌ **`src/ui/` 的 35 筆中立性違規**
- ❌ **目錄軸定案、膠囊格式**
- ❌ **把執行器實體搬進語言套件目錄**——本功能處理的是**清單**，不是檔案位置。搬檔案是下一步，且會與目錄軸定案綁在一起

---

## Dependencies

- **前置**：六條護欄（其中中立性與完備性是本功能的主要量尺）
- **知識地基**：`concepts/執行機構.md` 的第一條判準「沉默的正確和沉默的缺失撞在一起時，讓正確的那個說話」與「執行機構自己也可能是殼」；`experience.md`「與其偵測錯誤，不如換一個讓錯誤無法被表達的形式」；`history/017`「加嚴一個檢查可能比不檢查更糟」
- **解鎖**：階段 6.5 的 P2 後半（lift 搬移）與 Phase 7（Python 需要核心層真的語言無關）

## Risks & Mitigations

| 風險 | 緩解 |
|---|---|
| **把缺陷洗成宣告**——這是本功能唯一會讓事情變糟的方式，而且變糟之後**護欄會替它背書** | US1 整個故事在管這件事。FR-002 要求可驗證的理由；FR-003 要求判不過的仍算殼。**先做判斷再做宣告，順序不可反** |
| **數字下降卻沒有任何東西變好** | FR-031 要求報表分開「宣告」與「實作」造成的下降。**不分開的話，下一個人會用宣告刷數字** |
| **判為「還沒實作」而改成報錯，讓原本能跑的程式跑不了** | FR-042。這正是 `history/017`「加嚴一個檢查可能比不檢查更糟」的同一形狀——**先回答「被拒絕的東西去哪了」再動手** |
| **34 個全部判為「真的不執行」** | 那是判準太鬆的訊號，不是好消息。本功能的自我否證提示 |

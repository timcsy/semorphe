# Phase 0 研究：哪些「不執行」是真的

**日期**：2026-08-06 ｜ **方法**：跑真的直譯器，不推論

---

## F1：那份清單長什麼樣

```
src/interpreter/interpreter.ts:117-132
  const noop: ConceptExecutor = async () => {}
  for (const c of [ …34 個概念名… ]) reg(c, noop)
```

註解寫「編譯時/宣告性概念：無執行行為」。**那句註解是一個未經檢驗的宣稱**，而它替 34 個概念背書。

三個是**死條目**——`cpp:include`、`cpp:include_local`、`cpp:using_namespace` 用的是舊的冒號命名，在概念註冊表裡**根本不存在**（同一份清單裡的 `cpp_include` 等才是活的）。**實際有效 31 個。**

---

## F2：判準——看子槽，不看意見（**第一版是錯的，見 F2b**）

「這個概念該不該執行」聽起來像品味問題。它不是。

概念註冊表已經宣告了每個概念有哪些**子節點槽**。子槽裡裝的是**使用者寫的程式碼**。所以：

> **一個有子槽的概念，若它的執行器是空的，而且沒有別人去讀那些子槽——那些程式碼就被無聲丟棄了。**

三類：

| 類 | 判準 | 例 |
|---|---|---|
| **A 真的不執行** | **沒有子槽**，只有屬性 | `comment`、`cpp_include`、`cpp_define`、`cpp_raw_code` |
| **B 由父概念消費** | 有子槽，但**父概念的執行器會讀它** | `cpp_case`、`cpp_default`（`control-flow.ts:129` 讀 `caseNode.concept === 'cpp_default'`） |
| **C 還沒實作** | 有子槽，**沒有任何人讀** | `cpp_constructor`、`cpp_lambda`、`cpp_namespace_def` 等 |

**B 類是 spec 沒想到的。** spec 只寫了「真的不執行」與「還沒實作」兩類；實測發現有第三種**空得有理但理由不同**的——它的空不是因為沒有語義，是因為語義由父節點負責。宣告時必須寫得出是哪一種，否則下一個人看到 `cpp_case` 的宣告會以為 switch 也不執行。

---

## F2b：把 F2 自動化的第一版，答案是**反的**

三分類本身沒錯，錯的是把「有沒有人讀子槽」實作成 **grep 概念名**：

```
自動分類的結果            實測與程式碼的事實
─────────────────────    ────────────────────────────────
cpp_static_cast   → B     🔴 F3 實測輸出 0，是壞的
cpp_namespace_def → B     🔴 F3 實測報 UNDEFINED_FUNC
cpp_lambda        → B     🔴 F3 實測報 UNDEFINED_FUNC
cpp_case          → C     🔴 control-flow.ts:129 明明在讀它
```

**抓到它的不是 code review，是 F3 已經跑過的實測與它矛盾。**

根因：「檔案裡出現這個概念名」不等於「有人執行它的子槽」。那幾次額外提及是別的東西（見 F8）。

> **判準本身可以是對的，把它自動化的第一版仍然會量錯。** 這是「量測工具的第一版會安靜地量錯」的第五個實例，而這次的觸發點是**兩個量測互相矛盾**——先做的那個實測救了後做的那個掃描。
>
> **教訓**：F2 那種「靜態可判定」的宣稱要先在**已知答案的樣本**上驗過再拿來分類。三個已知答案（F3）就足以推翻它。

**因此分類必須是實測的**：每個概念跑一支最小程式，比對輸出。這與專案既有教訓一致——完備性護欄漏掉陣列 bug 的原因，正是它只跑合成的最小樣本而非真實程式碼。

## F3：C 類在跑真的程式時會怎樣（實測，不是推論）

```
🔴 static_cast    期望「3」實得「0」            ← 無聲的錯誤答案
🔴 namespace      期望「7」實得「」  UNDEFINED_FUNC
🔴 lambda         期望「42」實得「」 UNDEFINED_FUNC
✅ 對照-普通函式   期望「7」實得「7」            ← 證明量測本身能通過
```

測的程式碼：

```cpp
double d = 3.9; int n = static_cast<int>(d); cout << n;   // 印 0
namespace N { int f(){ return 7; } }  cout << N::f();      // 找不到函式
auto f = [](int x){ return x*2; };    cout << f(21);       // 找不到函式
```

**`static_cast` 是最糟的一個**：程式跑完、印出一個數字、而它是錯的。沒有任何錯誤、沒有降級標記。學生寫 `static_cast<int>(3.9)` 得到 0，不會知道發生什麼事。

另外兩個至少會報錯——**吵的錯比安靜的錯好**。

> 這正是專案既有的教訓：**靜默降級是 bug 的藏身之處**。而這裡的藏身處是一句註解：「編譯時/宣告性概念：無執行行為」。

## F4：宣告欄位早就在了，一次都沒用過

`ConceptDefJSON.skipPaths`（`src/core/types.ts:289`）是上一輪為此建的，註解寫得很清楚：

> 未宣告的空實作一律判為「殼」——正確的空與缺失的空長得一樣，所以要求正確的那個出聲。

實測：**宣告了 `skipPaths: ['execute']` 的概念有 0 個。**

而完備性報表的 54 個 execute 殼裡，**31 個就在那份寫死清單裡**。

所以現況是：**機制建好了、清單還在核心層、兩邊從未見面**，而護欄把刻意的空跟真的缺一起算進 92。

### 但 F3 改變了這件事的解讀

原本的算法是「92 個殼裡有 31 個是誤報」。**F3 之後不成立**——那 31 個裡有一大半是 C 類，它們**本來就該算殼**。

真正該取得宣告的只有 A 類與 B 類。**這個功能結束時，完備性的數字下降幅度會遠小於 31**，而那是對的結果。

> **若最後 31 個全部拿到宣告，那是判準太鬆的證據，不是成功。**（spec 的自我否證提示）

## F5：`skipPaths` 目前的定位需要改變

型別註解現在寫著：

> 純資料、可選、**不影響任何執行期行為**，只有完備性護欄讀它。

本功能要讓直譯器**讀它**。這句註解因此要改。

這不是把文件欄位臨時挪用，而是**它本來就該是機制**——概念檔的判準說得很白：把**推斷**改成**宣告**。目前的推斷是「核心層那份清單說了算」，宣告是「概念自己說」。

**同一個事實從兩處變一處**，順帶是 P4「殺雙重真相」的一筆首付。

## F6：第二份清單——除錯步驟

```
src/interpreter/interpreter.ts:436-445
  const statementConcepts = new Set([ …約 24 個概念名… ])
```

用途是判斷「哪些概念算一個除錯步驟」（除錯器要在哪裡停）。

這是**視圖層的關心**寫在核心層，而且用的是語言專屬的名字。專案已有既定落點——語義標註（`ConceptDefJSON.annotations`），`vision.md:98` 也已規劃過這個契約。

比 F1 那份單純：它沒有「宣告錯了會替缺陷背書」的風險，因為停多停少都不影響執行結果。

## F7：加嚴的代價——`history/017` 的第一次應用

C 類概念若從「空操作」改成「報未知概念」，**原本能跑完的程式會跑不完**。

`history/017` 剛學到的那條在這裡第一次派上用場：

> 一道會拒絕的檢查，必須同時回答「**被拒絕的東西去哪了**」。

三個選項：

| 做法 | 問題 |
|---|---|
| 改成報錯 | 原本印得出東西的程式現在整個停掉——比現況更糟 |
| 維持空操作 | 就是現在的病 |
| **維持空操作，但標記降級並出聲** ✅ | 程式照跑、結果可能不對、而**使用者知道哪裡不對** |

第三種與專案既有的「誠實降級」一致：`confidence` 與 `degradationCause` 已經是既有機制，不需要新東西。

**本功能不實作 C 類的執行**，只讓它們**停止假裝已完成**。

## F8：那份清單不只是文件——**它在覆蓋能用的執行器**

追查 F2b 那幾次「額外提及」，發現的是這個：

```
src/interpreter/interpreter.ts:54   registerOperatorExecutors(reg)
src/interpreter/interpreter.ts:56   registerFunctionExecutors(reg)   ← 這裡註冊了真的實作
...
src/interpreter/interpreter.ts:117  const noop = async () => {}
src/interpreter/interpreter.ts:125  for (const c of [… 'cpp_static_cast' …]) reg(c, noop)   ← 這裡蓋掉它
```

`ConceptExecutorRegistry.register` 是 `Map.set`（`executor-registry.ts:42`）——**後註冊的贏**。而 noop 清單在第 117 行，**在所有真實作之後**。

**四個轉型概念有能用的實作，被清單無聲關掉**：

| 概念 | 真實作位置 |
|---|---|
| `cpp_static_cast` | `functions.ts:130` |
| `cpp_dynamic_cast` | `functions.ts` |
| `cpp_reinterpret_cast` | `functions.ts` |
| `cpp_const_cast` | `functions.ts` |

這就是 F3 那個 `static_cast<int>(3.9) → 0` 的真正原因。**不是沒實作，是實作被關掉了。**

另外 10 個概念在 `functions.ts` 也註冊了 noop，與清單重複——無害的重複，但同一個病。

> **這是 051 那個病換一個註冊表重演**：同一個身分被登記多次，勝負由**載入順序**決定，而那個順序不是任何人設計的。051 為 lift 規則建了歧義護欄；**執行器註冊表沒有任何東西在看**。

### 這把功能的性質改了

原本以為主要工作是「重新分類 31 個概念」（不改行為）。實際上其中 **4 個是可以真的修好的 bug**——刪掉清單裡那四行，`static_cast` 就會開始正確運作。

**這是本功能唯一真正改變執行行為的部分，而它的方向是「讓原本壞的變好」，不是「讓原本好的變嚴」。**

## 自我否證：這份研究若在什麼情況下是錯的

- **F2b 已經是一次現形**：靜態掃描的分類答案是反的，靠 F3 的實測抓到。所以**分類一律以實測為準**，靜態判斷只能用來排順序、不能用來下結論。
- **F3 只實測了三個**。實作時要把 31 個**全部**跑過——這是本功能的第一個任務，不是最後一個。
- **若 31 個全部落入 A 或 B**——判準太鬆。這是最需要警覺的結果，因為它同時是最省事的結果。
- **F8 宣稱「刪掉那四行 `static_cast` 就會正確」是推理**（讀了註冊順序與 `Map.set`）。**實作要先跑出來再改**——跑不出來代表還有第三處在覆蓋。

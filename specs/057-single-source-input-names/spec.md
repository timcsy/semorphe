# Feature Specification: 唯一真相的機制建好了，91% 的地方沒用它

**Feature Branch**: `057-single-source-input-names`

**Created**: 2026-08-06

**Status**: Draft

---

## 為什麼做這個

積木的「插槽名稱」有兩處定義：積木宣告檔（JSON）與程式裡的動態註冊。兩邊不一致時，**只在切換積木外觀（存檔再讀回）時才炸**——平常測試全綠。

專案已經為此建過一個機制。那個模組的檔頭寫著：

> 「**唯一真相**。若 JSON 裡的插槽名稱改了，動態註冊會自動跟上——**不需要兩邊維護**。」

實測（2026-08-06）：

| | |
|---|---|
| 動態註冊裡寫**字串字面**的插槽名 | **70 處** |
| 用那個機制（JSON 導出的常數）的 | **7 處** |

**機制建好了，91% 的地方沒有用它。**

而且這是同一個病的第三次：上一輪發現「刻意不執行」的宣告欄位建好後**一個概念都沒用過**，再上一輪發現跨語言父概念的宣告**75% 指向不存在的東西**。

> **建一個機制不等於它在運作。** 這個專案已經有一條教訓在講執行機構，但那條講的是「規範沒有檢查」；**這一類是「機制有了，沒人接上」**。

### 為什麼是這個量法

先前的量法是「比對兩邊的插槽名稱集合，看有沒有分歧」。那個量法**量錯了兩次**：

1. 動態側只算「輸入」不算「欄位」，而 JSON 側兩者都算——**兩邊定義沒對齊**
2. 用常數寫的插槽名（`COUNT_LOOP_INPUTS.value[0]`）被判成「動態側沒有」——**那些恰恰是唯一真相的正例**

改量「有幾處寫死字面」之後，數字才對得上要治的病：**寫死才會分歧，用常數不會。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 寫死的插槽名被攤開 (Priority: P1)

**Why this priority**：70 處寫死目前**完全沒有被看過**。既有的一致性測試只檢查 JSON 格式良好，不檢查有幾處沒用機制。

**Acceptance Scenarios**：

1. **Given** 動態註冊的程式碼，**When** 掃描，**Then** 列出所有寫死的插槽名及其所在積木
2. **Given** 該數量，**When** 進基線，**Then** 只准下降
3. **Given** 有人新增一處寫死，**When** 檢查，**Then** 失敗並指名

---

### User Story 2 - 寫死的改用唯一真相 (Priority: P1)

**Why this priority**：與 US1 並列。攤開不改，等於把問題從隱形變成可見的待辦。

**Acceptance Scenarios**：

1. **Given** 每一處寫死的插槽名，**When** 改用 JSON 導出的常數，**Then** 積木的行為完全不變
2. **Given** 某個插槽名在 JSON 裡不存在，**When** 遷移，**Then** **不得硬湊**——那代表兩邊本來就不一致，要先查明哪一邊對
3. **Given** 遷移完成，**When** 改動 JSON 裡的插槽名，**Then** 動態註冊自動跟上，不需要改第二處

---

### User Story 3 - 分歧從此不可能發生 (Priority: P2)

**Why this priority**：低於前兩者。但少了它，下一個人還是會寫字面——因為那是最省事的做法。

**Acceptance Scenarios**：

1. **Given** 遷移後的程式碼，**When** 有人寫死一個插槽名，**Then** 檢查失敗並指出該用哪個常數
2. **Given** 報表，**When** 檢視，**Then** 說得出「用機制的比例」而不只是「有幾處寫死」

---

### Edge Cases

- **執行期生成的插槽**（可變參數的 `PARAM_0`、`ARG_0`）——那些**本來就沒有** JSON 對應物，不算寫死
- **輔助積木**（mutator 的容器、列項）——它們沒有語義概念，也沒有 JSON 宣告
- **插槽名在 JSON 裡不存在**——那是真正的分歧，要先查明哪一邊對，**不得為了遷移而硬加**
- **遷移後行為改變**——代表兩邊本來就不一致，那個改變**就是修好**，但必須逐一確認而非默默接受

---

## Requirements *(mandatory)*

- **FR-001**: MUST 列出所有寫死的插槽名，含所在積木與行號
- **FR-002**: 該數量 MUST 進基線與棘輪
- **FR-003**: 新增寫死 MUST 讓檢查失敗並指名
- **FR-004**: 執行期生成的插槽與輔助積木 MUST NOT 被計入（它們沒有 JSON 對應物）
- **FR-010**: 有 JSON 對應物的寫死插槽名 MUST 改用導出的常數
- **FR-011**: 遷移後積木行為 MUST 完全不變
- **FR-012**: 插槽名在 JSON 裡不存在時 MUST NOT 硬湊——記錄為待查
- **FR-020**: 報表 MUST 呈現「用機制的比例」，不只是絕對數量
- **FR-030**: 既有測試 MUST 全數通過；十項量測 MUST NOT 上升

### Key Entities

- **插槽名**：積木上一個輸入或欄位的識別字。**它是序列化契約的一部分**——改了會讓舊存檔讀不回來
- **唯一真相**：JSON 宣告。動態註冊從它導出，不自己寫
- **寫死**：在動態註冊裡直接寫字串字面。**它與 JSON 分歧時不會有任何錯誤，只在切換積木外觀時才炸**

---

## Success Criteria *(mandatory)*

- **SC-001**: 寫死的插槽名 **70 → ≤10**（剩下的必須是「JSON 裡真的沒有對應物」並記錄原因）
- **SC-002**: 用機制的比例從 **9% → ≥85%**
- **SC-003**: 積木行為完全不變；切換積木外觀的 round-trip 仍然正確
- **SC-004**: 新增一處寫死時檢查失敗並指名
- **SC-005**: 既有測試全數通過

---

## Assumptions

- **多數寫死的插槽名在 JSON 裡有對應物**，因為兩邊本來就是同一顆積木的兩份定義。
- **少數沒有對應物**（執行期生成、輔助積木），那些不算違規。
- **遷移是機械的**：把字面換成常數。若換完行為變了，**那代表兩邊本來就不一致**——那是發現，不是失敗。

---

## Out of Scope

- ❌ **統一「兩處定義」本身**——讓動態註冊完全由 JSON 生成是更大的重構，本功能只讓**名稱**不再分歧
- ❌ **欄位型別、顏色、tooltip 的一致性**
- ❌ **mutator 的執行期插槽**

---

## Risks & Mitigations

| 風險 | 緩解 |
|---|---|
| **遷移改變了序列化契約** | 插槽名是存檔格式的一部分。若某處寫死的名字與 JSON 不同，換過去會讓**舊存檔讀不回來**。FR-012：不硬湊，先查明哪一邊對；必要時走存檔版本閘門 |
| **為了讓數字下降而把不該遷的也遷了** | FR-004 明訂執行期插槽與輔助積木不計入。**分母要誠實** |
| **量測第三次量錯** | 前兩次都是「兩邊定義沒對齊」。這次改量「有幾處寫死」——單邊、可數、不需要對齊 |

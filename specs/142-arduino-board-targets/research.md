# Phase 0 研究：板子成為目標

**日期**：2026-08-19 · **規格**：[spec.md](spec.md)

> 🔴 **兩個發現改變了規格的判斷。** 兩者都寫在下面，並附了「規格要怎麼改」。

---

## R1｜「能力」該住在哪：`traits`，而且有現成的先例

**決定**：元件用 `component.json` 的 **`traits`** 宣告它需要什麼能力。

**理由**：`traits` 的定義逐字（`concepts/性狀.md`）：

> 「一顆元件對外宣告**它是什麼樣的東西**（`traits`），而別的程式碼**問那個性質**，
> 不寫死它的身分。」

🟢 **而它已經在做結構上完全相同的事**——`ioStyle`：

```
cpp:print             traits.ioStyle = 'iostream'
cpp:print_formatted   traits.ioStyle = 'cstdio'
cpp:serial_print      traits.ioStyle = 'serial'
```

那句話是「**這顆只在某個 I/O 風格的世界裡有意義**」，而板子要說的是
「**這顆只在有某個硬體能力的板子上存在**」——同一個形狀。

**被否決的替代方案**

| 方案 | 為什麼不 |
|---|---|
| 三份 `arduino-uno.json`／`-nano`／`-esp32` 課程清單 | 三份幾乎相同的檔案；`experience.md:31`「維度之間的職責必須分清」 |
| 目標直接列一串 conceptId | `experience.md:1508`「指它的性質而不是它的名字」——加一顆 ESP32 元件要改三個目標 |
| 新開一個 `boards.json` 對照表 | 那是**第三個真相來源**；`traits` ＋ `Target.provides` 兩邊各自宣告就夠 |

**能力的命名**：用**功能**不用板子（`'touch'`／`'ledc-pwm'`，不是 `'esp32-only'`）。
⚠️ 理由：`'esp32-only'` 把「誰有」寫進了能力的名字裡，而下一塊有觸摸感應的板子
會逼出 `'esp32-or-xxx-only'`。

## R2｜🔴 可拿性護欄**不需要放寬**——而它有一個新的洞

**規格 FR-008 的前提錯了。** 實測：

```
audit-toolbox-reachability.test.ts:58   import { cppCategoryDefs } from '…/toolbox-categories'
                                        ↑ 它算「拿得到」是看【分類定義】，與目標無關
```

工具箱分類是從登錄表導出的，**而過濾發生在那之後**。所以只要過濾點在「分類導出」
之後，這條護欄**原封不動就是綠的**——它今天量的其實已經是
「**在至少一個目標下拿得到**」，只是當時只有一個目標所以看不出差別。

> **一條護欄的判準有時不必改——要改的是我們對它在量什麼的理解。**

🔴 **而這一刀開了一個新的洞，它抓不到**：

```
元件宣告 traits.needsCapability = 'touch'
而【沒有任何目標】提供 'touch'
→ 這顆元件在所有板子上都拿不到，而可拿性護欄全綠
```

**處置**：新增一條檢查——**每一個被宣告需要的能力，至少要有一個目標提供它**。
硬性零（判準：留一筆在那裡，「這顆元件拿得到」這句話就是假的）。

⚠️ **規格要改**：FR-008 從「放寬可拿性判準」改成「**新增能力供給完備性檢查**」。

## R3｜🟡 腳位常數比想像的貴——建議 US3 不進本刀

實測 `src/components/cpp/pin_constant/component.json`：

```json
"properties": [{ "name": "value", "kind": "enum",
                 "values": ["HIGH","LOW","OUTPUT","INPUT","INPUT_PULLUP","A0"] }]
```

🔴 **`values` 是一個靜態宣告**。要讓它隨目標變，需要一個**今天不存在的機制**
（屬性的候選值由目標提供），而那會動到：

```
component.json 的 properties 契約     所有 175 顆元件的宣告形狀
積木渲染（下拉選項怎麼來）             block-registrar 的動態下拉
extract（選項變了，舊存檔怎麼辦）      存檔完整性護欄
```

**建議**：US3（P2）**不進本刀**，理由是憲法第一條：

> 「不得過度設計：僅實作當前需求……**新增的複雜度 MUST 有明確的當前需求作為理由**」

而 US1／US2（P1）**不需要那個機制**——它們只要「這顆積木在不在工具箱裡」。

⚠️ **而這不是砍掉它，是排序**：US3 的價值仍在（下拉裡出現不存在的腳位會誤導學生），
它應該成為**下一刀**，而那一刀的名字是「屬性的候選值由目標提供」——
一個比「板子」更一般的機制。

**規格要改**：FR-005 與 US3 移到「明確排除」，並在 vision 留一筆。

## R4｜過濾點：只過濾工具箱，不動畫布

**決定**：過濾發生在**工具箱組裝**（`toolbox-builder.ts`），
**不**動 `markOutOfScopeBlocks`（畫布上的灰階標記）。

**理由**：規格的邊界案例逐字要求「積木不消失」，而既有行為已經是
（`experience.md:35`）：

> 「workspace 既有積木不受層級切換影響（只影響 toolbox 可用性）」

⚠️ **而「要不要把板子不支援的積木標成灰色」是一個開著的問題**——
它有價值（學生看得到「這顆在你的板子上不會動」），而它**不是本刀的需求**。
憲法第一條：不為假設性需求預留。**留給實測回報**。

## R5｜lift 不受影響——這一條是免費的

`lift` 走 `PatternLifter` 與各元件的 `lift.ts`，**完全不看目標**。
所以 FR-004「任何目標下 `touchRead` 都要被認成 `cpp:touch_read`」
**今天就成立**，本刀只要**不去破壞它**。

🔴 **而它仍然要有測試**——理由是 `build-guardrail` 的第 9 步：

> 「**正確的輸入**：證明它**不亂報**。第二個不可省。」

一支「Uno 目標下貼 ESP32 程式碼，殘差 0」的測試，守的是
「**未來有人把過濾往上游搬**」——那是這一刀最自然的錯法。

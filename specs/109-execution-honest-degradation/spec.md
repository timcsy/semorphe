# Feature Specification: 執行那一路的誠實降級

**Feature Branch**: `109-execution-honest-degradation`
**Created**: 2026-08-10
**Status**: Draft（**2026-08-10 改寫一次**，見下方「原始前提被查證推翻」）
**Input**: 把 `specs/108` 掀出的 31 筆誤差歸根因並修掉可修的。

## 這個 spec 在治什麼

`specs/108` 蓋的第三十二條護欄第一次跑抓到 31 筆「直譯器與參照編譯器輸出不同」。
逐筆探測（2026-08-10）之後發現**它們不是同一種東西**：

| 類 | 筆數 | 是什麼 | 該怎麼辦 |
|---|---|---|---|
| **A 真缺陷** | ~15 | 功能有實作，實作是錯的（含原本被誤判為 B 的那批） | **修** |
| **C 條件性正確** | ~16 | 單獨測全部通過，**組合才壞** | 本輪只歸因，不修 |

### ⚠️ 原始前提被查證推翻——「已知不支援」這一類**不存在**

本 spec 第一版把 7 筆 OOP 歸為「已知不支援」，依據是
`knowledge/concepts/執行機構.md:168`（2026-08-06）：
「其餘 14 個跑起來結果是錯的（**十個是物件導向，直譯器不支援它**）」。

**那句話已經被三個 spec 推翻了，而我拿它當前提。** 查證：

```
specs/071-struct-execute  072-class-method-execute  073-oop-slice3   ← 之後真的實作了
unimplemented.ts 的 OOP_NOT_IMPLEMENTED = []                        ← 現在是空的
structs.ts:191  ctx.structs.declare(name, fields, methods, ctor, …)  ← 建構式有被登記
struct-types.ts:96  constructorOf(structName)                        ← 讀得到
```

而**決定性的一行**：

```
destructorOf    1 個呼叫者    ← structs.ts:151
constructorOf   0 個呼叫者    ← 死匯出
```

**機制全都在，只是沒有人呼叫它。** 這正是 `執行機構` 的**第六個實例**
（「有人替它寫了測試／實作——而那份實作沒有人用」），
不是「不支援」。

> **後果**：第一版 spec 圍繞「新增一個宣告值」設計的整套防洗數字機制
> （分欄、總和不變、只能宣告已記錄過的缺口）**全部不需要了**
> ——因為沒有東西要被宣告。**這是最好的結果：缺口不必被宣告，它可以被修。**

### ⚠️ 而使用者拿得到那些積木

```
A a;              預設建構子 → 什麼都不印
~A(){…}           解構子     → 會印        ← 不對稱
A a(5);           → 執行期錯誤「a（不是一個結構）」
class A{ int v=7; }  成員預設值 → 讀成 0
```

`cpp:class_def` 與 `c_constructor` **都有積木**——使用者拿得到、按下執行、
什麼都不發生。這是「可拿性」護欄的**執行版孿生**：不是拿不到，是**拿得到而按下去會說謊**。

### ⚠️ C 是第一次被抓到的一階病

`執行機構.md` 那張表把病分三階，而第三階寫著：

> 「**條件性正確**：在、不空，**單獨測都過，組合才壞**」

實測：陣列初始化列表 ✅、`sizeof(long)` ✅、`unsigned char` ✅、`new int` ✅、
`string.substr` ✅、`string.find` ✅——**單獨全過**，而在真實程式裡組合起來就錯。
**第三十二條護欄是第一個抓得到這一階的機制。**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 字元不再被印成數字（Priority: P1）

學生寫 `char c = 66; cout << c;`，預期看到 `B`，而系統印出 `6`。

**Why this priority**：這是**使用者可見**、**每天會踩**、且**修法明確**的一類。
教學工具印錯字元，學生會學到錯的東西。

**Independent Test**：`char c=66; cout<<c;` 輸出 `B`。

**Acceptance Scenarios**：

1. **Given** 一個字元變數持有數值 66，**When** 用輸出串流印它，**Then** 顯示 `B` 而非 `6`
2. **Given** 一個浮點數 `1.0/3`，**When** 用預設格式印它，**Then** 顯示六位有效數字
3. **Given** `try { throw 10; } catch (int e) { … }`，**When** 印出 `e`，**Then** 顯示 `10` 而非物件的字串形式
4. **Given** 一個整數序列與初值，**When** 求總和，**Then** 得到正確的和而非 0

### User Story 2 - 建構子真的會被呼叫（Priority: P1）

學生寫一個帶建構子的類別、按下執行，**建構子裡的輸出完全沒有出現**，
而同一顆物件的解構子**會**出現。

**Why this priority**：與 US1 同級。而它更難自己發現——**解構子有跑**，
所以「類別完全沒作用」這個明顯的線索不存在，看起來只是少了一行輸出。

**Independent Test**：`class A{ public: A(){ cout<<"ctor"; } }; int main(){ A a; }` 輸出 `ctor`。

**Acceptance Scenarios**：

1. **Given** 一個有預設建構子的類別，**When** 宣告該型別的變數，**Then** 建構子被執行
2. **Given** 一個有帶參數建構子的類別，**When** 以 `A a(5)` 宣告，**Then** 建構子以該引數被執行，不得丟出「不是一個結構」
3. **Given** 一個成員帶預設值的類別，**When** 讀該成員，**Then** 得到預設值而非 0
4. **Given** 一個沒有建構子的類別，**When** 宣告變數，**Then** 行為與現況相同（不得回歸）

### User Story 3 - 31 筆誤差每一筆說得出根因（Priority: P2）

維護者看到「誤差 31 筆」時，看不出哪些是同一個成因。實測顯示
**一筆 ≠ 一個工作**：四個根因涵蓋約 8 筆，而另外約 16 筆單獨測全部通過。

**Why this priority**：它讓 US1／US2 的成果可被歸屬，但本身不改變使用者體驗。

**Independent Test**：判定檔每一筆有根因欄，且相同根因的筆數對得起來。

**Acceptance Scenarios**：

1. **Given** 判定完成，**When** 讀判定檔，**Then** 每一筆有根因與理由
2. **Given** 修好一個根因，**When** 重跑護欄，**Then** 該根因下的所有筆數一起消失
3. **Given** 誤差數下降，**Then** 基線註明下降原因是「因為實作了」

### Edge Cases

- **建構子被呼叫兩次**：宣告路徑與明確呼叫路徑若都觸發會重複執行
- **沒有建構子的類別**：不得因為這次改動而開始丟錯
- **解構子的既有行為**：已經正確，不得回歸
- **浮點格式**：`cout << 1.0` 應印 `1` 不是 `1.000000`（C++ 預設去尾零）
- **字元的兩種存法**：字元值可能以字元或數字碼存放，兩種都要印成字元

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：字元型別的值經由輸出串流顯示時，MUST 顯示為字元，MUST NOT 顯示為數值或其截斷。
- **FR-002**：浮點值以預設格式顯示時，MUST 與參照編譯器的預設有效位數一致（六位有效數字、去尾零）。
- **FR-003**：例外攜帶的值被捕捉並顯示時，MUST 顯示該值本身，MUST NOT 顯示為物件的字串形式。
- **FR-004**：對整數序列求總和的標準演算法 MUST 回傳正確結果，MUST NOT 是回傳固定值的空實作。
- **FR-005**：宣告一個具有建構子的類別型別變數時，該建構子 MUST 被執行。
- **FR-006**：帶引數的建構式宣告 MUST 被辨識為建構，MUST NOT 丟出「不是一個結構」。
- **FR-007**：類別成員的預設值 MUST 在建構後可讀到。
- **FR-008**：沒有建構子的型別 MUST 維持現有行為（不得回歸）。
- **FR-009**：31 筆誤差 MUST 逐筆記錄**根因**，且每筆 MUST 有理由（沿用既有檢查）。
- **FR-010**：誤差數下降時，基線 `_meta` MUST 註明下降原因屬於「因為實作了」還是「因為宣告了」。
- **FR-011**：本輪 MUST NOT 新增任何「已知不支援」之類的宣告值——查證顯示沒有東西需要被宣告。

### Key Entities

- **根因**：一組誤差共同的成因描述（例：「字元經輸出串流時被當成數值」）
- **判定**：每筆誤差的分類 ＋ 根因 ＋ 理由

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：`char c=66; cout<<c;` 顯示 `B`。
- **SC-002**：五個根因各有一支釘住的回歸測試，且都通過。
- **SC-003**：帶建構子的類別執行時，建構子的輸出出現；沒有建構子的類別行為不變。
- **SC-004**：判定檔每一筆有根因欄。
- **SC-005**：誤差基線較 `specs/108` 的 31 下降，且 `_meta` 註明下降來自實作。
- **SC-006**：全部測試通過。

## Assumptions

- 「參照編譯器的預設有效位數」以 `-std=c++17` 下的預設行為為準（六位有效數字）。
- C 那 16 筆只歸因不修——它們是組合缺陷，逐一修需要先有更小的重現案例。

## Out of Scope

- **繼承／多型／運算子多載**——本輪只接上已經存在而沒人呼叫的建構式路徑
- **修 C 那 16 筆條件性正確的缺陷**——本輪只歸因
- 27 個檔的凍結讀數清償
- 殘差那一路（`raw_code` 的執行通道）

## 給實作者的警告

### ⚠️ 第一版 spec 錯在哪——「引用知識庫」不等於「查證」

第一版整份圍繞「新增一個宣告值」設計，依據是 `執行機構.md:168` 那句
「直譯器不支援物件導向」。**那句話寫於 2026-08-06，而 071／072／073
三個 spec 在那之後把它實作了。**

> **一句寫在知識庫裡的論斷，會被當成現況引用，而它記的是寫下當天的世界。**
> 這與「凍結的讀數是宣告不是量測」（`specs/108`）是同一個形狀，
> 只是這次凍結的不是 `g++` 的答案，是**我們自己對系統的判斷**。

→ 教訓：**引用知識庫裡的「現況」時，要像引用外部讀數一樣重新量一次。**
   而這次救它的是 `grep constructorOf` ——**零個呼叫者**。

### ⚠️ 這一輪的真正風險：接上一條沒人走過的路

`constructorOf` 是死匯出，代表**那條路從來沒有被執行過**。
接上它等於第一次啟用一段沒有覆蓋的程式碼。

- **一顆一個 commit**，每顆跑全套
- 特別盯 **FR-008**（沒有建構子的型別不得回歸）——那是最可能被打到的
- ⚠️ 既有教訓：「**修法要驗，不能只推理**」

### ⚠️ 既有教訓

- 「**靜默降級反模式**：多層 fallback 都用同一預設值會掩蓋真正的資料遺失」
  ——建構子不跑導致成員讀成 `0`，與「真的是 0」長得一模一樣。
- 「**解析不了時擲錯，不回傳「沒事」**」——這句話**就寫在 `numeric/executors.ts`
  裡**，而同一個檔案下面兩行的 `cpp:range_sum` 正是回傳固定值 0 的空實作。
  **殼寫在寫著「不要留殼」那句話的下面。**

### ⚠️ 一個我在規劃時猜錯的，記下來以免重犯

`isupper`／`islower` **不是壞掉**，是宣告過的缺口：

> `src/languages/cpp/std/cctype/executors.ts:46`：「第一版順手加了
> `isalnum`／`isupper`／`islower`……而它們**沒有概念定義、沒有辨識、
> 沒有產生器、沒有積木**……要加它們的話是**五路一起加**」

它連辨識都沒有，所以進不了語義樹——**那是殘差不是誤差**，
而誤差護欄本來就不會數到它（它會讓執行丟出未定義函式，落進「只有參照跑得動」欄）。

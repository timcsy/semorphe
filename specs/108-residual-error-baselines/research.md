# Research：兩條基線的可行性與判準

**日期**：2026-08-10 ｜ 全部是**實測**，不是推測。

## 一、參照編譯器**不是 GCC**

```
$ which g++ && g++ --version
/usr/bin/g++
Apple clang version 16.0.0 (clang-1600.0.26.6)
```

**Decision**：基線 `_meta` 記**版本字串原文**，不記「g++」這個名字。
**Rationale**：`g++` 在 macOS 上是 Apple clang 的別名。把它記成「g++」會讓
未來在 Linux 上跑出不同數字的人**找不到原因**——而那正是 FR-007 存在的理由。
**Alternatives**：記 `g++ -dumpversion`（❌ clang 回報的版本與 GCC 語義不同，會誤導）。

## 二、誤差語料的規模與第一次的數字

在既有測試檔裡撈出**帶 `int main` 的去重片段**，兩邊都跑：

```
帶 main 的去重語料          312
參照編譯器編得過並跑得動      294      （18 段跑不動）
直譯器跑得動                290      （22 段跑不動）
兩邊都成                    276
一致                       212
**不一致                    64**     ← 23.2%
```

**Decision**：誤差基線的第一版數字是 **64**（棘輪），且**必須逐筆分類**。
**Rationale**：符合 `build-guardrail` 6.5「第一次跑必須是紅的」——它紅了，而且紅得很大。
**Alternatives**：只記總數（❌ 違反 FR-004，而且下一節說明為什麼那會重蹈覆轍）。

### ⚠️ 這 64 筆**很可能又是語料問題**——而這正是上一次犯的錯

殘差第一版量成 48.83%、正確值 0.23%，差 200 倍，**錯的是語料不是程式**。
同一個坑在這裡的形狀是：

| 可能的分類 | 是不是真的誤差 |
|---|---|
| 語料要讀標準輸入（`cin`），無人值守時兩邊行為本來就不同 | ❌ **不是** |
| 語料是測試裡**故意寫錯**的示範 | ❌ **不是** |
| 直譯器真的算錯 | ✅ **是** |

**Decision**：實作**必須先分類再定基線**，不得直接把 64 寫進去。
**Rationale**：`build-guardrail` 第 6 步——「靜態判斷不能下結論，只能排順序」，
而這裡連實測都只能排順序，因為**判定哪一種是真誤差需要看每一段**。
→ 落點用第 11 步的 `decisions.json`：已判定的移出「要看」，且**每一筆要有理由**。

## 三、「跑不動」不可以從分母消失

```
參照跑不動 18 ｜ 直譯器跑不動 22 ｜ 只有一邊成功 =18
```

**Decision**：報告分**四欄**——兩邊都成 276／只有參照成 18／只有直譯器成 14／兩邊都不成 4。
**Rationale**：FR-005。若只報「兩邊都成的 276 裡不一致 64」，那麼**讓直譯器多壞掉幾段
會讓誤差率下降**——分母縮小比分子減少容易。
**Alternatives**：只記兩邊都成的（❌ 上面那句話就是它的反例）。

## 四、執行時間：294 次編譯 ≈ 10 分鐘（序列）

**Decision**：**並行編譯**（依 CPU 核心數），並在報告裡印出實際跑了幾段。
**Rationale**：`npm test` 多 10 分鐘會讓人改成手動跑，而**沒有人跑的護欄等於沒有護欄**。
並行後約 1–2 分鐘，可以接受。
**Alternatives**：
- 抽樣（❌ 違反「no silent caps」——抽樣要印出丟掉了什麼，而抽樣的護欄不能當棘輪）
- 用環境變數 opt-in（❌ 與 FR-006「缺編譯器要紅」精神衝突：可跳過的護欄會被跳過）

## 五、直譯器的呼叫介面（給實作用，避免重蹈）

```ts
const i = new SemanticInterpreter({ maxSteps: 100000 })
await i.execute(tree)
i.getOutput().join('')      // ← 輸出在這裡
```

⚠️ **不是 `i.getState().output`**——`getState()` 只回 `{status}`。
先前有一次基線把執行結果錄成空字串就是踩這個，靠 `build-guardrail` 第 10 步
（「先證明它真的測到了東西」）才抓到。

## 六、殘差那條的語料判準

```
全部語料 820 段  →  殘差 48.83%   ❌ 第一版
語法完整 467 段  →  殘差  0.23%   ✅ 正確
語法有錯 353 段  →  片段，不計入
```

**Decision**：用 tree-sitter 的 `rootNode.hasError` 分欄。
**Rationale**：那是解析器自己的判定，不是我們的啟發式——**已知答案樣本**是
「完整程式的殘差應該接近零」，而 48.83% 與那個常識矛盾，正是它被抓到的方式。
**Alternatives**：用「有沒有 `int main`」判斷（❌ 太嚴，會把合法的宣告片段濾掉）。

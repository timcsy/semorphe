# Research：怎麼分辨「身分引用」與「撞名字串」

> 日期：2026-08-06

本功能只有一個技術未知：**判別式是什麼。** 其餘都是搬運。

---

## 決策 1：沿用既有的「遮罩」機制，不引入型別分析

**Decision**：擴充 `tests/helpers/component-scan.ts` 既有的遮罩管線，不引入 ts-morph 或 TypeScript Compiler API。

**Rationale**：這個機制已經存在，而且它的紀律**已經寫在程式碼裡**（`component-scan.ts:83`）：

> 「這與註解剝離是同一條紀律：**掃描要分得出「這裡實作了它」與「這裡提到它」**。」

`maskAbstractTargets` 遮掉 `"abstractConcept": "x"` 的值，理由是「那不是 x 的實作足跡，而是別人在指向 x」。`splitCodeAndComments` 把註解剝掉。**本功能是同一招的第三次應用**，不是新發明。

**Alternatives considered**：

- **TypeScript AST 分析（ts-morph）**——判別力最強（型別位置 vs 值位置是編譯器知道的事），但引入新相依，違反規格的「不引入新的相依」。而且**它只解決三種誤報中的一種**（型別位置），另外兩種（欄位預設值、AST 節點型別）在型別上都是合法的 `string`，編譯器一樣分不出來。**判別力的來源不是型別系統，是語法位置**——那用文字比對就夠了。
- **白名單：只有出現在已知的身分位置才算**（`registry.get(...)`、`case ...`、`conceptId === ...`）——反過來做。否決：違反 FR-002 的保守原則。白名單的預設是「放行」，一個沒被列舉到的新身分位置會被靜靜漏掉，而**漏掉的違規不會有任何人發現**。遮罩的預設是「算違規」，漏掉的只是多報一筆。

## 決策 2：三個候選遮罩，只採用兩個

實測方式：對八個含違規的檔案分別套用，列出每個遮罩實際遮掉的字串，再與違規清單比對。

### ✅ A 型別位置——採用

`type X = 'a' | 'b'` 與 `prop: 'a' | 'b' | 'c'` 裡的字串。

**Justification**：型別位置的字串**永遠不可能**是執行期的身分引用——它在編譯後不存在。這不是啟發式，是語言規則。

實測遮掉 `src/core/types.ts` 的 55 個聯集成員，其中只有 `comment` 在違規清單裡。其餘（`pragma`／`before`／`cout`／`iostream`…）本來就沒被計。

### ✅ C UI 欄位預設值——採用

`new Field*(...)` 的第一個引數。

**Justification**：Blockly 的欄位建構式第一個引數是**值**，不是識別碼——那是使用者在積木上看到的文字。實測遮掉 `x`／`arr`／`hello`／`i`／`main`／`f`／`comment`，全都是預設值文字。

### ❌ B AST 節點型別比較——**否決**

`.type === 'x'` 的形式。

**Rationale for rejection**：**它會遮掉真違規。** 實測在 `src/ui/block-registrar.ts` 遮掉了 `cpp_string_declare`、`u_var_declare`、`c_for_loop` 等 14 個——那是 `block.type === '...'`，Blockly 的**積木型別**，而積木型別直接對應概念身分。**這正是 FR-003 要防的失效樣態：護欄改嚴之後把真違規一起濾掉。**

`node.type`（語法樹節點）與 `block.type`（積木）在文字上分不開。想靠變數名判（`node` vs `block`）是啟發式，而 `build-guardrail` 第 6 步明講：

> 「靜態判斷不能下結論，只能排順序。**判準本身可以是對的，把它自動化的第一版仍然會量錯。**」

**後果（必須明說）**：`src/core/lift/lifter.ts:145` 的 `node.type === 'comment'` **仍然被計為違規**。依 FR-002「判不出來算違規」，這是正確的保守結果。

而且**這一筆留著是對的**——見下。

## 決策 3：`lifter.ts` 有一個護欄看不見的、更嚴重的耦合

查證 `lifter.ts:145` 的上下文時發現第 152 行：

```
text: node.text.replace(/^\/\/\s?/, '').replace(/^\/\*\s?|\s?\*\/$/g, ''),
```

**核心層在剝 C 家族的註解符號。** 中立性護欄**完全看不到它**——護欄只找概念身分字串，不找語法。

這代表兩件事：

1. 如果採用遮罩 B，`lifter.ts` 會從違規清單消失，而**它其實比帳面上更耦合**。否決 B 的理由因此多了一條。
2. **FR-012 已經涵蓋它**——「核心層 MUST NOT 再含有任何註解的語法符號」。所以 US2 的搬移範圍是**兩處**，不只產生器。

**這是本功能自己的一個小型「量測工具量錯」實例**：護欄的判定維度（概念身分字串）與它宣稱要治的病（語言耦合）**不是同一個東西**。身分只是耦合的一種形式，語法是另一種，而護欄只看得到前者。這一點要寫進報表的「本護欄不檢測什麼」。

## 決策 4：預期數字，以及為什麼不是規格寫的那個

| 來源 | 筆數 |
|---|---|
| 目前 | 29 |
| 遮罩 A 移除（`types.ts` → `comment`） | −1 |
| 遮罩 C 移除（`block-registrar.ts` → `comment`） | −1 |
| 搬走產生器（`code-generator.ts` → 三筆） | −3 |
| **合計** | **24** |

**規格的 SC-001 寫 ≤23，是錯的。** 它假設 comment 家族六筆全消，而否決遮罩 B 之後 `lifter.ts` 那一筆留著。

**修法是改規格，不是加遮罩。** 為了打到一個先寫下的數字而放寬判定，正是本功能整篇在講的事。SC-001 改為 **≤24**，並記下 `lifter.ts` 那一筆留著的理由。

## 決策 5：搬移的接線方式

**Decision**：語言套件推、核心讀——與 `053-declare-noop-execute` 的 skip 宣告、`054/055` 的 executor 膠囊同形。

**Rationale**：這個形狀在本專案已經用過三次且測試齊備。核心提供一個 `declare*` 入口與一個 `all*()` 讀取函式，語言套件在載入時推進來。

**沒有語言套件時的行為（FR-014）**：MUST NOT 無聲產出空字串。既有的 executor 那次已經踩過——`053` 的教訓是刪掉核心登記處會讓「沒載入語言套件」從無聲變成報錯，而那次 144 個測試一次變紅。這次規模小（三個概念），但行為必須明確：**回退到一個語言中立的預設，或明說沒有語言套件**，二擇一，不得靜默。

**Alternatives considered**：把三個產生器直接複製進 C++ 套件、核心保留一份當 fallback——否決。那是雙重真相，專案有專門的護欄在數它。

# Feature Specification: 指定給一個沒宣告的名字，必須停下來

**Feature Branch**: `127-reject-undeclared-assign`
**Created**: 2026-08-15
**Status**: Draft
**路線圖位置**: 階段 6.7 的「第四個缺口」

## User Scenarios & Testing *(mandatory)*

一個學生打了

```
score = 90;
印出 score
```

**忘了說 `score` 是一個整數。** C++ 拒絕這段程式，而我們**跑完它並印出 90**。

> 🔴 **一個會執行的錯誤程式，教的不是「這裡有錯」，是「這裡沒有錯」。**

而它已經有一個受害者：**第二課花兩段講「宣告不能省」，
而系統本身允許省**——所以課文**繞了路**，避開這個寫法。

### User Story 1 - 少了宣告，程式停下來並說出是哪個名字 (Priority: P1)

學生寫了一個沒有宣告過的名字並指定值，程式**停在那一行**，
訊息說得出**是哪一個名字**。

**Why this priority**: 這是使用者原話「**寫錯還能順利執行就是不合理的**」
在今天**最便宜也最確定**的一個實例——同一個系統對「讀」已經會拒絕，
只有「寫」不會。

**Independent Test**: 跑一段沒有宣告就指定的程式，看它停不停、訊息說什麼。

**Acceptance Scenarios**:

1. **Given** 一段沒有宣告就指定的程式，**When** 執行走到那一行，
   **Then** 停下來，訊息**含那個名字**
2. **Given** 同一件事的「讀」版本（用一個沒宣告的名字），**When** 執行，
   **Then** 訊息**與寫的那一則相同**——⚠️ 同一件事不得有兩種說法
3. **Given** 一段**正常宣告過**的程式，**When** 執行，
   **Then** 一切照舊——🔴 這是本功能唯一可能弄壞既有東西的地方

### User Story 2 - 那道擋牆被拆掉，而理由被寫下來 (Priority: P1)

擋著這個修法的唯一一樣東西，是一支**把這個缺陷寫成規格的測試**。
它被改成斷言**拒絕**，**而新的理由寫在測試裡**。

**Why this priority**: 🔴 **這一次的根因就是「沒有寫理由」。**
那支測試來自最早的地基階段，描述的是**當時的實作**而不是**當時的意圖**
——而三年後沒有人分得出這兩者，於是它變成一道**看起來像決定的擋牆**。

> **一支沒有寫理由的測試，記的是當時的實作，不是當時的意圖。**

改成斷言拒絕而**不寫理由**，等於原地換一道同樣的牆。

**Independent Test**: 讀那支測試，看得出「為什麼是拒絕」而不只是「拒絕」。

**Acceptance Scenarios**:

1. **Given** 那支測試，**When** 有人讀它，
   **Then** 讀得到**為什麼**應該拒絕（不只是「應該拒絕」）
2. **Given** 這條規則哪天要被推翻，**When** 有人來讀，
   **Then** 讀得到**推翻它需要什麼**——而不是只能猜

### User Story 3 - 第二課不必再繞路 (Priority: P1)

第二課把繞路拿掉，**正面教「宣告不能省」，並用系統的回覆證明它**。

**Why this priority**: 🔴 **它是 US1 的消費者**。沒有它，修好的檢查
就是又一個「機制有了沒人接上」——而那件事在這個專案發生過至少四次。

⚠️ 而它同時是**這個修法唯一的使用者證據**：課文從「不能講」變成「講得了」。

**Independent Test**: 一個人照著第二課走完，而新的那一段走得通。

**Acceptance Scenarios**:

1. **Given** 第二課，**When** 有人照著走，**Then** 新的段落走得通
2. **Given** 課文引用的錯誤訊息，**When** 與系統實際輸出比對，
   **Then** **逐字相同**——🔴 不得是作者編的
3. **Given** 課文，**When** 有人讀它，
   **Then** 讀得到**這個檢查是在「跑到那一行」時才發生的**
   ——⚠️ 不得讓學生以為系統會在他打字時就攔住

### Edge Cases

- 🔴 **一個名字在別的地方宣告過，而在這裡被指定** → **必須放行**。
  ⚠️ 這是本功能最可能誤傷的形狀（外層作用域、迴圈外的變數、
  函式參數），而「作用域」在這個專案翻過車
- **指標指向的位置被寫入** → ⚠️ 那條路徑今天有一個「找不到就建立」的分支，
  **它可能是唯一真的需要隱式建立的地方**——必須單獨驗，不得跟著一起改
- **一個名字先被指定、後才宣告** → 停在指定那一行（C++ 也是）
- 🔴 **同一個名字在同一段程式裡被指定兩次而從沒宣告** → 停在**第一次**，
  ⚠️ 而不是「第一次建立、第二次成功」
- **停下來之後，已經印出的東西還在嗎** → 必須在——
  一道會拒絕的檢查必須回答「被拒絕的東西去哪了」

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 對一個**在任何可見範圍內都沒有宣告過**的名字指定值時，
  執行 MUST 停下來。
- **FR-002**: 該訊息 MUST 含那個名字，且 MUST 與「讀一個沒宣告的名字」
  用**同一則**訊息——MUST NOT 另立文案。
- **FR-003**: 名字在**外層可見範圍**宣告過時 MUST 放行。
- **FR-004**: 停下來之前**已經產生的輸出** MUST 保留。
- **FR-005**: 擋著這個修法的那支測試 MUST 改成斷言拒絕，
  且 MUST 在測試中寫下**為什麼**與**推翻它需要什麼**。
- **FR-006**: 指標寫入那條路徑 MUST 被**單獨驗證**，
  結論 MUST 寫下來——不論結論是「一起改」還是「保留隱式建立」。
- **FR-007**: 第二課 MUST 拿掉繞路，正面教這件事，
  且引用的訊息 MUST 與系統實際輸出逐字相同。
- **FR-008**: 🔴 系統 MUST NOT 宣稱「未宣告的指定不能執行」。
  能宣稱的只有「**跑到那一行時會停**」，而該限定 MUST 出現在
  **程式碼、規格、課文**三處。
- **FR-009**: 既有的自動化驗證 MUST 全數通過，
  且既有的量測基線 MUST 一個數字都不變。

### Key Entities

- **名字的可見範圍**：一層一層往外找的查找鏈。
  ⚠️ 今天它對「讀」與「寫」的**收尾行為不同**——讀找不到就拒絕，
  寫找不到就**建立**。本功能讓兩者一致。
- **一課**：說明 ＋ 期望輸出 ＋ 走查。第二課已存在，本功能改它一段。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 「沒宣告就指定」的程式，跑完的比例從 **1/1 降到 0/1**。
- **SC-002**: 因本功能而失敗的既有自動化驗證數 **= 1**，
  🔴 **而那一支必須是斷言此缺陷的那一支**。
  ⚠️ **若大於 1，代表這個修法比量到的貴**——停下來重新評估，不要硬修。
- **SC-003**: 55 段真實情境程式 ＋ 檢定語料的通過數**不變**。
- **SC-004**: 既有量測基線**變動的數字個數 = 0**。
- **SC-005**: 課文引用的訊息與系統實際輸出的**逐字不一致數 = 0**。
- **SC-006**: 🔴 「執行期，不是編輯期」這句限定**出現在 3 個地方**
  ——少一處即為未達成。
- **SC-007**: 指標寫入那條路徑的結論**存在且有證據**
  （不論結論是哪一種）。

## Assumptions

- 🔴 **這是執行期檢查，不是編譯期**。C++ 在編譯時拒絕，我們在**跑到那一行**
  時才停。**一段有這個錯誤而永遠跑不到那一行的程式，仍然會「成功」**
  ——⚠️ 而那不是這個功能失敗，是它的射程。**不得宣稱兩者等價。**
- **爆炸半徑已量過**：注入嚴格版跑全套，只有 1 支失敗。
  ⚠️ 而 SC-002 把它寫成**可否證的條件**——量過不等於不會變。
- **訊息不新增**：沿用「讀」那一則。⚠️ 措辭好不好是另一件事，
  本功能不改善它。
- **第二課的其他段落不動**——只拿掉繞路那一處。
- **不牴觸「殘差補得齊」**：那條講的是「我們還沒長到而程式是對的」，
  這一筆是**使用者寫壞了**，兩者是不同的格子。

## Out of Scope

- 編譯期／編輯期就攔住（那需要另一套機構）
- 型別檢查（大小寫打錯的識別字、用錯運算子那一類）
- 錯誤訊息措辭的改善
- 涵蓋率與假警報的量測（⚠️ 本功能會改變它的分子，所以它排在**之後**）
- 「按執行卻什麼都沒發生」那個介面缺陷
- 課程層級樹、主題設定、任何面板

## 一、🔴 「LED 亮」是新身分還是形態？—— **兩個都不是，它是【參數】**

### 先否決「新身分」，而理由是可以推的

`cpp:led_write` 要五路齊全，而 lift 那一路今天**做不到**：程式碼裡只有
`digitalWrite(ledPin, HIGH)`，要認出「這是 LED」需要關鍵字表——**而那是 ⑤，已拍板延後**。

於是它的 lift 只能 `skipPaths`，而後果**今天剛記過**
（`concepts/降級與認知邊界.md`「降級前的身分——閉環系統的回流」）：

```
學生拉「LED 亮」 → 產出 digitalWrite → 他改了別的地方 → code→blocks
→ 積木變回 digitalWrite　　🔴 【一個 round-trip 之內就侵蝕掉】
```

> **一個 lift 不回來的積木，在雙向系統裡活不過一次同步。**

### 而「形態」也不對

`form: { axis, value }` 的形態要有**驅動**（statement／expression 由位置決定）。
「這根腳位上接的是 LED」的驅動**在程式碼裡**，而那又回到辨識問題。
`BlockOverride` 是 per-topic 的（`cpp-competitive.json` 把 `print` 顯示成 `printf`），
一個 topic 裡給不出六種標籤。

### 🟢 答案：**零件是【接線宣告】的一個參數**

```
真實：  const int ledPin = 13;   ＋   pinMode(ledPin, OUTPUT);
積木：  [接上 (LED ▾) 到腳位 (13)，叫它 (ledPin)]
        └─ 零件種類是【下拉選單】＝ 一個參數，不是六個身分
動作：  [把腳位 (ledPin) 設成 (HIGH)]   ← 既有的 digital_write，不必新做
```

> **位置不是身分，是形態**（既有結論）
> **而零件不是身分，是參數**（本輪）

**為什麼這個切法成立**：
- 🟢 **lift 回得來**：認的是「`const int` ＋ `pinMode` 的配對」這個**結構**，
  不需要關鍵字表。而「接的是什麼零件」從變數名讀——**認不出來就退到一個通用值**，
  ⚠️ **結構不會侵蝕，只有那個標籤會**。那正是 ④「退回原始積木打底」的精確版本。
- 🟢 **符合 Sc2**：積木上的每一格在程式碼裡都有對應（型別、名字、腳位、模式）。
- 🟢 **教學上更對**：學生真的要先接線。而「接線」是硬體課的主題本身，不是記帳。

### ⚠️ 兩個選項的代價（不只講結論）

| | 新身分 `cpp:led_write` | 參數 `cpp:pin_attach{device}` |
|---|---|---|
| 積木長相 | 「LED 亮」最直接 | 多一顆接線積木 |
| lift | 🔴 今天不可能（等 ⑤） | 🟢 認結構，不等 ⑤ |
| 侵蝕 | 🔴 一次同步就沒了 | 🟢 結構穩定 |
| 六個零件 | 6 顆身分 × 動作數 | **1 顆 ＋ 既有動作** |
| 之後要改 | 關鍵字表來了也還是六顆 | 關鍵字表來了 → 標籤更準，**結構不動** |

## 二、`pinMode` 自動長出來——🟢 **它是 UI 行為，不是產生器機制**

查證：概念「宣告需求、而產出在別的位置」**有先例**（`requires: ['<vector>']` → `#include`），
⚠️ **但那個機制只認得鷹架的四段**（`imports`／`preamble`／`entryPoint`／`epilogue`），
而 `pinMode` 要落在**使用者自己的 `setup()` 函式裡**——鷹架完全不認識 `setup`
（Arduino 的 `entryShell: 'none'`，`setup`／`loop` 就是普通的頂層函式）。

🟢 **而 ② 的原文是「自動長出一顆【看得見的】積木」**——那是
**在畫布上插一顆 `pinMode` 積木進 `setup` 積木裡**，是 UI 層的動作。
產生器完全不必知道這件事，**五路保持乾淨**。

⚠️ 而它有一個前提：畫布上要有 `setup` 積木。`.ino` 一定有，而空白畫布沒有
——那時要一併長出 `setup`／`loop`（或提示）。**這一條是實作時的第一個坑。**

## 三、超音波「量距離」值不值得預組 —— 🟢 **7/7**

判準（`draft/2026-08-17-套件積木的粒度與預組.md`）：
> **一組總是一起出現的呼叫，才有資格被預先組好；而「總是」是一個可以數的東西。**

實測（兩份語料合計 40 段，用到 `pulseIn` 的 7 段）：

```
觸發序列（LOW → delayMicroseconds → HIGH → delayMicroseconds → LOW）
   ＋ 距離換算（× 0.034 / 2 或 ÷ 58 或 ÷ 29.1）
都齊的：7／7 = 100%
```

🟢 **而它 lift 回得來**：認的是那組**呼叫樣式**，不是名字——不需要關鍵字表。
⚠️ 而樣式辨識比名字強（`concepts` 已記：**樣式難以巧合**）。

## 四、第 1 批真正剩下什麼

| 零件 | 狀態 |
|---|---|
| **蜂鳴器** | ✅ **第 0 批已完成**——`tone`／`tone_stop` 的標籤已是「在腳位 %1 發出 %2 赫茲」 |
| **LED · 按鈕 · 類比感測** | 🟢 **不需要新概念**——既有的 `digital_write`／`digital_read`／`analog_read` ＋ 接線積木命名 |
| **超音波** | 🔵 新：`cpp:ultrasonic_read`（預組，7/7 證據） |
| **接線** | 🔵 新：`cpp:pin_attach`（device 是參數） |
| **伺服** | ⏸ 第 2 批（物件機制未拍板） |

## 五、概念目錄

### L0：基礎

| 概念 | 語法（產出） | 語義 | 積木輸入 | Layer | 降級路徑 |
|---|---|---|---|---|---|
| `cpp:pin_attach` | `const int ledPin = 13;` ＋ `pinMode(ledPin, OUTPUT);` | 接一個零件到腳位並命名 | 3（零件▾／腳位／名字） | lang-library | `cpp:var_declare_const` ＋ `cpp:pin_mode`（拆回兩顆） |

### L1a：函式與迴圈

| 概念 | 語法（產出） | 語義 | 積木輸入 | Layer | 降級路徑 |
|---|---|---|---|---|---|
| `cpp:ultrasonic_read` | 觸發序列 ＋ `pulseIn` ＋ 換算 | 量距離（公分） | 2（觸發腳／回音腳） | lang-library | 拆回 `digital_write`＋`delay_microseconds`＋`pulse_read`＋算式 |

⚠️ **兩顆的降級路徑都是「拆回組成它的那些既有概念」**——而那正是預組該有的降級：
D1 預組 → D2 **展開成零件**（不是 raw_code）。🔴 那讓 Sc1「認知鷹架可退場」真的成立：
學生後期把它拆開，看到的就是他在網路上會看到的那幾行。

## 六、落點

```
課程清單   pin_attach       → L0（與 pin_mode／digital_write 同關）
           ultrasonic_read  → L1a（與 pulse_read 同關）
工具箱     兩顆都進「腳位與時間」
           ⚠️ 不新開「零件」分類——只有兩顆，而理由與第 0 批不新開「聲音」相同
```

🔴 **而第 1 批【沒有】逼出「零件」這個分類軸**——因為零件變成了參數。
那個軸要等**零件多到接線積木的下拉選單裝不下**才會出現，而那是有訊號可等的。

## 七、需注意的邊界案例

- `pin_attach` 的 lift 要認**兩個相鄰但不同位置**的語句（宣告在頂層、`pinMode` 在 `setup`）
  ——🔴 **這是這一批最難的一段**，而它決定「拆開之後還能不能合回來」
- 學生手動改了變數名 → device 標籤退到通用值，⚠️ **而結構要保住**
- `ultrasonic_read` 的換算常數有三種寫法（`*0.034/2`／`/58`／`/29.1`）——都要認
- 空白畫布上沒有 `setup` 積木時，② 的自動插入要有處置

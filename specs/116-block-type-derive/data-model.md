# Phase 1：資料模型

## 實體

### 積木型別（BlockType）

一個字串，Blockly 用它當積木 registry 的鍵。

**本規格之後它不再是一個獨立宣告的名字，而是從概念身分導出的值。**

```
導出規則：
  預設形態      conceptId 把 ':' 換成 '_'
  非預設形態    再加 '_' + form.value

  cpp:stack_peek                        → cpp_stack_peek
  cpp:var_declare  form.value=expression → cpp_var_declare_expr
  cpp:container_push form.value=stack    → cpp_container_push_stack
```

**不變式**
- I1：同一顆身分的任兩個形態，導出名不得相同
- I2：導出名在**專案宣告的積木**範圍內唯一（使用者上傳的自訂積木不在此範圍）
- I3：導出名只由 `conceptId` 與 `form.value` 決定——**沒有第三個輸入**

### 存檔轉換表（BlockTypeMigration）

`舊積木型別 → 新積木型別` 的**凍結明表**。

**為什麼是明表不是規則**（照既有身分改名表的同一個理由）：
「那一版存在哪些名字」是**歷史事實**。從當下的登錄表推導的話，
往後每一次增刪元件都會悄悄改變這張表——而它要處理的是幾個月前存的檔案。

**不變式**
- I4：表是凍結的——加一顆新元件不得改變任何一筆既有對應
- I5：轉換冪等——新名餵進去仍是新名
- I6：表上沒有的舊型別 → **出聲**，不得靜默丟棄

### 存檔（SavedState）

已存在。本規格新增一個版本（v9 → v10），差別只在**積木狀態裡的型別字串**。

⚠️ **語義樹不動**——身分本來就是對的。這次動的是投影那一側，
而它之所以要遷移，是因為**它被存起來而且是載入時的還原來源**。

## 狀態轉移

```
v9 存檔  ──載入──▶  逐顆積木查轉換表  ──▶  v10 存檔
                          │
                          └─ 查不到 ──▶ 出聲（不吞）
```

⚠️ 兩個管道（localStorage 載入、匯入 JSON）共用同一個升級入口
——**一個轉換點，不是兩份**。

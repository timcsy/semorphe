# Feature Specification: 積木型別從概念身分導出

**Feature Branch**: `116-block-type-derive`
**Created**: 2026-08-11
**Status**: Draft
**路線圖位置**: 階段 6.5 **F1**（2026-08-11 從 draft 升格，見 `knowledge/vision.md` 的 F1 段落）
**設計理由（in-flight）**: `knowledge/draft/2026-08-10-掀出來但還沒做的.md` §二

## ⚠️ 規劃時查證的三件事——都與既有紀錄不同，寫在最前面以免照著錯的前提做

### ① 驗收數字不是 86，是 **153**（而 86 也是真的，只是量的是另一件事）

draft 寫「比 `blockDef.type` 是 86 顆」。2026-08-11 重量，**兩個數字都對，但它們量的不是同一個判準**：

| 判準 | 不同的筆數 |
|---|---|
| 主體不同（兩邊都去掉 `u_`／`c_`／`cpp_` 前綴後比） | **86** ← draft 說的 |
| **嚴格導出**（`type !== conceptId.replace(':','_')`） | **153** ← 本規格要收的 |
| 只差前綴（`cpp:address_of → c_address_of`） | 67 |
| 已經相符 | 33 |

`186 = 33 + 67 + 86`。

> **這一格若不先寫清楚，護欄第一次跑會報 153，而規格說 86——
> 而讀的人會以為護欄壞了。**

兩批的性質不同，因此本規格把它們**分成兩個使用者故事**：
67 筆是機械的（只改前綴），86 筆是**化石**（用了已被淘汰的詞）。

### ② `blocklyState` 從來沒有被遷移過——這會是第一次

draft 寫「`blocklyState` 已經在 v9 的版本鏈裡了（`storage-version.ts` 的 upgrade 有 `blocklyState` 欄位）」。**實查是錯的**：

```
src/core/storage-version.ts:36        SAVED_STATE_FIELDS = { …, blocklyState: 1, … }
                                      ↑ 只是欄位形狀宣告，不是升級步驟
src/core/storage-version.ts:202-219   八個升級函式，每一個都是
                                      N: (raw) => ({ ...raw, tree: 改寫身分(raw.tree, …), version: N+1 })
                                                             ^^^^ 只有樹
```

→ 不是「已經在版本鏈裡所以要付遷移」，而是**這個專案從來沒有寫過任何一次
`blocklyState` 遷移**。沒有先例可抄，成本比 draft 估的高。

### ③ 這件事適用 P8 的例外條款，理由要寫下來

`knowledge/principles.md:113`：

> 「**語義詞彙本身的變更不在此列**（例如 `componentId` 改名）：那動的是真實，
> **沒有東西可以重建它**……這種變更 MUST 附**一次性的轉換**」

積木型別按定義是**投影**，本來不適用。但 `src/ui/app.ts:563` 寫著：

```ts
// 1. Restore blocks FIRST (before level change triggers resync)
this.blocklyPanel?.setState(state.blocklyState)
```

> **一個被存起來、而且載入時當作還原來源的投影，行為上就是真實。**

與 `knowledge/draft/2026-03-11-已知工程待解問題.md:95` 記的那個已修缺陷同形
（「根公理是『唯一真實，各式投影』。而這裡是**投影寫回了真實**」）。

**所以：不可以直接改名不管舊檔。** 一次性轉換是硬性要求，不是可選項。

## User Scenarios & Testing *(mandatory)*

### 使用者是誰

- **學生／老師**：存過檔的人。他們感覺得到的只有一件事——**舊存檔還打得開嗎**。
- **維護者**：要加一顆新元件的人。今天他要想兩個名字，而**沒有任何機制擋得住第三個名字**。

### User Story 1 - 舊存檔照樣打得開 (Priority: P1)

一個學生兩週前存了一份用 `if`、`for`、`vector`、`cout` 的程式。改名之後他重新開啟，
**看到的積木與當初一模一樣**，程式跑起來輸出相同。

**Why this priority**: 這是唯一一個使用者感覺得到的面向。做壞了是資料遺失，
而其他所有故事的價值都建立在「沒有弄壞既有的東西」上。

**Independent Test**: 用一份 v9 存檔（含新舊兩批積木）走完整載入流程，
比對積木清單、語義樹、產生的程式碼三者都與遷移前相同。

**Acceptance Scenarios**:

1. **Given** 一份 v9 存檔，**When** 載入，**Then** 每一顆積木都被認得（沒有任何一顆掉成未知型別）
2. **Given** 同一份存檔，**When** 載入後產生程式碼，**Then** 程式碼與遷移前逐字相同
3. **Given** 同一份存檔，**When** 載入後執行，**Then** 輸出與遷移前相同
4. **Given** 一份已經是新版的存檔，**When** 載入，**Then** 不被重複遷移（冪等）
5. **Given** 一份存檔裡有**未知**的積木型別（不在遷移表上），**When** 載入，
   **Then** 系統**出聲**（可辨識的錯誤或警示），**不得靜默丟棄那顆積木**

### User Story 2 - 只差前綴的那 67 顆收斂 (Priority: P2)

`cpp:address_of` 的積木型別是 `c_address_of`——主體一樣，只有前綴不同。
`u_`／`c_`／`cpp_` 對應「universal／cpp core／cpp std」，
而**命名空間遷移之後 186 顆身分全部是 `cpp:`，那個三分法在身分層已經不存在**。

**Why this priority**: 機械、風險低、可先做完驗證整條遷移管線，再碰高風險的那批。

**Independent Test**: 這 67 顆遷移後，嚴格導出的不符數從 153 降到 86，
且 User Story 1 的五個情境全過。

**Acceptance Scenarios**:

1. **Given** 這 67 顆的任一顆，**When** 檢查其積木型別，**Then** 等於身分把 `:` 換成 `_`
2. **Given** 遷移表，**When** 檢視，**Then** 這 67 筆每一筆都看得見（凍結明表，不是規則）

### User Story 3 - 86 顆化石詞彙收斂 (Priority: P3)

`cpp:stack_peek` 的積木型別是 `cpp_stack_top`——而 `top` 是命名整理那次
**從封閉詞彙裡換掉**的詞（`peek` 才在表上）。同類還有
`cpp:loop_count → u_count_loop`（主體與操作順序相反）、
`cpp:literal_number → u_number`（積木名是身分名的截斷）。

> **積木型別保存著命名整理之前的整套舊命名——它是那次改名的化石層。**
> 「亂」的準確說法不是隨機，是**兩個時間層疊在一起**。

**Why this priority**: 收益最大（消滅雙重命名），風險也最高（86 筆、涉及舊詞彙）。
放在管線驗證過之後做。

**Independent Test**: 這 86 顆遷移後不符數降到 0，且 User Story 1 的五個情境全過。

**Acceptance Scenarios**:

1. **Given** 全部 186 顆積木，**When** 檢查，**Then** 嚴格導出的不符數為 **0**
2. **Given** 任何一顆積木型別，**When** 用命名整理的同一套判準檢查，
   **Then** 「操作詞不在封閉詞彙」與「裸的函式庫名」兩項都是 **0**
   （今天分別是 24 與 63，而身分那邊兩項都已經是 0）

### User Story 4 - 第三個名字進不來 (Priority: P2)

維護者加一顆新元件時**只需要想一個名字**。若他手寫了一個不導出的積木型別，
**檢查會變紅並指名是哪一顆**。

**Why this priority**: 沒有這一條，這次清償會在幾週內重新長回來——
而那正是這批化石當初形成的方式。

**Independent Test**: 故意把一顆積木型別改成不導出的名字，檢查必須報出**那一顆**；
把它改回來，檢查必須不再報（兩個方向都要釘）。

**Acceptance Scenarios**:

1. **Given** 一顆積木型別不等於其身分的導出名，**When** 跑檢查，**Then** 變紅並指名該顆
2. **Given** 全部符合，**When** 跑檢查，**Then** 通過且**不亂報**
3. **Given** 檢查本身，**When** 檢視其斷言，**Then** 沒有任何一句是
   「缺陷計數大於零」形式的錨點（那種錨點會在成功的那天變紅）

### Edge Cases

- **同一顆身分有多個積木形態**（多形態機制允許 `form: { axis, value }`）：
  導出名會相同 → **必須決定形態之間如何區分**，否則會產生重複的積木型別
- **未知積木型別**：遷移表上沒有的型別出現在舊存檔裡 → 出聲，不靜默丟棄（US1 情境 5）
- **積木型別出現在非字串字面的位置**：裸的物件鍵、正則、模板字串、型別聯集、
  測試標題、JSON 的值位置、拿形狀當判斷——**七種形狀已知**，改名前必須逐一掃過
- **`type` 這個欄位名長在多個型別上**：Blockly 的 block、blockDef、語義節點都有 `type`
  ——腳本改名時型別檢查看不到，這是最高風險
- **匯出的 JSON 檔在使用者手上**：不只 localStorage，還有匯出匯入的檔案

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓每一顆積木的型別**從其概念身分導出**（`:` 換成 `_`），
  不得有第二份獨立的命名。
- **FR-002**: 系統 MUST 提供一次性的存檔轉換，讓改名前存的檔案載入後仍然完整
  ——**這是 P8 例外條款的硬性要求**（理由見本文件開頭 ③）。
- **FR-003**: 存檔轉換表 MUST 是**凍結的明表**（每一筆列出來），不是從當下登錄表推導的規則。
  理由與既有的身分改名表相同：「那一版存在哪些名字」是**歷史事實**，
  從當下推導的話，往後每一次增刪元件都會悄悄改變這張表。
- **FR-004**: 存檔轉換 MUST 是**冪等**的——已轉換過的存檔再載入不得被二次改寫。
- **FR-005**: 載入時遇到**轉換表上沒有的**積木型別，系統 MUST 出聲，**不得靜默丟棄**。
- **FR-006**: 系統 MUST 有一條機械檢查，量「積木型別不等於其身分導出名」的筆數，
  且該數收**硬性零**（不是棘輪）。
- **FR-007**: 該檢查的**第一次執行必須是紅的**，並**逐項指名**違規的積木；
  基線在修完之後才產生。
- **FR-008**: 該檢查 MUST 同時釘住兩個方向：故意壞掉的輸入**會報**、正確的輸入**不亂報**。
- **FR-009**: 該檢查的自我否證聲明 MUST NOT 錨在「缺陷計數大於零」上
  ——那種錨點會在這條規範成功的那天變紅。錨要放在「工具吃到輸入沒有」上。
- **FR-010**: 同一顆身分若有多個積木形態，系統 MUST 有明確且可檢查的區分方式，
  不得產生重複的積木型別。
- **FR-011**: 改名 MUST 先在**已膠囊化的那批**（今天 10 顆，其中 5 顆不導出）上完成並驗證，
  再推向其餘積木——**分兩段，不是一次全推**。
- **FR-012**: 專案 MUST 保留一份改名前的真實存檔作為回歸樣本，
  讓「舊檔還打得開」這件事**每次跑測試都被驗證**，而不只在改名當天被人工確認一次。

### Key Entities

- **概念身分**：一顆元件的唯一名字（`cpp:stack_peek`）。**這是真實。**
- **積木型別**：Blockly 用來識別一種積木的字串（`cpp_stack_top`）。
  **本規格之後它不再是一個獨立的名字，而是身分的導出。**
- **存檔**：包含語義樹、積木狀態、程式碼等欄位。
  ⚠️ **積木狀態是載入時的主要還原來源**——這是本規格必須附一次性轉換的原因。
- **存檔轉換表**：舊積木型別 → 新積木型別的凍結明表。
- **封閉詞彙表**：命名整理那次定下的操作詞清單。身分已全部符合，積木型別還沒有。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 積木型別不等於身分導出名的筆數：**153 → 0**（硬性零）。
- **SC-002**: 用命名整理的同一套判準量積木型別：「操作詞不在封閉詞彙」**24 → 0**、
  「裸的函式庫名」**63 → 0**（今天身分那邊兩項都是 0）。
- **SC-003**: 一份改名前存的存檔，載入後**積木清單、語義樹、產生的程式碼、執行輸出
  四者全部與改名前相同**——而且是在瀏覽器裡實測過，不只測試綠。
- **SC-004**: 該存檔留在專案裡當回歸樣本，之後每次跑測試都會驗證它。
- **SC-005**: 新的機械檢查第一次執行是**紅的**，逐項指名，且修完之後基線註明
  下降原因是「**因為實作了**」而不是「因為重新分類」。
- **SC-006**: 全套測試綠。

### 明確不做

- `u_`／`c_`／`cpp_` 前綴與概念宣告的 `layer` 欄位**差 2 顆**那件事
  ——那是**分類**問題，不是命名問題。
- 積木「長相」的規範（欄位順序、顏色、形狀）——那需要先有一套設計語彙，而那要人先給內容。
- 剩下 167 顆元件的膠囊搬家本身。

## Assumptions

- **導出規則是 `:` → `_`**，因為已膠囊化的 5 顆已經在用它
  （`cpp:queue_back → cpp_queue_back`），是**已被驗證的形狀**而非新發明。
- **前綴 `u_`／`c_`／`cpp_` 的資訊不需要保留**：它對應的三分法在身分層已被命名空間取代。
  若之後需要「這顆屬於哪一層」，概念宣告的 `layer` 欄位才是該問的地方。
- **只有 localStorage 與匯出檔兩個存檔管道**，沒有第三個尚未發現的持久化路徑。
  （這一條若不成立，遷移會漏——實作時要驗證。）
- 「化石」那 86 筆**沒有一筆是刻意設計的差異**。若實作時發現某一筆的舊名有理由存在，
  那是一個發現，要記下來而不是硬改。

## ⚠️ 要套用的既有教訓（實作時逐條檢查）

| 教訓 | 怎麼套 |
|---|---|
| **身分不只以字串字面出現——而工具只看得到字串字面**（七種形狀：裸的物件鍵／正則／模板字串／型別聯集／測試標題／JSON 的值位置／拿形狀當判斷） | 改名前先問「**這個識別字有幾種不以字串字面出現的方式**」，不是先問「有幾處」。七種形狀逐一掃 |
| ⚠️ **最高風險**：同一個欄位名長在三個不同型別上時，腳本改名一定會錯——而型別檢查看不到（那次**回退了 121 個檔**） | `type` 在 Blockly／blockDef／語義節點上都有。→ **FR-011：先只改膠囊裡的 5 顆，驗證形狀，再推其餘** |
| **趁還沒有版本的時候改名是免費的** | **這裡不免費**，已在 v9。所以 FR-002／003／004 是硬要求 |
| **第一次跑必須是紅的**（先跑、確認紅、逐項指名、修好、最後才產基線） | FR-007。先產基線的話違規會被寫進基線變成「已知」，而**你永遠不會知道它們曾經存在** |
| **重構後開瀏覽器實測** | SC-003。存檔遷移**測試綠不代表使用者看到的是對的** |
| **模板字串組出來的身分，掃描器看不到**（上一輪剛付過代價：兩顆概念的產生器從未存在，而 35 條護欄全部看不見） | 掃積木型別時同樣要問這一句 |
| ⚠️ `component-rename` skill 是為**身分**改名寫的 | 用它之前先確認步驟表適用；**不適用就記下差異**，那是該 skill 的下一次修正 |

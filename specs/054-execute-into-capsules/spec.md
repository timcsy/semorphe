# Feature Specification: 執行那一路搬回它的模組——膠囊缺的那面牆

**Feature Branch**: `054-execute-into-capsules`

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "階段 6.5 P2 前半：execute 路搬進膠囊，先搬整檔可搬的四個。"

---

## 為什麼做這個

語言套件的模組已經有固定的形狀。每個標準函式庫模組的目錄長這樣：

```
std/string/
  concepts.json   ← 語義：這個概念是什麼
  blocks.json     ← 投影：它長什麼樣
  generators.ts   ← 產生程式碼那一路
  lifters.ts      ← 辨識程式碼那一路
  ??????          ← 執行那一路在哪？
```

**五條路裡有四條住在模組裡，只有「執行」那一條住在核心層。**

專案的原則要求每個概念都要有完整的五條路。而「模組缺一面牆」正是那條原則在檔案層級的樣子——不是要不要搬的問題，是那個模組本來就少一片。

實測（2026-08-06）：核心層的語言耦合剩 **174 筆**，其中 **134 筆（77%）在執行子系統**。

而其中有一部分是**整份都可以搬的**：

| 執行器檔案 | 語言專屬 | 性質 |
|---|---|---|
| 字串 | 27 筆 | **整份可搬** |
| 容器 | 20 筆 | **整份可搬**（涵蓋五個模組） |
| 指標 | 8 筆 | **整份可搬**（語言核心，非標準函式庫） |
| 數學 | 3 筆 | **整份可搬** |
| 其餘八個檔 | 43 筆 | 通用與語言專屬**混住**，要逐個判斷 |
| 執行引擎本體 | 33 筆 | 已知缺口清單 + 未歸類的內嵌執行器 |

**這個功能只做「整份可搬」那 58 筆。** 混住的那八個檔是判斷題不是搬運題，風險不同量級。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 拿掉 C++ 之後，執行引擎還認得出自己 (Priority: P1)

維護者要能回答：「把 C++ 語言套件整個拿掉，核心還剩什麼？」

目前答案是「核心裡還躺著 174 筆 C++ 專屬的概念身分」。這個故事拿掉其中 58 筆。

**Why this priority**：這是整個階段插隊到語言擴充之前的**原始理由**——第二個語言會繼承這些耦合。

**Independent Test**：搜尋核心層，那四份執行器涉及的概念身分不再出現。

**Acceptance Scenarios**：

1. **Given** 核心執行子系統，**When** 搜尋字串／容器／指標／數學相關的概念身分，**Then** 找不到
2. **Given** 語言耦合的量測，**When** 執行，**Then** 數字下降且**下降幅度可歸因到具體概念**
3. **Given** 那四份執行器，**When** 檢視它們的新位置，**Then** 每一份都與同模組的其他四條路並列

---

### User Story 2 - 搬完之後，執行結果一模一樣 (Priority: P1)

搬移最容易出的錯是**無聲漏掉**：某個概念的執行器在搬運途中掉了，而測試剛好沒覆蓋到它。

**Why this priority**：與 US1 並列。**搬移的價值全部建立在「行為沒變」上**——變了的話這就不是重構，是改行為。

**Independent Test**：比對搬移前後「執行引擎認得哪些概念」這個集合。

**Acceptance Scenarios**：

1. **Given** 搬移前的概念集合，**When** 搬移後再取一次，**Then** **兩個集合完全相同**——這比逐一比對輸出更直接，而且漏一個就會現形
2. **Given** 任一原本能執行的程式，**When** 搬移後執行，**Then** 輸出完全相同
3. **Given** 五路完備性的量測，**When** 執行，**Then** 執行那一欄的「缺」**沒有增加**——它對這種漏失最敏感

---

### User Story 3 - 「忘了載入語言套件」要當場說清楚 (Priority: P2)

搬移會擴大一個既有的相依：**執行 C++ 概念之前必須先載入 C++ 語言套件**。

那個相依是刻意的（核心不該認識任何語言概念），但它現在會影響更多地方。上一輪同類改動讓 144 個測試一次變紅，而失敗訊息只說「未知概念」——**看不出真正的原因是沒載入**。

**Why this priority**：低於前兩者，因為它不改變任何正確路徑的行為。但少了它，下一個人會在一個看不懂的錯誤訊息前面卡很久。

**Independent Test**：在沒有載入語言套件的情況下執行一個語言概念，檢查錯誤訊息。

**Acceptance Scenarios**：

1. **Given** 沒有載入任何語言套件，**When** 執行一個語言專屬概念，**Then** 錯誤訊息**說得出「可能是沒有載入語言套件」**，不只是「未知概念」
2. **Given** 已載入語言套件，**When** 執行同一個概念，**Then** 正常執行，訊息不出現

---

### Edge Cases

- **一份執行器涵蓋多個模組**（容器涵蓋五個）——要拆進各自的模組，不得整份塞進其中一個
- **概念不屬於任何標準函式庫模組**（指標是語言核心）——歸語言核心，不硬塞進某個模組
- **執行器之間互相呼叫**——搬移後仍要能呼叫，不得因為換了位置而斷掉
- **同一概念在搬移前後被註冊的次數改變**——那是重複註冊，已有量測在看，不得上升
- **搬移後某個模組沒有被載入**（使用者的程式沒用到該標準函式庫）——它的概念本來就不該被執行到；若被執行到，回報未知概念是正確行為

## Requirements *(mandatory)*

### Functional Requirements

**搬移（US1）**

- **FR-001**: 字串／容器／指標／數學四份執行器 MUST 搬進語言套件
- **FR-002**: 每一份 MUST 與同模組的其他路徑並列——模組的五面牆要齊
- **FR-003**: 涵蓋多個模組的那一份 MUST 依概念拆開，MUST NOT 整份塞進單一模組
- **FR-004**: 不屬於任何標準函式庫模組的概念 MUST 歸語言核心
- **FR-005**: 語言耦合的量測 MUST 下降，且下降幅度 MUST 可歸因到具體概念

**行為不變（US2）**

- **FR-010**: 搬移前後「執行引擎認得哪些概念」的集合 MUST 完全相同
- **FR-011**: 任一原本能執行的程式 MUST 產生完全相同的輸出
- **FR-012**: 五路完備性中執行那一欄的「缺」MUST NOT 增加
- **FR-013**: 同一概念被註冊的次數 MUST NOT 增加

**可診斷（US3）**

- **FR-020**: 未載入語言套件而執行語言概念時，錯誤 MUST 提示「可能是沒有載入語言套件」
- **FR-021**: 已載入時該提示 MUST NOT 出現

**回歸保護（全域）**

- **FR-030**: 既有測試 MUST 全數維持通過
- **FR-031**: 七項既有量測中，語言中立性 MUST 下降，其餘 MUST NOT 上升

### Key Entities

- **模組膠囊**：一個概念群的完整住所——語義、投影，以及五條路。**缺一面牆的膠囊不是膠囊**
- **執行那一路**：五條路中唯一還住在核心層的
- **整份可搬**：一份執行器裡的概念**全部**是語言專屬的，不需要逐個判斷
- **混住**：通用概念與語言專屬概念在同一份檔案裡。**這個功能不碰它們**——那是判斷題，不是搬運題

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 語言耦合 **174 筆 → ≤120 筆**
- **SC-002**: 核心執行子系統少掉四份執行器檔案
- **SC-003**: 搬移前後執行引擎認得的概念集合**完全相同**——一個都不能少
- **SC-004**: 任一原本能執行的程式輸出完全相同
- **SC-005**: 五路完備性的執行欄「缺」未增加；重複註冊未增加
- **SC-006**: 既有測試全數通過；其餘六項量測未上升
- **SC-007**: 未載入語言套件的錯誤訊息說得出可能原因——目前只說「未知概念」

---

## Assumptions

- **模組的既有形狀是正確的落點**，不需要新的目錄結構。四條路已經住在那裡，第五條照辦。
- **「整份可搬」的判準是實測的比例**（語言專屬佔該檔 ≥90%），不是印象。四份分別是 100%／100%／100%／100%。
- **搬移途中的風險是漏失，不是衝突**。因此主要防線是「概念集合完全相同」這個斷言，而不是逐一比對輸出——後者漏一個也不會現形。
- **「沒載入語言套件」的相依會擴大，但範圍已量過**：目前有 3 個測試檔建立執行引擎卻沒載入語言套件。這個數字在上一輪同類改動後已大幅下降。
- **不引入新的相依。**

---

## Out of Scope（明確排除）

- ❌ **八個混住的執行器檔**——要逐個判斷通用 vs 語言專屬，風險與這一刀不同量級
- ❌ **執行引擎本體剩的 33 筆**——已知缺口清單要等相關功能實作或另尋出路；未歸類的內嵌執行器要先決定歸屬
- ❌ **辨識那一路的搬移**——它的前置還沒做完
- ❌ **目錄結構定案、模組格式定案**
- ❌ **改變任何執行行為**——這是純搬移

---

## Dependencies

- **前置**：上一輪確立的接線方式（語言套件推、核心讀）；七條量測作為回歸基準
- **知識地基**：專案原則的「四項獨立性」與「五路完備性」；決策紀錄「清償從搬檔案改為把清單換成宣告」——那條明說搬移仍然要做，只是先做了別的；教訓「與其偵測錯誤，不如換一個讓錯誤無法被表達的形式」
- **解鎖**：混住檔案的拆分、第二個語言

---

## Risks & Mitigations

| 風險 | 緩解 |
|---|---|
| **搬移途中無聲漏掉某個概念** | FR-010 的集合比對是主防線——**漏一個就現形**。逐一比對輸出漏一個不會現形，所以不當主防線 |
| **「沒載入語言套件」的錯誤擴散且看不懂** | US3 整個故事。範圍已量過（3 個檔），且 FR-020 要求訊息說得出可能原因 |
| **涵蓋多模組的那份被整份塞進一個模組** | FR-003 明訂要拆。塞在一起的話，使用者只用其中一個標準函式庫時會載進另外四個的執行器 |
| **搬完發現某些概念其實不屬於任何模組** | 那是分類資訊，不是失敗。歸語言核心（FR-004），並記錄下來——它是下一刀的輸入 |

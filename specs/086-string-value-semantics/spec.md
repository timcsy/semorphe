# Feature Specification: 六支「不知道為什麼停用」的測試，追出四個疊在一起的缺陷

**Feature Branch**: `086-string-value-semantics` ｜ **Created**: 2026-08-06

## 為什麼做這個

缺陷帳裡有六支標成 `[UNVERIFIED]` 的 todo——**連停用理由都不知道**。

那個標記本身是誠實的（承認不知道，而不是編一個理由）。而它也意味著：
**沒有人查過它們**。

## 追查方式：寫程式、用真編譯器定期望值、餵進直譯器

| 缺陷 | 症狀 |
|---|---|
| 字串宣告**忽略初始值** | `string s = "abc"` 之後 `s` 是 `""` |
| 比較一律走數值轉換 | 兩個字串都變 0 → `==` **恆真**、`!=` **恆假** |
| `push_back` 讀錯子槽 | 完全沒作用，而且不出聲 |
| 字元字面掉 char 型別 | `'x'` 串接成 `"120"` |

**四個都是靜默的**：沒有錯誤訊息、沒有例外，輸出看起來像一段跑完的程式。
那正是它們當初被停用時「不知道為什麼」的原因——**症狀離現場很遠**。

## 第一個是根因，一修好就解掉三個症狀

字串沒有初始值 → `length()` 回 0、`substr()` 回空字串、`stoi()` 型別不符。
**三個看起來是三個 bug，其實是一個。**

## 第三個是 076 種下的，而護欄抓不到

076 把 `s.push_back(c)` 從通用容器版導到字串專屬版時，**辨識器放進 `value`
子槽，而字串專屬的執行器讀 `char`**——於是那個方法完全沒作用。

第十條護欄（宣告的子節點名沒有人讀）**抓不到這種**：它查「有沒有人讀」，
不查「**讀對不對**」。那條邊界本來就寫在它的「不檢測什麼」裡——
**現在有了一個真實的實例。**

## Requirements

- **FR-001**: 字串宣告 MUST 讀初始值
- **FR-002**: 字串比較 MUST 比內容，且 MUST 驗**不相等**——只驗相等的話「一律
  相等」也會過
- **FR-003**: 數字比較 MUST NOT 被影響
- **FR-004**: `push_back` MUST 真的接上字元
- **FR-005**: 字元字面 MUST NOT 變成數字碼
- **FR-006**: 期望值 MUST 由**真的編譯器**決定

## Success Criteria

- **SC-001**: 只有名字的測試 **46 → 40**
- **SC-002**: 四個修正各有正反測試
- **SC-003**: 既有測試全數通過

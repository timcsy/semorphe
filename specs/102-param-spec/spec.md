# Feature Specification: 參數規格化——讓「這顆元件有哪些參數」變成一份會被讀、會出聲的規格

**Feature Branch**: `102-param-spec`

**Created**: 2026-08-08

**Status**: Draft

**路線圖位置**: 階段 6.5 的 **C1**（A／B／C3／E 已完成，C2 延後，D／F 在後）

---

## ⚠️ 這份規格的形狀：**消費者先於宣告**

第一項任務**不是**改 124 顆宣告，是**把消費者的判準做可信**。

理由是這個專案最貴的一課，`concepts/執行機構.md`「機制有了，沒人接上」目前有**七個實例**：

| 機制 | 發現時的採用率 |
|---|---|
| `skipPaths` | **0 / 175** |
| `abstractConcept` | 33 / 131 |
| `block-input-names` | 7 / 77 |
| `introduces_scope` | **0 / 4** |
| 辨識脈絡的型別追蹤 | **0 呼叫者** |
| `buildIoCategoryContents` | 只有它自己的測試在叫 |
| **CI 跑測試** | **完全沒有**（2026-08-08 才接上） |

> **把 124 顆宣告寫得漂漂亮亮而沒有任何程式碼讀它，就是第八個。**
> 那會讓「124 → 0」變成一個刷出來的數字——`history/018`「用宣告刷數字」。

所以驗收**不是**「規格存在」，是「**規格被讀，而且讀出了東西**」。

---

## 現況（實測 2026-08-08）

- 元件 **177** 顆，其中 **124 顆**宣告了 `properties`，而型別側**全部**是 `string[]`——只有名字
- 不同的屬性名共 **54 個**：`name` 43 次、`obj` 30 次、`type` 16 次…而 **30 個只出現一次**
- **實例側幾乎全是字串**（177 顆裡唯一的例外是 `cpp_include.local` 的布林）

### 消費者的指涉物已經量出來，而量測本身還不可信

靜態比對「產生器／執行器**讀了**哪些屬性」vs「宣告**列了**哪些」→ **17 顆對不上**。
手動查證確認為真的兩筆：

| | 證據 |
|---|---|
| `var_declare.init_style` | 產生器用它分支（`core/generators/declarations.ts:30`），宣告沒列 |
| `array_declare.size` | 執行器讀它（`interpreter/executors/arrays.ts:16`），宣告沒列 |

⚠️ **而同一支掃描的自我驗證當場失敗**：它把 `print.value` 報成違規，查證後那行
`properties.value` 屬於 `g.set('cpp_define')`（`generators/statements.ts:248`）——大括號配對還在漏。

> **判準不準的話，那 17 筆裡混著真假，而修的人會去改一批沒問題的宣告。**

## User Scenarios & Testing

### User Story 1 — 宣告與實際使用對不上時會出聲 (Priority: P1)

維護者改了一個產生器，讓它讀一個新的參數，**而忘了更新宣告**。
今天沒有任何東西會叫；那顆元件的規格從此是錯的，而它看起來完全正常。

**Why this priority**：這是**規格的消費者**——沒有它，這個功能只是把 124 個空欄位填滿。

**Independent Test**：對照「程式碼讀的參數」與「宣告列的參數」，指名對不上的。

**Acceptance Scenarios**：

1. **Given** 一顆元件的產生器讀了宣告裡沒有的參數，**When** 跑檢查，**Then** 指名元件、參數名、檔案行號
2. **Given** 判準跑在已知答案的樣本上，**When** 檢查，**Then** `var_declare.init_style` **必報**、`array_declare.size` **必報**、`print.value` **必不報**
3. **Given** 宣告了一個**沒有任何程式碼讀**的參數，**When** 跑檢查，**Then** 報出來——那多半是改名時留下的殘骸

---

### User Story 2 — 參數的種類能生出真的檢查 (Priority: P1)

一顆元件宣告 `operator` 是「可列舉的運算子，範圍是 `+ - * / %`」。
有人產出了一個 `operator: "**"` 的節點 → **當場知道**。

**Why this priority**：這是「規格」與「名字清單」的分界線。
一份說不出「什麼值是錯的」的規格，加了也沒有人會讀。

**Independent Test**：合成一個違反種類的實例，確認被報出。

**Acceptance Scenarios**：

1. **Given** 一個宣告為可列舉的參數，**When** 實例帶了範圍外的值，**Then** 出聲
2. **Given** 一個宣告為識別字的參數，**When** 實例帶了空字串，**Then** 出聲
3. **Given** 一個合法的實例，**When** 檢查，**Then** **不出聲**——會亂叫的檢查很快就被忽略

---

### User Story 3 — 加一顆元件時，規格是宣告的一部分 (Priority: P2)

維護者新增元件。他寫參數規格時**被迫回答**「這個參數是什麼種類」，
而不是丟一個名字進陣列。

**Why this priority**：這是這個功能的長期價值，但它要等前兩項成立才有意義。

**Acceptance Scenarios**：

1. **Given** 一顆新元件只寫了參數名沒寫種類，**When** 跑檢查，**Then** 出聲
2. **Given** 一顆新元件的規格完整，**When** 跑檢查，**Then** 通過

## Requirements

### 消費者（先做，且必須先紅）

- **FR-001**: MUST 對照「程式碼實際讀的參數」與「宣告的參數」，雙向都報（讀了沒宣告／宣告了沒人讀）
- **FR-002**: 違反時 MUST 指名**元件 ＋ 參數名 ＋ 檔案行號**——只說「有 N 筆」修不了
- **FR-003**: 判準 MUST 先在**已知答案的樣本**上驗過，且該驗證 MUST 是一支會紅的測試
- **FR-004**: 消費者第一次跑 MUST 是紅的

### 參數規格

- **FR-005**: 每個參數 MUST 宣告**語義種類**，MUST NOT 只宣告 JS 型別
- **FR-006**: 種類詞彙 MUST 從實測的 54 個屬性名導出，MUST NOT 憑空發明
- **FR-007**: 每個種類 MUST 至少生得出一條**可能失敗**的檢查——生不出來的種類不該存在
- **FR-008**: 型別側 MUST 改名為參數規格；**實例側 MUST NOT 改動**

### 分批

- **FR-009**: MUST 先做一小批（`var_declare` 家族六顆）並確認消費者會叫，才展開到 124 顆
- **FR-010**: 展開之前 MUST 評估是否該 skill 化——同一種宣告改動要重複 124 次

### 不得退步

- **FR-011**: MUST NOT 動存檔：`CURRENT_VERSION` 不變
- **FR-012**: 全套測試 MUST 綠；既有 22 條護欄 MUST NOT 上升；**CI MUST 綠**

## Success Criteria

- **SC-001**: 參數欠規格 **124 → 0**
- **SC-002**: 消費者**指名它抓到的真違規**（至少含 `var_declare.init_style`、`array_declare.size`），而 `print.value` 這類假報 **0**
- **SC-003**: 每一個種類都有一支「合成違規 → 必報」與「合成合法 → 必不報」的雙向測試
- **SC-004**: 小批六顆做完時，消費者的報告**有變化**——沒有變化代表它沒在讀規格
- **SC-005**: `CURRENT_VERSION` 不變；全套綠；22 條護欄無一上升；CI 綠

## Key Entities

### 參數規格（型別側，取代 `properties: string[]`）

```
名稱      這個參數叫什麼
種類      語義種類（見下）
必填      沒有它這顆元件就不完整嗎
預設值    沒給的時候用什麼
```

### 語義種類——**從實測導出**

| 種類 | 實測的屬性名（節錄） | 它生得出什麼檢查 |
|---|---|---|
| **識別字** | `name`(43)、`obj`(30)、`var_name`、`class_name`、`alias`、`ns`、`method` | 不得為空；必須是合法識別字 |
| **型別運算式** | `type`(16)、`return_type`(8)、`target_type`(5)、`key_type`、`value_type`、`type1/2` | 不得為空；**這裡是 `long long` 被截斷那條債的所在** |
| **可列舉** | `operator`(6)、`position`、`inclusive`、`func` | **值必須在宣告的集合裡** ← 最強的一條 |
| **字面值** | `value`(4)、`char`、`text`、`brief`、`code`、`format`、`header` | 只驗存在——內容是使用者的資料 |
| **計數** | `rows`、`cols` | 必須是非負整數 |

⚠️ **這張表是起點不是結論**：54 個屬性名裡有 30 個只出現一次，
歸類要逐筆附證據（哪顆元件、產生器怎麼用它），不是憑名字猜。

## Out of Scope

- **實例側（`SemanticNode.properties`）完全不動**——只給宣告規格，存檔裡的樹一個位元都不改
- **C2 資訊軸**（已延後：今天沒有消費者）
- **D 命名空間遷移**（componentId 的**值**改動 ＋ 存檔轉換）
- **F 膠囊搬家**
- **真瀏覽器冒煙測試**（另一個決定，需要人拍板 Playwright 成本）
- **`params` 這個實例側名字**——那要等實例側動的時候

## Assumptions

- **型別側改名是順帶的，不是額外的**：`concepts/元件.md:213` 逐字寫著 `properties`
  **同名異義**（型別側 `string[]`、實例側 `Record`），而型別側反正要重寫。
  實例側不動，所以同名異義是**順帶消失**的。
- **「程式碼讀了哪些參數」可以靜態判定**：實測 `node.properties.X` 與 `node.properties['X']`
  兩種形式即可涵蓋。⚠️ 但**區塊切割是難點**——現有掃描就是在這裡漏的。
- **六顆小批具代表性**：`var_declare` 家族涵蓋識別字、型別運算式、以及待決的修飾詞問題。

## Risks & Mitigations

| 風險 | 來源 | 緩解 |
|---|---|---|
| **124 顆填成空殼、沒人讀** | 「機制有了沒人接上」七個實例 | **消費者先做、先紅**；SC-002 驗它抓到什麼而非它存在 |
| 判準不準 → 改到沒問題的宣告 | `print.value` 現在就是現成的假報 | FR-003 已知答案樣本，且是會紅的測試 |
| 種類設計成 JS 型別 → 沒有指涉物 | 實例側幾乎全是 string | FR-006 從實測導出；FR-007 生不出檢查的種類不該存在 |
| 一次改 124 顆，錯了難回頭 | — | FR-009 六顆小批先驗 |
| 動到存檔 | — | FR-011 `CURRENT_VERSION` 列入驗收 |
| 歸類憑名字猜 | 30 個屬性名只出現一次 | 逐筆附證據（哪顆元件、產生器怎麼用） |

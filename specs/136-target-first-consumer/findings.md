# Findings：目標第二刀撞到的坑

**日期**：2026-08-17　⚠️ 含「**因為知道答案而跳過的**」。

---

## 一、🔴 一次誤診，而它是本輪最貴的產出

**症狀**：開瀏覽器選「C 語言教學」，產出第一行仍是 `#include <iostream>`
（而第四行是 `printf`——所以風格切換是生效的）。積木區也顯示
`引入函式庫 iostream（輸入輸出）`。

**我的判定**：「`cpp:program` 的鷹架路徑會過濾掉**它自己補的** include，
而樹裡已經有一顆顯式的 `cpp:include` 節點時，走的是元件自己的 `generate`，
**那裡沒有人問過風格**。」——聽起來完全成立，而且與 `history/072`§三
「兩條產出路徑」是同一族。我照這個判定改了 `include/generate.ts`。

**而它重現不出來**：

```
build 產物   沒寫 include → stdio.h      寫了 include → stdio.h
全新 dev     沒寫 include → stdio.h
             ↑ 兩者都【沒有】我的修正
```

`cpp:include` 節點的 `header` 屬性**本身就被改寫成 `stdio.h`** 了，
那顆元件的 `generate` **從來沒看到過 `iostream`**。

**真正的原因**：那個 dev server 是我在**好幾個編輯之前**啟動的，HMR 沒跟上。

> 🔴 **一個開著沒關的 dev server，會讓「開瀏覽器實測」測到一個不存在的世界。**

⚠️ 而這**反過來限縮了** `experience`「重構後開瀏覽器實測」那條教訓：
**開瀏覽器只有在 server 是【改動之後】啟動的時候才算數。**
上一輪（spec 134）它救了人，這一輪它**製造了一個假缺陷**——
而假缺陷比沒抓到更貴，因為我為它寫了程式碼。

**處置**：修正**已還原**（它是死碼）。e2e 那一支**留著**，
而檔頭改成誠實的說法：它釘的是一條**本輪之前就成立**的契約。

## 二、🔴 而第一次注入證明也是假的——同一個病換了個地方

要驗那個「修正」有沒有用，我把它拿掉再跑 e2e——**綠的**。
我當時以為那代表測試沒抓到。

真正的原因：`playwright.config.ts` 的 `reuseExistingServer: !process.env.CI`
——**preview server 還開著，服的是上一次的 build**。

> **一份 `reuseExistingServer` 的設定，會讓注入證明測到舊的產物。**

⚠️ 而它與第一坑是**同一個形狀的兩次**：都是「**我以為我在測現在的程式碼**」。
→ 判準：**注入證明之前先殺掉 server**，或看建置有沒有真的跑。

## 三、判準只涵蓋一半——而那一半是我沒想到的一半

計畫寫的是「用 `requires` 推導排除清單，避免手抄」。實測：

```
🟢 函式庫層  requires 到 C 沒有的標頭 ∧ 無 ioRole 等價邊      59 顆
🔴 語言層    class／virtual／template／try／lambda／&引用     【requires 看不到】
```

`class_def`／`method_virtual`／`try_catch` **不需要任何標頭**，
所以「靠宣告推導」對它們**完全失效**。

> **一個「靠宣告推導」的判準，看不見那些【不需要宣告任何東西】的成員。**

**處置**：兩段判準——① 機械推導 59 顆 ② 具名清單 35 顆。
🔴 **而②是暫時的**：`draft`§三 的 `provides`／`requires` 能力求解才是對的機制
（目標宣告 `provides: ["cpp"]`、概念宣告 `requires: ["cpp"]`），
**而規格明確把它排除在本輪之外**。

⚠️ 那份清單有**兩道交叉驗證**（`c-topic-derivation.test.ts`），
而注入實測：把 `cpp:class_def` 放回 C 清單 → **兩支都紅、都指名它**。

## 四、⚠️ 而那份具名清單裡有 9 顆是「**該由①抓到而漏宣告**」的

```
container_empty/push/pop/clear/append/erase/count   7 顆   沒有 requires
string_at                                                  沒有 requires（該是 <string>）
istringstream_declare                                      沒有 requires（該是 <sstream>）
```

**正確的修法是補上 `requires` 宣告**，不是把它們寫進清單。

🔴 **而本輪【沒有修】**，理由是：`requires` **不是描述，是驅動自動 include 的資料**
——補一筆會讓程式多產一行 `#include`，那要驗行為
（`build-guardrail` 6.8 的第二個問題：「修一筆要付多少？」）。
**已記在 `c-topic-derivation.test.ts` 檔頭。**

## 五、e2e 的「0」差一點是空過的——而入口條件擋了兩次

`app.ts` 開機時 `enabledBranches = new Set([levelTree.id])`，**只有 L0**。
而 L0 那 19 顆**一顆都不用排除**（`print`／`input` 有 `ioRole`、其餘是 C 也有的）。

```
不展開層級   C++ 側 C++ 專屬概念 = 0  →  C 側也是 0  →  【功能沒做也會綠】
```

入口條件（「展開後 C++ 側必須 > 0」）**擋下了兩次**，而兩次都是**量測壞了**：

| | 症狀 | 真正的原因 |
|---|---|---|
| 一 | C++ 側量到 0 | `.blocklyTreeRow` 這個選擇器**不存在**（是 `.blocklyToolboxCategory`） |
| 二 | C++ 側量到 0 | 讀 `innerText`——**Blockly 積木是 SVG，`innerText` 回空字串** |

⚠️ 而第三個是我自己的：比對用 `/vector/i`／`/class/i`，
**積木上寫的是「建立 int 動態陣列」「定義類別」**——一個都不會命中。

> **一個量測壞掉的入口條件，症狀與「功能壞了」長得一模一樣。**

## 六、存檔的缺口——選擇本身沒有被存

`autoSave()` **只掛在 `blocklyPanel.onChange`** 上。所以在**空白工作區**換目標，
重新整理之後就跑掉了。

⚠️ **那是既有的缺口**（`topicId`／`styleId` 也一樣，只是沒有人問過），
而 e2e 的「重新整理之後選的還在」才問得出來。
**已修**（`onTargetChange` 尾端補 `autoSave()`），而 topic／style 那兩條**沒動**
——本輪的目標選擇器已經蓋掉它們的入口。

---

## 七、剪掉空子樹——而那讓「形狀相同」這個判準要改

C 扣完之後 **L3a（STL）／L3b（OOP）／L3c（例外）整棵是空的**。
留著會在選單裡顯示成**三個空分類**，而一個空的「L3b: OOP 進階」
告訴學生的是「這裡有東西而你看不到」——**正好是相反的訊息**。

**處置**：剪掉整個空子樹，而測試的判準從「形狀**相同**」改為「形狀是**子集**」，
並加一條「留下來的每個節點的 `id`／`level` 都要在 C++ 那份裡」。

# Feature Specification：擴充裡跑的就是網頁版本身

**Feature Branch**: `140-app-in-host`
**Created**: 2026-08-18
**Status**: Draft
**路線圖位置**: vision 階段 6.15
**上游**: `knowledge/history/082`（spec 139）

---

## 🔴 本規格的性質：**它是一次方向修正，不是一個新功能**

spec 139 做完之後，使用者逐字說：

> 「**你有聽懂我要什麼嗎？我要的是像網頁版那樣的面板，越像越好，
> 只是文字編輯的部分交給 IDE**」

而 139 交出來的是**一塊裝了儀表的畫布**：積木畫布 ＋ 一排診斷數字
＋ 兩顆手工按鈕。**那不是「像網頁版」，是另做了一個東西。**

### ⚠️ 而根因值得寫進規格，因為它會再犯

```
spec 138  性質是【否證】——問「畫布跑不跑得動」，所以它需要儀表。那是對的。
spec 139  🔴 我把那個框架整個帶進來：驗收全部寫成可量測的數字
          ⟹ 產出【完美符合我自己寫的規格】，而不符合使用者要的
```

> **一份把「怎麼證明它對」寫得很好的規格，
> 可以完全不描述「它該長什麼樣」。**

🔴 **所以這一份的第一條驗收是「看起來像不像」，而它由人判斷。**

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 學生打開面板，看到的就是他熟悉的那個介面 (Priority: P1)

一個用過網頁版的學生在 IDE 裡打開積木面板。
**他看到的東西與網頁版一樣**——同樣的工具列、同樣的分類、同樣的下方分頁。
**唯一的差別是：程式碼在旁邊的編輯器裡，不在面板裡。**

**Why this priority**: 這是使用者這一輪唯一的要求，而前一輪沒有做到。

**Independent Test**: 把網頁版與擴充並排截圖，逐區塊比對。

**Acceptance Scenarios**:

1. **Given** 面板開著，**When** 看最上方，**Then** 有**工具列**，
   而目標／課程／風格／語言的選擇器**都在**。
2. **Given** 面板開著，**When** 看畫布，**Then** 有工具箱與積木，樣子與網頁版一致。
3. **Given** 面板開著，**When** 看下方，**Then** 有**分頁**（主控台／變數）與**狀態列**。
4. **Given** 面板開著，**When** 找程式碼，**Then** 🔴 **面板裡沒有**——它在 IDE 的編輯器裡。
5. 🔴 **Given** 兩邊並排，**When** 人去看，**Then** **看得出是同一個產品**
   ——⚠️ **而這一條由人判斷，不是我說像**。

---

### User Story 2 - 他習慣的每一個動作都還在 (Priority: P1)

工具列上的每一顆按鈕、每一個選擇器，**做的事與網頁版相同**。

**Why this priority**: 「像」不只是長得像。一個長得一樣而按下去沒反應的按鈕
**比沒有那顆按鈕更糟**。

**Independent Test**: 逐一按過工具列上的每一個控制項。

**Acceptance Scenarios**:

1. **Given** 工具列，**When** 換一個目標，**Then** 工具箱與積木跟著換。
2. **Given** 工具列，**When** 換語言，**Then** 積木上的字跟著換。
3. **Given** 除錯工具列，**When** 按執行／單步，**Then** 積木依序高亮。
4. **Given** 下方分頁，**When** 程式輸出東西，**Then** 主控台看得到；
   執行到一半暫停時，**變數分頁看得到變數**。
5. ⚠️ **Given** 任何一個控制項，**When** 它在這個宿主裡沒有意義，
   **Then** 🔴 **它不該出現**——而不是出現了按下去沒反應。

---

### User Story 3 - 而他的檔案不能被弄壞 (Priority: P1)

學生打開一個既有的檔案，**面板不會用別的內容蓋掉它**。

**Why this priority**: 🔴 **這是唯一一條「做錯了會毀損使用者資料」的**。
網頁版開機時會從自己的存檔還原程式碼——而在 IDE 裡，**檔案才是真相**。

**Independent Test**: 用面板編輯檔案 A，關掉，打開檔案 B，看 B 的內容。

**Acceptance Scenarios**:

1. **Given** 一個有內容的檔案，**When** 打開面板，
   **Then** 🔴 **檔案的內容一個字元都沒變**。
2. **Given** 先用面板編輯過另一個檔案，**When** 打開這一個，
   **Then** **不會出現上一個檔案的內容**。
3. **Given** 面板開著，**When** 關掉再打開 IDE，**Then** 檔案還是檔案。

---

### User Story 4 - 而網頁版一個像素都不能變 (Priority: P1)

**Why this priority**: 這一刀動的是**網頁版的核心**（應用本體與版面組裝）。
`history/072` 的病歷正是這個形狀——**一條路徑全綠，而另一條安靜地錯了**。

**Acceptance Scenarios**:

1. **Given** 改完，**When** 跑全套，**Then** 全綠。
2. **Given** 同上，**When** 看護欄，**Then** 基線一個數字都不動、中立性違規 0。
3. **Given** 同上，**When** 跑探針，**Then** 殘差與漂移不變。
4. 🔴 **Given** 網頁版，**When** 打開它，**Then** **與改動前一模一樣**。

---

### User Story 5 - 上一輪做出來的能力一個都不能掉 (Priority: P2)

**Why this priority**: 上一輪的接線是對的，只是接在錯的殼上。
**換殼不該讓能力退步。**

**Acceptance Scenarios**:

1. 改一顆積木 → 只重寫改到的那一段。
2. 一次積木修改 = 一個復原步驟；拖位置不產生檔案變更。
3. 貼一段程式 → 積木跟著出來**而且停下來**。
4. 點積木／移游標 → 另一側跟著亮。
5. 單步 → 積木依序高亮，程式碼側跟著走。

---

### Edge Cases

- **面板開著而沒有任何檔案** → 畫布該顯示什麼？工具列還在嗎？
- **一個在這個宿主裡沒有意義的控制項**（例如「開啟檔案」）→ 🔴 **不該出現**。
- **面板很窄** → 版面要收得起來，而不是擠成一團。
- ⚠️ **未存檔的暫存分頁** → 全部功能同樣要成立。
- **程式碼那一側被別人改了**（格式化、還原）→ 積木跟著更新。
- ⚠️ **同一份程式碼開了兩個面板** → 本輪不支援，而**要說得出來**。

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 面板 MUST 呈現與網頁版**相同的介面元件**（工具列、選擇器、
  除錯控制、積木畫布與工具箱、下方分頁、狀態列）。
- **FR-002**: 面板 MUST NOT 包含程式碼編輯區——那由宿主的編輯器擔任。
- **FR-003**: 面板與網頁版 MUST **共用同一份組裝**，
  MUST NOT 各自維護一份「有哪些元件、怎麼擺」。
  - 理由：兩份會漂移，而**症狀是「網頁版改了而擴充沒改」，測試不會叫**。
- **FR-004**: 開啟面板 MUST NOT 改變使用者檔案的內容。
- **FR-005**: 應用 MUST NOT 在這個宿主裡把**文件內容**寫進自己的存檔。
- **FR-006**: 在這個宿主裡沒有意義的控制項 MUST 不出現，
  MUST NOT 出現而無作用。
- **FR-007**: 上一輪的雙向同步、復原分組、雙向高亮、單步高亮
  MUST 全部保留。
- **FR-008**: 既有的網頁版 MUST NOT 有任何行為或外觀改變。
- **FR-009**: 診斷用的量測 MUST 仍然拿得到，
  ⚠️ **而它 MUST NOT 佔用面板的版面**。

### Key Entities

- **程式碼視圖**：「顯示與編輯程式碼」這件事的**角色**。
  網頁版由內建的編輯器擔任；這個宿主由**IDE 的編輯器**擔任。
  🔴 **應用只認識這個角色，不認識任何一個具體的編輯器。**
- **存檔服務**：「把工作內容記下來」這件事的角色。
  ⚠️ 在這個宿主裡它**不記文件內容**——檔案才是真相。
- **面板組裝**：有哪些元件、怎麼擺。**一份，兩個宿主共用。**

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 🔴 **並排截圖比對，人看得出是同一個產品**
  ——⚠️ **這一條由使用者判斷，不由我宣稱**。
- **SC-002**: 網頁版有的介面區塊（工具列／畫布／下方分頁／狀態列），
  面板上**一個都不少**（程式碼區除外）。
- **SC-003**: 工具列上的控制項，**可用的都有作用**，
  **無作用的一個都不存在**。
- **SC-004**: 開啟面板後，檔案內容的變更 = **0 個字元**。
- **SC-005**: 上一輪的五項能力**全部仍然成立**。
- **SC-006**: 網頁版：全套綠、護欄基線 **0** 個變動、中立性 **0**、
  探針殘差與漂移**不變**。
- **SC-007**: 面板組裝的來源 = **1 份**（今天若是 2 份則為失敗）。
- **SC-008**: ⚠️ 未存檔的暫存分頁上，SC-002～SC-005 **同樣成立**。

### 🔴 而第一條驗收我做不到，這件事現在講清楚

```
🟢 我做得到   全套回歸、檔案零變更、能力清單、組裝只有一份
🔴 我做不到   「看起來像不像」——那是人的判斷
```

**處置**：交棒時附**網頁版與擴充的並排截圖**，讓判斷有依據。
⚠️ **而不是我描述它有多像。**

> **一個「像不像」的驗收，換成「有幾個區塊」就不再是同一條驗收了。**

---

## Assumptions

- 使用者要的「像」指的是**介面組成與操作**，不是像素級一致
  （字型與配色會跟隨宿主主題）。
- 行動版的版面在這個宿主裡不需要。
- 上一輪的同步機制正確，本輪只換它接的殼。

---

## 明確排除（防蔓延）

```
🔴 虛擬硬體 · 把執行做成宿主的除錯器 · 多面板／多文件 · 市集發佈
🔴 改內建編輯器本身的行為
   行動版版面
⚠️ 本輪【不】重新設計介面——目標是「一樣」，不是「更好」
```

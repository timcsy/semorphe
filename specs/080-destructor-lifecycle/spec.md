# Feature Specification: 解構式——物件生命週期

**Feature Branch**: `080-destructor-lifecycle` ｜ **Created**: 2026-08-06

## 為什麼這是最後一個，而且最難

前面每一個物件導向概念都是「**有人明確呼叫它**」。**解構式沒有人呼叫**——
它在物件離開作用域時自動跑。

所以這不是補一個執行器，是要在直譯器裡建立一個從來不存在的時機：
**作用域結束**。

而那個時機碰到每一個建立與銷毀作用域的地方：分支、迴圈、函式、方法、lambda。
**漏掉任何一個，那裡宣告的物件就永遠不會被收尾——而症狀是沒有症狀**
（少跑一段解構式，程式照樣跑完）。

因此核心加了一條**集中的離開作用域路徑**，五個地方全部改走它。

## 三件必須測的事，而它們單一物件時都看不出來

| | 為什麼 |
|---|---|
| 會跑 | 最基本 |
| **反序** | C++ 保證後宣告的先解構。順序錯的實作在單一物件時看不出來 |
| **每個實例各跑一次** | 跑成一次或跑成 N 次，單一物件時都看不出來 |

外加兩支反面：沒有解構式的類別不得出錯、**非物件的變數不得觸發任何收尾**
（沒有後者的話，一個「對每個變數都試著跑解構式」的實作也會通過前面每一支）。

## ⚠️ 第一版無限遞迴，而症狀是 OOM 不是錯誤訊息

解構式的本體跑在一個作用域裡，而那個作用域宣告了 `this`（指向這個物件自己）。
離開它時又對同一個物件跑一次解構式 → 堆疊爆掉。

兩道防線：`this` 不算這個作用域擁有的、以及一個「正在解構中」的集合。

## 分工

核心知道「作用域結束了」，但**不知道結束時該做什麼**——C++ 要跑解構式，
別的語言可能什麼都不做。掛勾由語言套件安裝，沒安裝時行為與加入本機制之前
完全相同。

## Requirements

- **FR-001**: 物件離開作用域時 MUST 執行它的解構式
- **FR-002**: 順序 MUST 是**反序**——後宣告的先解構
- **FR-003**: 每個實例 MUST 各跑一次，不多不少
- **FR-004**: 非物件的變數 MUST NOT 觸發任何收尾
- **FR-005**: 沒有解構式的類別 MUST NOT 出錯
- **FR-006**: **五個建立作用域的地方全部** MUST 走同一條離開路徑
- **FR-007**: MUST 有防線擋住解構式對自己遞迴
- **FR-008**: 核心 MUST NOT 認得「解構式」——那是語言套件的知識

## Success Criteria

- **SC-001**: 完備性的殼 **6 → 4**，缺維持 **0**
- **SC-002**: 六個行為各有測試，含兩支反面
- **SC-003**: 既有測試全數通過

## 順帶：一支測試變成了空殼

`consumed-by-parent-evidence` 有一支「解構式與 lambda 不得有宣告」的反面測試。
079／080 把兩者都實作了——**清單變空，那支測試於是什麼都沒驗到，自己成了
一個殼**。

留一個空清單假通過比刪掉它更糟：**它看起來還在守著什麼。**

改成**反過來查**：每一個宣告了「由父概念消費」的類別成員，都必須真的被收進
型別。這個形狀不隨「哪些概念實作了」而失效，而且下一個想偷渡宣告的概念會在
這裡被擋住。

（第一版的範圍寫太寬，把父概念是 switch 的兩個概念也報出來了——已收窄，
而那條邊界寫在測試裡。）

## 背景

老師出的題目常常有不只一種合理的讀法（「讀進一串數字印出最大的」——空輸入怎麼辦？負數算不算？讀到 0 停還是讀到結尾停？）。
今天一份課文任務只有一份參考解答與一組固定的輸入輸出，學生寫出「另一種合理的讀法」就被判錯，而老師看不到是題目的問題還是學生的問題。

這個功能讓題目可以宣告**候選解讀**，每個解讀一份參考解答；系統自動產生一批**情境**（輸入），把學生的程式與每份參考解答都交給判決，
告訴老師：學生的程式和哪幾種讀法一致、和其他讀法第一次不一致發生在哪個情境、兩邊各印了什麼。老師據此點選「題目指的是哪一種」。

分工：候選解讀由操作者提出（AI 或人）；成不成立由判決提供者（Cella）回答；並排與點選在 semorphe；定題意與留紀錄歸 cos-mos。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 學生的程式和哪幾種讀法一致（Priority: P1）

老師（或操作者）在一份 C 題目上宣告兩種以上的解讀，各附一份參考解答。學生交出程式後，系統產生一批標準輸入的情境，
把學生程式與每份參考解答各跑一次判決，回報：和哪幾個解讀在全部情境下輸出相同、和其餘解讀第一個不一致的情境是哪一筆、兩邊各輸出什麼。

**Why this priority**: 這是整個功能的核心價值——沒有它，其他部分都只是資料格式。

**Independent Test**: 拿一份已知有兩種讀法的題目（例：讀到 0 停 vs. 讀到檔案結尾停），三支程式（符合讀法 A、符合讀法 B、兩者都不符），
比對結果分別是 {A}、{B}、{}，而且每一筆「不一致」都附得出那個情境的輸入與兩邊的輸出。

**Acceptance Scenarios**:

1. **Given** 題目宣告解讀 A、B 各有參考解答，**When** 學生程式與 A 的解答在每個情境下輸出都相同，**Then** 回報一致的解讀是 A，並附上和 B 第一個不一致的情境（輸入、學生的輸出、B 的輸出）。
2. **Given** 學生程式在某個情境下判決不是成功執行（未定義行為、逾時、翻譯不了），**When** 比對，**Then** 那個情境照實標出判決的種類與原因，不算成「一致」也不假裝是輸出不同。
3. **Given** 題目只宣告了一個解讀（今天的課文都是這樣），**When** 比對，**Then** 行為退化成今天的「對不對」，不需要老師多做任何事。

---

### User Story 2 - Arduino 題目也能比（Priority: P2）

Arduino 題目的「輸入」不是一串文字，是板子上隨時間變化的感測值（按鈕在第 300 毫秒被按下、光感值從 200 升到 800）。
同一套比對流程要能用這種情境跑：系統產生一批時間序列輸入，學生程式與每份參考解答在同一批輸入下的輸出（序列埠文字、腳位的變化）逐一比較。

**Why this priority**: 驗證「情境的種類由領域套件決定、核心不認得任何一種」這個抽象真的成立——只有一種情境時看不出抽象對不對。

**Independent Test**: 一份 Arduino 題目（按下按鈕時亮燈 vs. 按住才亮），兩份參考解答、一支學生程式，比對結果指出一致的那一個，並附得出第一個不一致的時間點與兩邊的腳位狀態。

**Acceptance Scenarios**:

1. **Given** Arduino 題目宣告兩個解讀，**When** 比對，**Then** 產生的情境是時間序列輸入，回報的不一致附得出時間點、輸入、兩邊的輸出。
2. **Given** 核心程式碼，**When** 搜尋任何一種情境種類的名字，**Then** 找不到——種類只出現在領域套件的註冊裡。

---

### User Story 3 - 老師看並排畫面並點選（Priority: P3）

老師在課文頁上看到每一種解讀並排：一致／不一致、第一個不一致的情境、兩邊的輸出。老師點選「題目指的是這一種」，之後這份題目就以那個解讀判對錯。

**Why this priority**: 有了比對結果之後，人要能看懂並做決定；但比對本身（P1）先在測試與工具裡就能用。

**Independent Test**: 打開一份有兩個解讀的課文，交一支程式，畫面上看到兩欄並排、能點選其中一欄；點選之後再交一次，判對錯只照被選的那一個。

**Acceptance Scenarios**:

1. **Given** 比對完成，**When** 老師看畫面，**Then** 每個解讀一欄：名稱、一致或不一致、第一個不一致的情境與兩邊的輸出。
2. **Given** 老師點選了一個解讀，**When** 之後判這份題目，**Then** 只照那個解讀；這個選擇被記下來，下次打開還在。

---

### Edge Cases

- 參考解答本身在某個情境下判決不是成功執行（老師的解答有未定義行為）：那個情境對那個解讀不可比，照實標出，不影響其他情境。
- 兩個解讀在全部產生出來的情境下輸出都一樣：照實回報「這批情境分不出這兩種讀法」，不假裝分得出。
- 情境產生器產生不出情境（程式不讀任何輸入）：只跑一次空輸入，照常比對。
- 判決提供者還在準備（暖機中）：比對回報「還在準備」，不判成任何結果。
- 解讀的參考解答檔不存在：清楚指出是哪一個解讀缺了解答，其餘解讀照常比對。
- 一批情境數量很大、跑得很久：第一版設上限；更重的批次由 cos-mos 決定在哪裡跑（本功能不自己找後端）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 課文任務 MUST 能宣告零到多個解讀，每個解讀有識別碼與給人看的名稱；沒有宣告時行為與今天相同。
- **FR-002**: 每個解讀 MUST 能附一份參考解答，以檔名約定與任務對應；系統 MUST 能檢查「宣告了的解讀都有解答」。
- **FR-003**: 情境 MUST 是「種類＋內容」的形狀，種類由領域套件註冊；核心 MUST NOT 認得任何一種情境種類的名字。
- **FR-004**: C 領域 MUST 註冊「標準輸入」情境，產生器 MUST 依程式每一次讀取的型別與順序產生輸入（今天只存在於測試輔助的那一份要成為產品的一部分）。
- **FR-005**: Arduino 領域 MUST 註冊「時間序列輸入」情境（時間點、哪個輸入、值），形狀與今天判決請求接受的輸入相同。
- **FR-006**: 比對器 MUST 對同一批情境，把學生程式與每份參考解答各交判決提供者，回報：在全部可比情境下一致的解讀、每個不一致解讀的第一個不一致情境（輸入、學生輸出、解答輸出）、不可比的情境與原因。
- **FR-007**: 比對器 MUST 在瀏覽器與 Node 兩種宿主都能執行；MUST NOT 依賴畫面或檔案系統；判決提供者 MUST 由呼叫端提供。
- **FR-008**: 判決不是成功執行的情境 MUST 照實標出判決種類與原因，MUST NOT 被算成一致或不一致。
- **FR-009**: 只有一個解讀時，比對結果 MUST 等同於今天的對錯判斷。
- **FR-010**: 老師的畫面 MUST 並排每個解讀的比對結果，並能點選一個解讀；選擇 MUST 被保存，之後判這份題目只照被選的解讀。
- **FR-011**: 至少一份 C 課文與一份 Arduino 課文 MUST 宣告兩個以上的解讀並附解答，作為功能的活例子與回歸測試。
- **FR-012**: MUST 有機械化的檢查（護欄）擋住：宣告了解讀卻沒有解答、情境種類的名字出現在核心、比對器碰到畫面或檔案系統。

### Key Entities

- **解讀（Interpretation）**：一份題目的一種讀法；識別碼、名稱、對應的參考解答。
- **情境（Scenario）**：一次執行的輸入；種類（由領域套件註冊）＋內容（C：一段標準輸入文字；Arduino：一串時間點與輸入值）。
- **情境產生器**：給一支程式（與它的語意樹），產生一批情境；每個種類一個，由領域套件提供。
- **比對結果**：每個解讀的一致／不一致／不可比；不一致附第一個情境與兩邊輸出；不可比附判決種類與原因。
- **老師的選擇**：哪一份題目選了哪一個解讀。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對宣告了兩個解讀的示範題，三支示範程式（符合 A、符合 B、都不符）的比對結果 100% 正確，每一個「不一致」都附得出可重現的情境與兩邊的輸出。
- **SC-002**: 今天全部課文（沒有宣告解讀的）在功能上線前後的對錯判斷 100% 相同。
- **SC-003**: C 與 Arduino 兩種情境走同一套比對流程，核心程式碼中情境種類名字出現 0 次。
- **SC-004**: 同一份比對在瀏覽器與 Node 兩種宿主跑出相同的結果。
- **SC-005**: 一份示範題的完整比對（預設情境數）在一般學生電腦上 10 秒內完成。
- **SC-006**: 老師從看到並排畫面到點選完成，不需要閱讀任何說明文件（畫面上的名稱與第一個不一致情境就足以判斷）。

## Assumptions

- 判決提供者沿用今天的 Cella（瀏覽器裡的 worker）；判決的語義與今天相同。
- 候選解讀由人或 AI 事先寫好放進課文；本功能不負責自動提出解讀。
- 「題意的正式紀錄與誰定的」歸 cos-mos；第一版老師的選擇存在 semorphe 本地（同今天的課文進度），介面留給 cos-mos 之後接。
- 情境數量第一版設一個保守上限（例如每種 20 筆）；大量情境的批次由 cos-mos 決定環境。
- 「依據（warrant）」那一格不在這一版（草稿「相關、但這次不做」）。
- Python、圖、聲音等第三種情境等真的需要時再驗證抽象，不先為它設計。

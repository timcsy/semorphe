# Feature Specification: 操作者介面第一刀——「提議中」的變更

**Feature Branch**: `368-operator-proposals`
**Created**: 2026-11-09
**Status**: Draft
**Input**: User description: "操作者介面第一刀：「提議中」的變更（vision 286，history/334）。結構操作詞彙（插入、刪除、移動、改屬性），以節點指位置；提議 = 一串操作＋作者＋理由，接受才進語意樹、退回就丟掉；樹被改過而提議指的節點找不到或已不同 ⟹ 標過期、不硬套；操作不合法 ⟹ 整個提議被拒並說原因；使用者看得到差異、接受、退回；程式化入口讓 AI 送提議。不判對錯、不碰宿主。不做：委派自動套用、跨 lift 的穩定節點身分、元件詞彙的對外格式、多人同時編輯。"

## 背景

三方會議第三輪（history/334）使用者拍板：**AI 的變更預設是「提議中」，人接受才進語意樹**；「提議的呈現與操作（看差異、接受、退回）歸 semorphe」，權限紀錄歸 cos-mos。
同一份紀錄列了 semorphe 讓 AI 當操作者要補的四個缺口：結構操作的 API、穩定的節點身分、提議與已套用兩層狀態、元件詞彙的對外格式——「『提議中』那一層優先」。

今天的現況（2026-11-09 對著程式碼核過）：改動只有兩條路——把整段程式碼換掉、或把整棵樹換掉。
一個 AI 想「在第 3 行後面插一行輸出」，只能自己產出整段新程式碼，人看不出它改了哪裡，也沒有「先看看再說」這一步。

這一刀補第一與第三個缺口：**結構操作**（AI 和人用同樣的手勢改那棵樹）與**提議中**那一層。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - AI 提一個改動，人看過差異再決定 (Priority: P1)

學生（或老師）在編輯器裡寫程式。一個 AI 助手送來一個提議：「在讀入之後加一行輸出，印出讀到的值」，附上理由。
編輯器沒有被直接改掉；畫面上出現一個待處理的提議，顯示是誰提的、為什麼、程式碼改前改後的差異。
人按「接受」，改動進到程式裡（程式碼、積木都更新）；按「退回」，什麼都沒變。

**Why this priority**: 這是使用者拍板的那條規則本身——AI 的變更預設待人確認。沒有它，其他都沒有意義。

**Independent Test**: 用程式化入口送一個提議，確認：送出後程式沒變；畫面列出提議與差異；接受後程式等於「提議後的樣子」；另送一個並退回，程式不變。

**Acceptance Scenarios**:

1. **Given** 一支程式與一個合法的提議，**When** 提議送出，**Then** 程式本身不變，畫面上出現待處理的提議（作者、理由、改前改後的程式碼差異）。
2. **Given** 一個待處理的提議，**When** 人按接受，**Then** 程式變成提議後的樣子，所有視圖（程式碼、積木）一致更新，提議從待處理中移除。
3. **Given** 一個待處理的提議，**When** 人按退回，**Then** 程式與送出前完全相同，提議移除。
4. **Given** 接受後的程式，**When** 人用平常的「復原」，**Then** 回到接受前的樣子（接受是一次普通的編輯）。

---

### User Story 2 - 結構操作：AI 用和人一樣的手勢改樹 (Priority: P1)

提議裡的每一步是一個**結構操作**，與人在積木上做的事同一組：插入一個節點、刪除一個節點、把一個節點移到別處、改一個屬性。
操作指的是樹上的節點（不是行號、不是一段文字），所以不同的樣子（程式碼、積木）看到的是同一個改動。

**Why this priority**: 沒有結構操作，提議只能是「整段換掉」——人看不出改了哪裡，也無法判斷提議是否已經過期。

**Independent Test**: 對同一棵樹分別套用四種操作，檢查套用後的樹；再套用一串操作，檢查結果等於逐一套用。

**Acceptance Scenarios**:

1. **Given** 一棵樹與「在某節點的某個接點的第 k 個位置插入一個新節點」，**When** 套用，**Then** 新節點出現在那個位置，其他節點不動。
2. **Given** 「刪除某節點」，**When** 套用，**Then** 那個節點（連同它的子節點）不見，其他不動。
3. **Given** 「把某節點移到另一個接點的第 k 個位置」，**When** 套用，**Then** 它在新位置、舊位置沒有它，子節點跟著走。
4. **Given** 「把某節點的某個屬性改成某值」，**When** 套用，**Then** 只有那一個屬性變了。
5. **Given** 一串操作，**When** 套用其中一步失敗，**Then** 整串都不生效（全有或全無）。

---

### User Story 3 - 不合法或過期的提議照實說，不硬套 (Priority: P1)

AI 可能送錯：指一個不存在的節點、插到那顆元件沒有的接點、用一顆系統不認得的元件、把屬性改成那個屬性不接受的形狀。
提議送出後，人也可能自己又改了程式，提議指的節點就不在了，或已經是另一個東西。
這些情況都不得悄悄套用成別的樣子：不合法的整個被拒、說出哪一步、為什麼；過期的標成過期、不能接受，只能退回。

**Why this priority**: P6 誠實降級——把一個指錯地方的提議硬套上去，是在人不知情的情況下改掉他的程式，比不套還糟。

**Independent Test**: 準備一組錯誤的提議（每一種錯一支），每一支都被拒並說出原因；送一個合法提議後改動程式，那個提議變成過期且無法接受。

**Acceptance Scenarios**:

1. **Given** 一個指向不存在節點的提議，**When** 送出，**Then** 被拒，原因指出是哪一步、哪個節點。
2. **Given** 一個插到元件沒有宣告的接點、或用了不認得元件的提議，**When** 送出，**Then** 被拒並說出原因。
3. **Given** 一個待處理的合法提議，**When** 人在接受前改了程式，使提議指的節點不在或已不同，**Then** 提議標成過期、接受不可用、原因可見。
4. **Given** 一個待處理的合法提議，**When** 人改了程式中**與提議無關**的地方而提議指的節點都還在且相同，**Then** 提議仍可接受，差異以當下的程式重新算。

---

### User Story 4 - 多個提議排隊，依序處理 (Priority: P2)

AI 可能連續送好幾個提議。它們排成一列，人一個一個看、一個一個決定；畫面說得出還有幾個在等。
接受了前一個之後，後面的提議照 US3 的規則重新檢查（可能因此過期）。

**Why this priority**: 一次只能有一個的話，AI 第二個提議只能被拒或覆蓋掉第一個——兩者都會讓人漏看。

**Independent Test**: 連送三個提議，畫面顯示三個在等；依序接受、退回、接受，程式結果等於第一與第三個依序套用。

**Acceptance Scenarios**:

1. **Given** 連續送出的三個提議，**When** 畫面顯示，**Then** 看得到「還有幾個在等」，先處理最早的。
2. **Given** 接受第一個之後第二個指的節點已被第一個刪除，**When** 輪到第二個，**Then** 它是過期、只能退回。

### Edge Cases

- 提議裡沒有任何操作 → 被拒（「空的提議」）。
- 提議後的樹與目前完全相同（例如把屬性改成原本的值）→ 照常列出，差異顯示「沒有變化」，接受等於沒動。
- 操作把程式的根節點刪掉或移走 → 被拒（根不可刪、不可移）。
- 把一個節點移到它自己的子孫底下 → 被拒（會形成環）。
- 換了語言或目標（例如 C++ 換到 Python、或套用範例）→ 待處理的提議全部標成過期（它們是對舊的那棵樹提的）。
- 提議後的程式有錯（例如 Cella 判出錯誤）→ 系統照常讓人接受或退回，可以附上判決結果，但**不自己判斷對錯、不擋接受**。
- 送提議的作者名字是空的 → 照常收，顯示為「未具名」。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供四種結構操作：插入（新節點到某節點的某接點的某位置）、刪除（某節點）、移動（某節點到某接點的某位置）、改屬性（某節點的某屬性設為某值）；位置以樹上的節點指定。
- **FR-002**: 結構操作 MUST 與畫面無關，同一組操作在網頁版與 IDE 版行為相同。
- **FR-003**: 一個提議 MUST 由一串結構操作、作者、理由組成；套用時全有或全無。
- **FR-004**: 提議送出時 MUST 先在一份副本上檢查與套用，不改動目前的程式；不合法的提議 MUST 被拒，並指出是第幾步、哪個節點、什麼原因。
- **FR-005**: 合法性檢查 MUST 至少涵蓋：節點存在、元件認得、接點是那顆元件宣告的、屬性是那顆元件宣告的、根不可刪移、移動不成環、提議不是空的。
- **FR-006**: 每個提議 MUST 記下它所指的每個節點在送出當下是什麼（元件身分），供之後判斷是否過期。
- **FR-007**: 程式改變後（人編輯、接受了別的提議、換語言或目標、套用範例），系統 MUST 重新判斷每個待處理提議：指的節點都還在且仍是同一種元件 → 仍可接受；否則標成過期並說出原因。
- **FR-008**: 過期的提議 MUST 無法接受，只能退回。
- **FR-009**: 使用者 MUST 看得到每個待處理提議的作者、理由、狀態（可接受／過期）、以及改前改後的程式碼差異（以目前程式為基準計算）。
- **FR-010**: 接受 MUST 讓程式變成提議後的樣子，所有視圖一致更新，並能用一般的復原撤回。
- **FR-011**: 退回 MUST 不改動程式。
- **FR-012**: 多個提議 MUST 依送出順序排隊；畫面 MUST 說得出還有幾個在等。
- **FR-013**: 系統 MUST 提供程式化入口讓外部操作者（AI、測試）送出提議、讀取每個提議的狀態與被拒原因，並（在使用者授權給它之外）**不能**替人接受。
- **FR-014**: 系統 MUST NOT 依提議後程式的對錯擋下或自動接受提議；判決結果若附上，只作為給人看的資訊。

### Key Entities

- **結構操作**：插入／刪除／移動／改屬性之一；指一個節點（或節點的接點與位置）；插入時帶一個新節點（元件身分、屬性、子節點）。
- **提議**：一串結構操作 ＋ 作者 ＋ 理由 ＋ 送出時間 ＋ 狀態（待處理可接受／過期／已接受／已退回／被拒）＋ 被拒或過期的原因 ＋ 送出當下它所指節點的身分快照。
- **提議佇列**：待處理提議的有序清單；與目前的程式一起存在、不寫進程式本身。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 送出一個提議到畫面上看到它（含差異），在一般課文長度的程式上 1 秒內完成。
- **SC-002**: 一組刻意寫錯的提議（FR-005 列出的每一種錯至少一支），100% 被拒且原因指出正確的那一步。
- **SC-003**: 送出後程式被改到使提議指的節點不在或已不同的情境，100% 標成過期且無法接受；沒有任何一個情境是「悄悄套到別的地方」。
- **SC-004**: 接受後的程式與「在副本上套用的結果」逐字相同（程式碼）；退回後的程式與送出前逐字相同。
- **SC-005**: 四種結構操作在每一種語言（C、C++、Python、Arduino 各取一支課文程式）上套用後，程式碼能再轉回同一棵樹（不漂移）。

## Assumptions

- 「節點身分」用今天樹上的節點編號；它在程式碼重新解析時會換號（缺口②），所以**人改了程式碼之後，大部分提議會因節點找不到而過期**——這是誠實的結果，第一刀接受它；穩定身分是之後的一刀。
- 改積木（而不是改程式碼）時節點編號是否保留，以今天的行為為準；不在這一刀改變。
- 提議佇列只存在於目前的編輯工作階段，不寫進存檔、不跨重新整理保留。
- 「作者」是送出者自己填的文字，系統不驗證身分（權限與委派歸 cos-mos）。
- 程式化入口在網頁版與 IDE 版各有一個進入點；IDE 版的外部 AI 怎麼接到它（例如透過延伸模組的指令）若超出這一刀，列為後續。
- 差異以程式碼的文字呈現；積木上的差異呈現不在這一刀。

## 不做（明確排除）

- 委派某類變更自動套用（權限紀錄歸 cos-mos）。
- 跨重新解析的穩定節點身分（缺口②）。
- 元件詞彙給外部的格式（缺口④）。
- 多人同時編輯、提議之間的合併。
- 在積木上畫出差異。

# Feature Specification: 匯出是一份帶得走的作品，不是一個只有我們打得開的檔

**Feature Directory**: `specs/177-portable-export/`
**Created**: 2026-09-06
**Status**: ✅ Implemented（2026-09-06）
**Input**: vision「網頁版有檔案：主體、side-car、檔案系統埠」（2026-08-24 升格，
使用者拍板七題）的一條驗收，逐字：

> 驗收：匯出 zip（原始碼＋side-car）／匯入解壓；**離線可用**
> （`e2e/offline.spec.ts` 是硬條件）

---

## 🔴 開刀之前先推翻了 vision 上的一句話

vision 那一項底下逐字寫著：

> 🔴 **上面三條未做的驗收共用同一個前置：真的檔案**，而它卡在
> **File System Access API 驗不到**（需要使用者手勢，headless 的 e2e 叫不起 picker）。
> ⏳ **動工條件**：有一個能驗 FSA 的辦法——**不是「等有空」**。

**那句話對這一條是錯的**（2026-09-06 實測）：

```
匯出   Blob ＋ <a download>        storage.ts:265  downloadBlob()
匯入   <input type=file> ＋ FileReader   app-shell.ts:1939
```

**兩者都不碰 FSA。** 而 e2e 探針（跑過，1 passed）證明它**驗得到**：

```
page.waitForEvent('download')  → 檔名 semorphe-1788708649500.json
download.createReadStream()    → 478 bytes，解析得出 13 個頂層 key
```

> **一個「三條驗收共用同一個前置」的判斷，
> 在沒有逐條驗過的時候，記的是【它們寫在一起】。**

卡住的只有另外兩條：「新檔案可以選語言」要有檔案的概念、
「`semorphe-state` 遷成檔案」要等多檔案落地。**這一條沒有卡。**

---

## 這一刀在解什麼

**今天那份匯出，只有 Semorphe 打得開。**

實測的頂層 13 個 key，混在同一層：

```
code                                   ← 🔴 原始碼，唯一真實
blocklyState · flowLayout · codeHash   ← side-car（快取與排版）
topicId · language · styleId · targetId · enabledBranches
blockStyleId · locale · version · lastModified   ← 專案級
```

🔴 而 P1「**唯一真實，各式投影**」的唯一真實**是程式碼**。

> **一份匯出如果程式碼不是第一級的檔案，那份匯出把投影當成了真相。**

⚠️ 而**歸屬那一半早就做完了**（[history/151](../../knowledge/history/151-存檔裡的樹沒有人讀而還原路徑會把真相抹掉.md)
「一份存檔拆成四種歸屬」）——缺的是「拆開之後長成檔案的樣子」。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 我匯出的東西，別人用一般編輯器就打得開 (Priority: P1)

學生把作品匯出、寄給老師。老師解開之後看到一個 `.cpp`
——**用任何編輯器都打得開**，不需要 Semorphe。

**Why this priority**: 這是這一刀的全部。一份帶不走的作品是一個鎖。

**Independent Test**: 匯出、解開、拿文字編輯器打開那個原始碼檔。

**Acceptance Scenarios**:

1. **Given** 一份 C++ 作品，**When** 匯出並解開，
   **Then** 裡面有一個 `.cpp`，內容是**純程式碼**（沒有 JSON 包裝）
2. **Given** 同上，**When** 看解開後的結構，
   **Then** 積木擺放與設定在一個**分開的**側檔裡，不混在原始碼中
3. **Given** 解開後的原始碼檔，**When** 用一般編譯器編它，**Then** 編得過

### User Story 2 - 副檔名跟著語言走 (Priority: P1)

作品的語言換成另一個之後再匯出，**副檔名跟著換**。

**Why this priority**: 這是那條設計原則的**第一個機械實例**，
而它今天沒有任何地方在守。

> 副檔名是**產出的形狀**（存檔的結果），語言是**宣告**。
> （使用者 2026-08-24：「我開啟一個新檔案時是可以選擇語言，
> 但是**還沒存檔，所以沒有副檔名**」）

🔴 **而反推是錯的**——`traits.ts:60` 逐字：
「從產出的形狀反推它是什麼的判準，會安靜地做錯事」。

**Acceptance Scenarios**:

1. **Given** 語言是 C++，**When** 匯出，**Then** 原始碼檔的副檔名是該語言的
2. **Given** 換成另一個語言，**When** 匯出，**Then** 副檔名跟著換
3. **Given** 一個系統認不得的語言，**When** 匯出，
   **Then** 用一個中性的預設，**不得崩掉**

### User Story 3 - 舊的匯出還匯得進來 (Priority: P1)

使用者手上已經有的那些單一檔匯出，**照樣匯得進來**。

**Why this priority**: 🔴 那是**已經在別人硬碟上的東西**——
我們改不動它，而它一定要能回來。

**Acceptance Scenarios**:

1. **Given** 一份舊格式的匯出，**When** 匯入，**Then** 完整回來
2. **Given** 一份舊格式且版本較舊的匯出，**When** 匯入，
   **Then** 走**與自動載入同一套**的升級——不得有第二種鬆緊度
3. **Given** 一份壞掉的檔，**When** 匯入，**Then** 說得出「匯入失敗」而不是靜靜吃掉

### User Story 4 - 來回一趟，東西都還在 (Priority: P1)

匯出 → 匯入之後，**積木的擺放與流程的佈局都在原位**。

**Why this priority**: side-car 存在的理由就是這個。分開存之後**它必須還接得回去**。

**Acceptance Scenarios**:

1. **Given** 一份排過版的作品，**When** 匯出再匯入，
   **Then** 積木在原位、流程佈局在原位、程式碼逐字相同
2. **Given** 側檔被刪掉的匯入，**When** 匯入，
   **Then** **自動排版，不是壞掉**（既有規則，2026-09-06 已釘）

### Edge Cases

- 🔴 **離線**：`e2e/offline.spec.ts` 是**硬條件**——壓縮的能力必須跟著產品一起送，
  **不得在使用時向外要東西**
- **側檔的版本與現在不同** → 走同一套升級
- **側檔與原始碼對不上**（有人手改了原始碼）→ **重排版，不要拿一份不一致的積木**
  （既有規則，`sideCarUsable` 的失效條件）
- **作品沒有名字**——今天「檔名」這個概念不存在，見 A-003
- **原始碼是空的** → 照樣匯得出來，不得崩

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 匯出 MUST 產出一個容器，裡面**原始碼是一個獨立的檔案**
- **FR-002**: 原始碼檔的副檔名 MUST **由語言決定**，MUST NOT 反過來推
- **FR-003**: 積木擺放、流程佈局與設定 MUST 放在**與原始碼分開**的側檔裡
- **FR-004**: 匯入 MUST 認得新格式**與舊的單一檔格式**
- **FR-005**: 側檔的版本升級 MUST 走與自動載入**同一套**判定與升級
- **FR-006**: 匯出與匯入 MUST NOT 需要任何網路請求（離線硬條件）
- **FR-007**: 來回一趟之後，程式碼 MUST 逐字相同，擺放 MUST 在原位
- **FR-008**: 認不得的語言 MUST 有一個中性的預設副檔名，MUST NOT 讓匯出失敗

### Key Entities

- **帶得走的作品**：一個容器，內含**原始碼**（第一級）＋ **側檔**（附屬）
- **原始碼**：唯一真實。任何編輯器打得開
- **側檔**：投影的快取（擺放、佈局）＋ 專案級設定。⚠️ **它可以不在**
- **語言 → 副檔名**：一個單向的映射。🔴 **反向不成立**

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 匯出的容器解開後，原始碼檔的內容**逐字等於**編輯器裡的程式碼
- **SC-002**: 該原始碼檔**不含任何 JSON 包裝**（第一個字元不是 `{`）
- **SC-003**: 換一個語言之後匯出，副檔名**不同**且對得上那個語言
- **SC-004**: 舊格式的匯出**仍然匯得進來**——零回歸
- **SC-005**: 匯出 → 匯入之後，程式碼逐字相同、積木座標與流程佈局**逐一相同**
- **SC-006**: `e2e/offline.spec.ts` **仍然綠**（零外部請求）
- **SC-007**: e2e **有**匯出／匯入的來回測試——⚠️ 今天是 **0 支**
- **SC-008**: 側檔缺席時 → **自動排版**，不得是「匯入失敗」

## Assumptions

- **A-001**: 壓縮的能力**跟著產品一起送**（不走外部來源）。
  🔴 **理由**：離線是硬條件，而一個「使用時才去拿」的相依會讓它失效。
- **A-002**: 側檔的版本判定與升級**沿用既有那一套**，不新寫一份。
  🔴 **理由**：`storage.ts:252` 的既有教訓逐字——「走**同一個** `judgeJSON`
  ——與自動載入**不得有第二種鬆緊度**」。在此之前那裡只檢查 `version` 存在，
  於是 `version: 99` 通過。
- **A-003**: 作品名用**現有的資訊**（課程／時間）當預設，
  ⚠️ **不現在發明一個檔名欄位**。
  🔴 **理由**：「主體是誰」那一題屬於多檔案那一刀，而**現在發明一個欄位，
  等那一刀來的時候就要遷移它**。

---

## Out of Scope

- **File System Access API／真的檔案系統**——那是 `FileStore` 埠那一刀，
  ⚠️ 它**仍然**卡在驗不到（這一份沒有解掉那個問題，只證明了它不擋這一條）
- **多檔案**——一個容器裡今天只有一份作品
- **`semorphe-state` 遷成檔案**——要等多檔案落地
- **多檔之間的引用**（`#include "my.h"`）
- ⚠️ **不發明「檔名」這個欄位**——見 A-003

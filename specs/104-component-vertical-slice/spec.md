# Feature Specification: F 膠囊搬家——第一顆垂直切片

**Feature Branch**: `104-component-vertical-slice`

**Created**: 2026-08-09

**Status**: Draft

**Input**: F 膠囊搬家（垂直切片）：把元件從「散在共用檔」搬成「一顆一個資料夾」。本 spec 只做第一顆垂直切片 `cpp:vector_declare`，目的是量出「一顆要多久、卡在哪」，再乘出剩餘 176 顆的真實範圍。

---

## 動手前的實測（這份 spec 的地基）

`cpp:vector_declare` 今天的落點，逐一查證：

| 位置 | 類別 | 與幾顆元件共用 | 就近性護欄算得到？ |
|---|---|---|---|
| `src/languages/cpp/std/vector/concepts.json` | 宣告 | 4 | ✗ 只算「實作」類 |
| `src/languages/cpp/std/vector/blocks.json` | 宣告 | 4 | ✗ 同上 |
| `src/languages/cpp/std/vector/executors.ts` | 實作 | 4 | ✓ |
| `src/languages/cpp/std/vector/generators.ts` | 實作 | 4 | ✓ |
| `src/languages/cpp/core/lifters/strategies.ts` | 實作 | **48** | ✓ |
| `src/i18n/zh-TW/blocks.json`（8 筆） | — | 全部 | **✗ 完全看不到** |
| `src/i18n/en/blocks.json`（8 筆） | — | 全部 | **✗ 完全看不到** |
| `topics/cpp-{beginner,competitive}.json` | 清單 | 172／170 | ✗ 刻意不計（登錄表的視圖） |
| `id-migrations.ts` | 清單 | 147 | ✗ 刻意不計（歷史名冊） |

> **護欄回報 `{files: 3, dirs: 2}`，而實際落點是 8 個檔。**

### 三個從這張表落出的事實

**① 起點不是零。** `std/vector/` 資料夾已經存在——但它是**模組**資料夾（住 4 顆元件），
不是膠囊。搬家的實質是「模組資料夾 → 每顆一個資料夾」，加上把 lift 從 48 顆共用的檔裡拉出來。

**② i18n 是第五個「消失在數字裡的維度」。**
i18n 用積木訊息鍵（`CPP_VECTOR_DECLARE_MSG0`）索引，**檔案裡沒有任何 conceptId 字串**，
所以中立性、就近性、語法耦合三條護欄一筆都數不到。
（前四個：身分／語法／型別名／核心聯集，見 `knowledge/history/021`、`024`。）

**③ 現行就近性只算「實作」類，而碎裂的最大來源是「宣告」類。**
`concepts.json` 與 `blocks.json` 各被 4 顆元件共用——那正是要拆的東西，而現行維度看不到。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把一顆元件搬進它自己的資料夾，行為零改變 (Priority: P1)

維護者要修改 `cpp:vector_declare` 的任何一面（它的參數、它產生的碼、它怎麼被辨識出來、
它的中文標籤），今天要打開 8 個檔案，其中 3 個裡面住著別的元件（最多的一個住 48 顆）。
搬完之後，這些東西全部在 `components/cpp/vector_declare/` 底下。

**Why this priority**: 這是整個 F 的原子操作。它不成立，後面 176 次都不用談。
而它同時是**成本量測的載體**——F 的範圍要靠這一顆乘出來。

**Independent Test**: 全套測試綠著、`vector<int> v;` 的來回轉換與執行輸出與搬家前逐字相同，
而 `cpp:vector_declare` 在自己資料夾以外的檔案出現次數為 0。

**Acceptance Scenarios**:

1. **Given** 搬家前錄下的基準（該元件的五路輸出、來回轉換結果、i18n 標籤字串），
   **When** 搬家完成，
   **Then** 每一項與基準**逐字相同**。
2. **Given** 搬家完成，
   **When** 查詢「`cpp:vector_declare` 出現在哪些檔」，
   **Then** 除了 `components/cpp/vector_declare/` 底下與**明確豁免的清單類檔**
   （課程主題、歷史改名表）之外，結果為空。
3. **Given** 搬家完成，
   **When** 刪掉 `components/cpp/vector_declare/` 整個資料夾，
   **Then** 系統少一顆元件而其餘 176 顆**完全不受影響**（沒有 import 斷裂、沒有測試因無關原因變紅）。
4. **Given** 同資料夾的兄弟元件（`cpp:vector_size` 等 3 顆）**沒有**被搬，
   **When** 全套測試執行，
   **Then** 全綠——搬一顆不要求搬完整組。

---

### User Story 2 - 護欄要問兩個方向，而且要涵蓋看不見的那一維 (Priority: P2)

今天的就近性護欄只問「這顆元件散在幾個實作檔」。它答不出兩件事：
資料夾裡混進了不屬於這顆元件的東西；以及 i18n 那一維根本不在它的視野裡。

**Why this priority**: 沒有這條護欄，搬完第一顆之後**沒有東西擋著第二顆搬歪**。
而 `knowledge/experience.md` 記過：「護欄常常只問了一個方向……
把規範的主詞與受詞對調再讀一次，對調之後讀起來成立的，就是漏掉的那一半。」

**Independent Test**: 故意把一行實作留在共用檔 → 護欄變紅並**指名是哪一顆、哪一行**；
故意在膠囊資料夾裡放一個屬於別顆元件的東西 → 護欄變紅。

**Acceptance Scenarios**:

1. **Given** 一顆已膠囊化的元件，**When** 有人把它的一段實作加回共用檔，
   **Then** 護欄變紅並指名該元件與該檔案。
2. **Given** 一顆已膠囊化的元件，**When** 有人在它的資料夾裡加入屬於別顆元件的內容，
   **Then** 護欄變紅並指名那個外來身分。
3. **Given** 護欄第一次執行，**When** 它掃過全部 177 顆，
   **Then** 它是**紅的**——只有 1 顆膠囊化、176 顆未搬（第一次就綠代表判準或載入壞了）。
4. **Given** i18n 條目與元件的對應，**When** 有人把某顆已膠囊化元件的標籤留在共用的 i18n 檔，
   **Then** 護欄變紅——這一維不得再是盲區。

---

### User Story 3 - 量出成本與卡點，據此決定要不要／怎麼 skill 化 (Priority: P3)

做完第一顆之後，必須答得出「剩下 176 顆要花多少、會卡在哪幾種形狀」，
而不是憑感覺開一張票。

**Why this priority**: 膠囊契約自己寫著「**還不給週數**——建議先搬一顆當垂直切片，
量出『一顆要多久、卡在哪』，再乘出真實範圍」。這一項就是那個「再乘」的輸入。

**Independent Test**: 產出一份紀錄，含每一步的實際動作、卡點、以及**哪些步驟是這一顆特有的、
哪些會重複 176 次**——而分類的依據是查證過的，不是猜的。

**Acceptance Scenarios**:

1. **Given** 切片完成，**When** 讀該紀錄，
   **Then** 它列出至少三種**已查證**的元件形狀差異（例如：純宣告式無執行器、
   多形態、被 pattern 而非顯式 lifter 辨識），以及每一種對搬家步驟的影響。
2. **Given** 該紀錄，**When** 決定 `component-encapsulate` skill 的步驟表，
   **Then** 每一步都能指回切片裡**真的發生過的**一次操作或一次卡點——
   沒有發生過的步驟不得寫進去。

---

### Edge Cases

- **這顆元件的 lift 靠 pattern 不靠顯式 lifter**（`std/vector/lifters.ts` 明寫
  「This module's concepts use pattern-based lifting」）。那麼「lift 這一路搬到哪」
  的答案不是搬函式，而是搬**pattern 的宣告**——要先確認 pattern 住在哪、能不能單顆拆出來。
- **`concepts.json` 是 4 顆共用的陣列。** 拆出一顆之後，剩下 3 顆的載入路徑必須仍然成立，
  而且不得留下一個空陣列的殼。
- **i18n 拆出來之後語言檔怎麼合併。** 兩個語言各一份，將來會有第三個語言——
  拆法必須讓「加一個語言」不用碰任何膠囊。
- **兄弟元件之間的隱含依賴。** `vector_size`／`vector_pop`／`vector_back` 與
  `vector_declare` 是否共用執行期狀態或型別追蹤；若有，搬一顆會不會弄壞另外三顆。
- **搬完之後身分沒變**（膠囊契約：「scope 是所有權不是位置，**所以搬家不等於改名**」），
  所以**不需要存檔遷移**。這一點要有測試釘住，否則下一顆會有人「順手」改名。

## Requirements *(mandatory)*

### Functional Requirements

**膠囊本體**

- **FR-001**: 系統 MUST 讓 `cpp:vector_declare` 的身分、參數、接點宣告住在一個
  **只屬於這顆元件**的宣告檔裡，而非與其他元件共用的陣列。
- **FR-002**: 系統 MUST 讓該元件的五路實作（lift／generate／render／extract／execute）
  中**實際存在的那幾路**住在同一個資料夾底下；不存在的路必須**明確宣告**它不存在及理由，
  不得以沉默表示。
- **FR-003**: 系統 MUST 讓該元件的顯示標籤（含全部語言）住在同一個資料夾底下。
- **FR-004**: 該元件的膠囊 MUST 含一支自證測，且該測試 MUST **同時有正向與負向斷言**。
- **FR-005**: 自證測 MUST 證明它真的碰到這顆元件——不得只斷言輸出字串
  （前例：五支「通過」是假的，被測的概念根本沒出現在語義樹裡）。

**歸屬的來源**

- **FR-006**: 決定「哪些東西屬於這顆元件」MUST 從登錄表查，**不得從檔名或目錄名推斷**。
  （前例：`strings.ts` 橫跨兩個標準函式庫模組、`containers.ts` 跨六個。）

**兩條防線**

- **FR-007**: 系統 MUST 有一條檢查抓「**漏失**」——搬家前後，系統認得的元件身分集合、
  以及該元件五路的可及性，必須完全相同。
- **FR-008**: 系統 MUST 有一條**獨立於 FR-007** 的檢查抓「**錯置**」——實作跑進了錯的
  元件底下。（前例：兩筆註冊被併進錯的模組，**集合完全相同、防線全綠**。）
- **FR-009**: 這兩條檢查 MUST 各自聲明它**抓不到什麼**。

**護欄（雙向）**

- **FR-010**: 系統 MUST 有一條護欄回答「**已膠囊化的元件，它的東西都在自己資料夾裡嗎**」，
  違規時指名元件與檔案。
- **FR-011**: 系統 MUST 有一條護欄回答**反方向**：「**膠囊資料夾裡的東西，都屬於這顆元件嗎**」。
- **FR-012**: 上述護欄 MUST 涵蓋**顯示標籤那一維**——今天沒有任何護欄看得到它。
- **FR-013**: 上述護欄的**第一次執行 MUST 是紅的**，且違規項要**逐項指名**後才產基線。
- **FR-014**: 上述護欄 MUST 涵蓋「宣告」類的共用（今天的就近性只算「實作」類），
  且**新舊維度的數字要分開呈現**，不得讓維度變更混進 F 的成績裡。

**紀律**

- **FR-015**: 搬家 MUST 是搬移而非重寫；每一步結束時全套測試 MUST 綠，
  且每一步 MUST 是一個可獨立還原的單位。
- **FR-016**: 該元件的身分字串 MUST 不變，且 MUST 有測試釘住這一點
  （搬家 ≠ 改名 ⇒ 不需要存檔遷移）。
- **FR-017**: 未被搬移的 176 顆元件 MUST 完全不受影響。

**量測**

- **FR-018**: 系統 MUST 產出一份切片紀錄，含每一步的實際動作、遇到的卡點、
  以及「這一顆特有 vs 會重複 176 次」的分類與其查證依據。
- **FR-019**: 該紀錄 MUST 給出剩餘 176 顆的範圍估計，且估計 MUST 標明它**基於幾個樣本**
  ——一個樣本得出的估計要說出它是一個樣本。

### Key Entities

- **膠囊**：一顆元件的家。含它的宣告（＝規格）、它實際存在的那幾路實作、它的顯示標籤、
  它的自證測。**不含**共同測——共同測從宣告推導，不複製進膠囊。
- **切片紀錄**：這一顆的搬家過程、成本、卡點、以及對剩餘範圍的估計。
- **歸屬**：一段程式碼／一筆宣告／一則標籤屬於哪一顆元件。**唯一真相是登錄表**，
  檔案位置是上一次重構留下的痕跡。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `cpp:vector_declare` 出現在自己資料夾以外的**非清單類**檔案數：**8 → 0**。
- **SC-002**: 該元件的五路輸出與來回轉換結果，搬家前後**逐字相同**（0 筆差異）。
- **SC-003**: 全套測試在搬家的**每一個可還原步驟結束時**都是綠的（紅燈步數 = 0）。
- **SC-004**: 未搬移的 176 顆元件，其擴散度數字**一筆都沒有變差**。
- **SC-005**: 新護欄第一次執行時報出的違規數 **> 0**，且每一筆都被逐項指名（未指名數 = 0）。
- **SC-006**: 刪掉該膠囊資料夾之後，其餘元件的測試**零失敗**（可拆性）。
- **SC-007**: 切片紀錄給出剩餘 176 顆的估計，並列出至少 **3 種**已查證的形狀差異。
- **SC-008**: 顯示標籤那一維從「零護欄覆蓋」變成「有護欄覆蓋」，且該護欄能對
  一個人為製造的違規變紅。

## Assumptions

- **膠囊的資料夾位置**採 `components/<scope>/<name>/`。膠囊契約寫的是
  `components/<name>/`，但那是在 scope 決定之前寫的；D 之後身分是 `<scope>:<name>`，
  路徑跟著分兩層，避免第三方套件進來時撞名。**這是本 spec 的假設，不是已拍板的決定。**
- **不建共同測 harness**。膠囊契約設計了一支從宣告推導共同測的 harness，
  但一顆元件推不出它的價值（推導式與手寫的差別要在 N 顆之後才看得出來）。
  本切片沿用現有的 17 條全域護欄，harness 留給後續。
- **不搬兄弟元件**。`std/vector/` 另外 3 顆留在原地，用來證明「搬一顆」是原子的。
- **不動身分、不動存檔版本**。
- **不做 `cpp@1` 版本宣告**——那是獨立的路線圖項目。
- **「五路齊全」以完備性報表為準**（目前 shell 0、missing 0），不另行判斷。
- **豁免清單類檔**（課程主題、歷史改名表）不計入 SC-001，理由與現行就近性護欄一致：
  它們是登錄表的視圖與歷史名冊，不是實作擴散。

## Out of Scope

- 搬第二顆及其後的 176 顆
- 共同測 harness（從宣告推導共同測）
- `component-encapsulate` skill 的實作（本 spec 只產出「它該收哪些步驟」的依據）
- C2 資訊軸（`attachments` / `relation`）
- `cpp@1` 套件版本宣告
- 把現有 17 條全域護欄改寫成推導式的每顆合約測試
- 社群 PR 的機械判定流程

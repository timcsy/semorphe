# Feature Specification: 運算式當敘述的包裝積木

**Feature Branch**: `263-expr-stmt-block` | **Created**: 2026-11-04 | **Status**: Draft（實作等 262 合併：兩刀都改 `renderStatementChain`）
**Input**: spec 213 量到的釘子（history/337）：`cc[1];`、`(c ? A = 1 : A = 0);` 這類「運算式直接當敘述用」的程式，走一趟積木就跑到 main 外面。

## 背景

2026-09-10 決定：接不上語句鏈的積木（沒有敘述形態的運算式）**放在旁邊**——不丟、不硬接（硬接會讓 Blockly 拒絕整個工作區；丟掉會讓那一行消失）。
那個決定只處理了「畫得出來」；**抽回來時它不在原位**——它成了程式最外層的一顆積木，產回去的程式碼把那一行搬到 main 外面（不合法），翻給判斷功能時翻不出。

課文沒有這個寫法；學生語料 218 支裡有 3 支（離散化的 `cc[A[i]];`、三元運算子當敘述、raw 運算式當敘述）。

## User Scenarios & Testing

### User Story 1 - 學生寫了「運算式當敘述」，一動積木那一行不得換位置（P1）

**Independent Test**: `form-invariance` 那兩根釘子轉正；學生語料積木來回 3 → 0。

**Acceptance Scenarios**:
1. **Given** `cc[1];` 在 main 裡，**When** 轉積木再轉回，**Then** 那一行還在 main 裡、同一個位置，翻給判斷功能的程式不變。
2. **Given** 一個有敘述形態的元件（例如方法呼叫），**When** 轉積木，**Then** 照舊用它自己的敘述形態，不套包裝。
3. **Given** 學生在積木上把包裝裡的運算式換掉，**When** 轉回程式碼，**Then** 產出 `新的運算式;`。

### Edge Cases
- 包裝裡沒有接運算式（學生拖空了）：照「還沒寫完」處理（不產碼、判決的 incomplete），不得產出一個孤零零的 `;`。
- Python：裸運算式在頂層合法（`nums.append(9)`），同一個機制要依語言宣告（`expression-statement.ts` 已經是語言宣告的形狀）。

## Requirements
- **FR-001**: 語言套件宣告「運算式當敘述」的包裝積木型別（與降級積木同一個登記方式）；核心不點名任何語言的積木。
- **FR-002**: 渲染敘述鏈時，**只有運算式形態**的節點套上包裝；抽回時拆掉——語意樹不變（不新增語意節點）。
- **FR-003**: `form-invariance` 的兩根釘子轉正；學生語料探針積木來回 0 不同。
- **FR-004**: 積木的畫法改了 ⟹ 重產對照圖、跑 e2e。
- **FR-005**: 工具箱預設不放這顆（它是「把寫好的程式畫出來」用的，不是學生從頭拖的）——之後要放再說。

## Success Criteria
- **SC-001**: 學生語料 218 支，積木來回 0 不同（spec 213 量到 3）。
- **SC-002**: 2026-09-10 那幾個「載得進工作區」的形狀照樣載得進（第一百一十七條護欄全綠）。

## Assumptions
- 推薦的形狀（不需使用者決定，照 2026-09-10 的原則延伸）：語言宣告的結構性積木，像降級積木一樣不是元件；語意樹不變，formalize 本來就把敘述位置的運算式包成 `sExpr`。
- 替每一顆運算式元件加敘述形態（`form.axis = role`）不可行：什麼運算式都可能被當敘述用（`a == b;`、`x + 1;`）。

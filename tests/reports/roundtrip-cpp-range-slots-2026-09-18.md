## 🔴 缺陷一：`v.erase(a, b)` 走一趟積木回來變成 `v.erase(a)`

```
原始        v.erase(unique(v.begin(), v.end()), v.end());
走一趟積木  v.erase(unique(v.begin(), v.end()));
```

**那不是少一個引數，是換了一個意思**：刪一整段變成刪一格——**而它編得過**。

根因：`cpp:container_erase` 的兩個引數都放在**同一個接點** `key` 裡，
而積木上只有**一格** `KEY`。渲染器的 `inputs` 一格只接得住 `slots[0]`。

> **一個接點有落點，不代表那個落點裝得下它全部的孩子
> ——而「有沒有落點」是今天唯一被檢查的那一個。**

🟢 修法：第二個位置變成**它自己的接點** `key_end`（與範圍那一族同形），
兩端各有一格。第三十一條（投影遺失）從此看得到它們。

⚠️ **而修它的時候當場又犯了隔壁那顆膠囊警告過的錯**：第一版的判別只看
「erase ＋ 兩個引數」，於是把 `s.erase(2, 3)`（字串的「從第幾個字刪幾個」）
**搶走了**，三支測試當場紅。判準改成**問接收者的宣告型別**，查不到就讓開。

> 「一個只看引數個數的判別，在另一個型別剛好也收兩個引數時不會落空
> ——它會安靜地把那個東西當成自己的。」（`string_insert/lift.ts`，同一天寫的）

## 🔴 缺陷二：多宣告子的型別**從來沒有被記下來**

修完缺陷一之後，`vector<int> v, w;` 的 `v.erase(a, b)` **仍然**認不出是容器。

```
vector<int> v;      🟢 getType('v') → 'vector'
vector<int> v, w;   🔴 getType('v') → null
```

根因：宣告子是由具名策略（`liftSingleDeclarator`）**直接組出來**的，
不走 `liftWithContext` 的回傳點——而型別收集器掛在那個回傳點上。

> **一個掛在「每個 lift 回傳點」上的收集器，收不到那些沒有經過 lift 的節點
> ——而「由策略直接組出來」與「lift 出來」在樹上長得一模一樣。**

⚠️ 症狀是**型別查不到**，而查不到的下游全都走「判不出來就讓開」
——於是**同一個變數，宣告時多一個逗號就換了一種行為**，而沒有任何地方出聲。

🟢 修法：收集器也走 `slots.declarators`。

## 🟠 一支語料**刻意還是紅的**，而理由查證過

`w/APCS/e287.cpp`：

```cpp
int d2[10005][105];
fill(d2[0], d2[0]+10005*105, 1000000);   // 學生自己的註解：「將陣列全部填值」
```

那是**二維攤平**的慣用法：C++ 的列是連續的，所以 `d2[0]+N` 走進第二列。
而這個直譯器的二維陣列是**巢狀**的（每列自己一串格子），走不過那個邊界。

> **一個能表達「第 i 列」的模型，不一定能表達「跨過列的邊界」
> ——而 C++ 的二維陣列兩件事是同一塊記憶體。**

🟢 **這一刀讓它出聲**（在此之前它靜默地把那個容器撐成一百萬格——JS 的陣列會自己長）。
🔴 **何時該拔**：二維陣列從巢狀改成「一塊連續的格子 ＋ 每列一個位置」的那一刀。
⚠️ 那一刀**不會**同時解決另外兩支「讀進來的東西不知道要放哪裡：`cpp:array_2d_at`」
——那兩支是**左值**的問題，是另一族。

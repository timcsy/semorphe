## 🔴 這一關抓到的：積木與程式碼都好的程式，**按「執行」跑不動**

```
語義樹      🟢 修好了（rep(i,n) 展開成一顆計數迴圈）
積木        🟢 畫得出來
程式碼      🟢 一字不差
按「執行」   🔴 「這段程式有一處語法還不完整，所以還不能執行。」
```

**根因**：樹修復把樹修好了，**而原本那棵 AST 裡的 `ERROR` 節點還在**。
`lifter` 走到祖先（`func_def`）時仍然 `hasError`，把整支程式標成 `syntax_error`，
而執行前的閘（`core/diagnostics.ts` 的 `canExecute`）讀的正是那個標記。

> **一道「使用者按下去才會走到」的檢查，
> 任何直接呼叫下一層的測試都看不到它。**

🟢 **修法**：樹修復成功時登記那一段 AST，`hasErrorDescendant` 跳過它。

⚠️ **而修法本身踩了兩次，兩次都值得記**：

```
第一版  WeakSet<Node>       🔴 web-tree-sitter 每次存取 .children 都產生【新的】包裝物件
                               ——那個集合永遠回答「沒有」，看起來就像修復從來沒發生
第二版  if (node.hasError) return true 的早退
                            🔴 那個旗標是【往上傳播】的，於是「跳過修好的子樹」
                               那一行永遠走不到
```

> **一個用物件同一性當鍵的集合，在那些物件每次都是新的時候，
> 與一個空集合的行為完全相同。**

📌 五支常駐測試釘住它（含兩支 ★ 錨點：真的語法錯誤仍然要被擋、乾淨的程式照舊放行）。

## ⚠️ ② 的結果與我寫的判準不同——記下來，不改

我寫的判準是「**沒有碰過的那幾行要維持 `rep(...)`**」。實測：

```
碰過的那一顆    rep(k,3) → for (int k = 0; k < 5; k++)    🟢 對的
沒碰過的那幾行  rep(i,n) → for (int i = 0; i < n; i++)    ⚠️ 也一起變了
```

**理由**：碰一顆積木會觸發**整份程式**的 blocks→code 重生，
而 `layoutHints` 不會經過積木（那是它的契約：「投影記住它，積木看不到它」）。

🟢 **所以這不是缺陷，是那個契約的鈍邊**——同一個性質在
`cout << (…)` 的括號註記與 Python 的固定組合上完全一樣。
⚠️ 而要讓它變細（只有被碰的那一顆失去拼法），拼法就得住到積木上，
那會讓「積木看不到它」這句話變成假的。

> **一個「改過就不算數」的註記，它的粒度是【重生的粒度】，不是【改動的粒度】。**

## ③ 並排才看得出來的那一個

```
define constant [MAX] as [100]                      同族（小寫開頭）
Define expandable template [rep] with parameters …  我的（大寫開頭，照規範）
```

規範是「英文用大寫開頭的動詞短語」——**我的對、同族的不對**，而**並排就不一致**。
改了同族那一個字母（`define` → `Define`）。

> **標籤的一致性只有【並排】看得出來——而 API 答得出每一個字。**

⚠️ **而第三格裝的是一整行程式碼**（`for(int i=0;i<n;i++)`）：
在抽屜裡會被右緣切掉，**而拖到畫布上是完整的**。判定：可接受
（抽屜本來就會捲），不改——改的代價是把預設值變短，而那讓它變得不像真的用法。

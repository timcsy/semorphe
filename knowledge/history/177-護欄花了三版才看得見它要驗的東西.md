# 177 · 一條護欄花了三版才看得見它要驗的東西

**日期**：2026-08-26

## 起點：使用者看著流程面板說「上面的名稱要設計過」

畫面上是（一個字都沒改）：

```
func_def      name: main    return_type: int
include       header: iostream
loop_count    from  to  inclusive: FALSE   var_name: i   body
```

四處洩漏：標題是**元件身分的後半段**、欄位名是**原始的屬性鍵**、
值是**下拉的 value**（`FALSE`，而積木上那一格顯示「到（不含）」）、
接點名是**插槽的原始名**。

`principles.md:126` 逐字：「**使用者看得到的所有文字都是介面**」。

> ⚠️ **`FALSE` 比其他三個更糟**：它不只是內部詞彙，它是**同一個真實的另一個投影
> 說了不一樣的話**。

## 🔴 而在動手之前，我差點重做一件使用者已經否決過的事

我看著截圖推理出「運算式不該是盒子，它該折進父節點的欄位」，
命名的母體就從 332 → 167。而 `core/flow/node-graph.ts` 的**檔頭第 6 行**記著：

> 「我要的比較像是 **Node 然後有 Flow 可以接線可以呈現資料流**的那種，
>  **不是傳統意義上的『Flow Chart』**。」

```
流程圖   一個語句一格，「x > 3」是格子裡的字
節點圖   「>」自己是一個節點，左右兩條線接進來——資料流看得見
```

**`literal_number` 自己是一個盒子是刻意的。**
我是**看著畫面從頭推理，而沒有先讀那個檔頭**。

> **一個看起來像缺陷的設計，多半在某個檔頭裡有它的理由。
> 而截圖不會告訴你那個理由存在。**

## 三個量測決定了形狀

```
299 顆有 MSG0，而砍「第一個 % 之前」有 96 顆是【空字串】  → 導出那條路不通
導出標籤鍵（cpp:func_def → U_FUNC_DEF_MSG0）只中 14/233   → 鍵是每顆各自取的
屬性鍵 69 個 ／ 插槽名 121 個，**重疊 15**                → 它們是同一份詞彙
```

第三個是設計的關鍵：**「這個具名的位置叫什麼」是同一個問題**，
是屬性還是接點是**結構**差別不是**命名**差別。

## 兩個數字，而它們回答不同的問題

```
硬性零   有沒有代號上畫面      —— 原則。補一條【退路】就成立
棘輪     有幾顆真的被設計過     —— 進度。507 條文案寫不完在一刀裡
```

> **混成一個數字的話，「補一條退路」會看起來像「設計了 233 個名字」。**

退路是**積木的整句話**（插槽換成「…」）——它仍然是介面文字。
而位置名**沒有退路**（一個插槽在積木上根本沒有名字，它是句子裡的一個空格），
所以沒設計過就**不顯示名字，只顯示值**（P4 漸進揭露）。

## 🔴 而這條護欄花了三版才真的看得見

| 版 | 它說 | 而真相是 |
|---|---|---|
| 一 | 205 處違規 | **假的**——我在測試裡把 `label ?? key` 退回那個鍵，量的是自己補的預設值 |
| 二 | 0 違規 | **假的**——建圖時沒接埠，走不到退路那條路，標題一律 `null` |
| 三 | 0 違規 | **假的**——替身用 `component.json` 而 `blockDef` 在 `forms/blocks.json` |
| 四 | 233 顆 | 真的。而畫面上印的是 `%{BKY_C_INCLUDE_MSG0}` |

每一版的教訓都不同，而它們是同一個家族：

> **一個在判定前先補上預設值的護欄，量的是它自己補的那個值。**
> **一條只驗「沒有宿主」那條路的護欄，驗不到宿主接上之後的樣子。**
> **一個與被測者犯同樣錯誤的替身，會誠實地回報「沒問題」。**

⚠️ 而第五個缺陷是**開瀏覽器**抓到的，不是護欄：
`blockDef.message0` 是**原始的 JSON 字串**，`%{BKY_X}` 要等 Blockly 的
`jsonInit` 才解析——我在註解裡寫著「拿到時已經展開過」。

> **一個「應該已經處理過」的假設，寫在註解裡不會讓它成真。**

而三版護欄都放它過了，因為判準只認「等於那個鍵」。
→ 判準補寬成三種形狀：等於那個鍵 · 含 `%{`／`BKY_` · 純大寫常數。

## 第六個：`FALSE` 為什麼換不掉

屬性 `inclusive` 透過 `renderMapping.fields` 對到積木欄位 **`BOUND`**，
而埠拿 `inclusive` 去比 `args0` 的名字。

🔴 **而護欄的替身犯一模一樣的錯**，所以報表說 0 而畫面上 `FALSE` 還在。

→ 修法不是各修一份，是**把查找收成一份**（`labelSourceFromSpecs`），
面板與護欄**共用**。⚠️ 這正是「兩份會分岔」的教訓在同一輪內現形。

## 順帶結清：`appearance` 那一格

`FlowLabelSource` 就是路線圖那條「面板只 import 協定」的 `appearance` 埠。
⚠️ 而查證發現**它本來就已經是注入的**（`import type` ＋ 建構子參數）
——我延後了它四輪，而理由每一輪都是讀路線圖而沒讀那三行。
這一刀只是把它**具名**。

## 第二刀：`EditableView` 契約——而護欄第一次跑就改了它的形狀

路線圖驗收逐字：「`EditableView` 契約長出來，而流程面板是它的第二個實作
（今天 `extractSemanticTree()` 是 `blockly-panel` 的方法，不是契約）」。

### 🔴 我的第一版護欄禁錯了東西

第一版寫成「**組裝點不得叫一個具體面板的名字拿樹**」，抓到 `app.ts` 三處。
而那三處還一起用 `getBlockMappings()`／`staleReason`——它們是
**積木→程式碼**那一條特定的路，而 `app.ts` 是**組裝點**，
組裝點本來就認得具體的東西（[167](167-一個都不認得不是降級是沒接上.md)）。

> **一條護欄如果禁止的是「組裝點做它份內的事」，它擋的不是缺陷，是分工。**

改成簡報裡原本計畫的那條：**旗標↔能力的綁定**
（宣告 `editable: true` 就必須交得出真相）。它不需要第二個實作就成立。

### 🟢 而改對之後，它第一次跑就抓到一顆

```
掃到視圖宣告 5 ｜ 其中可編輯 2 ｜ 缺那個方法 1
🔴 monaco-panel
```

`monaco-panel` 宣告 `editable: true` 而**交不出樹**——因為程式碼那側的樹是
**解析出來的**（`syncCodeToBlocks(code)` → lifter），不在那個視圖手上。

```
積木     手上就是結構   → 交【樹】     syncBlocksToCode(tree, …)
程式碼   手上是文字     → 交【文字】   syncCodeToBlocks(code)
```

> **「可以當真相來源」與「手上有一棵樹」是兩件事，
> 而把它們合成一個方法，會逼其中一種視圖說謊。**

→ 契約改成 `readSource(): EditableSource`（判別聯集 `tree` ／ `code`）。

⚠️ **是護欄改了設計，不是設計改了護欄**——而那正是 `build-guardrail` §6.5
「第一次跑必須是紅的」要買到的東西：**那一次紅，買的是設計的修正。**

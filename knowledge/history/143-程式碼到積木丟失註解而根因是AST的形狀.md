# 143　程式碼到積木丟失註解——而根因是 AST 的形狀

**日期**：2026-08-24 ｜ **交付**：區塊第一行的註解不再掉 ＋ 埋在運算式裡的整句誠實降級
**前一則**：[142](142-開機不准喊系統錯誤.md)
**觸發**：使用者——「我還發現 **Python 程式碼到積木會丟失註解**」

## 先量，量出一個很利的邊界

一段一段量「原文幾句 → 樹幾顆 → 積木幾顆 → 產回幾句」：

```
✔ 區塊裡最後一行的註解      1｜1｜1｜1
✘ 區塊裡第一行的註解        1｜0｜0｜0      ← 掉在【抬升】那一段
✔ 頂層第一行的註解          1｜1｜1｜1
```

**邊界利到不像是邏輯錯誤，像是結構問題。** 於是去看 AST：

```
if_statement @0
  identifier @0 "a"
  :(anon)    @0
  comment    @1  "# 首"   ← 掛在【語句】上
  block      @2           ← 而不是在區塊裡
    expression_statement @2
```

> **一個「同一列」的判準，答得出「它屬於哪一行」，答不出「它屬於誰」
> ——而後者才是要收它的人。**

修法：核心收**直接子節點的所有註解**（不只同一列那顆），
`if`／`try` 的子句策略同樣放寬。四種區塊 ＋ 兩種子句一次修好。

## 而「沒有一行放得下它」的那一種，改成誠實降級

```python
x = (1 +  # 加
     2)
```

這顆註解埋在運算式裡，**沒有任何一行可以放它**——在此之前它被安靜丟掉
（產出 `x = (1 + 2)`，合法、來回無誤、而使用者打的字沒了）。
改成整句降級：原文逐字留著，看得見的灰色（P6）。

## 🔴 而判準寫錯了三次，每一次都是同一種錯：**把「形式」當成「內容」**

| 版本 | 判準 | 怎麼爆的 |
|---|---|---|
| ① | 「跳過底下有 `block` 的子樹」 | `block` 是 **Python** 的節點名，C++ 是 `compound_statement` → **C++ 整批誤降級（52 支紅）** |
| ② | 「原文的註解字串在樹裡找不找得到」 | `metadata.rawCode` **每顆節點都有**，於是永遠找得到 → 永遠說「沒掉」 |
| ③ | 剝掉開頭的 `#`／`/` 再比 | Arduino 的檔頭 `/* … */` 對不上 → 誤降級 |

🟢 收斂到的判準：**把所有非文字字元正規化掉再比**——註解符號、空白、換行全消失，
剩下「使用者打的那些字」。**這個判準不認識任何語言**（P9）。

> **一個寫死了某個語言節點名的判準，放在核心裡就是一顆定時炸彈
> ——而它會在第二個語言走到那一行的那天爆。**

## 還有一個指數的 bug

放寬「收直接子註解」之後，`_compound` 節點**把自己的子註解又收了一次**
——而那些註解已經被當成語句收過了：

```
一次來回  // bright enough, lamp off  ×2
二次來回  // bright enough, lamp off  ×4
```

**症狀不是「多一行」，是一段程式碼每存一次就長大一倍。**
🟢 修法一行：`_compound` 的主體就是它自己的子節點，不必再收。

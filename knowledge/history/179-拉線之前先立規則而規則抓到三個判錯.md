# 179 · 拉線之前先立規則——而那條規則自己判錯了三次

**日期**：2026-08-26

## 起點：(f) 必須先於 (c)

路線圖上 (c) 是「改接線」、(f) 是「畫一條不是父子關係的線 → 誠實拒絕」。
順序看起來是 (c) 先，而**反過來才對**：

> 先做拉線的話，「這條線存哪」會在寫 UI 的時候被順手決定，
> **而最順手的地方就是 `metadata`**。

`draft/語義樹只有樹沒有邊 §六` 逐字點名過那條路：

> 繞過去的方法很誘人：把接線存進 `metadata`。
> **那會讓邊變成一個沒有型別的角落。**

→ 規則（`core/flow/connect.ts`）與護欄（第八十條）先蓋，(c) 只能照著它做。

## 語義樹只有樹，所以線只有一種

```
🟢 真的   「讓這一顆變成那一格的子節點」
🔴 假的   兄弟連兄弟 · 連到自己的祖先 · 連到一個沒有宣告的位置
```

**那些不是「還沒支援」，是【表達不出來】。**

> **一個表達不出來的東西，誠實的處置是說出來，不是找個角落塞進去。**

而拒絕要回答 `history/017` 那句話（「被拒絕的東西去哪了」）
——四種理由各一句人話，每一句都以「**你的程式沒有被改動**」結尾。

## 🔴 而那條規則自己判錯了三次，每一次都是【開瀏覽器】抓到的

### ① 可拉的接點：跳掉了唯一能當來源的那一個

`attachWire` 寫成「`__` 開頭的內部接點一律跳過」。而 `__out__`
**正是運算式那一端要抓的**——於是畫面上一條線都接不上。

> **一個「跳過內部接點」的規則，跳掉了唯一能當來源的那一個。**

### ② 方向：用 `side` 判，而身體的接點是掛在父節點上的 `out`

第一版寫「`side === 'in'` 的那一端是目標」。而**身體**的接點
（`body`／`else_body`）是掛在**父節點**上的 `side: 'out'`，它仍然是目標。
於是「把一句話放進迴圈的身體」永遠被拒絕。

→ 改成**由「哪一端是具名的格子」決定方向**，不由 `side`。

### ③ 型別：宣告一直寫著，而沒有人讀

實測拉一條線之後畫面變成 **`int main(int)`**——那個 `0` 被搬進了
`cpp:func_def` 的 `params`。規則只判「語句 vs 運算式」，
而宣告裡明明寫著 `params: "param_decl"`。

> **一個宣告了而沒有人讀的型別，與沒有宣告是同一件事。**

→ `slotsOf` 多回一格 `allowed`，規則多判一關。
⚠️ 而那一格**在此之前零消費者**——這是這個 repo 反覆抓到的形狀，
今天它的症狀是「接得上一條荒謬的線」。

## 順帶：一個機制的存在理由，在今天失效了

`node-graph.ts` 的檔頭寫著「空的插槽不長接點」，理由逐字：

> 這與「節點編輯器都把接點畫滿」不同，理由是**這張圖是導出的，不是接出來的**：
> **使用者不會去接那個接點**，它只會是雜訊。

**(c) 讓那句話變成假的。** 沒有接點就沒有地方下手。

→ 「空插槽長不長接點」變成呼叫端的決定（`opts.emptySlots`）：
唯讀照舊、可編輯長出來。**而原本那個理由留在檔頭上，標明它哪天失效的。**

## 而第四十九條護欄抓到我漏了注入

第八十條有一支掃描（`metadata` 那條），而我沒給它「★ 注入」。
第四十九條逐字：「這些護欄會掃東西、會數數，而**沒有人證明過它的偵測器
認得出違規**。偵測器壞掉時它們全綠。」

⚠️ 而補上注入之後**當場抓到偵測器的一個漏洞**：
`metadata?.connections` 沒被認出來——正則寫成 `(\?\.)?\s*\.`，
**要求了一個多餘的點**。

> **注入不是形式：它抓到的第一個東西，是偵測器自己。**

## (d) palette 與 (e) 重排——而 (d) 的驗證留了一個誠實的缺口

### (d)：「讀同一份登錄表」有兩種做法，只有一種擋得住分岔

路線圖驗收逐字：「流程的 palette 與積木的工具箱**讀同一份登錄表**（不得各寫一份）」。

```
🔴 各自從登錄表算一次   同一份來源，兩份【篩選與排序的邏輯】
                        ——分岔的症狀是「工具箱有而 palette 沒有」，
                          而**兩邊都看起來對**
🟢 讀工具箱【產出的那個東西】  同一份來源、同一份邏輯、同一個順序
```

> **「用同一份資料」擋不住分岔，「用同一份結果」才擋得住。**

⚠️ 代價說得出來：palette 因此**繼承工具箱的分類與順序**，
而流程視圖將來若要不同的分組，那是一次**明確的**分道。

### (e)：一條線看起來像什麼，與它在真實裡是什麼

`A.__next__ → B.__in__` 讀作「B 接在 A 後面」——看起來是一條線，
而它**不是父子關係的改變**（A 與 B 是兄弟）。
它仍然表達得出來：**B 成為 A 的父親的那個身體裡、A 的下一個**。

→ 所以它有自己的規則（`tryReorder`），與 `tryConnect` 分開。
⚠️ 混在一起的話兩邊的拒絕理由會互相污染
——「不是父子」對重排來說根本不是一個問題。

## 🔴 兩個「看起來什麼都沒發生」的缺陷

### ① 用 DOM 索引去對應模型

`portUnder` 拿 `.fc-port` 在 DOM 裡的**索引**去索引 `node.ports`。

> **一個靠位置對應模型與畫面的東西，
> 會在其中一邊多插一個元素的那天安靜地錯開。**

（同一族：`build-guardrail` §11「鍵不要用行號——它報的不是違規，是 diff」。）
→ 改成把 `data-port` 寫在元素上，用**鍵**找。

### ② 修「被擋住」時動了那個擋住的東西

palette 是拖曳的起點，所以它**必然壓在圖上**，
而 `elementFromPoint`（單數）打到的是它。

第一版的修法是「拖曳中把 palette 設成 `pointer-events: none`」
——而那會把**已經捕捉指標的那個元素**移出命中測試。

> **修一個「被擋住」的問題時，不要動那個擋住的東西的狀態
> ——繞過它去看底下有什麼。**

→ 改用 `elementsFromPoint`（複數）穿過去找。

## ⚠️ 而 (d) 的驗證留了一個誠實的缺口

合成 `PointerEvent` 走通了（樹尾多一顆 `cpp:var_declare`、程式碼跟著變），
**而真人滑鼠拖曳我沒有驗成功**。

實測 `down: 0, mdown: 0, up: 1`——**按下沒有落在 chip 上**（放開有）。
看起來是自動化的座標對不上，不是產品缺陷。

> **而「看起來是」不能拿來宣稱它對。**

→ 路線圖上那一格標成「邏輯已驗、**真人手勢未驗**」，
而不是打勾。⚠️ 這一格要一支 e2e 來收，那是下一刀。

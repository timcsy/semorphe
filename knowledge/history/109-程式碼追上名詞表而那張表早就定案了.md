# 109 — 程式碼追上名詞表，而那張表早就定案了

**日期**：2026-08-20 · **狀態**：決定已記，實作分階段
**人拍板**：使用者，2026-08-20

## 決定

**協定的名詞統一成「元件」，`概念` 從詞彙裡退場。**

```
componentId          → componentId
ComponentRegistry    → ComponentRegistry
元件代數（文件）    → 元件代數
SemanticNode.componentId → componentId   ← 使用者 2026-08-20 明確點頭
```

## 為什麼——判準是使用者給的，而它比我提的強

> 「因為之後**硬體要加進來**，而為了整體協定的一致性，我希望把原本的概念這個詞都改成元件，
> 因為**概念不適合給硬體那邊用**。」

```
「電阻是一顆元件」   ✅ 讀得通
「電阻是一個概念」   ❌ 讀不通——它是一個東西，不是一個想法
「if 是一顆元件」    ✅ 讀得通（它有五路：lift／generate／render／extract／execute）
```

> **一個詞如果在協定要涵蓋的範圍裡有一半讀不通，那它不是統一詞彙的候選人。**

⚠️ 而我一度提議「把 `概念` 空出來給**等價類**用」——**在這個判準下那也是錯的**
（一組電阻的等價類叫「概念」一樣怪）。🟢 而等價類**早就有名字**：
`concepts/等價與觀察集.md`。所以 `概念` 可以**完全退場**，不必替它找新工作。

## 🔴 而這條決定【早就定案了】，是我沒查到

`concepts/元件.md:438` 的「**名詞表（跨域唯一）**」逐字：

| 角色 | 中文 | 程式 | 取代 |
|---|---|---|---|
| 身分鍵 | — | **`componentId`** | `componentId`、`typeId`、`SemanticNode.concept` |
| 登錄表 | 元件登錄 | `ComponentRegistry` | `BlockSpecRegistry` |

而它下面還有一整張「**現況落差（採用此表要改什麼）**」。

⚠️ **我上一輪對使用者說「我沒有在 knowledge/ 裡讀到這條決定的轉變記錄」——那是錯的。**
我只查了 `history/`，**沒查名詞表**。

> **一條決定可以住在【概念檔的名詞表】裡，而不是 `history/`
> ——查「這件事決定過沒有」時，只翻 `history/` 會漏掉它。**

🟢 而使用者記得（「我當時以為你已經同意了」）——**人的記憶是對的，我的檢索是錯的**。

## 🔴 為什麼它撐到今天沒被執行

```
活在名詞表        ✅ 定案且有落差表
活在 history/     ❌ 沒有轉變（所以我查不到）
活在護欄裡        ❌ 沒有任何東西擋舊名
活在程式碼裡      🟡 一半——函式名改了（isValidComponentId／allComponentIds），
                     而【資料欄位】沒改
```

⚠️ 後果是具體的：**我 2026-08-20 建第一顆 Python 膠囊時照抄了 `componentId`**
——我讀得到程式碼，讀不到那張表。

> **一個決定如果沒有機械檢查在守，它會被「照抄現況」慢慢反轉。**

## 🔴 兩件【不在這一刀】而必須被看見的事

### ① 根公理的措辭要不要動——`concepts/元件.md` 明寫著這條

> 「根公理現行措辭是『**元件節點**和關係邊』『節點的**元件身分**和屬性是語義』。
> 採用這張表意味著根公理的措辭要跟著動（元件身分 → 元件身分）。
> **根公理的 churn 應趨近零，此事 MUST 由人拍板，不得順手改。**」

**待拍板。這一刀不碰 `principles.md` 的根公理。**

### ② 名詞表要的其實是【合併兩個登錄表】，不只是改名

表上寫 `ComponentRegistry` **取代 `BlockSpecRegistry`**，而 `ComponentRegistry`
出自 `元件代數.md`。今天有**三個**登錄表：

```
ComponentRegistry           執行期索引（loadFromJSON）
BlockSpecRegistry         投影索引——名詞表批評它「以投影命名登錄表」
component/registry.ts     膠囊來源（glob）
```

⚠️ **合併是另一刀**。這一刀只把 `ComponentRegistry` 改名成 `ComponentRegistry`
（它是「承載意義的單位」的登錄表，名字對得上），
而 `BlockSpecRegistry` 的收斂**留給那一刀**。

## 🔴 而「概念」這個詞不是全域取代

知識庫裡 `概念` 出現 **1005 次／125 檔**——而其中很多是**日常語義**
（「這個概念很難懂」）。⚠️ **盲目全換會改壞意思。**

**只改【術語】**：`元件代數`→`元件代數`、`元件身分`→`元件身分`、`componentId`→`componentId`。

## 🔄 補記（同日）：根公理也改了，而它走了特別路徑

使用者中途拍板：「**我拍板，可以動根公理**」。

```
之前   程式是由「概念節點」和「關係邊」組成……每個節點 =（概念類型, 屬性, 子節點）
之後   程式是由「元件節點」和「關係邊」組成……每個節點 =（元件身分, 屬性, 子節點）
```

⚠️ **變的是措辭，不是公理**——節點仍然是（身分, 屬性, 子節點），投影仍然是投影。
🟢 而理由寫在 `principles.md` 的根公理**下方**（不是 commit 訊息裡）
——knowie：根公理的變更要留下**可追的理由**。

```

```

🟢 **而 FR-006 過了：34 個基線檔的數字，差異 0。**

> spec `140` 有過相反的病歷：改名讓護欄報「改善了 73 → 51」，而那是假的。
> **所以這一刀先拍了基線快照，改完逐項比對。**

`conceptId` 認身分引用——改完之後它會把身分引用判成「非身分」，**數字自己降下去**。

> **一條用名字認東西的檢查，在改名那天會安靜地失效。**

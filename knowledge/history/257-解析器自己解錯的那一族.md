# 257 — 解析器自己解錯的那一族

> 2026-09-19｜語料 4 支，而它們是唯一一批「往下追的每一層都是對的」

## 這個專案的每一層都假設樹是對的

lift 只問「這棵樹是什麼意思」。那個假設成立了兩百多刀，直到量語料時
剩下的 21 支裡有 4 支的錯誤訊息**指著一段看起來完全正常的程式**：

```
RUNTIME_ERR_UNRECOGNIZED_CODE ｜ ans < eps && ans >
RUNTIME_ERR_TYPE_MISMATCH     ｜ 這個東西不能被指定值（它不是一個位置）
```

第一個訊息的引文**在一個 `>` 上斷掉**——那是唯一的線索。

```
寫的              tree-sitter 給的            C++ 說的
!K--              (!K)--                      !(K--)
a < b && c > -d   template_function<…> - d    (a<b) && (c>-d)
```

> **一個「解析器解錯了」的缺陷，長得與「我 lift 錯了」一模一樣
> ——而往下追的每一層都是對的。**

## 🔴 判準：修得起來才修，而且要證明得出它恆真

這裡**不做啟發式**。兩條規則各有一個「它不可能是別的意思」的證明：

```
① (!K)--／(-K)--／(~K)-- 在 C++ 裡【根本不合法】
   後置 ++／-- 的運算元必須是可改的左值，而 !／-／~ 的結果是純右值。
   ⟹ 看到這個形狀，唯一合法的讀法就是 !(K--)。

② 樣板名是一個【宣告過的變數】時，它不可能是樣板。
   ⟹ 那個 `<` 是小於號。
```

⚠️ 而 `*p--` 與 `&x--` **刻意不收**：`(*p)--` 是合法的 C++，證明不成立。
（實測 tree-sitter 對那兩個本來就解得對。）

> **同一條重寫規則，對「本來就不合法」與「合法但少見」的成立理由不同。**

## 🔴 「重組」試過，而它在第三個 `&&` 上就錯

```
a < b && c && d > -x
  E = b && c && d 的頂層切點在【最後一個】 &&（左結合）
  重組 ⟹ (a < (b&&c)) && (d > -x)      ← 錯
  真正的 ⟹ ((a<b) && c) && (d > -x)
```

> **自己算一次優先級，等於在解析器旁邊養第二份文法——
> 而兩份文法不一致的那一天，紅的不會是這裡。**

🟢 處方是**讓 tree-sitter 再解一次**，而只加一對不可能改變語義的括號
（把那個名字包起來）。括號運算式不能當樣板名，於是它只剩一種讀法。
九種形狀實測全對。

## 🔴 三個坑，每一個都讓「修好了」變成假的

### ① 掛錯層：手寫 lifter 一次都沒被叫到

第一版把修復寫進 `binary_expression` 的手寫 lifter。
而 `PatternLifter` **跑在手寫 lifter 之前**，`cpp/arithmetic/lift-pattern.json`
先認領走了 `template_function - d`。單元測試全綠（規則函式自己是對的），
而**語料一支都沒修好**。

> **一個掛在「手寫 lifter」上的修復，修的是那些沒有樣式認領的節點
> ——而解析器解錯的地方，樣式照樣認領得很順。**

🟢 於是有了 `core/lift/ast-repairs.ts`：**在所有辨識之前**問一句
「這棵樹是不是一開始就解錯了」。它與 `post-processors.ts` 是兩件事：

```
後處理   in >> a   樹是對的，而「位移還是讀取」要看型別   → 改判
樹修復   !K--      樹說 (!K)--，而 C++ 說 !(K--)          → 換一棵樹
```

### ② 判準照著我舉的例子長，不是照著那個病

第二版寫「`binary_expression` 的**左**子節點是 `template_function`」。
語料的 `AP325/7/7_3.cpp` 是：

```cpp
return (i>=0 && i<m && j>=0 && j<n);
//              └──── 被當成樣板，而它在 && 的【右】邊
```

後面那個 `=0` 於是變成**指定值**，整句被 lift 成「把 0 指給一個邏輯運算」。
那一版跑完語料，這支照樣紅，**而它紅的訊息與修之前一模一樣**。

> **一條「左子節點是 X」的規則，量到的是我舉的那個例子的形狀，不是那個病。**

### ③ 我插進去的括號留在使用者的程式裡

`cpp_unwrap_parens` 把括號拆掉並記成 `layoutHints.parenthesized`，
產生器再照它放回去。於是 `ans < eps` 產成 **`(ans) < eps`**。

那條樣式自己的 `_why` 逐字：「只拆不記的話…**而那不是使用者寫的東西**」。
反過來也成立：**我插進去而使用者沒寫的括號，記著就是替他加了一對。**

🟢 修復要負責擦掉自己的痕跡，而**擦的依據是位置不是名字**：
`ans < eps && ans > -eps` 裡那個名字出現兩次，照名字擦會擦錯一個
——而那個錯的症狀是**另一個位置憑空多出一對括號**，不是紅。

## ⚠️ 順手抓到的兩件事

**a. 一個說不出「誰」的錯誤訊息，讓每一次重複發生都要從頭查一次。**
`resolvePlace` 原本只說「這個東西不能被指定值」。語料裡兩支撞到它，
而「這個東西」是**不同的元件**。追第二支時我花了一輪去讀那支程式，
而答案（`cpp:logic`）本來就在手上。加上身分之後，`7_3` 一行就招了。

**b. 型別宣告管不到測試的合成物件。**
`AstNode` 宣告 `parent: AstNode | null`，而單元測試的合成節點給 `undefined`。
照著宣告寫 `n !== null` 的症狀是 **28 支單元測試同時炸**，而那些測試
根本不碰這條規則。

## ⚠️ 消毒器抓不到 `std::string` 的越界（順手量到的）

`tioj_godteach/pratice_question/8_toj485_AC.cpp` 讀 `cin >> n >> s`，
而測資產生器把 `n` 與 `s` **各自生**，於是 `s[n-1]` 越界。
那與 [[256-把東西移出缺陷帳要外部權威]] 那五支是同一種病，而消毒器**沒有指名它**：

```
（無旗標）                                   沒叫
-D_LIBCPP_HARDENING_MODE=…_DEBUG            沒叫
-D_GLIBCXX_DEBUG                            沒叫
```

`std::string` 的小字串最佳化把那幾個位元組放在物件**裡面**，所以 ASan 看不到。

🔴 **照 256 自己寫的規則，那兩支仍然算我們的帳**——
「消毒器只能證實，不能否證」那一條如果反過來用，它就變成一台漂白機。

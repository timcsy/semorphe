# 314 · 積木的收合不再是第二個機制——它成了共享狀態的投影，並且進了存檔

> 日期：2026-11-01（spec 188，vision〈分子〉「積木／程式碼的投影」的積木那一半）
> 轉變：Blockly 原生的收合（右鍵「收合這一塊」）原本是**第二個收合機制**——只存在 `blocklyState` 裡、從程式碼重畫就攤開，
> 與流程面板（spec 187）各管各的。draft〈分子與粒度切換〉早就點名：「否則 B 到的那一天會有兩個收合機制，而沒有人記得哪個是哪個」。

## 做法：同一份狀態，Blockly 原生的收合當它的形態

```
狀態 → 積木   每次語義更新、每次廣播之後照狀態 setCollapsed（蓋 BUS_GROUP、不進復原堆疊）
積木 → 狀態   使用者用 Blockly 選單收／展（BUS_GROUP 以外的 collapsed 變更）→ granularity:request
收編          積木上收著、狀態裡沒有、上一次也不是照狀態收的 → 請求
```

「上一次照狀態收的」那一格是必要的：流程面板展開一塊時，積木上那塊還收著——沒有它就分不出「該跟著攤開」與「該收編」。

## 存檔 v25：`collapsed`（鑰匙）

與 `flowLayout` 同一個性質：**導不出來 ⟹ 狀態**（沒有人算得出使用者想收哪幾塊），存鑰匙、不吃 `codeHash`、對不上就安靜地掉。
24 → 25 只改版號，不補空陣列。自動載入與匯入兩條路都還原。

## e2e 抓到的那一個：收編要在【載入的當下】做

第一版收編寫在「每次語義更新之後」，而舊存檔升級後積木照樣被攤開。原因是開機順序：

```
載入 side-car 的積木（帶著 collapsed）→ 工作區「還沒畫過」，不往外同步 → 從程式碼重畫 → 收合沒了
```

收合**只在載入那一刻的積木上**。改成在 `setState` 當下從積木抽出一棵樹、算出收著那幾塊的鑰匙，等第一次語義更新對到新樹再請求。
（⚠️ 載入時事件是關著的，所以「使用者收／展」那條路也走不到。）

> 這一段是補驗收時才寫的：原本的 e2e 只驗「新存檔重開」，那條路走的是存檔的鑰匙，**不經過收編**——第一版的缺陷在它底下是綠的。

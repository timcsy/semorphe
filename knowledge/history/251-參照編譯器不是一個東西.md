# 251 — 「參照編譯器」不是一個東西

**2026-09-18** · 使用者只說了三個字：「CI失敗」

## 讀數

```
本機   npm test   7144 綠，0 紅        （四次合併，每一次都跑了）
CI     npm test   7 紅                （四次合併，每一次都紅，而我一次都沒看）
```

而那七支的錯誤訊息是：**「🔴 參照編譯器收不下（測試自己的問題）」**。

## 一、兩台參照編譯器

```
本機   Apple clang（libc++）    <set> 遞移帶進 <deque>、<map> 帶進 <queue>／<tuple>
CI     GNU g++（libstdc++）     不帶
```

於是 `deque<int> d{1,3};` 在一個只 `#include <set>` 的檔案裡，
**在我的機器上編得過**。

> **本機那一台比 CI 那一台寬鬆的地方，量不出來的不是缺陷
> ——是【我的判準有多寬】。**

⚠️ 而那句錯誤訊息**是對的**（確實是測試自己的問題），
只是它說不出**是哪一台**參照編譯器——所以它在本機上永遠不會出現。

## 二、它咬過兩次，而第一次的修法讓第二次照樣發生

2026-09-17 加 `multiset` 那三題時缺 `<set>`。當時的修法是**補上那一個標頭**，
並在旁邊寫了一句：

> ⚠️ **這一行是【判準的一部分】**：少一個標頭，那一題會以
> 「參照編譯器收不下」紅掉，而訊息會說「測試自己的問題」。

那句話描述得很準確——**而它描述的是一個陷阱，不是一個想要的性質**。
2026-09-18 缺 `<queue>` 與 `<tuple>`。

> **補一個實例不會讓下一個不發生。
> 而一句寫得很好的警告，與一個機構的差別，是後者不需要有人記得它。**

🟢 處方早就在這個 repo 裡：`tests/fixtures/refcc-shim` 的 `bits/stdc++.h`
（它 2026-09-16 為了語料而做——206/218 支學生程式用它）。
本機由 `SEMORPHE_REFCC_INCLUDE` 指過去，CI 上用真的 GCC 標頭。
**同一輪加的 `fuzz-cpp-containers-2.test.ts` 用了它，而它在 CI 上是綠的
——證據當時就在那一份 CI 報告裡。**

## 三、而真正的缺口是「沒有人去看」

CI 從第 182 刀起紅，**連續四次合併**。每一次我都：
跑了全套（7000+ 綠）· 跑了 54→119 條護欄 · 量了語料五個面向 · 重產了對照圖 ·
開了瀏覽器驗收——**而沒有按過一次 `gh run list`**。

⚠️ 這與 2026-08-25 那天**一模一樣**（CLAUDE.md 逐字記著）：
「一天改了六刀 UI，每一刀都跑了全套（5600+ 綠）＋ 開瀏覽器實測，
**而 e2e 一次都沒跑**——CI 從那天 00:20 起紅，19 支，是使用者發現的。」

> **一條「本機全綠就等於好了」的習慣，量到的是本機那台機器的寬鬆程度。**

🟢 機構：
- CLAUDE.md 的「什麼時候跑什麼」多一列：**push 之後 `gh run list --limit 3`**
- 第 120 條護欄 `audit-refcc-headers`——手列標頭的檔數，棘輪（8 → 2）

⚠️ 剩下的 2 個**各有理由**：`audit-behavior-error` 的標頭多樣性**本身就是語料**；
`run-cpp-no-orphans` 量的是逾時後的孤兒行程，而 `bits/stdc++.h` 會讓它變慢
——**而慢正是它在量的東西**。

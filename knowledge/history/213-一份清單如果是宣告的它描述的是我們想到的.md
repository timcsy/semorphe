# 一份清單如果是宣告的，它描述的是「我們想到的」

**日期**：2026-09-06 · **spec**：`specs/176-types-grow-with-code/`

## 轉變

```
舊  型別的下拉 ＝ 語言宣告的七個內建型別（模組載入時就定了）
新  型別的下拉 ＝ 那七個 ∪ 【這支程式真的用過的】
```

## 為什麼變

vision「開放值域的欄位要寫得出來」的最後一條驗收，逐字：

> 選項跟著程式長——用過的型別會出現在其他積木的下拉裡（**導出的，不是宣告的**）

而它的現場是這樣的：學生寫 `struct Point { int x; int y; }; Point p;`，
然後拉一顆變數宣告積木——**型別的下拉裡沒有 `Point`**。

🔴 **而它不是一個正確性的 bug。** 那個型別**打字寫得出來**
（`dynamic-dropdown-field` 早就「認不得的值不會被換掉」，那一半在
2026-08-26 就兌現了）。壞的是**可發現性**：他知道自己宣告過，而清單不知道。

> **一份「這個欄位可以填什麼」的清單，如果它是宣告的而不是導出的，
> 那它描述的是【我們想到的】，不是【這支程式裡有的】。**

## ⚠️ 而這一刀最花時間的不是掃描，是「樹怎麼送到下拉手上」

下拉來源的簽章是 `(ctx?) => 選項[]`，而 `ctx` 裡只有
「這顆積木是誰、接在誰身上」——**沒有樹**。

三條路，選了第三條：

| | 為什麼不 |
|---|---|
| 把樹塞進 `ctx` | **每一個**下拉來源都要收它（語系、風格、板子都不需要）——把一個特例變成所有人的簽章 |
| 在 `sync-controller` 的六個發佈點各餵一次 | **六個要記得同步的地方** |
| 🟢 核心一個具名的登記處，組裝點餵一次 | 「現在畫面上是哪一棵樹」在組裝點有**唯一**的答案，而它已經在維護那個欄位 |

⚠️ 而先例（`getWorkspaceVarOptions`）走的是**掃 workspace 的積木**那條路
——它拿的是積木不是樹，所以這一刀沒有沿用它。
FR-005 逐字要求「讀語義結構，不得重新解析程式碼字串」，而護欄驗了那一點。

## 🔴 兩條刻意畫下來的界線

**① `vector<int>` 掃不到，而那是對的。** 實測：

```
vector<int> v;   → cpp:vector_declare 的 type 是 "int"   ← 元素型別
int* p;          → cpp:pointer_declare 的 type 是 "int"   ← 同上
struct Point{};  → cpp:var_declare    的 type 是 "Point"  ← 這一個才是目標
```

> **一個「用過哪些型別」的掃描，掃到的是【元素】而不是【容器】
> ——因為容器那一層的資訊住在【身分】裡，不在屬性裡。**

⚠️ 而那條界線被**釘在測試裡**（`types-in-use-e2e` 有一條反向斷言），
不然下一個人會以為掃描漏了東西。

**② 打錯字的型別（`itn`）照樣進下拉。** 系統**分不出**「打錯字」與
「還沒宣告的自訂型別」，而猜錯的代價不對稱：

```
漏掉一個真的型別   學生選不到 → 那正是今天的 bug
多一個錯字         多一列
```

> **一個會替使用者修正錯字的清單，
> 會在它猜錯的時候把真的東西藏起來。**

## ⚠️ 而護欄自己第一次寫出來時誤傷了

「列舉那一支裡不准出現 C++ 的型別名」——而 `typeof t === 'string'`
裡的 `string` 是 **TypeScript 的**型別。

> **一條「不准出現這個字」的護欄，
> 要先扣掉那個字在【另一個語言裡】的合法用法。**

# 172 · 一個把長度上限寫進配對規則的掃描器，不會少給你東西——它會給你不存在的東西

**日期**：2026-08-26

## 起點：新護欄讓兩條舊護欄變紅，而紅的是語料

蓋完第七十四條（面板不得 import 積木引擎）之後，全套裡兩條護欄說
「語料變大了」——各 **+1 段**。而我沒有碰任何語料。

追下去：`tests/integration/*.test.ts` 裡帶 `;` 或大括號的**反引號片段**
會被七支護欄與探針當成 C++ 語料撈走。我的檔頭寫了一句
`` `import type { BlocklyPanel }` ``，於是它變成一段「C++」。

⚠️ 這一步本身照 [`build-guardrail` §6.5](../skills/build-guardrail/SKILL.md)
「紅的是世界，還是語料」判對了。**而順著它往下看到的東西大得多。**

## 🔴 那個掃描器的正則有一個缺陷，而它的方向與直覺相反

七處各自寫著

```js
/`([^`]{4,400})`/g
```

`{4,400}` 看起來只是「太長的不要」。它真正做的事是：

```
一段超過 400 字的樣板字串  →  【配不到對】
  → 它的收尾反引號改跟【下一段的開頭反引號】配
  → 夾在中間的【測試程式碼本身】變成一段語料
```

實測（`tests/integration/`）：

```
配對錯位（原本）  1078 段     其中「語法完整」534 ／「片段」544
配對正確          904 段      其中「語法完整」689 ／「片段」215
```

> **它不是漏掉長的那些——它同時【丟掉真的】與【生出假的】。**
> 真的段落 534 → **689**（+155，而那 155 段正是最長最複雜的那半）；
> 幽靈片段 544 → 215（-329）。

⚠️ 而 `audit-projection-residual` 的檔頭本來寫著
「820 段裡 353 段是**片段**（語法本來就不完整）」——那個診斷**有一半是錯的**：
片段的大宗不是「語料裡本來就有片段」，是掃描器自己造的。

## 修法：先正確配對，再篩長度

`tests/helpers/backtick-corpus.ts` 的 `backtickSpans(src, min, max)`：
`[^`]*` 讓每一對反引號自己配到自己，長度在**配對之後**才判。

⚠️ **刻意不做任何內容篩選**——`[;{]`／`int main`／排除清單留在七個呼叫端，
因為那是「這一支要什麼語料」的問題，各家不同。這裡只負責**切得對**。

## 🔴 修好之後，四條護欄各自看到了它們本來看不見的東西

| 護欄 | 動了什麼 | 是什麼意思 |
|---|---|---|
| 形態的殘差（31） | 0.45% → **0.35%** | 改善，而且是在語料變大 31% 的情況下 |
| 字串屬性（72） | 要看 33 → **35** | `cpp:include.header`／`cpp:priority_queue_declare.type` **一直都在**，只是碰得到它們的語料是幽靈 |
| 宣告完整性 | 無法確定 151 → **140** | 14 顆（多為 Arduino 執行期表面）判得出來了；它們的舊判定被孤兒檢查抓到 |
| 語料自己夠不夠（53） | 該補 0 → **5** | 五個語法形狀以前算「碰到」，而碰到它們的是幽靈 |

### 而最說明問題的是 `cpp:raw_code`

它從「語料有碰到」掉進「無法確定」。理由一想就通：

> **那 329 段幽靈是 TypeScript，餵進 C++ 的 lift 當然全部降級成 `raw_code`。**
> 一份壞掉的語料，會讓**降級目標**看起來一直在被行使。

同一個形狀還有 `cpp:string_find_{first,last}_not_of`：它們唯一的「覆蓋」
來自 `string-find-not-of.test.ts` 裡一段**單引號**的 JS 字串
——真正的 C++ 從來沒有寫進反引號，是錯位配對意外把它連著 JS 一起撈走的。

## 判定與基線怎麼處理

- 三筆新判定（`raw_code` ＋ 兩顆 string），逐筆寫明「以前的覆蓋是幽靈」。
- 十四筆過期判定**拔掉**——`build-guardrail` §11：
  「判定與基線不同，**基線過期會被棘輪抓到，判定過期不會**」，
  而這次是孤兒檢查抓到的。
- 五個語法形狀歸**保守桶**「該補進語料」，**不是**「這個工具不做」
  ——後者是一個關於能力的宣稱，而沒有人驗過（§5：判不出來就說判不出來）。
  🔴 **所以那 5 是一筆真的待辦**，不是把數字挪個位置。
- 每一份基線的 `note` 都寫了這次為什麼動，因為
  「commit 訊息沒有人會回頭翻，而基線檔是下一個看到這個數字的人一定會打開的地方」。

## 教訓的一般形

> **一個量測工具的「上限」如果寫在它的【切分規則】裡，
> 溢出的那一筆不會被丟掉——它會把邊界後面的東西一起帶進來。**

⚠️ 而症狀是**數字看起來像一個發現**（「語料裡有一半是片段」），
這正是 §6.5 那三次語料錯的同一個方向：**每一次錯誤的數字都比正確的大。**
這是第四次。

→ 判準：一個掃描器如果同時做「切分」與「篩選」，**問切分規則裡有沒有篩選條件**。
有 → 被篩掉的那一筆會讓後面的切分整個錯位。

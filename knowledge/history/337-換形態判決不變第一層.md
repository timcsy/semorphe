# 337 · 換形態，判決不變（第一層）——宣告的第五個面向

> 日期：2026-11-04
> 轉變：「同一棵語意樹換一種形態再轉回來，翻給 Cella 的程式相同」從一句承諾變成常駐的檢查（`tests/integration/form-invariance`），
> 學生語料另有探針（`tests/probes/form-invariance-studycpp`）。三方會議第三輪的不變式 ①（[334](334-三方會議第三輪符號學三面向與操作者介面.md) 後記）在 semorphe 這側成立。
> 做法：spec 213（`specs/213-form-invariance/`），第 262 刀。

## 為什麼需要第五個面向

前四個面向（產出的程式碼、語義的不動點、載得進工作區、走一趟積木回來）都是**形狀**。6c 之後「意思」由 Cella 判，
於是可以直接問：換一種形態再回來，**交給 Cella 的那一份**變了沒有。形狀全對而意思被換掉的缺陷，只有它看得到——這一刀就量到兩個。

## 量到的

| 轉換 | 課文（109 支） | 學生（218 支，8 支原本就翻不出） |
|---|---|---|
| (a) 同風格產碼再讀回 | 0 不同 | 0 不同 |
| (b) 只改格式的風格切換（命名空間寫法不算） | 0 不同 | 0 不同 |
| (c) 轉積木再抽回 | 7 → **0**（修了） | 6 → **3**（修了 3；剩 3 釘住） |
| I/O 風格切換（cout → printf），比判決與輸出 | **17 支不同**，全部釘住並歸因 | — |

修掉的三個（都是「形狀全對、意思被換掉」）：
- 🔴 **Serial／EEPROM／WiFi 的接收者走一趟積木就不見**：積木上沒有接收者欄位，抽取沒補；產生器補預設值，所以程式碼看起來對，而 formalize 照實讀、翻不出。
  修法：積木形態可以顯式宣告「這個形態固定了哪些屬性」（`renderMapping.fixed`），8 個形態補上。照「屬性宣告只描述、不驅動抽取」的原則，不從宣告推。
- 🔴 **struct 裡 `int x, y;` 走一趟積木整組消失**：那一顆中間節點（`_multi_field`）沒有積木形態，渲染時被跳過；登記處的說明還寫著「攤平後就消失，不會進入語義樹」——而它會。
  修法：渲染敘述鏈時攤平宣告為 sentinel 的中間節點；說明照現況改寫。
- **空的 case（往下掉）走一趟積木就翻不出**：抽取不建空的 `body`，而 switch 的 formalize 靠「有沒有 body」認子句。改成認元件宣告的 `insideParentOnly`。

## 釘住的（排成接下來的刀）

- **運算式當敘述**（`cc[1];`、`(c ? A = 1 : A = 0);`）走一趟積木會跑到 main 外面：2026-09-10 決定把接不上語句鏈的積木「放在旁邊、不丟也不硬接」，而抽回來時它就不在原位了。修法是一顆「運算式當敘述」的包裝積木。
- **printf 產碼沒有型別表**（缺陷帳 2026-09-20 那一根）：這一刀第一次在判決層量到它——課文有 11 支，學生按下 printf 風格，執行結果就變了（字元印成數字、double 判 ubPrintf、字串當指標）。
- **Cella：printf 的格式字串裡直接寫中文會亂碼**（6 支，`%s` 帶同一串則正常）——已回報，cella 在修。

## 學到的

- 量尺自己先錯過一次：正規化只換了 `n` 欄位，而變數參照也拿宣告節點的 id 當名字——第一次跑每一支都「不同」，連注入都紅。**注入那一條就是為了這種時候**：它紅的方式說出了是量尺壞了，不是世界壞了。
- I/O 風格會換掉語意樹本身——「換形態，判決不變」的「形態」要先分清楚哪些是表面、哪些是意思；後者只能比判決。

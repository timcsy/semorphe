# 208 — 骨架告示合成一條路，而「該問哪一棵樹」那個問題本身問錯了

> 2026-09-06（spec 172）。vision「🧾 未清的債」最老的一筆 🆕，
> 2026-08-30 交付流程視圖的骨架顯示時**明知而留下**的。

## 轉變

```
舊   積木視圖：組裝點算好骨架 → 【直接呼叫】面板，順便決定用 ghost 還是 editable
新   積木視圖：從 semantic:update 的骨架告示收——與流程視圖同一條路

舊   骨架告示的 nodeIds 從【真相那一棵】算
新   從【兩棵樹的聯集】算（真相 ∪ 畫布上那一棵）

舊   鷹架深度變了 → 組裝點直接叫面板重蓋
新   真相那一側發一則【不帶 blockState】的更新
```

## 為什麼

### 一、組裝點做的兩個決定，只有一個是它的

```
算出哪幾顆是骨架     ✅ 可以——那是接線
這個深度該畫成什麼   🔴 不可以——那是【視圖】的事
```

而第二件正是 [191](191-骨架在流程視圖上是一句謊話.md) 那條教訓的另一面：

> **一個模式如果在某個視圖上與另一個模式長得一樣，那個視圖就沒有實作它
> ——而選單仍然讓人選得到。**

⚠️ 組裝點替視圖決定「ghost 還是 editable」的時候，
**那個視圖有沒有實作它，沒有人問得出來**。

### 二、🔴 而「該問哪一棵樹」有兩個都對的答案——那表示問題問錯了

實作中先寫成「從顯示樹算」（理由充分：增強器補的 `#include`／`using`
只存在於顯示樹上，而它們**是**骨架——2026-09-02 使用者報過
「兩顆實心的積木站在一堆淡的裡面」）。

**e2e 當場紅**：流程視圖的 `hidden` 與 `editable` 長得一模一樣。
因為 `hidden` 模式下顯示樹**已經把骨架剝掉了**，於是告示是空的
——沒有人知道要隱藏誰。

```
只問真相那棵     漏掉「顯示樹多出來的」（增強器補的）
只問顯示樹       漏掉「真相多出來的」（被剝掉的）
```

🔴 兩棵樹**各自多了對方沒有的東西**，而不是一棵比另一棵完整。

> **「該問哪一棵樹」如果有兩個都對的答案，那個問題問錯了
> ——要問的是「這兩棵各自知道什麼別人不知道的」。**

🟢 淨效果是流程視圖**變好了**：它現在也認得增強器補上去的那兩顆。

### 三、一則「只做一件事」的事件，而那個開關早就長在收的那一端

鷹架深度變了而樹沒變——那不是一次語義更新。而重發一則完整的更新
會重畫積木，打斷拖曳、清掉復原堆疊。

🟢 而積木面板的重畫**本來就閘在 `event.blockState` 上**（2026-08-27 為了
「不要打斷自己的編輯」加的）。所以發一則**不帶 `blockState`** 的更新，
它就只會套骨架。

> **一個「這則事件要做多少事」的旋鈕，剛好已經長在收的那一端了
> ——而它本來是為了別的理由長出來的。**

### 四、⚠️ 驗收標準錨錯了一格，而它在做對事情的時候紅給你看

spec 原本寫「四項獨立性量表的**方法呼叫數**下降」。跑下去它**上升**了
（2969 → 2971）——那一格是 `assertCorpus`（**輸入量**）：
加了一支方法、加了一條護欄，它本來就會漲。

而真正該錨的那一格 2026-08-26 就被分出去了，理由逐字：

> 「`directViewCalls` 五天內被**上調四次**，而每一次的理由都是
> 『組裝點把兩端接起來』——**一個正確的動作**。」

改錨到 `compositionRootViewCalls`：**72 → 71** ✅

> **一個驗收標準如果錨在「總量」上，它會在【做對事情】的時候也動
> ——而那時沒有人知道該慶祝還是該修。**

### 五、🔴 而它逼出一個【一直靠巧合活著】的等待

「排回去」那一題（2026-09-05 交付、當天綠）在這一刀之後紅了：
**積木散開了，而程式碼一個字都沒變。**

量出來的：`userChanged` 跑了 **19 次**，而變更處理器第一行
`if (this._codeToBlocksInProgress) return` 把 19 次全部折返。

```
syncCodeToBlocks 的 await 回來時，_codeToBlocksInProgress 【還是 true】
```

而 `seedArrange` 等的是 `scaffoldMarked()`——**它需要的其實是「同步真的結束了」**。
在此之前骨架標記由組裝點在 `setTimeout(…, 900)` 裡做，
於是那個迴圈**順便**等掉了那 900 毫秒。骨架改走匯流排之後標記變成同步的，
那個巧合就沒了。

> **一個等 A 的迴圈，如果它真正需要的是 B，
> 那它在「A 變快了」的那一天會安靜地全部落空
> ——而在那之前，它一直在靠一個沒有人寫下來的巧合活著。**

⚠️ 而那支迴圈**自己的註解**就寫著這條教訓的前半：
「一個依賴『另一件事已經做完』的判準，在它自己跑得比較快的那一天會安靜地全部落空。」
——**寫下那句話的人（我）當時挑錯了要等的那件事。**

### 六、⚠️ 三個猜錯的假設，與它們留下的痕跡

定位這個 bug 時試過三條路，**每一條都有充分的理由，而三條都不是**：

```
把套用移到重畫之後       理由：蓋在畫之前等於沒蓋   → 鷹架 e2e 反而紅 3 支
給告示加「內容變了才套」  理由：重套不是冪等的       → 對，但不是這個 bug
把整段包進事件停用       理由：純視覺不該發事件     → 拿掉照樣綠，撤回
```

🟢 前兩個留下了（它們各自修掉一個真的問題），第三個**撤回**
——一個「根據錯誤假設加的、拿掉也沒事的」防禦，留著只會讓下一個人以為它在守什麼。

> **一個改動如果只有「它可能有幫助」這個理由，那它是雜訊；
> 而雜訊在程式碼裡看起來跟保護一模一樣。**

## ⚠️ 這一刀【沒有】做的一件事

`markOutOfScopeBlocks()` **仍然同時做兩件事**（標記超出範圍 ＋ 叫真相重發骨架）。
它有 6 個呼叫點，其中 4 個包在 `setTimeout(…, 900)` 裡——而那個 900 毫秒
擋的是 2026-09-02 的一個雷（換目標途中「這個主題看得到哪些元件」還沒算完，
整個畫布被判成超出範圍）。

**拆它不在這一刀**，而寫在這裡是因為：不寫的話下一個人會以為那是漏掉的。

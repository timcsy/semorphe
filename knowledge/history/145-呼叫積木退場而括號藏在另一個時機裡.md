## 逐筆判「哪一邊對」，而這一顆三格三個答案

| 格 | 判定 | 理由 |
|---|---|---|
| 函式名 | **命令式對** | 它是**跟著工作區長的下拉**；宣告是一個死文字框。判例逐字：「`cpp_var_ref` 宣告只有死文字框 → 命令式對」 |
| `ARGS` 文字欄 | **兩邊都不對** | 它是「參數是一個字串」時代的化石，而 `renderMapping` 早就走 `ARG_{i}` 值插槽——命令式沒有它，宣告有一個**沒有人讀**的它 |
| 引數增減 | **命令式對** | 宣告補 `builder: "variadic"`（`minCount: 0`——`f()` 是合法的呼叫） |

## 🔴 而「一模一樣」是假的——括號藏在另一個時機裡

護欄說一模一樣，而 skill 第 3 步那一問（「**它有沒有一段只在別的時機才跑的邏輯？**」）
問出了 `rebuildArgLabels_`：

```
argCount = 0   呼叫函式 [f]  ⊕⊖
argCount > 0   呼叫函式 [f] （ ⟨引數⟩ ） ⊕⊖     ← 括號只在這時候長出來
```

**比對護欄只比「剛建好的樣子」**（0 個引數），那時兩邊都沒有括號。
少了這一段，使用者會在**加第一個引數的那一刻**看見差異，而測試全綠。

🟢 建構子因此多了 `openLabel*`／`closeLabel*`（有插槽時才出現）
——`paramList` 早有同名的兩個鍵，沿用命名。

> **「一模一樣」只在那條護欄看得到的範圍內成立，而它看得到的是一個時刻。**

## 🔴 第二個，只有瀏覽器看得到：存檔鍵不一樣

刪完打開瀏覽器——**工作區一片空白**。console 逐字：

```
The block "cpp_func_call_expression" is missing a(n) ARG_0 connection
```

命令式與 `renderMapping.countSource` 都用 `argCount`，而建構子**寫死 `itemCount`**。
🟢 修法：`countKey` 可指定（存檔契約）。

⚠️ **而護欄為什麼沒抓到**：昨天我補 `declarableKeys` 時，
替 variadic 積木**同時加了兩個鍵**（`itemCount` 與宣告的 `countSource`），
於是那一維變成**超集合檢查**——「命令式存 A、建構子存 B」被判成一模一樣。

> **一個判定寫成「宣告表達得出的鍵 ⊇ 命令式吐出的鍵」，
> 就會把「兩邊用不同的鍵」讀成「沒問題」。**

修法是只加**它實際會用的那一個**。

# 066　護欄錨在供給端，所以量不到消費端——而缺陷隔天就從第二個地方冒出來

> 日期：2026-08-15
> 觸發：第一課的學生犯錯探針。
> 本檔記的是**一個判準的錨點錯了**，不是交付了什麼（那在 spec `126`）。

## 轉變

```
old  第四十二條護欄守著「診斷訊息不得顯示成代號」
new  🔴 它守的是【文案在不在】，而缺陷是【顯示端有沒有查】
     —— 文案齊全而沒有人查它，護欄是綠的

old  修完一個缺陷，問「同一族還有誰」
new  🔴 問「這個判準錨在供給端還是消費端」
     —— 錨在供給端的護欄，量不到消費端的缺失
```

## 一、缺陷隔了一天，換一個顯示點復發

2026-08-14（spec `121`）修好：程式碼面板查 `window.Blockly?.Msg` 永遠走
fallback，把 `DIAG_MISSING_CONDITION` 顯示給使用者。**並蓋了第四十二條護欄。**

2026-08-15 的探針量第一課的學生會犯的 9 種錯，放行的兩種：

```
RUNTIME_ERR_UNDECLARED_VAR: {"%1":"Cout"}
```

**同一個形狀，換一個顯示點。**

## 二、而「加一族進護欄」接不住它

```
第四十二條量的   文案【在不在】       ✅ 文案就在 blocks.json:134
而缺陷是         顯示端【有沒有查】    🔴 execution-controller 直接推 e.message
```

> **文案齊全，而沒有人查它。**

⚠️ 那與「機制有了沒人接上」是**第四次**（`mappings` 零接收者、
23 筆 `min` 零消費者、`children.allowed` 41 筆）。

**判準**（已進 [experience](../experience.md)）：

> **蓋護欄時問一句「如果供給那一側全部齊全而沒有人消費它，
> 這條護欄會是綠的嗎？」會 → 錨錯端了。**

## 三、而換錨點的過程，順手解掉了「誤報」這個死法

第一個設想是掃 `src/ui/` 找顯示呼叫。⚠️ 而 `src/` 裡到處都是開發期日誌
——`build-guardrail` 第 11 步：**一條會誤報的護欄會被人學會忽略**，
而那時它報的真違規也一起被忽略。

**改成**：單位 ＝ **一個 (錯誤身分, 拋出點傳的參數) 組合走過顯示路徑的結果**。

> **開發期日誌永遠進不了那個集合——它們不經過顯示路徑。**

🔴 **而一個錨對地方的判準，抓到了我沒預期的同族**：

```
① 顯示端不查表          → 出現代號         （原本知道的）
② 三個身分【沒有文案】   → 沒退路就出現代號  🆕 查證出來的
③ 文案要 %1 %2 而只傳 %1 → 出現未替換的 %2   🆕 查證出來的
```

②③ 都不是「同一族」，而是**同一個顯示邊界上的不同缺陷**。

## 四、⚠️ 而護欄的第一次跑報了 66 筆，其中 44 筆是誤報

括號沒有配對地數——用「往後 300 字」的視窗把後面不相干的物件字面
一起吃進來，於是 `參數[%1]` 被報成 `參數[%1,type,value,offset]`。

**那不會造成假違規**（多餘的參數只是被忽略），⚠️ **而它讓報表說謊**
——而一份說謊的報表推導不出「使用者到底看到什麼」。

→ 改成配對地數括號，66 → 22（11 組合 × 2 語言），**逐筆都是真的**。

> **一個不影響判定的誤報，仍然要修——因為護欄的產出不只是那個布林值，
> 還有那份給人讀的清單。**

## 五、而教材當了一次量測工具

第二課走不通：**只按「執行」，輸出區完全空白**，必須先按「程式碼→積木」。
而課文從頭到尾沒說——因為寫課文的人心裡跑的是 e2e 的步驟。

🔴 **而第二課還繞了一次路**：它花兩段講「`int` 不能省」，
而實測 `score = 90;`（沒有 `int`）**在我們的直譯器上跑得完**。

> **教材說出「工具哪裡不對」的方式是繞路，不是報錯。
> 繞路的地方就是下一個規格。**

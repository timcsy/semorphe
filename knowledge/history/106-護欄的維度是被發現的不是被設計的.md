# 106 — 護欄的維度是被發現的，不是被設計的

**日期**：2026-08-20 · **spec**：`155-import-dimension` · **狀態**：完成

## 轉變

```
之前   中立性護欄兩維（身分字面 0、積木型別 33），而【import】沒有人掃
       src/core/lift/lifter.ts:10 import 了一顆 cpp 元件——兩維都看不到
```

## 🔴 同一族護欄的第三個盲點，而它們是連著三天發現的

```
① 概念身分字面（cpp:print）   一直都有
② 積木型別字面（cpp_print）   spec 153（08-20 上午）——量到 44 筆
③ import                     spec 155（08-20 下午）——量到 1 筆
```

前兩維掃的都是**字串字面**，而
`import { buildBlock } from '.../components/cpp/block/lift'` 裡
**一個身分字面都沒有**。

> **一條護欄的維度是被發現的，不是被設計的。**

⚠️ 而 **P9 的原文早就寫著第三維**（`principles.md:158` 逐字）：

> 「拔掉 C++，只裝 Python stub → 所有視圖仍啟動，**無 `languages/cpp/` import**」

🔴 **判準寫在規範裡，而沒有任何機械檢查在守它**——那正是
`concepts/執行機構.md` 說的「規範沒有機械化的檢查就是裝飾」。

## 那一筆：把字面耦合換成模組耦合

`components/cpp/block/lift.ts` 的檔頭逐字：

> 「這裡只提供建構子，讓那一處**不必寫死身分字串**。」

🟢 用意是好的——**而它把「字面耦合」換成了「模組耦合」**，
於是第一維（掃字面）看不到它，而第三維那時還不存在。

修法：`core/standalone-block.ts` 宣告登記處，與 `degradation-blocks` 逐字同形；
宣告放在 `registerCppLifters()` 裡，讓**產品與測試兩個組裝點自動都有**。

## 🔴 而「沒宣告時拋錯」是刻意的，不是防禦性程式設計

`lifter` 是**每次 lift 都會走**的主路徑。猜一個 `'block'` 身分的話，
它會**靜靜地產生錯的語義樹**——那種錯要到 round-trip 或執行才浮現。

> **主路徑上的降級要出聲；一個看起來合理的預設值在這裡是最貴的。**

## 而注入實測發現：那條路徑【沒有任何測試走過】

拿掉宣告之後，**全套 4730 支一支都沒紅**。

> **一條「主路徑」如果沒有測試走過，它壞掉的時候是靜默的。**

🟢 補了 `standalone-block-declared.test.ts`（lift 一段獨立的 `{ … }`），
再注入 → 紅。

## 順帶：判準借用既有的那一份

第三維第一版把 `languages/style`（中立的 `CodingStyle` 型別）也算成違規。
🟢 改成借用 `audit-four-independences` 既有的 `isLanguageSpecificImport` 規則
——**不要寫第二份，兩份判準遲早會漂**。

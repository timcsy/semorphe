# 149 · 核心第一次在別人的建置工具下跑起來——而例子一路照出四個坑

> 2026-08-24。`vision.md` 階段 8「核心可獨立出貨」的第一條驗收關掉：
> `examples/bring-your-own-view/` 用 **esbuild** 建、在 **Node** 跑，
> 一個面板都沒用，程式碼 ↔ 語義樹雙向各走一次，往返**一字不差**。

## 一、🔴 需求被我推導錯了一格

規劃時我把驗收寫成「**膠囊清單改成建置期產生**」——也就是要動 8 個
`import.meta.glob` 站點，那是核心載入路徑的大手術。

而第一次紅之後才看清楚：

> **「非 Vite 的專案能用」說的是【消費者】不必用 Vite，不是【我們】不能用。**
> 函式庫本來就出貨打包好的產物。

於是正解是 `vite build --lib` → `dist-sdk/semorphe.mjs`，膠囊在**打包那一步**
被靜態展開進產物裡，**核心一行沒改**。

| | 錯的推導 | 對的推導 |
|---|---|---|
| 動到哪 | 核心的 8 個載入站點 | 多一個建置設定 |
| 風險 | 高（整個 app 的載入路徑） | 低 |
| 「加一顆膠囊零編輯」 | **會壞掉** | 完好 |

## 二、四個坑，每一個都是實測出來的

```
① import.meta.glob is not a function       core/component/registry.ts:54
② Dynamic require of "path"（jsdom）         languages/<lang>/pack.ts → ui/ → blockly
③ if 安靜地降級成 unresolved                 膠囊的 lift 策略沒人登記
④ ⟨unknown component: python:program⟩      產生器沒人登記（pack.install()）
```

**②是真正的架構債，而且已經修掉。** 兩個語言套件為了兩件小事
（查一個字、登記一個下拉來源）把整個視圖層拖進來：

```
languages/<lang>/pack.ts  →  ui/dynamic-dropdown-field  →  blockly  →  jsdom
                          →  import * as Blockly（只為了讀 Blockly.Msg）
```

修法是這個 repo 的兩個既有形狀：

| 拆出來的 | 去哪 | 形狀 |
|---|---|---|
| `declareDropdownSource`／`dropdownSourceNames` | `core/dropdown-sources.ts` | **宣告登記處**（第 N 個） |
| `Blockly.Msg[key] \|\| fallback` | `core/messages.ts` 的 `msg()` | **埠**——宿主接翻譯表 |

> **一個登記處與一個使用它的欄位住在同一個檔案裡，
> 就等於要求每一個登記者都依賴那個欄位的實作。**

⚠️ 而症狀**只在 Node 裡現形**：瀏覽器本來就有 DOM，這條線一直是綠的。

③④ **今天仍然要消費者自己做**，而它們的症狀都是**降級**不是錯誤——
`if` 變成 `unresolved`、產出變成 `⟨unknown component⟩`，程式一聲不吭。

## 三、第五十八條護欄

`audit-portable-core`：建產物 → esbuild 建例子 → Node 跑 → 比對往返。
**硬性零**（判準：「核心可以獨立出貨」如果有一條路徑非我們的工具不可，那句話就是假的）。

⚠️ **它第一次跑不是紅的**，而那是 `build-guardrail` 6.5 的具名例外：
它守的東西與它同一輪做出來。健康檢查靠注入——把 `import * as Blockly`
加回語言套件，護欄當場紅，**而且指得出是哪一段**（「例子在 Node 跑不起來」）。

## 四、同一招第二次成功

`draft/目錄結構對硬體的適配` §六 記著 `semantic-tree-view` 那次：
「**一個假的實作，用來否證結構假設**」——而它逼出了 `ViewHost` 契約。

這次是同一招的第二個實例：**一個假的視圖（一塊字串緩衝）**，
逼出了四個沒有人知道存在的組裝步驟。

# 196 · 第一次打開就不能用，而沒有人測「什麼都還沒做的時候」

**日期**：2026-08-31
**前一步**：[195](195-市集上架，而擴充ID是一個發佈之後改不了的決定.md)

## 一、使用者回報的那句話

> 「semorphe 在一開始打開的時候畫面是空的，拉積木也沒反應，
>  我是**去載入範例**才開始有反應。」

實測（無存檔的全新頁面）：

```
開機    code:""  blocks:0  staleReason:'not-rendered'
拉一顆  code:""  blocks:1  staleReason:'not-rendered'   ← 積木進去了，程式碼沒動
```

**零錯誤訊息。** 機制是一條鏈：

```
沒有存檔 → restoreState() 直接 return → 開機那一次同步從來沒跑過
        → 匯流排沒畫過樹 → hasRendered 永遠 false
        → staleReason 永遠 'not-rendered' → 每一次積木編輯被殘態守衛擋掉
```

而那道守衛**刻意不出聲**——2026-08-24 使用者說過「每次重新整理都跳一條紅字
會讓人以為系統錯誤」，所以它只寫一行 `console.debug`。

> **一道「等畫過再說」的閘，遇到「永遠不會被畫」的情況時，
> 不會變成錯誤——它會變成一個安靜的死結。**

⚠️ 載入範例會讓匯流排畫一次樹，閘就解除了——**那正是使用者說的那句話**。

🔴 而 `refused`（存檔載不進來）那條**不比照辦理**：凍住是刻意的，不能讓一次
自動存檔蓋掉救得回來的東西。**兩條早退看起來一樣，最壞情況相反。**

## 二、為什麼 5961 支單元測試 ＋ 220 支 e2e 全綠

**每一支 e2e 都先做點什麼**——載入範例、貼一段程式碼、選一堂課。而那些
動作全都會讓匯流排畫一次樹，於是**閘在被測到之前就解除了**。

```
既有 e2e 測的是   「做了 X 之後，Y 對不對」
沒有人測的是      「什麼都還沒做的時候」
```

> **一個只在「使用者還沒做任何事」時成立的缺陷，
> 會被每一支「先做點什麼」的測試跳過去。**

第九十條護欄因此規定：**它的第一個動作必須是拉積木，不得先載入任何東西。**

## 三、而修好它之後 9 支 e2e 紅了——沒有一支是產品壞掉

先在乾淨 worktree 跑過確認是迴歸（18 支全過），再逐一歸因。三個都是
**測試建立在「開機時編輯器是空的」這個假設上**：

| | 真正的原因 |
|---|---|
| execution ×3、debug | 「選全 → 打字」做整份取代 |
| var-ref-scope ×2 | 就緒條件是「積木數 > 1」，而骨架本來就滿足它 |
| templates ×3 | 應用會問「套用（現在的內容會不見）」，而測試沒回答 |

**①「選全再覆蓋」不是原子的**（實測兩輪壞一輪）：打第一個字元 → 整份被
取代 → 觸發 code→blocks → 積木還是舊的那棵 → 骨架回寫進來 → 剩下的字元
打在它中間。⚠️ **加等待救不了**（刪光＋等 1.2 秒＋再選一次，還是壞）。

> **只要另一邊會自動回寫，用鍵盤做「整份取代」就不是原子的
> ——那不是等待長度的問題，是它中間必然有一瞬間是空的。**

**②** > **一個「有東西了嗎」的就緒條件，只在「一開始什麼都沒有」時
> 才等得到正確的那一刻。**

**③ 那個確認框是對的**——事件序列 `["remove","add"]` 證明範例選單關掉後又
開了一個確認框，應用在保護使用者的內容。

> **一個「只在有內容時才出現」的確認框，
> 在測試永遠從空白開始的世界裡是看不見的。**

## 四、手機：三件事，而它們各自的根因都不在症狀上

**① 拖曳被誤判成右鍵**（第九十一條護欄）

```
按住 200ms 再拖  →  選單沒開          ✅ 恰好被「移動超過 8px 就取消」擋掉
按住 700ms 再拖  →  🔴 選單開了，而節點也移動了 120px
```

> **一個「取消待辦」的機制，對「已經發生的事」沒有任何效力
> ——而這兩種情況在程式碼裡長得一模一樣。**

🔴 而修法的第一版沒有用：拖曳的每一次移動都會 `paint()`，而 `paint()` 把整個
SVG 重建——收到 `pointerdown` 的那顆元素當場被換掉（實測 `pointermove=0`，
而節點確實移動了 120px）。

> **一個把狀態放在「會被重畫掉的元素」上的手勢處理器，只在第一幀裡是對的。**

**② 還原鈕只有積木分頁看得到**（第九十二條護欄）

`switchToMobile` 把整條快速列搬進 `mobileBlocksContainer`，而 ↩↪ 是它的一員。

> **一顆全域的按鈕，住在一個會被分頁藏起來的容器裡，就只是那個分頁的按鈕。**

⚠️ 處置**不是「每個分頁各放一對」**——2026-08-30 才把三對合併成一對
（[193](193-三對還原收成一對，而一顆選單先退場.md)）。搬同一組 DOM 節點。

**③ 而搬到標頭在真手機上把它擠爆了**

使用者在約 390px 的手機截圖回報：「▶ 執行」折成兩行、↩↪ 疊在一起。
⚠️ 而我在 **500px** 的 e2e 上量到 32x28，看起來完全正常。

> **一個「量得到就算過」的寬度，不是使用者手上那一支的寬度。**

護欄改用 390×844。⚠️ 而**像素判準抓不到它**：把 ↩↪ 塞回標頭做注入，
Playwright 在 390px 下量到的執行鈕沒有折行——瀏覽器的字型排版比真手機窄。
主要偵測器因此改成**結構的**（↩↪ 必須在那一列裡）。

> **一個「看起來還好嗎」的判準，只在你這台機器的排版上成立。**

## 五、四條工具列併成一條，而補樣式那條規則反手拆了搬進來的按鈕

使用者：「總之整合成一個工具列」→「只能有一列」。行動版原本有**四條**
各自為政的橫列，而第一版只搬了兩條。

> **只要還有一個投影自己帶一條，使用者看到的就還是兩層。**

🔴 `adoptActionBarSections()` **必須可以重跑**：`.bottom-panel-tabs` 要等
`enableConsoleTab`、`.monaco-clipboard-bar` 要等編輯器 `init()`——晚到的那一段
沒有人再搬一次，就留在原處變成第二條列。

而接著兩個症狀是同一個決定的兩端：

```
「底色還是白的」    ↩↪ = rgb(239,239,239)（ButtonFace）
                   它原本靠 `.quick-access-bar button` 上色，被【單獨】搬出來
「藍色底線不見了」  我補的 `#mobile-action-bar button { border: none }` 掃到了
                   搬進來的每一段，清掉了 `.bottom-tab-btn.active` 的底線
```

> **樣式掛在容器上的按鈕，搬家等於脫光。**
>
> **而一條「幫新容器裡的按鈕補樣式」的規則，
> 會順手拆掉那些本來就有樣式的按鈕。**

⚠️ **`style.css` 裡已經有這個病的墓碑**（「檔案選單」那一段，2026-08-25 從
快速列搬到標頭時踩的同一個，症狀逐字寫著「一顆瀏覽器預設的灰框按鈕」）
——**而讀過它的我又踩了一次**。

🔴 而主控台**不給還原鈕**：它顯示的是執行的輸出，不是程式本身。

> **「全域」的意思是「每一個投影都在」，不是「每一個分頁都在」。**

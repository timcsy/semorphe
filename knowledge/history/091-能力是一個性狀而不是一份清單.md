# 091 — 能力是一個性狀，而不是一份清單

**日期**：2026-08-19 · **spec**：`142-arduino-board-targets` · **狀態**：US1／US2 完成

## 轉變

```
之前   一個 arduino 目標，三塊板子共用一份工具箱
       → 用 Uno 的學生【拉得到 ESP32 才有的積木】，燒錄時才發現編不過
       ⚠️ 而錯誤訊息出現在 Arduino IDE，不在 Semorphe 裡——學生無從得知是積木選錯了

之後   元件宣告 traits.needsCapability，目標宣告 provides，工具箱取交集
```

## 為什麼是 `traits` 而不是新機制

🟢 **`ioStyle` 已經在做結構完全相同的事**：

```
cpp:print       ioStyle = 'iostream'        「我只在某個 I/O 風格的世界裡有意義」
cpp:touch_read  needsCapability = 'touch'   「我只在有那個硬體的板子上存在」
```

被否決的：三份 `arduino-*.json` 課程清單（三份幾乎相同的檔）、
目標直接列 componentId（加一顆 ESP32 元件要改三個目標）。

⚠️ **能力用【功能】命名不用板子命名**——`esp32-only` 把「誰有」寫進能力的名字裡，
而下一塊有觸摸感應的板子會逼出 `esp32-or-xxx-only`。

## 🔴 而 Phase 0 推翻了規格自己寫的兩件事

| 規格原本說 | 查出來 |
|---|---|
| 可拿性護欄的判準要放寬 | **不必改**——它算的是分類定義，與目標無關 |
| 三塊板子的腳位常數要不同 | `properties.values` 是靜態宣告，需要一個不存在的機制 → 移出 |

> **一個 Phase 0 如果沒有改到任何規格，它多半沒有真的去查。**

而第一條留下一句更一般的：

> **一條護欄的判準有時不必改——要改的是我們對它在量什麼的理解。**

## 三條既有護欄各抓到一件事

| 護欄 | 抓到 |
|---|---|
| **就近性** | 我在四顆 PWM 膠囊的 `_traits_why` 裡寫「理由同 `cpp:touch_read`」——**把另一顆元件的身分洩進了它們的資料夾** |
| **我自己的新護欄** | 它第一版手寫四個目標 import，加完三塊板子後仍報「0/4」——**看不到新目標，它守的事悄悄變成空的** |
| **宣告完整性** | `cpp:touch_read` 的判定過期。🔴 而原因是**我們沒修什麼**——那條護欄的語料是 `tests/integration/*.test.ts` 裡的片段，新測試帶進一段真 ESP32 sketch，於是那顆從「碰不到」變成「碰得到而且對」 |

## 開瀏覽器實測（T016）

```
esp32          219 顆   五顆全在
arduino-uno    214 顆   五顆全無   ← 剛好差 5
arduino-nano   214 顆   五顆全無
cpp / c / 競程  一格不變

Uno 目標下貼 ESP32 程式碼 → 專屬觸摸積木，零降級
ESP32 下拉一顆積木再切 Uno → 積木還在畫布上（沒吃掉學生的作品）
```

⚠️ **順手看到一件規格沒問的事**：狀態列印的是**課程清單名**，
而三塊板子共用同一份清單 → **切了板子，狀態列看不出差別**。
下拉選單看得出來，所以不是缺陷；記在這裡當下一個看到的人的線索。

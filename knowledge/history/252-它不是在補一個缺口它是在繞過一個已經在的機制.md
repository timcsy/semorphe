# 252 — 它不是在補一個缺口，它是在繞過一個已經在的機制

**2026-09-18** · 管線 188（範圍那一族：`begin`／`end` 從字串屬性換成接點）

## 讀數

```
語料（218 支）正在失敗的        4 支   「無法解析範圍『begin(array)』」等
第七十二條「要看」的字串屬性    39 個  其中 13 個是這一族
執行期那個 parser 的長度        ~70 行
換掉之後                        ~10 行，而四支全部救回來
```

## 一、被換掉的東西，它自己的檔頭寫著要換

`runtime/range.ts` 的舊檔頭逐字：

> 「⚠️ **技術債**：範圍本來就該是結構化的（`{ array, from, to }`），
> 存成字串之後每個消費者都要自己 parse……**這裡先解析，型別結構化另外排。**」

而它解析用的那條 regex 只認得**一個裸識別字**開頭的東西：

```
/^([A-Za-z_]\w*)\s*(?:\.\s*(begin|end)\s*\(\s*\))?\s*(?:\+\s*(.+))?$/
```

於是學生真的寫的三種形狀全部斷在那裡——
`begin(array)`、`d2[i].begin()`、`d2[0]`。

> **一個用 regex 認左值的執行器，它支援的形狀是「我想得到的那幾種」，
> 不是「這個語言長得出來的那些」。**

## 二、而拆掉之後才發現：**結構早就在了，只是沒有人接上去**

`interpreter/pointer.ts` 的 `isCellPointer` 註解逐字：

> 「判準是 `type === 'array'` ＋ `value` 真的是一串格子。
> **容器本身也長這樣，而那是對的**：`v` 退化成指標時就是「指著第 0 格」。」

三件事**一件都不用發明**：

| | 誰做 | 做多久了 |
|---|---|---|
| 裸陣列名 → 第 0 格 | `cpp:var_ref` 求值出來就是那串格子 | 一直都是 |
| `A+n` → 第 n 格 | `cpp:arithmetic` 的位置分支 | 2026-09-17 |
| `v.begin()`／`d2[i].begin()` | `cpp:container_iter` | 接收者 2026-09-18 才變接點 |

於是新的 `resolveRange` 全文是「求值兩個接點、問它們是不是同一串格子」。

> **那條 regex 解析的東西，執行期早就會算了
> ——它不是在補一個缺口，它是在【繞過】一個已經存在的機制。**

## 三、這個形狀值得認得出來

它與 [[執行機構]]「機制有了，沒人接上」是**同一族，而方向相反**：

```
機制有了沒人接上   那個機制【零呼叫者】          → 症狀是「做不到」
繞過一個已在的     那個機制有呼叫者，而【不是這裡】 → 症狀是「支援的形狀很奇怪」
```

後者更難發現，因為**它是動的**：`sort(A, A+n)` 那 33 處一直是綠的。
只有當有人寫出那條 regex 想不到的形狀時才會紅，而那時的錯誤訊息
（「無法解析範圍」）指著**使用者的寫法**，不指著繞路這件事。

→ 判準：看到一個**自己解析原始碼片段**的執行期函式時，先問
「**這一段文字，別人求值出來會是什麼**」。答得出來的話，那個 parser 是繞路。

## 四、順帶量到的兩件事

🔴 **一個躲過護欄的投影遺失**：`cpp_range_sort` 的積木上只有一格
（對到 `begin`），**`end` 從來沒有落點**。第三十一條看不到它，因為它掃**接點**，
而 `end` 當時是屬性。

> **一個「還沒結構化」的欄位，連「它有沒有被畫出來」都不會被問。**

🔴 **填充那一路靜默地寫過頭**：二維攤平的慣用法
（`fill(d2[0], d2[0]+R*C, x)`）在巢狀表示上走不過列的邊界，
而舊碼直接 `arr[i] = v`——**JS 的陣列會自己長**，於是那個容器被撐成一百萬格
而沒有人出聲。換成接點的同時補了界線檢查。

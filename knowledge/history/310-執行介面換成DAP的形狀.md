# 310 · 執行介面換成 DAP 的形狀：從「每步回呼宿主」到「宿主下指令」

> 日期：2026-10-31～11-01（spec 183，重構階段 5b）
> 轉變：`ExecutionSession` 原本是 JS 直譯器的形狀——直譯器每走一步回呼宿主，宿主在回呼裡決定停不停；
> 單步模式甚至是**先把整支跑完、錄下軌跡再重播**。現在是 DAP 的形狀：`launch`／`continue`／`stepIn`／`pause`／`terminate`、
> `supplyInput`，每個指令回一個「停在哪／結束／失敗／不接」。Cella 的工作階段（`cella-lang/dap`）因此成為第二個宣告 `session` 的提供者。
> 設計：[draft](../draft/2026-10-31-重構的設計-能力介面與降級路徑.md) 二、四、五之一；規格 `specs/183-cella-debug-session/`。

## 為什麼不能保留回呼模型

量出來的（`tests/probes/cella-dap-cost.test.ts`）：Cella 的 `stepIn` 每步 3.5 ms，一次跑到底 28 ms。
保留回呼模型 ⟹ Cella 那側每一步都要往返一次，「執行」慢 25 倍。DAP 是 Cella 承諾的介面，也是 VSCode 的語彙。
P8：介面換一次，兩個提供者都照新形狀——JS 直譯器的回呼在它自己的提供者裡轉成指令（原本在控制器裡的 `animateResolve` 那一套搬過去）。

## 新的形狀

```
控制器    一個驅動迴圈：拿到結果 → 依模式決定「自動下一步」或「等使用者」
            執行／除錯   continue 到中斷點
            單步         stepIn；按「繼續」＝照速度自動往下走
            動畫         stepIn ＋ 延遲；碰到中斷點或「暫停」才等
          等輸入、跑到認不得的東西 —— 都只是一種停下原因
核心      openSession：照登錄順序問；不接的記下原因、往下找；launch 才發現跑不了（declined）也往下找
Cella     createSession 對「還沒暖機／翻不出來／除錯模組還在準備」回 Declined——由 JS 跑，狀態列說得出為什麼
```

## 舊的哪些前提換掉了

- **「停在一顆」＝那一顆執行完了**：JS 直譯器的每步記錄在執行**之後**——停在 `cout` 時已經印出去，改值來不及影響。
  DAP 的慣例（Cella 量到的也是）是停在**即將執行**的那一顆。直譯器加了「執行之前」的掛鉤，兩個提供者一致。
- **單步的輸出在第一步之前就全部印出**：先錄再播的副作用。`e2e/debug.spec` 的「加速」那一支原本量到的正是它——改成照真實語義多走一步。
- **覆蓋標記（哪幾塊沒跑到）一定有**：Cella 的快路徑給不出——cella 答應下一輪加 `coverage()`；在那之前狀態列誠實說「這次沒有覆蓋資料」。

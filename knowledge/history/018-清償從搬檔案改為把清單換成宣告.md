# 018：清償「碎裂」的做法，從「把東西搬走」改為「把清單換成宣告」

> 日期：2026-08-06

## 轉移

- **舊**：路線圖的 P2 寫「lift + execute 搬回模組（17 次）」。清償碎裂的手段被想成**搬移**——東西散在核心層，把它搬回它該在的語言套件就好。
- **新**：**搬檔案解決不了主要的那一塊。** `interpreter.ts` 的 61 筆中立性違規裡，34 筆根本不是執行器，是**兩份寫死的清單**（「哪些概念不執行」34 個 + 「哪些概念算一個除錯步驟」27 個）。清單搬到哪裡都還是清單。要治它得換形式：**讓概念自己宣告，核心只讀宣告**。

## 為什麼變

因為去量了才發現形狀不對。

原本要開的功能就叫「execute 搬回語言套件」。Phase 0 一查——那些「違規」有一半以上是概念名的**字串清單**，不是可以搬走的程式碼。

而且上一輪（`specs/049-audit-guardrails`）為這件事**建好的機制一直沒被接上**：`ComponentDefJSON.skipPaths` 欄位存在、註解寫得很清楚（「未宣告的空實作一律判為殼——正確的空與缺失的空長得一樣，所以要求正確的那個出聲」），而**宣告了它的概念有 0 個**。

> 一個為了讓「刻意的空」出聲而建的機制，自己從沒被接上——`concepts/執行機構.md` 裡正好有一節叫「執行機構自己也可能是殼」。

## 那份清單還不只是文件

追下去發現更糟的一層：執行器註冊表是 `Map.set`（後註冊的贏），而那份清單在**所有真實作之後**才跑。

**四個轉型概念有能用的實作，被清單無聲覆蓋。** `static_cast<int>(3.9)` 輸出 `void`——程式跑完、印出東西、而它是錯的，沒有任何提示。

不是沒實作，是實作被關掉了。修法是刪掉清單裡那四行。

## 但「把清單換成宣告」有一個陷阱，而它是這個轉移最重要的部分

**宣告會讓兩條護欄的數字同時下降，而系統一點都沒變。**

原本以為工作是「把 34 個都改成宣告」。實測（每個概念一支最小程式，跑直譯器比對輸出）：

| 判定 | 數量 |
|---|---|
| 真的不執行 | 10 |
| 由父概念消費（父節點的執行器會走訪它） | 2 |
| **還沒實作（跑起來結果是錯的）** | **14** |
| 判不出來（概念沒出現在語義樹裡） | 5 |
| 死條目（概念註冊表中不存在） | 3 |

**只有 12 個配得上宣告。** 十四個裡有十個是物件導向——直譯器不支援它，把它們做成空操作，讓「不支援 OOP」看起來像「OOP 不需要執行」。

把 34 個都宣告掉不是落實那條判準，是**拿那條判準當藉口**：把缺陷洗成設計，然後讓護欄替它背書。

所以宣告需要門檻，而理由**只有兩個值且不得增加**——第三個值就是在替「還沒做」找一個體面的名字。

## 狀態

✅ 已採用。`specs/053-declare-noop-execute` 已實作。

**這是階段 6.5 第一次讓護欄的數字真的下降**：中立性 216 → 174 筆、完備性殼 92 → 76。但只有 4 個是真的修好（那四個轉型），其餘是說清楚。完備性報表因此**改成三欄**（實作／已宣告不提供／殼），否則用宣告刷數字看起來會像進步。

**P2 的搬移仍然要做**——`interpreter.ts` 還剩 33 筆（15 條已知缺口 + 18 個 inline 執行器），那些才是真的要搬的東西。這條轉移改的是**先做哪一塊**，不是取消 P2。

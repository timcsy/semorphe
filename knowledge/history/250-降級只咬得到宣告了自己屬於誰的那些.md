## 一、它為什麼躲得過前五關

`downgradeComponentsForLevel`（漸進揭露）會把「不在這一軌可見概念集裡」的節點
換成**它自己宣告的抽象父**。而

```
cpp:var_declare_sequence   abstractComponent: cpp:var_declare      ← 有父 ⟹ 會被降級
cpp:container_find         abstractComponent: null                 ← 沒父 ⟹ 原樣畫出來
```

⚠️ 所以**「不在課程清單就會降級」不是通則**——`container_find`／`container_iter`
同樣只在進階那一軌的清單裡，而它們在初級軌畫得出來。

> **降級只咬得到「宣告了自己屬於誰」的那些元件
> ——而那正是最該被完整保留的那些（它們有更多格）。**

而五個面向**每一個都不經過那條投影**：
①②④⑤ 都不看課程清單，③ 量的是「載得進去嗎」而不是「載進去的是不是同一顆」。

> **一個只在【某一條投影】上壞掉的缺陷，
> 任何不經過那條投影的測試都會是綠的。**（這支 skill 的檔頭，逐字）

## 二、而錨點才讓結論成立

第一眼的讀數是「那一行不見了」。如果就這樣下結論，修的會是錯的東西。

```
負向   beginner 軌上 cpp:var_declare_sequence 畫不出來
正向   beginner 軌上 cpp:container_find       畫得出來    ← 而它也不在那一軌的清單裡
```

**兩者的差別是「有沒有宣告抽象父」，不是「在不在課程清單裡」。**
沒有那個正向錨點，我會去改課程清單的機制，而不是去看 `abstractComponent`。

## 三、修法與機構

- **修法**：把那顆元件補進另外兩軌的「容器操作」那一關
  （前置——容器與一對值——就在同一關；教學順序由**分支啟用**控制，不由清單缺席控制）
- **機構**：第 119 條護欄 `audit-silent-downgrade`
  ——「有抽象父 ∧ 比父多格子 ∧ 某一軌只收了父」的暴露數，棘輪盯著它。
  今天量到 **27 筆 / 337 顆元件 / 5 軌**。

⚠️ 那 27 筆**不是 27 個缺陷**：一筆只有在學生真的在那一軌寫出那個概念時才會發作，
而 `c-beginner` 上的 C++ 容器是合理的。**護欄量的是暴露，不是已經壞掉。**

## 四、還沒修的那一半

降級之後 blocks→code 有一條還原路（`identityBeforeDowngrade`），
而它還原的是**身分**——那些多出來的格子在積木上根本沒有位置可放，
所以抽回來時它們已經沒了。

🔴 **何時該修**：降級的目標若比來源少格子，那條路要嘛**拒絕降級**、
要嘛在畫面上**說出它省略了什麼**（`principles.md:135`：降級必須可見）。
第二個獨立來源出現時做。

# 102 — 兩條路徑的護欄第一次跑就抓到一個，而我對「哪條是死路」的判斷是錯的

**日期**：2026-08-20 · **spec**：`151-dual-path-parity` · **狀態**：完成

## 轉變

```
之前   cpp:program 有兩條產出路徑，而【沒有任何東西在比對它們】
       ——同一個轉換寫兩次，修一條、忘一條，測試全綠
之後   三個共用轉換 × 兩條路 ＝ 十支斷言；七種注入逐一驗過會紅
```

## 🔴 而這一刀開工時，我對路由的理解是錯的

我原本斷言「**legacy 是產品到不了的死路**」，理由是 `app.ts:188` 無條件裝鷹架。
`generate.ts:51` 逐字：

```ts
if (ctx.programScaffold && ctx.scaffoldConfig && !hasMainFunc) {
```

**兩條路產品都會走**：

```
樹裡【有】 main（完整的 C++ 程式）      → legacy
樹裡【沒有】main（L0 的身體／Arduino）  → 鷹架
```

⚠️ 而那個錯誤讓第一版的比對變成 **legacy vs legacy**——兩邊當然一樣。

> **一個「兩條路一樣」的綠燈，可能只是因為你兩次都走了同一條。**

🟢 **抓到它的是錨點**：「鷹架獨有的 preamble 要真的出現」那一條紅了。
⚠️ 而我第一次還把它誤判成「錨點選錯風格」（`google` 是 `explicit`，本來就沒 preamble）
——**改對風格之後它仍然紅**，那時才查到路由條件。

## 🔴 護欄第一次跑就抓到一個真的缺陷

**C 目標走鷹架那條時，手寫的 `#include <iostream>` 原樣留著**（編不過）。

根因：spec `146` 把「C 裡什麼標頭滿足這個需求」放進 `cIoHeaderFor`，
而**只落在 legacy 那條**；鷹架那條的 `cHeaderLine` 只用 `toCHeader`
（它答的是「名字」，`iostream` 在 C 裡沒有別名 → 原樣回）。

⚠️ **而 spec 146 的護欄有真的跑 `gcc`**——它仍然沒抓到，
因為**它的每一段源碼都有 `main`**，於是每一次都走 legacy。

> **同一件事寫在兩條路上，修其中一條的測試會綠
> ——而「測試很嚴格」擋不住這件事，因為嚴格的是判準，不是路徑覆蓋。**

一行修好：`cIoHeaderFor(h) ?? toCHeader(h)`，與 legacy 逐字同一條規則。

## 判準不是「兩條路產出一模一樣」

鷹架多做 preamble、進入點外殼——**那正是它存在的理由**。
量的是「**兩條路都實作的那三個轉換，效果一不一致**」：

| | 轉換 | 鷹架 | legacy |
|---|---|---|---|
| ① | C 方言的標頭改名 | `cHeaderLine` | `cIoHeaderFor` ／ `toCHeader` |
| ② | 板子的標頭替換 | `aliasIncludeLine` | 節點層的 `aliasHeader` |
| ③ | `bool` → `<stdbool.h>` | 直接 `code +=` | `buildInclude` |

🔴 **加新一格的時機沒有機械方式強制**，所以判準寫在測試檔頭：
**「在兩條路各寫一次的東西，這裡就要有一格。」**

## 量到的規模（而它沒有變成一次遷移）

```
946 支測試／139 檔（全套 20%）  在【沒裝鷹架】的世界裡跑
```
⚠️ **而那不等於它們測錯了**——`main` 存在時產品也走 legacy。
🔴 所以**沒有**去遷移那 946 支，也**沒有**刪掉 legacy 路徑：
**要不要刪，由這支護欄的結果決定，不是先決定。**

## 順帶：`build-guardrail` 補上注入的第四種結局

```
真的紅 · 真的綠 · 【沒跑起來】（注入讓建置壞掉，而輸出裡沒有 failed 字樣）
```
> **一個編不過的注入，證明的是編譯器會擋，不是護欄會擋。**

# 125　跑測試的瓶頸不在直覺的地方——兩個假設，實測都是零

**日期**：2026-08-21 ｜ **交付**：[`1d67731a`](../../.git)、[`d4d41ae0`](../../.git)
**前一則**：[124](124-護欄有了而量測機構自己沒有人量.md)
**觸發**：使用者說「跑測試變成開發的瓶頸，能不能一般時間只跑子集？」

## 轉變：問「跑哪個子集」，答案是「子集這個做法沒有用」

vitest 自己的階段分解（全套 412 檔）：

```
Duration 131.99s
  import      521.57s   ← 每個測試檔各自載入一次整個系統
  environment 213.06s   ← 而其中【只有 20 個檔真的需要 DOM】
  tests        95.01s   ← 真正跑測試只有這個
  transform    31.70s
```

機器 8 邏輯核 / **4 效能核**，實測並行度 4.1x——已經打滿。

### 兩個假設，實測都是零

| 假設 | 實測 |
|---|---|
| 排掉最慢的五個檔（它們佔 per-file wall 的 **90%**） | 132 → 133 秒，**零**。它們被並行 overlap 掉，不在關鍵路徑 |
| **護欄分層**（54 條護欄單獨跑要 85 秒） | 扣掉護欄跑全套 **141 秒，沒有變快** |

第二個是**我自己在討論裡提的方案**，而且講得很有道理
（「護欄問的不是你這次改對了嗎，是這個 repo 符不符合它宣稱的性質」）。
道理沒錯，**而它省不到時間**。

> **成本是 per-file 的模組載入，幾乎均勻攤在 412 個檔上
> ——所以「少跑一塊固定的子集」省不到那一塊單獨跑的時間。**

有效的子集是「**與這次改動相關的那幾個檔**」：`tests/unit/core`（39 檔）＝ 4 秒。
那不是「比較小的固定範圍」，是**跟著改動走的範圍**。

## 交付

1. **預設測試環境 `node`**，20 個碰 DOM 的檔在檔頭寫 `@vitest-environment happy-dom`。

   ⚠️ **安全性先查過才改**：`grep -rn "typeof window\|typeof document" src/` **零命中**
   ——產品程式碼沒有任何「偵測 DOM 存在」的分支。
   **沒查這件事就換環境，症狀會是「測試全綠而行為不同」。**

   哪 20 個：`--environment=node` 實跑抓到的 11 個失敗 ∪ 直接用 DOM API 的 19 個。

2. **分層指令 ＋ 判準寫進 `CLAUDE.md`**。判準一句話：
   **你改的是「行為」，還是「這個 repo 的形狀」？** 後者才需要護欄。

   ⓘ 順帶發現 `CLAUDE.md` 教的 `npm run lint` **不存在**——與 README 那次同一個病。

## ⚠️ 量測本身的教訓：絕對時間在這台機器上不可比

連續量測半小時之後，**同一份設定跑出 132 秒與 202 秒**（降頻）。
只有**背靠背**的比值可信：

```
背靠背（同機器狀態）   happy-dom 202s  →  node 177s     快 12%
39 個純邏輯檔取樣      happy-dom 5.97s →  node 3.85s    快 35%
environment 階段 CPU   213.06s         →  8.49s
```

> **一個需要跑三十分鐘才量得出來的指標，量到後半段時，
> 量測環境已經不是前半段那個了。**

## 順帶結清一筆掛了三次的帳

`bus-update-not-user-edit.test.ts` **第三次**在高負載下變紅，而治它的
`until()`（等條件不等時間）2026-08-20 就加進去了——14 支裡有 6 支還在用
固定 60ms 的 `tick()`。**機制修好了，而繞過它的那條路仍然是預設的走法。**

兩條教訓反流到 `experience`：

- [正向與負向斷言等太短，症狀相反](../experience.md#正向與負向斷言等太短症狀相反所以修法也不同)——正向假紅、負向**假綠**，
  而「等條件」對負向幫不上忙（沒辦法輪詢「某件事沒發生」）
- [一個固定的等待，往往同時是「等」與「讓別人跑完」](../experience.md#一個固定的等待往往同時是等與讓別人跑完換成條件輪詢只保住前者)
  ——換過去的當下 14 綠變成 2 紅，**而那兩支一行都沒動**

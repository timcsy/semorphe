# 187 · 鷹架要淡、要固定，而學生的積木要插得進去——那是同一個旗標的兩面

**日期**：2026-08-28
**前一步**：[186](186-課程有了一個看得到的入口而四個假設被使用者用一次就推翻.md)

## 轉折

`ghost` 模式（鷹架顯示但不可動）的第一版把「不可動」實作成
`block.setMovable(false)`。它做對了使用者要的第一件事，**而它讓第二件事失效**：

> 「**我的積木也要是可以插入在 main 和 return 之間的**」

實測：把 `setMovable(false)` 拿掉，插入立刻成立；換成一個
`isMovable() → false` 的拖曳策略，插入又失效。

> **「不能拖」與「不能被移動」在 Blockly 裡是同一個旗標，而我們只要前者。**

連接判定要把被擠掉的那一塊移開，而它問的正是 `isMovable()`。
所以 `ghost` 的鷹架必須**對引擎宣稱自己可動**，
再把**拖曳的每一步變成沒有動作**（`startDrag`／`drag`／`endDrag` 皆空）。

## 而「不被連帶拖走」是另一件事，它也不能用內建的那一招

使用者要的第二件事是「**回傳 0 不應該一起被拉動**」。Blockly 內建
`shouldHealStack`（按 Alt 拖曳）會把**後面整串**都留下——而使用者接著說：

> 「**我可能拖的不是只有一個積木喔**」

學生自己的那一串要跟著走，只有鷹架該留下。兩者在 Blockly 的內建語彙裡
是同一個「後續積木」，分不開。

🟢 做法：**拖曳開始前把鷹架從那一串裡摘出來，結束後接回容器尾端**
（`src/ui/panels/ghost-drag-strategy.ts`）。摘與接都包在
「不進復原堆疊」裡——那不是使用者做的動作。

## 而失敗的四版，每一版都對了一半

```
① 監聽事件、看父節點變了沒     鷹架的父節點【從頭到尾沒變】
② 監聽事件、看容器裡還有沒有它  `return 0` 消失了——容器本體是空的那一刻它被判成「不在」
③ 結構上把 main 裡的鷹架剝掉    使用者否決：「我又想彈的那邊【也都是積木】，只是不能動而已」
④ 內建 healStack               留下【全部】後續，而學生的積木該跟著走
```

③ 的否決是這一段的分水嶺：**鷹架不是「畫出來的背景」，它是積木**
——只是不能動。那句話同時否決了「用 SVG 疊一層」與「乾脆不要畫它」。

## 連帶

- **淡是畫在子元素上，不是畫在整組上**。第一版把 `main` 那一組
  `<g>` 設 `opacity`，於是「**裡面的東西不見了**」——SVG 的不透明度會
  蓋住整個子樹。改成直接子代選擇器（`.ghost-block > .blocklyPath`）。
- 一條**已經存在**的護欄斷言「淡的一定要 `isMovable() === false`」
  ——那條被這次實測推翻，改成墓碑，並把「拖不動」交給三支 e2e 各自驗。

## 留下的檢查

`e2e/scaffold-code-complete.spec.ts` 三支，各釘一件使用者說過的事：
拖走學生的整串（鷹架留下）· 插得進 `main` 與 `return` 之間 · 直接拖鷹架什麼都不會發生。

# 128　「渲得出積木」——而渲的是一份 JSON

**日期**：2026-08-22 ｜ **交付**：第五十一條護欄 `audit-block-instantiable`
**前一則**：[127](127-驗收改成跟真的直譯器對答案.md)
**觸發**：九顆新元件做完、5312 支測試全綠之後，照慣例[開瀏覽器看](../skills/verify-in-browser/SKILL.md)。

## 看到的

打開 Python 的「流程控制」分類，裡面**只有 `if`**。
`for`、`while`、`break`、`continue`、`try` 全部不見。

```
Error: Block "python_loop_for": Message index %2 out of range.
```

`message0` 是「對 %2 裡的每一個 %1」，而 `args0` **只有一格**
——被綁定的那些名字是 `paramList` **接上去的 input**，不是訊息的引數。
`python_lambda` 一模一樣的病。

⚠️ 而 Blockly 對一顆建不起來的積木的處置是**放棄整個 flyout 的其餘部分**，
所以症狀不是「少一顆」，是「這個分類從某一顆開始就沒有了」。

## 轉變：「渲得出積木」這句話換了定義

**舊的**：樹 → `BlockState`（一份 JSON），比對 `type` 欄位。
**新的**：樹 → `BlockState` → **Blockly 真的 `newBlock` 起來**。

三道防線各自漏在不同的地方：

| | 做的事 | 為什麼看不到 |
|---|---|---|
| 渲染那條路的測試 | 樹 → **BlockState（JSON）** | 沒有真的建積木 |
| 比對護欄 | 真的建，**而建不起來時 `catch { }` 跳過** | 被自己的容錯吃掉 |
| 可拿性護欄 | 這顆在不在工具箱的**來源**裡 | 在，只是建不出來 |

> **一整排「渲得出積木」的測試，如果渲的是一份 JSON，
> 那麼它們對「Blockly 建不建得起來」這個問題一個字都沒說。**

而第二列更值得記：那個 `catch { }` 是**為了讓比對繼續跑**而寫的，
它把自己本來會發現的缺陷吃掉了。

## 新護欄的兩個設計選擇

- **兩種語系各跑一遍**：`jsonInit` 展開 `%{BKY_...}` 是在**建的那一刻**，
  所以同一份宣告可以一個語系成功、另一個失敗。只跑一種等於只驗一半。
- **注入③ 專門把「訊息沒載入」排除在外**：`%{BKY_不存在}` 展不開時 Blockly
  把它留成字面，那**不是**建不起來。不排除的話真正的失敗會淹在雜訊裡
  ——這條在 `experience` 有前科（「訊息沒到齊會長得像宣告寫錯」）。

先蓋、**第一次跑是紅的（4 筆）**、再修。

## 同族的第二個症狀，同樣只有看得出來

工具箱拖出來的 `for` 是**「對 ⬤」**——中間少了那個要被綁定的名字，
而**零個名字的 `for` 不是合法的 Python**（`for  in xs:`）。

`paramList` 因此多一個宣告 `minCount`，`for` 宣告 1、函式定義與匿名函式維持 0
（`def f():` 與 `lambda: 3` 都合法）。

> **「最少幾格」是那個語言的規則，所以它是一個宣告，不是一個預設值。**

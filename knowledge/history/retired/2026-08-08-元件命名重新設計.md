## 判準

根公理是「唯一真實，各式投影」。推論：**名字要命名語義，不能命名任何一種投影。**

檢驗：換一個語言，這個名字還說得通嗎？

- `lang:endl` — C++ 的 token 名，Python 沒有。**不及格**
- `lang:count_loop` — 沒說 `for`，說的是「數著跑」。**及格**（現有最好的一顆）
- `cpp:ternary` — 「三個運算元」是怎麼寫，不是做什麼
- `cpp:comma_expr` — 命名了一個標點符號

### 導出的三條

1. **主體用抽象資料型別，不用具體容器**——`vector` 是拼法，語義是「可增長的序列」。
   但 `stack`／`queue` 保留，它們的語義**真的不同**（LIFO vs FIFO）。
2. **操作用語義動詞，不用 std 方法名**——`push_back` → `append`。
3. **分不出來就是同一顆，差異變成參數**——判準就是 B 項與 C1 反覆撞到的那個：
   **差異能寫成參數而執行器只是分支，那它就是參數不是身分。**

## 實測：177 顆分四堆

| 堆 | 顆數 | 意思 |
|---|---|---|
| **① 通用化零風險** | **40** | C++ 只有一種拼法（`string_length` → `.length()` 永遠是它） |
| **② 需要語義參數軸** | **42** | 多種拼法，但說得出語義意圖 |
| **③ 不該通用化** | **67** | 說不出語義意圖，語言特定性是**真的** |
| **④ 已經對了** | **28** | 通用層既有元件 |

**① ＋ ② = 82 顆（46%）目前掛在 `cpp:`，而語義是通用的。**
那是 scope 劃分錯的規模——現在的 scope 記錄的是「這顆從哪個語言長出來的」，
不是「它屬於誰」，而 D 的設計文件白紙黑字寫著 scope 是所有權。**名字沒改，
那條決定只落實了一半。**

**③ 有 67 顆（38%）不用動**——指標／手動記憶體、四種轉型、前處理器、
C 字串函式、C++ 物件模型、`printf`/`scanf`。這是好消息：大部分不必碰。

### 順帶抓到三顆掛錯的

- **`lang:endl`** —— 命名了 C++ token，卻掛在 `lang:`
- **`lang:forward_decl`** —— 前向宣告是 C/C++ 編譯模型的東西，不該在 `lang:`
- **`lang:builtin_constant`** —— 值域混了通用（`true`/`false`）與 C 家族（`EOF`/`NULL`/`nullptr`）

## 歧義風險：只有兩組，7 顆

「通用化之後轉回來會不會有歧義」是這個設計唯一會出事的地方。實測合併族
在合併後對到幾種 C++ 拼法：

| 合併族 | 顆數 → 拼法數 | 判定 |
|---|---|---|
| 空否 / 清空 / 加到尾端 / 索引取值 | 2 → 1 | ✅ 拼法相同，合併零歧義 |
| 容器宣告 | 6 → 6 | 🟡 差異本來就要寫進參數（存取紀律），參數自己選得出來 |
| 字串搜尋 | 3 → 3 | 🟡 同上（方向／否定） |
| **大小** | **2 → 2** | 🔴 `.size()` vs `.length()` |
| **看某一端** | **5 → 3** | 🔴 `.back()` / `.top()` / `.front()` |

**只有這兩組（7 顆）需要靠上下文才選得出拼法**，而上下文是**接收者的型別**。

> ⚠️ 而那套型別追蹤**已經存在**——`TYPED_METHOD_TO_CONCEPT` 在 lift 方向用著
> （`string.clear` → `cpp:string_clear`）。缺的是**把它接到 generate 方向**。
> 那是一件具體的工程，不是未知數。

## 真正的陷阱不是歧義，是耦合搬家

`lang:sequence_declare` 帶一個參數 `impl: vector|deque|list` —— **一個 `lang:`
元件的參數值域是 C++ 詞彙。** 耦合沒有消失，它從身分搬到了參數。

而**中立性護欄量不到這一維**：它掃元件身分字串，不掃參數的允許值。

這與 `history/021` 是同一個形狀（「中立性的數字只量身分那一維」）。
照著做下去，我們會把耦合搬到一個**沒有護欄的維度**上，然後數字看起來更漂亮。
**那比不通用化更糟。**

→ 參數必須是**語義軸**（`discipline: sequence|lifo|fifo|priority`），
不是實作軸（`impl: vector|stack|queue`）。而這需要一條新護欄：
**`lang:` 元件的參數值域不得出現語言專屬詞彙。**

## 一個要避開的錯答案

把原始拼法塞進 `metadata` 保 round-trip。**不要。** metadata 不是真實，
靠它保 round-trip 等於承認真實不在語義樹裡——那正是 P8 推導自的
「投影可重建」在講的東西。要嘛進參數（是真實），要嘛不通用化。

## 時機

**必須在 F（膠囊搬家）之前。** F 讓每顆元件搬進自己的目錄，而**目錄名會從
元件名來**。名字晚一步改，F 就得做兩次。

## 安全網

- **來回轉換測試**——通用化如果丟了資訊，`vector<int>` 轉一圈變成別的，當場紅
- **概念身分驗證**——roundtrip 測試會驗語義樹用的是正確的 conceptId
- **存檔轉換**——D 已經把 `registerIdMigration()` 的機制建好，這次是沿用

做錯的通用化**會被抓到**，風險從「安靜地壞掉」降到「會紅」。

## 未決的

1. **要不要做**——82 顆改名 ＋ 兩組型別上下文接線，換到的是 P9 真的成立、
   Python 進來時不用再叫一次 `py:list_declare`
2. **`lang:if_else` 是 `lang:if` 的形態還是身分**——B 項合併過同型的東西
3. **語義軸的詞彙要怎麼定**——`discipline`、`end`、`direction` 這些軸名本身
   要有人拍板，而拍錯了會像 `impl:` 那樣把耦合藏起來

# 翻轉（2026-08-08 同日，「假設已經支援多種語言」重看）

## 上面那份分類是從一個樣本判的

假設 Python／JS 現在就在，重看「③ 不該通用」那 67 顆：

| 我的判定 | 我當時寫的理由 | 三語言在場時 |
|---|---|---|
| `cpp:try_catch`／`throw` | 「catch 型別是 C++ 的」 | Python `try/except/raise`、JS `try/catch`。**catch 型別是參數不是身分** |
| `cpp:lambda` | 「capture 是 C++ 的」 | Python lambda、JS arrow。**capture 是只有 C++ 會填的參數** |
| `cpp:range_for` | 「介面是 C++ 的」 | Python 的 `for x in xs` 是**主要**迴圈，比 `count_loop` 更通用 |
| `cpp:class_def`／`constructor` | 「C++ 風味的物件模型」 | Python `class`／`__init__`。C++ 味的是 `virtual`／`operator_overload`，不是整族 |
| `cpp:printf` | 「格式字串是 C 家族特有的介面」 | Python 的 `%` 格式化**就是從 C 繼承的** |
| `cpp:switch`／`enum` | 「C 家族語法構造」 | Python 3.10 `match`、`enum.Enum` |

至少十幾顆。而錯的方向**一致**：只看得到 C++ 時，什麼都像 C++ 特有的。

> **這是「已知答案的樣本必須是查過的」的又一個實例**——我當時沒有第二個樣本可查，
> 於是用內省代替了查證，而內省產出的數字看起來與查證產出的一模一樣。

## 更關鍵：這個劃分本身不穩定

如果 scope 表達「通用還是特定」，它的值**會隨語言增加而改變**：

```
今天（只有 C++）    cpp:try_catch
Python 進來那天     lang:try_catch     ← id 變了 → 存檔要遷移
```

而 D 自己拒絕過這件事：

> Go／Modelica 走另一條：**id ＝ 位置**。買到「就近性不可能違反」，
> 代價是**搬家＝改名＝存檔遷移**。不採。
> ——`2026-08-07-元件目錄與膠囊契約.md:81`

**我們拒絕了 id＝位置，卻做了 id＝通用性——而通用性和位置一樣會變。**
只有一個語言時看不出來，因為它從來沒被迫改過。

## 而「怎麼取一個通用的名字」是一個錯問題

（這一條來自 `等價的觀察集與回饋.md` 的內涵／外延之分）

**名字是內涵的**——它只需要對得起自己的定義。而「通用」是**外延的**，
它根本不住在名字裡。

`cpp:string_find_first_not_of` 這個名字**沒有錯**，它誠實地命名了一個 C++ 的東西。
錯的是我期待名字同時宣告它的外延範圍。

於是命名規則只剩一條，而且很低調：

> **名字要說得出這顆元件自己是什麼，不必宣稱它跟誰一樣。**

## 選項改了（⚠️ 而這三個又被 (D) 取代了，見文末）

| | | |
|---|---|---|
| **(A)** | 表達通用性，但凍結（命名時掛什麼就永遠是什麼） | `cpp:try_catch` 會永遠掛著一個假的語言歸屬 |
| **(B)** | **不表達——全部 `lang:`，語言特定性當資料** | Python 進來時**零重新命名**；「誰實作它」本來就記在套件裡 |
| **(C)** | 等第二個語言再定案 | 判定從「我覺得」變成「幾個套件投影它」，是機械的。代價是 F 要等 |

~~**我傾向 (B)**~~ ——**這個推薦是錯的，見文末 (D)**。當時的理由是「它沒有問那個問不了的問題」：
`lang:`／`cpp:` 的劃分要求你現在就宣告每顆元件通不通用，而那正是
只有一個語言時說不出口的話。

D 拒絕 `universal:` 的理由是「硬體進來那天會被讀成所有域通用」——
而 `lang:` 這個名字已經把那個歧義解掉了：它說的是**語言域**，
不是「所有語言都有」。

## 不受翻轉影響的

`lang:endl`、`lang:forward_decl`、`lang:builtin_constant` 三顆。
它們不是「掛錯 scope」，是**名字命名了投影**——不管選 A／B／C 都該修。

## 還未決

1. **A／B／C 選哪個**（人拍板）
2. **`lang:if_else` 是身分還是形態**——已查證**不是身分**：
   `src/languages/cpp/core/generators/statements.ts:144-145` 兩個 conceptId
   共用同一個 `ifGenerator`，else 分支由 `children.else_body` 決定。
   依專案自己的判準（差異能寫成子槽而執行器只是分支 → 不是身分）

# (D) 各語言自理 ＋ 轉換規範分開（2026-08-09，人拍板的方向）

> **這一條取代 (A)(B)(C)。** 前三個都在問「哪些元件是通用的」，
> 而 (D) 讓那個問題不存在。

## 內容

- **每個套件擁有自己的元件**，用自己的方式命名。`cpp:vector_declare`、
  將來 `py:list_declare`——**各自完整，互不依賴**
  （⚠️ 原本寫「每個**語言**」，2026-08-09 修正為**套件**——見文末）
- **通用性住在轉換規範裡**，不住在名字裡、也不住在 scope 裡
- 加一個語言 = 新增一個自足的套件 ＋ 若干條轉換規範。**既有的一顆都不用改名**

## 我為什麼推薦錯了（比結論有用）

(B) 說「全部 `lang:`，語言特定性當資料」。它看起來避開了「這顆通用嗎」的問題。

**但它只是把決定延後。** Python 進來那天，(B) 要求對每一個 Python 構造問
「這是既有的 `lang:` 元件，還是新的一顆？」——那是**身分決定**，不可撤回，
而且需要知道既有的 177 顆。知識負擔一點沒少，只是從今天挪到那天。

(D) 把同一個判斷挪到**轉換規範**裡，而規範是可撤回、可量測、可附損失刻畫的。

> **同一個判斷，放在身分層是承諾，放在轉換層是觀察。**

而我自己在上一則違反了 [等價與觀察集](../../concepts/等價與觀察集.md) 剛立下的那條
——「外延等價可以收回，內涵身分收不回」。`lang:` 這個大桶**仍然是在身分層做宣稱**，
我只是把桶做大到讓那個宣稱看起來無害。

## 一個技術優點（推薦錯的時候沒看到）

| | 在 C++ 編輯 → 顯示 Python |
|---|---|
| 共用詞彙（(B)） | C++ →共用（有損）→ Python（有損）＝ **兩段有損** |
| **(D)** | C++ → cpp 樹（**無損**，同一套詞彙）→ Python（有損）＝ **一段有損** |

樹用的就是正在編輯的那個語言的詞彙，那一段是恆等變換。
**主要使用情境的損失更少。**

## 這不是改方向，是把現況講明白

**177 顆裡 145 顆已經是 `cpp:`。** 專案一直在做 (D)，只是沒說出口。

那 32 顆 `lang:` 才是異例。→ **要處理的是那 32 顆，不是那 145 顆。**
（我原本建議把 82 顆搬去 `lang:`，方向正好相反。）

## 還沒定的一個分岔：那 32 顆怎麼辦

「各自語言處理好自己的」有兩種讀法，成本差很多：

| | 做法 | 代價 |
|---|---|---|
| **D1**（純） | 32 顆也語言化：`lang:if` → `cpp:if`，通用消失，全靠轉換規範 | 32 顆改名 ＋ 每個語言各一份通用積木的宣告 |
| **D2**（務實） | `lang:` 降級成「**一個被各語言重用的套件**」，不是「通用宣稱」——C++ 可以選擇用 `lang:if` 而不自己造 | 幾乎零改名；但「重用」與「通用宣稱」的界線要靠紀律維持 |

**D2 仍然滿足 (D) 的精神**：語言自己決定要重用什麼、要自己造什麼——
那是**語言在處理自己的事**，只是它選了不重造輪子。

尚未決定走哪一個。

## 三件要解的事

**① 轉換規範必須能被機器用，不能只是文件**

否則 `cpp:if` 和 `py:if` 就是兩份執行器、兩份積木、兩份測試。
**宣告重複無可避免，實作重複不該**——規範要能讓系統知道
「這兩顆在這些觀察下等價，所以共用實作是合法的」。

積木層尤其關鍵：**學生從 C++ 換到 Python，應該看到同一顆積木**。
那顆積木要掛在轉換類別上，不是掛在單一語言的元件上。

**② 圖可以稀疏，但組合會累積損失**

新語言只要對某一顆既有元件宣告對應，其餘靠傳遞——`N-1` 條而不是 `N²`。
但 C++ → Python → JS 的損失會疊。**要精度的那幾對補直接的邊。**
（邊上帶著「保住哪幾路」，見 [等價與觀察集](../../concepts/等價與觀察集.md)。）

**③ 語義樹在哪個規範裡**

唯一真正的架構問題。答案大概是：**樹用它來源語言的詞彙，而「它現在在哪個
規範」是樹的一部分**。換語言 = 一次轉換，並記下損失。

這會鬆動「唯一真實」的讀法——真實不再是一棵語言中立的樹，而是
**一棵樹加上它的規範標記**。我認為這是誠實的鬆動：語言中立的樹本來就不存在，
我們只是一直假裝它存在（**而它其實長得像 C++**）。

## 對 F（膠囊搬家）的影響是正面的

F 要的就是**套件自足**。(D) 讓那件事變乾淨：`cpp:` 的東西全部在 cpp 套件裡，
沒有一顆元件的定義住在「通用」而實作住在語言側。

而且 **F 之前不需要大規模改名了**——145 顆不動。

## 不受影響、隨時可修的三顆

`lang:endl`、`lang:forward_decl`、`lang:builtin_constant`。
在 (D) 底下更明顯該修：`endl` 是 C++ 的 token，就該是 `cpp:endl`。
不管走 D1 還是 D2 都一樣。

`declare` 22 ／ `assign` 6 ／ `access` 5 ／ `back` 5 ／ `cast` 4 ／
`literal`・`loop`・`def`・`of` 各 3 ／其餘 2

## 命名孤島 83 顆（47%）——但不全是壞的

`if`／`break`／`return`／`print` 本來就該是單字。真正雜亂的是其中**約 35 顆裸的函式庫名**：

```
strlen strcmp strcpy strcat strncpy strncmp strchr strstr memset memcpy
sort reverse fill min max swap getline to_string stoi stod rand srand
abs exit atoi atof isalpha isdigit toupper tolower accumulate iota
partial_sum gcd lcm make_pair
```

## 同義操作詞（各用一次，所以頻率表看不到）

| 一件事 | 現在有幾個字 |
|---|---|
| 大小 | `size`（vector）／`length`（string） |
| 加入 | `push`／`push_back`／`insert`／`append` |
| 取值 | `access`／`at` |
| 看某一端 | `top`／`back`／`front` |

## 接收者參數名的分歧

`obj` **30 顆** vs `vector` **3 顆**（`vector_size`／`vector_pop_back`／`vector_back`）。
**同一個角色兩個名字，而少數方只有 3 顆——最便宜的一筆。**

## 機械掃描順帶抓到的一類（我沒預期）

**同一個字在不同位置扮演不同角色：**

- `static` → `static_cast`（轉型）、`static_declare`（宣告）、`static_member`（成員）
  ——它是**修飾詞**，卻站在主體的位置
- `const` → 同樣（`const_cast`／`const_declare`）
- `back` → 有時是方向（`push_back`）有時是操作本身（`vector_back`）
- `array_2d` → **維度寫進了名字**（照跨域規則第 ②，那該是參數）

| 量 | 現在 | 目標 |
|---|---|---|
| 同一角色的參數名種類 | 2 | **1** |
| 同義操作詞群 | ≥4 | **0** |
| 裸的函式庫名 | ~35 | **0** |
| 修飾詞站在主體位置 | 2 族 | **0** |

# 三個懸而未決的問題，已有答案（2026-08-09）

## 分隔符：統一 `_`

現行設計文件裡兩種都有（`cpp:vector_declare` 底線、`hw:arduino-uno` 連字號）。

不採「scope 用 `-`、name 用 `_`」——那是借了 npm 的慣例卻沒借它的理由
（npm 用 `-` 是因為套件名出現在 URL 與 shell）。我們的 id 出現在字串字面與目錄名。

**成本**：改一份還沒實作的 draft 裡的兩個例子。而且這一條要進護欄——
分隔符是最容易被下一個人「順手」用成另一種的東西。

## 套件粒度：scope ≠ 套件

見 [元件套件管理](../../draft/2026-08-09-元件套件管理.md)。一個 scope 可以有多個套件；
拆合套件不改任何 id。

## 積木住哪裡：**各語言各自**（推翻了我的提案）

我原本提「積木共用，掛在轉換類別上」。**錯的，而且錯在同一個地方兩次。**

**錯誤一：共用一顆積木會變成所有語言需求的聯集。** C++ 要型別下拉、Python 不要
——於是 Python 學生看到一個他永遠不會動的欄位。而每加一個語言聯集就長大一次。

> **那就是 `impl: vector|deque|list` 的重演**——一個只有某個語言會填的槽，
> 寄生在共用的東西上。我前一則才說那是陷阱，然後自己在積木層又做了一遍。

**各語言各自的積木才是誠實的**：C++ 的有型別下拉因為 C++ 真的需要。

**錯誤二：把共通的意義塞進機器層。** 我一直想把抽象概念掛積木、掛執行器，
所以卡在「轉換類別要不要有 id」。它該在**圖鑑／教學**——那裡不需要 id，
因為沒有人執行它。

### 那「換語言時使用方式類似」靠什麼

不是靠共用產物，是靠**設計慣例**：一致的詞彙 → 一致的標籤 → 一致的形狀。

> **G 不是美化工程，它就是「使用方式可轉移」的實作。**

### 修正後的五路共用

| 路 | 共用嗎 |
|---|---|
| generate ／ lift | ✗ **語言的差異就在這裡** |
| render ／ extract | ✗ 積木各語言各自 |
| execute | **可以，但要證明**（等價在這一路成立才共用） |

**共用縮到最多一路，而且是 opt-in 加證明。**

### 重複的成本，以及一個不創造身分層的中間選項

`py:if` 和 `cpp:if` 的積木宣告會幾乎一樣。可以接受，因為**它們遲早會分岔**
（Python 有 `elif`／`for...else`）——提早抽象的代價是分岔那天要拆，而拆比重複貴。

中間選項：**積木模板**，各語言套件實例化一份共用模板。那是共用實作不是共用身分。
晚點決定。

## 連帶確定的：D1（純的）

`lang:` 這個 scope 沒有工作了——不是元件套件（各語言自足）、不是積木套件
（積木各語言各自）、抽象概念住在圖鑑（是內容不是 scope）。

→ 32 顆變成 `cpp:*`。Python 來的時候 `py:if` 是**新元件**，不是改名。

# 修正：scope 是套件擁有者，不是語言（2026-08-09）

(D) 一路寫成「各**語言**自理」。更準的是「各**套件**自理」。

第一方的情況下兩者重合（`cpp:` 的東西都針對 C++），所以區別看不見。
**第三方一出現就分開**：有人發佈 Boost 的元件，語義上是 C++ 的，
但擁有者不是第一方，所以是 `@someone:*`。而一支 C++ 程式可以自由混用兩者。

→ **「這顆元件針對哪個語言」是欄位，不是 scope。**

這才符合 D 自己的決定（scope ＝ 所有權，不是分類）。把它讀成語言，
是因為當時只有第一方。

# 122　切語言之後才發現的三處——而它們都是同一句話

> 日期：2026-08-21　specs 171／172
> 起點：使用者回報「切到 Python 會有 `⟨unknown component: cpp:program⟩`」
> 與「那邊的積木選擇無法選到前面已經有的變數」
> 上游：[history/121](121-Python的執行期而十七顆執行器第一次被跑過.md)

## 轉變

```
old  三個組裝點各自寫死了「某一個語言的答案」，而它們在啟動時決定、切語言時不變
       ① 程式根的建構子     ② 語言的安裝     ③ 哪些積木會產生變數名
new  🟢 三個都改成【問宣告】，而語言套件多了兩格（programRoot／install）
```

## 一、三處，而它們是**同一句話**的三個實例

> **組裝點知道「要把每個語言接上」是正常的，
> 知道它們各自怎麼接不是——後者代表加第三個語言要再編輯它一次。**

| # | 寫死的東西 | 症狀 |
|---|---|---|
| ① | `import { buildProgram } from '.../cpp/program/lift'` | `⟨unknown component: cpp:program⟩` |
| ② | `registerCppLanguage()`（只接一個語言） | 根對了而**沒有人認得它** |
| ③ | 一長串積木型別（`cpp_var_declare`…） | 新語言的變數**一個都進不了下拉** |

## 二、🔴 第二層藏在第一層的錯誤訊息**後面**

修好 ① 之後，訊息從 `⟨unknown component: cpp:program⟩`
變成 `⟨unknown component: python:program⟩`——**只差那個前綴**。

> **訊息「變了」與訊息「消失了」是兩件事。**
> 一個「未知的 X」修好之後，要**再跑一次同一個情境**，
> 而不是看到訊息變了就當作修好了。

## 三、🔴 而 ① 只在**單一方向**上壞掉

```
程式碼 → 積木    根是 lift 出來的     🟢 對
積木 → 程式碼    根是【組裝點建的】   🔴 而它寫死了
```

⚠️ **我當天驗過那條路**——而我驗的是 `syncCodeToBlocks`（貼程式碼進來）。
使用者是**按了執行**才走到另一個方向。

> **一個缺陷如果只在某一條投影上出現，任何不經過那條投影的檢查都會是綠的。**

`verify-in-browser` 的檔頭早就寫著這句話，而它講的是「測試 vs 瀏覽器」
——**這一次是同一個面板的兩個方向。同一句話，更細的粒度。**

## 四、`programRoot` 是**兩份宣告**，而它們說的不是同一句話

```
元件說   「我是一個程式根」          traits.programRoot     （它自己的性質）
套件說   「我的程式根是【它】」      LanguagePack.programRoot（這個語言選了誰）
```

🔴 **不能用 `componentWithTrait('programRoot')` 代替後者**——它回傳第一個匹配。

> **一個「全域只有一個」的假設，在第二個成員出現時不會報錯——它會挑一個。**

（這句話 `traits.ts` 的 `isProgramRoot` 檔頭在 spec 160 就寫下來了，
而**寫下來沒有讓它不再發生**——因為那一處改了，別處沒有。）

🟢 兩份由護欄互相對帳，並加一條**反向**：
每一顆說自己是根的元件，都要有某個套件認領它
——**一顆沒有人認領的程式根，是一個永遠用不到的根，而它看起來很正常。**

## 五、③ 的修法是「加第二條路」，不是改既有那條

C++ 那一長串**沒有動**：它是 `vision` 記著的那批命令式定義的一部分，
改它要走比對護欄。**兩條並存到那批退場為止。**

⚠️ 而護欄因此要顯式豁免 `cpp`——**那是一筆記在帳上的債，不是這條護欄的漏洞**。

🟢 護欄用**注射**證明擋得住：拿掉三顆的宣告 → 紅（指名 `python`）→ 還原 → 綠。

## 六、順帶：P3 護欄抓到我的**註解**

`block-registrar` 不准出現任何語言的名字，而我在新註解裡寫了「Python」。

🟢 而那是對的——**P3 的精神是「加一個語言不必動這個檔」，註解也一樣**。

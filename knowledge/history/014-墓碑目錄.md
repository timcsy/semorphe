# 014：墓碑目錄（考慮過但未採用的選項）

> 日期：2026-03-04 ～ 2026-08-05（各條列於下）

這裡放**曾經被認真考慮、但從未生效**的選項。它們不是轉移（沒有東西被 superseded），但「為什麼不選」往往是最濃的 why——沒記下來的話，未來會有人重新提案，而且提得理直氣壯。

---

## 讓 LLM 當核心引擎

⚰️ 已否決（2026-03-07）

**考慮過什麼**：既然 LLM 能理解程式碼，直接讓它做 lift、做跨語言轉換、做概念辨識。

**為什麼不選**：語義結構是確定性的，LLM 是機率性的。讓 LLM 當核心，語義結構就從 source of truth 變成「LLM 覺得大概是這樣」——根公理「語義結構是唯一真實」隨即失效，roundtrip test 也失去意義（沒有穩定的 T 可比對）。

**正確定位**：語義結構提供 guardrails，LLM 在 guardrails 內活動。LLM 可以留言，不能 merge。

**解凍條件**：無。這條是根公理的直接推論，除非根公理改變。

## 模擬 C preprocessor 來解決巨集

⚰️ 已否決（2026-03-09）

**考慮過什麼**：自己實作 C preprocessor，展開巨集後再交給 tree-sitter，解決巨集導致的大面積降級。

**為什麼不選**：重新實現 C preprocessor 的正確性成本極高，而收益只在 S3-S5（大型專案分析）——而那些 Scope 的視圖本身就是唯讀的（R3-R4），精確度要求較低。S0-S2 的教學場景根本不需要（學生程式碼不會用框架巨集）。

**改採**：多 parser 融合——tree-sitter（快速、增量、不展開巨集）處理非巨集區域，clang AST（較慢、完整、展開巨集）補充巨集區域，兩者在**語義樹層面**合流。不需重新實現 preprocessor，只需在語義層整合兩個已有 parser。

**解凍條件**：若 clang 依賴在目標環境不可行，且 S3-S5 分析成為主要場景，需重新評估。

## 向後相容 / migration / 過渡期

⚰️ 已否決（2026-03-09，隨「不做向後相容」原則確立）

**考慮過什麼**：每個 Phase 保留舊 API、寫 migration script、設過渡期讓兩套並存。

**為什麼不選**：語義結構是唯一真實，投影可重建——舊格式的資料可以用新程式碼重新產生，不需要相容層。而相容層的代價是永久的：每一個 `??` 預設值、每一個 `if (isOldFormat)` 分支都會活得比它該活的久，並在某天把資料遺失偽裝成正常降級。

**改採**：clean break。編譯器就是驗證器。

**已知的踩坑**：`??` 被誤用為向後相容機制時，正是靜默降級的溫床——見 [experience.md](../experience.md)「靜默降級是 bug 的藏身之處」。

## 用單一 level 數字解決 toolbox 過濾

⚰️ 已否決（2026-03-11，隨 [008 樹狀層級樹](008-概念層級從線性改為樹狀加-topic.md) 確立）

**考慮過什麼**：`level <= currentLevel` 一條判斷決定積木是否顯示。

**為什麼不選**：實作中發現至少四個正交維度同時作用——IO 偏好（iostream vs cstdio）、Code Style（APCS 不需要 `bits/stdc++.h`）、語言專屬 vs universal 積木的 level 協調、Topic。硬塞進一個數字會讓這些維度互相污染。

**改採**：`f(Topic, P4 概念層級, View Params)`，三者職責分明不混用。

## 每個等級用不同語法（Hedy 路線）

⚰️ 已否決（2026-03-04，隨根公理確立）

**考慮過什麼**：像 Hedy 一樣，L0 用簡化語法、L1 用中階語法、L2 才是真正的 C++。

**為什麼不選**：這會讓「同一個程式」在不同層級是**不同的東西**，違反根公理。Semorphe 的做法是同一棵語義樹、不同投影解析度——L0 學生看到的和 L2 學生看到的是同一份真實的不同投影，切換層級不需要重寫任何東西。這也是 Sc2（鷹架可退場）的前提：積木不可引入文字程式碼中不存在的概念。

## 在程式碼之上疊一層積木

⚰️ 已否決（2026-03-04，隨根公理確立）

**考慮過什麼**：以程式碼為真實，積木作為一層可視化包裝（Blockly/Scratch 的傳統做法）。

**為什麼不選**：這使積木→程式碼單向不可逆（R4），失去雙向 round-trip。**只有語義層存在**，程式碼和積木都是參數化投影——這是與所有現有工具的根本差異。

## codeTemplate 與 hand-written generator 並存

⚰️ 已否決（2026-03-09）

**考慮過什麼**：兩者都留著，讓 template 處理簡單情況、generator 處理複雜情況，互為後備。

**為什麼不選**：template 優先，所以 hand-written generator 完全不會被執行，而**開發者不知道自己的程式碼根本沒用**。更糟的是真實 app 載入 template、測試常常沒載入，導致**測試通過但實際行為不同**。

**改採**：互斥——改用 hand-written 時必須從 JSON 刪除 `codeTemplate`。長期方向是移除 hand-written，讓 template 成為唯一來源（減少雙真相源）。

## 用「最近節點」啟發式歸屬獨立註解

⚰️ 已否決（2026-03-08）

**考慮過什麼**：獨立註解（`// section header`）依「離哪個節點最近」附著到該節點上。

**為什麼不選**：註解會漂移——插入或刪除相鄰語句時，註解會突然改變歸屬。

**改採**：獨立註解作為**無操作的平級節點**進入 children，不附著任何節點。行尾註解才用附著模型。

## 把 λ-calculus / Cubical TT 當通用 IR（取代語義樹）

⚰️ 已否決（2026-08-05）

**考慮過什麼**：用一套極簡核心（無型別 λ-calculus 5 節點：Constant/Variable/Let/Application/Match，或更早的自寫 Rust Cubical TT）當通用 IR，把 C++／Python／各語言都 desugar 進去，再投影成積木與程式碼。理由是「圖靈完備 + 5 節點就能包一切 + 和 Blockly 1:1」。

**為什麼不選**：

- **根公理反向**：Semorphe 的真實是**高階語義概念**（`count_loop`／`print`／`cpp_vector_push_back`，發現而非發明）。λ-core 做的是 lowering——把 for 迴圈降成尾遞迴+Match、print 降成 Application——**摧毀語義意圖**。
- **違反 Sc2／Sc3**：把 `while` 存成 `let rec loop = λx…` 憑空引入學生程式碼裡沒有的遞迴與 lambda（Sc2）；for 拆成遞迴+Match 後積木不再 1:1 對一個語法結構（Sc3）。
- **可逆性反而變差**：for 和 while 降到同一個 Match+遞迴結構 → 丟失區別 → round-trip 從 R0 掉到 R1。「和 Blockly 1:1」是假的——積木對齊高階概念，不對齊 Let/App/Match，轉出去還要「resugar」猜回來。
- **Untyped 是退步**：型別退回文字貼紙，違反已學到的「屬性的結構化邊界」——正是「複合型別字串解析」那條技術債的根因。

**正確定位**：λ-core 有合法位置，但**在語義樹底下**當直譯器的 lowering target，不是取代 `SemanticNode` 的編輯 IR；Cubical TT 可當未來程式驗證投影（R3-R4）的**選配分析後端**。核心是根公理直接推論：語義樹是唯一真實，不換核。

**解凍條件**：無（同「讓 LLM 當核心引擎」——除非根公理改變）。

**場景**：這條的心路歷程見 [episodes/2026-08-05-λ與cubical-tt探索](../episodes/2026-08-05-λ與cubical-tt探索.md)。

## 開一個獨立的硬體專案（像 Blockly 那樣）

⚰️ 已否決（2026-08-05）

**考慮過什麼**：把 ArduinoCAD 改名後留成獨立專案，負責硬體那一面（零件、電路、2D/3D、物理），Semorphe 負責軟體那一面，兩者靠協定溝通。類比是「Blockly 是獨立的，Semorphe 只是用它」。

**為什麼不選**：

- **Registry 必須是一個。** 跨域接線（積木輸出 → 硬體 pin）需要共同的登錄表與共同的 `componentId` 命名空間。兩個專案＝兩個 registry＝回到 N×M，合流的整個賣點消失。
- **沿域切會複製「按機制分檔」那個病。** 碎裂的根因診斷是「按機制組織，於是任何單一元件必然被攤散」。開硬體專案就是把元件沿**域**再攤一次——同一個病、換個維度，而且 repo 切分是最貴的一種切。
- **和 [concepts/元件](../concepts/元件.md) 的核心主張衝突。** 「元件是三域同一抽象」「關係律跟資源走不跟域走」。硬體要獨立專案，那 UI 將來也要一個、第四域再一個——母抽象退化成口號。
- **類比不成立。** Blockly 對 Semorphe 是**投影後端**（它不知道 `count_loop`）；ArduinoCAD 的內容有四成是**元件與求解器**，那是語義不是投影。

**正確定位**：切分是「**語義 vs 投影後端**」，不是「軟體 vs 硬體」——元件庫與守恆求解器進 Semorphe，只有渲染／幾何留在 seam 後。見 [硬體域併入計畫](../draft/2026-08-05-硬體域併入計畫.md)。

**解凍條件**：無（除非根公理改變）。

## 把渲染／幾何抽成獨立 npm 套件

⚰️ 已否決（2026-08-05）——**帶解凍條件，非永久**

**考慮過什麼**：把 2D SVG renderer、3D circuit renderer、參數化 CAD 引擎抽成獨立套件，理由是「它們是投影後端、不理解語義，邊界乾淨，像 Blockly 一樣」。

**為什麼現在不選**：

- **過不了 [over-justify](../skills/over-justify/SKILL.md)。** 多解釋 ✗（同一份碼換地方）、多預測 ✗、壓縮 ✗（一樣的量，多一份 package.json 與發版流程）。三個都不中。
- **只有一個消費者。** Blockly 是獨立套件因為 Google 為很多消費者寫；單一消費者的套件，介面是對**想像**設計的，不是對壓力——那正是 011／048「各統一一半」的溫床。
- **決定性論據：seam ≠ package 邊界。** ArduinoCAD 的零相依 ethos 就是這樣達成的——THREE／Rapier／three-bvh-csg 全隔離在注入 seam 後、`package.json` 維持 `{}`、**而那條 seam 在同一個 repo 裡**，撐過 32 條 history。薄協定要的是**窄接縫，不是分開的倉庫**。
- **repo 切分是最貴的一種切**，而本專案的頭號病就是「同一塊碼沿不同軸反覆重切 ＝ 碎屑」。

**正確定位**：`src/render/` ＋ 一條 `audit-render-boundary` 測試（斷言不 import 語義層）。**零洩漏被測試保證，所以哪天真要抽，那個資料夾直接搬走就是套件**——決定被推遲到有資訊的時候。

**明確不是理由**：bundle 大小。THREE＋Rapier＋CSG 對只寫 C++ 的使用者是負擔，但那是 code-splitting 的事。另外，**零相依是 ArduinoCAD 的紀律、不是 Semorphe 的**（本專案本來就有 `blockly`／`monaco-editor`／`web-tree-sitter` 三個執行期相依）——別把對方的約束當自己的。

**解凍條件**：**出現第二個消費者**（有人不透過語義樹就想渲染零件）。

## `var_declarator`——「宣告子」當成一個概念

⚰️ 已否決（2026-08-07，B 項身分整併時實測發現）

**考慮過什麼**：`int a = 1, b = 2, c;` 裡的每一個宣告子（`a = 1`／`b = 2`／`c`）是一個概念，properties 只有 `name`、children 只有 `initializer`，五路裡四路標著「由父概念消費」。

**它曾經真的存在**：有概念定義、有執行器、有抽取策略。**而沒有任何辨識路徑產出過它**——第十八條護欄（元件身分健檢）報出的「零測試足跡」三顆之一。

**為什麼不選**：它假設**所有宣告子都是純名字**，而那不成立：

```cpp
int a = 1, *p = nullptr, arr[3];
//  ↑ var_declare  ↑ cpp_pointer_declare  ↑ array_declare
```

三個宣告子是**三個不同的概念**。系統實際做的（每個宣告子各自是完整的宣告概念，掛在外層 `var_declare` 的 `declarators` 槽裡）比這個模型richer且正確。

> **系統做對了，模型錯了。** 而模型錯了三個月沒有人發現，因為**沒有東西在檢查「有沒有路徑到得了這個概念」**——直到蓋了那條護欄。

**解凍條件**：無。要重提的話，得先說明它怎麼裝下不同形狀的宣告子。

## 把位置編碼進元件身分（`*_expr` 雙版本）

⚰️ 已否決（2026-08-07，階段 6.5 的 B 項）

**考慮過什麼**：`i++` 當敘述用與當運算式用是兩個概念，各有 id、各有五路。系統一度有**六對**：`func_call`／`cpp_method_call`／`cpp_increment`／`cpp_compound_assign`／`var_declare`／`cpp_scanf`。

**它為什麼會出現**：078 修一個真缺陷——辨識器永遠產出運算式版，敘述位置的身分拿不到。修法是依語法樹的父節點在兩個身分之間選。**症狀修好了，但位置被修進了錯的槽。**

**為什麼不選**：

- 協定裡 `role` 是**屬性**，不是身分的一部分（`concepts/元件.md`）
- 代價是每一對都要在五路上各維護一份，而 `saveExtraState` 的格式契約要**人工同步**——memory 記著那個坑
- 實測：六對的 properties 與 children **完全相同**，只差 `role`
- 而且四個敘述版產生器**早就是位置感知的**（`ctx.isExpression`），`_expr` 產生器是純重複

**正解**：位置由**形態**表達——一個身分、兩個積木、由呼叫端說位置（097 的多形態機制）。

**解凍條件**：若哪天發現某一對的**行為**真的不同（不只是值有沒有被用到），那一對該拆回去——但那時它是兩個概念，不是「同一個概念的兩個位置」。

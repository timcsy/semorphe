## 一、三個建構子，而**加減的是什麼**才是它們的分界

```
variadic     加減【值插槽】       EXPR0、EXPR1…                每格接一顆積木
paramList    加減【欄位組】       PARAM_0、PARAM_1…            每格是文字／下拉欄位
branchList   加減【成對的插槽】   ELIF_COND_i ＋ ELIF_BODY_i    ＋ 一個可有可無的尾巴
```

⚠️ 後兩者**不建整顆積木**（與第一個不同）：`jsonInit` 先建靜態的部分，
它們再把動態的那一段接上去。

> **一個「從零建整顆」的建構子，遇到「只有一部分是動態的」積木時，
> 唯一的出路是把靜態的部分也吞進去——而那正是它會弄丟欄位的原因。**

🟢 而三者的 extraState 鍵**刻意沿用命令式那份**（`itemCount`／`paramCount`／
`elseifCount`＋`hasElse`）——**它們的下一個消費者就是 C++ 那幾顆**，
換一個鍵名等於讓那些退不了場。

## 二、🔴 而「前置的啞輸入」是**為了另一件事**才被做出來的

使用者：「函式呼叫初始參數量應該是零才對」。

`minCount: 0` 一裝上去就露出一個更深的問題：第一版把**標籤掛在第一個值插槽上**，
而零格時**根本沒有那個插槽 → 標籤整個不見**。

> **一個「把標籤掛在第一個資料上」的版面，在資料可以是零個的時候就崩了。**

修法是把標籤搬進自己的啞輸入——**而那正是前一天量出來、記在 vision 上的那個缺口**。

## 三、第二個轉變：一條既有的 experience 被**挑戰**，不是被補充

`experience` 早就有「重構後開瀏覽器實測——測試綠不代表使用者看到的是對的」。
**而我以為自己在遵守它**：我在瀏覽器裡跑 `syncCodeToBlocks`、數積木型別、
用 `getColour()` 逐顆比對顏色。

使用者連續回報**五件事**，全部在 4900 多支測試全綠的情況下：

```
① 工具箱裡找不到 Python 積木     我數的是分類數，不是內容
② 顏色與 C++ 不一致
③ 有些積木沒有 mutation
④ 工具箱只有一顆 if，該有三顆     我數 length：先多一顆、再少一顆
⑤ mutation 的按鈕位置不一樣       🔴 純版面，沒有任何 API 問得出它
```

使用者逐字：「很多問題是你沒有直接在瀏覽器把工具箱截圖，有的話就不會犯這低級錯誤」

> **去瀏覽器而不看畫面，等於把瀏覽器當成另一個測試框架。
> 「開瀏覽器」不是動作，是【用眼睛】。**

🟢 判準已寫進 `experience` 與 [skills/manual-acceptance](../skills/manual-acceptance/SKILL.md)：
**這條規範的主詞是不是「看起來」**——是的話截圖，不要查 API。

## 四、順帶還掉的一筆已知權宜

`python:func_def` 的參數列原本是一個逗號分隔的**字串**，
而 `knowledge` 記著「需要 parse 回結構才能用的字串，就不該是字串」。

🔴 **逼它還債的不是重構，是一個 UI 需求**（「函式定義還沒有 mutation」）：
做得出 `+`／`−` 的前提就是**每個參數是一格**。

> **一個 UI 上的 mutation，逼出的是資料模型上的一個結構。**

## 五、而 lift 的第一版猜錯了 AST 的形狀

以為 `elif_clause` 像 C 那樣**遞迴巢狀**。實測：

```
if_statement [identifier, block, elif_clause, elif_clause, else_clause]   ← 全部是兄弟
```

症狀不是崩潰，是**只拿到第一個 elif、else 永遠拿不到**——而產出來的是一個
「少了兩個分支」的 if，看起來完全正常。

> **一個結構猜錯了，症狀不是崩潰，是【安靜地少做】。**

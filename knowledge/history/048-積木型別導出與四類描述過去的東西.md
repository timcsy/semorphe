# 積木型別從身分導出——而改名腳本誤傷了四類「描述過去的東西」

**日期**：2026-08-11 ｜ **交付**：`specs/116-block-type-derive`，F1 完成
**前一則**：[047](047-模組是搬家的中途站不是終點.md)

## 轉變一：積木型別不再是一個獨立宣告的名字

到這一天為止，一顆元件要取**兩個**名字。186 顆積木裡 **153 顆**的積木型別
不等於身分的導出名——而那不是隨機，是**兩個時間層疊在一起**：

```
身分     停在命名整理（G 項）之後   peek 在封閉詞彙表上
積木型別 停在命名整理之前           top  是被換掉的那個詞
```

> **積木型別是那次改名的化石層。**

改完之後：`blockType = deriveBlockType(componentId, form)`，153 → **0**（硬性零，
第三十六條護欄）。加一顆新元件只需要想一個名字，而**寫錯第二個名字的路被封了**。

## 轉變二：一個被存起來的投影，行為上就是真實

這件事本來不該需要存檔遷移——積木型別是**投影**，而 P8 說投影可以不相容
（「投影可重建」）。

而 `src/ui/app.ts` 載入時：

```ts
// 1. Restore blocks FIRST (before level change triggers resync)
this.blocklyPanel?.setState(state.blocklyState)
```

> **一個被存起來、而且載入時當作還原來源的投影，行為上就是真實。**

所以它適用 [P8 的例外條款](../principles.md)（「語義詞彙本身的變更 MUST 附
一次性的轉換」）。這是 v9 → v10，**這個專案第一次改寫積木狀態**——
既有八個升級步驟每一個都只碰語義樹。

## ⚠️ 轉變三：改名腳本誤傷了四類「描述過去的東西」

第一版腳本把 `(?<![A-Za-z0-9_])OLD(?![A-Za-z0-9_])` 掃遍整個 repo。
四次誤傷，**每一次都是同一個形狀**：

| 誤傷 | 後果 |
|---|---|
| **另一張凍結明表**（身分改名表） | ⚠️ **最危險**。它的鍵是 v2 時代的**身分**（`cpp_stack_top`），字面與積木型別一模一樣而意思完全不同。改掉 = **真實使用者的舊存檔升級不了** |
| `knowledge/` | 湮滅「化石長什麼樣」的證據 |
| 基線與有日期的稽核報表 | 基線要**顯式重產並註明原因**，不是被腳本靜靜改掉 |
| **護欄自己的注入錨點** | 「壞名字」`cpp_stack_top` 被改成對的名字——**壞的輸入變成對的，注入測試靜靜失去意義** |
| **描述舊資產的斷言** | 「這份 v9 存檔含 `c_stack_push`」被改成新名——斷言還在，但**它問錯了問題** |

> **一次改名要問的不只是「哪些地方要改」，還有
> 「哪些地方**因為描述過去**而不能改」。**

判準：**這個字串是在描述現在的世界，還是在描述一個已經過去的世界？**
而它們往往長得跟要改的東西一模一樣——這正是危險的地方。

已寫回 [`component-rename`](../skills/component-rename/SKILL.md) 第六步。

## 轉變四：「拿形狀當判斷」的第二次與第三次

`experience.md` 的七種形狀表裡，最後一列是「拿形狀當判斷」。這一輪它出現三次：

1. `toolbox-builder` 的 `startsWith('u_')` 分「通用 vs 語言專屬」
   ——前綴消失後恆為空，排序偏好**靜靜失效**
2. **三支測試用同一個判斷**——測試與被測物同時犯同一個錯，
   **那時測試不保護任何東西**
3. `skip-declaration-gate` 用**字串手術**組出積木型別
   （`` `u_${componentId.split(':').pop()}` ``）。它壞過一次、被補了一則註解，
   **而註解擋不住第二次**

> **會漂移的不是那一行，是「用手拼出另一個系統的名字」這件事本身。**

三處全部換成**問宣告**：`ConceptMapping` 新增 `layer` 欄位，
`skip-declaration-gate` 改呼叫 `deriveBlockType`。

## 順帶修掉的三件事

**① 匯出的存檔自稱 `version: 1`。** `buildSaveState()` 寫死 1，而
`CURRENT_VERSION` 是 9。自動存檔沒事——`storage.save()` 會強制蓋掉；
**而匯出繞過 `save()`**。

> **一個欄位有兩個寫入點，其中一個是對的，症狀就只在另一條路上出現。**

**② 遷移不冪等。** C2 契約當場抓到：跑第二次時新名不在表上 → 被當成未知 → 丟錯。
而這正是 ① 會踩到的路——一份**已經轉換過**的內容會再被餵進去一次。

> **一個「只跑一次才對」的轉換，遲早會被跑第二次。**

**③ `writeBaseline` 會靜默清掉 `_meta`。** 前一天才在 `toolbox-snapshot` 的
**區域**寫入器上修過同一個病，**而沒有掃同形的地方**——共用的那一份也有。
又一次「一個教訓被記下來、處方也被記下來，而程式碼仍然帶著那個病」。

## ⚠️ 而瀏覽器實測掀出一個不屬於這一輪的缺陷

貼 v9 存檔重載：積木**全部正確還原**，而按執行得到
`RUNTIME_ERR_TYPE_MISMATCH: array`。

**不是改名造成的**——那份存檔錄於任何改名之前，而它的 `tree` 裡已經是
`cpp:var_declare`、`code` 欄位已經是 `int v;`。

> **課程降級的結果被寫進了存檔。**

**根因比「修法沒覆蓋存檔」更準**（2026-08-11 追查）：

`sync-controller.ts` 的 **code→blocks** 方向是對的——第 270 行
`this.currentTree = tree` 存的是**真實**，降級只作用在 `cloneTree` 出來的顯示樹上。

而 **blocks→code** 方向（第 179-180 行）：

```ts
const tree = blocklyState.tree     // ← 從**被降級的積木**抽回來的
this.currentTree = tree            // ← 它成為真實
```

> **降級的視圖被使用者動一下，就變成了真實。**

錄樣本時我為了觸發自動存檔**拖了一下積木**——那一下就把 `int v` 寫回了真實。
使用者不必做任何特別的事：**載入一份降級過的程式，碰任何一顆積木，原始語義就沒了。**

2026-08-09 那次修的是「顯示不要就地改寫真實」，而**沒有問「反方向呢」**
——`enhanceDisplayTree`／`downgradeConceptsForLevel` 的產物會經由使用者的
一次拖曳回到輸入端。**閉環的系統裡，輸出端的損失會從輸入端回來。**


那一項的性質因此變了：原本是「使用者看到一個壞掉的東西」，
現在是「**使用者的資料被改壞了**」——**而那不是設計問題，是缺陷**，同日已修：
降級時記下 `nodeId → 原身分`，blocks→code 抽回來時還原
（`_blockIdToNodeId` 本來就在來回轉換保住原 nodeId）。

⚠️ 還原有一條界線：**使用者真的把它換成別的概念時不得還原**
——那是編輯不是投影損失。少了這一條，還原會吃掉使用者的修改，比原本的缺陷更糟。

留在 draft 的是**設計問題**：降級本身該不該閉環（四個選項各有代價）。
見 [draft/已知工程待解問題](../draft/2026-03-11-已知工程待解問題.md)。

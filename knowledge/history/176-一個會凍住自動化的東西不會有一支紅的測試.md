# 176 · 一個會凍住自動化的東西，不會有一支紅的測試——它會有【沒有測試】

**日期**：2026-08-26

## 起點：路線圖上「執行的誠實」最後一條活的驗收

`vision.md` 逐字：「驗收：這個決定走**匯流排**，`confirm()` 從 `execution-controller`
消失（VSCode 與 Node 宿主答不了一個瀏覽器對話框）」。

而它已經被付掉一半：拿掉 `'skip'` 那天，「要不要跳過」那三處
**連問題一起消失**（[173](173-拿掉錯的那個答案問題也跟著消失.md)）。
剩下三處問的是**另一件事**——「積木改過了，要先同步嗎？」，三段一字不差。

## 🔴 而這個專案已經做過兩次同樣的替換

```
ui/prompt-dialog.ts:4        為 window.prompt 做過（2026-08-24）
ui/toolbar/style-action-bar.ts:3  逐字「Replaces confirm() dialogs」
```

> **一個專案做過兩次同樣的替換而還有殘留，代表那個決定沒有機構在守。**

⚠️ 而 `prompt-dialog.ts:20` 自己寫著它「**會有第二個消費者**」
（「執行的誠實要問使用者①②③，而那件事今天用的是 `confirm()`」）
——**那個消費者已經不存在了**：那個問題被前一刀連根拿掉。
註解描述的是一個**再也不會來的未來**。

## 🔴 而真正的發現是覆蓋率那一格

`grep dialog|confirm e2e/` → **零命中**。三處 `confirm()` 從來沒有被 e2e 碰過。

一開始我把它當成「覆蓋率缺口」。而它不是：

> **一個會凍住 Playwright 的東西，測試寫不下去。
> 它不會被寫成一支紅的測試——它會被寫成【沒有測試】。
> 而沒有測試看起來與沒有問題一模一樣。**

→ 判準：看到某條使用者路徑 **e2e 一支都沒有**時，先問
**「是還沒寫，還是它根本寫不下去」**。後者是設計缺陷，不是覆蓋率缺口。

## ⚠️ 而理由只用【已驗證的那一半】

寫簡報時我本來要拿 P9 宿主獨立性當主要理由
（「`confirm` 在 VSCode webview 裡點了沒反應」）。查證後停住：

```
🟢 已驗證   confirm() 阻塞整個頁面，自動化工具也一起凍住（prompt-dialog.ts 第三點）
🟡 未驗證   confirm() 在 VSCode webview 裡的行為
           —— prompt-dialog.ts 的那個證據是關於 `window.prompt`，【不是 confirm】
```

> **一條護欄如果拿一個沒驗過的前提當理由，
> 那個前提遲早會被人拿去推別的事。**

→ 護欄的檔頭把兩半**分欄寫**，未驗證的那一半明講「**所以這裡不拿它當理由**」。

## 轉移：第七十七條護欄 ＋ 一支終於寫得下去的 e2e

```
靜態  audit-no-native-dialog（硬性零）  擋「長回來」
行為  e2e/native-dialog-gone.spec.ts    擋「換了載體而那個問句其實按不到」
```

⚠️ **兩種缺陷長得完全不一樣，缺一個都不算守住。**
注入驗過：把 `confirm` 放回去，**兩層各自變紅**。

實作選 QuickPick 而不是 `showStyleActionBar`，理由是**控制流一行都不用改**
（包成 Promise 就能 `await`），而 action bar 是非阻塞的、
會逼 `handleRun` 從「等答案」改寫成「回呼裡繼續」。

### 🟡 一個刻意留著的問句

今天 Esc ＝「就跑現在這一份」（與舊的 `confirm` 取消**逐字相同**）。
而從一個選單逃出來，多數人期待的是「什麼都不要發生」。

**這一刀刻意不動它**——換載體的那一刀如果順手改了語義，紅了就無法歸因。
它寫在 `askSyncBeforeRun` 的檔頭上，是一個**看得見的**未決，不是一個被忘記的。

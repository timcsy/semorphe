# 162 · 判一顆積木「缺什麼機制」，而那個判斷重了

**日期**：2026-08-26

## 起點

命令式積木退場只剩最後一顆（`cpp_var_declare`）。我在 `history/160` 那一輪
收尾時把它寫成路線圖項目，判定是：

> 「`variadic` 的每一格同形、`paramList` 的 `optionalGroups` 只做得出**欄位**群
>  ——**兩個建構子都表達不完**。」
>
> 「那是一個**新建構子**的設計，不是這一輪的清償。」

**那個判斷重了。** 隔天再查一次程式碼，差的只有一格參數。

## 兩份定義攤開來看

```
需要的形狀   每格一個 NAME_i；有的格子還要 = ⟨接點⟩，有的不要；齒輪切換
             存檔是 { items: ('var_init'|'var')[] }

paramList    每格有欄位 ✅ 有齒輪開關的「選用群」✅ 存檔 { paramCount, paramOpts }
             ❌ 而那個群只建得出【啞輸入】（`param-list-block.ts:378`）
```

差的是**一格**：`optionalGroups` 能不能是接點。而存檔那一半根本不用設計——
`paramOpts: string[][]`（每格開了哪些群）與 `items`（每格是哪一種）
**攜帶同一份資訊**，轉換是純粹的重新編碼。

## 🔴 為什麼會判重——而它與前一天那三顆是同一個形狀

前一天退三顆陣列／向量積木時，它們的 `_why` 都寫著

> 「改成命令式註冊，因為初始值需要**動態插槽**，而宣告式的 `args0` 只描述固定欄位。」

而那個限制 2026-08-22 就沒有了。那一輪的教訓寫成：

> **一句「因為機制表達不出來」的註解，不會在機制補上的那天自己更新。**

⚠️ **然後我在同一輪的收尾，對最後一顆下了同一個形狀的判斷**——而這次那句話
是我自己新寫的，還附了「兩個建構子都表達不完」當理由。

差別在於**我用的是印象，不是清單**：我記得 `optionalGroups` 是「欄位群」，
而沒有去讀它建的是什麼、也沒有去比對存檔格式。

> **「缺什麼機制」不是一個可以憑印象回答的問題
> ——它要逐個列出既有建構子的能力，而那是一份可以真的打開來讀的清單。**

## 判準

宣稱「這需要一個新機制」之前，**逐條寫出既有機制差在哪一格**，
而每一條要指得出**檔名與行號**。指不出來的那一條，就是還沒查。

⚠️ 而這條判準的成本很低：這次從「需要新建構子」到「差一格參數」
花的是**三個 grep**。

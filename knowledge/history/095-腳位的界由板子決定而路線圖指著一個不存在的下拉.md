# 095 — 腳位的界由板子決定，而路線圖指著一個不存在的下拉

**日期**：2026-08-19 · **spec**：`145-board-pin-model` · **狀態**：完成

## 🔴 路線圖寫的那件事不存在

驗收原文：「**三塊板子的腳位下拉不同**」。實測：

```
pinMode 的 PIN     input_value（Expression）——學生插一顆數字積木進去
腳位下拉            只有一個，而它是 cpp:pin_constant 的常數清單裡那個 A0
```

**沒有腳位下拉。** 而真正跟板子有關的東西在**執行期，寫死成 Uno**：

```
arduino-pins.ts:36    const MAX_PIN = 19
arduino-pins.ts:84    「腳位號碼 25 超出範圍——這塊板子只有 0–19」
```

⚠️ 用 ESP32 的學生跑 `digitalWrite(25, HIGH)` 被告知「這塊板子只有 0–19」
——**而那對他的板子是錯的**。

> **一個錯的錯誤訊息比沒有訊息更糟——而「板子寫死」讓它變成
> 【對某些使用者永遠是錯的】。**

🔴 **這是這一輪第三次**「路線圖的前提對照程式碼後不成立」
（前兩次：`properties.values` 沒有消費者、6.7 的三個缺口只剩一個半）。

## 那格為什麼不放 `provides`

```
provides   ['touch', 'ledc-pwm']       「有沒有」——布林集合
board      { maxPin, constants }       「是多少」——值
```

> **一個宣告如果同時裝「有沒有」與「是多少」，讀它的每一個消費者
> 都要先分辨自己拿到的是哪一種——而那個分辨會在每個消費點各寫一次。**

## ⚠️ 而護欄在同一個位置抓到我第二次

把型別放進 `languages/cpp/…` 之後，`execution-controller`（視圖層）
import 了它 → **第三十九條護欄（四項獨立性）當場紅**。

而那條護欄的病歷裡**已經有一模一樣的一筆**（`ioTraitOf` 原本住在語言套件，
「視圖層為了問一句話而 import 了整個 C++ 語言套件」）。

🟢 處置也相同：型別搬進核心——**它一個 C++ 的字都不認識**，只是三個數值欄位。

> **同一條護欄在同一個位置抓到同一種錯，第二次。
> 那不是護欄太嚴，是那個位置真的很容易走錯。**

## 交付

```
UNO_BOARD    maxPin 19   常數 11 個（含 A0–A5）
NANO_BOARD   同 Uno      而驗收【逐塊斷言】不從 Uno 推論
ESP32_BOARD  maxPin 39   常數 5 個——🔴 沒有 A0
```

⚠️ **ESP32 的 34–39 只能輸入**——**這一刀不做那一層**（需要「方向能力」的模型，
無當前需求）。🔴 所以將來要擋它是**一條新需求，不是這裡的 bug**。

## 明確留下的缺口

`cpp:pin_constant` 這顆積木的下拉仍然靜態含 `A0`
——**它是積木自己的值，而「下拉由目標提供」在規格裡明確排除**。
⚠️ 於是 ESP32 目標下，那顆積木仍選得到 `A0`（而裸識別字 `A0` 已經查不到）。
**那個不一致是已知的，重開條件是「真的要做一個由目標提供選項的下拉」。**

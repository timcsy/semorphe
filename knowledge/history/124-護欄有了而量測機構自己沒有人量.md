# 124　護欄有了，而量測機構自己沒有人量

**日期**：2026-08-21 ｜ **交付**：[`49b8f4dd`](../../.git)、[`a3c61225`](../../.git)
**前一則**：[123](123-一筆判定把半個故事當成全部.md)
**觸發**：使用者問「有沒有已經過時的護欄是可以移除或是整理的？」

## 轉變：找「過時的護欄」，找到的是「沒有人在看的量測」

原本預期會找到一批規則變舊的護欄。**一條都沒有。**
這個專案的護欄寫得夠好，舊規則多半仍然對——它們的病在別的地方：

> **一條護欄過不過時，不看它的結論舊不舊，看它的【輸入】還在不在、
> 它的【偵測器】有沒有被證明過會說話。**

而這兩件事**都沒有任何東西在看**。

## 一、分母沒有人看（第四十八條護欄）

```
記了掃描／語料規模的基線      9 條
有斷言那個數字的              0 條（four-independences 只有下限 `> 20`）
```

裝上語料棘輪（`assertCorpus`）之後**九條當場紅，全部是「變大」**：

```
anchor-rot            護欄檔數 35 → 55      真實身分數 176 → 257   (+46%)
shared-file-husks     共用檔  157 → 217     export    359 → 513   (+43%)
declaration-assembly  測試檔  256 → 346
declared-props        語料段  416 → 456     節點     9324 → 9961
projection-residual   完整段  488 → 515     殘缺段    378 → 487
four-independences    ui 檔    33 → 37      方法呼叫 2409 → 2549
behavior-error        語料總段數 337 → 341
completeness          五路×元件 1280 → 1285
silent-fallback       掃描檔  176 → 244     return    127 → 163
```

沒有一條是壞的。而**沒有一條的基線是準的**。`anchor-rot` 的「真實身分 176」
是 Python 那批元件進來**之前**的世界。

> **一個記在基線裡而不被斷言的數字，是一個看起來有人在看的數字。**

⚠️ 而「變大也要紅」是刻意的，與 `assertRatchet` 同一個理由：只擋縮水的話
基線停在舊值，於是「244 掉回 200」照樣過關。代價是**加一顆元件要上調幾條基線**
——那是設計上的摩擦，不是意外。

🔴 它有一個明確的誤用方式：**看到紅就整批重產**。那會把語料以外的變動一起洗掉。
**而我當場就犯了**——重產之後逐欄比對，四條有語料欄以外的變動（三條是改善、
一條是新測試檔把一顆 `int` 片段刮進語料）。沒有一筆是退步，
**而我只有因為去查了才知道**。

## 二、偵測器沒有被證明過（第四十九條護欄）

```
錨點   問「我有沒有吃到東西」        → 防【空語料】
注入   問「我的偵測器認得出違規嗎」  → 防【壞掉的偵測器】
```

**兩者不能互相代替**——而 🔴 **這件事早就記在
[`experience`](../experience.md) 的「注入釘住的是機制，不是輸入」那一條裡，
連那張兩欄對照表都在**，而我當天照樣走了一遍反向：先補分母，
然後才「發現」偵測器那一維沒人管。

> **一條記下來而沒有被取用的教訓，與沒有記下來的差別，
> 只在事後查證的時候才看得出來。**

所以這一刀的處置不是再寫一條教訓，是**把它變成會紅的東西**。

一條讀了 500 個檔、而正則寫錯的護欄：**錨點會過，違規計數永遠 0，全綠。**

⚠️ `audit-locality` 特別值得記：**膠囊化整個階段的驗收依據，
而它從沒被證明過會說話。**

### 而「有幾條沒有注入」這個數字估錯了兩次

| 量法 | 結果 |
|---|---|
| grep 字串「注入」 | 九條——**其中兩條是案例型，根本不會空過** |
| `it('★ 注入` | 十條——漏認了最常見的寫法 `★ 合成注入` |
| `it('…注入…` | 四條——三條其實有，只是叫「壞的輸入會報」 |

**同一件事在這個專案有三個名字。** 處置是**統一詞彙**（`壞的輸入會報` →
`★ 注入(x)：…`），而不是第三次放寬偵測樣式。

> **一個偵測器如果只認得自己作者的用字，它量的是文風不是事實。**

### 判準本身：「每支護欄都要有注入」是錯的

注入防的是「偵測器空過」，而空過只可能發生在**掃描／數數型**護欄上。
**案例型**（`it('int* ptr = &x → cpp_pointer_declare')`）每一支斷言都是正向的
——lift 回 null 直接紅，**不可能空過**。要它們加注入是儀式。

> **一條規則如果對它涵蓋的一半對象是儀式，那一半就會被敷衍，
> 而敷衍的樣子與遵守長得一樣。**

→ 判準是「掃描型必須有注入」，案例型**具名豁免並附理由**。

### 多出來的一維：注入不得在缺陷消失時提前跳出

```ts
it('★ 注入一處舊格式引用 → **必須被計入**', () => {
  const old = [...allIdentities].filter((id) => !isNamespaced(id))
  if (old.length === 0) return   // ← 遷移完成那天起，這支【無條件通過】
```

> **一支錨在缺陷上的斷言，會在成功那天【變紅】——吵，但看得見。
> 一支在缺陷消失時【return】的注入，會在成功那天變成空的——安靜，看不見。**

第三十五條（`anchor-rot`）看的是前者，看不到後者。

⚠️ 這個判準**收了三次，每次都是誤報**：`\breturn\b` 命中注入素材裡的 C++
`int main(){ … return 0; }` 與 JSDoc 自己的範例 → 跳過註解、要求行首 → 仍命中
合成實作物件裡的 `return true` → **要求恰好四格縮排**。三次都往變窄走，
而變窄的錯誤會**漏報**，所以六支注入把兩個方向都釘住。

## 三、退休兩塊（這是這一則真正的「轉變」）

### 🪦 `identity-namespace` 的「舊格式引用」半條

`legacyRefs` 的第一行是 `if (old.size === 0) return { ts: 0, json: 0 }`，
而遷移（specs 116／158）完成後 `old` 恆為空——**掃描從來沒有執行過**。
兩支斷言恆真、兩列棘輪錨在恆 0 的量上、兩支注入無條件通過，
而報表印「舊格式引用 ts 0 ／ json 0」，**讀起來像量過**。

> **一個結構上不可能非零的數字，被當成量測結果印出來，
> 就是一句每次都在說的假話。**

🟢 **它防的東西沒有變得沒人管**：`isNamespaced` 的「格式違規」硬性零是它的
**前提**，而前提還守著。原處留墓碑註解，回答「為什麼沒有這個檢查」。

### 🪦 `component-locality` 的棘輪 → 硬性零，基線檔刪除

階段 6.5 的 F 步收工後 `notEncapsulated` 恆為 0，而
`tests/baselines/component-locality.json` 的全部內容就是一個 `0`；
護欄本身還手刻了一份 `assertRatchet` 的複製品（連錯誤訊息都一樣）。

> **一份只記著一個 0 的基線，記的不是一個量測值，是一句斷言
> ——而斷言該寫在測試裡，不是存在檔案裡等人去讀。**

⚠️ 副作用：`skills/component-encapsulate/SKILL.md` 引用了那份基線，已改指硬性零。

## 四、順帶：`add-language` skill 的新增（2026-08-20）沒有留下紀錄

它與 `component-pipeline` **是兩條不同的路**——後者假設語言已經在了。
從零加一個語言要處理的是另一批東西：接上解析器、**讓系統知道每條辨識規則
是寫給哪個文法的**（少了這一步，新語言的 `if` 會被當成舊語言的 `if`，
而且不會有任何錯誤訊息，見 [118](118-文法不是語言而歸屬要用宣告的.md)）、
以及四件登記處。

它的存在本身就是一個轉變：**在 Python 之前，「加一個語言」這件事沒有人做過，
所以沒有人知道它與「加一顆元件」是不同的操作。**

# 303 · 一個中位數說服得了「走得通」，說服不了「不會卡住」

> 日期：2026-10-01～02（第 289／290 刀）
> 轉變：「L3 可以當**主要檢查**」**撤回一半**——
> 存活的是「L3 從離線的奢侈品變成負擔得起」，
> 撤回的是「它可以在學生**打字的時候**出現」。
> ⟹ **L3 接到明確的動作上（按執行／按檢查），不接每一次按鍵。**

## 舊的那句話，以及它站在什麼上面

`draft/2026-09-22-元件宣告的契約化.md` 逐字：

```
🔴 cella 量到   型別檢查在瀏覽器裡【接近】互動級
               冷啟動 9,724 ms → 108–180 ms（改走 .cell 快照）
               每次編輯 **中位數約 140 ms**（80·118·119·163·182·189）

⟹ L3 從「貴、離線、給關鍵元件用的奢侈品」變成「可以當【主要檢查】」。
```

**那個結論整個站在一個中位數上。**

## 它被推翻的順序：同一個數字，三次問題，一次比一次根本

```
① 2026-09-25  六個樣本【挑最好的兩個】報成範圍（80–119）   對方自己更正   方向還對
② 2026-09-30  排序要用 140 不是 100                      我們更正       方向還對
🔴 ③ 2026-10-01 它【只有中位數,沒有上界】                 ⟹ 結論本身不成立
🔴 ④ 2026-10-02 那個中位數【本身過期了】—— 實測 1.38 秒,十倍
```

③是我們向對方要上界時發現的；④是對方量上界時**順手量到基線**才冒出來的。
④的成因他逐字說了：

> 140 ms 是 2026-09-30 預載 **3 個**模組時量的；之後預載擴大到 **10 個**，
> **我沒有重量**。

## 🔴 而撤回它的不是 1.38 秒，是上界

對方把預算做成**確定性的步數**之後給出的數字：

```
預設 10M 步    Chrome 上界 8.2 秒
壓到 10⁶ 步    Chrome 上界 1.2 秒    ← 即使壓到最低,上界仍是【秒級】
```

而「主要檢查」的定義是**學生每打一個字都跑**。那條路上一次卡死就等於
這條路不能走。

> **慢是體驗問題，停住是「它壞了」。**
>
> **一個中位數可以說服人「這條路走得通」，
> 而只有一個上界能說服人「它不會卡住」。**

## 兩個不是結論、而會留下來的東西

**① 根因不是紀律，是那個數字住錯了地方。**

```
註解／訊息裡的數字   沒有人回來量 → 一個月後它錯了,而它讀起來很正常
基線裡的數字         每次跑測試都量 → 變了就紅,而且報得出變成多少
```

而我們建議對方做成棘輪時，順手量了自己：**報「最大值／上界／p95」的檔 23 個，
報「中位數／平均」的 5 個**——這個庫自己本來就偏向尾巴。

⟹ 🔴 **缺口不在我們的量測紀律，在【引用別人的讀數】那一步。**

> **外來的讀數不會自動繼承我們對讀數的紀律。**

**② 而棘輪要盯步數，不要盯秒。**

我們踩過「時間當判準」的坑（e2e 同一天兩次假紅，兩次都是**等不到畫面**
而不是斷言不符，單獨重跑就綠）。而一條會假紅的護欄，人很快學會忽略它。

```
秒      機器相關、會假紅、CI 與本機不同   ← 不要當棘輪
步數    確定性、跨機器相同、可重現       ← 🟢 當棘輪
```

對方照這條做了，而那條步數棘輪**當場抓到 38.6 萬步裡的 37 萬是死工作**
——九十多個 feature 裡沒有任何一條測試會因為它而紅。

## 而這個決定不會因為對方變快而改變

即使上界降到 100 ms，大概還是留著那個按鈕，理由是教學的：

> **一個隨時在跑的檢查，會讓學生以為「沒有紅就是對的」。**
> 而 L3 驗的只是它說得出口的那些。

一個要按的按鈕說得出「我現在檢查了什麼」。

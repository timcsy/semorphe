# 142　開機不准喊「系統錯誤」——兩種殘被混成同一句話

**日期**：2026-08-24 ｜ **交付**：`staleReason` 分兩種；另一條寫回路徑補上安全網
**前一則**：[141](141-反白對不上而它是一條靠記得呼叫的契約.md)
**觸發**：使用者附截圖——「我每次重新整理下面都會跳出一條這個，
我覺得**這會讓使用者有誤會，以為剛開啟的時候系統錯誤**」

## 那句紅字說的不是實情

```
積木沒有完整載入，暫停同步到程式碼——請按「程式碼→積木」重載
```

而截圖裡整份積木都在。它只是**還沒被匯流排畫過**。

判定原本是一個布林：

```ts
get isStateStale() { return this.stateLoadFailed || !this.hasRendered }
```

兩種狀態合成一個值，於是**它們只能共用一句話**：

| 狀態 | 要不要擋寫回 | 要不要對使用者說 |
|---|---|---|
| `load-failed` 真的載壞了 | ✅ 要 | ✅ 要 |
| `not-rendered` 還沒畫過 | ✅ 要 | 🔴 **不要**——那是開機的正常過渡 |

> **一個防禦性的檢查要分兩層問：「要不要擋？」與「要不要說？」**
> **把它們寫成同一個布林，就會在正常路徑上誤報。**

而誤報的代價不是吵：**它把紅色變成背景噪音**，真的壞掉那天沒有人會看。

🟢 修法是把布林換成理由（`staleReason: 'load-failed' | 'not-rendered' | null`），
`isStateStale` 仍然兩種都為真——**分開的是說什麼，不是擋不擋**。

## 順手發現的第二半：安全網只蓋住一條路

`resyncAfterTopicChange()` 同樣「從積木產生程式碼並寫回去」，
而它**一次都沒問過工作區殘不殘**。`setState` 失敗之後走到這一條，
半份積木照樣蓋掉程式碼。

> **一張只蓋住一條路的安全網，與沒有安全網的差別，只在缺陷走的是哪一條路。**

⚠️ 而它只擋 `load-failed`：`not-rendered` 在還原路徑上是正常的
——那一條正是還原時負責把程式碼生出來的人。

## 留下什麼

- `tests/integration/startup-no-false-alarm.test.ts`（4 支靜態檢查，含錨點）
  ——反向驗過：把 `load-failed` 的判斷拿掉，它當場紅。
- 🟢 **瀏覽器實測過**（2026-08-24，擴充重連之後）：存了一份積木、重新整理，
  **畫面上沒有紅字**，積木與程式碼都完整還原。
  ⚠️ 靜態檢查守得住「有沒有分開」，守不住「分得對不對」——所以這一步要人去看，
  而它現在看過了。

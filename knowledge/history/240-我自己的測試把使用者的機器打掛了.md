# 240 · 我自己的測試把使用者的機器打掛了

**日期**：2026-09-16
**觸發**：使用者：「剛剛 memory leak，甚至到 1.96TB，你應該要檢查一下」

## 🪦 而我第一個結論是錯的

我量了當下的狀態：沒有殘留行程、記憶體可用 43%、`/tmp` 清乾淨了，於是回答
「1.96 TB 是**虛擬**記憶體，Apple Silicon 上每個行程都保留 1–2 TB，不是真的用掉」
——並附上證據（閒置的 `node` 虛擬 0.38 TB、VS Code 1.79 TB）。

那段證據本身是對的，**而結論是錯的**，因為我量的是**重開機之後**的機器：

```
uptime                18 分鐘
15 分鐘平均負載        53.22      ← 這個數字才是那一刻的現場
kern.boottime         14:57:34
```

> **我量不到而使用者看得到的時候，先問「我的路徑跟他的差在哪」
> ——而「他的那台機器已經重開過了」也是一種差別。**

⚠️ 使用者補的那一句（「當時是跳出一個視窗警告我」）才是關鍵：
macOS 那個視窗**只在 swap 用盡時才跳**，它報的是真的。

## 真正的證據：活得過重開機的那些

```
14:31–14:33   26 支 clang（第一次跑那支探針）
14:48–14:53   30 支 clang
14:51:16      kernel: memorystatus: killing_idle_process …
              接下來 2,880 次 kill，一路到 15:00
14:57:34      重開機
15:04–15:07   57 支 clang   ← 重開之後【我又跑了一次】
```

而 kernel 自己說出了機制：

> `clang[…] triggered unnest of range … of DYLD shared region` ——
> **this increases system memory footprint until the target exits**

每一支 clang 都把原本**共用**的動態庫區段解巢，於是那份記憶體不再共享。
⚠️ **所以「單支峰值 94 MB × N」低估了成本**——那份不再共享的區段
在 `ps` 的 RSS 上看不見。

## 🔴 而讓它變重的，正是我以為在修的那一步

第一次量到 **212/218 編不過**，而那是量測工具的問題：206 支用
`bits/stdc++.h`（GCC 專屬，Apple clang 沒有）。補了墊片之後數字變成 204 編得過
——**而成本翻了**：在那之前那 206 支在第一行就失敗（幾乎免費），
之後它們真的去編整個標準函式庫。

> **一個把「大部分都失敗」修成「大部分都成功」的修法，
> 會生出一份不在報告裡的帳單——失敗是便宜的，成功不是。**

## 做了什麼

```
並行度   8 → 3（`COMPILE_CONCURRENCY`，理由寫在那個常數的上面）
判準     會叫編譯器的探針，並行度要留餘裕給機器上其他東西
         ——它跑在 vitest 裡，而 vitest 自己還開著十幾支 worker
```

🟢 查證過 `npm test` 裡三支會叫編譯器的（`header-follows-style`、
`c-style-parity`、`two-projections-behave`）用的是 `-fsyntax-only`、
也沒有 `bits/stdc++.h`——**它們不是風險，我新加的那支才是**。

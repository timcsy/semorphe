# 059　棘輪假設「同樣的輸入給同樣的數字」——而參照編譯器在兩台機器上是兩個實體

> 日期：2026-08-14
> 觸發：CI 的 `audit-behavior-error` 報「判定過期了」，**而本機全綠**。
> 本檔記的是那個假設被指名的過程，不是修了什麼（那在 `d4389e0`）。

## 轉變

```
old  棘輪的基線是一個【數字】——只准下降
new  那個數字必須是【環境無關】的，否則基線在兩台機器上無解
```

## 症狀：本機綠、CI 紅，而兩邊都正確地執行了同一條規則

唯一那筆判定掛在一段 **UB**（讀未初始化變數）上：

```
macOS / clang   int x; cout << x  →  38518960（堆疊垃圾）→ 不一致 → 判定命中
CI     / gcc    同一段            →  0                    → 一致  → 判定成【孤兒】
```

⚠️ **而修掉孤兒之後 CI 仍會紅，只是換一個原因**：

```
基線記 1  →  CI 實測 0  →  「棘輪有改善，請下調基線」
基線記 0  →  本機實測 1 →  「棘輪退步」
```

> **兩邊都無解——因為分子裡混了一個沒有唯一答案的樣本。**

## 🔴 而這個假設此前從來沒有被說出來

`build-guardrail` 6.8 問了兩個問題來決定用棘輪還是硬性零：

> 「留一筆在那裡，這條規範還成立嗎？」（規範值不值得存在）
> 「修一筆要付多少？」（硬性零還是棘輪）

**兩個都對，而它們都假設了「量得出一個穩定的數字」。**
那個假設在單機開發時永遠成立，所以它一直是隱形的
——**直到有一條護欄的量測工具是外部的**（參照編譯器）。

→ 6.8 加第三個問題：**「這個量在別台機器上一樣嗎？」**

## 處置：移出分子，而且另立一欄

與 `undecidable`（讀 `cin`／`rand`）同一條——它不該在分子裡。

⚠️ 而它**另立一欄**（`environmentDependent`）而不是靜靜消失。
`build-guardrail` 第 11 步的理由在這裡照樣成立：
**縮分母比修分子容易，所以縮掉的東西要看得見。**

## ⚠️ 語料的來源：兩條護欄對同一段程式的期待相反

那段 UB 不是隨便撿來的，它是
`tests/integration/roundtrip-variables-ops.test.ts` 的
**`executes uninitialized int as 0`**——一支**刻意在測「我們自己定義的行為」**
的測試（未初始化的 `int` 在這個直譯器裡是 0）。

而 `audit-behavior-error` 從測試檔的樣板字面撈語料，於是把它拿去
**與參照編譯器對答案**——而參照那一側對 UB 沒有定義行為。

> **一條護欄從別人的測試裡撈語料時，撈到的可能是「另一條規範的斷言」，
> 而那條規範說的正好是它要去挑戰的東西。**

## 🔴 而我的第一個診斷是錯的，錯得很有說服力

我先判定是「護欄從自己所在的目錄撈語料，把**自己的注入樣本**吃了進去」，
並照著改了 `fetchCorpus`、寫了一段很篤定的註解。

**而那個注入樣本用的是單引號**，`fetchCorpus` 的 regex 只抓反引號
——那條因果從一開始就不成立。改動已回退。

⚠️ 那個錯誤診斷的危險之處**不是它錯**，是它**解釋得通而且有教育意義**：
「護欄吃自己的注入樣本」聽起來就像這個專案會犯的錯，
與檔案裡既有的十幾條教訓同一個口吻。**差一點就被寫進知識庫。**

→ 併入 `experience`「宣稱『與我無關』之前先去量」那一條
（同族：一個聽起來很合理的判斷，而驗證它很便宜）。

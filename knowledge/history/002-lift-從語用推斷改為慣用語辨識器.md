# 002：從「lift() 做語用推斷」到「lift() 是慣用語辨識器」

> 日期：2026-03-08

## 轉移

- **舊**：`lift()` 被定位為「語用分析」——把語法結構推斷為使用者意圖。語用學三層（語法/語義/語用）中，語用層被整個放在 lift() 身上。
- **新**：`lift()` 是**語法慣用語（syntactic idiom）的結構化辨識器**——用 pattern matching 和上下文查表辨識已知的慣用寫法。真正需要意圖推斷（「為什麼在這裡寫這個」）的語用分析劃歸 LLM 層。

## 為什麼變

原本的定位把兩件性質完全不同的事混在一起：

```
辨識「這是 count_loop」        ← 確定性、可驗證、有明確判定法
推斷「作者為什麼要寫這個迴圈」  ← 機率性、不可驗證、無唯一答案
```

混在一起的後果是**無法回答「lift() 什麼時候算對」**——如果它負責意圖推斷，那就沒有客觀的正確性標準，roundtrip test 也失去意義。

拆開之後，四件原本說不清楚的設計決策同時有了答案：

1. **為什麼 lift() 需要符號表和作用域棧** — 慣用語辨識需要上下文（區分 `cout` 是 stream 物件還是自定義變數）
2. **為什麼 Pattern Engine 有多層** — Layer 1 處理純語法映射，Layer 2+ 處理需要上下文查表的慣用語
3. **為什麼降級存在** — 辨識基於已知 pattern 庫，未收錄的寫法無法辨識
4. **為什麼高 Scope 比低 Scope 難** — Scope 0-2 的慣用語相對局部，Scope 3+ 需要跨檔案語境，超出 pattern matching 能力

這條界線後來成為 [三維錨定](../concepts/三維錨定.md) 的基礎：確定性系統可自動寫入語義結構，機率性系統只能建議。

## 狀態

✅ 已採用。lift() 的結果直接寫入語義結構；Scope 3+ 的推斷標記 `llm_suggested`，需使用者確認。`metadata.confidence` 標記辨識的確定程度。

# 130　「這顆積木建得起來」與「這一段程式的積木擺得上去」是兩個問題

**日期**：2026-08-22 ｜ **交付**：語料 73 → 95 段五軸全零、第五十一條護欄的第二個維度
**前一則**：[129](129-一個插槽比一個最多兩層的欄位多表達了無限層.md)

## 轉變：護欄自己長出了第二個維度，而那是**看**出來的

[128](128-渲得出積木而渲的是一份JSON.md) 蓋的第五十一條問：**這顆積木建得起來嗎**。
它把 `for` 迴圈那一族的洞補起來了，而三天不到它自己被同一種方式抓到不足：

開瀏覽器貼一段有 `super().speak()` 的程式——**主控台印出正確的答案，
而積木畫布一片空白**。

```
MissingConnection: The block "python_method_call" is missing a(n) OBJ connection
```

`python_method_call` **建得起來**（`init` 跑得完，第五十一條說它沒問題）。
壞的是它的 `args0` 宣告的 `OBJ` 與 `METHOD` **兩格都不存在**
——可變參數的建構子從零建整顆（標籤 ＋ 一個前置**欄位** ＋ 插槽），
而它表達不了「**插槽在前**」的形狀。

> **「這顆積木建得起來」與「這一段程式的積木擺得上去」是兩個問題：
> 前者只要 `init` 跑得完，後者要【每一個被指名的插槽真的存在】。**

⚠️ 而 `METHOD` 被丟掉時**連錯都不報**：`getFieldValue` 靜靜回 `null`。
出聲的只有 `OBJ`，因為只有它是一個**連接**。

## 🔴 而那個建構子的檔頭早就寫過這條——對「未來」說的

`variadic-block.ts` 2026-08-21 的檔頭逐字：

> **一個「從零建整顆」的建構子，遇到「只有一部分是動態的」積木時，
> 唯一的出路是把靜態的部分也吞進去——而那正是它會弄丟欄位的原因。**

那時它是一段解釋（「為什麼參數列那一種要另寫一個模組」）。
一天之後它變成一個缺陷的診斷書。

> **一句寫得夠準的註解，會在它預言的那件事發生時自己指出根因
> ——而它不會自己去修。**

## 這一段的其餘（都在同一個迴圈上）

參照直譯器這四輪再抓到十三筆靜默錯答案，其中兩筆掀出**第三份真相**：

| | 幾份 | 症狀 |
|---|---|---|
| 格式規格 | **三份** | f-string 只認 `.Nf`、`.format` 只認 `{}`、`%` 只認沒有寬度精度的 |
| 比較 | **兩份** | 排序那一份只認數字與字串 → 序對的鍵讓排序**退化成原本的順序** |

第二個特別值得記：它看起來像「`key=` 沒生效」，而其實是比較器不認得那種鍵。

而 `all(x > 0 for x in xs)` 產出 `all(x > 0, for x in xs)`
——tree-sitter 把產生器運算式當成 `arguments` **本身**（沒有 `argument_list` 包著），
而那一筆樣式用 `liftChildren` 攤開那個欄位的子節點。

> **一個「攤開這個欄位的子節點」的宣告，假設了那個欄位一定是一個清單。**

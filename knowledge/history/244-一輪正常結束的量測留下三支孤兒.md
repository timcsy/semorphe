# 244 · 一輪「正常結束」的量測，留下三支孤兒

**日期**：2026-09-17
**觸發**：連續三次「全套測試被系統以記憶體不足砍掉」，而我每一次都歸因成
**測試自己太重**——還因此把 `maxWorkers` 從預設調到 3、再調到 2。

## 真正的原因不在這一輪，在上一輪

第四次被砍之後去數行程：

```
PID    MEM   CPU    COMMAND
70003  2.8%  90.5%  /tmp/semorphe-refcc/a64591_260
72866  1.8%  89.1%  /tmp/semorphe-refcc/a64591_385
69928  0.0%  88.7%  /tmp/semorphe-refcc/a64591_257
```

三支學生的程式還在跑，各燒 90% CPU、記憶體持續長大。
而它們來自一輪**已經正常結束（exit 0）**的語料探針。

> **一個被殺掉的父行程，不會帶走它的孩子——
> 而一支沒有人再看著的孤兒，它的帳會記在下一個人頭上。**

⚠️ **這個缺陷不會讓任何一支測試變紅**。它只讓**下一次**量測變得不可靠，
而下一次的人（我）會去找一個不存在的原因。

## 根因是一個被【靜默忽略】的選項

```ts
exec('bin < file', { timeout })       // 跑的是 /bin/sh -c "bin < file"
```

Node 的 `timeout` 殺得到的是**那個 shell**，而真正在跑的程式是它的**孫子**。

而我第一版的修法是加 `detached: true` 再 `kill(-pid)`——**它回 ESRCH**。
量出來才知道為什麼：

```
PID    PPID   PGID   COMMAND
96515  96514  96510  /bin/sh -c sleep 30 & wait    ← PGID 不是自己的 PID
96516  96515  96510  sleep 30                      ← 殺了 shell，這支活下來
```

**`detached` 不在 `exec` 的選項表裡**（它是 `spawn` 的），所以它被靜默忽略，
那個 shell 從來沒有當上群組長。

> **一個不存在的選項不會報錯，它只會讓你以為那件事生效了。**

🔴 而這條**這個 repo 自己寫過**：`component-generate` 的 skill 裡逐字寫著
「`textIn` 不是合法的鍵，於是那個限制完全沒有生效而測試照樣綠」。
**同一條教訓，在另一個 API 上又收了一次學費。**

🟢 修法：改用 `spawn('/bin/sh', ['-c', cmd], { detached: true })`，逾時殺 `-pid`。
＋ 單支那條路從 `execSync`（走 shell）換成 `execFileSync`（直接跑那支執行檔）。

## 護欄：`tests/integration/run-cpp-no-orphans.test.ts`

兩支，而**正向錨點不可少**：

```
★ 跑得完的那一支真的跑完了     ← 沒有它，「零孤兒」可能只是【什麼都沒跑】
🔴 跑不完的那一支逾時後不得還活著
```

修好前後的讀數差很多：那支測試從 **120 秒掛住**（`exec` 的 callback 等不到
stdout 關閉，因為孤兒還握著管線）變成 **6.9 秒**。

## ⚠️ 而 `maxWorkers: 2` 要不要退回去

**不退。** 它是一個獨立成立的量測（8 與 3 都被砍過，而那幾次至少有一次
沒有孤兒在場）。但這一則要記著：**那三次被砍裡，有幾次是孤兒造成的分不出來**
——因為當時沒有人在數行程。

> **同一個症狀有兩個原因時，先修好的那一個會讓另一個看起來已經解決。**

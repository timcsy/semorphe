# 017：「補上缺的檢查」從單純的好事，到「必須連同安全網一起做」

> 日期：2026-08-06

## 轉移

- **舊**：路線圖上的「補存檔版本閘門」是一行阻斷前置，性質被當成**單純的補漏**——目前不檢查版本，加上檢查就好。同一份路線圖上還有一整排同型的項目（消歧義、殺雙重真相、kernel 約束脊椎），全部被當成同一種「補上缺的檢查」。
- **新**：**加嚴一個檢查，可能讓事情比不檢查更糟。** 一道檢查一旦會「拒絕」，就必須同時回答「被拒絕的東西去哪了」。答不出來的話，這道檢查會把「不知道有問題」變成「資料被刪掉」。

## 為什麼變

實作 `specs/052-storage-integrity-gate` 時，設計走到一半發現一條四步鏈：

```
1. load() 因版本不符回傳 null
2. 呼叫端的 if (!state) return —— 分不出「沒有存檔」與「存檔被拒絕」
3. 使用者以為是新的一頁，開始操作 → 觸發自動存檔
4. save() 呼叫 load()，又拿到 null，所有欄位落到預設值 → 寫回去
```

**「拒絕載入」在四步之內變成「永久刪除」。**

當時那條鏈是**推理**——每一環都查證了程式碼，但沒有實際跑過。所以實作的第一個任務就是把它跑出來：

```
原始存檔：{"version":1,"code":"使用者的作品","lastMod
一次自動存檔之後：{"version":1,"tree":null,"blocklyState":{},"code":"int main(…
```

原內容無法復原，而且**沒有留在任何地方**。

在此之前，那份存檔至少還躺在使用者的瀏覽器裡，只是載進來會出錯。加了檢查之後，它會被無聲地清掉。

## 這一條的可推廣性

階段 6.5 剩下的項目**幾乎全是同一型**：

| 項目 | 加嚴之後拒絕誰 | 被拒絕的東西去哪了 |
|---|---|---|
| P2–P3 消歧義 | 搶匹配的辨識規則 | 那段語法變成 `raw_code`？還是整個檔案打不開？ |
| P4 殺雙重真相 | 與註冊表不一致的積木定義 | 使用者存檔裡的那顆積木？ |
| P5 核心型別改名 | 舊格式的存檔 | 已由本次的備份機制接住 |
| P7 kernel 約束脊椎 | 違反約束的語義樹 | 使用者正在編輯的程式？ |

**每一項都要先回答第三欄，才動手做第二欄。**

## 順帶推翻的一個事實記載

路線圖記的是「`version` 只檢查存在不檢查值」。實測發現那描述的是**匯入檔案**那條路徑；**自動載入那條（每次開頁面都跑）連存在都不檢查**，`{hello:'world'}` 會被原樣當成存檔回傳。

而且旁邊還躺著一個**現在就在傷害使用者**的 bug：`blockStyleId` 與 `locale` 每次存檔都被無聲丟掉——積木外觀與介面語言從來沒有被保存過。

> **去量那一列的時候，才發現它旁邊還有三個。** 這是「量測工具的第一版會安靜地量錯」的鄰居：**不是量錯，是根本沒去量**，而記錄下來的那句話讓人以為量過了。

## 狀態

✅ 已採用。`specs/052-storage-integrity-gate` 的 US3 就是這條的落實：拒絕之前先把原始內容搬到備份鍵，`refused` 分支在型別上必帶 `backedUpTo`——「拒絕了但沒備份」編不出來。

# 兩個機制回答同一個問題的時候，答案不一致是遲早的

2026-09-20｜第 205 刀（層級樹退場）

## 一句話

> **兩個機制回答同一個問題的時候，答案不一致是遲早的；
> 而先出聲的那一個，通常不是對的那一個。**

## 事情

使用者：「**我們現在已經有課程了，應該就沒有需要再用 levelTree 了吧**」
「**我是覺得自由模式就是全部揭露，要漸進揭露就去課程**」

工具箱的內容在那之前是：

```
levelTree ∩ 已啟用分支 ∩ 當前那一課
```

而**中間那一項與第三項是同一件事做兩次**。

🔴 **而做兩次的那一次會靜默吃掉另一次說要的東西**（掃全庫 69 課量到的）：

```
arduino/13-溫濕度  宣告了 cpp:container_iter
                   而 arduino 的 levelTree 沒有它
                   → 學生在那一課拿不到課文要他用的積木，而沒有人出聲
```

📌 而前一刀（204）在瀏覽器抓到的 `cpp:string_at`／`cpp:queue_back`
是**同一個病的另一面**（自由模式那一側）。

## 🔴 而「完全拿掉」撞到一個硬阻斷，先量出來才知道

```
c-beginner 的 levelTree   93 顆
該語言（cpp）的全部       250 顆
```

C 沒有 `vector`／`class`／`cout`。而**擋住它們的就是 levelTree 本身**
——`Target.provides`（原設計四格之一）逐字「**本輪沒做**」
（`languages/cpp/target-dialect.ts` 的檔頭），`filterByTarget` 的第一行是
「沒宣告 provides 就什麼都不濾」。

> **一個看起來多餘的機制，可能正扛著另一個沒做完的機制的責任
> ——而它扛著的那一半不會寫在它自己的名字裡。**

🟢 所以拿掉的是**層**，不是**清單**：

```
拿掉   children · level · enabledBranches · 「選擇範圍」的狀態 · 存檔那一格
留下   Topic.components——一張平的「這個世界有哪些積木」
```

C 與 Arduino 是不同的世界，而「世界有什麼」不是分層，是清單。

## 證據：那一層本來就已經空轉

`ui/app.ts` 裡**每一個**設定它的地方都是「全開」，而註解自己寫著：

```
「收窄由【課】來做，不由層級做」
「留一半層級一半課的話，同一件事有兩個開關，而它們會不同意」
「使用者 2026-08-12 的原話已經否證過那個設計：
  『我會乾脆叫學生把全部都打勾，那有沒有這個漸進揭露是沒用的』」
```

而那顆**控制項**早在 2026-08-28 就退場了（`core/host/controls.ts` 的墓碑）
——**留下來的是它的狀態**。

> **一顆控制項退場之後，它的狀態會繼續活著，而且繼續參與計算。**

## 改測試的判準：問它本來想保護什麼

七個檔的測試綁在「集合怎麼算出來」上，而它們受測的東西不是那個：

```
toolbox-builder     測「集合越大，積木越多」   → 換兩個顯式的子集，判準一格沒變
level-switching     測 isBlockVisible(積木,集合) → 換顯式集合，每一支自己說得出假設
c-topic-derivation  測「C 那棵樹的節點是子集」  → 換成「C 的元件是子集」，而且【更強】
toolbox-snapshot    測「第一眼看到的東西」      → 冷開沒選課，那就是主題的全部
```

> **一支測「f(x) 對不對」的測試，綁在「x 怎麼產生」上的那一天，
> 它會隨著 x 的產生方式一起死掉——而 f 還活著。**

⚠️ 而 `c-topic-derivation` 那一支換完之後**比舊的強**：舊的比「樹長什麼樣」，
新的比「裡面有什麼」，而後者才是學生看得到的東西。

## 量到的

```
刪掉    core/lesson/level-tree.ts（六支匯出）· ui/toolbar/level-tree-selector.ts
        enabledBranches（app 狀態 · 存檔 v24 · VSCode 設定）
新增    core/lesson/topic-components.ts（兩支匯出）
基線    七條護欄的輸入量【下調】（檔數 · import 行數 · 方法呼叫數 · export 數 · 存檔欄位數）
        判定格一格未動
```

🟢 **決定性的驗證**：`e2e/c-target.spec.ts` 的「選 C 目標 → 工具箱裡拿不到
C 沒有的東西」**不再需要手動展開層級就成立**——C 的世界沒有被打開。

## 判準

- 兩個機制回答同一個問題時，**先量哪一個真的在答**（這一次其中一個從來沒答過）
- 拿掉一個看起來多餘的機制之前，問「**它有沒有順便扛著別的東西**」
- 改測試時問「**它本來想保護什麼**」，不是「它現在怎麼寫」

## 為什麼是「旁邊帶一串鍵」

換成別的容器（`vector<pair<K, V>>`）會讓讀寫全部改成線性搜尋的小函式——一支只是要照順序印出來的程式，換出來的 C++ 認不出原本的樣子。
旁邊帶一串鍵是學生自己會寫的那一種：`map` 照舊、讀寫照舊，只多「新的鍵記下來」一行。

收得很窄，因為那一串鍵只在三個地方被維護（指定整個字典、`d[k] = v`、走訪）：

- `pop`、`del`、傳給函式、在函式裡、`global` ⟹ 那一串跟不上 ⟹ 照舊保留
- `d[k] = v` 的鍵要是名字或字面量——要先問 `count` 再寫，鍵會算兩次
- 走訪時本體改了那個字典 ⟹ 保留（Python 長度變了會丟 RuntimeError；`changesDict` 保守地把任何寫入都算進去）

## 兩個被判決攔下來的寫法

- `string c(1, ch)`：Cella 判 accept 但帶 `string.max_size` 的假設（填充建構子的長度可能超過上限），Python 那邊沒有 ⟹ 改成 `string c = ""; c += ch;`（沒有假設）。我們的 C++ lift 也收不進 `string c(1, ch);`（降成原文）。
- 集合字面量 `{"a", "b", "a"}` → `set<string>`：輸出相同，而 **Cella 判 Python 那邊帶 `str.hash` 的假設**（只問 `len` 也帶）——C++ 沒有那個假設，兩邊判決不同 ⟹ 集合照舊保留（`09/rebuild` 因此還在保留清單）。只問大小不該依賴雜湊——11-13 問了 Cella，回覆同意過寬（集合的大小只看相等，假設應在觀察到順序時才記），排進切換後的 Python 一輪；修好之後把集合也換過去。

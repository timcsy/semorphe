# 241 · 第五個面向：形狀完美，而它印出來的是別的東西

**日期**：2026-09-16
**觸發**：使用者：「你有幫我驗證語料庫的執行結果與模擬的是一致的嗎？」——**沒有**。

## 那四個面向，沒有一個是行為

CLAUDE.md 的表寫著一個宣告有四個面向：①產出的程式碼 ②語義的不動點
③載得進工作區 ④走一趟積木回來。而四支 `studycpp-*` 探針裡
`interpret`／`execute` 的出現次數是 **0**——**四個都是形狀**。

> **殘差量的是「我沒認出來」，而它對「我認錯了」保持沉默。
> 而形狀層的「認錯」與行為層的「認錯」，也不是同一件事。**

## 測資怎麼來：使用者拍板「依照題目生」

那 218 支是 AP325／TIOJ／zeroJudge 的題目，大多要讀 stdin，而語料沒有測資。
做法是**問程式自己**：語義樹裡有每一次讀取的型別與順序，照那個生。

🔴 而判準不是「這份輸入對那一題有意義」，是**兩邊餵同一份**——
輸入合不合題意，不影響「g++ 印 A 而我們印 B」這個判定。
型別要對（拿 `abc` 餵 `cin >> n` 會讓後面全部失效），數量要夠。

所以「不一致」不是餓死造成的。

## 兩族，而它們都只錯在 `execute` 那一路

    cout << '\n'   印出一個【反斜線】
    int a{7}       變成 1；int a{} 變成 1；long long ans{} 什麼都不印

`literal_char` 的 `properties.char` 存的是**原始碼引號中間那段文字**
（`'\n'` 是兩個字元），而 execute 直接 `charCodeAt(0)`。
字串那一路早就在用 `unescapeC`，**字元那一路漏了**。

`int a{7}` 的初始值是一顆 `cpp:initializer_list`，求值出來是一個陣列，
然後被 `coerceType(…, 'int')` 壓成 1。純量的大括號初始化沒有被拆開。

🔴 **兩個的 lift 與 generate 都是對的**——樹逐字正確，產生器照樣吐回
`'\n'` 與 `int a{7};`。所以第一百一十五／一百一十七／一百一十八條**全綠**。

> **一個只錯在 execute 那一路的缺陷，形狀是完美的
> ——而形狀完美正是它活下來的原因。**

修完：**內容真的不同 37 → 14**，一致 50 → 76（兩邊都跑完 93 支）。

## 第二輪：清那 90 支「解譯器出錯」

**先分族，不要一支一支追**——90 支的清單看不出下一刀該切哪裡。

    19 支  #define 巨集（#define x first、#define pii pair<int,int>）
     9 支  步數預算用完
     8 支  sort(h, h+N) 的【變數】偏移
     6 支  cin.tie / cin.ignore ——「cin」不在作用域裡
    12 支  索引越界
     4 支  vector<int> d2[107] ——vector 的陣列
     2 支  數字分隔符 10'0000'0007

打掉三族（一族一處）：

```
數字分隔符   literal_number/execute 先剝掉 `'`——它是寫法不是值
變數偏移     range.ts 的偏移只收 (\d+)，放寬成「數字／變數／它們的加減」
串流設定     method_call 加一份【窄的】白名單：tie/ignore/sync_with_stdio…
             🔴 會【讀走東西】的（get/peek/getline/read）不在裡面，要繼續報錯
```

> **一個「忽略掉不認識的東西」的放行，與一個「這幾個我知道可以忽略」的白名單，
> 差別在前者會把「它其實讀走了一個字」也一起忽略掉。**

    解譯器出錯 90 → 68 ／ 兩邊都跑完 93 → 106 ／ 一致 76 → 87

🪦 而「步數預算用完」**獨立成一格，不算缺陷**：那 9 支是 N 皇后回溯那一類，
g++ 幾毫秒跑完，而樹走式解譯器慢 10–100 倍。把預算開到 40M 之後剩 4 支。

> **一個「跑不完」的觀察，要先分開【它錯了】與【我給的時間不夠】。**

🪦 也在這一輪刪掉一支重複的測試——它是前一輪留下的，而且寫著**並行度 8**
（[history/240] 那個把機器打掛的數字）。

## 第三輪：pair、聚合、別名——而最重的一個是**靜默的資料遺失**

追「19 支 `#define x first`」的時候，最小重現**六個全紅，而且與 `#define` 無關**：

    pair<int,int> A[10];   A[0].first = 3;   → 「（不是一個結構）」

根因在核心：`defaultValue('pair<int,int>')` 把「帶尖括號」一律當成容器，
回一個**空陣列**。而 lift 是對的。

> **「帶尖括號」說的是它是一個樣板，不是它是一個容器。**

再往下挖，`pair<int,int> pr = {3,4}` 的初始值**整個從語義樹上消失**：
組裝路徑只認 `values`／`source`／`size` 三種槽，而 `pair_declare` 宣告的是
`source`、大括號進的是 `values`——兩條都不成立就掉到最後的 `createNode(props)`。

    解譯器   pr.first 讀到 0（而 make_pair(3,4) 是好的）
    學生     一動積木，`= {3,4}` 就從他的程式碼裡不見了   ← 更嚴重的是這一層

> **一條「我認得的槽有三種」的組裝路徑，第四種不會報錯
> ——它會安靜地少一塊，而少掉的那一塊是使用者打的字。**

這一輪修的（每一個都附最小重現進了常駐回歸網）：

```
defaultValue      有聚合形狀的樣板型別 → 那個形狀的物件（判準是「有沒有登記」，不是型別名）
組裝路徑          大括號進 values 而元件的槽叫 source → 包成一顆聚合串列放進去
                  ⚠️ 而它【不得寫死 `cpp:initializer_list`】——共用檔可以【問】哪一顆是，
                     不可以【說】哪一顆是（膠囊就近性那條護欄當場抓到我）
pair_declare      來源走 evalInitializer，不要「認不得就給一個空 Map」
var_declare       非結構路徑也走 evalInitializer——兩份實作，壞的永遠是沒人走的那一份
array_declare     陣列記住自己的 elemType
array_assign      `A[0] = {3,1}` 照 elemType 填
struct_at_member  讀【與寫】都認別名——只認讀的話症狀是「改了沒反應」
aliases.ts        名字的別名表：查不到才問一次，而【樹一個字都不動】
max/min           `max({a,b,c})` 的串列形式
```

> **一個為了讓執行器看懂而做的替換，如果它會回頭改寫使用者的程式碼，
> 那它換掉的不只是一個名字。**（所以別名是「查不到才問」，不是預處理。）

    解譯器出錯 68 → 60 ／ 兩邊都跑完 106 → 114 ／ 一致 93 → 100

## 第四輪：假名字、型別別名、以及被壓成文字的接收者

🪦 **最大的那一族，19 支的錯誤訊息全是假的。** 它們都報
`UNDECLARED_VAR: x`，而那些程式裡**沒有一支有叫 `x` 的變數**——
那是 `input/execute.ts` 的一行回退：

    ctx.scope.set(String(varRefNode.properties.name ?? 'x'), got.value)

位置解不出來、節點又沒有名字時，它去寫一個叫 `x` 的假變數。於是
`#define x first` 與 `pii A[…]` 兩個**完全不同的根因**，被同一個假名字蓋住。

> **一個回退用的預設值，會變成錯誤訊息的內容
> ——而那句話會把每一個不同的根因說成同一件事。**

拿掉它（解不開就照實說「讀進來的東西不知道要放哪裡」）之後，那 19 支立刻
分成兩族，而兩族都修得掉：

```
型別別名     defaultValue 認 `#define pii pair<int,int>`——型別也可能是一個小名
元素型別     `vector<pair<int,int>> vt(n)` 的每一格以前寫死 int 0
接收者       `d2[3].push_back(5)` 的接收者被壓成【字串】"d2[3]"
```

最後那一個是設計層的：**37 個元件各自 `scope.get(那個字串)`**。
沒有去改接收者的表示法（那要動宣告、積木與對照圖），而是加一處
`receiver.ts`，把 34 個元件的那一行機械地換成同一個呼叫。

> **一個被壓成文字的結構，解開它的地方要只有一個
> ——三十七份各自的字串處理，是三十七個會各自壞掉的地方。**

⚠️ 而它**解不開就原樣送回去**（`d2[f(i)]`），讓原本的人報原本那句話
——自己造一個「大概是這個吧」的答案，只會讓錯誤訊息指向別的地方。

    解譯器出錯 60 → 53 ／ 兩邊都跑完 114 → 121 ／ 一致 100 → 107

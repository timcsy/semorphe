# 273 — 脫下原文，還站得住嗎

**2026-09-21** · 第 211 刀 · 分支 `211-lift-honest-degradation`

## 起點：一根三天前立的釘子

第 208 刀讓產生器誠實了，而瀏覽器驗收量到它**只守住一條路**：

```
lift → 產碼                        metadata.rawCode 還在 → 🟢 誠實
lift → render → extract → 產碼     rawCode【存不進積木】 → 🔴 int x = cout << x;
```

當時列了三個修法方向，而都卡在同一個地方——

> B（lift 時就整段降級）最根本，而它需要一個「lift 弄丟了東西」的判準。

而那個判準**試過五種，每一種都誤傷**：子節點認領、重新 parse、只看字面值、
前綴、換行。反例永遠是同一個：**風格投影本來就會換掉使用者寫的字**
（`cout << x` → `printf("%d", x)`），而那與「弄丟」在字面上長得一模一樣。

## 🟢 第六種成立，因為它換了一個問法

```
不是問「弄丟了嗎」          ← 那要先定義「什麼算丟」，而五種定義都誤傷
是問「脫下原文還站得住嗎」   ← 把 rawCode 拿掉再產一次碼，還原得出使用者寫的字嗎
```

> **一個「這一段我看不懂」的節點，脫下原文之後如果還原不出使用者寫的字，
> 那它就不該假裝自己是那個東西。**

⚠️ 而「脫下原文」**正是走一趟積木回來的處境**——所以這一問問的，
恰好就是那條路上會發生什麼。**判準與症狀對齊了**，這是它與前五種的差別。

量出來（七種形狀）：

```
漏分號（下一行是宣告）  int x = 1            → int x = 1;          🟢 站得住 → 不動
漏右大括號              int main(){ …        → 補上 }              🟢 站得住 → 不動
語句／引數位置的亂碼    @@  ／  , @@         → 本來就是 raw_code   🟢 no-op
──
漏分號（下一行是 cout） int x = 1 ⏎ cout<<x; → int x = cout << x;  🔴 那個 1 還原不出來 → 降級
括號運算式裡的亂碼      (x @@ 2)             → (x)                 🔴 降級
宣告初值是亂碼          int x = @@@;         → int x;              🔴 降級
──
★ 裸片段 cout << x;                                                🟢 不誤傷
★ 完全合法                                                         🟢 不誤傷
```

## ⚠️ 我猜錯了一件事，而它險些讓這一刀誤傷一整族

第 272 則的最後一節寫著：

> 🟢 線索：風格投影那個反例（`cout << x` → `printf`）**在 lift 那一側不存在**
> ——所以判準可能比產生器那一側簡單。

**那是錯的。** 頂層裸片段 `cout << x;` 會被標成 `syntax_error`（它確實不是
一份合法的翻譯單元）而它**完全被理解了**，在 printf 風格下產出少字
——與產生器那一側**一模一樣的反例**。

🟢 所以 `honest-degradation` 也要「換一個風格再問一次」。
而量出來的時候它是一行讀數，不是一個推論——**探針先跑，猜測後驗**。

## ⚠️ 兩個保守條款，缺一個就誤傷

```
① 兩種 I/O 風格都要問   少掉的字換一個風格就回來 → 它是投影不是弄丟
② 語句路與運算式路都問   一個語句節點走運算式路會少一個分號 → 那是問錯了路
```

而第二條是量出來的：第一版只問運算式路，於是裸片段的 `print`（原文帶分號、
運算式產出不帶）被誤判成「弄丟」。

## 🟢 而「不確定就不動」是預設

與 `ast-repairs.ts` 的契約①同一條：產生器沒接上、產碼丟例外、沒有 `rawCode`
——一律讓開。⚠️ **少了這一條，一個「組裝點忘了 install 產生器」的狀態
會讓每一個節點降級**，而那是一個比原缺陷更糟的失敗模式。

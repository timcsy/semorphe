# 024：耦合的維度從三種（import／身分／語法）增為四種——型別名

> 日期：2026-08-07

## 轉移

- **舊**：[history/021](021-中立性的數字只量身分那一維.md) 列出三種耦合形式——「**import 是耦合的一種形式，身分是另一種，語法是第三種**」，並蓋了語法耦合護欄（第九條）補上第三種。
- **新**：**還有第四種——標準函式庫的型別名。** 而**三條護欄裡沒有一條數得到它**。

## 為什麼變

因為實作 `istringstream` 時自己寫了一筆。

`in >> a`（從串流讀值）與 `num >> 1`（位元位移）**語法完全相同**，分得出來的唯一依據是根變數的型別。判斷規則的第一版寫在 `src/core/lift/lifter.ts`：

```ts
if (rootType !== 'istringstream' && rootType !== 'stringstream') return null
```

核心層於是出現兩個寫死的 C++ 型別字串。

| 護欄 | 量什麼 | 有沒有數到 |
|---|---|---|
| 中立性 | 元件身分字串 | ✗ 型別名不是身分 |
| 語法耦合 | 前置處理指令／`std::`／註解符號 | ✗ 清單裡沒有型別名 |
| 就近性 | 一個元件的實作散在幾個檔 | ✓ **但它量的不是語言耦合** |

**叫的那一條，量的甚至不是這件事。** 它報的是 `input` / `var_ref` / `arithmetic` 三個元件的擴散度各 +1 檔，指向同一個新檔案——一個關於「碎裂」的訊號，恰好與這筆語言耦合同源。

## 這一次比 021 更難發現

021 那六處是**去查證別的東西時撞見的**。這一次不一樣：

> **如果我把那條規則寫進一個已經提到那三個概念的既有檔，三條護欄會全綠。**

也就是說，這筆耦合能不能被發現，**取決於我把它寫在哪個檔案**——而那與它是不是耦合毫無關係。一個維度外的違規，被另一個維度**偶然**照到。

## 後果

- 語法耦合護欄的「確定」桶新增四個型別名：`istringstream` / `ostringstream` / `stringstream` / `size_t`。判準是「在 TypeScript 裡沒有任何合法用途」——`int` / `string` 同形於核心的執行期型別標籤，仍在「無法確定」。
- 合成注入的正向那一支**直接餵當時寫錯的那一行**，不是一個編出來的例子。
- 五個看起來該是「確定」的記號（`printf` / `scanf` / `cout` / `cin` / `iostream`）**實測後歸「無法確定」**：它們在 `src/ui/` 是風格偏好的識別字（`io_style === 'printf' ? 'cstdio' : 'iostream'`），不是被產生出去的語法。判成違規是「為了數字好看而**悲觀**歸類」，與樂觀歸類同樣是量錯。
- 「無法確定」48 → 60。**那不是惡化**，是清單變長之後照出本來就在那裡的東西；它不計入棘輪，正是為了不讓「把記號移出清單」變成刷分數的方式。
- 規則本身搬進語言套件：`src/core/lift/post-processors.ts` 收宣告（語言套件推、核心讀，與 `comment-syntax.ts` 同形），`cppStreamRead` 住進 `languages/cpp/core/lifters/expressions.ts`。

## 編號要接得上

本輪的規格與程式註解初稿三處都把型別名寫成「**第三種**」——那會讓讀者以為 021 只講了兩種。已更正為第四種。**一條靠序數指涉的知識，序數本身就是連結**；接錯等於指向不存在的地方。

## 這條仍然會重演

021 說過「其他護欄也各自只看一個維度」。這一次證明了更強的版本：**新增一種違規形式時，最先叫的那條護欄可能量的是完全不同的東西**——所以「有護欄叫了」不代表「那條護欄涵蓋了這個問題」。

判準見 [concepts/執行機構.md](../concepts/執行機構.md)「一條規範被機械化時，選了哪一維會消失在數字裡」。

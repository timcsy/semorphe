# 253 — 一個接點有落點，不代表那個落點裝得下它全部的孩子

**2026-09-18** · 管線 188 的 round-trip 那一關（面向④：走一趟積木回來）

## 讀數

```
原始        v.erase(unique(v.begin(), v.end()), v.end());
走一趟積木  v.erase(unique(v.begin(), v.end()));
```

**那不是少一個引數，是換了一個意思**：刪一整段變成刪一格
——而它**編得過**，g++ 一聲都不吭。

## 一、根因是一個「看起來完整」的宣告

```jsonc
// cpp:container_erase
"slots": { "obj": "expression", "key": "expression" }
// forms/blocks.json
"args0": [ { "input_value": "OBJ" }, { "input_value": "KEY" } ]
```

兩個接點、兩格落點——**第三十一條（投影遺失）看起來是滿分的**。

而 `v.erase(a, b)` 的兩個引數都進了 `key` 這一格，
於是 `key` 有**兩個孩子**，而渲染器的 `inputs` 一格只接得住 `slots[0]`。

> **一個接點有落點，不代表那個落點裝得下它全部的孩子
> ——而「有沒有落點」是今天唯一被檢查的那一個。**

🟢 修法：第二個位置變成**它自己的接點** `key_end`，兩端各有一格。

## 二、而修它的時候當場又犯了隔壁膠囊警告過的錯

第一版的判別只看「`erase` ＋ 兩個引數」，於是把
`s.erase(2, 3)`（字串的「從第幾個字刪幾個」）**搶走了**，三支測試當場紅。

而那個警告寫在 `string_insert/lift.ts` 裡，**是同一天早上寫的**：

> 「一個只看引數個數的判別，在另一個型別剛好也收兩個引數時不會落空
> ——它會安靜地把那個東西當成自己的。」

判準改成**問接收者的宣告型別**，查不到就讓開。

⚠️ 這是那個病的**第四次**（`erase` 一次、`insert` 兩次、這次一次），
而每一次的修法都只修了那一顆。

## 三、修完之後它**還是**紅的，而那是第二個缺陷

```
vector<int> v;      🟢 getType('v') → 'vector'
vector<int> v, w;   🔴 getType('v') → null
```

多宣告子的名字是由具名策略（`liftSingleDeclarator`）**直接組出來**的節點，
不走 `liftWithContext` 的回傳點——而型別收集器掛在那個回傳點上。

> **一個掛在「每個 lift 回傳點」上的收集器，收不到那些沒有經過 lift 的節點
> ——而「由策略直接組出來」與「lift 出來」在樹上長得一模一樣。**

⚠️ 症狀是型別查不到，而查不到的下游全都走「判不出來就讓開」——於是
**同一個變數，宣告時多一個逗號就換了一種行為**，而沒有任何地方出聲。

## 四、那支新測試自己紅過兩次，兩次都是【檢查】的問題

| 症狀 | 根因 |
|---|---|
| 面向④ **18 支全紅**（含全部正向錨點） | 過濾器照**原文**比對骨架，而走一趟積木回來會把 `int A[5], fx[8], …;` 攤成四顆 |
| 比較器那一條紅 | 過濾器的 `^\}` 吃掉了 lambda 的收尾 `});` |

> **當一個新的檢查連【正向錨點】都紅的時候，先懷疑那個檢查。**

# 237 · 使用者看得到而我量不到的那一行

**日期**：2026-09-15
**觸發**：使用者：「積木跟程式碼好像 highlight 的地方對不上，會差一行」

## 我先修錯了地方，還推了一版

第一次量的時候我看到對照表寫著「行 1」而那一行是第二行，判定「差一行」
——**而 `CodeMapping` 是 0-based**（消費端逐字寫著 `m.startLine + 1`，
因為 Monaco 是 1-based）。那批數字其實是對的。

第二次我找到一個**真的**缺陷（補丁器在最上面插一行 `#include`，而對照表停在
補之前），修了、推了（`cdfd4e80`）。而使用者換了 bundle 之後**症狀原封不動**。

> **在斷言「這個數字對不對」之前，先去找【誰在用它】
> ——基準寫在消費端，不在產生端。**

## 轉折點是他在主控台跑的那一行

我把每一條想得到的路都量過了——從課文按鈕進、帶著舊狀態、不清 localStorage、
真滑鼠點擊、本機與線上各一次——**全部都是對的**。

於是我不再改程式碼，改成請他把**他那一份的實際狀態**印出來：

```
控制器 / 面板   都說 startLine = 2   → 那一行是 "int main() {"   ← 確認不是游標行
bundle          index-BGyA5sr7.js                              ← 比我一直在量的【還新】
節點            node_28                                        ← 動過很多次之後
```

三格各解掉一個死結。最後那一格讓我寫出**會一直動的探針**，而觸發點是
**第 ⑤ 步「改積木上的字」**——我先前的測試全都停在第 ④ 步。

> **我量不到而使用者看得到的時候，該問的是「我的路徑跟他的差在哪」，
> 而不是再改一次程式碼。**

## 根因

`cpp:program` 的產生器，**合成骨架**那條路：

```ts
trackOwnText(ctx, code)          // ← 只算到 preamble（#include、using）為止
…
code += entryFns.map((f) => {
  let block = f.open.map(...)    // 🔴 進入點那一行在這之後才接上，沒被算
```

於是 `main` 裡面的每一顆都少一行。

> **一個共用的行號計數器，它的正確性靠「每一段自己記得報數」。
> 而漏報的那一段，產出的程式碼一個字都不會錯。**

⚠️ 它只在「骨架是產生器合成的」那條路上（積木→程式碼、而樹裡沒有 `func_def`）。
從程式碼那側進來時對照表是 lift 給的，一直都對——所以它看起來像「有時候才歪」。

## 而第五十六條護欄為同一族缺陷立過，卻抓不到它

那條的緣起逐字是「我還發現有時候 **HighLight 兩邊對不上**」，
而它三個 C++ 探針的原始碼**都自己帶著 `int main()`**
——於是走的是「樹裡已經有框」那條 legacy 路徑，一個都走不到合成那一條。

> **一條護欄的探針如果都長同一個樣子，它保護的是那個樣子，不是那個性質。**

## 🪦 而這一輪我踩了三次「量到的不是真的」

```
探針自己的 console 過濾寫 includes('[T]')  → `[T5]` 不含 `[T]`，三次追蹤全被我濾掉
Playwright 重用既有 preview 伺服器          → 量到上一次建置（今天第二次）
用 grep 過濾樹的輸出                        → 樹根那一行沒有前導空白，被我濾掉，
                                            於是我以為「樹是一顆孤立的 print」
```

三次都是**我自己的工具在騙我**，而三次的症狀都是「證據不見了」而不是「證據錯了」。

> **一個「什麼都沒印出來」的觀察，先懷疑那支筆，不要先懷疑那張紙。**

# 316 · 收合的鑰匙要認得整塊——一條拿真實語料量的護欄，第一次跑就抓到「對到別顆」

> 日期：2026-11-01（spec 190，vision〈分子〉「階層下的來回一致」）
> 轉變：draft〈分子與粒度切換〉§八之 3：「展開與收合不得改變語義。護欄的形狀已經很熟：`分子 → 展開 → 收合 → 分子` 逐字相同。」
> 新護欄 `audit-collapse-roundtrip` 拿課文語料（101 支、1381 顆收得起來的節點）逐顆量三層：框、語義、對回去。

## 第一次跑的讀數

```
重新 lift（id 全換）      對回 1381｜對不回   0｜對錯 0
最前面插一行（路徑全位移） 對回  739｜對不回 638｜對錯 4   ← 硬性零紅了
```

對錯的四顆都是 `return`：`ex1.cpp` 有 `add`、`mul` 兩個函式，在最前面插一行之後，**`mul` 的 `return` 的路徑鍵指到了 `add` 的 `return`**。

## 原因：同一個配對器，用在一個它沒被設計來的母體上

`layout-key.ts` 的 `matchByKeys` 判「這把鑰匙曖昧嗎」，數的是**存下來的那一批**（`countA`）。
流程的手拖位置存的是整棵樹，那個數有意義；**收合只存收著的那幾顆**——每一把鑰匙在那一批裡都「唯一」，
於是路徑鍵（最脆的那一把）被當成可信的。兩個 `return` 自己的內容一樣（`cpp:return{}`），只有**子樹**分得出來。

## 修法：子樹鍵

收合多存一把**子樹鍵**（整塊的身分＋屬性遞迴，FNV-1a 雜湊）。對回時：

```
子樹鍵在新樹裡唯一        → 就是那一顆
有好幾顆一模一樣的        → 由路徑鍵挑；挑不出就不對（寧可對不回去）
一顆都沒有（裡面被改了）  → 才退回路徑鍵
```

修後：插一行 對回 1260｜對不回 121｜**對錯 0**。剩下的 121 是內容一模一樣、路徑又位移了的（重複的 `cout << endl`、`i++`）——安靜地攤開。
v25 第一版存下的（沒有子樹鍵）照舊配對。

## ⚠️ 留著的問題

流程的手拖位置用的是同一個 `matchByKeys`，母體是整棵樹，`countA` 有意義——但「內容曖昧＋路徑位移」時，路徑鍵仍可能指到別顆。
它沒有在這一刀處理：要先在它自己的護欄（`audit-layout-key`）上加「最前面插一行」那種擾動量過，再決定。

# 137　「註解不見了」，而它底下有四個洞

**日期**：2026-08-23 ｜ **交付**：註解在整條路上都活著 ＋ `elif` 主體不再掉行
**前一則**：[136](136-補課的第一輪就抓到三個缺陷.md)
**觸發**：使用者貼了一張截圖——「程式碼後面的註解不見了」

## 一句回報，四個各自獨立的缺陷

| 在哪一段路 | 症狀 |
|---|---|
| **抬升** | `if a:  # 為什麼` 的註解是那個語句的**子節點**（不是兄弟），而「同一列 → 接在前一句」那條規則看不到它 |
| **抬升** | 🔴 `elif` 的主體**只留第一行**——那不是註解，那是**整段程式碼**掉了 |
| **渲染／抽取** | 沒有 mutation 的積木**根本沒有 `extraState` 這條路**（Blockly 只在積木自己實作 `save/loadExtraState` 時才理它） |
| **抽取** | 有 mutation 的積木的 `loadExtraState` **只讀自己那幾個鍵**，把別人的吃掉 |

四個**都不報錯**：產出的碼合法、積木畫得出來、5500 個測試全綠——而**使用者打的字沒了**。

## 第二個才是最重的：`elif` 只留第一行

```python
elif r == 0:
    x = int(...)
    print(x)        ← 這一行整段不見
```

根因在資料模型：`elif_condition` 與 `elif_body` 是**兩個靠索引配對的平行清單**，
於是「一支」只能是**一個節點**。抬升那一路寫著 `elifBodies.map(b => b[0])`
——而產生器的註解早就預言了它的近親：

> 「錯開之後每一格都還在，只是接錯了人。」

而抽取那一路**反過來錯**：它把一支的整串攤進同一個清單，於是第二支的條件
配到第一支的第二行。**兩個方向各錯一半，而它們互相看不見。**

🟢 修法是把「一支」變成**一個節點**：多行包成 `_compound`（核心本來就有的
「一段」的結構身分），一行的照原樣。渲染、抽取、產生、執行四處各拆一次。

> **一個「一個 input ⇄ 一個孩子」的契約，寫下來之前兩邊都以為自己是對的。**

## 註解要有一個**看得到**的家

前三個洞可以用 metadata 修，而 metadata 在使用者動一下積木之後就沒了。
所以：**沒有 slot 的註解進「註解泡泡」**（Blockly 原生會存檔，而且看得到、改得動）；
**有 slot 的**（`if …:  # 為什麼` 那種「某一行」的）走 `extraState`，
由那顆元件自己放回原位。

⚠️ 而兩條路**不能都放**：實測時同一句註解**重複出現，還跑到整段的最後一行**。

## 一個包裝，差點弄瞎一條護欄

「別人的鍵原樣帶著走」是包在 `saveExtraState` 外面的一層。而有一條護欄
**靠讀 `saveExtraState` 的原始碼**量「這顆積木存了哪些鍵」——包裝之後那份原始碼
裡一個鍵都沒有，於是那一維**整個瞎掉，而它不會變紅**。

🟢 它自己抓到了自己：那條護欄下面有一則**指名清單**（「這幾顆必須被報出來」），
而清單一夕清空就是紅的。它的檔頭逐字寫著理由：

> **一條只擋「變差」的棘輪，擋不住「量得更少」。**

修法：包裝把原本那一份掛在 `__semorpheInner` 上，護欄拆開再讀。

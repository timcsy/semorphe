# 一個「由父節點吃掉」的宣告，要說得出是哪一個父節點

**日期**：2026-09-09
**取代**：`cpp:comma_expr` 的 `skipPaths: ["extract", "render"]`（理由 `consumed-by-parent`）
**決定者**：使用者

---

## 舊的決定，與它為什麼看起來成立

`cpp:comma_expr` 有 lift、有產碼、有執行器，而它的 `forms/blocks.json` 是 `[]`。
`component.json` 上兩行宣告說明了為什麼：

```json
"skipPaths": ["extract", "render"],
"skipReasons": { "render": "consumed-by-parent", "extract": "consumed-by-parent" }
```

而 `tests/assets/projection-home-decisions.json` 裡有一筆判定替它背書，逐字：

> 逗號運算式（`i++, j--`）在教學裡只出現在 for 的更新段，
> 而那一段由迴圈那顆自己裝。沒有積木就沒有「哪一格」可談。

🟢 **那句話寫得很具體，而它是可以被否證的**——只是在此之前沒有人去量。

---

## 量了之後

拿學生的競賽練習當語料（218 個 `.cpp`，見 [[223]]）：

```
語句位置        138 次   ← 父節點是 body，沒有人吃它
for 的更新格      2 次   ← ✅ 判定說的那一種，真的存在
值的位置          0 次
```

⚠️ 判定沒有說錯「有這一種」，它說錯的是「**只有**這一種」。

而 138 筆的下場，實測積木那一側：**整行變成一顆 `cpp_raw_code` 黑盒**。
那 138 筆裡有 134 筆是同一行——競賽 C++ 的第一行
`ios::sync_with_stdio(0), cin.tie(0);`。

> **一個「由父節點吃掉」的宣告，要說得出【是哪一個父節點】
> ——否則它在沒有那個父節點的位置，就是一句沒有人檢查的話。**

---

## 🔴 而使用者選的不是我建議的那一條

我建議**在語句位置把逗號拆成兩句**：值被丟掉之後它只剩「先做這個再做那個」，
而積木畫布已經在用上下疊放表達順序——一顆逗號積木在那裡畫的是畫布已經畫過的東西。
那條路 138 筆全解，2 筆留著。

使用者逐字：**「我比較想為了兩根指標的迴圈而做一個逗號的運算子積木」**。

而那是對的，理由是**我把「多數」當成了判準，而他看的是「那 2 筆是誰」**：

```
for (int a = 0, b = n; a < b; a++, b--)
```

兩根指標是 AP325 的常見技巧，而在此之前那個迴圈的**第一格與第三格是兩個
打不開的黑盒**。拆語句救不了它——那 2 筆正好是拆不掉的那 2 筆。

> **當一個方案解掉 138 筆而留下 2 筆，要先問那 2 筆是不是【本來就最難的那 2 筆】。
> 「多數」不是判準，「剩下的是誰」才是。**

---

## 🔴 而做出來之後，138 筆也一起好了

一顆積木同時服務兩個位置——**只是它需要兩個形態**。

`role` 是 `expression`（產出 `a, b`，分號由 `asStatement` 補）。而只給運算式版的話，
語句位置那 138 筆**會從畫布上消失**：

```ts
// renderStatementChain
if (this.expressionOnlyBlockTypes.has(block.type)) continue
```

⚠️ **那比黑盒更糟——黑盒至少看得見。**

🟢 形狀與函式呼叫那一顆逐字相同（同樣 `role: expression`，一個語句版
＋ 一個運算式版，`renderMapping.expressionCounterpart` 串起來）。
那正是 spec 097 定下的「一個身分可有多個形態」。

---

## 交付

```
積木        cpp_comma_expr（語句版）＋ cpp_comma_expr_expression（運算式版）
標籤        「依序」，變長插槽，minCount 2
工具箱      運算（自動收——owner (core) ＋ category operators）
符合性      「無法確定」4 → 3
```

驗收（第一百一十六條護欄 `comma-block`）：
`for (int a = 0, b = n; a < b; a++, b--)` **三格全部是真積木，零黑盒**。

⚠️ **還開著的**：`for (i = 0, …)`（賦值當初始，沒有 `int`）仍有黑盒
——`cpp:var_assign` 沒有運算式形態。而**那與逗號無關**：
`for (i = 0; …)` 今天本來就是黑盒。那是另一刀。

## 🔴 而做完之後，開瀏覽器實測抓到一個 6495 條測試沒抓到的

那顆積木做好了、護欄綠了、全套 6495 綠。**打開瀏覽器貼上那個迴圈**：

```
積木載入失敗：cpp_var_declare_expression is missing a(n) INIT_1 connection
extraState={"items":["var_init","var_init"]}
```

⚠️ **與逗號無關**（實測隔離：把逗號拿掉照樣紅）。真因是**既有的**：
`for` 的第一格那顆積木有**兩個形態**，而只有語句版補完整：

```
cpp_var_declare            paramList（NAME_{i} ＋ INIT_{i}，可以加宣告子）  ✅
cpp_var_declare_expression 寫死的 NAME_0 ＋ INIT_0                        🔴
```

而渲染那一路（`cpp:renderVarDeclare`）對兩個形態吐**同一份狀態**，
於是它老實地吐出 `INIT_1`，而運算式版建不出那一格。
抽取那一側也是：它只讀第 0 格，`b = n` 一動積木就沒了。

> **兩個形態的宣告，只有一邊補得完整時，
> 另一邊會在【使用者拖到它】的那天壞掉。**

### ⚠️ 為什麼 6495 條測試看不到

第五十一條護欄的檔頭早就寫著這一句：

> 渲染那條路的測試產出的是 **BlockState（JSON）**——它對「Blockly 建不建得起來」
> 一個字都沒說。而 `jsonInit` 的失敗只在**建的那一刻**發生。

而我新寫的護欄也住在 JSON 那一側。**那句話在那裡等了很久，而它是對的。**

🟢 修法：運算式版補上同一份 `paramList`；兩個形態的抽取共用**同一支**
`readDeclarators`（不留兩份會漂移的迴圈）。
兩條新斷言進了第一百一十六條護欄。

⚠️ 代價：`for` 的第一格多了一個齒輪（可以加宣告子）。
68 張對照圖重產，**其中 1 張的幾何真的變了，而字一個都沒變**。

## 一顆積木不夠——插槽裡裝的東西也要有那個形態

逗號積木做好之後，競賽模板那一行在畫面上是這樣：

```
依序 [直接寫運算式：ios::sync_with_stdio(0)] [直接寫運算式：cin.tie(0)]
```

**看得見，而拆不開。** 逗號的插槽收的是**運算式**，而 `cpp:io_sync` 與
`cpp:io_tie` 那時只有敘述形態——它們在運算式位置只能退成黑盒。

使用者：「**補**」。兩顆各加一個運算式形態（`form: { axis: 'role', value: 'expression' }`），
與遞增那一顆逐字同形。

```
之前   依序 [黑盒] [黑盒]
之後   依序 [設定輸入輸出與 C 標準流同步 0] [設定 cin 的連動輸出對象為 0]
```

⚠️ 而**敘述位置仍然用敘述形態**——多一個形態不得把原來那個擠掉（護欄有驗）。

> **一顆積木的到位，量的不是它自己畫不畫得出來，
> 是它的插槽裡裝得下真東西還是黑盒。**

🟢 實測：整支競賽程式跑得動，輸出 `01234`，迴圈標著 ×5。

⚠️ 同族還開著一個：`cpp:var_assign` 沒有運算式形態，所以
`for (i = 0; …)`（不帶型別的那種）的第一格仍是黑盒。
**語料裡只有 2 個檔**，所以沒有跟著補——那是量出來的決定，不是遺漏。

# 309 · 判決第一次被學生看到：Cella 的判決與型別查詢接進診斷通道

> 日期：2026-10-31（spec 182，重構階段 5a）
> 轉變：Cella 的判決在這之前只在探針裡（`tests/probes/c18-verdict`）——零個學生看得到。現在它是一個**提供者**：
> 宣告 `verdict`／`types`、排在 JS 直譯器前面，在 Web Worker 裡判；結果轉成既有的 `Diagnostic`，
> 積木上的警告圖示與程式碼的波浪由兩個視圖既有的 nodeId 投影畫出。
> 設計：[draft](../draft/2026-10-31-重構的設計-能力介面與降級路徑.md) 二、四；規格 `specs/182-cella-verdict-provider/`。

## 新的形狀

```
app（組裝點）  semantic:update ─防抖→ provide('verdict').check({ tree＋骨架積木, 目標, 風格, 骨架, 測資 })
providers/cella   provider.ts  補進入點 → formalize → 帶版本號送 worker；翻不出來的直接回 unknown＋unsupported
                  worker.ts    IndexedDB 有編好的模組 → 直接載；沒有 → 下載套件、編譯、存起來
core              verdict-diagnostics.ts  判決／型別 → Diagnostic（來源 cella；判不出來是 info）
視圖              error 紅、info 藍——積木的圖示與程式碼的波浪同一個顏色語言
```

## 舊的哪些前提換掉了

- **「診斷只有兩個產出端（規則、樹的性質）」**：第三個是判決。三者仍然**一次廣播**（`runAllDiagnostics` 是全集取代），
  判決結果住在 app 等下一次廣播，不自己廣播。
- **「判不出來」沒有樣子**：在此之前沒有 `info` 這個嚴重度。P6「必須區分原因（程式碼錯誤／系統能力不足）」第一次有了畫面上的分別。
- **快取要兩層（套件檔＋編好的模組）**（research R6 原案）：量到**編好的模組不需要 Cella 執行環境**（13 毫秒載起來就能判），
  前一層沒有用處。第二次打開 25.7 秒 → 0.16 秒。
- **文案寫在核心的表裡**（data-model 原案）：既有的診斷文案都住 i18n、有第四十二條護欄守完備性——判決的規則身分交給那條護欄。

## 實作途中量到、而設計沒寫到的

- **L0 的樹沒有 `main`**：骨架隱藏時 `int main() {` 是產生器包上的文字。第一次在瀏覽器開，預設程式被判成「缺 main」。
  補進入點的規則照產生器（`components/cpp/program/generate.ts` 的 mustStayTopLevel ＋ 骨架宣告的 `hostsBody`）。
- **e2e 會被它拖慢**：每個頁面閒下來都開始編十幾秒的模組，四個併行就是那條「忙碌機器上的假紅」——自動化瀏覽器不自動暖機。
- **可達性護欄不認得 worker 入口**：`new Worker(new URL(…))` 不是 import，worker 帶進來的整支會被判成「產品走不到」。
- **Vite 的 worker 預設 IIFE**：動態載 cella-lang 會分塊，建置直接失敗——`worker.format: 'es'`。

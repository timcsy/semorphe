# 139　註解變成一顆看得到的積木（而 138 的欄位整套退場）

**日期**：2026-08-24 ｜ **交付**：行末／標頭註解 → 灰色註解積木；`Annotation.slot` 與註解欄位全數移除
**前一則**：[138](138-註解有了一個看得到的家.md)（**同一天做的，同一天被換掉**）
**觸發**：使用者看了 138 做出來的樣子——「我覺得這樣有點醜，沒有其他改法嗎？」

## 一句話的轉折

138 把註解做成**積木上的欄位**（白框、齒輪、寄放、`annotationFields` 宣告…）。
我提了四種外觀讓使用者挑，使用者挑完之後補了一句：

> 「**我的意思是用灰色註解積木就好。**」

——而那顆積木**本來就存在**（`python:comment`／`cpp:comment`，五路俱全）。

> **在發明一個新機制之前，先問「這件事有沒有一顆既有的積木已經在做」。**

138 蓋的整套（`annotation-fields.ts`／`note-field.ts`／`statement-note.ts`／
`branchList.notes`／`func_def` 的註解列／`Annotation.slot`）**當天全部拆掉**。

## 擺在哪裡——使用者給的規則

> 「一般的 statement，註解在**上面**；而對於結構，註解在**區塊內**。」
> 「這樣的原因是**可以讓學生比較容易看到註解**，對學習更有幫助。」

```
x = 1  # 起始值          →   # 起始值
                             x = 1

if a != 0:  # 兩個根     →   if a != 0:
    x = 1                        # 兩個根
                                 x = 1
```

實作落在**抬升**那一路（`lift/lifter.ts`）：同一列的註解不再掛成 `annotation`，
而是 `ctx.lift` 成一顆註解節點，放進「它說的那一行」的位置
——一般語句放在它**前面**，結構放進 `children.body` 的**第一格**。
`elif`／`else`／`except`／`finally` 由那兩顆元件的策略各自放進自己那一支。

🟢 **下游零改動**：渲染、抽取、產生、執行四路對「一顆註解節點」本來就會做事。
這正是它比 138 便宜一個數量級的原因。

## 代價：不再一字不差，而它**具名**

行末註解會被搬到自己一行。語料護欄裡多了一個具名豁免 `COMMENT_REFLOW`
（今天只有一段），理由寫在那裡。

> **一個豁免要具名**（[018](018-規則順便放過.md) 的老教訓：靠規則順便放過＝用宣告刷數字）
> ——這裡少比一段，就要在那裡看得到是哪一段、為什麼。

## 這一天的教訓

- **「醜」是一個設計訊號，不是一句抱怨**：它指的通常不是顏色，而是
  **這個東西被做成了錯的種類**（一個欄位，而它其實是一句話）。
- **問清楚形式再蓋機制**：138 的欄位、齒輪、寄放、宣告，每一樣單獨看都是對的，
  而它們合起來回答的是一個**沒有人問的問題**。
- 🟢 138 留下來的東西不是零：`blockOptText` 的「齒輪關掉＝收起來不是燒掉」留著了，
  而 `for … else` 整段消失、`except` 註解掉字、降級重印那三個修正也留著。

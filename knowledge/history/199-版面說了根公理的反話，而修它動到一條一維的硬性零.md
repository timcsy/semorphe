# 199 — 版面說了根公理的反話，而修它動到一條一維的硬性零

> 2026-08-31 → 09-01（spec 168）。起點是使用者一句話：
> 「你現在把積木和流程用 tab 切換我不太喜歡，**因為這樣程式碼面板就變得比較特別了**」。

## 轉變

```
舊   佈局宣告 `layers: UnderstandingLayer[]`——一維，說得出「開哪幾層」
新   佈局宣告 `areas: LayoutSlot[][]`——二維，說得出「哪一層在哪一格」

舊   編輯區 ＝ SplitPane ＋ 巢狀 flex
新   編輯區 ＝ 一張 CSS Grid，四個面板是平等的直接子節點

舊   第八十一條的兩條硬性零（一維）
新   六條不變式（二維）
```

## 為什麼

### 那個不對稱說的是根公理的反話

```
程式碼   永久佔一欄
流程 ┐
積木 ┘  共用一欄，用分頁互斥
```

三個都是投影，而只有一個不必跟別人搶位子——**而被特別對待的那一個，
正是整個專案存在的理由要說「它不特別」的那一個**（唯一真實，各式投影）。

⚠️ 它也違反了自己的宣告：`compare` 宣告 `[element, space]`，
而那一欄實際是「space **或** relation」。

### 而 `layers: []` 表達不出解法

解法是「十字」：`程式碼｜積木 ／ 流程｜主控台`，四層各一格。
一維的清單說不出「哪一層在哪一格」，所以**宣告本身要換形狀**。

🔴 這是同一天第二次撞到同一個病（另一次是 `arduino.json` 的三段空欄，見 v0.11.4）：

> **一個裝不下的形狀，最常見的偽裝是一句解釋它為什麼該是空的註解。**

## 十字的排法換過兩次，而第二次保住的是更大的一塊

```
🪦 我提的     程式碼｜流程 ／ 積木｜主控台
              賣點是「閱讀順序恰好等於 LAYER_ORDER」——而那是一個【過度加權的巧合】，
              代價是切「對照 → 十字」時積木會從右上跳到左下

🪦 第二版     程式碼｜積木 ／ 流程｜主控台
              保住「程式碼與積木兩格不動」

🟩 定案       程式碼｜流程 ／ 主控台｜積木        （2026-09-01 使用者拍板）
              保住【整個左欄】——它與「對照」逐格相同（程式碼在上、主控台在下）
```

> **從「對照」切到「十字」，整個左半一個像素都不動——右半才從「積木佔滿」
> 拆成「流程／積木」。**

而它的二維說法是：**左行是「我寫的東西 ＋ 它說的話」，右行是兩個視覺投影。**
⚠️ 代價是積木從右上移到右下，而那不是缺陷——**流程進來了，總得有人讓位**。

## 🔴 動到的那條硬性零：是「改準」不是「放寬」

第八十一條原本兩條都是一維的，而十字兩條都違反：

```
舊  由左到右必須是 `LAYER_ORDER` 的子序列 → 攤平成一維後 space 跑到 relation 前
舊  `state` 不得出現在編輯區的預設裡     → 十字的宣告裡有 state
```

升成：

```
新 I3  【每一列】與【每一欄】都必須是 `LAYER_ORDER` 的子序列（連續重複＝跨格）
       ⚠️ 而 `state` 不參與——它不是程式的投影，是【程式在講話】
新 I4  `state` 必須在【每一個】版面裡恰好一個連續矩形——**不得缺席**
```

🔴 舊那條 `state` 規則的理由逐字是「**列它進來會讓面板區變成一個可以被佈局關掉的
東西**」——而十字沒有關掉它，是給了它一個對等的格子。

> **一條規則如果是為了防止「消失」而寫成「不准出現」，
> 它會連「換個位置出現」一起擋掉。**

🟢 新規則仍然擋得住鏡像版面（`space, element` 不是子序列）——那才是它存在的理由。

# 210 — 把例外換成回傳值之後，接例外的那一段安靜地變成永遠成功

> 2026-09-06（spec 173）。vision「網頁版有檔案」的第二個驗收：
> `FileStore` 埠 ＋ 兩個實作，而 VSCode 那側不實作。

## 轉變

```
舊   core/storage.ts 與 core/progress.ts 直接叫 localStorage（7 處）
新   叫一個【鍵值存放的埠】，而實作住在 src/ui/

舊   寫入失敗用【拋例外】表達（localStorage.setItem 在配額滿時拋）
新   用【回傳 boolean】表達

舊   測試換掉 globalThis.localStorage 當替身
新   測試注入一個實作——它不再依賴全域
```

## 為什麼

### 一、一個核心如果它的存檔只在一個宿主上跑得起來

```
Node                  沒有 localStorage
VSCode 的擴充主程序    沒有
無痕／擋掉 storage     叫它會拋
```

> **一個「核心」如果它的存檔只在一個宿主上跑得起來，
> 那它不是核心，是那個宿主的一部分。**

🟢 而 VSCode 那側**今天就沒有用它**（它有自己的 `DocumentlessStorage`）
——所以這一刀不是去讓它實作，**是別讓它有一天變成必須實作**。

⚠️ **這個破口不會在破的那天出聲**：`localStorage.setItem(…)` 在瀏覽器裡
跑得好好的，壞掉的是第二個宿主，而它可能一年後才出現。
那正是 P9 的形狀——第一百零七條護欄因此是硬性零。

### 二、🔴 把例外換成回傳值，接例外的那一段會安靜地變成永遠成功

`refuse()` 的職責是「拒絕一份存檔之前先備份，而備份**失敗時要說出來**」
——它的註解逐字寫著「寧可讓使用者看到『載入失敗且沒有備份』，
也不假裝備份好了」。

而它的實作是：

```ts
try { store.write(BACKUP_KEY, raw); backedUpTo = BACKUP_KEY } catch { }
```

埠把「寫入失敗」從**拋**換成**回 `false`** 之後，那個 `catch` 永遠不會走到
——於是 `backedUpTo` **永遠被設成成功**。

> **把一個例外換成回傳值的時候，接例外的那一段不會報錯
> ——它只是安靜地變成永遠成功。**

🟢 抓到它的是 T026：「備份沒寫成功卻回報備份好了，**比沒有備份更危險**」。
⚠️ 而那條測試是 2026 年為另一件事寫的，**它在這一刀之前從來沒有紅過**。

### 三、⚠️ 一個換掉全域的測試替身，在被測的東西不再看全域的那天會開始量另一件事

四個測試檔用同一種替身：把 `globalThis.localStorage` 換成一個 mock。
注入化之後**它們讀不到了**，而症狀各不相同：

```
progress.test.ts            測試之間不再重置 → 資料累積 → 斷言值變多
storage-version.test.ts     mock 沒被用到 → 讀不回自己塞的東西
audit-storage-integrity     🔴 「兩條讀取路徑判定不一致」0 → 2
```

第三個最值得記：它**不是紅在一個斷言上**，是紅在**這條護欄自己的棘輪**上
——那個護欄量的是「同一份資料，自動載入與匯入結論相不相同」，
而替身失效讓「自動載入」讀到空的。

> **一個換掉全域的測試替身，在被測的東西不再看全域的那天不會報錯
> ——它只是開始量另一件事。**

🟢 而換成注入之後那些測試**變好了**：不再依賴全域、不再需要記得
呼叫 `clear()`、`progress.test.ts` 連 `happy-dom` 環境都不用了。

⚠️ **一個陷阱**：替身重置寫成 `backing = new FlakyStore()` 是**無效的**
——`StorageService` 在 `beforeEach` 就握住了舊的那一個。

> **一個被注入出去的東西，換掉持有它的那個變數不會換掉它
> ——而那看起來像重置了。**

### 四、⚠️ 一個「測試一行都不改」的硬條件

spec 原本的 SC-002 寫著「既有的存檔測試**與** e2e 一條不改」。
而這一刀改的**正是測試的替身機制**——那個條件不可能成立。

修正成「**產品行為**逐字不變——**e2e 一條不改**」（e2e 跑真的瀏覽器）。

> **一個「測試一行都不改」的硬條件，在改動本身就是【換掉測試的替身機制】時
> 是不可能成立的——而它讀起來像一個嚴謹的標準。**

## ⚠️ 這一刀刻意少做的

- **「列出鑰匙」**那個操作——驗收原文寫著「讀／寫／刪／列」，而**列**零個消費者。
  > **一個埠上的操作如果沒有人叫它，它記的不是能力，是想像。**
- **File System Access API 的實作**（驗收裡的「原生」）——它需要**使用者手勢**，
  端對端測試驗不到。🔴 **一個驗不到的實作與一個不存在的實作，在 CI 上長得一樣。**
- 路徑樹的形狀——鍵值就夠了，而多檔案來的那天**路徑就是一種鑰匙**。

## 交付

- `core/host/key-value-store.ts`（埠 ＋ `MemoryKeyValueStore`）
- `ui/browser-store.ts`（⚠️ **住在 UI 層**：知道宿主的那一層是 UI）
  ——能力偵測是**真的寫一次**，因為無痕模式下 `localStorage` 存在而 `setItem` 會拋
- 第一百零七條護欄：核心裡直接叫宿主儲存 API 的次數 **7 → 0**，
  ⚠️ 而它另有一條「**埠真的接上產品路徑了嗎**」——因為
  **一個埠如果它的預設實作能讓測試通過，那「忘了接」與「接好了」在測試上長得一模一樣**

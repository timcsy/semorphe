# 055　全修一輪——缺陷的**形狀**比缺陷本身更重複

> 日期：2026-08-13
> 觸發：使用者問「C++ 那邊有什麼功能值得做但還沒做好」，然後說「全修」。
> 起點：第三十二條護欄的 **18 段缺口 ＋ 14 筆誤差**。

## 結果

```
缺口   18 → 0    🎉  （兩邊都跑得動 225 → 243，只有參照 0）
誤差   14 → 1        （唯一一筆是 UB，已判定為**非缺陷**）
缺陷帳 36 → 34       （兩根釘子被修好而變紅，已拔）
漏宣告  1 → 0
同優先權群組  2 → 1
形態殘差             同步下降（樣板類別不再整段降級）
```

**十五輪，而每一輪的形狀都在下面重複出現。**

⚠️ 剩下的那一筆誤差是**讀未初始化變數**：真編譯器印出堆疊上的垃圾值，
直譯器老實回 0。把它算成誤差是**指控一個沒有唯一答案的問題有唯一答案**，
而受指控的還是比較誠實的那一邊。判定已改成「其他」並附根因。

## 一、🔴 同一個形狀出現了三次：**對稱的資料遺失**

```
pair<int,string> p = make_pair(…)   初始值：辨識掉、產生也掉
new int[n]                          大小：  辨識掉、產生也掉
vector<int> v(5)                    大小：  辨識掉、產生也掉
```

**三者的來回轉換比對全都一直是綠的。**

> **一個對稱的資料遺失不會讓任何比對變紅——它只會讓執行結果變成別的程式。**

⚠️ 而**只有把執行結果拿去跟真編譯器比**才照得出來。這是第三十二條護欄
（行為的誤差）存在的全部理由，而它今天第一次被大規模使用。

## 二、🔴 「共用一個症狀不代表共用一個根因」——**我犯了三次**

`build-guardrail` 早就記過這條，而我還是按錯誤訊息分組，三次都錯：

| 我的分組 | 實際 |
|---|---|
| 「pair 那 5 段」 | 只有 4 段同根，第 5 段是 `v[i].first`（另一個機制） |
| 「char 的型別語義 4 筆」 | `(char)d`／直印／`isalpha`／比較**本來全對**，只有 `s[i]` 的算術錯 |
| 「`sizeof(long long)` 與 `~0 & 0xFF`」 | 兩個都已經對了；真正錯的是 `sizeof(3.14)` 與 `static_cast<unsigned char>` |

> **錯誤訊息是症狀的名字，不是根因的名字。而按名字分組會給出一個看起來很整齊的清單。**

→ **判準**：分完組之後，**在每一組裡挑兩筆分別跑最小重現**。三次裡有三次
是那一步推翻了分組。

## 三、🔴 一個**假的「顯式的空」**比誠實的遺漏危險

`cpp:pair_declare` 宣告 `skipPaths: ["execute"]`，理由 `"declarative"`，
`_execute_why` 逐字「這顆沒有獨立的執行語義。**顯式的空，不是遺漏。**」

而 `pair<int,int> p;` 當然有執行語義。

> **一個假的「顯式的空」不會隨時間過期——它從第一天就是假的，
> 而正因為它長得像一個決定，沒有人會回頭質疑它。**

⚠️ 對比：`cpp:define` 那筆是**真的過期**（實作條件編譯之後才有可觀察效果），
而 `skip-declaration-gate` 的註解早就記過那一次。**兩種要分開講**。

### 🔴 而它有第二個實例，本輪查到但未修

`cpp:destructor` 也宣告 `skipPaths: ["execute"]`——而解構子當然有執行語義
（離開作用域時呼叫）。症狀：`~Scope() { cout << "exit"; }` **從來不印**，
而程式照樣跑完（誤差第 3 筆）。

⚠️ **更值得注意的是它沒有被任何機制擋下**：`skip-declaration-gate` 有一份
「該宣告的 11 個」對照組清單，而 `destructor` **不在那份清單裡**
——它有 `skipPaths`，卻從來沒有被那道門審核過。

> **一道門只檢查走進來的人，而它不知道有多少人翻牆。**

#### ⚠️ 而我對這一筆的診斷後來被自己推翻了一半

`cpp:destructor` 的 `skipPaths` **其實是對的**：它的執行語義由 `class_def`
承載（`splitMember` 把它拆成 `dtor` 交給 `structs.declare`）——就像
`cpp:operator_overload` 一樣。

🔴 **真正缺的是「誰呼叫 dtor」**：登記了，而沒有任何地方在作用域結束時叫它。

> **「這一路是空的」與「這一路的實作住在別人身上」在 `skipPaths` 上長得一樣
> ——而它們缺的東西完全不同。**

→ 修它要一個 RAII 機制（作用域結束時回呼），是一個獨立的功能。

## 四、🔴 兩份宣告同時存在時，輸的那一份**不會報錯**

`cpp:struct_at_member` 同時有 `blocks.json` 的 `astPattern` 與
`lift.ts` 的 `registerAstBranch`。astPattern 優先，於是膠囊那一份
**從來沒有被呼叫過**——實測方式：加一行 `console.log`，跑一次，**零輸出**。

> **兩份宣告同時存在時，輸的那一份不會報錯——它只是安靜地沒有作用。**

移除之後 `lift-ambiguity` 的「同優先權群組 2 → 1」。

## 五、🔴 一個對照組基線**凍結了錯的行為**

`declaration-change-parity` 的 `execute.string_append_char` 是
`"completed|99"`，而 `99` 是 `'c'` 的碼位——`s = "ab"; s += 'c'` 應該是 `abc`。

> **一個對照組基線只保證「行為沒變」，不保證「行為是對的」
> ——它第一次錄的時候錄到什麼，就把什麼當成正確。**

⚠️ `build-guardrail` 6.5「第一次跑必須是紅的」防的就是這個，
而**對照組型的基線天生沒有那一步**：它的第一次就是「把現況封為合格」。
→ 這一類基線需要一個不同的入場檢查，而今天沒有。

## 六、🔴 而我修 `writeBaseline` 時，判準**在同一輪內就被證明不夠**

同一個病的第三次（前兩次記在那個函式的檔頭）：14 條護欄的呼叫端全都傳
`note: RATCHET_NOTE`，於是「傳進來的贏」讓 `_meta` 的保存機制**全部失效**。

而我的第一版判準寫「新 note **等於** `RATCHET_NOTE` 才保留舊的」
——**只涵蓋了我手上那個實例**。其餘護欄各自組一段更長的固定說明，
於是三個基線裡剛加上去的理由**在同一輪內又被吃掉一次**。

> **一個判準如果是照著手上那個實例寫的，它只會涵蓋那個實例。**

→ 改成**追加關係**（舊 note 以新 note 開頭 ⇒ 保留舊的），並補 5 支測試
——②那次修好時沒有留下測試，所以③沒有任何東西會說話。

## 七、護欄抓到我三次，而每一次都是對的

| 護欄 | 抓到什麼 |
|---|---|
| 識別字必須是英文（#40） | **兩次**——測試裡的 `const 具體`、`半個視圖`。⚠️ 那條護欄是我同一天早些時候建的 |
| 膠囊就近性 | `address_of` 裡寫死 `'cpp:array_at'`，**兩個方向都報** |
| 缺陷帳的 `it.fails` | 兩根釘子因為缺陷修好而變紅，如設計般提醒拔釘子 |

> **護欄防的不是別人，是同一輪的自己。**

## 八、後半程又長出四個形狀（第九～十五輪）

### ⑦ 一個機制的消費者少一個，那個機制就對那條路徑不存在

`operator==` 寫了也沒用：`cpp:arithmetic` 一直在問運算子多載，
**而 `cpp:compare` 沒有**。機制齊全（`memberRole:"operator"` ＋ `splitMember`
＋ `structs.method()`），缺的只是那一顆去問。

### ⑧ 「這一路是空的」與「這一路的實作住在別人身上」在 `skipPaths` 上長得一樣

我把 `cpp:destructor` 的 `skipPaths` 診斷成「第二個假的顯式的空」，
查證後**推翻了自己一半**：它是對的（執行語義由 `class_def` 承載）。
🔴 真正缺的是**「誰呼叫 dtor」**——而追下去發現的是⑨。

### ⑨ 一個作用域少了，症狀不是「變數不見」而是「變數活太久」

獨立的 `{ … }` 被展平，於是 `int main(){ { int x=1; } cout << x; }`
在真編譯器是編譯錯誤，而這裡印出 1。**活太久不會報錯。**

### ⑩ 一個回退值若剛好是某些情況的正確答案，它會偽裝成正確很久

- `container_empty` 對非 array 回 `true` → `if (from.empty()) return s;`
  對非空字串成立 → 整個 `replaceAll` 一次都沒替換，**而輸出是原字串**
- `sizeof` 查不到時回 4 → `sizeof(3.14f)` 「剛好對」，`sizeof(3.14)` 才露餡
- `numericCast` 認不得的型別原封回傳 → `static_cast<unsigned char>(~0)` 是 -1

### ⑪ 一句承諾了兩條路的註解，只走過其中一條

`cpp:string_find` 的檔頭說「`!= -1` 與 `!= string::npos` **兩種寫法都對**」
——而 `string::npos` **整個 lift 不出來**。

### ⑫ 「未經檢驗是否正確」的東西被原樣保留了五個月

`cast.ts` 的檔頭逐字：「命名轉型的 `char` 回整數（**既有行為，未經檢驗是否
正確**——保留，不在搬家的 diff 裡改）」。今天檢驗了，而它是錯的。

> **而保留它的那句話本身，就是它可以被檢驗的證據。**

### ⑬ 一支「未知構造要降級」的測試，會在那個構造被支援的那天變紅

兩支測試用 `template<typename T> class Foo {};` 當未知構造的例子。

> **它需要的是一個新的未知例子，不是把支援拿掉。**

### ⑭ 一個宣告式的機制表達不了的東西，硬塞給它會變成一個看起來有值而其實是空的欄位

`exception_make` 第一版寫 `"ast": "arguments.0"`——那個路徑語法不存在，
於是訊息永遠是空字串，而 `caught: ` 印出來**看起來只是「訊息剛好是空的」**。

### ⑮ 一個退路的安全性不在它退到哪裡，在它的入口條件有多窄

`e.what()` 的處置：`method_call` 找不到方法時看同名欄位
——**必須無引數、且必須真的有那個欄位**，兩者有一個不成立就照樣丟錯。

## 九、而「加一顆元件」有一張固定的清單

新增 `cpp:block` 與 `cpp:exception_make` 各觸發一次，兩次一模一樣：

```
命名一致性     主體詞彙表／單字名清單要收它
課程清單       收錄進 Topic（否則「未收錄 MUST」會紅）
積木型別集合   identity-namespace +1
工具箱／課程快照
執行器清冊     GENERATE_INVENTORY
膠囊搬家防線   component-move-parity
就近性         共用檔呼叫膠囊匯出的建構子，身分字串只留一處
```

⚠️ **那份清單今天散在七條護欄的失敗訊息裡，而不在任何一份文件上。**
→ 已補進 `component-generate` skill 的步驟八（那份 skill 同一天才重寫過）。

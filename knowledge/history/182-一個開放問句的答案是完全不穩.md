# 182 · 「nodeId 穩不穩定」——路線圖問了很久，而沒有人去量

**日期**：2026-08-27
**commit**：`d78f281b`

## 舊：一個寫成問句的前置

`vision.md` 逐字：

> 🔴 **它買到的硬問題**：佈局記在 `nodeId` 上，而**nodeId 穩不穩定**
> （9.2 的前置「階段 5b nodeId 穩定性」）——不穩就對不回去

它以問句的形式躺在路線圖上，而**問句不會自己變成答案**。

## 新：量出來比「不穩」更硬

```
改一行不相干的程式碼再同步一次
  節點      9 → 11
  id 相同    0     ← 連【沒有變】的 func_def／program 都換了 id
```

根因是 `generateId()` 的形狀（`node_${++idCounter}_${Date.now().toString(36)}`）
——計數器與時戳兩個都會變。**這是設計上必然，不是偶然。**

🔴 **而它不是「還沒持久化」，是今天就在掉東西**：面板的 `rebuild()` 會刪掉
不在新樹裡的位移，而重新解析後沒有一個 id 還在。

> **使用者手拖十顆節點，在程式碼裡打一個字，十顆全部跳回自動排版的位置。**

⚠️ 所以那一項的敘述（「重開後在原位」）**漏掉了更急的一半**。

## 為什麼是三把鑰匙——那是量出來的，不是推出來的

```
                路徑    行號    內容    三把一起
改一個值         ✅      ✅      ❌
在後面加一行      ❌      ❌      ✅
在中間插一個兄弟   ❌      ❌      ✅
                83%     92%     96%    🟢 100%
```

> **三把鑰匙的價值在於失效條件互斥。把其中一把的條件抄進另一把，
> 就等於少了一把。**

（第一版的內容鍵把父路徑編了進去，於是它跟著路徑鍵一起壞——
`return 0;` 那顆 `0` **三把全掉**。）

## 🔴 順序有講究，而抓到它的是單元測試不是瀏覽器

第一版是路徑先，於是插一個兄弟之後**舊節點的佈局被指給了新插進來的那顆**。

> **一把先被試的脆鑰匙，不只是「配不到」——它會配到別人身上，
> 而那比配不到更糟。**

⚠️ 而瀏覽器那次「中間插一個 9/9」**看不到這件事**：畫面上的座標字串照樣都在，
只是掛在錯的節點上。（`build-guardrail` §8：一個因為錯誤理由而給出正確結果的
檢查，看起來與健康的完全一樣。）

## 手拖的座標從此是絕對的

原本是「自動排版的底座 ＋ 位移」，於是底座一動、手拖過的節點也跟著動
（實測：位移都正確搬到新 id 上了，而九顆裡仍有兩顆移位）。

> **一個相對於「會自己動的東西」的座標，不是位置，是一個關係。
> 而使用者拖的時候心裡想的是位置。**

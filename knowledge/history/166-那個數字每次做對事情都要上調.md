# 166 · 那個數字每次做對事情都要上調

**日期**：2026-08-26

## 起點：一個開了兩週的項目，其實只差註解

`execution:at-node`（2026-08-12 升格）的四條驗收，逐條核之後：

```
① execution-controller 對兩個面板的呼叫 → 0    🟢 真正的呼叫【早就是 0】
                                              🔴 而護欄報 3 筆——三筆都在【註解】裡
② getMappingForNode 不再回傳兩個視圖的座標     🔴 它還在，而且【零個消費者】
③ 斷點命中的判斷裡沒有行號                     🟢 已完成
④ 瀏覽器實測四件事                             ❓ 沒有人做過
```

## 🔴 一：護欄把「解釋自己不再那樣做」的註解算成違規

那三筆是 `blocklyPanel.highlightBlock`／`clearHighlight`／`monacoPanel.revealLine`，
**全部來自 `execution-controller.ts` 的一段區塊註解**——而那段註解的第一句是

> 「broadcastState「執行走到了這個節點」。**不呼叫任何面板。**」

它在解釋自己**取代了什麼**。

> **一條把「解釋自己不再那樣做」的註解算成違規的護欄，
> 會讓寫下那個解釋的人付代價。**

⚠️ 而隔壁的 `audit-language-plugin` **一開始就跳過註解**
（`line.trimStart().startsWith('*')`）——**同一個掃描問題，兩條護欄，
一條跳一條不跳**。修法是把那一行抄過來。

## 🔴 二：`getMappingForNode` 是那張中央對映表的殘骸

它回傳 `{ blockId, startLine, endLine }`——**一次回答兩個視圖的座標**，
而那正是這一項要拆掉的東西。實測**今天零個消費者**：收攏成廣播之後，
每個視圖自己查自己那一維（程式碼視圖用 `codeRangeForNode`）。

> **一個「一次回答所有視圖」的查詢，它的存在本身就是那張中央對映表。**

刪掉。

## 🔴 三：而真正的收穫是那個數字被拆開

`directViewCalls` 的基線 note 記著它**五天內被上調四次**（67→68→70→73→75），
每一次的理由都是「組裝點把兩端接起來」——**一個正確的動作**。
而那份 note 自己還寫著「🔴 上調不是常態」。

> **一個每次做對事情都要上調的數字，量的是兩件事。**

分欄（與 `audit-language-plugin` 同一個處置，那邊的基線逐字：
「第一版把兩者混成一個數字（47），而那讓『做完了沒』問不出答案」）：

```
75 → 70   註解不再被算成呼叫
70 → 21   組裝點那 49 筆搬進 compositionRootViewCalls（可見，不入棘輪）
```

⚠️ **那 49 筆一筆都沒有消失**——搬的是「哪些數字回答哪個問題」。
組裝點接線本來就會隨功能長，而「一個控制器指揮視圖」不該。

🟢 而剩下的 21 筆現在**答得出自己的目標**了，其中一類（`nodesInAncestorScope`
這種「詢問」）**本來就不該上匯流排**——設計 draft 逐字：
「那是依賴，該依賴介面，不是事件」。

## 驗收④：那四件事測試碰不到，實測過了

```
逐步       execution:at-node { nodeId, follow }  ← 只有節點，沒有 blockId／行號
積木       「把 s 設成 s + i」發光
程式碼     第 6 行 monaco-line-highlight
變數       s=0 i=0
停止       { nodeId: null } → 兩個視圖各自清高亮
斷點       execution:breakpoints { nodeIds: [...] } ← 沒有行號（③ 的機械證據）
           跑到斷點真的停：{ status: 'paused', reason: 'breakpoint' }
```

# 012：從「單一輸入模式」到「三模式參數（select / compose / custom）」

> 日期：2026-03-08

## 轉移

I/O 積木（cout、scanf）的參數設計走過三個版本：

- **V1 純 ValueInput**：只能用積木組合。
- **V2 純 FieldDropdown**：只能從 workspace 掃描到的變數中選。
- **V3 三模式**：dropdown 中加入特殊選項 `__COMPOSE__`（切換到積木組合）和 `__CUSTOM__`（切換到自由輸入），用 validator + `setTimeout` 動態切換 input 類型。

| 模式 | UI 元件 | 用途 |
|------|---------|------|
| select | FieldDropdown | 從 workspace 變數清單選擇（最低認知負荷） |
| compose | ValueInput | 用積木組合複雜表達式（完整表達力） |
| custom | FieldTextInput | 直接輸入文字（最大自由度） |

## 為什麼變

**V1 → V2**：純 ValueInput 對初學者太複雜——輸出一個變數要先拖一個變數積木再插進去。同期變數名稱也從 FieldTextInput 改為 FieldDropdown，因為自由輸入讓初學者打出 `my var`、`123abc` 這類不合法名稱，而且看不到有哪些變數可用。

**V2 → V3**：純 dropdown 解決了初學者的問題，卻拿掉了表達力——無法輸入常數（`cout << 42`）或表達式（`cout << a + b`）。

V3 不是折衷，而是承認**不同情境需要不同的認知負荷**：簡單情境用 select、複雜情境用 compose、特殊情境用 custom。這正是 CLT 的實作——外在負荷應該隨任務複雜度調整，而不是固定在某個水平。

V3 的 UI 複雜度超出原本預期（validator 攔截特殊值 + `setTimeout` 觸發 rebuild），但這個代價是必要的：把它壓回單一模式，等於強迫所有情境共用同一個認知負荷水平。

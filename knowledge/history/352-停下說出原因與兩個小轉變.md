# 352 · 停下時說出原因，與兩個小轉變（scanf 的位置、CI 的安裝）

> 日期：2026-11-08
> 決定：353 是使用者 11-07 的決定（模擬停下時寫出原因）；354、356 AI 照推薦（`/goal` 迭代）。

## 353 · 硬體分頁停下時說出原因（d7678eec）

- 轉變：硬體分頁的模擬停下來時，畫面只是不動了——學生分不出是「模擬到上限」「步數用完」還是「出錯」，也看不出哪些輸出腳還開著（燈還亮、馬達還轉）。
- 改成：`HardwareRecord.stop {kind: simulated | fuel | error}` ＋ `outputsStillOn`（還開著的輸出腳）；分頁上 `.hardware-stop` 說原因、`.hardware-still-on` 點名腳位。
- 為什麼排在這時候：致動器安全狀態 v0（與 cos-mos 談定，③ 介面）的呈現建立在「停下」這個時刻上——先讓停下本身說得出原因，安全狀態（confirmed／unconfirmed／failed）才有地方接。
- 還開著：致動器安全狀態的呈現（semorphe 只讀只呈現；cos-mos 11-08 上板驗收後第五欄多了 `failed`）。

## 354 · scanf 放得進運算式位置（b181f853）

- 轉變：`for (; x != 0; scanf("%d", &x))` 的第三格被包成原文——scanf 的元件只宣告了敘述位置，而 scanf 有回傳值。
- 改成：`cpp:input_formatted` 宣告 `positions: [statement, expression]`（產生器與運算式積木早就在）。
- 牽動：宣告完整性護欄的語料裡唯一降級成 `raw_expression` 的就是這一段 ⟹ 它掉出母體，判定放回「元概念」——**不補一段故意降級的語料**（那等於為了量測留一個缺口）。

## 356 · CI 的 npm ci 不跑安裝腳本、只重建 esbuild（0da69330）

- 轉變：`tree-sitter-cli` 的安裝腳本要從 GitHub releases 下載執行檔；那一分鐘 504，三次重試都一樣（npm 登錄庫是好的），一整輪 CI 作廢、promote 被跳過。
- 改成：deploy 的五處 `npm ci --ignore-scripts` ＋ `npm rebuild esbuild`。理由：這條流程用的是 `public/` 裡收好的 wasm，tree-sitter-cli／tree-sitter-cpp／python 的安裝腳本都用不到；要跑腳本的只有 esbuild。vsix.yml 不改（vsce-sign／keytar）。
- 量到的：下一輪 CI 的 npm ci 6～7 秒、第一次就過。同一天本機的新 worktree 也撞到同一個 504，用同一行裝好（upgrade-cella 的 358）。
- 理由也寫在 `.github/workflows/deploy.yml` 的那段註解（重試那一段之後）。

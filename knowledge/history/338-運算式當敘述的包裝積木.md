# 338 · 運算式當敘述的包裝積木

> 日期：2026-11-04
> 轉變：沒有敘述形態的運算式（`cc[1];`、`(c ? A = 1 : A = 0);`）在敘述位置不再「放在旁邊」，而是套上語言宣告的包裝積木、接在原位；抽回時拆掉，語意樹不變。
> 做法：spec 214（`specs/214-expr-stmt-block/`），第 263 刀。接續 [337](337-換形態判決不變第一層.md) 釘住的那一族。

## 為什麼

2026-09-10 決定接不上語句鏈的積木**不丟、不硬接、放在旁邊**——那解決了「畫得出來」（硬接會讓 Blockly 拒絕整個工作區）。
而「換形態，判決不變」第一次量到它的代價：放在旁邊的積木抽回來是程式的最外層，那一行跑到 main 外面，翻給 Cella 時翻不出。

## 怎麼做

- 降級積木的登記處（`core/blocks/degradation-blocks.ts`）多一格 `expressionStatement`：**名字由語言宣告**（`cpp_expression_statement`、`python_expression_statement`），核心只提供機制。
- 渲染敘述鏈時，運算式形態的積木套上包裝再接；抽取時拆掉；空的包裝不產節點（還沒寫完）。
- 包裝**不是元件**：它不在語意樹裡，只是「這個運算式被當成一行」在積木上的樣子。為每一顆運算式元件加敘述形態不可行——什麼運算式都可能被當敘述用。

## 順手修的

學生語料剩下的第三支（`basic/14_array_1`）不是這一族：`for (int* offset = begin(number); …)` 的第一格是指標宣告，而 `pointer_declare` 沒有運算式形態，在 `for` 的 INIT 被降級成原文積木。
補上與 `cpp_var_declare_expression` 同形的運算式形態。

### 排版提示走一趟積木就被改寫（同一刀，查證 337 留下的「抽取時丟屬性」清單）

靜態掃描列了 15 個「積木上沒有一格」的屬性，8 個（Serial／EEPROM／WiFi 的接收者）在 337 用 `fixed` 修了；剩下 7 個實測：
`include` 的引號、`for` 第一格的初始化寫法都有抽取策略接住；**真的丟的是四個「排版提示，不給學生編輯」**——
`v.emplace_back(1)` 走一趟積木變 `push_back`（`int &r = v.emplace_back(1)` 變成取 void 的值；多參數時不合法）、`s.emplace` 變 `insert`、
Python `{x for x in xs}` 變 `[x for x in xs]`（集合變串列——行為變了）、`enumerate(xs, start=1)` 變 `enumerate(xs, 1)`。

判定本身是對的（拼法不該看起來像語義選擇），缺的是**它住在哪裡**：判定說「不給學生編輯」，而沒有任何地方記著它。
修法：`renderMapping.hints`——渲染時放進 `extraState.hints`（Blockly 由 `preserveForeignExtraState` 原樣保住，行末註解走的也是這條），抽取時讀回。積木外觀不變。

## 量到的

學生語料 218 支（8 支原本就翻不出）：(a)(b)(c) 三種轉換 **全部 0 不同**（spec 213 時 (c) 是 3）。

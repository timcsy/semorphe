> 日期：2026-08-18　spec 140（階段 6.15）
> 上游：[history/082](082-擴充長成能用的而一個缺口只在大家都不那樣寫的地方.md)（spec 139）
> 起點是使用者的一句話：「**你有聽懂我要什麼嗎？我要的是像網頁版那樣的面板，越像越好，只是文字編輯的部分交給 IDE**」

## 轉變


## 一、🔴 起點的錯不在實作，在**規格的框架被沿用了**

spec 138 的性質是**否證**（問「畫布跑不跑得動」），所以它需要儀表——那是對的。
⚠️ 而我把那個框架整個帶進了 139：驗收全部寫成可量測的數字，
於是產出**完美符合我自己寫的規格，而不符合使用者要的**。

> **一份把「怎麼證明它對」寫得很好的規格，可以完全不描述「它該長什麼樣」。**

## 二、抽象的產出是「少了多少」，不是「多了什麼」

`CodeView` ＋ `HostProfile` 兩個介面（約 320 行）換掉了約 1000 行重複。

> **一次抽象如果沒有換掉任何資料，它換掉的是「誰有權知道什麼」
> ——而它的產出常常是【少了多少】，不是【多了什麼】。**

而**同步邏輯刻意不抽**（使用者拍板走「兩份並存」）：擴充那側的同步性質真的不同
（跨行程、非同步、有外來變更），硬合成一份會做出一個兩邊都不好用的抽象。
⚠️ 那是一個**已知的重複**，標記在程式碼裡，不是沒有人知道的。

## 三、🔴 而真正的代價在交付之後：使用者連續七次回報，我修了七次

每一次都「修好了」，而下一次的症狀往往是**上一次的修法造成的**。

> **每一條都不會拋錯，而且每一條都讓「壞了」看起來像「正常」。**

## 四、🔴 而最貴的一課是關於**方法**，不是關於程式

前四次我都是**看截圖推理 → 改 → 交付**。第五次使用者說「還是一樣」時我才承認：

> **一個沒有紀錄的系統，只能被推理；
> 而推理出來的修法，要靠下一次災難來驗證對不對。**

換了做法之後才收斂：

```
① 讓後果變小   安全網：一次同步不得刪掉大半個檔案
② 讓證據留下   寫入流水帳、鏡像對帳指紋、載入失敗的訊息與堆疊
③ 讓錯誤出聲   刪掉那個 `catch {}`
```

而第 7 條（真正的根因）**是推出來的**——但那是在①②③之後，
手上已經有「檔案怎麼一步步變壞」的完整形狀時才推得出來。

## 五、模擬環境的三層天花板——**每一層都讓一個真的缺陷變綠**

```
① 只記訊息的假宿主   驗得到「有沒有送」，驗不到「收不收得下」   → 版本差一
② 會回話的假宿主     驗得到協定，驗不到宿主【怎麼實作】那個協定  → Range 翻譯
③ Chromium ≠ Theia   同一份檔案內容，一邊 9 顆積木一邊 TypeError
```

> **一個模擬環境驗得到「我送了什麼」，驗不到「對面怎麼處理」。**

🟢 而處置不是放棄模擬，是**讓兩邊用同一個函式**（`applySpan`）
——沒有第二份翻譯，就沒有第二份規格。

## 六、順帶記下的小坑（各自付過一次時間）

- **Theia 的解壓快取以「名字」為鍵**：`deployedPlugins/<名字>/` 不含版本，
  覆蓋 vsix 不會重新解，而它不報錯。差一點讓使用者測到四個版本以前的東西。
  → `npm run install:ide`。
- **樣板字串裡的反引號**一天切斷三次 → 假宿主搬進真的 `.js` 檔。
  **處置不是小心，是讓它不再是字串。**
- **掃原始碼的檢查會掃到自己的註解**（文件裡的反例讀起來與真的違規一樣）
  → 先去掉註解再掃。
- **機械地壓掉型別錯誤**（`mobileTabBar!`）＝把它從編譯期搬到執行期。

## 🟢 後續：最後一條驗收在同一天結清

「`.ino` 改完之後 **Arduino IDE 編得過**」——這條從 spec 138（階段 6.13）掛到今天，
2026-08-18 使用者回報**編得過**。

⚠️ 它值得單獨記一筆，因為它問的東西與其他驗收**不同類**：
其餘的問「畫面對不對／檔案有沒有跟著變」，而它問的是
**產出的是不是真的程式碼，而不只是看起來對的文字**。

> **一個雙向投影系統最後一道驗收，不在它自己身上——
> 在下游那個不認得它的編譯器身上。**

## 🟡 那個 `indexOf` 的下場：**停止復現，而不是證明修好**

修好第 7 條（宿主自己翻譯行範圍）之後，使用者回報 `indexOf` 也不再出現。
最可能的解釋是它是**下游**——檔案被寫成錯位的形狀 → lift 出畸形的樹 → Blockly 載不動。

🔴 **而那是推論，不是量到的。** 它從來沒有在 Chromium 重現過，
所以**沒有一個會紅的檢查在守它**。

> **一個症狀在上游被修好之後消失，是證據，不是證明——
> 而兩者的差別在於：下一次它回來時，有沒有東西會先出聲。**

⚠️ 所以結案的是**追查**，不是**保證**。留下來的不是一句「已修復」，是兩道防線：

```
isolateFailingBlock   再發生時直接指出是哪一顆積木 ＋ 它的 extraState
isStateStale          殘的工作區不得覆蓋程式碼（後果不會是「檔案沒了」）
```

🟢 而追查本身的收穫是方法上的：三個假設全錯之後才換掉做法。
**排除三個假設用掉的時間，比做那個隔離器還多。**

# 005：從「禁止 Pattern 歧義」到「註冊時偏序仲裁」

> 日期：2026-03-09

## 轉移

- **舊**：P3 的規則是「如果兩個 pattern 可能匹配同一個 AST 節點，系統必須在註冊時偵測到歧義並**報錯**」。一刀切禁止。
- **新**：歧義依 constraints 集合的**偏序關係**分三種情況處理：

```
情況一：偏序可比較（A.constraints ⊂ B.constraints）
  → 安全仲裁：最特化匹配（B 優先）— 這是 DSL 擴充的正常模式

情況二：偏序不可比較（交叉歧義）
  → 無法安全仲裁 → 報註冊錯誤，要求合併為 hand-written lifter

情況三：不相交 → 無歧義，各自匹配
```

## 為什麼變

先是**執行時的事故**推動了「註冊時報錯」這條規則：`c_pointer_op` 的 astPattern 宣告 `nodeType: "unary_expression"` 但 constraints 為空，結果 `++i`（tree-sitter 也分類為 unary_expression）被搶匹配成指標操作。Pattern Engine 按登記順序嘗試，先匹配到的就贏——**新增一個 JSON 就悄悄改變了既有積木的行為**。

這推翻了一個隱含假設：P3 說「只加 JSON 不改既有程式碼」，但沒說「加 JSON 不會影響既有行為」。**禁止歧義比仲裁歧義更安全**成為當時的結論。

但一刀切禁止很快遇到反例：跨套件擴充**本來就應該**能特化既有 pattern（「擴充已有語言模組」是 P3 的正當用途）。若一律報錯，開放擴充就名存實亡。

偏序仲裁是兩者的平衡：**可比較 → 自動仲裁（低門檻）；不可比較 → 強制手寫（高門檻但安全）**。關鍵在於「最特化匹配」是一個**確定性且可預測**的規則，而「按登記順序」不是。

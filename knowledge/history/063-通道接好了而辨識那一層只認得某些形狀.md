# 063　通道接好了，而辨識那一層只認得某些形狀的「少分號」

> 日期：2026-08-14
> 觸發：[history/062](062-把使用者的錯歸進了我們的殘差.md) 的處置做完
> （spec `119`），而**驗證時樣本一換就量不到東西**。
> 本檔記的是**一個被通道問題蓋住的辨識缺口**，不是修了什麼（沒修）。

## 轉變

```
old  「少一個分號」會被 lift 標成 syntax_error——單元測試釘住了
new  🔴 只有【某些形狀】會。而那支單元測試剛好用到了會的那一種
```

## 怎麼冒出來的：e2e 的入口條件擋下了一個假結論

新的 e2e 要驗「少分號 → 程式碼面板出現錯誤級波浪」。第一次跑**紅在入口條件上**：

```
expect(seen.any, '程式碼面板一個標記都沒有 → 這支測不到任何東西').toBeGreaterThan(0)
                                                                    ↑ 0
```

⚠️ **而它紅在對的地方**。如果沒有那條入口條件，紅的會是
「`seen.error` 不大於 0」——而那個訊息會把我推去改**通道**，
但通道是對的，錯的是**根本沒有東西可以送**。

> **一條「量得到東西嗎」的入口條件，擋下的不是失敗，是一個【指錯方向的失敗訊息】。**

## 實測：三種形狀，只有一種被標記

在瀏覽器裡逐一試（`app.currentTree` 走一遍找 `degradationCause`）：

```
A   int x = 1 ⏎ return 0;      → degraded []                    ❌
B   int x = 1 ⏎ cout << x;     → cpp:var_declare/syntax_error   ✅
C   int x = 1 ⏎ int y = 2;     → degraded []                    ❌
```

**而 `tests/unit/core/lift-syntax-error.test.ts` 用的正是 B。**

> **一支測試證明的是「這個樣本會被標記」，不是「這類錯誤會被標記」。
> 而兩者的差別，只有換一個樣本才看得見。**

⚠️ 這與 [history/057](057-缺陷清單只包含被記下來的缺陷.md) 同族：
那次是「清單只包含被記下來的缺陷」，這次是
**「涵蓋率只包含被寫成樣本的形狀」**。

## 第二個缺口：抄回來的原文是 ERROR 節點的文字，不是那一行

瀏覽器實測，積木上真正顯示的是：

```
「這一段程式我看不懂，積木上這塊是照抄原文的：1」
                                            ↑ 只有「1」
```

`lifter` 的 `rawCode` 取的是 `errs.join(' ') || node.text`
——**ERROR 節點的文字優先**，而這裡 ERROR 節點只涵蓋 `1`。

**技術上正確，教學上沒有用。** 而整行 `int x = 1` 反而在 `node.text` 裡。

> **一個「原文照抄」的通道，抄回來的東西有沒有用，
> 取決於「原文」的邊界是誰畫的——而那個邊界是解析器畫的，不是我們。**

## 為什麼兩個都不在 spec `119` 裡修

`119` 的 Out of Scope 第一條逐字：「**不動 lift**：`degradationCause: 'syntax_error'`
仍然標在同一個節點上。本輪改的是**顯示與計量的通道**，不是樹。」

**那個界線是對的，而它讓這兩個缺口第一次現形**——
通道接好之後，「送過去的東西夠不夠用」才變成一個可以問的問題。

⚠️ 而 `119` 的 e2e **把挑樣本的理由寫在註解裡**，
不是靜靜換一個會過的樣本。

## 出口條件

- **A 與 C 的形狀被標記** → 「少分號」從「某些形狀」變成「這類錯誤」
- **`rawCode` 的邊界重看** → 決定 ERROR 文字與節點文字誰優先，
  ⚠️ 而那要同時看**殘差通道**的用法（那裡 `unsupported` 的原文是整段，是對的）
- ⚠️ **在此之前不得宣稱「少分號已經處理好了」**——只有 B 那種形狀是

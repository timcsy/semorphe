# 063　通道接好了，而辨識那一層只認得某些形狀的「少分號」

> 日期：2026-08-14
> 觸發：[history/062](062-把使用者的錯歸進了我們的殘差.md) 的處置做完
> （spec `119`），而**驗證時樣本一換就量不到東西**。
> 本檔記的是**一個被通道問題蓋住的辨識缺口**，不是修了什麼（沒修）。

## 轉變

```
old  「少一個分號」會被 lift 標成 syntax_error——單元測試釘住了
new  🔴 只有【某些形狀】會。而那支單元測試剛好用到了會的那一種
```

## 怎麼冒出來的：e2e 的入口條件擋下了一個假結論

新的 e2e 要驗「少分號 → 程式碼面板出現錯誤級波浪」。第一次跑**紅在入口條件上**：

```
expect(seen.any, '程式碼面板一個標記都沒有 → 這支測不到任何東西').toBeGreaterThan(0)
                                                                    ↑ 0
```

⚠️ **而它紅在對的地方**。如果沒有那條入口條件，紅的會是
「`seen.error` 不大於 0」——而那個訊息會把我推去改**通道**，
但通道是對的，錯的是**根本沒有東西可以送**。

> **一條「量得到東西嗎」的入口條件，擋下的不是失敗，是一個【指錯方向的失敗訊息】。**

## 實測：三種形狀，只有一種被標記

在瀏覽器裡逐一試（`app.currentTree` 走一遍找 `degradationCause`）：

```
A   int x = 1 ⏎ return 0;      → degraded []                    ❌
B   int x = 1 ⏎ cout << x;     → cpp:var_declare/syntax_error   ✅
C   int x = 1 ⏎ int y = 2;     → degraded []                    ❌
```

**而 `tests/unit/core/lift-syntax-error.test.ts` 用的正是 B。**

> **一支測試證明的是「這個樣本會被標記」，不是「這類錯誤會被標記」。
> 而兩者的差別，只有換一個樣本才看得見。**

⚠️ 這與 [history/057](057-缺陷清單只包含被記下來的缺陷.md) 同族：
那次是「清單只包含被記下來的缺陷」，這次是
**「涵蓋率只包含被寫成樣本的形狀」**。

## 第二個缺口：抄回來的原文是 ERROR 節點的文字，不是那一行

瀏覽器實測，積木上真正顯示的是：

```
「這一段程式我看不懂，積木上這塊是照抄原文的：1」
                                            ↑ 只有「1」
```

`lifter` 的 `rawCode` 取的是 `errs.join(' ') || node.text`
——**ERROR 節點的文字優先**，而這裡 ERROR 節點只涵蓋 `1`。

**技術上正確，教學上沒有用。** 而整行 `int x = 1` 反而在 `node.text` 裡。

> **一個「原文照抄」的通道，抄回來的東西有沒有用，
> 取決於「原文」的邊界是誰畫的——而那個邊界是解析器畫的，不是我們。**

## 為什麼兩個都不在 spec `119` 裡修

`119` 的 Out of Scope 第一條逐字：「**不動 lift**：`degradationCause: 'syntax_error'`
仍然標在同一個節點上。本輪改的是**顯示與計量的通道**，不是樹。」

**那個界線是對的，而它讓這兩個缺口第一次現形**——
通道接好之後，「送過去的東西夠不夠用」才變成一個可以問的問題。

⚠️ 而 `119` 的 e2e **把挑樣本的理由寫在註解裡**，
不是靜靜換一個會過的樣本。

## 🔴 第三個缺口，judge 掃出來的：那個標記分不出是誰的錯

`src/core/lift/lifter.ts:314-317` 逐字：

```typescript
private determineDegradationCause(node: AstNode): DegradationCause {
  if (node.type === 'ERROR' || this.hasErrorDescendant(node)) {
    return 'syntax_error'
  }
```

**唯一的訊號是「tree-sitter 產生了 ERROR 節點」**，而那有兩種來源：

```
① 真的寫錯了          使用者的問題        ✅ 該紅
② 合法而文法不涵蓋    🔴 我們解析器的問題  ← 現在也顯示成紅色「你的語法不完整」
```

⚠️ **這正是 [history/062](062-把使用者的錯歸進了我們的殘差.md) 的錯格【反過來】**：
那次是「我們的問題被顯示成殘差」，這次是**我們的問題被顯示成使用者的錯誤**。
而 `119` 把它從灰色 Info 加嚴成紅色 Error，**傷害因此變大了**。

### 而 `history/017` 早就寫過這個形狀

[017](017-加嚴一個檢查可能比不檢查更糟.md) 逐字：

> 「**加嚴一個檢查，可能讓事情比不檢查更糟。**
> 一道檢查一旦會『拒絕』，就必須同時回答『被拒絕的東西去哪了』。」

**而 `119` 沒有問過這個問題。** judge 靠「那份 history 是孤兒」才把它翻出來
——⚠️ **一份沒有人引用的教訓，等於沒有寫過**。

### 量了：今天沒有發生（55 段 / 誤標 0）

```
語料   tests/probes/scenario-coverage 的三情境（競賽 27 ／ APCS 18 ／ Arduino 10）
結果   55 段合法程式，被誤標 syntax_error 的：【0 段】
```

**所以風險是結構性的，而不是現行的。** ⚠️ 但**沒有任何東西守著它**
——語料一擴、tree-sitter 一升版，它就可能變成非零而沒有人知道。

→ **提議：把這個 probe 收成護欄（硬性零）**，
入口條件錨在「語料段數 > 40」（合成量）。那正是 017 說的「安全網」。

## ✅ 而第一、二個缺口 2026-08-14 關掉了（spec `121`）

**根因是一句話**：解析器有**兩種**標記錯誤的方式，而我們只認得一種。

```
實體 ERROR 節點   int x = 1 ⏎ cout << x;   ✅ 一直認得
傳播旗標          int x = 1 ⏎ return 0;    🔴 漏掉——而它是【更常見】的那一種
                  int x = 1 ⏎ int y = 2;   同上
```

⚠️ 而本檔原本的說法是「**只有某些形狀**會被標記」——那是**症狀不是根因**。
根因不是「形狀」，是**表示方式**。

> **當一份缺陷清單按「症狀」分類時，同一個根因會看起來像好幾個缺陷。**

- **缺口一（只認得某些形狀）** ✅ 關掉——三種漏分號全過，
  ⚠️ **順帶關掉一格能力邊界**：「少一個右大括號標不出來」那支釘子紅了
  （MISSING 節點也帶旗標）
- **缺口二（原文只有片段）** ✅ 關掉——`rawCode` 一律用節點原文，
  積木上從「照抄原文的：1」變成完整的一行
- **缺口三（分不出是誰的錯）** 🔴 **仍然開著**，而它由第四十三條護欄守著

## 出口條件

- **A 與 C 的形狀被標記** → 「少分號」從「某些形狀」變成「這類錯誤」
- **`rawCode` 的邊界重看** → 決定 ERROR 文字與節點文字誰優先，
  ⚠️ 而那要同時看**殘差通道**的用法（那裡 `unsupported` 的原文是整段，是對的）
- ⚠️ **在此之前不得宣稱「少分號已經處理好了」**——只有 B 那種形狀是

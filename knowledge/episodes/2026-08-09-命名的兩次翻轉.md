# 命名的兩次翻轉

**日期**：2026-08-09（討論跨 08-08 ～ 08-09）
**結果**：[history/032](../history/032-G命名整理-詞彙表就是護欄的輸入.md)（G 完成）
**在建設計理由**：[draft/元件命名重新設計](../history/retired/2026-08-08-元件命名重新設計.md)（已退場）

> **為什麼記這個場景**：兩次翻轉的**理由**比結論有用，而結論一寫進
> `concepts/元件.md` 就會看不出它是被推翻出來的。
> 沒有這份紀錄，未來的讀者只會看到「各套件自理」這個結論，
> 而不知道我先推薦了相反的東西、以及**為什麼那是錯的**。

## 起點：一個看起來很紮實的分類

使用者說想大規模改名，理由是「讓名字漂亮一點，不像雜亂無章」。

我量了 177 顆，分成四堆，回報：

> ① 通用化零風險 40｜② 需語義參數軸 42｜③ 不該通用化 **67**｜④ 已經對了 28
>
> 「③ 有 67 顆（38%）不用動——這是好消息，大部分不必碰。」

那份報告有顆數、有分族、每一族附理由。**它看起來與查證出來的一模一樣。**

## 翻轉一：「用假設我們已經支援多種語言的處境再看一次」

使用者只說了這一句。那堆分類當場垮掉：

| 我判「C++ 特有」 | 我當時寫的理由 | 三語言在場時 |
|---|---|---|
| `try_catch`／`throw` | 「catch 型別是 C++ 的」 | Python `try/except`、JS `try/catch`。**catch 型別是參數不是身分** |
| `lambda` | 「capture 是 C++ 的」 | Python lambda、JS arrow |
| `range_for` | 「介面是 C++ 的」 | Python 的 `for x in xs` 是**主要**迴圈 |
| `printf` | 「格式字串是 C 家族特有」 | Python 的 `%` 格式化**就是從 C 繼承的** |

至少十幾顆，而錯的方向**一致**：**只看得到 C++ 時，什麼都像 C++ 特有的。**

### 這一次錯的機制與以往不同

專案裡「量測工具第一版會安靜地量錯」已有八個實例，但那些都是**工具**錯
（入口用錯、粒度太粗、詞義錯、判準對但自動化錯）。

這一次**工具沒錯**——是我沒有第二個樣本可查，於是**用內省填了答案**。
而內省產出的分類表，看起來與查證產出的完全一樣。

→ 教訓進了 `experience.md`：「只有一個樣本時，別問『這個通用嗎』」。

## 中間：使用者連續給了四個重構，每一個都打掉前一個

| 重構 | 打掉了什麼 |
|---|---|
| 「通用不是大家一樣，是彼此能轉換」 | 打掉「要有一個絕對元件／正規名字」 |
| 「這讓我想到內涵相等與外延等價」 | 打掉「合併合法 ⟺ 拆得回來」 |
| 「損失有時無關緊要，取決於精度要求」 | 打掉「無損」的布林形式 |
| 「都在於回饋、殘差、開放系統」 | 打掉「結構性／累積性」是損失的兩類 |

這一串產出了 `concepts/等價與觀察集.md`。**值得注意的是它們的形狀都一樣**：
每一次都是把一個我當成「東西的性質」的判斷，改成「關係的性質」或
「環路的性質」。

## 翻轉二：我在剛立完概念的下一則違反了它

概念寫完之後，我推薦 **(B)：全部 `lang:`，語言特定性當資料**，
理由是「它沒有問那個問不了的問題」。

使用者說：不要用 `lang` 統一，**各自語言處理好自己的，然後再寫轉換規範**。

而他是對的，理由比我當時想的硬：

> (B) 只是把決定延後。Python 進來那天仍要對每個構造問「這是既有的還是新的」
> ——那**還是身分決定**，不可撤回，而且需要知道既有的 177 顆。

**而我剛寫進 `concepts/等價與觀察集.md` 的那條就是**：外延等價可以收回，
內涵身分收不回。`lang:` 那個大桶**仍然是在身分層做宣稱**，我只是把桶做大到
讓那個宣稱看起來無害。

> **同一個判斷，放在身分層是承諾，放在轉換層是觀察。**

### 一個推薦錯的時候沒看到的技術優點

| | 在 C++ 編輯 → 顯示 Python |
|---|---|
| (B) 共用詞彙 | C++ →共用（有損）→ Python（有損）＝ **兩段有損** |
| (D) 各套件自理 | C++ → cpp 樹（**無損**，恆等變換）→ Python（有損）＝ **一段有損** |

### 而它根本不是改方向

**177 顆裡 145 顆已經是 `cpp:`。** 專案一直在做 (D)，只是沒說出口。
那 32 顆 `lang:` 才是異例——**我原本建議把 82 顆搬去 `lang:`，方向正好相反。**

## 第三次（同一輪）：共用積木是同一個陷阱換了一層

我提議「積木共用，掛在轉換類別上」。使用者說不對——**類似功能的積木有類似的
使用方式**，但積木各語言各自。

我在前一則才指出：`impl: vector|deque|list` 是陷阱，因為那是
「只有某個語言會填的槽寄生在共用的東西上」。**然後我在積木層又做了一遍。**

認不出來是因為陷阱的特徵在原層有名字（`impl` 參數），換層之後那個名字不見了，
剩下的是「共用一顆積木」——**聽起來像優點（減少重複），而不像陷阱**。

→ 與層無關的版本進了 `experience.md`：
**共用的東西不得包含只有部分成員會用到的槽。**

## 執行期：護欄第一版誤報 84 顆

量測時數到 ~35 顆裸的函式庫名，護欄卻報 84。三個原因，第三個最值得記：

1. 主體清單不全
2. 缺「語言構造 vs 函式庫函式」的判準（`switch` 可以是單字名，`strlen` 不行）
3. **我自己剛寫下的規則③（主體在前）被 `count_loop` 違反了，而我沒有檢查它**

第 3 點的機制特別：它**不產生奇怪的數字**——那些迴圈被歸進了「裸的函式庫名」，
所以症狀是**別的類別**多報。

→ 教訓進了 `experience.md`：**一條新規則落地時，第一件事是拿它掃一遍現有的資料。**

## 收場

六輪改名，六次存檔遷移（v3 → v9），六項驗收全部歸零並收硬性零。

而回頭看，**最貴的不是改 3000 處字串**——那有工具。最貴的是
**在只有一個樣本的時候，我對著 177 顆做了一份看起來很紮實的判斷**，
而它要靠使用者的一句話才垮。

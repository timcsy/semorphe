# 四次整批回退——而兩次的真因不在被搬的元件身上

> 2026-08-11，F 膠囊搬家 167 → 0 的過程中。17 批成功、**4 批整批回退**。
> 這一則記的是那四次的完整判斷過程——**因為其中兩次我的第一個診斷是錯的**，
> 而錯的方式值得被記住。

## 為什麼「整批回退」是預設處置

批次搬家一次動 3～6 顆元件，跨十幾個共用檔。失敗時可以選：

- **逐顆回退**：留下已經成功的部分
- **整批回退**：全部還原，重做

這一輪固定選後者，理由是第一次失敗那天學到的：**部分回退會產生一個
「看起來完成、而某條路斷掉」的狀態**，而護欄的數字會下降（因為未膠囊化少了幾顆），
於是**下一批會建立在一個壞掉的基線上**。

---

## 第一次：OPP 六顆——真因是我自己

**症狀**：六顆元件的身分仍然洩在三個共用檔裡，看起來像「這一批同時被三個
消費者依身分分派，解一個不夠」。

**我的第一個結論**：這六顆卡在一個結構問題上，需要三個機制。

**而那是錯的。** 真因是：我在批次中途跑了

```
git checkout -- src/languages/cpp/core/generators/statements.ts
```

去修一個壞掉的閉包提升——**那把同一批已經剪掉的產生器一起還原了**。

它們其實只被**一個**消費者依身分分派（`structs.ts` 的 `拆解成員`），
另外兩處是**本來就該剪走的 `g.set` 與 `createNode`**。

> **一次批次改動中途做 checkout，會把同一批已完成的部分一起還原**，
> 而症狀看起來像「這一批本來就搬不動」。

**改法**：前置重構**單獨 commit**，批次期間不碰任何共用檔的既有內容。
之後 17 批都照這個順序，沒有再犯。

---

## 第二次：ternary 五顆——真因在**別人**身上

**症狀**：`x += 5` 辨識不出 `cpp:var_assign_compound`。

**追查**：九個建立點逐字對照過、lift 的產出也驗過是正確的。
問題在 pure-JSON 那條路——`cpp:pointer_assign` 與 `cpp:var_assign_compound`
的 astPattern **都認 `assignment_expression`、都宣告 `constraints: []`**，
於是誰贏由陣列順序決定。

而 `pointer_assign` 的手寫分支明明寫著：

```ts
if (op !== '=' || left?.type !== 'pointer_expression') return null
```

**它其實有條件，只是宣告裡沒說。**

在共用檔裡 core 排在膠囊前面所以一直沒事；`var_assign_compound` 一搬進膠囊，
glob 的字母序（`pointer_assign` < `var_assign_compound`）就把它翻掉。

> **一個少報約束的宣告，會讓一顆比它一般的元件搶走它的語法。**

**改法**：補上那條約束（**改的是另一顆元件**），這一批就一次過。

---

## 第三次：if_else + 四顆——越補越多

**症狀**：`cpp:if_else` 的產生器**就是 `cpp:if` 的產生器**——一個捕捉 `style`
的閉包，內部遞迴時還提到 `'cpp:if'`。

**判斷**：可搬性第 5 條（五路實作是另一顆元件的別名）。

**而我先試著中途把 if_else 抽掉、手工還原它的宣告與積木**——結果越補越多：
`universal-concepts` / `universal-blocks` / labels / 清冊各一處，每補一處
就冒出新的一支紅。

> **回退整批比留一個半成品便宜**——這是這一天第二次證實它。

**改法**：`ifGeneratorFor(style)` 提升為模組層級（**同一個檔案裡的第三個**閉包提升，
前兩個是 `openBrace` 與 `formatParams`），下一批 `if` 與 `if_else` 都進去了。

---

## 第四次：var_declare——這次不是為了紀律

**症狀**：`declaration-change-parity` 報一筆差異。
⚠️ **那是對照組不是棘輪**（它不准變）：

```
class C { public: int x; private: int y; protected: int z; };
                                 ^^^^^ 產出變成 int x;（三個成員全部）
```

**我當下沒有定位到**，於是回退並在 commit 裡寫明「問題在投影那一側，
而我沒有找到」。

**下一輪用二分法找到了**：
- 只做「`createNode` → 建構子」那一半 → **綠**
- 只做 `mk.剪一顆`（把 blockDef 搬進膠囊）→ **紅**

於是問題在 blockDef 的移動。再看膠囊的 `forms/blocks.json`：

```
cpp_var_declare_expression   ← 批次工具把變體排在前面
cpp_var_declare              ← 中性
```

`BlockSpecRegistry.loadFromSplit` 的註解寫著「第一個勝出——後者覆寫的話，
改變 JSON 順序就會改變行為」。**那句話擋住了覆寫，而沒有擋住
「中性的那一顆排在變體後面」。**

> **「第一個勝出」只在「該贏的那個排第一」時才是規則，
> 否則它只是把順序偽裝成規則。**

**改法**：不是把那個檔排好，是**讓輸入順序不再有影響**——`loadFromSplit`
先把中性形態排到前面。**故意把 JSON 排成亂序驗證過**，仍然綠。

---

## 這四次共同教會的

1. **第一個診斷可能是錯的，而錯的方式是「把自己的操作誤讀成系統的性質」**
   （第一次）。
2. **真因可能在別的元件身上**（第二次、第四次）——搬 A 失敗，改的是 B。
3. **回退的門檻不是「修不好」，是「留著會不會讓下一批建立在壞掉的基線上」**
   （第三次），或**「留著會不會改壞使用者的東西」**（第四次）。

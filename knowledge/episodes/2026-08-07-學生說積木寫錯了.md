# 2026-08-07：學生說 stack 和 queue 的 push 積木寫錯了

> 這一則之所以值得留，不是因為那個 bug 有多大，而是因為**它是這條線上第一個真實使用者的證據**。
> 協定、五槽、命名空間、膠囊——全部來自第一原理推導與跨專案協商。那些都是好論證，
> 但它們都沒有被真人打過臉。

## 現場

一名學生跟使用者反應：**stack 和 queue 的 `push` 意思不一樣，所以他覺得積木寫錯了。**

使用者的反應是「我覺得有道理，但還來不及改」。

在對談中這件事被重新提出來，當時的脈絡是相反的方向——AI 正在主張把
`cpp_container_push` **維持統一**（因為 stack 與 queue 的 push 行為相同），
而使用者用這個學生回報反駁。

## 查證：兩邊都對，但對在不同的層

**執行器完全不分支：**

```ts
register('cpp_container_push', async (node, ctx) => {
  …
  arr.value.push(val)      // stack 與 queue 走同一行
})
```

行為完全相同 → **身分是對的**，不該拆成 `stack_push` / `queue_push`。

**但標籤說謊了：**

```
CPP_CONTAINER_PUSH_MSG0     "推入 %2 到 %1"  /  "Push %2 onto %1"
CPP_CONTAINER_PUSH_TOOLTIP  "將值推入容器"
```

**英文的 “onto” 字面就是「放到…上面」——那是堆疊的語義。**
佇列的元素不是放到誰上面，是排到後面去。中文的「推入」中性一點，但一樣**沒說放到哪裡**。

而同一個檔案裡，vector 那顆的標籤**反而寫對了**：

```
CPP_CONTAINER_PUSH_BACK_MSG0  "在 %1 尾端加入 %2"  /  "Append %2 to %1"
```

**它說了「尾端」。** 所以這個專案知道怎麼寫好標籤，只是共用的那顆沒寫。

## 診斷：身分對，形態說謊

學生感覺到的不一致是真的，只是**根因不在他以為的地方**——他以為積木寫錯了，
其實是**標籤寫錯了**。而那個錯誤剛好落在所有既有檢查的外面：

| 檢查 | 會不會叫 |
|---|---|
| 執行測試 | ✗ 行為是對的 |
| 來回轉換 | ✗ 產出的 C++ 是對的 |
| 五路完備性 | ✗ 五路都在 |
| 就近性／中立性／語法耦合 | ✗ 與它們無關 |
| **使用者** | ✓ |

## 解法：一個身分，兩個形態

```
component: container_push          ← 一個身分（執行器就是一份）
  forms:
    block:
      stack:  「推到 %1 的頂端」
      queue:  「加到 %1 的尾端」
```

- 積木上看起來是兩顆，標籤各自說清楚元素跑到哪 → 學生的困惑消失
- toolbox 可以分別掛在 stack 與 queue 分類下 → 找得到
- 執行器仍然是一份 → 不會有兩份會漂移的實作
- **圖鑑顯示一個概念、兩個投影** → 教的是真的東西

### 為什麼不拆身分

拆成 `stack_push` / `queue_push` 之後，會被迫接著拆 `pop`、`top`/`front`
——**六顆元件，差別只有一個屬性**。而且 LIFO/FIFO 這個性質會**同時寫在容器和每個操作上**。

**紀律應該住在容器裡（一次），不是散在每個操作上（六次）。**

這與 `*_declare` 那兩組（`var_declare` 家族 6 顆、`stack/queue/set_declare` 3 顆）
是同一個判準——見 [元件身分健檢護欄](../../tests/integration/audit-component-identity-review.test.ts)。

## 為什麼這一則要留

**所有內部論證都自洽，而沒有東西能證偽「這樣好教」。**

查了一下，`semorphe/knowledge/` 裡**沒有任何一則來自實際學習者的回報**——
而這個專案的 telos 是教育。ArduinoCAD 那邊反而有（那個 repo 的 `knowledge/episodes/005-TinkerCAD-接線手感迭代.md`，UX 手感迭代）。
⚠️ 這裡**刻意不寫成連結**：它在另一個 repo 裡，而一條指到 repo 外面的連結，
它的死活取決於**讀的人那台機器上有什麼**——2026-09-01 它讓 CI 紅了一次。

那是知識庫的一個真實破洞，而且是最貴的那種。

## 結局（2026-08-07 當日）

修好了，走的正是上面推的那條路——**一個身分，兩個形態**：

| 積木 | 學生讀到的字 |
|---|---|
| 堆疊 | **推 %2 到 %1 的頂端** |
| 佇列 | **加 %2 到 %1 的尾端** |
| 堆疊 pop | 從 %1 的頂端移除 |
| 佇列 pop | 從 %1 的前端移除 |

執行器**仍然只有一份**，產出的 C++ 完全相同。元件數 181 → 181。

規格 `specs/097-multi-form-projection/`，決策轉移見 [history/027](../history/027-A項多形態機制從阻斷變成解除.md)。

### ⚠️ 但這一則還沒有真正結束

**沒有人拿去問過學生。**

機器驗得到的是「字串裡有沒有『頂端』兩個字」；驗不到的是**讀了之後知不知道 pop 會拿到什麼**。而那正是這一則存在的理由——**這個困惑是一個人回報的，也只有人能確認它消失了**。

`specs/097-multi-form-projection/tasks.md` 的 T038 標著未執行。**在有人驗過之前，這一則的狀態是「我們認為修好了」，不是「修好了」。**

# 使用者叫我修的那個不是缺陷——而追下去的那個更嚴重

**日期**：2026-08-21 ｜ **commit**：[`ec5f4c9e`](../../.git) `fix(cin): 失敗會黏住`
**支撐的教訓**：待收（見本篇「留下什麼」）

## 為何（why）

前一刀（spec 173）把 Python 的 `input()` 修成會等使用者。我在結案的摘要裡
順手記了一筆**沒修的**：

> ⚠️ 順帶記下一筆**沒修的**：C++ 的 `cin` 在沒有輸入時**靜默回 0**
> ——同一個位置的另一個病，而它不在這一刀。

使用者回：「順便把 C++ 那個靜默回 0 也修掉」。

## 怎麼（how）——三次「我以為」被量測推翻

### ① 「靜默回 0」不是缺陷

```
if (raw === null) return { type: 'int', value: 0 }
```

我把它讀成「讀不到就給變數一個 0」。**不是。** 那是 `cin >> a >> b` 的
**回傳值**——讀成功幾筆。`while (cin >> x)` 正是靠這個 falsy 的 0 終止的。
**動它會炸掉 C++ 最常見的讀到底慣用法。**

分辨它的方法不是再讀一次程式碼，是**跑三段探針**看輸出。

### ② 「C++11 說失敗時要把變數設成 0」——條文對，量測不對

我準備照 C++11 §27.7.2.2.3 把變數設成零值。先跟參照編譯器對一次：

```
printf '' | ./d     →  a=9 fail=1      ← 變數【沒動】
echo "abc 5" | ./e  →  n=0 fail=1      ← 變數【設成 0】
```

Apple clang / libc++ 在 EOF 時 `sentry` 就失敗了，轉換根本沒跑，所以變數不動；
格式不符時 `num_get` 跑了而失敗，才 value-initialize。
**同一份標準，兩種情境，兩種結果——而我原本要寫的是一種。**

### ③ 真正的缺陷在旁邊一行，而它更嚴重

C++ 的 `>>` 一失敗就設 `failbit`，之後每一次 `>>` **立刻失敗**直到 `clear()`。
本專案每次都當作全新：吞掉壞掉的 token、給變數一個 0、**繼續讀下一個**。

| 輸入 | 真 g++ | 本專案（修前） |
|---|---|---|
| `cin>>n; cin>>m;` ← `abc 5` | `n=0 m=7` | `n=0` **`m=5`** |
| `while(cin>>x)` ← `1 abc 3` | 跑 **1** 圈 | 跑 **3** 圈 |

第二條是競賽課最常見的慣用法，而**中間沒有任何東西出聲**。

### ④ 護欄自己弄紅了別人

第一版護欄在每支 `it` 裡用 `runCppDetailed`（`execSync`）各跑一次 g++。
全套跑起來 `bus-update-not-user-edit` **每輪紅不同支**；那個檔單獨跑是綠的，
乾淨樹全套也是綠的。`execSync` 阻塞整條 Node 執行緒，把時間敏感的測試
推過門檻。改成 `beforeAll` 一次批次（`exec`，有並行上限）之後穩定。

⚠️ 值得記的是**我怎麼確認的**：不是猜，是 `git stash` 之後全套跑一遍
——「乾淨樹 4981 全綠 vs 我的樹紅一兩支」才把「本來就浮動」這個藉口排除掉。

## 結果

十條護欄（每條對照參照編譯器）、`cin` 的 failbit 黏著、`readCinToken` 跳過空行、
`getline` 會等使用者且看得到同一條流的失敗。4992 綠、連續兩輪零紅、瀏覽器實按。

## 留下什麼（待人確認後寫進 experience）

1. **一個回傳值不得同時是合法結果與失敗的代號**——那時「它到底失敗了沒有」
   在程式裡沒有地方可以問。這是「[靜默降級是 bug 的藏身之處](../experience.md)」
   的更深一層：不是回退**掩蓋**了缺陷，是**失敗這件事根本沒有被表達**。
2. **一支自己會過的測試，可以只因為它佔住執行緒的時間而弄紅別人**
   ——而那時紅的是別人，沒有人會來查這一支。
3. **標準條文不是量測**：同一份標準在兩種情境下給出兩種結果，
   而條文讀起來像一種。

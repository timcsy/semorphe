# 護欄自己量錯了兩次——而抓到它的不是 code review

> 日期：2026-08-06

## 為何值得回憶

教訓已經蒸餾進 [經驗](../experience.md)（「量測工具的第一版會安靜地量錯」）與 [concepts/執行機構](../concepts/執行機構.md)（「執行機構自己也可能是殼」）。

這裡留的是**現場**——因為那條教訓的難處不在道理（誰都同意工具會出錯），而在**你怎麼知道自己現在正在看一個錯的數字**。兩次都不是靠讀程式碼發現的，而那個「怎麼發現」才是會救人的東西。

## 場景

`specs/049-audit-guardrails`：為 Semorphe 蓋四條審計護欄，量出碎裂、殼、條件性正確的基線。整個功能的立論是「規範沒有機械化的檢查就是裝飾」。

於是有一個很尷尬的處境：**我正在蓋的東西，就是那條規範的檢查本身。** 如果它量錯了，錯誤會以「權威數字」的形式進入知識庫、進入路線圖、進入後續每一期的決策。

它確實量錯了。兩次。

## 第一次：84 個假的缺

完備性護欄要判定每個元件的 render 路徑是實作／殼／缺。第一版用 `renderToBlocklyState()` 當入口，跑出來的結果是：

```
generate  殼 4 ｜ 缺 0
lift      殼 34 ｜ 缺 4
render    殼 84 ｜ 缺 0
extract   殼 0  ｜ 缺 84
execute   殼 54 ｜ 缺 1
```

**數字很大、分佈看起來很合理**——render 84 個殼、extract 84 個缺，甚至有一種「兩者相關，所以應該是對的」的說服力。

真正不對勁的是 **`extract` 是「0 殼 ／ 84 缺」**。那個組合說不通：extract 的判定是「render 產出的積木還原得回來嗎」，如果 render 真的產出了 91 個積木，extract 不可能一個殼都沒有卻有 84 個缺。

追下去才發現：`renderToBlocklyState()` **需要 `program` 外殼、而且只處理 statement**。所有 expression 元件在它手上一律回傳空狀態——那 84 個不是「缺路徑」，是**我用錯了入口**。

改用 `PatternRenderer` / `PatternExtractor` 直接跑之後：

```
render    殼 0 ｜ 缺 0
extract   殼 0 ｜ 缺 0
```

**84 個假的缺全部消失。** 如果沒發現，這 84 個會被寫進基線，然後在後續每一期被當成「要清償的債」去追。

## 第二次：被自己寫的免責聲明救了

兩組態比對（FR-023）要回答「JSON 宣告的 template 與實際跑的東西差在哪」。第一版比的是 **verdict**（實作／殼／缺），跑出來是：

```
（無差異——若這裡是空的，多半是護欄沒接對，見 research.md F2／F3）
```

那句括號裡的話是我**在寫報表時就先寫進去的**——因為研究階段已經查到「app 從來沒接上 TemplateGenerator，93 個概念宣告了 `codeTemplate`」，所以我預期差異一定非空，並把這個預期寫成了報表的一部分。

於是工具吐出「無差異」的瞬間，**工具自己貼的標籤就把這個結果判為可疑**。

原因是 verdict 粒度太粗：兩種組態都產得出「有效輸出」，所以 verdict 都是 `implemented`，看不出差別。真正的差異在**產生的文字**。改成比對程式碼字串之後：

```
35 個元件在兩種組態下的 generate 判定不同：
      cpp_auto_declare   現行: auto x = 1;      宣告: auto x = ${VALUE};
      cpp_compound_assign 現行: x[1] + 1;       宣告: x ${OP} 1;
```

**而且順帶查出一件更糟的事**：那些 template 不只是沒被用，**有些是壞的**——會吐出未取代的佔位符。因為從來沒被執行過，所以沒人知道。

## 兩次的共同結構

| | 第一次 | 第二次 |
|---|---|---|
| 錯誤長什麼樣 | 一個大數字 | 一個空結果 |
| 為何看起來合理 | 分佈有內在關聯 | 「沒有差異」是一種正常結果 |
| 怎麼抓到 | **內部矛盾**：render 全過卻 extract 全缺 | **預先寫下的失效樣態** |

第一次靠的是**領域直覺**——你得先懂 extract 依賴 render，才會覺得那個組合不可能。這種抓法不可靠，它取決於當下夠不夠清醒。

第二次靠的是**制度**——失效樣態在跑之前就被寫下來了，工具吐出結果時，判準已經在那裡等著。**這一種可以複製。**

## 於是那條教訓的形狀

> **給每個量測工具寫一句：「如果結果長成 ○○，代表工具壞了，不是世界長這樣。」**

不是加一層檢查去檢查檢查（無限後退），而是**讓工具自己聲明它的失效樣態**。

同一形狀在這個功能裡還有第三個實例，只是方向相反：完備性護欄的報表固定印出「**本護欄不檢測條件性正確**」。那不是免責，是劃出能力邊界——**一條只抓得到「殼」的護欄若被誤讀成完備性保證，比沒有護欄更危險**。

## 一個不算巧合的巧合

這個功能的立論是「沒有執行機構的規範是殼」。而它自己在實作過程中，**兩次做出了會安靜量錯的執行機構**。

如果連一個以「揪出殼」為唯一目的的功能，都會在自己身上長出殼——那說明這個病不是紀律問題，是**結構性的**：任何產出數字的東西都天生看起來像證據，包括你為了對抗這件事而蓋的東西。

## 第三次與第四次（2026-08-06 晚，`specs/053-declare-noop-execute`）

前兩次是「結果不合理」抓到的。這兩次的**發現方式又不一樣**。

### 兩個量測互相打架

任務是把核心層一份 34 個概念的「無執行行為」清單分類：哪些是真的不執行、哪些是還沒實作。

判準想得很清楚：**概念有子槽，子槽裡是使用者寫的程式碼；若執行器是空的而且沒人去讀那些子槽，那些程式碼就被無聲丟棄了。**

判準是對的。把它自動化的第一版**答案是反的**：

```
自動掃描的結果            已經跑過的實測
──────────────────      ────────────────────────────
cpp_static_cast  → 好    🔴 輸出 0，是壞的
cpp_case         → 壞    🔴 control-flow.ts:129 明明在讀它
```

根因很無聊：把「有沒有人讀子槽」實作成 **grep 概念名**。檔案裡出現這個名字，不等於有人執行它的子槽。

**救它的不是 code review，是半小時前跑過的三筆實測與它矛盾。** 沒有那三筆，這份反過來的分類會直接變成 31 個宣告——而每一個宣告都會讓護欄的數字下降。

> **判準本身可以是對的，把它自動化的第一版仍然會量錯。**

### 測試通過，卻什麼都沒測到

換成實測分類之後，第一版跑出 17/31 通過。看起來很合理。

但裡面有假的：

- `cpp_ifdef` 用「`N` 未定義」測——body 本來就不該跑，**空操作也會給同樣的輸出**
- `cpp_destructor` 用空的解構式測——等於沒測
- 有五列的概念**根本沒出現在語義樹裡**（用 `static_cast` 代測 `dynamic_cast` 之類）

加上一道「這個概念必須真的出現在樹裡」之後，通過數從 17 掉到 **12**。

> **一支斷言「輸出正確」的測試，要先證明它真的執行到了被測的東西。**

### 還有一件事：自我否證聲明自己過期了

那支分類測試寫了自我否證：「已知 `static_cast` 是壞的（實測輸出 0）——它若通過，代表這支測試沒有真的在跑。」

**同一個功能的下一個 Story 就把 `static_cast` 修好了。**

那句話於是變成「叫未來的讀者不要相信一個正確的結果」——比沒有聲明更糟。改成錨在物件導向那十個（直譯器不支援 OOP，本功能也不打算實作）才穩。

> **錨點要挑「這個功能不會修好的東西」。** 一句會過期的自我否證聲明，過期之後看起來與有效的完全一樣。

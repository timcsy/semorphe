# 一個月重現不了的紅——直到陷阱自己說出現場

> 日期：2026-10-02 → 2026-10-31

## 症狀

`e2e/c-target.spec.ts`「使用者自己寫的 `#include`，在 C 目標下也要換掉」間歇紅，收到的程式碼只有 `int main() {`。
⚠️ 簽名不是「等不到畫面」（那一類是忙碌機器的假紅，CLAUDE.md 有判準），而是內容斷言——所以那條判準不適用。

## 一個月裡排除的假說（2026-10-02／03）

```
❌ 等得不夠久        好的那幾輪 110 ms 就對了；壞的那一輪 63 ms 就錯、兩秒內不變
❌ 鷹架深度 0        深度 0 會連 main 一起剝掉，而壞的輸出有 main
❌ CPU 負載          六個燒滿 CPU 的行程 ＋ 8 次，全綠
❌ 輪詢式觀測        每 100 ms 問一次 → 5/5 全綠 ⟹ 儀器本身改變了被量的東西
```

紅過的幾次都在**剛跑完 28 分鐘整輪 e2e 之後**——條件是長跑累積出來的，量它就要再跑一次長跑。
⟹ 不再追，改設**陷阱**：只在失敗時把 target／skeleton／depth／style／元件清單印出來。

## 陷阱說話（2026-10-31，第 392 刀）

```
target c｜skeleton main｜depth 2          ← 全對
ids    cpp:program,cpp:func_def,cpp:return,cpp:literal_number
```

**樹上沒有學生的任何東西**——不是少一個標頭，是那份程式碼從沒進過樹。往回追，三層：

1. **測試（最常發作的那一個）**：只等「編輯器出現」就 `setCode`，而 init 的後段從預設的樹重投影、把編輯器寫回預設程式。
   量到的空窗：編輯器出現後 +15～+104 ms 才做完；那個空窗裡餵的程式碼 4 輪被蓋 1 輪。
2. **產品**：`syncCodeToBlocks` 在解析器（tree-sitter wasm，非同步）接上之前 `return false`。
3. **產品**：同一個函式的下一行 `if (this.syncing) return`——另一次同步進行中也吞掉。

每一條觀察都對得上：機器忙 ⟹ wasm 載得慢、init 做得慢 ⟹ 空窗變長；輪詢讓事件迴圈有機會把事情做完。

## 修了兩次才修完

- 第一次修 ②③（等、不丟）＋ ①的共用 helpers 與兩支 spec——**c-target 在合併前的最後一輪又紅一次**，現場逐字相同。
- 第二次（同一天）量出 init 空窗，`main.ts` 設 `window.__appReady`，所有就緒判準等它。
- 第三次（第 394 刀）：換 `console-comes-back` 紅——它**自己定義了一份 `freshApp`**，第一次只修了共用的那份。
  補齊 6 支自己寫 ready 的 spec，立護欄 `audit-e2e-waits-app-ready`。

## 為什麼值得回放

設陷阱而不是繼續追的判斷是對的：一個月裡所有合成重現都失敗，**自然發作的那一刻才有資訊**。
而「修一個實例」三次都沒修完——直到用護欄掃同形的全部。

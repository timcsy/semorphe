## 為什麼做這一項

前一天（097）使用者拖了一次積木，第一句話是「這樣會不會讓學生困擾找不到積木？」。會——變體做出來了，工具箱裡沒有。那次的修法是兩行，而根因是**工具箱的內容從來沒有人量過**。

蒸餾成一條教訓寫進 `experience.md`，然後——

## 三顆不是「忘了登記」——那個第一直覺是錯的

我原本準備把七顆都加進清單。查 `cpp_getline` 的宣告時發現它的 `category` **已經是 `'io'`**——`cpp_ifstream_declare`／`cpp_ofstream_declare` 也是。

真正吃掉它們的是排序函式：

```ts
const universalIo = ioTypes.filter(t => t.startsWith('u_'))
const cppIo       = ioTypes.filter(t => t.startsWith('c_'))   // ← cpp_ 兩邊都不屬於
```

`'cpp_getline'.startsWith('c_')` 是 **false**。三顆宣告完全正確的積木，被一個分堆邏輯**靜靜地丟掉**。

**症狀與「忘了登記」完全一樣（使用者拿不到），修法完全不同。**

## 而那段邏輯有第二份拷貝，跑了三個月沒人叫

`toolbox-categories.ts` 裡有一份 `buildIoCategoryContents`——與 `toolbox-builder.ts` 的 `buildIoContents` 是同一段邏輯，**沒有任何產品程式碼在用它**（`isIoCategory` 走的是 builder 的預設路徑），只有它自己的單元測試在叫。

那支測試三個月來一直是綠的。**而那份拷貝有一模一樣的缺陷。**

> 一支測著死程式碼的測試，與一支測著活程式碼的，綠燈長得一模一樣。

已刪，測試改成走 `buildToolbox` 的真實路徑，並補一支迴歸釘。

## 「沒有宣告 form」在兩條軸上意思不一樣——七顆最常用的積木消失了

導出的第一版，我把「沒宣告 `form` 而兄弟有多個形態」一律當成**中性退路**排掉。跑完快照比對：

```
【資料】少： u_var_declare
【運算】少： c_increment c_compound_assign
【函式】少： u_func_call cpp_method_call
【輸入/輸出】少： u_input c_scanf
```

**七顆最常用的敘述版積木從工具箱消失。**

原因：`KNOWN_AXES` 有兩條軸，而它們的 `from` 不一樣——

| 軸 | `from` | 沒宣告 `form` 的那一顆是 |
|---|---|---|
| `container_kind` | `property` | **退路**——型別查不到時才用它 |
| `role` | `position` | **敘述版**——一個真正的選項 |

位置永遠知道（它是結構性的），所以 `role` 軸**不需要退路**。判準要看**軸的 `from`**，不是「有沒有 form」。

護欄補了一支反向注入釘住這件事：**沒有它，「所有沒宣告 form 的都是退路」這個錯誤判準會通過中性形態那一支。**

### 而 judge 階段又踩了一次——這次錯的是我

想量「匯出但只有測試在叫的函式」有多少，掃描器報 `generateCode`（384 次測試引用）
是死的。我憑印象判定掃描器壞了、**而且已經對使用者說了那個結論**。

去查之後：**掃描器是對的**。production 走的是 `generateCodeWithMapping`，
`generateCode` 真的零呼叫者——而且兩者是**同一段 setup 的兩份拷貝**。
它是 `buildIoCategoryContents` 的放大版：384 支測試跑在一條 production 不執行的路徑上。

> 「在已知答案的樣本上驗過」——**只有在那個答案是查過的時候才有效。**
> 用記得的答案去驗工具，驗的是記憶不是工具。

## 尾聲：使用者截圖，通用積木整批不見了

E 項 commit、push、judge 反流全部做完之後，使用者打開瀏覽器：
**起始關卡只剩「資料」與「程式設定」兩個分類，沒有任何 statement 積木，整數也不見了。**

根因是我：導出改用 `owner` 比對之後，我建了 `src/blocks/universal.ts` 當蓋章的唯一
入口，**卻只把測試路徑改過去**。`app.ts:130` 與 `module.ts:60` 仍 import 原始 JSON，
於是每個 `{ from: '(universal)' }` 段落在正式路徑上回傳零筆。

**而全套 222 檔全綠。**

這與本檔前面那條 `buildIoCategoryContents` 是同一個病，**隔了三個 commit**——
而且更嚴重：那次是多一份沒人跑的程式碼，這次是**同一份資料有兩條載入路徑**，
測試走對的那條、production 走錯的那條。

三道新檢查，每一道都對應一個「為什麼前面沒抓到」：

| 沒抓到的原因 | 補的檢查 |
|---|---|
| 組裝有兩份 | `all-declarations.ts`——**只留一份**，分歧無法被表達 |
| 漏蓋章不產生違規，只產生**空段落** | 「每顆積木都蓋了 owner 章」 |
| 段落打錯字也只是回傳空陣列 | 「每個宣告的來源段落都必須對得到積木」（第一次跑就抓到我自己宣告的死段落 `(core)/io`） |
| 快照用「全部可見」，少掉的被數量蓋過去 | 快照加**起始關卡**那一段 |

**最後一列是最有價值的**：全部可見的快照結構上看不到這個病。
**快照要釘在使用者實際會看到的狀態上，不是最大的那個狀態。**

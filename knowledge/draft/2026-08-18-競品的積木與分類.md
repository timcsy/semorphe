# 競品的積木與分類（SOTA 調查）

> 2026-08-18　使用者：「去研究一下 SOTA 的競品……參考一下人家的積木和分類如何設計」
> ⚠️ **狀態：調查完成，而三個提案未拍板**

## 為什麼查這個

剛做完階段 6.16，而其中兩個決定是**推導**出來的、沒有外部對照：

```
零件不是身分，是參數        六顆零件 → 一顆接線積木 ＋ device 下拉
開了「零件與模組」那一格      因為「腳位與時間」的名字不再描述它的內容
```

🔴 **而查完之後最有價值的不是「別人怎麼做」，是「別人為什麼做得不一樣」。**

## 一、分類軸有兩派，而沒有人混用

| 產品 | 分類 |
|---|---|
| MakeCode micro:bit | Basic · Input · Music · **Led** · Radio · Game · Images · **Pins** · Serial · Control · Bluetooth |
| MakeCode Maker（Arduino 向） | Loops · Logic · Variables · Math ＋ **Music · Pins · Control · Serial** |
| Open Roberta | **Action · Sensors** · Control · Logic · Math · Text · Colours · Variables · Functions · Messages |
| Tinkercad Circuits | **Output · Input** · Notation · Control · Math · Variables |
| **我們** | 資料 · 運算 · 控制 · 函式 · 輸入/輸出 · …… · **腳位與時間 · 零件與模組 · 序列埠** |

```
子系統軸   MakeCode 與我們     Pins／Music／Serial——照硬體的功能區塊分
方向軸     Open Roberta、Tinkercad   Action／Sensors、Output／Input——照資料流方向分
```

⚠️ **兩派各自自洽，而混用會壞掉**：一顆 `analogRead` 在子系統軸是「腳位」，在方向軸是「輸入」。
🟢 我們是子系統軸，與 MakeCode 同一派——**保持一致比選對更重要**。

## 二、🔴 MakeCode 自己在「servo 該放哪」上翻覆了三次，至今未決

```
PR #125   把 servo 從 Pins 移除
（回滾）   又放回 Pins
PR #333   另外做了一個 Servo extension
結果      兩邊都有，而 extension 那邊【沒有積木出現】
```

維護者**沒有在討論串裡給結論**，使用者自己換板子繞開。
⚠️ 而 MakeCode 的迴避方式是 `servo write pin` **放在 Pins 裡**——**用操作躲開物件**，不做伺服物件。

> **這一題不是我們特別笨才難——它在微軟那邊也開著。**

## 三、🔴🔴 而最重要的發現：**單向的工具可以隱式長出物件，我們不行**

`DFRobot/ext-oled12864` 的 `main.ts`（Mind+ 官方擴充）**一顆宣告積木都沒有**，
六個積木全是動作，而物件從動作積木自己長出來：

```ts
export function println(parameter, block) {
  Generator.addInclude('oled12864', '#include <oled12864.h>');
  Generator.addObject(`myoled`, `OLED_12864`, `myoled;`);   // ← 物件
  Generator.addSetup(`myoled.begin`, `myoled.begin();`);     // ← setup 裡的初始化
  Generator.addCode(`myoled.printLine(${str});`);
}
```

`addObject` 5 次、`addSetup` 9 次、`addInclude` 7 次——**每個方法積木都重複發一次**，
靠第一個參數當**去重鍵**。

而 WebDuino 走另一條（196 顆積木，`blocks/webduino.js`）：**每一族一個 `_new`**

```
led_new / led_state / led_toggle / led_intensity / led_blink
dht_new / dht_get      servo_new / servo_angle      ultrasonic_new / ultrasonic_get
buzzer_new / relay_new / photocell_new / soil_new / rfid_new / max7219_new …
```

⚠️ 而 `led_new` 是**運算式**（`setOutput(true)`），`led_state` 用 `FieldVariable` 指它。

### 🔴 而 Mind+ 那條路我們**抄不了**，理由是根本性的

> **Mind+／mBlock／BlocklyDuino／WebDuino 全都是單向的**（積木 → 程式碼）。

所以他們可以讓物件憑空長出來——**因為那行程式碼永遠不必變回積木**。
而 `OLED_12864 myoled;` 從程式碼回來時**沒有任何積木對應它**。

| | Mind+／mBlock | WebDuino | **我們** |
|---|---|---|---|
| 方向 | 單向 | 單向 | **雙向** |
| 宣告 | 無（隱式長出） | `xxx_new`（運算式） | `xxx_declare`（敘述） |
| `setup` 注入 | `Generator.addSetup()` 去重 | 不需要（JS 執行期） | **看得見的伴生積木** |
| 兩顆同型零件 | 🔴 做不到 | ✅ | ✅ |

🟢 **這解釋了為什麼我們的做法沒人做**：不是他們沒想到，是**他們不必面對這個約束**。

## 四、`Generator.addSetup()` 是我們那條路的【對照組】

探索報告第二節寫過「鷹架只認得四段，`setup` 對它是普通函式 → **做不到**」——**那仍然成立**。
而 Mind+ 證明**另一種架構做得到**（一個可以注進 `setup()` 的產生器 API）。

🔴 **而自動注入那條路的失敗形狀有實證**：`OttoDIY/blockly` issue #168
——蜂鳴器積木讓 `pinMode` **被宣告兩次**，而修法建議逐字是
「做一顆顯式的 `pinMode` 積木，並從其他積木裡拿掉它」。

> **我們的②（自動長出一顆【看得見的】`pinMode` 積木）
> 正好是那個 issue 建議的解——而看得見的東西不會重複兩次而沒人發現。**

⚠️ 所以這不是「我們少一個機制」，是**我們選了另一邊，而那一邊有實證支持**。

> ```
>
> ⚠️ **而偵測器驗過**（四類注入都會報、兩個對照組不亂報）——**0 是量到的，不是漏掉的**。
>
> 🔴 **但 0 答的不是我問的問題**：那 140 段是**AI 生成的**。
> LLM 寫 Arduino 會用教科書腳位（LED 接 13、PWM 接 9），**因為訓練資料就是那些**。
>
> > **一個量測的效力，上限是它的樣本來自誰
> > ——一份沒有學生寫過的語料，量不出學生的錯誤。**
>
> **處置**：①**不升格**。它的證據還不存在，而**造證據的成本比做它高**
> （要收真實的學生程式碼）。
> 🟢 而那支探針**留著當回歸線**：真實學生語料進來的那天，這個 0 會變，**那才是訊號**。
>
> ⚠️ 而「四家裡三家做了」**不是證據**——它們是單向工具，
> 下拉對它們是純粹的輸入輔助；對我們**還要處理「貼進來的值不在選單裡」**
> （見 `style`／`decl_type` 那條：不記形式的 round-trip 會改掉使用者的檔案）。
> **同一個功能，我們的成本比較高而收益未經證實。**

### ② 伴生積木補「宣告」，不只補 `pinMode`

學生拉了 `servo_write` 而沒拉 `servo_declare` 時，自動長出宣告積木。
⚠️ 機制昨天已經做好（`companion`），加一筆宣告就有——
**而它偷的正是 Mind+「物件從動作長出來」的那一半**，差別是**我們的看得見**。

### ③ 接線做成敘述而不是運算式——**維持不動**

WebDuino 的 `led_new` 是運算式，我們的 `pin_attach` 是敘述。兩者同構（都靠一個名字連起來），
而**我們的更好**：它產出真的 C++ 一行，WebDuino 那顆在程式碼裡沒有對應物。

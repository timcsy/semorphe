## 一、問題：意圖在程式碼裡消失

`digitalWrite(9, HIGH)` 與「LED 亮」是**同一個程式**，而後者多了意圖。
使用者問的是：拉完零件積木，意圖保留得住嗎？程式碼轉積木時補得回來嗎？

🔴 **而答案由根公理先決定**：`principles.md:107` **Sc2**「積木不可引入文字程式碼中不存在的概念」，
`concepts/三維錨定.md:235`「**系統不能無中生有**」。

→ **意圖若不在程式碼裡，積木就不該顯示它。** 所以設計的方向不是「把意圖存在旁邊」，
而是**讓意圖成為程式碼裡真的東西**。

⚠️ 而流失的範圍比直覺小：

```
有函式庫的零件（Servo／DHT／LCD／MFRC522）  型別名就是意圖 → 零流失
無函式庫的零件（LED／按鈕／蜂鳴器／繼電器／L298N） → 🔴 只有這一類會流失
```

## 二、🔴 量到的：貼上的程式碼**幾乎都自帶意圖**

語料：`tests/probes/arduino-realistic-corpus.json`（20 段，出題者被要求寫
「**典型的、AI 助手會生成的 Arduino 程式**」——**正好就是「學生貼 LLM 程式碼」那個族群**）。

```
18/20   有具名腳位          ledPin · buttonPin · trigPin/echoPin · relayPin · potPin · redPin…
10/20   用函式庫            型別名即意圖
 0/20   把數字直接丟進呼叫   🔴 沒有任何一段寫 digitalWrite(13, HIGH)
19/20   至少一種認得出

宣告形式   const int 35 · int 8 · #define 6   ⚠️ 辨識器三種都要認
```

> **語言模型幾乎不寫裸腳位——它們被訓練成寫教材風格，而教材風格就是具名常數。**

⚠️ **這個數字的極限，要跟結論一起記**：n=20、**單一模型單次生成**、族群偏差沒量過。
而那 19/20 的那個 1 是 `rgb-led-colors`（`redPin/greenPin/bluePin`）——
🔴 **我可以把關鍵字表補到 20/20，而那就是過擬合 n=20**，也正是
[粒度與預組](2026-08-17-套件積木的粒度與預組.md) 警告的「清單先於證據存在」。

## 三、兩個族群，一棵樹

```
初學者   拉積木           blocks → code
學生     貼 LLM 程式碼    code → blocks
```

**判準**：任何設計都要通過——

> **兩邊做出來的必須是同一棵樹。若初學者拉出來的與貼進來的產生不同的樹，那就是兩個系統。**

而這條判準否掉了我一開始的問法（「腳位長在積木上」vs「先接線再用名字」二選一）。

## 四、收斂到的形狀：一顆積木 ＋ 一個**腳位插槽**

```
初學者拉出來   [ LED (13) 亮 ]         插槽裡是數字
貼上的程式碼   [ LED (ledPin) 亮 ]     插槽裡是變數——因為程式碼裡就是變數
```

**同一顆積木**；插槽裡放什麼由來源決定。🟢 這同時解掉「初學者要多拉一顆」與
「不要把貼進來的 `ledPin` 改名」兩件事。

### `pinMode` 歸誰——三個選項

```
(甲) 一顆「接上 LED 到(13)」積木          初學者要多拉一顆
(乙) 第一次拉 LED 積木時【自動長出一顆】   ← 傾向
(丙) 產生器偷偷寫，積木上看不到           🔴 已否決：違反 Sc2
```

(乙) 的理由是**可以數的**（符合粒度 draft 的判準「總是一起出現，而『總是』可以數」）：
語料裡 `pinMode` 28 次，**每一次都跟著 digitalWrite/analogWrite**。
而「學生自己組會裝錯」也成立——忘記 `pinMode` 是 Arduino 初學者最經典的 bug。

⚠️ (乙) 的代價：自動長出來的積木會嚇到人 → 它必須長在**看得見**的地方（`setup` 裡）。

### 已否決的選項（連理由一起留著）

```
❌ 自製 Led/Button 函式庫（像 Servo 那樣）
   理由：要出一個 .h 給學生 → 那就不是純 Arduino 了，貼出去別人跑不動
❌ 自創標記註解  // @semorphe:led pin=9
   理由：① 只有我們懂 ② 與程式碼是兩份真相，改腳位不改註解就開始說謊
        ③ 學生切到文字看到的不是 Arduino，是我們的方言——正是 Sc2 要擋的
```

## 五、辨識器：四種來源，強度不同

| 來源 | 例 | 信心 |
|---|---|---|
| **型別** | `Servo myservo;` `DHT dht(2, DHT11);` | `high`——近乎事實 |
| **呼叫樣式** | `trigPin` ＋ `echoPin` ＋ `pulseIn` 同時出現 | `inferred`（比名字強：**樣式難以巧合**）|
| **具名腳位** | `const int ledPin = 13;` | `inferred` |
| **註解** | `// LED 接在 13 腳` | 🔴 傾向**不用**——註解與程式碼會脫節 |

🔴 **只有型別那一列可以顯示成實線**，其餘都是虛線。

🟢 而「型別辨識」那一列**不需要關鍵字表**，10/20 段直接受惠——
⚠️ 所以它可以在語料擴充之前先做，**沒有過擬合風險**。

## 六、工具箱分類（草案）

```
🔌 接線   💡 LED   🔘 按鈕   🔊 蜂鳴器   📏 超音波   ⚙️ 伺服
🌡️ 溫濕度   🖥️ LCD   ⏱ 時間   📡 序列埠
────────────────────────────────────────
🔧 進階／腳位   pinMode · digitalWrite · digitalRead · analogRead · analogWrite · map
```

🔴 **最後一排不刪**——`principles.md` Sc1「認知鷹架可退場」要求學生後期看得到底層，
而且他一定會遇到網路／AI 的範例是那樣寫的。

> 而這裡有一個**這個工具特有的教學價值**：同一顆積木，切到程式碼那一格就看得到 `digitalWrite`。
> 別的積木工具給不了——**它不只是「比較好找」，它是「鷹架看得見自己」**。

## 七、實作順序（估）

```
第 0 批  內建函式缺口   tone/noTone · pulseIn · delayMicroseconds · micros · constrain
                        Serial.available/read · analogReadResolution
         🔴 不需拍板、不需物件機制——而蜂鳴器與超音波【卡在這裡】
第 1 批  六個零件       LED · 按鈕 · 蜂鳴器 · 超音波 · 伺服 · 類比感測
第 2 批  要物件機制     DHT · LCD · OLED · EEPROM · IRremote · MFRC522
第 3 批  ESP32          WiFi · HTTPClient · ledcWrite · touchRead
                        （住在 `esp32` 目標，不是同一個工具箱——見 vision 6.11）
```

## 八、待拍板（五項）

```
✅ ① 腳位插槽（數字或變數）＋ 一顆積木一個動作          拍板（2026-08-18）
✅ ② pinMode 走 (乙) 自動長出一顆看得見的積木           拍板
✅ ③ 第一批零件＝ LED·按鈕·蜂鳴器·超音波·伺服·類比感測   拍板
🟡 ④ 認不出來時：退回原始積木打底 ＋（可選）問學生一次   **仍開著**
🟡 ⑤ 要不要先把語料擴到 ~80 段再定關鍵字表              **仍開著**
```

🔴 **①②③ 不需要等 ⑤**——初學者拉積木那條路完全不碰辨識器。

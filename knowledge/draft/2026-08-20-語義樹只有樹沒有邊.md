# 語義樹只有樹，沒有邊

> 2026-08-20　從「現在專心磨協定」那句話往下查出來的
> ⚠️ **狀態：落差已查證，方向未定——而這是一個【定了就很貴】的方向性決定**

## 一、根公理說三種形狀，型別只表達得出一種

[根公理](../principles.md)：

> 程式是**由「概念節點」和「關係邊」組成的語義結構**：
> 在檔案內是樹，在檔案間是圖，在系統間是超圖。

而 `src/core/types.ts:26`：

```ts
export interface SemanticNode {
  id: string
  componentId: string
  properties: Record<string, PropertyValue>
  children: Record<string, SemanticNode[]>   // ← 只有這一個結構關係
  annotations?: Annotation[]
  metadata?: NodeMetadata
}
```

| 根公理說 | 型別表達得出 |
|---|---|
| 檔案內是**樹** | ✅ |
| 檔案間是**圖** | ❌ |
| 系統間是**超圖** | ❌ |

🔴 **`src/core/` 裡唯一的 edge 是 `dependency-resolver` 的 include 邊，
而那是【導出的】，不是真實的一部分**（`#include` 屬於「結構性依賴宣告」，
可從概念使用集合確定性推導——見 [投影](../concepts/投影.md) §資訊分類學）。

## 二、概念在，實作沒跟上

[元件](../concepts/元件.md) §「組裝：三種關係邊，樹是其中一種的形狀」
——**詞彙已經有了**，缺的是型別。

> **這是「概念先行、型別落後」的一個實例，
> 而它和 P9 那批（宣告對了、程式碼沒跟上）是同一族。**

## 三、🔴 為什麼現在就要看它，即使 Node-Flow 不是現在做

使用者定調：Node-Flow 之後才做，現在磨協定。**而這一條正是協定本身。**

Node-Flow 的每一種圖（呼叫圖、資料流、依賴圖）要的都是同一個東西：
**一條不是 parent-child 的邊**。而問題不在於「以後補一個 edges 欄位」，
在於方向：

```
A. 樹是邊的一個特例        邊是基礎，children 是「結構邊」的糖
B. 邊是樹的擴充            樹是基礎，另外掛一張邊表
```

> **A 和 B 一旦選定，序列化格式、存檔遷移、走訪 API 全部跟著走。
> 這是「定了就很貴」的那種決定，而它現在就在協定裡。**

⚠️ 而 knowie 的教訓在這裡適用：
**[護欄的維度是被發現的，不是被設計的](../history/106-護欄的維度是被發現的不是被設計的.md)**
——協定也一樣，磨不出一個對「還不存在的消費者」正確的協定。

🟢 **所以對策不是想周全，是【便宜的探針】**：
做一個小到可以丟掉的同類投影（例如一個唯讀的依賴圖），讓協定自己說它哪裡不夠。
**不是做 Node-Flow，是做一個會逼出這個決定的最小東西。**

## 四、姊妹問題：`lift()` 的輸入是不是硬綁 AST

⚠️ **未查證。**

自然語言＋SDD 是 roadmap 上的（使用者：「之後也會加入，不過也不是現在」），
而 spec 沒有 tree-sitter grammar。如果 `lift()` 的**輸入型別**寫死在
tree-sitter 的 node 上，那條路以後要開就得動核心。

> **這和剛清完的「核心層硬編語言專屬身分」是同一個病，只是換了一個維度。**

[開放擴充](../concepts/開放擴充.md) §「加入新語言的完整清單」預設有一份 grammar
——那份清單本身可能就是那個假設的所在。

**要查的**：`src/core/lift/` 的入口簽名吃的是什麼型別。

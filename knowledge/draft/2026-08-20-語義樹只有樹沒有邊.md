# 語義樹只有樹，沒有邊

> 2026-08-20　從「現在專心磨協定」那句話往下查出來的
> ⚠️ **狀態：落差已查證，方向未定——而這是一個【定了就很貴】的方向性決定**

## 一、根公理說三種形狀，型別只表達得出一種

[根公理](../principles.md)：

> 程式是**由「概念節點」和「關係邊」組成的語義結構**：
> 在檔案內是樹，在檔案間是圖，在系統間是超圖。

而 `src/core/types.ts:26`：

```ts
export interface SemanticNode {
  id: string
  componentId: string
  properties: Record<string, PropertyValue>
  children: Record<string, SemanticNode[]>   // ← 只有這一個結構關係
  annotations?: Annotation[]
  metadata?: NodeMetadata
}
```

| 根公理說 | 型別表達得出 |
|---|---|
| 檔案內是**樹** | ✅ |
| 檔案間是**圖** | ❌ |
| 系統間是**超圖** | ❌ |

🔴 **`src/core/` 裡唯一的 edge 是 `dependency-resolver` 的 include 邊，
而那是【導出的】，不是真實的一部分**（`#include` 屬於「結構性依賴宣告」，
可從概念使用集合確定性推導——見 [投影](../concepts/投影.md) §資訊分類學）。

## 二、概念在，實作沒跟上

[元件](../concepts/元件.md) §「組裝：三種關係邊，樹是其中一種的形狀」
——**詞彙已經有了**，缺的是型別。

> **這是「概念先行、型別落後」的一個實例，
> 而它和 P9 那批（宣告對了、程式碼沒跟上）是同一族。**

## 三、🔴 為什麼現在就要看它，即使 Node-Flow 不是現在做

使用者定調：Node-Flow 之後才做，現在磨協定。**而這一條正是協定本身。**

Node-Flow 的每一種圖（呼叫圖、資料流、依賴圖）要的都是同一個東西：
**一條不是 parent-child 的邊**。而問題不在於「以後補一個 edges 欄位」，
在於方向：

```
A. 樹是邊的一個特例        邊是基礎，children 是「結構邊」的糖
B. 邊是樹的擴充            樹是基礎，另外掛一張邊表
```

> **A 和 B 一旦選定，序列化格式、存檔遷移、走訪 API 全部跟著走。
> 這是「定了就很貴」的那種決定，而它現在就在協定裡。**

⚠️ 而 knowie 的教訓在這裡適用：
**[護欄的維度是被發現的，不是被設計的](../history/106-護欄的維度是被發現的不是被設計的.md)**
——協定也一樣，磨不出一個對「還不存在的消費者」正確的協定。

🟢 **所以對策不是想周全，是【便宜的探針】**：
做一個小到可以丟掉的同類投影（例如一個唯讀的依賴圖），讓協定自己說它哪裡不夠。
**不是做 Node-Flow，是做一個會逼出這個決定的最小東西。**

## 四、姊妹問題：`lift()` 的輸入是不是硬綁 AST

⚠️ **未查證。**

自然語言＋SDD 是 roadmap 上的（使用者：「之後也會加入，不過也不是現在」），
而 spec 沒有 tree-sitter grammar。如果 `lift()` 的**輸入型別**寫死在
tree-sitter 的 node 上，那條路以後要開就得動核心。

> **這和剛清完的「核心層硬編語言專屬身分」是同一個病，只是換了一個維度。**

[開放擴充](../concepts/開放擴充.md) §「加入新語言的完整清單」預設有一份 grammar
——那份清單本身可能就是那個假設的所在。

**要查的**：`src/core/lift/` 的入口簽名吃的是什麼型別。

## 五、🟢 2026-08-20 傍晚：探針的**消費者出現了**，而它不只一個

使用者具名了三個預計要加的面板：**流程圖、硬體 2D 接線、硬體 3D 組裝**。

🔴 而這改變了 §三 的結論的**適用範圍**，不是它的對錯：

```
§三 說   「依賴圖最便宜」——因為 dependency-resolver 已經算得出邊
仍然對   如果要買的是【邊】（A／B 那個決定）
────────────────────────────────────────────
而       流程圖要買的是另一樣東西：per-panel 的佈局狀態
         見 [面板協定的三個頻道](2026-08-20-面板協定的三個頻道.md)
```

> **「最便宜的探針」是一個問錯的問題——探針的價值不在它多便宜，
> 在它逼出哪一個決定。而兩份 draft 想逼出的決定不同。**

### ⚠️ 2026-08-20 更正：上面這一段的第一版，理由是錯的

第一版寫：「流程圖的邊**可以**用 children 表達（順序＝下一句），於是它繞過 A／B」。
**那句話不成立**，而反證就在自己的直譯器裡：

```
src/interpreter/executors/control-flow.ts:3
  export class BreakSignal    { readonly _brand = 'break' }
  export class ContinueSignal { readonly _brand = 'continue' }
```

> **直譯器必須【丟訊號】來實作 break／continue，正因為那條邊樹表達不出來。**

真正的流程圖有**匯合點**（兩條分支指向同一個下一步）、**back edge**（迴圈末端回條件）、
以及 break／return 的非區域跳躍——**沒有一個是 parent-child**。

### 🟢 而結論仍然成立，理由是【導出 vs 儲存】

```
流程圖的邊    導得出來（從樹算）      像 §一 說的 DependencyEdge  →  不必決定 A／B
接線圖的邊    導不出來（使用者畫的）  D13 → LED+ 算不出來，只能存 →  🔴 這才逼 A／B
```

🎯 **接線是這個系統第一條「無法導出」的邊。**
而 A／B 問的正是「邊要不要進真相」——**導得出來的邊回答不了那個問題。**

> **一個結論對、而理由錯的判斷最危險：理由會被拿去做下一個決定。**
> 這一次差別很實在——按錯的理由，流程圖是個陷阱（會讓人以為圖譜驗過了）；
> 按對的理由，流程圖是**正確的第一步**（便宜地買到詞彙與面板機制，把貴的決定留給有資格回答它的人）。

## 六、🔴 2026-08-24：出貨替這個決定加上了**期限**

兩件事同一天發生：

**① 流程面板交付了，而它確實是靠「導出」繞開這一題的**（§五 的預測成立）。
`core/flow/node-graph.ts` 的邊全部從子槽與 `role` 算出來，**一條都沒有存**。
所以流程面板**沒有**替 A／B 提供任何證據——那正是當初說的「便宜地買到詞彙與面板機制」。

**② 使用者當天提出把 `core` 對外出貨**（教學網站、自帶視圖的第三方——
見[可嵌入與可插拔的四個軸](2026-08-24-可嵌入與可插拔的四個軸.md)）。

> 🔴 **一旦 `core` 有外部使用者，改公開型別的代價就從「改幾個檔」
> 變成「破壞別人的專案」。** 而 A／B 改的正是最核心的那個型別。

所以這一題多了一個**時間點**（原本只有「誰來逼它」）：

| 選項 | 買到什麼 | 代價 |
|---|---|---|
| **出貨前答** | 公開型別一次到位 | 在沒有接線視圖的情況下決定——**回到「導得出來的邊回答不了那個問題」** |
| **出貨後答**（v1 只給樹，接線進來時明確發 v2） | 用真實使用者的回饋驗協定 | 一次破壞性版本，且外部使用者要遷移 |

⚠️ **兩條都合理**，差別是先買**協定的正確性**還是**外部使用者的回饋**。
而第一列有個陷阱：它看起來比較負責，實際上是**在沒有資格回答的時候回答**。

### 🟢 決定（2026-08-24）：**明確留給 v2**

理由是這一份自己的結論：**導得出來的邊回答不了那個問題**，而接線圖還沒有。
出貨前回答 A／B ＝ 在沒有那個消費者的情況下決定一個很貴的型別。

於是配套是**兩件事**（缺一不可，否則「留給 v2」只是拖延）：

1. **`dist-sdk` 的版本從 v0 開始**，而 README 要說「**語義樹的型別在硬體域進來時會有一次破壞性改版**」
   ——把「還沒答」寫成一個**外部使用者看得到的事實**，而不是一個我們心裡知道的風險
2. **接線圖是那個閘門**：它一進來就必須回答 A／B，**而不是繞過去**
   （繞過去的方法很誘人：把接線存進 `metadata`。那會讓邊變成一個沒有型別的角落）

> **「留給 v2」與「拖延」的差別，在有沒有寫下【誰來逼它】與【什麼時候】。**

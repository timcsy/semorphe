## 形狀（領域通用）

```
模糊的需求（老師的題目）
  → 候選解讀（操作者提出：AI 或人）
  → 每個解讀一份參考解答
  → 在一批自動產生的「情境」下，學生程式與每份參考解答交給判決提供者
  → 回報：和哪幾個解讀一致、第一個不一致的情境與輸出
  → 老師點選「題目指的是哪一種」
```

分工（照 history/334 的白話版）：候選＝操作者；成不成立＝Cella；並排與點選＝semorphe；誰定題意、記錄＝cos-mos。

## semorphe 要出的

1. 課文任務多一欄 `interpretations: [{ id, label }]`；每個解讀一份參考解答（沿用 `solutions/<任務>.<副檔名>`，多一段 `.<解讀>`）。
2. **情境 `scenario: { kind, payload }`，kind 由領域套件註冊，核心不認得任何一種**：
   - C：`stdin`（文字）——產生器從語意樹每次讀取的型別與順序（今天在 `tests/helpers/stdin-from-tree.ts`，要搬進產品）
   - Arduino：板子的時間序列輸入 `[{ t, key, value }]`（判決請求今天就收這個形狀，`runCella` 的 `inputs`）
   - 判準：第三種（圖、聲音……）等它真的來了再驗證這個抽象，不先為它設計。
3. 比對器：同一批情境，學生程式與每份參考解答各交判決提供者，列出一致與第一個不一致。
4. 老師看的並排畫面。

## 限制（使用者定的）

- **純前端**：情境產生與比對都在瀏覽器裡跑（今天的 Cella 判決本來就在瀏覽器的 worker 裡）；不需要伺服器。
- 需要更重的環境（大量情境、長時間的模擬）時，由 cos-mos 決定在哪裡跑——semorphe 不自己找後端。
- ⚠️ 設計約束（cos-mos 工人核對後，經 cos-mos-main → cella-main → semorphe-main 轉達，11-07）：cos-mos 那一側跑在開發機的 **Node 批次**（經 `slot.mjs` 排隊、用共享快取；瀏覽器讀不到共享存放、也不受排隊管）。
  ⟹ **情境產生與比對要寫成兩個宿主都能跑的純模組**：瀏覽器（semorphe 產品）與 Node（cos-mos 批次）。不碰 DOM、不碰檔案系統；判決提供者由呼叫端注入（同今天 `Provider` 的做法）。

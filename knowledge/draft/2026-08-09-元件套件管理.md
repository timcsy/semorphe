# 元件套件管理

> 日期：2026-08-09
> 怎麼冒出來的：談命名風格時，使用者說「未來規劃是想要有一個元件套件管理機制，
> 方便大家擴充。可以分對內和對外的名字」。
> **狀態：未決。** 這裡沒有一條被實作過。它是 [G 命名整理](../vision.md) 的**下游**，
> 但有一件事會反過來影響 G——見「唯一擋著 G 的一件事」。

## 它帶進來一個前面都沒談的東西：版本

**有了套件管理，名字就不再是唯一的契約——契約是 `名字 ＋ 版本`。**

於是改名不再是禁忌，而是**一次有版本的遷移**：套件發 v2，隨附 v1→v2 的對應表，
載入舊資料時自動轉換。

這條路 [膠囊契約](2026-08-07-元件目錄與膠囊契約.md) 已經寫過：

> Modelica 沒有迴避「搬家＝改名」，他們把它**制度化**：套件隨附轉換腳本
> （`convertClass("OldClass","NewClass")`），載入舊模型時自動轉換。

而 **D 已經把機制建好了**——`registerIdMigration()`，套件登錄自己的改名表，
核心只提供機制。

> **缺的只有一樣：那張表現在不屬於任何版本。**

用綁定的說法（見 [元件](../concepts/元件.md) 的命名章節）：
**版本 = binder。** 存檔裡的 id 之所以是自由變數，是因為它沒有 binder；
記成 `套件@版本 ＋ 名字`，它就綁在那個版本上了。**版本化把自由變數重新綁起來。**

## 相容性就是我們已經定義過的東西

semver 的「破壞性變更」是什麼？**一個原本通過的觀察，現在不通過了。**

> **套件相容性 = 帶觀察集的外延等價**（見 [等價與觀察集](../concepts/等價與觀察集.md)）。

不需要兩套系統。`v1 → v2` 是否相容，答案是「v1 的使用者會問的問題，v2 有沒有
全部保住」——而那個判斷是**算出來的**。

## scope ≠ 套件（已定）

| | 是什麼 | 進 id 嗎 |
|---|---|---|
| **scope** | 命名空間的擁有者 | ✓ `cpp:` |
| **套件** | 發佈與依賴的單位 | ✗ |

**一個 scope 可以有多個套件。** npm 就是這樣：`@babel` 底下有幾十個套件，
拆合套件不影響任何識別字。

**理由**：如果 scope = 套件，那拆套件（`cpp` → `cpp-core` ＋ `cpp-stl`）就是改名，
就是存檔遷移。而**你現在不知道正確的粒度**——那正是不該把它編進 id 的理由。

這也和 D 自己的原則一致：「域已經是欄位（唯一真相），再編進 id 就是雙重真相」。

**好處是直接的**：初學課程可以只裝 `cpp-core`，不必載入 STL 全部；
而這個決定隨時可以改，因為它不在 id 裡。

## 「對內／對外」實際上是三層

見 [元件](../concepts/元件.md) 的命名章節。這裡只記結論與那條判準：

> **一個名字能不能自由改 = 它是 bound 還是 free**——引用它的人是不是都在你看得見的範圍內。

**對內名唯一值得的用法是「省略 scope」**：套件內部寫 `string_size`，
出了套件才是 `cpp:string_size`。那是**語法便利，不是第二個名字**
（一對一、可機械還原、不可能漂移），而且好處實際：套件裡的程式碼不會到處
寫死自己的 scope，未來整包改名或 fork 時不用動內部。

⚠️ **判準**：如果內外的對應表是一對一而且可機械導出，它不是第二個名字；
**需要人維護的話，它就是**——而這個專案花了整個階段 6.5 在清雙重真相。

## 唯一擋著 G 的一件事

其餘都可以晚點決定，但這一條不行：

> **改名表要不要帶版本？**

因為 G 就是一次大規模改名。如果先做 `registerIdMigration('cpp', 1, 2, 表)`，
那 G 之後每一次美化都是「發一個版本」，**不必一次做對**。
如果不做，G 就得一次到位——而「一次到位的命名」正是這串討論證明做不到的事。

**建議**：G 開工前先做這一小步。它很小（一個函式簽章 ＋ 存檔多一個欄位），
而它把 G 的性質從「不可撤回的決定」變成「可以迭代的工程」。

## 未決

1. **套件的邊界怎麼定**——`cpp-core`／`cpp-stl` 這種拆法要不要現在就做，還是等有人抱怨載入太慢
2. **依賴要不要有版本範圍**（semver range），還是釘死
3. **第三方套件的審核**——完全開放，還是有一層登錄
4. **轉換規範自己是不是一個套件**——`@someone` 可以發佈「C++ ↔ Python 的對應」嗎
5. **相容性檢查跑在哪**——發佈時、安裝時、還是載入時

## 誠實的限制：開放生態系裡管不到命名

第一方可以在 CI 強制詞彙表，`@someone:` 管不到。第三方只能靠**誘因**
（可發現性、轉換規範好寫、共用實作的槽對得起來）。

→ 詞彙表該是一份**公開、可提案擴充**的清單，而不只是規則。

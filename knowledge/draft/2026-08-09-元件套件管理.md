# 元件套件管理

> 日期：2026-08-09
> 怎麼冒出來的：談命名風格時，使用者說「未來規劃是想要有一個元件套件管理機制，
> 方便大家擴充。可以分對內和對外的名字」。
> 🟡 **狀態：已升格（2026-08-24）**——路線圖項目 `vision.md` 階段 8
> 「**元件套件管理：契約是「名字 ＋ 版本」**」。
> 🔴 **它連十二輪標熟而未升格**，而讓它變成現在式的是 `dist-sdk` 出貨：
> **一份對外的產物，它的詞彙就是公開介面。**
> **這一份是它的 in-flight 設計理據，做完才反流退場。**
> **它是 [G 命名整理](../vision.md) 的下游**——`cpp@1` 是 G 的產物，不是 G 的前提。
> （這一句一度寫反過，見文中「順序反了」那一節。）

## 它帶進來一個前面都沒談的東西：版本

**有了套件管理，名字就不再是唯一的契約——契約是 `名字 ＋ 版本`。**

於是改名不再是禁忌，而是**一次有版本的遷移**：套件發 v2，隨附 v1→v2 的對應表，
載入舊資料時自動轉換。

這條路 [膠囊契約](retired/2026-08-07-元件目錄與膠囊契約.md) 已經寫過：

> Modelica 沒有迴避「搬家＝改名」，他們把它**制度化**：套件隨附轉換腳本
> （`convertClass("OldClass","NewClass")`），載入舊模型時自動轉換。

而 **D 已經把機制建好了**——`registerIdMigration()`，套件登錄自己的改名表，
核心只提供機制。

> **缺的只有一樣：那張表現在不屬於任何版本。**

用綁定的說法（見 [元件](../concepts/元件.md) 的命名章節）：
**版本 = binder。** 存檔裡的 id 之所以是自由變數，是因為它沒有 binder；
記成 `套件@版本 ＋ 名字`，它就綁在那個版本上了。**版本化把自由變數重新綁起來。**

## 相容性就是我們已經定義過的東西

semver 的「破壞性變更」是什麼？**一個原本通過的觀察，現在不通過了。**

> **套件相容性 = 帶觀察集的外延等價**（見 [等價與觀察集](../concepts/等價與觀察集.md)）。

不需要兩套系統。`v1 → v2` 是否相容，答案是「v1 的使用者會問的問題，v2 有沒有
全部保住」——而那個判斷是**算出來的**。

## scope ≠ 套件（已定）

| | 是什麼 | 進 id 嗎 |
|---|---|---|
| **scope** | 命名空間的擁有者 | ✓ `cpp:` |
| **套件** | 發佈與依賴的單位 | ✗ |

**一個 scope 可以有多個套件。** npm 就是這樣：`@babel` 底下有幾十個套件，
拆合套件不影響任何識別字。

**理由**：如果 scope = 套件，那拆套件（`cpp` → `cpp-core` ＋ `cpp-stl`）就是改名，
就是存檔遷移。而**你現在不知道正確的粒度**——那正是不該把它編進 id 的理由。

這也和 D 自己的原則一致：「域已經是欄位（唯一真相），再編進 id 就是雙重真相」。

**好處是直接的**：初學課程可以只裝 `cpp-core`，不必載入 STL 全部；
而這個決定隨時可以改，因為它不在 id 裡。

## 「對內／對外」實際上是三層

見 [元件](../concepts/元件.md) 的命名章節。這裡只記結論與那條判準：

> **一個名字能不能自由改 = 它是 bound 還是 free**——引用它的人是不是都在你看得見的範圍內。

**對內名唯一值得的用法是「省略 scope」**：套件內部寫 `string_size`，
出了套件才是 `cpp:string_size`。那是**語法便利，不是第二個名字**
（一對一、可機械還原、不可能漂移），而且好處實際：套件裡的程式碼不會到處
寫死自己的 scope，未來整包改名或 fork 時不用動內部。

⚠️ **判準**：如果內外的對應表是一對一而且可機械導出，它不是第二個名字；
**需要人維護的話，它就是**——而這個專案花了整個階段 6.5 在清雙重真相。

## ~~唯一擋著 G 的一件事~~ → **順序反了，版本在 G 之後**（2026-08-09 修正）

> **上面這一節寫過「G 開工前先讓改名表帶版本」。那是錯的。** 保留是為了記住錯在哪。

**版本化的意思是「把當下的狀態變成一個永久承諾」。** 先版本化，`cpp@1` 就等於
現在這套要丟掉的命名——之後每個讀到 v1 的人，都會看到一個**違反我們剛寫下的
命名規則**的版本。

而它有一個具體、不可逆的後果：

> **先版本化的話，G 的每一個舊名字都會變成永久墓碑。**

墓碑不得重用（Protobuf 的 `reserved`）。於是命名空間裡會**永久**保留約
100 個你認為是錯的名字（`strlen`、`string_length`、`vector_size`…），
每一個新加元件的人都要繞過它們。

G 先做的話，那批舊名字**從來沒有在版本下發佈過**——是史前，不是歷史，不需要墓碑。
**前例已經有了：D 剛改了 177 顆名字，一個墓碑都沒立**，因為那時沒有版本的概念。

### 我原本的理由還剩多少

「先版本化，G 就不必一次做對」——比當時講的弱。G 有**客觀的驗收數字**（四項，
可機械檢查），不是品味問題；萬一要修，用 D 剛在 174 顆規模上跑過的機制
（schema 版本 ＋ 遷移表）就夠。

### 連帶收回一條

我曾說「墓碑名單不得重用，**現在就該做**」。那個急迫性來自錯的順序——
在正確的順序下，**墓碑紀律是跟著版本一起開始的**，而版本在 G 之後。

### G 之前真正需要的

不是版本，是兩樣：**四條驗收護欄先就位且先紅**、**D1 拍板**。

### 而 G 的範圍要包含詞彙表

如果 G 的目的是「一個好的開始」，它就不能只是改 177 顆名字，
**要一併把封閉詞彙表定下來、接上護欄**。不然半年後有人加元件時又長出
`length`、又長出 `count`——**而那時已經有版本了，改起來就貴**（要發版、遷移、立墓碑）。

> **趁還沒有版本的時候，把會反覆發生的錯誤先擋住。**
> 「乾淨的開始」不只是名字乾淨，是**讓它保持乾淨的機制先就位**。

### 正確的順序

```
四條驗收護欄（先紅） → D1 拍板 → G（改名 ＋ 定詞彙表 ＋ 收綠）
      → 宣告 cpp@1  ← 版本紀律從這裡開始
      → 墓碑不得重用、事件紀錄、快照、相容性自動計算
```

**版本 1 是 G 的產物，不是 G 的前提。**

## scope 是套件擁有者，不是語言（2026-08-09）

見 [元件](../concepts/元件.md) 的命名章節。這裡只記對套件管理的後果：

- **`cpp` 撞不了**——`@` 是第三方標記，第一方 scope 是白名單（npm 模型）
- 社群要做自己的 C++ 套件就叫 `@someone:*`，而那**更有資訊**
- 第三方要**擴充**而非取代：`@someone:boost_vector` 宣告一條轉換邊到
  `cpp:vector_declare`，就自動進同一個抽象元件、同一個圖鑑條目——
  **不需要第一方批准，不需要改 `cpp:` 一個字**
- 於是「這顆元件針對哪個語言」是**欄位**，不是 scope

## `@` 被用了兩次，但只在人機介面

`@timcsy:x` 的 scope 標記 vs `x@3` 的版本——同一個字元兩個意義。

**而版本不進 id**，資料裡是 key-value（`packages: { cpp: 1 }`），
所以 `@` 在持久化的東西裡只有一個意思。剩下的只有文件與 CLI 怎麼寫，
npm 靠位置消歧（`@babel/core@7.0.0`）活得下去，照抄即可。

⚠️ **`@timcsy:my-sensor` 的連字號要改成 `_`**——分隔符已定為底線，
而第三方會照著文件裡的例子寫。

## 誠實的限制：開放生態系裡管不到命名

第一方可以在 CI 強制詞彙表，`@someone:` 管不到。第三方只能靠**誘因**
（可發現性、轉換規範好寫、共用實作的槽對得起來）。

→ 詞彙表該是一份**公開、可提案擴充**的清單，而不只是規則。

## 🆕 它多了一個消費者：教材（2026-08-27）

原本這份只想過**開發者裝套件**。而使用者 2026-08-27 提出
「**教材可能會搭配自己的擴充元件庫**」——那是一個新的消費者，
而它的信任模型完全不同：

```
開發者裝套件   他讀得懂那份程式碼，他自己承擔
老師發連結給小學生   小學生【分辨不出】那個元件庫是誰寫的
```

🔴 而元件帶的是**會跑的東西**（抬升策略、產生器、`execute.ts`）：

```
教材的文字錯了     學生看到錯的說明
教材的元件庫壞了   學生的編輯器行為被改寫，而他分辨不出來
```

⚠️ MakeCode 的答案是**預設信任、事後封鎖**（逐字：「unless they are banned,
packages can be loaded without approval by providing an exact URL」）
——那是一個**有團隊在看**的模型。

> **「教材帶的元件」與「別人寫的元件」在系統看來是同一種東西
> ——差別只在誰推薦你裝它。**

→ 所以**不要另做一套裝載機制**：`@someone:*` 的機制就是教材要的那個。
   設計見 [教案是一個宣告](2026-08-27-教案是一個宣告.md)、
   [出貨與定位 §五](2026-08-27-出貨與定位.md)。

## 未決

2. **依賴要不要有版本範圍**（semver range），還是釘死
3. **第三方套件的審核**——完全開放，還是有一層登錄
4. **轉換規範自己是不是一個套件**——`@someone` 可以發佈「C++ ↔ Python 的對應」嗎
5. **相容性檢查跑在哪**——發佈時、安裝時、還是載入時

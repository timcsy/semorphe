# 發到 npm，與套件的拆法

> 狀態：🟡 討論中（2026-11-01）。使用者已定：**發 npm、線上資源走 jsDelivr**；拆法、官方套件、生態系要再討論。
> 前情：學生反映 semorphe.com 開要一分多鐘——量到首屏 2.1 MB 在 GitHub Pages 掉速時約 60 秒、Cella 暖機 157 個請求 12.5 MB 共 79.5 秒
> （[線上載入慢是託管不是程式碼](2026-09-16-線上載入慢是託管不是程式碼.md) 的續篇）。jsDelivr：`max-age=31536000, immutable`、Cloudflare 香港節點、6 MB 約 1 秒。

## 〇、🟢 2026-11-03 使用者定：先發 npm，再讓 semorphe.com 從 jsDelivr 抓（路線 B）

**觸發**：使用者觀察到「前端很慢才準備好，因為 index.js 和 monaco editor.js 都是從 GitHub 取得，但是 GitHub 很慢」。
量到（2026-11-03，本機）：GitHub Pages 的 index.js 3.9 MB 這一刻 0.87 秒——**時好時壞**（11-01 掉速時約 60 秒）；jsDelivr 的 cella wasm 6 MB 約 1.1 秒、`immutable` 快取一年。
大檔：Cella wasm 6.1 MB、index.js 3.8 MB、Monaco 3.3 MB、Cella 語言包每個 0.6～1 MB；`dist/` 共 68 MB。

**問過的三條路**：GitHub 分支走 jsDelivr（推薦，不需 token）／**先發 npm 再走 jsDelivr（使用者選）**／只換 Cella 的檔。

**做法（兩步，各自可驗、可退）**：
- **A**：`semorphe` 可發布（`files: ["dist"]`、版本照 cella 用時間戳 `0.1.<YYYYMMDDHHMM>`）；CI 的 `promote`（測試全綠之後）多一步 `npm publish`——**只在 `NPM_TOKEN` 存在時跑**。網站不動。
  ⚠️ 使用者要做的：在 GitHub repo 的 Secrets 加 `NPM_TOKEN`（npm 的 granular token，`semorphe` 的 publish 權限）；token 不經過 AI。
- **B**（A 第一次發布成功、jsDelivr 抓得到之後）：頁面的入口先從 `cdn.jsdelivr.net/npm/semorphe@<版本>/dist/` 抓、抓不到退回本站。
  🔴 **坑**：Cella 的 worker 用 `new Worker(new URL(…, import.meta.url))`——跨網域的 module worker 瀏覽器不准起 ⟹ worker 要留在本站（或 blob 起）；入口跑在 CDN 上時 `import.meta.url` 會指到 CDN，要逐一檢查用到它的地方。
  驗收：e2e 全綠＋真瀏覽器（清快取）量首屏與 Cella 就緒的時間，與改之前對照。

## 二、cella-lang 怎麼拆（對照）

```
cella-lang              引擎（wasm）＋ 標準庫 ＋ 主機（host、dap）
@cella-lang/cfamily     C 家族共用的深嵌入核心
@cella-lang/c、cpp、arduino   各分支
@cella-lang/python      Python
@cella-lang/machine     共用的機器模型
```

**依語意的邊界拆**：每個套件是一套可以單獨判決的語言；版本一起發（同一個時間戳）。
我們的五層與它的對應：cella 的「分支」≈ 我們的③元件套件（依語言）；cella 沒有①④⑤（它沒有視圖、沒有應用）。

## 三、推薦的拆法——分三期，跟著阻斷走

| 期 | 套件 | 給誰 | 前置 |

**為什麼不一開始就照五層拆**：今天元件在建置時就被 glob 打包進核心——現在拆③，等於先做一次登錄表的大改，而沒有任何一個使用者在等它。
cella 能一開始就依語言拆，是因為它每個語言本來就是獨立的語意套件；我們的膠囊雖然在資料夾上已經分好，登錄還沒分。

## 四、生態系

- **命名**：官方用 `@semorphe/*`（要先在 npm 建 org，保留名字）；第三方用 `semorphe-*` 或 `@作者/semorphe-*`。
- **登錄處就是 npm**：不自建 registry。發現機制先用 npm 的 keyword（`semorphe-package`）。
- **版本**：照〈套件協定〉的傾向——課文釘精確版本＋內容雜湊（「學生兩台電腦上看到的積木不一樣」買不到任何東西）。
- **🔴 還沒有人想過的**：第三方的膠囊裡有 TypeScript（`generate`、`lift`），裝了就會在學生的瀏覽器裡跑——信任與沙箱。
  這一條在第 3 期之前一定要有答案。

### 五之六、cella 對 cos-mos 的回覆（2026-11-02，Cella 那側的看法，不是決定）

**總評**：構想和既有的盟約（2026-10-20 的八條約定）一致，「Contract OS 幾乎就是那份約的產品化」；同意 Cella 與 semorphe 各自能單獨用、cos-mos 站在上面。

1. **「Cella 那一半」**＝一個 Cella 套件。以 Arduino 感測器為例，今天就是 `@cella-lang/arduino` 裡的裝置模型（`devices/dhtsensor.cella`：環境模型＋C++ 標頭轉成的語法樹），
   對外介面是判決（verdict JSON、assumes）與除錯器（DAP）。第三方可以自己寫，但 Cella 這側還缺兩件（見 4）。
2. **formalize 統一放在應用的 semorphe 那一半**（約定第 2 條：formalize 是 semorphe 的翻譯義務），Python 的 `components.json` 之後也搬過來。
   好維護的關鍵是**有一個判定者**：程式 JSON 的形狀由 Cella 的資料型別產生，加上判決綁定的檢查（Cella 印回 C++、clang 比兩棵樹），翻錯在 CI 變紅。
3. **發布：兩半各自發，`@cos-mos/<應用>` 是清單加膠水**——放兩半的確切版本＋雜湊（Cella 的每個定義本來就有 merkle 雜湊）、formalize、課程；不把兩半的內容複製進去
   （「複製一份等於排定它過期的那天」）。整合工具負責順序：先發 Cella 那一半，再發 semorphe 那一半，最後發清單。
4. **要先改或先有的**（Cella 那側）：
   - 接受第三方應用，會觸發他們兩個「等觸發才做」的項目：套件的索引與 lockfile、PKI 簽章（判決要說得出是誰發的）。
   - Cella 的原始碼與工具在發表前不公開——第三方要寫 Cella 套件，需要他們發布編好的工具（CLI 或瀏覽器版）與文件。
   - **名字要分清楚**：Cella 路線圖裡的「第二個應用」是 **wasm 作業系統**（Cella 當工具鏈與驗證者，給 esp32c3 一類的裝置），和 cos-mos 的「作業系統」（應用的組合與目錄）不同。
   - 沒有發現讓構想不成立的技術障礙。

⟹ 和使用者原本說的「整合套件時會自行處理 cella 和 semorphe 的發佈」接得上：**整合工具管順序與清單，兩半各歸各的家**。

### 五之七、🟢 使用者：「我希望 cos-mos 其實就是一個 wasm 作業系統了，可以寄生在很多宿主上」（2026-11-02）

⟹ Cella 路線圖上的「第二個應用：wasm 作業系統」與 cos-mos **是同一件事**（cella 擔心的名字衝突因此消失）。

**今天已經有的雛形**：
| 作業系統的部分 | 今天的對應 |
|---|---|
| 核心（wasm） | Cella 的判決與除錯模組——第 210 刀起是建置時編好的 wasm，任何宿主拿到 bytes 就能跑 |
| 宿主轉接層 | 同一支 Cella worker 跑在網頁版（Web Worker）、VSCode（blob worker，spec 198）、Node（測試）——差的只是「檔案在哪」 |
| 系統呼叫 | 〈重構〉的能力介面（判決、型別查詢、執行與除錯、步數）——核心與介面只認介面 |
| 應用 | 一個領域：Cella 那一半＋semorphe 那一半＋formalize＋課程，由 `@cos-mos/*` 的清單綁定 |
| 寄生的協定 | P9 宿主獨立性 |

**宿主之間差的是能力**：有畫面的（瀏覽器、VSCode、Arduino IDE）跑完整的應用；Node／命令列跑判題與本機架設；
esp32c3 這類裝置只跑 Cella 那一半，由有畫面的宿主來看——宿主給多少能力就展開多少（與 semorphe 的降級路徑同形）。

**要兩邊一起想的**：① 核心是什麼——semorphe 的形態那一半今天是 TypeScript，要不要也成為 wasm，還是「有 JS 的宿主才有形態那一半」；
② 這是兩邊共同的作業系統，主導權與 repo 放在哪裡。已轉告 cella（照使用者原話）。

### 五之八、cella 對「cos-mos 就是 wasm 作業系統」的回覆（2026-11-02，Cella 那側的看法；等使用者定）

1. **原本的 wasm 作業系統怎麼併進來**：esp32c3-wasm-66（WAMR 跑在 esp32c3 上）變成 cos-mos 的**一種宿主**（沒有畫面、只跑 Cella 那一半），與網頁、VSCode、Node 並列；Cella 的角色不變（工具鏈與驗證者）。
   - **兩種 wasm 要分開講**：(a) 系統模組＝Cella 的判決與除錯引擎（第 210 刀編好的那些）；(b) 使用者的程式＝由 Cella 編成 wasm、跑在宿主上。
   - **系統呼叫因此分兩層**：給應用的能力介面（判決、型別查詢、執行與除錯、步數——semorphe 的）；給使用者程式的外部函式（`gpio_write`、`delay_ms`…，`cella_extern.*`——Cella 的）。
   - **要補一份寫下來、帶版本的 ABI**：宿主宣告自己提供哪些能力與外部函式（盟約第 4 條「宣告能力」的形狀）；程式用到宿主沒有的，判決降級並說出缺哪一項，不在執行時才撞到「未連結的匯入」。
2. **核心要小**：Cella 的 wasm（判決、執行、除錯）＋那份 ABI，就是「契約」本身。semorphe 的形態那一半當成**有畫面的宿主上的系統服務**（也可以是 wasm，但不進最小核心）。
   判準：**核心是「每個宿主都要有的」，其餘依能力載入**——esp32c3 用不到形態；兩邊仍各自能單獨用。
3. **主導權與 repo**：cos-mos 放在**自己的 repo**（ABI 規格、宿主轉接層、整合與發布工具、應用目錄），**只依賴兩邊發布的產物**（npm 上的 wasm 與套件）、不依賴原始碼——也剛好符合 Cella 原始碼發表前不公開。
   主導權照盟約：形式（ABI 裡外部函式的型別、判決的意思、能力不足時怎麼降級）由 Cella 判；呈現與宿主轉接由 semorphe 做；ABI 變更照第 6 條（兩邊先溝通，牽涉使用者定案的先不改）。
- cella 另外提：判決與除錯模組改成建置時編好的 wasm（就緒約 80 秒 → 0.1～0.3 秒）對「寄生在很多宿主上」很關鍵，這是他們想保持的方向：Cella 的產物都是編好的 bytes。

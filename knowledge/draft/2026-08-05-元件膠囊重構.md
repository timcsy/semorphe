# 元件膠囊重構（按元件聚合 IR 周邊機器）

> 日期：2026-08-05（詞彙於同日對齊 [concepts/元件](../concepts/元件.md)）
> 怎麼冒出來的：一場「要不要為 Semorphe 制定新 IR」的討論。使用者原想用自寫的 Rust Cubical TT／無型別 λ-calculus 當通用 IR，評估後否決（見 [墓碑目錄](../history/014-墓碑目錄.md)），但過程中診斷出**真正該重構的不是 IR，是 IR 外圍的元件機器**。
> **詞彙權威在 [concepts/元件](../concepts/元件.md)**——元件（單位）／實例／埠／參數／形態／行為／符合性。本檔沿用該表；「膠囊」是本檔自己的比喻（一個資料夾裝齊一個元件的所有槽），不是名詞表裡的詞。

## 一句話

**語義樹不換核；碎的是包在它外面的「四路完備性機器」——按機制組織、多套平行機制、雙重真相。** 重構的對象是後者。

**而它有兩個病,不是一個**：

| | 症狀 | 難度 |
|---|---|---|
| **碎裂** | 東西散在太多地方 | 看得出來 |
| **殼** | 東西在該在的地方,**但它是空的** | **看起來像完成** |

碎裂用「就近聚合」治;**殼要用「跑一次看它吐什麼」才驗得出來**——存在性檢查會把空 stub 算成覆蓋。

> **2026-08-05 修正**：原文寫「語義樹（`SemanticNode`）本身是乾淨、穩定的、**不要動**」。「不換核」仍成立（別再被誘惑換成 λ-core），但「完全不動」已被 [concepts/元件](../concepts/元件.md) 推翻——語義樹欠著根公理的債（公理說「節點＋**關係邊**」，實作只有 `children` 沒有邊；參數只有名字沒有型別）。見下方「絕對不能動的」。

## 問題：碎裂是實測的（2026-08-05 審計快照）

以 `cpp_string_at`（最規矩的 lang-library 元件）為準：一個元件的實作散在 **~13 個原始檔、~10 個目錄**（含測試那次 commit 動 16 檔）。四路完備性由 **~8 個引擎**分攤。沒有單一「在這裡新增元件」的位置——同一元件的埠名、code template、i18n 標籤各自在 2 個以上的檔手動同步。

> 數字是時間點快照，會漂移；重點是**結構性成因**，不是精確數值。

**2026-08-05 補測**：把 `cpp_string_at` 的 9 個原始檔攤開，成因**不是一種，是四種**——修法各不相同：

| 成因 | 實例 | 修法 |
|---|---|---|
| **① 路徑逃逸** | lift 在 `core/lifters/expressions.ts`、execute 在 `interpreter/executors/strings.ts` | **搬回**模組 |
| **② 雙重真相** | `block-registrar.ts:1485` 重定義 `Blockly.Blocks['cpp_string_at']` | 宣告式化後**消失** |
| **③ 手維護清單** | `toolbox-categories.ts:78` 列出 concept id、`topics/cpp-beginner.json` 同理 | **反轉註冊**——元件宣告自己屬於哪個分類／層級，清單**生成** |
| **④ UI 層 per-concept switch** | `blockly-panel.ts:385` 的 `case 'cpp_string_at':` | 收進膠囊的 render 宣告 |

**③ 的修法和「搬進膠囊」不同**——清單不該搬，該 derive。**④ 是第五套平行機制**（下方原本只數到四套），而且它同時是中立性違規：UI 面板裡有概念知識。

**中立性基線（更重要的那個數字）**：`src/core`／`src/ui`／`src/interpreter`／`src/views` 底下**有 12 個檔硬編 C++ 專屬 conceptId**——`app.ts`、`sync-controller.ts`、`blockly-panel.ts`、`block-registrar.ts`、`interpreter.ts` ＋ `executors/{io,variables,operators,functions,strings,control-flow,containers}.ts`。**那 12 個就是 Rust 或硬體進來時會爆的地方**，而且今天就測得出來，不必等第二語言。

**安全網**：158 測試檔／3006 測／20 秒跑完，其中 57 個 roundtrip/fuzz 檔。重構的形式因此是「在測試全綠下抽換機器」，不是豪賭。

## 更難的一半：殼（做一半但看起來做完了）

碎裂是「東西散在太多地方」，這是另一個病：**東西在該在的地方，但它是空的**。而且它比碎裂更危險——**碎裂看得出來，殼看起來像完成**。

實測有三層：

**① 空 stub（看得見的殼）**——8 個以上的 `std/*/lifters.ts` 整個檔只有一個空函式，還附一句讓人安心的註解「This module's concepts use pattern-based lifting / No explicit lifter registrations needed」。**註解說「不需要」,實際上是「還沒做」**——真正的 lift 邏輯逃逸到 `core/lifters/` 和 `lifters/io.ts`。

**② 64 個 `it.todo`（記錄代替修復）**——幾乎全在 fuzz 測試：`fuzz-cpp-string` 11、`arrays-pointers` 11、`types-advanced-ops` 10、`cstring` 8、`control-flow` 6…。**每一個都是 fuzz 找到、但被記錄而非修好的破口**；檔案存在、看起來有覆蓋，實際上那幾個 case 是空的。（使用者早就給過「fuzz/roundtrip 發現的 bug 必須修復,不能只留 `it.todo`」這條回饋。）

**③ P2 沒有執行機構（最深的殼）**——`principles.md` 的 **P2 四路完備性（零容忍）**與 `concepts/概念代數.md` 的 `∀ concept: ①lift ②render ③extract ④generate ⑤execute` 寫得很清楚,但 `tests/integration/` 底下**沒有任何一個測試在檢查它**（只有 `audit-concept-identity`、`audit-ptr-concepts`）。**原則本身是殼**——寫下來了、看起來被遵守,沒有東西在檢查。這是「以為做完了」的最深形式:不是某個元件是殼,是**那條保證元件不是殼的規則**是殼。

### 靜態檢查抓不到殼

殼有六種樣態,只有兩種靜態看得出來:

| 樣態 | 靜態抓得到？ | 要怎麼抓 |
|---|---|---|
| 空 stub 函式 | ✓ 函式體沒有註冊呼叫 | 靜態 |
| `it.todo` | ✓ | 靜態計數 |
| **noop executor** | ✗ **有些 noop 是對的**（`cpp_include` 這種宣告性概念） | 見下 |
| 錯的 `codeTemplate` | ✗ 語法合法、語義錯 | roundtrip |
| 死的 `blockDef` 欄位 | ✗ 只在 serialize→deserialize 才暴露 | Block Style 切換 |
| lift 永遠降級到 `raw_code` | ✗ 路徑「存在」,但每次都退化 | 跑 lift,斷言 confidence |

> **存在性檢查抓不到殼。必須跑一次,看它吐什麼。**

這直接推翻了 P0 護欄的原始設計——**數檔案數會把空的 `lifters.ts` 算成覆蓋**。

### 讓「故意為空」出聲

noop 那格是唯一真正棘手的:**正確的空和錯誤的空長得一模一樣**。

解法不是更聰明的偵測,是**要求正確的那個出聲**——從**推斷**改成**宣告**:

```
execute: "noop"        ← 顯式宣告:這個概念本來就不執行
（缺這個欄位）          ← 缺失
```

缺失於是自動變成可偵測的。這和本專案已知的「**靜默降級反模式**」是同一個形狀（多層 fallback 都用同一個預設值 `'x'`,於是資料遺失和正常路徑長得一樣）——**沉默的正確和沉默的缺失撞在一起時,讓正確的那個說話。**

具體碎裂源（每條都對應一種病灶）：

1. **按機制分檔,不是按元件** —— 所有 lift 堆一起、所有 generate 堆一起,於是任何單一元件必然被攤散。這是根因。
2. **lift 有四套平行機制** —— ①`lift-patterns.json` 宣告式 ②`core/lifters/*.ts` 手寫 per-node ③`lifters/io.ts` 的 `METHOD_TO_CONCEPT` 呼叫分派表 ④`core/lifters/strategies.ts` 具名 strategy。哪個語法走哪套,由註冊順序決優先權。
3. **`std/{module}/` 的就近聚合是假象** —— 模組資料夾都有 `lifters.ts`,但幾乎全是空 stub,真正的 lift 邏輯逃逸到兩層外的 `core/lifters/` 和 `lifters/io.ts`。且存在兩個 lifter 目錄。（**這條同時是「殼」的第一層**,見上——`cmath` 66 行、`cstdio` 39 行是**已完工的樣板**,其餘 15 個是 3–7 行的空殼。完成度 2/17,不是設計缺陷而是**未完成的遷移**。）
4. **generate 兩個引擎、無規則決定用哪個** —— `cpp_string_at` 的 `generators.ts` 回傳 `${obj}[${index}]`,blocks.json 又寫 `codeTemplate.pattern`,兩邊都填。（此病灶的原則已在墓碑「codeTemplate 與 generator 並存」定為互斥——但 lift/generate 尚未貫徹。）
5. **雙重真相** —— 積木形態在 `blocks.json` blockDef 和 `ui/block-registrar.ts` 各定義一次（後者用動態下拉蓋掉前者,JSON 的 OBJ 欄位其實是死的,因為「先註冊者贏」）；control-flow 的埠名同時在 JSON 和 `block-input-names.ts`。**這正是 [concepts/元件](../concepts/元件.md) 說的符合性（conformance）缺席**——沒有「每個形態的埠集合 == 語義埠」這條不變式在擋。
6. **`core/` 與 `std/` 兩套存放慣例**（前者用子目錄多檔,後者用平面四檔）。
7. **半途遷移並存** —— 舊 `BlockSpec` 與新拆分格式（`ConceptDefJSON`+`BlockProjectionJSON`）同存於 `types.ts`。

## 為什麼會變成這樣（成長速度的凝結,不是設計失誤）

25 個重構性 spec + 318 commit 擠在 ~4.5 個月。碎裂是幾股**讓專案變好的力量**的影子面：

- **同一塊碼沿不同軸反覆重切**（four-dimensions / decoupling / sync-decouple / app-split / concept-blockdef-split / std-modules / unify-extractor）——同一蛋糕切 8 個平面 = 碎屑。
- **clean break 清得掉資料格式,清不掉程式機制** —— 新機制加了,舊的還能跑、編譯器不抱怨,沒人被迫刪。兩個 "unify" spec（011、048,相隔 37 號）就是「只統一一半」的指紋。
- **P2 四路完備性(零容忍) × 按機制組織** —— 「每元件必須四路」在按機制的結構下,把每個元件攤得更開。
- **宣告式蓋不掉 100%**（P3 的 80/15/5）—— 手寫層必須並存,但始終沒有共同前門。
- **純執行期需求戳破 JSON 單一真相** —— 動態下拉靜態 JSON 表達不出,只好 imperative 重定義。
- **core 先於 modules** —— 跨切面 dispatcher（`io.ts`）先於模組結構存在,沒被吸收進去。
- **AI 元件管線把碎裂模板一起規模化** —— 加元件的速度超過清理的紀律（孤兒 i18n 標籤、死 blockDef 欄位）。

**IR 乾淨,正因為它是那個「不准動的核」——churn 全發生在可替換的投影層。這是系統照設計運作,代價是投影層堆滿殘骸。**

## 提案：元件膠囊 + 單一 dispatch 脊椎

核心翻轉：**從「按機制分檔」→「一個元件 = 一個自足膠囊,五條路徑都在裡面」。**

```
components/cpp/string/at/
  component.json  # componentId, layer, ports, paramSpecs, role, semanticContract
  form.json       # 積木形態（blockDef）—— 積木形狀的唯一權威
  paths.json      # lift pattern + generate template + render + extract（宣告式優先）
  strategy.ts     # 選配：宣告式表達不了時就近放,manifest 指向它
  behavior.ts     # 行為投影：直譯器 step
  i18n.json       # 所有語系標籤
```

檔名直接對上 [concepts/元件](../concepts/元件.md) 的五槽——`component.json` 是身分＋埠＋參數（真實），`form.json`／`behavior.ts` 是兩族投影，`paths.json`＋`strategy.ts` 是真實↔形態之間的雙向路徑。

kernel 縮到只剩：實例型別 + 膠囊載入器 + **每方向一條 dispatch 脊椎**。連 `core/` kernel 元件也變同形狀膠囊,手寫 lifter 變就近 `strategy.ts`；`core/`↔`std/` 兩套慣例消失成一套。

四個關鍵設計決策：

- **每方向只有一個前門** —— lift resolver：`宣告式 pattern → 膠囊自帶 strategy → 降級 raw_code`。render/extract/generate 同樣各一條脊椎。平行機制歸零。
- **殺雙重真相的通法：補強宣告式表達力,讓 imperative 不必出手** —— 例如給 `form.json` 宣告式「動態選項來源」（`{field:"OBJ", optionsFrom:"workspace.stringVars"}`）,由單一 registrar 解讀,JSON 重新成為唯一權威。每個雙重真相都用這招消,不用「手動同步」忍。
- **generate/lift 各二選一** —— 一個元件不准兩邊都填（延伸墓碑「codeTemplate 與 generator 並存」的互斥原則到 lift）。
- **兩份 lift schema 合一**（`lift-patterns.json` ⊕ 內嵌 `astPattern`）。

**避開的陷阱**：別再「全部宣告式統一」然後又長出平行 imperative（011/048 各統一一半就是此坑）。修法——**escape hatch 是一等公民、就近放膠囊裡**,承認 20% 需要程式碼並給它有尊嚴的固定位置,它就不會再散開。

## 做得到嗎：兩張網讓它從豪賭變成有檢查點的遷移

1. **IR 穩定 = 地基不動**，不是在流沙上重蓋，是在不動的核外換鷹架。（「不動」指**不換核**；上面那三筆還債是加法式的增量，且應該**排在膠囊遷移之外獨立走**——別把兩個大件綁成一個不能分開 ship 的東西。）
2. **roundtrip + fuzz + 直譯器輸出等價是「格式無關的黃金測試」** —— 斷言行為（code→tree→code 不變、stdout 相等），不管機器怎麼組織。可在測試全綠下抽換機器,每換一塊立刻知道有沒有弄丟東西。

## 目標架構（2026-08-05 補：為多語言與硬體預留）

原提案只講「按元件聚合」，沒講**頂層軸**。而現行頂層是 `languages/`，**硬體進來時它沒有位置**——`arduino-uno` 不是語言概念。三軸正交的推導見 [concepts/元件](../concepts/元件.md)「元件住在哪」。

```
src/
  kernel/          ← 機制。不認識任何具體語言或域（中立性測試守）
    instance/        語義樹型別、邊、關係
    registry/        ComponentRegistry —— 跨域唯一
    paths/           lift/generate/render/extract/execute 各一條脊椎
    constraints/     全樹流敏感約束（DRC ＋ borrow check 共用骨架）
    bus/ host/       SemanticBus, ViewHost
  components/      ← 內容。一元件一膠囊
    universal/       count_loop, print, if…（跨語言）
    cpp/  rust/  hardware/
  render/          ← 形態後端（Blockly / Monaco / 2D / 3D / 幾何）
  app/             ← panels、組裝編輯器、圖鑑
```

驗收性質：**加一個語言／加硬體域／加一個視圖，kernel 零改。**

`src/blocks/{semantics,projections}` 已經把 universal 從 `languages/` 分出來了——方向對，只是沒推到底。

> **目錄軸要先於格式定案。** 「膠囊長什麼樣」可以等（見下方「還沒想清楚的」），但「檔案搬去哪」不能——若遷進 `languages/cpp/`，硬體來了要再切一次，那是第 9 刀。

## 遷移形狀：絞殺式清潔切割（不是 big-bang）

有真實的疤：`009-restore-legacy-features`（一次重構弄丟功能要專開 spec 救回）。20 模組 × 4 路一次全掀 = 放大那個疤。正確：

1. 新膠囊格式 + 新 kernel **蓋在舊的旁邊**。
2. **一個元件垂直切片**（`cpp_string_at`）證明格式跑得通、黃金測試綠。
3. **一模組一模組遷移**,每落地一個就刪掉對應舊機制。
4. 舊 kernel 沒人用了,整片刪。

每個模組遷移獨立可 ship,不會有掀開一半不能收的懸空。

**遷移引擎 = 現成的 `component-pipeline` skill**：把它們的輸出目標改成膠囊格式,再寫一次性 migrate（讀舊散落檔 → 吐新膠囊）。遷移完,新元件天然落在「一資料夾五槽」,碎裂在源頭不再發生。

## 分期執行計畫（2026-08-05，使用者說「不計成本，因為後面越貴」時擬）

**先用 [over-justify](../skills/over-justify/SKILL.md) 的紀律檢查「不計成本」豁免掉的是哪一層**——這一步不能跳，因為上一次就是這樣豁免錯層的：

| 先前的保留 | 論據是哪一層 | 能不能豁免 |
|---|---|---|
| 別把改名綁進膠囊遷移 | 當時是「兩個未定案綁一起」 | ✅ 已失效——名詞表定案了 |
| 別動 `properties`（進了序列化） | 成本 | ✅ 豁免，寫遷移層 |
| 語義樹三筆債先不動 | 成本 | ✅ 豁免 |
| **絞殺式、每模組獨立可 ship** | **風險**（009 弄丟功能的疤） | ❌ **豁免不到** |
| **先就近性、後宣告式** | **認識論**（沒看過 17 個模組的形狀就定不出 schema） | ❌ **豁免不到** |

> **不計成本擴大了範圍，沒有改變順序。** 順序是從風險與認識論推出來的。

| 期 | 內容 |
|---|---|
| **P0 三條護欄** | 見下。**純加法、零風險、立刻止血**,不必等任何重構決定 |
| **P1 認領協定** | `claim(node, ctx) → Node \| null`,仲裁規則「**恰好一個模組認領**,多於一個是 CI 錯誤」。解掉 `insert`／`erase` 靠 arg count 分辨 string vs set 的歧義,把「註冊順序決優先權」換成編譯期可偵測的衝突。**唯一需要思考的設計決定**,先於所有機械勞動 |
| **P1.5 目錄軸定案** | `kernel/` `components/` `render/` `app/` 四分——**在搬東西之前** |
| **P2 lift ＋ execute 搬回家** | 17 次,每次獨立 ship。從 `string` 開始（最大、帶歧義方法）;`cmath`／`cstdio` 已完工是樣板。順手清 `interpreter/executors` 的中立性違規 |
| **P3 io.ts 塌成路由器** | 不是獨立工作,是 P2 重複 17 次的殘留物 |
| **P4 殺雙重真相＋清單＋UI switch** | 上表 ②③④,加上刪掉舊 `BlockSpec` |
| **P5 核心型別（原子）** | `properties`→`params`＋`ParamSpec`、`concept`→`componentId`、`SemanticNode`→`Instance`、`children`→`attachments`＋`relation`、`taint` 傳播、localStorage 遷移層。**不能分模組**（每個 lifter/generator/executor 都讀）,放 P2–P4 之後因為那時要改的地方最少 |
| **P6 膠囊格式定案＋遷移** | 到這裡才第一次**看見** 17 個模組的共同形狀,schema 是歸納的不是猜的。新名字隨遷移落地。**只定單語言部分**（見下） |
| **P7 kernel 約束脊椎** | `kernel/constraints/`——電氣 DRC 與 Rust borrow check 共用的遍歷／傳播骨架。加 Rust 或硬體域之前必須有 |

### P0 的三條護欄（兩條靜態、一條執行式）

| # | 護欄 | 形式 | 基線 |
|---|---|---|---|
| ① | **就近性** | 靜態：每個 componentId 被幾個檔提到 | `cpp_string_at` 13 檔／7 目錄 |
| ② | **中立性** | 靜態：kernel／app／render 不准提到具體 componentId | 12 檔違規 |
| ③ | **完備性** | **執行式**：跑一次五路的最小樣本,看它吐什麼 | 未知（跑了才知道） |

③ 對 registry 裡每個 componentId 分三類:

| | 意思 |
|---|---|
| ✅ 實作 | 五路都吐出**非退化**結果 |
| 🈳 **殼** | 路徑存在但退化——noop 未宣告、lift 降級 `raw_code`、generator 回傳佔位、blockDef 欄位讀不到 |
| ❌ 缺 | 路徑不存在 |

**輸出是報表,不是 pass/fail**——8+ 個 stub 加 64 個 todo,第一天不可能綠。它是第三個棘輪:**🈳 與 ❌ 的數字只准往下**。

**這張報表就是 C++ 的補完地圖。** 碎裂審計、中立性審計、完備性審計是同一次遍歷;跑完才會第一次看到 C++ 真正做到哪。

> 順帶:`component-refactor` skill 的職責裡就寫著「偵測四路完備性缺口、死概念」——**能力早就寫好了,只是沒有人在 CI 裡跑它**。③ 某種程度上是把那支 skill 的判斷固化成測試,不是從零蓋。

**驗收標準（可量測,不靠感覺）**：

1. `cpp_string_at` 從 13 檔／7 目錄 → **1 資料夾**
2. 新增一個元件觸碰的檔案數 = 1（P0 ① 持續證明）
3. lift 平行機制 **5 套 → 1 條脊椎**
4. 中立性違規 **12 → 0**（P0 ②）
5. **殼 🈳 與缺 ❌ 歸零**（P0 ③）;`it.todo` 從 **64 → 0**
6. 3006 個測試全程綠,**一次都不准紅著過夜**

## 絕對不能動的（2026-08-05 修訂）

- **不換核** —— 第三次別再被誘惑去換核心（前兩次：Cubical TT、λ-core,見墓碑）。這條不變,是本檔的地基。
- **但「語義樹完全不動」已收回。** [concepts/元件](../concepts/元件.md) 定案後,語義樹有三筆該還的債,每一筆都是**還原根公理、不是重新想像**：
  1. **參數結構化** —— 型別側只有名字清單,沒有型別/範圍/預設值（原文已列,仍成立;也是「複合型別字串解析」那條技術債的根因）。
  2. **埠與邊** —— 根公理寫的是「概念節點＋**關係邊**,檔案內是樹、檔案間是圖」,實作只有 `children`、沒有邊。`children` 的真身是 containment 型的埠。
  3. **`taint` 傳播** —— 原文已列,不變。
- **判準：還公理的債 = 可以動；換一套核 = 不可以動。** 前者保留語義意圖（`count_loop` 還是 `count_loop`,Sc2/Sc3 不破、可逆性不變）,後者摧毀它——這正是墓碑否決 λ-core 的那條線。

## 還沒想清楚的

- **膠囊粒度**：一元件一資料夾,20 std 模組 × 每模組 N 元件會不會目錄爆炸？是否該一模組一膠囊檔（內含多元件）而非一元件一資料夾？
- **「殼」該擋在哪一關**：P0 ③ 只是**報表＋棘輪**（存量太大,擋不住）。但遷移完之後,新元件的殼應該是**硬失敗**——膠囊格式要不要規定「五路缺一就載入失敗」？那會讓 `execute: "noop"` 這類顯式宣告變成強制欄位。傾向要,但沒想過它對 escape hatch（20% 需要程式碼的那些）會不會太硬。
- **64 個 `it.todo` 誰來清**：它們是 fuzz 找到的真 bug,不是待辦。要在 P0 之後獨立排一輪清償,還是隨對應模組的 P2 遷移順手修？後者風險是「遷移＋修 bug」混在一起,壞了不知道是誰壞的——傾向獨立排。
- **全樹約束該掛哪**（2026-08-05 新增，加 Rust 前必須有答案）：borrow check 與電氣 DRC 是同一台機器——**流敏感的全樹約束求解**。它**不是元件的第六個槽**（per-元件膠囊裝不下跨節點的順序與生命週期），是 kernel 的一條新脊椎。膠囊格式定案前要先給它位置，否則遷移完才發現要再切一次。見 [concepts/元件](../concepts/元件.md)「守恆的兩種律」、[語義診斷系統](2026-08-05-語義診斷系統.md)「缺一層」。
- **universal vs 語言專屬的膠囊形狀**（唯一需要第二語言才答得出的）：`count_loop` 在 C++／Rust／Python 都有，膠囊是一顆還是三顆？
  - **A** 一顆通用膠囊內含每語言路徑（`components/universal/count_loop/{component.json, cpp/paths.json, rust/paths.json}`）——內聚高
  - **B** 每語言一顆、指向抽象元件（`components/cpp/count_loop/` 宣告 `abstractComponent: "universal:count_loop"`）——**對應現有機制**（`ConceptDefJSON.abstractConcept` 已存在）
  - **C++ 單獨看分不出勝負**，因為只有一個語言時兩者長得一樣。**這正是「先就近性、後宣告式」比之前更硬的理由——唯一答不出來的 schema 問題，恰好就是唯一需要第二語言的那個。** 建議 P6 只定單語言部分,universal 那格留空明標「等 Rust」。
- **`paths.json` 統一 schema 的表達力邊界**：四方向塞進一個宣告式檔,會不會又踩到「表達不了就退化」的老路？escape hatch 的介面契約要先定清楚。
- **「動態選項來源」宣告式化**能覆蓋所有目前逼 `block-registrar` 出手的 case 嗎？需要先枚舉現有的 imperative 重定義。
- **和 [語義診斷系統](2026-08-05-語義診斷系統.md) 的順序**：兩個都動 lift 之後的管線,誰先做、會不會互相影響膠囊格式。
- **成熟後的出口**：這是 vision 的哪個 Phase？介於 Phase 6（完成）和 Phase 7（Python）之間——**在加第二語言前收斂,還是先出 Python 驗證語言無關性再收斂**？先收斂能讓 Python 直接用膠囊格式（不繼承碎裂）；先 Python 則有第二語言當膠囊格式的壓力測試。未決。
  - **2026-08-05 補**：現在有第三個候選——**硬體域**（見 [硬體域併入計畫](2026-08-05-硬體域併入計畫.md)）。對它答案明確：**就近性必須先收斂**。硬體域比 Python 更該等,因為它帶來的是**新的槽**（形態多了 2D/3D、行為多了 `step`）,格式沒收斂就接等於邊搬家邊改結構;且 23 顆零件會繼承碎裂模板、之後要清兩次。

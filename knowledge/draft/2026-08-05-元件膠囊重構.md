# 元件膠囊重構（按元件聚合 IR 周邊機器）

> 日期：2026-08-05（詞彙於同日對齊 [concepts/元件](../concepts/元件.md)）
> 怎麼冒出來的：一場「要不要為 Semorphe 制定新 IR」的討論。使用者原想用自寫的 Rust Cubical TT／無型別 λ-calculus 當通用 IR，評估後否決（見 [墓碑目錄](../history/014-墓碑目錄.md)），但過程中診斷出**真正該重構的不是 IR，是 IR 外圍的元件機器**。
> **詞彙權威在 [concepts/元件](../concepts/元件.md)**——元件（單位）／實例／埠／參數／形態／行為／符合性。本檔沿用該表；「膠囊」是本檔自己的比喻（一個資料夾裝齊一個元件的所有槽），不是名詞表裡的詞。

## 一句話

**語義樹不換核；碎的是包在它外面的「四路完備性機器」——按機制組織、多套平行機制、雙重真相。** 重構的對象是後者。

> **2026-08-05 修正**：原文寫「語義樹（`SemanticNode`）本身是乾淨、穩定的、**不要動**」。「不換核」仍成立（別再被誘惑換成 λ-core），但「完全不動」已被 [concepts/元件](../concepts/元件.md) 推翻——語義樹欠著根公理的債（公理說「節點＋**關係邊**」，實作只有 `children` 沒有邊；參數只有名字沒有型別）。見下方「絕對不能動的」。

## 問題：碎裂是實測的（2026-08-05 審計快照）

以 `cpp_string_at`（最規矩的 lang-library 元件）為準：一個元件的實作散在 **~13 個原始檔、~10 個目錄**（含測試那次 commit 動 16 檔）。四路完備性由 **~8 個引擎**分攤。沒有單一「在這裡新增元件」的位置——同一元件的埠名、code template、i18n 標籤各自在 2 個以上的檔手動同步。

> 數字是時間點快照，會漂移；重點是**結構性成因**，不是精確數值。

具體碎裂源（每條都對應一種病灶）：

1. **按機制分檔,不是按元件** —— 所有 lift 堆一起、所有 generate 堆一起,於是任何單一元件必然被攤散。這是根因。
2. **lift 有四套平行機制** —— ①`lift-patterns.json` 宣告式 ②`core/lifters/*.ts` 手寫 per-node ③`lifters/io.ts` 的 `METHOD_TO_CONCEPT` 呼叫分派表 ④`core/lifters/strategies.ts` 具名 strategy。哪個語法走哪套,由註冊順序決優先權。
3. **`std/{module}/` 的就近聚合是假象** —— 模組資料夾都有 `lifters.ts`,但幾乎全是空 stub,真正的 lift 邏輯逃逸到兩層外的 `core/lifters/` 和 `lifters/io.ts`。且存在兩個 lifter 目錄。
4. **generate 兩個引擎、無規則決定用哪個** —— `cpp_string_at` 的 `generators.ts` 回傳 `${obj}[${index}]`,blocks.json 又寫 `codeTemplate.pattern`,兩邊都填。（此病灶的原則已在墓碑「codeTemplate 與 generator 並存」定為互斥——但 lift/generate 尚未貫徹。）
5. **雙重真相** —— 積木形態在 `blocks.json` blockDef 和 `ui/block-registrar.ts` 各定義一次（後者用動態下拉蓋掉前者,JSON 的 OBJ 欄位其實是死的,因為「先註冊者贏」）；control-flow 的埠名同時在 JSON 和 `block-input-names.ts`。**這正是 [concepts/元件](../concepts/元件.md) 說的符合性（conformance）缺席**——沒有「每個形態的埠集合 == 語義埠」這條不變式在擋。
6. **`core/` 與 `std/` 兩套存放慣例**（前者用子目錄多檔,後者用平面四檔）。
7. **半途遷移並存** —— 舊 `BlockSpec` 與新拆分格式（`ConceptDefJSON`+`BlockProjectionJSON`）同存於 `types.ts`。

## 為什麼會變成這樣（成長速度的凝結,不是設計失誤）

25 個重構性 spec + 318 commit 擠在 ~4.5 個月。碎裂是幾股**讓專案變好的力量**的影子面：

- **同一塊碼沿不同軸反覆重切**（four-dimensions / decoupling / sync-decouple / app-split / concept-blockdef-split / std-modules / unify-extractor）——同一蛋糕切 8 個平面 = 碎屑。
- **clean break 清得掉資料格式,清不掉程式機制** —— 新機制加了,舊的還能跑、編譯器不抱怨,沒人被迫刪。兩個 "unify" spec（011、048,相隔 37 號）就是「只統一一半」的指紋。
- **P2 四路完備性(零容忍) × 按機制組織** —— 「每元件必須四路」在按機制的結構下,把每個元件攤得更開。
- **宣告式蓋不掉 100%**（P3 的 80/15/5）—— 手寫層必須並存,但始終沒有共同前門。
- **純執行期需求戳破 JSON 單一真相** —— 動態下拉靜態 JSON 表達不出,只好 imperative 重定義。
- **core 先於 modules** —— 跨切面 dispatcher（`io.ts`）先於模組結構存在,沒被吸收進去。
- **AI 元件管線把碎裂模板一起規模化** —— 加元件的速度超過清理的紀律（孤兒 i18n 標籤、死 blockDef 欄位）。

**IR 乾淨,正因為它是那個「不准動的核」——churn 全發生在可替換的投影層。這是系統照設計運作,代價是投影層堆滿殘骸。**

## 提案：元件膠囊 + 單一 dispatch 脊椎

核心翻轉：**從「按機制分檔」→「一個元件 = 一個自足膠囊,五條路徑都在裡面」。**

```
components/cpp/string/at/
  component.json  # componentId, layer, ports, paramSpecs, role, semanticContract
  form.json       # 積木形態（blockDef）—— 積木形狀的唯一權威
  paths.json      # lift pattern + generate template + render + extract（宣告式優先）
  strategy.ts     # 選配：宣告式表達不了時就近放,manifest 指向它
  behavior.ts     # 行為投影：直譯器 step
  i18n.json       # 所有語系標籤
```

檔名直接對上 [concepts/元件](../concepts/元件.md) 的五槽——`component.json` 是身分＋埠＋參數（真實），`form.json`／`behavior.ts` 是兩族投影，`paths.json`＋`strategy.ts` 是真實↔形態之間的雙向路徑。

kernel 縮到只剩：實例型別 + 膠囊載入器 + **每方向一條 dispatch 脊椎**。連 `core/` kernel 元件也變同形狀膠囊,手寫 lifter 變就近 `strategy.ts`；`core/`↔`std/` 兩套慣例消失成一套。

四個關鍵設計決策：

- **每方向只有一個前門** —— lift resolver：`宣告式 pattern → 膠囊自帶 strategy → 降級 raw_code`。render/extract/generate 同樣各一條脊椎。平行機制歸零。
- **殺雙重真相的通法：補強宣告式表達力,讓 imperative 不必出手** —— 例如給 `form.json` 宣告式「動態選項來源」（`{field:"OBJ", optionsFrom:"workspace.stringVars"}`）,由單一 registrar 解讀,JSON 重新成為唯一權威。每個雙重真相都用這招消,不用「手動同步」忍。
- **generate/lift 各二選一** —— 一個元件不准兩邊都填（延伸墓碑「codeTemplate 與 generator 並存」的互斥原則到 lift）。
- **兩份 lift schema 合一**（`lift-patterns.json` ⊕ 內嵌 `astPattern`）。

**避開的陷阱**：別再「全部宣告式統一」然後又長出平行 imperative（011/048 各統一一半就是此坑）。修法——**escape hatch 是一等公民、就近放膠囊裡**,承認 20% 需要程式碼並給它有尊嚴的固定位置,它就不會再散開。

## 做得到嗎：兩張網讓它從豪賭變成有檢查點的遷移

1. **IR 穩定 = 地基不動**，不是在流沙上重蓋，是在不動的核外換鷹架。（「不動」指**不換核**；上面那三筆還債是加法式的增量，且應該**排在膠囊遷移之外獨立走**——別把兩個大件綁成一個不能分開 ship 的東西。）
2. **roundtrip + fuzz + 直譯器輸出等價是「格式無關的黃金測試」** —— 斷言行為（code→tree→code 不變、stdout 相等），不管機器怎麼組織。可在測試全綠下抽換機器,每換一塊立刻知道有沒有弄丟東西。

## 遷移形狀：絞殺式清潔切割（不是 big-bang）

有真實的疤：`009-restore-legacy-features`（一次重構弄丟功能要專開 spec 救回）。20 模組 × 4 路一次全掀 = 放大那個疤。正確：

1. 新膠囊格式 + 新 kernel **蓋在舊的旁邊**。
2. **一個元件垂直切片**（`cpp_string_at`）證明格式跑得通、黃金測試綠。
3. **一模組一模組遷移**,每落地一個就刪掉對應舊機制。
4. 舊 kernel 沒人用了,整片刪。

每個模組遷移獨立可 ship,不會有掀開一半不能收的懸空。

**遷移引擎 = 現成的 `component-pipeline` skill**：把它們的輸出目標改成膠囊格式,再寫一次性 migrate（讀舊散落檔 → 吐新膠囊）。遷移完,新元件天然落在「一資料夾五槽」,碎裂在源頭不再發生。

## 絕對不能動的（2026-08-05 修訂）

- **不換核** —— 第三次別再被誘惑去換核心（前兩次：Cubical TT、λ-core,見墓碑）。這條不變,是本檔的地基。
- **但「語義樹完全不動」已收回。** [concepts/元件](../concepts/元件.md) 定案後,語義樹有三筆該還的債,每一筆都是**還原根公理、不是重新想像**：
  1. **參數結構化** —— 型別側只有名字清單,沒有型別/範圍/預設值（原文已列,仍成立;也是「複合型別字串解析」那條技術債的根因）。
  2. **埠與邊** —— 根公理寫的是「概念節點＋**關係邊**,檔案內是樹、檔案間是圖」,實作只有 `children`、沒有邊。`children` 的真身是 containment 型的埠。
  3. **`taint` 傳播** —— 原文已列,不變。
- **判準：還公理的債 = 可以動；換一套核 = 不可以動。** 前者保留語義意圖（`count_loop` 還是 `count_loop`,Sc2/Sc3 不破、可逆性不變）,後者摧毀它——這正是墓碑否決 λ-core 的那條線。

## 還沒想清楚的

- **膠囊粒度**：一元件一資料夾,20 std 模組 × 每模組 N 元件會不會目錄爆炸？是否該一模組一膠囊檔（內含多元件）而非一元件一資料夾？
- **全樹約束該掛哪**（2026-08-05 新增，加 Rust 前必須有答案）：borrow check 與電氣 DRC 是同一台機器——**流敏感的全樹約束求解**。它**不是元件的第六個槽**（per-元件膠囊裝不下跨節點的順序與生命週期），是 kernel 的一條新脊椎。膠囊格式定案前要先給它位置，否則遷移完才發現要再切一次。見 [concepts/元件](../concepts/元件.md)「守恆的兩種律」、[語義診斷系統](2026-08-05-語義診斷系統.md)「缺一層」。
- **`paths.json` 統一 schema 的表達力邊界**：四方向塞進一個宣告式檔,會不會又踩到「表達不了就退化」的老路？escape hatch 的介面契約要先定清楚。
- **「動態選項來源」宣告式化**能覆蓋所有目前逼 `block-registrar` 出手的 case 嗎？需要先枚舉現有的 imperative 重定義。
- **和 [語義診斷系統](2026-08-05-語義診斷系統.md) 的順序**：兩個都動 lift 之後的管線,誰先做、會不會互相影響膠囊格式。
- **成熟後的出口**：這是 vision 的哪個 Phase？介於 Phase 6（完成）和 Phase 7（Python）之間——**在加第二語言前收斂,還是先出 Python 驗證語言無關性再收斂**？先收斂能讓 Python 直接用膠囊格式（不繼承碎裂）；先 Python 則有第二語言當膠囊格式的壓力測試。未決。
  - **2026-08-05 補**：現在有第三個候選——**硬體域**（見 [硬體域併入計畫](2026-08-05-硬體域併入計畫.md)）。對它答案明確：**就近性必須先收斂**。硬體域比 Python 更該等,因為它帶來的是**新的槽**（形態多了 2D/3D、行為多了 `step`）,格式沒收斂就接等於邊搬家邊改結構;且 23 顆零件會繼承碎裂模板、之後要清兩次。

# 過程是一等公民——而今天有兩條互不相干的歷史

**日期**：2026-08-31 ｜ **狀態**：設計（未決，出口是路線圖）
**起點**：使用者「動態執行，儲存過程（包含結構變動）／流程資料流、內部狀態顯示」

## 一、那三句話是同一個東西

```
動態執行              → 時間軸上「現在」這個游標可以移動
儲存過程（含結構變動）  → 軸上有兩種事件：狀態事件與結構事件
流程資料流、內部狀態    → 那條軸的【投影】
```

一句話：**把「過程」變成一等公民，而畫面上的一切都是它的一個游標位置。**

## 二、🟢 它是收攏，不是新增

今天有**兩條互不相干的歷史**（2026-08-31 量測）：

```
結構歷史  sync-controller.ts:326  past/future: SemanticNode[]（整棵樹 structuredClone）
狀態歷史  execution-controller.ts:887  scopeSnapshot——【用完就丟】
關聯      grep 互相引用 = 0
```

而它是 2026-08-30「三對還原收成一對」（[history/193](../history/193-三對還原收成一對，而一顆選單先退場.md)）的**下一步**：

> **還原不再是一個功能，而是「游標往回移一格」。**
> 往回那一格是狀態事件 → 時光旅行除錯；是結構事件 → 還原。
> **它們本來就該是同一顆按鈕，因為它們是同一條軸上的相鄰兩點。**

### 過得了 over-justify 嗎——理由是**壓縮**

```
① undo/redo          past/future 兩個陣列 ＋ 清 future 的規矩
② 執行的分步          interpreter 的游標
③ scopeSnapshot      餵變數面板，用完就丟
④ 流程的 highlighted  當下在哪顆節點
```

過程一等公民之後 **②③④ 變成「讀游標」，① 變成「移游標」**。而它還**預測**出兩個今天做不到的：**回放**（學生怎麼一步步寫出這支程式）與 **hot-fix**。

## 三、🟩 已答（2026-08-31）：兩個讀法都錯，因為它們在同一條軸上

原本的兩個選項——「元資訊，可丟」與「真實，動公理」——**都預設答案在公理維度裡**。
而 `concepts/三維錨定.md:12` 逐字寫著第三個位置：

```
| **情境（Data）** | 環境反饋與觀測數據 | 經驗性、後驗 | AST 解析、round-trip 測試 |
```

> **語義樹決定的是一個【函數】，不是一個值。**
>
> ```
> 公理維度   語義樹 ↦ f : 輸入 → 行為       先驗、確定性
> 情境維度   執行 ＝ f(世界給的那組輸入)     後驗、經驗性
>            追蹤 ＝ 那一次套用的【觀測紀錄】
> ```

投影是把 f **換一種寫法**（資訊量相同）；執行是把 f **用掉一次**（產出一半來自世界）。
**兩者不是同一種關係。**

### 論證：按 P1 自己的公式，追蹤本來就不是投影

`concepts/投影.md:7`：`view = project(structure, scope, viewType, viewParams)`——一個純函數。
**而追蹤需要「結構以外的輸入」才算得出來。**

### 🟢 而它解釋了四件【已經發生】的事（回溯驗證，不是預測）

| 既有事實 | 這個說法怎麼解釋 |
|---|---|
| `audit-behavior-error` 語料第一欄「不可判定（讀輸入／亂數）99 段」被排除在分子外 | 那一欄就是**世界進來的地方**——護欄的實踐早就把執行當情境維度處理 |
| clang vs gcc 在 UB 上的分歧（macOS 與 CI 結果不同） | **UB ＝ 語義樹在那裡沒有決定一個函數**；公理維度不完整，只有觀測說得出發生了什麼 |
| 追蹤沒有輸入就不可重現 | 觀測沒記下條件就不是觀測——經驗科學的形狀，不是工程偏好 |
| P1 的公式算不出追蹤 | 因為它是純函數，而觀測不是 |

**四件事，一個說法。** 而保守／激進兩個讀法一件都解釋不了——那是它們都錯的證據。

### 🟢 「可不可丟」也因此有了非任意的答案，而且有現成先例

過程是觀測 ⟹ 問題變成「一次觀測要不要留下來」⟹「要重現或要比較的時候才留」。

**而 `tests/baselines/*.json` 就是這個專案已經維護了 20 幾份的「被保存的觀測」**
——有版本、有 note 解釋它為什麼變、只准往一個方向走。

🟢 **這繞開了第五節擔心的 event schema versioning**：基線不是事件流，是
**觀測的快照 ＋ 一段散文**。要補的只有一件事——**值的型別要容得下結構**
（見 [同像性與投影的恆等](2026-08-31-同像性與投影的恆等.md)）。

## 四、從 event sourcing 借四條，明確不借一條

| 借 | 內容 |
|---|---|
| **事件是事實，不是命令** | 「節點 X 的 name 從 a 變成 b」可重放；「還原」不行——意思取決於重放時的狀態 |
| **關鍵影格** | 快照是最佳化不是真相。`maxSteps` 預設 100000 ⟹ 每步存整份 scope 不可行 |
| **輸入也是事件** | `cin`／`rand` 是既知的兩個不決定性來源（護欄語料早就指名過）。記下來，一次執行才可重現 |
| **讀模型可重建** | SemanticBus ＋ ViewHost **已經是**那個形狀（第三十九條護欄守著） |

🔴 **不借**：「log 即真相」——那就是第三節那個公理問題。

### ⚠️ 而「事件是事實不是命令」這一課，這個專案已經付過學費

`blockly-panel.ts` 逐字：

> 「那顆積木屬於**重畫之前的那個工作區**。重放它等於把一個已經不存在的過去接回現在的畫布上」
> 「**重放那份歷史不是「還原」，是【把兩個世界混在一起】。**」

Blockly 的復原堆疊裡是**命令**，而工作區被重畫過 —— 一顆 `int x;` 因此憑空長回來。

## 五、🔴 不要持久化事件

ES 最貴的問題不是效能，是 **event schema versioning**：v10 寫的事件，v20 必須永遠讀得懂。

而這個專案已經有體感：`storage-version.ts` 是 **9 次**存檔遷移，而 `history/026` 定調 P8 不做向後相容**管投影與程式碼、不管存檔**。

> **把事件寫進存檔，等於把那筆債乘上事件型別的數量。**

🟢 保守讀法剛好繞開它：過程是 session 範圍的、關掉就沒了。跨 session 回放是**另一個要人拍板的決定**，不該搭便車。

## 六、hot-fix：不是「禁止」，是「明確化」

初版判斷是「禁止執行中改結構」。**那是保守派（JVM HotSwap）那一格，不是唯一答案。**

| 系統 | 怎麼處理「改了程式，而狀態還在」 |
|---|---|
| Erlang/OTP | 兩版本共存；狀態遷移是具名回呼 `code_change/3` |
| CLOS | `update-instance-for-redefined-class`，捕捉被丟棄的槽 |
| JVM HotSwap | 只准改方法本體，**形狀不准變** |
| Elm／React | 狀態與程式本來就分離 |
| PyTorch | `load_state_dict(strict=False)`——名字形狀對得上的搬過去 |

> **沒有一個系統允許「隨意改形狀 ＋ 隱式修好狀態」。
> 允許改形狀的，都要求你【說出狀態怎麼遷移】。**

🔴 **這一段已經升格成概念**：[狀態遷移](../concepts/狀態遷移.md)——四個世界的對照、
剪枝力、以及四條可以拿來測設計的判準都在那裡。

### 🟢 而 Semorphe 的遷移器已經存在

`src/core/flow/layout-key.ts`——`keysOfNodes`／`matchByKeys`／`matchNodes`，用「內容／行號／路徑」三把鑰匙跨樹配對，live 重排與存檔還原共用同一份，**曖昧已經處理過**（有配對率門檻）。

它是為了流程佈局做的，而**它剛好就是 hot-fix 缺的那一塊**。

### 三階段

```
一  值可以改，結構不行          游標不動 → 零風險，覆蓋多數情境（gdb 的 set var）
二  restart：錯了修完從那一步繼續  有明確觸發點（錯誤），游標多半還在（Common Lisp）
三  結構可以改                   用既有配對器搬游標 ＋ 記錄遷移結果 ＋ 配不上要誠實
```

🔴 **第三階段的關鍵**：**把遷移的【結果】記進 log，不要重算**。配對器是啟發式的，重算可能給出不同答案；記下結果之後，重放就是決定性的。

> **一個啟發式只要把它的結論寫成事實，重放就不必再猜一次。**

⚠️ 而它引入一個**新的失敗模式**：配對錯 → 從錯的地方繼續。那比「不能改」更難察覺，所以要有自己的護欄（配對率低於門檻就拒絕接續，不硬接）。

## 七、🔴 一個今天就存在的洞——而 2026-08-31 量出來它比想的嚴重

原本這一節寫「沒有任何機制擋住結構編輯」。量完之後要換成更難聽的版本：

```
232 / 309  個 execute.ts 直接讀 node.children（沒有經過 ctx 收口）
  0        條測試蓋「執行中改結構」
  0        個跟執行狀態掛勾的鎖（blockly-panel 全域 grep 為空）
```

⟹ **使用者現在在執行中改積木，直譯器已經會「亂看見一半」**——沒有時機、沒有規則、
沒有測試。**那不是「live editing 還沒做」，那是未定義行為。**

兩個修法方向，而它們都是「把未定義變成定義」：

```
甲  把現有執行器釘成「對【快照】的觀測」——明確不可中途改      一個下午
乙  加一個「位置是值」的執行器——明確可中途改、有規則          見 執行器是可插拔的 §九
```

🟢 **甲不擋住乙**（乙 ＝ 甲 ＋「快照可在中途被替換，而替換本身被記錄」），
而甲讓現有執行器在乙長大的那幾個月裡是安全的。

## 八、最小版本

**「執行時流程節點旁顯示當下的值」＋「一條可以往回拖的時間軸」，底下是事件記錄，只含狀態事件。**

🔴 **而「顯示什麼、顯示在哪」是另一整軸，已經拆出去了**：
[內部狀態要怎麼顯示](2026-08-31-內部狀態要怎麼顯示.md)——那裡有 SOTA 三對照、
「每個視圖回答一個獨有問題」那條約束、三個做法的排序、以及節點尺寸的限制。

⚠️ **兩軸相交在一個地方**：迴圈裡的節點該顯示的不是「現在的值」，是
**「它每一次的值」**（`0 → 1 → 3 → 6 → 10`）——那是本份這個公理決定的直接紅利，
而三個 SOTA 工具沒有一個有它。

⚠️ 而 `flow-panel.ts` 的 `onExecutionAtNode` 今天**只設 `highlighted`**，它的註解自己承認：

> 「而鏡頭這一刀還沒有。**先亮起來**：那是這個事件對這個視圖最小而誠實的投影。」

**機制全部都在**（事件在、節點在、`snapshotScope()` 在），缺的是把值畫出來。

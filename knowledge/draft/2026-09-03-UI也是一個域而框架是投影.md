# UI 也是一個域，而框架是投影

> 日期：2026-09-03
> 狀態：**設計未決**——出口是 vision 路線圖（要人拍板），不是直接清償。
> 怎麼冒出來的：使用者：「如果我把**前端 UI 也納入我們的元件系統**，能不能搭配
> React 之類的？總之我想給使用者用這些零件組出 UI，然後用程式之類的下去寫
> **資料與控制流**，那我要用什麼框架？**Web Component 有沒有幫助**？」
> 接著：「那如果**結合 Lit** 呢？」
>
> ⚠️ 前提早就定了：`concepts/元件.md:508` 的軸表裡，**域的值是
> `software / hardware / UI`**——UI 一開始就是三個域之一，不是新東西。
> 這一份問的是：那個域**怎麼落地**。

## 一、「用什麼框架」其實是三個問題

```
① 真相用什麼表達        → 元件樹。【定義上就必須與框架無關】
② 產生的程式碼是什麼     → 這是【投影】，可以有很多個
③ 預覽畫面用什麼跑起來   → 某一個視圖的實作細節
```

拆開之後答案自己出來：**UI 框架 ＝ 另一種語言套件**。

React 不該進核心，就像 C++ 不在核心裡（`concepts/宣告登記處.md`：核心不認得
任何語言，語言套件推、核心讀）。⚠️ 而 `concepts/元件.md:508` 已經標好了：
**語言只在 software 域內有意義**——所以嚴格說「React 是一種語言」是錯的，
它是 **UI 域的一種產出目標**。這個位置要想清楚再動軸表。

## 二、🔴 最重要的一條：預覽與產出，必須是同一份實作

| 設計 | 產出的程式碼 | 預覽怎麼跑 | 評價 |
|---|---|---|---|
| **A** | 純 HTML ＋ JS | **跑產出的那一份**（iframe） | 🟢 一份實作，零分歧 |
| **B** | Lit | **跑產出的那一份** | 🟢 一份實作，換來反應式與可重用 |
| **C** | 純 HTML ＋ JS | 用 Lit（或任何框架）自己畫一份 | 🔴 **兩份實作** |

🔴 **C 是陷阱，而它是最自然會滑進去的那一個**：編輯器裡用框架比較好寫，
產出時再組一份漂亮的 HTML。代價是「**在編輯器裡會動，貼出去不會動**」
——而那個分歧會安靜地長大，因為兩邊各自都通過測試。

> **跑的不是你以為的那一份。**

⚠️ 這條教訓 `experience.md` 已經有一份了：「**e2e 測的是 build 產物
——還原原始碼不等於還原產物**」。同一個根。

🟢 而「預覽＝把產出丟進 iframe 跑」順便讓**樣式隔離免費**——iframe 比
shadow DOM 隔得更徹底，而且它就是學生真的會遇到的環境。

## 三、Web Components：一半有用，一半沒用

### 有用的那一半：它的介面模型與五槽對得上

```
attribute / property      ←→  參數槽
<slot>                    ←→  🔴 【組合接點】，不是埠
CustomEvent               ←→  ？（見下面的待決）
```

⚠️ **`<slot>` 那一格不可以寫成「接點」就算了**——`concepts/元件.md:286` 逐字：

> 「埠 ＝ 關係為守恆或資訊的接點——對等、可 Link、雙方獨立存活。
> **組合接點（積木的 `body` 槽、UI 的 `slots`）是【擁有】不是【連接】，不是埠。**」

那條判準已經點名了 UI 的 slots。這份草稿一開始把它寫成「接點」，是**回頭核對
才發現的**——記在這裡當提醒：五槽的詞彙已經很精確，不要用口語重寫它。

### 沒用的那一半

- **它是執行期的元件模型，不是編寫模型**。真相是一棵宣告樹，不是 DOM。
  WC 對「資料怎麼流」「狀態放哪」**一個字都沒說**。
- **產生 WC 的程式碼給學生看很難看**：`customElements.define`、
  `attributeChangedCallback`、`connectedCallback`。
- Shadow DOM 對初學者有個惡名昭彰的坑：「**為什麼我的 CSS 沒有作用**」。

🟢 而你真正會痛的是 **shadow root（隔離）**，不是 custom element（註冊全域標籤）
——兩者常被綁在一起講，只有前者現在就有用。而如果走設計 A/B，iframe 已經蓋掉它。

## 四、資料流才是難題——而一半已經有了

| 模型 | 形狀 | 對初學者 |
|---|---|---|
| **事件 → 語句**（Scratch） | 按鈕的 `onClick` 掛一段積木 | 🟢 最好懂，**與現有的語句積木完全相容** |
| 反應式綁定（React／Vue／Lit） | `<Text value=${count}>`，狀態變了自動重繪 | 🟡 要先懂「狀態」與「重繪」 |
| **混合** | 狀態是變數、繪製自動跟隨、行為掛積木 | 🟢 推薦 |

🔴 混合模型幾乎是**免費**的，因為兩塊零件都在：

- **UI 的 state 就是變數**——變數面板直接變成「這個畫面現在是什麼狀態」的檢視器
- **UI 的資料流可以畫在流程圖那一側**——[[硬體域併入計畫]] 已經寫下
  「流程圖 ↔ 2D 接線」，而 UI 的事件連線是同一種拓撲圖

還有一個對得上的：**跑起來的畫面是「執行」，不是投影**——與主控台同一格
（三維錨定的情境維度，[history/198](../history/198-執行追蹤不是投影而護欄早就這樣對待它了.md)）。
所以「按了按鈕」是一個執行事件，既有的執行追蹤／主控台那套機器接得上。

> **UI 域不需要新的視圖，它需要的三個視圖都已經有了。**

## 五、Lit 的定位：第二種匯出，不是第一投影

三個好處都成立：**不需要 build step**（直接對上〈離線可用〉，JSX 一定要編譯）·
**反應式**（於是「state 就是變數」自動成立）· **產出是標準 custom element**
（貼進任何網站，與〈開放擴充〉同向，也與 [[寄生在別人的編輯器裡]] 同一條路）。

而代價對「教初學者」很具體：

```js
class MyCounter extends LitElement {           // ← class
  static properties = { count: { type: Number } }  // ← 靜態欄位
  render() { return html`<button @click=${() => this.count++}>${this.count}</button>` }
}
customElements.define('my-counter', MyCounter)   // ← 註冊
```

對照：

```html
<button id="b">0</button>
<script>
  let count = 0
  b.onclick = () => { count++; b.textContent = count }
</script>
```

下面那份**就是我們在教的東西**：變數、事件、賦值。上面那份先要學生接受三個
**與資料流無關**的概念，而它們正好擋在最前面。

🔴 還有一個更硬的：**Lit 要 import**。學生把 HTML 存下來、拿回家、沒有網路
→ 打不開（除非把 Lit 一起打包進那個檔）。純 HTML/JS **雙擊就會動**
——在學校電腦與離線環境，這件事的份量比看起來大。

### 三個匯出，用途不同，不是二選一

```
純 HTML/JS   教學、看得懂、雙擊就動、預覽跑的就是它     ← 第一投影
Lit          「把我做的零件帶去別的地方用」            ← 可重用的匯出
React        「這是我會的東西」——業界／履歷           ← 面向不同的匯出
```

🟢 而**加一個投影只是加一份 codegen**——這是已經付過的錢（Python 是那個證明）。

⚠️ 若哪天要選一個框架目標，**Lit 與五槽對應最直接**（properties／slots／events／
styles 四個都對得上，React 的 children 對 slot 比較勉強）。但「要不要框架」與
「要哪個框架」是兩題。

## 六、⚠️ 一個要先擋掉的念頭

**不要順手把 Lit 用來重寫自己的面板。**

[[面板模組化]] 的痛是「加一種投影要改七八個地方」，而那是**宣告**的問題
（`panel-spec.ts` 那條路已經開始），不是渲染框架的問題。面板裡最大的兩塊
（Blockly、Monaco）本身就是命令式的，Lit 幫不上忙，只會多一層。

> **框架解決的是「畫面怎麼跟著資料變」，
> 而那份草稿的痛是「加一種東西要改幾個地方」。**

## 七、兩個會咬人的地方

1. **範圍爆炸**：UI 是三個域裡表面積最大的（HTML/CSS 幾乎無限）。第一刀要
   **先定一個小零件集**（10～15 顆：按鈕、文字、輸入框、圖片、清單、容器、開關…），
   其餘走既有的招——**認不出來的保留原文**（〈降級與認知邊界〉）。
2. 🔴 **CSS 是裝不進元件樹的第四維**。這是最容易失控的地方。第一刀
   **只給一組預設樣式 ＋ 少數幾個槽**（顏色、大小、對齊），**不做自由 CSS**
   ——與〈漸進揭露〉同一條原則：不是做不到，是先不給。

## 八、第一刀的順序

1. **10 顆 UI 元件的宣告**（五槽填好，不寫任何渲染）
2. **來回一致性護欄**：`HTML → 元件樹 → HTML` 逐字相同 ← 護欄與 fuzz 直接搬既有的
3. **渲染成畫面**：把產出丟進 iframe 跑（不引入框架）
4. **事件掛積木**：`onClick` → 一段既有的語句積木
5. 這時候才談 Lit／React 匯出

第 2 步排在渲染前面是刻意的：**三個域都靠「來回一致」立身**，UI 沒有理由例外，
而它是最便宜的證偽——一棵 UI 樹如果來回不一致，後面全是沙上的城堡。

## 九、待決／待查

1. 🔴 **`CustomEvent`／事件綁定算不算「埠」**？`concepts/元件.md:286` 的定義是
   「關係為守恆或資訊的接點——對等、可 Link、雙方獨立存活」。事件看起來像
   **資訊**的有向邊（一源 fan-out 多讀者），那它就是埠；而 slot 明文不是。
   ⚠️ **這一題要在寫任何 UI 元件宣告之前答**，不然十顆元件會各自猜一次。
2. 「React 是一種語言嗎」——軸表說語言只在 software 域內有意義，
   所以它是 **UI 域的產出目標**。那麼 UI 域內要不要一個對應「語言」的軸？
3. 第一刀那 10 顆零件的清單。

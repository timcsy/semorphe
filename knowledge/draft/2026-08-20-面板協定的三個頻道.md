# 面板協定的三個頻道——而第三個是 per-uri，不是 per-panel

> 2026-08-20　使用者：「我希望可以把面板徹底解耦……使用者可以決定要開啟哪一個面板或是佈局，
> 這樣更好和 VSCode 或是 ArduinoIDE 融合」
> 接著：「**我之後還會想預計加一些基礎面板，例如流程圖面板、硬體 2D 接線面板、硬體 3D 組裝面板等等，
> 所以才會現在想確立這機制**」
>
> ## 🟡 進行中的設計依據——**已升格，不得回收**
>
> ✅ **2026-08-20 升格成路線圖項目**：`vision.md`「面板協定：第三個頻道（per-panel 狀態）」。
> 這一份是它的 in-flight 設計理據，**等那一刀完成才反流退場**。
> 順序見 §六（Python → 流程圖 → ArduinoCAD 合流）。
>
> ⚠️ 仍有未決（末節），而它們不擋升格——擋的是動工前要先答的那一條：
> **網頁版沒有文件，共同真相住哪。**

## 〇、🔴 這件事變了什麼：協定有了**名字**，不只是數量

`vision.md:56` 逐字，執行器直接持有面板那一條的狀態欄是：

> 「**沒有人在看**」　❌ **現在在這裡**（67 處，未清的債）

而 [history/105](../history/105-核心層的積木型別歸零而佔位值差點變成新的靜默降級.md):68 與
[history/106](../history/106-護欄的維度是被發現的不是被設計的.md):73 都逐字記著同一句判準：

> **重寫一個沒有第二個消費者的抽象，等於用猜的決定介面。**

🟢 **今天使用者一次講出三個具名的消費者。** 那正是這條判準要等的東西。

⚠️ **而「具名」不等於「存在」**——三個都還沒做。所以這份是**設計**，
它的出口是路線圖（人拍板），不是直接開工。

## 一、三個頻道

```
① 語義樹        唯一真實。所有面板共享，可寫視圖都能改
② 執行狀態      唯讀廣播（執行到哪個節點、變數值）
③ 面板私有狀態  🟡 【擴充那側已經有了】，而它是 per-uri，不是 per-panel
```

⚠️ **本檔第一版寫「③ 今天不存在」——錯的。** `src/vscode/sync/view-state.ts`
就是 ③，2026-08-18 隨 spec 140 交付：

```ts
export interface ViewState { scrollX, scrollY, scale, blockPositions: Record<blockId,{x,y}> }
// 儲存體是宿主的 workspaceState，key ＝ `semorphe.viewState:<uri>`
```

**缺的不是機制，是兩件事**：(1) key 少一個維度（哪個面板），(2) 網頁版沒有對應物。

①② 已經有機制：`SemanticBus` 的 `semantic:update` 與
[draft/執行器直接持有五個面板](2026-08-11-執行器直接持有五個面板.md) §二之二 設計的
`execution:at-node`（已升格成路線圖項目，`vision.md:433`）。

**③ 是這一份的主要產出。**

## 二、③ 是什麼，以及為什麼積木與文字兩個面板逼不出它

```
積木面板   積木的位置可以重算（Blockly 自己排版）
文字面板   縮排可以重算（style 設定決定）
────────────────────────────────────────
2D 接線圖  🔴 我辛苦擺好的線，重開必須在原位
流程圖     🔴 我拉開的節點佈局，重開必須在原位
```

> **前兩個面板的「位置」是導出的，所以三頻道從來沒有被逼出來。
> 第三個面板進來時，位置變成使用者的勞動成果——而勞動成果不能被重算掉。**

### 🔴 而現有的 ③ 有一句註解，它在接線圖上會出事

`view-state.ts:33` 逐字：

> `blockId → 位置`。⚠️ 它是外觀，所以**丟了不會損失語義**。

**那句話是對的，而它不足以支持「可以丟」。**

```
丟掉積木的擺放     Blockly 自動排版，使用者聳個肩
丟掉接線的擺放     使用者半小時的功沒了——而語義一個位元都沒少
```

> **「丟了不會損失語義」是一個關於【真相】的判斷，
> 不是一個關於【可不可以丟】的判斷。而 ③ 存在的理由是後者。**

⚠️ 而它**不能塞進語義樹**，理由是這個專案自己拍過的板
（[history/028](../history/028-B項身分整併-位置不是身分.md)）：

> **位置不是身分，是形態。**

那時講的是 statement／expression 的雙版本。**在這裡它字面上成立。**

## 三、🔴 而它接在一個既有的分類上，並且補了第三格

[draft/擴充的形狀](2026-08-17-擴充的形狀.md) §二（已退場，但那份分類仍是唯一的一份）
說真正的工作是「**31 個欄位，哪些是 per-document**」，並且逐字：

> **一個「只有一個 X」的假設，不會出現在任何介面上——它出現在【誰持有狀態】上。**

那份分類是**二分**。而三個新面板要的是**三分**：

| | 例 | 誰存 |
|---|---|---|
| **per-app** | 積木定義、語言套件 | 應用 |
| **per-document** | 語義樹、目前語言、目前 target | 文件 |
| 🔴 **per-panel** | 佈局、縮放、使用者擺放的座標、跟隨執行 | **今天沒有人存** |

⚠️ 而 `autoScroll`（[draft/執行器直接持有五個面板](2026-08-11-執行器直接持有五個面板.md) §二之二）
當初拍板走 A（事件帶 `follow`），理由是「**開關在哪裡，就說明了它屬於誰**」，
而否決 B 的理由逐字是「**要多一條偏好的線，而今天沒有那個機制**」。

🔴 **③ 就是那個機制。** 如果它為了三個新面板而被建起來，
那個否決理由就失效了——**但 A 那個決定不必翻案**，因為它的正面理由（開關長在除錯工具列上）
與「有沒有偏好機制」無關。**要重看的是理由，不是結論。**

## 四、它自帶一條可機械驗證的護欄

> **面板私有狀態，不得影響任何別的面板。**

```
改 ③ 之後，① 的雜湊必須不變
```

**如果在 2D 面板拖一顆元件會讓程式碼變了，那它就不是私有的——它偷偷是真實**，
而那筆帳會在第四個面板進來時付。

⚠️ 這條護欄要在 ③ **被建立的同一刀**蓋起來，不是之後
（[skills/build-guardrail](../skills/build-guardrail/SKILL.md) 6.5：第一次跑必須是紅的）。

## 五、🔴 與 `history/083` 的關係——**「面板」是兩個不同的字**

使用者 2026-08-20 質疑：「面板就是網頁版的 App……那之後流程圖面板加進來如何？不合理呀」
**對，而查證之後不合理的地方與雙方原先想的都不一樣。**

### 🟢 宿主那一側的機制已經是對的

`src/vscode/manifest.ts:159` 逐字：

> 於是 `viewsContainers` ＋ `views` 整組拿掉，換成一個指令
> ——面板由 `vscode.window.createWebviewPanel` 建

`createWebviewPanel` 開的是**編輯器區域的分頁**（`panel.ts:616` `ViewColumn.Beside`），
不是側邊欄的固定格。**想開幾個就開幾個，而拖拉／分割／關掉哪一個是 VSCode 的事。**

🟢 **佈局那一半不用我們做。** 加流程圖 ＝ 加一個指令 ＋ 一個分頁。

### 🔴 不合理的是分頁裡裝什麼

```
083 的「面板」  ＝ 宿主給的那個分頁
使用者的「面板」 ＝ App 內部的一格（積木／流程圖／接線）
```

083 把**全部的後者**塞進**一個**前者。開第二個分頁 ⟹ 兩份積木工作區、兩份工具列。

> **它對兩個面板是對的，而在第三個進來時就不再是一個分解了。**
> （同一個形狀見 [執行器直接持有五個面板](2026-08-11-執行器直接持有五個面板.md) §三
> 的「一個下游看起來像前置，三個下游才顯出自己」。）

⚠️ **所以 083 不是被推翻，是它的適用範圍被指出有邊界**——
而那個邊界在它拍板時還不存在（那時只有兩個面板，而使用者要的是「越像網頁版越好」）。

### 🟢 而換掉內容物之後，VSCode 那側幾乎不用改協定

`src/vscode/sync/view-state.ts:5` 逐字：

```
網頁版    沒有檔案 ⟹ 積木的擺放【就是】真相，存檔存的是它
VSCode    程式碼是真相 ⟹ 積木的位置【純粹是外觀】
```

🔴 **在 VSCode 裡真相是那個檔，而它本來就在宿主手上。**
於是「N 個 webview 互相看不見」不是問題：每個分頁各自 lift 同一份文件，
誰改了就 `applyEdit` 回文件（`sync/messages.ts:90`），宿主廣播 `document`（`:33`），其餘重 lift。
**那個迴圈已經實作好了，只是今天只有一個訂閱者。**

### 🔴 所以難的是**網頁版**，不是 VSCode——這與直覺相反

網頁版沒有文件。多開一個面板，**沒有一個現成的地方放共同真相**。

> **一個宿主看起來比較「受限」，而它的限制正好替我們回答了共同真相住在哪。
> 沒有那個限制的那一側，問題反而沒有答案。**

### ⚠️ 而「同步刻意不抽」那條仍然成立，理由要換

`history/083` 逐字：

> **同步邏輯刻意不抽**（使用者拍板走「兩份並存」）：擴充那側的同步性質真的不同
> （跨行程、非同步、有外來變更）

🟢 **那條不變**——上面剛證明擴充那側的同步性質**更不同了**（文件是真相）。
⚠️ 要重看的不是結論，是它的一個隱含前提：**「擴充那側只服務一個視圖」**。

## 六、🟢 順序已定（2026-08-20，使用者）

> 「我想把大部分 Python 功能寫完之後，用流程圖逼出 per-panel，
> 而流程圖就開始帶邊了，所以到時候也要從 ArduinoCAD 那邊慢慢合流了」

| 步 | 買到的貴決定 | 消費者到場了嗎 |
|---|---|---|
| ① **Python 功能寫完** | 語言軸的第二個消費者 | 🟢 中立性那筆債（`neutrality.json` 33 → 19）等的就是它 |
| ② **流程圖面板** | per-panel（③）＋「邊」第一次有詞彙 | 🟢 本檔 |
| ③ **ArduinoCAD 合流** | 🔴 A／B：邊進不進真相 | 🟢 接線——**而 ② 已經把 ③ 的前置做完** |

🎯 **每一步剛好買一個貴的決定，而且每一步的消費者都已經到場。**

⚠️ 而 ② 與 ③ 的分工是**導出 vs 儲存**，不是「小圖 vs 大圖」
（見 [語義樹只有樹沒有邊](2026-08-20-語義樹只有樹沒有邊.md) 的 2026-08-20 更正）：

```
流程圖的邊  導得出來  →  逼 per-panel，【不必】決定 A／B
接線圖的邊  導不出來  →  🔴 這才逼 A／B
```

🟢 **附帶**：流程圖同時是 `execution:at-node`（`vision.md:433` 已升格）的**第三個消費者**
——那條「每個視圖自己決定高亮代表什麼」不再只有兩個實例。

## 七、探針的取捨（🟢 §六 已答，留作理由）

三個具名面板不該直接做——先做一個小到可以丟掉的，讓協定自己說它哪裡不夠
（[draft/語義樹只有樹沒有邊](2026-08-20-語義樹只有樹沒有邊.md) §三 的「便宜的探針」）。

| 候選 | 需要新的真實？ | 逼得出 ③？ | 既有判斷 |
|---|---|---|---|
| **依賴圖**（唯讀） | 🟢 不用 | 🟡 佈局有，但唯讀、可重算 | ✅ 那份 draft 已判「最便宜」（`dependency-resolver` 已算得出邊） |
| **流程圖** | 🟢 不用 | 🟢 佈局是使用者的 | ⚠️ 我在對話裡推薦了它，**而當時不知道依賴圖已被判定最便宜** |
| **硬體 2D** | 🔴 要（接點／接線） | 🟢 | ⚠️ 是[硬體域併入計畫](2026-08-05-硬體域併入計畫.md) 的第四步，很貴 |

🔴 **而它們逼出來的東西不一樣**，這才是真正的取捨：

```
依賴圖   逼出「邊」（A／B 那個定了就很貴的決定）  ← 語義樹只有樹沒有邊 要的
流程圖   逼出 ③（per-panel 狀態）                 ← 本檔要的
硬體 2D  兩個都逼，而且要新的真實                  ← 最貴
```

> **兩份 draft 各自推薦了不同的探針，因為它們要買的東西不同。
> 而這表示「最便宜的探針」問錯了——要問的是【現在最想買哪一個】。**

# 套件協定（而它今天的成熟度，約等於元件協定填到第四個域）

> 日期：2026-09-26
> 怎麼冒出來的：使用者問「現在有元件、連接、組裝，這樣**套件結構**是不是也要改？」
> 接著問「可以參考其他套件管理、Web Component 作法、OOP 等等的嗎？」
>
> 🟡 **狀態：未承諾的設計庫存。** 不寫完成條件。
> ⚠️ 用的方法是這個專案驗證過的那一個——**填不同的系統，直到結構不再變**
> （元件協定填了 18 個域才收斂，見 [元件宣告的契約化](2026-09-22-元件宣告的契約化.md) §十二）。

---

## 地基：三個主體逼出一個今天沒有的位置

協定拆成 [元件](../concepts/元件.md) · [連接](../concepts/連接.md) · [組裝](../concepts/組裝.md) 之後，
第三個主體立刻撞到套件結構——而**撞到的是一條護欄**：

```
就近性   「一個元件的實作應該【只出現在它自己的資料夾】」
組裝約束  「這條 net 只有一個 driver」「Σ RAM ≤ 2048」—— 本質上在講【好幾顆】
```

⟹ **組裝約束放進任何一個元件資料夾都會讓就近性紅，而那是結構性的，不是擺錯地方。**

🟢 而這件事這個會期**已經撞過一次**：第 226 刀在 `array_at` 的宣告裡寫
`requires: ["cpp:compare"]`，就近性當場紅（見下面〈依賴不是一個關係〉——
那一次的真正原因比「放錯資料夾」更精確）。

> **就近性紅的時候，它不是在擋路，它在告訴你「這條宣告的宿主不是元件」。**

## 填了十三個系統

⚠️ **證據等級不齊**：`custom-elements.json` 的 schema、ROS 的 REP-149、
VSCode 的 contribution points **讀了原始文件**；其餘是既有知識，**沒有逐份查證**。

| 系統 | 它逼出什麼 | |
|---|---|---|
| **ROS `group_depend`** | 聚合者依賴一個**群**，成員宣告自己是成員——**兩邊都不點名對方** | 🔴 改結構 |
| **ROS 的十種依賴標籤** | 「依賴」不是一個關係，軸是**什麼時候需要** × **會不會傳遞** | 🔴 改結構 |
| **VSCode 38 個貢獻點** | 套件不匯出符號，它往**一張宿主擁有的具名表**裡加列，而**表不只一張** | 🔴 改結構 |
| **ROS `.msg` / Maven BOM** | 詞彙／約束是一個**可以被依賴的單位**，獨立版本 | 🔴 改結構（新增一層） |
| **LSP 能力協商** | 雙方各自宣告，**取交集**；對方舊就**降級**，不是失敗 | 🔴 改結構 |
| **Nix** | 拒絕版本範圍，改精確釘選 ＋ 內容定址 | 🔴 逼一個決定 |
| **Debian `Provides`** | 多個實作提供同一個抽象身分，而它是**多對多** | 🟡 ＋ 一條更正 |
| **CEM `mixins[]`** | 同上——也是陣列 | 🟡 第二個獨立來源 |
| **CEM `events[]`** | 元件宣告「我會發出什麼」＝ **出向的資訊埠** | 🔴 資訊軸的第四次 |
| **CEM `schemaVersion` · `deprecated`** | 格式版本；而「過時」是**節點級**的性質 | 🔴 兩個純缺口 |
| **Arduino `architectures=`** | 相容性宣告 | 🟢 確認（域/語言/layer 三軸） |
| **PEP 508 markers** | 對組裝環境的條件依賴 | 🟢 確認（`needsCapability`） |
| **KiCad／PDK** | symbol · footprint · DRC 三個獨立版本 | 🟢 確認（形態多個 ＋ 約束分開） |
| **Cargo features** | ⚠️ 可加的旗標在組裝層被**聯集** | 警告，不是處方 |

### 🔴 最強的那個讀數：四個不相干的系統，答案一樣

```
Maven     BOM —— 一個【只裝約束、不裝程式碼】的套件
半導體     PDK 的 DRC deck 與 cell library 分開出貨、各自版本
Debian    套件是套件,policy 是 policy
ROS       .msg 獨立於節點出貨,兩個節點靠「都依賴同一個 msg 套件」才通得了
```

**四個從來沒對過話的系統，都把「約束／詞彙」與「元件」分開出貨。**

## 收斂到今天的層

```
① 核心      協定 ＋ 匯流排 ＋ 登錄表           不認識任何 componentId
② 詞彙套件   🔴 新的一層 —— 關係律 · 組裝約束 · 單位
③ 元件套件   lang-cpp · hardware-arduino      依賴 ②,貢獻到工具箱
④ 視圖套件   panel-*                          只依賴 ①
⑤ 應用      組裝 ②③④
```

⚠️ **這推翻了本串第一次的回答**（當時說「層數不變，② 的內容分兩級」）。
推翻它的是 ROS 與 Maven **各自獨立地**說同一件事，而理由很硬：
`lang-cpp` 與 `hardware-arduino` **都要用同一套關係律**，
放進其中一個，另一個就得依賴它——**那就是就近性那條紅線的套件版本**。

🟢 **而層數在那之後穩住了**：ROS 與 VSCode 兩份文件讀完，**一層都沒有再加**，變的全是欄位。

> **一個穩定的架構，不是沒有東西在長
> ——是長的東西都長在它預留的那幾欄裡。**

（那正是 §十二 判「收斂」用的同一條判準。⟹ **層可以先定，欄位還要再填幾個系統。**）

---

## 🔴 改結構的三條

### ① 成員資格：今天是「位置」，要換成「宣告」

ROS 的問題敘述逐字是我們的：

> 「packages need to be built after **all instances of a particular kind of package**…
> yet it **shouldn't list each member explicitly by name**」

那就是**工具箱**。而我們今天的版本是 `src/components/**` 的 glob：

> **今天的 glob 是「位置即成員資格」；套件化就是把它換成【宣告的】成員資格。**

位置那一版在所有人都在我們目錄底下時**完全等價**，而第三方套件不在。

⚠️ ROS 明訂一條我們會撞的：**「即使把群依賴算進去，圖仍必須是無環的」**
——所以元件不能反過來依賴工具箱。

### ② 🔴 依賴不是一個關係，而這一條回頭解釋了第 226 刀

ROS 有**十個**依賴標籤（`build` · `buildtool` · `build_export` · `buildtool_export` ·
`exec` · `depend` · `doc` · `test` · `conflict` · `replace`），
軸是**什麼時候需要它** × **會不會傳遞**。

對照我們：`requires` **一個欄位，103 / 349 顆在用**。拿一顆測：

```
requires: ["<vector>"]
  generate   🟢 要 —— 產碼得吐 #include
  lift · render · extract   ❌ 完全不需要
  execute    🟡 直譯器不需要 include
  formalize  ❌ —— 而 formalize 有它【自己】的依賴
```

🔴 **於是第 226 刀那次撞牆讀得出來了。**我在 `array_at` 寫 `requires: ["cpp:compare"]`
（因為它的 `contract.cella` 引用了 compare 定義的 `LtB`），就近性紅。
當時我改成「從引用關係算拓樸序」繞開，而真正發生的事是：

> **我想宣告的是一個 formalize-time 的事實，
> 而唯一能用的那個欄位，語義是 generate-time 的。**

所以就近性紅是**對的**，而它抗議的其實是**欄位用錯**，不是理念錯。

⟹ **六路各自有依賴，而我們只有一個 `requires`。**

### ③ 貢獻點不只一張表

VSCode 不是「一個通用擴充機制」，是**三十八張由宿主擁有的具名表**。

我們至少五張：**工具箱 · 課程清單 · 詞彙表 · 執行器 · 視圖**。
而今天**只有工具箱是這個形狀**（E 步把它從手寫 80 筆改成 45 段有序來源）。

## 🟡 可借的

```
ROS condition        表達式【只做字串比較】—— 封閉 vs 謂詞之間一個刻意很窄的中間點
VSCode when          條件式的貢獻,而條件講【程式狀態】不是課程
                     「陣列取值在沒有任何陣列被宣告時不出現」—— 今天沒有
ROS metapackage      只有執行期依賴、用來裝一整組 🔴 ＝ 課文
ROS architecture_independent   訊息套件就是這樣標的 ＝ 詞彙套件
CEM schemaVersion    349 個檔沒有一個說得出自己是哪一版的格式,而格式【正在改】
CEM deprecated       十二個以上的節點都有 ⟹「過時」是節點級的性質。我們政策有、機制零
```

⚠️ **`when` 不違反「元件不知道教材」**——它的條件是程式狀態，不是課程歸屬。

## 🟢 確認的（我們已經是這個形狀）

```
ROS <export> 容器          ＝ 我們的 annotations（61 顆）—— 同一個逃生艙
宣告／實作分離              ＝ component.json ＋ paths.*
「出現在哪」不寫在自己身上    ＝ E 步把工具箱順序放在工具箱那側
<scope>:<name>            🔴 比 VSCode 強 —— 它靠命名慣例,我們靠格式
Arduino architectures      ＝ 域／語言／layer 三軸
PEP 508 markers           ＝ needsCapability
KiCad 三分                 ＝ 形態多個 ＋ 約束分開
ROS msg 的 checksum        ＝ engineHash（已經在跑）
```

🔴 **而 VSCode 有一個成熟系統的公開缺口值得知道**：它的文件**沒有明講**
兩個擴充貢獻同一個東西時怎麼解決（只有 welcome content 有層序）。
⚠️ 而我們「撞名不可能」≠「衝突不可能」：兩個套件各給一顆語義相同的
「陣列取值」，那是 `abstractComponent` 的事，不是命名的事。

```
VSCode configurationDefaults 一個套件改別人的預設值 —— 它是 VSCode 有名的混亂來源,

```

## 要拍板的

- 🔴 **版本範圍 vs 精確釘選。** Nix 的立場是「範圍是問題的來源不是解法」
  （Cargo 的 feature unification 就是那個問題的實例）。
  而我們有一個特殊條件讓 Nix 那側更有吸引力：**教材是被策展的**——
  一份課文用的元件集合，正確行為就是「這一份，就是這一份」。
  範圍在這裡買不到東西，只買到「學生兩台電腦上看到的積木不一樣」。
  🟢 **傾向精確釘選 ＋ 內容雜湊**，因為我們已經在用（`engineHash` · 346 張對照圖），
  而且那條路上踩過並修好了一次（第 218／219 刀）。
- 🟡 **能力協商要不要雙向。** 今天 `ViewConfig` 的三個 port 是面板向核心要（單向）。
  LSP 是雙向取交集 ＋ 降級。而我們有 [降級與認知邊界](../concepts/降級與認知邊界.md)，
  只是沒接到套件協商上。**一個舊面板碰到一個有它不懂的形態軸的新元件套件，會怎樣？沒有人想過。**
- 🟡 **`abstractComponent` 複數化** —— 而這是**第三個**來源：
  Debian `Provides`（多對多）· CEM `mixins[]`（陣列）·
  以及 §十二之④ 從完全不同的方向說的「等價要帶著問題集合，布林指標裝不下」。

---

## 🟢 可以現在就動的那一條

**把 `requires` 分成六路各自的依賴。**它是三條改結構裡唯一不欠前置的：

```
🟢 有現成的觸發案例   第 226 刀
🟢 有護欄會驗        就近性（它已經紅過一次,而它那次是對的）
🟢 不欠資訊軸        與邊／組裝完全無關
⚠️ 而它動 103 顆宣告 ⟹ 要跑 npm run test:guard
```

⚠️ 而順序上它**先於**「成員資格宣告化」與「貢獻點多張表」，
因為那兩條的消費者（第三方套件）**一個都還沒到**，而這一條的消費者**已經到過了**。

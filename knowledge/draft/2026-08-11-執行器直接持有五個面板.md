# 執行器直接持有五個面板——而匯流排上宣告好的執行事件一個都沒發

> 日期：2026-08-11
> 怎麼冒出來的：使用者要「軟體的 UI／執行方式，與硬體的 2D／3D 接線圖，
> 不要攪在一起」。查視圖那一側時發現登錄表缺一格（已補，commit `9a9e080`），
> **而查發送端時發現的東西更大。**

## 一、量測

```
this.panels.<某個>Panel   src/ui/execution-controller.ts   81 次
emit('execution:state')   整個 src/                         0 次
emit('execution:output')  整個 src/                         0 次
emit('execution:run')     整個 src/                         0 次
```

`SemanticBus` 第 20–30 行宣告了四個執行事件，`ViewHost` 宣告了 `onExecutionState`
——而**沒有任何一個被發過**。執行器直接持有 `blocklyPanel`／`monacoPanel`／
`consolePanel`／`variablePanel`／`bottomPanel` 五個引用，逐一呼叫。

> **只接收端不夠。一條沒有人發的線，與一條沒有接的線，在執行時完全相同。**

```
write       3  → emit('execution:output', { text, stream: 'stdout' })
error       5  → emit('execution:output', { text, stream: 'stderr' })
變數快照     1  → emit('execution:state', { status: 'paused', step })
```

護欄第三十九條的「跨層直接呼叫」**125 → 95**（execution-controller 69 → 39）。

## 二、⚠️ 而剩下的 57 處**不是同一種東西**

這是這份 draft 真正的內容。第一版我想的是「把 81 處全部換成事件」，
而拆開之後那是錯的：

| | 例子 | 筆數 | 上匯流排？ |
|---|---|---|---|
| ~~**廣播**（狀態變了，誰想知道誰聽）~~ | 變數快照、輸出文字、狀態列 | ~~~20~~ **實測 38，已清** | ✅ **已做** |
| **命令**（對一個特定視圖說「做這件事」） | `highlightBlock(id)`／`revealLine(n)`／`showTab('variables')`／`centerOnBlock` | ~55 | ❓ 見下 |
| **詢問**（跟視圖要資料） | `getBreakpoints()`／`getWorkspace()`／`promptInput()` | ~6 | ❌ 不是事件 |

> **把命令與廣播一起丟上匯流排，會做出一個假的解耦**——
> 訊息變成 `{type:'highlightBlock', blockId}` 之後，
> **發送端仍然知道接收端有積木、有 blockId、有「高亮」這個動作**，
> 只是不再直接持有那個物件。**耦合搬了家，沒有變少。**

### ⚠️ 清償廣播時多學到的一件事：**「狀態」與「為什麼」要分兩層**

24 處 `setStatus` 只有 **8 種狀態**，而執行器在傳的是
`Blockly.Msg['EXEC_STATUS_RUNNING'] || 'Running'` ——**文案、i18n 鍵、CSS class**。

> **一個知道對方要顯示什麼字的發送端，換不掉那個接收端。**

而 8 種塞不進 `ExecutionStatus` 的 5 種。硬擴充那個型別會**把 UI 的語彙灌進直譯器**。
正確的拆法是兩層：

```
status  直譯器真的處在哪個狀態    idle / running / paused / completed / error
reason  為什麼                   awaiting-input / breakpoint / aborted
```

8 種 UI 狀態落在 5×reason 上，而**文字是視圖自己的事**。

⚠️ 這個形狀對命令那一堆**也適用**：`highlightBlock` 與 `revealLine`
是「執行到這個節點了」的兩種投影，而不是兩個命令。

### 命令那一堆真正的問題是**它們預設了視圖的種類**

`highlightBlock(blockId)` 與 `revealLine(n)` 是同一件事的兩種說法：
**「現在執行到這個語義節點了」**。而執行器同時說了兩遍，因為它知道有兩個視圖。

→ 正確的形狀大概是一個廣播：`execution:at-node { nodeId }`，
**由每個視圖自己決定那代表什麼**——
積木視圖高亮一顆積木、程式碼視圖捲到一行、2D 接線圖也許讓一顆元件發光。

而那正是根公理：**唯一真實（執行到哪個節點），各式投影。**

⚠️ 這需要 `syncController.getMappingForNode` 那一層**搬進視圖**
（今天執行器替視圖查對映），而那是這份 draft 裡最大的一塊未估。

## 二之二、`execution:at-node` 的設計

> ✅ **已升格成路線圖項目**（2026-08-12，`vision.md`「執行機構自己接上」那一節）。
> 這一節是它的 in-flight 設計理據——**做完才退場**。
> **`autoScroll` 已決：走 A（事件帶 `follow`）**，理由記在 vision 那一條。

### ⚠️ 先看一眼那個回傳型別——問題比「執行器呼叫太多」更深

```ts
// sync-controller.ts:536
getMappingForNode(nodeId): { blockId: string | null; startLine: number | null; endLine: number | null } | null
```

**一個中央對映表，回傳兩個視圖的座標。** `blockId` 是積木的、`startLine/endLine`
是程式碼的。加第三個視圖（2D 接線圖）**要改這個型別**，而改了之後
所有既有呼叫端都要處理一個它們不在意的欄位。

> **一張「什麼都查得到」的中央對映表，就是視圖清單的另一種寫法。**

所以 `execution:at-node` 不只是把 3 處呼叫換成 emit——**它要拆掉這張表**。

### 三側的現況差很多（查證，不是估計）

| | 現況 | 要做什麼 |
|---|---|---|
| **積木** | ✅ `blockly-panel.highlightByNodeId(nodeId, 'execution')` **已經存在**，內部自己 `getBlockIdForNodeId` 反查，`_blockMappings` 也住在面板裡 | 幾乎不用做，見下方缺口 |
| **程式碼** | ❌ `codeMappings` 住在 `sync-controller`，**不在面板裡**——與積木那側不對稱 | 搬進 `monaco-panel` |
| **斷點** | ⚠️ 方向是反的 | 見下 |

⚠️ **積木那側的缺口只有一個**：`highlightByNodeId` **不捲動**，
而執行器今天多做了 `getWorkspace()!.centerOnBlock(blockId)`。

⚠️ 而 `findAncestorWithCodeMapping`（表達式節點沒有 `codeMapping`，往上找祖先）
是**程式碼投影專屬的知識**——積木那側沒有這個問題，因為每個節點都有積木。
它要跟著 `codeMappings` 一起搬進 `monaco-panel`。

> **一個只有某一種投影才會遇到的問題，它的解法就該住在那種投影裡。**

### ⚠️ 斷點：今天的方向是反的，而它讓執行器知道「行」這個概念

```ts
// execution-controller.ts:288-291
const breakpoints = this.panels.monacoPanel?.getBreakpoints() ?? []
const hit = breakpoints.some(bp => bp >= mapping.startLine! + 1 && bp <= mapping.endLine! + 1)
```

執行器跟 monaco 要**行號**，然後自己做區間比對。而斷點完全住在 monaco
（`private breakpoints: Set<number>`）。

→ **反轉**：monaco 把斷點翻譯成 **nodeId 集合**推給執行器，執行器只比對 nodeId。
那樣執行器**不知道有「行」這個東西**，而 2D 視圖也可以推它自己的斷點
（「這顆元件被觸發時停」）。

⚠️ **前置**：翻譯要在 monaco 那側算，而它需要 `codeMappings`
——所以「搬 codeMappings」是「反轉斷點」的前置，順序不能顛倒。

### ⚠️ 一個真的未決：`autoScroll` 開關歸誰

執行器今天讀 `this.debugToolbar.isAutoScrollEnabled()` 決定要不要捲動。
而「跟隨執行」**是一個檢視偏好**，照理該是視圖自己的事——
但那個開關長在除錯工具列上，而工具列是執行器的。

兩個選項，**需要人拍板**：

| | 做法 | 代價 |
|---|---|---|
| ✅ **A（已選）** | 事件帶著它：`{ nodeId, follow: boolean }` | 簡單。⚠️ 而**發送端又知道了一件接收端的事**（「你會捲動」） |
| **B** | 視圖自己訂閱一個檢視偏好 | 乾淨。⚠️ 要多一條偏好的線，而今天沒有那個機制 |

**決定（2026-08-12）：A。** 而拍板時換了一個比原先更硬的理由——
原本我寫的是「`follow` 描述的是這一次廣播的意圖」，而那**很接近詭辯**
（任何耦合都可以重新描述成「意圖」）。

真正站得住的理由是：**開關在哪裡，就說明了它屬於誰。**
使用者是在**除錯工具列**上打開「跟隨執行」的，不是在積木面板的設定裡
——那是對「執行」的指令。而 B 要為一個布林建一條新的偏好機制，
那正是 `concepts/執行機構.md` 整章在講的溫床。

> **一個理由如果換個說法就能支持相反的結論，它不是理由，是修辭。**

### 驗收（升格用）

1. `execution-controller.ts` 對 `blocklyPanel`／`monacoPanel` 的呼叫 → **0**
   （護欄第三十九條的「跨層直接呼叫」隨之下降，數字說話）
2. `getMappingForNode` **不再回傳兩個視圖的座標**——拆掉或只留 nodeId 層
3. 斷點命中的判斷裡**沒有行號**
4. ⚠️ **瀏覽器實測**：逐步執行時積木高亮＋捲動、程式碼行高亮＋捲動、斷點會停
   ——這四件事測試碰不到（前一輪的變數面板就是靠實測才發現它從來沒活過）
5. `npm test` 全綠

### ⚠️ 不在範圍內

- `promptInput()`（要回覆，匯流排是單向的——見 §二的「詢問」）
- `getWorkspace()`／`getBreakpoints()` 本身（那是依賴，該依賴介面，不是事件）
- 2D 視圖本身

### `promptInput()` 那一筆特別麻煩

它**要一個回覆**（使用者輸入的字）。匯流排是單向的。
今天的 `execution:input` 事件宣告在那裡，而它與 `consolePanel!.promptInput()`
的 await 語義**不是同一個東西**。→ 這一筆要單獨想，不要順手改。

## 三、為什麼它擋硬體域的路

`draft/2026-08-05-硬體域併入計畫.md` 的第四步是「2D 面板當第一塊垂直切片」。
一個 2D 接線圖進來時，它需要知道「執行到哪了」——
而今天要拿到那個資訊只有一條路：**讓 `ExecutionController` 認識它**。

> **一個視圖要能被換掉，發號施令的那一端就不能知道它叫什麼名字。**

而 `ExecutionPanels` 這個型別今天明列五個欄位。加一個視圖 = 改那個型別。
**那正是登錄表剛剛在視圖那一側解掉的東西，而發送端還沒解。**

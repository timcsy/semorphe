# 執行器直接持有五個面板——而匯流排上宣告好的執行事件一個都沒發

> 日期：2026-08-11
> 怎麼冒出來的：使用者要「軟體的 UI／執行方式，與硬體的 2D／3D 接線圖，
> 不要攪在一起」。查視圖那一側時發現登錄表缺一格（已補，commit `9a9e080`），
> **而查發送端時發現的東西更大。**

## 一、量測

```
this.panels.<某個>Panel   src/ui/execution-controller.ts   81 次
emit('execution:state')   整個 src/                         0 次
emit('execution:output')  整個 src/                         0 次
emit('execution:run')     整個 src/                         0 次
```

`SemanticBus` 第 20–30 行宣告了四個執行事件，`ViewHost` 宣告了 `onExecutionState`
——而**沒有任何一個被發過**。執行器直接持有 `blocklyPanel`／`monacoPanel`／
`consolePanel`／`variablePanel`／`bottomPanel` 五個引用，逐一呼叫。

> **只接收端不夠。一條沒有人發的線，與一條沒有接的線，在執行時完全相同。**

已搬一處（`displayStep` 的變數快照 → 廣播），**80 處還在**。

## 二、⚠️ 而剩下的 80 處**不是同一種東西**

這是這份 draft 真正的內容。第一版我想的是「把 81 處全部換成事件」，
而拆開之後那是錯的：

| | 例子 | 筆數 | 上匯流排？ |
|---|---|---|---|
| **廣播**（狀態變了，誰想知道誰聽） | 變數快照、輸出文字、狀態列 | ~20 | ✅ 該上 |
| **命令**（對一個特定視圖說「做這件事」） | `highlightBlock(id)`／`revealLine(n)`／`showTab('variables')`／`centerOnBlock` | ~55 | ❓ 見下 |
| **詢問**（跟視圖要資料） | `getBreakpoints()`／`getWorkspace()`／`promptInput()` | ~6 | ❌ 不是事件 |

> **把命令與廣播一起丟上匯流排，會做出一個假的解耦**——
> 訊息變成 `{type:'highlightBlock', blockId}` 之後，
> **發送端仍然知道接收端有積木、有 blockId、有「高亮」這個動作**，
> 只是不再直接持有那個物件。**耦合搬了家，沒有變少。**

### 命令那一堆真正的問題是**它們預設了視圖的種類**

`highlightBlock(blockId)` 與 `revealLine(n)` 是同一件事的兩種說法：
**「現在執行到這個語義節點了」**。而執行器同時說了兩遍，因為它知道有兩個視圖。

→ 正確的形狀大概是一個廣播：`execution:at-node { nodeId }`，
**由每個視圖自己決定那代表什麼**——
積木視圖高亮一顆積木、程式碼視圖捲到一行、2D 接線圖也許讓一顆元件發光。

而那正是根公理：**唯一真實（執行到哪個節點），各式投影。**

⚠️ 這需要 `syncController.getMappingForNode` 那一層**搬進視圖**
（今天執行器替視圖查對映），而那是這份 draft 裡最大的一塊未估。

### `promptInput()` 那一筆特別麻煩

它**要一個回覆**（使用者輸入的字）。匯流排是單向的。
今天的 `execution:input` 事件宣告在那裡，而它與 `consolePanel!.promptInput()`
的 await 語義**不是同一個東西**。→ 這一筆要單獨想，不要順手改。

## 三、為什麼它擋硬體域的路

`draft/2026-08-05-硬體域併入計畫.md` 的第四步是「2D 面板當第一塊垂直切片」。
一個 2D 接線圖進來時，它需要知道「執行到哪了」——
而今天要拿到那個資訊只有一條路：**讓 `ExecutionController` 認識它**。

> **一個視圖要能被換掉，發號施令的那一端就不能知道它叫什麼名字。**

而 `ExecutionPanels` 這個型別今天明列五個欄位。加一個視圖 = 改那個型別。
**那正是登錄表剛剛在視圖那一側解掉的東西，而發送端還沒解。**

## 四、傾向

**先做廣播那 20 筆**（狀態、輸出、變數），它們形狀清楚、風險低，
而且做完 `console-panel` 與 `variable-panel` 就完全不必被執行器持有。

**命令那 55 筆先不動**，直到 `execution:at-node` 那個設計想清楚——
⚠️ 它牽涉「對映查詢住哪」，而那是一個真的架構決定，不是搬移。

⚠️ **不要為了讓數字歸零而把詢問那 6 筆也事件化。** 
`getBreakpoints()` 是執行器**跟視圖要資料**，那本來就該是一個依賴，
只是該依賴一個介面而不是一個具體面板。

## 出口條件

- **廣播那批做完** → 反流進 `history/`，這裡只留命令與詢問
- **`execution:at-node` 有設計** → 升格成路線圖項目（走 draft → roadmap 的閘）
- **2D 面板動工** → 數字會說話，回來重讀

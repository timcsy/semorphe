## 🟡 要你決定：其餘幾組文案還帶著 reason 原文

| 文案 | 積木側 | 程式碼側 | 原文是什麼 |
|---|---|---|---|
| `CELLA_REJECT`（編譯不過） | 這樣寫不合規則：{reason} | 不合規則：{reason}（{clause}） | clang 式的英文，例如 `expression is not assignable` |
| `TYPE_MISMATCH` | 型別接不上：{reason} | 同 | 型別檢查器的英文 |
| `CELLA_UNSUPPORTED` | —— | 判斷功能還不支援這個構造：{reason} | 例如 `scanf is not supported yet` |
| `CELLA_TERMINATION`／`UNCLASSIFIED`／`INVALID` | 帶 {reason} | 帶 {reason} | |
| `CELLA_OTHER`（通用） | ✅ 已改成種類名稱 | {kind}：{reason} | |

你說過兩句話，在這裡互相拉扯：
- 「學生看到的文字不得直接是 reason 原文」（三方會議第三輪後記二）
- 「越像實際編譯器吐出的訊息越好……**不過積木側可以不一樣**」（2026-08-14，診斷的兩個面板各自措辭）

而 `REJECT` 的 reason 是學生**唯一**的線索——拿掉它，學生只知道「不合規則」，不知道哪裡不合。

| 選項 | 學生看到的 | 後果 |
|---|---|---|
| **A（推薦）積木側不給原文、程式碼側保留像編譯器的原文** | 積木：「這樣寫不合規則：{種類的名稱}」；程式碼：「不合規則（{種類的名稱}）：`expression is not assignable`」 | 兩句話都守得住（程式碼側像編譯器、積木側是教學的）；積木側要 Cella 把 reject 細分成結構化的種類才說得具體——先請 cella 排 |
| B 兩側都不給原文 | 都是種類名稱 | 守住後記二的字面；reject 的線索在 Cella 細分之前幾乎沒有 |
| C 照舊 | 都是原文 | 違反後記二 |

**推薦 A**：程式碼側本來就是給「準備讀真實編譯器訊息」的那一面，原文在那裡是對的；積木側的收件人是初學者，原文是噪音。
A 的積木側要等 Cella 把 `reject` 細分（今天 `reject` 一個種類裝了所有編譯錯誤）——細分之前，積木側的 reject 先說「這樣寫不合規則，看程式碼那一格的說明」。

## 盤點：「名字合不合法」歸誰（給 cos-mos）

semorphe 今天自己檢查名字（`core/component/param-check.ts`，由元件宣告的 `kind: 'identifier'` 驅動），**來源標成形態**（`source: 'component'`），而**嚴重度是 error**：

| 規則 | 例 | 誰也會說 |
|---|---|---|
| `BAD_NAME_STARTS_WITH_DIGIT` | `int 123;` | Cella 判 reject（編不過） |
| `BAD_NAME_RESERVED` | `int if;` | Cella 判 reject |
| `BAD_NAME_BAD_CHAR` | `int a-b;` | Cella 判 reject（或解析就失敗） |
| `BAD_NAME_EMPTY` | 積木上那一格沒填 | 程式碼還沒成形——Cella 判不到 |

**判斷**：這是**詞法的形態**（一個字串是不是一個合法的名字），不是判決（程式意思對不對）——semorphe 判它不違反「不判斷對錯」。灰色只在呈現：它是紅色的 error，與判決的 reject 長得一樣，而且常常與 Cella 對同一顆節點的 reject 重複。
✅ **已做**（spec 216）：保留在形態；同一顆節點 Cella 也 reject 時只留形態那一則（措辭比較教學）——`dropRejectsCoveredByNameChecks`，與 `TYPE_MISMATCH` 對 `CELLA_REJECT` 的去重同一個做法。
⚠️ 給 cos-mos：「名字合不合法」不需要 Cella 的判決就能檢查，semorphe 的元件宣告（`kind: 'identifier'`）就說得出——若 cos-mos 的宿主也想在送判決之前擋，可以讀契約的參數型別（日後在 `@cos-mos/<領域>` 加 `identifier` 這個型別？今天五種型別裡沒有）。

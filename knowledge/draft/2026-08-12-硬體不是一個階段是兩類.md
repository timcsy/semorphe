# 硬體不是一個階段，是兩類——而純資訊那一類今天就做得了

> 日期：2026-08-12
> 怎麼冒出來的：使用者問「**如果硬體那邊傳回來的部分資料是可複製資訊
> 而不是需整體守恆資源呢？這樣是否可以把這種屬性的硬體接進來，作為資訊輸入？**」
> ——而那個問題**已經被 `concepts/元件.md` 答了一半**，只是沒有人把它用在排期上。

## 一、那條律早就定案了

`concepts/元件.md:173` 的三種關係律：

| 關係 | 結構 | 律 | 是埠嗎 |
|---|---|---|---|
| **守恆** | 約束網 | 不可自由複製；**全網求解** | ✓ |
| **資訊** | 有向邊 | 一源 **fan-out** 多讀者，可複製、無基質 | ✓ |

而 `:191` 逐字：

> **守恆 = 有守恆基質；其上的邏輯／命令是該基質的投影。**
> **資訊 = 沒有基質的純資料流**，可自由 fan-out。

`:196` 的推論直接答了使用者的問題：

> **adapter 邊界被釘在型別上**。**資訊↔資訊直接接**；一端有守恆基質就要 adapter。

## 二、⚠️ 而它推翻了一個排期上的分法

我先前（`draft/完整願景與它的邊界`）把硬體整包排在 2D／3D 面板之後。
**按這條律，那個分法是錯的**：

| | 例子 | 需要什麼 | 什麼時候做得了 |
|---|---|---|---|
| **純資訊源** | 回傳 JSON 的感測器服務、MQTT topic、序列埠讀數 | 一個輸入來源 ＋ `execute` 的一條路 | **今天** |
| **守恆網** | LED 接哪支腳、電阻分壓、I²C 匯流排 | 2D 接線 ＋ 全網求解 ＋ C2 資訊軸 | 等那些 |

> **通訊協定天生是資訊關係。守恆是接線的事，不是網路的事。**

而使用者上一輪提的 **MQTT／ROS2／HTTP API 全部落在第一格**。

## 三、常駐服務的真正角色是 **adapter**，不是通訊管道

`:196` 已經給了 Arduino 的實證：

> 「`digitalWrite`／`analogWrite` 是**資訊→守恆**，
> `digitalRead`／`analogRead`／`pulseIn` 是**守恆→資訊的投影**，
> `pinMode` 宣告的正是『這個接點在網裡是 driver 還是 reader』」

所以那個「常駐小 OS／服務」的價值不在它會講 MQTT，在於：

> **它把守恆側的一切關在自己裡面，對外只吐資訊。**

「誰在讀那支腳、會不會互相影響」的問題被它吸收掉了
——**同一個感測器，經過服務之後就變成純資訊了**。

⚠️ 這也給了那個服務一條設計判準：**它對外的介面若需要「先接線」，
它就沒有做完 adapter 的工作。**

## 四、判準：不是「吐的是不是數字」

`:187` 警告過一個混淆：

> 「一條 GPIO 線既是電壓（守恆）**又是**邏輯位階（資訊）」

所以判準是：

> **這個值，讀第二次會不會改變它、或改變別人讀到的？**

- 溫度透過 MQTT 推 `23.5`，十個訂閱者都拿到 `23.5` → **資訊**
- 一顆共用 ADC 通道被兩個元件同時採樣，會互相影響 → **守恆**（有基質）

## 五、⚠️ 而真正沒答的問題不是「非同步」——`cin` 已經是先例了

我原本以為的難題是「非同步輸入源怎麼接進同步執行器」。**查證後那不是問題**：

```ts
// interpreter.ts:154
setInputProvider(provider: (() => Promise<string>) | null): void

// execution-controller.ts:293
this.interpreter.setInputProvider(() => this.panels.consolePanel!.promptInput())

// components/cpp/input/execute.ts:48
const line = await ctx.awaitInput()
```

**`cin` 今天就是一個非同步輸入源**，而直譯器有現成的注入點。
一個 MQTT 感測器可以用**同一個形狀**接進來。

> **一個看起來要新機制的需求，先問「現有的哪一個東西已經是它的退化情形」。**

### 真正的問題是**失敗語義**

| | `promptInput()` | MQTT／HTTP |
|---|---|---|
| 會不會失敗 | ❌ 不會（使用者總會打字或取消） | ✅ **斷線、逾時、服務沒開** |
| 延遲 | 人的速度 | 網路 ＋ 硬體 |
| 值會不會過期 | 不會 | ✅ **上一次讀到的 23.5 五分鐘前的** |

而今天的執行模型**沒有「讀失敗」這個狀態**——`awaitInput()` 的簽名是
`Promise<string>`，它只能成功或永遠不回來。

⚠️ 這連到上一輪的那條邊界：

> **不要把硬體通訊接到 `SemanticBus` 上**——那會讓一個本來不會失敗的匯流排
> 開始需要處理逾時與重連。

**同一個道理適用於 `awaitInput`**：把一個會失敗的東西塞進一個不會失敗的簽名，
失敗就會以最糟的形式出現（永遠 pending，或吞掉錯誤回空字串）。

### 三個候選（都沒驗過）

1. **讀失敗 = 執行期錯誤**（像 `RUNTIME_ERR_*`）——最簡單，
   而⚠️ 學生看到的會是「程式壞了」而不是「感測器沒接」
2. **讀失敗 = 一個值**（`null`／上一次的值 ＋ 時戳）——教學上比較誠實，
   而它要求語義層有「可能沒有值」這個概念（型別系統的事）
3. **讀之前先確認連線**（一個 `hw:connect` 元件）——把失敗搬到一個
   明確的時間點，⚠️ 而那讓「接感測器」變成兩顆積木

**⚠️ 選哪個是教學決定，不是技術決定**——它決定學生第一次遇到硬體故障時看到什麼。

## 六、下一步的提議

`draft/完整願景與它的邊界` §七 的探針 B 是 `hw:led`——**那是守恆的例子**，
它逼出的是最難的那些（接點、C2、電氣求解）。

→ **改提議一顆純資訊的**（`hw:temperature` 之類）。它逼出的問題完全不同，
而且都是眼前的：

- `execute` 怎麼拿到值？→ **逼出通訊層的介面**（正是使用者想定的邊界）
- 讀失敗怎麼辦？→ **逼出 §五 那個選擇**
- 積木長什麼樣？→ 就是 `input` 類的一顆，形態這一格已經有答案

**而它不需要 2D 接線、不需要 C2 資訊軸、不需要電氣求解。**

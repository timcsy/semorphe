# 元件目錄結構與膠囊契約（設計，未承諾）

> 日期：2026-08-07
> 怎麼冒出來的：談 ArduinoCAD 何時併入時，使用者問「semorphe 是不是還沒準備好元件」。往下追發現協定已定（[concepts/元件](../concepts/元件.md)）但**協定刻意不管檔案佈局**，而佈局正是碎裂的所在。使用者接著提出兩個新目標——**社群擴張**與**測試分兩層**——那兩個目標解掉了原本平手的未決題。
>
> **狀態：captured ≠ committed。** 本檔是設計，出口是 vision 的路線圖項目，要人拍板。
> **理論地基**：[concepts/元件](../concepts/元件.md)（五槽／關係律／三軸正交／薄協定判準）。
> **順序上的前置**：[元件膠囊重構](2026-08-05-元件膠囊重構.md)、[硬體域併入計畫](2026-08-05-硬體域併入計畫.md)。

## 一句話

**目錄沿元件切；共同測從宣告推導、不放進膠囊；自證測放進膠囊、強制正負兩向。宣告即紅燈。**

## 為什麼是現在談佈局

協定（`concepts/元件.md`）已經定案並進長期層，但它是**薄協定**——只標介面，刻意不管目錄。
而碎裂全部發生在目錄上：181 顆元件平均散在 **7.9 個檔**，`≤2 檔的元件是 0 個`。

`元件.md` 自己已經推論出這條不變式，只是還沒落地：

> **就近性**——一個元件的實作**應該只出現在它自己的資料夾**

所以「用元件當目錄」不是新提案，是**把一條已拍板的推論落地**。

## 一、佈局：域 → 語言 → layer → 元件

層級順序也是 `元件.md` 定的：「一個元件的家由『域 →（若是 software）語言 → layer』三段決定」。

```
hardware/arduino-uno/
ui/button/
software/cpp/lang-library/cpp_vector_declare/
software/universal/if/            ← 這一格卡在下面那個未決
```

### 已解：universal 元件是**一顆**膠囊，分化的投影住語言側

`元件膠囊重構` 懸著的「一顆還是每語言一顆」，原本兩案平手（一顆＝P9 乾淨，每語言一顆＝膠囊完整）。
**社群擴張這個新目標讓它不再平手**：

| | 社群加一個 Python | 社群加一顆新的通用元件 |
|---|---|---|
| 每語言一顆 | 要建 **181 顆** universal 膠囊 | N 個語言各建一顆 |
| **一顆 ＋ 分化投影住語言側** | **一棵新資料夾樹，既有零編輯** | N 個新檔，各在明顯位置 |

**沒有貢獻者會接受第一列。**

```
components/if/                    身分、接點、參數、（共用的）形態與行為
languages/cpp/projections/if/     碼形態、lift
languages/python/projections/if/
```

副作用：**P9 從此靠結構守，不靠護欄量**——通用膠囊裡不出現任何語言名，加語言＝新增一棵樹、拔語言＝刪一個資料夾。

> ⚠️ 理由要記成**社群擴張**而不是 P9。P9 是紀律，社群是「有沒有人願意來」——後者才是真正決定它的那個。原決策時沒有這個資訊。

### 仍未決：`componentId` 命名空間

原本只是「`arduino-uno` 要不要 `hw:` 前綴」的美感問題。**一旦開放社群就變成阻斷性的**——
第二個人貢獻 `servo` 就撞名，而命名空間定錯之後要改會動到所有存檔。

## 二、碎裂與因式分解的分界

一個貫串全篇的判準，值得單獨立出來：

> **碎裂的痛不在「碰幾個檔」，在「碰幾個既有的共用檔」。**

- 加一個通用概念要在每個語言說它怎麼寫——**這件工作不可約**，跟檔案怎麼擺無關。
- 差別是它長成 **N 個新檔、各在明顯位置**（可以看、可以刪、可以數），
  還是 **N 次對既有共用檔的編輯**（`universal-concepts.json` 加一筆、某個 switch 加一個 case、`index.ts` 加一行註冊）。

後者才是碎裂：**每一次編輯都可能弄壞別人的，而且沒有一次是看得見的。**

## 三、膠囊契約：測試分兩層

### Part 1：共同測——**推導**的，不放進膠囊

⚠️ **不得每顆一份。** 500 份長得一樣的共同測 = 複製了 500 份同一個真相（本專案的頭號病），
而且會漂移：改了協定，改不到的那幾份會安靜地繼續綠。

**形式**：一個 harness 走過 `components/*/component.json`，從宣告推出案例。膠囊裡不放檔。

推得出來的至少有：五路是否齊備、**符合性**（每個形態的接腳集合 == 語義接腳）、往返是不動點、
宣告的 `accepts` 與實際邊的 `relation` 自洽、實作沒洩漏到 kernel／app／render、實作只出現在自己資料夾。

> 符合性在 `元件.md` 裡目前是「**無名，只有零星 guard test**」——這個設計給它一個家。

**這其實就是現在那 17 條護欄，換了位置：**

| | 現在（全域掃描） | 膠囊之後（每顆的合約測試） |
|---|---|---|
| 形式 | 掃全 repo，報一個數字 | 這顆過或不過 |
| 基線與棘輪 | 要 | **不要**——沒有「還剩幾筆」 |
| 誰維護 | 中央 | 沒有人，從宣告長出來 |
| **貢獻者送出前跑得了嗎** | **跑不了** | **跑得了** |

最後一列對社群是決定性的。

**分域是自動落出來的**：一顆元件沒宣告守恆接點，守恆相關的檢查就產出零個案例。
協定仍然不需要理解 `kind`——那正是「`kind` 是不透明酬載」的兌現。

### Part 2：自證測——人寫的，放進膠囊

這顆元件的**語義**。`vector<int> v = f()` 必須是複製不是共用——這推導不出來。

**難題不是怎麼寫，是怎麼防空洞。** `it('works', () => expect(true).toBe(true))` 也會綠。
而這專案踩過那個坑的精確版本：五支「通過」是假的，**被測的概念根本沒出現在語義樹裡**
（用 `static_cast` 代測 `dynamic_cast`）；加上「必須真的出現在樹裡」之後，通過數 17 → 12。

兩條機械後設檢查：

1. **每支自證測必須證明它真的碰到這顆元件**——`componentId` 出現在語義樹裡，或行為真的被執行到
2. **強制正向與負向兩向**。只有正向的話，一個過寬的實作會全綠——095 若沒有「`num >> 1` 必須仍是位移」那支負向，一條把所有位移都認領走的規則會通過全部測試

## 四、TDD 的形狀：宣告即紅燈

TDD 通常卡在「要先寫一支會紅的測試」，而人會偷懶。這裡不用寫：

1. 建 `component.json`，宣告身分／接點／參數 —— **這就是規格**
2. harness 立刻產出 N 支紅燈：沒有形態、沒有行為、符合性無從驗
3. 一格一格填，每填一格轉綠一支
4. 語義（Part 2）在寫 behavior **之前**寫

**你不需要寫那支會紅的測試——你宣告了一顆元件，紅燈自己出現。**

**這直接治「殼」**：殼 = 宣告了路徑但沒有實作。現在它是報表上的數字，膠囊之後從第一天就是紅的。
（095 實作 istringstream 時我先加了執行器，孤兒實作護欄才叫。膠囊 TDD 下那個紅燈會在我寫執行器**之前**亮，而且亮在我自己的資料夾裡。）

### 膠囊長相

```
components/if/
  component.json      身分、接點、參數      ← 規格，紅燈的來源
  forms/              積木、（共用的）形態
  behavior.ts
  spec.test.ts        自證測（人寫，正負兩向）
                      ← 共同測不在這裡，它從 component.json 推導
```

## 五、三條紀律（2026-08-07 人已同意）

1. **共同測不得超出協定。** 在協定裡的可以測，不在協定裡的不是共同測。
   推論：**新增一條共同測 = 修改協定 = 要人拍板**，同一個閘門，不另開後門。
   這擋掉最常見的退化——共同測慢慢變成風格警察（命名規則、註解格式、檔案大小），而那些都不在協定裡。
   也擋掉另一個方向：共同測若能無限成長，每加一條就讓既有元件全紅，於是沒人敢加、或加得很鬆。
2. **自證測強制正負兩向。** 對貢獻者是實實在在的門檻，但這一輪救最多次的就是負向斷言。
3. **宣告了沒實作的路徑：擋 merge，但允許明確宣告 `skipPaths` ＋ 理由。**
   不擋的話殼會回來；全擋的話沒辦法漸進貢獻。宣告理由這條的門檻見
   [history/018](../history/018-清償從搬檔案改為把清單換成宣告.md)——已有護欄在看理由會不會被濫用。

## 六、社群 PR 因此可以機械判定

| 判定 | 誰做 |
|---|---|
| 共同測全綠 | 機器（推導出來的，賴不掉） |
| 自證測存在且真的碰到這顆元件 | 機器 |
| 自證測有正向也有負向 | 機器 |
| **語義對不對** | **人——但只需要讀那一個資料夾** |

**審查者不需要理解整個系統，只需要理解一顆元件。** 這是膠囊真正買到的東西。

## 七、順序不能反

本專案自己的診斷是「**AI 元件管線把碎裂模板一起規模化**」。
skill 是放大器——**它放大的是它寫進去的那個形狀**。

膠囊沒定就先寫社群 skill，等於把現在的 7.9 檔規模化到社群。
與併入計畫同一條紀律：**膠囊先，管線後。**

## 八、剪枝力要守住

`元件.md` 的警語：「一切都是元件」當口號是空的——泛到能裝任何東西＝沒有剪枝力的假母概念。

新域的門檻不是「想不想」，是**五槽填不填得滿**：身分？接點＋關係律？形態＋符合性？行為＋時鐘？組裝？
填得出白拿整套機器，填不出就代表那個域不是元件。

三域表已經兌現過一次——UI 填完之後**學到了新東西**（唯一沒有守恆關係的域，這解釋了它為何最好教）。

**Agent／AI 技能目前填不滿**：接點講不出關係律，多表示只有一份 `SKILL.md`（沒有第二個表示就沒有符合性可守）。
它不是被剪掉，是**還沒進場**——要納入得先填那兩槽。

## 還沒想清楚的

- **`componentId` 命名空間**（見上，開放社群後是阻斷性的）
- **現在那 7.9 個檔裡，有幾個其實不隨元件變、應該留在機制側。** 這個拆分才是就近性從 7.9 走到 1 的實際路徑，也決定這件事是兩週還是兩個月。**未量。**
- **181 顆裡通用的佔幾顆、它們的槽實際分化到什麼程度。** 未量。
- **共同測 harness 與現有 17 條護欄的遷移路徑**——哪幾條可以直接改寫成推導式、哪幾條本質上就是全域的（例如全樹流敏感約束）
- **`spec.test.ts` 的「真的碰到這顆元件」怎麼判**——語義樹裡出現 `componentId` 是一種，行為被執行到是另一種，兩者對純宣告式元件（`skipPaths: ['execute']`）都不成立

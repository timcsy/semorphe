# Semorphe 加 cella 與 DDD——一個帶著證明的上下文地圖

> 日期：2026-10-05
> 怎麼冒出來的：使用者問「這樣的 Semorphe 和 cella 結合的模式和 DDD 有什麼關係嗎？」
> 接在 [cella 接受的程式保證了什麼](2026-10-05-cella-接受的程式保證了什麼.md) 與
> [cella 推廣到程式語言以外的領域](2026-10-05-cella-推廣到程式語言以外的領域.md) 之後。
>
> 🟡 **狀態：對照，未決**。沒有排程；它主要的用處是**給套件協定一套業界通用的詞彙**
> （見 [套件協定](2026-09-26-套件協定.md)）。

一句話：**這個結合模式是 DDD 的嚴格化**——DDD 用對話與程式碼維持的邊界與不變量，
在這裡變成機器檢查得了的型別與證明。

## 一、戰略層：幾乎一對一

**限界上下文（Bounded Context）＝ cella 的原則 C15。**

```
DDD     「客戶」在銷售與客服是兩個模型，用轉譯連起來
C15     int 在 C++（32 位元、溢位是 UB）與 Python（任意大）是兩個型別，用嵌入連起來
```

差別：DDD 的轉譯靠人維護；C15 的轉譯**證過**（`toInt` 嵌入＋對應定理）。
C15 否決的「以名字等同」就是 DDD 警告的「全公司共用一個模型」。

**上下文地圖（Context Map）：**

| DDD 的關係 | 在這裡 |
|---|---|
| Customer–Supplier | 我們下游、cella 上游；我們提需求、他們排進去（explicit 模式、Merkle、洞的回報）——**不是 Conformist** |
| Published Language／Open Host Service | `index.json`、`cpp.*` 的名字、判決的 JSON |
| Anti-Corruption Layer | 走訪器＋每顆元件的 `contract.cella`：把語義樹翻成 cella 的模型 |
| Shared Kernel | 套件協定的「詞彙套件」：`lang-cpp` 與 `hardware-arduino` 共用同一套關係律 |

🔴 **防腐層那一格最要緊**：`Nat` 那個缺陷（第 305 刀，C15 之後才看見）就是**防腐層翻錯**
——把我們的 int 翻成另一個上下文的東西，驗的是另一支程式。
⟹ 我們的對齊測試（負向對照、差分比對）在 DDD 的語彙裡就是**防腐層的測試**。

**共通語言（Ubiquitous Language）**：元件名詞表、cella 的 `vocabulary()`，以及還沒做的
「錯誤訊息要講領域的話」（「13 號腳 62 mA 超過上限」而不是 `InRange 16 60000`）
——那是把共通語言一路帶到使用者介面。

## 二、戰術層：DDD 在執行期守的，這裡在編譯期證

```
值物件（Value Object）   cpp.IntN ＝ 值 ＋ 在範圍內的證明 —— 自我驗證的值物件,
                        而且是「造不出不合法的值」,不是「建構子丟例外」
規格（Specification）    NonNeg、LtB、InRange —— 具名謂詞,而且證得了,不只求得了值
聚合與不變量（Aggregate）「組裝」主體 —— Σ RAM ≤ 2048、一條網一個 driver
                        不屬於任何一顆元件（就近性說的）,屬於聚合根
領域事件（Domain Event） 匯流排上的 execution:* 事件
```

## 三、超出 DDD 的三件事

1. **一個模型，多種投影**：同一棵語義樹同時是積木、程式碼、流程圖、cella 的命題
   ——「唯一真實，各式投影」。DDD 的模型在一個上下文裡通常只有程式碼一種表達。
2. **帶著證明的上下文地圖**：上下文之間不是信任，是證明＋指紋。上游改了，Merkle 說得出
   是哪些定義、哪些下游契約要重驗——DDD 裡那通常靠整合測試，或出事才知道。
3. **判官的種類**：DDD 不分「算得出來」與「要量測」的不變量；推到物理領域後要分
   formal／reference／human（演繹／經驗之牆，見 [一條比我們自己的軸更好的牆](2026-09-30-一條比我們自己的軸更好的牆.md)）。

## 四、DDD 能還給我們的

1. **詞彙**：套件協定的層與關係可以用 Context Map 的名詞重標一次——跟 cella 或外部的人溝通不必重新解釋。
2. **一個警告**：Shared Kernel 要**共同治理**，否則變成雙方都不敢動的耦合點。
   詞彙套件與 cella 的 Library 一旦有第二個發布者，「誰有權改、改了怎麼通知」就是這個問題
   ——cella 說的「第二個發布者觸發簽章」在 DDD 裡就是 Shared Kernel 的治理。
3. **一個檢查點**：與 cella 的關係刻意維持在 Customer–Supplier，不要滑向 Conformist。
   哪天變成「他們發什麼我們只能接什麼」，防腐層就要變厚。

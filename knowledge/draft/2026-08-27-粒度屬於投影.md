# 粒度屬於投影——而層級改的今天只是名字

> 日期：2026-08-27
> 怎麼冒出來的：使用者逐字——
>
> > 「不同的漸進揭露層級會需要不同的**粒度**，或許這也是互相轉換的關鍵，
> > 來處理程式碼和積木的**多對多**問題。」
>
> **狀態：設計，未升格。** 出口是 vision 路線圖，而那道閘在人。
>
> ⚠️ **本檔同日修正過三處**（都是我自己第一版說得太寬）：
> §四「同一個旋鈕的兩端」→ **粒度是旋鈕、解析度是推導出來的需求** ·
> 新增 §四之二「上面只講了讀，寫是另一回事」（雙向轉換的兩條律） ·
> §五② 原本寫「被 `.sem` 解掉了一半」→ **`.sem` 幫不上這一題**。

## 一、今天的層級改的是【詞彙】，不是【形狀】

`src/core/sync-controller.ts:427` 的 `downgradeComponentsForLevel`：
看不見的節點換成它宣告的父概念（`abstractComponent`），
並把原本的身分記進 `identityBeforeDowngrade` 好讓 blocks→code 還原。

```
今天    層級 → 看不見的節點【換一個名字】，位置與數量不變
提案    層級 → 【幾顆節點】本身就不一樣
```

⚠️ 而降級是套在 `cloneTree(tree)` 上的——**真實沒有被改**，改的是投影。
這一點很重要：它代表今天的機制**已經站在對的那一側**，只是表達力不夠。

## 二、🔴 而這條縫已經開著了（2026-08-27 量測）

掃全部宣告了 `abstractComponent` 的元件，比對子／父的子槽：

```
cpp:loop_for       → cpp:loop_count   掉出宣告的槽：init, cond, update
cpp:ternary        → cpp:if_else      掉出：true_expr, false_expr
cpp:array_2d_at    → cpp:array_at     掉出：row, col
cpp:vector_declare → cpp:var_declare  掉出：values, source, size, fill
cpp:map_at         → cpp:array_at     掉出：key
cpp:loop_do_while  → cpp:loop_while   掉出：cond
…共 14 對以上
```

⚠️ **量的是宣告的不一致**（子有父沒宣告的槽），**不是**「執行時真的掉東西」
——後者要另外驗。而這就是「概念降級」那個已知問題的骨架。

> **所以「粒度」不是一個新需求，是一個已經在系統裡、而沒有被命名的東西。**

## 三、它可以從既有判準推出來

`concepts/投影.md:607`「排版屬於投影，不屬於真實」的判準逐字：

> **它換一個投影還存在嗎**

拿它問粒度：「這個 for 迴圈顯示成一顆盒子」——換到程式碼投影還存在嗎？
**不存在**，程式碼永遠有 init/cond/update。

> **所以粒度屬於投影，不屬於真實——與排版同一族。**

推出三件事：

| | 降級（今天） | 粒度是投影（提案） |
|---|---|---|
| 真實 | 被改寫（換名字） | **不動** |
| 還原 | 靠 `identityBeforeDowngrade` 側表 | **不需要**——真實從來沒變 |
| 損失 | 語義的（那顆節點的身分沒了） | 只是視覺的（摺起來） |

🔴 那張側表今天的存在，**正是「真實被改壞了所以要補」的證據**。
摺疊不需要那張表。

## 四、對「多對多」的判斷——它是兩個問題，而解不同

```
A  一顆積木 ↔ 好幾個程式碼構造   計數迴圈 ↔ for(int i=0;i<n;i++)
   🟢 粒度直接解掉：固定層級之後，那是「摺疊深度」決定的一個函數

B  一行程式碼 ↔ 好幾顆積木       int x = f(a) + g(b);  一行六顆
   🔴 那是 [對照的解析度](2026-08-20-對照的解析度.md)，解是【字元級區間】
```

### 🔴 而兩者有一個耦合，那份 draft 自己寫著

> 「**一行一個語句的時候，行級與字元級沒有差別。
> 而那正是第一課的形狀——所以這個缺陷在第一課量不到。**」

反過來讀：**層級越粗，解析度的問題咬得越輕**。

> **粒度是旋鈕，解析度是它推導出來的需求。**
>
> ```
> 粗粒度 → 一顆積木蓋好幾行 → 行級高亮【夠】
> 細粒度 → 一行好幾顆積木   → 行級高亮【不夠】
> ```

⚠️ **這一句 2026-08-27 同日修正過**：原本寫的是「同一個旋鈕的兩端」，
而它們不是同一個東西的兩端，是**一個決定另一個**。
差別有實務意義：**如果課程永遠停在粗粒度，字元級高亮永遠不必做。**

→ 如果這成立，它改變 `對照的解析度` 的**優先序**：字元級不是「哪天要做的功能」，
是「**開放到某個層級之後才付得起的入場費**」。
⚠️ 而那份 draft 的出口條件第三條「有第三種投影上線（流程圖面板）」
**已經在 2026-08-24 觸發了**。

## 四之二、🔴 而上面只講了【讀】——寫是另一回事

摺起來是讀的方向。而學生在 L0 拖一顆計數迴圈、填「從 0 到 5」時，
真實必須變成有 init/cond/update 的細結構——**那不是摺疊，是「從粗的長出細的」**。

兩個方向都要，這就不是一個投影，是一組**雙向轉換**，而它必須滿足兩條律：

```
摺了再展開   ≡ 原本      不能憑空多東西
展開再摺起來 ≡ 原本      不能把使用者【看不到的東西】弄丟
```

🔴 **第二條正是使用者最初擔心的嚴格版本**：學生在 L0 編輯一個
「裡面藏著 `i -= 2`」的迴圈時，那個 `-= 2` **必須活下來**
——即使畫面上沒有任何地方顯示它。

### 🟢 而這個 repo 已經有一個成功的先例：空行

`concepts/投影.md:609` 逐字：

> 2026-08-19 使用者拍板：**空行是排版**。程式碼投影記住使用者的垂直留白，
> 重寫時對回去；積木那側看不到、也加不出空行。

**同一個形狀**：看不到、改不到、而它活著。

⚠️ 差別在**代價**：空行是行末的空白，而 `i -= 2` 是**一段語義**。
把它藏在一顆摺起來的積木裡，等於在真實裡放一個「這裡有你看不到的東西」
——**而 P6 說降級必須可見**。

> 那顆摺起來的迴圈，畫面上要不要有一個記號說「裡面還有你沒學到的東西」？

🔴 **這一題原本被列在 §五① 當成次要的，而它其實是這個設計成不成立的那一格。**

## 五、兩個硬問題

- [ ] **① 🔴 摺起來的東西，怎麼讓學生知道「裡面還有」？**（**升為主要**，見 §四之二）
      P6 逐字「降級……**必須可見**」——一顆摺起來而看起來像普通積木的東西是
      **安靜的損失**。而加一個「裡面還有」的標記又與 P4「為學生減少選項」拉扯。
      ⚠️ **這是教學判斷，留給人。**
      ⚠️ 而它不只是「要不要加個記號」：它是**雙向轉換第二條律**的介面
      ——那個看不到的東西必須活著，而「活著卻不出聲」與「活著並且說一句」
      是兩種不同的產品。
- [ ] **② 老師用進階寫法、學生開在 L0**
      `for (int i = 10; i > 0; i -= 2)` 摺不成「從 0 數到 n」。
      🔴 **2026-08-27 修正：`.sem` 幫不上這一題。**
      原本寫「被 `.sem` 解掉了一半」——而量測顯示那條線在別的地方：
      `.sem` 只在**程式碼相同而意圖不同**時有用（LED vs 繼電器），
      而這裡程式碼**就是不一樣**（`i -= 2`），差別在程式碼裡就在。
      > **意圖只有在程式碼相同時才需要被保存。**
      → 所以這一題**完整地**開著，見 [版面與檔案 §.sem④](2026-08-24-版面與檔案.md)。

## 六、⚠️ 而它可能讓「漸進揭露把選項轉嫁給老師」那個抱怨消失

使用者 2026-08-12 逐字：「我會乾脆叫學生把全部都打勾，那有沒有這個漸進揭露是沒用的」。

如果摺疊做得夠好，老師不必選「開哪些概念」，只要選「**摺到哪一層**」
——**那是一個比勾選清單少很多決定的介面**。

⚠️ 這是推論，不是使用者說的。

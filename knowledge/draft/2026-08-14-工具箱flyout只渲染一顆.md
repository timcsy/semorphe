# 工具箱的 flyout 只渲染一顆——而它不是這一輪造成的

> 日期：2026-08-14
> 怎麼冒出來的：使用者回報「陣列與列表這邊行為怪怪的」，附截圖：
> flyout 只顯示**一顆積木的片段**，位置跑到左上角。
> **狀態：✅ 根因找到並修好**（2026-08-14，`block-registrar` 的重複定義）。
> 保留這份是因為**排錯的路徑**值得留——四個假設錯了三個。captured ≠ committed。

## 🔴 首先：它不是這一輪的迴歸

使用者**第一張截圖**（回報「沒有 initializer」那次，`[Image #7]`）
是在積木改成命令式**之前**拍的，而**那張的 flyout 已經是壞的**
——同樣只有一顆片段。

> **兩張截圖的症狀相同，而中間隔著一次改動。
> 那個改動不可能是原因。**

⚠️ 而我第一時間把它當成自己的迴歸去修（顏色鍵那次是真的迴歸，
但**它修好之後症狀沒變**）——那是一個獨立的缺陷，見下。

## 在瀏覽器裡量到的（`localhost:5173`，真滑鼠點擊）

```
分類數                 12（開了 L0–L3c 之後）
「陣列與列表」該有      33 顆（tests/baselines/toolbox.json）
flyout 實際渲染         1 顆
console 錯誤            0 筆      ← **不是 init 拋錯**
flyout 尺寸             150 × 300  ← Blockly 的**預設值**，不是算出來的
window resize 之後      高度 → 635（跟上容器），**而積木數仍是 1**
```

## 已排除的三個假設

| 假設 | 怎麼排除的 |
|---|---|
| 某顆積木的 `init` 拋錯 | console 全乾淨；`window.onerror`／`unhandledrejection`／`console.error` 三個都攔了，零筆 |
| 是這一輪把積木改成命令式造成的 | 使用者改動前的截圖症狀相同 |
| 分類真的只有一顆積木 | 快照說 33 顆 |

## 兩條線索

**① flyout 的尺寸是 Blockly 的預設值（150×300），而 resize 之後高度會修正。**
那指向**初始化時序**：flyout 建立時容器還沒有尺寸。
⚠️ 而高度修正之後**積木數仍是 1**，所以尺寸只是症狀的一半。

**② 「每個分類都剛好 1 顆」**——資料／控制／陣列／文字／堆疊全都是 1。
那個「剛好」不像過濾（過濾會讓各分類數量不一），比較像
**渲染在第二顆就停**，或**flyout 的內容根本只收到一顆**。

## ⚠️ 而新加的 e2e 是假陽性

`e2e/toolbox.spec.ts` 斷言「每個分類至少 2 顆」，**而它是綠的**。

兩個原因，兩個都要修：

1. **e2e 起的是全新狀態（`localStorage.clear()`），只有 5 個分類**
   ——使用者的 12 分類世界它從來沒進去過
2. 它的 `blocks.first()` 可見性檢查可能抓到**上一個 flyout 的殘留**
   （Blockly 重用 DOM）

> **一支測試綠，不是它有效的證據——它可能量的是另一個世界。**

## 順帶修好的一個真迴歸（已 commit `6a7466b`）

`CATEGORY_COLORS.containers` 打錯字（正確是 `cpp_containers`），
而 `Record<string, string>` 讓 tsc 放行。改成 `as const` 之後
tsc 抓得到——**反向驗證過**。那是真的缺陷，只是**不是這個症狀的原因**。

## ✅ 根因：同一個鍵被賦值兩次，而第二次是靜默的覆蓋

```
block-registrar.ts:604    Blockly.Blocks['cpp_array_declare'] = { … }   ← 這一輪新加的（動態插槽）
block-registrar.ts:1690   Blockly.Blocks['cpp_array_declare'] = { … }   ← 既有的，**後定義的贏**
```

於是新定義**從來沒有生效過**。而舊的用 `ARRAY_DECLARE_INPUTS.value[0]`，
那個常數是**從 `blocks.json` 的 `args0` 導出的**（`core/block-input-names.ts:79`）
——把 `args0` 移除之後它變成**空字串**：

```
Error: Value inputs must have a non-empty name
  at BlockSvg.init (block-registrar.ts)
  at BlockFlyoutInflater.createBlock          ← 在 flyout 的建構裡
```

**而 console 是乾淨的**——Blockly 把它吞在 flyout 的 inflater 裡，
症狀只剩「後面的積木都不見了」。

> **同一個鍵被賦值兩次，第二次是靜默的覆蓋
> ——而雙重真相護欄看的是「JSON 與命令式」，看不到「命令式與命令式」。**

### 🔴 而這是這一輪造成的——我前一份 draft 說「不是」，那句話錯了

前一份的推理是「使用者改動前的截圖症狀相同」。而**那張截圖是在同一輪的
更早一步拍的**——`array_declare` 的 `args0` 在那之前就已經被我移除了。
兩張截圖之間沒有改動，是因為**兩張都在缺陷之後**。

> **「改動前後症狀相同」只有在你確定哪一刻是「前」的時候才成立。**

## 排錯路徑：四個假設錯了三個

| # | 假設 | 怎麼排除的 | 對嗎 |
|---|---|---|---|
| 1 | 某顆積木的 `init` 拋錯 | console 全乾淨，三種 handler 都攔了 | 🔴 **對，而 console 看不到** |
| 2 | 不是這一輪造成的 | 使用者改動前的截圖症狀相同 | ❌ 錯（見上） |
| 3 | 分類真的只有一顆 | 快照說 33 顆 | ❌ 排除正確 |
| 4 | flyout 的 layout 壞了 | 尺寸是 Blockly 預設值、resize 後修正 | ❌ 那是症狀不是原因 |

**找到它的是這一步**：`ws.newBlock(type)` 逐顆試建——
`cpp_array_declare → Value inputs must have a non-empty name`。

> **一個被吞掉的錯誤，要用「把那件事單獨做一次」逼出來
> ——而不是去讀它沒有留下的訊息。**

## 一、`block-registrar.ts` 有十二對 `plus_`／`minus_`，落成三個家族

2026-08-10 實測（`src/ui/block-registrar.ts`）：

| 家族 | 積木 | 加什麼 |
|---|---|---|
| **A 參數列** | `u_func_def`、`c_forward_decl` | dummy input ＋ 型別下拉 ＋（名字輸入） |
| **B 運算式列** | `u_print`、`u_func_call`、`u_func_call_expr`、`u_var_declare`、`u_if` | value input |
| **C 變數選擇列** | `u_input`、`u_input_expr`、`c_printf`、`c_scanf`、`c_scanf_expr` | `SEL_n` 欄位 |

### A **已經是兩份拷貝，而且已經漂移**

| 方法 | 相似度 |
|---|---|
| `loadExtraState` | **100%** |
| `minusParam_` | 96% |
| `saveExtraState` | 92% |
| `plusParam_` | 89% |
| `rebuildParamLabels_` | 33% |

三個變異點**全部是資料不是邏輯**：

1. **要不要名字欄位**——`int a` vs `int f(int, int);` ⇒ 一個布林
2. **括號的標籤**——⚠️ **`c_forward_decl` 的括號沒有走 i18n**（寫死 `"("`／`")"`），
   而 `u_func_def` 走 `Blockly.Msg`。**那是抄過去時漏掉的，不是設計**
3. **插在哪個 input 之前**（`'BODY'` vs `'PARAMS_END'`）

`rebuildParamLabels_` 那 33% 有一半是**假的差異**——分支順序調換、中間變數內聯。
那是抄完之後各自微調留下的漂移。

> **抽出工廠不是為了讓 lambda 好升級，是因為它已經重複了。**
> 而重複的兩份已經開始漂移——i18n 那筆就是證據。
> 判準是 `history/033` 的那條：**重做時會不會漏掉上次學到的東西**。抄的時候就漏了。

### ✅ A 已抽（2026-08-10，`specs/107-params-row-factory`）

行為程式碼 2 份 → 1 份，兩顆各剩六行宣告。順手把 `c_forward_decl` 的括號
統一走 `Blockly.Msg`（**fallback 是原字元**，所以顯示完全不變）。

**而這次最值得記的不是結果**：查覆蓋時發現那 12 對 `plus_`／`minus_`
**零行為覆蓋**，`block-registrar.test.ts` 的四支測試是 grep 檔案文字。
那條約束**直接決定了工廠放在同一個檔**——搬走會讓那四支因為錯誤的理由變紅，
而這次沒有第二個 oracle 能分辨對錯。
→ 教訓進 `experience.md`：**沒有行為覆蓋的地方，重構的形狀會被測試的形狀綁架。**

### 未決

- **B（5 份）與 C（5 份）** 收益更大但動作也更大
- **lambda 那六顆要不要從文字欄位升級成 A**，仍然是**教學決定**。
  抽出工廠之後成本從「82 行 × 6」降到「六行宣告」，
  **但成本降低不構成該做的理由**——判準仍是 `specs/105` 寫下的三個訊號

## 二、積木型別與元件身分是**兩份會漂移的命名**

2026-08-10 實測：

```
186 顆積木型別：  c_ 92 ｜ cpp_ 67 ｜ u_ 27
id 與 blockDef.type 相同 120 顆，**不同 66 顆**

  cpp:stack_peek     →  blockDef.type = cpp_stack_top      ← 名字本身不同
  cpp:char_is_alpha  →  blockDef.type = cpp_isalpha
```

那 66 顆是比 `id` 欄位。**比 `blockDef.type` 是 86 顆**——接近一半。

### 用 G 的同一套判準量積木型別（2026-08-10 實測，186 顆）

| | 積木型別 | 身分（G 整理後） |
|---|---|---|
| **與身分不同名** | **86** | — |
| 操作詞不在封閉詞彙 | **24** | **0** |
| 裸的函式庫名（拆不出主體） | **63** | **0** |
| 主體不在前 | 0 | 0 |

> **G 把身分的六項驗收全部收到硬性零，而積木型別上同樣的判準是 24 與 63。**

**不同名的方式有三種，第三種最能說明問題**：

```
u_number       ≠  cpp:literal_number    ← 積木名是身分名的截斷
u_count_loop   ≠  cpp:loop_count        ← 主體與操作的順序相反
cpp_stack_top  ≠  cpp:stack_peek        ← 用了 G 換掉的舊詞
```

`stack_top` 是 G 從封閉詞彙裡換掉的（`peek` 才在表上）；`count_loop` 是 G 的
規則③「主體在前」抓到而改成 `loop_count` 的那一顆。

> **積木型別保存著 G 之前的整套舊命名——它是那次改名的化石層。**
> 「亂」的準確說法不是隨機，是**兩個時間層疊在一起**：
> 身分停在 G 之後，積木型別停在 G 之前。

### 而前綴本身也是化石

`u_`／`c_`／`cpp_` 對應「universal / cpp core / cpp std」，
而 **D 之後 177 顆身分全部是 `cpp:`**——那個三分法在身分層已經不存在。

它與概念宣告的 `layer` 欄位是**兩份分類，而邊界不一樣**：

```
u_ 前綴          27 顆
layer: universal  29 顆
```

差 2 顆。**那個差就是雙重真相在漂移的證據。**

### ⚠️ 改積木型別名 = 一次存檔遷移

`SavedState` 存 `{ tree, blocklyState, code, … }`，而載入時
**`blocklyState` 是主要來源**（`app.ts:566` 先 `setState`，再「generate code from
restored blocks」）。`blocklyState` 裡每顆積木帶著 `type: "u_if"`。

> G 那條「**趁還沒有版本的時候改名是免費的**」**在這裡不適用**
> ——`blocklyState` 已經在 v9 的版本鏈裡了（`storage-version.ts` 的 upgrade
> 有 `blocklyState` 欄位）。

### 未決（而我有一個明確的建議）

「刪掉 `u_` 還是改名」有第三個答案：**讓積木型別從 conceptId 導出**
（`cpp:stack_peek` → `cpp_stack_peek`），一個名字而不是兩個。
那正是第一顆膠囊已經在做的事（`forms/blocks.json` 的 `id` 就是 conceptId）。

> **但不要現在單獨做。** 它會與 F（膠囊搬家）撞在一起——每顆元件搬進膠囊時
> 本來就要碰它的 `forms/`。**兩件事合成一次做，遷移只付一次**；
> 分開做要付兩次，而且中間那段時間有一半元件是新名一半是舊名。

## 二之二、積木這一整層**沒有規範也沒有機制**——名字和長相都是

| | 有規範嗎 | 有機制嗎 |
|---|---|---|
| 身分的名字 | ✅ G 的封閉詞彙 | ✅ 第二十七條護欄 |
| 接點 | ✅ | ✅ #29／#30 |
| **積木的名字** | ❌ | ❌ |
| **積木的形態** | ❌ | ❌ |

而 `concepts/元件.md:22` 把**形態**列為五槽之一，與身分、接點、行為、組裝
平起平坐。今天它**只有實作層**：12 對 `plus_`／`minus_` 各自長出來、
`c_forward_decl` 的括號漏掉 i18n、86 顆與身分不同名。

⚠️ **而形態的正確性沒有外部 oracle，那是結構性的**
（見 [等價與觀察集](../concepts/等價與觀察集.md) §七）——所以機制只能做到
「宣告了什麼就照什麼來」，**最後一哩是人看**。那正是標籤說謊那次
十八條護欄都不叫的原因。

### 未決：這需要一個路線圖項目，不是繼續當「教學決定」擱著

形狀大概是三段，而其中一段只有人能給：

| | 誰做 |
|---|---|
| **形態的設計語彙**（欄位 vs 插槽、動態 vs 固定、標籤句型、命名軸） | **內容是教學判斷** |
| 護欄（詞彙表與護欄一起交，否則是第八個「宣稱了沒有檢查」） | 我 |
| 瀏覽器實測進 CI | **成本要拍板**（`vision.md:162` 已標） |

> 名字與長相要**一起**定，因為它們是同一層。

## 三之二、殘差每天被算出來十九次，而沒有一次被記下來

29 個測試檔真的呼叫 `g++`，而它們在做**兩件不同的事**：

```
19 檔   直譯器輸出  vs  g++ 輸出        ← 模擬保真
 3 檔   g++(原碼)   vs  g++(產回去)     ← 來回保義（兩邊都是實體）
```

⚠️ **兩者混在同一批檔案裡而沒有被分開命名**，所以看檔名分不出來
——我自己一開始就把 fuzz 那批誤認成前者，查了才發現兩邊都是 `g++`。

而 **25 條基線裡沒有一條在量模擬與實體的殘差**。那 19 個檔把它當成
pass/fail 斷言，用完就丟。

### 未決（而這是清單上最便宜的一項）

1. **把兩種環路分開命名**——「模擬保真」與「來回保義」
2. **把殘差變成一條基線**——19 個檔已經在算了，只是沒記。
   收得到數字，而且不需要任何新的量測機制

理論地基見 [等價與觀察集](../concepts/等價與觀察集.md) §七：
**投影之間不對稱，只有一個接得到外部的權威。**

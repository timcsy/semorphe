## 軸 1：一個語義角色用什麼呈現

**實測**（186 顆積木的欄位／插槽）：

```
field_input        153      input_value       134
field_dropdown      44      input_statement    27
field_multilinetext  2      field_number        1
```

**而 14 個語義角色有多種呈現，84 個只有一種**：

| 角色 | 幾種 | 實例 |
|---|---|---|
| `value` | **4** | `input_value`×36 ｜ `field_input`×2 ｜ `field_number`×1 ｜ `field_dropdown`×1 |
| `type` | 2 | `field_dropdown`×15（`u_array_declare`）｜ **`field_input`×1（`cpp_new`）** |
| `obj` | 2 | `field_input`×42 ｜ `field_dropdown`×3（`cpp_string_at`） |
| `name` | 2 | `field_input`×37 ｜ `field_dropdown`×2 |
| `condition` | 2 | `input_value`×4（`u_if`）｜ `field_input`×2（`c_ifdef`） |

### ⚠️ 有些差異**可能是對的**，不要一起清掉

```
cpp_min   的 a / b  →  input_value    可以接任意運算式
cpp_swap  的 a / b  →  field_input    必須是變數（左值），接運算式沒有意義
```

**那是語義差異，不是漂移。** 而 `cpp_new` 的 `type` 用 `field_input`
（其餘 15 顆用 dropdown）看起來就是漂移。

> **這條軸真正要定的不是「用哪一種」，是「什麼情況下該用哪一種」的判準。**

**判準候選（我猜的，等你定）**：

| 情況 | 呈現 |
|---|---|
| 接受任意運算式 | `input_value` |
| 值域封閉且可列舉 | `field_dropdown` |
| 必須是識別字／左值 | `field_input` |
| 是一串陳述 | `input_statement` |

⚠️ 而 `c_ifdef` 的 `condition` 用 `field_input`——它是前置處理器的巨集名，
**不是運算式**。所以那也可能是對的。**判準要能解釋它。**

## 軸 2：可變數量的子項怎麼呈現

**實測**：`block-registrar.ts` 有 **12 對 `plus_`／`minus_`**，落成三個家族
（A 參數列 2 份、B 運算式列 5 份、C 變數選擇列 5 份），加上 105 新增的第四種。

| 做法 | 用在哪 | 代價 |
|---|---|---|
| 固定插槽 | 絕大多數 | 最便宜 |
| **一個文字欄位**（`childrenAsField`） | lambda 等 6 顆的 `params` | 四行宣告 |
| **動態插槽 ＋／−** | `u_func_def`、`u_print`… 12 顆 | 曾經是 82 行，抽工廠後六行 |
| **mutator ＋ 子積木** | `u_if` 的 elseif／else | 最貴 |

**已有的升級判準**（`specs/105` 寫下，三個訊號任一出現就升級）：

1. 使用者在該欄位打錯字造成的缺陷**出現第二次**
2. 需要對它做**逐項操作**（重排、單獨刪一個、下拉選單）
3. 該邊界情形從「測試裡的案例」變成**課程裡真的會教的東西**

> **這條軸只缺一件事：mutator（第四種）什麼時候用。** 目前只有 `u_if` 在用，
> 而沒有人寫下它與「動態插槽」的分界。

## 軸 3：標籤的句型

**實測**（182 條 `MSG0`）：

| 句型 | 條數 | 例 |
|---|---|---|
| 詞開頭 ＋ 1 槽 | 63 | `取得 %1 的大小` |
| 詞開頭 ＋ 2 槽 | 57 | `把變數 %1 設成 %2` |
| 詞開頭 ＋ 3 槽 | 33 | `建立 %1 變數 %2 = %3` |
| **槽開頭** ＋ 1 槽 | 10 | `%1 的末端元素` |
| 槽開頭 ＋ 2 槽 | 7 | `%1 的 %2 次方` |
| 詞開頭 ＋ 0 槽 | 5 | `跳出迴圈` |

**163 條詞開頭、19 條槽開頭。** 而槽開頭那批幾乎都是**運算式**
（`%1 的末端元素`），詞開頭那批幾乎都是**陳述**（`把…設成…`）。

**判準候選**：**陳述用祈使句（動詞開頭），運算式用名詞片語（主體開頭）。**
⚠️ 這條如果成立，19 條裡有幾條是例外要查。

## 軸 4：標籤要不要說出「作用在**哪裡**」

**這一條有血的教訓**：`stack`／`queue` 的 push 標籤說「Push %2 onto %1」——
`onto` 是堆疊語義，而佇列是加到尾端。**十八條護欄一條都不叫，學生第一眼看出來**
（`episodes/2026-08-07-學生說積木寫錯了`）。

**實測**：182 條裡 **34 條含位置／方向詞**：

```
陣列 %1 的第 [ %2 ] 格
串接文字 %2 到 %1 後面
把 %2 存到 %1 指向的位置 (*)
複製 %2 的前 %3 個字元到 %1
```

**判準候選**：

> **這個操作有沒有第二個同族操作，差別只在位置？有 → 標籤必須說出位置。**

`container_push` 在 stack 是頂端、在 queue 是尾端 → 必須說。
`string_length` 沒有「另一種長度」→ 不必說。

⚠️ **這條可能可以半機械化**：同一個 `axis` 下的多個 `form`，它們的標籤若**逐字相同**
就是可疑的。那是**排順序**不是下結論（`build-guardrail` 第 6 步）。

## 軸 5：保真度要不要標註 ⚠️ semorphe 這邊是零

**ArduinoCAD 已實作**（`PartReference`）：

```ts
approximate?: boolean   // 「造型為示意/近似——誠實標註」
photo?: string          // 「無則不冒充擬真」
source?: string         // 來源標註
```

**實測（24 顆零件）**：

```
{ approximate: false, source: 'Wokwi 擬真圖稿' }        ← arduino-uno / mega / nano
{ approximate: true,  source: '參數化幾何示範（非實物零件）' }  ← bracket
```

**它真的在用，而且兩個值都出現過。**

> **一個不宣告自己是近似的形態，會被讀成擬真的。**
> 與 P6 誠實降級是同一條原則的另一面：**降級要出聲，近似也要出聲。**

**未決**：積木有沒有對應的東西？候選——**這顆積木是不是課程降級後的替身**、
**這顆積木的標籤是不是簡化過的**。

## 軸 6：資訊卡／圖鑑要不要是形態的一部分

**ArduinoCAD**：24 顆零件裡 **21 顆填了 `info`**（`name`／`category`／`subtitle`／
`description`／`specs`／`reference`）。

```
LED（發光二極體）｜ 輸出/顯示 ｜ 單向導通、通電發光的基礎輸出元件
specs: { 極性: '有（anode / cathode）', 順向電壓: '約 1.8–3.2V（依顏色）',
         注意: '需串聯限流電阻（DRC 會檢查）' }
```

**semorphe 只有 `category` ／ `toolboxCategory`**——沒有 subtitle、description、specs。

**未決**：這是**形態**還是**第六槽**？我傾向不是形態
（它不與其他形態互相決定——剪枝力④），而是**元件的中繼資料**。
但它與圖鑑那條線（`draft/圖解形態與資料結構圖鑑`）綁在一起，要一起想。

## 軸 7：＋／− 按鈕放哪、停用怎麼表現

**實測**：目前一律**放在最後**（`PARAMS_END` / `TAIL`），停用時換灰色圖示
（`setMinusState`）。**12 顆一致**——這是少數沒有漂移的地方。

**未決**：這條要不要寫進語彙？我傾向**要**——因為它現在一致是**因為都是抄同一份**，
而抄的來源正在被抽成工廠。**工廠一旦存在，它就從「碰巧一致」變成「宣告一致」。**

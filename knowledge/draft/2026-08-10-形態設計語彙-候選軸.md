## ⚠️ 第一版錯在哪（保留，因為它是被推翻的過程）

第一版從**積木的實際做法**反推候選軸，列了七條。而回頭審的時候發現
**三個缺口，其中一個推翻了框架**：

| 缺口 | 內容 |
|---|---|
| **①** | **文字形態早就有語彙了**（`StylePreset` 六維、三組預設），而七條軸完全沒提 |
| ② | 軸 3 的句型判準**跨不了語言**（182 條裡 15 條中文名詞片語、英文動詞開頭） |
| ③ | **降級後的形態**是一條沒被納入的軸（`degradationCause` 會改變積木外觀） |

而查證缺口①時又發現：**`BlockStylePreset` 也已經存在**（`renderer`／`density`／
`colourScheme`／`inputsInline`，三組預設 scratch／classic／teaching）。

> **所以「積木沒有語彙」是錯的判斷。真相是：語彙存在，但它只涵蓋一半。**

---

## 一、真正的區分：**預設維度** vs **著作規則**

第一版最大的問題是把兩種不同的東西混成「軸」。它們的機制完全不同：

| | **預設維度** | **著作規則** |
|---|---|---|
| 誰決定 | 使用者切換（全域） | 寫元件的人（逐顆） |
| 變的時機 | 執行期 | 著作期 |
| 現有的例子 | `StylePreset`、`BlockStylePreset` | **G 的封閉詞彙表**（名字） |
| 機制 | 產生器／渲染器讀它 | 護欄查它 |
| 錯了會怎樣 | 全部元件一起變 | **那一顆**不一致 |

**兩者都需要，而且都不能拿來代替對方。**

## 二、現況盤點：**四個格子，兩個是空的**

| | 預設維度 | 著作規則 |
|---|---|---|
| **文字形態** | ✅ `StylePreset` 六維 | ❌ |
| **積木形態** | ⚠️ `BlockStylePreset` 四維，**只有視覺** | ❌ |
| 2D／3D | ❌ | ⚠️ AC 有欄位（`approximate`），無成文規則 |

### 已有的兩組，長什麼樣

```
StylePreset（文字）        io_style / naming_convention / indent_size
                          brace_style / namespace_style / header_style
  apcs         cout   / camelCase  / 4 / K&R / using    / individual
  competitive  printf / snake_case / 4 / K&R / using    / bits
  google       cout   / snake_case / 2 / K&R / explicit / individual

BlockStylePreset（積木）   renderer / density / colourScheme / inputsInline
  scratch   zelos / compact / scratch / true
  classic   geras / normal  / classic / false
  teaching  …
```

### ⚠️ 而 `StylePreset` 自己混了兩層

```
排版：      naming_convention  indent_size  brace_style
語義呈現：  io_style（cout vs printf ← 不同的元件身分！）
            namespace_style  header_style
```

**`io_style` 切換的是「用哪顆元件」，不是「怎麼排版」。** 那與 `indent_size`
放在同一個結構裡，是既有的一個混層——記在這裡，不在本輪處置。

> **而 `BlockStylePreset` 四維全部是視覺**。積木缺的正是 `StylePreset` 有的那一半
> ——**語義呈現的預設維度**。

## 三、積木缺的「語義呈現維度」候選

判準：**它是全域切換的嗎？** 是 → 預設維度；否（逐顆決定）→ 下一節的著作規則。

| 候選維度 | 值域候選 | 證據 |
|---|---|---|
| **參數的呈現粒度** | `text`（一個文字欄位）／`slots`（逐項插槽） | `specs/105`：六顆用文字欄位、`u_func_def` 用逐項。**今天是逐顆寫死的，而它看起來該是全域的** |
| **型別的選擇方式** | `dropdown`／`free_text` | 實測 44 個 dropdown；而 `cpp_new` 的 `type` 是 `field_input`（其餘 15 顆 dropdown） |
| **標籤的詳細度** | `terse`／`normal`／`verbose` | 182 條 MSG0 槽數 0–4；`teaching` 預設可能想要更長的標籤 |
| **可變項的操作** | `fixed`／`plus_minus`／`mutator` | 12 對 `plus_`／`minus_`；`u_if` 用 mutator，而**沒有人寫下分界** |

⚠️ **這四條我不確定哪幾條真的該是全域的。** 「參數用文字還是逐項」在
`teaching` 預設下也許該一律逐項，而在 `scratch` 下一律文字——**那就是全域維度**。
但也可能它其實取決於**那顆元件的參數會不會被學生改**——**那就是著作規則**。
**這一題我答不了。**

## 四、著作規則候選（逐顆，護欄查得到）

### 規則 A：同一個語義角色，同一種呈現——**除非說得出語義理由**

**實測**：14 個角色有多種呈現、84 個一致。而其中**有些差異是對的**：

```
cpp_min  的 a / b  →  input_value    可以接任意運算式
cpp_swap 的 a / b  →  field_input    必須是變數（左值）      ← 語義差異，不是漂移
c_ifdef  的 condition → field_input  前置處理器巨集名，不是運算式  ← 同上
cpp_new  的 type   →  field_input    其餘 15 顆是 dropdown    ← 這看起來是漂移
```

> **護欄能做的是排順序，不是下結論**（`build-guardrail` 第 6 步）：
> 報出「這個角色有 N 種呈現」，由人判定並**留下理由**——
> 判定的落點就是第 11 步那種 `decisions.json`。

### 規則 B：標籤要說出**作用在哪裡**——當有同族操作差別只在位置

**血的教訓**：`stack`／`queue` 的 push 標籤都說 "Push %2 onto %1"，
而 `onto` 是堆疊語義。**十八條護欄一條都不叫，學生第一眼看出來**
（`episodes/2026-08-07-學生說積木寫錯了`）。

**判準候選**：**同一個 `axis` 下的多個 `form`，標籤不得逐字相同。**
那是可機械偵測的——而它只排順序（相同不一定錯，但一定可疑）。

⚠️ **不要寫成句型規則**。實測：182 條共同的 MSG0 裡

```
zh=詞開頭 en=詞開頭   163
zh=槽開頭 en=詞開頭    15      「%1 的頂端元素」／「Top of %1」
zh=槽開頭 en=槽開頭     4
```

中文的所有格把主體推到前面，英文推到後面——**那是語言的性質，不是不一致**。

> **規則要寫在語義層（「必須說出位置」），實現留給各語言**
> ——與 G 的封閉詞彙「核心給機制、套件給資料」同一個形狀。

### 規則 C：**形態要誠實**——不宣稱自己是它不是的東西

**這條把第一版的軸 5 與缺口③合併**，因為它們是同一件事的兩面：

| 情況 | 現況 |
|---|---|
| 造型是示意的，不是擬真的 | ✅ AC 的 `approximate`／`source`，24 顆裡兩個值都真的在用 |
| 這顆積木是**降級後的替身** | ⚠️ `degradationCause` 有寫進 `extraState` 並改變外觀，**但不在任何語彙裡** |
| 標籤是簡化過的 | ❌ 沒有 |

> **一個不宣告自己是近似／替身的形態，會被讀成真的那個。**
> 與 **P6 誠實降級**是同一條原則的另一面：降級要出聲，近似也要出聲。

### 規則 D：＋／− 的位置與停用表現

**實測**：12 顆一致（一律在最後、停用換灰色圖示）。而**那是因為都抄同一份**。

> `specs/107` 把 A 家族抽成工廠之後，它從「碰巧一致」變成「宣告一致」。
> **現在正是把它寫下來的時機**——工廠存在了，下一顆手寫的才會偏。

## 五、沒有放進來的，以及為什麼

| 想過但沒放 | 理由 |
|---|---|
| 顏色／分類色 | 已由 `CATEGORY_COLORS` ＋ `colourScheme` 覆蓋 |
| 積木形狀（statement/expression 缺口） | 由 `role` 軸決定，屬**結構層**不是教學層 |
| 積木型別的命名 | 已定為**從身分導出**（併入計畫「形態槽的形狀」），不是設計題 |
| 資訊卡／圖鑑（AC 的 `info`） | **不是形態**——它不與其他形態互相決定（剪枝力④），是元件的中繼資料。與圖鑑那條線一起想 |

## 六、未決（依我認為的重要性）

1. **第三節那四條，哪幾條真的是全域維度、哪幾條其實是著作規則**
   ——這一題答錯的話，機制會做在錯的層
2. **規則 A 的判準**——要能解釋 `cpp_swap` 與 `c_ifdef` 為什麼是對的
3. **規則 C 積木那一格**——降級替身要不要在畫面上宣告，怎麼宣告
4. **`StylePreset` 混層要不要處理**（`io_style` 是語義、`indent_size` 是排版）

## 七、⚠️ 兩句釘死的

**① 語彙定完要立刻接護欄**，否則是第八個「宣稱了沒有檢查」
（`concepts/執行機構.md`）。可機械化：規則 A（排順序）、B（同軸標籤不得逐字相同）、
C（宣告存在性，像 AC 的 `conformance` 查 `bindsTo`）、D。

**② 討論完備擋得掉「不一致」，擋不掉「一致地錯」。**
那次 `stack`／`queue` 的 bug——十八條護欄不叫、任何靜態分析也不會叫——
**是學生用了才發現的**。教學層沒有 oracle 這件事，不會因為語彙寫得好而改變。
所以規則 B 那類**要留一個回饋入口**（課程試教後回收），
而**「語彙寫完」不等於「形態對了」**。

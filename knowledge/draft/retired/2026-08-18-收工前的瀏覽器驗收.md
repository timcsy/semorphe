## 為什麼是候選

專案的 experience 有一條逐字：

> 「一個功能做完之後，**去看它的入口**……那個入口通常是一份手寫清單，
> 而手寫清單不在任何護欄的視野裡」

⚠️ **而那條教訓兩次都是使用者發現的，不是測試。** 於是每一輪整合都要求
「收工前開瀏覽器」——而**怎麼開**每次重推。

🔴 **這一輪它抓到兩個測試看不到的東西**：

```
分類的名字不成立了     「腳位與時間」36 顆，其中一半不是腳位也不是時間
                       ——可拿性護欄量不到（它只問「拿不拿得到」）
積木插槽不夠            液晶的建構參數只放得下第一個
                       ——lift 與 generate 兩側的測試都是綠的
```

## 與 `diagnose-in-browser` 的差別

那一支是**診斷已知問題**用的（先讀 console、量 DOM、做對照實驗）。
這一支是**驗收新功能**：不知道有沒有問題，去看。**入口不同、順序不同。**

## 這一輪實際踩到的坑（skill 要寫進去的）

```
① 工具箱分類是【toggle】     連點兩次會關掉——而畫面看起來只是「沒開」
② flyout 要捲                積木在 y=733（畫面外），`fw.scroll(0, -680)`
③ localStorage 會殘留        上一次的工作區狀態會蓋掉貼進去的程式碼
                             → 先按「清空」或 setCode 之後再轉換
④ 長腳本會 CDP 逾時          45 秒。setCode／click／讀結果要【分三次呼叫】
⑤ 程式化 newBlock 不發事件    伴生積木那類「使用者操作才觸發」的東西，
                             必須用真的 `left_click_drag`
⑥ dev server 要先起         而改完程式碼要 reload，不是只等 HMR
```

## 順序（草案）

```
1. npm run dev → 開分頁 → 切目標（topic dropdown）
2. 問工具箱：`ws.getFlyout().getWorkspace().getTopBlocks(false).map(b=>b.type)`
   —— 🔴 不要用眼睛數，用它問
3. 量每一格的積木數 → 有沒有哪一格【名字不再描述內容】
4. 貼一段真實程式碼 → 轉積木 → 斷言專屬身分
5. 轉回程式碼 → 🔴 比對【形式一字不差】（不只是語義對）
6. 需要「使用者操作」的功能 → 真的拖曳，不要程式化建積木
7. 截圖存檔給使用者
```

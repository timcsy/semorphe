## 一句話

**目錄沿元件切；共同測從宣告推導、不放進膠囊；自證測放進膠囊、強制正負兩向。宣告即紅燈。**

## 為什麼是現在談佈局

協定（`concepts/元件.md`）已經定案並進長期層，但它是**薄協定**——只標介面，刻意不管目錄。
而碎裂全部發生在目錄上：181 顆元件平均散在 **7.9 個檔**，`≤2 檔的元件是 0 個`。

`元件.md` 自己已經推論出這條不變式，只是還沒落地：

> **就近性**——一個元件的實作**應該只出現在它自己的資料夾**

所以「用元件當目錄」不是新提案，是**把一條已拍板的推論落地**。

## 一、佈局：域 → 語言 → layer → 元件

層級順序也是 `元件.md` 定的：「一個元件的家由『域 →（若是 software）語言 → layer』三段決定」。

```
hardware/hw/arduino-uno/
ui/button/
software/cpp/lang-library/vector_declare/
software/lang/if/                 ← 跨語言的軟體元件
```

**注意 id 與路徑「通常一致但不綁定」**——scope 是所有權不是位置（見下），
所以搬家不等於改名。這是刻意不追求 Go／Modelica 那個「id ＝ 位置」的性質。

### 已解：universal 元件是**一顆**膠囊，分化的投影住語言側

`元件膠囊重構` 懸著的「一顆還是每語言一顆」，原本兩案平手（一顆＝P9 乾淨，每語言一顆＝膠囊完整）。
**社群擴張這個新目標讓它不再平手**：

| | 社群加一個 Python | 社群加一顆新的通用元件 |
|---|---|---|
| 每語言一顆 | 要建 **181 顆** universal 膠囊 | N 個語言各建一顆 |
| **一顆 ＋ 分化投影住語言側** | **一棵新資料夾樹，既有零編輯** | N 個新檔，各在明顯位置 |

**沒有貢獻者會接受第一列。**

```
components/lang/if/                 身分、接點、參數、（共用的）形態與行為
languages/cpp/projections/if/       碼形態、lift
languages/python/projections/if/
```

副作用：**P9 從此靠結構守，不靠護欄量**——通用膠囊裡不出現任何語言名，加語言＝新增一棵樹、拔語言＝刪一個資料夾。

> ⚠️ 理由要記成**社群擴張**而不是 P9。P9 是紀律，社群是「有沒有人願意來」——後者才是真正決定它的那個。原決策時沒有這個資訊。

### 已收斂：`componentId` 命名空間 = `<scope>:<name>`，scope 是**所有權**

```
lang:if                 跨語言的軟體元件
cpp:vector_declare      C++ 語言套件
hw:arduino-uno          硬體元件套件
@timcsy:my-sensor       社群
```

> ## ⚠️ 兩處後續修正（2026-08-09）
>
> **① 例子裡的連字號**：`hw:arduino-uno`／`@timcsy:my-sensor` 用 `-`，
> 而 `cpp:vector_declare` 用 `_`。**分隔符已統一為 `_`**——不借 npm 的 `-`
> （那個慣例的理由是套件名出現在 URL 與 shell，這裡不成立）。
>
> **② scope 讀成「語言」是錯的**：`cpp:` 是「**第一方的 C++ 套件**」，
> 不是「C++ 這個語言」。第三方擴充（`@someone:boost_*`）一出現就分開了，
> 而「針對哪個語言」是欄位。這其實才符合下面第 ① 條自己說的
> 「scope ＝ 所有權，不是分類」。
>
> 見 [元件](../../concepts/元件.md) 的命名章節。

**四個決定，各有理由：**

**① scope ＝ 所有權，不是分類、也不是位置。**
域已經是 `component.json` 的欄位（唯一真相），再編進 id 就是雙重真相——而且是最糟的那種，
因為 id 進了存檔改不動。npm 的 `@scope` 解的是所有權，KiCad 也明講
「**library nicknames 不必與函式庫的檔名或路徑有關**」。
（Go／Modelica 走另一條：**id ＝ 位置**。買到「就近性不可能違反」，代價是**搬家＝改名＝存檔遷移**。不採。）

**② 核心不用裸名。** 統一格式，沒有例外。
- 裸名意味著解析器有一條特例「沒有 `:` 就是核心」——而特例是偵測，統一格式是**消除**
- **現在改是免費的**：`cpp_vector_declare → cpp:vector_declare` 這個遷移反正要做
- `if`／`print`／`return` 這種短通用字是**子字串陷阱的最大值**（本專案被詞界問題咬過四次，其中兩次是漏報）
- 膠囊模型裡核心不特殊——通用元件套件只是又一個擁有者
- 原本引用的 Web Components「保留無前綴空間給平台」**不適用**：那是受限於既有 HTML 標籤的歷史妥協，不是主動設計。而 **KiCad 每顆符號都有 nickname，沒有裸名這回事**。

**③ 分隔符用 `:`。**
- KiCad（`Audio:AD1853`）與 Maven 兩個前例，而 KiCad 是硬體領域最近的那個
- **KiCad 規範強制冒號不得出現在 nickname 或 symbol 名裡**——分隔符不可能出現在名字內，split 不會錯
- `:` 在檔名裡不合法，**反而清楚表達「這不是路徑」**（呼應 ①）
- 順帶：`src/core/types.ts` 早就宣告過 `` LanguageSpecificConcept = `${string}:${string}` `` ——
  **冒號格式當初就決定過，只是實際 id 用底線，而 `SemanticNode.componentId` 是 `string` 所以型別攔不到。**
  這不是填空白，是接回一個沒人接上的決定。

**④ 第一方 scope 是描述性的，第三方是所有權——這是 npm 的模型。**

我原本說「scope ＝ 所有權」，然後同時提了 `lang:`（分類）與 `arduinocad:`（專案名）
——**兩種風格混在一起**。理清楚之後：

| | 第一方 | 第三方 |
|---|---|---|
| **npm** | 裸名、**描述性**（`react`、`lodash`） | `@org/name`、**所有權** |
| **本案** | `lang:` `cpp:` `hw:` `ui:` | `@timcsy:` |

**第一方的 scope 說「裡面裝什麼」，第三方的說「這是誰的」。**
這不是妥協——第一方本來就不需要證明所有權，因為它就是平台本身。

**⑤ 硬體的 scope 叫 `hw:`，不叫 `arduinocad:`。**
- ArduinoCAD 自己的 vision 寫著它是「**拋棄式研究刺探**」——拿一個要封存的 repo 名
  去命名**永久的**命名空間，方向就錯了
- 「Arduino」把範圍縮小（零件庫會有電阻、馬達、ESP32——他們的 `history/012` 就是
  「**非開發板零件**擬真升級」），而且是商標
- 「CAD」講的是工具不是元件。併入計畫自己的判準：「名字說它**渲染什麼**、不是**服務誰**」

死掉的候選：`part:`（每顆元件都是 part，沒有剪枝力）、`circuit:`／`elec:`（把機械排除了）、
`device:`（撞 KiCad 的通用符號庫語義）。

> **這回答了併入計畫標成未決的一半**：那裡問「改名的對象是哪一塊？零件庫（**進 Semorphe，
> 不需要名字**）、渲染套件、還是 spike repo 本身」。命名空間這個決定讓**零件庫需要名字了**。
> spike repo 本身仍然該**封存，不是改名**。

> **之後可能要拆**：硬體其實有兩種守恆（電氣／機械），將來或許該分成 `elec:`／`mech:`。
> **拆得起**——因為遷移已經制度化（見下節），這是那個決定的第一個實際回報。

**⑥ 跨語言軟體元件的 scope 叫 `lang:`，不叫 `universal:`。**
今天沒有歧義，**但硬體進來那天 `universal:if` 會被讀成「所有域通用」**——它其實是「所有語言通用」。
新貢獻者看到 `universal:print` 與 `hw:led` 並列，會以為前者是更上層的東西；
**錯，它們是同層的兩個套件，只是一個在軟體域、一個在硬體域。**
`lang:` 說出它在語言軸上，且與 `cpp:`／`python:` 讀起來同族。

### 「通用」是軟體通用，不是硬體也通用

`元件.md` 的三軸表已經定死：**layer 是「語言內部」的階，而語言只在 software 域內有意義。**
硬體沒有 layer——「它沒有 lang-core 可以依賴」。

**實測**：30 顆通用元件裡，**27 顆是純軟體**（`while_loop` 不是一顆零件）。
唯一可能跨域的是**註解那三顆**（`comment`／`doc_comment`／`block_comment`）——電路圖有文字標註，
而註解正好是「有身分、有參數、有形態、無行為、無埠」的退化情形。
（那一族正是 059 搞出「維度」教訓的那批。）

> **跨域共用的是協定，不是元件。** 元件屬於一個域（接點的關係律由域決定），協定跨所有域。
> 三域表就是在講這件事——三個域各自填五槽，填出來的內容完全不同，共用的是那張表本身。

**觀察，非結論**：軟體有 universal 層是因為它有多語言；硬體沒有語言軸，但**有通用／具體的梯度**
（KiCad 的 `Device:LED` vs `LED_SMD:LED_0805`）。真要一般化，layer 或許該理解成
「在該域的**變異軸**上有多通用」——軟體的變異軸是語言，硬體的是封裝／廠商。**未驗，先記著。**

### 遷移要制度化，不是一次性工具

**Modelica 沒有迴避「搬家＝改名」，他們把它制度化**：套件隨附轉換腳本
（`convertClass("OldClass","NewClass")`），載入舊模型時自動轉換；重新命名父類別會連帶所有子類別。

semorphe 已經做過一次型別感知的 codemod（089，131 檔／560 處），**機制在手上，缺的是讓它變成
隨版本發布的常態**。否則往後每次重構分類都會因為「不敢動存檔」而卡住——而那正是這條紀律要防的。

## 一之二、遷移策略：現有 repo 裡開新樹，兩棵並存，舊樹縮到零（2026-08-07 人拍板）

**設計不必遷就現況，遷移必須。**

使用者要的是「不計成本、一次做好、乾淨的重新開始」。拆開來看是兩件事：

- **設計層面**——已經在這麼做了。回頭看每一個決定都**沒有遷就現況**：五槽（現況只有 4 槽，
  接點與邊完全不存在）、`<scope>:<name>`（推翻既有的 `cpp_` 底線）、核心不用裸名
  （現況 30 顆全裸）、一顆膠囊＋投影住語言側（現況 30/30 全散在語言檔裡）。
  **擔心的那件事沒有發生過。**
- **程式碼層面**——不重寫，搬家。

### 為什麼不重寫

**本專案自己的反面證據：**

- **089** 是純機械的型別改名（131 檔／560 處），**出錯三次**，一次要整個 revert 重做。
  三次全部由測試抓到，**沒有一次是 code review**。
- **087** 改了一個量測範圍，殼從 2 變 13，整個 revert。

一次機械改名都能錯三次。181 顆同時重寫會拿到一份**紅得無法歸因**的套件——
而這專案所有護欄都建立在「數字動了，指得出是哪一項」上面。**歸因不了時，17 條護欄全部失效。**

**而且要重寫的東西是健康的**：實測殼 0、缺 0、833 個 ✅、全套 211 檔全綠。
那 181 顆的**內容是對的**，錯的只有它們住在哪裡。而內容裡累積的是跟真的 `g++`
對答案對出來的一堆小真相（光這一輪就翻出 20 幾個真實缺陷）。
**用重寫換位置，是拿健康的內容去賭一個組織問題。**

### 護城河：測試測的是行為，不是結構

```
run('istringstream in("10 20 30"); … cout << a+b+c;')  ===  '60'
```

這支測試不在乎實作住哪裡。**所以搬家過程中它一路綠著**，而且每搬一顆就驗一次。

### 形狀

1. 新的 `components/` 樹按**最終設計**建，**完全不參考舊佈局**
2. 一次搬一顆，搬完舊的那份就刪掉
3. 全套測試每一步都必須綠——**搬一顆就是一個可 revert 的單位**
4. 舊樹歸零那天，重構結束

**不新開 repo。** 併入計畫已經寫過：「repo 切分是最貴的一種切，而這專案的頭號病
就是**同一塊碼沿不同軸反覆重切 ＝ 碎屑**」。

### 有幾樣是改結構，不是搬——而且要在搬之前

`元件.md` 的「現況落差」那張表，這幾條換位置解決不了：

| | 現況 | 性質 |
|---|---|---|
| `attachments` ＋ `relation` | `children` 全是組合、**資訊軸不存在** | **新增一整條軸** |
| `params` / `ParamSpec` | 型別側只有 `string[]`——**沒有型別、沒有範圍、沒有預設值** | 結構化，不只改名 |
| `componentId` | `SemanticNode.componentId: string`，型別攔不到 | 型別化 ＋ 命名空間遷移 |
| `ComponentRegistry` | `BlockSpecRegistry`（**以投影命名登錄表**） | 改名＋改索引 |
| 課程／toolbox 清單 | 手寫；前兩大共用檔各提 172／170 顆 | **改成從登錄表導出** |

理由同前：**膠囊定義裡少一槽，那個膠囊就得做兩次。**

## 二、碎裂與因式分解的分界

一個貫串全篇的判準，值得單獨立出來：

> **碎裂的痛不在「碰幾個檔」，在「碰幾個既有的共用檔」。**

- 加一個通用概念要在每個語言說它怎麼寫——**這件工作不可約**，跟檔案怎麼擺無關。
- 差別是它長成 **N 個新檔、各在明顯位置**（可以看、可以刪、可以數），
  還是 **N 次對既有共用檔的編輯**（`universal-concepts.json` 加一筆、某個 switch 加一個 case、`index.ts` 加一行註冊）。

後者才是碎裂：**每一次編輯都可能弄壞別人的，而且沒有一次是看得見的。**

## 三、膠囊契約：測試分兩層

### Part 1：共同測——**推導**的，不放進膠囊

⚠️ **不得每顆一份。** 500 份長得一樣的共同測 = 複製了 500 份同一個真相（本專案的頭號病），
而且會漂移：改了協定，改不到的那幾份會安靜地繼續綠。

**形式**：一個 harness 走過 `components/*/component.json`，從宣告推出案例。膠囊裡不放檔。

推得出來的至少有：五路是否齊備、**符合性**（每個形態的接腳集合 == 語義接腳）、往返是不動點、
宣告的 `accepts` 與實際邊的 `relation` 自洽、實作沒洩漏到 kernel／app／render、實作只出現在自己資料夾。

> 符合性在 `元件.md` 裡目前是「**無名，只有零星 guard test**」——這個設計給它一個家。

**這其實就是現在那 17 條護欄，換了位置：**

| | 現在（全域掃描） | 膠囊之後（每顆的合約測試） |
|---|---|---|
| 形式 | 掃全 repo，報一個數字 | 這顆過或不過 |
| 基線與棘輪 | 要 | **不要**——沒有「還剩幾筆」 |
| 誰維護 | 中央 | 沒有人，從宣告長出來 |
| **貢獻者送出前跑得了嗎** | **跑不了** | **跑得了** |

最後一列對社群是決定性的。

**分域是自動落出來的**：一顆元件沒宣告守恆接點，守恆相關的檢查就產出零個案例。
協定仍然不需要理解 `kind`——那正是「`kind` 是不透明酬載」的兌現。

### Part 2：自證測——人寫的，放進膠囊

這顆元件的**語義**。`vector<int> v = f()` 必須是複製不是共用——這推導不出來。

**難題不是怎麼寫，是怎麼防空洞。** `it('works', () => expect(true).toBe(true))` 也會綠。
而這專案踩過那個坑的精確版本：五支「通過」是假的，**被測的概念根本沒出現在語義樹裡**
（用 `static_cast` 代測 `dynamic_cast`）；加上「必須真的出現在樹裡」之後，通過數 17 → 12。

兩條機械後設檢查：

1. **每支自證測必須證明它真的碰到這顆元件**——`componentId` 出現在語義樹裡，或行為真的被執行到
2. **強制正向與負向兩向**。只有正向的話，一個過寬的實作會全綠——095 若沒有「`num >> 1` 必須仍是位移」那支負向，一條把所有位移都認領走的規則會通過全部測試

## 四、TDD 的形狀：宣告即紅燈

TDD 通常卡在「要先寫一支會紅的測試」，而人會偷懶。這裡不用寫：

1. 建 `component.json`，宣告身分／接點／參數 —— **這就是規格**
2. harness 立刻產出 N 支紅燈：沒有形態、沒有行為、符合性無從驗
3. 一格一格填，每填一格轉綠一支
4. 語義（Part 2）在寫 behavior **之前**寫

**你不需要寫那支會紅的測試——你宣告了一顆元件，紅燈自己出現。**

**這直接治「殼」**：殼 = 宣告了路徑但沒有實作。現在它是報表上的數字，膠囊之後從第一天就是紅的。
（095 實作 istringstream 時我先加了執行器，孤兒實作護欄才叫。膠囊 TDD 下那個紅燈會在我寫執行器**之前**亮，而且亮在我自己的資料夾裡。）

### 膠囊長相

```
components/if/
  component.json      身分、接點、參數      ← 規格，紅燈的來源
  forms/              積木、（共用的）形態
  behavior.ts
  spec.test.ts        自證測（人寫，正負兩向）
                      ← 共同測不在這裡，它從 component.json 推導
```

## 五、三條紀律（2026-08-07 人已同意）

1. **共同測不得超出協定。** 在協定裡的可以測，不在協定裡的不是共同測。
   推論：**新增一條共同測 = 修改協定 = 要人拍板**，同一個閘門，不另開後門。
   這擋掉最常見的退化——共同測慢慢變成風格警察（命名規則、註解格式、檔案大小），而那些都不在協定裡。
   也擋掉另一個方向：共同測若能無限成長，每加一條就讓既有元件全紅，於是沒人敢加、或加得很鬆。
2. **自證測強制正負兩向。** 對貢獻者是實實在在的門檻，但這一輪救最多次的就是負向斷言。
3. **宣告了沒實作的路徑：擋 merge，但允許明確宣告 `skipPaths` ＋ 理由。**
   不擋的話殼會回來；全擋的話沒辦法漸進貢獻。宣告理由這條的門檻見
   [history/018](../../history/018-清償從搬檔案改為把清單換成宣告.md)——已有護欄在看理由會不會被濫用。

## 六、社群 PR 因此可以機械判定

| 判定 | 誰做 |
|---|---|
| 共同測全綠 | 機器（推導出來的，賴不掉） |
| 自證測存在且真的碰到這顆元件 | 機器 |
| 自證測有正向也有負向 | 機器 |
| **語義對不對** | **人——但只需要讀那一個資料夾** |

**審查者不需要理解整個系統，只需要理解一顆元件。** 這是膠囊真正買到的東西。

## 七、順序不能反

本專案自己的診斷是「**AI 元件管線把碎裂模板一起規模化**」。
skill 是放大器——**它放大的是它寫進去的那個形狀**。

膠囊沒定就先寫社群 skill，等於把現在的 7.9 檔規模化到社群。
與併入計畫同一條紀律：**膠囊先，管線後。**

## 八、剪枝力要守住

`元件.md` 的警語：「一切都是元件」當口號是空的——泛到能裝任何東西＝沒有剪枝力的假母概念。

新域的門檻不是「想不想」，是**五槽填不填得滿**：身分？接點＋關係律？形態＋符合性？行為＋時鐘？組裝？
填得出白拿整套機器，填不出就代表那個域不是元件。

三域表已經兌現過一次——UI 填完之後**學到了新東西**（唯一沒有守恆關係的域，這解釋了它為何最好教）。

**Agent／AI 技能目前填不滿**：接點講不出關係律，多表示只有一份 `SKILL.md`（沒有第二個表示就沒有符合性可守）。
它不是被剪掉，是**還沒進場**——要納入得先填那兩槽。

## 八之二、形態的正確性沒有內部 oracle——驗收要納入

一名學生回報「stack 和 queue 的 push 積木寫錯了」。查證：**執行器不分支（身分對），
標籤說謊（`"Push %2 onto %1"` 的 onto 是堆疊語義）**。

**十八條護欄一條都不會叫**——行為對、來回轉換對、五路齊備。而使用者第一眼就看出來。

這對膠囊契約有兩個直接後果：

1. **「一個身分、多個形態」不是理論偏好，是這個案例要求的**：
   ```
   component: container_push        ← 一個身分，執行器一份
     forms:
       block:
         stack:  「推到 %1 的頂端」
         queue:  「加到 %1 的尾端」
   ```
   拆成兩個身分的話會被迫接著拆 `pop`／`top`／`front`——**六顆元件差別只有一個屬性**，
   而 LIFO/FIFO 會同時寫在容器和每個操作上。**紀律該住在容器裡一次，不是散在操作上六次。**

2. **驗收標準要加一條**：每顆元件的標籤要說出**作用在哪裡**，不只說做什麼。
   這一條**可能可以機械化**（`container_push` 與 `container_push_back` 的標籤品質差異
   是可見的：一個提到位置、一個沒有），但**先確認教訓成立再蓋護欄**——
   而那要問使用者，不是問程式碼。

見 [episodes/2026-08-07-學生說積木寫錯了](../../episodes/2026-08-07-學生說積木寫錯了.md)。

## 九、量測結果（2026-08-07 實測，取代先前的推論）

### 通用元件的槽分化：100%

（`input` 最極端：14 檔，5 個在 `languages/` 底下）。

這證實「一顆膠囊 ＋ 投影住語言側」不是理論偏好，是**描述現況**——
分化的投影確實存在且普遍，只是現在散在共用檔裡而不是各自成檔。

### 順帶掀出：中立性歸零之後還剩 30 筆，在護欄的維度外面

`元件.md` 的不變式寫的是：

> **中立性**——kernel／app／render 的檔案**不准提到任何具體 componentId**

實測：**核心層提到 30 顆元件身分，語言專屬 0 顆、通用 30 顆。**
`src/core/types.ts` 裡是一個字面聯集（`| 'if' | 'count_loop' | …`）。

護欄回報 0 是**正確的**——它只數語言專屬身分。但不變式說的是「任何」。**30 筆落在差距裡。**

**這是「選了哪一維會消失在數字裡」的第四個實例**（前三：身分／語法／型別名，見
[history/021](../../history/021-中立性的數字只量身分那一維.md)、[history/024](../../history/024-耦合的第四種形式是型別名.md)）。
而這次的差距不是新造成的，是**護欄從一開始就實作了比不變式弱的版本**。

後果具體：加一顆通用元件要編輯核心的聯集型別；硬體與 UI 進來之後那個聯集會無限長。

**選項**：把中立性護欄改成不變式的原版，數字會從 0 變 30——那是**揭露不是退步**
（`history/055` 的「有實作卻沒宣告」那次同型）。

### 對排期的意義

- **好**：71% 的檔次集中在 20 個檔，最大的兩個可以用「從登錄表導出」一次解決
- **壞**：專屬檔只有 24 個 ＝ **膠囊今天幾乎不存在**，等於從零建 181 個資料夾
- **卡**：`componentId` 命名空間沒定之前，資料夾名字不能定（現已收斂，見上）

**還不給週數**——建議先搬一顆當垂直切片（`cpp:vector_declare`，五路齊全、有兩種子槽），
量出「一顆要多久、卡在哪」，再乘出真實範圍。

## 還沒想清楚的

- **中立性護欄要不要改成不變式的原版**（只數語言專屬 → 數任何 componentId）。改了數字從 0 變 30，
  那是**揭露不是退步**。但它會讓一條歸零過的護欄重新變紅，要不要接受，是取捨不是對錯。
- **`hw:` 之後要不要拆成 `elec:`／`mech:`**——兩種守恆確實不同律，但現在拆是為想像設計
- **共同測 harness 與現有 17 條護欄的遷移路徑**——哪幾條可以直接改寫成推導式、哪幾條本質上就是全域的（例如全樹流敏感約束）
- **`spec.test.ts` 的「真的碰到這顆元件」怎麼判**——語義樹裡出現 `componentId` 是一種，行為被執行到是另一種，兩者對純宣告式元件（`skipPaths: ['execute']`）都不成立

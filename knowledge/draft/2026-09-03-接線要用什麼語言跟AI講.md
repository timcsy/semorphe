# 接線要用什麼語言跟 AI 講

> 日期：2026-09-03
> 狀態：**設計未決**——出口是 vision 路線圖（要人拍板），不是直接清償。
> 怎麼冒出來的：使用者：「硬體的接線等等的我們有沒有需要用什麼樣的語言，
> 就是用這格式**貼給 AI**，或是 **AI 用這格式貼給我們**都方便的？」
> 接著追問：「所以 **Wokwi 是硬體接線和組裝上最好跟 AI 溝通用的語言嗎？**」
>
> ⚠️ 前提已經在 [[硬體域併入計畫]] §「與軟體那側的視圖對應」定了：
> **硬體那側也該有一個文字真相（網表）**。這一份接著問的是：那份文字長什麼樣，
> 以及**它同時要當人機介面**這件事會怎麼改變它。

## 一、先切開兩件事——混在一起是所有既有格式壞掉的地方

```
邏輯連接（net）        LED 的陽極 → 220Ω → D13          ← 與麵包板無關，這是【真相】
物理擺放（placement）  LED 插在麵包板 e12，跳線 j12→D13  ← 【投影】，而且是好幾種之一
```

與軟體那側同構：**語義樹 vs 版面**。

🔴 而混在一起對 AI 特別致命：畫面資料（座標、線的顏色、繞線路徑）對它是純噪音，
而**它一定會照著編**——你會拿到幻覺出來的座標，看起來很像真的。

> **交換格式只裝 net，不裝畫面。** 擺放要嘛自動算，要嘛是另一份可選的註記。

## 二、Wokwi 是不是最好的？——在它的範圍內是，而我們的範圍比它大

| 判準 | Wokwi `diagram.json` |
|---|---|
| ① AI 寫不寫得出來（見過沒有） | 🟢 Arduino／ESP32 麵包板這個範圍內大概最強 |
| ② 語義精確、能驗證 | 🟡 夠用，而混著畫面資料 |
| ③ 涵蓋我們要做的範圍 | 🔴 **只到麵包板**——使用者問的「**組裝**」它一個字都沒有 |

第三格是關鍵：路線圖上的 ArduinoCAD 合流要的是機構、支架、3D 擺放，
而 Wokwi 是**一個模擬器的輸入格式**，不是裝配描述。

四個具體限制：

1. **零件表是別人的封閉清單**（`wokwi-led`／`board-esp32-devkit-c-v4`……）
   ——不在表上就寫不出來。而〈開放擴充〉整個原則就是在反對這件事。
2. **混了畫面**：`top`／`left`／`rotate`、線色、`["v0","*"]` 的繞線路徑。
3. **腳位名是 Wokwi 的**，不見得是規格書的。
4. **第三方相依**：它會改版而我們不會收到通知（＝[[寄生在別人的編輯器裡]] 的同一條風險）。

## 三、比「哪個格式」更重要的一個區分：**有沒有我們在中間**

```
有我們在中間   我們的 app 呼叫 API：能塞規格、塞兩三個範例、把檢查器的錯誤回饋回去
               → 自訂格式完全可行，而且【更好】（精確、可擴充、沒有噪音）

沒有我們在中間 使用者自己複製一段貼進 ChatGPT
               → 「AI 見過沒有」才是決定性的，因為沒有人能附規格
```

🔴 **「LLM 有沒有看過這個格式」是一個真實的設計參數**，而它的權重**取決於上面那一格**
——能給範例的時候，它會縮到很小。

所以答案不是二選一，是**兩個出口**（一個真相，各式投影）。

## 四、草案：行導向，而不是 JSON

```
board  uno  : arduino-uno
part   led1 : led       color=red
part   r1   : resistor  value=220

wire   uno.D13 -- r1.1
wire   r1.2    -- led1.A
wire   led1.K  -- uno.GND
```

四個理由，每一個都是 LLM 的實際行為：

1. **一行一個事實** → 改一件事就是改一行。JSON 的巢狀讓「把 LED 換到 D12」
   變成重寫一整塊，而重寫就有機會弄丟別的東西
2. **不靠位置** → `uno.D13` 自己說得出自己是誰；`["uno:13", …]` 的第三、四格
   靠位置，AI 一定會亂填
3. **名字有語義** → `led1.A`／`led1.K`（陽極／陰極）遠勝 `part3.pin2`
   ——LLM 靠語義推理，給它編號它就只能猜
4. **括號少 → 壞得少** → JSON 漏一個逗號整份失效；行導向壞一行只壞一行，
   而且**看得出來是哪一行**

⚠️ 而它要**對得上元件的五槽**（腳位＝槽，接線＝關係律的一個實例）
——不要為硬體發明第二套詞彙。

## 五、要能承載「不知道」

```
part  r1 : resistor  value=220        # 明確
part  r2 : resistor  value=?          # AI 不知道
part  x1 : unknown "OLED 0.96寸 I2C"  # 認不出來的零件，原文保留
```

第三行就是既有的招：**「認不出來的 `goto` 變成一顆寫著原文的積木」**搬到硬體。
認不出來的零件不該讓整份失敗，也不該被安靜丟掉——它變成一顆帶原文的零件，
而使用者看得到它是灰的（〈降級與認知邊界〉）。

## 六、AI 貼回來的東西**要先過檢查器，不要直接畫**

這是硬體與程式碼最大的差別：**一份語法正確的接線可以燒掉板子。**

```
LED 沒有限流電阻            → 一定要說
5V 接到 3.3V 的腳           → 一定要說
VCC 與 GND 直接相連         → 短路
同一支腳被兩個輸出源驅動     → 衝突
腳位不存在（Uno 上的 D14）   → 那個腳沒有
```

與〈模擬的誠實〉同一條原則：**畫得出來 ≠ 這樣接是對的**。
而 AI 產生的接線更需要它——它會很有自信地給你一個燒掉東西的電路。

🔴 **而檢查器的輸出也是交換格式的一部分**：「你這裡少一顆電阻」要能**貼回給 AI**，
那是最有用的一次往返。別讓錯誤只活在畫面上。

## 七、真正決定 AI 溝通品質的，不是格式，是**回饋迴路**

> **一個格式如果有可執行的裁判，AI 的輸出就能被驗證，而驗證結果又能回饋給它再改一次。
> 沒有裁判的格式，再漂亮都只是「看起來對」。**

🟢 而這正是 Wokwi 最強的地方——**不是「LLM 看過」，是它有一個跑得動的模擬器**。

所以我會這樣用它：**當出口與裁判，不當母語**。匯出 `diagram.json` 丟進模擬器跑，
是很便宜的正確性檢查，而它同時解決「讓學生看到電路真的會動」。

## 八、形狀

```
真相      我們的元件圖（五槽 ＋ 關係律）——組裝那一半只有它裝得下
入口 ①    人話描述 →（AI 幫忙解析）→ 過檢查器 → 進元件圖
入口 ②    行導向格式
出口 ①    行導向格式（給 API、給要精確的場合）
出口 ②    diagram.json（給模擬、給裸貼 ChatGPT 的使用者）
出口 ③    人話（給老師看、給討論用）
```

⚠️ **入口 ① 不要小看**：「Uno 的 D13 接 220Ω 電阻，再接紅色 LED 的長腳，短腳接 GND」
是使用者**真的會貼**的東西，而 LLM 對它的理解其實非常好。
它不可驗證，所以它是**入口**，不是真相。

## 九、第一刀的順序（刻意的）

1. **檢查器**的前五條規則 ← 🔴 **先做這個，不是格式轉換**
2. 行導向格式 ＋ 它與五槽的對映（不做 UI）
3. **來回一致性護欄**：`文字 → 元件圖 → 文字` 逐字相同
   （與「程式碼 → 語義樹 → 程式碼」是同一個問題，護欄與 fuzz 的做法直接搬）
4. 這時候才畫東西，而第一個「畫」可以只是示意圖
5. `diagram.json` 匯出（拿到模擬能力）

為什麼檢查器優先：**「AI 給的接線對不對」才是使用者真正會踩的坑**，
而格式再漂亮也擋不住一個少了限流電阻的電路。
⚠️ 麵包板擺放最貴、最不精確、而且最不影響「能不能跟 AI 對話」——排最後。

## 十、要拍板／待查

1. 這一格進不進路線圖（它與 [[硬體域併入計畫]] 的關係是「那份的網表那一格的細節」）
2. 行導向格式的具體語法要不要先寫成 spec，還是先用檢查器逼出它的形狀
3. 待查：Wokwi 的零件表與 `diagram.json` 的授權／ToS——當出口可以，
   而**不可以**讓它的零件命名滲進我們的登錄表

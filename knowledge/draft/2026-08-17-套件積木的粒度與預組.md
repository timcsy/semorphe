# 套件積木的粒度與預組

> 日期：2026-08-17
> 怎麼冒出來的：談「補 ESP32／Nano／常用套件」時，使用者問了**兩個被我混在一起的問題**。
> **狀態：機制未決，而內容【刻意留空】**——見末節。
> 判準那一半已經定案並反流到 [concepts/投影](../concepts/投影.md)；這裡留的是**還沒答的**。

## 一、兩個問題，而我第一次答錯了方向

```
問題一  「套件的一連串功能，積木要不要合成一顆？」    → 概念的【粒度】
問題二  「工具箱能不能有已經組合好的積木？」          → 工具箱的【調色盤】
```

⚠️ 我把問題二答成了問題一，講了一整段可逆性——**而問題二完全不碰語義樹**。

> **拉出一串三顆連好的積木，與學生自己拉三次再接起來，產生的樹一模一樣。**

🟢 所以問題二**便宜**：可逆性、墓碑、根公理都不管它。它純粹是「調色盤上放什麼」。

**問題一已有答案**（判準是可逆性，三條合法的路 ＋ 一個反模式）→ [concepts/投影](../concepts/投影.md)。
**本檔只留問題二。**

## 二、而一半已經有了

`src/languages/cpp/toolbox-categories.ts:70` 逐字：

> 「同一顆 `cpp_if` 用三個不同的預設狀態出現——那是**教學設計**
> （讓學生直接拖到「有 else 的 if」），**登錄表推不出來**，所以留著。」

```ts
extraTypes: [
  { type: 'cpp_if' },
  { type: 'cpp_if', extraState: { hasElse: true } },
  { type: 'cpp_if', extraState: { elseifCount: 1, hasElse: true } },
]
```

**「同一顆積木的多個預設狀態」是既有機制。**

缺的是**一串**：flyout 項目今天只傳 `{ kind, type, extraState }`
（`src/ui/toolbox-builder.ts:165`），而 Blockly 的 flyout **本來就吃得下
`inputs`／`fields`／`next`**——也就是整棵子樹。**我們只是沒傳過去。**

→ 技術上很小：把 `extraTypes` 的形狀放寬成完整的 Blockly block 規格，原樣傳下去。

## 三、🔴 而真正該小心的不是技術，是它會長成什麼

那個註解自己說了：「**登錄表推不出來，所以留著**」。今天 **1 筆**。

而這個專案的病史裡，「手寫清單」翻車過好幾次：

```
工具箱歸屬     80 筆手寫 → 45 段有序來源（spec 100）
課程清單護欄   手寫兩個 topic 的 import → spec 136 的 c-beginner 它從來沒看到過
```

> **一份「登錄表推不出來所以手寫」的清單，加到第二筆的時候還好，
> 加到第二十筆的時候它就是第二個真相來源。**

### 傾向（而它未拍板）：預組屬於**套件**，不屬於任何一顆概念

「LCD 的三行常用組合」不屬於其中任何一顆概念，**它屬於那個套件**。
而 `owner`（`(arduino)`／`<vector>`／`(core)`）已經是那個層級的名字。

→ 那就與膠囊同一個處置：**套件自己一個檔，被 glob 掃到，
加一組預設 ＝ 新增一個檔，零編輯。** ⚠️ **而不是擴充 `extraTypes` 那份中央清單。**

## 四、⚠️ 第二個風險，而它不是技術的

[漸進揭露把選項轉嫁給了老師](2026-08-12-漸進揭露把選項轉嫁給了老師.md) 那份的標題就是警告。

一個塞滿預組積木的工具箱，**選項會變多**——而「該拉哪一個」的負擔
就從系統轉給了學生。`cpp_if` 三態還好；一個套件十個預設組合就不一定。

🔴 **判準（傾向，未拍板）**：

> **一組預設要進工具箱，理由必須是「學生自己組會裝錯」，不是「這樣比較快」。**

`if/else` 三態符合前者（巢狀結構學生真的會裝錯）；
「LCD 初始化四行」比較像後者——**而那種東西的正確答案是函式**（見 concepts/投影 的第三條路）。

## 五、🔴 而內容【刻意留空】

**機制可以先做，而預設組合本身要等資料。**

理由與「收哪些套件」同一條：
[history/077](../history/077-虛擬硬體往後推而先做寬度.md) 決定了
「讓 AI 生一批真實 Arduino 程式，量殘差，用量出來的分佈決定收哪些」。

**那批語料同時回答兩個問題**：

```
哪些套件真的常出現        →  決定收哪些
哪些呼叫【總是成群出現】  →  🔴 那正是預組的候選，而它是【量出來的】不是猜的
```

> **一組總是一起出現的呼叫，才有資格被預先組好；而「總是」是一個可以數的東西。**

⚠️ 空著猜的話，會長出一份沒有 pruning power 的清單——而那份清單會**先於**證據存在。

## 🔴 2026-08-18 實作時的精確化：「都齊」與「緊鄰」是兩個不同的問題

本文的判準原話是：

> **一組總是一起出現的呼叫，才有資格被預先組好；而「總是」是一個可以數的東西。**

而**「總是」要數什麼**沒有寫清楚，於是第一次量錯了。

`cpp:ultrasonic_trigger` 的探索報告量出「觸發序列 ＋ 距離換算 7/7 = 100%」，
結論是兩者一起摺。⚠️ **而那個 7/7 問的是「這支程式裡兩者都有嗎」。**

語料擴到 100 段之後重量（14 段用到 `pulseIn`）：

```
觸發序列（LOW → 2µs → HIGH → 10µs → LOW，同一根腳）  14/14 = 100%   🟢 有資格
觸發 ＋ 換算【緊鄰】                                  9/14 =  64%   🔴 沒資格
   └ 5 段被 `if (duration == 0) return …;` 這個守衛隔開
```

**摺起來會把中間那段吃掉**，所以要問的是「它們**緊鄰**嗎」，不是「都有嗎」。

> **「都齊」與「緊鄰」是兩個不同的問題，而只有後者決定摺不摺得起來。**

🟢 而縮成只摺觸發之後，14 段**全部**轉得動——原本的設計會讓那 5 段帶守衛的失配。

**判準補上一句**：數的是**相鄰出現率**，而中間夾了任何別的語句就不算。

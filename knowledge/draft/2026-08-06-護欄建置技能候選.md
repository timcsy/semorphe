# 技能候選：蓋一條護欄

> 建立：2026-08-06 ｜ 型別：程序性記憶候選（procedural）｜ 狀態：**待人確認才能固化進 `skills/`**

## 為什麼是候選

**同一套操作已經做了五次**（`specs/049-audit-guardrails` 四條 + `specs/051-lift-claim-arbitration` 一條），每次的形狀高度一致，而且**每次都有一部分是靠記得上一次的教訓才沒出錯**。

階段 6.5 還有 P2–P7，每一期都可能再蓋一條。這是 knowie 說的「在下一次手動重做之前就技能化」的典型時機。

技能是**被執行**的，門檻比知識高——所以這裡只記候選，不自行固化。

## 這五次做的是同一件事

| 護欄 | 量什麼 | 規範 |
|---|---|---|
| 就近性 | 一個元件散在幾個檔 | P3 |
| 中立性 | 核心層硬編幾筆語言專屬身分 | P9 |
| 完備性 | 每元件每路徑是實作／殼／缺 | P2 |
| 缺陷帳 | 停用測試，分「有本體」與「只有名字」 | 使用者明示 |
| 辨識歧義 | 多少規則靠登記順序決勝負 | P3 |

## 步驟（暫記，未打磨）

1. **先問「違反它時什麼會變紅」**——答不出來的不是護欄題，是規範該不該存在的題（走 `/over-justify`）
2. **先寫自我否證聲明，再寫量測**——「如果結果長成 ○○，代表工具壞了，不是世界長這樣」。順序不能反：寫完量測再補聲明，你會照著已經看到的結果去寫它
3. **寫「本護欄不檢測什麼」**——劃能力邊界，避免被誤讀成完備性保證
4. **從實際載入後的狀態量，不讀靜態設定**——登記順序取決於模組匯入順序，讀設定檔算不出來
5. **判定保守**：判不出來就歸「無法確定」，且**不計入安全**。為了讓數字好看而樂觀歸類，比沒有護欄更糟
6. **產基線**（`GENERATE_BASELINE=1 npx vitest run <檔>`）→ `tests/baselines/*.json`
7. **棘輪測試**：只准下降；上升時**必須指名是哪一項**新增的（不能只說「數字變大了」）
8. **自我驗證測試**：釘住一個**已知必然會被報出來**的項目——漏報它就是工具壞了（FR-022 那類）
9. **同時釘住一個不該被報的**——誤報最常用的那一對，維護者會立刻學會忽略整個護欄

## 明確否決的做法

- ❌ **vitest snapshot**——`-u` 會靜默更新，等於「跑一下就自動接受惡化」，那本身就是 `concepts/執行機構.md` 在講的殼
- ❌ **永久紅的測試**——會讓「全套綠」失去意義，而所有護欄的價值都建立在那個訊號上。要釘住已知缺陷用 `it.fails`（缺陷還在＝綠且出聲，修好了＝紅且提醒拔釘子）

## 這個技能存在的理由是三次翻車

1. 完備性護欄第一版 → 84 個假的 missing
2. 兩組態比對第一版 → 「無差異」，真實是 35 個元件
3. 缺陷帳第一版 → 分類語義錯，優先序灌水 3–10 倍
4. 歧義判定第一版 → 太弱，5 條 constraints 相同的規則被判成「無法確定」

**四次裡有兩次是靠上面第 3、8 步抓到的**，不是靠 code review。步驟表的價值就在這裡。

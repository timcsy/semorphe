# 圖解形態與資料結構圖鑑

> 日期：2026-08-05
> 怎麼冒出來的：使用者問「一個程式語言的概念是不是也可以對應到圖解——用箱子或一塊記憶體代表變數、呈現程式如何管理記憶體與運算？堆疊／佇列／樹／圖這些進階概念是否也能有可視化，就像元件有圖鑑一樣？」
> ⚠️ 🔴 **檔名把兩件事綁在一起了**（2026-08-14 分清）：
> **圖解**是【執行狀態】的投影（隨時間變），**圖鑑**是【元件登錄表】的投影（不變）。
> 三個投影對象的表已進 [concepts/投影](../concepts/投影.md)。
> **本檔仍然有效**，而讀的時候要分清哪一段在講哪一個。
>
> **狀態：未承諾。** captured ≠ committed。理論地基是 [concepts/元件](../concepts/元件.md) 的形態槽與 [投影](../concepts/投影.md) 的 R0-R4。

## 一句話

**圖解不是新功能，是形態槽的第六格**（積木／文字／2D／3D／URDF／**圖解**）。真正需要新東西的不是圖解本身，是**讓值有身分**。

## 先分三格，否則設計會擰

使用者的問題橫跨三件不同的事。它們的鍵不同、住的地方不同：

| | 是什麼 | 鍵 | 住哪 |
|---|---|---|---|
| **① 元件的圖解形態** | for 迴圈畫成流程方塊、`if` 畫成分岔 | `componentId` | 膠囊的 `form.json` |
| **② 值的圖解** | stack 一疊箱子、tree 節點加邊、pointer 一支箭頭 | **型別** | ？—— 目前**無處可掛**，見下 |
| **③ 執行的可視化** | 記憶體隨時間變化、控制流走到哪、變數 `x: 0→1` | **行為軌跡** | panel，消費執行 trace |

使用者舉的例子分佈：「變數是一個箱子」＝ ①＋②；「看程式如何管理記憶體」＝ ③；「堆疊佇列樹圖的可視化」＝ 純 ②。

**②③ 的分界最容易搞混**：`cpp_stack_push` 是一個**元件**（一個操作），但**堆疊是一個執行期的值**。操作沒有圖解，值才有。把值渲染器掛在操作元件上會立刻壞掉——同一個 stack 被十個不同操作碰過，圖只有一張。

③ 也不是元件的槽——[concepts/元件](../concepts/元件.md) 已經定案「**行為軌跡是行為投影吐出來的東西，不是真實**」，所以它是 trace 的呈現，不是元件的形態。

## ② 揭露一個地基缺口：型別不是一等公民

要讓 `stack` 有圖解，得有地方掛那個渲染器。現況掛不上：

- `properties` 型別側只有名字清單，**沒有型別資訊**
- `func_def` 的 params **存成字串**（已知技術債；renderer 的 `parseParamTypeAndName` 用已知複合型別清單做前綴匹配）
- `stack<int>` 在語義樹裡就是某個 property 上的一串字

**沒有身分，就沒有地方掛渲染器。**

這給「複合型別字串解析」那筆債加了第二個、而且更有說服力的理由——原本只是「解析很醜」，現在是「**它擋住了整個資料結構可視化**」。也和 [元件膠囊重構](retired/2026-08-05-元件膠囊重構.md) P5 的 `params`／`ParamSpec` 結構化是同一筆債的兩面。

### 提案（賭注，非結論）：型別也是元件

用 [over-justify](../skills/over-justify/SKILL.md) 過一遍：

- **多解釋** ✓ —— 解釋為何複合型別要用字串 hack、為何值渲染沒地方掛、為何 `ParamSpec` 需要型別欄位
- **多預測** ✓ —— 預測「加一個新容器型別」該是「註冊一個元件」而非「加一個 case」；也預測 Rust 的 `relation` 由流過的型別決定（見 [concepts/元件](../concepts/元件.md)「`relation` 屬於邊」）**必須**要型別有身分才做得到
- **壓縮** ✓ —— 型別清單／值渲染器／參數型別收成同一個 registry

三個都中，但**兩個槽是虛的，明標**：

| 槽 | 型別填得出嗎 |
|---|---|
| 身分 | ✓ `cpp:stack` |
| 接點 | ⚠️ `stack<T>` 的 `T` 算 composition 接點？勉強成立，但泛型參數和 `body` 槽是不是同一種東西沒想清楚 |
| 參數 | ✗ 想不出 |
| 形態 | ✓ 值圖解、型別名的文字形態 |
| 行為 | ⚠️ 操作動畫算不算它的 behavior？操作本身是別的元件 |

照五槽模板的剪枝力判準，**填不出就代表不是元件**。這裡填出三格、虛兩格——所以是**方向、不是結論**，標成賭注、鎖在 draft。

**替代方案沒想過**：也許型別不需要是元件，只需要在 registry 有一筆「值渲染器」條目（比元件輕）。這個更小的版本可能才是對的，未評估。

## ② 的回報：圖鑑三合一

先前已經發現 **Blockly 的 toolbox ＝ ArduinoCAD 的 codex ＝ 登錄表的瀏覽投影**，統一 registry 後自動合併（見 [硬體域併入計畫](2026-08-05-硬體域併入計畫.md)）。型別也進 registry 的話，同一個圖鑑裡有三種東西：

```
圖鑑
├─ 積木／概念   count_loop、cpp_string_at…
├─ 零件         arduino-uno、led、hc-sr04…
└─ 資料結構     stack、queue、tree、graph…   ← 新的
```

每格都是「身分 ＋ 多形態 ＋ 行為 ＋ 說明」。**資料結構的「行為」就是它的操作動畫**（push 進去掉下來、pop 彈出來），和零件的 `behavior.step` 是同一個槽。

**這對教育 telos 命中得準**：學生在同一個地方認識「積木、零件、資料結構」，一個心智模型通吃——正是三真金裡的**學習遷移**。

### 補上第四格：**抽象元件**（2026-08-09）

跨語言的共通意義住在圖鑑，不住在機器層（見
[等價與觀察集](../concepts/等價與觀察集.md) 第六章）。於是圖鑑多一格：

```
圖鑑
├─ 積木／概念   ← 各語言各自的元件
├─ 零件
├─ 資料結構
└─ 抽象元件     ← 新的：一群可互換的元件
```

⚠️ **這一格的成員是導出的，不是人挑的**：

> **一個抽象元件 = 某個容差底下的等價類**（從轉換邊算出來）。
> 名字、解釋、容差是人寫的；**成員不是**。

護欄要管的是**來源**不是大小——單元素聚類合法
（`cpp:pointer_declare` 只有 C++ 有，而圖鑑寫「這個概念沒有其他語言的對應」
本身就是有價值的教學內容）。

**而它今天就能起跑**，不必等第二個語言：語言內部已經有四群同義操作
（大小／加入／取值／看某一端）——那就是第一批抽象元件。

**同一組邊、不同容差 → 不同粗細的圖鑑**：粗容差給初學（「序列」涵蓋一切有順序的），
細容差給進階（分出隨機存取／循序）。**漸進揭露因此有了機械基礎。**

## ③ 有一條紀律必須在畫第一個箱子之前就立

記憶體圖解會誘發一件危險的事：**在圖上拖一個值**。

那時候改的是**執行期狀態**（行為投影），**不是程式**（唯一真實）。ArduinoCAD 有一條 experience 正好講這個：

> **調的是「視圖投影」還是「語義真相」，要分明。**

所以：

- 記憶體圖解對**程式**而言是**唯讀投影**——照 P1 投影定理，只能單向的視圖 MUST 標記唯讀
- 它對**執行狀態**可以是可寫的（改一個值繼續跑）
- **兩者在 UI 上必須看得出差別**

這條之後很難拆，要先定。照 [投影](../concepts/投影.md) 的 R0-R4，圖解形態大概落在 R3／R4（視覺化，不可逆回語義）。

## 前置相依（哪些現在就能做、哪些要等）

| 要做的 | 前置 | 現況 |
|---|---|---|
| **基本型別的箱子圖解** | **無** | `src/ui/panels/variable-panel.ts`（167 行）已經在顯示變數——把表格換成箱子，**資料來源不變** |
| 指標／參考的箭頭 | 無 | `cpp_address_of`／`cpp_pointer_declare`／`cpp_pointer_deref`／`cpp_ref_declare` 概念都在 |
| 容器（vector/stack/map）圖解 | **型別要有身分** | 擋住 |
| 執行時間軸／記憶體演變 | **結構化的執行 trace** | 未評估直譯器現在吐什麼 |
| 資料結構圖鑑 | 型別身分 ＋ 統一 registry | 擋住 ×2 |

**便宜的第一步是「基本型別箱子」**——零新地基，而且它會逼出「唯讀 vs 可寫」那條紀律的第一個實例，成本低、資訊多。

## 還沒想清楚的

- **型別是元件，還是只是 registry 裡一筆更輕的「值渲染器」條目？** 五槽只填得出三格，可能該用更小的版本。
- **① 元件圖解形態的價值有多高？** 流程圖是很老的東西，而積木本身已經是視覺形態——`if` 畫成分岔比積木多解釋了什麼？**沒想清楚就別做**（過不了 over-justify 的話 ① 該砍，只留 ②③）。
- **執行 trace 的形狀**：直譯器現在吐什麼？③ 全部建立在這上面，但完全沒評估。
- **和 [漸進揭露](../concepts/漸進揭露.md) 的關係**：圖解適合哪個 Level？箱子圖對 L0 很好，但對 L3 可能是噪音——形態要不要隨 Level 切換？
- **和膠囊格式的順序**：② 需要型別身分＝改核心型別（P5），③ 需要 trace。兩者都在 [元件膠囊重構](retired/2026-08-05-元件膠囊重構.md) 的中後期之後。**只有「基本型別箱子」可以插隊。**

> 本檔是它的 **in-flight rationale**，做完才退休。——而量出來之後，難的地方不是我以為的那個

> 日期：2026-08-13
> 怎麼冒出來的：使用者問「C 和 C++ 需不需要算同一種語言」，接著五輪追問
> （版本 → Python／JS／硬體 → 目錄結構 → 環境／積木／風格 → 「你可以多想一點嗎，
> 因為 C/C++ 真的是很難分難捨」）。
> **狀態：兩個量測已做（全量 ＋ 對照），C style 已加，兩個現成缺陷已查出，
> 而「目標」那個設計未決。** captured ≠ committed。

## 一、量出來的答案

`node tests/probes/c-vs-cpp.mjs`（**探測，不是護欄**——沒有東西該被推向零）：

```
262 段教學語料，C99 編得過 5 段

而 C 編不過的第一個錯誤是什麼：
  230  #include <iostream>
    9  其他 C++ 標頭（<string> <vector> <algorithm>）
    6  cout／endl
    3  bool 未宣告（C99 要 <stdbool.h>）
    2  try
    2  vector
    2  class
    1  must use 'struct' tag to refer to type 'Point'   ← 唯一一個真的語義差異
```

### 分成三類之後，「難分難捨」的形狀就變了

| 種類 | 筆數 | 已經有機制嗎 |
|---|---|---|
| **寫法**（`iostream`／`cout`） | ~245 | ✅ `style` 的 `io_style` ＋ 元件的 `ioStyle` 性狀 |
| **有沒有那個東西**（`class`／`try`／`vector`） | ~15 | ✅ Topic 的 `levelTree`（可見集合） |
| **需要一個 include**（`bool` → `<stdbool.h>`） | 3 | ✅ `requires` |
| 🔴 **真的語義差異** | **1** | ❌ `struct Point p;` vs `Point p;`——產生器層 |

> **扣掉「寫法」與「有沒有」之後，262 段教學語料裡真正的 C/C++ 語義差異是 1 筆。**

⚠️ 而那 1 筆是**產生器**的事（產出時要不要加 `struct` 標籤），不是概念的事。

## 二、🔴 而第一版量測問錯了問題——那是這輪最貴的產出

第一版數的是「兩邊都編得過而輸出不同的段數」，得到 **0 / 5**。

那個 0 讀起來像「C 與 C++ 完全一致」，**而真相是只有 5 段兩邊都編得過**
——分母幾乎是空的。

> **一個語料庫如果全部用同一種風格寫成，它量不出「風格差多少」
> ——它只會告訴你它自己選了哪一種。**

這是 `build-guardrail` 6.5「**先問紅的是世界，還是語料**」的**第四次**，
而形式是新的：

| 前三次 | 這一次 |
|---|---|
| 語料**壞掉**（片段、續行符被吃、讀 cin） | 語料**沒壞，而它的分佈本身帶著答案** |

⚠️ 前三次靠「數字不合理」抓到；這一次的數字（0）**看起來像一個乾淨的結論**。
救它的是去看分母。

→ **提議進 `experience`**（待人確認）：

> **一個「差異為 0」的量測，要先確認分母不是 0——
> 而分母為 0 的最常見原因不是語料壞掉，是語料早就選了一邊。**

## 三、五輪追問的共通線

| 問題 | 答案的形狀 |
|---|---|
| C 算不算 C++ | 身分不分（`scope` 是**擁有者**，`concepts/元件.md:117`） |
| 版本（C89／C++11／C++17） | `requires` 多一種值（`"c++11"` 與 `"<vector>"` 同類） |
| Python／JS／硬體也有版本 | 同一個**需求 ↔ 能力**求解的更多實例 |
| 目錄叫 `cpp` 會不會誤會 | 白名單擋下「建一個 `components/c/`」那個**行動** |
| 使用時三樣都不一樣 | 三個機制各自對，**而沒有東西保證它們指向同一個世界** |

> **每一次「這是一個新問題嗎」的答案都是「不是，它是既有機制還沒被用到的那一格」。**

⚠️ **而第五輪指出了唯一真正缺的東西**：三個機制（Topic／style／參照編譯器）
today 各存一半，而使用者要選三次且必須一致。那個東西叫**目標**：

```
target: c99-teaching
  visible    → levelTree      （哪些積木看得到）
  io         → cstdio         （產出 printf 還是 cout）
  provides   → ["c99", …]     （requires 對它求解）
  reference  → gcc -std=c99   （驗證）
```

**它不是新的抽象層，是把三個既有欄位綁成一個具名的組合**——就像 `style`
已經把一堆排版選項綁成 `apcs`／`google`／`competitive`。

⚠️ 而「等第二個目標出現」的條件**已經滿足了**：`cpp-competitive` 有自己的
`levelTree` 而**沒有自己的 style**——所以今天就可以問「競賽班用 printf 還是 cout」，
如果答案是「看老師」，不一致已經存在，只是還沒有人撞到。

### 🔴 而 2026-08-14 它找到了第一個**真消費者**：語義診斷

[語義診斷系統](2026-08-05-語義診斷系統.md)（2026-08-14 的 §一）：

```
auto x = 1;        C++03 錯、C++11 對
bool b = true;     C++ 對、C99 要 <stdbool.h>
Point p;           C++ 對、C 要寫 struct Point p;
```

> **診斷不是語義樹的函數，它是 `(樹, 目標)` 的函數。**

而「目標」正是本節設計的那四個欄位。**兩份 draft 各自缺對方**：
這一份缺消費者（所以 `target` 一直沒被做），那一份缺第二個輸入。

### 🔴 而 2026-08-17 出現第二個消費者，**它比第一個硬**

使用者逐字：「**Arduino 的話我想要先把它至少視為不同風格或是不同語言，
而不是純粹 C++**」。

而這個專案的三個現成的軸，Arduino **落在中間那一格**：

```
style      APCS／競賽／Google      排版與慣用法        ⚪ 便宜
🔴 target  已設計、【零消費者】     能力／可見／驗證    🟡 中
language   cpp／python            完整語言套件        🔴 貴——而 Arduino 就是 C++
```

**`style` 裝不下它**：`setup/loop` vs `main`、`String` vs `string`、沒有 `iostream`
——⚠️ 那不是排版，是**哪些概念存在**。而 `style` 今天的六個欄位
（`io_style`／`naming`／`indent`／`brace`／`namespace`／`header`）
**沒有一格裝得下它**。硬塞會讓 `style` 長出一個它不該有的責任。

**`language` 太重**：實測十段 Arduino **殘差節點 0/10**，177 顆膠囊直接可用。

而 `target` 的四個欄位**正好是 Arduino 與 C++ 的全部差異**：

```
target: arduino-uno
  visible    → levelTree      沒有 main，而有 setup／loop
  io         → Serial         而不是 cout／printf
  provides   → ["arduino"]    pinMode／digitalWrite 的 requires 對它求解
  reference  → arduino-cli    而不是 g++
```

#### 🔴 而它比診斷那個消費者硬

```
診斷      「先不做也不會怎樣」——今天的診斷仍然有用，只是分不出 C++03/11
Arduino   🔴 【無路可走】——setup／loop 不是 C++ 的合法程式進入點
```

> **一個「不做就繞不過去」的消費者，與一個「不做會少一點準確度」的消費者，
> 對一個等了很久的機制來說是兩種完全不同的訊號。**

#### ⚠️ 而它順手更正了一個我下錯的結論

2026-08-17 用 wasi clangd 當裁判時，十段 Arduino 全部歸「無法確定」，
我把理由寫成「**裁判看不懂那個方言**」（`history/071`）。

**更準的說法是：我們沒有告訴它目標是什麼。**
`reference` 那一欄如果是 `arduino-cli` 而不是 `clangd --target=wasm32-wasi`，
那十筆**就是可判的**。

> **裁判的能力邊界不是固定的——它是【目標】的函數。**

⚠️ 而 `history/071` 那條教訓（「一個裁判的能力邊界，會偽裝成被判者的缺陷」）
**仍然成立**，這一段是它的細化不是推翻：邊界確實存在，
**而它的位置由我們給的目標決定**。

⚠️ 這也修正了本節原本的排期理由：`target` 等的不是「第二個教學目標出現」，
而是**第一個需要它的功能**——而那個功能已經排在下一個了。

## 四、順手查到的兩個現成缺陷

### ① `tree-sitter-c` 裝了，而完全沒有被接上

```
public/tree-sitter-c.wasm        ✅ 檔案在
package.json  "tree-sitter-c"    ✅ 依賴在
src/ 與 tests/ 引用它            ❌ 零次
```

**有人在某個時候決定要支援 C，裝了文法，然後停在那裡**——而知識庫零記載。

⚠️ 它是「機制有了沒人接上」的又一個實例，**而這次是一個未完成的意圖**，
不是一個壞掉的機制。→ 要嘛接上（它是量差異的另一半），要嘛拔掉
（一個裝了不用的依賴會讓人以為支援 C）。

### ② `io_style` 與 `ioStyle` 是同一件事的兩套詞彙

```
style 說     io_style: "printf"   （snake_case，值是 printf／cout）
元件說       ioStyle:  "cstdio"   （camelCase，值是 cstdio／iostream）
```

**同一件事，兩個欄位名、兩套值。** 而它們今天靠某處的翻譯對上
——那是一個等著出問題的接縫（`concepts/元件.md` 的命名章節管的正是這個）。

## 五、✅ 對照實驗做了——而兩次獨立的量測給出同一個答案

`src/languages/cpp/styles/c.json`（`io_style: printf`、`namespace_style: explicit`）
＋ `tests/probes/c-style-parity.test.ts`。

⚠️ **不用改型別**：`namespace_style: 'explicit'` 已經讓
`useNamespaceStd = false`（`sync-controller.ts:21`）——**那個值域早就留了位置**。

```
同一棵語義樹 → C style     → gcc -std=c99   ：6 通過 / 10
                            ✘ use of undeclared identifier 'bool'   ×3
                            ✘ must use 'struct' tag to refer to type 'Point'  ×1
             → C++ style   → 產 cout（對照組）
```

🔴 **與 §一 全量量測的結論完全對上**：

| §一（262 段，只有一邊的語料） | §五（10 段，同一棵樹兩種投影） |
|---|---|
| `bool` 要 `<stdbool.h>` — 3 筆 | ✘ `bool` — 3 筆 |
| `must use 'struct' tag` — 1 筆 | ✘ `struct` 標籤 — 1 筆 |
| 其餘全是寫法 | ✅ C style 產出**零** `cout`／`iostream`／`using namespace` |

> **兩個方法、不同的語料、同一個答案——而其中一個方法的語料是偏的。
> 那讓「1 筆語義差異」從一個可疑的數字變成一個站得住的結論。**

### 而剩下的兩項各自是什麼

| 失敗 | 性質 | 修法 |
|---|---|---|
| `bool` 未宣告（3 筆） | **`requires` 的事**——C99 的 `bool` 住在 `<stdbool.h>` | 產生器按 style 決定補哪個標頭 |
| `struct Point p;`（1 筆） | 🔴 **唯一真的語義差異**——C 要標籤，C++ 不要 | 產生器按 style 決定要不要加 `struct` |

**兩者都在產生器層，都不動任何概念身分。**

### ⚠️ 而測試本身教了一件事

第一版的反向測試（「C++ style 仍然產 cout」）**空過**：它先撈中性語料再篩
「有輸出的」，而那批剛好都用 `printf`——篩完是空集合，`.some()` 永遠 false。

> **一支反向測試如果它的輸入是被篩出來的，那個篩選就是它的盲點。**

改成 inline 語料（同一棵樹，兩種投影，斷言它們不同）。

## 六、下一步——而它只剩兩件很小的事

對照實驗（§五）把問題縮到兩個**產生器層**的缺口，而它們都不動概念身分：

```
① bool → <stdbool.h>    產生器按 style 決定補哪個標頭
                        ⚠️ 而那是 requires 的既有機制——今天 requires 記的是
                        C++ 的標頭名（`<cstdio>`），C style 要的是 `<stdio.h>`
                        → 一張「同一個東西在兩個世界的名字」對映表

② struct Point p;       產生器按 style 決定要不要加標籤
                        🔴 唯一真的語義差異，而它是一個 if
```

⚠️ **而①比看起來大一點**：`<cstdio>` vs `<stdio.h>` 不是特例，是**整族**
（`<cstring>`／`<cstdlib>`／`<cctype>`／`<cmath>` 都有兩個名字）。
那張表有 ~10 筆，而它今天不存在。

### 而做完之後才問得了下一個問題

```
今天    C style 產出的碼「編得過」            ← §五 驗的
之後    C style 與 C++ style 的產出【行為相同】 ← 還沒驗
```

**編得過只是門檻。** 真正的對照是把兩邊都跑起來比輸出——而那要等①②修完，
因為今天有 4/10 段編不過，分母不夠。

⚠️ 那與 §二 的教訓是同一條：**分母不夠時，任何「差異為 0」都不算數。**

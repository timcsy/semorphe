# C 和 C++ 難分難捨——而量出來之後，難的地方不是我以為的那個

> 日期：2026-08-13
> 怎麼冒出來的：使用者問「C 和 C++ 需不需要算同一種語言」，接著五輪追問
> （版本 → Python／JS／硬體 → 目錄結構 → 環境／積木／風格 → 「你可以多想一點嗎，
> 因為 C/C++ 真的是很難分難捨」）。
> **狀態：一個量測已做，兩個現成缺陷已查出，設計未決。** captured ≠ committed。

## 一、量出來的答案

`node tests/probes/c-vs-cpp.mjs`（**探測，不是護欄**——沒有東西該被推向零）：

```
262 段教學語料，C99 編得過 5 段

而 C 編不過的第一個錯誤是什麼：
  230  #include <iostream>
    9  其他 C++ 標頭（<string> <vector> <algorithm>）
    6  cout／endl
    3  bool 未宣告（C99 要 <stdbool.h>）
    2  try
    2  vector
    2  class
    1  must use 'struct' tag to refer to type 'Point'   ← 唯一一個真的語義差異
```

### 分成三類之後，「難分難捨」的形狀就變了

| 種類 | 筆數 | 已經有機制嗎 |
|---|---|---|
| **寫法**（`iostream`／`cout`） | ~245 | ✅ `style` 的 `io_style` ＋ 元件的 `ioStyle` 性狀 |
| **有沒有那個東西**（`class`／`try`／`vector`） | ~15 | ✅ Topic 的 `levelTree`（可見集合） |
| **需要一個 include**（`bool` → `<stdbool.h>`） | 3 | ✅ `requires` |
| 🔴 **真的語義差異** | **1** | ❌ `struct Point p;` vs `Point p;`——產生器層 |

> **扣掉「寫法」與「有沒有」之後，262 段教學語料裡真正的 C/C++ 語義差異是 1 筆。**

⚠️ 而那 1 筆是**產生器**的事（產出時要不要加 `struct` 標籤），不是概念的事。

## 二、🔴 而第一版量測問錯了問題——那是這輪最貴的產出

第一版數的是「兩邊都編得過而輸出不同的段數」，得到 **0 / 5**。

那個 0 讀起來像「C 與 C++ 完全一致」，**而真相是只有 5 段兩邊都編得過**
——分母幾乎是空的。

> **一個語料庫如果全部用同一種風格寫成，它量不出「風格差多少」
> ——它只會告訴你它自己選了哪一種。**

這是 `build-guardrail` 6.5「**先問紅的是世界，還是語料**」的**第四次**，
而形式是新的：

| 前三次 | 這一次 |
|---|---|
| 語料**壞掉**（片段、續行符被吃、讀 cin） | 語料**沒壞，而它的分佈本身帶著答案** |

⚠️ 前三次靠「數字不合理」抓到；這一次的數字（0）**看起來像一個乾淨的結論**。
救它的是去看分母。

→ **提議進 `experience`**（待人確認）：

> **一個「差異為 0」的量測，要先確認分母不是 0——
> 而分母為 0 的最常見原因不是語料壞掉，是語料早就選了一邊。**

## 三、五輪追問的共通線

| 問題 | 答案的形狀 |
|---|---|
| C 算不算 C++ | 身分不分（`scope` 是**擁有者**，`concepts/元件.md:117`） |
| 版本（C89／C++11／C++17） | `requires` 多一種值（`"c++11"` 與 `"<vector>"` 同類） |
| Python／JS／硬體也有版本 | 同一個**需求 ↔ 能力**求解的更多實例 |
| 目錄叫 `cpp` 會不會誤會 | 白名單擋下「建一個 `components/c/`」那個**行動** |
| 使用時三樣都不一樣 | 三個機制各自對，**而沒有東西保證它們指向同一個世界** |

> **每一次「這是一個新問題嗎」的答案都是「不是，它是既有機制還沒被用到的那一格」。**

⚠️ **而第五輪指出了唯一真正缺的東西**：三個機制（Topic／style／參照編譯器）
today 各存一半，而使用者要選三次且必須一致。那個東西叫**目標**：

```
target: c99-teaching
  visible    → levelTree      （哪些積木看得到）
  io         → cstdio         （產出 printf 還是 cout）
  provides   → ["c99", …]     （requires 對它求解）
  reference  → gcc -std=c99   （驗證）
```

**它不是新的抽象層，是把三個既有欄位綁成一個具名的組合**——就像 `style`
已經把一堆排版選項綁成 `apcs`／`google`／`competitive`。

⚠️ 而「等第二個目標出現」的條件**已經滿足了**：`cpp-competitive` 有自己的
`levelTree` 而**沒有自己的 style**——所以今天就可以問「競賽班用 printf 還是 cout」，
如果答案是「看老師」，不一致已經存在，只是還沒有人撞到。

## 四、順手查到的兩個現成缺陷

### ① `tree-sitter-c` 裝了，而完全沒有被接上

```
public/tree-sitter-c.wasm        ✅ 檔案在
package.json  "tree-sitter-c"    ✅ 依賴在
src/ 與 tests/ 引用它            ❌ 零次
```

**有人在某個時候決定要支援 C，裝了文法，然後停在那裡**——而知識庫零記載。

⚠️ 它是「機制有了沒人接上」的又一個實例，**而這次是一個未完成的意圖**，
不是一個壞掉的機制。→ 要嘛接上（它是量差異的另一半），要嘛拔掉
（一個裝了不用的依賴會讓人以為支援 C）。

### ② `io_style` 與 `ioStyle` 是同一件事的兩套詞彙

```
style 說     io_style: "printf"   （snake_case，值是 printf／cout）
元件說       ioStyle:  "cstdio"   （camelCase，值是 cstdio／iostream）
```

**同一件事，兩個欄位名、兩套值。** 而它們今天靠某處的翻譯對上
——那是一個等著出問題的接縫（`concepts/元件.md` 的命名章節管的正是這個）。

## 五、下一步：用 semorphe 自己產生對照語料

第一版量測的問題是「語料只有一邊」。而**這個專案有辦法生出另一邊**：

```
同一棵語義樹 → generate(style = C 風格)  → gcc -std=c99
             → generate(style = C++ 風格) → g++ -std=c++17
                                          ↑ 輸出一樣嗎
```

**那才是真正的對照實驗**——同一個語義，兩種投影，比它們的行為。

⚠️ 而今天缺的只有一樣：**一個真的 C style**。`competitive` 的 `io_style`
已經是 `printf`，但它仍然產 `using namespace std;`（`namespace_style: "using"`）。

→ 那讓「加一個 C style」變成一個**很小而且立刻可驗**的下一步。

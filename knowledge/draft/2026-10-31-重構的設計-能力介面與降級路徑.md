## 一、三個視角怎麼說

**principles**
- 根公理「唯一真實，各式投影」：語意只能有一份 ⟹ 切換後 `execute` 的語意不得留在元件裡（10-20 已定）。
- P6 誠實降級（principles.md:156）：「降級必須單調遞減、**必須可見**、必須區分原因」⟹ 每個結果帶**出處**與**少了什麼**，不能靜默換一個比較弱的答案。
- P9 四項獨立性（principles.md:204）：「Core 不 import View……跨層通訊只走 Bus」⟹ 提供者是核心外的實作，核心只宣告角色。
  這與 `src/core/execution.ts` 檔頭的判準同一條：「**核心宣告角色，實作在外面**……直譯器是它的**第一個實作**，而不是它的擁有者。」

**vision**
- 304：網頁版一律 Cella；外接用標準工具鏈（DAP）；不再維護 JS 直譯器。
- 盟約（305）：Cella 觀測、semorphe 行動；第 4 條「致動器宣告能力（粒度、`setInput` 與 `setVariable` 分開、給不給步數）」；
  第 8 條「修復而非解約：一方失約時判決降級並標出哪一環斷了」。
- 防腐層（formalize）在 DDD 裡的位置與它超出 DDD 的地方：[Semorphe 加 cella 與 DDD](2026-10-05-Semorphe-加-cella-與-DDD.md)（⚠️ 例子是淺嵌入時期的走訪器＋契約，結論仍成立）。

**experience**（今天量到的）
- 盤點：產品裡**直接**碰 `SemanticInterpreter` 的只有 `src/ui/execution-controller.ts`（969 行，三處 `new SemanticInterpreter`：360／453／700）；
  `core/iterations.ts` 讀它的 `getVisitCounts()`。其餘 28 個 import 都在 `languages/*/runtime`、`executors` 與元件的 `execute.ts`——也就是**直譯器的內部**。
  ⟹ 接縫很窄：包住直譯器的那一層，幾乎只要替換 `ExecutionController` 的三個建構點。
- 匯流排已經有一組執行事件（`core/sync/semantic-bus.ts`）：`execution:state`／`output`／`at-node`／`coverage`／`breakpoints`／`run`／`input`／`set-variable`。
  ⟹ 這就是行動插槽的 UI 那一半；**事件不用改**，改的是誰發它們。

## 二、形狀

```
                ┌──────────── 核心（core/）只認這一層 ────────────┐
                │ Capability    verdict │ types │ session │ steps   │
                │ Provider      { id, declares: Capabilities, … }  │
                │ Registry      有序：[Cella, JS 直譯器, …] → 每項能力挑第一個宣告了它的 │
                │ Result<T>     { value, provenance: providerId, missing: Capability[] } │
                └─────────────────────────────────────────────────┘
                     ▲ 實作（核心外，可整個刪）
      providers/cella/     providers/js-interpreter/     （之後）providers/clang-wasm/、providers/dap/
```

- **四項能力**（第 1 題已定）：
  - `verdict(program) → {verdict, problems[{kind, at:nodeId, clause}], assumes[], basis}`——形狀照抄 Cella 的判決 JSON，不另發明。
  - `types(program, candidates) → slots{fits{level}}`——同 Cella 的型別查詢。
  - `session(program, inputs) → DAP 形狀`：`run`／`stop`、`at-node`、`frames`／`globals`、`setInput`、`setVariable`、`feed`。
  - `steps`：「一步 ＝ 進入帶標籤的節點一次」（雙方同意的定義）。
- **能力宣告**（盟約第 4 條）：`{ granularity: 'statement' | 'node', setInput: bool, setVariable: bool, steps: bool, timeModel?: 'ms' }`。
- **結果帶出處**：UI 一律讀 `provenance` 與 `missing`，在畫面上標「這是 X 給的、少了 Y」（P6「必須可見」）。
- **沒有任何提供者**：該能力回 `missing`，UI 照第 3 題顯示（型別：「型別檢查需要 Cella」；判決：unknown）。

## 三、階段 1 要做到的（spec 的驗收來源）

1. 介面與登錄表住在 `core/`；`ExecutionController` 不再 `new SemanticInterpreter`，改向登錄表要 `session`。
2. **JS 直譯器包成第一個提供者**：宣告 `session`（node 粒度、`setInput` 否、`setVariable` 是、`steps` 是）；`verdict` 與 `types` **不宣告**
   ——今天的 JS 直譯器沒有判決與型別查詢這兩種能力，假裝有就違反 P6。
3. **分層護欄**：`core/`、`ui/` 不得 import `providers/*`；只有組裝點（`main.ts`／`app.ts` 的註冊）可以。
4. 行為不變：e2e 全綠、課文判題照舊；`execute.ts` 一個字不動（第 4 題）。

## 五、🔴 設計中冒出來、還沒人定的（附推薦）

1. **判題（課文 check）走哪一項能力？** 今天判題是「跑一次、比 stdout」。
   推薦：判題用 `verdict`，`verdict` 沒有提供者時退回 `session` 跑一次比輸出——**並在結果上標出處**。
   理由：Cella 的判決同時給 `out` 與 `problems`，比只比輸出多擋一類「輸出對、但有 UB」的解答；而退回路徑讓階段 1～4 期間判題照舊。
2. **提供者住哪個目錄？** 推薦 `src/providers/<id>/`，與 `core/`、`languages/`、`ui/` 平級，分層護欄好寫。
   另一個選項是放進 `languages/<lang>/`——但 Cella 提供者跨四個語言，放哪個語言下都不對。
3. **同一項能力有兩個提供者時，要不要「並跑比對」？** 推薦：**不在產品裡並跑**（使用者 10-11 選的是「不維護兩份語意」）；
   比對只在切換前的探針裡做一次（`step-budget` 對 Cella 再跑一次，已列在切換清單）。

## 五之五、🟢 已定：階段 2 的 `component.json` 新形狀——**視圖優先，包一層 `views`**（使用者 2026-10-31）

> ✅ **已落地**（2026-10-31，spec 181）：349 個宣告改成新形狀；`judges.ts` 的鍵是格子名（`blocks.render`、`code.lift`……，視圖在前，與宣告的巢狀順序一致）。

我原本推薦「動詞 → 視圖」，使用者問「如果是先視圖呢？」——視圖優先更好：字面上就是「每個視圖一對 render／lift」，
同一個視圖的一對放在一起；只能單向的視圖（診斷、對照圖）只寫 `render`；刪一個視圖是整塊拿掉。`formalize`／`execute` 不是視圖，所以包一層 `views` 隔開：

```json
"paths": {
  "views": {
    "blocks": { "render": "./forms/blocks.json", "lift": "./forms/blocks.json" },
    "code":   { "render": "./generate.ts",       "lift": "./lift-pattern.json" }
  },
  "formalize": "./formalize.ts",
  "execute":   "./execute.ts"          // 🪦 階段 6 拿掉
}
```

以下是決定之前的提案紀錄：

10/20 定了方向（每個視圖一對 render／lift，generate、extract 退場），四之十三把「視圖的名字與 component.json 的新形狀」留到排刀時再提。今天的形狀：

```json
"paths": { "render": "./forms/blocks.json", "extract": "./forms/blocks.json",
           "generate": "./generate.ts", "execute": "./execute.ts", "lift": "./lift-pattern.json" }
```

⚠️ 今天的 `render`／`lift` **已經被佔走**：`render` 指的是「畫成積木」、`lift` 指的是「從程式碼辨識」——只是名字，各對一個視圖。

**推薦（形狀 A）**：路徑名改成「動詞 → 視圖 → 檔」兩層。

```json
"paths": {
  "render":    { "blocks": "./forms/blocks.json", "code": "./generate.ts" },
  "lift":      { "blocks": "./forms/blocks.json", "code": "./lift-pattern.json" },
  "formalize": "./formalize.ts",
  "execute":   "./execute.ts"          // 🪦 階段 6 拿掉
}
```

- 視圖名：`blocks`（積木）、`code`（程式碼）；之後的流程圖、電路圖照樣加一個鍵，**不加新動詞**（使用者的理由：未來有程式以外的領域）。
- 檔名（`generate.ts`、`lift-pattern.json`）**先不改**——改名只改宣告的鍵，檔名留到各自被碰到時（避免一次動 349×2 個檔、和進行中的分支大面積衝突）。
- 五路完備性改成「每個出現的視圖 render／lift 成對 ＋ formalize」；`judges.ts` 的 `PATH_JUDGE` 鍵改成 `render.blocks`、`render.code`……（今天它已有 `render`／`lift` 兩個鍵，平鋪的話會撞號）。

另一個選項（形狀 B，不推薦）：平鋪成 `renderBlocks`／`renderCode`／`liftBlocks`／`liftCode`。簡單，但視圖名被編進鍵名，加一個視圖就是加兩個新鍵——正是使用者要避免的。

⚠️ 這一刀動 349 顆元件的宣告、載入器、五路完備性與 `judges.ts`；要等 389（formalize 搬進膠囊）合進 main 之後再開，免得衝突。

## 五之六、🟢 已定：通用函式呼叫要不要依函式名補標頭（第 394 刀，Cella 判決量測時翻出）

> 🟢 **2026-10-31 使用者照推薦定 A；第 395 刀做完、2026-11-01 合進 main**（bddb705b）：新元件 `cpp:time`（「現在的時間（秒）」，
> 宣告 `<ctime>`），第 12 課改用它。B（函式名 → 標頭的表）仍是「等第二個同類案例再做」——**它是本節唯一還開著的事**。

**量到的**：課文 `cpp-beginner/12-猜數字/make2.cpp` 寫 `srand(time(0));`。`srand` 有自己的元件（`cpp:random_seed`，宣告 `<cstdlib>`），
而 `time(0)` 落到**通用的函式呼叫**——相依解析（`DependencyResolver`）只認元件身分，所以 `<ctime>` 從來補不到。
產出的程式碼今天能編，是靠編譯器遞移帶進標頭（與「本機比 CI 寬鬆」那一類同形：換一台編譯器就可能紅）。整個 repo 沒有任何地方宣告 `<ctime>`。

**選項**：

| | 做法 | 代價 |
|---|---|---|
| A | 給 `time(0)` 一顆自己的元件（例如「現在的時間（秒）」），宣告 `<ctime>` | 工具箱多一塊積木——**使用者看得到的設計**；只解這一個函式 |
| B | 相依解析多認「通用函式呼叫的函式名 → 標頭」（一張表，語言套件提供） | 所有標準函式一次解決；但那張表是第二份「函式在哪個標頭」的知識（Cella 的標頭模型是另一份） |
| C | 不修，等階段 5：Cella 的判決對「用了沒 include 的函式」會判 reject（未宣告），積木上標出來 | 學生看得到原因；但產出的程式碼在那之前照樣靠遞移 |

**推薦 A**（短期）＋ 記下 B 的需要：`time(0)` 在課文裡出現的形狀幾乎只有「亂數種子」這一種，給它一塊積木與「`random_seed` 的種子」一起出現最好懂；
B 等第二個同類案例出現再做（一個實例不足以撐起一張表）。⚠️ A 會改工具箱與課文的積木，要你點頭。

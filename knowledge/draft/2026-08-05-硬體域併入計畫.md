# 硬體域併入計畫（ArduinoCAD → Semorphe）

> 日期：2026-08-05
> 怎麼冒出來的：跨專案詞彙／連接理論協商（五封往返）收斂後，使用者問「ArduinoCAD 該怎麼併——開一個像 Blockly 的硬體專案，還是 Semorphe 直接處理軟硬體？渲染／幾何要不要獨立套件？有沒有現成的？」
> **狀態：未承諾排期。** 合流本身在 ArduinoCAD 側仍是 draft（captured≠committed）。本檔記的是**併入的形狀與順序**，不是排期。
> **理論地基**：[concepts/元件](../concepts/元件.md)（接點／關係律／守恆分兩律／薄協定判準）。

## 一句話

**切分不是「軟體 vs 硬體」，是「語義 vs 投影後端」。** 元件與求解器進 Semorphe；渲染與幾何留在 `src/render/` 後面一條 seam；**不要開硬體專案**。

## ArduinoCAD 不是一個東西，是四種

| 內容 | 是什麼 | 去哪 |
|---|---|---|
| 23 顆零件定義（`typeId`／`pins`／`representations`／`behavior`／`info`） | **元件庫**，和 `std/vector/` 同型 | **進 Semorphe** |
| 電氣傳播／DRC（`propagation.ts`、`simulation-state.ts`） | **守恆求解器**＝全樹流敏感約束 | **進 kernel**（新脊椎） |
| 2D SVG renderer、3D circuit renderer、參數化 CAD 引擎（`archetypes/`） | **形態投影後端**，不理解語義 | **`src/render/`**（seam 後） |
| 圖鑑 `codex.html`、接線／擺放 UX | **登錄表的視圖 ＋ 組裝編輯器** | **app 層 panel** |

## 為何不開「負責硬體的專案」

三條都來自 [concepts/元件](../concepts/元件.md)：

1. **Registry 必須是一個。** 跨域接線（積木輸出 → 硬體 pin）需要共同的登錄表與共同的 `componentId` 命名空間。兩個專案＝兩個 registry＝回到 N×M，合流的整個賣點就沒了。
2. **沿域切會複製「按機制分檔」那個病。** [元件膠囊重構](retired/2026-08-05-元件膠囊重構.md) 的根因診斷是「按機制組織，於是任何單一元件必然被攤散」。開硬體專案就是把元件沿域再攤一次——同一個病，換個維度。
3. **概念檔的核心主張直接反對它。** 「元件是三域同一抽象」「關係律跟資源走不跟域走」。硬體要獨立專案，那 UI 將來也要一個、第四域再一個——母抽象退化成口號。

## 渲染／幾何：不分套件（現在）

**用 over-justify 測「分」這個動作本身**：多解釋 ✗（同一份碼換地方）、多預測 ✗、壓縮 ✗（一樣的量，多一份 package.json 與發版流程）。**三個都不中，現在分過不了自己那把刀。**

反面成本是實的：

- **repo 切分是最貴的一種切**，而這專案的頭號病就是「同一塊碼沿不同軸反覆重切 ＝ 碎屑」。
- **只有一個消費者。** Blockly 是獨立套件因為 Google 為很多消費者寫；單一消費者的套件，介面是對想像設計的——那正是「011／048 各統一一半」的溫床。
- **合流期正是共同設計期**，每改一次渲染層就 publish + bump，是每次改動要繳的稅。

### 決定性論據：ArduinoCAD 自己證明了 seam ≠ package 邊界

他們的零相依 ethos 是這樣達成的：`part-3d.ts` 用**注入**拿 THREE、主 App 不 import、`package.json` 維持 `{}`。**THREE／Rapier／three-bvh-csg 全隔離在 seam 後，而那條 seam 在同一個 repo 裡**，撐過 32 條 history、六個大階段。

**薄協定要的是窄接縫，不是分開的倉庫。** 五封信談定的「域內部當不透明酬載」講的是**介面**，不是 npm 套件。

### 落地形狀

```
src/render/          ← 只吃資料形，不認語義
  circuit-2d/        （svg-renderer、繞線、命中測試）
  circuit-3d/        （three-circuit-renderer、three-kit、part-3d）
  geometry/          （solid、sketch2d、expr、params、csg-loader）
  physics/           （rapier seam）
```

邊界用 `tests/integration/audit-render-boundary.test.ts`⟨規劃⟩ 守：斷言 `src/render/**` **不 import** `src/core/`、`src/languages/`、Blockly、Monaco。

符合既有 idiom——`tests/integration/` 已有 `audit-concept-identity.test.ts`／`audit-ptr-concepts.test.ts`，審計式測試是本專案既有的做法。**一條測試取代整套 workspace 工具鏈。**

便宜的未來選項：真要抽出去時，因為測試保證零洩漏，**那個資料夾直接搬走就是套件**。

### seam 的形狀（比分不分重要）

```
進：  元件的形態配方（Solid 樹 / 2D SVG spec / 接點座標）
      組裝（網表 + 位置 + connector frames）
      狀態（behavior state，給動態綁定）
出：  渲染輸出 + 命中測試資訊
禁：  import ComponentRegistry / SemanticNode / 任何語義層
```

**只吃資料、不吃語義**——正是 Blockly 對 Semorphe 的關係（Blockly 不知道 `count_loop`，這層也不該知道 `arduino-uno` 是什麼）。

**seam 對了，之後怎麼切都便宜；seam 錯了，現在分也救不了。**

## 形態槽的形狀（2026-08-10 補；上面那句「新的槽」的展開）

順序那一節寫著硬體「帶來的是**新的槽**（形態多了 2D/3D）」。那是預測，
而這一節是它的內容——**兩邊的形態怎麼合成同一個槽**。

### 對照：AC 把形態當**槽**，semorphe 把它當**頂層記錄**

```
AC        一顆零件一筆記錄  { typeId, pins, representations: { '2d-svg': …, 日後 '3d' } }
semorphe  一個形態一筆記錄  { id, conceptMapping.componentId, blockDef, … }
                              ↑ 靠 componentId 聚合
```

**這是命名漂移的根因，不是有人疏忽**：形態一旦是頂層記錄，它就必須有自己的 `id`，
而兩個身分一定會漂。實測（2026-08-10）：186 顆積木型別裡 **86 顆與身分不同名**、
63 顆拆不出主體，而 `cpp_stack_top` 保存著 G 已經換掉的舊詞。

> **形態一旦是頂層記錄，它就會長出自己的身分。**

⚠️ **這一點讓上面順序的第 2 步不夠**：「統一 registry ＋ `componentId` 命名空間」
統一的是**元件**的身分，而**形態的 id 是另一個命名空間**，不在那一步的範圍裡。

### 合成的骨架：AC 的容器 ＋ semorphe 的軸

```
Component {
  componentId                     ← 唯一身分（形態不再有自己的 id）
  接點 { name, kind, accepts }     ← children ／ pins ／ ports 合流
  參數規格 ParamSpec[]
  forms: {
    <viewKind>: {                 ← 'block' | 'text' | '2d-svg' | '3d'
      <axisValue>?: Form          ← semorphe 的 form:{axis,value} 收成第二層鍵
    }
  }
  behavior
}
```

**形態的名字全部導出**（`componentId` ＋ `viewKind` ＋ 軸值）——沒有第二個身分可以漂。

而 semorphe 的軸是 AC 沒有的東西：`cpp:container_push` 的 `stack`／`queue` 兩種標籤、
`role: statement/expression` 兩種形態。**9 顆多形態元件全部已經宣告了軸**，
那個機制要保住。

### ⚠️ 三個欄位必須明確歸在 seam 的「進」那一側

seam 的形狀寫著「進：元件的形態配方」。而 AC 已經實證了**三樣容易掉進 renderer 的東西**，
它們必須留在資料側：

| 欄位 | AC 的原話 | 不留在資料側會怎樣 |
|---|---|---|
| `dynamic: DynamicBinding[]` | 「把動態表示從 **renderer 硬編**（`.part-rotor` 轉、`.led-glow` 亮）變成**表示自己宣告**」 | 回到硬編。semorphe 這邊還有 **12 對 `plus_`／`minus_`** 是硬編的 |
| `bindsTo` ＋ conformance | 「對應的視覺子件 selector——**conformance 守其存在**」 | 形態的結構層失去唯一一條現成護欄 |
| `approximate` ／ `photo` | 「造型為示意/近似——**誠實標註**」「無則**不冒充擬真**」 | **一個不宣告自己是近似的形態，會被讀成擬真的** |

第三條與 P6 誠實降級是同一條原則的另一面：**降級要出聲，近似也要出聲。**

### 形態有兩層，而只有一層機械化得了

| 層 | 問什麼 | 有外部 oracle 嗎 |
|---|---|---|
| **結構層** | 接點表達得出來嗎？接腳集合對得上嗎？ | ✅ semorphe＝#29 符合性；AC＝`conformance.ts`；硬體另有 **datasheet** |
| **教學層** | 標籤有沒有說謊？好不好懂？ | ❌ **只能問人** |

見 [等價與觀察集](../concepts/等價與觀察集.md) §七。這一刀決定了護欄管得到哪裡
——**結構層蓋護欄，教學層只能靠設計語彙 ＋ 人審**，而語彙的**內容是教學判斷**。

實證：`stack`／`queue` 的 push 標籤說謊那次，**十八條護欄一條都不叫**，學生第一眼看出來。

### 2D 與 3D 是**同一個槽的兩個值**，不是兩條軸

AC 的 `representations: Partial<Record<ViewKind, …>>` 已經是這個形狀
（`ViewKind = '2d-svg'`，註解寫著「結構容許日後加 3d」）。

而「3D 帶有 2D 沒有的資訊」不成立——接腳的**身分**是語義的，**座標**是各表示各自的：

```
表示上：  pinPos / portPos            （2D 座標）
語義埠上：connector3d { pos, axis }   （3D 座標框）
```

⚠️ 但這裡有一個**不對稱**要確認是不是刻意的：**2D 座標掛在表示上，3D 座標掛在語義埠上**。
要支援「同一顆零件的兩種 3D 模型」（簡化／擬真）時，那個框就得搬到表示層。

### ⚠️ 排期更正：形態結構整合**不能塞進 F**

一度想過「與 F（膠囊搬家）合併做，遷移只付一次」。**那是錯的**，理由就是上面順序那節
自己的硬條件——**格式沒收斂就接，等於邊搬家邊改結構**。而形態結構整合改的是
**槽的形狀本身**，比灌零件更深。

| 動作 | 何時 | 為什麼 |
|---|---|---|
| **積木型別改名**（導出） | **綁在 F 裡** | 純命名、規則導得出來、不改槽的形狀；而每顆搬進膠囊時本來就要碰 `forms/` |
| **形態結構整合**（`forms` 容器） | **F 之後、硬體零件之前** | 它改槽的形狀。在 F 進行中做＝邊搬家邊改結構 |


## 什麼時候才真的分出去

**觸發條件只有一個：出現第二個消費者**（有人不透過語義樹就想渲染零件）。在那之前分，是為想像中的使用者設計介面。

要先排除一個看似的理由：**bundle 大小不是分 repo 的理由**。THREE + Rapier + CSG 對只寫 C++ 的使用者是純負擔，但那是 code-splitting 的事（ArduinoCAD 已用 CDN 懶載入解掉，Vite dynamic import 更簡單）。

**順帶釐清一個容易搞混的約束**：Semorphe 本來就有執行期相依（`blockly`／`monaco-editor`／`web-tree-sitter`），加 THREE 不牴觸任何 ethos。**零相依是 ArduinoCAD 的紀律，不是 Semorphe 的**——別把對方的約束當成自己的。

## 現成的能用嗎：基質有，上面那層沒有

**基質層外包**（已在用）：THREE（3D）＋ three-bvh-csg（CSG）＋ Rapier（物理）。

**組裝／參數化那層沒有能用的，而且不該用**：

| 候選 | 死因 |
|---|---|
| JSCAD / OpenSCAD-wasm | **script-driven**——寫 JS 產幾何。違反「要投影的東西得是資料而非程式」，而那正是參數化 CAD 引擎存在的理由 |
| Replicad / OpenCascade-wasm | B-rep 真核心 ~10MB+；ArduinoCAD vision 已否決：**製造精度 regime，與教學可視化相反** |
| planegcs（FreeCAD 約束求解） | 只解草圖約束一格，而他們已有自寫 LM 求解器（4 測驗過） |
| Wokwi elements | 他們**刻意**從執行期相依退成 render-to-data 抽取，回頭是倒退 |
| KiCad / EasyEDA | 是應用程式，不是可嵌入函式庫 |

**2D 電路視圖完全沒有現成的**——帶零件圖稿＋接腳座標＋杜邦弧繞線避障的麵包板渲染是領域特定的。

自維護的那層其實不大：`solid`／`sketch2d`／`expr`／`params`／`csg-loader` 五個檔，全純函式、全數字 ground-truth 測過。

## 視圖：地基已經在了

`src/core/view-host.ts` ＋ `semantic-bus.ts` 已存在，`src/ui/panels/` 底下 `blockly-panel`／`monaco-panel`／`variable-panel`／`console-panel` 已是可插拔單位。要加的是同型的 panel：

```
積木視圖    blockly-panel      ← 形態投影
程式碼視圖  monaco-panel       ← 形態投影
2D 組裝     circuit-2d-panel   ← 形態投影（新）
3D 組裝     circuit-3d-panel   ← 形態投影（新）
圖鑑        registry-browser   ← 登錄表的視圖（新）
```

**圖鑑那格是白拿的**：Blockly 的 toolbox 和 ArduinoCAD 的 codex **本來就是同一個東西**——登錄表的瀏覽投影。統一 registry 之後自動合併，積木與零件在同一個圖鑑裡分類、搜尋、預覽。

## 順序（有一個硬條件）

**膠囊重構的「就近性」必須在硬體元件進來之前做完。**

理由是 [元件膠囊重構](retired/2026-08-05-元件膠囊重構.md) 自己的診斷：「**AI 元件管線把碎裂模板一起規模化**」。現在加一個元件要動 13 個檔；直接灌 23 顆零件 × 5 槽進來，是把碎裂放大一輪，而且那 23 顆會**繼承**碎裂模板，之後要清兩次。

這也回答了那份 draft 懸著的「先收斂還是先 Python」——現在有第三個候選（硬體域），答案不變：**先收斂就近性**。而且硬體域比 Python 更該等，因為它帶來的是**新的槽**（形態多了 2D/3D、行為多了 `step`），格式沒收斂就接，等於邊搬家邊改結構。

1. **膠囊就近性**——把 lift 搬回模組，`io.ts` 塌成路由器
2. **統一 registry** ＋ `componentId` 命名空間——所有其他事的前提
3. **組裝模型進語義樹**（邊、關係、連接）——現行 `SemanticNode` 只有 `children`、沒有邊
4. **2D 組裝 panel** 當第一個垂直切片——證明形態投影可插，風險最低
5. **守恆求解器進 kernel**——同時是 Rust borrow check 的地基
6. 3D／CAD 引擎／物理——加值，不阻斷

**第 5 步是併進來最大的技術收穫，比 23 顆零件值錢**：ArduinoCAD 蓋的電氣傳播，是 Semorphe 加 Rust 時要用的同一台機器的一半（同一類全樹流敏感約束、不同終局判定，見 [concepts/元件](../concepts/元件.md)「守恆的兩種律」）。

## 一個實務警告：併入 ≠ 搬 codebase

ArduinoCAD 的 vision 自己寫著它是**拋棄式研究刺探**，且「TDD 僅適用於要萃取回 semorphe 的核心邏輯；拋棄式 UI 原型以瀏覽器手感評估、不堆單元測試」。

| | 內容 |
|---|---|
| **可搬**（資料形＋純函式，有測試） | 零件定義、`circuitToUrdf`、`resolveAssembly`／`resolveCarAssembly`、`describeSolid`、`circuitToPhysicsSpec`、傳播邏輯 |
| **該重寫**（拋棄式原型） | `codex.html`、接線 UX 膠水、app 綁定層 |

好消息：他們的紀律讓這條線很清楚——「**要投影的東西得是資料而非程式**」那條 experience 的直接回報就是**該搬的幾乎都已經是資料或純函式**。

## 還沒想清楚的

- **命名**：若未來真要抽套件，判準是「像 Blockly 一樣，名字說它**渲染什麼**、不是**服務誰**」。使用者提過想把 ArduinoCAD 改名——但**改名的對象是哪一塊**？零件庫（進 Semorphe，不需要名字）、渲染套件（需要）、還是那個 spike repo 本身（可能該封存而非改名）？未定。
- **組裝模型放語義樹哪裡**：電路是圖、程式是樹，兩者都要進同一棵語義樹嗎？還是「程式」與「電路」是同一個 program 節點下的兩個子樹？沒想。
- **序列化**：ArduinoCAD 的 `CircuitJSON`（`SCHEMA_VERSION=1`）與 Semorphe 的 `semorphe-state` 要合一還是並存？合一意味著存檔格式的大改。
- ~~**`componentId` 命名空間**：硬體要不要 `hw:` 前綴~~ ✅ **已決**（2026-08-07，
  [元件目錄與膠囊契約](retired/2026-08-07-元件目錄與膠囊契約.md) 決定 ⑤）：叫 `hw:` 不叫 `arduinocad:`
  ——拿要封存的 spike repo 名去命名**永久的**命名空間方向就錯了；「Arduino」把範圍縮小且是商標；
  「CAD」講的是工具不是元件。
- **與 [語義診斷系統](2026-08-05-語義診斷系統.md) 的關係**：DRC 是診斷的一種嗎？若是，硬體 DRC 應該長在那條線上而不是另開。
- **形態的教學層語彙**（上面「形態槽的形狀」那節）：標籤句型、什麼時候用文字欄位 vs 動態插槽、
  ＋／− 放哪——**沒有 oracle，內容只有人能給**。而它與命名要**一起**定，因為是同一層。
  → 初稿見 [形態設計語彙——候選軸](2026-08-10-形態設計語彙-候選軸.md)。
  ⚠️ 而那份的重點是一個**區分**：**預設維度**（全域切換，`StylePreset`／`BlockStylePreset`
  已有）vs **著作規則**（逐顆，護欄查得到，G 的封閉詞彙是這型）。
  **積木缺的是「語義呈現的預設維度」＋ 全部的著作規則**——不是「沒有語彙」。
- **`connector3d` 掛在語義埠還是表示上**：今天掛在語義埠（`MechanicalPort`），
  而 2D 座標掛在表示。支援「同一零件多種 3D 模型」時要搬。

# 擴充要怎麼重做（雙向同步／高亮／風格）

> 日期：2026-08-17
> 怎麼冒出來的：第一刀（spec 138）跑完了，而使用者看到面板說
> 「**怎麼離網頁版的差這麼多**」，接著：
> 「**我覺得可以好好計劃一下再重做，包含雙向同步、高亮、風格等等要如何呈現**」
> **狀態：設計未決。** ⚠️ 而本檔開頭有**一個已經被量出答案的問題**，那一題不必再吵。

## 一、🟢 先把已經有答案的那題結掉：**範圍編輯值得做**

[history/080](../history/080-ArduinoIDE吃VSCode擴充而那不是一個平台是一個位置.md)§六
給範圍編輯留了一個**觸發條件**，逐字：

> 觸發　有人真的在用之後，量一件事：【一次積木編輯平均動到幾行】
> 　　　多數是一兩行　→ 範圍編輯的收益很大，值得做
> 　　　動輒半個檔案　→ 範圍編輯自動退化成整份重寫，不急

**2026-08-17 量了**（`tests/probes/edit-blast-radius.test.ts`，20 段典型 Arduino 語料）：

```
① 欄位編輯（407 筆）  中位 1 行｜p90 1 行｜最大 13 行
                      ≤1 行 99.5%      佔整檔平均 2.5%
② 結構編輯（80 筆）   中位 1 行｜p90 3 行｜最大 22 行
                      ≤1 行 90.0%      佔整檔平均 4.7%
🔴 跨距 > 半個檔案：0 筆
```

⚠️ 而量的**不是 diff**，是「**範圍編輯真的會寫的那一段**」
——去掉共同的開頭與結尾之後剩下的、必須整段重寫的行數。
兩者會差很多：改動兩個相隔 50 行的地方，diff 說「2 行」，**單一範圍是 52 行**。

> **觸發了，而且不是勉強觸發。**

## 二、🔴 而有一個【前提】變了，所以那個決定要重議

`history/080`§六 拍板「整份重寫，照網頁版」，理由逐字：

> **兩邊做同一件事 ⟹ 只有一個行為要推理、一個地方要修。**

而它依據的事實是：**程式碼面板是我們的**（`monaco-panel.ts:352` 的 `setValue`）。

🔴 **在 VSCode 裡它不是我們的。** 整份取代一個原生 `TextDocument` 的代價，
和取代 Monaco 的內容**完全不同**：

```
undo 堆疊    整份取代 ＝ 一個巨大的 undo 項 → 使用者按 Cmd+Z 跳掉整段編輯歷史
游標／選取   每次回到開頭
摺疊狀態     全部展開
git gutter   整個檔案顯示為變更
其他擴充     decoration 全部重置
```

> **「兩邊做同一件事」的前提，是兩邊的那件事代價一樣。
> 而換了宿主之後，同一個動作的代價變了。**

⚠️ **這不是說原本的決定錯了** ——它在它的前提下是對的。
**是前提沒了。**

🟢 而換過去的成本很低：`CodeMapping { nodeId, startLine, endLine }`
（`core/projection/code-generator.ts:12`）與 `metadata.sourceRange`
（`core/types.ts:49`）**都已經在了**，而且已經有消費者（斷點）。
**換的是一個範圍計算，不是蓋一個新機制。**

### 傾向（**未拍板**）

```
粒度②「只重寫改到的那一段」    ← 量測支持它：99.5% 的欄位編輯只要 1 行
```

⚠️ 而「哪一段」有兩種取法，**這一刀要選**：

| 取法 | 怎麼算 | 代價 |
|---|---|---|
| **從語義樹算** | 改到的節點的 `sourceRange` | 🟢 精確，⚠️ 而結構變動時下游行號要重算 |
| **從產出比對算** | 產生新全文，去頭去尾取中間 | 🟢 **零額外機制**（本次量測就是這樣算的），⚠️ 每次都要產全文 |

🔴 **後者可能就夠了**：產全文很便宜（20 段語料整輪量測 325 ms），
而它**不需要任何 sourceRange 正確性的保證**——
> **一個只依賴「產出是決定性的」的做法，比一個依賴「行號對得上」的做法少一個會壞的地方。**

## 三、🔴 一個網頁版**根本不存在**的問題：兩個 undo 堆疊

```
Blockly workspace   有自己的 undo
VSCode document     也有自己的 undo
```

**使用者在畫布上按 Cmd+Z，該退哪一個？**
退了積木之後程式碼要不要跟著退？而如果程式碼那邊**先被別人改了**
（另一個擴充、格式化工具、Git 還原）呢？

⚠️ 這在網頁版不存在，因為**兩邊都是我們的、共用一個真相**。
🔴 **它是「宿主獨立性」這個閘門第一個真正咬人的地方**
（`principles.md:160`，四項獨立性裡從來沒被驗過的兩項之一）。

**三個可能，都沒拍板**：

| | 做法 | 代價 |
|---|---|---|
| (a) | 積木的編輯**不進** Blockly 的 undo，一律走文件的 undo | 🟢 只有一個堆疊，⚠️ 而畫布上的「移動位置」也會變成文件編輯？ |
| (b) | 兩個堆疊各自獨立，**不同步** | 🔴 使用者會看到「退了積木而程式碼沒退」——最糟 |
| (c) | 積木編輯包成 `WorkspaceEdit`，讓宿主的 undo 一次退掉 | 🟢 最像原生，⚠️ 而 Blockly 的 undo 要**關掉**，那會不會讓畫布操作變難用 |

⚠️ **而它與第二節是同一題的兩面**：整份重寫時 undo 天然是「一次退全部」，
範圍編輯才會讓「退一步」有意義。**兩題要一起答。**

## 四、面板跟哪一份文件 —— 🟢 **量完之後這一題不貴了**

```
(a) 跟著 active editor 走     像 Outline
(b) 綁定一份，可 pin／unpin   中間，而「綁定」要有 UI 與狀態
(c) 一份文件一個面板          🔴 要求 18 個 per-document 欄位【先拆乾淨】
```

出處：[draft/擴充的形狀](2026-08-17-擴充的形狀.md)第二節
——`App` 有 31 個欄位，**9 個 per-app、18 個 per-document、4 個不確定**。

### 反對 (a) 的唯一理由是「切分頁要重新載入，貴」。**量了，不貴。**

2026-08-17 實測：

```
parse + lift              中位 4.9 ms｜最大 9.2 ms   （20 段典型語料，node）
Blockly 畫 76 顆積木        7.9 ms                   （瀏覽器，preview.html）
                          150 顆 10 ms｜300 顆 24 ms
initCppModule（一次性）     5 ms／209 筆規格
────────────────────────────────────────────────
一次切分頁                 ≈ 13 ms
```

⚠️ **這是下界**：benchmark 建的是**沒有連接、沒有 mutator** 的單純積木，
而真實的樹要走 PatternRenderer → 序列化 → load，並且含動態積木
（`cpp_var_declare` 的 mutator、`cpp_print` 的 `+`／`-`）。
🟢 **而就算差 5 倍也只有 65 ms。**

> **一個被當成「架構限制」的東西，量完之後常常只是一個沒人量過的假設。**

### 🔴 而真正的收穫是：**它把那 18 個欄位拆成兩堆，而只有一堆是問題**

如果面板一次只服務一份文件，那 18 個「per-document」欄位**不必變成 N 份**
——它們只要**在切換時重建**。而重建得了的條件是：

```
可從文件重新導出   currentTree／currentTarget／currentTopic／enabledBranches
                   currentStylePreset／currentIoPreference／codeParserCache
                   → 🟢 切分頁時【丟掉重算】，13 ms
不可導出的「視圖狀態」  捲動位置／縮放／積木擺放位置／undo 堆疊／dirty 旗標
                   → ⚠️ 丟掉的話，切回來畫布會【重排】——那是真的 UX 代價
```

> **一個「per-document 的欄位」，如果從文件本身重算得出來，
> 那它就不是狀態，是快取。**

🔴 **所以要 per-uri 保存的只有第二堆，而它小得多。**
那讓 (a) 從「便宜但會掉東西」變成「便宜而且補得起來」。

### 傾向（**未拍板**）：**(a) ＋ 一小份 per-uri 的視圖狀態**

⚠️ 而 (b) 的 pin **不必現在做**——它是 (a) 之上的一個加法，不是另一條路。

### ⚠️ 而 untitled buffer 讓「per-uri」這個 key 有一個坑（2026-08-17 實測撞到）

使用者開 `Untitled-1`、語言選 C++，入口沒出現——因為 `resourceExtname` 是空的。
🔴 **而那正是主場景之一**（使用者逐字：「AI 給的 Code 他們貼上來」）。

```
一份文件 ≠ 一個檔案
untitled 沒有路徑 ⟹ 「以路徑為 key」會撞牆
```

🟢 而 VSCode 的 `Uri.toString()` 對 untitled 也給得出穩定的字串
（`untitled:Untitled-1`），**所以 key 有解**。
⚠️ **真正的坑在存檔那一刻**：`untitled:Untitled-1` 會變成 `file:///…/foo.ino`
——**同一份文件換了身分**，而視圖狀態要跟著搬。
`workspace.onDidRenameFiles` 管不到它（那是檔案改名，不是 untitled 落地）。

**這一條也直接影響 `storageService`**（`core/storage.ts:4` 的固定 key
`'semorphe-state'`，draft 那 4 筆不確定之一）。

## 五、高亮其實是**三件事** —— 🟢 **而地基比想像的紮實**

```
積木 → 程式碼    CodeMapping{nodeId,startLine,endLine} → setDecorations ＋ revealRange
程式碼 → 積木    游標行 → sourceRange 反查 nodeId → 選取積木
執行中高亮       ⚠️ 而【執行在 VSCode 裡做不做】沒答（第六節）
```

### 量過的（2026-08-17，20 段語料 / 1516 個節點）

```
metadata.sourceRange   1493 / 1516 = 98.5%
node.id                1516 / 1516 = 100%
樣本  cpp:comment → {startLine:1, startColumn:0, endLine:1, endColumn:32}
```

🟢 **兩個方向的資料都已經在樹上了**，而且是 lift 當下就帶著的，不是要另外算的。
而「游標行 → 哪個節點」是一趟 76～131 個節點的樹走訪 ——
⚠️ **我原本擔心 `onDidChangeTextEditorSelection` 很吵會卡，那個擔心是多餘的**：
一次反查是微秒級，而事件再吵也是人手移動游標的頻率。

> **一個「會不會太慢」的擔心，在量之前不值得拿來設計。**

### ⚠️ 剩下的 1.5% 是一個真的缺口

23 個節點沒有 `sourceRange`。**沒查是哪些** ——
多半是合成出來的節點（沒有對應的原始碼區間）。
🔴 而高亮在那些節點上會**安靜地沒有反應**，那又是「不會報錯的壞」那一族。
**要查，而且要決定：往上找最近的有範圍的祖先，還是不高亮。**

### 而 VSCode 這一側有兩個網頁版沒有的新問題

```
程式碼那一側不是我們的  只能用 TextEditorDecorationType 疊上去
                        ⚠️ 顏色／優先序／與其他擴充的 decoration 打架
選取的來源有兩個        點積木 vs 移游標 —— 🔴 而它們會互相觸發
                        （選了積木 → 照亮程式碼 → 游標動了 → 反查 → 選積木 → …）
```

🔴 **後者與第三節的 undo 是同一個形狀**：兩個宿主各有一份「目前選了什麼」，
而同步它們需要防迴圈——**而 `history/080`§五② 記過，非同步宿主用布林旗標不夠。**

## 六、執行做不做（⚠️ 而它連著一個已知的坑）

`history/080` 的結論是「**燒錄 ＝ 真的執行，而且比任何模擬器都準**」。
那 VSCode 裡直譯器還跑不跑？

```
不跑   🟢 少一大塊，而執行高亮跟著沒有
       ⚠️ 但「按一下就看到結果」是網頁版的教學價值之一
跑     主控台放哪？（Terminal／Output／webview 內）
       🔴 而膠囊要進【主行程】 ⟹ esbuild／CJS 那個坑【原封不動回來】
```

坑的出處逐字（`core/component/registry.ts:22-48`）：

```
Vite    → CJS 269 KB → node 跑得動 → 189 顆膠囊全部載入   🟢
esbuild → CJS 4.6 KB → 🔴 import_meta.glob is not a function
```

⚠️ **而第一刀是【繞開】它不是【解決】它**：畫布住在 Webview（瀏覽器環境）。
處置已經寫在那個檔頭裡（Vite `ssr`＋`lib`＋`cjs`，已實測可行）。

> **一個繞開的坑不會消失，它只是換一天出現。**

## 七、風格／目標怎麼呈現（`target`／`topic`／積木外觀／I-O 風格）

網頁版：工具列下拉選單，全部存在 `localStorage` 一個固定 key。

VSCode 有兩條原生的路：

| | 住哪 | 性質 |
|---|---|---|
| (a) | `settings.json`（user／workspace） | 🟢 **看得見、進版控、老師可以設一次、學生可覆寫** |
| (b) | `workspaceState` | ⚠️ 隱形——改不到也看不到 |
| (c) | 面板內的工具列（照搬網頁版） | ⚠️ 與宿主的設定系統**各有一份真相** |

🔴 **我傾向 (a)，而理由不是「比較 native」，是教學場景**：
一個班的 `target` 應該是**老師設一次進 workspace**，不是每個學生自己摸。
而 spec 136 讓 `target` 成為「topic ＋ style 的具名組合」——
**它天生就是一個設定值的形狀。**

⚠️ **而 (a) 有一個代價要先想**：`settings.json` 是 per-workspace 的，
而 `currentTarget` 在 draft 的分類裡是 **per-document**
（`.ino` 是 Arduino、`.cpp` 是 C++）。**兩者會打架** ——
可能的解法是「設定給預設值，副檔名可覆寫」，**但那沒有被想清楚**。

## 八、工具箱（第一刀明確排除，而它其實不只是「補上去」）

`buildToolbox()` 需要 `visibleConcepts`／`ioPreference`／`categoryColors`，
而那些來自 `currentTopic`／`enabledBranches`／`currentStylePreset`
——**正是第四節那 18 個欄位裡的三個**。

🟢 而外觀那一半是**三行的重用**：網頁版 `Blockly.inject` 傳七項，第一刀傳三項。

```
renderer   zelos（圓潤）   ← 第一刀用 Blockly 預設（geras，方角）
theme      dark_scratch    ← 第一刀沒傳 → 白底
grid       20px            ← 第一刀沒有
```

⚠️ `createDarkTheme()` 今天是 `blockly-panel.ts:764` 的 **private** ——要抽出來。

## 一、🟢 先把已經有答案的那題結掉：**範圍編輯值得做**

[history/080](../history/080-ArduinoIDE吃VSCode擴充而那不是一個平台是一個位置.md)§六
給範圍編輯留了一個**觸發條件**，逐字：

> 觸發　有人真的在用之後，量一件事：【一次積木編輯平均動到幾行】
> 　　　多數是一兩行　→ 範圍編輯的收益很大，值得做
> 　　　動輒半個檔案　→ 範圍編輯自動退化成整份重寫，不急

**2026-08-17 量了**（`tests/probes/edit-blast-radius.test.ts`，20 段典型 Arduino 語料）：

```
① 欄位編輯（407 筆）  中位 1 行｜p90 1 行｜最大 13 行
                      ≤1 行 99.5%      佔整檔平均 2.5%
② 結構編輯（80 筆）   中位 1 行｜p90 3 行｜最大 22 行
                      ≤1 行 90.0%      佔整檔平均 4.7%
🔴 跨距 > 半個檔案：0 筆
```

⚠️ 而量的**不是 diff**，是「**範圍編輯真的會寫的那一段**」
——去掉共同的開頭與結尾之後剩下的、必須整段重寫的行數。
兩者會差很多：改動兩個相隔 50 行的地方，diff 說「2 行」，**單一範圍是 52 行**。

> **觸發了，而且不是勉強觸發。**

## 二、🔴 而有一個【前提】變了，所以那個決定要重議

`history/080`§六 拍板「整份重寫，照網頁版」，理由逐字：

> **兩邊做同一件事 ⟹ 只有一個行為要推理、一個地方要修。**

而它依據的事實是：**程式碼面板是我們的**（`monaco-panel.ts:352` 的 `setValue`）。

🔴 **在 VSCode 裡它不是我們的。** 整份取代一個原生 `TextDocument` 的代價，
和取代 Monaco 的內容**完全不同**：

```
undo 堆疊    整份取代 ＝ 一個巨大的 undo 項 → 使用者按 Cmd+Z 跳掉整段編輯歷史
游標／選取   每次回到開頭
摺疊狀態     全部展開
git gutter   整個檔案顯示為變更
其他擴充     decoration 全部重置
```

> **「兩邊做同一件事」的前提，是兩邊的那件事代價一樣。
> 而換了宿主之後，同一個動作的代價變了。**

⚠️ **這不是說原本的決定錯了** ——它在它的前提下是對的。
**是前提沒了。**

🟢 而換過去的成本很低：`CodeMapping { nodeId, startLine, endLine }`
（`core/projection/code-generator.ts:12`）與 `metadata.sourceRange`
（`core/types.ts:49`）**都已經在了**，而且已經有消費者（斷點）。
**換的是一個範圍計算，不是蓋一個新機制。**

### 傾向（**未拍板**）

```
粒度②「只重寫改到的那一段」    ← 量測支持它：99.5% 的欄位編輯只要 1 行
```

⚠️ 而「哪一段」有兩種取法，**這一刀要選**：

| 取法 | 怎麼算 | 代價 |
|---|---|---|
| **從語義樹算** | 改到的節點的 `sourceRange` | 🟢 精確，⚠️ 而結構變動時下游行號要重算 |
| **從產出比對算** | 產生新全文，去頭去尾取中間 | 🟢 **零額外機制**（本次量測就是這樣算的），⚠️ 每次都要產全文 |

🔴 **後者可能就夠了**：產全文很便宜（20 段語料整輪量測 325 ms），
而它**不需要任何 sourceRange 正確性的保證**——
> **一個只依賴「產出是決定性的」的做法，比一個依賴「行號對得上」的做法少一個會壞的地方。**

## 三、undo ＋ 防迴圈 —— 🟢 **而它與第二、七節是【同一個決定】**

### 問題

```
Blockly workspace   有自己的 undo
VSCode document     也有自己的 undo
```

使用者在畫布上按 Cmd+Z，該退哪一個？而如果程式碼那邊**先被別人改了**
（另一個擴充、格式化、Git 還原）呢？

⚠️ 這在網頁版不存在，因為**兩邊都是我們的、共用一個真相**。
🔴 **它是「宿主獨立性」這個閘門第一個真正咬人的地方**（`principles.md:160`）。

### 🟢 機制查證過了（2026-08-17，`@types/vscode` ＋ `node_modules/blockly`）

```
editor.edit(cb, { undoStopBefore, undoStopAfter })   → 一次積木編輯 ＝ 一個 undo 項
Blockly.Events.setRecordUndo(false)                  → 可以不進 Blockly 的堆疊
TextDocument.version   「strictly increase after each change, including undo/redo」
TextDocumentChangeEvent.reason → Undo | Redo         → 認得出「這是使用者在復原」
```

**所以三個選項裡，(c) 是做得到的，不是理論。**

### 🔴 而答案由第七節導出來，不是另外選的

第七節量到一件事：**在 VSCode 裡，積木的擺放位置是【外觀】不是真相**
（程式碼才是）。把那條套進來，undo 就自己分好了：

```
會改到程式碼的積木操作   → 一個 document undo 項（undoStopBefore/After）
                          並且對 Blockly setRecordUndo(false)
純外觀的操作（拖動位置）  → Blockly 自己的 undo，【不進文件】
```

🟢 **兩邊各退各的，而它們退的是不同種類的東西——所以不會打架。**

⚠️ 而如果不這樣分，會出現一個很怪的行為：使用者把積木拖了 20px（程式碼沒變），
按 Cmd+Z **會跳過那個動作、退掉上一次真正的程式碼修改**。

> **兩個 undo 堆疊不是問題，「兩個堆疊裝同一種東西」才是。**

### 🔴 防迴圈：`history/069` 那條教訓**可以升級**

原文逐字：

> 「**同步宿主用布林旗標就夠，非同步宿主要加時間**」

而 PoC 正是那樣做的：一個 `isUpdating` 布林 ＋ 四處散落的 `setTimeout`
（`history/080`§五②：「**那些 `setTimeout` 就是症狀**」）。

🟢 **而 `TextDocument.version` 讓它不必加時間**：

```
我們送出編輯 → 記下產生的 version
onDidChangeTextDocument 進來 → version 是我們產生的那個嗎？
    是   → 自己的回音，忽略
    不是 → 真的外來變更，重新 lift
```

> **非同步宿主要的不是「時間」，是【一個身分】。
> 加時間是在猜「回音應該多久之內回來」——而那個猜測沒有上界。**

🔴 **那條教訓因此要【改寫】，而不是再加一個實例** ——
`experience.md:2866`「同一個防迴圈的問題，在同步宿主用布林旗標就夠，
在非同步宿主要加時間」。

🟢 **而它自己就標了它是猜的**，逐字：

> ⚠️ 用時間的那個版本，**那個常數是猜的**（50ms 沒有人驗過夠不夠）。
> 把它標成猜測，並在它出問題時**先懷疑它**

⚠️ **但本檔【還不能】去改它**：我查證的是「`TextDocument.version` 存在且單調遞增」，
**不是「回音比對這個做法跑得通」**。那要等它真的被實作出來。

> **一個更好的做法在被實作之前，只是一個更好的猜測。**

### 還開著的

```
❓ 外來變更進來時，畫布上未套用的編輯怎麼辦（衝突）
❓ e.reason === Undo 時要不要特別處理，還是一律當外來變更重新 lift
   🟢 後者比較簡單，而「簡單」在這裡可能就是對的
```


## 四、面板跟哪一份文件 —— 🟢 **量完之後這一題不貴了**

```
(a) 跟著 active editor 走     像 Outline
(b) 綁定一份，可 pin／unpin   中間，而「綁定」要有 UI 與狀態
(c) 一份文件一個面板          🔴 要求 18 個 per-document 欄位【先拆乾淨】
```

出處：[draft/擴充的形狀](2026-08-17-擴充的形狀.md)第二節
——`App` 有 31 個欄位，**9 個 per-app、18 個 per-document、4 個不確定**。

### 反對 (a) 的唯一理由是「切分頁要重新載入，貴」。**量了，不貴。**

2026-08-17 實測：

```
parse + lift              中位 4.9 ms｜最大 9.2 ms   （20 段典型語料，node）
Blockly 畫 76 顆積木        7.9 ms                   （瀏覽器，preview.html）
                          150 顆 10 ms｜300 顆 24 ms
initCppModule（一次性）     5 ms／209 筆規格
────────────────────────────────────────────────
一次切分頁                 ≈ 13 ms
```

⚠️ **這是下界**：benchmark 建的是**沒有連接、沒有 mutator** 的單純積木，
而真實的樹要走 PatternRenderer → 序列化 → load，並且含動態積木
（`cpp_var_declare` 的 mutator、`cpp_print` 的 `+`／`-`）。
🟢 **而就算差 5 倍也只有 65 ms。**

> **一個被當成「架構限制」的東西，量完之後常常只是一個沒人量過的假設。**

### 🔴 而真正的收穫是：**它把那 18 個欄位拆成兩堆，而只有一堆是問題**

如果面板一次只服務一份文件，那 18 個「per-document」欄位**不必變成 N 份**
——它們只要**在切換時重建**。而重建得了的條件是：

```
可從文件重新導出   currentTree／currentTarget／currentTopic／enabledBranches
                   currentStylePreset／currentIoPreference／codeParserCache
                   → 🟢 切分頁時【丟掉重算】，13 ms
不可導出的「視圖狀態」  捲動位置／縮放／積木擺放位置／undo 堆疊／dirty 旗標
                   → ⚠️ 丟掉的話，切回來畫布會【重排】——那是真的 UX 代價
```

> **一個「per-document 的欄位」，如果從文件本身重算得出來，
> 那它就不是狀態，是快取。**

🔴 **所以要 per-uri 保存的只有第二堆，而它小得多。**
那讓 (a) 從「便宜但會掉東西」變成「便宜而且補得起來」。

### 傾向（**未拍板**）：**(a) ＋ 一小份 per-uri 的視圖狀態**

⚠️ 而 (b) 的 pin **不必現在做**——它是 (a) 之上的一個加法，不是另一條路。

### ⚠️ 而 untitled buffer 讓「per-uri」這個 key 有一個坑（2026-08-17 實測撞到）

使用者開 `Untitled-1`、語言選 C++，入口沒出現——因為 `resourceExtname` 是空的。
🔴 **而那正是主場景之一**（使用者逐字：「AI 給的 Code 他們貼上來」）。

```
一份文件 ≠ 一個檔案
untitled 沒有路徑 ⟹ 「以路徑為 key」會撞牆
```

🟢 而 VSCode 的 `Uri.toString()` 對 untitled 也給得出穩定的字串
（`untitled:Untitled-1`），**所以 key 有解**。
⚠️ **真正的坑在存檔那一刻**：`untitled:Untitled-1` 會變成 `file:///…/foo.ino`
——**同一份文件換了身分**，而視圖狀態要跟著搬。
`workspace.onDidRenameFiles` 管不到它（那是檔案改名，不是 untitled 落地）。

**這一條也直接影響 `storageService`**（`core/storage.ts:4` 的固定 key
`'semorphe-state'`，draft 那 4 筆不確定之一）。

## 五、高亮其實是**三件事** —— 🟢 **而地基比想像的紮實**

```
積木 → 程式碼    CodeMapping{nodeId,startLine,endLine} → setDecorations ＋ revealRange
程式碼 → 積木    游標行 → sourceRange 反查 nodeId → 選取積木
執行中高亮       ⚠️ 而【執行在 VSCode 裡做不做】沒答（第六節）
```

### 量過的（2026-08-17，20 段語料 / 1516 個節點）

```
metadata.sourceRange   1493 / 1516 = 98.5%
node.id                1516 / 1516 = 100%
樣本  cpp:comment → {startLine:1, startColumn:0, endLine:1, endColumn:32}
```

🟢 **兩個方向的資料都已經在樹上了**，而且是 lift 當下就帶著的，不是要另外算的。
而「游標行 → 哪個節點」是一趟 76～131 個節點的樹走訪 ——
⚠️ **我原本擔心 `onDidChangeTextEditorSelection` 很吵會卡，那個擔心是多餘的**：
一次反查是微秒級，而事件再吵也是人手移動游標的頻率。

> **一個「會不會太慢」的擔心，在量之前不值得拿來設計。**

### ⚠️ 剩下的 1.5% 是一個真的缺口

23 個節點沒有 `sourceRange`。**沒查是哪些** ——
多半是合成出來的節點（沒有對應的原始碼區間）。
🔴 而高亮在那些節點上會**安靜地沒有反應**，那又是「不會報錯的壞」那一族。
**要查，而且要決定：往上找最近的有範圍的祖先，還是不高亮。**

### 而 VSCode 這一側有兩個網頁版沒有的新問題

```
程式碼那一側不是我們的  只能用 TextEditorDecorationType 疊上去
                        ⚠️ 顏色／優先序／與其他擴充的 decoration 打架
選取的來源有兩個        點積木 vs 移游標 —— 🔴 而它們會互相觸發
                        （選了積木 → 照亮程式碼 → 游標動了 → 反查 → 選積木 → …）
```

🔴 **後者與第三節的 undo 是同一個形狀**：兩個宿主各有一份「目前選了什麼」，
而同步它們需要防迴圈——**而 `history/080`§五② 記過，非同步宿主用布林旗標不夠。**

## 六、執行做不做 —— 🔴 **而我上一版寫的前提是錯的**

### 上一版寫的

> 跑　主控台放哪？（Terminal／Output／webview 內）
> 　　🔴 而膠囊要進【主行程】 ⟹ esbuild／CJS 那個坑【原封不動回來】

⚠️ **那句話的前提沒有被檢查過**：**為什麼執行要在主行程？**

```
Webview ＝ 瀏覽器環境
而網頁版的直譯器【就跑在瀏覽器裡】
```

🟢 **所以執行整個留在 Webview 就好，主行程一行都不必碰膠囊。**
CJS 那個坑**不會因為做執行而回來**。

> **我把一個「東西該住哪」的問題，寫成了一個「架構限制」。**

### 🔴 而真正在關鍵路徑上的是另一件事，它沒人試過

`code → blocks` 一定要 **tree-sitter 的 wasm**。而 Webview 有 CSP。

**2026-08-17 實測**（用與正式面板**完全同一條** CSP，只把來源換成 `'self'`）：

```
script-src 'self'
  → 🔴 CompileError: WebAssembly.compile() violates CSP because
       'unsafe-eval' is not an allowed source of script

script-src 'self' 'wasm-unsafe-eval'
  → 🟢 compile 成功，152 項匯出
```

⚠️ **而兩次的 console 錯誤都是 0** ——它丟的是一個**可以被 catch 的
`CompileError`**，在非同步初始化裡很容易被安靜地吞掉。

> **這是第四個同族的東西**（media 少一個斜線／`img-src data:`／`connect-src`），
> 而它們的共同點是：**白名單漏一項，失敗不出聲。**

🔴 **本輪【不要】先把它加進 CSP。** 現在沒有任何東西需要 wasm，
而**加一個還沒有人要用的權限**，等於把它從「下一刀要處理的事」
變成「已經在那裡、沒有人記得為什麼」。**記在這裡，用到時再加。**

### 所以執行的成本重估

```
架構    🟢 零 —— 直譯器是純 TS，跟膠囊一起打包進 webview.js
資料    🟢 零 —— 樹已經在 Webview 裡
真正的成本   主控台要長在哪，以及它與宿主的 Terminal／Output 的關係
```

**「執行做不做」因此不是一個架構決定，是一個 UI 決定。**

### 三個放法（**未拍板**）

| | 主控台住哪 | 性質 |
|---|---|---|
| (a) | Webview 面板內 | 🟢 最像網頁版、零宿主整合，⚠️ 而畫布空間要分一塊出去 |
| (b) | VSCode 的 Output channel | 🟢 原生、可捲動、與其他擴充並列，⚠️ **唯讀**——`cin` 那類輸入做不了 |
| (c) | 整合式終端機 | 🔴 那是給真的行程用的，我們是直譯器——**形狀不對** |

⚠️ **(b) 的唯讀那條是硬的**：網頁版的 `cpp:input` 需要使用者輸入。
🟡 而 `showInputBox` 可以擋一下，**但那與「主控台」的心智模型不同**。

### 而它與燒錄的關係要講清楚

`history/080` 的結論是「**燒錄 ＝ 真的執行，而且比任何模擬器都準**」。
🟢 **兩者不衝突，它們答的是不同問題**：

```
燒錄     這段程式在【真的板子】上做什麼      ← 準，但要有板子
直譯器   這段程式的【語義】是什麼            ← 沒有板子也能問，而且可以單步
```

⚠️ 而虛擬硬體往後推（`history/077`）意味著**直譯器跑 Arduino 程式時
看得到的效果有限**——腳位狀態記在 `WeakMap` 裡，而顯示是之後的事。


## 七、風格／目標怎麼呈現 —— 🔴 **它不是一題，是三題**

### 先看網頁版把什麼混在一起了

`core/storage.ts` 的 `SavedState`（**一個** `localStorage` key）：

```
tree / blocklyState / code                        ① 文件內容
targetId / topicId / styleId / enabledBranches    ② 組態
blockStyleId / locale                             ③ 使用者偏好
```

**在網頁版它們可以混在一起**，因為只有一份文件、一個使用者、一個 storage。
🔴 **而 VSCode 對這三種各有一個原生的家** ——
所以「設定住哪」問錯了，該問的是「**這三種各住哪**」。

| | 網頁版 | VSCode |
|---|---|---|
| ① 文件內容 | localStorage | 🔴 **不存**——檔案就是真相，`code` 與 `tree` 都由它導出 |
| ① 積木擺放（`blocklyState`） | localStorage（**是真相**） | ⚠️ 在這裡只是**外觀** → per-uri 的 `workspaceState` |
| ② 組態 | localStorage | 🟢 `settings.json` |
| ③ 偏好 | localStorage | 🟢 `settings.json`（user scope） |

> 🔴 **`blocklyState` 的身分變了，而那是這一節最容易漏掉的一格。**
> 網頁版沒有檔案，所以積木的擺放**就是**真相；
> 在 VSCode 裡程式碼是真相，積木的位置**純粹是外觀**。
>
> **同一份資料，換一個宿主就從真相降級成快取。**

🟢 而它與第四節那個分類是同一條線：**導得出來的就不是狀態**。

### 🟢 而「per-workspace vs per-document 會打架」那個顧慮，VSCode 原生就解了

上一版這裡寫著「⚠️ 兩者會打架……**但那沒有被想清楚**」。**現在想清楚了。**

VSCode 有**語言範圍的設定**：

```jsonc
"semorphe.target": "cpp-beginner",                    // workspace 預設——老師設一次
"[arduino]": { "semorphe.target": "arduino-uno" }     // 這個語言覆寫
```

**2026-08-17 查證**（`@types/vscode` ＋ VSCode 1.129.0 bundle）：

```
ConfigurationScope = Uri | TextDocument | WorkspaceFolder | { uri?, languageId }
  → workspace.getConfiguration('semorphe', { uri, languageId }) 解得出語言範圍
"language-overridable"   在 bundle 裡出現 76 次 → 是真的設定值，不是我編的
```

⚠️ **前提是宣告時要寫 `"scope": "language-overridable"`**
——不寫的話語言覆寫**安靜地不生效**。**又是那一族。**

### 傾向（**未拍板**）

```
② 組態    settings.json，且宣告 language-overridable
          🔴 理由不是「比較 native」，是【教學場景】：
             一個班的 target 該是老師設一次進 workspace、進版控、學生可覆寫
③ 偏好    同上，user scope
① 內容    不存；而積木擺放進 workspaceState，per-uri
```

🟢 **順帶答掉一筆**：`storageService` 在 [draft/擴充的形狀](2026-08-17-擴充的形狀.md)
是「4 筆不確定」之一，問的是「per-uri 化之後**存哪裡**」。
**答案是：它大部分不搬家，是【消失】** ——因為它存的第一類東西在 VSCode 裡有真相了。

### ⚠️ 而它有一個代價，要說在前面

```
網頁版   工具列下拉選單，改完立刻看到
VSCode   改設定要開 settings.json 或設定 UI —— 【離開了畫布】
```

🔴 **面板內要不要仍然有一組下拉選單？** 要的話，它改的是誰？

```

              ⚠️ 而「動一個下拉選單會寫進版控」很意外
只改當下      🔴 兩份真相——而這個專案付過那個學費（history/072）
```

**沒答。而這是本節真正剩下的問題。**

## 核心洞察

**錯誤訊息本質上也是語義結構的一種投影**——它是對「語義結構與預期之間差距」的結構化呈現。

如果這個看法成立，診斷就不需要另一套資料結構：Diagnostic 掛在語義節點上。

```
SemanticNode
  ├── conceptId, props, children
  └── diagnostics: [
        { rule, severity, anchor: { nodeId, field? }, suggestions: [...] }
      ]
```

## 分析三層

1. **概念自身 constraint** — 節點層級，「我自己合不合法」（如：name 不可為空）
2. **關係規則** — 樹層級，「我和 parent/sibling 的關係對不對」（如：return 必須在 function 內）
3. **語言特有規則** — 語言模組層級（如：C++ const 語義）

核心只負責遍歷語義樹、依序執行三層、收集 Diagnostic。

## C++ 這種複雜語言怎麼辦：分層委派

- **Level 1 我們自己做** — 語義樹上就能判斷的結構性錯誤（缺 main、return 在函式外、break 不在 loop 內）。成本低、教育價值高。
- **Level 2 委派編譯器** — generate 出程式碼 → 餵給編譯器 → 用 `_lineBox` line tracking 映射回語義節點。型別系統、overload resolution 不需自己做。
- **Level 3 翻譯層** — 把編譯器 diagnostic 用 pattern matching 轉譯成分級教育訊息。社群可貢獻翻譯表，沒匹配到就 fallback 顯示原始訊息。

## 投影與漸進揭露

同一個 Diagnostic 在不同面板有不同呈現：程式碼面板紅色波浪底線、積木面板邊框變色、語義樹 badge、獨立錯誤清單面板。

訊息深度跟著 Level 走：

```
L0：「『加法』需要兩個數字，但右邊放的是文字」
L1：「型別不符：+ 的右運算元期望 int，收到 string」
L2+：「type mismatch: binary operator+ expects int operand, got const char*」
```

**修正建議**：Suggestion 是語義樹的 patch（SemanticPatch），不是文字。可投影成程式碼 diff 或積木面板的「點擊套用」按鈕。

## 架構位置

插在 lift 之後、投影之前。Diagnostic 只是語義樹上多掛了資料，現有 renderer 不認識就忽略。

```
程式碼 ──lift──→ SemanticTree ──analyze──→ SemanticTree + Diagnostics
                                              │
                        ┌───────────────┬──────┴──────┬──────────┐
                     code投影        block投影     tree投影   問題清單投影
```

## 缺一層：全樹流敏感約束（2026-08-05 補）

上面三層**裝不下 borrow check**。第 2 層是**局部結構**檢查（return 在不在 function 內、break 在不在 loop 內），但借用檢查是**流敏感**的——第 3 行的 move 殺掉第 5 行的 use，那是順序與生命週期，不是父子關係。

這條在加 Rust 時會變成阻斷（使用者已確認會加）。而且它和硬體 DRC 是**同一台機器**——電氣傳播也是流敏感的（誰在驅動、驅動到哪、有沒有衝突），且兩者的錯誤形狀一一對應：

| | 電氣 | Rust |
|---|---|---|
| 多重驅動 | `CONFLICT` | cannot borrow as mutable more than once |
| 無驅動 | `FLOATING` | use of moved / uninitialized value |

推導見 [concepts/元件](../concepts/元件.md)「守恆的兩種律」。**架構後果**：這一層屬於 kernel 的一條脊椎，**per-元件的膠囊裝不下全樹約束**——見 [元件膠囊重構](retired/2026-08-05-元件膠囊重構.md)。

## 二、⚠️ 錨點是 `blockId` 而不是 `nodeId`——而這個病我們剛治過

那一個欄位決定了全部：

```
錨在 blockId  → 只有積木視圖看得到；Monaco 拿不到（它不認識 blockId）
錨在 nodeId   → 每個視圖自己投影：積木高亮、程式碼波浪、2D 元件發紅
```

**而這與 `execution:at-node` 改造前的狀態一模一樣**——執行位置原本也是靠
`blockId` 傳的，改成 nodeId 廣播之後程式碼視圖才拿得到
（見 [history/051](../history/051-P9從沒有執行機構到病換了位置.md)）。

> **診斷今天卡在 `execution:at-node` 改造之前的那個狀態。**

→ **處方可以直接抄**：一個 `diagnostics` 事件掛 `nodeId`，各視圖自己決定
怎麼呈現。`experience.md`「照抄已驗證的形狀，不要自己換一個判準」。

⚠️ 而抄的時候要注意 `execution:at-node` 那次學到的：**命令與廣播不是同一種東西**。
診斷是**廣播**（狀態變了，誰想知道誰聽），不是命令——所以不該是
`monacoPanel.showSquiggle(...)`。

## 三、硬體診斷掛在**邊**上——本檔檔頭那句話因此被推翻

| | 錨在哪 | 例子 |
|---|---|---|
| 軟體診斷 | **節點** | 這個變數沒宣告、這個型別不符 |
| **硬體診斷** | **邊** | ⚠️ 這兩支腳不能接、這條線短路、這個接點沒接東西 |

「LED 的陽極接到 GND」——那個錯誤**不屬於 LED 也不屬於 GND，屬於那條連線**。

→ **本設計成為 C2 資訊軸（邊）的第一個真消費者**。
而 C2 在 `vision.md` 的 A–F 表裡標「⏸ 延後」，理由逐字是
「**今天沒有消費者**……現在加一整條沒人讀的軸就是預約第九個〔機制有了沒人接上〕」。

⚠️ **所以這一項不是「診斷要等 C2」，而是「C2 等到消費者了」**——順序是反的。

## 四、「錯了」與「還不會檢查」不可合併——照抄第三十二條護欄

`tests/integration/audit-behavior-error.test.ts` 的檔頭逐字：

> 「⚠️ 這不是殘差。**誤差高＝模型是錯的**（系統會騙人）；
> **殘差高＝模型還沒長到那裡**（系統仍然正確）。**兩者不可合併**
> ——混起來的話，多蓋幾顆元件會讓『會騙人』的數字看起來在改善。」

套到診斷上是兩種完全不同的狀態：

| | 意思 | 該顯示什麼 |
|---|---|---|
| **這段程式錯了** | 診斷規則判定它違規 | 錯誤／警告 |
| **我們還不會檢查這種錯** | 沒有規則涵蓋它 | ⚠️ **什麼都不顯示，而那正是危險的地方** |

**如果診斷把後者也報成錯誤，學生被假警報淹沒；如果默默略過，學生以為程式是對的。**

→ 而**委派編譯器**正好解掉這一格：編譯器涵蓋的範圍就是「我們不會檢查但它會」。
所以本檔 §分層委派 的 **fallback**（「沒匹配到就顯示原始訊息」）
**不只是相容措施，它是誠實的來源**——那句原文訊息代表「這個錯我們沒有教育版本」。

⚠️ 而這也給了一條可量的東西（`draft/一致是量出來的不是保證的` 的形狀）：

```
編譯器報了幾個錯   而我們自己抓到幾個   → 涵蓋率
我們報了幾個錯     而編譯器不認為是錯   → 假警報
```

**兩個數字都要記**，理由與第三十二條護欄的「分母必須進基線」相同。

## 今天的狀態（比 2026-08-12 那次又新了一點）

```
Diagnostic.blockId                                    ❌ 仍是積木 id，規則 4 條

```

🔴 **同一個系統裡兩種錯誤用兩種錨點**：執行期錯誤已經走完
`execution:at-node` 那次改造，而**靜態診斷停在改造之前**。
而 §二 說「處方可以直接抄」——抄的東西比它想的還現成：那個映射已經寫好了。

## 一、🔴 診斷不是語義樹的函數——它是 `(樹, 目標)` 的函數

本檔通篇假設診斷只吃樹。而同一棵樹的對錯**取決於第二個輸入**：

```
auto x = 1;        C++03 錯、C++11 對
bool b = true;     C++ 對、C99 要 <stdbool.h>
Point p;           C++ 對、C 要寫 struct Point p;
```

而那個「目標」**已經被設計出來了**——[C 和 C++ 難分難捨](2026-08-13-C和C++難分難捨.md)§三：

```
target: c99-teaching
  visible    → levelTree      哪些積木看得到
  io         → cstdio         產出 printf 還是 cout
  provides   → ["c99", …]     requires 對它求解
  reference  → gcc -std=c99   驗證
```

🔴 **兩份 draft 各自缺對方**：診斷缺第二個輸入，而 `target` 那份說
「等第二個目標出現」——**診斷就是它的第一個消費者**。

⚠️ 而這個問題比它看起來大：它決定診斷是一個 **lint 工具**，
還是**教學情境的一部分**。前者只需要樹，後者需要知道「這個學生在哪一課」。

## 二、🔴 學生最常撞到的錯誤，這個設計看不到

診斷掛在語義樹上。**而分號忘了的時候沒有語義樹**：

```
語法錯誤  → tree-sitter 產 ERROR → lifter 降級成 raw_code
            ＋ degradationCause: 'syntax_error'（lifter.ts:262）
            → 沒有語義結構可掛診斷
語義錯誤  → 有樹 → 診斷看得到
```

**第一週最常撞的那一類，落在這個設計的視野外。**

⚠️ 而資料**已經在節點上了**（`degradationCause` 三種值：`syntax_error`／
`unsupported`／`nonstandard_but_valid`），缺的只是投影——沒有人把它當診斷用。

## 三、✅ 而那條未決有答案：**不要統一**

本檔原本問「降級是否該統一為 Diagnostic 的一種」。答案是不要，
而理由與 §四（第三十二條護欄）**是同一條線**——只是多了一格：

| | 意思 | 錨在哪 | 該顯示什麼 |
|---|---|---|---|
| **殘差** | 我們沒看懂這段 | `degradationCause` | 「這段我還不認得」——**不是錯誤** |
| **誤差** | 你寫錯了 | `Diagnostic` | 錯誤／警告 |
| **沉默** | 我們不會檢查這種錯 | 沒有東西 | 🔴 危險的那一格（§四 已述） |

> **把殘差併進 Diagnostic，學生會看到「你的程式有 12 個錯誤」，
> 而其中 11 個是我們的問題。**

⚠️ **而反過來也成立**：`raw_code` 在畫面上**應該有存在感**，只是不能長得像錯誤。
那是「誠實降級」在 UI 上的兌現——見 [降級與認知邊界](../concepts/降級與認知邊界.md)。

### ✅ 2026-08-14 做了（驗收③），而做之前先修掉一個更底層的缺陷

程式碼側用 `MarkerSeverity.Info` ＋ **獨立的 marker owner**（`semorphe-residual`）
——診斷變了不會清掉殘差，反過來也是。**兩個數字要能分開看。**

🔴 **而本節的前提原本不成立**：`degradationCause` 說是「已經在節點上」，
實測 `int x = @@@;` 被 lift 成一顆**乾淨的 `cpp:var_declare`，信心 `high`**
——`ERROR` 節點是 `declaration` 的子節點，而 lift **只走它認得的那些**。

> **一段語法錯誤的程式碼被 lift 成一棵看起來完全健康的樹。**

那讓「殘差 0%」讀起來像「模型長全了」，而真相有一部分是**壞掉的那段被丟了**。
判準見 [降級與認知邊界](../concepts/降級與認知邊界.md) 的 **Lift-0**。

## 四、訊息的軸有兩條，而本檔只寫了一條

本檔的 L0／L1／L2 是按**學生程度**分級。

⚠️ 🔴 **而 2026-08-14 查證後，這一組也不成立**——見文末「詞彙集不是等級」。
本節保留原文以記錄轉變，**但 `(level, panel)` 這個措辭已被取代**。而使用者 2026-08-12 的原話是
「越像實際編譯器吐出的訊息越好……**不過積木側可以不一樣**」——那是按**面板**分。

**兩條軸獨立**：

| | 積木側 | 程式碼側 |
|---|---|---|
| L0 | 「這裡需要一個數字」 | 「這裡需要一個數字」 |
| L2 | 「右邊要 int」 | `error: invalid operands to binary +` |

L2 的程式碼側**刻意要像 clang**，L2 的積木側**刻意不要**
——那不是同一個訊息的兩種深度，是 `(level, panel)` 的二維表。

⚠️ **實作後果**：`Diagnostic` 不能只帶一個 `message`。最小形式是
**規則 id ＋ 參數**，訊息在**投影時**才組出來——與程式碼生成同一個形狀
（語義樹不存字串，`generate` 時才產）。

## 五、委派編譯器：那個「還沒想清楚」比想像中更接近答案

本檔說「WASM clang 體積大／遠端破壞離線」。而**參照編譯器在這個專案裡
已經是一個成熟的概念**——`tests/helpers/run-cpp.ts` 檔頭逐字：

> 「軟體域的那顆**實體**……**行為由量測定義，不由宣告定義**」

所以 **L2 不是新東西，是把已經存在的參照元件從測試路徑接到產品路徑**。

⚠️ 而「離線 vs 體積」因此變成一個已知形狀的問題：
**參照元件在不在場，是一個可量的狀態，不是一個要藏起來的失敗。**
`run-cpp.ts` 已經是這樣寫的：

> 「沒有編譯器**不是**『這一段跑不動』，是量測機構壞了。丟出去，別混進統計。」

→ 沒有編譯器時 L2 不該靜默消失，它該說「這一層現在不在」。

## 🔴 第一版把它寫成「L1／L2／L3 三層」，而那個形狀是錯的

使用者逐字：「**我其實不太想用 L 分類，因為太沒有本質意義，也沒有彈性。**」

**它把兩個不同的問題編成了一個階梯**：

```

委派編譯器  ┘

```

事實相反——**先委派，自己寫的那一堆規則有大半就不必寫了**。
一個「1、2、3」讓一個**選擇**看起來像一個**順序**。

⚠️ 而「沒彈性」是第二個代價：`target` 當第二個輸入

> 「位置不是身分，是形態」、C2 資訊軸）——**階梯是進口的。**


## 🔴 而 §四 的兩個數字，其中一個的方向要寫清楚

不知道（「`while(true)` 可能是你不想要的無窮迴圈」是教學判斷）→ 手寫，
而且**只手寫那些**。

⚠️ **所以答案不是「每顆元件加一個 `diagnose.ts` 第六路」**。
大部分元件一行都不用寫——那正是膠囊化的意義：宣告一次，五路都吃得到。

### ⚠️ 而現在不做，代價會漲

`src/languages/cpp/diagnostics.ts` 是一個**共用檔**。元件到 500 顆時它就是
下一個碎裂病灶——而 **`component-locality` 護欄看不到它**：
它比對的是元件身分，而診斷規則寫的是**積木型別**（`cpp_if`）。

## 二、整體／邏輯錯誤：那是【另一台機器】

```
逐節點的約束    看一個節點就判得出來    便宜、可完備、【硬性零】
全樹的性質      要走一遍並帶著狀態      貴、註定不完備、【只能盡力】
```

§「缺一層：全樹流敏感約束」逐字已經指出這一層裝不下：

> 「第 3 行的 move 殺掉第 5 行的 use，那是**順序與生命週期**，不是父子關係。」

而它同時說了關鍵的一句：**這台機器與硬體 DRC 是同一台**。所以它不為診斷單獨蓋。

🔴 **兩者不可混進同一條護欄**——第一種能推到硬性零（漏一個就是缺陷），
第二種**永遠不是零**（不完備是它的本質）。合起來量，那個數字就讀不出任何東西。

## 三、有沒有不處理的？有，而「不處理」要看得見

```
我們自己查   只有我們知道的：語義樹的性質、教學意圖、積木特有的狀態
委派編譯器   語言規則：型別、未宣告、模板、UB —— 【不要重寫】
不處理       執行期才知道的（除非直譯器真的跑到）
```

而第三格**不能安靜**。處置是現成的——`audit-behavior-error` 檔頭逐字：

> 「**殘差高＝模型還沒長到那裡（系統仍然正確）**；**誤差高＝模型是錯的**。」

殘差通道已經在了（`semorphe-residual` ＋ `MarkerSeverity.Info`）。
「我們不查這種錯」要走那條通道說出來——**那正是驗收⑤ 說的危險的那一格**。

## 四、超越編譯器：先說清楚【哪裡不要比】

🔴 **不要比它強的地方**：型別推導、模板實例化、UB。
`scenario-coverage` 已經把參照編譯器當成**行為的權威**在對答案
（`history/059`）。跟它比那個是輸的，而且輸得沒有意義。

### 真正超越的四個地方，而第一個今天已經在做了

**① 積木製造了編譯器碰不到的錯誤狀態**

「一個 `if` 沒有條件」**在 C++ 原始碼裡寫不出來**——它不會 parse。
而積木上它是一個合法的中間狀態。

> **今天的 3 條診斷規則，沒有一條是編譯器報得出來的。**
> 那不是巧合——那個空間本來就只屬於我們。

**② 我們知道讀的人是誰**

編譯器**永遠**不知道誰在讀。而「可用詞彙集」就是這件事
（見文末「詞彙集不是等級」）。一句用了學生沒學過的詞的訊息，
正確但沒用。**這是結構上做不到，不是懶得做。**

**③ 我們可以執行**

直譯器在跑、執行位置在廣播（`execution:at-node`）：

```
這一行從來沒有被執行到
這個迴圈跑了 100000 次而你只有 10 筆資料
這個變數被讀之前沒有被寫過（實際跑到的那條路徑上）
```

⚠️ 靜態證明這些很貴，而**我們可以直接觀察**。
而它只對跑到的路徑成立 → 天生屬於**第二台機器**（不完備），不可收硬性零。

**④ 節點是概念，不是語法**

編譯器的 AST 節點是 `binary_expression`；我們的是 `cpp:array_at`、`cpp:loop_for`。
所以認得出**意圖層級的樣式**——「你在遍歷陣列，而這裡的邊界是 `<=`」。
編譯器沒有這個詞彙。

## 五、順序（未承諾）

```
① 讓 min／enum／requires 真的被讀   便宜；23 顆立刻有診斷，而且是【導出】不是手寫
② 委派編譯器                        讓「語言規則」那一格整片消失
③ 執行期觀察                        機器已經在了
④ 全樹流敏感                        貴，且等硬體 DRC 一起（同一台機器）
```

⚠️ **①現在就該做**，因為它同時清一筆既有的債：**23 個宣告零消費者**。
而「[一份宣告可能正在驅動行為](../experience.md)」的**反面**是：

> **一份沒有人讀的宣告會慢慢變成假的。**

那 23 筆放愈久，愈可能已經有幾筆是錯的而沒人知道。

## 出口條件（本次新增）

- **①做了** → `children.min` 從零消費者變成診斷的來源，而那 23 筆會第一次被驗
- **手寫規則降到只剩教學判斷** → 「登錄表知道嗎」那條判準在診斷上兌現
- **第二台機器有第一個實例** → 那時才知道它與硬體 DRC 是不是真的同一台
- ⚠️ **診斷規則搬出共用檔** → 而它今天 `component-locality` 看不到，
  所以**要先讓那條護欄看得到它**，否則搬完沒有東西守著

# 2026-08-14（四）：🔴 而最常見的那個錯，走的不是診斷這條路

> 觸發：使用者「**連分號的錯誤訊息都沒有處理的很好？甚至還不會報出來。**」
> **完整轉變見 [history/062](../history/062-把使用者的錯歸進了我們的殘差.md)。**
> 本節只記它**如何改寫上一節的三分法**。

上一節按「誰擁有那個預期」分成 A（元件）／B（編譯器）／C（意圖），
而實測之後多出一件事：**B 今天不是「還沒做」，是【被吞進殘差通道】了。**

```
少一個分號  → 樹上標了 syntax_error（有測試釘住 ✅）
            → 程式碼側 MarkerSeverity.Info ／ owner semorphe-residual
            → 🔴 不走 onDiagnostics，驗收④ 的整套一點都沒套到它
```

## 所以「誰擁有預期」之外，還要問「誰的問題」

```
殘差     我還沒長到那裡     我們的問題，系統仍正確    Info
誤差     我算錯了           我們的問題，系統是錯的    護欄在看
使用者   你寫壞了           🔴 使用者的問題            Error ← 該走診斷
```

`degradationCause` 的三個值裡，**只有 `syntax_error` 屬於第三格**
——而三個共用同一個通道。

> **一個對的判準（殘差 vs 誤差）被套寬了一格：
> 它分的是「我們的問題有兩種」，而列舉裡混進了「不是我們的問題」。**

## ⚠️ 而這改變了順序——它該排在驗收⑤ 之前

上一節排的順序是 ①宣告導出 → ②委派編譯器 → ③執行期 → ④全樹。
**而「把 `syntax_error` 搬回診斷通道」比它們全部都前面**：

| | 誰會撞到 | 多早撞到 | 成本 |
|---|---|---|---|
| **搬 `syntax_error`** | 🔴 **每一個學生** | **第一週** | 便宜（改 severity ／ owner ／ 兩份文案） |
| ①宣告導出 | 拖錯積木的人 | 隨時 | 便宜 |
| ②委派編譯器 | 寫得出能編的程式的人 | 中期 | 貴（離線／體積未答） |

判準用 `experience`「排技術債的優先序，問的是**使用者多早會撞到**」。

⚠️ **而它也讓驗收⑤ 的兩個數字才有意義**：今天分號不在診斷的分母裡，
所以「涵蓋率」量的是一個**不含最常見錯誤**的集合。

## 出口條件（本次新增）

- **`syntax_error` 走診斷通道** → 少分號的程式在程式碼面板出現 **Error 級**波浪
  （今天是 Info，所以那支測試現在就會紅）
- ⚠️ **`audit-residual` 的基線分母跟著變** → 一次基線調整，**要指名理由**
- **`concepts/降級與認知邊界` 重看 `syntax_error`** → 它不是認知邊界，是輸入壞了

# 2026-08-14（五）：文獻怎麼說——而它推翻了本檔的一句話

> 觸發：使用者「**我想要研究看看有沒有 SOTA 對這方面的處理。**」
> ⚠️ **這是知識庫第一次引用外部文獻**（慣例沿用
> [concepts/認知鷹架](../concepts/認知鷹架.md) 的 Sweller 1988／Vygotsky 1978 形式）。
> ⚠️ **兩篇 PDF 抓下來是二進位、ACM 403**——以下依據搜尋摘要與摘要頁，
> **沒有讀完任何一篇全文**。要當作主張之前需要真的讀。

## 一、🔴 這個領域六十年沒有共識，而共識偏向「沒效」

```
2014  Denny / Luxton-Reilly / Carpenter   對照實驗 → 加強語法錯誤訊息【無顯著效果】
2016  Becker                              ~200 學生／~50,000 個錯 → 有效果
2019  Becker 等回顧 107 篇（1967 起）       那些指引【大多沒有嚴謹證據，常屬軼事】
2024  Not the Silver Bullet               GPT-4 訊息在 6 個任務只贏 1 個（修好時間）
                                          🔴 而【手寫的解釋仍然贏過 LLM 與原生訊息】
```

> **「我們把訊息寫好一點」是一個做了六十年而證不出來的宣稱。**

### ⚠️ 而它驗證了⑤ 的驗收方向

`vision` 驗收⑤ 寫的是「兩個數字都要記，而假警報只准下降」，
**不是**「訊息變好了」。**後者正是文獻證不出來的那一個。**

## 二、🔴 而它推翻了本檔「兩條軸」那一節的一句話

本檔文末寫過：

> 「呈現的形式　原文 ──── 教育版　🟡 翻一條好一條，而它**可以停**」

**那句話太寬鬆。** 文獻說的不是「翻譯有效但可以停」，是
**「翻譯的效果本身未經證實」**。所以正確的說法是：

```
舊   翻一條好一條，可以停在任何一天
新   🔴 得【先證明它有用】——而 60 年的文獻沒證出來
     ⚠️ 唯一站得住的線索：2024 那篇說【手寫的贏過 LLM 與原生】
        → 有價值的是「人寫的那份工」，不是機制
```

## 三、有實證支持的可讀性因子——而我們已經對齊而不自知

CHI 2021（*On Designing Programming Error Messages for Novices:
Readability and its Constituent Factors*）量出四個真的影響可讀性的因子：
**訊息長度、術語、句子結構、詞彙**。

⚠️ 而 `knowledge/skills/component-generate` 的**積木標籤風格規範早就在做這件事**
（逐字：「函式名不直接當標籤」「語言關鍵字不當標籤」「語法符號不當標籤」）
——那是「避免術語」的一個嚴格版本，**而它是為積木標籤寫的，不是為錯誤訊息**。

→ **診斷文案直接沿用那份規範，不要另寫一套。**

## 四、我們與 Droplet 撞了同一個機制，而歸檔不同

Droplet／Pencil Code（Bau，雙模態編輯器，本專案最近的前人）
處理模式切換的做法：**把簡單的文字語法錯誤轉成特殊的「錯誤積木」**，
讓切換還能進行；複雜的則擋住切換。

**那就是我們的 `raw_code`／殘差通道**，獨立長出來的同一個機制。

⚠️ **而歸檔不同**：他們歸在「**錯誤復原**」，我們歸在「**認知邊界**」。
從外面看，[history/062](../history/062-把使用者的錯歸進了我們的殘差.md) 那筆錯格更明顯
——我們把一個**錯誤復原**機制放進了「我還沒學會」的抽屜。

## 五、一格我沒找到前人（而「沒找到」不等於「沒有」）

**「同一則錯誤，在兩個表示上用不同措辭」**——雙模態的文獻談的是
**模式切換**與**遷移**，我沒找到談「兩個視圖同時各說各話」的。

⚠️ **只跑了幾輪搜尋、沒讀完全文。** 要當賣點得先做真的文獻檢索。

## 出口條件（本次新增）

- **有人讀完 Becker 2019 的指引全表** → 那 12 條指引哪些有證據、哪些沒有，
  今天只知道「大多沒有」
- **「雙視圖不同措辭」做過文獻檢索** → 從「沒找到」變成「沒有」或「有，是誰」

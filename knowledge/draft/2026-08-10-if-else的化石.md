# if/else 的化石

> 日期：2026-08-10
> 怎麼冒出來的：使用者說「我記得當時調整很久，後來是用動態的積木才完成的，
> 有些可能是當時遺留的化石」，要求先深入了解目前的運作。
> **狀態：診斷完成，處置未決。** 四個候選裡只有一個已經被釘住。

## 目前怎麼跑（查證過，不是回憶）

**語義層只有 `cpp:if` 一顆在跑。**

```
cpp:if
  children: condition / then_body / else_body
  else-if = 巢狀的 cpp:if 掛在 else_body 下 ＋ properties.isElseIf = 'true'
```

`lift-patterns.json:377` 一直把 AST 的 `alternative` 掛成 `else_body`。

**積木層是一顆帶 mutator 的動態積木 `u_if`**（`block-registrar.ts:955`）：
`elseifCount_` / `hasElse_`，mutator 子積木 `u_if_elseif_input` / `u_if_else_input`。
`cpp:renderIf` 策略負責**把巢狀的 else-if 攤平**成 `ELSEIF_CONDITION_n` /
`ELSEIF_THEN_n`——靠讀 `isElseIf`。這就是「用動態積木才完成」的那一部分。

## ⚠️ `cpp:if_else` **不是**化石

它是**宣告過的降級目標**：

```json
"skipPaths": ["lift"], "skipReasons": { "lift": "degradation-target" }
```

`cpp:ternary.abstractConcept = "cpp:if_else"`，而 `SkipReason` 的定義要求
降級目標過兩道門檻（「① 必須真的有概念宣告它為 `abstractConcept`
② 必須不在工具箱裡」）——兩條都成立。

> 2026-08-10 稍早我推測它「可能是不可達的殼」，**那是錯的**。
> 它是被設計成從降級抵達的，而且已經有閘門在驗。記在這裡以免有人重犯。

## 四個化石候選

### ① `isElseIf` 是投影提示長在語義樹上，而且**沒有宣告** ⚠️ 未處置

`cpp:if` 的 `properties` 是 **`[]`**，而：

| 誰 | 做什麼 |
|---|---|
| `pattern-lifter.ts:552` | 設 `properties.isElseIf = 'true'` |
| `renderers/strategies.ts:80` | 讀它，決定要不要攤平成 mutator 插槽 |
| `extract-strategies.ts:165` | 產生帶它的節點 |

**兩個問題疊在一起**：

1. 它違反三層契約——Layer 1 是語義宣告、**Layer 2 才是投影提示**。
   「這顆 if 是不是 else-if」是**呈現**的事，不是語義的事：
   同一棵樹在別的投影下（例如純文字）根本不需要這個標記。
2. 它是**未宣告的屬性**——這正是第三十條護欄（宣告完整性）的**屬性版本**。
   那條護欄目前只看接點，看不到這個。

→ **開著的問題**：要先蓋屬性方向的護欄（會一次抓出一批），
還是先單獨處理這一顆？

### ② `u_if_else` 的 `renderMapping` 與它的積木對不上 ⚠️ 未處置

```
投影宣告：  statementInputs { THEN: "then",  ELSE: "else" }
實際積木：  Blockly.Blocks['u_if_else'] = Blockly.Blocks['u_if']   ← 別名
           而 u_if 的 THEN 裝的是 then_body
```

同一個插槽名 `THEN`，在**同一個積木型別**上有兩種意思。

### ③ 而 ② 有後果：**身分在來回轉換中改變** ✅ 已釘住

```
cpp:if_else --render--> u_if_else（內容完整）--extract--> cpp:if
```

已用 `it.fails` 釘在 `tests/integration/degradation-identity.test.ts`
（`[BLOCKED:cpp:if_else]`），含兩個對照組與範圍界定（**只換身分，不掉資料**）。

**修法兩條路**，代價不同：

| | 做法 | 代價 |
|---|---|---|
| A | 讓 `extractIf` 依積木型別回傳對應身分 | 最小改動，但要順帶處理子節點名（`then_body`/`else_body` vs `then`/`else`）|
| B | 讓 `cpp:if_else` 不再需要自己的積木型別，`u_if_else` 整個退場 | 更乾淨，但要先答一個**教學問題** |

> **B 的前提**：降級成 `cpp:if_else` 的節點，需要與 `cpp:if` 在畫面上分得出來嗎？
> 那是教學決定，不是技術決定——要問使用者。

### ④ 執行器的註解過期 ⚠️ 未處置（最便宜）

`control-flow.ts:26` 寫著 `cpp:if_else`「有積木投影（`u_if_else`，
**使用者拖得到**）」——而 `toolbox-categories.ts:56` 早就
`excludeTypes: ['u_if_else']` 了。註解停在排除之前。

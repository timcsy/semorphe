# 完整願景與它的邊界——哪些現在定，哪些等第一個跨過去的東西

> 日期：2026-08-12
> 怎麼冒出來的：使用者分享了對專案的完整想像（VSCode 外掛、多視窗面板、
> 硬體實際回饋、網頁版並存），並說「**我想要先訂好這些模組的邊界以及互動方式
> 還有資料夾結構，免得到時候一團混亂還要花很多時間重構**」。
> **狀態：願景未承諾排期。** captured ≠ committed。

## 一、使用者的想像（原話整理）

- **VSCode 外掛**，不同視窗展示不同面板：程式碼、Blockly、模擬執行、
  硬體 2D 接線、硬體 3D 組裝
- 因為以 VSCode 為底，**甚至可以用 Arduino IDE 開啟**
- **硬體實際的回饋**——寫一個「常駐小 OS 或服務」，
  用 **API／MQTT／ROS2** 等通訊方式
- **不只針對 VSCode**，也要有網頁版
  （「其實目前 C++ 而言目前的網頁版設計我已經蠻喜歡的了」）

## ⚠️ 二、這不是新方向——架構圖裡已經有一半，而那一半從沒被檢驗

`vision.md:85` 的架構圖逐字：

```
宿主環境（瀏覽器 / VSCode / Electron）
  ↕ ViewHost 介面
多個獨立視圖（積木 / 程式碼 / 主控台 / 變數 / 資料流 / 接線 / 模擬）
  ↕ SemanticBus（瀏覽器=EventEmitter / VSCode=postMessage）
SemanticCore（零 DOM 依賴）
```

`principles.md` P9 第三條逐字：

> **宿主獨立性**：同一套件在瀏覽器和 VSCode 中語義行為完全相同

連 WebView 隔離模型都寫好了（`vision.md:116`）：「VSCode 中 blocks = WebviewPanel、
code = **原生 TextEditor**、console = Terminal + postMessage。
**Core 跑在 Extension Host，不跑在 WebView。**」

**所以問題不是「要不要這樣做」，是「那些話今天是不是真的」。**

## 三、⚠️ 實測：P9 第四條有一筆違規，而且零驗證

```
vitest 的環境        happy-dom（全部 3957 支）
→ 沒有任何一支證明「Node.js 環境可執行」

src/core   碰 DOM 的檔：1   ← src/core/storage.ts:207 `document.createElement('a')`
src/interpreter          0
src/languages            0
src/ui     碰 DOM：23 / 30 檔
```

P9 第四條逐字：「`src/core/` ＋ `src/languages/` ＋ `src/interpreter/`
**零 DOM import，Node.js 環境可執行**」。

那一筆是 `downloadBlob()`——**一個瀏覽器專屬的下載動作住在核心的 storage 裡**。
它不會被 `tsc` 抓到（`document` 是全域型別），也不會被測試抓到（`happy-dom` 有它）。

> **一條「在 X 環境可執行」的規範，只有在 X 環境跑過一次才算數。
> 而如果測試環境永遠提供 X 沒有的東西，那條規範就沒有任何機會失敗。**

`src/ui` 的 **23/30** 則是**宿主 seam 的實際大小**——VSCode 版要面對的就是那 23 個檔。

## 四、判準：邊界現在定，介面等（✅ **已進 `experience`**）

使用者要「先訂好邊界免得之後一團混亂」，而前一輪才說過「等第二個實作才看得見
正確形狀」。**兩句都對，適用的東西不同**：

| | 現在定 | 等 |
|---|---|---|
| **邊界的位置**（誰不准 import 誰） | ✅ 定，而且蓋護欄 | |
| **介面的形狀**（那條線上傳什麼） | | ⚠️ 等第一個真的跨過去的東西 |

> **邊界是可以否證的，介面不行。**

理由：邊界畫錯了**護欄會告訴你**——這一週已經發生兩次（中立性抓到 `universal`
放錯層、P9 護欄抓到視圖 import 語言）。而介面猜錯了要等有人用才知道，
那時已經有一堆程式碼依賴它。

⚠️ **這條判準我已經用它做過一次決定**（決定「現在定邊界、等介面」）
——reliance 是 capture 的觸發信號，所以它在這裡被記下來。
~~**提議進 `experience`**，待人確認。~~ ✅ **已執行**——
`experience.md`「邊界是可以否證的，介面不行」。

## 五、逐項過使用者的願景

### 🟢 定得了，而且該現在定（有護欄可以守）

| | 現況 | 可以立刻量的 |
|---|---|---|
| **宿主 seam** | `src/ui` 23/30 檔碰 DOM | 那個數字就是搬到 VSCode 要面對的量 |
| **硬體 render seam** | 已定案（`draft/硬體域併入計畫`）：`src/render/` 只吃資料形 | 連 `audit-render-boundary` 護欄都設計好了，只是還沒有東西可守 |
| **通訊層的邊界** | — | ⚠️ 見下 |

**通訊層**：MQTT／ROS2／HTTP API 是**三個實作、一個介面**。它們的共同點是
**非同步、可能斷線、有延遲**——而 `SemanticBus` 是**同步、本地、不會失敗**的。

⚠️ **而「非同步」其實不是難點**（2026-08-12 查證）：`cin` 今天就是一個
非同步輸入源（`setInputProvider(() => Promise<string>)`），直譯器有現成的注入點。
**真正沒答的是失敗語義**——`awaitInput()` 的簽名只能成功或永遠不回來，
而 MQTT 會斷線、逾時、值會過期。見
[硬體不是一個階段是兩類](2026-08-12-硬體不是一個階段是兩類.md) §五。

> ⚠️ **不要把硬體通訊接到 `SemanticBus` 上。**
> 那會讓一個本來不會失敗的匯流排開始需要處理逾時與重連。

### 🟡 定得了一半

**視圖的分類**：`vision.md:115` 已寫「可編輯 / 唯讀-執行 / 唯讀-分析 / 唯讀-硬體」。
而使用者的 **2D 接線是可編輯的**（要拉線），所以它不屬於「唯讀-硬體」。
→ 那個分類要重做，而依據是**2D 面板要不要能編輯**——產品決定，不是技術決定。

### 🔴 現在定不了，建議不要猜

- **硬體「常駐服務」的形狀**：daemon？VSCode extension 的一部分？獨立進程？
  決定它的是「要支援哪些板子、要不要免安裝」——今天沒有答案。
- **「Arduino IDE 也能開」**：Arduino IDE 2.x 基於 Eclipse Theia，理論上吃 VSCode
  extension。**而那是相容性問題，要有一個能跑的 extension 才驗得了。**

## 六、⚠️ 教學視圖不是第六個視圖，是**第二種投影對象**

（使用者補充「還有教學視圖，元件或概念的圖鑑和圖解，然後相關教學內容」之後才看出來。）

`ViewHost` 契約今天承載的三個事件**全部是「當前這個程式」的**：

```ts
onSemanticUpdate(tree)        當前程式的語義樹
onExecutionState(status)      當前程式的執行狀態
onExecutionAtNode?(nodeId)    當前程式執行到哪
```

而圖鑑要的是「**所有元件的清單**」——與使用者現在打開的程式無關。

> **其他視圖回答「這個程式長什麼樣」，圖鑑回答「有哪些東西可以用」。**

```
投影對象          誰在投影它
語義樹（當前程式） 積木、程式碼、2D 接線、3D 組裝、執行動畫
登錄表（所有元件） 工具箱、圖鑑／教學            ← 契約今天不認識這一種
```

⚠️ **硬塞進 `ViewHost` 的話，`onSemanticUpdate` 對圖鑑永遠是空實作**
——而這一週才剛清掉四個那種空樁。

**而這件事早就有名字**：`draft/圖解形態與資料結構圖鑑` 逐字寫著
「**Blockly 的 toolbox ＝ ArduinoCAD 的 codex ＝ 登錄表的瀏覽投影**」。
工具箱**已經是圖鑑了**，只是只顯示了「可以拖出來」那一格。

→ 需要第二個契約（`RegistryView` 之類）。而**它的資料源已經存在**
（`registeredComponents()`／`componentTraits()`／工具箱用的那些）。

⚠️ 而**教材是第三格**，見
[漸進揭露把選項轉嫁給了老師](2026-08-12-漸進揭露把選項轉嫁給了老師.md)
——它不只是圖鑑的裝飾，**是讓 `levelTree` 有理由存在的東西**。

## 七、下一步的提議：兩個假東西，各驗一個地基

使用者的擔心（之後一團混亂）的解法**不是「想得更周全」，是讓錯誤現在就發生**。

前例是 `src/views/semantic-tree-view.ts`——它的檔頭逐字「Used to **verify** that
the concept/blockDef split enables views independent of the Blockly projection
layer」。**它成功了**（`ViewHost` 契約接手，`specs/117` 才讓它退休）。

### A. 一個 20 行的假宿主（最便宜，而且驗的是整個 VSCode 計畫的地基）

不是真的 extension，是一支 **Node.js 腳本**：載入 core、跑一次
lift → generate → execute，**完全不碰 DOM**。

**今天跑它會立刻紅**——`src/core/storage.ts:207` 的 `document.createElement`。
那正是重點：**P9 第四條今天是假的，而沒有任何東西在說**。

配套：一條護欄（`src/core`／`interpreter`／`languages` 不得出現 `document.`／
`window.`），⚠️ **第一次跑必須是紅的**（`build-guardrail` 6.5）——已知 1 筆。

### B. 一顆 `hw:led`（逼出硬體的答案）

> ⚠️ **本項在同一天被修正**（見
> [硬體不是一個階段是兩類](2026-08-12-硬體不是一個階段是兩類.md)）：
> `hw:led` 是**守恆**的例子，它逼出的是最難的那些（接點、C2、電氣求解）。
> **而純資訊那一類今天就做得了**——`concepts/元件.md:196`
> 「資訊↔資訊直接接；一端有守恆基質才要 adapter」。
> → 先做一顆 `hw:temperature` 之類的純資訊源，它逼出的是通訊層的介面
> 與**讀失敗的語義**，而那兩個都是眼前的問題。


- 它的**行為**（通電會亮）住哪？→ 逼出 `interpreter/` 該不該改名
- 它的**接點**（陽極／陰極）與 `cpp:if` 的接點是同一個機制嗎？→ 逼出 C2 資訊軸
- 它的共用實作（電氣模型）住哪？→ 逼出 `languages/` 的答案

### C.（更便宜的第三個）用現有的工具箱資料渲染一頁圖鑑

不做教學內容、不做圖解，只把「登錄表的完整投影」畫出來。
**資料已經全部都在**，所以成本比 2D 面板低一個數量級。
它會立刻問出：`ViewHost` 夠不夠用？教學內容掛哪？型別要不要進登錄表？

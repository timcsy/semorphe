# 核心硬編了別人的文法詞彙——耦合的第三維

> 日期：2026-08-11
> 怎麼冒出來的：把 23 條性狀逐條問「換一個語言，會不會有另一顆元件宣告它」，
> 發現 `elseIfChainable` 是 C 家族的、而它的消費者在核心。
>
> ⚠️ **這份 draft 的第一版整個是錯的**，因為我把那段程式碼讀反了。
> 錯的版本判定「核心把 `else { if }` **摺成** `else if`，那是 C 家族的語法知識」，
> 並開了 A/B/C/D 四個候選處置。**那四個都在解一個不存在的問題。**
> 更正的過程留在下面「§一」，因為錯的方式本身有內容。

## 一、⚠️ 更正：那不是摺疊，是標記，而目的正好相反

```ts
// src/core/lift/pattern-lifter.ts:566-574
// Mark direct "else if" chains: when an else_clause contains
// a direct if_statement (not wrapped in compound_statement),
// mark the resulting if node with isElseIf so renderer/generator
// can distinguish from "else { if (...) {} }"
```

沒有那個標記，`else if` 與 `else { if }` 會 lift 成**一模一樣的樹**——
來回轉換就把使用者寫的形式改掉了。

**它是保住區別的東西，不是合併。**

於是「這個標記該不該存在」這個問題，[等價與觀察集](../concepts/等價與觀察集.md)
已經答了：觀察集是**五路**，而兩者在 `render` 那一路**不等價**（積木長得不同）。
那份概念檔的處方是「**傾向少合併、多記對應**」——那個標記就是「記對應」。

用它的詞彙講，`isElseIf` 是**殘差**：語義模型分不出、而原始碼分得出的那一點差。
「模型 ＋ 殘差 ＝ 完整」。

### ⚠️ 而我錯的方式值得留著

我在三輪對話裡連續說了三次「核心把 else { if } 摺成 else if」，
**而我從頭到尾沒有讀那八行程式碼**——我從函式名（`isElseIfChainable`）
和呼叫位置推出了一個行為，然後把它當成事實推了三層結論。

> **一個名字取得夠好，會讓人以為自己已經讀過它了。**

（`experience.md` 有一條同族的：「一個函式長得像實作，不代表它是實作」
——那次是把 40 行的分支當成新形狀。這次是反過來：把 8 行的標記當成一個機制。）

## 二、真正的問題：三個文法節點名

```
src/core/lift/pattern-lifter.ts:570   'else_clause'
src/core/lift/pattern-lifter.ts:571   'if_statement'
src/core/lift/lifter.ts:65            'compound_statement'
```

**tree-sitter 的文法節點名硬編在核心。**

而三條護欄一條都抓不到：

| 護欄 | 找什麼 | 為什麼漏掉 |
|---|---|---|
| 中立性（身分掃描） | 元件身分字串 | 這三個都不是身分 |
| 中立性（import 檢查） | `from '…languages/…'` | 沒有 import |
| 就近性 | 膠囊身分出現在膠囊外 | 不涉及膠囊 |

> **耦合的第三維不是「範疇名」，是「別人的文法詞彙」。**

（前兩維：`history/021` 記的**身分**，與同一則記的**語法符號**——
核心層寫死 `//`、`/* */`，那次的處方是 `comment-syntax.ts` 登記處。）

### 這三個有多嚴重？誠實的評估：不太嚴重，而它會長大

- `if_statement` 湊巧 Python 的 grammar 也有這個名字
- 而「`else_clause` 裡直接包一個 `if_statement`」這個**結構**是 C 家族的
  ——Python 有獨立的 `elif_clause`
- 所以對 Python 它**不會誤觸發，只是死的**

⚠️ 而「死的」正是這個專案追了很多次的東西：`concepts/執行機構.md` 的整個主題。
一段對第二個語言永遠不跑的程式碼住在核心，它不會壞，**它只是在說謊**
——說「核心不知道任何語言」。

## 三、處置：這次只有一條，而它跟前兩維一致

**加一個維度到中立性護欄：核心不得出現 AST 文法節點名。**

前兩維的處置都是同一個形狀：

| 維 | 護欄 | 處置 |
|---|---|---|
| 身分 | 中立性身分掃描 | 元件宣告 → 登錄表 |
| 語法符號 | 註解語法檢查（065） | `comment-syntax.ts` 登記處（語言推、核心讀）|
| **文法節點名** | **沒有** | ？ |

而這一維**量得出來**——不像我上一版設想的「範疇名」（`isBinaryOperator` 算不算？
每個語言都有二元運算子）。文法節點名有一個現成的判準：

> **這個字串是不是某個 tree-sitter grammar 的 node type？**

那是一份**可以列舉的清單**（`tree-sitter-cpp` 的 `node-types.json` 就有），
所以護欄的判定不需要人判。

### ⚠️ 而第一次跑一定要是紅的

今天已知 3 筆。`build-guardrail` 第 6.5 步：先跑、確認紅、**逐項指名**、
修好，最後才產基線。3 筆修得完的話就收硬性零；修不動的話走棘輪。

### 三筆各自的處置（未定）

- `lifter.ts:65` 的 `compound_statement`——它做的是「進入一個作用域」。
  那可能是一條**性狀**（`opensScope`），而**掛在 AST 節點型別上不是元件上**
  ⚠️ 那是一個新東西：今天的性狀都掛在 `componentId`，這個要掛在文法節點型別。
- `pattern-lifter.ts:570-571`——`isElseIf` 這個標記本身可以留（見 §一），
  而「什麼形狀該標」要下沉。最小處置：讓語言套件推一份
  「哪些 AST 形狀要標哪個屬性」的規則。

## 四、我的傾向

**先蓋護欄，不急著修那三筆。**

理由：這一維今天只有 3 筆，**而蓋護欄的價值不在修這 3 筆，
在 Python 進來時它不會長到 30 筆**。而如果先修再蓋，
那 3 筆會被「順便」修掉，**而它們的同類還會再來**
（`build-guardrail` 6.5 的那條推論）。

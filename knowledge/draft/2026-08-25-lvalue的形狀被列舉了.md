# 字串屬性裡裝著程式碼——lvalue 只是其中一族

> 2026-08-25 使用者：「我的意思是 **lvalue 的型態應該百百種吧，這樣不就寫死了？**」
>
> 起因：那天修好「`a[i] += 2` 的索引掉了」之後，我報告「範圍是所有容器的下標複合指定」
> ——⚠️ **而那個回答答錯了層次**：問題不是「還有哪些容器」，是**賦值的左邊是一個文法**。

## 一、現況：三顆元件在表示同一個文法

```
cpp:var_assign          obj  = 字串
cpp:array_assign        obj  = 字串  ＋ index          ← 一層下標
cpp:array_2d_assign     obj  = 字串  ＋ row, col       ← 兩層下標，另開一顆元件
cpp:var_assign_compound name = 字串  ＋ index
cpp:increment           name = 字串  ＋ index
```

**五顆元件，target 全部是【字串屬性】，而下標的層數被寫進元件的身分裡。**

🔴 三層下標沒有第三顆元件——它會被塞進那個字串。

## 二、量測（2026-08-25，語料 = 整合測試裡的樣本）

```
cpp:var_assign             純識別字 107  ｜ 塞了別的東西 12 種   r.x · p.first · s.side · v.i …
cpp:array_assign           純識別字  69  ｜ 塞了別的東西  0 種
cpp:array_2d_assign        純識別字   2  ｜ 塞了別的東西  0 種
cpp:var_assign_compound    純識別字  29  ｜ 塞了別的東西  0 種
cpp:increment              純識別字  23  ｜ 塞了別的東西  0 種
```

### 🔴 而「0 種」不是好消息

同一天在瀏覽器裡**三十秒**就做出四種語料沒有的：

```
a[i][j] += 1   →  name = "a[i]"   index = j     ← 第一層下標被烤進字串
o.x    += 1    →  name = "o.x"
p->x   += 1    →  name = "p->x"
*q     += 1    →  name = "*q"
```

> **語料乾淨不代表模型對——它代表語料是照著模型長出來的。**

而 `cpp:var_assign` 的 **12 種**是這個專案自己的測試裡**已經存在**的證據。

## 三、症狀不是「壞掉」，是**假裝結構化**

那些都**來回得回去**——因為產生器是**字串串接**。所以：

- 測試綠、殘差不動、`audit-block-instantiable` 硬性零也是 0
- 而積木上那顆欄位是 `field_dynamic_dropdown`（`source: vars`）
- **點開它，看到的是工作區的變數清單**。學生在 `o.x += 1` 上點一下改成 `i`，
  那個成員存取就沒了——**沒有任何東西會出聲**

> **一個看起來結構化、實際上是字串的欄位，比一個誠實的 `raw_code` 更危險
> ——`raw_code` 至少長得像降級。**

## 四、🔴 而今天補的 `altLayout` 是這個病的症狀

`hasIndex` 之所以要變成「同一顆積木的第二種佈局」，**正是因為 target 不是一個接點**。

```
今天    var_assign_compound { name: 字串, index?: 運算式, value: 運算式 }
應該    compound_assign     { target: 運算式, op, value: 運算式 }

b[i]  += 1   target = array_access(b, i)
a[i][j] += 1 target = array_access(array_access(a, i), j)
o.x   += 1   target = member_access(o, x)
p->x  += 1   target = arrow_access(p, x)
*q    += 1   target = deref(q)
```

**一種佈局、沒有旗標、而 lvalue 的文法是開的。**

> **`hasIndex` 不是「缺一個機制」——它是「target 不是節點」漏出來的症狀。
> 而我今天做的機制讓一個錯的模型更好表達，不是讓它變對。**

⚠️ 所以 `altLayout` **留著**（它修好了一個活了五天的缺陷，`cpp_increment` 的退場也靠它），
而**把它記成一個過渡機制**：target 變成接點的那天，它才該退。

## 五、它服務的原則

- **P3 開放擴充**：一個文法該由組合表達，不由列舉表達
- **[[元件代數]]**：`array_2d_assign` 存在的唯一理由是「兩層下標」——那不是一個身分，是一個組合
- **P6 誠實降級**：現在的做法**既不誠實也沒降級**——它看起來成功了

## 六、⚠️ 而這一刀的成本要先講清楚

**它動的是語義詞彙本身**，`principles.md:158` 逐字：

> 「**但語義詞彙本身的變更不在此列**（例如 `componentId` 改名）：那動的是真實，
> **沒有東西可以重建它**，推導鏈對它不成立。這種變更 MUST 附**一次性的轉換**」

所以它**必須附一次性轉換**：舊存檔的 `name: "o.x"` 要被解析成
`member_access(o, x)` 節點——⚠️ **而那需要一個 parser**，因為那個字串裡裝的是程式碼。

🟡 好消息是那個 parser 已經在（tree-sitter）；壞消息是轉換要在**載入時**跑。

## 七、量完整圈之後：**44 個字串屬性裝了「不只是原子」，而它們是三種病**

> 使用者 2026-08-25：「**都量**」。語料同上（整合測試裡的樣本）。

### 🟢 甲、字串就是對的（不是問題）

`literal_string.value`（54 種）·`comment.text`·`block_comment.text`·
`doc_comment.brief`／`param_*_desc`／`return_desc`——**內容本來就是文字**。

🟡 邊界：`print_formatted.format`／`input_formatted.format`（`"%d\n"`）
——格式字串是一個迷你語言，**而它在原始碼裡本來也是字串常值**。放著。

### 🟡 乙、型別（**15 個屬性**）

```
param_decl.type · func_def.return_type · var_declare.type · pointer_declare.type
array_declare.type · var_declare_const.type · vector_declare.type · malloc.type
using_alias.orig_type · typedef.orig_type · operator_overload.param_type
cast_dynamic.target_type · cast_const.target_type · loop_range.var_type · try_catch.catch_type

實測值：int* · int** · int& · int[] · vector<T> · pair<int, int> · const Vec& · auto& · unsigned int
```

**型別本身是一個文法**（`vector<pair<int,string>>*`）。
⚠️ 而這個庫已經記過同一句話：

> **需要 parse 回結構才能用的字串，就不該是字串。**

🟡 而它的**急迫性低於丙**：型別今天是「顯示什麼就是什麼」，
沒有一顆下拉會假裝它是一個可選的原子。

### 🔴 丙、運算式（**約 19 個屬性**）——這一族才是真的病

```
cpp:var_assign.obj          原子 107 ｜ 非原子 12    r.x · p.first · s.side
cpp:struct_at_member.obj    原子  29 ｜ 非原子  4    arr[0] · a[0]
cpp:sizeof.target           原子  12 ｜ 非原子  1    arr[0]
cpp:lambda.capture          原子   6 ｜ 非原子  1    x = y
cpp:enum.values             原子   0 ｜ 非原子  2    "RED, GREEN, BLUE" · "DHT11 = 99"
cpp:func_call.name          原子  87 ｜ 非原子  3    Math::square      🟡 限定名，邊界
```

#### 🔴🔴 而最刺眼的是 `range_*` 那一族：**原子 0**

```
range_sum.begin/end · range_sort.begin/end · range_reverse.begin/end
range_fill.begin/end · range_fill_sequence.begin/end · range_sum_partial.begin/end/dest

實測值：v.begin() · nums.end() · arr + 5 · r.begin()
        ——13 個屬性，【每一個值都是運算式，一個原子都沒有】
```

`cpp:range_sum` 的宣告逐字：`properties: ['begin','end']`、`children: {init}`。
**兩個運算式當屬性、一個運算式當接點——同一顆元件裡兩種待遇。**

> **一個「原子 0」的欄位，說明的不是資料很雜，
> 是那一格從一開始就不該是欄位。**

### ⚠️ 丁、一個看起來像 lift 缺陷的

```
cpp:var_declare.name   原子 533 ｜ 非原子 1    "f()"
```

**`name` 裝著一個呼叫。** 這不像設計選擇，像抽取時漏出來的
——🔴 **未查**，而它值得單獨看一眼。

## 八、所以它是什麼等級的問題

**不是一顆元件的問題，是一個系統性的模式**：

```
乙 型別      15 個屬性   🟡 文法存成文字，而沒有假裝它是原子
丙 運算式    19 個屬性   🔴 文法存成文字，【而下拉假裝它是原子】
丁 疑似缺陷   1 個屬性   ⚠️ 未查
```

🔴 **丙與乙的差別在「有沒有一個 UI 假裝它是可選的原子」**：
`o.x += 1` 那顆下拉列的是變數清單，點一下就毀掉成員存取。
而型別那格今天沒有這個問題。

> **同樣是「字串裝著文法」，會出事的是那個【被投影成選單】的。**

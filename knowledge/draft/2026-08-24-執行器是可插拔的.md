> 這如果能和外部 Debugger 或是真實環境也有串接的機會就更好了**」
>
> 🟡 **狀態：已升格（2026-08-24，使用者「我點頭」）**——路線圖項目
> `vision.md` 階段 8「**執行器可插拔**」。

## 一、🟢 契約已經寫好了，只是沒有人替它命名

```
執行器 →  execution:state（status ＋ reason ＋ step）
          execution:at-node（nodeId, follow）
          execution:output
執行器 ←  execution:breakpoints（monaco 把行號翻成 nodeId 發上來）
```

`ExecutionStatus` 是封閉詞彙、`ExecutionReason` 也是、**斷點講的是 nodeId 不是行號**——
這些設計當初是為了解耦視圖，而**它們實際上定義的是「執行器」這個角色**。
差的只是：它只有一個實作，所以沒有人發現那是契約。

🔴 而 `concepts/模擬的誠實.md` 的「情境」那一格早就寫著這件事的一半：

> 「虛擬硬體之前，『執行』由**真板子**提供（燒錄）；模擬只保證跑得完與可重現」

**「執行由誰提供」本來就是一個變數**——這一份只是把它變成契約。

## 二、🟢 前置昨天剛買到，而當時不是為了這個

外接除錯器講 **file:line**，我們講 **nodeId**。中間那張表是 `CodeMapping{nodeId, startLine, endLine}`
——而**第五十六條護欄（對應表指到自己那一行）2026-08-24 才把它釘住**，
九顆複合產生器原本把標頭那一行算錯。

> **外接 debugger 的第一個前置不是協定，是「行號對得準」——而那條剛剛才綠。**

## 三、Runner 契約：收的是**樹 ＋ 對映**，不是程式碼字串

```
capabilities: {
  steppable      能不能單步            （真板子：不能）
  resettable     能不能重來            （真板子：LED 亮了就是亮了）
  variables      'push' | 'pull'       （我們的直譯器推；DAP 要你去要）
  timeModel      'immediate' | 'ticked'（硬體模擬有時間軸）
}
load(tree, mappings) · run · pause · step · stop · setBreakpoints(nodeId[])
```

**為什麼不收程式碼字串**：nodeId 是所有視圖的共同語言。外接 runner 在**它自己內部**
投影成程式碼去跑，回報時再用 mappings 翻回 nodeId。這樣「哪個節點在跑」對
積木／程式碼／流程／2D接線**四個視圖同時成立**，而換 runner 不影響任何一個。

⚠️ `capabilities` 是**能力宣告**而不是新的 status 值——
`concepts/執行機構.md:279` 那條仍然管用：**「第三個值就是在替『還沒做』找一個體面的名字」**。

## 四、三種外接的形狀不一樣

| 外接 | 翻譯發生在哪 | 難點 |
|---|---|---|
| Pyodide／真 CPython | runner 內部：tree→code 跑，line→nodeId 回報 | 對映要準（已備） |
| **DAP**（VSCode 那側白撿） | 我們當 DAP 客戶端，把它的事件翻成 `execution:*` | **變數是 pull**，今天的契約只有 push |
| 真板子 | 產韌體 → 燒錄 → 序列埠回報 | 不能單步、不能倒帶；**要用能力宣告誠實講出來**（P6） |

## 五、兩個最容易被低估的

### A. 時間軸不是換實作，是換**執行模型**

我們的直譯器同步走完（只有 `awaiting-input` 一個非同步點）。
硬體模擬要 tick：延遲、中斷、腳位隨時間變。
**那是執行模型的實質擴張，別跟「換一個 runner」混為一談**——它該是自己的一輪設計。

### B. `declareSkips` 今天是全域的，而它其實屬於**某一個執行器**

「`python:with` 不執行，因為這個直譯器沒有 `__enter__`／`__exit__` 也沒有檔案系統」
——那是**針對我們這顆**的宣告。換成 Pyodide，`with` 就能跑了。

> **一旦有兩個 runner，跳過宣告要變成 per-runner**，
> 否則症狀是「明明跑得動卻被跳過」，而它不會報錯。

## 六、最會咬人的：兩個執行器不一致時，誰是對的？

教育場景下一定會發生：**模擬跑得過、真板跑不過。**
處方照這個 repo 一貫的做法——**別假裝一致，量它**：

- 差異用宣告寫下來（同 `skipPaths` 的形狀）
- 護欄：**同一組語料上，兩個執行器的分歧數**——棘輪，只准下降
- UI 誠實標示「這一段在模擬與真實環境行為不同」

> **一個沒有被量的差異，會以「學生的程式在板子上不動」的形式被發現。**

⚠️ 而這一條與 `concepts/模擬的誠實.md` 是**同一條線的兩端**：
那一份管「模擬器不准編數字」，這一條管「模擬器與真實不一致時要說出來」。

## 七、🟢 一個幾乎免費的賣點

同一份真相、兩個執行投影，**而使用者看到的東西講同一種語言（nodeId）**——
所以「先在模擬跑、再燒到真板」是**同一個 UI、同一組斷點、同一個高亮**。
教育場景下這很硬，而它的前提只有一個：**runner 契約從一開始就講 nodeId。**

## 八、🆕 2026-08-31 補：四格能力，來自另一串討論

那串討論（[借鑑那些流程工具](2026-08-31-借鑑那些流程工具.md)、
[過程是一等公民](2026-08-31-過程是一等公民.md)）逼出了 `capabilities` 缺的四格：

| 能力 | 從哪來 | 誰有 |
|---|---|---|
| **`replayable`** | event sourcing——一次執行能不能記成事件、決定性重放 | 我們的直譯器（若 `cin`／`rand` 也是事件）✅／真板子 ❌ |
| **`incremental`** | Grapycal 招牌功能的真身＝**髒節點重算** | ML 後端 ✅／教學直譯器**不需要**（跑 20ms，重跑免費） |
| **`hotFix`** | [狀態遷移](../concepts/狀態遷移.md)（Erlang／CLOS／PyTorch 收斂到同一招） | 我們的 🟡（配對器已存在）／DAP ❌（那是別的行程的碼） |
| `timeModel` **少一個值** | ML 訓練 | `immediate` ／ `ticked` ／ **`long-running`** |

⚠️ **`long-running` ≠ `ticked`**：ticked 要一個虛擬時鐘（硬體模擬）；long-running 沒有時鐘，
它要的是**進度、可取消、中間結果**。混成一格，硬體與 ML 會互相扭曲對方的設計。

### 🔴 而 `replayable` 不只是資訊欄位——它決定產出能不能被當成事實引用

§六 說「兩個執行器不一致 → 量它、棘輪、UI 誠實標示」。那在「模擬 vs 真板」上行得通，
**因為真板是 oracle**。

**而 ML 沒有 oracle**——訓練本來就不決定性（隨機初始化、非決定性 kernel、浮點累加順序）。
所以那條棘輪在 ML runner 上量不出東西，它需要不同的處置：

> 不是「兩個執行器要一致」，而是「**這個 runner 宣告自己不可重現**，
> 所以它的結果不進課程驗收，也不進分歧棘輪」。

### 🟢 而這推翻了另一串討論裡的一句話

那串裡曾判斷「不要把 ML 塞進 Semorphe，那是另一個產品」。**在這份的框架下那是錯的**：

```
當時的假設  執行是內建的 ⟹ 換執行體制 ＝ 換產品
實際的形狀  執行是一個埠 ⟹ 換執行體制 ＝ 換一個 runner ＋ 誠實宣告能力
```

**分叉線不在產品層，在能力宣告層。** 而教學那條一個字都不用改——
我們的直譯器宣告的是相反的那組能力。

### 對「第一個外接 runner 選誰」的補充判準

> **挑那個能逼出最多格能力宣告的。**

- **Pyodide**：`steppable: false`、per-runner skips 全部要重算 → 逼出 §五B
- **DAP**：`variables: 'pull'` → 逼出契約裡唯一還沒定義的那一格
- **ML 後端**：逼出 `incremental` ＋ `long-running` ＋ `replayable: false` → 最多，也最遠

**建議 Pyodide 先**（證明「同一棵樹、兩個執行器」成立，且不需要新執行模型），
⚠️ **而設計 `capabilities` 時要照 ML 那組留欄位**——契約一旦有兩個實作就改不動了。

## 九、🆕 2026-08-31 量出來：這份契約的第一個消費者是「執行中改結構」

[借鑑那些流程工具](2026-08-31-借鑑那些流程工具.md) 想要的 Grapycal 式「執行中改圖」，
量完之後**不是一個修法，是這份契約的第一個真實需求**。

### 三個測量

```
src/interpreter/interpreter.ts   693 行，`yield` 出現 0 次 → async 遞迴
  ⟹ 執行位置住在 JS 呼叫堆疊：不可檢視、不可序列化、不可遷移
  ⚠️ async/await 給的是「暫停」，不是「把位置當成值拿出來」

232 / 309  個 execute.ts 直接讀 node.children → 沒有收口
  ⟹「我在跑哪一版結構」這個問題現在問不出來

SemanticNode { id: string, ... }   ← 唯一的好消息：遷移的 key 在
```

### 🟢 而這推出的結論，正好是這份草稿的形狀

> **「執行中改結構」不是把現有直譯器改造成可中途改**——那是 309 個 executor
> 改簽名，而且改完只換到「可暫停」，位置仍然不能遷移。
> **它是【加第二個執行器】。**

```
執行器 A（現有，async 遞迴）  快、309 顆元件全支援、位置在 JS 堆疊 → 不可中途改
執行器 B（新，顯式狀態機）     慢、先只支援最小子集、位置是【資料】 → 可中途改
```

🟢 B 一旦存在，這些是**白拿**的（全都是「位置是值」的推論，不用另外做）：
單步、斷點、回放、時間軸拖曳、「炸了 → 修 → 從那一步繼續」。

### 四步

```
① ⚠️ 驗 id 的穩定性——這一步不過，後面全部作廢
   程式碼 → 樹 → 程式碼 之後，同一個節點的 id 還是同一個嗎？
   若每次 lift 都重生，PC 遷移就沒有 key，第一件事變成「讓 id 可追溯」

② 執行器 B：最小子集（賦值／if／while／印出，四五顆元件）
   位置 = { nodeId, phase, frames[] }，可序列化
   🟢 護欄：「同一份程式，A 與 B 的輸出必須一致」——第一次跑會紅
   （這正是 §六「兩個執行器不一致時誰是對的」的第一個實例）

③ 換版點 ＋ 遷移：結構改了 → 用 nodeId 比對 → 對得上續跑、對不上停下來問
   ＝ Erlang code_change/3 的形狀 ＝ concepts/狀態遷移.md 已經寫好的規則
   （core/flow/layout-key.ts 做過一次同形狀的事——是先例，不是巧合）

④ A 一行都不動，永遠留著；契約就是 A 與 B 都得滿足的那張介面
```

### 🔴 而 Grapycal 好做、這裡難做，理由是結構性的不是偶然的

```
Grapycal   dataflow——沒有單一 PC，改一條邊只是改「下一則訊息去哪」
Semorphe   控制流樹走訪——有單一 PC，而它在 JS 呼叫堆疊裡
```

**「執行中改圖」在資料流裡便宜、在控制流裡貴。** 之後引用 Grapycal 時要連這句一起引，
否則會把它的成本估成它那邊的成本。

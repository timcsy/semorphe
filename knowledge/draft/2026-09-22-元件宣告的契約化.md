## 一、元件宣告今天已經是契約，只是三個欄位的名字沒統一

把 `component.json` 的欄位逐個問「它其實是哪一種契約」：

| 今天的欄位 | 它其實是 |
|---|---|
| `positions: ["statement","expression"]` | **pre**（脈絡：我能出現在哪） |
| `slots.allowed` / `min` / `max` | **pre**（子節點：誰能放進來、幾個） |
| `ports.accepts` | **pre**（邊：我能參與哪些關係） |
| `params.kind` / `values` / `required` | **pre**（參數）＝ refinement type |
| `requires: ["<vector>"]` | **pre**（程式全域：這個標頭要在） |
| `consumed-by-parent` | **pre**（脈絡）——而它今天寫成「**跳過的理由**」 |
| `role` | 🔴 **post**（generate 產出什麼）——文件裡就叫「**產生器契約**」 |
| `law: shared \| exclusive` | **invariant** |
| `relation: 組合` 的「恰好一個父、刪父連子一起死」 | **invariant**（結構） |

```
pre         擠滿了，六種
post        🔴 只有一個，而且它已經叫「契約」
invariant   兩條，而它們的定義寫在 .md 的散文裡
```

> **元件系統今天把「什麼時候可以用我」講得非常細，
> 把「我保證什麼」講得幾乎沒有。**

而這個不對稱正好對得上完備性護欄的兩個病灶：post 只驗「產出非空」、121 格判不出來。

🔴 **所以要改的不是用詞，是那三欄的分佈。**

## 二、🔴 閉集 vs 謂詞：本檔最重要的取捨

使用者的原始想法是把 `shared` 這類用詞換成形式化的原語言。方向對，而**不能換成自由謂詞**。

### 列舉值有剪枝力，謂詞沒有

`law` 今天恰好兩個值。正因為它是閉集，填五槽的時候才量得出
「**UI 是三域中唯一沒有守恆關係的**」——而那句話解釋了為什麼 UI 最好教、硬體最難教。

**那個觀察來自列舉，不來自謂詞。** 換成 `invariant: <任意謂詞>` 之後：

```
沒有人知道總共有幾種律
跨域那張地圖（三域 × 三關係）畫不出來
「加一種律」從顯式決定變成一次 commit
```

⚠️ 這條與 `concepts/元件.md` 的既有規則同一條：**各域自己的是封閉詞彙表，而加字是顯式動作。**

### 🟢 兩者可以同時要：具名不變量（named invariant）

列舉留著，而每個值的定義從散文換成一條寫得出來的謂詞：

```
今天   law: "shared"   而 shared 的意思在 concepts/元件.md 的一段文字裡
改後   law: "shared"   而 shared 指向一條寫在表裡的不變量
```

```
exclusive   ∀t. |{ holders(r, t) }| ≤ 1
shared      Σ through(e) = 0  ∧  ∀ e,e′. across(e) = across(e′)     （e ∈ edges(n)）
```

寫出來之後有一件事自己浮現：**它們不是同一種東西。**

```
exclusive   持有者的基數限制    → 型別檢查得掉（線性【邏輯】）
shared      網上的方程組        → 要求解器（線性【代數】）
```

🔴 **兩個「線性」不是同一個。** 而它們今天並列在同一個 `law` 欄位裡，
消化它們的機器卻不同。這是具名不變量第一個會逼出來的東西。

🟢 而這正好兌現 [history/232](../history/232-一個好名字會讓它的判準變成同義反覆.md)
那句話——**具名不變量讓「名字＝判準」字面成立**。

### ⚠️ 同一條規則對 `pre` 也成立，而這裡更危險

`positions` / `slots.allowed` / `ports.accepts` 今天都是閉集，而**讀它們的不只一個消費者**：

```
positions      渲染器（挑形態）· 第 126 條護欄
slots.allowed  工具箱（能不能拖進去）· 積木定義產生器
accepts        連接層（能不能連）
params.values  下拉選單的選項來源
```

**換成自由謂詞，只有求解器讀得懂。** 工具箱沒辦法從一條全稱命題生出一個下拉選單。

🟢 所以要兩層，而規則是既有的**導出，不要並存**：

```
L1  結構化的 pre    閉集、多消費者讀得懂        ← 源，人寫
L2  謂詞形式的 pre   求解器讀得懂               ← 由 L1 導出，不手寫
                   ＋ L1 表達不出來的才手寫（逃生艙）
```

⚠️ 兩層各自手寫就是第三次踩雙重真相，而前兩次的症狀都是**安靜地說了兩句不同的話**。

## 三、守恆有兩個宿主，而第二個不在五槽裡

使用者指出 `shared` 可以由 invariant 處理——對，我原先把「形式化」預設成 QTT 的多重性，
因此得出「換掉硬體那一半」的結論，**那條說窄了**。

而剩下一個真的殘差，不是表達力問題，是**宿主問題**：

```
守恆的【律】   「我這幾支腳的電流加起來是零」      局部  → ✅ 元件的 invariant 放得下
守恆的【網】   「這條 net 沒有多重驅動／沒有浮接」   全域  → ❌ 不屬於任何一顆元件
```

而這件事專案已經獨立撞到兩次：

> 「per-元件的膠囊**裝不下全樹約束**」——borrow check 與電氣 DRC 是同一台機器
> 「**硬體診斷掛在邊上**」——「LED 的陽極接到 GND」不屬於 LED 也不屬於 GND

| | 住哪 | 誰消掉它 |
|---|---|---|
| 元件的 invariant | 五槽裡 | 型別檢查／局部推理 |
| **組裝的 invariant** | 🔴 **組裝**（真實，但不屬於任何一顆元件） | **求解器**，不是型別檢查器 |

⚠️ `shared` 連分離邏輯都不對口：分離邏輯處理**互斥**的資源（`*` 要求 disjoint），
而 `shared` 的定義逐字是「**多方可同時持有同一份**」。它既不要線性，也不要分離。

🟢 **組裝**本來就是五槽沒有的那一格，而契約聚合與 blame assignment 也住這裡。

## 四、五路是 DbC 的骨架，而契約的內容從來沒寫進去

DbC 有兩層，對照一下：

| DbC | 五路今天有什麼 |
|---|---|
| **五個 routine** | 🟢 完整 |
| 每一路的 **post** | 🟡 只有「產出非空、非佔位、非 raw_code」——最弱的那種 post |
| 每一路的 **pre** | ❌ 沒有（見 §五） |
| **class invariant** | ❌ 護欄裡不存在。`①→②→③→④→① ≡ identity` 只寫在散文裡 |

> **五路是一份 DbC 規格的 routine 清單，而契約的內容從來沒有寫進去。
> 「沒有最終標準」的感覺來自這裡，不是來自那五個名字。**

### 名字本身：逐個過專案的判準，只有一個弱

判準是 2026-09-13 立的那條（殺掉 `balance` 的）：**廣泛使用，而且它的常見意思就是你要的那個意思**。

| 名字 | | |
|---|---|---|
| `lift` | 🟢 反編譯／二進位分析的標準詞（machine code → IR 就叫 lifting），方向與意思都對 | 留 |
| `generate` | 🟢 | 留 |
| `render` | 🟢 | 留 |
| `execute` | 🟢 | 留 |
| `extract` | 🟡 **唯一弱的**：常見意思是「抽出來」，這裡要的是「render 的逆」 | 留，記理由 |

⚠️ `extract` 沒有現成好名字是有結構性原因的：**UI 領域是單向的，render 沒有逆。**
那個逆的標準名字在雙向轉換（BX）領域，是 `put`——而 `put` 更泛（put 什麼？放到哪？），
換過去是拿一個準確的名字去換一個泛用的。**淨損。**

🟢 **而改名的成本其實很低**：路徑名沒有進存檔，依 `concepts/元件.md` 的 bound／free 判準
它是 **bound 變數，α 轉換免費**（不像 componentId）。所以「留著」是**因為不值得**，
不是因為改不動。

### 🔴 真正該引進標準用詞的是定律那一層，因為它今天是空的

五路不是五個獨立操作，是**兩對雙向轉換 ＋ 一個觀察**：

```
真實（語義樹） ── generate ──▶ 程式碼        真實 → 投影 ＝ get
              ◀── lift ─────                投影 → 真實 ＝ put

              ── render ───▶ 積木
              ◀── extract ──

              ── execute ──▶ 行為           單向，有外部 oracle
```

lens 有三條定律，而它們正好是「最終標準」該長的樣子：

| lens 定律 | 意思 | Semorphe 今天叫什麼 |
|---|---|---|
| **GetPut** | 拿出來原樣放回去，真實不變 | 「語義的不動點」（面向②）·「走一趟積木回來」（面向④） |
| **PutGet** | 放進去再拿出來，拿到你放的那個 | P1 投影定理「來回轉換無損」 |
| **PutPut** | 連改兩次 ＝ 只做後面那次 | 🔴 **沒有名字，也沒有人檢查** |

第五路不是 lens，它的標準名是 **refinement／觀察等價**——而這個詞這個 repo
**已經在用了**（`concepts/等價與觀察集.md`）。

#### PutPut 不是「漏了一條」，是「從來沒有表態」

PutPut 對**保存資訊**的 lens 常常不成立，而 Semorphe 的 lift 正是保存資訊的
（`raw_code` 殘差、`annotations`、註解）。所以它很可能**應該明確地不要**。

> **一組標準的定律，真正的回報不是多幾條要通過的測試
> ——是它會告訴你哪幾條你決定過、哪幾條你還沒表態。**

## 五、undecidable 121 是「缺 precondition 的見證輸入」

判成 `undecidable` 的實際理由（`audit-completeness.test.ts`）逐字有四種：

```
① generate 由父概念消費，合成流程產不出程式碼——lift 沒有輸入可測
② 量測用的是 C++ 解析器——非 C++ 的元件在這裡碰不到
③ 合成樣本不是合法的獨立程式（此概念需要父節點才成立）
④ 概念宣告了 consumed-by-parent——它只在父節點裡出現，單獨量不到
```

**①③④ 是同一件事**：護欄用 `synthMinimalNode` 自己捏一份最小樣本，
而捏出來的東西不滿足那顆元件成立的條件（`case 1:` 脫離 switch、類別成員脫離類別）。

**那個「成立的條件」就是 precondition，而缺的是滿足它的見證輸入。**

🔴 而宣告機制**已經存在**：護欄裡那行

```ts
if (skipReason(id, 'execute') === 'consumed-by-parent') → undecidable
```

`consumed-by-parent` 就是一條前置條件，只是它被寫成「跳過的理由」而不是「成立的條件」：

```
跳過的理由        →  從分母移出去    →  undecidable（判不出來）
成立的條件＋見證   →  用那份見證去量  →  implemented 或 shell（判得出來）
```

> **一句「這個東西只在父節點裡出現」，當成豁免就讓量測閉嘴，
> 當成前置條件就讓量測有輸入。**

⚠️ ② 不同族——量測工具用錯解析器（Python 元件送去給 C++ 文法），契約救不了它，
要逐語言解析器。所以 121 不會歸零。

## 六、形式化語言能接管哪幾格

使用者問過「能不能用契約式設計和形式化驗證的語言取代從 ArduinoCAD 整理過來的那一套」。逐格驗：

| 槽／關係 | 宿主 | 形式機制 |
|---|---|---|
| 身分 | JSON | — （形式化對「叫什麼」沒有話說） |
| 形態 | JSON | — （🔴 結構上沒有外部 oracle） |
| 參數 | JSON 宣告形狀 ＋ 謂詞 | refinement type |
| 接點・組合 | JSON | 歸納結構／擁有權 |
| 接點・資訊 | 形式核 | 多重性 `ω` |
| 接點・守恆 `exclusive` | 形式核 | 多重性 `1` |
| 接點・守恆 `shared` | 形式核 | **invariant ＋ 求解器**（§二、§三） |
| 行為 | 形式核 | Hoare → Guarded |
| **組裝** | 🔴 新的一格 | 全網 invariant ＋ 契約聚合 |

🔴 **結論：五槽不是要被形式化語言取代的東西——它是那張模式圖本身。**

三值 `relation` 在這張表裡沒有被吸收掉，**它變成選哪一列的那個鍵**。

⚠️ 而這也是使用者自己筆記裡 MTT 的結論（「不要大一統空間，要微型宇宙網絡」）
與本 repo「**合併是錯的目標**」的同一條線——兩邊各自到達，而它們說的是同一件事。

### ⚠️ 表達力越強，剪枝力越弱

五槽的價值在它**排除**什麼（`concepts/元件.md` 開宗明義：填不出就不是元件）。
而依值型別論什麼都編碼得進去——那是它作為驗證工具的長處，
**也是它作為本體論的致命傷：一個能表達一切的詞彙，對「這不是元件」說不出口。**

## 七、宿主與分工

### JSON 外殼 ＋ 形式核那一刀，與「真實／投影」不是同一刀

```
專案的切法    真實（身分・接點・參數）  ｜  投影（形態・行為）
使用者的切法   JSON（身分・形態・元資料） ｜  形式核（邏輯）
                     ↑                        ↑
               接點與參數落在哪？——兩邊都要
```

- JSON 那側要它們：登錄表、工具箱、渲染器今天就在讀
- 形式核那側要它們：契約的謂詞要指得到那些接點與參數

🔴 **這正是本 repo 的頭號架構陷阱**（雙重真相）。處方同 §二：**導出，不要並存**。

⚠️ **那條護欄要先於拆分存在，不是之後補**——這個 repo 的疤都是同一個形狀：
一條沒有人檢查的縫不會出聲。（最近一次：`role: expression` 被 `buildFormSets`
摺進 `container_kind`，第 219 刀才修掉。）

### Lean 4 與 cella 驗的不是同一層

| | Lean 4 | cella |
|---|---|---|
| 在五槽裡的位置 | **外部 oracle**——像 `g++`，**不在登錄表裡** | **第 N 種投影**——在登錄表裡 |
| 驗什麼 | 投影管線的定律（**後設層**） | 學生程式的資源／時序性質（**對象層**） |
| 風險 | 語義樹編碼進 Lean，**那層對映會漂** | **兩個未完成的系統互相依賴** |

🟢 **而「證明義務是第六條投影」這句話白拿三樣東西**：五路變六路（缺的護欄叫得出來）、
可逆性分級 R0–R4 直接適用（證明義務是 R4）、
以及第 126 條護欄那個形狀可複製（「宣告說得出的，證明就要做得出來」）。

⚠️ Guarded TT 的第一個消費者**已經在產品裡**——Arduino 那一軌的
`10-不要用delay`（`millis()` vs `delay()` 是標準的時序性質）。不是未來的硬體。

### 🔴 第一個值得證的東西不是學生的程式

是**投影管線本身**。那是關於**我們的程式**的全稱命題，而它今天全部靠取樣：

| 要證的 | 今天怎麼量 |
|---|---|
| 語義的不動點 | 218 支語料取樣（而 144 支轉一圈回來不是同一棵樹） |
| 行為等價 `execute ≡ g++` | 91 支 |
| 走一趟積木回來 | 第 118 條護欄，53 條形狀 |

**證明失敗比證明成功更有用**：卡住的位置就是缺的那條不變量，而那正是 CEGIR。

## 八、階梯：契約怎麼從「寫了」走到「證了」

```
L0  沒宣告            →  「不可驗證」，計入分母
L1  宣告了，執行期檢查   →  直譯器跑到就檢查，違反 = 一條診斷
L2  宣告了，取樣驗證     →  語料 ＋ fuzz ＋ g++ 對答案（🟢 今天就有）
L3  宣告了，證明過       →  出一張證書
```

**這道階梯同時是解耦器**：形式核還沒好，契約停在 L1／L2；好了就升到 L3，
**宣告一個字都不用改**。於是 cella 的進度不會變成 Semorphe 的阻斷。

兩條不可合併，都是既有護欄的形狀：

```
L0（沒寫）    ≠  L1 違反了    ← 第三十二條護欄：「還不會檢查」≠「錯了」
契約違反      ≠  拒絕組合     ← 使用者自己那條：錯了要顯示，不是不給組合
```

🔴 **證明不進存檔。** 語義樹與契約是真實、要存；證明是導出物，
用 `engineHash` 那個已經在跑的機制——契約變了或驗證器版本變了，證書就過期。

> ⚠️ 而第 218／219 刀那個教訓在這裡會再出現一次：
> **一個修好了的缺陷，在它的產物重產之前，讀數上與沒修一模一樣。**

## 九、邊界：形式化到不了的地方

### 🔴 形態那一維結構上沒有 oracle

`render` 的 post 寫得出「產出的 state 載得進工作區」（＝面向③），
**寫不出「這顆積木的標籤沒有說謊」**。

這不是還沒建，是結構性的（`concepts/等價與觀察集.md` 已定案）。
而那正是 stack／queue 的 push 標籤說謊那次——**十八條護欄一條都不叫，學生第一眼看出來**。

⟹ 契約化之後，**render 會是唯一一路，它的 post 蓋不住它的真實風險**。

### ⚠️ 空洞為真的契約 ＝ 這個 repo 踩過五次的假綠

前置條件永遠不可滿足 ⟹ 後置條件恆真。這是形式化版本的假綠，
而形狀與今年九月那五次逐字相同（最近一次：整個 `main` 降級成 `raw_code`，
於是「沒有註解積木」與「註解在行末」同時為真）。

🟢 處方照抄：**每一條 pre 都要附一個滿足它的見證輸入**——
而那同時就是 §五 消掉 undecidable 的那個東西。**一件事付兩次帳。**

> **一份「全部證明通過」的報告，先問那些命題裡有幾條是空洞為真的。**

### 累積性那一欄，契約（布林謂詞）蓋不住

`concepts/等價與觀察集.md` §四 已經分好：

| | 結構性的差別 | 累積性的差別 |
|---|---|---|
| 該用 | 鄰域取樣（fuzz） | **界**（誤差上界、傳播分析） |

而文件註明「硬體／數位孿生進來時**第一個撐不住的就是這裡**」。
右欄的契約不是 `x > 0`，是 `|err| ≤ δ`——使用者說的「連續函數當導航員、
邏輯當守門人」在這一欄才有位置。

## 2026-09-25 與 cella 對接

兩個 session 往返四輪。cella 逐題查了自己的 code 才答，所以下面是**它那側的現況**，
不是它的計畫。

### 一、改掉的六處

**① ⚠️「L3 比 L1 快」不是 cella 給的。** cella 沒有 codegen（執行是 NbE）。
它只能告訴你「這條 precondition 以 usage 0 結清」，**真正省下那段 runtime check
的是 semorphe 的 `generate` 不發那段碼**。資訊在它那、加速在我們這。

**② 🔴「模式」換成「片段」，而結構比本檔 §六 那張表嚴。**
cella 09-24 評估過 MTT，結論是 mode graph 的表達力不需要而代價是全局的，
改走**片段**（每個定義宣告它需要多少型別論，檢查器強制它不越界）。
正確的形狀是**四個在牆內、兩個在牆外**：

```
牆內（片段，而且只准有【包含】關係，成一條鏈）
     struct  ⊆  info(ω)  ⊆  linear(0/1/ω)  ⊆  timed
牆外
     numeric（求解器）      opaque（形態，oracle 是人）
```

🔴 **而本檔原本把兩種 adapter 混成一種了**：

```
片段 → 片段   非包含關係 → 一次真正的 parse     （cella 的「閘門 1」）
牆內 → 牆外   digitalWrite / analogRead        ← 這根本不是型別論操作，是離開形式系統
```

🟢 兩邊獨立推到同一條線：cella 從 `Checked<F>` 的參數化推出「只准包含關係」，
本檔從 adapter 的位置推出「跨模式必經 adapter」。

**③ 🔴 證據等級要記「誰背書」，不只是「到哪一級」。**
cella 今天說 OK 的是 elaborator；第二個獨立 kernel 2026-09-23 才重新接回、
**預設不阻擋**，而且只驗過 stdlib 833 個定義裡的 488 個（遞迴定義全部驗不了）。
所以 `L3` 要拆成 `L3-elab`／`L3-kernel`。

> **一個會說謊的等級欄位，比沒有等級欄位糟。**

**④ 🔴 cella context 是帶雜湊的建置產物，不是每次檢查都建。**
`admit` 的成本隨已收定義數**平方**成長（實測：N=4 是 12 ms、N=68 是 3,048 ms）。
用那個係數外推，349 顆逐次 admit 的總和是立方級、**約 2.6 小時**（粗估，沒量）。

⟹ 它要落進既有機制：像積木對照圖一樣帶雜湊、宣告變了才重產。
⚠️ 而[第 219 刀](../history/281-一個身分可以有兩條形態軸.md)那個教訓會一字不改地再來一次
——context 過期的症狀是**型別檢查驗的是上週的元件庫**。

**⑤ 洞的型別要不要結構化：現在不要。**
cella 的 `HoleInfo` 今天給 `expected_type: String`（pretty-print 過），內部有
`m.ty: Value` 只是沒對外暴露，改起來是小的 API 改動。**而我們回絕了**，理由是
本檔 §二 的規則②：

```
blame 的位置       String 夠了   🟢 今天就能做
給學生的那句話     String 夠了   🟢 今天就能做
投影給求解器       要結構化      ⏸ 第三步才有消費者
```

在手寫十顆之前開需求，就是預約一個沒人讀的欄位——`relation`／`law` 零採用的形狀。

**⑥ L3 的天花板比本檔 §八 假設的低。** cella 的 `linarith` 只做 exact-match
（F207 從 2026-05-01 dormant），`i < n` 這類義務**自動結清的能力很弱**，
多半要手寫證明項。⟹ **範圍／界限那一類契約，規劃時就當 L2 是天花板。**

⚠️ 而本檔 §例一 的 `array_at` 剛好不受影響（它本來就因為「界限看執行期的值」停在 L2）
——**那是巧合不是設計對了**，當時寫的理由和真正的限制不是同一條。

### 二、確認的分界（架構 A）

使用者 09-25 逐字：「讓 cella 負責**形式化驗證語義的部分的投影**」。

```
cella      帶契約的簽章 ＋ 一個項，然後型別檢查        ＝ 第六條投影
semorphe   lift / generate / render / extract / execute 全部留著
L1 的執行期檢查                                      在 semorphe 的直譯器裡
型別層的規範化（NbE、conv）                           在 cella
```

🔴 **拍板它的是一個 oracle 的論證，不是耦合度**：

> `execute` 是五條投影裡**唯一有外部 oracle** 的那一條（`g++`，218 支語料裡
> 91 支逐字比對過輸出）。交出去等於丟掉唯一有參照權威的一路。

而 cella 把它抽成一條普遍判準收進自己的 knowledge：
**把唯一有 oracle 的東西搬到沒有 oracle 的地方，是在製造「沒有東西會因為我錯了而變紅」。**

🟢 **而這一條 09-25 當天就收斂了，是使用者主動更正的**（不是兩個 session 對出來的）。

09-24 他曾說「semorphe 就是形態，其他的之後再說」，而那句與上面那句的差距是
「第六路」vs「只剩 render/extract」。更正的原話：

> 「應該不是 semorphe 就是形態，我那時候太急講太快了，應該是
> **semorphe 負責形態投影，cella 是對應的形式化語義驗證的那個投影**。」

⟹ 兩邊各用**代表性投影**命名分工，而編輯管線（lift／generate／extract／execute）
跟著 semorphe。**A 因此有使用者背書，不再只是「現行架構所蘊含」。**

> **一句話講太快留下的歧義，成本不在那句話本身
> ——在別人已經照它推了兩輪之後。**

🟢 順帶定下的：**形態不乘 Cell**（四顆積木、一顆元件、一顆 Cell）·
**`abstractComponent` 不進 cella**（它是導得出來的，進去會多一條該被導出的命名軸）·
componentId ↔ `CellName = (module, local)` 的對應由我們宣告、不進 cella 的 wire format。

#### 🔴 而 A 有第二個理由，它與 oracle 那條獨立

使用者 09-25 補的：

> 「執行另外處理還有另外一個原因，因為我到時候也有可能要**對接外部執行器**，
> 例如 debugger、實際硬體、等等，我希望**執行器是可插拔的**。」

oracle 那條說的是「不要把有參照權威的東西搬到沒有的地方」。
這一條更根本：**`execute` 根本不是一個東西，它是一個槽。**

```
語義樹 ──execute──▶ 瀏覽器直譯器（逐步播放給學生看）
                 ──▶ g++ 編出來跑（參照後端）
                 ──▶ 外部 debugger
                 ──▶ 實體硬體
```

⟹ **「cella 接手 execute」這句話本來就不是良構的**——cella 最多只能是其中一個後端，
而它不是（NbE 沒有 IO、沒有單步、不面向學生）。**這一條不需要比較耦合度就判得出來。**

🟢 **而它把 `g++` 從特例變成常規**：[等價與觀察集](../concepts/等價與觀察集.md) §七
那張表（軟體：直譯器 vs `g++`／硬體：模擬器 vs 實體板子）**本來就是一張後端表**，
只是當時沒這樣叫它。

⚠️ **今天量到的現況——那條軸不存在：**

```
有的    元件 → 它的 execute 函式        src/interpreter/executor-registry.ts（349 顆各一個）
要的    語義樹 → 哪一個【後端】去跑它    ❌ 只有一個 SemanticInterpreter
呼叫點  src/ui/execution-controller.ts   🟢 產品裡唯一一個
```

`executor-registry.ts` 是**另一條軸**，不是後端軸。好消息是產品的呼叫點只有一個。

#### 🔴 於是 `execute` 的 post 必須是 backend 中立的

不能寫「我們的直譯器怎麼做」，要寫「**任何合格的後端都得產出什麼**」。

而這一條今天**不成立**：探針的判準是「跟 `g++` 比」，那是拿**一個實作**當規格。

接上[契約代數](#四-組裝mode-graph-放錯位置了你要的是契約代數)的 ≼：

```
execute 的 post                ＝ 規格（backend 中立）
直譯器 · g++ · 硬體 · debugger   ＝ 各自是那份規格的一個 refinement
「execute ≡ g++」               ＝ 對其中一個後端做一致性檢查，不是特例
接一個新後端                    ＝ 跑同一套一致性套件
```

這是 WebAssembly spec tests／SQL conformance 的形狀。
🟢 **而它是 vision「讓硬體進來從架構風險變成資料擴充」那句話在執行那一路的版本。**

### 三、🔴 三個實測讀數

**① 語料裡 `new`／`delete`／`malloc` ＝ 0 支**（218 支全掃，只有 7 支有指標語法）。
所以 `linear 1` 那一格**沒有語料地基**——那是競賽／教學語料的性質，不是漏掉。

**② UBSan 的四種行為，實際編出來跑過：**

```
除以零              🟢 開火，指在使用者那一行
VLA 長度 ≤ 0        🟢 開火，指在使用者那一行
陣列越界（VLA）      🟢 開火，指在使用者那一行
空容器取頭尾        ⚠️ 開火，而【位置指到 libc++ 內部】（deque:1519）
未初始化讀取        🔴 完全沉默
```

**③ 後兩行是這批探針最重要的兩格，而理由不同：**

- **空容器**：oracle 說「有 UB」而**位置沒有用**。🔴 **且機器相依**——本機 libc++、
  CI libstdc++。這個坑踩過三次（09-17 `<set>`、09-18 `<queue>`／`<tuple>`、
  09-19 NaN 的正負號），教訓是**拿參照編譯器當權威前，先問那一段有沒有被標準定死**。
  空容器 `front()` 是 UB，標準沒定死任何症狀 ⟹ 只取「有沒有開火」，而且要記哪一台。
- **未初始化**：oracle **結構上看不見**（那要 MSan）。它會落進「契約擋了而 UBSan 沒叫」
  那一欄，而 🔴 **那一欄混著兩種東西**：

```
真的太嚴              →  該把契約放寬
真的錯了而 oracle 瞎了  →  🔴 放寬就是修錯方向
```

> **一個單向的 oracle（只證實、不否證），它的沉默要分成兩種讀法
> ——而把兩種併在一欄，會讓「修對了」與「把偵測器關掉」長得一模一樣。**

### 五、🔴 三個「自洽而錯」是同一個形狀

使用者 09-25 對形式化的效力下了一個界：

> 「驗證通過至少代表執行大部分時候是對的（**如果我們的驗證有跟意圖對齊的話**，
> 如果沒有對齊就不能保證這形式化規格契約的效力，**但這不是系統的問題**）」

前半對，而且形式系統**結構上**到不了那裡——那是 validation 不是 verification
（本檔 §起點 那批想法的第一條就是這個）。

而要加的那一格是：

> **保證對齊不是系統的責任，但「對齊壞了的時候有沒有東西會變紅」是。**

把這一串對話裡各自擔心的三件事並排，它們是同一個形狀：

|---|---|---|

### 七、🔴 第二輪讀數：洞的型別是這整份文件的第一個讀數（2026-09-25）

#### 基線

#### 🟢 它退回去驗證了一個當時沒有證據的決定

§六（改掉的六處）之⑤決定**不要**把 `expected_type` 從 `String` 改成結構化的 `Term`，
理由是本檔 §二的規則②（先有消費者）。當時那是**判斷**。

現在 `LtB u n` 這個字串對指名的那兩個消費者**已經夠了**（blame 的位置、
給學生的那句話），而第三個消費者（求解器）仍然不存在。

> **一個「先不要」的決定，最好的收場不是後來證明它對，
> 是後來拿到了原本沒有的讀數，而那個讀數說它對。**

#### 🔴 「不同的東西印成同一個樣子」——與 `nan`/`-nan` 配成一對

洞壞在兩層，而第二層是：型別印成 `LtB ?13 ?11`，cella 診斷成「未解的
metavariable」並加了 zonk，**沒用**——`?N` 是 pretty printer 對
**查不到名字的變數層級**的 fallback，和 meta 的 `?{id}` 剛好長得一樣。

把它和我們自己那條疤並排：

| | 實例 | 代價 |
|---|---|---|
| 不同的東西印成同一個樣子 | `?N`（未知層級）vs `?{id}`（meta） | 一次沒用的修法 |
| 同一個東西印成不同樣子 | `nan`（libc++）vs `-nan`（libstdc++） | CI 紅了三次合併 |

> **兩條的處方是同一條：不要拿印出來的字串當判準。**

`nan` 那次的修法是把判準換成不靠列印的性質（NaN 的正負號未指定 ⟹ 判準改成
「那個值不等於它自己」，`c != c` 兩台機器都印 `1`）。
套到 meta：**問「它有沒有 solution」而不是「它印成什麼」**。

cella 這一輪還把 `_`（推導佔位）也標記成使用者的洞——**而解析器早就分開了**
（`_` 解不出要報錯、`?` 才是洞）。它「修」了沒壞的那個，弄紅兩個測試，已還原。

```
第一次   報告裡有量測工具的缺陷    探針沒註冊渲染堆疊 → 回報八顆全畫不出來
```

#### 🔴 ⑤ 不是是非題：同一支 C++，兩種編碼落在不同格

```
lift 產出布林測試     match ltNat u n with | true => arrayAt n A u ?h   → 洞出現
lift 產出判定程序     match decLt u n with | yes p => arrayAt n A u p   → 無洞，p 就是證明
```

⟹ **形式核不需要流敏感。需要的是 `lift` 產出判定程序。**

本檔 §三 引用的預測（「全樹流敏感約束裝不進 per-元件的契約」）**沒有被推翻，但不適用**
——不必讓檢查器讀懂控制流，只要讓 `if` 的條件本身是一個判定，證明就從 `yes` 分支掉出來。

##### 而做法不是「讓 lift 認出守衛」，是換一顆元件的 postcondition

cella 提的代價是「`lift` 要知道這個 `if` 的條件對應哪一條 precondition」，而那會脆弱。
可以繞掉：

```
今天    cpp:compare 的 post ＝ 回傳 bool
改後    cpp:compare 的 post ＝ 回傳 Dec (LtB a b)

規則    if 的條件的 post 是 Dec P  ⟹  then 分支在【多一個 p : P】的脈絡裡展開
```

`cpp:if_else` 今天已經有 condition／then／else 三個槽，**這條規則完全是局部的**
——不看流、不走樹、不比對語法。

> **需求從檢查器移到 lift，而移過來的不是一個脆弱的比對，
> 是一顆既有元件的 postcondition 換一個回傳型別。**

##### 於是邊界講得出來，而不是「不夠乖就壞掉」

| 守衛的形狀 | 結果 |
|---|---|
| 🟢 就是那個比較 | `if (u < n) A[u]` → `p : LtB u n` 直接掉進 then |
| 🟢 合取 | `if (0<=u && u<n)` → Dec 的合取還是 Dec |
| 🟡 比要的更強 | `if (u < n-1)` → 要一次弱化，是**證明義務**不是猜測 |
| 🔴 存進了變數 | `bool ok = u<n; if(ok)` → `Bool` **在指派那一步就丟了證明** |
| 🔴 是另一個量 | `if (u < m)` 而界是 `n` → 本來就不該過 |

第四行才是真的需要非局部推理的那一格，而它的成因講得出來（`bool` 丟掉了證明），
救法也講得出來（讓那個變數的型別自己帶判定），而那是**型別推斷**不是流敏感分析。

#### 兩條可以直接用的

**① `@[irreducible]` 決定 blame 讀到什麼**

```
def（透明）           → ltNat u n ≡ true      學生看到【實作】
@[irreducible] def    → LtB2 u n              學生看到【契約的名字】
```

⟹ 規格慣例：**契約謂詞一律 `@[irreducible]`**，實作細節不准洩漏到 blame 裡。
而它跟「見證要給人讀」是同一條線的兩端：見證說「這個契約是什麼意思」、
契約名說「你少了哪一個」、**實作兩邊都不該看到**。

**② 常數那道天花板不存在**：`LtB 1 3` 由 `refl` **定義性結清**，
`arrayAt 3 A 1 refl` 直接過。常數不用手寫證明，也用不到 `linarith`。

**③ implicit 的隱藏（§七 那個 (a)）：不值得做。** 六支裡**零支**的洞帶 implicit 引數
——照判準，等有一支真的被咬到再說。

#### 🟢 而 lambda 那個形狀，cella 量了：它也涵蓋，成本全在我們這側

```

match inB x y with | yes p => gridAt n m g x y p     🟢 無洞

對照：同一個守衛回傳 Bool
match inB x y with | true => gridAt n m g x y ?h     🔴 洞 = InB x y n m
```

`Dec P` 是一般的歸納族，使用者定義的函式回傳它不需要特殊處理
——「元件的 post 回傳 Dec」那條規則**套在 lambda 上跟套在 `cpp:compare` 上是同一件事**。

⟹ 我判斷的「不免費」在形式核那側**不成立**。剩下的成本全在
`cpp:lambda` 的 post 表達力，那在我們這側。

🟢 **而那個對照順帶證了一件先前沒有獨立證據的事：洞不是亂出現的。**
同一個結構、只換回傳型別，一個有洞一個沒有。
——這是當初堅持要兩支第四格對照組的那個理由的加強版。

⟹ 涵蓋率從 86% 推到約 **96%**（86% ＋ 3% 誤報 ＋ lambda 那 3 支）。

#### 🔴 而「分類的名字對了，歸屬錯了」與 `?13` 是同一個形狀

cella 的觀察：看到「11 支條件是光禿禿的變數」時，第一反應會是
「這就是第四格，需要非局部推理」。**去看了才知道是 `yn`／`yes`／`is_p` 這種答案旗標。**

```
?13         看起來像 metavariable，其實是【沒名字的變數層級】   → 加了沒用的 zonk
if (yn)     看起來像【存起來的界限檢查】，其實是答案旗標        → 差點判成需要流敏感
```

> **兩個不同的東西長得一樣，而讀的是形狀不是來源。**

#### 五次那張表本身是一條讀數

**五次裡沒有一次是產品的缺陷。** 這個比例在說：兩邊目前的瓶頸都不在**被量的東西**上，
在**量的方式**上。

---

## 🔴 量測階段到此結束，而結論是可以排程的

使用者 09-25 定的順序是「先等十顆的讀數再排程」。讀數齊了：

```
十顆定義載得進          10 / 10
洞的機制                 7 / 7
六支語料的假綠           0          ← 編碼沒有漏契約
守衛形狀的涵蓋率         ~96%       ← 判定式這條路走得通
形式核需要新機制嗎        ❌ 不需要  ← 成本全在 semorphe 側
```

**於是排程要決定的只剩一件事：要不要動 `cpp:compare`（與 `cpp:lambda`）的 postcondition。**

而它的代價與收益都量過了：

```
代價   一顆（或兩顆）既有元件的 post 換回傳型別；if 多一條局部規則
收益   語料裡 ~96% 的守衛，證明會自己從 yes 分支掉出來
       ⟹ 正確的程式【不會】滿是洞，而那是這套東西可不可用的分水嶺
```

⚠️ **而這一節刻意不寫「所以下一刀是什麼」**——那是使用者的決定，
本檔的體例是不寫完成條件。

## 尚未表態的

- **PutPut 要不要**（§四）。傾向「明確地不要」，而沒有論證過。
- **`extract` 留不留**（§四）。目前判「留，記理由」，而理由是「不值得」不是「它對」。
- **形態那一維要不要有【人的 oracle】的機制**（§九）。今天是零——
  標籤說謊只能靠使用者看到。而它與 `認知鷹架`／`漸進揭露` 可能有關，沒查。
- **契約要不要進存檔**（§八 只說了證明不進）。契約是真實，照理要進，
  而它一旦進存檔就變成自由變數——**改一條 pre 就要遷移表**。沒想清楚。
- **三張登錄表那一列**（`concepts/元件.md` 待拍板）與本檔的 L1／L2 兩層有沒有關係。沒對過。

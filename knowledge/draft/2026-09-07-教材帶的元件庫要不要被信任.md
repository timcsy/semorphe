# 教材帶的元件庫，要不要被信任

> 日期：2026-09-07（從 [[元件套件管理]] 反流出來——那一份的 roadmap 項目
> 2026-09-06 三個驗收全清，於是它退場，而**這一題還開著**）
> 狀態：**待人拍板**——它不是一個技術選擇，是一個關於「誰承擔」的決定。
> 怎麼冒出來的：使用者 2026-08-27：「**教材可能會搭配自己的擴充元件庫**」。

## 一、🔴 它是一個新的消費者，而信任模型完全不同

```
開發者裝套件          他讀得懂那份程式碼，他自己承擔
老師發連結給小學生     小學生【分辨不出】那個元件庫是誰寫的
```

而元件帶的是**會跑的東西**（抬升策略、產生器、`execute.ts`）：

```
教材的文字錯了      學生看到錯的說明
教材的元件庫壞了    學生的編輯器行為被改寫，而他分辨不出來
```

> **「教材帶的元件」與「別人寫的元件」在系統看來是同一種東西
> ——差別只在誰推薦你裝它。**

## 二、🟢 而機制不必另做一套

`@someone:*` 的第三方 scope **就是**教材要的那個
（2026-09-06 驗過：身分、登錄、抽象元件三層本來就成立，一行產品程式碼都沒改）。

⚠️ **所以這一題不是「怎麼做」，是「要不要放行、放行到什麼程度」。**

## 三、三個選項，而它們的成本落在不同的人身上

| | 誰承擔 | 代價 |
|---|---|---|
| **預設信任 ＋ 事後封鎖** | 我們（要有人在看） | MakeCode 的模型，逐字：「unless they are banned, packages can be loaded without approval by providing an exact URL」——⚠️ 那是一個**有團隊**的模型 |
| **白名單** | 我們（要有人審） | 生態系長不起來，而那與 P3 開放擴充牴觸 |
| **只准資料不准程式** | 教材作者（表達力受限） | 🟢 唯一一個**不需要有人在看**的；⚠️ 而「只准資料」在這個系統裡很難劃線——`liftStrategy` 是資料還是程式？ |

🔴 **而現實是「一個人維護」**——那讓前兩個選項的成本不是理論上的。

## 四、⚠️ 待決（要人拍板）

1. **選哪一個**——或第四種
2. 如果是「只准資料」：**線畫在哪**（宣告式 lift pattern 算資料嗎？）
3. 教材與一般套件要不要**分開的信任等級**——⚠️ 上面那句「系統看來是同一種東西」
   說的是它們**不該**分，而那句話本身要不要被推翻

## 五、而那一份 draft 留下的其餘未決（同樣要人拍板）

1. **套件的邊界怎麼定**——`cpp-core`／`cpp-stl` 這種拆法要不要現在就做，
   還是等有人抱怨載入太慢
2. **依賴要不要有版本範圍**（semver range），還是釘死
3. **轉換規範自己是不是一個套件**——`@someone` 可以發佈「C++ ↔ Python 的對應」嗎
4. **相容性檢查跑在哪**——發佈時、安裝時、還是載入時

⚠️ 這四條的共同點：**它們都要等「有第二個人真的在寫套件」才問得出答案**。
🔴 而在那之前它們**不該被猜**——猜出來的答案會變成一個沒有人驗證過的機制。

> **一個「開放生態系該怎麼管」的決定，
> 在生態系裡只有一個人的時候，量到的是那個人的偏好。**

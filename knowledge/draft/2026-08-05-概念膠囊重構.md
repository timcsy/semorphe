# 概念膠囊重構（按概念聚合 IR 周邊機器）

> 日期：2026-08-05
> 怎麼冒出來的：一場「要不要為 Semorphe 制定新 IR」的討論。使用者原想用自寫的 Rust Cubical TT／無型別 λ-calculus 當通用 IR，評估後否決（見 [墓碑目錄](../history/014-墓碑目錄.md)），但過程中診斷出**真正該重構的不是 IR，是 IR 外圍的概念機器**。

## 一句話

**語義樹（`SemanticNode`）本身是乾淨、穩定的、不要動；碎的是包在它外面的「四路完備性機器」——按機制組織、多套平行機制、雙重真相。** 重構的對象是後者。

## 問題：碎裂是實測的（2026-08-05 審計快照）

以 `cpp_string_at`（最規矩的 lang-library 概念）為準：一個概念的實作散在 **~13 個原始檔、~10 個目錄**（含測試那次 commit 動 16 檔）。四路完備性由 **~8 個引擎**分攤。沒有單一「在這裡新增概念」的位置——同一概念的欄位名、code template、i18n 標籤各自在 2 個以上的檔手動同步。

> 數字是時間點快照，會漂移；重點是**結構性成因**，不是精確數值。

具體碎裂源（每條都對應一種病灶）：

1. **按機制分檔,不是按概念** —— 所有 lift 堆一起、所有 generate 堆一起,於是任何單一概念必然被攤散。這是根因。
2. **lift 有四套平行機制** —— ①`lift-patterns.json` 宣告式 ②`core/lifters/*.ts` 手寫 per-node ③`lifters/io.ts` 的 `METHOD_TO_CONCEPT` 呼叫分派表 ④`core/lifters/strategies.ts` 具名 strategy。哪個語法走哪套,由註冊順序決優先權。
3. **`std/{module}/` 的就近聚合是假象** —— 模組資料夾都有 `lifters.ts`,但幾乎全是空 stub,真正的 lift 邏輯逃逸到兩層外的 `core/lifters/` 和 `lifters/io.ts`。且存在兩個 lifter 目錄。
4. **generate 兩個引擎、無規則決定用哪個** —— `cpp_string_at` 的 `generators.ts` 回傳 `${obj}[${index}]`,blocks.json 又寫 `codeTemplate.pattern`,兩邊都填。（此病灶的原則已在墓碑「codeTemplate 與 generator 並存」定為互斥——但 lift/generate 尚未貫徹。）
5. **雙重真相** —— 積木形狀在 `blocks.json` blockDef 和 `ui/block-registrar.ts` 各定義一次（後者用動態下拉蓋掉前者,JSON 的 OBJ 欄位其實是死的,因為「先註冊者贏」）；control-flow input 名同時在 JSON 和 `block-input-names.ts`。
6. **`core/` 與 `std/` 兩套存放慣例**（前者用子目錄多檔,後者用平面四檔）。
7. **半途遷移並存** —— 舊 `BlockSpec` 與新拆分格式（`ConceptDefJSON`+`BlockProjectionJSON`）同存於 `types.ts`。

## 為什麼會變成這樣（成長速度的凝結,不是設計失誤）

25 個重構性 spec + 318 commit 擠在 ~4.5 個月。碎裂是幾股**讓專案變好的力量**的影子面：

- **同一塊碼沿不同軸反覆重切**（four-dimensions / decoupling / sync-decouple / app-split / concept-blockdef-split / std-modules / unify-extractor）——同一蛋糕切 8 個平面 = 碎屑。
- **clean break 清得掉資料格式,清不掉程式機制** —— 新機制加了,舊的還能跑、編譯器不抱怨,沒人被迫刪。兩個 "unify" spec（011、048,相隔 37 號）就是「只統一一半」的指紋。
- **P2 四路完備性(零容忍) × 按機制組織** —— 「每概念必須四路」在按機制的結構下,把每個概念攤得更開。
- **宣告式蓋不掉 100%**（P3 的 80/15/5）—— 手寫層必須並存,但始終沒有共同前門。
- **純執行期需求戳破 JSON 單一真相** —— 動態下拉靜態 JSON 表達不出,只好 imperative 重定義。
- **core 先於 modules** —— 跨切面 dispatcher（`io.ts`）先於模組結構存在,沒被吸收進去。
- **AI 概念管線把碎裂模板一起規模化** —— 加概念的速度超過清理的紀律（孤兒 i18n 標籤、死 blockDef 欄位）。

**IR 乾淨,正因為它是那個「不准動的核」——churn 全發生在可替換的投影層。這是系統照設計運作,代價是投影層堆滿殘骸。**

## 提案：概念膠囊 + 單一 dispatch 脊椎

核心翻轉：**從「按機制分檔」→「一個概念 = 一個自足膠囊,五條路徑都在裡面」。**

```
concepts/cpp/string/at/
  concept.json    # id, layer, properties, children, role, semanticContract
  block.json      # blockDef —— 積木形狀的唯一權威
  paths.json      # lift pattern + generate template + render + extract（宣告式優先）
  strategy.ts     # 選配：宣告式表達不了時就近放,manifest 指向它
  execute.ts      # 第五路：直譯器 executor
  i18n.json       # 所有語系標籤
```

kernel 縮到只剩：`SemanticNode` + 膠囊載入器 + **每方向一條 dispatch 脊椎**。連 `core/` kernel 概念也變同形狀膠囊,手寫 lifter 變就近 `strategy.ts`；`core/`↔`std/` 兩套慣例消失成一套。

四個關鍵設計決策：

- **每方向只有一個前門** —— lift resolver：`宣告式 pattern → 膠囊自帶 strategy → 降級 raw_code`。render/extract/generate 同樣各一條脊椎。平行機制歸零。
- **殺雙重真相的通法：補強宣告式表達力,讓 imperative 不必出手** —— 例如給 block.json 宣告式「動態選項來源」（`{field:"OBJ", optionsFrom:"workspace.stringVars"}`）,由單一 registrar 解讀,JSON 重新成為唯一權威。每個雙重真相都用這招消,不用「手動同步」忍。
- **generate/lift 各二選一** —— 一個概念不准兩邊都填（延伸墓碑「codeTemplate 與 generator 並存」的互斥原則到 lift）。
- **兩份 lift schema 合一**（`lift-patterns.json` ⊕ 內嵌 `astPattern`）。

**避開的陷阱**：別再「全部宣告式統一」然後又長出平行 imperative（011/048 各統一一半就是此坑）。修法——**escape hatch 是一等公民、就近放膠囊裡**,承認 20% 需要程式碼並給它有尊嚴的固定位置,它就不會再散開。

## 做得到嗎：兩張網讓它從豪賭變成有檢查點的遷移

1. **IR 穩定 = 地基不動**，不是在流沙上重蓋，是在不動的核外換鷹架。
2. **roundtrip + fuzz + 直譯器輸出等價是「格式無關的黃金測試」** —— 斷言行為（code→tree→code 不變、stdout 相等），不管機器怎麼組織。可在測試全綠下抽換機器,每換一塊立刻知道有沒有弄丟東西。

## 遷移形狀：絞殺式清潔切割（不是 big-bang）

有真實的疤：`009-restore-legacy-features`（一次重構弄丟功能要專開 spec 救回）。20 模組 × 4 路一次全掀 = 放大那個疤。正確：

1. 新膠囊格式 + 新 kernel **蓋在舊的旁邊**。
2. **一個概念垂直切片**（`cpp_string_at`）證明格式跑得通、黃金測試綠。
3. **一模組一模組遷移**,每落地一個就刪掉對應舊機制。
4. 舊 kernel 沒人用了,整片刪。

每個模組遷移獨立可 ship,不會有掀開一半不能收的懸空。

**遷移引擎 = 現成的 concept-pipeline skill**：把它們的輸出目標改成膠囊格式,再寫一次性 migrate（讀舊散落檔 → 吐新膠囊）。遷移完,新概念天然落在「一資料夾五路徑」,碎裂在源頭不再發生。

## 絕對不能動的

- **`SemanticNode` / 根公理** —— 頂多兩個小增量（結構化 property、補 `taint` 傳播）,不是重新想像。第三次別再被誘惑去換核心（前兩次：Cubical TT、λ-core,見墓碑）。

## 還沒想清楚的

- **膠囊粒度**：一概念一資料夾,20 std 模組 × 每模組 N 概念會不會目錄爆炸？是否該一模組一膠囊檔（內含多概念）而非一概念一資料夾？
- **`paths.json` 統一 schema 的表達力邊界**：四方向塞進一個宣告式檔,會不會又踩到「表達不了就退化」的老路？escape hatch 的介面契約要先定清楚。
- **「動態選項來源」宣告式化**能覆蓋所有目前逼 `block-registrar` 出手的 case 嗎？需要先枚舉現有的 imperative 重定義。
- **和 [語義診斷系統](2026-08-05-語義診斷系統.md) 的順序**：兩個都動 lift 之後的管線,誰先做、會不會互相影響膠囊格式。
- **成熟後的出口**：這是 vision 的哪個 Phase？介於 Phase 6（完成）和 Phase 7（Python）之間——**在加第二語言前收斂,還是先出 Python 驗證語言無關性再收斂**？先收斂能讓 Python 直接用膠囊格式（不繼承碎裂）；先 Python 則有第二語言當膠囊格式的壓力測試。未決。

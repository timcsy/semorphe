# 一致是量出來的，不是保證的——而逼近的機制這個專案已經有了

> 日期：2026-08-12
> 怎麼冒出來的：談硬體數位孿生時，使用者說
> 「**我也發現一個原則，就是要讓模擬越接近實體，不太可能一次到位，
> 而是藉由一次次的回饋慢慢修慢慢逼近**」。
> **狀態：未驗證**（還沒做過任何模擬／實體對比）。captured ≠ committed。

## 一、它補上了 `等價與觀察集` 沒說的那一半

| | 回答什麼 |
|---|---|
| [等價與觀察集](../concepts/等價與觀察集.md)（ε／T） | **現在差多少** |
| **本檔這條原則** | **怎麼縮小它** |

那份概念檔 `:37` 逐字：

> 「觀察集會長大（加語言、**加精度要求、硬體進來**）」

它陳述了「觀察集會長大」這個事實，**而沒說長大的過程該長什麼樣**。

## 二、而它的機制化形式在這個專案裡已經有名字：棘輪

`build-guardrail` 第 7 步：**基線 ＋ 只准下降 ＋ 上升時必須指名**。
那正是「一次次回饋慢慢逼近」的工程形式，**而它已經被驗證過四十次**（40 條護欄）。

套到模擬／實體上：

```
同一段程式，模擬跑一次、實體跑一次   → 兩條軌跡
落差 = 在 ε 底下有幾步不同           → 一個數字
那個數字進基線                        → 只准下降
```

⚠️ **而「觀察」那一半不用發明**：`stepRecords`（執行軌跡）已經存在，
而 `等價與觀察集` 說的「觀察」正是它。

## 三、🔴 三個與護欄棘輪不同的地方——而這是本檔最該先寫下來的

### ① 目標不是 0

護欄的棘輪目標是缺陷清光。而模擬／實體的落差**不該是 0**：真實硬體有雜訊、
溫漂、時序抖動。要求歸零等於**要求模擬器模擬雜訊**——做不到，也沒有教學價值。

> **形式不是「落差 → 0」，是「落差 ≤ ε，而 ε 是被宣告出來的」。**

### ② ⚠️ 而那開了一個刷分數的門

`build-guardrail`「數字下降時，先問是哪一種」：

| 下降原因 | 意義 |
|---|---|
| 因為**實作**了 | 系統多會做一件事 |
| 因為**宣告**了 | 系統沒變，只是我們終於說清楚 |
| **因為 ε 放寬了** | ⚠️ **新的第三種** |

> **一個「差距 ≤ 容差」的指標，可以靠調容差達成
> ——而那看起來與真的改善一模一樣。**

→ **護欄要分兩欄記**：`ε 是多少` 與 `在那個 ε 底下差幾步`。
**ε 的每一次變動都要指名理由**，就像基線上調時那樣
（`build-guardrail` 第 7 步：「真的要上調時，把理由寫進**基線檔的 `note`**」）。

⚠️ 而 `等價與觀察集:122` 已經警告過同族的事：

> 「render 問 render，執行情境問 execute。**容差是為一個用途定的，卻被另一個用途用了。**」

### ③ 落差的來源不只一種，而它們的處置相反

| 落差來自 | 該怎麼辦 |
|---|---|
| 模擬器少做了一件事 | **修模擬器** |
| 硬體的物理特性（雜訊、延遲） | **調 ε 或改 T**——而這是①說的那種「不該歸零」 |
| **adapter 的實作與模擬器不一致** | ⚠️ **那是雙重真相**，見下 |

第三種最危險，因為它偽裝成第二種——「大概是硬體誤差吧」。
→ **判準**：同一個輸入重跑十次，落差穩定嗎？穩定 = 實作不一致；
飄動 = 物理。

## 四、⚠️ 而數位孿生天生製造雙重真相

一顆 LED 的行為會有兩份實作：

```
模擬側   src/components/hw/led/execute.ts   TypeScript
實體側   板子上 adapter 裡的那段            C／MicroPython
```

**「落差」就是那兩份漂移的症狀**——而雙重真相是這個專案追了整年的頭號病。
它比一般的雙重真相更難：**兩份跑在不同語言、不同硬體上，無法互相 import**。

**處方的形狀**（未驗證）：讓行為**只有一份宣告**，兩邊各自解讀它
——與 `lift-pattern.json` 是資料不是程式同一個形狀。

```
component.json 的 behavior 槽    ← 一份宣告（狀態機／真值表／時序約束）
  ├─ 模擬器讀它 → TypeScript 執行
  └─ 板子上的 adapter 讀它 → 實際驅動
```

⚠️ **而它要求「行為」宣告得成資料**。對簡單元件（LED、按鈕、繼電器）可行；
對複雜的（PID、通訊協定）不行。**那個分界在哪，今天不知道**
——而它決定了數位孿生能覆蓋多少元件。

## 五、這條原則的精確版本

> **模擬與實體的一致不是一個目標，是一個被量出來的量；
> 而讓它變小的唯一方法是每次都量、每次都比上次好。**

而它有一個推論，比原則本身更有用：

> ⚠️ **在還沒有東西在量之前，「模擬跟實體差不多」這句話沒有意義
> ——它不會錯，因為它不可能錯。**

那正是這個專案對付「機制有了沒人接上」的同一把刀。

## 六、⚠️ 它不只適用硬體

任何「模型 vs 現實」的對比都吃這條：

- **模擬執行 vs 實體硬體**（本檔的起點）
- **模擬執行 vs 真的編譯器**——⚠️ **這個今天就有**（第三十二條護欄「行為的誤差」
  已經在量 semorphe 的直譯器與參照編譯器的差距）
- **跨語言等價**——Python 的 `for` 與 C++ 的 `for` 在什麼 ε 底下相同
- **降級的正確性**——`vector<int>` 降成 `int` 在什麼觀察下無害
  （那正是 2026-08-08 炸出 bug 的地方）

⚠️ **第二項值得單獨看**：它是這條原則**已經在跑的一個實例**。
而讀完它之後（2026-08-12 當天）發現：**它比本檔 §三 寫的更成熟，
已經解掉了兩個陷阱中的兩個。**

### 第三十二條護欄已經解掉的（逐字引用它的檔頭）

**① ε 的位置**——它不用「容差」，它用**回饋週期**：

> 「一個凍結的讀數是**宣告**，不是量測。而
> `concepts/等價與觀察集.md`：『**行為由量測定義，不由宣告定義**』。
> **回饋週期是無限大 ⇒ 開環**，而 §三 記過開環正是出事的地方。」

→ 它每次跑都重新量，所以沒有「調 ε」這個動作可以刷分。
**把 T 設成「每次執行」，②那個門就不存在了。**

**② 分母必須進基線**——那正是本檔 §三② 的同族陷阱，而它更早被看見：

> 「⚠️⚠️ **分母必須進基線**。只記分子的話，**讓直譯器多壞掉幾段就能讓誤差下降**
> ——縮分母比修分子容易。所以五欄都記：不可判定／兩邊都跑得動／
> 只有參照／只有直譯器／兩邊都不成。」

**③ 誤差與殘差不可合併**——這一條本檔完全沒想到：

> 「⚠️ 這不是殘差。**誤差高＝模型是錯的**（系統會騙人）；
> **殘差高＝模型還沒長到那裡**（系統仍然正確）。**兩者不可合併**
> ——混起來的話，多蓋幾顆元件會讓『會騙人』的數字看起來在改善。」

⚠️ **那一條直接適用於硬體**：模擬與實體的落差也分兩種
——「模擬做錯了」與「模擬還沒模擬那個東西」。**混在一起的話，
多支援幾顆元件會讓錯誤率看起來在下降。**

→ **本檔 §三 應該照抄那三條，而不是重新發明。**
`experience.md`「照抄已驗證的形狀，不要自己換一個判準」。

## 出口條件

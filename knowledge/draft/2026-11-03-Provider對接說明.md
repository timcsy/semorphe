# Provider 對接說明（給 cos-mos 階段 3）

> 2026-11-03　三方會議第三輪議題三（[history/334](../history/334-三方會議第三輪符號學三面向與操作者介面.md)）。vision〈Provider 對接說明〉那一項的設計理據；對接完成之後收進 `concepts/`。
> 讀者：cos-mos 的瀏覽器宿主（階段 3：學生在 semorphe 按「執行」，由 cos-mos 載入、驗證、執行）。
> 權威是程式碼：`src/core/capabilities.ts`。這份說明與它不一致時，以程式碼為準，並請告訴 semorphe。

## 一、接上的方式：在宿主入口登記一個 Provider

semorphe 的組裝點（`src/ui/app.ts`）**不登記任何執行提供者**（第 243 刀起）；由宿主入口登記：

```ts
import { registerProvider } from '<semorphe>/core/capabilities'
registerProvider(cosmosProvider, { first: true })   // first：排在前面，先問它
```

今天的兩個宿主入口：網頁版 `src/main.ts`、VSCode 擴充 `src/vscode/webview/cella.ts`，各登記一個 Cella 提供者。
cos-mos 的宿主登記自己的 Provider 即可——**面板那一側不用改**。執行控制器只透過 `openSession` 問提供者，不認得任何一個提供者的名字。

## 二、Provider：要實作什麼

```ts
interface Provider {
  id: string                                   // 狀態列與紀錄裡的名字（例：'cosmos'）
  declares: CapabilityDeclaration              // 宣告會什麼（見下）
  createSession?(options, program): ExecutionSession | Declined   // 「執行」要它
  check?(req): Promise<CheckAnswer>            // 判決（狀態列的「判斷：…」、課程判題）
  supports?(language: string): boolean         // 可選：只接某些語言
  readiness?(): Readiness                      // 可選：'idle'|'loading'|'ready'|'unavailable'
  onReadiness?(cb): void                       // 可選：就緒狀態變了就通知
  warmUp?(): void                              // 可選：提早開始準備（頁面一打開就呼叫）
}
```

| 能力 | 宣告 | 方法 | 階段 3 要不要 |
|---|---|---|---|
| 執行（執行、除錯、單步、動畫） | `declares.session = { granularity, setInput, setVariable, steps }` | `createSession` | **要** |
| 判決 | `declares.verdict = true` | `check` | 可選（不實作的話，判決仍由 semorphe 內建的 Cella 提供者給） |
| 型別查詢 | `declares.types = true` | `check` 回 `types` | 可選 |

`SessionDetails`：`granularity`（`'statement'` 或 `'node'`，Cella 是 `'node'`）、`setInput`（能不能改板子的輸入）、`setVariable`（能不能改變數）、`steps`（給不給得出每個節點的次數）。
宣告是**誠實的**：宣告沒有的能力，畫面會說出來（例：`steps` 是 false ⟹ 覆蓋率那一格說「這個執行器給不出」），不是留白。

`SessionOptions` 帶來：`maxSteps`、`board`（板子的腳位模型）、`formal`（語意樹與目標／風格／骨架——要翻成 Cella 程式時用它）。

## 三、接不了：`Declined`

`createSession` 可以回 `{ declined: string, nodeId?, pending? }` 而不是一個工作階段：

| 情況 | 回什麼 | 畫面 |
|---|---|---|
| 還在準備（模組載入中） | `{ declined: '…', pending: true }` | 狀態列「準備中」，每 400 毫秒再問一次、好了自動開跑；120 秒還沒好就照實說 |
| 翻不出／不支援這支程式 | `{ declined: '…還不支援…', nodeId }` | 主控台說明（中文／English 由宿主的語系查字），`nodeId` 指的那一行與那一塊亮起來 |

⚠️ `declined` 的文字是一份**契約**：要說得出「還不支援」——那是系統能力不足，不是學生寫錯（`tests/integration/python-execution.test.ts`、`tests/unit/interpreter/unknown-component-stops.test.ts` 在守）。

## 四、ExecutionSession：形狀照 DAP（宿主下指令，每個指令回一個 Outcome）

```ts
launch(program, { stopOnEntry }) / continue() / stepIn() / supplyInput(line) / closeInput()  → Promise<Outcome>
pause() / terminate()
setBreakpoints(nodeIds)                 // 節點 id（不是行號）；執行中也可以改
onOutput(cb)                            // 程式印的東西，邊跑邊送（出錯前印的要留著）
variables()                             // 停著的時候看得到的變數 { name, type, value }
setVariable(name, raw)                  // 可以回 Promise
environment()                           // 板子當下的狀態；不是板子的程式回 null
setInput?(key, value)                   // 可選：宣告了 setInput 才有
coverage()                              // 每個節點進入幾次；給不出回 null
loopCounts?: 'entries' | 'checks'       // 迴圈的次數怎麼算（Cella 是 'checks'）
recordedInputs()                        // 這次從外面拿到的輸入（重播、插手紀錄）
```

`Outcome`：
- `{ kind: 'stopped', stop: { reason, nodeId, detail? } }`——`reason` 是 `entry`／`breakpoint`／`step`／`pause`／`awaiting-input`；
- `{ kind: 'ended' }`；
- `{ kind: 'failed', error: SessionStop }`——未定義行為、執行期錯誤、被停止，都是這一種。`SessionStop` 帶 `kind`（`'aborted'`／`'runtime'`）、`i18nKey`（`RUNTIME_ERR_*`，畫面查語系）、`params`、`nodeId`（指回出錯的那一顆）；
- `{ kind: 'declined', reason }`——只會是 `launch` 的結果：開跑時才發現跑不了（一步都沒跑）。

## 五、狀態怎麼回報（宿主的畫面看到什麼）

| 提供者給的 | 狀態列／主控台 |
|---|---|
| `readiness()` 是 `loading`，或 `createSession` 回 `pending` | 「準備中…（好了會自動開始）」 |
| `stopped`（breakpoint／step／pause） | 「已暫停」；那一行與那一塊亮起來；變數面板顯示 `variables()` |
| `stopped`（awaiting-input） | 「等待輸入」；主控台出現輸入列 |
| `ended` | 「程式執行完畢」；有 `coverage()` 就畫次數 |
| `failed` | 主控台印 `i18nKey` 查到的說明（含條文），指回 `nodeId`；切到主控台分頁 |
| `declined`（非 pending） | 主控台說明「還不支援」，指回 `nodeId` |
| 這次由誰跑 | 狀態列「執行：<id>」 |

## 六、驗收：拿 `tests/contract/session-contract.test.ts`

那一檔對 `PROVIDERS` 陣列裡的**每一個**提供者跑同一份契約（C++ 十一條、Python 七條），包括：
跑完印出、中斷點停在那一顆且看得到變數、中斷點設在運算式敘述與迴圈裡、單步、改變數之後輸出反映它而且留下紀錄、
讀輸入、讀到 EOF（`closeInput`）、執行期錯誤回 `failed` 帶 `SessionStop`、停著時 `terminate` 不會卡住。

cos-mos 的提供者加進 `PROVIDERS` 一筆（`{ id: 'cosmos', make: () => … }`），整份過了就算接上。
（spec 208 起那一檔只剩 Cella 一筆；迴圈的形狀刻意留著，就是為了這一天。）

## 七、未定（之後對接時再談）

- cos-mos 的宿主是在瀏覽器頁面裡（同一個行程）還是另一個 worker／iframe——`ExecutionSession` 的方法都是非同步的，跨 postMessage 也接得住；`variables()`／`environment()`／`coverage()` 是同步的，跨邊界時要在每次 `stopped`／`ended` 時一起帶回來快取（Cella 提供者今天就是這樣做的）。
- 判決（`check`）要不要也由 cos-mos 給：階段 3 的成功標準說「cos-mos 的瀏覽器宿主載入、驗證、執行」——若判決也走 cos-mos，`declares.verdict` 宣告即可，semorphe 這側不用改。

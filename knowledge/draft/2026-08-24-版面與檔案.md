## 一之二、🔴 那個順序不是「誰比較重要」——是**理解的四個層次**

> 🔴 **我第一版把它讀成產品訊號（「程式碼是主體」），使用者更正：**
> 「程式碼、流程、積木、主控台這個順序是我用**「元素、關係、空間、動力」**來思考，
> **代表理解的不同層次**（靈感從 Transformer 裡面運算的順序而來），**不是誰比較重要**。」
>
> 🟢 **同日收斂為「元素、關係、空間、狀態」**（使用者：「好像更好」）。

| 層次 | 面板 | 在問什麼 | Transformer 的對應 |
|---|---|---|---|
| **元素** | 程式碼 | 有哪些東西 | token／嵌入 |
| **關係** | 流程 | 誰跟誰有關 | attention |
| **空間** | 積木 | 它們怎麼被擺在一起 | 表示空間 |
| **狀態** | 主控台 | 現在裡面裝了什麼 | 那一層之後的殘差流 |

⚠️ **第四個字從「動力」改成「狀態」不是修辭**：`concepts/投影.md:141` 的三個對象裡
**已經有【狀態】**（「執行狀態 → 變數面板／圖解 **【狀態】** 現在裡面裝了什麼」）。
用「動力」等於替同一件事造第二個名字，而這個知識庫的不變式之一是**收斂**。

> **一個新詞如果指的是既有詞已經指到的東西，它不是更精確，它是分裂。**

### 🎯 而這個透鏡做得出一個預測，**而那個預測已經被獨立地觀察到了**

`面板協定 §九` 使用者 2026-08-24 提過另一件事：
「流程圖很像是硬體那邊的 **2D 接線視圖**，積木很像硬體那邊的 **3D 組裝視圖**」。

用這個透鏡看，**那個對應不是巧合，是推論**：

```
關係層   流程圖  ↔  2D 接線圖      都在問「誰跟誰有關」
空間層   積木    ↔  3D 組裝        都在問「它們怎麼被擺在一起」
```

> **兩個獨立提出的直覺互相推導得出來，那通常表示底下有一個真的結構。**

### 它同時細分了 `concepts/投影.md:141` 的三個對象

那一節把投影分成【結構】【狀態】【能力】。這個透鏡說：
**【結構】其實有三層**（元素／關係／空間），而第四層**就是**【狀態】。

```
元素 · 關係 · 空間   →  【結構】的三層
狀態                 →  【狀態】
```

⚠️ 所以「有幾個結構投影」不是隨意的——**三個，因為理解有三層**。
而 2D 接線與 3D 組裝進來時，它們是**填進既有的層**，不是加新的面板類型。

### 🔴 而這個透鏡的**邊界**也因此看得見了：它不管【能力】

對照那三個對象，**【能力】（工具箱／圖鑑）不在這四層裡**——而那不是遺漏：

```
四個層次   在理解【這一個程式】
【能力】   在回答【這個系統有什麼】
```

> **一個好的透鏡要說得出它不管什麼。**

⚠️ **而「不在四層裡」只說得出它不屬於編輯區，說不出它該去哪**——
我第一版從這裡推出「所以住側邊欄」，**而那一步是錯的**（見 §六之二）。

## 一之三、第 5 題選 A 的理由要重講（原本的理由是錯的）

我原本寫「程式碼排第一 ⟹ 程式碼是主體 ⟹ 所以檔案存原始碼」。
**前半錯了，而結論仍然成立，理由要換**：

> 檔案存原始碼，是因為**原始碼是最通用的那一份投影**——別的工具打得開、
> 版本控制看得懂、與 VSCode 那側一致。**與「哪一層比較重要」無關。**

⚠️ 這是 `語義樹只有樹沒有邊 §五` 記過的同一種事故：
**「一個結論對、而理由錯的判斷最危險：理由會被拿去做下一個決定。」**

## 二、🔴 「要有檔案」把兩個宿主的真相模型統一了

今天這句話是真的，而它是所有不對稱的根：

> `src/vscode/sync/view-state.ts:5` 逐字
> 「網頁版 **沒有檔案** ⟹ **積木的擺放【就是】真相**，存檔存的是它
> VSCode 程式碼是真相 ⟹ 積木的位置**純粹是外觀**」

網頁版有了檔案之後，**左半邊作廢**：兩邊都是「檔案是真相，積木的位置是外觀」。

連帶結清三件懸著的事：

| 懸著的 | 結清 |
|---|---|
| [面板協定 §八](2026-08-20-面板協定的三個頻道.md)「共同真相是什麼」 | **主體 ＝ 檔案**，兩個宿主同一個答案 |
| ③ per-panel 狀態的 key | **`檔案 × 面板種類`**——§八 的 A 答完了 |
| §八 的 B「能不能同時兩個焦點」 | 開兩個檔案就是兩個焦點——**能** |

> **一個宿主看起來比較受限，而它的限制正好替我們回答了共同真相住在哪。**（§五 逐字）
> 這一刀是把那個答案**搬到沒有限制的那一側**。

### 🎯 而 side-car 就是 ③ 的家

```
foo.py                    真相——原始碼
.semorphe/foo.py.json     side-car：積木座標 · 流程節點位置 · 摺疊 · 面板私有狀態
```

**side-car 可丟**——丟了就自動排版。那正是「排版不是真相」那條線的落地
（`experience.md`：改了它程式的行為會不會變？不會 → 它是排版）。

⚠️ **而它換出一個新問題**：檔案改名／搬移時 side-car 要跟著，否則變孤兒。
VSCode 那側的 `ViewState` 是 per-uri，**同一個問題，今天也沒答**。

### 🆕 `.sem`：把 side-car 的資料夾當成 `.git` 那種東西（2026-08-27，使用者提）

> 使用者逐字：「未來如果要進行持久化儲存，可以考慮用 **.sem 資料夾**儲存相關的資訊，
> **如同 .git 一般**」。

⚠️ 先分清楚：「**一個資料夾裝旁邊那些東西**」上面已經拍板了（第 5 題），
所以這一則的內容**不是那個**。名字 `.semorphe` → `.sem` 只是取捨
（`.sem` 更靠近 `.git`／`.svn` 那一族，而 CLI 已經在走縮寫路線叫 `smorph`）。

**`.git` 這個類比真正帶進來的是三件事，而它們原本都不在第 5 題裡。**

#### ① 它是一個「專案根」標記——而那是**多一個概念**，要走閘

今天的答案是「**主體 ＝ 檔案**」（上面那張表）。`.git` 的形狀隱含
「有一個**專案**，而它有一個**根**」，並且**由任一個檔案往上走就找得到它**。

那不與「主體＝檔案」矛盾（git 也有 worktree 裡的個別檔案），
但它是一個**新的承諾**：這個系統從此有「專案」這個東西。

⚠️ 今天唯一會需要它的是**多檔之間的引用**，而 `vision.md` 明寫那**不在本項**。
→ 所以這一條要走 draft → 路線圖那道閘，**不能因為「反正資料夾都要建了」就順手帶進去**。

#### ② 它解掉這份 draft 自己記著的那個未決：**孤兒**

上面逐字寫著：

> ⚠️ **而它換出一個新問題**：檔案改名／搬移時 side-car 要跟著，否則變孤兒。
> VSCode 那側的 `ViewState` 是 per-uri，**同一個問題，今天也沒答**。

而 `git` 的答案是**根本不拿路徑當身分**——它認內容。

🟢 **同一招的縮小版 2026-08-27 已經在跑了**：節點佈局的鑰匙換成
「**內容 → 行號 → 路徑**」三把一起（`src/core/flow/layout-key.ts`），
量出來三者的失效條件互斥（83%／92%／96% → **一起 100%**），
而**內容是最強的那一把**。

> **拿「它在哪」當身分的東西，會在它搬家的那天變成孤兒；
> 拿「它是什麼」當身分的不會。**

→ 放大一層，`.sem` 就不會因為改名／搬移產生孤兒。⚠️ 而代價要說清楚：
內容當身分**容易撞**（兩個一模一樣的檔案），所以撞到時的規則要先定
——縮小版那邊的規則是「**曖昧的鍵一律不算命中**，寧可對不回去，不要對到別人身上」。

#### ③ 它給「不屬於任何一個檔案」的東西一個家——這一點是純賺的

今天 `topicId`／層級／啟用的分支住在 `localStorage` 的 `semorphe-state`，
而 **per-file 的 side-car 裝不下它們**（它們不屬於任何一個檔案）。
一個專案級的資料夾正好是它們的家。

#### ④ 🆕 它裝得下「程式碼表達不了的那個差別」——LED 還是繼電器

> 🪦 這一節的標題原本是「它裝得下**當初用的是哪顆積木**——而那**解掉粒度那一題的一半**」。
> **兩句都被同日的量測推翻**，改法見下面第一小節。
> 留這個墓碑是因為那個較寬的說法很吸引人，而下一個人很可能會再想到一次。

> ⚠️ **先讀 [粒度屬於投影](2026-08-27-粒度屬於投影.md)**——本節是它 §五② 的解。
>
> 使用者（2026-08-27）：「只要有 .sem 就可以保有**當初的動機**，之後就知道如何轉換層級了……
> 我當時候是怕還原回去的時候變不回那個粗積木，變成很多細積木，**學生就看不懂了**。
> 但是有了 .sem，就可以知道當初用什麼積木，甚至還能幫助像是 Arduino 那邊，
> 同樣都是 digitalWrite 但是用不同積木（例如 LED 或是開關之類的）」

##### 🔴 第一版把範圍寫得太寬，而量測把它縮小了（2026-08-27 同日修正）

原文寫著：`identityBeforeDowngrade`（`sync-controller.ts:556` 的 `restoreDowngrade`）
「**就是**當初用的是哪顆積木」，只是活不過重新整理。

**那句話太寬。** 它記的是「**這一次同步中被降級的節點原本叫什麼**」，
而使用者在 L0 拖一顆計數迴圈時**根本沒有發生降級**——樹裡本來就是 `cpp:loop_count`。

實測那條來回：

```
L0 拖一顆計數迴圈（樹裡就是 loop_count）
  → 產生 for (int i = 0; i < 5; i++)
  → lift 回來：loop_count = true，loop_for = false
```

**「還原回去變成一堆細積木」在這個例子上不會發生**——不是因為有人記住了，
是因為 **lifter 認得那個樣式**。

##### 🟢 而這推出一條窄很多、也硬很多的判準

```
程式碼【不一樣】   for(i=0;i<5;i++) vs for(i=10;i>0;i-=2)
                  差別在程式碼裡就在，lifter 認得出 → 【不需要 .sem】

程式碼【一樣】     digitalWrite(13,HIGH) 出自 LED 積木 vs 繼電器積木
                  差別在程式碼裡【不存在】     → 【只有 .sem 裝得下】
```

> **意圖只有在程式碼相同時才需要被保存。
> 程式碼不同時，那個資訊已經在程式碼裡了。**

⚠️ 這條判準把提案**縮小**了，而那讓它更值得做：從「一個模糊的還原保險」
變成「**一個明確的、程式碼表達不了的維度**」。
🔴 而 Arduino 那個例子因此從「附帶好處」變成**唯一的核心理由**。

##### 而它留下的缺口是真的

```
🟢 程式碼一樣、意圖不同     .sem 裝得下                → 這一則解掉
🔴 進階寫法要在 L0 摺起來   i -= 2 摺不成「從 0 數到 n」 → .sem 幫不上
🔴 外面來的程式碼           沒有 .sem                  → 只能落回最細的積木
```

> **`.sem` 保存意圖，而它不產生意圖。**

⚠️ 第一條線決定：**貼一段網路上的 Arduino 程式碼，小學生仍然看不懂**。
要讓那種程式碼也長出粗積木，需要的是**辨識**（「這看起來是 LED 的樣式」），
那是 lifter 的工作、**另一個機制**。兩者混在一起會以為做了 `.sem` 就全解了。
⚠️ 第二條是 [粒度屬於投影](2026-08-27-粒度屬於投影.md) §五②，**仍然開著**。

##### 🔴 而它讓 `.sem` 裝進第二類東西——「可丟」那條線要重畫

上面（③）寫的判準是「刪掉之後**程式的行為**都不可以變」。
意圖記錄**通過那一條**（刪掉 → 一樣的 `digitalWrite`），而它換出一個新的問題：

```
排版類   丟了 = 重算一次        無損
意圖類   丟了 = 降到最細的粒度  行為無損，而【認知有損】
```

> **一份東西可以「行為上可丟」而「認知上不可丟」——
> 而只用行為當判準的話，第二種損失是看不見的。**

⚠️ 這不是反對，是**那條判準要補一句**，否則將來有人照著「反正 side-car 可丟」去清它。
**而「認知上可不可丟」是教學判斷不是工程判斷——這一格留給人。**

##### 已知的第二份真相陷阱，這個 repo 踩過一次

`SavedState.blocklyState` 的檔頭逐字：

> ⚠️ 失效條件是 `codeHash`：對不上就**寧可重排版**，也不要拿一份與程式碼不一致的積木
> ——**那會變成第二份真相**。

意圖記錄一模一樣：`.sem` 說「這是 LED 積木」，而有人在 Semorphe 外面把
`digitalWrite(13,HIGH)` 改成 `analogWrite(13,128)`——**那筆意圖現在是錯的**，
照著它渲染會渲出一顆騙人的積木。

🟢 **而 2026-08-27 的佈局鑰匙正好是答案**：意圖記錄若**用內容當鍵**
（與佈局共用 `core/flow/layout-key.ts` 的 `matchByKeys`），節點一改鍵就對不上，
**那筆意圖自己失效**——不必外掛一個雜湊。

> **佈局與意圖是同一個問題的兩個實例：
> 「這顆節點的某個非語義屬性」怎麼跨編輯活下來。**

→ 如果這成立，`.sem` 裡不是兩張表，是**一張表兩種欄位**。實作小很多。

##### Arduino 那個例子比它看起來更強

同樣 `digitalWrite`，用 LED 積木還是繼電器積木——
**那個差別在程式碼裡不存在，而它是學生理解那一行在幹嘛的全部。**

推出一件事：`.sem` 不只是「還原得回粗積木」，它是**「這個檔案的領域是什麼」的載體**。
同一份 `digitalWrite`，在「交通號誌」與在「自動門」那一課該長成不同的積木
——⚠️ 而那個資訊**今天沒有任何地方裝得下**。

⚠️ **未查證**：這與 `concepts/元件.md` 的五槽／關係律有沒有衝突，還沒對過。

### 🔴 而有一條線**不可以**跟著類比一起搬

`vision.md` 的驗收條款逐字：

> **side-car 刪掉 ＝ 自動排版**（不是壞掉）

而 `.git` **恰恰不可丟**——丟了歷史就沒了。所以這裡借的是**形狀，不是賭注**。

判準寫成一句：

> **`.sem` 裡的任何東西，刪掉之後程式的行為都不可以變。**

哪一天有東西不符合這句話，那條「**排版不是真相**」的線就被跨過去了
（`concepts/投影.md:607`：判準是問「它換一個投影還存在嗎」）。

⚠️ 類比最弱的一格是**網頁版**：那裡沒有檔案系統，`.sem` 作為「資料夾」
是 VSCode 那一側的形狀。已決的 `FileStore` 埠（兩個實作，**而 VSCode 那側不實作**）
就是為了這個——`.sem` 在網頁版會是那個埠底下的一種**佈局**，不是一個真的資料夾。

### ⚠️ 語言屬於**文件**，而副檔名只是它存檔後的投影

> 🔴 **這一段第一版寫錯了**，使用者當場更正：
> 「『語言從副檔名來』這句話不對，因為當我**開啟一個新檔案**時，我是可以選擇語言，
> 但是**還沒存檔，所以沒有副檔名**。」

而它錯的形狀，庫裡有一模一樣的一則（`src/core/component/traits.ts:60`）：

> **一個「從產出的形狀反推它是什麼」的判準，
> 會在那個形狀有例外的時候安靜地做錯事——而宣告不會。**

副檔名是**產出的形狀**（存檔的結果），語言是**宣告**。反推的那一版，
在「還沒存檔」這個例外上直接沒有答案。

**正確的形狀**：

```
語言      文件的屬性——新檔案由使用者選（topic 可以給預設）
副檔名    存檔時【跟著語言走】，不是反過來
開啟舊檔  副檔名是一個【推導的預設】，而使用者仍可改
```

🟢 這與 VSCode 的語言模式是同一個形狀（untitled 檔可以選語言模式，存檔時副檔名跟著）
——**又一次「宿主的限制替我們回答了問題」**。

（⚠️ topic／課程仍然是 UI 的——那是教學的分層，不是文件的屬性。）

## 三、檔案系統是一個**埠**，三個實作

```
FileStore   list() · read(path) · write(path, text) · delete · rename
```

| 實作 | 宿主 | 備註 |
|---|---|---|
| `MemoryFileStore` | 網頁版預設 | localStorage／IndexedDB |
| `NativeFileStore` | 網頁版（授權後）／Electron | File System Access API |
| **不需要實作** | VSCode | **workspace 本身就是**——`vscode.workspace.fs` |

🎯 這是**宿主獨立性的第三個實例**（前兩個：儲存、程式碼視圖）。同一個形狀第三次出現，
表示它是對的：**宿主提供能力，核心只認得埠。**

### 匯出／匯入

- 匯出 ＝ **zip**（原始碼 ＋ `.semorphe/` side-car），單檔也可以直接下載
- 匯入 ＝ 解壓；⚠️ 要處理「zip 裡有 side-car 但版本不同」
- 🔴 **新的 npm 依賴**（`fflate` 之類）——而 **`e2e/offline.spec.ts` 的離線可用是硬條件**，
  所以必須打包進來，不能走 CDN

## 四、流程圖可編輯——界線已經有名字

| 編輯動作 | 樹表達得出來嗎 | 拍板 |

| (a) 拖節點 | 不碰樹 | ✅ 已有（排版不是程式） |
| (b) 改節點欄位（`>` → `<`） | 改一個 property | ✅ **都做** |
| (c) 資料線改接到另一個節點 | 換插槽的子節點 | ✅ **都做**——這是節點圖的靈魂 |

⚠️ **(f) 的處置是這一刀的誠實底線**：圖看起來能接線，使用者一定會試。
那時要說得出「這條線我畫不出來，因為 X」——**不能安靜地塞進 `metadata`**
（那正是 `語義樹只有樹沒有邊` §六 寫的「不得繞過去」）。

### 🔴 它逼出兩個機制

1. **`EditableView` 契約**：今天 `extractSemanticTree()` 是 `blockly-panel` 的方法，**不是契約**
   （`draft/可嵌入與可插拔的四個軸` 第 4 步就是這個）。
   **流程可編輯是那個介面的第二個實作，也就是它的第一次真考。**
2. **palette ＝ 工具箱的另一個投影**：流程面板要有「可以拉什麼進來」的清單，
   而那是**【能力】投影**（`concepts/投影.md:141` 的第三個對象）。
   🔴 **不該各寫一份**——工具箱與流程 palette 讀同一份登錄表。

## 五、同步按鈕：方向模型徹底不可行了

```
2 個可編輯視圖 → 2 個方向按鈕（今天）
3 個可編輯視圖 → 6 個方向          ← 沒有人要按這個
```

所以「誰是來源」**只能是導出的**：

```
狀態列        以【流程】為準 · 已同步      ← 你最後動的那個，導出的
面板標題列    ⟳ 以此重建其他                ← 例外動作，每個結構面板一顆
工具列        ⏸ 暫停同步                    ← 保留；它是【暫停】不是【方向】
```

⚠️ **暫停中要一直看得見**，否則症狀是「我打字積木怎麼沒動」。

## 五之二、🔴 同步是**三態**，不是兩態——而暫停暴露了「導出的來源」的洞

> 使用者 2026-08-25 追問：「**會不會有時候有需要手動同步？還是不會有這需求？
> 還有會不會有時候想要暫停同步？**」

兩個都需要。而問題本身戳到 §五 的一個洞。

### 舊按鈕在做**兩件事**，所以它看起來像 N²

```
(a) 「現在同步一下」  → 時機（when）    自動同步開著時不必要
(b) 「以這一邊為準」  → 來源（which）   兩邊分岔時無可取代
```

方向是 N²，**來源只有 N**。舊的兩顆把 (a)(b) 寫成同一顆，所以加第三個視圖時會爆炸。

### 🔴 而「來源是導出的」在暫停之後失效

§五 說「誰最後被編輯就是來源」。**暫停、兩邊都改、解除暫停**——那時「最後編輯」
是任意的，而系統會**安靜地挑一個**：那是替使用者做了一個他沒做的決定。

```
同步中    來源是導出的（誰最後編輯）              ← 平常
已暫停    沒有來源——兩邊各自為政                  ← 明確顯示
分岔了    🔴 系統【停下來問】，不自己挑一邊        ← §五 漏掉的那一態
```

> **有暫停，就一定要有手動來源；而分岔之後系統該【問】，不該【推】。**

### ⚠️ 而「暫停同步」今天真正在做的事，不是它的名字

最硬的那個場景：**你在程式碼那側改一行，積木重新 lift ——你排好的版面沒了。**

而「保住排版」要用 `nodeId` 當鍵，那是**階段 5b 的前置**（`generateId()` 帶時間戳）。

🎯 **所以「暫停」今天承擔的是「別把我的排版弄掉」——它是 5b 缺席的代償。**

| 場景 | 強度 |
|---|---|
| 保住另一邊的排版 | 🔴 **強**——今天無解 |
| 打字中途程式碼不合法，積木一直降級 | 中（防抖大致擋得住） |
| 大檔案的效能 | 中 |
| 教學：先寫完再看積木 | 弱但真實 |

⚠️ **5b 之後回來重看**：暫停的需求會**縮小，但不會消失**——分岔那一個永遠在。

### 🔴 2026-08-25 更正：三態**兩個宿主都要**，而我推錯了一步

我一度把整件事範圍成「只有網頁版需要」，理由是
「VSCode 那側真相是文件，所以沒有『誰是來源』的問題」。

**那個理由本身是對的，而結論是錯的**——使用者當場反問「為何 VSCode 那邊不做？應該也是需要的呀」。

> **「其中一個問題在那邊不存在」推不出「這個機制在那邊不必要」。**
> 我拿三態裡的**一態**不存在，推掉了**三態**。

逐條查證之後：

| 三態的成分 | 網頁版 | VSCode／Theia |
|---|---|---|
| **來源是誰** | N 選一（沒有文件） | 🟢 **文件永遠是來源**——我的論證只在這一格成立 |
| **暫停**（別把我的排版弄掉） | 需要 | 🔴 **同樣需要**：`vscode-code-view.ts:145` 收到 `document` 就 `changeCb(mirror)` → 積木重 lift → **排版沒了** |
| **分岔** | 需要 | 🔴 **更常見**——文件還可能被 git／別人／另一個編輯器改 |

🎯 **而它其實是一個統一，不是分歧**：同一個三態模型，兩個宿主，
**只有「來源」那一格在 VSCode 塌成二選一**（文件 vs 這個面板）。

→ **機制住在核心**（`sync-controller` 昨天剛搬進 `core/`），兩個宿主各自接入口：

```
core        三態狀態機 ＋ 分岔偵測 ＋ 來源解析（來源清單由 viewsWith('editable') 導出）
網頁版入口   我們自己那條狀態列（已存在）
VSCode 入口  createStatusBarItem ＋ 命令（今天零個——新工作，但薄）
```

⚠️ 而 `vscode-code-view` 裡已經有一個叫 `divergences` 的計數器
（樂觀更新的鏡像對帳），**與這裡的「分岔」不是同一件事**——命名要避開。

## 五之三、入口在**狀態列**，不在側邊欄，也不在面板裡

> 使用者 2026-08-25 拍板：「我希望是**全域**，然後**不會放在面板裡面的**……
> 可能點擊活動列的 icon 展開側邊欄裡面就有 ListView 之類的可以進行操作吧，
> **還是有更好的設計？**」

側邊欄 ListView **對開關這件事過重**：

| | 側邊欄 ListView | 狀態列 |
|---|---|---|
| 開關一次幾步 | **四步** | **一步** |
| 暫停中看不看得見 | 🔴 **收起來就看不見** | **永遠可見** |
| 佔用成本 | 一個活動列格子（很貴） | 一格文字 |
| 宿主慣例 | 可瀏覽的**集合** | **全域狀態**（語言模式、行尾、Git 分支） |

第二列是硬傷——驗收裡有一條是「**暫停中必須看得見**」，而會被收起來的位置滿足不了它。

```
狀態列    ⇄ 同步中 · 以【程式碼】為準      點一下開 QuickPick
          ⏸ 已暫停
          ⚠️ 兩邊都改了                    分岔態，點它去解決
QuickPick ⏸ 暫停自動同步 · ⟳ 以【X】為準（清單由 `viewsWith('editable')` 導出）
命令面板  具名動作、可綁快捷鍵
側邊欄    **投影清單 ＋ 各自狀態**——看的東西，不是按的東西
```

🟢 三個宿主都有狀態列，而**網頁版那一條已經存在**——⚠️ 而它在
`src/ui/app-shell.ts` 的 `updateStatusBar`，**不是** `src/ui/layout/status-bar.ts`。
後者是一個**零呼叫者的死類別**（見 [[死匯出的四種死法]]），而它也建一個
`id="status-bar"` 的 footer——**兩份長得一樣，而使用者看到的是前者**。

### 🔴 2026-08-25 落地：面板不畫，宿主自己畫

使用者截圖後說：「**狀態列是不應該放在裡面的**」。

處置是**一格宣告**（`HostFeatures.statusBar`），不是一個 `if`：

```
statusBar: true    網頁版自己畫（今天那條）
statusBar: false   IDE 有自己的狀態列 → 面板【不建】那個 footer
                   而它背一個義務：CodeView.reportSyncPhase 必須有實作
```

⚠️ **兩端要對釘**（第六十三條護欄）——不然症狀是
「面板那條不見了、宿主那條沒出現」，而使用者讀到的不是「少一條狀態列」，
是「**同步壞了**」。

🔴 而真正的根因不在版面，在**兩個重畫函式**：`refreshStatusBar` 畫面板那條、
`refreshSyncStatus` 送宿主那條——而**開機只走了前者**。已合併成一個。

> **同一份狀態的兩個投影，如果由兩個函式寫，
> 遲早會有一條路徑只走到其中一個。**

## 五之四、🔴 跨宿主的判準（比版面本身重要）

> 使用者同日：「**確保 ArduinoIDE 那邊也是可以順利使用的**」
> 🟢 **2026-08-25 確認：指的是 Theia**（Arduino IDE 2.x 建在它上面）。

### ⚠️ 而我把它當成「第三個宿主」是錯的——**它早就是被支援的第二個**

而那份 skill 連坑都記著了：

> 「它驗得到『我送了什麼』，驗不到『對面怎麼處理』，**更驗不到 Theia 與 Chromium 的差異**」

`tools/install-ide.mjs` 也早就兩個都裝。

自訂工具列與花俏的貢獻點**才是各宿主分岔的地方**——

🔴 **而 skill 那句「驗不到 Theia 與 Chromium 的差異」直接打到這一刀**：

🔴 **推論**：這一刀不是「把按鈕搬家」，是**把同步的入口從我們自己畫的 chrome，
換成宿主都有的 chrome**——那就是「宿主獨立性」在 UI 上的樣子。

## 六之二、🔴 工具箱與圖鑑不是「同一格」——分界在**使用的姿勢**

> 使用者更正（2026-08-24）：「**工具箱 · 圖鑑不應該放在側邊欄，而是一個獨立面板**，
> 因為 **VSCode 的側邊欄用來做這個版面不夠大**。」

我第一版把它們一起丟進側邊欄，理由是「它們都是【能力】投影」。
**那是拿分類當版面**，而版面要問的是另一件事：**這東西是怎麼被用的？**

| | 工具箱／palette | 圖鑑 |
|---|---|---|
| 姿勢 | **取用**——拿一顆進來 | **認識**——有什麼、長什麼樣、怎麼用 |
| 需要什麼 | **與它服務的工作區相鄰**（要拖得過去） | **面積** |
| 位置 | **附著在那個編輯視圖上**，不是一格 | **獨立面板**（編輯器分頁） |

🔴 **而「相鄰」不是順手，是硬限制——使用者實測過**（2026-08-24）：

> 「我以前試過，**獨立面板的拖曳效果超爛**，後來就**放棄獨立面板**了。」

所以工具箱**不能**被拆成獨立面板。這一條原本被我列成「未實測」，
**而它其實已經被試過並否決過**——差點被我當成一個新選項重新提一次。

> **一個「理論上等價」的版面改動，在互動上可能完全不等價。**
> 拖曳是一個**跨越距離**的操作，它對「在不在同一個 DOM 裡」極度敏感——
> 而那件事在版面圖上看不出來。

### ⚠️ 連帶：圖鑑因此**不能靠拖曳**

圖鑑是獨立面板（它要面積），而獨立面板拖不動——於是「在圖鑑看到一顆想用的」
**不能用拖的**。它要嘛給一顆「插入到目前的工作區」按鈕，
要嘛只負責認識、把取用交還給工具箱。

🔴 這是一個**真的產品決定**，不是實作細節：
**圖鑑是「讀」的地方，取用永遠發生在附著的工具箱。**

🎯 **連帶答了一個先前的未決**：流程面板的 palette 也是**附著的**，
不是共用一個側邊欄。它與積木的工具箱**讀同一份登錄表**（單一真相），
而**各自渲染在自己的視圖旁邊**——那正是「一個概念、各式投影」。

### 於是版面的判準要重寫

我原本寫「側邊欄＝【能力】投影」。**改成：**

```
編輯區    需要【面積】的東西      三層投影 · 圖鑑 · 設定頁
側邊欄    導覽用的【窄清單】      檔案總管 · 大綱
面板區    【狀態】                主控台 · 變數 · 圖解
附著      取用用的                積木的工具箱 · 流程的 palette
```

🟢 **而這與 VSCode 自己的慣例一致**：它的設定、延伸模組、快捷鍵**都開在編輯區**
——編輯區從來不是「只放文件」，是「放需要空間的東西」。

> **版面的分界不是「這是哪一類」，是「這東西怎麼被用」。**

## 六、版面：一套 slot 詞彙，兩個宿主

**slot 用 VSCode 的詞彙**——「這個面板該放哪」只要回答一次：

```

panel         主控台 · 變數 · 圖解        ← 【狀態】

（附著）      積木的工具箱 · 流程的 palette ← 不是一個 slot，長在它服務的視圖上
```

⚠️ **`圖鑑` 在編輯區而不在側邊欄**——見 §六之二（使用者以「VSCode 側邊欄不夠大」更正）。

| 宿主 | 誰決定版面 |

| **手機平板** | 分頁列：**程式碼 · 流程 · 積木 · 主控台** ＋ 虛擬鍵盤（保留） |

🟢 **VSCode 那側的佈局工作幾乎是零**（`面板協定 §五` 查證過）。

⚠️ **P4 漸進揭露**：活動列＋檔案總管會讓教育產品長得像 IDE。
→ 用既有機制擋：`profile.features.*`（程式碼面板就是這樣被關掉的）。
**版面由 profile／topic 決定，不是由使用者拖。**

控制項宣告   { id, 標籤, 種類: picker | action, 領域: session | view | project }

**關掉的義務是「有人接手」**——不然症狀又會是

   2026-08-25 已經踩過一次「面板關了還在說同步中」
3. **`editor/title/run` 在 webview 分頁上的支援**——⚠️ 拍板了長相，

4. **主控台／變數／流程那三個分頁**該去 VSCode 的 `panel` 區——**是另一刀**，

## 六之四、🔴 網頁版也搬了——而「像 IDE」不是一句形容詞，是四個具體決定

> 使用者 2026-08-25（在 IDE 那一刀交付之後）：
> 「**網頁版也照 §六 把 picker 移到狀態列，但是行動版可以另外設計**」
> 「我希望網頁版的狀態列**長得跟 IDE 的盡可能一樣**，現在的樣子差蠻多的」
> 「**然後選單也是學 IDE**」「**然後應該靠右，跟 IDE 一樣**」
> 「還有這個檔案，應該放在 Semorphe 右邊，**像是一般視窗軟體那樣**」
> 「**程式碼視圖應該預設在左邊**，像一般 IDE 的習慣」

⚠️ 這六句是**分五次講的**——而每一次都是看到上一版之後才講得出來的。

> **「像 IDE」在說出口的時候是一句形容詞；
> 它要被拆成「沒有框、沒有箭頭、靠右、頂端置中的清單、
> 功能表在標題旁、程式碼在左」才變成可以做的事。**
> 而拆解的人不是提出的人——**是把它做出來給他看的人**。

### 四個決定

| 決定 | 為什麼 |
|---|---|
| picker ＝ **文字項目**，不是 `<select>` | 洗得掉外框，**洗不掉那張原生清單** |
| 選單 ＝ **QuickPick**（頂端置中、可過濾、鍵盤可走、支援多選） | 位置不是美感——使用者的肌肉記憶在那裡 |
| 整組**靠右**，順序照 `panel.ts` 的優先序 | 同步 100、picker 99 遞減；VSCode 右側**優先序愈大愈靠左** |
| 程式碼**在左**、積木在右 | 與 VSCode 的「編輯器在左、面板開在右」同一個版面 |

### 🟢 而它們長得一樣的原因不是有人照著抄

```
ControlState ──→ createStatusBarItem ＋ showQuickPick   （IDE）
             ──→ 文字按鈕 ＋ ui/toolbar/quick-pick.ts    （網頁版）
```

> **兩邊長得一樣，不是因為有人照著抄，
> 是因為它們畫的是同一份東西。**

### ⚠️ 過程中踩到的三個

1. **同步的入口消失了**——picker 搬進狀態列時，把「`⇄ 同步` 留在工具列」
   那個判斷一起刪掉了。三態還看得見，**而按不下去**。
   > 把一顆按鈕換成一段長得一樣的字，使用者要按到第二次才會發現它壞了。
2. **`innerHTML =` 把 picker 清掉**——`updateStatusBar` 原本整條列重寫。
   > 一個用 `innerHTML =` 更新文字的地方，在那塊區域長出第二個東西的那一天，
   > 會安靜地把它清掉。
3. **檔案選單搬家之後變成瀏覽器預設的灰框**——它的樣式掛在
   `.quick-access-bar button` 上。
   > 搬動一個元素等於搬離它的樣式作用域；而「功能還在」會讓人以為搬完了。

### 行動版：沒有動（依使用者授權）

那四顆下拉仍在漢堡選單裡。桌機的狀態列改成文字項目之後它們**沒有地方可待**，
所以有一個只在 `mobileLayout` 宿主才建的暫存處（`#mobile-selector-parking`）。
⚠️ 它不是「建了再藏起來」——**視窗寬度隨時可能跨過斷點**。

## 六之五、🔴 流程住錯格了——**關係層被放進了狀態層**

2026-08-25 查證（使用者問「流程面板也要開始考慮放哪裡」時發現的）：

```ts
// src/ui/layout/mobile-tab-bar.ts:1
export type TabId = 'blocks' | 'code' | 'console'
```

**三個分頁，沒有流程**——而 §一之二 拍板的是四個。
而桌機版的流程今天是**下方面板的一個分頁**（與主控台、變數並排），
⚠️ 而 §六 的 slot 詞彙逐字寫著：

```
editor   程式碼 · 流程 · 積木 · 圖鑑 · 設定頁
panel    主控台 · 變數 · 圖解
```

### 判準不是「它多大」，是**它是哪一層**（[[理解的層次]]）

流程是**關係層**，與積木（空間層）同級：兩者都是**程式本身的投影**、
都需要面積、都可編輯。主控台與變數是**狀態層**——執行時才有東西看。

> **把關係層塞進狀態層那一格，等於宣稱「流程是執行的產物」
> ——而它不是，它是程式的另一個投影。**

### 落點

| 宿主 | 放哪 |
|---|---|
| **IDE** | 自己的編輯器分頁——`semorphe.openFlow`，與 `semorphe.openBlocks` 同形 |
| **網頁版桌機** | `editor` 區的第三格。⚠️ 而 SplitPane 只有兩格——**最省的一步是讓右欄變成分頁（積木｜流程）**，不要一次做三欄拖曳 |
| **手機** | 第二個分頁（補上就是） |

### 🎯 而它有一個**會自己成立**的結果——那是一個可否證的預測

可編輯的流程 ＝ 第三個可寫視圖 ⇒ `viewsWith('editable')` 變三個
⇒ **同步選單的「以哪一邊為準」自動長出第三項**。

那正是同步從「方向」（N²）改成「來源」（N）的理由。

> **這一格不該需要改任何同步的程式碼；
> 如果需要，那就代表那一刀做錯了。**

### 🔴 而它是**兩刀**，不是一刀（2026-08-25 使用者確認後補）

> 使用者：「**流程面板現在是唯讀，未來會改成可編輯**」

```
② 流程進 editor 區      唯讀的流程也搬得動——它只是換一個 slot
②′ 流程可編輯           改 flow-panel.ts:60 那一格 editable: false → true
```

⚠️ **兩刀分開排的理由**：②只是版面，②′會讓它變成**第三個真相來源**
——同步、存檔、衝突解決全部要面對它。混成一刀的話，版面出問題與
資料出問題會**同時發生而分不出是哪一個**。

🟢 而好消息是那一格**已經是宣告**（`capabilities.editable`），不是散落的判斷：
② 做完之後，②′ 的第一步就是把 `false` 改成 `true`，然後看
`viewsWith('editable')` 有沒有自己長出第三項。

> **一個「改一格布林就能驗證的預測」，比一段解釋值錢。**

## 六之六、主控台與 IDE：**不是搬面板，是走它已經有的四個管道**

現況（`src/vscode/panel.ts:66`）只有一行：

```ts
const OUTPUT = vscode.window.createOutputChannel('Semorphe')
```

**沒有 DiagnosticCollection、沒有 Terminal、沒有 Debug Adapter。**

> **搬面板只是換了個位置；走管道才拿得到 F8、紅色波浪線、中斷點，
> 以及使用者已經會的每一個快捷鍵。**

| VSCode 的家 | 我們的 | 機制 |
|---|---|---|
| **Problems** | 診斷 | `languages.createDiagnosticCollection` |
| **Output** | 工具日誌 | 已經有 ✔ |
| **Terminal** | 主控台（**會讀輸入**） | `Pseudoterminal` |
| **Debug Console ＋ Variables ＋ Call Stack ＋ 中斷點** | 變數面板 ＋ 逐步 | **DAP** |

### 三刀，由便宜到貴

1. **診斷 → Problems**——最便宜、報酬最高，**完全不必動執行器**。
   今天診斷只活在面板裡；接上之後錯誤進 Problems、檔案總管標紅、`F8` 逐個跳。
2. **主控台 → Terminal，不是 Output**。🔴 理由很硬：我們的程式**會讀 `cin`**，
   而 **Output channel 是唯讀的**。
   > **一個唯讀的輸出格會讓「輸入」沒有家——而那正是主控台今天存在的理由。**
   搬進 Output 等於把它的一半功能丟掉。
3. **變數／逐步 → Debug Adapter**（終局）。`execution-controller` 的六個模式
   （執行／除錯／動畫×3／逐步）對得上 `continue / next / stepIn / pause`。

⚠️ **別把 DAP 跟 [[執行器是可插拔的]] 混成一件事**：
DAP 是**另一個宿主介面**，不是另一個執行器。混掉會長出一個
「VSCode 專用的執行器」，而那違反宿主獨立性（P9）。

## 六之七、行動版：**同一份宣告的第三個渲染器**

| **副作用** | `#mobile-selector-parking` 與那四顆 `<select>` **一起退場** |

## 六之八、順序（🟢 前四刀已交付，2026-08-25，0.10.0）

```

✅ ② 流程進 editor 區          版面
✅ ③ 行動版四分頁 ＋ sheet     順手清掉 parking 與四顆 select
✅ ④ 主控台 → Terminal        要處理輸入，中等
⏳ ⑤ 變數／逐步 → DAP          大，且要先實測 Theia（**人拍板：前四刀**）
```

### 🔴🔴 最貴的一個：**CI 從 00:20 起就紅了，而是使用者告訴我的**

2026-08-25 一天之內改了六刀 UI（控制項離開面板、網頁版狀態列、流程進 editor、
行動版、主控台→終端機、行動選單），每一刀都跑了 `npm test`（5600+ 綠）
＋ 開瀏覽器實測。**而 e2e 一次都沒跑。**

CI 的 e2e **19 紅**，而它們指向的是同一批東西：

```
15 支  在等 `程式碼→積木`      ← 同步那一刀刪掉的方向按鈕
 3 支  在等 `積木→程式碼`      ← 同上
 4 支  在 `select.topic-dropdown` 上 selectOption  ← 那幾顆下拉退場了
 1 支  數 `.toolbar-select`    ← 同上
```

> **`npm test` 驗的是「這些函式做對了嗎」；
> e2e 驗的是「**使用者按得到的東西還在不在**」。
> 而我這一天做的每一刀，改的正好都是後者。**

⚠️ 而「開瀏覽器實測」也沒抓到——**因為我實測的是我剛做的那條路**，
不是那些**沒有人再去看的舊路**。

🔴 **判準**：`CLAUDE.md` 的那張表要多一列。
改動只要動到「使用者按得到的東西」（按鈕、選單、面板結構），
**`npm run test:e2e` 就不是 PR 的事，是這一刀的事**。

### 🔴 交付之後使用者抓到的三件事（2026-08-25，全部已修）

**一、行動版的選單「使用者體驗不好」。** 舊的是漢堡從**上面**掉下來，
點一列又從**底部**彈出 QuickPick。

> **一次操作裡換兩種介面，使用者要重新找一次「按哪裡」。**

改成**兩層都是同一張 QuickPick**（第一層是控制項＋目前的值，第二層是值）。
🪦 `MobileMenu`、`renderSheetControls`、`mobile-sync-btn`（與狀態列那顆重複）一起退場。

**二、「為何變數面板還在積木面板那裡？」** ——變數是⑤的內容（它的家是
Debug 的 Variables 視圖）。🔴 **而截圖裡那個不是「留在原地」，是一個退步**：
`execution-controller` 有四處呼叫 `showTab('console')`，而主控台已經搬去終端機，
舊的 `showTab` 照樣展開、照樣把每一格藏起來 → **半個高度的空面板**。

> **移走一格 UI 而沒有移走它的呼叫端，那些呼叫不會報錯
> ——它們會把版面弄成一個沒有人要的形狀。**

**三、Arduino IDE 打不開終端機**（見「未決」那一條）。而重點不是難看，
是**執行的輸出會完全沒有出口**。

### 🔴 做完之後才看得清楚的三件事

**一、②那個「會自己成立」的預測【還沒被驗到】。**
流程搬進 editor 區時它**仍然是唯讀**（`flow-panel.ts:60`），
所以 `viewsWith('editable')` 還是兩個。預測留著，等 ②′。

> **一個預測沒有被觸發，不等於它被驗證了。**

**二、面板的 action 按鈕原本是【逐顆用 id 接】的。**
宿主那側走登錄表，而面板那側寫死四顆。加「積木 ｜ 流程」之後
**宿主按得動、面板按了沒反應**，而**沒有任何測試會紅**。

> **同一種東西有兩個接線處，第二次加東西的時候一定只會接到其中一個。**

**三、「主控台在哪」不該是第五格布林——它是登錄表的一列。**
新增 `ControlKind` 的 `output` 與 `ControlSurface` 的
`panelBottom` / `hostTerminal`。🟢 而那是我自己的護欄逼出來的：
第六十三條的驗收①「`HostFeatures` 布林數只准下降」。

> **一條擋得住作者本人的護欄，才算擋得住。**

## 七、快速切換版面：**一份預設宣告，三個渲染器**

> 使用者 2026-08-25：「我希望做一個可以**快速切換版面配置**的功能，
> 就是點下去之後，或跳出一些**建議的版面配置示意圖**，選下去就可以用那個版面」

⚠️ **這不是新方向，是 §六 那條決定的介面**。`§六` 逐字：

> 「**佈局預設**（專注積木／對照／三欄）＋ 可拖分隔線。**不做自由 docking**」
> 「**版面由 profile／topic 決定，不是由使用者拖。**」

> **「不做自由 docking」的替代品，就是「給幾個好的預設讓人挑」
> ——而那個決定一直缺一個介面。**

### 七之一、🔴 先拆成兩件事，因為它們的宿主邊界不同

```
① 哪幾個視圖開著     跨宿主都有意義    我們說了算
② 它們怎麼排         只有網頁版歸我們   IDE 的版面是宿主的
```

`§六` 逐字：「🟢 **VSCode 那側的佈局工作幾乎是零**」——在 IDE 裡「排」是
VSCode 原生的 split，我們去動它就是跟宿主打架（P9 宿主獨立性）。

**而 ① 在 IDE 完全成立**：「專注積木」＝ 只開積木分頁；
「對照」＝ 積木開在程式碼旁邊（`ViewColumn.Beside`，2026-08-25 已經在用）。

> **一個預設在 IDE 裡是「開哪幾個」，在網頁版裡是「開哪幾個 ＋ 怎麼排」
> ——而前者是後者的子集，不是另一件事。**

### 七之二、示意圖：同一份宣告、三個渲染器

與 [[控制項登錄表]] 同一個形狀（`§六之三`）：

```
LayoutPreset ──→ 網頁版：縮圖格（小 SVG，點一下套用）
             ──→ IDE：QuickPick（框線字元當縮圖）
             ──→ 手機：不出現（它本來就是分頁切換）
```

⚠️ **VSCode 的 QuickPick 放不了圖片**（只有 codicon）。而框線字元在等寬字型下夠用：

```
┌─────┬─────┐   對照
│ 程式 │ 積木 │
└─────┴─────┘
```

🔴 **要在 IDE 裡放真的圖，就得是我們自己的 webview**——而那會是第四個
「不在宿主 chrome 裡的東西」，與 2026-08-25 一整天的方向相反。**否決。**

### 七之三、預設清單（按[[理解的層次]]）

| 預設 | 版面 | 什麼時候用 |
|---|---|---|
| **專注積木** | 積木佔滿 | 初學、純積木課 |
| **對照** | 程式碼 ｜ 積木 | 最常用；今天的預設 |
| **關係** | 程式碼 ｜ 流程 | 讀懂一段別人的程式 |
| **執行** | 程式碼 ｜ 積木 ＋ 主控台展開 | 跑起來看輸出 |
| **三欄** | 程式碼 ｜ 流程 ｜ 積木 | 🔴 **前置沒到**（見下） |

### 七之四、⚠️ 三個硬東西

**一、三欄要先有 N 路分割。** `src/ui/layout/split-pane.ts` 只有
`getLeftPanel()`／`getRightPanel()`——**兩格，寫死的**。
三欄**不是多加一個預設，是一個機制**。

**二、🟢 它會吃掉一段臨時的判斷（好消息）。**
2026-08-25 讓「切不切版面」由 `codeEditorPane || 有下方面板` 決定
（`app-shell.ts`）——**而那應該是預設說了算**。做這一刀時那段要退場，
否則會有兩個「版面是什麼」的真相。

> **它不是新增一層，是把一個臨時的判斷換成一份宣告。**

**三、存在哪。** 🟡 **意見：使用者層級**（網頁版 localStorage、IDE 走設定），
**不進 side-car**——「我習慣怎麼排」跟著**人**走，不跟著**檔案**走。
而 `§八` 的 A 已經把「哪些面板開著」判給使用者，這一條與它同族。

### 七之五、🟢 選了預設之後**還能拖**（2026-08-25 使用者拍板）

於是「記哪一個」有一個不必再問的答案——**兩個都記，而它們是不同的東西**：

```
preset   使用者【挑】的那一個      對照
ratio    使用者【拖】出來的比例    0.62
```

> **預設是起點，拖出來的是狀態——把它們寫成同一格，
> 就得在「回不到乾淨的起點」與「每次丟掉調整」之間二選一。**

🟢 **而這樣切之後，「重置」不需要一顆按鈕**：

> **再選一次同一個預設 ＝ 重置。**

⚠️ 清單裡把目前那個標成「目前」（與 QuickPick 一致）。而拖過之後它仍然
標「目前」——**因為使用者確實還在那個版面上，只是調過寬度**。

🟡 上面「兩個都記 ＋ 再選一次即重置」是**從「還能拖」推出來的**，
不是使用者逐字說的——做之前值得再確認一次。

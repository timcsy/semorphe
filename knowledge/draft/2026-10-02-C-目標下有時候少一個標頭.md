# C 目標下有時候少一個標頭——而它只在多檔並跑時發作

> 日期：2026-10-02
> 怎麼冒出來的：驗第 291 刀（`tree.delete()`）的 e2e 時，4 支紅。三支判得掉，
> 這一支**簽名不對**——不是等不到畫面，是內容斷言。
>
> 🟡 **狀態：確認是真缺陷、確認與那一刀無關、而根因未找到。**
> 本檔記的是**證據與排除過的假說**，免得下一個人重推一遍。

---

## 症狀

`e2e/c-target.spec.ts:165`「使用者自己寫的 `#include`，在 C 目標下也要換掉」：

```
Expected substring: "stdio.h"
Received string:    "int main() {      ← 產出的程式碼【少了標頭】
```

⚠️ **這不是 CLAUDE.md 記的那種假紅。** 那一條的簽名是
`expect(locator).toBeVisible() failed`（等不到畫面）；這一支是**內容斷言**。
**簽名不同，所以那條判準不適用。**

## 🔴 它是真的，而且與第 291 刀無關（收起改動對照過）

```
有第 291 刀的改動   --repeat-each=6  紅 1 次
沒有那一刀          --repeat-each=6  紅 2 次   ← 同樣的簽名
```

## 排除過的假說（這一節是本檔的價值）

```
❌ 「等得不夠久」      輪詢量過：好的那幾輪,stdio.h 在【約 110ms】就出現
❌ 「出現後被蓋掉」    錄整段時間軸：壞的那一輪在 63ms 就是 "int main() {",
                     而它【兩秒內都沒有變】⟹ 最終狀態早就定了,定錯就一直錯
❌ 鷹架深度 0         深度 0 會連 main 一起剝掉,而壞的輸出【有 main】
❌ shaping 還沒載好   它是【建構時一次性】建立的,不隨目標變
❌ CPU 負載           起六個 CPU 燒滿的行程,8 次全好
```

## 🔴 而唯一的必要條件目前是：**多檔並跑**

```
單獨跑這一支          28 次全好（--repeat-each=14 ×2）
單獨跑 ＋ CPU 負載     8 次全好
多檔並跑              紅過三次（整輪 28 分一次、四檔並跑兩次）
```

⟹ 所以它**不是** CPU 競爭，而是某個與「同時有別的 page／worker」相關的東西。
而這也是為什麼我沒找到根因：**在隔離環境裡它不發作，而加上儀器之後更不發作。**

## 🔴 2026-10-03 再追一輪：還是重現不了，而排除清單長了三條

```
❌ 瞬時 CPU 負載      六個燒滿 CPU 的行程 ＋ 8 次 —— 全綠
                     （上一輪就排除了,這次再確認）
🔴 ❌ 輪詢式的觀測     每 100ms 一次 page.evaluate → 5/5 全綠
                     ⟹ 【儀器本身改變了被量的東西】—— 它逼著事件迴圈轉
❌ 不打擾的複製       逐字照原測試（一次固定等待、讀一次）× 6 —— 全綠
❌ 原指令事後重跑      完全相同的那道指令 × 6 —— 12/12 全綠
```

🔴 **而紅過的兩次，都在【剛跑完 28 分鐘整輪 e2e 之後】。**

⟹ 條件是「**一次長跑累積出來的狀態**」，而那在實務上**量不來**
——要量它就得再跑一次長跑，而長跑本身就是那個條件。

### ⚠️ 而那一輪我自己又學到一條

> **一個會輪詢的儀器，可能會把它要抓的東西抓不到
> ——因為輪詢讓那個系統有機會把事情做完。**

（我第一版的時間軸探針每 100ms 問一次，而它 5/5 全綠。
改成「一次固定等待、讀一次」之後才跟原測試同形。）

### 🟡 一個沒驗證的時間巧合，記著但不要當結論

會紅的那兩次，是在 `tree.delete()` 的洩漏修好**之前／同時**。
那個洩漏是**每次 parse 漏 0.9 MB**，而一次 28 分鐘的 e2e 會 parse 幾千次
——所以當時的長跑累積的不只是時間，還有**幾百 MB 的 wasm 記憶體**。

⚠️ 而這**不構成證據**：我當時收起改動對照過，沒有那一刀它紅得更頻繁（2/6 vs 1/6）。
記在這裡是因為下一個人該知道「那兩次的環境已經不存在了」。

## 🟢 所以改成設陷阱，而不是繼續追

重現不了就不要再花時間重現。`e2e/c-target.spec.ts:165` 裡已經放了一段
**只在失敗時才跑**的 dump（target／skeleton／depth／style／topic／元件清單）。

> **下次它自然發作的時候，它會自己把現場說出來。**

而那一刻才是真正有資訊的時刻——比任何一次合成重現都接近真相。

## 好的那一輪，狀態長這樣（給下一個人當對照）

```
target    {"id":"c","name":"C","topic":"c-beginner","style":"c"}
skeleton  main｜depth 2
ids       cpp:program, cpp:include ×2, cpp:func_def, cpp:var_declare,
          cpp:literal_number, cpp:print_formatted, cpp:var_ref, cpp:return
```

🔴 **壞的那一輪的同一份 dump 我沒抓到**——那大概就是答案。
下一個人要做的第一件事是**在多檔並跑的情境下**把這份 dump 抓出來。

## 為什麼它值得修，而不是調測試

```
產出的程式碼少一個標頭 ⟹ 它【編不過】
而學生看到的就是那段程式碼
```

⚠️ 而「把固定等待改成輪詢」**不會讓它變綠**——壞的狀態是**永久的**，
輪詢只會等滿逾時。那個測試是對的，飄的是產品。

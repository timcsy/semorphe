# 經驗

從 Semorphe 開發中蒸餾出的教訓——理論與實作碰撞後留下的東西。完整的因果軌跡在 [history/](history/)，完整的除錯現場在 [episodes/](episodes/)。

## 教訓

### 型別分裂在「兩邊都能跑」時最危險

- **理論說**：根公理定義了 SemanticNode 的標準形式，實作照著寫就好。
- **實際發生**：同時存在兩套不相容的 SemanticNode 定義（`children` 一個是 `SemanticNode[]`、一個是 `SemanticNode | SemanticNode[]`）。TypeScript 的 structural typing 讓聯合型別在某些用法下相容，**靜態檢查不報錯**，問題直到 runtime 才爆炸。interpreter 因此塞滿 `as SemanticNode` 斷言和 `Array.isArray()` 判斷。
- **解決方式**：統一為單一定義（陣列版 children），刪除 `semantic-model.ts`，工具函式遷入 `semantic-tree.ts`，約 15 個檔案的 import 更新 + 所有測試重寫。
- **教訓**：型別分裂是漸進開發的自然結果，關鍵是**發現時立刻統一，不要因為「兩邊都能跑」就容忍共存**。structural typing 會隱藏不一致，必須靠 review 或定期掃描發現。
- **來源**：[history/001-兩套-semanticnode-型別統一.md](history/001-兩套-semanticnode-型別統一.md)

### R0 雙射是設計目標，不是工程現實

- **理論說**：P1 定義 blocks 投影為 R0（雙射），`lift(project(T)) ≡ T`，投影是純函數。
- **實際發生**：Blockly 有大量有狀態的副作用——動態積木的 FieldDropdown 選項來自即時掃描 workspace（不是 `project(tree)` 能覆蓋的）、mutator 的 `decompose()`/`compose()` 生命週期由 Blockly 控制、積木的視覺狀態和語義資訊被框架混在一起。
- **解決方式**：承認投影不純但確保語義層等價——用 `const self = this` 把 workspace 狀態注入投影過程；用 `extraState` 補語義樹與積木之間的間隙；把反向過程命名為 `extractBlockInner()` 而非 `lift()`，在命名上承認它不是理論中的純投影反函數。
- **教訓**：在第三方 UI 框架中，投影管線必須適應框架的狀態模型。**正確做法是確保 roundtrip 結果在語義層等價，即使中間經過了有狀態的中介。**
- **來源**：[concepts/積木投影管線.md](concepts/積木投影管線.md)

### 四路完備性需要自動化驗證，不能靠記憶

- **理論說**：P2 要求每個概念有四條路徑（lift → render → extract → generate）。
- **實際發生**：加入 `u_negate` 積木時完成了 BlockSpec、動態積木、generator、測試，卻忘記在 `UNIVERSAL_CONCEPTS` registry 註冊。結果 diagnostics 報「unknown concept」、code-to-blocks 轉換失敗，但**積木本身能正常使用**，容易讓人以為沒問題。根因是四條路徑分散在不同檔案，沒有統一檢查點。
- **解決方式**：補上 registry 條目，並建立認知——新增任何概念時第一步就是註冊。
- **教訓**：**靠開發者記憶力不可靠。** 應寫測試或 lint 規則：遍歷所有 BlockSpec 的 `conceptId`，檢查每個都在 registry 中存在。
- **來源**：[concepts/概念代數.md](concepts/概念代數.md)

### P4 在理論上是一維的，在實作中是多維的

- **理論說**：漸進揭露只要 `level <= currentLevel` 就能決定積木是否顯示。
- **實際發生**：IO 偏好（iostream vs cstdio）需要額外維度；某些積木只在特定 Code Style 下有意義；語言專屬積木和 universal 積木的 level 需要協調。而且切到 L0 時 workspace 上可能已有 L1 積木，使用者看到 toolbox 沒有卻在畫布上有，會困惑。
- **解決方式**：`buildToolbox()` 實作多維度過濾（level × category × ioPreference × language）；workspace 既有積木不受層級切換影響（只影響 toolbox 可用性）；level 值由教育判斷決定並記錄在 BlockSpec，工程只負責正確過濾。
- **教訓**：**不要試圖用單一 level 數字解決所有問題。** 接受過濾邏輯天然需要多個正交維度，但維度之間的職責必須分清（Topic 管層級樹結構、Level 管可見性、View Params 管呈現）。
- **來源**：[concepts/漸進揭露.md](concepts/漸進揭露.md)

### 「只加 JSON 不改程式碼」不等於「不影響既有行為」

- **理論說**：P3 開放擴充——新概念可加入而不破壞既有結構。
- **實際發生**：`c_pointer_op` 的 astPattern 宣告 `nodeType: "unary_expression"` 但 constraints 為空，結果 `++i`（tree-sitter 也分類為 unary_expression）被搶匹配成指標操作而非 increment。Pattern Engine 按登記順序嘗試，**先匹配到的就贏**。
- **解決方式**：禁止空 constraints（除非該 nodeType 全局唯一）；歧義改在**註冊時**偏序仲裁而非執行時碰運氣。這個經驗直接推動了第一性原理的修訂。
- **教訓**：**禁止歧義比仲裁歧義更安全。** 開放擴充的前提是新 pattern 不能改變既有 pattern 的匹配結果——這個保證必須由註冊時的檢查提供，不能靠開發者自律。
- **來源**：[history/005-pattern-歧義從禁止到偏序仲裁.md](history/005-pattern-歧義從禁止到偏序仲裁.md)

### 第一性原理提供方向，不提供具體設計

- **理論說**：CLT 說「最小化外在認知負荷」，Sc3 說「一個積木 = 一個語法結構」。
- **實際發生**：怎麼最小化需要反覆試錯。積木文字 `"宣告 %1 型別 變數 %2"` 讀起來生硬，改成 `"宣告 %1 變數 %2"` 又讓 `%1` 語義模糊；變數名用 FieldTextInput 會讓初學者輸入不合法名稱，改成 FieldDropdown 又在 workspace 沒有變數時讓 Blockly 拋錯；I/O 參數從純 ValueInput（太複雜）到純 Dropdown（無法輸入常數）走了三個版本才收斂到三模式。
- **解決方式**：message 拆成獨立 label key，每段都有明確語義；dropdown 加 fallback 選項；三模式（select/compose/custom）讓簡單情境用最低認知負荷、複雜情境保有完整表達力。
- **教訓**：**積木文字和互動模式的設計本質上是 UX 問題，不能純靠理論推導。** 原理負責否決錯誤方向，不負責生出正確設計。
- **來源**：[history/012-io-參數從單一模式到三模式.md](history/012-io-參數從單一模式到三模式.md)

### 需要 parse 回結構才能用的字串，就不該是字串

- **理論說**：P2 定義 properties 為 `Record<string, PropertyValue>`，但沒規定何時用字串、何時用結構化物件。
- **實際發生**：`func_def` 的 params 存成字串陣列 `["long long base", "int y"]`。同一份字串在四個環節被不同方式解讀——lifter 整串存入、generator 照原樣拼接（正確）、renderer 用 `split(/\s+/)[0]` 取型別（`long long` 被截斷成 `long`）、extractor 從 UI 欄位讀（正確）。
- **解決方式**：短期用已知複合型別清單做前綴匹配（從最長候選開始）；長期應結構化為 `[{ type: "long long", name: "base" }]`。
  → **✅ 長期那條已經做了**（2026-08-07 實測確認）：`func_def` 的參數現在是 `param_decl` 子節點，`{type: "long long", name: "base"}`／`{type: "const string&"}`／`{type: "int*"}` 全部完整。**這一欄曾經過期**——教訓成立，而狀態寫著一個已經付掉的債。
- **教訓**：**判定準則——如果一個屬性值在管線中需要被拆分或解析，它就不該是字串。** 壓扁的唯一合理場景是該值只會被完整傳遞、不會被拆分。
- **來源**：[concepts/概念代數.md](concepts/概念代數.md)

### 複製貼上積木定義是序列化契約分裂的溫床

- **理論說**：同一概念的 statement 版和 expression 版只是投影差異，語義相同。
- **實際發生**：`u_input_expr` 是從 `u_input` 複製貼上再改的。`u_input` 的 `saveExtraState` 讀 `getFieldValue('SEL_i')` 存成 `{ text }`，`u_input_expr` 卻直接複製內部狀態 `argSlots_`，而 dropdown validator 寫入的是 `selectedVar` 不是 `text`。`STATEMENT_TO_EXPRESSION` 映射直接搬移 extraState，欄位名不一致導致 `cin >> s` 變成 `cin >> x`——**所有變數 fallback 成預設值**。
- **解決方式**：兩版本的 `saveExtraState`/`loadExtraState` 格式統一，抽成共用函式而非各自實作。
- **教訓**：**序列化格式是隱式的 API 契約**，違反不會在編譯期報錯，只在特定語境（如 if 條件中的 cin）才暴露。新增雙版本積木時共用序列化函式，不要複製貼上。
- **來源**：[episodes/2026-03-12-cin-變數名靜默降級.md](episodes/2026-03-12-cin-變數名靜默降級.md)

### 功能完成 ≠ 功能接通

- **理論說**：auto-include 的元件都寫好了——ModuleRegistry、`computeAutoIncludes()`、工廠函式、`GeneratorContext.moduleRegistry` 欄位。
- **實際發生**：UI 層從來沒呼叫 `setModuleRegistry()`。`GeneratorContext` 建構時 `moduleRegistry` 永遠是 `undefined`，`if (ctx.moduleRegistry)` 永遠不進去。**所有單元測試都通過**（因為測試手動注入了 registry），但瀏覽器中功能完全無效。同一時期 `ModuleRegistry.register()` 還寫錯欄位名（`concept.id` 而非 `concept.conceptId`），structural typing 沒報錯，registry 靜默註冊了一堆 `undefined` 當 key。
- **解決方式**：加入全域 setter 並在初始化時呼叫；修正欄位名；認識到依賴解析架構上該抽離為獨立的 Scaffold 層。
- **教訓**：**端到端驗證不可省**——單元測試手動注入依賴會繞過真實的接線路徑。**全域 setter 模式的風險**：呼叫順序和遺漏都無法被型別系統捕獲。
- **來源**：[episodes/2026-03-10-auto-include-寫好了卻沒接上.md](episodes/2026-03-10-auto-include-寫好了卻沒接上.md)

### 四路完備性不等於可執行

- **理論說**：P2 的四路完備性（lift → render → extract → generate）保證概念正確。
- **實際發生**（現場：[episodes/2026-03-12-cmath-pow-回傳0](episodes/2026-03-12-cmath-pow-回傳0.md)）：`<cmath>` 概念完成四路、round-trip 測試全過，但使用者按「執行」時 `pow()` 算出 0，二次方程式解錯。原因是「執行」走的是 `SemanticInterpreter` 而非 C++ 編譯器，而這些概念沒註冊 interpreter executor——interpreter 原本的邏輯是 `if (concept.includes(':')) return`，**靜默跳過所有語言特定概念**，回傳 `undefined` 一路轉換成 `0`。
- **解決方式**：四路完備性擴充為五層（加執行層）；移除靜默跳過改查 executor registry；宣告性概念註冊 noop executor；未知概念透過 `unknownConceptHandler` 讓使用者選擇跳過或中止。
- **教訓**：**編輯管線的完備性不等於執行管線的完備性。** 宣告性概念也要註冊 noop executor，才能區分「已知不執行」和「未知」。
- **來源**：[history/011-四路完備性擴充為五層.md](history/011-四路完備性擴充為五層.md)

### 靜默降級是 bug 的藏身之處

- **理論說**：fallback 值提供 null safety，讓系統在資料缺失時不崩潰。
- **實際發生**：`cin >> s` 變成 `cin >> x` 的 bug 有**四層防線，每層都靜默降級為同一個預設值 `'x'`**——沒有 console.warn、沒有 annotation、沒有任何可觀察的信號。從使用者角度程式碼「就是錯了」，但系統毫無提示。多層 fallback 用同一預設值會互相掩蓋，讓真正的資料遺失點無法定位。
- **解決方式**：改為優先嘗試恢復（如檢查 `selectedVar`、讀正確的欄位名），只在確實沒有更好選擇時才用預設值。
- **教訓**：**「資料格式不符預期」不等於「沒有輸入」。** 前者應該嘗試恢復或發出信號，後者才用預設值。這也是「不做向後相容」的另一面——`??` 是 null safety，不是吞掉舊格式的工具。
- **來源**：[episodes/2026-03-12-cin-變數名靜默降級.md](episodes/2026-03-12-cin-變數名靜默降級.md)

### Extractor 讀的欄位名必須與積木定義一致

- **實際發生**：`getFieldValue('VAR')` 是想像中的欄位名，真實積木用的是 `'SEL_0'`（動態 dropdown）或 `'NAME'`（JSON blockDef）。`getFieldValue` 對不存在的欄位**只回傳 null，不報錯**，所以這類不匹配在靜態分析中很難發現。
- **解決方式**：修正欄位名並建立 fallback 鏈（`'SEL_0'` → `'NAME'` → 預設值）。
- **教訓**：欄位名稱改動必須**全鏈路同步**：blockDef → extract → generate → lift → adapter。**Extractor 測試應覆蓋「欄位名正確性」**——用 mock block 驗證讀取的欄位名確實存在於積木定義中。
- **來源**：[concepts/積木投影管線.md](concepts/積木投影管線.md)

### 同一概念同時有 template 和 hand-written generator，測試會騙人

- **實際發生**：`input` 概念同時有 universal template 和 hand-written generator。真實 app 中 template 優先，但測試中（未載入 template）hand-written 優先。**測試通過但實際行為不同。** 更早之前也發生過開發者寫了 hand-written generator，卻因為 JSON 還留著 `codeTemplate` 而完全不會被執行，本人毫不知情。
- **解決方式**：兩者互斥——改用 hand-written 時必須從 JSON 刪除 `codeTemplate`；若必須並存，測試要明確覆蓋兩條路徑。
- **教訓**：**優先移除 hand-written generator，讓 template 成為唯一來源**（減少雙真相源）。雙真相源的代價不只是維護成本，還包括「測試環境與生產環境走不同路徑」這種最難察覺的失敗模式。
- **⚠️ 敘述已過期，警告仍成立（2026-08-06 實測更正）**：原文說「真實 app 中 template 優先」。**實際上 app 從來沒接上 TemplateGenerator**——`setTemplateGenerator()` 在 `src/` 內零呼叫、唯一會接它的 `initCppModule()` 是死碼。所以 app 恆走 hand-written，而**93 個概念宣告的 `codeTemplate` 一行都沒被用到**。
  兩組態比對（`audit-completeness`）進一步發現：其中 **35 個元件在「接上 template」與「不接」下產出不同的程式碼**，而且有些 template 是**壞的**——`cpp_auto_declare` 會吐出未取代的佔位符 `auto x = ${VALUE};`。**因為從來沒被執行過，所以沒人知道。**
  → 原文的**方向**（雙真相源會讓測試與生產走不同路徑）完全正確，只是這次是「宣告了一整套、實際上一條都沒走」——比走錯路徑更難察覺。
- **來源**：[concepts/積木投影管線.md](concepts/積木投影管線.md)、`specs/049-audit-guardrails/research.md` F1–F3

### 論證會壞在三種地方，只自查第一種會漏掉另外兩種

2026-08-05 跨專案協商（五封往返）裡，本側的論證壞了四次，**失敗模式有三種**，前兩種靠自查抓到、後兩種靠對方抓到：

| 模式 | 實例 | 為何難自查 |
|---|---|---|
| **搬別處的權威句子** | 「投影是超集」與五槽「並列不包含」自相矛盾；「發現而非發明」原本講語義概念 vs λ-core，被誤套到物理零件；「不計成本，故豁免」豁免錯了層 | 引用的句子本身是對的，錯在**適用範圍** |
| **類比推過頭** | 「Rust 的 aliasing XOR mutability 就是麵包板的一個 driver 多個 reader」——被 open-drain／I2C 砍掉（多 driver 合法） | **前 90% 都對**，只有最後一步不成立 |
| **推導沒走完** | 同時寫了「`balance` 永遠可滿足」和「數位模型把 DRC 慣例烘進模型」，**沒發現後者就是前者的例外來源**（理想化） | 兩半都在紙上，**看起來已經完整** |

**教訓**：自查時除了問「這個論據撐得住嗎」，還要問「**這個類比在哪裡開始不成立**」和「**我寫下的兩件事之間有沒有沒接起來的關係**」。

**附帶發現**：敵對式驗證的產出常常不是「你錯了」，而是「**你的東西比你以為的更站得住，只是理由不是你講的那個**」——那句被砍掉的麵包板等式，若成立反而會讓兩律變成同一條律、使分律過不了 over-justify。**對方的更正救了本側的提案。**

- **來源**：ArduinoCAD `draft/2026-08-05-回送semorphe-*.md`（五封）、[concepts/元件.md](concepts/元件.md)

### 豁免一條反對意見時，要指名豁免的是它的哪一層論據

- **實際發生**：跨專案詞彙統一時，使用者說「不計成本、不計代價」。我方用這個豁免推翻了 ArduinoCAD 的一條教訓（「加法式併行通道 >> 加寬共享型別」），理由是「那條的理由是 blast radius＝成本，故豁免」。**查證後那條教訓有兩層理由**：成本層（blast radius）**＋語義層**（「數位 HIGH/LOW 本是類比電壓的量化讀數，兩者本就分層」；判準是「先問這是**加法**還是**改寫**」）。語義層不是成本論，豁免不到它。
- **對方一句話點破**：**over-justify 不是成本測試——所以「不計成本」不能替一個抽象脫罪。** 抽象要嘛多解釋、多預測、要嘛壓縮；三個都不中就是裝飾，跟花多少力氣無關。
- **更普遍的模式**：這是同一輪裡第三次**先有結論、再從別處搬權威句子當理由**（另兩次：「投影是超集」與五槽「並列不包含」自相矛盾；「發現而非發明」原本講語義概念 vs λ-core 人造編碼，被誤套到物理零件）。前兩次自查出、第三次靠外部反駁抓到。
- **教訓**：豁免一條反對意見時，先把它的論據**逐層列出來**，再指名豁免哪一層、為什麼那層可豁免。整條豁免掉最省事，也最容易漏掉真正擋你的那層。**成本可以豁免，語義不行。**
- **來源**：ArduinoCAD `draft/2026-08-05-回送semorphe-埠統一沉到連接層.md`、[concepts/元件.md](concepts/元件.md)

### 寫下一條規則之後，要回頭掃「現有的資料違反它嗎」

- **實際發生（2026-08-09，G 項）**：我在 `concepts/元件.md` 寫下跨域命名規則③
  「主體在前，限定在後」，然後做了一條護欄。護欄報「裸的函式庫名 84 顆」，
  而我量測時只數到 ~35。差額裡有一批是 `count_loop`／`while_loop`／`for_loop`
  ——**它們違反的正是我剛寫下的規則③**，而我的護欄沒有檢查那一條。
- **為什麼會漏**：寫規則的時候是在想「未來的人該怎麼命名」。
  於是檢查也只朝未來看——**而規則同時也是對現況的一個宣稱**。
- **教訓**：**一條新規則落地時，第一件事是拿它掃一遍現有的資料。**
  掃出來的數量就是它的初始債務；掃不出東西才要懷疑規則沒接上。
  這與「第一次跑必須紅」是同一件事的另一半：那條講的是護欄要接上，
  這條講的是**規則的涵蓋面要完整**。
- **它同時是分類表誤報的成因**：84 → 36 的修正過程裡，三個原因有兩個是
  「詞彙表不全」，一個是「規則沒被檢查」。**前者是資料問題，後者是覆蓋問題**，
  而後者更難發現，因為它不會產生看起來奇怪的數字——它產生的是**別的類別**
  的誤報（那些迴圈被歸進了「裸的函式庫名」）。

### 身分不只以字串字面出現——而工具只看得到字串字面

- **實際發生**：命名空間遷移（`specs/103`，177 顆身分／3251 處引用）用 TypeScript AST
  掃字串字面來定位。做完之後測試紅了 128 檔，而根因**沒有一個是字串字面**：

  | 形狀 | 例 | 壞掉的方式 |
  |---|---|---|
  | 裸的物件鍵 | `cpp_isalpha: (c) => …` | 是 Identifier 不是 StringLiteral |
  | 正則裡的形狀 | `/^cpp_(\w+?)_declare$/` | 型別追蹤靜默失效 |
  | 模板字串 | `` createNode(`cpp_string_${m}`) `` | 概念建不出來 |
  | 型別聯集 | `type X = 'if' \| 'print' \| …` | 24 顆 |
  | 測試標題 | `[BLOCKED:cpp_xxx]` | 阻斷者指不到 |
  | JSON 的值位置 | `routes['+'] = 'arithmetic'` | 鍵是運算子、值才是身分 |
  | **拿形狀當判斷** | `if (concept.includes(':')) return` | 命名慣例一改就靜默失效 |

- **教訓**：**凡是「這個字串是什麼」需要靠人讀上下文才知道的地方，工具就看不到它。**
  大規模改名之前，先問「這個識別字有幾種不以字串字面出現的方式」，而不是先問「有幾處」。
- **最兇的是最後一列**：`if (concept.includes(':')) return` 原意是「語言專屬的概念不算
  除錯步驟」——它**把命名慣例當成了契約**。慣例一改，它安靜地變成「什麼都不記錄」。
  → **命名慣例不是契約。** 要判斷「這顆概念是不是 X」，就宣告一個 X 標註，
  不要看名字長什麼樣。
- **第三個實例（2026-08-09，G 項）**：第九條護欄用 `/_declare$/` 判「宣告族」。
  G 把修飾詞移到後面之後 `var_declare_const` 不再以 `_declare` 結尾——
  **整族從信號裡消失，五筆判定同時變孤兒**。
  ⚠️ **而這發生在同一輪重構裡**：修掉前兩個實例的人（我）沒有去掃同形的地方。
  這正是本檔記過的「一個教訓被記下來、處方也被記下來，而程式碼仍然帶著那個病」。
  → 抓到這一類時，**立刻 grep 全樹的同形寫法**（正則裡的名字、`startsWith` 前綴、
  `endsWith` 後綴、字串拼接出來的 id），而不是只修眼前這一處。
- **救它的不是掃描器，是既有的護欄**：deny-list 誤擋一筆時，抓到它的是 C3 的
  引用完備性護欄（`specs/101`）——它掃的是**執行期建出來的身分**，不是字串，
  所以它看得見掃描器看不見的東西。**兩種量測方式的價值在於它們的盲區不同。**
- **半套比兩個極端都糟**：裸名那段先試「只改分類器有把握的位置」，952 支測試紅
  ——約 800 處身分引用落在分類器涵蓋不到的形狀。要嘛全改（附一份量出來的
  例外清單），要嘛不動。

### 同一個陷阱會在不同的層重演，而在新層上它不像那個陷阱

- **實際發生（2026-08-09）**：討論命名時我先指出一個陷阱——
  `lang:sequence_declare` 帶一個參數 `impl: vector|deque|list`，那是
  **一個只有某個語言會填的槽，寄生在共用的東西上**，而中立性護欄量不到參數這一維。
  **然後我在同一場對話的下一個問題上又做了一遍**：提議「各語言共用一顆積木」。
  共用的積木必須是所有語言需求的聯集——C++ 要型別下拉、Python 不要，
  於是 Python 學生看到一個永遠不會動的欄位，而每加一個語言聯集就長大一次。
  **一模一樣的形狀，換到積木層，我沒認出來。**
- **為什麼認不出來**：陷阱的**特徵**（「只有某一方會填的槽」）在原層有具體的名字
  （`impl` 參數），換層之後那個名字不見了，剩下的是「共用一顆積木」——
  聽起來像優點（減少重複），而不像陷阱。
- **教訓**：抓到一個陷阱時，**把它抽象成一句與層無關的話**，否則你只認得它的那一件外衣。
  這一個的與層無關版本是：
  > **共用的東西不得包含只有部分成員會用到的槽。**
  這句話在參數層、積木層、介面層、資料格式層都成立，而 `impl` 那個講法只在參數層成立。
- **它同時解釋了為什麼「重複」有時是對的**：`py:if` 和 `cpp:if` 的積木宣告幾乎一樣，
  而它們遲早會分岔（Python 有 `elif`／`for...else`）。**提早抽象的代價是分岔那天要拆，
  而拆比重複貴**——因為重複只花空間，拆要動已經被依賴的東西。

### 只有一個樣本時，別問「這個通用嗎」——內省會產出跟查證一樣好看的數字

- **實際發生（2026-08-08）**：規劃元件命名重新設計時，我把 177 顆分成「通用／需要參數軸／
  語言特定／已經對了」四堆，並回報「38% 真的是 C++ 特有，不用動」。
  使用者只說了一句「用假設我們已經支援多種語言的處境再看一次」，那一堆當場垮掉：

  | 我判「C++ 特有」 | 我寫的理由 | 三語言在場時 |
  |---|---|---|
  | `try_catch`／`throw` | 「catch 型別是 C++ 的」 | Python `try/except`、JS `try/catch`。**catch 型別是參數不是身分** |
  | `lambda` | 「capture 是 C++ 的」 | Python lambda、JS arrow。**capture 是只有 C++ 會填的參數** |
  | `range_for` | 「介面是 C++ 的」 | Python 的 `for x in xs` 是**主要**迴圈，比 `count_loop` 更通用 |
  | `printf` | 「格式字串是 C 家族特有」 | Python 的 `%` 格式化**就是從 C 繼承的** |

  至少十幾顆，而錯的方向**一致**：只看得到 C++ 時，什麼都像 C++ 特有的。
- **與「量測工具第一版會量錯」的差別**：那幾次是**工具**錯（入口用錯、粒度太粗、詞義錯）。
  這次工具沒錯——**是我沒有第二個樣本可查，於是用內省填了答案**。
  而內省產出的分類表，看起來與查證產出的一模一樣：一樣有顆數、一樣分族、一樣附理由。
- **教訓**：**「這個東西通用嗎」是一個關於關係的問題，而關係需要兩端。**
  只有一端時它不是「難回答」，是**問不出來**——正確的提法會讓你當場發現手上沒有證據。
  → 判斷前先問：**我這個判斷的證據，來自幾個獨立來源？** 答案是一時，那不是判斷，是猜測。
- **它同時是一個設計判準**：如果一個 formulation 會讓人在資訊不足時**還是答得出來**，
  那個 formulation 本身有問題。好的提法會讓過早的問題**問不了**（見
  [等價與觀察集](concepts/等價與觀察集.md)）。

### 量測工具的第一版會安靜地量錯——救它的是「結果長這樣代表工具壞了」

- **實際發生**：實作四條審計護欄（`specs/049-audit-guardrails`）時，有兩支量測**產出了看起來合理、實際上錯誤的數字**：
  - **完備性護欄第一版**用 `renderToBlocklyState` 當 render 的入口，但它需要 `program` 外殼且只處理 statement——於是所有 expression 元件被判為缺，產出 **84 個假的 missing**。數字很大、很像真的。
  - **兩組態比對第一版**比的是 verdict（實作／殼／缺），得到「**無差異**」。而 verdict 粒度太粗：兩種組態都產得出有效輸出，差別在**文字**。真實差異是 35 個元件。
- **怎麼抓到的**：**不是靠檢查程式碼，是靠結果不合理**。extract 顯示「0 殼 ／ 84 缺」——`render` 全過卻 `extract` 全缺，這個組合不可能。而兩組態那次，救命的是我自己寫進報表的那句「**（無差異——若這裡是空的，多半是護欄沒接對）**」：工具吐出的空結果，被工具自己預先貼上的標籤判為可疑。
- **教訓**：**給每個量測工具寫一句自我否證提示**——「如果結果長成 ○○，代表工具壞了而不是世界長這樣」。量測工具是最容易變成殼的東西：它產出數字，而數字天生看起來像證據。沒有這句提示，一個安靜量錯的護欄比沒有護欄更糟——它會讓你**帶著假的安全感**去做重構。
- **第三個實例，而且觸發方式不同（2026-08-06）**：缺陷帳護欄把「被關掉的測試」（22 筆，`it.skip` 有本體）與「只有名字的測試」（64 筆，`it.todo` 無本體）**當成同一種東西數**。數字是對的、分類是對的，**只有「停用測試」這個詞的語義錯了**——它把兩種需要完全不同工作量的東西包在一起，讓優先序灌水 3–10 倍（「修 `print` 解鎖 21 個」實際是 5 個）。
  前兩個實例靠「結果不合理」抓到；**這個是拿它來規劃真實工作時才暴露的**。
- **第四個實例，觸發點與第三個相同但對象是自己（2026-08-06 同日）**：辨識歧義護欄報出「5 條規則的限定條件完全相同」，我據此在 vision 與 history 寫下「另外 4 條是**死規則**」並列為最嚴重的發現。**下一步要照它規劃工作時去實測，全部推翻**——`vector`／`map`／`stack`／`queue`／`set` 宣告都辨識正確，因為那 5 條指向**同一個 strategy**。它們不是 5 條規則，是同一條規則被登記 5 次。
  護欄報的**事實**是對的（那 4 條確實不會被試到），錯的是我從事實推出的**嚴重性**。而且護欄的自我驗證測試（FR-022）當時**通過了**——它只釘住「這一群必須被報出來」，沒有釘住「必須因為正確的理由被報出來」。
  → **自我否證聲明要釘的是理由，不只是結果。** 一個因為錯誤理由而給出正確結果的護欄，看起來與健康的護欄完全一樣。
- **第八個實例，而它是「綠」（2026-08-08，`specs/102`）**：**綠不等於檢查有效。** 參數規格化加了一條「`enum` 的 `values` 必須等於積木下拉的選項」，第一次跑就是綠——而那是因為那 29 筆 `values` **本來就是從下拉抄出來的**。同一份來源比對自己，永遠一致。
  前七個實例的症狀都是「數字錯」，這個的症狀是「**沒有數字**」——一條由建構保證的綠看起來與一條真的守住了的綠完全一樣。
  救它的是額外注入一顆**真實元件**（`arithmetic`）宣告錯的值域，證明檢查會叫。
  → **`build-guardrail` 第 6.5 步（第一次跑必須紅）在推導出來的資料上失效**，因為推導者與檢查者是同一個人、同一份來源。那時要問的不是「它紅了嗎」，是「**它能不能紅**」。

- **第七個實例，機制是新的（2026-08-06）**：**元件身分與普通英文單字撞名。** 中立性護欄的判定是純文字比對（「只匹配完整的引號字串字面」），於是 `'comment'` 這個字串不論它是概念身分、語法樹的節點型別、一個列舉的成員、還是使用者在積木上看到的提示文字，一律被計為違規。六筆裡三筆是誤報。
  前六個實例的機制是入口用錯／粒度太粗／詞義錯／從事實推錯嚴重性／判準對但自動化錯／測試沒測到東西。**這個是第七種，而且它對每一個與普通單字撞名的元件身分都同樣脆弱**——修的時候不知道還有幾個。
  → **修法是遮罩，而每個遮罩的判準必須是語言規則、不是統計傾向。** 三個候選只採用兩個：型別位置（編譯後不存在，不可能是執行期引用）與 Blockly 欄位建構式的第一引數（那是值不是識別碼）。第三個 `.type === 'x'` 被**實測否決**——它會遮掉 14 筆真違規，因為 `block.type === 'cpp_string_declare'` 與 `node.type === 'comment'` 在文字上完全相同。**判不出來一律留著算違規。**
  ⚠️ 同一次還撞見一個**更根本、不屬於這條教訓**的東西：護欄量的**維度**不是規範的全部（它找身分，看不見語法）。那不是工具實作錯，是規範被機械化時選了一維而那件事消失在數字裡——見 [concepts/執行機構.md](concepts/執行機構.md)「一條規範被機械化時，選了哪一維會消失在數字裡」與 [history/021](history/021-中立性的數字只量身分那一維.md)。
- **第十一個實例，而它不在量測工具裡，在註解裡（2026-08-06）**：三處註解把「還沒接上」寫成「做不到」——「為了避免型別消歧問題」「辨識器**沒有**型別資訊（`ARCHITECTURAL`）」「辨識器產出的是運算式版（`architectural`）」。三句都是假的：型別追蹤的機制一直都在（零呼叫者），位置判斷只要看語法樹的父節點。
  → **一句解釋為什麼「只能這樣」的註解，會讓那個限制看起來是本質的**，而大寫的 `ARCHITECTURAL` 讓它看起來像已經有人想過了。**這比沒有註解更難發現**——沒有註解的話下一個人會去查。判準：這類標籤要附**哪一條設計決定**，指不出來就只是一句沒有依據的斷言。
- **第十個實例，而它揭露前九個共有的一個機制（2026-08-06）**：以名字為基礎的比對**忘了詞界**，一天之內四次——`comment` 撞名普通英文字、`'u_endl'` 裡含 `endl`、剝註解的規則寫在正則字面裡（只掃字串就看不到）、`children.init` 是 `children.initializer` 的子字串。
  **四次的後果不一樣**：前兩次多報（數字虛高），**後兩次漏報（數字虛低，而 0 與健康的 0 長得一模一樣）**。漏報那一種更危險——它讓護欄在最需要出聲的時候安靜。第四次那條護欄的第一版回報「0 個問題」，而它要抓的那一筆正好被自己的子字串遮掉。
  → **任何以名字為基礎的比對，先寫一支專門釘詞界的注入測試**：「一個更長的名字包含了它，不得算它出現過」。那支測試比報表上的數字更能說明護欄有沒有壞。
- **第九個實例，而這次它被「已知答案的樣本」當場擋下（2026-08-06）**：語法耦合護欄的偵測器第一版只掃**字串字面**，於是漏掉核心層剝除註解符號的那一整段——那一處寫在**正則字面**裡（`/^\/\/\s?/`）。
  **抓到它的不是 code review，是 `build-guardrail` 第 6 步要求的已知答案樣本**：拿 git 裡那個功能動工之前的真實程式碼當輸入，斷言「這條護欄必須抓得到當時確實存在的耦合」。抓不到就代表它沒有存在的價值。
  同一次的第一輪真實量測，5 處裡有 4 處是誤報（子字串、概念身分、型別位置）——**與撞名那個實例同一個坑的第三次**。
  → **靜態判斷的驗證要有三層**：合成注入雙向、**加上一個真實的、已知有問題的樣本**。前兩層只證明邏輯自洽，第三層才證明它對真實世界有效。
- **第十二個實例，而它在 shell 裡，不在 TypeScript 裡（2026-08-07）**：知識庫的孤兒掃描寫成 `grep -rl --include=*.md`，**zsh 把 `--include=*.md` 當成 glob 去展開**，找不到符合的檔案 → 每個 grep 靜默回傳零 → **44 個檔全被報成孤兒**。修正引號之後實際只有 4 個。
  前十一個實例都在應用程式碼或測試裡。**這個在跑量測的那行指令裡**——工具邏輯完全正確，是餵給它的東西在到達它之前就壞了。而它的失敗方向最糟：**空集合在這個掃描裡代表最嚴重的結果**（全是孤兒），所以錯誤看起來像一個驚人的發現。
  → **一次性的掃描指令也是量測工具**，同樣適用「如果結果長成 ○○，代表工具壞了」。判準很便宜：**先問這個數字的合理範圍**——「知識庫 44 個檔全是孤兒」在任何健康的專案裡都不可能。
- **第八個實例，而它是「讀量測的人」出錯（2026-08-06）**：全套測試的失敗清單被 `head -N` 截斷，我沒讀完就報「全綠」——**而且連報兩次**（059、061）。紅的那支是概念數量的斷言，在 059 就壞了，兩輪之後才被下一個功能撞出來。
  前七個實例是**工具量錯**；這個是**工具量對了、報表也對了，讀的人只看了前幾行**。→ **截斷輸出等於沒有讀。** 檢查全套結果時，要嘛完整列出失敗清單、要嘛只看「Test Files: N passed」那一行的判定，**不要用 `head` 看 FAIL 列**——它會給你一個看起來完整的清單。
- **因此教訓有三個觸發點**：
  1. **結果不合理**（可自查，但取決於當下夠不夠清醒）
  2. **照它行動時**（不可預先自查，但必然會現形）——所以**每次照量測行動的第一步，都要準備好推翻它**
  3. **量測結果被寫進知識庫之後**——這時它已經不是數字，是**後續每一次決策引用的權威**。所以第 2 點的「準備好推翻它」包含推翻自己剛寫下的東西
- **第五、六個實例，觸發點又不同（2026-08-06）**：
  - **判準對、自動化錯**：「有子槽而沒人讀 ＝ 還沒實作」這個判準是對的，但把它實作成 grep 概念名之後，答案是**反的**——壞掉的 `cpp_static_cast` 被判成好的，好的 `cpp_case` 被判成壞的。抓到它的是**先做的實測與它矛盾**：兩個量測互相打架。→ **判準本身可以是對的，把它自動化的第一版仍然會量錯。** 靜態判斷要先在已知答案的樣本上驗過再拿來下結論。
  - **測試通過卻什麼都沒測到**：分類測試有五列的「通過」是假的——那些概念根本沒出現在語義樹裡（例如用 `static_cast` 代測 `dynamic_cast`）。加上「這個概念必須真的出現在樹裡」之後，通過數從 17 掉到 12。→ **一支斷言「輸出正確」的測試，要先證明它真的執行到了被測的東西。**
- **相關**：自我否證聲明本身也會過期——判準已於 2026-08-06 加強為「**根本別錨在真實狀態上**」（護欄修好了它要量的東西，就是它的錨點爛掉的時候）。見 [concepts/執行機構.md](concepts/執行機構.md) 與 [history/022](history/022-護欄的自我否證不得錨在真實狀態.md)

### 量一個**新刻度**時，最可能錯的是語料——而語料的錯看起來像世界的性質

- **與上一條的關係**：上一條那十一個實例**全部是工具錯**（入口用錯、粒度太粗、
  詞義錯、從事實推錯嚴重性、綠是建構保證的……）。這一條的三次**工具都是對的**，
  錯的是餵進去的東西。**修法不同，所以是兩條而不是第十二個實例。**

- **實際發生（2026-08-10，`specs/108`，一輪之內三次）**：

  | | 第一版 | 正確 | 語料錯在哪 |
  |---|---|---|---|
  | 形態的殘差 | **48.83%** | **0.23%** | 820 段裡 353 段是測試檔裡的**片段**，語法本來就不完整 |
  | 行為的誤差 | 64 筆 | 40 筆 | 61 段讀 `cin`／用 `rand`，無輸入時**兩邊都不可判定** |
  | 行為的誤差 | 40 筆 | **31 筆** | 抽取器把 `\n` 錯拆成「反斜線＋真換行」＝ C 的**續行符**，`printf` 的格式字串被吃掉——**這一個是我自己寫壞的** |

- **為什麼它比工具錯更難發現**：工具錯的症狀是「數字不合理」，
  而**語料錯的症狀是「數字看起來像一個發現」**。
  `48.83%` 讀起來就是「**模型只理解一半的程式碼**」——它不像壞掉，它像壞消息。
  順著它走的話，下一步會是「去補模型」，而模型根本沒有問題。

- **判準（比「結果不合理」更早生效）**：
  > **這個數字如果是真的，它與我已知的事實矛盾嗎？**

  已知事實是「這個系統天天在用，完整程式的殘差應該接近零」。
  48.83% 與那句話矛盾——**而矛盾的來源有兩個候選（工具、語料），
  上一條只教你查前者。**

- **處置：語料的分欄要進基線，不是靜默排除。** 兩條護欄各有一欄「不算數的語料」
  （殘差的「語法有錯片段 353」、誤差的「不可判定 61」）。
  理由是對稱的：**只記分子的話，「加一段讀 `cin` 的語料」就能縮分母讓比率下降
  ——而縮分母比修分子容易。**
  → 這是「用宣告刷數字」（`history/018`）在語料上的變形：
    **不是改宣告，是改進來的東西。**

- **推廣**：任何**新**刻度都適用，因為新刻度沒有歷史數字可以對照。
  已經跑過幾輪的護欄有棘輪替它擋（數字跳動會被看見），
  **第一次跑的那個數字沒有任何東西在守。**

### 知識庫存得住「當時的觀察」，存不住「現在的事實」——而兩者長得一樣

- **實際發生（2026-08-10，`specs/109`）**：整份 spec 的第一版圍繞
  「新增一個『已知不支援』宣告值」設計，連防洗數字的機制都寫好了
  （分欄、總和不變、只能宣告已記錄過的缺口）。
  **依據是 `concepts/執行機構.md:168`（2026-08-06）**：
  「其餘 14 個跑起來結果是錯的（**十個是物件導向，直譯器不支援它**）」。

  而查證的結果是 `specs/071`／`072`／`073` **在那之後實作了它**，
  `unimplemented.ts` 的 `OOP_NOT_IMPLEMENTED` 現在是**空陣列**。

- **它與「凍結的讀數」是同一個形狀**：`specs/108` 記過「27 個檔的 `g++` 答案
  是人工量一次凍進註解的——**一個凍結的讀數是宣告，不是量測**」。
  這次凍結的不是外部工具的答案，是**我們自己對系統的判斷**。
  → **同一件事的兩個方向都撞過了**：對外部權威的讀數會凍結，
    對自己系統的判斷也會。

- **為什麼特別難防**：知識庫裡的句子**沒有時間戳的語感**。
  「直譯器不支援物件導向」讀起來像一條性質，不像一次觀察。
  而它旁邊就寫著日期——**日期在，語氣沒有跟著**。

- **判準（讀的時候問，不是寫的時候）**：
  > **這句話是「當時的觀察」還是「現在的事實」？**

  凡是描述**系統現況**的（支不支援、有沒有實作、剩幾筆、誰呼叫誰），
  一律當成前者，**引用前重新量一次**。
  凡是描述**推理或決定**的（為什麼這樣設計、否決了什麼、判準是什麼），
  才是知識庫真正存得住的東西。

- **而救它的是 `grep`，不是讀得更仔細。** 這一點與「量測工具第一版會安靜地
  量錯」同一個結論：**不要用更用力的閱讀去對抗一個機械問題。**

### 照抄已驗證的形狀，不要自己換一個判準

- **實際發生（2026-08-10，`specs/109`）**：修「`char c = 66` 印出 `6`」時，
  第一版寫成

  ```ts
  const n = this.toNumber(val)
  if (val.type !== 'char' && Number.isFinite(n)) return { …, value: String.fromCharCode(n) }
  ```

  而 **`toNumber({type:'string', value:'a'})` 回傳 `0`，不是 `NaN`**
  → `char s[8]="a"` 的每個字元都變成 NUL → `strcat` 的測試當場變紅。

- **而同一題早就被解過**：`std/cctype/executors.ts` 的 `charOf` 用的是
  `typeof v.value === 'number'`，並且**在它上方寫著**
  「⚠️ **不能一律 `String(value).charAt(0)`**」。
  **我讀過那段註解、在修法裡引用了它，然後換了一個自己的判準。**

- **為什麼會想換**：既有形狀看起來「不夠通用」——`typeof === 'number'`
  漏掉了「數字存成字串」的情況，而 `toNumber` 看起來涵蓋更多。
  **改動的動機是把它做得更好，而不是偷懶。** 這正是它危險的地方：
  一個看起來更周全的判準，沒有那份形狀背後的實測。

- **判準**：
  > **這個問題別的地方解過嗎？解過的話，先照抄，再問要不要改。**
  > 而**要改就得付出原本那份形狀付過的驗證代價**——它是誰在什麼情況下驗出來的。

- **它同時是另一條的實例**：「**修一條路時要問：同一個缺陷在別的路上長什麼樣**」
  ——`cctype` 修過 char 的取法，而**核心的轉型沒有**，所以缺陷在核心又活了一次。
  → 兩條合起來的操作：**先 grep 這個症狀在別處有沒有解，有就照抄；
    沒有就修完之後回頭找同族。**

- **相關**：[history/038](history/038-過期的論斷被當成現況引用.md)

### 探測腳本的**過濾器**也是語料的一部分——而它比語料更隱形

- **實際發生（2026-08-10，`specs/110` 規劃時）**：查 `s.size()` 為什麼回 0，
  寫了一支探測腳本印出語義樹，並用 `x.includes('string')` **過濾**要看的節點
  （理由：這是字串的方法）。輸出是

  ```
  cpp:program cpp:include cpp:string_declare cpp:literal_string cpp:var_declare
  ```

  沒有任何 `size` 相關的節點 → 我的結論是「**`s.size()` 完全沒有被 lift**」，
  並據此推薦蓋一條「量得到靜默丟棄」的護欄。

  **兩個都錯。** 拿掉過濾器再跑一次：`s.size()` lift 成 **`cpp:vector_size`**
  ——它有 lift，只是**身分錯**。而 `vector_size` 不含 `string`，
  **剛好被我的過濾器濾掉。**

- **它是「語料錯看起來像世界的性質」的近親，但更難防**：

  | | 錯在哪 | 會不會被看見 |
  |---|---|---|
  | 語料錯 | 餵進去的東西不對 | **語料通常會被印出來**（段數、字元數） |
  | **過濾器錯** | 看的窗開錯地方 | **過濾器不會被印出來**——它只留下一個乾淨的輸出 |

  > **一個過濾掉答案的探測，輸出看起來與「答案不存在」一模一樣。**
  > 而後者是一個「發現」，前者是一個 bug。

- **判準**：**探測腳本的過濾器，要在已知答案的樣本上驗過。**
  這次只要加一句「`s.length()` 必須出現在輸出裡」就會當場戳破——
  因為 `.length()` 是已知會被正確辨識的那一支。
  → 具體做法：**任何過濾器旁邊放一個「這個一定要留下來」的對照**。

- **它也是「靜態判斷只能排順序」的一個新面向**：那條講的是判準錯，
  這條是**判準對但視野被裁掉**——而裁掉的動作看起來像「聚焦」。

- **相關**：[history/039](history/039-靜默回退掩蓋辨識歧義.md)、
  本檔「量一個新刻度時，最可能錯的是語料」

### 一件「該做但不急」的事，會被合理地推遲到永遠——而每一次推遲都有好理由

- **實際發生（2026-08-10）**：`specs/104` 的切片紀錄開頭就寫著

  > 「哪些步驟會**重複 176 次**。沒有它，剩下的 176 顆仍然是憑感覺開票。」

  而它寫完之後**過了五輪才被 skill 化**（`specs/108`–`112` ＋ judge 的連鎖）。
  那五輪不是浪費——它們抓到 `p->x` 壞掉、`char c=66` 印成 `6`、建構子不執行。
  **每一輪的選擇單獨看都是對的。**

- **它與「忘了做」不同**：忘了做的東西**沒有人記得它存在**；
  這一種**每一輪都被看見、被評估、然後被合理地排在後面**。
  → 而清單上它們**長得一模一樣**：都是「還沒做」。

- **兩個症狀**：
  - **一直被合理地推遲**與**其實不重要**，在待辦清單上分不出來
  - 而推遲的成本**不是線性的**：skill 化的價值是「省下的重複」，
    第 176 次之前 skill 它省 175 次，第 175 次之後省 1 次

- **判準**：**這件事的成本會隨推遲而增加嗎？**
  - 不會（修一個 bug、還一筆債）→ 排在後面是對的
  - **會**（skill 化、識別碼的設計、格式定案）→ **它不該與其他項目一起排序**，
    因為排序比的是「現在多重要」，而它的代價在**未來**

  > 判定落點的鍵是同一個形狀：它出過三次問題，而每一次都只修那一條護欄。
  > **第 175 次膠囊搬家之前修完它，比第 175 次之後便宜 175 倍。**

- **可操作的形式**：待辦清單上把這一類**另立一區**，而不是給它一個順位。
  它們的排序判準與其他項目**不可比**。

### 注入釘住的是**機制**，不是**輸入**——而一條沒吃到輸入的護欄，注入照樣全綠

- **實際發生（2026-08-10，judge 收 `specs/112` 時查到）**：第七條護欄
  「執行器重複註冊」自 2026-08-06 起**量的是一個空的註冊表**——
  它在量測前**沒有呼叫 `registerCppLanguage()`**，所以 C++ 的執行器一個都沒註冊。

  ```
  基線寫的      duplicateConcepts: 0        （四天以來一直是這個）
  真實的數字     4                          （method_call／struct_at_member／
                                             struct_at_ptr／template_function 各兩次）
  ```

- **而它有注入測試，而且一直是綠的。** 注入手動 `reg.register()` 同一個名字兩次，
  再確認被數到——它證明的是「**計數器會數**」。
  > **計數器會數 ≠ 註冊表裡有東西。**

- **它的自我否證聲明也寫了，而且問錯了問題**：
  「⚠️ 這個數字若是 0，先確認計數真的有接上……判斷依據是『★ 注入』那支測試」
  ——那句話把讀者**明確地指向注入**，而注入正好是看不到這個缺口的那一支。
  → **一句錯誤的自我否證提示，比沒有提示更糟**：它讓人停止懷疑。

- **教訓**：**把量測的入口條件寫成斷言**——
  「掃了幾個檔／載入了幾條規則／註冊表裡有幾個概念／語料幾段」。
  這條在 `experience.md` 早就寫過（「盲區的大小量不出來」那條的具體做法），
  **而它被理解成「注入的補充」，其實是「注入涵蓋不到的另一半」**：

  | | 釘住什麼 | 漏掉什麼 |
  |---|---|---|
  | 注入 | 判定邏輯**會不會報** | 真實輸入**有沒有進來** |
  | 入口條件 | 真實輸入**有沒有進來** | 判定邏輯對不對 |

  **兩者不能互相取代，而「有注入」很容易讓人以為已經夠了。**

- **順帶**：這條護欄修好之後第一件事，就是抓到四筆真的重複註冊——

  它們沒出事是因為真實作載入在後、蓋掉了空操作——**靠註冊順序，不是靠設計**。

### 一個分類機制長出或收掉類別時，人的判定詞彙要跟著改

- **實際發生（2026-08-10，兩個方向各一次）**：

  | | 機器 | 人的詞彙 | 後果 |
  |---|---|---|---|
  | `#33` | **長出**新類別（型別不符／缺子節點） | 沒跟上 | 8 筆被硬套成「靜默回退」，**判定檔說 8 個缺陷、護欄說 0 個** |
  | `#32` | **接管**了一個類別（`不可判定()` 自動濾掉讀 `cin` 的語料） | 沒縮回 | 值域裡兩個值**永遠不可能被用到** |

- **兩個方向的症狀不同，而報表都正常**：
  長出的那邊是**兩份紀錄各說各話**（讀哪一份決定你以為有幾個缺陷）；
  收掉的那邊是**死值留著**（看起來還有人在判那一類）。

- **教訓**：**每次改動機器的分類規則，去看一眼判定的值域還對不對。**
  → 機械化的形式是一條斷言：**人的判定與機器的分類必須相容**
    （`#33` 已有；相容表要允許「合法」出現在任何一欄，
     因為 `strcmp` 相等回 0 那種語義可能落在任何形狀底下）。

- **為什麼容易漏**：改分類規則時人在想「機器怎麼分」，
  而判定檔是**另一個檔案、另一個時間寫的**。
  兩邊都合理，合起來才矛盾——**而沒有任何一次執行會同時讀到兩邊**。

### 數到了東西，不代表那些東西**會發生**——而計數天生看起來像證據

- **實際發生（2026-08-10，連續兩輪，同一個形狀）**：

  | 我的推薦 | 依據 | 實測 |
  |---|---|---|
  | 「把靜默回退護欄擴到產生器」 | **26 處，比執行器多三倍** | 415 段語料觸發 **0 次** |
  | 「第三十三條護欄抓到 9 筆」 | **9 筆，第一次跑就紅** | **8 筆是死分支** |

  兩次的推薦都建立在**計數**上。而計數回答的是「**有幾個長這樣的東西**」，
  不是「**有幾個會發生的東西**」。

- **它與「量測工具第一版會安靜地量錯」不同**：那條講的是量測錯。
  **這兩次量測都是對的**——26 處確實存在，9 筆確實符合判準。
  錯的是**從「量到了」推出「值得做」**這一步。
  → 前者的修法是修工具；這條的修法是**多問一個問題**。

- **為什麼特別容易中**：一個數字自帶「已經查證過」的氣味。
  「26 處」聽起來像調查的結論，而它其實只是**一次 grep**。
  而下一步的規劃會直接接在那個數字上，**沒有人會回頭問那 26 處會不會發生**。

- **判準**：
  > **任何以「有 N 筆」為依據的推薦，先問「這 N 筆在真實輸入上發生過幾次」。**

  ⚠️ 而**量活性要有對照**——否則「0 次」有兩種解釋：
  它不會發生，或者**輸入根本沒碰到那個概念**。
  這次的對照是「那些概念有沒有出現過」：5/10 出現、共 14 次 → 量測有效。

- **推論：不會發生 ≠ 不該存在。** 那 8 個防禦分支永遠不執行，
  但它們防的是**未來的壞樹**。處置是**留著，記成一個可見的數字，不進棘輪**
  ——而不是刪掉，也不是讓它假裝是缺陷。

- **相關**：[history/040](history/040-護欄抓到的九筆有八筆是死分支.md)、
  `knowledge/skills/build-guardrail/SKILL.md` 6.5 之後那條

### 識別碼必須識別得出那個東西——截斷的鍵會讓「已判定」變成謊話

- **實際發生（2026-08-10，`specs/110` 收尾）**：`specs/108` 建的判定落點
  （`build-guardrail` 第 11 步）用「語料正規化後的前 80 字元」當鍵。實測：

  ```
  17 筆明細  →  16 個不同鍵
  19 筆判定  →  16 個不同鍵
  ```

  碰撞的是三段開頭相同的 `#include <iostream> #include <cctype> …`。

- **後果比「數字不準」嚴重**：判定落點有兩道防線，**兩道都靠鍵**——
  - **孤兒檢查**（訊號消失了、判定還在）→ 別名讓過期判定繼續生效
  - **「要看」清單**（未判定的命中）→ **一筆新缺陷會被同鍵的舊判定吸收，
    而報表上顯示「已判定 N，要看 0」**

  > **一個被誤認為已經看過的缺陷，比一個沒被報出來的更糟**
  > ——後者至少不會讓人以為看完了。

- **它與「以名字為基礎的比對忘了詞界」是同一族，而機制不同**：
  那次是**子字串**（`children.init` 落在 `children.initializer` 裡），
  這次是**截斷**（兩個不同的東西前 80 字元相同）。
  → 合起來的判準：**任何從內容導出的識別碼，先問「兩個不同的東西會不會拿到同一個」。**
    答不出來就加雜湊——它便宜，而碰撞的代價是靜默的。

- **為什麼當初會這樣寫**：鍵要**人看得懂**（報表上要顯示是哪一段程式）。
  那個需求是對的，錯在**用同一個字串同時當顯示與識別**。
  → **顯示與識別要分開**：`前 60 字元 + '#' + 全文雜湊` 兩者都滿足。

- **相關**：[history/039](history/039-靜默回退掩蓋辨識歧義.md)、

### 行為對、身分對，標籤仍然可以說謊——而只有使用者會發現

- **實際發生**：一名學生反應「stack 和 queue 的 `push` 意思不一樣，所以積木寫錯了」。查證後**兩邊都對，但對在不同的層**：執行器完全不分支（`arr.value.push(val)`，stack 與 queue 走同一行）→ **身分是對的**；而標籤 `"Push %2 onto %1"` 的 **“onto” 字面就是「放到…上面」——那是堆疊語義**，佇列的元素是排到後面去。中文的「推入」中性一點，但一樣沒說放到哪裡。
- **同一個檔案裡有反證**：vector 那顆的標籤反而寫對了——`"在 %1 尾端加入 %2"`／`"Append %2 to %1"`，**它說了「尾端」**。所以這個專案知道怎麼寫好標籤，只是共用的那顆沒寫。
- **它落在所有既有檢查的外面**：執行測試綠（行為對）、來回轉換綠（產出的 C++ 對）、五路完備綠（五路都在）、就近性／中立性／語法耦合無關。**十八條護欄一條都不會叫，而使用者第一眼就看出來。**
- **教訓**：**「換一個檢視它會變嗎」那條試金石判得出身分，判不出形態有沒有說謊。** 形態的正確性沒有內部 oracle——產出的程式碼可以完全正確，而描述它的那句話完全錯誤。
  → 可操作的判準：**一個操作的標籤要說出「作用在哪裡」，不只說「做什麼」。**「推入容器」是做什麼，「推到頂端」才是作用在哪裡。同一顆元件在不同上下文的標籤**應該不同**——那不是重複，那是形態的職責。
- **而這揭露了一個更大的洞**：`knowledge/` 裡**沒有任何一則來自實際學習者的回報**，而這個專案的 telos 是教育。所有內部論證都自洽，**而沒有東西能證偽「這樣好教」**。協定、五槽、命名空間、膠囊全部來自第一原理推導與跨專案協商——那些是好論證，但它們都沒有被真人打過臉。
  → **使用者回報是唯一能證偽「這樣好教」的證據，它的權重與實測相同**，不該被當成軼事。
- **來源**：[episodes/2026-08-07-學生說積木寫錯了](episodes/2026-08-07-學生說積木寫錯了.md)

### 共用一個實作，可能是「行為一樣」，也可能是「差別沒被模型化」

- **實際發生**：身分健檢護欄報出六顆宣告概念**宣告完全相同**，並問「型別是身分還是參數？」。量執行器：五顆共用 `execVarDeclare`，只有 pointer 有自己的——**看起來像「行為一樣，可以合併」**。
- **跟 `g++` 對答案之後，答案是第三種**：

  | | 直譯器 | g++ |
  |---|---|---|
  | `static int n` 跨呼叫保存 | **111** | 123 |
  | `int& r = a; r = 9;` | **59** | 99 |

  **兩顆的身分是對的，缺的是行為。** 而它們之所以三個月沒被發現，正是因為共用執行器讓「沒實作」長得像「一樣」。
- **這是一個新的偽裝**：既有的教訓講的是「量測工具量錯」與「標籤說謊」。這個不同——**程式碼本身是誠實的**（它確實共用一個函式），誤導的是**從「共用」推出「相同」**這一步。
- **教訓**：**看到兩個概念共用一個實作，先問「它們**應該**一樣嗎」，而不是「它們一樣，所以可以合併」。** 判準是外部真實（編譯器、規格），不是自家程式碼的形狀——**自家程式碼正是可能漏掉那個差別的地方。**
  → 操作化：合併任何身分之前，**先為每一顆寫一支對照外部真實的行為測試**。測試綠了才談合併；紅了就是找到缺陷，而那比合併有價值。
- **來源**：`specs/099-*`、`tests/integration/declare-family-semantics.test.ts`

### 量測錯了，會逼出一個假的宣告——因果方向是新的

- **實際發生**：完備性 harness 靠正則剝掉「看起來像鷹架」的行（`#include`／`using `／`int main`…）來算「這個概念自己產出了什麼」。而 `cpp_include`／`cpp_using_namespace` 這幾個概念的**產出就是那個形狀**——輸出被自己的過濾器剝光 → 判成殼。
- **然後有人把殼消掉了**：那四顆被加上 `skipPaths: ['generate']`、理由 `consumed-by-parent`。**實測推翻**（樹裡有 include 節點 → 出現；拿掉 → 不出現）：是節點自己產生的，父概念沒有消費它。
- **`history/018`「用宣告刷數字」的因果方向是新的**：那條講的是「有人為了讓數字好看而宣告」。這裡是**量測工具先報了一個假的殼，宣告是為了消掉那個假殼**——動機甚至是正當的，而結果一樣是把一個實作說成不存在。
- **教訓**：**一個宣告出現時，先問「它在回應什麼」。** 如果它在回應一條護欄的紅燈，那要先確認**那個紅燈是真的**——否則護欄與宣告會互相背書：護欄說有殼、宣告說那是設計，而兩邊都是錯的。
  → 修法不是刪宣告，是**修量測**：「這個概念自己產出了什麼」改用**差分**算（有節點 vs 只有鷹架），不用形狀猜。**沒有這個節點時也會出現的，就不是它產的**——這條判準不需要知道哪些行是鷹架。
- **來源**：`tests/integration/audit-completeness.test.ts` 的 generate 那一段

### 機制做對了，而使用者拿不到它——工具箱／入口從來沒有人量過

- **實際發生**：097 把「一個身分、多個積木形態」做出來了，測試全綠、十七條護欄零上升、積木確實顯示「推 1 到 stk 的頂端」。**使用者拿去跑，第一句話是：「這樣會不會讓學生困擾找不到積木？」**
- **會，而且比找不到更糟**：工具箱裡只有中性版，學生拖出來、填入變數、**同步之後那顆積木被換成另一個型別，文字自己變了**。他沒有要求任何改變。而「推到頂端」那顆根本不在工具箱裡。
- **為什麼十七條護欄一條都沒叫**：**工具箱的內容從來沒有人量過**。五路完備管的是「這個元件的五條路都在」，不管「使用者找不找得到它」。**「做得出來」與「拿得到」是兩件事，而所有既有的檢查都只量前者。**
- **修法出乎意料地小**：工具箱是一份手寫清單，換兩行就好——而且**教得更好**（學生在工具箱就看到堆疊與佇列的差別，不必拖出來才知道）。原本打算建一條「動態標籤」通道，查了之後否決：多一整條推／讀通道去解一個兩行的問題，違反憲章 I。
- **教訓**：**一個功能做完之後，去看它的入口。** 元件加好了、路徑通了、測試綠了——然後問「使用者要從哪裡拿到它？」那個入口（工具箱、選單、搜尋）通常是一份**手寫清單**，而手寫清單不在任何護欄的視野裡。
- **這是第二次由使用者發現、而不是由測試發現**（前一次是同一輪的標籤說謊）。兩次都落在「機器驗得到的正確性」與「人拿得到的價值」之間那道縫裡。
- ⚠️ **原本的判準不夠，而證明它不夠的是我自己（2026-08-07，E 項）**：這一條原本寫著
  「新增一個使用者選得到的東西時，**同時問**『它在哪個清單裡』」。寫下它之後，
  **同一個 session** 我又漏了兩顆——098 的 `c_map_assign`、095 的 `cpp_istringstream_declare`。
  真的蓋了護欄之後第一次跑，指名 **7 顆**（另含 `<fstream>` **整個模組**使用者拿不到）。
  → **修正後的判準：問清單不夠，要蓋機械檢查。**
  「新增使用者選得到的東西時同時問一句」是一條**靠記得**的規範，而這一條教訓
  自己就是它失效的證據。**一條教訓寫進知識庫，不會讓下一次不發生——只有機械檢查會。**
  （第十九條護欄「可拿性」：`tests/integration/audit-toolbox-reachability.test.ts`）
- **這與「處方只留在發現它的那一處」是同族的第二個實例，而且更乾淨**：那次是
  處方沒被推廣到同形的檔案；這次是**教訓寫下之後，同一個作者在同一個 session 裡又犯**。
  中間沒有時間、沒有換人、沒有換檔案——只有「靠記得」這個機制本身失效。

### 症狀是「忘了登記」，而宣告其實是對的——呈現層把它吃掉了

- **實際發生（2026-08-07，E 項）**：可拿性護欄報出七顆使用者拿不到的積木，我準備把七顆都加進工具箱清單。查 `cpp_getline` 的宣告時發現它的 `category` **已經是 `'io'`**——`cpp_ifstream_declare`／`cpp_ofstream_declare` 也是。三顆宣告完全正確。
- **吃掉它們的是一個分堆邏輯**：

  ```ts
  const universalIo = ioTypes.filter(t => t.startsWith('u_'))
  const cppIo       = ioTypes.filter(t => t.startsWith('c_'))   // ← cpp_ 兩邊都不屬於
  ```

  `'cpp_getline'.startsWith('c_')` 是 **false**。兩堆都不收，於是靜靜地丟掉。
- **這是第三種偽裝**，前兩種是「量測工具量錯」與「共用執行器讓沒實作看起來像一樣」。這一種的特徵：**症狀與「忘了登記」一模一樣（使用者拿不到），而修法完全相反**——加進清單只會多一份手寫真相，真正要修的是分堆邏輯。
- **一般化的形狀**：**把集合分成兩堆時，第二堆要是「其餘」，不是另一個述詞。**
  `filter(p)` ＋ `filter(q)` 只在 `q ≡ ¬p` 時才是**劃分**；只要有一個元素兩者皆非，它就消失了，而**沒有任何地方會出聲**。
  → 判準：看到兩個並列的 `filter`／`if`，問一句「**有沒有東西兩邊都不屬於？**」寫成 `filter(p)` ＋ `filter(!p)` 就不可能漏（讓錯誤無法被表達）。
- **診斷順序也要換**：報表說「拿不到」時，**先讀那顆東西的宣告，再去看清單**。反過來做的話，第一直覺（忘了登記）會給出一個能讓測試轉綠、而根因還在的修法——下一顆 `cpp_*` 的 I/O 積木還是會消失。
- **來源**：`src/ui/toolbox-builder.ts`（`buildIoContents` 的註解）、[episodes/2026-08-07-使用者拿不到那七顆](episodes/2026-08-07-使用者拿不到那七顆.md)

### 一支測著死程式碼的測試，綠燈與測著活程式碼的長得一模一樣

- **實際發生（2026-08-07，E 項）**：`toolbox-categories.ts` 裡有一份 `buildIoCategoryContents`，與 `toolbox-builder.ts` 的 `buildIoContents` 是**同一段邏輯的第二份拷貝**。`isIoCategory` 走的是 builder 的預設路徑，所以**沒有任何產品程式碼在用它**——只有它自己的單元測試在叫。
- **那支測試三個月來一直是綠的。而那份拷貝有一模一樣的缺陷**（同樣把 `cpp_*` 的 I/O 積木丟掉）。它的綠燈**不但沒有保護任何東西，還讓那段邏輯看起來被覆蓋過了**。
- **與「機制有了，沒人接上」的差別**：那條講的是**機制**沒有呼叫者——症狀是「功能沒發生」。這條講的是**測試**沒有被測對象——症狀是「信心是假的」。後者更難發現，因為前者至少會有人抱怨功能不對。
- **它落在所有十九條護欄的外面**：`audit-orphan-implementations` 量的是「已註冊執行器的概念」減「概念定義檔宣告的概念」（基線 `_meta.rule` 逐字），看不到「匯出了但只有測試在叫的函式」。
- **量了之後發現它不是孤例**：`src/` 匯出 178 個函式，**26 個產品程式碼零引用**。而最嚴重的一筆是 `generateCode`——它與 `generateCodeWithMapping` 是**同一段 setup 的兩份拷貝**，production 走後者，而**384 次測試引用走前者**。兩份一旦分歧，整套測試會在驗證一條沒有人執行的路徑，**而全套仍然是綠的**。
- ⚠️ **量它的時候我差點丟掉正確的結果**：掃描器報 `generateCode` 是「只有測試在叫」，我憑印象判定掃描器壞了、對使用者說了那個結論，去查才發現**錯的是我**。
  → **「在已知答案的樣本上驗過」只有在那個答案是查過的時候才有效。** 用**記得的**答案驗工具，驗的是記憶不是工具。這是那條判準（本檔「靜態判斷不能下結論，只能排順序」）沒說出來的前提。
- ⚠️ **寫完這一條之後三個 commit，我又做了一次——而且更嚴重（2026-08-07）**：
  導出改用 `owner` 比對時，我建了 `src/blocks/universal.ts` 當蓋章的唯一入口，
  **卻只把測試路徑改過去**。`app.ts` 與 `module.ts` 仍 import 原始 JSON，
  於是每個 `(universal)` 段落在正式路徑上回傳零筆——**通用積木整批從工具箱消失，
  學生的起始關卡只剩兩個分類、沒有任何 statement 積木**。全套 222 檔全綠。
  **是使用者截圖發現的。**
  → 症狀比死程式碼更難察覺：死程式碼至少是**多**一份沒人跑的；這次是
  **同一份資料有兩條載入路徑**，測試走 A、production 走 B，而 A 是對的。
- **教訓**：**一段程式碼唯一的呼叫者是它自己的測試時，那不是「被測過」，是「只有測試需要它」。**
  → 判準：寫測試時問一句「**產品程式碼從哪裡進到這個函式？**」答不出路徑就先答這個，再寫斷言。
  → 而**重複的兩份實作最容易掉進這裡**：其中一份被接上，另一份留著測試——兩份都綠，而只有一份在跑。
  → **建了「唯一入口」之後，第一件事是搜尋舊入口還有誰在用**，不是改測試。
    留一個舊入口在那裡，等於宣告「唯一」的那句話是假的。
- **修法不是把 import 改對——那只是再賭一次沒有人會忘記**。真正的修法是讓
  **組裝只剩一份**（`all-declarations.ts`），測試與 production 用同一個函式，
  於是分歧**無法被表達**。＋ 一條護欄看「每顆積木都蓋了章」——因為漏蓋不會產生違規，
  它產生的是**空段落**，而空段落與「這個分類就是這麼小」長得一模一樣。
- **而它不是一次手滑，是系統性的**：事後量，**還有 21 個測試檔**握著同一扇舊門。
- ⚠️ **一年後（2026-08-10）還有八扇沒關，而是新功能撞出來的**：
  搬第一顆元件進膠囊（`specs/104`）時，`all-declarations.ts` 那句
  「**所有宣告的唯一組裝點**」被證實是假的——測試 helper（4 份）、
  整合測試（3 份）、`strategies.ts` 的一段推導（1 份），共八處各自組一份。
  症狀**各不相同且都指向錯的方向**：孤兒實作、幽靈積木、render 缺、初始值被丟掉。
  → **它們全部在同一天現形**，因為元件膠囊是第一個「**只存在於正式路徑**」的
    宣告來源。在此之前八份的內容完全一樣，所以沒有任何訊號。
  → **一份重複的組裝不會自己現形，要等到兩份的內容真的不一樣那天**
    ——而那天通常是重構日，也就是最不想同時處理八個無關紅燈的那一天。
  → 上面那條處方（「建了唯一入口之後，第一件事是搜尋舊入口還有誰在用」）
    **當時就寫下來了，而它沒有被執行**。這是「教訓記下來、處方記下來，
    而程式碼仍然帶著那個病」的又一個實例——**處方需要的是一條護欄，不是一句話**。
  → 所以判準要再往前推一步：**建了「唯一真相」之後，第一個動作是讓舊路徑無法通行**
  （搬走／改名，讓 `tsc` 當場爆），**不是改測試**。舊路徑還走得通 ＝「唯一」那句話
  是假的，而它會安靜地假下去。已蓋成第二十條護欄（唯一入口，**硬性零不用棘輪**——
  棘輪是給「大量既有違規慢慢還」用的，這一條只要開一個口就整條失效）。
- **不對稱是關鍵**：**多餘是吵鬧的，缺失是靜默的。** 多一顆積木看得到；少一整包
  只會讓某個分類「看起來就是這麼小」。→ 斷言要寫成**存在性**（「這些必須在」），
  不能只寫成一致性（「和上次一樣」）——一致性比對的是我選的那個狀態，而我選錯了狀態。
- **相關**：[concepts/執行機構.md](concepts/執行機構.md)「機制有了，沒人接上」；本檔「與其偵測錯誤，不如換一個讓錯誤無法被表達的形式」（**只有一份實作**就沒有這個問題）
- **快照為什麼也沒抓到**：工具箱快照用「**全部概念可見**」，而使用者看到的是課程的**起始關卡**。全部可見時少掉的那批被其他分類的數量蓋過去，結構上看不出來；只有起始關卡會裸露（那一關幾乎只有通用積木）。
  → **快照要釘在使用者實際會看到的狀態上，不是最大的那個狀態。**
- ⚠️ **第三次，而這次「最大狀態」換了一個維度（2026-08-07）**：`priority_queue` 補齊五路、
  進了工具箱、專屬測試全綠——**而它沒有被任何課程收錄**，`getVisibleConcepts` 把它擋掉，
  學生永遠看不到。測試用的是「全部概念可見」，使用者看到的是**課程的可見集合**。
  使用者的話是「priority_queue 我沒看到呀」。
  → 前一次的判準寫「不是最大的狀態」還不夠精確——**可見度有兩層**（課程收錄 × 關卡解鎖），
    而測試預設把兩層都開到最大。判準要問的是：**這顆東西要通過幾道閘門才會到學生眼前？
    每一道都測了嗎？**
- **而「忘了收錄」是完全靜默的**：課程護欄刻意不把「未收錄」算成違規（做成違規會逼出
  「為了讓護欄綠而亂塞課程」）。修法不是改成違規，是**不強迫收錄、但強迫做決定**——
  沒收錄就要寫下為什麼不教。同一次清出另外 **8 顆**同樣靜默的（093／095／098 加的），
  它們全都是「加了元件而忘了課程那一格」。
- **五次都是使用者發現的**（標籤說謊、變體不在工具箱、通用積木消失、
  `priority_queue` 學生看不到、飛出選單一團亂），而共同點不是不夠小心，
  是**我量的東西不是使用者看到的東西**——所有量測都停在瀏覽器之前。
  → **而五次裡有四次現在有機械檢查了**（可拿性／唯一入口／課程可見度／訊息參數一致性）。
    只剩「標籤說謊」那次沒有，因為它是**語義正確性**——`push` 在堆疊與佇列上意思不同，
    那本來就是人的領域。**這個比例是這一輪真正的成果**：不是「更小心」，是把四種
    失敗方式各自變成一條會紅的檢查。
  這一格**目前無解且明確未補**：Blockly 12 的 FocusManager 在 happy-dom 下 inject
  失敗；退而求其次用 headless Workspace 的 spike 報了 13 筆**全是假的**違規
  （未註冊的是命令式動態積木、建不出來的是沒載 i18n）。
  → **半調子的冒煙測試比沒有更糟**：第一天 13 筆誤報，只會教人忽略它。
    要補這一格該走真瀏覽器，不是 happy-dom。在那之前，「人工看一眼」是流程的一步，
    不是可省的收尾。
- ⚠️ **而它當天就咬了（2026-08-07）**：使用者回報工具箱「怪怪的」，我第一時間從
  螢幕截圖的像素去推，推了兩輪都沒指到根因。**改用真瀏覽器 ＋ DOM 量測**之後，
  一次就看到：飛出選單裡每一顆積木的 `transform` 都是 `translate(0, 0)`、高度 0、
  `textContent` 空的——`updateToolbox()` 換掉工具箱時，開著的飛出選單不會跟著重排。
  → **看得到的東西不要用猜的。** 從像素推 UI bug 的錯誤率高到不值得——
    真瀏覽器 ＋ 量 DOM 是幾分鐘的事，而它給的是**數字不是印象**。
  → 同一次也證明了**修法要驗，不能只推理**：第一版修法（換完再關）看起來合理，
    而**把它退掉之後數字一模一樣**——它既沒修好也不是原因。
    ⚠️ 真正的根因是**少一個 i18n 鍵**：`%{BKY_…}` 展不開 → 訊息沒有 `%1` →
    Blockly `jsonInit` 拋例外 → `clearOldBlocks()` 中斷 → 舊積木永遠清不掉。
    **「重疊」與「少一個翻譯鍵」之間沒有任何直覺連結**——照著堆疊追，不要照著症狀猜。
  → 這條已 skill 化：[[diagnose-in-browser]]（先讀 console → 量 DOM → 做對照實驗）。

### 同一件事推導兩次，兩份就會分歧——而分歧的症狀在很遠的地方

- **實際發生（2026-08-08）**：沒有顯式 `renderMapping.fields` 的積木投影
  （實測 **107 / 131**）靠推導決定「積木欄位 ↔ 語義參數」的對應。
  而推導有**兩份**：`pattern-renderer.ts:365` 與 `pattern-extractor.ts:225`。
- **兩份不一樣**：渲染那份認 `field_multilinetext`，抽取那份不認。於是
  `c_comment_block` 的內容**渲染得出去、抽取不回來**——
  使用者在積木編輯器裡寫的區塊註解**會消失**。
- **症狀離根因很遠**：唯一的表現是「切換積木風格之後東西不見了」，
  而那時使用者已經不記得自己寫過什麼。**沒有任何錯誤訊息。**
- **而它躲得住是因為隔壁那顆活著**：`c_comment_doc` 幾乎一模一樣，
  只因為它剛好有**顯式**的 `fields` 就沒中。
  → **一顆會掉、一顆不會，兩顆看起來一樣**——這比兩顆都掉更難發現。
- **與「一支測著死程式碼的測試」同族，但更糟**：那次是**同一段邏輯的兩份拷貝**
  （`buildIoCategoryContents`），有同樣的缺陷；這次是**兩份不同的拷貝**——
  它們不只重複，還分歧，而分歧只在某些輸入上顯現。
- **收場（同一天）**：兩份合併成一份，再把 **186 筆對應固化成顯式宣告**，
  然後把推導**刪掉**。做法是 E 項那一招：**先拍合併後的照片 → 固化 → 驗一字不差 → 才刪**。
  → 而固化的真正目的不是消滅重複，是**解耦**：推導拿 `concept.properties` 去比對
    積木欄位名，於是**參數宣告驅動了抽取行為**。刪掉之後，把 `var_declare` 的參數列
    整個換成不相干的名字，抽取結果一模一樣——那正是 C1 需要的自由。
  → **代價要有收據**：新積木必須自己宣告對應，忘了不會靜默推導，
    由第二十五條護欄當場指名。**顯式 ＋ 護欄，不是隱式魔法。**
- **教訓**：**同一件事在兩個地方各推導一次，就是在等它們分歧。**
  → 判準：看到「推導／衍生／fallback」出現在兩個模組裡，先問
    **「這兩份會不會不一樣？」**——問法不是讀程式碼比對，是**餵同一個輸入給兩邊，比對輸出**。
  → 而 MEMORY.md 早就記著這個坑的形狀（「只在 Block Style 切換時才暴露」）。
    **記著形狀不會讓它不發生**；把它變成「餵同一個輸入比對兩邊」的護欄才會。
- **來源**：`tests/integration/audit-derive-agreement.test.ts`（第二十四條護欄）、
  `tests/integration/comment-block-roundtrip.test.ts`

### 正則不適合對有巢狀結構的程式碼動刀——同一天栽三次

- **實際發生（2026-08-08）**：把重複的推導合併、把測試改成新契約，我三次用正則
  切／插 TypeScript 區塊，**三次都壞**：
  1. 刪方法時多刪了一堆匯入與私有欄位
  2. 再刪時把 `PatternRenderer.render` 整個刪掉
  3. 插入 `renderMapping` 時插到物件的閉合括號**之後**，語法直接炸
- **三次都是 `tsc` 或測試當場叫住**，所以沒有流出去——但每一次都要還原重來。
- **成功的做法是兩種**：**精確字串取代**（`Edit` 的 old/new 必須完全相符），
  或**先算出行號範圍再逐行操作**。兩者的共同點是**不靠正則去理解巢狀**。
- **這與掃描器那幾次是同一個根**：本檔「量測工具的第一版會安靜地量錯」裡，
  區塊切割、註解誤判、子節點混淆——**全部是正則在假裝它懂結構**。
  差別只在：掃描器錯了會給出假數字（靜默），改程式碼錯了會語法炸（大聲）。
- **教訓**：**要按結構操作程式碼，就用能理解結構的工具。**
  → 讀：TypeScript 編譯器 API（`tests/helpers/param-reads.ts` 就是這樣做對的）
  → 寫：精確字串取代，或行號範圍
  → **正則只適合「找出候選」，不適合「決定邊界」。**

### 一份「宣告」可能正在驅動行為——改它不是文件工作

- **實際發生（2026-08-08，C1）**：`concepts.json` 的 `properties: string[]` 看起來是
  **描述**（這顆元件有哪些參數）。要把它結構化成規格，第一步是讓宣告符合實際。
  改下去，來回轉換兩次變紅。
- **它其實是資料**：`PatternExtractor.deriveRenderMapping`（`pattern-extractor.ts:243`）
  拿 `concept.properties` 去比對積木欄位名（`findMatchingProperty('NAME', […])`），
  推導出抽取用的欄位對應。**改參數列 ＝ 改抽取行為。**
- **兩次撞牆**：把 `input` 的參數列改成「實際被讀的那三個」→ 身分守恆紅
  （`name` 是抽取器經推導對應讀的）；刪掉 `cpp_increment` 看似死掉的大寫退路
  → 來回轉換紅（那個退路是抽取器餵的）。兩次都還原。
- **教訓**：**動一份宣告之前，先問「有沒有人拿它當資料用」。**
  → 判準：grep 那個欄位名在 `src/` 的**讀取**（不是宣告處），
    看有沒有出現在 `if`／查表／比對裡。出現了就不是描述。
  → 而**掃描器看不到這種讀取**：它是「拿整份清單去比對」，不是「讀某一個欄位」。
    我的參數讀取掃描器有三條路徑（TS 產生器／執行器、`codeTemplate`、
    **推導出的欄位對應**），而它只看得到前兩條。
- **連帶**：這也改了護欄的判定方式——見 [[build-guardrail]] 第 6.8 步補的第二個問題
  （「留一筆規範還成立嗎」決定規範值不值得；「**修一筆要付多少**」決定硬性零還是棘輪）。
- **來源**：`specs/102-param-spec/research.md` 決定 6

### 計畫裡的機制斷言，要嘛附行號，要嘛標「未驗」

- **實際發生**：097 的計畫排了一條**「不可調換的硬邊」**——存檔轉換必須先於積木型別改名，理由寫得斬釘截鐵：「反過來做的話，中間會有一段時間任何人重開專案都會壞，那是不能賭的」。實作時去讀程式碼，前提整個垮掉：`app.ts:241` 載入時 `blocklyState` **原樣還原**、`sync-controller.ts:202` **任何編輯都從語義樹重新渲染** → 正確做法是**加法式**（舊型別保留當中性形態），**根本不需要改名，也不需要轉換**。整條硬邊消失。
- **同一輪的第二次**：規格指名阻斷點是 `BlockSpecRegistry.byConceptId`。研究階段一查，它**零呼叫者**——真正的活路徑是 `PatternRenderer.renderSpecs`。
- **兩次的共同形狀**：一個**讀程式碼就會知道**的事實，被當成已知寫進計畫，而且**寫得比任何有證據的段落都更有信心**（「不可調換」「必須」）。
- **這不是「量測工具第一版會安靜地量錯」**：那條講的是工具實作錯。這裡沒有工具，只有**沒去查**。差別在修法：那條要修工具，這條要**改寫計畫的方式**。
- **而流程救了其中一次**：`research.md` 抓到了阻斷點那個，因為它被寫成一個要回答的問題。硬邊那個沒被抓到，因為它**被寫成結論，沒有被寫成問題**。
- **教訓**：**計畫裡任何一句「X 會導致 Y」的機制斷言，要嘛附行號，要嘛標成未驗。** 標了未驗它就會進研究階段；沒標它就會被當成地基，而蓋在上面的東西（排程、硬邊、風險表）全部要重做。
  → 而**語氣愈斬釘截鐵，愈該要求行號**——那正好是最不會有人回頭去查的那一句。
- **同族的第二種：不是假的，是空的（2026-08-07，E 項）**。研究階段的決定 3 寫著
  「讓 `registryCategories` 支援**更細的比對**——而**細分規則本身是宣告的資料**」。
  它讀起來像一個決定，有理由、有否決的替代方案。實作時才發現**那句話沒有指涉物**：
  `containers` 這個 `category` 底下 49 顆積木要散進四個工具箱分類，而它們身上
  **除了 conceptId 之外沒有任何欄位分得開**——而「用 conceptId 比對」正是決定 3
  自己否決掉的做法。
  > **一個沒有指涉物的設計，讀起來與一個有指涉物的完全一樣。只有去實作它才會發現。**
  → 判準：**設計句子裡的每個名詞，指得出一個欄位、函式或檔案嗎？** 指不出來就
  標未驗，和機制斷言同一條紀律。「更細的比對」「適當的抽象」「合適的機制」
  這類**看起來已經決定、其實只描述了願望**的句子，是這個坑的入口。
- **兩者的差別在修法**：假的斷言修完之後計畫還在（換一條路）；空的設計**沒有東西可修**——
  它要作廢重來，而且愈晚發現重做的範圍愈大（決定 3 是在 tasks 都寫完之後才垮的）。
- **來源**：`specs/097-multi-form-projection/`（plan.md 的硬邊、research.md 的更正）、`specs/100-registry-derived-lists/research.md`（決定 3 作廢那一節）、[history/029](history/029-E項登錄表導出-清單不是碎裂是量測算錯了.md)

### 修好一個 bug 之後，去掃同形的地方——否則處方只留在發現它的那一處

- **實際發生**：097 新增的 `form` 欄位在 `BlockSpecRegistry.loadFromSplit` 被**逐欄位列舉**的建構丟掉，症狀看起來像形態選擇函式壞掉，而其實資料在進到它之前就沒了。
- **而處方早就寫在本檔**：「與其偵測錯誤，不如換一個讓錯誤無法被表達的形式」那一則的第一個實例逐字寫著「**展開合併 → 漏欄位不可能**」。**它只被套用在發現它的那一處（存檔）。** `loadFromSplit` 是一模一樣的形狀，沒有人去掃。
- **所以這不是「第 N 個實例」，是更難看的一種**：教訓記了、處方也記了、**而程式碼仍然帶著那個病**，只是換一個檔案。記錄本身讓人以為處理過了——與 [history/025](history/025-那個-flake-從真實變數改為診斷過但沒人接上.md) 同族，只是那次是沒建機制，這次是機制建了沒推廣。
- **教訓**：**一個 bug 的處方寫進知識庫時，同時做一次「還有哪裡是同一個形狀」的掃描**，而且那個掃描要留在原地（一支測試、一條護欄、或至少一行「已掃過 X、Y、Z」）。
  → 判準：**這個處方如果只有一個使用者，它就還沒完成。**
- **而同一條判準也適用於「機制」**（2026-08-07，B 項一輪四次）：`Scope.declareRef`（別名）、`Scope.parent`（走到根作用域）、`ctx.isExpression`（產生的位置）、`SAMPLE_CONTEXT`（合成樣本的脈絡）——**四個機制都早就在，而各自只有一個使用者**，於是需要它的第二處各自繞路或直接壞掉。
  這與 [concepts/執行機構.md](concepts/執行機構.md)「機制有了，沒人接上」是同一件事的兩半：那裡講的是「零個使用者」，這裡講的是「**只有一個**」——而只有一個的更難發現，因為它看起來是在用的。
  → **新增一個機制時，最後一步是找出它的第二個使用者。** 找不到就先不要抽象化（那是 YAGNI）；找得到卻沒接上，那才是這裡說的病。
- **來源**：`src/core/block-spec-registry.ts` 的展開合併（2026-08-07 才補上）

### 契約要能執行，才發現得了契約自己不自洽

- **實際發生**：097 的 `data-model.md` 寫了不變式 **FS-2「fallback 必須在 forms 的值域裡」**。第一版把中性形態**只寫在 `fallback` 而沒放進 `forms`**——於是 FS-2 **永遠不成立**。契約測試第一次跑就紅在「合法的形態集合必須通過」那支。
- **修的是設計，不是測試**：中性形態是一顆**真實存在的積木**（統一的 `c_container_push`），它本來就該被宣告出來。因此引入保留鍵 `_`。
- **關鍵**：這個矛盾**用讀的看不出來**——`data-model.md` 每一條分開看都合理，是把它們一起編碼成可執行的斷言時才撞在一起。
- **教訓**：**契約文件寫完不算數，把它變成會跑的斷言才算。** 而且第一次跑要**同時餵合法與非法輸入**——只餵非法的話，一個「什麼都拒絕」的驗證器會全部通過，而契約自己不自洽這件事永遠不會現形。
- **來源**：`specs/097-multi-form-projection/`（data-model.md FS-2、`tests/unit/core/form-selection.test.ts`）

### 「不在本次範圍」要留下一個會叫的機制，不是留一句話

- **實際發生**：`fuzz-cpp-*` 幾個呼叫編譯器的測試在高負載下隨機變紅。成因**四天前就診斷對了**，逐字寫在 draft 裡：「沒有自訂 timeout，吃 vitest 預設的 5000ms」「**不在 P0 範圍**（只量不修），記在此供後續期別處理」。
  範圍切得對——P0 只量不修是紀律。**壞的是「供後續期別處理」沒有任何機制**：沒有測試、沒有護欄、沒有路線圖項目，只有一句話。
- **那句話產生了反效果**：它讓「**已知的載入敏感 flake**」變成一個**看起來已經處理過的說法**。後續開發中它被用來帶過紅燈至少四次，每次都附「單獨跑就綠」當證據——那個證據是真的，而它剛好是**逾時不足的症狀**。修好之後全套連兩次 211 檔全綠、零 FAIL。
- **順帶推翻了它自己的分類**：當時歸成「真實變數（機器負載消除不了）」。負載確實消除不了，**但逾時是我們設的**——把一個可調的參數說成環境條件，等於把問題移出可修的範圍。→ 判準：**這裡面有沒有一個是我們設的參數？** 有的話它就不是環境。
- **教訓**：**寫下「之後再處理」的那一刻，它就從一個問題變成了一則記錄**——而記錄看起來像處理過了。這與「記錄代替修復」是同一種便宜，只是延後的形式讓它更難察覺：那時你**確實**做了正確的事（診斷、切範圍），只是停在最後一步。
  → **延後要留機制**：一支 `it.fails`、一條護欄的基線、或一個帶驗收標準的路線圖項目。三者都會在該叫的時候叫。**一句話不會。**
- **相關**：[concepts/執行機構.md](concepts/執行機構.md)「機制有了，沒人接上」——這一則更極端，機制連建都沒建；下一條「宣稱『與我無關』之前先去量」的歸因做**對**了，本則揭露的是歸因做對之後仍然可以停在半路
- **來源**：[history/025](history/025-那個-flake-從真實變數改為診斷過但沒人接上.md)、`specs/096-vector-source-init/`

### 停用測試的標籤有四層可信度，而只有最底層是證據

- **實際發生**：查證停用測試的第八批，三支全部標著 `[UNSUPPORTED:vector 的初始化列表語法尚無對應概念]`。實測後：**兩支標籤過期**（初始化列表 094 早就做了，直接開回來就綠，測試本體一個字沒改），**一支標籤方向錯**（列表支援了，掉的是**函式呼叫**當初始值）。
- **它打在既有判準的縫裡**：既有的判準是「逐筆註解是一手記錄，檔案層級的概括是二手概括，衝突時信前者」。這一次衝突發生在**同一支測試內部**——**標題裡的標籤**錯了，而**它下面的註解本體**（「function call initializer is not lifted」）是對的。
- **階梯其實有四層**：檔頭概括 ＜ 逐筆標題標籤 ＜ 逐筆註解本體 ＜ **實測**。愈上面愈是為了「歸檔」而寫，愈下面愈是為了「記住剛才看到什麼」而寫。**標籤是給護欄數的，註解是給人讀的**——前者被寫的時候，寫的人在意的是分類欄位填得對不對，不是它指的方向對不對。
- **八批累計的規律**：~50/64 的標籤是過期的或指錯方向的，而查證過程本身翻出 20+ 個真實缺陷。命中率最高的一批是標著 `[UNVERIFIED]`（「不知道為什麼停用」）的——**因為沒有人假裝知道，所以也沒有人去看**。
- **教訓**：**只有最底層那一層是證據，上面三層都是關於證據的說法。** 照標籤規劃工作之前先量一次；成本通常是跑一支測試，而收益是不去改一段已經正確的程式碼。
- **相關**：本檔「量測工具的第一版會安靜地量錯」第三個實例——**護欄把兩種停用測試當成同一種數**。那條講的是護欄量錯，這條講的是**被量的東西上面貼的標籤本身不可信**：即使護欄數對了，它數的是一堆說法。
- **來源**：`specs/096-vector-source-init/`、`tests/baselines/defect-ledger.json`

### 宣稱「與我無關」之前先去量——歸因不做就只是推託

- **實際發生**：P0 完成後全套測試在高負載下失敗 2–8 個。直覺是「這是既有 flake，跟我的護欄無關」——聽起來很合理，因為失敗的是呼叫編譯器的 fuzz 測試。
- **做法**：**切回功能前的 commit 跑同一套**，結果失敗 **8 個**（比加了護欄之後的 2–3 個更多）；再做 A／B 量測（含護欄 27.21s vs 不含 27.84s）確認護欄本身幾乎不增加耗時。**這時才敢寫「與本功能無關」。**
- **教訓**：「這不是我造成的」是一個**可驗證的宣稱**，而驗證通常很便宜（切一個 commit、跑兩次）。不驗就說，和「記錄代替修復」是同一種便宜——**聽起來像處理過了，實際上只是講過了**。
- **來源**：`knowledge/draft/2026-08-05-元件膠囊重構.md` 坑 ⑥

### 守「未來」的規範，症狀恆為零——所以它最容易空著沒人發現

- **實際發生**：`history/005`（2026-03-09）決定 pattern 歧義用偏序仲裁，三種情況各有處置，狀態欄寫「✅ 已採用」。四個月後第一次為它蓋執行機構才發現：**情況二（交叉歧義報註冊錯誤）從來沒有實作過**，實測 18 對規則落在那裡卻無人報錯；情況一用的是 constraint **數量**這個代理指標而非偏序本身，導致 5 條 constraints 完全相同的規則同分，其中 4 條成為永不被試到的死規則。
- **為什麼能空四個月**：因為它守的不是「現在是對的」，而是「**未來的變更不會破壞現在**」。靠登記順序決勝負的規則**現在幾乎都是對的**（否則專案早就不能用了）——它不會出現在任何失敗測試、任何 bug 報告裡。**零症狀不是健康，是這類規範沒實作時的正常表現。**
- **兩種護欄要分開講**：多數護欄量的是「**有多少東西壞了**」，辨識歧義那條量的是「**有多少東西靠運氣**」。後者的數字下降**不代表修好了 bug**，而代表移除了一個未來會咬人的機會。把兩者混在同一個「品質分數」裡，會讓人以為靠運氣的那部分是安全的。
- **教訓**：一條規範如果的形式是「新增 X 不得改變既有 Y」，**它不做也不會痛，直到很痛**——因此它比任何其他規範都更需要註冊時的機械化檢查。而且**知識庫自己的狀態欄也會存殼**：`history/` 標「已採用」的是當時的**意圖**，不是實作的證據。回頭引用一條舊決定時，先問「它的哪一半真的落地了」。
- **相關**：[concepts/執行機構.md](concepts/執行機構.md)、[history/016](history/016-偏序仲裁的情況二從未實作.md)、[history/005](history/005-pattern-歧義從禁止到偏序仲裁.md)
- **來源**：`specs/051-lift-claim-arbitration`、`tests/baselines/lift-ambiguity.json`
- ⚠️ **同一個病的第二個實例，而它在同一條護欄上連續發生兩次（2026-08-10）**：
  蓋符合性護欄時，第一版比對 `blockDef` 的 input 名與接點名（報 9 筆），
  第二版改讀 `block-registrar.ts` 的 `appendValueInput('X')`（還是 9 筆）。
  **兩版都在量名字對不對——而那是代理。** 符合性問的是「接點回不回得來」。
  第三版改成**合成節點走一次 render → extract 再比對回來的子節點**，報 7 筆，
  而且**完全不比名字**——`extract` 自己會套用 `renderMapping`，走完來回名字問題就不存在了。
  → 判準：**「我量的這個東西，與我想知道的那件事，中間隔了幾層推論？」**
    隔了一層以上就是代理，而代理會在你沒想到的那一層失效。
  → 救它的是「先在**已知答案的樣本**上驗過」（`build-guardrail` 第 6 步）——
    沒有那個樣本，9 筆誤報會被當成真相寫進基線。


### 一個取捨若沒有退出條件，它會永遠留著

- **實際發生**：修函式族的參數時（`specs/105`）要在兩條路之間選——
  照 `u_func_def` 複製 82 行 Blockly 動態積木 × 6，或讓那六顆沿用既有的
  單一文字欄位、加一個宣告式映射。選了後者，理由是前者**正是這階段在治的碎裂**。
- **而那個選擇與專案自己的一條教訓有張力**：
  「需要 parse 回結構才能用的字串，就不該是字串」。
- **處置不是忽略張力，也不是為它辯護，是給它一個出口**：
  寫下**三個升級訊號**，任一出現就該改成結構化插槽——
  ① 使用者在那個欄位打錯字造成的缺陷**出現第二次**
  ② 需要對它做**逐項操作**（重排、單獨刪一個、下拉選單）
  ③ 那個邊界情形從「測試裡的案例」變成**課程裡真的會教的東西**
- **教訓**：**一個取捨若沒有寫下退出條件，它就不是取捨，是預設值。**
  → 而退出條件要是**可觀察的事件**，不是「等我們有空」或「等它變嚴重」。
    「出現第二次」數得出來，「變嚴重」數不出來。
  → 這與護欄的「本護欄不檢測什麼」是同一條紀律：**劃出邊界，
    而不是假裝沒有邊界**。差別是那個講能力，這個講時間。


### 「沒有值」與「沒有人讀」是兩個不同的問題

- **實際發生**：要把六顆元件的 `args`／`params` 從**屬性**移到**接點**（`specs/106`），
  動手前立了一道閘門——**先量那個屬性有沒有值**。量完六顆都是「出現 0 次」，
  於是判定它是死宣告，安全可移。
- **而移完之後有一條護欄變紅**：`audit-param-spec` 報「程式碼讀了規格裡沒有的參數」。
  去查，兩處 legacy fallback 正在讀 `node.properties.args`。
- **兩者都是對的**：那個屬性**真的沒有值**，而**真的有人在讀它**——讀到 `undefined`，
  走進一條永遠走不到的分支。
- **教訓**：**「這個欄位有沒有值」與「有沒有人讀這個欄位」是兩個問題，
  而只量前者會漏掉後者。**
  → 移除一個宣告之前，兩個都要量：**寫的人**（有沒有值）與**讀的人**（有沒有引用）。
  → 而這一次的答案讓修法更好——那兩處是**死程式碼**，該刪掉而不是保留；
    只量了「有沒有值」的話，會把它們留著，於是宣告收不乾淨。
- **順帶**：一條護欄替另一條護欄的盲區補了位。
  `audit-param-spec` 量的是「讀的人」，而我立的閘門量的是「寫的人」——
  **兩條合起來才是完整的問題**。這也是為什麼護欄要多而不是要大。


### 量測低報到**零**是最糟的方向——看不見的缺陷與不存在的缺陷長得一樣

- **實際發生**：缺陷帳（追蹤停用測試的護欄）在同一個月裡被發現**三個**盲區，
  每一個都讓某一整類缺陷從帳上完全消失：

  | | 盲區 | 怎麼發現的 |
  |---|---|---|
  | 1 | 掃描範圍只有 `tests/`，而元件膠囊的自證測住在 `src/components/` | 寫第一顆膠囊的自證測時 |
  | 2 | 掃描是**逐行**的——把標題換到下一行那筆就消失 | 同上，而全庫只有我那一筆是跨行的，**所以從來沒被觸發過** |
  | 3 | 完全不認 `it.fails` | 釘住一個已知缺陷時 |

- **第 3 個最難看**：`build-guardrail` **明確推薦**用 `it.fails` 釘住已知缺陷
  （它會跑：缺陷還在時綠、修好時紅並提醒拔釘子）。而缺陷帳看不到它。
  → **「用推薦的方式釘住缺陷」＝「那筆缺陷從帳上消失」。**
    那是一個**獎勵錯誤行為**的量測。補上之後多出來的兩筆裡，
    有一筆已經在那裡很久了，而且沒有分類標記。
- **教訓**：**量測出錯的方向要分開看。低報到「少一點」還有得救——
  數字不對但形狀還在；低報到「零」沒有：一筆看不見的缺陷，與一筆不存在的缺陷，
  在報表上長得一模一樣。**
  → 判準：**「這個量測有沒有某一整類輸入會回報零？」**
    有 → 那一類就是它的盲區，而**盲區的大小量不出來**（它在盲區裡）。
  → 具體做法：把量測的**入口條件**寫成斷言（掃了幾個目錄、認得哪幾種寫法、
    語料幾段），而不是只斷言結果。三個盲區裡有兩個是靠「換一種寫法試試」
    發現的，不是靠讀程式碼。
- **而護欄要多而不是要大**：三個盲區有兩個是**別的護欄**替它補位發現的
  （`audit-param-spec` 量「讀的人」、符合性量「回得來嗎」）。
  一條大而全的護欄沒有第二雙眼睛。


### 一支斷言「檔案裡有這個字串」的測試，全綠不代表行為是對的

- **實際發生**：要把兩顆積木重複的參數列抽成工廠（`specs/107`）。動手前查覆蓋，
  發現那個檔的 12 對動態插槽行為**零自動化覆蓋**：
  - `happy-dom` 跑不動 Blockly 12 的 FocusManager
  - 生產的投影入口 `renderToBlocklyState` 產的是純 JSON，**完全不經過 `Blockly.Blocks`**
  - 而 `block-registrar.test.ts` 的四支測試是 **`readFileSync` ＋ `toContain('saveExtraState')`**
- **那四支測試會通過任何一次重構**，只要字串還在檔案裡——包括把功能改壞的那些。
- **而它們同時會擋住對的重構**：把行為搬到另一個檔，字串就不在了，
  測試變紅——**為了一個錯誤的理由**（能力沒有消失，只是被共用了）。
- **教訓**：**斷言「原始碼長什麼樣」與斷言「系統做什麼」是兩件事，
  而前者會同時放過真的退步、擋住真的改善。**
  → 判準：**「這支測試會因為什麼而紅？」** 答案若是「檔案內容變了」而不是
    「行為變了」，它就不是行為測試，報表上不該算成覆蓋。
  → 而它**仍然可以有用**——「`app.ts` 裡不得有 `Blockly.Blocks[`」是一條真的架構約束，
    文字就是它要管的東西。**問題不在它存在，在它被讀成行為覆蓋。**
- **這一次它直接改變了一個設計決定**：工廠因此**放在同一個檔**，
  而不是抽成新模組——不是因為那樣比較好，是因為搬走會讓那四支測試
  因為錯誤的理由變紅，而**這次沒有第二個 oracle 能分辨對錯**。
  → 沒有行為覆蓋的地方，**重構的形狀會被測試的形狀綁架**。


### 與其偵測錯誤，不如換一個讓錯誤無法被表達的形式

- **實際發生**：存檔層把 `blockStyleId` 與 `locale` 每次都丟掉——呼叫端傳了、介面宣告了、組合新狀態時**沒有列舉到**。兩個欄位在型別上是選填的，編譯器不會抱怨。使用者的積木外觀與介面語言**從來沒有被保存過**。
- **兩條修法**：
  - **偵測**——保留逐欄位列舉，加一支測試抓漏。下次還會漏，只是會被抓到。
  - **消除**——改用展開合併 `{...預設, ...既有, ...傳入}`。**漏欄位在結構上不可能發生。**
- **同一個功能裡出現三次**：
  1. 展開合併 → 漏欄位不可能
  2. `refused` 分支型別上必帶 `backedUpTo` → 「拒絕了但沒備份」**編不出來**
  3. `satisfies Record<keyof Required<T>, 1>` → 欄位清單與型別漂移**編不過**
- **關鍵的但書**：**消除之後，偵測的測試仍然保留**。它守的不是同一件事——修法消除的是今天的 bug，測試守的是「有人日後把展開改回列舉」。以為消除之後就不用測，是把兩種保護當成同一種。
- **判準**：拿到一個 bug 先問「有沒有一種寫法讓它連寫出來都不行」。答得出來就選那個，然後**仍然把測試留著**。答不出來才退回偵測。
- **相關**：[concepts/執行機構.md](concepts/執行機構.md)「把推斷改成宣告」是同一個家族——那條講的是讓**缺失**可偵測，這條講的是讓**錯誤**不可表達
- **來源**：`specs/052-storage-integrity-gate/research.md` F4／F5

### 檔案怎麼分，和東西屬於誰，是兩回事

- **實際發生**：把執行器搬進各自的模組時，spec 寫的是「`strings.ts` → `std/string/executors.ts`」。**錯的**——那個檔跨兩個標準函式庫模組（`<string>` 17 個、`<cstring>` 10 個）。同樣地 `containers.ts` 跨六個。
- **為什麼會寫錯**：檔名長得像歸屬。但**執行器檔案是按「誰跟誰寫在一起方便」分的，歸屬則寫在概念註冊表裡**，兩者從來沒有義務一致。
- **怎麼查對**：不看檔名，去問註冊表——每個概念宣告在哪個模組的定義檔裡，它就屬於誰。查完才發現還有 7 個跨容器的泛用操作**不屬於任何標準函式庫**，而它們的產生器早就在語言核心——**它們的家本來就在核心，只有執行那一路走丟了**。
- **教訓**：**重構前先問「這個東西屬於誰」，答案要從宣告來，不從檔案位置來。** 檔案位置是上一次重構留下的痕跡，不是事實。
- **來源**：`specs/054-execute-into-capsules/research.md` F1／F2

### 每條防線都有它抓不到的形狀，而那個形狀要說出來

- **實際發生**：搬移的主防線選了「搬移前後執行引擎認得的概念集合必須完全相同」——因為逐一比對輸出**漏一個不會現形**（測試沒覆蓋到就過了），集合比對會。這個選擇是對的，它在第一次搬移就抓到「推送函式寫了卻沒人呼叫」。
- **但它抓不到另一種錯**：拆分工具第一版用括號深度找區塊邊界，字串裡的括號把計數弄歪，**把兩筆註冊併成一塊**。併起來之後概念**還在**，只是跑進了錯的模組——**集合完全相同，防線全綠**。
- **抓到它的是別的東西**：27 vs 25 這個對不上的數字。而 research 的自我否證正好預先寫過「若某份執行器用批次註冊，正規表示式會漏掉」。
- **教訓**：選一條防線的時候，同時寫下**它抓不到什麼**。「漏失」與「錯置」是兩種形狀，集合比對只抓得到前者。**沒說出來的話，全綠會被讀成「都對了」。** 這與護欄要聲明「本護欄不檢測什麼」是同一條紀律，只是套用在臨時的驗證手段上。
- **來源**：`specs/054-execute-into-capsules/`、[concepts/執行機構.md](concepts/執行機構.md)

### 護欄常常只問了一個方向

- **實際發生**：完備性護欄迭代**概念註冊表**，所以它問的一直是「已宣告的概念，五條路都有實作嗎」。**它從來沒問過反方向**——「有實作的東西，有被宣告嗎」。於是 4 個有執行器卻沒有定義的概念**完全不在任何報表上**。補上宣告後，它們身上藏了很久的 8 個缺口才第一次現形。
- **同一天的第二個實例**：P9 的原文是「拔掉 C++ 後核心**無 `languages/cpp/` import**」，而中立性護欄從第一天起數的是**概念身分字串**。一個核心檔可以一個 C++ 概念名都不提、卻直接 import 整個語言套件——身分掃描全綠，P9 已經破了。**那條原則自己寫下的檢查，兩個月來沒被做過。**
- **為什麼會這樣**：護欄是照著「我們怕什麼」寫的，而怕的通常是**已經被咬過**的那一種。沒被咬過的方向就沒人想到。
- **教訓**：蓋一條護欄時多問一句——**「這條規範還有沒有另一個方向？」** 具體做法是把規範的主詞與受詞對調再讀一次：「宣告的有沒有實作」→「實作的有沒有宣告」；「核心提到語言概念」→「核心引用語言套件」。對調之後讀起來成立的，就是漏掉的那一半。
- **相關**：[concepts/執行機構.md](concepts/執行機構.md)、`specs/055-finish-executor-move`

### 「指不到」與「沒有」回傳同一個值時，破 75% 也沒人知道

- **實際發生**：131 個概念宣告了語言中立的父概念，**98 個（75%）指向根本不存在的概念**。查詢的函式長這樣：

  ```
  findAbstract(id) {
    if (!concrete?.abstractConcept) return undefined   // 沒有宣告
    return this.concepts.get(concrete.abstractConcept) // 指不到 → 也是 undefined
  }
  ```

- **所以它壞掉的樣子，與「這個概念沒有宣告父概念」完全一樣**——而後者是完全可以接受的狀態。於是一個四分之三是破的抽象層，看起來像「大部分概念還沒填父概念」。
- **連帶的後果**：介面層需要「這個概念退回哪個通用概念」時，抽象層指不到東西，只好**自己寫一份 16 行的對照表**。同一個事實因此有兩處記載，而正解那一處是壞的。
- **教訓**：一個查詢若把**「沒有設定」與「設定了但指不到」回傳同一個值**，那個欄位的完整性就永遠沒有人會發現。**判準**：對每個「指向別的東西」的欄位問一句——「填錯的時候，回傳值跟沒填一樣嗎？」一樣 → 需要一條檢查存在性的護欄。
- **相關**：[concepts/執行機構.md](concepts/執行機構.md)「護欄常常只問了一個方向」
- **來源**：`specs/056-abstract-concept-integrity`

### 掃描要分得出「這裡實作了它」與「這裡提到它」

- **實際發生**：把 30 個概念的父概念改指向 `var_declare` 之後，就近性護欄把 `var_declare` 的擴散度從 12 檔算成 **19 檔**——它把 `"abstractConcept": "var_declare"` 這個**值**當成 `var_declare` 的實作足跡。
- **那是反的**：越多概念認它當父概念，它就越「碎裂」。而事實正好相反——那代表抽象層更完整。
- **同一個形狀先前出現過兩次**：中立性護欄要剝離註解（提到 ≠ 耦合）；P9 的 import 檢查第一版忘了剝離，把一句解釋用的註解報成違規。
- **教訓**：任何以「字串出現次數」為基礎的掃描，都要先問**「這一次出現，是實作、是引用、還是只是提到？」** 三者混算的話，數字會在**做對事情的時候變糟**——那比數字錯更危險，因為它會懲罰正確的改動。
- **來源**：`specs/056-abstract-concept-integrity`

### 半條路修好，比沒修更難察覺

- **實際發生**：`specs/050` 修好了陣列初始值的**辨識**——`int a[3] = {1,2,3}` 的值會進到語義樹的 `values` 子槽，測試也釘住了。但**執行那半從來沒接上**：`array_declare` 的執行器只按大小配置預設值，從頭到尾沒讀過 `values`。
- **症狀**：`int a[3]={3,1,2}; cout << a[0];` **輸出 0**。而在語義樹上、在積木上、在產生的程式碼上，那三個值**都看得見**。
- **為什麼特別難察覺**：修好的那半會產生「已經修好了」的證據——round-trip 測試綠、語義樹裡有值、缺陷帳上那條被劃掉。**證據是真的，只是不完整。**
- **教訓**：修一條跨越多個路徑的缺口時，**逐路確認，而不是確認「那個 bug 的測試綠了」**。這個專案有五條路（辨識／產生／渲染／取回／執行），一條路的測試綠不代表另外四條接上了。
- **相關**：[concepts/執行機構.md](concepts/執行機構.md)「功能完成 ≠ 功能接通」是同一族——那條講的是「元件都寫好了但沒人呼叫」，這條講的是「一條路修好了，另一條沒有」
- **來源**：`specs/053-declare-noop-execute/classification.md` 追加分類

### 殼的數字要按**原因**分組，才看得出它是幾個問題

- **實際發生**：完備性報表說有 78 個殼。按原因分組之後：

  ```
  38  execute｜空操作且未宣告      ← 真工作
  34  lift｜找不到原本的身分        ← **一個根因**
   4  generate｜輸出為空或佔位
   2  lift｜降級成 raw_code
  ```

- **那 34 個不是 34 個問題**：查下去發現多數是合成樣本產生了錯的程式碼（`compare` 產生 `1 + 1`）或語法上孤立的片段（`case 1:` 沒有 switch）。**20 個是量測造成的。**
- **教訓**：一個護欄報「N 個違規」時，先問**「這 N 個是幾個原因？」** 不分組的話，一個根因會被讀成 N 個待辦，而清償優先序會照著那個假的 N 排。**分組的成本是十行程式碼，不分組的成本是把力氣花在錯的地方。**
- **來源**：完備性護欄的原因分佈區塊

### 機制跨不過分層時，複製一份到界線另一邊，而不是把機制變大

- **實際發生**：積木插槽名的「唯一真相」機制住在核心側，只涵蓋通用積木。語言專屬積木的插槽名因此仍然寫死。第一個結論是「**遷不了**——要涵蓋語言積木，那個模組就得引用語言套件，與『核心不認識語言』相衝」。
- **那個推論漏了一步**：正確的形狀不是讓核心那份變大，是**讓語言套件自己提供一份**。語言套件引用自己的宣告檔完全沒有問題，而消費者（介面層）從兩邊各取所需。
- **一般化**：當一個機制「涵蓋不到某類東西」而理由是**分層限制**時，先問——**這個機制能不能在界線的另一邊各存在一份？** 能的話，兩份同形的小機制勝過一份跨界的大機制。跨界的那份會把分層打破，而分層本來就是為了讓拔掉一邊還能運作。
- **代價要記**：多一份模組，就多一個檔提到那些概念。這次是 `cpp_string_at` 從 9 檔變 10 檔——**殺掉雙重真相換一個元件多碰一個檔**，與先前拆分執行器時的交易同型。
- **來源**：`specs/057-single-source-input-names`

### 量錯的方向通常是「把不該算的算進來」

- **實際發生**：同一個問題的量法換了三次，每次數字都更小、更誠實：

  | 版本 | 量什麼 | 數字 | 錯在哪 |
  |---|---|---|---|
  | 一 | 比對兩邊的插槽名集合 | 29 | 動態側只算輸入不算欄位，JSON 側兩者都算——**兩邊定義沒對齊** |
  | 二 | 對齊之後再比 | 18 | 用常數寫的插槽名被判成「動態側沒有」——**那些恰恰是正例** |
  | 三 | **有 JSON 對應卻仍寫死** | **13** | — |

- **第三版還排除了 57 處**：mutator 容器、執行期生成的插槽、純排版用的虛擬輸入——它們沒有 JSON 對應物**是設計如此**。
- **模式**：三次錯都是**把不該算的算進來**，沒有一次是漏算。原因很直白——**寬鬆的量法比較容易寫**，而數字大看起來又像「發現了很多問題」。
- **判準**：一個護欄報出 N 之後，先問**「這 N 裡面有哪些本來就該長這樣？」** 而不是先問「怎麼把 N 降下來」。
- **來源**：`specs/057-single-source-input-names`

### 單向的棘輪不會自己收緊——改善也要紅

- **實際發生**：一條護欄的基線寫著 4，實際量到 1。前一個功能修好了三個，**沒有重新產生基線**。而棘輪只擋上升，所以它**默許退回 4** 而不會有人發現。
- **改善訊息一直都印著**（「有改善，可下調基線」），印在 stdout 上。**沒有人會為了一行輸出去改檔案。**
- **教訓**：棘輪要真的「棘」，**兩個方向都要出聲**。改善時擲錯，訊息寫「請下調基線並與這次改善一起 commit」——下調是十秒鐘的事，而且本來就該在同一個 commit 裡。
- **與「不准紅著過夜」不衝突**：那條講的是不要**放著**，不是不要紅。一個十秒能修的紅，比一個沒人看的 stdout 有用得多。
- **推廣**：任何「只在變壞時出聲」的機制，都要問一句——**變好的時候誰負責把門檻拉上來？** 答案是「靠人記得」的話，那個門檻遲早會鬆掉，而且鬆掉的樣子與從來沒緊過完全一樣。
- **來源**：`tests/helpers/guardrail.ts` 的 `assertRatchet`

### 合成測試的**環境**也要真實，不只輸入要真實

- **實際發生**：完備性護欄與身分測試都寫著 `const STYLE = { id: 'default' } as StylePreset`——一個**不存在的風格**。於是 `io_style` 是 undefined，產生器走了非預期的分支：

  ```
  假風格  print → 「printf("%d", 1);」→ 辨識回 cpp_printf  🔴
  真風格  print → 「cout << 1;」      → 辨識回 print       ✅
  ```

- **後果不只是一個數字錯**：那個假象被 `specs/050` **當成已知缺陷釘住**，還附上「兩條修法都會動跨風格既有行為，因此擱置」的完整分析。**那整段分析建立在一個假的測試環境上。**
- **釘住一個量測假象，比不釘更糟**——它讓後續每一個讀到的人相信系統壞了，而且釘子本身看起來像盡責。
- **`it.fails` 這個機制沒錯**：假象一被修掉，它立刻變紅提醒拔釘子，完全按設計運作。**問題不在機制，在釘之前沒有先確認缺陷是真的。**
- **教訓**：合成測試裡凡是「隨手造一個物件塞進去」的地方都要問——**真實流程裡這裡是什麼？** 輸入的真實性通常有人管，**環境（風格、設定、註冊表狀態）的真實性沒有**。
- ⚠️ **「輸入的真實性通常有人管」在 2026-08-10 被推翻了一半**：那是對**單筆合成輸入**說的（有人會盯著看），而對**大批撈來的語料**不成立——`specs/108` 一輪之內語料錯了三次，其中一次差 200 倍。
  → 分界：**輸入是一顆一顆寫的，就有人管；是一批撈的，就沒有。** 見本檔「量一個新刻度時，最可能錯的是語料」。
- **來源**：`specs/057`、`specs/050/research.md` D3

### 「後註冊的贏」的註冊表，順序就是優先權——而順序沒有人在設計

- **同一件事咬了三次**：

  | 何時 | 什麼被蓋掉 | 症狀 |
  |---|---|---|
  | 052 之後 | 四個轉型概念的真實作被「無執行行為」清單覆蓋 | `static_cast<int>(3.9)` 輸出 `void` |
  | 054 之後 | 模組的執行器被同一份清單覆蓋 | 概念從清冊裡消失 |
  | 057 | 語言套件的條件編譯實作被核心的缺口清單覆蓋 | `#ifdef` 的 body 不跑 |

- **三次都不是「寫錯」**，是**註冊順序**：`Map.set` 後寫的贏，而順序取決於建構式裡幾行呼叫的先後——**那個先後從來沒有人刻意設計過**。
- **修法不是每次都去調那一行**，是把優先權變成結構：**語言套件對自己的概念有最終發言權，所以它的註冊放在最後**，並在那段程式碼旁邊寫明「這一段不能往前搬」。
- **判準**：任何「後寫的贏」的註冊表，都要問一句——**誰應該贏？** 答得出來就把順序固定下來並寫明理由；答不出來的話，那個註冊表需要的是**衝突偵測**而不是順序約定。
- **相關**：`specs/051` 為辨識規則建了歧義護欄，執行器註冊表的重複計數是 055 才有的（第七條護欄）
- **來源**：`specs/057`

### 同一個欄位名長在三個不同型別上時，腳本改名一定會錯——而型別檢查看不到

- **實際發生**：要把語義樹的 `concept` 改名成 `componentId`（跨專案協商定案的詞彙）。做法是「先改介面，讓編譯器指出每一處」——那一步很乾淨，94 處一次改完。
- **然後就翻車了**，因為 `concept` 這個名字**同時長在三個不同的型別上**：

  | 型別 | 欄位 | 意思 |
  |---|---|---|
  | `SemanticNode` | `concept: string` | 這是哪個元件的實例 ← **要改的** |
  | `BlockSpec` | `concept: { conceptId }` | 這顆積木對應的概念物件 ← **不能改** |
  | `ConceptMapping` | `concept` | 又是另一回事 ← **不能改** |

- **編譯器只守得住第一個**。測試檔裡的 `concept: { conceptId: 'number_literal' }` 被改成 `componentId: {...}` 之後**照樣編得過**（測試不在型別檢查範圍內），只有跑起來才錯。
- **腳本還做了兩件更糟的事**：刪掉一整段執行器、把一個**刻意擺在建構式最後**的區塊移到中間（那個位置有註解寫著「放在前面的話核心的空操作會蓋掉語言的真實作，這個專案已經被同一件事咬過三次」）。
- **最後回退了。** 121 個檔改動、10 個檔紅著、根因不明，而**這次改名沒有任何功能價值**（純詞彙對齊）。無法在合理時間內逐一驗證的修改不該留著。
- **教訓**：
  1. 大規模改名前，先問**「這個名字在幾個型別上出現？」** 只有一個才適合腳本。
  2. **型別檢查涵蓋不到的地方（測試、JSON、字串鍵）就是腳本會錯的地方**——那裡沒有安全網。
  3. 腳本改名要**每次只動一種語法形式**（屬性存取／物件鍵／型別標註各一輪），而不是一次全部。混在一起的話，出錯時分不出是哪一種形式錯了。
- **來源**：`specs/058-core-type-vocabulary`（已回退，方法要換）

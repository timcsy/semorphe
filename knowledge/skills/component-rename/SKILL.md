# 大規模改名（component-rename）

## 這個 skill 做什麼

把一批**元件身分或參數名**從舊形態改到新形態，範圍是**上千處引用、上百個檔案、
跨 JSON 與 TypeScript**，而且**每一次都必須附一次性存檔轉換**（P8 的範圍，見
`knowledge/history/026`：不做向後相容管的是投影與程式碼，**不管語義詞彙本身**）。

（緣起：這個操作在 089／103／D／G 裡重複了**八次**。G 一輪就六次——D1、主體、
操作詞、函式庫名、修飾詞、接收者。我每次都從零重建同一支工具，而**重建時漏了欄位**：
`blocks.json` 的 `id` 在四輪裡都不在允許清單上，第五輪才補了 11 處。
這份清單存在的唯一理由就是那 11 處。）

## 這把刀先問一句

> **「改完之後，紅的那一條測試，我指得出是哪一段改的嗎？」**

答不出來 → **先分段**。一次改 6228 處然後看到 900 支紅，你只會全部還原重來。
089 的 560 處出錯三次，就是因為沒分段。

### ⚠️ 而分段要按「誰驗收它」切，不是按「它是什麼類型」（2026-08-20）

`concept` 家族改名先切成「JSON 鍵／檔名／匯出符號／內部變數／tests」——**按類型**。
段落跑完測試整片紅：`TypeError: n.concepts is not iterable`。
**`src` 的匯出符號與 `tests` 的引用是同一份契約，中間沒有可驗收的斷面。**

```
❌ 按類型   src 的 TS ｜ tests 的 TS              ← 中間沒有綠的狀態
🟢 按驗收   {src TS ＋ src JSON ＋ tests ＋ e2e}   ← tsc ＋ 全測試一起驗
            {檔名 ＋ 引用它的字串}                 ← tsc 驗
```

> 畫邊界之前先問：**「這一段跑完，什麼東西會告訴我它對了？」** 答不出來 → 那是一段的一半。

分段的目的是**歸因**，不是把改動切小。**一段可以很大，只要它跑完有東西驗得起來。**

## 步驟

### 1. 護欄先蓋，而且第一次跑必須是紅的

走 [[build-guardrail]]。**驗收數字要在動手之前就量出來**，不是改完再回頭找理由。

⚠️ 順序不可反的理由在 build-guardrail 6.5：**改名會「順便」修掉違規**，
而被順便修掉的缺陷不留紀錄，它的同類還會再來。

### 2. 量規模，用**位置**分角色，不用字串比對 ⚠️

`tests/helpers/identity-refs.ts` 是現成的（TypeScript AST，分
`componentId`／`blockType`／`非身分`）。**不要重寫，不要用 grep 代替。**

理由是實測的：177 顆身分裡 32 顆是**裸名**（`if`／`print`／`comment`／`input`），
而它們同時是 DOM 標籤、tree-sitter 節點型別、除錯動作、產生出來的原始碼文字。
更兇的是 **66 顆身分與積木型別同名**——改錯邊的症狀是「積木消失」，
而積木消失有十幾種成因，那正是「紅得無法歸因」的長相。

### 3. JSON 用**允許清單**，TS 用**拒絕清單** ⚠️ 兩邊方向相反

這一條是整份 skill 最貴的一行。

| | 策略 | 為什麼 |
|---|---|---|
| **JSON** | 只改**指名的鍵** | 值裡到處是自然語言標籤、程式碼片段、型別名。全改必炸 |
| **TypeScript** | 改**全部**，只跳過量出來的非身分位置 | 身分經由變數傳好幾層，AST 追不到 |

**TS 用允許清單試過一次：952 支測試變紅**——約 800 處身分引用落在角色分類器
看得見的範圍之外。分類器是**低報**的工具（它自己的註解就這麼寫），
拿低報的工具當允許清單，等於把它看不見的都留在舊形態。

#### ⚠️ 鍵改名走**文字層正規式**，不要 parse → dump（2026-08-20）

`json.loads` → 改鍵 → `json.dumps(indent=2)` 寫回：**707 個檔被改動，真正有那些鍵的只有 64 個**
——其餘全是縮排重排。重排過的檔案，之後任何一次 review 都看不出真正改了什麼。

→ 用 `re.sub(r'"key"(\s*:)', …)`。只有**真的要改結構**時才 parse。
發現重排了就**全部還原、換工具、重跑**，不要就地把多餘的 643 個檔 checkout 回來
（你不會知道自己有沒有漏掉一個）。

#### JSON 的鍵清單——照抄，不要憑印象重打

```
componentId, component, id, type, blockType,
abstractComponent, extends, requires, provides, blocks[], components[]
```

⚠️ **`id` 是漏過四輪的那一個。** `blocks.json` 用 `id` 而不是 `blockType`，
而我每次重建工具時都從「componentId 開頭」想起，想不到那裡去。

**每次跑完，對沒被改到的檔案做一次反向抽查**：如果某個檔案一處都沒改，
問「它本來就沒有身分，還是它的鍵不在清單上」。

### 4. 一段一驗收，紅了**整段還原**——不要在紅的狀態上疊改動

D 的第 ① 段跑了 **128 → 62 → 20 → 0** 四輪，每一輪都是**整段 `git checkout` 還原**
再重跑改良過的工具。

在紅的狀態上手動補 62 處看起來比較快——而那 62 處會混進下一輪的量測，
於是你再也不知道工具改良了沒有。**還原是為了保住量測，不是為了潔癖。**

### 5. 一次改名 = 一次存檔版本 ＋ 一張凍結的明表

`registerIdMigration()` / `registerPropertyMigration()`——**核心給機制，套件給資料**。

⚠️ **改名表不得寫在 `src/core/`。** 犯過兩次，隔一天一次：D 的 174 筆表寫進核心
（中立性護欄報 284 筆違規），G 的 `naming.ts` 裡有 `istringstream`（語法耦合護欄抓到）。
第二次沒認出來，是因為第一次的形狀是「一張表」，這次是「一份詞彙」。

#### 表要**凍結成明表**，不要從當下的登錄表推

規則很單純，而「v2 那時存在哪些身分」是**歷史事實**。從登錄表推導的話，
往後每一次增刪元件都會悄悄改變這張表——而它要處理的是兩年前存的檔案。

#### ⚠️ 遷移表的鍵**屬於它那個版本**，不屬於現在

G 的參數改名跑在 v3→v4，身分改名跑在 v4→v5。我一度把參數表的鍵「順手」
更新成 `cpp:*`——**那會讓 v3 的樹完全對不上，結果是「id 改了而參數沒改」，
而分段各自的單元測試都會過。**

→ **必須有一支端到端測試**：從最舊的版本一路跑到最新，斷言身分與參數
**都**落在最終形態。分段測試抓不到這個。

### 6. 改完之後，掃一遍「拿名字的形狀做判斷」的地方 ⚠️

**這是改名最常見的靜默災難，而它已經發生三次，其中兩次在同一輪重構裡。**

| 何時 | 哪裡 | 症狀 |
|---|---|---|
| D | `lifter.ts` 的 `/^cpp_(\w+?)_declare$/` | 型別追蹤靜默失效 |
| D | `interpreter.ts` 的 `if (concept.includes(':')) return` | 單步除錯完全失效 |
| G | 第九條護欄的 `/_declare$/` | `var_declare_const` 不再以 `_declare` 結尾，整族從信號消失，五筆判定變孤兒 |

三次都**不會讓測試變紅**——功能安靜地少做事，或護欄安靜地少量一族。

**機械做法**：改名前 grep 一次，把命中處列成清單帶進改名，改完逐筆看過。

```
grep -rnE "(startsWith|endsWith|includes|match|test)\(\s*['\"/][a-z_:]" src/
grep -rnE "/\^?[a-z_]*(cpp_|_declare|_expr)" src/
```

> **命名慣例不是契約。** 要判斷「這顆概念是不是 X」，就宣告一個 X。

### 7. 有詞彙表的話，詞彙表與護欄是**同一份交付**

沒有明列的詞彙，「名字一致嗎」問不出答案。所以
`src/languages/<lang>/naming.ts`（詞彙）與 `audit-naming.test.ts`（護欄）一起交。

**表是目標不是快照**——同義詞各留一個，其餘故意不列，於是它們會被指名。
而「加一個新字是顯式動作」是防腐的關鍵：免費加字的話詞彙表會爆炸，
必須改一份明列清單的話，**有人會在寫 `length` 的時候看到清單上已經有 `size`**。

### 8. 一條新規則落地時，第一件事是拿它掃一遍**現有的**資料 ⚠️

G 的護欄第一版誤報 84 顆（實測 ~35）。第三個原因最值得記：
**我自己剛寫下的規則③（主體在前）被 `count_loop` 違反了，而我沒有檢查它。**

而它的症狀特別：**不產生奇怪的數字**——那些迴圈被歸進了「裸的函式庫名」，
所以**別的類別**多報。你會去查那個類別，查不出所以然。

### 9. 量測工具不得量到自己

改名的棘輪會數到**自己的基線 JSON**（1516 → 1690）與**遷移表**
（那張表按設計就是要列出舊名字）。

→ 排除 `tests/baselines/`、排除被分類為「清單」的檔案，**而豁免要具名附理由**
（`identity-refs.ts` 的 `豁免` 陣列就是這個形狀）。靠路徑規則順便放過，
就是 `history/018` 的「用宣告刷數字」。

### 10. 被擋住的測試用 `[BLOCKED:]`，不要 `it.todo`

改名途中會有測試因為別的原因暫時過不了。標題前綴 `[BLOCKED: 原因]` 讓它
在缺陷帳裡看得見；`it.todo` 會讓它消失（見 [[feedback_fix_bugs_not_document]] 的紀律）。

## 2026-08-11 實測：**改名積木型別**（不是身分）——五步全部適用，而多一條

`spec 116` 把 153 顆積木型別改成從元件身分導出。**五個步驟一條都沒有失效**
（護欄先蓋且第一次紅、一段一驗收、一次改名＝一次存檔版本＋凍結明表全部照用），
而它掀出一條這張表沒有的：

### ⚠️ 第六步：**先列出「描述過去的東西」，把它們排除在腳本之外**

第一版腳本把 `(?<![A-Za-z0-9_])OLD(?![A-Za-z0-9_])` 掃遍整個 repo。
**四類誤傷，每一次都是同一個形狀：那個字串描述的是過去，不是現在。**

| 誤傷 | 後果 |
|---|---|
| **另一張凍結明表**（身分改名表） | ⚠️ **最危險**。它的鍵是舊時代的**身分**，字面與積木型別一模一樣而意思完全不同。改掉 = **真實使用者的舊存檔升級不了** |
| 知識庫 | 湮滅「化石長什麼樣」的證據 |
| 基線與有日期的稽核報表 | 基線要**顯式重產並註明原因**，不是被腳本靜靜改掉 |
| **護欄自己的注入錨點** | 「壞名字」被改成對的名字——**壞的輸入變成對的，注入測試靜靜失去意義** |
| **描述舊資產的斷言** | 「這份 v9 存檔含 `c_stack_push`」被改成新名——斷言還在，但它問錯了問題 |
| **別處指向 `specs/` 的路徑字串**（2026-08-20 新增） | 護欄讀 `specs/059-concept-id-vs-lookalike/baseline-29.txt`，路徑被改 → ENOENT，整支載入失敗。⚠️ 我豁免了 `specs/` 底下的**內容**，卻沒豁免**從外面指向它的字**——而那正是它會出現的地方 |

> **一次改名要問的不只是「哪些地方要改」，還有「哪些地方**因為描述過去**而不能改」。**

判準：**這個字串是在描述現在的世界，還是在描述一個已經過去的世界？**
描述過去的 → 排除。而它們往往長得跟要改的東西一模一樣，這正是危險的地方。

### ⚠️ 第七步：改名會打破「拿形狀當判斷」的消費者——**連測試一起**

`toolbox-builder` 用 `startsWith('u_')` 分「通用 vs 語言專屬」。
前綴消失之後它恆為空，排序偏好**靜靜失效**。

而**三支測試用同一個判斷**——測試與被測物同時犯同一個錯，
**那時測試不保護任何東西**。

同一個病的第三處是用**字串手術**組出另一個系統的名字
（`` `u_${componentId.split(':').pop()}` ``）。它壞過一次、被補了註解，
**而註解擋不住第二次**。

> **會漂移的不是那一行，是「用手拼出另一個系統的名字」這件事本身。**

→ 改名前 grep 三種形狀：`startsWith('<前綴>')`、`endsWith('<後綴>')`、
  用樣板拼名字。**每一處都要換成「問宣告」，而且要順手掃測試。**

## 明確否決的做法

| 做法 | 為什麼不行 |
|---|---|
| `sed -i 's/old/new/g'` 全庫替換 | 裸名會撞 DOM 標籤／節點型別／原始碼文字 |
| 「先全改，紅的再修」 | 900 支紅無法歸因，你只會全部還原 |
| 從登錄表推導遷移表 | 表要處理的是舊存檔，而登錄表是現在的 |
| 改名表寫在 `src/core/` | 核心不得認得任何語言的詞彙（犯過兩次） |
| 不改存檔版本 | 使用者的存檔會靜默壞掉，而它一週後才打開 |

## 驗收

- [ ] 護欄在動手前先跑過且是**紅的**，數字記在 spec 裡
- [ ] 每一段結束時全測試綠；紅了整段還原而不是就地補
- [ ] 存檔版本 +1，遷移表是**凍結的明表**且放在套件側
- [ ] **端到端遷移測試**：最舊版本一路到最新，身分與參數都對
- [ ] 第 6 步的「名字形狀判斷」清單逐筆看過
- [ ] 棘輪收硬性零（改名是**修法便宜**的那一類，見 build-guardrail 6.8）

## 🔴 `__app` 那個除錯把手——型別檢查**完全看不到它**

2026-08-19：`App.monacoPanel` 被改名成 `codeView`（spec 140），
`npx tsc --noEmit` 全綠、`npm test` 4600 多支全綠，**而 e2e 19/28 紅**。

```
src/main.ts                 (window as any).__app = app       ← 逃逸點
e2e/*.spec.ts × 6           __app.monacoPanel.setCode(...)    ← 26 處，全走 as any
```

⚠️ **`as any` 就是為了逃出型別檢查而寫的**——所以改名時它一定不會出聲。

> **一個為了測試而開的逃生口，在改名時是一個【型別檢查看不到的引用集合】。**

### 改任何 `App` 上的欄位名之前

```bash
grep -rn "__app" e2e/ src/ | grep -v "= app"
```

⚠️ 而**不要只 grep 舊名字**——有些地方是 `app.codeView?.setCode` 這種
可選鏈，改名後**執行期靜默回傳 undefined**，測試會逾時而不是報錯。

### 而更根本的：這件事的機制在哪

CI 在 2026-08-19 之前**只在 push 到 main 時跑**，所以那 84 個 commit
**合併之前從來沒跑過 e2e**。已補 `pull_request` 觸發。

> **一個只在【合併之後】才跑的檢查，擋不住任何東西
> ——它只負責在事後告訴你已經來不及了。**

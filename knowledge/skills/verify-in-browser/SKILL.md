# 收工前的瀏覽器驗收

## 什麼時候用

一刀做完、測試全綠、**還沒有人真的看過它**的時候。

⚠️ **與 [[diagnose-in-browser]] 的差別**：

```
diagnose-in-browser   已知有問題 → 先讀 console、量 DOM、做對照實驗
verify-in-browser     不知道有沒有問題 → 去看
```

**入口不同、順序不同，所以是兩支不是一支帶兩個模式。**

## 🔴 為什麼測試綠了還要開

專案實測，這三種缺陷**測試全綠而使用者一看就發現**：

```
新積木拿不到          忘了加進課程清單——可拿性護欄量不到（它只問「宣告了拿不拿得到」）
積木插槽不夠          液晶的建構參數只放得下第一個——lift 與 generate 兩側都綠
分類名不再描述內容    一格塞了 20 顆之後，「腳位與時間」不再是那格的內容
```

> **一個只在【某一條投影】上壞掉的缺陷，
> 任何不經過那條投影的測試都會是綠的。**

## 順序

```
1. npm run dev → 開新分頁 → ⚠️ 先清 localStorage
2. 切到要驗的目標／課程清單
3. 🔴 用【問的】列出工具箱內容，不要用眼睛數
4. 貼一段真實程式碼 → 轉積木 → 斷言【專屬身分】不是「看起來對」
5. 轉回程式碼 → 比對【形式一字不差】
6. 需要「使用者操作」才觸發的東西 → 真的拖曳
7. 截圖存檔給使用者
```

### 第 3 步的做法

```js
// 走 production 的組裝函式，不要自己走 flyout
const tb = window.__app.callBuildToolbox()
new Set(tb.contents.flatMap(c => (c.contents||[]).map(b => b.type)))
```

⚠️ **而它有一個會讓你判錯的陷阱**（2026-08-19 撞到）：
工具箱的內容是 `課程清單 ∩ 已啟用分支`。只開根分支的話，
**深層的積木一顆都不會出現**——那看起來像「過濾把它們濾掉了」，
而其實是你沒開那些分支。

```js
function allBranchIds(n, acc=[]) { acc.push(n.id); for (const c of n.children||[]) allBranchIds(c, acc); return acc }
```

> **一個「東西不見了」的讀數，要先排除「你根本沒開它」。**

## ⚠️ 六個實際踩過的坑

| | 坑 | 症狀長什麼樣 |
|---|---|---|
| ① | 工具箱分類是 **toggle** | 連點兩次會關掉，而畫面看起來只是「沒開」 |
| ② | flyout 要捲 | 積木在畫面外（`y=733`），看起來像不存在 |
| ③ | **localStorage 會殘留** | 上一次的工作區狀態蓋掉你貼進去的程式碼 |
| ④ | 長腳本會 CDP 逾時（45 秒） | 設定／點擊／讀結果要**分三次呼叫** |
| ⑤ | 程式化 `newBlock` **不發事件** | 「使用者操作才觸發」的東西驗不到，必須真的拖曳 |
| ⑥ | dev server 要先起 | 改完程式碼要 **reload**，不是只等 HMR |

⚠️ **⑦（2026-08-19 新增）**：`window.__app` 的方法名在某些橋接下會被遮蔽成
`[BLOCKED: Base64 encoded data]`。**那時就改用真的 UI**
——而那本來就是人工驗收該做的事，不是退路。

## 判準：什麼時候可以收工

**每一條負向觀察前面都要有一個正向錨點。**
「Uno 看不到那五顆」單獨不算數——要先證明「ESP32 看得到那五顆」，
否則你量到的可能是**整個工具箱沒組起來**。

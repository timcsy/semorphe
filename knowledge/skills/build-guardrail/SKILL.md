# 蓋一條護欄（build-guardrail）

## 這個 skill 做什麼

把一條**規範**變成一條**會變紅的檢查**，並附上基線與只准下降的棘輪。

理論地基是 [[執行機構]]：**一條規範沒有機械化的檢查，它本身就是殼——而殼看起來像完成。**

（緣起：2026-08-06 一天之內蓋了七條護欄——049 四條、051 一條、052 一條、053 一條。**四次翻車**，其中兩次是靠下面第 2、8 步抓到的，不是靠 code review。步驟表的價值就在那兩次。）

## 這把刀先問一句

> **「如果有人違反這條規範，什麼東西會變紅？」**

答不出來 → 這不是護欄題，是**這條規範該不該存在**的題。走 [[over-justify]]，別急著蓋。

## 步驟

### 1. 決定量什麼——一條規範對一個可數的量

量不出數字的規範蓋不了護欄。「程式碼要乾淨」不行，「核心層有幾筆語言專屬元件身分」可以。

### 2. 先寫自我否證聲明，再寫量測 ⚠️ 順序不可反

> 「**如果結果長成 ○○，代表工具壞了，不是世界長這樣。**」

**寫完量測再補聲明，你會照著已經看到的結果去寫它**——那句話就失去否證能力。

**錨點不要挑真實世界的狀態，挑合成的。** 兩次都栽在同一件事上：錨在一個當時壞掉的東西上（「declaration 那 8 條沒被判為會撞就代表護欄壞了」），後來把它修好，那句聲明於是變成**叫未來的讀者不要相信一個正確的結果**——比沒有聲明更糟。

→ 錨在**餵給判定函式的合成輸入**上（第 9 步的注入）。合成規則不隨真實世界的修復而失效，而真實世界的狀態遲早會被你自己修掉——**護欄修好了它要量的東西，就是它的錨點爛掉的時候。**

#### ⚠️ 這條散文擋不住——**用語法簽名**（2026-08-07，第五次犯之後補）

上面那段寫得很清楚，而**知道它、讀過它、還是又犯了一次**。所以它需要一個
機械的判準，而不是一句提醒：

> **斷言的那個數字，是不是這條護欄想推向零的？**
>
> - **是** → 錨錯了。**它會在成功的那天變紅。**
> - **不是**（掃到幾個檔、載入幾條規則、有幾顆元件）→ 對的錨。

一句話：**錨在「工具吃到輸入沒有」上是對的；錨在「缺陷還在不在」上必然會爛。**

**簽名一**：健康檢查裡出現 `expect(<缺陷計數>).toBeGreaterThan(0)`。

> ✅ **這三個簽名於 2026-08-10 機械化了**——第三十五條護欄
> （`tests/integration/audit-anchor-rot.test.ts`）掃 `audit-*.test.ts` 的
> 注入與健康檢查，報出「**期望值裡出現真實元件身分**」的行，硬性零。
> 它不判對錯（第 6 步要求的已知答案樣本本來就用真實身分），
> 而是把命中交給判定落點。
> ⚠️ 它第一次跑是**綠**的，因為那八次都已經被修掉了——
> 這種情況靠的是注入，不是靠第一次的紅（見 6.5 的例外）。

**簽名三**（2026-08-10，第八次之後補）：**注入或健康檢查裡出現一個
真實存在的元件身分／檔案路徑**，例如

```ts
expect(r.命中.map(h => h.鍵)).toContain('cpp:include.local')   // ← 具名的真實缺陷
```

前兩個簽名抓的是**計數**，而這一次錨的是**名字**——同一個病換了個寫法就溜過去了。
判準：**注入用的輸入應該是合成的。** 一旦注入裡出現 `cpp:` 開頭的真實身分，
問一句「這個東西被修好的那天，這支測試會不會紅」。

⚠️ **第八次不是我看出來的，是全套測試在同一輪抓到的**——我在同一個 commit 裡
補了那個宣告，注入當場爛掉。**那正是這一步存在的理由：它防的不是別人，是同一輪的自己。**
寫下這一行時停一下——那個計數就是你在努力消滅的東西。

實例（五次，全部同一個形狀）：

| | 錨在什麼上 | 什麼時候爛的 |
|---|---|---|
| 辨識歧義 | 「那 8 條沒被判為會撞就是壞了」 | 修好那 8 條時 |
| 雙重真相 | 「兩處都有定義 > 10」 | 清償到 10 以下時 |
| 分類 | OOP 那批的真實狀態 | 實作 OOP 時 |
| 完備性 | 「數字不為零」 | 殼歸零時 |
| 元件身分健檢 | 「確定桶不得為空」 | **B 項把那 9 筆修完的當天** |
| 重複定義（#41） | 「命令式賦值總數 > 20」 | **每退一顆命令式積木就掉一次**（30 → 20 → 19） |

#### 第九次（2026-08-25）：**它的註解已經承認自己會爛，而那沒有救它**

第四十一條的入口條件錨在「命令式賦值總數」，而**整個退場計畫就是要把
那個數字推向零**。它的註解逐字寫著：

> 「🔴 而這個錨**本來就會隨著清理下降**……所以下調時要問的是
> 『它還擋不擋得住掃描器根本沒讀到檔案』」

⚠️ **那句話讓它變成一條「每隔幾週要人來下調一次」的護欄**——而下調的人
每一次都會做出同一個正確的判斷，然後那個錨繼續爛。

> **一個承認自己會爛的錨，不會因為承認而不爛
> ——它只是把成本從「發現」搬到「維護」。**

修法是換錨：改成**掃描器讀進了多少字**（`> 10_000`）。
真的沒讀到是 **0**，而它不會因為缺陷被修好而變小。
🟢 而賦值數仍然量、但**不設下限**——它有一天會是 0，而那時這條護欄
該退休，不是變紅。

> 而 2026-08-07 掃了一次，**還有兩處活著**：缺陷帳的「應該有真的被關掉的測試」
> （目標是 85 → 1，成功即紅）與辨識歧義的「數字不為零」——**後者就寫在解釋
> 這個教訓的註解上方三行**。散文規則擋不住，語法簽名才擋得住。

兩次都不是 code review 抓到的，是**數字掉下來時測試自己變紅**。

#### 第六、七次（2026-08-10），而**第六次發生在寫下這條規則的同一輪**

| | 錨在什麼上 | 什麼時候爛的 |
|---|---|---|
| 宣告完整性（#30） | 「`cpp:func_def` 必須在**違規清單**裡」 | `specs/106` 修好那顆的當天 |
| 符合性（#29） | 「這三顆**整顆**是安全的」 | 給 `var_declare` 補一個接點的當天 |

第六次是舊形狀的複發——寫護欄的人（我）讀過上面那段、也在同一個檔案裡
引用了它，**然後在下一個 `it()` 裡犯了它**。

**第七次的機制是新的，上面那個語法簽名抓不到**：

> **錨在「整顆乾淨」上，等於錨在一個會隨世界變動的合取。**

`expect(整顆的桶).toBe('安全')` 沒有出現任何缺陷計數，所以第一個簽名
放它過。但它斷言的是「這顆元件的**每一個**接點都沒問題」——只要有人
**正確地**多宣告一個接點，那個合取就垮了。

#### 第八次（2026-08-11）：**錨在一個「包含缺陷的更大集合」上**

前兩個簽名**都抓不到它**。第三十九條護欄的入口條件錨的是

```ts
expect(r.掃描.視圖呼叫含生命週期).toBeGreaterThan(100)
```

那看起來是輸入量——它**含 `init`／`dispose` 這些永遠不會被清掉的呼叫**，
所以我判定它與缺陷無關。而把 32 處搬上匯流排之後它從 130 掉到 100，
**入口條件當場紅**。

> **一個「包含缺陷的更大集合」不是輸入量，它只是一個比較慢爛的錨。**

它不是缺陷計數（簽名一放它過），也不是合取（簽名二放它過）。

**第三個簽名**（判準，不是語法）：

> **這個量會不會因為違規被修好而變小？**
>
> - **會** → 錨錯了，不管它看起來多像輸入量。
> - **不會**（掃到幾個檔、幾行 import、`src/` 裡**任意**方法呼叫數）→ 對的錨。

修法：那次改錨 `src/ui` 裡**任意**的方法呼叫（2275）
——把 `panel.foo()` 換成 `this.廣播(...)` 之後它不會變小，
**換掉一個呼叫仍然是一個呼叫。**

**第二個簽名**：

> **斷言的對象是不是一個合取？**（整顆、全部、每一個、都）
>
> - **是** → 錨太寬。它會在任何一個合取項變動時紅，而那些變動大多是對的。
> - **否**（單一事實：這一個接點走得通、這一段碼 lift 得出那個節點） → 對的錨。

修法都一樣：**把錨從「狀態的合取」換成「一個不隨修復改變的單一事實」**
——「lift 對 `int f(int a)` 產得出 `params` 接點」在修好宣告前後都成立。

### 3. 寫「本護欄不檢測什麼」

不是免責，是**劃出能力邊界**。一條只抓得到「殼」的護欄若被誤讀成完備性保證，比沒有護欄更危險。

### 4. 從實際載入後的狀態量，不讀靜態設定

勝負常常取決於模組匯入順序，讀設定檔算不出來。

### 5. 判定保守——判不出來就說判不出來

歸「無法確定」，且**不計入安全**。為了讓數字好看而樂觀歸類，比沒有護欄更糟。

### 6. 靜態判斷不能下結論，只能排順序 ⚠️

**判準本身可以是對的，把它自動化的第一版仍然會量錯。** 曾經有一次靜態掃描給出的分類是**反的**——壞的判成好的、好的判成壞的，而根因只是把「有沒有人用它」實作成 grep 名字。

救它的不是 code review，是**先做的實測與它矛盾**。

→ 有辦法實測就實測。要用靜態判斷，先在**已知答案的樣本**上驗過。

### 6.5 第一次跑**必須是紅的**——一開始就綠代表護欄壞了 ⚠️

新護欄的第一次執行，是它一輩子唯一一次面對**沒有被它管過的世界**。那個世界裡
一定有東西不合規——否則這條規範早就自動被遵守了，你根本不需要蓋它。

實測（2026-08-07，一輪蓋了三條）：

| 新護欄 | 第一次跑抓到 |
|---|---|
| 可拿性 | **7 顆**使用者拿不到的積木，含 `<fstream>` 整個模組 |
| 課程清單懸空引用 | **2 筆**，自兩個月前就存在 |
| 工具箱不得指向幽靈 | **1 筆**（而它是誤報，靠這個發現判準要再切一刀） |

**所以第一次綠有三種可能，沒有一種是好消息**：判準寫錯了、資料沒載入、
或**基線是先產生的**（那等於把現況直接封為合格）。

→ **順序**：先跑、確認紅、**逐項指名**、修好，**最後才產基線**。
先產基線的話，違規會被寫進基線變成「已知」，而**你永遠不會知道它們曾經存在**。

→ 同一條的推論：**護欄先蓋，功能後做。** 如果那條規範是為了配合某次重構才立的，
把重構先做完，違規會被重構「順便」修掉——**一個被順便修掉的缺陷不會留下任何紀錄，
而它的同類還會再來。**


#### ⚠️ 而第一次跑紅了之後，先問「紅的是世界，還是語料」（2026-08-10 補）

`specs/108` 一輪之內**語料錯了三次**，而每一次錯的數字都比正確的大：

```
形態的殘差   48.83%  →  0.23%     820 段裡 353 段是**片段**（語法本來就不完整）
行為的誤差   64      →  40        61 段讀 cin／rand，無輸入時**兩邊都不可判定**
行為的誤差   40      →  31        抽取器把 `\n` 錯拆成「反斜線＋真換行」＝ C 的續行符
```

**語料錯比工具錯難發現**，因為它的症狀不是「數字不合理」，是
「**數字看起來像一個發現**」——48.83% 讀起來就是「模型只理解一半的程式碼」。

→ **判準**：這個數字如果是真的，**它與我已知的事實矛盾嗎**？
（已知事實：這個系統天天在用，完整程式的殘差應該接近零。）

→ **處置**：不算數的語料**另立一欄進基線**，不是靜默排除。
理由是對稱的——只記分子的話，「加一段不可判定的語料」就能縮分母讓比率下降，
而**縮分母比修分子容易**。

#### ⚠️ 第一次跑紅了，還要問「這個條件實際上會不會發生」（2026-08-10 補）

6.5 只說「第一次跑必須是紅的」。**紅了不代表抓到的是東西。**

`specs/110` 蓋的靜默回退護欄第一次跑抓到 9 筆，看起來很成功。
`specs/111` 實測它們的**活性**（415 段語料）：

```
型別不符   if (x.type !== 'array')         上游辨識判錯時發生  → **會**發生
缺子節點   if (!v) / (nodes.length === 0)  語義樹壞掉時發生    → **0 次**
```

**9 筆裡 8 筆是死分支。** 而它們在語法上與活的那一筆長得一模一樣。

> **一條數字永遠不動的棘輪，與一條沒有人跑的護欄是同一件事。**

→ **判準**：新護欄的每一類命中，問「**觸發它的條件在真實語料上發生過幾次**」。
  答案是 0 的那一類**不要進棘輪**——把它記成一個可見的數字就好。
  ⚠️ 而「不會發生」**不等於「不該存在」**：防禦性分支防的是未來的壞樹。

→ **量活性要有對照**：這次的對照是「那些概念有沒有出現過」——
  5/10 出現、共 14 次，證明量測有效。**沒有對照的話，0 次可能只是語料沒碰到。**

#### ⚠️ 一叢違規看起來像一個根因，而那是假設不是結論（2026-08-10 補）

`specs/110`：5 筆 `fuzz-cpp-cctype` 誤差全部用 `s.size()` 當迴圈條件，
看起來是同一個根因。修好 `s.size()` 之後——**只消掉 2 筆**。
其餘 3 筆的根因不同（`islower` 未定義、字元轉型）。

> **共用一個症狀不代表共用一個根因。**
> 而「一叢」這個說法本身會讓人停止查——它聽起來像已經歸因過了。

→ **判準**：宣稱「這 N 筆是同一個根因」之前，
**在其中至少兩筆上分別驗過那個根因會不會消掉它**。
驗不了就寫成「疑似同族」，不要寫成根因。

### 6.8 硬性零 vs 棘輪——不是所有護欄都該用棘輪

**棘輪**是給「大量既有違規、要慢慢還」的量用的。用錯地方會變成合法化。

| | 用棘輪 | 用**硬性零** |
|---|---|---|
| 違規是**程度問題** | ✅ 就近性 8.5 檔、中立性 216 筆 | |
| 違規**開一個口就整條失效** | | ✅ 唯一入口、幽靈積木 |

判準：**問「留一筆在那裡，這條規範還成立嗎？」**
「唯一真相有兩個入口」——留一個口，「唯一」那句話就是假的，護欄變成在替它背書。

⚠️ **但那只是第一個問題，還有第二個：修一筆要付多少？**（2026-08-08 撞到）

我把「參數規格與實際使用一致」判成硬性零，理由是「留一筆規範就不成立」——
那句話仍然對。而動手修的時候才發現：那些宣告**不是描述，是驅動抽取的資料**，
每一筆修法都會改變行為（兩次改動、兩次來回轉換變紅、兩次還原）。

→ **兩個問題要分開問：**

| 問題 | 答什麼 |
|---|---|
| 「留一筆規範還成立嗎？」 | 決定這條規範**值不值得**存在 |
| 「修一筆要付多少？」 | 決定用**硬性零還是棘輪** |

規範成立 ＋ 修法便宜 → 硬性零。
規範成立 ＋ **每一筆都要驗行為** → 棘輪，慢慢還。

⚠️ **而還有第三個問題，它在單機開發時永遠是隱形的**（2026-08-14 撞到）：

> **「這個量在別台機器上一樣嗎？」**

`audit-behavior-error` 的不一致筆數在 macOS 是 1、在 CI 是 0
——同一條規則、同一份語料，**而參照編譯器在兩台機器上是兩個實體**
（macOS 的 `g++` 是 Apple clang）。那筆是 UB（讀未初始化變數）：
clang 印堆疊垃圾、gcc 印 0。

**於是基線無解**：

```
基線記 1  →  CI 實測 0  →  「棘輪有改善，請下調基線」
基線記 0  →  本機實測 1 →  「棘輪退步」
```

→ **環境相依的樣本不該在分子裡**——與「不可判定」（讀 `cin`／`rand`）同一條。
⚠️ 而移出去的要**另立一欄**，理由與第 11 步相同：
**縮分母比修分子容易，所以縮掉的東西要看得見。**

判準：**這條護欄的量測工具是外部的嗎**（編譯器、網路、時鐘、檔案系統）？
是 → 它的數字可能環境相依，而那在單機上量不出來。

**先判硬性零、動手後才發現修不動，是可以的**——把判定改回棘輪並記下原因，
比硬撐著把 13 筆硬修完再說。

### 7. 產基線 + 棘輪

```
GENERATE_BASELINE=1 npx vitest run <護欄檔>   → tests/baselines/*.json
```

棘輪只准下降，且**上升時必須指名是哪一項**新增的——不能只說「數字變大了」。

**真的要上調時**（有，而且會是對的決定）：把理由寫進**基線檔的 `note`**，不是只寫在
commit 訊息裡。commit 訊息沒有人會回頭翻，而基線檔是下一個看到這個數字的人**一定會打開**的地方。

> 實例：`dual-truth` 32 → 33——`u_input_expr` 補上 JSON 投影，把「登錄表看不見它」
> 換成「與其餘四顆同樣的已知雙重定義」。**上調不是常態，所以理由要留在數字旁邊。**

🔴 **順序：先重生，再寫註記。**

`GENERATE_BASELINE=1` **整份重寫那個 JSON**，而**有幾條的產生器不保留 `note`**
（2026-09-03 實測：`layering` 保留，`four-independences` 與 `shared-file-husks`
被吃掉）。先寫註記再重生的話，註記當場消失——而**它不會報錯**：
基線是綠的，只是理由沒了。

```
❌  改 note → GENERATE_BASELINE=1 → note 不見了（而測試是綠的）
✅  GENERATE_BASELINE=1 → 改 note → 再跑一次確認綠
```

> **一個「會把整個檔重寫」的工具，與一段「手寫在那個檔裡」的理由，
> 順序反了就是靜靜地失去它。**

### 8. 自我驗證：釘住**理由**，不只釘結果 ⚠️

不只斷言「這一項必須被報出來」，還要斷言**報出的理由正確**。

曾經有一條護欄的自我驗證測試**通過了**，卻沒擋住一個錯誤結論——因為它只釘結果。**一個因為錯誤理由而給出正確結果的護欄，看起來與健康的完全一樣。**

### 9. 兩個方向都要釘

| 注入 | 證明什麼 |
|---|---|
| 故意壞掉的輸入 | **會報** |
| **正確的輸入** | **不亂報** |

第二個不可省。沒有它，一個「什麼都報」的掃描器也能通過第一個。

⚠️ **而兩個都釘完，還漏掉第三件事：輸入有沒有進來。**（2026-08-10）

第七條護欄自蓋好起量的是一個**空的註冊表**（量測前沒載入語言套件），
基線 `0/0` 四天都是假的，真實是 4。**而它的三支注入全綠**
——注入手動註冊兩次再確認被數到，證明的是「計數器會數」。

> **計數器會數 ≠ 註冊表裡有東西。**

→ 每條護欄再加一支**入口條件**斷言，錨在**合成量**上：
掃了幾個檔／載入幾條規則／註冊表幾個概念／語料幾段。

| | 釘住什麼 | 漏掉什麼 |
|---|---|---|
| 注入 | 判定邏輯**會不會報** | 真實輸入**有沒有進來** |
| **入口條件** | 真實輸入**有沒有進來** | 判定邏輯對不對 |

⚠️ **而注入還有第四種結局，它長得跟綠的一樣**（2026-08-19，兩次）：

```
真的紅        護欄抓到了
真的綠        🔴 護欄沒抓到——這是要處理的
【沒跑起來】   注入讓建置／型別檢查壞掉，測試根本沒執行
```

第三種的輸出裡**沒有 `failed` 字樣**，而一個「找 `N failed`」的判讀器
會把它讀成 **0**——也就是「綠的」。

> **一個編不過的注入，證明的是編譯器會擋，不是護欄會擋。**

→ 注入器要**先分辨這三種**，並把「沒跑起來」印成一個顯眼的字樣。
⚠️ 常見成因：注入讓某個參數或匯入變成未使用（`TS6133`）。
**改成一個仍然用到它的變體**（例如把回傳值換成固定清單，而不是刪掉來源）。

⚠️ 那條護欄的自我否證聲明還**把讀者指向注入**（「判斷依據是『★ 注入』那支」）
——而注入正是看不到這個缺口的那一支。
**一句錯誤的自我否證提示，比沒有提示更糟：它讓人停止懷疑。**

**基線是 0 的時候，這一步是唯一的健康檢查**——一條回報零違規的健康護欄，與一條什麼都沒量到的護欄，產出完全相同。

### 10. 測試通過之前，先證明它真的測到了東西

一支斷言「輸出正確」的測試，要先確認被測的東西**真的出現在**被測的結構裡。曾經有五列「通過」是假的——那些東西根本沒進到樹裡。加上這道檢查之後，通過數從 17 掉到 12。

### 11. 護欄要能記錄「看過了」——否則它會永遠報同一件事

一條只會**報**、不會**收**的護欄，會把同一批項目報到人學會忽略它為止。而那時
它報的新東西也一起被忽略了——**護欄的價值不在它報什麼，在有沒有人讀**。

所以「只排順序、不下結論」的護欄（第 6 步那種）需要一個**判定的落點**：

```
tests/assets/<護欄名>-decisions.json
  { componentId, signal, decision, reason }
```

#### ⚠️ 鍵不要用行號——它報的不是違規，是 diff（2026-08-11 補）

第三十九條護欄的明細用 `檔案:行號`。清償了 32 處之後，剩下的每一行都往上移，
於是**整片被判成「新增違規」**——一次正確的清償讓護欄全紅。

> **一個會因為程式碼往下移了幾行就報「新增違規」的鍵，報的不是違規，是 diff。**

而它的症狀很像「真的有新違規」，因為報表印的是一長串沒見過的位置。

→ **鍵要用「不隨編輯移動的東西」**：`檔案 → 被 import 的路徑`、
  `檔案 → 接收者.方法`。行號留在報表裡給人看，識別用不到它。

⚠️ 這與下面「鍵會碰撞」是**同一個決定的兩端**：鍵太脆（行號）會假報，
鍵太鬆（前 80 字元）會漏報。兩邊都要問一句「**什麼變了，這個鍵才該變**」。

#### ⚠️ 鍵會碰撞，而碰撞讓「已判定」變成謊話（2026-08-10 補）

`specs/108` 的判定鍵用「語料前 80 字元」——`specs/110` 實測
**17 筆明細只有 16 個不同鍵**。兩道防線**都靠鍵**，所以兩道都失效：

- 孤兒檢查 → 別名讓過期判定繼續生效
- 「要看」清單 → **新缺陷被同鍵的舊判定吸收，而報表顯示「要看 0」**

> **一個被誤認為已經看過的缺陷，比一個沒被報出來的更糟。**

→ **顯示與識別要分開**：`前 60 字元 + '#' + 全文雜湊`。
   鍵要人看得懂是對的需求，錯在用同一個字串同時當顯示與識別。

已判定的移出「要看」，另立一欄。兩道防線缺一不可：

- **每一筆判定必須有理由**——說不出理由的判定是把「懶得看」寫成「看過了」
- **判定會過期**：信號已經不再出現卻還留著判定 → **報孤兒**。
  底下的事實變了，判定可能不再成立，留著會讓一個過期的結論繼續生效

第二條特別重要：**判定與基線不同——基線過期會被棘輪抓到，判定過期不會。**

## 明確否決的做法

- ❌ **vitest snapshot**——`-u` 會靜默更新，等於「跑一下就自動接受惡化」。那本身就是 [[執行機構]] 在講的殼。
- ❌ **永久紅的測試**——會讓「全套綠」失去意義，而所有護欄的價值都建立在那個訊號上。要釘住已知缺陷用 `it.fails`：缺陷還在＝綠且出聲，修好了＝紅且提醒拔釘子。
- ❌ **`it.todo` 當釘子**——它**沒有測試本體**，所以缺陷被修好時**什麼都不會發生**。

  | | 缺陷被修好時 |
  |---|---|
  | `it.fails`／`it.skip`（有本體） | **變紅**——逼人來拔釘子 |
  | `it.todo`（無本體） | **一聲都不出**，而缺陷帳繼續把它算成「還沒做」 |

  ⚠️ 實例（2026-08-13）：`[BLOCKED:cpp:destructor] inner block scope` 被
  `cpp:block` 修掉了，**而那筆 `it.todo` 躺了整整一輪**——是人去梳理
  「還有什麼沒做」時才發現它已經不是問題。

  > **`it.todo` 本身就是一種殼：它宣告了一個缺陷，
  > 而沒有任何機構在看那個缺陷還在不在。**

  → 真的還沒有重現方式時，寫一個**會失敗的最小重現**當 `it.fails`；
  連重現都寫不出來，那筆該進 `draft/` 而不是測試檔。

## 一個數字**因為做對事而必須上調**時，它混了兩個母體

⚠️ 這一節在「數字下降時」**之前**——因為它問的是更早的事：
**這個數字回答得了「做完了沒」嗎？**

實例（2026-08-26 一天之內兩次，而它們是同一個病）：

```
audit-language-plugin     第一版把兩者混成一個數字（47），而那讓「做完了沒」問不出答案
                          → 分成【選單接線】（硬性零）與【語言管線】（棘輪）
audit-four-independences  「跨層直接呼叫」五天內被上調四次（67→68→70→73→75），
                          每一次的理由都是「組裝點把兩端接起來」——一個正確的動作
                          → 分成【組裝點接線】（可見不入棘輪）與【其餘】（棘輪）
```

> **一個每次做對事情都要上調的數字，量的是兩件事。**

**判準**：翻一次那條護欄基線的 `note`。如果它記著**上調**，而每一筆上調的理由
都是「我們做了一件對的事」——那就分欄。

⚠️ **而分出去的那一欄必須【可見】**（印在報表上、進基線），不是豁免、
不是排除在掃描外。理由是這條護欄自己的規矩：

> **下降必須是「真的拆掉了」，不是「把檔案排除在掃描外」或「改了判準」。**

🔴 **搬欄不是清償**——搬的是「哪些數字回答哪個問題」，那些筆數一筆都沒有消失。
基線的 `note` 要把這句話寫進去，否則下一個讀到「75 → 21」的人會以為清了 54 筆。

## 數字下降時，先問是哪一種

| 下降原因 | 意義 |
|---|---|
| 因為**實作**了 | 系統多會做一件事 |
| 因為**宣告**了（或重新分類） | 系統沒有變，只是我們終於說清楚 |

**混在同一個數字裡的話，用宣告刷數字看起來會像進步**，而護欄會替它背書。報表要分欄，棘輪只看真正的缺口。

## 可複用的東西

- `tests/helpers/guardrail.ts`——`loadBaseline` / `writeBaseline` / `printReport` / `newItems`（回傳**新增項清單**而非布林，因為失敗時要指名）
- 既有護欄可當範本：就近性／中立性／完備性／缺陷帳／辨識歧義／存檔完整性／執行器重複註冊
- ⚠️ **報表要印在 `loadBaseline` 之前**。否則護欄第一次跑（基線還不存在）時
  拋的是「基線檔不存在」，而**看不到它抓到了什麼**——而 6.5 要的正是
  「先跑、確認紅、**逐項指名**」。**一個在指名之前就拋出的護欄，指不了名。**

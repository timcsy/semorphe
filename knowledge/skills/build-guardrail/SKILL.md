# 蓋一條護欄（build-guardrail）

## 這個 skill 做什麼

把一條**規範**變成一條**會變紅的檢查**，並附上基線與只准下降的棘輪。

理論地基是 [[執行機構]]：**一條規範沒有機械化的檢查，它本身就是殼——而殼看起來像完成。**

（緣起：2026-08-06 一天之內蓋了七條護欄——049 四條、051 一條、052 一條、053 一條。**四次翻車**，其中兩次是靠下面第 2、8 步抓到的，不是靠 code review。步驟表的價值就在那兩次。）

## 這把刀先問一句

> **「如果有人違反這條規範，什麼東西會變紅？」**

答不出來 → 這不是護欄題，是**這條規範該不該存在**的題。走 [[over-justify]]，別急著蓋。

## 步驟

### 1. 決定量什麼——一條規範對一個可數的量

量不出數字的規範蓋不了護欄。「程式碼要乾淨」不行，「核心層有幾筆語言專屬概念身分」可以。

### 2. 先寫自我否證聲明，再寫量測 ⚠️ 順序不可反

> 「**如果結果長成 ○○，代表工具壞了，不是世界長這樣。**」

**寫完量測再補聲明，你會照著已經看到的結果去寫它**——那句話就失去否證能力。

**錨點要挑「這個功能不會修好的東西」。** 曾經錨在一個當時已知壞掉的東西上，同一功能的下一個 Story 把它修好了，那句聲明於是變成「叫未來的讀者不要相信一個正確的結果」——比沒有聲明更糟。

### 3. 寫「本護欄不檢測什麼」

不是免責，是**劃出能力邊界**。一條只抓得到「殼」的護欄若被誤讀成完備性保證，比沒有護欄更危險。

### 4. 從實際載入後的狀態量，不讀靜態設定

勝負常常取決於模組匯入順序，讀設定檔算不出來。

### 5. 判定保守——判不出來就說判不出來

歸「無法確定」，且**不計入安全**。為了讓數字好看而樂觀歸類，比沒有護欄更糟。

### 6. 靜態判斷不能下結論，只能排順序 ⚠️

**判準本身可以是對的，把它自動化的第一版仍然會量錯。** 曾經有一次靜態掃描給出的分類是**反的**——壞的判成好的、好的判成壞的，而根因只是把「有沒有人用它」實作成 grep 名字。

救它的不是 code review，是**先做的實測與它矛盾**。

→ 有辦法實測就實測。要用靜態判斷，先在**已知答案的樣本**上驗過。

### 7. 產基線 + 棘輪

```
GENERATE_BASELINE=1 npx vitest run <護欄檔>   → tests/baselines/*.json
```

棘輪只准下降，且**上升時必須指名是哪一項**新增的——不能只說「數字變大了」。

### 8. 自我驗證：釘住**理由**，不只釘結果 ⚠️

不只斷言「這一項必須被報出來」，還要斷言**報出的理由正確**。

曾經有一條護欄的自我驗證測試**通過了**，卻沒擋住一個錯誤結論——因為它只釘結果。**一個因為錯誤理由而給出正確結果的護欄，看起來與健康的完全一樣。**

### 9. 兩個方向都要釘

| 注入 | 證明什麼 |
|---|---|
| 故意壞掉的輸入 | **會報** |
| **正確的輸入** | **不亂報** |

第二個不可省。沒有它，一個「什麼都報」的掃描器也能通過第一個。

**基線是 0 的時候，這一步是唯一的健康檢查**——一條回報零違規的健康護欄，與一條什麼都沒量到的護欄，產出完全相同。

### 10. 測試通過之前，先證明它真的測到了東西

一支斷言「輸出正確」的測試，要先確認被測的東西**真的出現在**被測的結構裡。曾經有五列「通過」是假的——那些東西根本沒進到樹裡。加上這道檢查之後，通過數從 17 掉到 12。

## 明確否決的做法

- ❌ **vitest snapshot**——`-u` 會靜默更新，等於「跑一下就自動接受惡化」。那本身就是 [[執行機構]] 在講的殼。
- ❌ **永久紅的測試**——會讓「全套綠」失去意義，而所有護欄的價值都建立在那個訊號上。要釘住已知缺陷用 `it.fails`：缺陷還在＝綠且出聲，修好了＝紅且提醒拔釘子。

## 數字下降時，先問是哪一種

| 下降原因 | 意義 |
|---|---|
| 因為**實作**了 | 系統多會做一件事 |
| 因為**宣告**了（或重新分類） | 系統沒有變，只是我們終於說清楚 |

**混在同一個數字裡的話，用宣告刷數字看起來會像進步**，而護欄會替它背書。報表要分欄，棘輪只看真正的缺口。

## 可複用的東西

- `tests/helpers/guardrail.ts`——`loadBaseline` / `writeBaseline` / `printReport` / `newItems`（回傳**新增項清單**而非布林，因為失敗時要指名）
- 既有七條護欄可當範本：就近性／中立性／完備性／缺陷帳／辨識歧義／存檔完整性／執行器重複註冊

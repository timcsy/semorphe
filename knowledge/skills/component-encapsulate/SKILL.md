# 把一顆元件搬進膠囊（component-encapsulate）

## ⚠️ 可搬性的六個條件（2026-08-11，177 顆全部搬完之後補完）

**一顆元件搬得動，要同時滿足六件事。** 前三條是「切得出來嗎」，
後三條是「切出來之後別人還認不認得它」——而**後三條才是真正的阻斷**。

1. **五路都切得出來**（工具的事）
2. **lift 不與別顆共用一個不可分割的函式**（**產出**單一）
3. **沒有別的共用檔還提到它的身分**（**引用**單一）
4. **它有積木、因此有標籤**——⚠️ 沒有積木的元件（`cpp:comma_expr`）
   膠囊契約沒有為它設計過位置，就近性護欄會說「UI 空白」
5. **五路實作不是另一顆元件實作的別名**——`cpp:if_else` 的產生器**就是**
   `cpp:if` 的產生器，那顆搬不動除非先把共用的部分提升
6. **沒有一族消費者依它的身分分派**（執行／產生／辨識三路各一個）

> **第 2 與第 3 的差別是最貴的一課：產出單一不等於引用單一，
> 而搬得動要的是後者。**

### 第 6 條的處置：**性狀**，不是把消費者搬走

```ts
// 之前
if (caseNode.conceptId === 'cpp:default') { … }
// 之後
if (isDefaultCase(caseNode.conceptId)) { … }
```

```json
{ "traits": { "defaultCase": true } }
```

> **「另一顆元件需要認得它」是真的耦合，不是碎裂。**
> 消費者有它自己的家——處置是把「我是什麼」變成元件自己的宣告。

⚠️ **性狀只講得出「我是什麼」，講不出「我在哪裡時算什麼」**：
`return` 只有在 `main` 裡才是鷹架。條件要切兩半，一半宣告一半留在消費者。

詞彙地基見 [[性狀]]（`concepts/性狀.md`），19 條實例全部是踩到才長出來的。

### 三種寫死身分的地方，處置各不相同

| | 例 | 處置 |
|---|---|---|
| 程式碼 | `node.conceptId === 'cpp:default'` | 問性狀 |
| 登錄表 | `{ push: 'cpp:container_push' }` | 元件自己登錄 |
| **宣告** | `"wrap": "cpp:var_ref"`（在 `forms/blocks.json` 裡）| **指性質**（`wrapTrait`）|

第三種最難發現——它不在任何 `.ts` 檔裡，掃程式碼的工具看不到它。
抓到它的是就近性護欄的**反向檢查**。

## 過渡表：機制先落地，資料慢慢遷

搬家會遇到「這條性狀的機制建好了，而還有 N 顆沒搬進來」。處置是一張**過渡表**：

```
src/languages/<lang>/pending-<什麼>.json    { "traits": { "cpp:foo": {...} } }
```

三條紀律：

1. **靜態 import 的 JSON，不是登錄呼叫。**
   > **把資料做成登錄呼叫，等於替它發明一個會忘記呼叫的時序。**
   （2026-08-10 記下，2026-08-11 又犯了一次——第一版做成
   `registerPendingMemberRole()`，壞了 16 支測試。）
2. **消費者先問膠囊，查不到才問過渡表**——已膠囊化的元件兩邊答案要相同。
3. **只減不增。** 搬一顆刪一列。

### ⚠️ 而它搬完就要**退場**，不是留一個空的在那裡

2026-08-11 F 完成時兩張過渡表都變成 `{}`，而**一個空的 JSON 被 import 進來，
讀起來像「這裡還有一批沒處理的」**。

> **過渡的機制留著不會壞，而它會說謊。**

處置：連檔案帶 import 一起刪，消費者退回單一來源。
**下一次遷移開始時照這三條重建**——形狀在這裡，不必留一個空殼佔位。

## ⚠️ 批次搬家的紀律（2026-08-11，17 批成功 4 批回退換來的）

1. **前置重構單獨 commit，批次期間不碰任何共用檔的既有內容。**
   中途 `git checkout` 會把**同一批已完成的部分一起還原**，
   而症狀看起來像「這一批本來就搬不動」。
2. **有紅就整批回退，不要逐顆挑。** 半成品會讓下一批建立在壞掉的基線上。
3. **每搬一批問一次：哪條護欄的掃描範圍沒跟著走？**
   （目錄跟上了、檔名沒跟上；只掃 `tests/` 掃不到 `src/scripts/`…）
4. **一個迴圈註冊出來的 N 個實作，拆進膠囊後護欄會突然多報**
   ——那不是新缺陷，是**本來就在而按位置記帳的護欄看不見**。

## 步驟

### 1. 錄基準——**然後打開檔案看內容** ⚠️

錄五路的產出（宣告／積木／標籤／產生／執行）當搬家前後的對照。

⚠️ **錄完必須打開基準檔看裡面有沒有東西。** 第一顆的基準把「執行那一路」
**全部錄成空字串**，包含一支應該印出 `3 4\n2` 的樣本——
**執行那一路等於完全沒有被防線覆蓋，而基準檔看起來是滿的。**

> 這是 `build-guardrail` 第 10 步在膠囊上的實例：
> **測試通過之前，先證明它真的測到了東西。**

### 2. 剪，不是搬

依形狀表從共用檔剪出 1–3 段。**剪完共用檔要少一段**——
如果共用檔沒變小，那是複製不是搬家，而**兩份會漂移**。

### 3. 自證測：每一條負向前面先釘一個正向錨點 ⚠️

```ts
expect(ids).not.toContain('cpp:vector_declare')   // ← 這一句在集合是空的時候也會過
```

`lift` 回傳 `null` 時集合是空的，負向斷言**空過**——
**一支空過的測試與健康的長得一模一樣。**

→ **每一條負向前面先釘一個正向**：「這段碼必須產生 `cpp:array_declare`」。
那句話證明量測跑到了，負向才有意義。

### 4. 接回載入路徑——**問「有幾個組裝點」**

第一顆掀出 **8 份「各自組裝」**（最貴的一項）。那八份已經收斂成
`all-declarations.ts`，所以**不會重複 176 次**——
但每次搬完仍要問一句：**有沒有第九個組裝點？**

判準：搬完之後 grep 那顆元件的舊身分，**共用檔裡不該還有它**。

### 5. 跑全套、對基準、下調棘輪

`tests/baselines/component-locality.json` 的「未膠囊化」只准下降。

⚠️ **下降的原因要註明**——「因為搬了」不是「因為重新分類」。

### 處置

1. **膠囊接在段落最後是可以接受的**——除非那顆是「**該第一眼看到**」的
2. 而「該第一眼看到」是**一個很短的清單**（已知一筆：`vector_declare`
   排在「陣列與列表」第一），它值得被明確寫下來

### ⚠️ 而搬家真正弄丟的不是順序

`vector_declare` 排第一**不是偶然**，是有人這樣放的——而那個意圖今天
**只存在於陣列位置裡，沒有人寫下來過**。

> **一個沒有被宣告的意圖，會在承載它的機制改變時安靜消失。**

→ 搬一顆之前問一句：**它是不是它那個分類的「入門那一顆」？**
  是 → 把那個意圖寫下來（而不是靠陣列位置隱含）。
  不是 → **接在最後就好，不必為它設計機制。**

### 而那次嘗試賺到三件事，全部保留

**① 第三種形狀確認：lift 是「一整個 pattern 物件」**

```
strategies.ts 41 顆   分派表的一列      → 登錄呼叫
io.ts 68 顆           分派表的一列      → 登錄呼叫
**共用產生器 97 顆**  **一整筆 pattern** → **glob 直讀**
```

**② 資料不需要被登錄，它需要被找到** ⚠️ 這一條最貴

第一版把 pattern 寫成登錄呼叫（照抄前兩種的形狀），**壞了兩次**：

1. 讀取發生在登錄之前（`loadLiftPatterns` 早於 `registerCppLifters`）→ 讀到空陣列
2. 改成惰性併入之後仍然壞——**8 個測試檔各自組裝 lifter 而不呼叫
   `registerCppLifters`**，登錄從未發生

而**它沒有立刻爆**：共用檔裡還留著同名 pattern 時看不出來。

> **把資料做成登錄呼叫，等於替它發明一個會忘記呼叫的時序。**
> 判準：**這個東西有沒有人要「查」它？**
> 有（「`vector` 這個名字屬於我」）→ 登錄。
> 沒有（一整筆資料）→ **glob 直讀**，與 `component.json`／`forms/blocks.json` 同類。

**③ 八個各自組裝的 lifter**

```
自建 lifter 的測試檔    8
用共用 createTestLifter  113
```

那是卡點 6「八份各自組裝」在 **lift 這一維**的重演。
⚠️ **搬完要問「有沒有下一個組裝點」——而它每一維各有一批。**

## ⚠️ 未解的卡點：同模組的第二顆

`E` 項把工具箱做成有序來源，順序來自該來源 `blocks.json` 的**宣告順序**。
一顆元件搬出去之後它的積木從那個陣列消失，**接在最後面就會從分類的第一個
掉到最後一個**——測試抓得到順序變了，而**使用者感覺到的是「建立列表」不見了**。

第一顆的處置是「併進 owner 模組的段落、排在模組積木之前」，
**而那只對一顆成立**。

> **同一個 owner 底下第二顆搬進來之前，必須先決定元件之間的順序。**
> 今天是身分的字母序，而**那不是教學順序**。

→ **選下一顆時先看它的模組裡有沒有膠囊。** 有 → 先解這個，別硬搬。

## 已實測兩顆之後的修正（2026-08-10，`specs/113`）

**`specs/104` 的估計把 `io.ts` 那 68 顆列為「處方尚未實測」。實測結果：
它與 `strategies.ts` 那 41 顆是同一種形狀**——lift 都是
**共用分派表裡的一筆資料**，不是函式。處方相同：
判別邏輯留在共用檔，**資料**回到膠囊，共用檔改查登錄表。

```ts

export function registerLift(): void {

```

→ **那 109 顆的估計可以合併。** 而過渡表要留一句話：

### 第三顆的實測（2026-08-10，`specs/114`）：**教訓省下了兩個坑，而冒出第三個**

同一顆上次被回退，這次**六支自證測一次過**。省下的：

```
✅ lift 用 glob 直讀（不是登錄呼叫）      上次壞兩次
✅ component.json 顯式宣告 owner          核心元件沒有 requires
```

**而仍然冒出一個新的組裝點**——第三處：

```
tests/helpers/toolbox.ts + all-declarations.ts
  原本列舉「std 模組的 header」＋「沒有 owner 的（null）」
  而 `(core)` **兩類都不是** → 積木從工具箱整個消失
```

> **列舉已知的 owner，等於保證下一個新 owner 會被漏掉。**
> 修法不是再列一個，是改成「**扣掉已處理的，其餘全要**」（`componentBlocksNotIn`）
> ——新的 owner 自動被涵蓋。

⚠️ **所以步驟 4 的問法要更新**：不只問「有沒有下一個組裝點」，
還要問「**這個組裝點是列舉式的還是扣除式的**」。
列舉式的每加一種 owner 就漏一次；扣除式的不會。

### ⚠️ 順帶：膠囊化會**還掉別的債**

`char_is_alpha` 搬完之後，第三十三條護欄的「缺子節點」少一筆
——共用檔裡那句 `if (!v) return 0` 隨它搬進膠囊，而**新實作丟錯不回 0**。

> **搬家是重寫那一路的機會**，而重寫時既有的護欄清單就是檢查表。
> 但⚠️ **不要把重寫混進搬家的 diff**——搬移不重寫是預設，
> 要重寫就在**另一個 commit**，否則對不出基準。

## 2026-08-11 實測十顆之後的修正

### 形狀表補到五種——而**第五種長得不像表**

```
strategies.ts 41 顆   分派表的一列          → 登錄呼叫（container-templates）
io.ts 自由函式          分派表的一列          → 登錄呼叫（call-concepts）
io.ts 方法呼叫          switch 的一個 case    → 登錄呼叫（method-concepts）
共用產生器 97 顆       一整筆 pattern        → **glob 直讀**
**std/<mod>/lifters.ts**  **一個 40 行的函式**  → **拆開之後也是登錄呼叫**
```

⚠️ 第五種是 `<cmath>` 的 `tryCmathLift()`：三個分支、自己組 `createNode`，
**看起來完全像實作**。拆開之後只剩三列「名字 → 身分 ＋ 引數槽名」。

> **一個函式長得像實作，不代表它是實作。**
> 判準：**把它的分支排成表，每一列還剩下什麼？只剩資料 → 它是分派表。**

三張登錄表各對**一個語法位置**（宣告的型別／自由函式呼叫／方法呼叫），
不合併——**位置決定形狀**（方法多一個 `obj`，宣告根本不是呼叫）。

### ⚠️ 「一顆一個 commit」在同模組的第二顆就破了

三顆 `<string>` 的宣告住在同一個 JSON 的相鄰項，其中兩顆更是共用
`io.ts` 的**同一個 case**——切一半會留下跑不動的中間狀態。

> 那條規則預設了「膠囊之間不共用原始碼區域」，而**同模組的第二顆就打破它**。

→ 破例可以，但**在 commit 訊息裡寫明是哪幾顆綁在一起、為什麼拆不開**。

### ⚠️ 樣板字串組出來的身分：連「缺了哪一路」都量不出來

`find_first_not_of` / `find_last_not_of` 的身分原本是
`` createNode(`cpp:string_${method}`) ``。掃描器只匹配字面字串，於是：

- 就近性護欄把它們記成「1 檔」——`io.ts` 那一檔**根本沒被算進去**
- 而 `generateCode` 對這兩顆回 `⟨unknown concept⟩`：
  **一條真實可寫的 C++ 走「程式碼 → 積木 → 程式碼」一圈會變成錯誤訊息**，
  而沒有任何護欄看得見

> **一個看不見的身分，連它缺了哪一路都量不出來。**

→ 搬家把身分變成字面，那個洞當場現形。**膠囊化的收益裡有一項是「變得可量」**，
  而它不會出現在「未膠囊化」那個數字上。

補一條從未存在的路**可以**與搬家同一個 commit——「搬移不重寫」防的是
「對不出基準」，而沒有既有實作就沒有基準可以對歪。

### 護欄在搬家當下會抓到什麼（十顆的實測）

| 護欄 | 抓到 |
|---|---|
| 參數規格一致性 | 照抄來的 `?? 'str'` 退路，宣告裡沒有 |
| 反向就近性 | 我在**註解**裡寫了別顆的字面 id → 「膠囊裡混進別顆」 |
| 缺陷帳 | `it.fails` 也算停用測試，要帶分類標記 |
| 元件身分完備性 | 測試裡隨手寫的 `cpp:literal` 根本不是概念 |

→ **搬完先跑全套，別先產基線**——這四條沒有一條是我自己看出來的。

## 明確否決的做法

- ⚠️ **批次搬多顆**——原本禁止（估計只有一個樣本）。
  **2026-08-10 起條件放寬**：三種形狀都驗過了，估計穩定。
  但**每批仍要跑全套並逐一對基準**——三顆裡有**兩顆**冒出新的組裝點，
  而那是批次最容易吞掉的東西。
  → 建議：**同形狀的可以批次，跨形狀的不要**。
- ❌ **挑最便宜的那 7 顆來「驗證流程」**——它們已在專屬資料夾，
  搬起來不會遇到剪裁，**驗過等於沒驗**。
  ⚠️ **而這條只管「驗證」這個目標**（2026-08-11 修正）：
  三種形狀都驗過之後，目標從**驗證**變成**產出**，而對產出來說
  **最便宜的就是最好的**。→ 兩個目標要分開問：
  「我現在是要證明處方，還是要推量？」

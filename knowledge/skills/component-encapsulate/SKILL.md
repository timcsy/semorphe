# 把一顆元件搬進膠囊（component-encapsulate）

> **語言指示**：輸出用當前對話的語言。

## 這個 skill 做什麼

把一顆元件散在共用檔裡的五路實作，剪進 `src/components/<scope>/<name>/`。

**來源**：`specs/104-component-vertical-slice/slice-record.md`——第一顆的切片紀錄。
那份紀錄自己說了它為什麼存在：

> 「哪些步驟會**重複 176 次**。沒有它，剩下的 176 顆仍然是憑感覺開票。」

⚠️ **而它寫完之後過了五輪都沒有被 skill 化**，中間又蓋了五條護欄。
這個 skill 就是那個延遲的償還——**`knowie-next` 的 skill 候選是預防性的：
在第 176 次手動重做之前 skill 它，不是之後。**

## 這把刀先問三句

1. **這顆元件的實作住在哪幾個共用檔？**（決定成本，見下方形狀表）
2. **它的模組裡已經有膠囊了嗎？** → 有的話**先解卡點 4**（工具箱順序），別硬搬。
3. **它的五路各自有沒有基準？** → 沒有就先錄，而**錄完要打開檔案看內容**。

## 形狀表——搬之前先分類（決定它有多貴）

`specs/104` T051 實測 177 顆：

```
  7 顆  已在專屬模組資料夾（std/<mod>/）    最便宜：移動而非剪裁
109 顆  lift 住在共用判別式或路由器      ✅ **兩批已實測是同一種形狀**
          41  core/lifters/strategies.ts    第一顆（vector_declare）驗過
          68  lifters/io.ts（已是路由器）    第二顆（char_is_alpha）驗過
 97 顆  產生器住在共用 statements/expressions/declarations
 69 顆  執行器住在共用 core/executors/
```

> **170/177 至少有一路住在共用檔**——所以「搬一顆」對大多數元件是
> **從共用檔裡剪一段出來**，不是移動一個檔案。

## 步驟

### 1. 錄基準——**然後打開檔案看內容** ⚠️

錄五路的產出（宣告／積木／標籤／產生／執行）當搬家前後的對照。

⚠️ **錄完必須打開基準檔看裡面有沒有東西。** 第一顆的基準把「執行那一路」
**全部錄成空字串**，包含一支應該印出 `3 4\n2` 的樣本——
**執行那一路等於完全沒有被防線覆蓋，而基準檔看起來是滿的。**

> 這是 `build-guardrail` 第 10 步在膠囊上的實例：
> **測試通過之前，先證明它真的測到了東西。**

### 2. 剪，不是搬

依形狀表從共用檔剪出 1–3 段。**剪完共用檔要少一段**——
如果共用檔沒變小，那是複製不是搬家，而**兩份會漂移**。

### 3. 自證測：每一條負向前面先釘一個正向錨點 ⚠️

```ts
expect(ids).not.toContain('cpp:vector_declare')   // ← 這一句在集合是空的時候也會過
```

`lift` 回傳 `null` 時集合是空的，負向斷言**空過**——
**一支空過的測試與健康的長得一模一樣。**

→ **每一條負向前面先釘一個正向**：「這段碼必須產生 `cpp:array_declare`」。
那句話證明量測跑到了，負向才有意義。

### 4. 接回載入路徑——**問「有幾個組裝點」**

第一顆掀出 **8 份「各自組裝」**（最貴的一項）。那八份已經收斂成
`all-declarations.ts`，所以**不會重複 176 次**——
但每次搬完仍要問一句：**有沒有第九個組裝點？**

判準：搬完之後 grep 那顆元件的舊身分，**共用檔裡不該還有它**。

### 5. 跑全套、對基準、下調棘輪

`tests/baselines/component-locality.json` 的「未膠囊化」只准下降。

⚠️ **下降的原因要註明**——「因為搬了」不是「因為重新分類」。

## 🔴 阻斷：卡點 4 必須先解，F 才能繼續（2026-08-10 升級）

第三顆的嘗試（`cpp:literal_char`）**因為這一條被回退**。原本它只是
「同模組第二顆之前要解」，實測之後發現它更寬：

> **`literal_char` 的 owner 是 `(core)`——它沒有模組可以併進去，
> 而核心分類裡積木的順序就是學生看到的順序。**

前兩顆能繞過去是因為它們有 owner 模組（`<vector>`／`<cctype>`），
**而 177 顆裡大多數是核心元件**。所以這不是「第二顆才遇到」，是**多數都會遇到**。

⚠️ **處置需要人拍板**：讓順序變成宣告的一部分（膠囊自己說排哪裡）
是技術上明確的，但**第一版的順序是教學決定**。
把它以字母序悄悄生效，比停下來誠實。

### 而那次嘗試賺到三件事，全部保留

**① 第三種形狀確認：lift 是「一整個 pattern 物件」**

```
strategies.ts 41 顆   分派表的一列      → 登錄呼叫
io.ts 68 顆           分派表的一列      → 登錄呼叫
**共用產生器 97 顆**  **一整筆 pattern** → **glob 直讀**
```

**② 資料不需要被登錄，它需要被找到** ⚠️ 這一條最貴

第一版把 pattern 寫成登錄呼叫（照抄前兩種的形狀），**壞了兩次**：

1. 讀取發生在登錄之前（`loadLiftPatterns` 早於 `registerCppLifters`）→ 讀到空陣列
2. 改成惰性併入之後仍然壞——**8 個測試檔各自組裝 lifter 而不呼叫
   `registerCppLifters`**，登錄從未發生

而**它沒有立刻爆**：共用檔裡還留著同名 pattern 時看不出來。

> **把資料做成登錄呼叫，等於替它發明一個會忘記呼叫的時序。**
> 判準：**這個東西有沒有人要「查」它？**
> 有（「`vector` 這個名字屬於我」）→ 登錄。
> 沒有（一整筆資料）→ **glob 直讀**，與 `component.json`／`forms/blocks.json` 同類。

**③ 八個各自組裝的 lifter**

```
自建 lifter 的測試檔    8
用共用 createTestLifter  113
```

那是卡點 6「八份各自組裝」在 **lift 這一維**的重演。
⚠️ **搬完要問「有沒有下一個組裝點」——而它每一維各有一批。**

## ⚠️ 未解的卡點：同模組的第二顆

`E` 項把工具箱做成有序來源，順序來自該來源 `blocks.json` 的**宣告順序**。
一顆元件搬出去之後它的積木從那個陣列消失，**接在最後面就會從分類的第一個
掉到最後一個**——測試抓得到順序變了，而**使用者感覺到的是「建立列表」不見了**。

第一顆的處置是「併進 owner 模組的段落、排在模組積木之前」，
**而那只對一顆成立**。

> **同一個 owner 底下第二顆搬進來之前，必須先決定元件之間的順序。**
> 今天是身分的字母序，而**那不是教學順序**。

→ **選下一顆時先看它的模組裡有沒有膠囊。** 有 → 先解這個，別硬搬。

## 已實測兩顆之後的修正（2026-08-10，`specs/113`）

**`specs/104` 的估計把 `io.ts` 那 68 顆列為「處方尚未實測」。實測結果：
它與 `strategies.ts` 那 41 顆是同一種形狀**——lift 都是
**共用分派表裡的一筆資料**，不是函式。處方相同：
判別邏輯留在共用檔，**資料**回到膠囊，共用檔改查登錄表。

```ts
// 兩顆都長這樣
export function registerLift(): void {
  register<某種>表('isalpha', 'cpp:char_is_alpha', 'cpp/char_is_alpha')
}
```

→ **那 109 顆的估計可以合併。** 而過渡表要留一句話：
「剩下的那幾筆是**還沒膠囊化**的，不是設計；它只減不增。」

### ⚠️ 順帶：膠囊化會**還掉別的債**

`char_is_alpha` 搬完之後，第三十三條護欄的「缺子節點」少一筆
——共用檔裡那句 `if (!v) return 0` 隨它搬進膠囊，而**新實作丟錯不回 0**。

> **搬家是重寫那一路的機會**，而重寫時既有的護欄清單就是檢查表。
> 但⚠️ **不要把重寫混進搬家的 diff**——搬移不重寫是預設，
> 要重寫就在**另一個 commit**，否則對不出基準。

## 明確否決的做法

- ❌ **批次搬多顆**——成本估計目前**基於一個樣本**（`specs/104` 自己標的）。
  第二顆的作用是**否證那個估計**，所以要一顆一顆搬到估計穩定為止。
- ❌ **挑最便宜的那 7 顆來「驗證流程」**——它們已在專屬資料夾，
  搬起來不會遇到剪裁，**驗過等於沒驗**。
  挑估計最弱的形狀（`io.ts` 那 68 顆尚未實測）。

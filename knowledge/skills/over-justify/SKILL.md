# 過度合理化的偵測（over-justify）

## 這個 skill 做什麼
一把刀，砍**過度抽象**（理論/概念）與**過度設計**（程式/架構）——同一把刀、兩層。
一個抽象要嘛比它取代的具體東西**多解釋/多預測**，要嘛**壓縮**它（更少假設、同樣預測）；兩者皆無，就是裝飾或過早設計，該砍或降為賭注。
（緣起：使用者「不能帶來比現行實現更強的解釋預測力，就是多餘的過度抽象」2026-07-27，來自姊妹專案 ArduinoCAD；2026-08-05 跨專案協商時搬入本專案，因為它在那五封往返裡裁決了四次：砍掉「合併 `Port[]`」、留下「守恆分兩律」、擋下「渲染獨立成套件」、否決「加第四個 `relation` 值」。見 [[元件]]、[[硬體域併入計畫]]。）

## 判準（核心，就這把刀）
對每個被審的抽象/層/理論/新原則：
1. **指出它抽象/取代的那個具體東西**（現行實現／更簡單的寫法）。說不出 → 可能是憑空抽象。
2. **它比那個具體多解釋或多預測了什麼？** 具體、可檢驗地說。
3. 第 2 若空，退一步：**它壓縮了什麼？**（更少假設、更好延伸、同樣預測——像 Maxwell。）注意：**翻成更重的詞彙不是壓縮，是反壓縮。**
4. 分類與處置：
   - 現在就**多解釋/多預測** → 留（賺到了）。
   - **壓縮** → 留（賺到了）。
   - **對未實作未來的設計** → 不砍，但**明標「未驗證的賭注、無現值」**、鎖 draft，別當理解 parade。
   - **純重述/裝飾**（砍了沒人會發現） → **砍**。

## 何時用
- 提出新抽象/新層/新設計模式/新原則/新理論時（動手前更好）。
- review 一份 draft / concept / PR，覺得「很漂亮但說不清值在哪」時。
- `/knowie-judge`、`/simplify` 順手帶一刀。

## 與別的 skill 分工
`/simplify` 管程式乾不乾淨、`/code-review` 抓 bug；**這條管「值不值得存在」**——上游的價值判斷。它是把 knowie 既有「砍了 AI 會不會默默跳過」「真母概念 vs 假的、有無 pruning power」兩測試收成的一把刀，且同刀砍程式的過度設計。

## 踩坑
- **別讓這 skill 變成它要防的東西**：保持極簡（一問 + 分類），別長成一套方法論，否則它自己就是過度設計。
- **賭注 ≠ 理解**：未實作未來的藍圖可以有價值，但要誠實標成賭注，別打扮成「已理解/已驗證」。
- **壓縮的豁免**：同樣預測但更少假設/更好延伸算賺到；別誤砍真壓縮——但翻譯成別的詞彙不算。
- **這不是成本測試。** 「不計成本」「反正要重寫」豁免不掉這把刀——抽象要嘛多解釋、多預測、要嘛壓縮，三個都不中就是裝飾，跟花多少力氣無關。（2026-08-05 本專案就是這樣用「不計成本」替一個反壓縮的合併脫罪，被 ArduinoCAD 抓到；見 [[經驗]]「豁免一條反對意見時，要指名豁免的是它的哪一層論據」。）
- 產出：每個被審項給「留／砍／降為賭注 + 一句理由」，不是長篇。

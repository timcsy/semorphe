# 寫一張人按得完的驗收清單

## 這把刀什麼時候用

一條規範**永遠變不紅**的時候：捲動位置有沒有還在、積木有沒有依序高亮、
⌘Z 之後畫面是不是使用者預期的。

⚠️ **先問一句**：

> **這條真的測不起來，還是【還沒被拆開】？**

`spec 140` 的第 1 條原本整條掛在人工驗收上，拆開之後**一半是機械的**
（拖曳中不得寫回、沒有語義變動時不寫、重畫後清掉復原歷史——全部有護欄了）。
拆得掉的那一半交給 [[build-guardrail]]，**這把刀只處理剩下的**。

## 🔴 先問第二句：**這條的主詞是不是「看起來」**

是的話**截圖**，不要查 API——而這條是付過學費的（2026-08-21，使用者連續回報五件事）：

| 問題 | 查得出來嗎 |
|---|---|
| 這個分類有幾顆積木 | 🟢 `getContents().length` |
| 這顆積木什麼顏色 | 🟢 `block.getColour()` |
| 這顆積木**長得對不對** | 🔴 **只有看** |
| 兩個語言的同一顆積木**一不一樣** | 🔴 **只有並排看** |

⚠️ 那五件裡有一件是**純版面**（mutation 按鈕在 else 前面還是後面）
——**沒有任何 API 問得出它**。

> **「開瀏覽器」不是動作，是【用眼睛】。
> 去了瀏覽器而不看畫面，等於把它當成另一個測試框架。**

🟢 **積木類的改動，收工前固定截三張**：工具箱的每個分類、拖一顆出來的樣子、
以及**同一顆積木在另一個語言那側**（一致性只有並排看得出來）。

## 一條驗收要有三段——⚠️ 缺任何一段都有已知的死法

```
① 這在測什麼      一句話的動機
② 怎麼按          從零開始的操作序列
③ 好與壞長什麼樣   兩邊都要寫
```

### ① 缺「這在測什麼」→ **它安靜地留在清單上不被按**

實例（2026-08-19）：八條裡七條被按過，剩下那一條沒被按的原因**不是麻煩，是看不懂**
——使用者逐字：「5b 我不知道是什麼意思」。

> **一條沒有人看得懂的驗收，與一條沒有人按的驗收，結果完全一樣。**

判準：讀的人要能決定「**值不值得花這三分鐘**」，而那個決定需要「為什麼」。

### ② 按法**必須自己走過一遍**

實例：條文寫「按 `▶ 執行` 旁的單步」——**而單步鍵不在那裡**，
要先從 `▾` 選 `🔍 除錯`，除錯工具列才出現。

🔴 **按不到看起來像功能壞了。** 一個按法寫錯的條文，會製造一個假的缺陷報告。

### ③ 「壞的長什麼樣」不可省

沒有它，「看起來還好」會被當成通過。⚠️ 而它**比「對的長什麼樣」更難寫**
——要寫得出來，你得先想過這條會怎麼壞。

## 🔴 而最容易漏的一條：**對照組**

實例：條文寫「按 `⌘Z` → 一次還原就是好的，要按好幾次就是壞的」。
實測「要按兩次」→ 判成缺陷 →⚠️ **而使用者自己去試才發現宿主手打也要按兩次**。

> **一條沒有對照組的驗收，量到的是「宿主 ＋ 我們」的總和，
> 而它的失敗訊息會指著我們。**

判準：**這一條的結果裡，有沒有一部分不是我們造成的？**
有 → 條文要先要求量一次基準線，判準寫成「**不差於基準線**」，不要寫絕對值。

⚠️ 這一族的另一面：**宿主給不給我們可以分辨的東西**。
`.ino` 在 Arduino IDE 是 `arduino`、在 VSCode 是 `cpp`——
一條「`.ino` 與 `.cpp` 要不同」的驗收在後者**驗不起來**，而那不是缺陷。
→ 條文要分開寫**機制有沒有接上**（我們的）與**宿主分不分得出來**（它的）。

## 清單層級的四條規矩

```
1. 版本標示要對得上   清單押在版本上；「修法沒載到」與「修法沒用」在畫面上同形
2. 哪一條壞了說哪一條  不必全部按完
3. 沒按的維持 🟠      🔴 不得因為其他條過了就一起勾掉
4. 不得自己勾         交付 ≠ 驗收。它要的是人在真的環境裡按
```

## 條文的前提被換掉時，它就不再是同一條驗收

⚠️ **這是最隱蔽的一種腐爛**：系統修好了，而舊條文仍然在描述舊世界。

實例：「純移動不該產生任何檔案變更」——**在空行還原做好之前是不可能成立的**
（純移動也會重寫全檔）。**用舊條文去驗新版本，會把一個真的修好判成沒修。**

→ 每次相關的機制改動，回頭問：**這一條現在驗的還是同一件事嗎？**

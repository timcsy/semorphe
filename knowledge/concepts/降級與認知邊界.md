# 降級與認知邊界

> **降級不是失敗，而是系統的認識論承諾**——選擇保留原始資訊而非強行結構化的正確行為。

系統的誠實不在於聲稱能理解一切，而在於**精確地標記自己理解的邊界**。

**這個概念本身是一次轉移的產物**：原本投影被隱含地當成二分（能轉換／不支援），
而二分之下遇到轉不了的東西唯一的答案是「不做」——整個投影族群（流程圖、敘事、呼叫圖）
因此被排除在架構之外。改成 **R0–R4 分級**之後它們才進得來。
見 [history/003](../history/003-可轉換性從二分改為-r0-r4-分級.md)。

**三視角投影：**

- **原則**：誠實降級——禁止強行結構化；降級單調遞減、可見、原因可區分
- **願景**：多 parser 融合擴大可辨識範圍；LLM 輔助擴大 pattern 覆蓋率
- **經驗**：靜默降級是 bug 的藏身之處——多層 fallback 用同一預設值會互相掩蓋

## 發現大於發明

語義結構不是系統「發明」的任意建構，而是對程式中**客觀存在的邏輯秩序的發現與解碼**。

```
數學家不發明定理——他們發現定理。
Semorphe 不發明語義——它解碼語義。

printf("hello")  中的「輸出」語義
for(i=0;i<n;i++) 中的「計數迴圈」語義
  → 這些結構在程式碼被寫下的瞬間就已存在
  → lift() 的工作是辨識它們，不是創造它們
```

三個實踐推論：

1. **概念命名不是任意的**：`count_loop` 不是給 for 迴圈取的暱稱，而是對客觀模式的辨識結果。命名的優劣取決於是否精確指向底層結構，而非使用者偏好。
2. **降級是誠實，不是失敗**：`raw_code` 是在說「這裡的真實超越了我當前的解析能力」——認識論上的誠實聲明，不是工程上的技術遺憾。
3. **自舉的目標是還原，不是演化**：優化 Topic 層級樹不是「發明更好的教學路徑」，而是「更精確地映射知識的內在結構」。

## confidence：系統的認知自評

```
high            ← 「我確定這裡的結構」（Protocol + Data 雙重驗證）
warning         ← 「結構匹配但我不太確定語義」（Protocol 通過，Data 存疑）
inferred        ← 「我根據已知模式推斷」（Protocol 啟發式推斷）
user_confirmed  ← 「我不確定，但使用者審查後接受了」（Agency 介入）
llm_suggested   ← 「機率性建議，尚未驗證」（Data 維度的輔助）
raw_code        ← 「此處超越我的理解能力」（三維皆不足）
```

**禁止強行結構化：**

```
對於不確定的語義：
  ✗ 給出一個「看起來合理」的結構    → 偽造（violation of Protocol）
  ✓ 標記 raw_code 並保留原始文字    → 誠實降級
```

**raw_code 覆蓋率是系統對自身認知邊界的誠實度量，而非缺陷數量的度量。**

這與「LLM 不能自動寫入語義結構」同源：**聲稱理解你不理解的東西，比承認不理解更危險。**

## 降級的三條規則

**1. 單調遞減**：一旦節點降級到某個 confidence 等級，除非有新的外部資訊（使用者確認、LLM 建議、更完整的上下文），不會自動恢復到更高等級。

**2. 必須可見**：

| 狀態 | 含義 | 視覺提示 |
|------|------|---------|
| 精確（high） | 系統完全理解 | 正常顯示 |
| 警告（warning） | 結構匹配但有可疑點 | 黃色邊框 + tooltip |
| 推斷（inferred） | 系統推測但不確定 | 淡色邊框 |
| 降級（raw_code） | 無法結構化理解 | 依原因區分 |

**3. 原因必須區分**（防止 Pattern 依賴的教育反噬）：

| 降級原因 | 視覺語義 |
|---------|---------|
| 程式碼錯誤 | 紅色警告——合理的負面回饋 |
| 系統能力不足 | 中性灰色 + 「系統尚未支援此寫法」——**不歸因於使用者** |
| 寫法非標準但正確 | 綠色邊框 + 「進階寫法」——鼓勵探索 |

若所有降級都用相同灰色，學習者會把「系統不認識」讀成「我寫錯了」，進而只寫系統能匹配的程式碼——**鷹架變成認知牢籠**。判定依據：能通過編譯/執行驗證但不匹配 pattern → 「非標準但正確」。

**強制性規則**（從 Sc4 推導）：任何 `patternType: 'composite'` 的 pattern，結構匹配成功但未通過所有語義驗證，**必須**設 `confidence: 'warning'`。跳過語義驗證直接設 `high` = 架構違規。

```
composite pattern 匹配流程（強制）：
  ① 結構匹配（AST 欄位類型檢查）  → 不通過 → 不匹配
  ② 語義驗證（副作用、變數修改等） → 不通過 → confidence: 'warning'
  ③ 所有檢查通過                   →          confidence: 'high'
```

## lift() 的完備性邊界

```
Lift-1: 結構匹配   — AST pattern 唯一對應，語義明確
Lift-2: 上下文推導 — 查找 declaration/context 消除歧義
Lift-3: 未決保留   — 建立 unresolved 節點，保留 AST 結構
Lift-4: 降級       — 真正無法處理 → raw_code
```

**Lift-3 vs Lift-4**：Lift-3 保留結構（知道是 binary expression、知道運算子），Lift-4 只保留文字。

**動態語言的歧義**：多個候選語義時**不猜測**，建立 unresolved 節點：

```typescript
{
  concept: 'unresolved_binary_op',
  properties: { operator: '+', candidates: ['math_add', 'string_concat'] },
  children: { left: a, right: b }
}
```

跨語言轉換的**前置條件**：語義樹中不可有 unresolved 節點。使用者不想手動消歧時，該節點降級為 raw_code。

**lift() context**：`declarations`（推導型別）、`using_directives`（辨識 cout vs std::cout）、`includes`（判斷可用函式庫）、`macro_definitions`（避免誤判巨集調用）。

## 巨集：真正的硬邊界

tree-sitter 不展開巨集。影響分三種情況：

```
情況 1 — 獨立巨集調用（FOR(i,0,n)、DECLARE_PTR(Foo)）：
  巨集調用本身降級為 unresolved_macro，但引數子樹各自獨立嘗試 lift()
  ——不一刀切。已知巨集可由語言模組 opt-in 擴充。

情況 2 — 成對巨集（BEGIN_MAP/END_MAP、Qt 的 signals/slots）：
  tree-sitter 無法產生有效 AST，整個區塊變成 ERROR 節點，
  「子樹各自嘗試」的前提不成立 → 整片降級為 raw_code。
  這是物理限制，不是架構缺陷。

情況 3 — 巨集定義型別（DECLARE_SMART_PTR(Foo) → 生成 FooPtr）：
  符號表缺少巨集生成的型別 → 所有使用該型別的節點連鎖降級。
  符號表應標記這些節點為 tainted_type，使降級更精細
  ——不是「不認識就全降」，而是「知道為什麼不認識」。
```

**誠實的邊界**：對重度使用框架巨集的 C++ 專案（Qt、MFC、gtest），巨集密集區域會整片降級。如果 80% 程式碼降級為 raw_code，語義結構的優勢將消失殆盡。

**緩解路線——多 parser 融合**（未實作）：

```
tree-sitter（快速、增量、不展開巨集）→ 結構骨架 + 非巨集區域的完整語義
clang AST（較慢、完整、展開巨集）   → 巨集區域的語義補充
兩者在語義樹層面合流——同一棵樹，不同區域由不同來源填充
```

比「模擬預處理器」可行：不需重新實現 C preprocessor，只需在語義層整合兩個已有 parser。代價是 clang 成為可選依賴，且融合邏輯需處理兩個 parser 對同一區域的不同解讀。

**對 Scope 的意涵**：S0-S2（教學場景）不需要融合——學生程式碼不會用框架巨集。S3-S5（大型專案分析）需要，但這些 Scope 的視圖本身就是唯讀的（R3-R4），精確度要求較低。

## 汙染追蹤（Taint Tracking）

```typescript
interface TaintInfo {
  kind: 'tainted_type' | 'tainted_symbol' | 'macro_expansion'
      | 'missing_include' | 'dynamic_dispatch'
  source?: string             // 汙染源識別（巨集名稱、缺失的 header）
  propagatedFrom?: string     // 汙染傳播自哪個節點 ID
  severity: 'hard' | 'soft'   // hard: 阻止執行/投影，soft: 標記但可繼續
}
```

執行時 raw_code 的汙染擴散也應在語義結構中顯式標記傳播路徑。**Raw code 解毒**：若能提供外延等價（∀ 合法輸入，A(input) ≡ B(input)）的執行體，汙染就被阻斷：

```
x = 5                             // ✅ interpret
y = compiled_call("complex_algo") // ✅ 編譯執行，回傳具體值
z = x + y                         // ✅ interpret（y 已是具體值）
```

## 工程上的反面教材：靜默失敗

理論上的「誠實降級」在實作中最常見的違反形式是**靜默降級**——系統降級了，但沒有任何可觀察的信號。

**反模式一：整類概念被靜默跳過**

```
if (concept.includes(':')) return   // ← 跳過所有語言特定概念

語義樹正確 → round-trip 測試全過 → 使用者執行 → 結果錯誤
                                                    ↑ 沒有任何錯誤訊息
```

修復：移除靜默跳過，改查 executor registry；宣告性概念註冊 noop；未知概念透過 `unknownConceptHandler` 讓使用者選擇。見 [history/011](../history/011-四路完備性擴充為五層.md)。

**反模式二：多層 fallback 用同一預設值**

四層防線都靜默降級為 `'x'`，沒有 warn、沒有 annotation。從使用者角度程式碼「就是錯了」，但系統毫無提示——而且多層用同一值會**互相掩蓋**，讓真正的資料遺失點無法定位。

**守則**：fallback 值只在「確實沒有更好的選擇」時使用。如果 `saveExtraState` 回傳了 args 但裡面沒有 text，這不是「沒有輸入」，而是「**資料格式不符預期**」——應該嘗試恢復（如讀 `selectedVar`），而非直接用預設值。

見 [episodes/2026-03-12-cin-變數名靜默降級.md](../episodes/2026-03-12-cin-變數名靜默降級.md)。

## 誠實的判定法

> **「如果這裡出錯，會有人發現嗎？」** 答案是「不會」的每一處，都是一個等待發生的靜默降級。

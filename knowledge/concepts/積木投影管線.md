# 積木投影管線

理論上是 `project` / `lift` 的一對；工程上是**四段各自可能出錯、且錯了不會報錯**的鏈路。這個概念存在的理由是：Semorphe 絕大多數的 bug 都出自這四段之間的契約不一致。

```
        ┌──────────── generate ────────────┐
   Code │                                  │ Blocks
        └── lift ──→ SemanticNode ── render ┘
                          ↑
                       extract
```

**三視角投影：**

- **原則**：P2 路徑完備性、Sc4 最小驚訝
- **願景**：加入新語言時，這條管線的檢查清單就是驗收標準
- **經驗**：管線的每個接縫都出過事——搶匹配、雙真相源、欄位名不同步、序列化契約分裂

## 積木定義的兩層架構

**JSON 宣告層**（`src/blocks/universal.json`、`src/languages/{lang}/blocks/*.json`）：

```jsonc
{
  "id": "c_increment",
  "language": "cpp",
  "category": "operators",   // toolbox 分類
  "level": 1,                // 認知層級（0=beginner）
  "concept": { ... },        // 語義概念定義
  "blockDef": { ... },       // Blockly 積木外觀（message0/args0）
  "codeTemplate": { ... },   // 簡單的程式碼產生模板（可選）
  "astPattern": { ... }      // AST→積木的 lifting 規則（可選）
}
```

**動態覆蓋層**（`registerDynamicBlocks()`）：`init` / `saveExtraState` / `loadExtraState`。

**覆蓋規則（易踩）：**

- 動態層的 `init()` **完全取代** JSON 的 `blockDef`（`message0`、`args0` 全部失效）
- 但 JSON 的 `concept`、`codeTemplate`、`astPattern`、`level`、`category` **仍然有效**

**何時需要動態覆蓋**：動態 FieldDropdown（變數列表）、mutator 齒輪、+/- 按鈕動態增減欄位、三模式參數。

> **雙真相源警告**：`universal.json` 的 blockDef 和動態註冊定義了**相同積木的 input names**。改任一方必須同步另一方。PatternRenderer 對沒有顯式 renderStrategy 的積木會從 JSON blockDef 自動推導 input mapping——**若 JSON 名稱錯誤，只在 Block Style 切換（serialize→deserialize）時才暴露**。

## 程式碼產生的優先順序

```
TemplateGenerator.generate(node)   ← 1. 先嘗試 codeTemplate（JSON）
        ↓ 回傳 null
GeneratorContext.generators.get()  ← 2. 後備：hand-written generator
```

**如果 `codeTemplate` 存在且能產生非 null 結果，hand-written generator 永遠不會被呼叫。**

- 改用 hand-written 時**必須移除 JSON 中的 codeTemplate**——否則你的程式碼根本沒在跑
- 測試時：`generator.generate()` 只測 template 路徑；測完整管線需用 `generateNode()` + `GeneratorContext`
- 真實 app 載入 template、測試常常沒載入 → **測試通過但實際行為不同**

## Lifting（Code → Semantic）

兩條路徑：宣告式 `astPattern`（優先）與 hand-written lifter（逃生口）。詳見 [開放擴充](開放擴充.md) 的 pattern 章節，包含歧義仲裁、constraint-before-strategy、Lossless Lift 原則。

## Extraction（Blocks → Semantic）

兩種方式：通用 JSON-driven（`extractFromSpec`，依 BlockSpec 的 concept 定義自動提取）與手寫 case。

**何時需要手寫**：動態數量的欄位（`NAME_0`、`NAME_1`…）、三模式參數、特殊語義轉換（如 scanf 的 `noAddr` 標記）、mutator 產生的動態結構。

2026-03-16 起分散的 extractor 已統一為 PatternExtractor strategies，見 [history/013](../history/013-extractor-統一為-patternextractor.md)。

## 全鏈路欄位同步（最常見的資料遺失來源）

```
blockDef (init) → extractBlockInner → generator → lifter → adapter
   NAME_0            NAME_0            NAME_0      NAME_0    NAME_0
```

**任何一環沒改到都會造成資料丟失或產生錯誤碼**，而且 `getFieldValue()` 對不存在的欄位**只回傳 null 不報錯**——這類不匹配在靜態分析中幾乎無法發現。

**守則**：Extractor 測試應覆蓋「欄位名正確性」——用 mock block 驗證 extractor 讀取的欄位名確實存在於積木定義中。

## 動態積木的常用模式

**`const self = this`**：必須定義在 `registerDynamicBlocks()` 的**最頂層**。若定義在某個 block 的 scope 內，其他 block 的 closure 抓不到（症狀：`self.xxx is not a function`）。

**動態 FieldDropdown**：用箭頭函式包裝以便每次展開時即時掃描 workspace。**Blockly 不允許空選項陣列**，必須至少有一個 fallback（`options.push(['x','x'])`）。

**+/- 按鈕**：`moveInputBefore` 確保新參數插在 TAIL 之前；`saveExtraState`/`loadExtraState` 保證序列化還原；**重建 labels 時要先 `getFieldValue` 儲存再 `setFieldValue` 還原**，否則 field value 會消失。

**三模式參數（select / compose / custom）：**

| 模式 | UI 元件 | 用途 |
|------|---------|------|
| select | FieldDropdown | 從 workspace 變數清單選擇 |
| compose | ValueInput | 用積木組合複雜表達式 |
| custom | FieldTextInput | 直接輸入文字 |

透過 `buildArgSlot()` / `rebuildArgSlot()` 共用邏輯（可配置 `getVarOptions`、`separator`、`inputPrefix`、`defaultVar`、`customDefault`）。切換機制：dropdown validator 攔截特殊值（`__COMPOSE__`、`__CUSTOM__`），用 `setTimeout` 觸發 rebuild。

> **validator 的隱藏陷阱**：dropdown validator 寫入的欄位名（`selectedVar`）可能與 `saveExtraState` 讀取的欄位名（`text`）不同。這正是 `cin >> s` 事故的第一層。

**Mutator 齒輪**：Container block（齒輪 mini-workspace 的頂部容器）+ Item blocks；`decompose()` 主積木→mini-workspace、`compose()` 反向、`saveConnections()` 記住已連接的子積木。**Mutator 內的文字也要遵守積木文字準則**——使用者看得到。

**Statement↔Expression 雙版本**：`block-renderer.ts` 的 `STATEMENT_TO_EXPRESSION` 集中管理映射。關鍵約束——兩版本的 `saveExtraState`/`loadExtraState` 格式**必須完全相同**（映射時直接搬移 extraState）；generator 用 `ctx.isExpression` 判斷是否加 indent/分號；只需要一個 `extractBlockInner` case。

**FieldMultilineInput**：Blockly 12.x 已移至獨立套件 `@blockly/field-multilineinput`。PatternRenderer 的 `deriveRenderMapping` 也需辨識 `field_multilinetext` 類型。

## 形態的軸——**`from` 決定「沒宣告 form 的那一顆」是什麼意思**

一個元件身分可以有多個積木形態（097）。形態掛在一條**軸**上，而軸的定義是核心的一張表
（`src/core/projection/form-selection.ts` 的 `KNOWN_AXES`），不是每個變體各寫一份。

| 軸 | `from` | 值從哪來 | **沒宣告 `form` 的那一顆是** |
|---|---|---|---|
| `role` | `position` | 積木擺在哪（敘述位／運算式位） | **敘述版——一個真正的選項** |
| `container_kind` | `property` | 去查那個變數的型別 | **退路**——型別查不到時才用它 |

⚠️ **這兩者不能混為一談，而它們長得一模一樣**（都是「這顆沒有 `form` 欄位」）。

判準是**軸的 `from`**：

- `position` **永遠取得到**（它是結構性的，看語法樹的父節點就知道）→ 那條軸**不需要退路**，
  沒宣告 `form` 的是一個正當的形態。
- `property` **可能取不到**（型別推不出來）→ 才需要一顆退路。

**實際代價**：E 項第一版把兩者混為一談，一律當退路排除，於是
`u_var_declare`／`u_input`／`u_func_call`／`cpp_method_call`／`c_increment`／`c_scanf`
**七顆最常用的敘述版積木從工具箱消失**。判準與反向注入測試見
`src/ui/toolbox-builder.ts` 的 `isTypeLookupFallback` 與
`tests/integration/audit-toolbox-reachability.test.ts`。

**工具箱只放形態，不放退路**——退路是型別查不到時的降級，不是學生選得出來的選項。
這條由上表**推導**，不是一份排除清單：漏寫一顆，中性版就會混進工具箱，
而那正是學生回報過的困惑（見 [episodes/2026-08-07-學生說積木寫錯了](../episodes/2026-08-07-學生說積木寫錯了.md)）。

## Toolbox

**歸屬是導出的，順序是宣告的。** 一個工具箱分類宣告**有序的來源段落**
`{ from, category }`（`from` 是 std 模組 header／`(core)`／`(universal)`），
段落的**成員**由登錄表推導。

- 往既有模組加一顆積木 → **零編輯**，它自己出現在對應分類的對應位置
  （順序＝該模組 `blocks.json` 的宣告順序）
- 一顆積木要跟它的來源不同家 → **它自己**宣告 `toolboxCategory`
  （`<cstdlib>` 的 `abs` 是運算、`exit` 是控制、`atoi` 是文字——一個標頭三個教學意圖）。
  同時屬於兩個分類是真的，所以型別是 `string | string[]`

判準：**問「登錄表知道嗎」，不問「這是不是一份清單」。** 見
[history/029](../history/029-E項登錄表導出-清單不是碎裂是量測算錯了.md)。

**預配置變體（extraState Presets）**：同一積木類型可在 toolbox 中以不同 `extraState` 出現，展示概念的不同結構複雜度（如 `u_if` 的「如果」/「如果否則」/「如果否則如果否則」）。搭配 `excludeTypes` 排除舊版積木避免重複。**這一類保留為宣告**——「有 else 的 if 值得一個獨立入口」是教學判斷，登錄表推不出來。這是 [漸進揭露](漸進揭露.md) 中「表面形態」的實作。

**護欄**：`audit-toolbox-reachability`（第十九條）——每顆有積木投影的元件都必須在某個分類裡拿得到；明確排除（`excludeTypes`／退路形態）分開計。它**不檢測**「放對分類」，只檢測「在某個分類裡」。

## 常見陷阱速查

| 陷阱 | 症狀 | 解法 |
|------|------|------|
| `const self = this` 位置錯誤 | `self.xxx is not a function` | 移到 `registerDynamicBlocks()` 最頂層 |
| template 和 hand-written 並存 | 產生錯誤或不完整的程式碼 | 移除 JSON 中的 `codeTemplate` |
| astPattern 搶匹配 | 錯誤的積木類型被 lift 出來 | 加 constraints 或改用 hand-written lifter |
| FieldDropdown 空選項 | Blockly 拋錯 | 加 fallback 選項 |
| mutator extraState 格式不相容 | 舊存檔載入後積木形狀錯誤 | 直接升級格式、刪除舊路徑（`??` 是 null safety 不是相容層） |
| 欄位名稱不同步 | 資料丟失或產生錯誤碼 | 全鏈路搜尋確認一致 |
| `rebuildArgLabels_` 丟失 field value | 重建後 dropdown 選項重置 | 先 `getFieldValue` 儲存，重建後還原 |
| 重複的積木概念 | 語義衝突、lifter 不確定用哪個 | 合併為一個 |
| 積木不出現在 toolbox | 使用者看不到新積木 | 檢查 `level` 和 `category` 設定 |
| concept 未在 registry 註冊 | diagnostics 報 unknown、code-to-blocks 失敗 | 新增概念的第一步就是 registry |
| Lift 有損正規化 | round-trip 丟失 format string | lift 保留語言特定概念，style exception 做可選正規化 |
| 複合型別被截斷 | `long long` 變成 `long` | 前綴匹配已知複合型別，或結構化存儲 |
| statement/expression extraState 不一致 | expression 版欄位全部 fallback 為預設值 | 雙版本序列化格式必須完全相同 |
| liftStrategy 在 constraint 之前執行 | 錯誤的 AST 節點進入 strategy | constraint-before-strategy |
| `FieldMultilineInput is not a constructor` | Blockly 12.x 移除了內建版本 | 安裝 `@blockly/field-multilineinput` |
| Mutator label 暴露原始語法 | 使用者看到 `@param`、`*/` | mutator label 同樣遵守積木文字準則 |
| 概念缺 interpreter executor | round-trip 全過但執行結果錯誤 | 註冊 executor；宣告性概念註冊 noop |

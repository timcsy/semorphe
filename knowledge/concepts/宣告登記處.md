# 宣告登記處（Declaration Registry）

核心需要知道**「有這種東西」**，而不需要知道**它叫什麼、也不該假設它有幾個**。
登記處就是這句話的資料結構：**語言套件在載入時推進去，核心在需要時問**。

## 三視角

- **原則**：P3 開放擴充（「不修改既有程式碼就能加入新語言」）＋ P9 語言獨立性
  （「拔掉 C++，只裝 Python stub → 所有視圖仍啟動，無 `languages/cpp/` import」）
- **願景**：中立性三維（元件身分／積木型別／import）歸零的**唯一**清償路徑
- **經驗**：「核心層是所有語言共用的那一份，所以它的違規比視圖層更硬。」

## 這句話有兩半，而第二半是踩到才長出來的

```
核心可以知道「有這種東西」          ← 2026-08-11 起就寫在 core/component/traits.ts:112
              ↓
不該知道它叫什麼                    ← 第一半
不該假設它有幾個                    ← 🔴 第二半，spec 160（2026-08-20）才補上
```

**第二半的來歷**：`componentWithTrait('programRoot')` **回傳第一個匹配**。
C++ 有一個程式根、Python 也有一個，於是渲染器裡的

```ts
if (tree.componentId !== programRootComponent()) return { blocks: [] }
```

**挑了一個**——另一個語言的樹永遠不是「那個根」，回空清單、**零錯誤**，
使用者看到**空白畫布**。

> **一個「全域只有一個」的假設，在第二個成員出現時不會報錯——它會挑一個。**

🟢 正解是**換問法**，不是加參數：`isProgramRoot(componentId)`——**問這顆自己的宣告**。
換完之後「有幾個語言」對核心而言不再是一個要知道的數字。

## 判準：什麼該做成登記處

| 問 | 是 → 登記處 |
|---|---|
| 核心需要這個資訊嗎 | 需要（否則它根本不該在核心） |
| 這個資訊**因語言而異**嗎 | 是（`//` vs `#`、`cpp_raw_code` vs …） |
| 核心猜得到嗎 | **猜不到**——而猜一個「看起來合理的」正是 P6 禁止的 |

⚠️ **沒有宣告時要誠實**：回 `null`／空陣列，讓呼叫端知道「這個語言沒有」
——**不要猜一個名字**。`degradation-blocks` 的檔頭逐字：
「回 `null`，讓呼叫端知道『這個語言沒有降級積木』——**不要猜一個名字**」。

## 現況（2026-08-20 實測九個）

```
core/board-constant-dropdown-blocks   declareBoardConstantDropdown
core/comment-syntax                   declareCommentSyntax
core/degradation-blocks               declareDegradationBlocks
core/language-executors               declareExecutor
core/non-components                   declareNonComponent
core/skip-declarations                declareSkips
core/standalone-block                 declareStandaloneBlockBuilder
core/toolbox-categories               declareToolboxCategories        ← spec 160 新增
core/variable-dropdown-blocks         declareVariableDropdownBlock
core/language-packs                   declareLanguagePack             ← spec 161 新增
```

### 🔴 而第十個掀出一條這個模式自己的坑

**登記表不能自己 `import.meta.glob` 自己的宣告者。**
`eager: true` 的 glob 被 Vite **提升成靜態 import**，於是宣告者在
`const PACKS = new Map()` **之前**就執行 → `ReferenceError`。
→ 登記表與載入器**分成兩個檔**（`language-packs.ts` ／ `load-language-packs.ts`）。

### 🔴 而其中八個**只有一個宣告者**——那是這個模式今天最大的弱點

登記處是為了「核心不認得任何語言」而蓋的，**而八個的宣告者都是 `languages/cpp/`**。
一個只有單一宣告者的登記處，**與一個寫死的值在行為上分不出來**——
它的正確性要等第二個語言進來才驗得了（`isProgramRoot` 那件事就是這樣被驗出來的）。

### 🟢 `toolbox-categories` 的不對稱**已收**（spec 161）

它曾經只有 python 一個宣告者——`app.ts` 直接 `import cppCategoryDefs`，繞過登記處。
兩個語言都走 `pack.ts` 之後，那九個登記處**第一次有兩個語言在用**。

## 與別的概念的關係

- [元件代數](元件代數.md)——登記處裝的多半是**元件的性狀**，而不是元件本身
- [開放擴充](開放擴充.md)——登記處是 P3 的**實作形狀**：Layer 1 是資料，這是資料的入口
- [執行機構](執行機構.md)——⚠️ 一個沒有人宣告的登記處**就是殼**，而它綠得跟真的一樣

# 連接（Link／邊）

**連接是兩個埠之間的那條邊——而決定「接起來會發生什麼」的不是接點，是【關係】。**

```
結構   樹 · 有向邊 · 網（具名、多對多）
關係   組合 · 資訊 · 守恆
🔴 兩者【正交】—— 電氣 net 與 ROS topic 結構相同，只是律不同
```

**三視角投影：**

- **原則**：根公理逐字寫著「元件**節點**和**關係邊**」——邊不是新決定，是還債。
- **願景**：跨域合流的接縫。同一條邊在電氣叫 `Net`、在機械叫 `joint`、在 ROS 叫 topic。
- **經驗**：把「這個關係長什麼結構」寫進關係的定義裡，讓「同一個關係換一種結構」變成一個看不見的格子——而它藏了一年。

⚠️ **本檔 2026-09-25 從 [元件](元件.md) 搬出來**，內容是原樣搬移（另有兩處更正，標了紅字）。

## 接點的關係律：三種，不是一種

**接點不都是埠。** 決定「兩個接點接起來會發生什麼」的，是**關係**：

| 關係 | 律 | 是埠嗎 |
|---|---|---|
| **組合**（composition） | 父擁有子；恰好一個父；刪父連子一起死 | ✗ |
| **守恆**（conserved） | 不可自由複製；全網求解（見下方兩種律） | ✓ |
| **資訊**（information） | 可複製、無基質 | ✓ |

## 🔴 而「結構」與「關係」是**正交**的（2026-09-25 更正）

這張表原本有第四欄「結構」，把**組合＝樹 · 守恆＝約束網 · 資訊＝有向邊**綁死。
**那一格是錯的**，而推翻它的是 **ROS 的 topic**：

```
一個 topic   具名 · 多個發布者 · 多個訂閱者      ⟹ 它是一張【網】
而它載的是   資訊（可複製、無基質）              ⟹ 不是守恆
```

⟹ **電氣 net 與 ROS topic 結構上是同一個東西**（具名的多對多會合點），
**只是律不同**。而原表把「網」當成守恆的特徵記了一年。

|  | 樹 | 有向邊 | **網**（具名、多對多） |
|---|---|---|---|
| **組合** | ✓ | — | — |
| **資訊** | — | ✓（一源 fan-out） | 🔴 **ROS topic** |
| **守恆** | — | — | ✓ 電氣 net |

⚠️ 所以「資訊 ＝ 一源 fan-out 多讀者」要改口成
**「資訊在【有向邊】這個結構上是一源 fan-out；在【網】上可以多源」**。

> **把「這個關係長什麼結構」寫進關係的定義裡，
> 會讓「同一個關係換一種結構」變成一個看不見的格子。**

（推翻它的過程見 `draft/2026-09-22-元件宣告的契約化.md` §十二——
拿十個域逐一填這張元件模板，而 ROS 是第十個。）

### 🔴 而它一年內第二次想塌回去，第二次換了個軸（2026-09-25 下午）

同一天下午，使用者問：「所以實際上是因為在處理不同的**階層式元件粒度**，
也關注不同的**連接形態**囉？」——**一半對**。

```
🟢 對的一半   粒度確實換【結構】   根公理逐字：檔案內是樹 · 檔案間是圖 · 系統間是超圖
🔴 錯的一半   粒度【不】決定關係
```

反例兩個方向都有，而且都在本檔裡：

```
組合在【粗】粒度也有   URDF 的 link ⊂ 機械臂 · `numpy.linalg` 的命名階層
守恆在【細】粒度也有   Rust 的 `let b = a`（String）是 move —— 運算式粒度的守恆
```

**把粒度 × 關係填一遍，九格都有東西：**

| | 檔案內（樹） | 檔案間（圖） | 系統間（網／超圖） |
|---|---|---|---|
| **組合** | 運算式的子槽 | 命名階層 `numpy.linalg` | URDF link ⊂ 機械臂 |
| **資訊** | def →use（算的） | 函式呼叫 | ROS topic |
| **守恆** | Rust move | 所有權跨模組 | 電氣 net |

**九格都填得出來 ⟹ 關係與粒度正交**，而這比上面那張 3×3（只有四格）
是更硬的證據——**每一格都有實例，不是「理論上可以」。**

⚠️ **而值得記的是它塌回去的次數，不是它錯在哪**：

```
第一次   關係 ＝ 結構    綁了一年,ROS topic 推翻
第二次   關係 ＝ 粒度    同一天下午,問法完全不同而形狀一樣
```

> **一個被拆開的綁定會再回來，而它下一次穿的是另一個軸的衣服
> ——因為「粗的東西接起來的方式跟細的不一樣」在每一個域裡都【看起來】是真的。**

🟢 **判準一句話**：問「**換一個粒度，這條關係的律變了嗎**」。
沒變（`Σ through = 0` 在一顆電阻裡與在一整塊板子上是同一條）⟹ 它不是粒度的函數。

**埠 = 關係為守恆或資訊的接點**——對等、可 Link、雙方獨立存活。組合接點（積木的 `body` 槽、UI 的 `slots`）是**擁有**不是**連接**，不是埠。

**`relation` 屬於「邊」，不屬於「接點」。** 接點宣告的是「我能參與哪些關係」（`accepts`）。硬體是退化情形——兩端都是電氣接腳，邊必然守恆，看起來像接點自己的性質；軟體是一般情形——同一個語法接點，關係由流過的**型別**決定：

```rust
let b = a;      // a: i32    → 複製，資訊
let b = a;      // a: String → move，守恆
let r = &a;     // 共享借用 → 守恆基質的非消耗性投影，可 fan-out
let r = &mut a; // 獨佔借用 → 取得驅動權，不可 fan-out
```

## 守恆＝有基質；其上的邏輯是基質的投影

**守恆接點常常同時載著資訊**——一條 GPIO 線既是電壓（守恆）又是邏輯位階（資訊）。單值 `relation` 看似裝不下，解法是不要把它當第二條關係：

> **守恆 = 有守恆基質；其上的邏輯／命令是該基質的投影。**
> **資訊 = 沒有基質的純資料流**，可自由 fan-out。

於是 GPIO 的關係是**守恆**，邏輯位階是它的投影。這和本檔另外兩個判決（「行為軌跡是投影不是真實」）是同一把刀——**同一個論證形狀成立三次。**

推論：**adapter 邊界被釘在型別上**。資訊↔資訊直接接；一端有守恆基質就要 adapter。Arduino API 就是這層的既有實證——`digitalWrite`/`analogWrite` 是資訊→守恆，`digitalRead`/`analogRead`/`pulseIn` 是守恆→資訊的投影，`pinMode` 宣告的正是「這個接點在網裡是 driver 還是 reader」。

## 守恆的兩種律

| `law` | 律 | 域 |
|---|---|---|
| `shared` | across 相等、through 相加為零（克希荷夫／力平衡）——**多方可同時持有同一份** | 電氣 ✅ 已驗；機械、未來熱／流體＝**設計意圖，未驗**（見下） |
| `exclusive` | 資源不可自由複製，合法性需要一份帳——**同時只有一個持有者** | Rust ownership、`unique_ptr`、`shared_ptr`、mutex、file handle |

🪦 **`shared` 這個值曾經叫 `balance`**（2026-09-14 改名，見 [history/232](../history/232-一個好名字會讓它的判準變成同義反覆.md)）。
使用者一句話判死它：「**我一看根本無法望文生義**」——而它確實過不了本檔
2026-09-13 才立的那條判準（「廣泛使用，而且它的常見意思就是你要的那個意思」）：
`balance` 的日常意思是餘額／平衡，沒有一個是「through 相加為零」。

🟢 而 `shared | exclusive` 是**鎖的那對詞**：POSIX `LOCK_SH`／`LOCK_EX`、
資料庫的 S／X lock、`shared_mutex` 的 `lock_shared()`／`lock()`、`RwLock` 的讀寫。
**不需要教任何人這對詞。**

🟢 **「across／through」不是我們發明的**（2026-09-13 查證補上）：它是 **bond graph**
的語彙（Henry Paynter，1959-04-24），而 bond graph 的整個賣點就是
**一套模型跨電、機、液、熱**——與本檔「預測未來加熱學／流體域會重用同一張平衡網」
是同一個主張，早了六十七年。effort × flow ＝ 功率，是各域共通的貨幣。

它的工業後代是 **Modelica**，規格逐字：連接點上非 flow 變數 `a1=a2=…=an`、
flow 變數 `z1+z2+(-z3)+…+zn=0`。⚠️ **不採用 `flow` 這個字**——它在軟體域會被讀成資料流，
而這個 repo 的「流程」面板已經佔著它。引用 Modelica 是為了**讓下一個人知道這不是自創的**，
以及未來與模擬工具交換模型時有一條現成的接縫（與 `step` 對齊 FMI 同一種白拿）。

兩律**可證不同**，這是分律賺得起位置的理由：**open-drain／I2C 的多 driver 在 `shared` 下合法，在 `exclusive` 下非法**。

🟢 而請注意這句話在改名之後**變成了同義反覆**——「多方持有在『多方可持有』下合法」。
那不是論證退化，那是名字接手了論證：

> **一個好名字會讓它的判準變成同義反覆；
> 一個壞名字要靠一個反例才撐得住。**

（在 `balance` 那個名字底下，這句話需要讀者已經知道 KCL 才成立。）

**為什麼是兩律**——差異的根不在「守不守恆」，在**有沒有可以退回去的連續基質**：

| | `shared`（物理模型） | `shared`（理想化模型） | `exclusive` |
|---|---|---|---|
| 律本身 | **永遠可滿足**（短路也有解，只是電流很大） | **借來可滿足性違反** | **只有可滿足性** |
| 違反長什麼樣 | 解出來的值比**額定**（過流、超出 SOA） | 方程不一致，無解 | 二值，沒有「違反多少」 |
| 需要的機器 | 求解器 ＋ 門檻 | 可滿足性檢查 | 可滿足性檢查 |

**KCL 從不禁止任何東西；禁止的是額定。** 借用檢查沒有「額定」——它直接說有沒有合法指派。

**理想化是可滿足性違反的來源，跨域同形**（ArduinoCAD 回送）：

| | 理想化 | 後果 | 去掉理想化 |
|---|---|---|---|
| 電氣 | 理想源（0Ω 推挽） | 5V 與 0V 短接 → KVL 方程不一致、**無解** | 有限輸出阻抗 → 解存在＋過流（額定違反） |
| 機械 | 剛體（無順應） | 兩馬達不同轉速同軸 → **無合法角度指派** | 有扭轉順應 → 軸扭轉＋強度違反 |

所以 `CONFLICT` 和運動學鎖死是**同一個現象**——都是理想化的產物。

## 這條讓 `law` 塌回基質

於是兩律的差別**塌回本節自己的核心論題**：

- **有連續基質** → 退得回去 → 物理模型可滿足、違反是額定 → `shared`
- **沒有連續基質** → 退無可退 → 只有可滿足性 → `exclusive`

`law` 不是第二條獨立的軸，**它是「有沒有連續基質」的推論**。「守恆＝有基質」這個判準在本節第四次成立。

> **可測後果（未驗，標為預測）**：若 `law` 可從基質推導，它就該是**衍生欄位而非宣告欄位**。而且這預測**軟體域最終也會有 `shared`**——速率限制／頻寬／token 預算有連續基質，超用是降級（額定違反）而非失敗。目前無證據。

> **機械域的誠實標記**（ArduinoCAD 查證）：他們的 `coupleKinematics` 目前是**單向剛性導出**（driver→driven，1:1），不是全網平衡求解；兩端同 role 直接略過、不產生 CONFLICT；無額定檢查；只跑開放運動鏈。**「機械是 `shared`」是設計意圖，不是已實作驗證的現實**——上面那些表**只有電氣列被驗過**。要等機械長出閉環或多驅動（兩馬達一軸、四連桿）才會同時取得額定面與可滿足性面。

> ⚠️ **一句被否決的過度宣稱**：本檔原版寫「Rust 的 aliasing XOR mutability 就是麵包板的『一個 driver、多個 reader』」。**不成立**——電氣的 `CONFLICT` 不是「不只一個 driver」，是「不只一個**不一致**的 driver」：兩個推挽都 HIGH 不衝突；open-drain／I2C 多 driver 合法且正常（那是 I2C 仲裁的整個基礎）。而 Rust 不管一不一致，第二個 mutator 就是錯。
>
> **正解**：數位推挽的「一線一 driver」是**施加在 `shared` 基質上的 DRC 慣例**，不是物理律——`shared` 律結構上不可能禁止它。這也解釋了為何 `CONFLICT`／`FLOATING` 是「求解的定性」而非電壓讀數：**數位 `NetLevel` 模型把 DRC 慣例烘進了模型本身**；類比模型裡沒有 `CONFLICT`，只有分壓出來的一個電壓。
>
> 教育後果：初學者被教的「一線一 driver」是慣例非定律，**工具該講對，否則學生一碰 I2C 就困惑**。

仍然成立的對應（弱一點，但足夠）：

| | 電氣 net | Rust ownership |
|---|---|---|
| 無驅動／未定 | `FLOATING` | use of moved / uninitialized value |
| 非消耗性讀取可 fan-out | `digitalRead` ×N | `&T` ×N |
| 取得驅動權 vs 讀取 | `pinMode(OUTPUT)` vs `INPUT` | `&mut` vs `&` |

**`&T` 之於 ownership，就是 `digitalRead` 之於電壓**——非消耗性的投影。這條沒被推翻，它正是「守恆＝有基質、其上是投影」在第二種 law 下的實例。

**不加第四個 `relation` 值**——那會把「兩者都是不可複製＋全網求解」這個深層相同點藏起來。

> **未解**：`exclusive` 底下其實有兩條不變式——**銷毀恰好一次**（`unique_ptr`／`shared_ptr`／Rust drop）與**同時至多一個可變存取**（`&mut`／mutex）。兩者的關係未證。
>
> 一個**賭注級**的收斂方向（來自 ArduinoCAD）：真正的不變式是「恰好一次銷毀／無 UAF／無 double-free」，而 **static borrow-check 與 dynamic refcount 是同一不變式的兩種執行**。若成立，`shared_ptr` 仍是 `exclusive`、只是動態強制。
>
> mutex 看似不合（它跟銷毀無關），但有個更好的歸宿：**Rust 的 `Mutex<T>` 是「動態產生 `&mut` 的東西」**（`lock()` 的 guard deref 成 `&mut T`）——不是第四類，是 `exclusive` 邊的動態產生器。**當方向、別當結論。**

## 第三層：角色

律**之內**還有角色，它是邊在該律內的進一步定性：

```
關係 relation    composition | conserved | information
  └ 律 law       （conserved 才有）shared | exclusive
      └ 角色 role  driver / reader   ·   &mut / &
```

`pinMode` 改的是**角色**，不是 relation（relation 固定為守恆-shared）。這正對映 Rust 的 `&mut`／`&`——`exclusive` 律內的兩個角色。

⚠️ **而 `&` 的中文俗名正是「共享借用」（shared borrow），它住在 `exclusive` 律裡面。**
兩層各有一個 shared，而它們**不是同一件事**：

```
律   shared      多方持有【同一份守恆量】，量在網上分配        ← 電氣 net
角色 & (shared)  在 exclusive 律內，非消耗性地讀同一份資源     ← 借用
```

判準是**層**：`law` 回答「這份東西能不能被多方分著持有」，
`role` 回答「在這條律內，這一端是哪一種參與者」。
記在這裡是因為**下一個人一定會問**。**「角色在律內變、律本身不變」兩域一致**，這反過來加固「relation 屬於邊、接點宣告 `accepts`」的框架。

## 這條戳破了膠囊格式的一個假設

守恆的兩種律都需要**全樹流敏感約束求解**——電氣傳播（誰在驅動、驅動到哪、有沒有衝突）與 borrow check（第 3 行的 move 殺掉第 5 行的 use）是**同一類機器**。

（**收窄**：同一類、不同終局判定——照上面那張表，`shared` 是求解器＋門檻、`exclusive` 是可滿足性檢查。共用的是**遍歷與傳播骨架**，不是判定邏輯。）

[語義診斷系統](../draft/2026-08-05-語義診斷系統.md) 的三層（節點 constraint／parent-sibling 關係／語言特有規則）**裝不下它**——第 2 層是局部結構檢查，借用檢查是流敏感的。

所以：**per-元件的膠囊裝不下全樹約束**。那是 kernel 的一條新脊椎，不是元件的第六個槽。加 Rust 之前必須先有這個位置。

兩件事跟著這條走：

- **關係律跟著「資源」走，不跟著「域」走。** 電氣 net 與機械連接結構長得一樣，因為它們是**兩個域的同一種東西**（`shared` 守恆網）。所以該共用的是**守恆求解器**，不是把電氣接腳和機械埠併成一個陣列。（**注意**：類比訊號驅動**不是**資訊——net 上的電壓當然守恆。它是基質本身，數位位階才是它的投影。這一格 ArduinoCAD 前後兩封改過分類，第二封才對。）
- **接點的儲存要加法式、域專屬。** 電氣接點帶電氣能力（2 欄）、機械接點帶運動框（9 欄），形狀不相交、也沒有消費者統一遍歷它們——硬合成判別聯集是**反壓縮**。統一發生在**接縫投影**上：接點 `{name, kind, accepts}`、邊 `{relation, law?, role?}`。

`kind`（電氣／機械／結構／資料）是**域標籤，協定不需要理解它**，照「跨域機器需不需要理解」那條判準，它是不透明酬載；`relation`／`law`／`role` 才是協定的心臟，因為它們決定連接律。加一個新域＝加一個 `kind` 值，協定不動。

> **來源與修訂**：本節是 2026-08-05 與 ArduinoCAD 五封往返協商的產物，被推翻過三次：
>
> 1. **原版**主張「三個平行埠陣列合併成一個 `ports` 帶 `kind`」＋「`children` 是 containment 型的埠」。**ArduinoCAD 推翻**：合併不相交型別是反壓縮，過不了 over-justify（**而 over-justify 不是成本測試，「不計成本」豁免不到它**）；組合不是連接，把 containment 塞進埠是類別錯誤。
> 2. **本側第二版**用單值 `relation`。**ArduinoCAD 推翻**：電氣接點同時是守恆又載資訊，單值裝不下 → 解法是「守恆＝有基質，其上的邏輯是投影」。
> 3. **本側第三版**寫「aliasing XOR mutability 就是麵包板規則」。**ArduinoCAD 推翻**：那是 DRC 慣例不是物理律（見上方警語）——而**這個更正反而救了分律**，因為它提供了兩律可證不同的實例。
>
> 本側的貢獻是：接點／埠拆兩詞、`kind`／`relation` 分家、composition 收進 `relation`、`relation` 屬於邊、`law` 二分、「永遠可滿足 vs 約束圖形狀」那條根。既有實證：Modelica 的 physical／signal connector、bond graph 的 effort／flow、Arduino API 就是 adapter 層。
>

## 🔴 三種關係各有【常見】結構，而那不是定義

根公理已經寫死了「邊」：

> 程式是由「元件節點」和「關係邊」組成的語義結構：**在檔案內是樹，在檔案間是圖，在系統間是超圖**。

所以「組裝有邊」不是新決定，是**還原根公理**——現行 `SemanticNode` 只有 `children`、沒有具名的邊，是實作欠公理的債。

但**還這筆債不等於把 `children` 改叫埠**。三種關係各有結構：

```
組合  父─┬─子   樹。擁有、獨佔、生死與共。       ← children 在這裡
資訊  源──▶讀者  有向、可 fan-out、可複製。
守恆  ●───●───●  平衡網。across 相等、through 歸零。
```

`children: Record<string, Instance[]>` 是**組合關係**。要還的債是**把資訊關係補上**（積木輸出→另一積木輸入→硬體 pin），那是一條**新增的軸**，加法式，不是把 `children` 重新詮釋成埠。

**一個要標清楚的細節**：Blockly 的 value input（`arithmetic` 的運算元）在樹裡是組合，語義上卻帶資訊流向。這不是矛盾——**運算式樹是 DAG 在「無共享」時的無損編碼**。它變成真問題只在兩種情況：同一子運算式要餵兩處（共享），或跨元件接線（積木輸出→硬體 pin）。在那之前，用組合編碼資訊流是誠實且無損的。

**檢查它不違反墓碑**：`count_loop` 還是 `count_loop`，condition／body 還是具名組合接點，**沒有任何語義意圖被降級**。Sc2／Sc3 不破，可逆性不變。通過。

> ⚠️ ArduinoCAD 的經驗「**加法式併行通道 >> 加寬共享型別**」不只是 blast radius。原文的判準是「先問這是**加法**還是**改寫**」——那是語義問題，不是成本問題（原文：「數位 HIGH/LOW 本是類比電壓的量化讀數，兩者本就分層」；程式碼註解：「機械埠是**電氣之外的語義域**」）。本檔原版用「不計成本」豁免它，**豁免錯了層**。這條教訓對地基決定同樣適用。

🔴 **⚠️ 而上面那個「三種關係各有結構」的框，2026-09-25 已被推翻**（見本檔〈結構與關係正交〉）。
它列的是**每一種關係最常見的那個結構**，不是它的定義：資訊在**網**上也成立（ROS topic）。
保留它是因為 `children` 那筆債的論證還靠它，而**讀的時候要知道那三行是例子不是分類**。

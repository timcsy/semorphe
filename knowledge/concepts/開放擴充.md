# 開放擴充（Open Extension）

系統可以在**不修改既有程式碼**的前提下加入新概念、新語言、新套件。核心引擎只有一條管線——不存在雙管線競爭或黑名單切換。

**三視角投影：**

- **原則**：P3——擴充只加不改；新 pattern 不得改變既有 pattern 的匹配結果
- **願景**：多語言（Python/Arduino）、外部套件生態、語義套件市場都靠這條原則成立
- **經驗**：「只加 JSON 不改程式碼」不等於「不影響既有行為」——搶匹配是真實發生過的事故

## 擴充點

| 擴充什麼 | 加什麼 | 改什麼既有檔案 |
|---------|-------|--------------|
| 新翻譯 | + locale JSON | 無 |
| 新風格 | + style preset | 無 |
| 新套件積木（簡單） | + block JSON（Layer 1） | 無 |
| 新套件積木（需轉換） | + block JSON + transform 註冊（Layer 2） | 無 |
| 新語言概念（複雜） | + block JSON + strategy 註冊（Layer 3） | 無 |
| 新通用概念 | + UniversalConcept type | concept-registry（加一行） |
| 新語言 | + language module | 無（plugin 式載入） |

## Pattern Engine 的多層表達能力

真正的開放擴充是：**語言模組能用自己的程式碼擴充引擎的行為，而不修改引擎本身。**

```
Layer 1: 純 JSON 聲明          — 覆蓋 ~80% 場景
Layer 2: JSON + 具名 transform — 覆蓋 ~15% 場景（純文字轉換 string → string）
Layer 3: JSON + 具名 strategy  — 覆蓋 ~5% 場景（完全控制 lift/render 邏輯）
```

```typescript
interface TransformRegistry {
  register(name: string, fn: (text: string) => string): void
}
interface LiftStrategyRegistry {
  register(name: string, fn: (node: AstNode, ctx: LiftContext) => SemanticNode | null): void
}
interface RenderStrategyRegistry {
  register(name: string, fn: (node: SemanticNode) => BlockState | null): void
}
```

**核心引擎只有一條管線**：PatternLifter / PatternRenderer 是唯一路徑。遇到 `transform` 欄位查 TransformRegistry，遇到 `liftStrategy` / `renderStrategy` 查 StrategyRegistry。

**優先使用宣告式**：19 個手寫 lifter 曾在 2026-03-11 被遷移為宣告式 JSON pattern，見 [history/009](../history/009-手寫-lifter-遷移為宣告式-pattern.md)。Layer 3 是逃生口，不是預設選項。

## astPattern 的宣告格式

```jsonc
{
  "astPattern": {
    "nodeType": "update_expression",
    "constraints": [{ "field": "$operator", "value": "++" }],
    "fieldMappings": [
      { "semantic": "name", "ast": "argument", "extract": "text" },
      { "semantic": "operator", "ast": "$operator", "extract": "text" }
    ]
  }
}
```

- `nodeType`：匹配的 tree-sitter AST 節點類型
- `constraints`：篩選條件，用來區分同類型節點（`$` 前綴 = AST 屬性而非子節點）
- `fieldMappings`：`extract: "text"` 取文字、`"lift"` 遞迴提升

**Constraint 匹配擴充**：除了精確匹配（`value: "++"`），支援前綴匹配 `{ "field": "$text", "match": "startsWith", "text": "/**" }`。真實案例：`/** doc comment */` 和 `/* block comment */` 的 tree-sitter nodeType 都是 `comment`，用 `startsWith` 區分。**Pattern 定義順序很重要**：具體的（`/**`）必須排在寬泛的（`/*`）前面。

## 歧義偵測與仲裁（註冊時強制）

開放擴充的前提是：**新增的 pattern 不能改變既有 pattern 的匹配結果。** Pattern 的 constraints 集合形成偏序關係（⊆），歧義處理取決於偏序是否可比較：

```
∀ pattern A, B ∈ Registry, A.nodeType = B.nodeType:

  情況一：偏序可比較（A.constraints ⊂ B.constraints）
    → A 更寬泛，B 更特化
    → 安全仲裁：最特化匹配（B 優先）
    → 這是 DSL 擴充的正常模式

  情況二：偏序不可比較（A ∩ B ≠ ∅ 但 A ⊄ B 且 B ⊄ A）
    → 交叉歧義，無法安全仲裁
    → 報註冊錯誤，要求合併為 hand-written lifter

  情況三：不相交（A ∩ B = ∅）
    → 無歧義，各自匹配
```

**設計原則**：偏序可比較 → 自動仲裁（低門檻）；偏序不可比較 → 強制手寫（高門檻但安全）。

**同套件 vs 跨套件**：同一 JSON 檔的 pattern 開發者有義務自洽——偏序可比較的情況應儘量避免，改為在一個 pattern 中用 constraints 區分。跨套件允許偏序特化，這是「擴充已有語言模組」的正當用途。

**空 constraints 的處理**：`constraints: []` 匹配該 nodeType 的所有節點。若該 nodeType 只有一個 pattern 是安全的；若有多個，空 constraints 自動成為最寬泛的兜底（被任何有 constraints 的 pattern 特化），這是可預測的。**但實務上仍應避免**——`c_pointer_op` 的空 constraints 曾搶走 `++i`。

**逃生口**：同一 nodeType 需要根據內容映射到不同概念（`unary_expression` 可能是 `-x`、`&x`、`*p`、`!flag`），且 constraints 交叉時，用 Layer 3 的 hand-written liftStrategy 在一個函式中處理所有分支。

## constraint-before-strategy（不變式）

**先驗證 constraint 通過，才執行 liftStrategy。** 這保證 strategy 函式只處理已經確認屬於自己的 AST 節點。

早期實作反過來——先跑 strategy，成功後才檢查 constraint——結果 `// 單行註解`（nodeType 也是 `comment`）跑進 `cpp:liftDocComment`，產出錯誤的 doc_comment。見 [history/006](../history/006-constraint-先於-strategy.md)。

## Lossless Lift 原則

Lift 應優先產出**語言特定概念**（如 `cpp_printf`），而非直接壓扁成通用概念（如 `print`）。正規化由 style exception 系統在下游**可選**執行。

```
Code → lift → cpp_printf { format: "%.2f\n", args: [x] }   ← 無損
                ↓ style exception（可選）
             print { values: [x] }                          ← 有損但使用者明確選擇
```

**判斷準則：**

- 有結構化資訊（format string、特殊語法）→ lift 為語言特定概念
- 天然映射且無資訊丟失（`cout << x` → `print`）→ 直接 lift 為通用概念
- Style exception 系統 = **正規化提議器**（「保留」= no-op，「統一」= normalize）

見 [history/004](../history/004-lift-改為無損保留語言特定概念.md)。

## DependencyResolver：語言模組的依賴推導職責

核心引擎只定義介面，每個語言模組提供自己的實作：

```typescript
interface DependencyResolver {
  resolve(conceptIds: string[]): DependencyEdge[]
}
interface DependencyEdge {
  sourceType: 'builtin' | 'stdlib' | 'external'
  directive: string      // 如 '#include <iostream>'
  packageSpec?: string   // external 時的套件規格
}
```

DependencyResolver 是 **Scope 3 的索引建構器，不屬於 generator pipeline**——它在 project() 之前獨立運行，將概念使用集合映射為依賴邊集合。新語言只需註冊自己的 resolver，無需修改核心引擎。

C++ 範例：`{cout, endl, vector}` → `[{directive: '#include <iostream>'}, {directive: '#include <vector>'}]`。

見 [history/007](../history/007-依賴推導從-generator-抽離.md)。

## 加入新語言的完整清單

**必要檔案：**

```
src/languages/{lang}/
  blocks/       basic.json / advanced.json   ← BlockSpec 定義
  generators/   statements.ts / expressions.ts / io.ts
  lifters/      statements.ts / expressions.ts
  adapter.ts                                  ← semantic↔block 雙向轉換
```

**需要修改的現有檔案**：`src/i18n/*/blocks.json`（文字 key）、`src/ui/app.ts`（需動態行為的積木）、`src/ui/panels/blockly-panel.ts`（複雜積木的 extraction case）、`src/ui/theme/category-colors.ts`（新類別顏色）、`tests/`。

**檢查清單：**

- [ ] 所有 concept 已在 registry 註冊（**第一步就做，不要最後才補**）
- [ ] 每個積木都有 code generator（template 或 hand-written，**二擇一不共存**）
- [ ] 每個需要 lifting 的 AST 節點都有對應規則
- [ ] 動態積木的 `extractBlockInner` case 已加入
- [ ] i18n 兩種語言的 key 都已加入
- [ ] toolbox category 和 level 設定正確
- [ ] `saveExtraState`/`loadExtraState` 可正確序列化還原
- [ ] 欄位名稱全鏈路一致（blockDef → extract → generate → lift → adapter）
- [ ] 測試涵蓋 template 和 hand-written 兩條路徑
- [ ] astPattern 的 constraints 足夠具體，不會搶匹配
- [ ] 每個可執行概念都註冊了 interpreter executor，宣告性概念註冊 noop

## 外部套件與依賴規則

```
packages/{name}/
  ├─ manifest.json          ← { id, language, extends, provides: { concepts, hardware } }
  ├─ semantics/concepts.json
  ├─ projections/blocks/ + code/
  └─ hardware/              ← components.json + simulation.json
```

**依賴規則**：擴充可引用基礎套件概念，**不可引用其他擴充**（避免菱形依賴）。

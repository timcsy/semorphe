# 認知鷹架（Cognitive Scaffolding）

> **積木是認知鷹架，不是替代品。**
> 目標是降低外在認知負荷，讓學習者在近側發展區內建立心智模型，並**最終過渡到文字程式碼**。

**三視角投影：**

- **原則**：Sc1-Sc4 四條鷹架原則，從 CLT + ZPD 推導
- **願景**：讓鷹架隨能力增長而退場，而非永遠依賴積木；教學路徑本身可被封裝分享
- **經驗**：原理提供方向不提供設計——積木文字和互動模式本質上是 UX 問題，只能試錯

## 理論基礎

### 認知負荷理論（Sweller 1988）

| 類型 | 定義 | 積木系統的角色 |
|------|------|--------------|
| **內在負荷** | 學習材料本身的複雜度 | 不可消除——程式邏輯就是那麼複雜 |
| **外在負荷** | 不良教學設計帶來的額外負擔 | **積木的首要任務是消除這類負荷** |
| **增生負荷** | 建立心智模型的有益負荷 | 積木應**引導**學習者投入這類負荷 |

積木消除外在負荷的方式：

```
語法記憶 → 拖拽選擇
型別錯誤 → 形狀約束
結構錯誤 → 巢狀限制
```

### 🔴 而「消除」不等於「學會」——2026-08-14 的外部證據

*Scaffolding Progress: How Structured Editors Shape Novice Errors When
Transitioning from Blocks to Text*（arXiv [2302.05708](https://arxiv.org/abs/2302.05708)，
26 個高中生，Scratch → Python）實測：

```
用結構化編輯器的期間   語法問題 4.6x 更少、型別問題 1.9x 更少   ✅ 上表成立
轉到一般文字編輯器後   🔴 語法錯誤【4x 更多】                    ← 上表沒說的那一半
```

⚠️ **型別那一格保住了，語法那一格沒有。** 也就是說上表的三行**代價不同**：

| 消除的方式 | 遷移後 |
|---|---|
| 型別錯誤 → 形狀約束 | 🟢 保住（1.9x 的優勢延續） |
| **語法記憶 → 拖拽選擇** | 🔴 **退步 4x** |

> **一個被鷹架擋掉的錯誤，如果從來沒有被學習者看見過，
> 鷹架撤掉的時候它會原封不動地回來。**

**這直接打到本檔開頭那句「最終過渡到文字程式碼」**——過渡不是自動的，
而「退場」的成本沒有被算進去。

⚠️ 而 Semorphe 的處境**與那份研究不同，也更急**：他們的學生是「先積木、後文字」，
而**我們的學生兩邊同時看得到**。所以語法錯誤在這裡不是轉場才出現的，是**每天都在**。

→ 設計後果：**擋掉一個錯誤的同時要讓它被看見**，而不是讓它安靜地不存在。
見 [history/062](../history/062-把使用者的錯歸進了我們的殘差.md)——我們曾經反過來做。

#### 🆕 而那個風險的第一個對策（2026-08-16，使用者提出）

> 逐字：「**我覺得讓學生練習看真實委派編譯器的錯誤訊息也是有幫助的，
> 因為輔助輪拿掉之後也可以適應，只是我們也輔助訊息更好**」

**上面那一節寫了兩天，而它下面一直是空的。** 這是第一個對策，
而它的形狀正好對上：**不是「不要擋」，是「擋了之後還要讓他看過真的那一句」**。

```
替換   一個代號 → 一句我們的話          🔴 學生【永遠沒看過】真的那一句
並陳   我們的話 ＋ 【編譯器的原文】       他明天在別的地方會再看到一次
```

⚠️ **而它不是「兩則訊息」**：`monaco-panel.ts:95` 記過同一族的坑
——「把殘差併進診斷，學生會看到『你的程式有 12 個錯誤』，
而其中 11 個是我們的問題」。**同一個錯誤變成兩行，第一課的學生會以為有兩個問題。**

→ 形狀是**一則兩層**，不是兩則。

##### 「一則兩層」（定義）

> **同一個節點上的一則診斷，帶兩個【來源不同】的說法：
> 上層是我們的（可翻譯、可調深淺），下層是編譯器的原文（不翻譯、不刪）。**

⚠️ **兩層不是「粗版與細版」**——它們的來源不同，所以三種情形都可能：

```
① 兩邊都說（漏分號）      我們：「這一行的語法不完整」  clang：expected ';'
② 🔴 只有 clang 說（型別）  我們【沒有上層】——除非對映代號
③ 🔴 只有我們說（殘差）     clang 根本不會提「這個寫法我還不認得」
```

**「細緻度」解釋不了 ② 和 ③。** 而下層永遠可以缺席（沒有委派時），
**上層不能**——沒有上層就退回原文，而那正是 2026-08-15 之前的狀態。

🔴 **而它給「編譯器必須跑在瀏覽器裡」一個比離線更硬的理由**：
`build-guardrail` 6.8 記過參照編譯器**環境相依**（macOS clang 與 CI gcc
對同一段程式給不同答案）。

> **教材需要「每個人看到同一句話」，而只有瀏覽器內的編譯器給得起。
> 離線是便利；這是教材【可否驗證】的前提。**

⚠️ **而「誰決定要不要看真的那一句」是未決**——見
[draft/語義診斷系統](../draft/2026-08-05-語義診斷系統.md)。

### 近側發展區（Vygotsky 1978）

```
┌─────────────────────────────────────┐
│  學習者無法獨立完成的區域             │
│  ┌──────────────────────────────┐   │
│  │  ZPD：在鷹架輔助下可完成的區域  │   │
│  │  ┌───────────────────────┐   │   │
│  │  │  學習者已能獨立完成的區域 │   │   │
│  │  └───────────────────────┘   │   │
│  └──────────────────────────────┘   │
└─────────────────────────────────────┘
```

層級切換是**控制在 ZPD 內可見的元件數量**。

## 四條鷹架原則

從 CLT + ZPD 推導出的**開放集合**（目前四條，允許追加）：

```
Sc1 鷹架可調性：同一元件在不同層級有不同的鷹架強度（對應 P4）
Sc2 鷹架可退場：積木不可引入文字程式碼中不存在的概念
Sc3 認知一致性：一個積木 = 一個語法結構，不多不少
Sc4 最小驚訝：積木行為和生成的程式碼一致
```

**Sc2 與根公理呼應**：積木是語義樹節點的視覺化，不應發明語義樹中不存在的概念。系統不能無中生有。

## 積木設計準則

```
Sc3 → 一個積木 = 一個語法結構。判定法：拿掉某個欄位後仍有意義 → 該拆成兩個積木
Sc2 → 積木概念必須在文字程式碼中有直接對應
Sc4 → 積木行為和生成的程式碼一致
Sc1 → 同一元件在不同層級提供不同程度的輔助
CLT → 每個積木最小化外在認知負荷
```

## 積木文字設計準則

- **Message**：動詞 + 身份 + 名稱，回答「對誰做什麼」。串起來讀起來像一段中文敘述。
- **Tooltip**：一句定義 + 一句場景 + 注意事項。Universal 用生活比喻；Advanced 重點放在「什麼時候用」。
- **Dropdown**：型別用 `英文術語（中文）`，運算子用 `中文（符號）`。型別清單由語言模組提供。
- **語法隔離**：積木上**不出現目標語言的語法符號**（`@`、`*/`、`<<`、`;`）。例如 doc comment 的 mutator 用「參數」和「回傳」而非 `@param` 和 `@return`。語法符號是程式碼投影的細節，不是積木投影的一部分。
- **Mutator 一致性**：mutator 彈窗中的 container / item label 遵守與主積木相同的準則。**使用者看得到的所有文字都是介面**——這條是踩過坑的：只改了主積木文字、忘了 mutator 內的 label，使用者就在齒輪彈窗裡看到 `@param`。

## 試錯留下的東西

原理否決錯誤方向，但不生出正確設計。三個真實的試錯軌跡：

**message 語序**：`"宣告 %1 型別 變數 %2"`（生硬）→ `"宣告 %1 變數 %2"`（自然但 `%1` 語義模糊）→ 最終拆成獨立 label key（`HEADER_LABEL` +TYPE dropdown+ `VAR_LABEL` +NAME field），每段都有明確語義。

**變數輸入方式**：FieldTextInput（自由輸入，初學者可能打出 `my var`、`123abc`，且看不到有哪些變數可用）→ FieldDropdown（掃描 workspace，但沒有變數時 Blockly 會拋錯）→ Dropdown + fallback 選項 `[['x','x']]`。

**I/O 參數**：V1 純 ValueInput（只能積木組合，太複雜）→ V2 純 FieldDropdown（只能選現有變數，無法輸入常數）→ V3 三模式 select/compose/custom。V3 的 UI 複雜度超出預期，但確實達成 CLT 目標：簡單情境最低負荷、複雜情境完整表達力、特殊情境最大自由度。見 [history/012](../history/012-io-參數從單一模式到三模式.md)。

## i18n 是 Locale 投影

message/tooltip 是**呈現資訊**，分離到 locale 檔案（`src/i18n/{locale}/blocks.json`）。

```
JSON blockDef：  { "message0": "%{BKY_C_INCREMENT_MSG0}" }
動態積木：       Blockly.Msg['C_INCREMENT_VAR_LABEL'] || '變數'
```

**從 JSON 改為動態積木時**，原本混在一起的 `message0`（`"把變數 %1 設成 %2"`）需拆成獨立 label key（`LABEL: "把變數"` + `SET_LABEL: "設成"`）。動態積木不使用原本的 MSG0——這是換 key 而非改 key，符合「不做向後相容」。

## 🔴 回饋有三種，而只有一種沒有別人在做（2026-08-20）

比較 TextBricks 時分出來的。起點是一個**被否定的假設**：
「Semorphe 教學上的優勢是回饋更【即時】」——**不是**。
如果關鍵是延遲，clang + LSP 早就贏了，它在你打字的當下就畫紅線。

真正把它們分開的是三軸：

| 軸 | 編譯器／LSP | 積木 |
|---|---|---|
| **層次** | 糾錯——只在你【錯】的時候說話 | **確認**——在你【對】的時候也說話 |
| **可操作性** | 唯讀，只能讀完回去改原始碼 | **R0 雙射，回饋本身可以動手** |
| **門檻** | 程式要接近合法才有用 | 容錯 ＋ `raw_code` 保底，永遠成立 |

「層次」那一軸是最反直覺的：**編譯器對正確的程式永遠沉默**，
而沉默對初學者不是「沒問題」，是「沒資訊」。

「門檻」那一軸不是延遲，是**適用範圍**：`syntaxGaps` 讓解析器指名「該有而沒有」，
學生寫到一半，系統就已經認得他寫出來的那些部分。

於是回饋不是一個東西，是三種：

| 回饋種類 | 一般 IDE | Semorphe |
|---|---|---|
| 語法 | ✅ | ✅ 一則兩層（我們的話 ＋ 編譯器原文） |
| **語義** | ❌ | 🔴 **獨有** |
| 行為 | 部分（debugger） | ✅ 時空旅行 |

> **沒有任何主流工具會告訴你「你寫的這段是什麼概念」，
> 因為對專業開發者來說那是廢話。對初學者不是。**

**而這一節是下面兩節的上位分類**：〈教育學上的紅線〉管的是語義回饋的**歸因**，
〈執行透明度也是鷹架〉是**行為回饋**那一格。

⚠️ 而 R4 的執行軌跡是唯讀的，卻極有價值——所以「可操作」是加分項，
**不是有效回饋的必要條件**。

🔴 **最後一個條件，不滿足則以上全部失效：回饋必須可歸因。**
一個歸因錯的回饋，比沒有回饋更糟。→ 見下一節。

## 教育學上的紅線

**降級原因必須視覺區分**，否則鷹架變成認知牢籠：

| 降級原因 | 視覺語義 | 說明 |
|---------|---------|------|
| 程式碼錯誤 | 紅色警告 | 語法或型別錯誤，合理的負面回饋 |
| 系統能力不足 | 中性灰色 + 「系統尚未支援此寫法」 | **不歸因於使用者** |
| 寫法非標準但正確 | 綠色邊框 + 「進階寫法」 | 鼓勵探索，不懲罰創意 |

**為什麼必須區分**：如果所有降級都用相同的灰色，學習者會隱性地將「系統不認識」解讀為「我寫錯了」，進而只寫系統能匹配 pattern 的程式碼。判定依據：能通過編譯/執行驗證但不匹配 pattern → 「非標準但正確」。

詳見 [降級與認知邊界](降級與認知邊界.md)。

## 執行透明度也是鷹架

| 模式 | 策略 | 時空旅行 | 副作用 | P4 對應 |
|------|------|---------|-------|---------|
| 全透明（教學） | interpret + 每步快照 | 無限回溯 | Virtual I/O | L0 最大鷹架 |
| 混合（進階） | hybrid + 關鍵點快照 | 回溯到關鍵點 | Virtual I/O 可選 | L1 鷹架退場中 |
| 效能（專家） | compiled + 無快照 | 不可用 | 直接作用 | L2 鷹架已退場 |

**混合執行和 P4 一致——你想看多深就看多深**：`main()` 逐步看、`my_sort()` 展開看自己寫的、`std::sort()` 只看結果。

## 🔴 三輪車不是輔助輪（2026-09-03）

使用者逐字：「我會想要用 Arduino IDE 的原因是我希望這成為學生的**輔助輪**，
最終是可以看懂程式碼的」。

這句話把一個一直分散在各處的判準說清楚了：

```
輔助輪   裝在【同一台腳踏車】上 → 拆掉之後，車還是那台車
三輪車   是【另一台車】        → 你不是拆掉它，你是換車
```

而市面上 Arduino ＋ 積木的工具幾乎都是三輪車（另一個網站、另一個桌面程式、
或一個開獨立視窗的外掛）。學生在那裡學會了，「畢業」的意思是**面對一個他從來
沒見過的視窗**——不同的選單、不同的錯誤訊息、不同的燒錄按鈕。
**那一天他失去的不只是積木，是整個環境。**

而在他真的會用的那個 IDE 裡，拆輪子是**關掉一個分頁**：檔案、板子、序列埠監控、
他按了三個月的那顆 ✓——一個都沒有動。

> **輔助輪的價值不在它扶著你的時候，在它拆掉的那一刻你還在同一台車上。**

### 三個決定，其實是同一個理由

這條判準一次解釋了三件過去各自有理由的事：

| 決定 | 過去的理由 | 而真正的理由是同一個 |
|---|---|---|
| **擴充住在 IDE 裡**，不是另一個 app | 「與宿主一致」 | 拆輪子時環境不能變 |
| **否決桌面版** | 「編譯燒錄我們不想接管」 | 桌面版就是三輪車 |
| **積木不得比程式碼強** | P1：積木是投影 | 只有積木做得到的能力＝**焊死的輪子** |

🔴 **第三列值得單獨記**：如果出現一顆「沒有對應語法」的魔法積木，學生只要用了它
就回不到純程式碼。所以**任何能力都要先在程式碼裡成立**。
🟢 而這條**已經有護欄在守**——來回一致性（`積木 → 程式碼 → 積木` 逐字相同）
在構造上就排除了「只存在於積木的能力」。
> **為了「唯一真實，各式投影」立的護欄，同時是在守「輔助輪拆得掉」。**

### 輔助輪的終點不是消失，是「需要時才放下來」

⚠️ 「最終過渡到文字程式碼」不等於「有一天積木就不見了」。終點的形狀是：
**程式碼為主，而積木是他卡住時才打開的那個分頁**。

🟢 這與「主控台可以關，而它一定叫得回來」是**同一個形狀**
（[history/202](../history/202-十字退場而主控台回到它本來的位置.md)）——
一個東西能不能退場，看的是它**回得來嗎**，不是它在不在。

### 而「看得懂程式碼」是量得到的

系統本來就知道每一次編輯**來自哪一個投影**（同步那一側必須判斷來源）。
所以可以在本機算出一句話：「這一課你改了 8 次——積木 2 次、程式碼 6 次」。

> **一個輔助輪最誠實的成效指標，不是「他學會了幾個語法」，
> 是「他這一課有多少次是直接改程式碼的」。**

⚠️ **只留在本機、只給學生與老師看**——送出去就破了〈離線可用〉那條硬性零，
而且那個數字的價值在於它是**給他自己看的進度**，不是給我們看的數據。

### ① 誰決定「現在看哪一種表徵」——研究說：系統給預設，而不准鎖

學習者控制的整合分析（Karich 等 · Granger & Levine）：

> 效果「**既不強也不一致**」；高先備知識者受益，
> 而**準備不足的學習者常被過多選擇淹沒**。
> 而關鍵的那一句：**「sequence control is the only type that generally does not harm」**。

🟢 這給了一個乾淨的形狀，而**它與 `scaffold` 今天的形狀一模一樣**：

```
系統給預設   課程說這一段適合哪一種看法
學生可以改   順序與版面的控制權——那一種不會傷
🔴 不准鎖住
```

> **版面只能是【建議】，不能是【閘門】——而那不是客氣，是研究說的。**

⚠️ 它同時解釋了一件我們原本只憑直覺的事：
[[漸進揭露]] 的修訂條①說「過濾機制要附帶條件從哪來」，
而這條研究說出了**為什麼那個來源不能是學生自己**——他正是先備知識最低的那一個。

### ② 語意波：換一種表徵的【理由】與【形狀】

Maton 的 LCT「語意波」——**已被英國 NCCE 列為十條教學原則之一**：

> 有效的課會**下沉（unpack）再上浮（repack）**：把抽象概念拆到具體，再收回抽象。
> **平的語意曲線（一直抽象，或一直具體）教學效果差。**

🟢 而 Semorphe 的三種投影**天生就是一條語意軸**：

```
程式碼       抽象、語意密度高
積木         中間——結構看得見
流程／執行    具體——它在跑什麼看得見
```

> **「什麼時候換一種看法」有了一個可檢查的判準：這一課有沒有下沉再上浮？**

⚠️ 而它對「積木為主」那種課是一句警告：**一直待在積木也是平的**。
這與下面「三輪車不是輔助輪」是同一件事的兩個面向
——三輪車不會自己變成腳踏車，而**平的語意曲線也不會自己浮上來**。

#### 🟢 而它現在是一條**可機械檢查**的判準（2026-09-05 落地）

`core/semantic-wave.ts` 把五種看法定成一根抽象度尺，於是「有沒有下沉再上浮」
變成一個函式：

```
code 3 · compare/three 2 · blocks 1 · flow 0
waveOf(views) → { descends, ascends, isWave }
```

🔴 **上升只有在下降之後才算數**——這一行是整支函式最重要的一行。
少了它，一課從頭到尾往上爬（`flow → blocks → code`）也會被判成波，
而那正是「**從來沒有解包過**」：NCCE 的十條原則裡列為最常見的失誤是
**只解包不重打包**，而它的鏡像（從沒解包）同樣是平的。

> **「先下再上」不是兩個獨立的條件，是一個有順序的條件。
> 而一個沒有順序的檢查，會把最該擋的那一種放過去。**

護欄 `audit-lesson-wave` 因此驗的是**條件式**而不是計數式：
「宣告了 `view` 的課必須是一條波」，不是「前 5 課都要有 view」
——前者驗得了第 6 課，後者在第 6 課寫進來的那天不會出聲。

⚠️ 而**不是每一課都波得動**：頂層只有一句話的課（01、04）打散不了、
也沒有第二個看法可換。那幾課不宣告，護欄也不追。

### ③ ⚠️ 而並排顯示只做到【對映】，做不到【轉換】

blocks→text 的系統性回顧：

> 「直接翻譯的工具把積木與程式碼並排顯示——對【**對映**】有幫助，
> 而它們往往**沒有處理**從拖拉到【**打字與除錯**】的概念轉變。」

🔴 這是對「對照視圖」最直接的一句提醒：它是必要的，而**它不充分**。
拆輪子那一段（[[拆輪子的曲線]]）要包含**打字**與**除錯**，
不只是「把哪一格放大」。

### ④ 🟢 而「完成題」有名字，也有數字：Parsons 題

Ericson 等人：

> **把打散的程式碼排回去，學習成效與「自己寫程式」相同，而只花 70% 的時間。**
> Adaptive／Faded 變體再降低挫折感。

而在這個專案裡它幾乎是免費的——**積木本來就會卡榫、會拒絕接錯**，
而那些研究全部在用「文字行卡片」。

> **一個為了教學而發明的載體（打散的卡片），
> 在這裡本來就是產品的主體。**

### ⑤ PRIMM：學生要先【講】程式碼，才寫得出程式碼

Sentance, Waite & Kallia（2019），*Computer Science Education* 29(2-3)。
🟢 與語意波同一個 NCCE 圈子，而它的理論根是 Vygotsky 而不是 Maton。

五個階段逐字：

> **Predict** Students discuss a program and predict what it might do, drawing or
> writing out what they think will be the output. …
> **Run** Students run the program so that they can test their prediction and discuss in class …
> **Investigate** … tracing, explaining, annotating, debugging, but with the scaffolding
> provided by an existing solution …
> **Modify** Students edit the program to change its functionality via a sequence of
> increasingly more challenging exercises; the transfer of ownership moves from the code
> being "not mine" to "partly mine" …
> **Make** Students design a new program that uses the same structures but that solves
> a new problem (i.e. has a new function)

🔴 **Predict 是【兩人一組】的，不是一個人猜**：

> At the beginning of a PRIMM lesson, students are given a short program on the board,
> or on paper, **to look at in pairs**.
> …
> Discussion of the question should ideally take place **in pairs or groups**.

⚠️ 而它的理由不是「合作學習比較好」，是**語言本身就是理解的媒介**：

> "Thought is not merely expressed in words, **it comes into existence through them**"
> （Vygotsky, 1962, p. 125，PRIMM 論文 §3.3 引）

證據：13 所學校、493 名實驗組學生（對照組 180）、11 至 14 歲。

> our research has shown that classes using PRIMM for **10 or more lessons** do
> significantly better in a post-test than those in a control group.
> （後測 Mann-Whitney：`Z=-3.392, p<.05, r=.13`）

⚠️ **效果量很小（r=.13）**——它是「有，而且站得住」，不是「很大」。

🔴 而**這篇論文自己點名了一個落差，而我們正落在那裡**：

> Six teachers alluded to a **'modify ceiling'**, indicating for a variety of reasons
> that some learners **did not get beyond the modify part of the lesson**.

量測（2026-09-12，掃 `lessons/*/*/lesson.json`）：

```
66 課 136 題
  66 題  「跟著做」   —— 每一課的第一題，一課一題，無例外
  67 題  「練習：…」  —— 絕大多數是改一個地方
   3 題  「排回去」
題型宣告：arrange 4 · debug 1 · 其餘 131 題未宣告
```

PRIMM 建立在 Use-Modify-Create（Lee 等人 2011）上，
而**這個 repo 有 Use，有 Modify，Create 那一階整個不存在**。

> **一堂課如果停在「改一個地方」，學生帶走的是那個地方，不是那個概念。**

⚠️ 而 `predict` 這一格**已經在產品裡了**（`core/predict.ts`）——⚠️ 而它今天是一個人猜
（查證：那個檔裡「討論／同學／兩人」出現 0 次）。
差的是「跟旁邊那個人講」，而那一步才是 PRIMM 的重點。

### ⑥ 同儕討論有效，而且它不是抄答案

Smith, Wood, Adams, Wieman, Knight, Guild & Su（2009），*Science* 323(5910), 122-124。

設計的關鍵在**第三題**：同一個概念、不同包裝的「同構題」，而且**單獨作答**。

> In class, students were first asked to answer one question of the pair individually (Q1).
> Then they were invited to discuss the question with their neighbors and revote on the
> same question (Q1ad for "Q1 after discussion"). Finally, students were asked to answer
> the second isomorphic question, **again individually** (Q2). **Neither the answers … nor
> the histograms of student answers were revealed until after the voting on Q2**.

🔴 **那個「都不揭曉」是整個設計的支點**：不擋住答案，Q2 就只是在量「他記不記得剛才那個字母」。

結果逐字：

> of the students who answered Q1 incorrectly and Q1ad correctly, **77% answered Q2 correctly**.
>
> … students who answered **both Q1 and Q1ad incorrectly** still appeared to learn …
> Of these students, **44% answered Q2 correctly**, significantly better than expected
> from random guessing.
>
> Our results suggest that peer discussion can be effective for understanding difficult
> concepts **even when no one in the group initially knows the correct answer**.

> **討論的價值不是「旁邊那個人知道答案」——兩個都不知道的那一對，也會變好。**

⚠️ 樣本 350 人，一門大學遺傳學。**不是程式課**，搬過來要打折。
🟢 而 CS 這邊有自己的複製研究（Porter 等人，SIGCSE 2013，"Halving fail rates
using peer instruction"）——⚠️ **那一篇這一輪沒有讀**，要引用之前先抓全文。

⚠️ 那條「第一次正確率三成五到七成才吵得起來」的操作準則，**不在這篇論文裡**
（我查證過，Smith 2009 與 PMC 的評論都沒有這句）。它是實務圈的口訣，
**不要當成研究結論引用**。這篇有的是另一件相關的事：題目越難，討論的增益越大。

### ⑦ 先失敗再教（Productive Failure）——而「好題目」有一張清單

> ⚠️ **名字先講清楚，不要用縮寫。**
> 原文叫 *Productive Failure*，直譯是「有生產力的失敗」，而那個中文一樣難懂。
> 它講的事情很簡單：**先讓學生在還沒教的概念上亂試一輪，試不出來，然後才教**。
> 下面一律叫它**「先失敗再教」**。⚠️ 引號裡的原文保留 `PF`，那是人家的字。

Kapur 與 Roll 的實務摘要（BOLD），轉述 Sinha & Kapur（2021）的統合分析。

> Productive Failure (PF) is a learning design that affords students opportunities to
> **generate representations and solutions to a novel problem that targets a concept they
> have not yet learned**, which is followed by **consolidation and knowledge assembly**,
> where they receive instruction on the targeted concept.

數字（轉引，未讀本體）：

> … more than 12,000 participants in **166 experimental comparisons** … Cohen's
> **d = 0.36** [95% CI 0.20, 0.51] … The higher the **fidelity to the design principles**
> of PF, the stronger the effect (with Cohen's **d up to 0.58**).

🔴 **而這一段才是使用者真正要的東西**——它是一張「怎樣才算好題目」的清單，逐字：

> a. **Contrasts.** Tasks should include contrasts that can be intuitively, and even better
>    if perceptually, evaluated. … learners should be able to evaluate their own generated methods.
> b. **Variant-invariant relations.** Varying certain features of the task and keeping others
>    invariant affords students the opportunities to focus on the critical features.
> c. **Affective draw.** … the tasks should be engaging.
> d. **Room for baby steps.** Correct solutions should not require insights.
> e. **Invite multiple solutions and representations.** … tasks should invite a variety of
>    solutions or representations.
> f. **Low computational load.** Students should focus on designing ideas … rather than on
>    calculating or applying solutions.
> g. **Be problem oriented.**
> h. **Working alone or together.** … the evidence shows that PF is effective in both configurations.

⚠️ **(b) 就是變異理論**（Marton）：只變一個維度，其餘固定。
使用者自己那條「印 1~10 → 1~20 的奇數 → 前 10 個奇數」的階梯，
是憑直覺做對了這一條。

⚠️ **(h) 推翻了一個想當然耳**：**先失敗再教不要求分組**。討論是加分，不是前提。

🔴 而它也說了**什麼時候不要用**：

> compared to DI, PF is **not more effective for procedural fluency** …
>
> **Do not use PF in every lesson.** Instead, target **3-5 key concepts and big ideas**
> over the course of a semester.

> **一個對三五個大概念有效的設計，套在每一課上會把它自己稀釋掉。**

🟢 而它對「課堂文化」的那一句，剛好對上這個 repo 立過的規矩
（「一個永遠說對的勾會讓所有的勾都貶值」）：

> The guiding principle is that **every answer that can be explained is a good answer**.

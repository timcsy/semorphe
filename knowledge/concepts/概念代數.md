# 概念代數（Concept Algebra）

概念不是散落的集合，而是**有結構的代數系統**：可分層、可組合、可映射。這個結構是所有正確性檢查的依據——沒有它，「新增一個積木」就沒有可驗證的完成標準。

**三視角投影：**

- **原則**：P2——每個概念在 ConceptRegistry 有唯一條目，且路徑完備（0 容忍）
- **願景**：跨語言轉換、語義套件市場都建立在抽象概念映射之上
- **經驗**：完備性靠記憶力不可靠，靜默的 coverage gap 能存活很久

## 概念分層

概念分層是一個**開放有序集**，越後面越專門：

```
Layer 0: Universal      — 所有語言共有（variable, loop, if, function, print）
Layer 1: Lang-Core      — 語言核心語法（pointer, template, decorator）
Layer 2: Lang-Library   — 標準/外部函式庫（vector, printf, numpy）
...                     — 框架允許追加
```

每一層嚴格依賴上一層，**不能反向依賴**。新增概念層時只需在有序集末端追加，不影響既有層。

## 完備性：從四路到五層

```
∀ concept ∈ ConceptRegistry:
  ① ∃ lift path     (AST → concept)        — 可辨識
  ② ∃ render path   (concept → Block)      — 可顯示
  ③ ∃ extract path  (Block → concept)      — 可還原
  ④ ∃ generate path (concept → Code)       — 可生成
  ⑤ ∃ execute path  (concept → Behavior)   — 可執行
```

①-④ 是**編輯管線**的完備性，roundtrip 由四條路徑組合驗證（①→②→③→④→① ≡ identity）。⑤ 是**執行管線**的完備性——直譯器直接走訪語義樹執行，每個可執行概念需要註冊 executor。

**分類：**

- **可執行概念**（`arithmetic`、`if`、`while_loop`、`cpp:math_pow`）→ 需要 executor
- **宣告性概念**（`cpp_include`、`cpp_using_namespace`、`comment`）→ 需要 **noop executor**
- **未知概念** → 通知使用者決定跳過或中止，**不可靜默跳過**

宣告性概念也要註冊 noop，才能區分「已知不執行」和「未知」。這條規則是 cmath 事故的直接產物，見 [history/011](../history/011-四路完備性擴充為五層.md)。

**ConceptRegistry 的彙整來源**：BlockSpec JSON 的 `concept.conceptId`、`lift-patterns.json`、liftStrategy 註冊、renderStrategy 註冊。

**判定法**：靜態分析腳本收集所有概念 ID，對每個 ID 檢查五條路徑是否存在。缺任一條 = coverage gap = 架構缺陷。

## 概念映射與降級

每個具體概念**必須**聲明映射到哪個抽象概念：

```
D1: 有具體積木       → 用具體積木（如 cpp:vector_push_back）
D2: 有抽象概念       → 用通用積木表示（如 func_call）
D3: 連抽象概念都沒有 → raw_code 降級
D4: 標記為不支援     → 保留在模型中不丟失
```

**概念的生命週期**（套件安裝/移除時的狀態機）：

```
階段 0: 不認識          → raw_code 降級
階段 1: 認識但無積木     → 通用 func_call 降級
階段 2: 有專屬積木       → 完全支援
階段 3: 有 abstract 映射 → 可跨語言轉換
```

## 語義阻抗（Semantic Impedance）

跨語言轉換從映射自然推導，但存在阻抗：

```
阻抗-1 — 結構等價（可自動映射）：控制流、基本運算、函式定義
阻抗-2 — 語義近似（需要適配）：容器操作、I/O、字串處理
阻抗-3 — 無法映射（降級）：語言特有概念（C++ template、Python decorator）
```

**三個層次：**

```
節點級阻抗（可標記、可近似）：
  push_back vs push — 回傳值、副作用差異
  → semanticContract 可偵測，標記 semantic_gap + 生成 TODO 註解

拓撲級阻抗（無法節點級映射，需要重構子圖）：
  C++ RAII → Python 中沒有「所有權」這個結構維度
  Go goroutine + channel → C++ 中沒有對等的結構模式

  結構等價的三個判定層次：
  (a) 節點等價：f(x) ↔ f(x)              → 自動映射
  (b) 子樹等價：if-else chain ↔ match     → 局部重寫，pattern-based
  (c) 拓撲等價：RAII ↔ with+try-finally   → 依賴圖重著色，不可局部化

  (c) 的核心困難：隱式語義→顯式語義的轉換需要型別語義
  （哪些物件持有資源），這超出語法樹的範圍。

  正確行為：(a)(b) 自動映射；(c) 呈現選項由使用者決定，不自動選擇；
           無對等 → 降級 + 差異報告

語言模型級阻抗（超出形式化範圍）：
  記憶體模型（手動 vs GC）、併發模型（goroutine vs pthread）
  → constraints 欄位記錄，但無法自動處理，走降級 + 「需人工調整」
```

抽象概念攜帶 `semanticContract`（effect / returnSemantics / chainable）和 `constraints`（may_reallocate / invalidates_iterators / worst_case / thread_safe / throws）。跨語言映射時自動偵測差異並標記 `semantic_gap`。L0-L1 教學場景不需要知道差異，但 **L2 高階使用者必須能看到**。

**對 Scope 3 的影響**：涉及語言特有結構模式時，Scope 3 退化為「顯示差異報告」而非「自動轉換」——這是正確的退化。

## 概念命名空間

```
概念的完整 ID = language:package:concept

衝突解決：
  階段 1 — Pattern Match（必要條件）：function name + arg count → 候選清單
  階段 2 — Context Disambiguation：#include / prefix → 精確匹配
  無法精確匹配 → confidence: 'inferred'（不降級為 generic_call）
```

## 概念組合

```
複雜概念 = 簡單概念的組合
組合保持語義：meaning(A + B) = meaning(A) + meaning(B)
```

**判定法**：如果一個積木拿掉某個欄位後仍然有意義，那它應該拆成兩個積木。

## 概念角色的語境依賴

角色（statement / expression）**不是固有屬性，而是語法語境決定的**：

```
cin >> a >> n >> m;         ← statement（獨立語句）
if (cin >> a >> n >> m)     ← expression（條件）
x = y = 5;                  ← 右側 y = 5 是 expression，整行是 statement
```

**原則**：概念定義一個**主要角色**（`ConceptDef.role`），投影層負責語境切換：

```
Statement → Expression 語境時：
  ① 移除 indent 和語句結尾（分號、換行）
  ② 視覺投影切換為 expression 版積木（output 連接器取代 prev/next）
  ③ 語義不變——同一棵子樹，不同投影
```

**實作約束（硬契約）**：同一概念的 statement / expression 兩版本的 `saveExtraState` / `loadExtraState` 格式**必須完全相同**，因為投影層在語境切換時**直接搬移 extraState**。違反不會在編譯期報錯，只在特定語境才暴露——見 [episodes/2026-03-12](../episodes/2026-03-12-cin-變數名靜默降級.md)。

## 屬性的結構化邊界

```
判定準則：如果一個屬性值在管線中需要被拆分或解析，它就不該是字串。

字串適用：值只被完整傳遞或顯示（name: "main"、operator: "++"）
結構適用：值包含多個語義子部分（type+name、format+args）
```

**反例**：`params: ["long long x", "int y"]` 把型別和名稱壓扁成字串，renderer 必須反向解析——`split(/\s+/)[0]` 把 `long long` 截斷成 `long`。正確做法是 `params: [{ type: "long long", name: "x" }]`。

**推論**：C/C++ 型別系統本身有結構（修飾符 + 基礎型別 + 指標/引用），應視為語義子結構而非原子字串。這在支援 `auto`、模板參數（`vector<int>`）、多維陣列時會成為必要條件。

| 屬性 | 被壓成字串的東西 | 症狀 |
|---|---|---|
| `array_declare.name = "a[2]"` | **維度** | 執行時變數就叫 `a[2]`，`a[1][2]` 說「a 未宣告」 |
| `var_swap.a = "a[j]"` | **一個 lvalue** | 「a[j] 未宣告」——**看起來像使用者打錯字** |
| `constructor.init_list = "v(x)"` | **一串賦值** | 執行那一路從未讀它：**投影對、執行錯** |

🔴 **三個都是「產出的碼完全正確，而執行是錯的」**——來回轉換比對永遠是綠的，
因為那個字串**原樣印出去就對了**。

> **一個屬性如果原樣印出去就是正確的程式碼，
> 那它在投影那一路不會出事——出事的是所有需要理解它的地方。**

⚠️ 而修法都要動積木形態（欄位 → 接點）。那一度被判為「該走 spec、要存檔遷移」，

**動的是投影，不是語義詞彙**（P8 的範圍見 [history/026](../history/026-P8-的範圍不含語義詞彙本身.md)）。

## SemanticNode 的標準形式

```typescript
interface SemanticNode {
  id: string                                 // 穩定識別符（語義 diff 與版本控制用）
  concept: ConceptType                       // 來自 ConceptRegistry
  properties: Record<string, PropertyValue>
  children: Record<string, SemanticNode[]>   // ← 一律陣列，不接受聯合型別
  annotations?: Annotation[]
  rawText?: string                           // 降級時保留的原始文字
  confidence?: 'high' | 'warning' | 'inferred'
              | 'user_confirmed' | 'llm_suggested' | 'raw_code'
  degradationCause?: 'syntax_error' | 'unsupported' | 'nonstandard_but_valid'
  taint?: TaintInfo
  metadata?: Record<string, unknown>         // 呈現資訊、語法偏好等
}
```

**語義結構核心（Semantic Kernel）** = 這個介面 + ConceptRegistry。所有投影、執行、擴充機制都是外掛——核心只定義節點、概念、和結構操作（traverse、query、filter、diff、merge、validate）。

`children` 一律是陣列，**不接受 `SemanticNode | SemanticNode[]`**——這條是踩過坑換來的，見 [history/001](../history/001-兩套-semanticnode-型別統一.md)。

## 🔴 「X 不是身分，是參數」——一條反覆出現的裁決

「屬性的結構化邊界」問的是**一個屬性該不該升格成接點**。
而它有一個更常見的**反方向**：**一個看起來像新身分的東西，其實是既有身分的一個參數。**

2026-08-07 到 08-18 之間出現了**四次**，每次都讓概念數往下掉：

```
位置不是身分，是形態     statement／expression 的雙版本 → 一個身分 ＋ form 軸
                        （元件 182 → 175）
零件不是身分，是參數     LED／按鈕／蜂鳴器…六個零件 → 一顆接線積木 ＋ device 下拉
                        （六顆 → 兩顆）
量什麼不是身分，是參數    readHumidity／readTemperature → 一顆 ＋ quantity
                        status／localIP → 一顆 ＋ quantity（22 顆 → 19 顆）
形式不是身分，是參數     const int／#define／裸 int → 一顆 ＋ style
                        LiquidCrystal／_I2C → 一顆 ＋ decl_type
```

### 判準：**問「它們的形狀一不一樣」，不是「它們像不像」**

```
🟢 是參數    引數個數相同、接點相同、角色相同——差別只有【一個值】
🔴 是身分    引數個數不同、或語義上做的事不同
```

⚠️ 反例（**它們真的是兩顆**）：
`ledcAttach(pin,freq,res)` 與 `ledcAttachPin(pin,ch)`——引數個數與語義都不同。

### 🔴 而第三次是**命名護欄逼出來的**

第 2 批第一版用了七個新操作詞（`humidity`／`temperature`／`state`／`address`…），
而詞彙表的硬性零全數擋下。**找不到既有詞的時候，問題常常不是詞不夠。**

> **一個逼你用既有詞彙的限制，會在你找不到詞的時候問你：
> 是這個詞不夠，還是這顆概念不該存在？**

見 [history/032](../history/032-G命名整理-詞彙表就是護欄的輸入.md) 的後續段。

### ⚠️ 而參數化有一個**硬條件**

那個差別如果**在程式碼裡是真的**，參數就**必須被帶著**——否則 round-trip
會改掉使用者的檔案：

```
style        不帶 → 學生的 `#define` 被改寫成 `const int`
decl_type    不帶 → `LiquidCrystal_I2C` 被改寫成 `LiquidCrystal`
                    🔴 而那支程式【再也編不過】（建構參數完全不同）
```

> **一個不記得原文形式的 round-trip，
> 會在使用者沒有要求的時候改掉他的檔案。**

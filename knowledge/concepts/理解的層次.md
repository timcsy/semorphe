# 理解的層次——元素 · 關係 · 空間 · 狀態

> **剪枝力**：它回答一個問題——**這個系統該有哪些視圖，以及它們的順序**。
> 答案是「四層，而它們是有序的」，而不是「想到什麼就加一格」。
> 它同時說得出**它不管什麼**（見最後一節）。

> 來源：使用者 2026-08-24。討論版面時，我把手機分頁的順序
> 「程式碼、流程、積木、主控台」讀成重要性排序，被當場更正：
>
> 「這個順序是我用**「元素、關係、空間、動力」**來思考，**代表理解的不同層次**
> （靈感從 Transformer 裡面運算的順序而來），**不是誰比較重要**。」
>
> 同日第四個字收斂為**「狀態」**（使用者：「好像更好」）。

## 四層

| 層次 | 在問什麼 | 軟體域 | 硬體域（預測） | Transformer |
|---|---|---|---|---|
| **元素** | 有哪些東西 | 程式碼 | 零件清單 | token／嵌入 |
| **關係** | 誰跟誰有關 | 流程（節點圖） | **2D 接線圖** | attention |
| **空間** | 它們怎麼被擺在一起 | 積木 | **3D 組裝** | 表示空間 |
| **狀態** | 現在裡面裝了什麼 | 主控台 · 變數 · 圖解 | 模擬 · 真板子回報 | 那一層之後的殘差流 |

## 🎯 它做得出一個預測，而那個預測是**獨立地**被觀察到的

使用者在**另一場**討論裡（`draft/面板協定的三個頻道 §九`）提過：
「流程圖很像是硬體那邊的 **2D 接線視圖**，積木很像硬體那邊的 **3D 組裝視圖**」。

用這個透鏡看，那個對應**直接掉出來**——關係層對關係層、空間層對空間層。

> **兩個獨立提出的直覺互相推導得出來，那通常表示底下有一個真的結構。**

**剪枝**：2D 接線與 3D 組裝進來時，它們是**填進既有的層**，
不是加兩個新的面板類型。而「為什麼結構投影剛好是三個」也有答案了
——**三個，因為理解有三層**。

## 它與 [投影](投影.md) 的三個對象是什麼關係

`投影.md` 把投影分成【結構】【狀態】【能力】三個對象。這個透鏡**細分了第一個**：

```
元素 · 關係 · 空間   →  【結構】的三層
狀態                 →  【狀態】
```

⚠️ **第四個字用「狀態」而不是「動力」是刻意的**：那個詞已經存在。

> **一個新詞如果指的是既有詞已經指到的東西，它不是更精確，它是分裂。**

## 🔴 它不管什麼：【能力】

```
四層      在理解【這一個程式】
【能力】  在回答【這個系統有什麼】（工具箱 · 圖鑑）
```

工具箱與圖鑑**不在這四層裡**，而那不是遺漏——它們投影的是**元件登錄表**，不是某一個程式。

### ⚠️ 而「不管它」**不等於「知道它該去哪」**

這一條是踩出來的（2026-08-24）：我從「工具箱不在四層裡」推出「所以它住側邊欄」，
被使用者兩次更正——先是**寬度**（VSCode 側邊欄不夠大），再是**實測**
（「獨立面板的拖曳效果超爛，後來就放棄獨立面板了」）。

> **一個透鏡說得出它不管什麼，是它的優點；
> 而拿它去決定它不管的那些東西，是誤用。**

版面那一半的判準是另一條（**使用的姿勢**：取用要相鄰、認識要面積），
記在 [draft/版面與檔案 §六之二](../draft/2026-08-24-版面與檔案.md)。

## 三個投影

| | |
|---|---|
| **規範** | 加一個視圖之前先問「它在哪一層」。答不出來 → 它可能不是這四層的東西（例如工具箱），該用別的判準安置 |
| **情境** | 手機分頁的順序、桌機佈局預設、硬體視圖進來時的歸位，都由這一層決定；而它們不必各自吵一次 |
| **存在** | 它解釋了一個既有的困惑：「積木是入門、程式碼是進階」那個直覺**是錯的**——它們不是難度的兩端，是理解的兩層（空間 vs 元素） |

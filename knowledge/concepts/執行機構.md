# 執行機構（Enforcement）

**一條規範沒有機械化的檢查，它本身就是殼——而殼看起來像完成。**

這兩句是同一件事的兩面：**宣稱存在、檢查不存在**。原則、版本欄位、空 stub、被歸檔的缺陷，全是同一個形狀——它們都通過了「看一眼」，因為看一眼檢查的是**存在**，不是**作用**。

**三視角投影：**

- **原則**：P2「0 容忍」與 P9「四項獨立性」都是規範，兩條都**沒有任何測試在檢查**
- **願景**：每個階段的成功標準都寫「所有測試通過」，但沒有東西檢查**完備性**——通過的是已經寫出來的測試，不是該有的測試
- **經驗**：殼的六種樣態、64 個被歸檔的缺陷、`version` 欄位、`src/` 裡零個 TODO

## 同一個形狀出現五次（2026-08-05 實測）

| 宣稱 | 檢查 | 後果 |
|---|---|---|
| P2「缺任一條路徑 = 架構缺陷（**0 容忍**）」 | **無** | 15/17 個 `std/*/lifters.ts` 是空 stub，沒人發現 |
| P9「拔掉 C++…**無 `languages/cpp/` import**」 | **無** | 12 個 kernel／app 檔硬編 C++ conceptId |
| P3「歧義**在註冊時仲裁，不在執行時碰運氣**」 | **無** | 「哪個語法走哪套，由註冊順序決優先權」 |
| 「**零 todo 為目標**」（已寫進四支 skill） | **無** | 64 個 `it.todo` |
| `storage.ts` 的 `version: 1` | **只檢查存在，不檢查值** | 改格式時舊存檔會被當成相容的載進來 |

**五次都不是疏忽，是同一個結構性缺口。** 而最後一列是最乾淨的標本——`version` 欄位存在、名字對、看起來就是版本控制，**但沒有任何東西 branch on 它**。

> **後續（2026-08-06）**：**五列全部補完**。P2／P9／零 todo 見 `specs/049-audit-guardrails`，P3 見 `specs/051-lift-claim-arbitration`，`version` 見 `specs/052-storage-integrity-gate`。
>
> 最後一列補的時候還多挖出三個：自動載入那條路徑（每次開頁面都跑）**連 `version` 存在都不檢查**，`{hello:'world'}` 會被原樣當成存檔回傳；而 `blockStyleId` 與 `locale` **每次存檔都被無聲丟掉**——使用者的積木外觀與介面語言從來沒有被保存過。**去量那一列的時候，才發現它旁邊還躺著三個。**

## 為什麼「看一眼」永遠抓不到

因為殼的定義就是「**存在但不作用**」，而看一眼檢查的是存在。

需要的檢查隨病加深而升級：

| 病 | 症狀 | 檢查形式 |
|---|---|---|
| **碎裂** | 東西散在太多地方 | **靜態計數** —— 數它出現在幾個檔 |
| **殼** | 東西在該在的地方，但是空的 | **執行式** —— 跑一次，看它吐什麼 |
| **條件性正確** | 在、不空，**單獨測都過，組合才壞** | **組合式** —— 隨機生成真實程式（fuzz） |

**每一階都抓不到下一階。** 靜態計數會把空 stub 算成覆蓋；執行式的最小樣本，就是那個會過的 case。

## 兩條可操作的判準

### 一、沉默的正確和沉默的缺失撞在一起時，讓正確的那個說話

有些「空」是對的（`cpp_include` 這種宣告性概念本來就不執行），有些是缺。**兩者長得一模一樣**，所以偵測不了。

解法不是更聰明的偵測，是把**推斷**改成**宣告**：

```
execute: "noop"        ← 顯式宣告：這個概念本來就不執行
（缺這個欄位）          ← 缺失
```

缺失於是自動變成可偵測的。

> **這條判準在 2026-08-06 第一次真的被落實**（`specs/053-declare-noop-execute`）。而落實的過程本身推翻了一個直覺：
>
> 核心直譯器有一份寫死的 34 個「無執行行為」概念清單。原本以為工作是「把 34 個改成宣告」——**實測只有 12 個配得上**。其餘 14 個跑起來結果是錯的（十個是物件導向，直譯器不支援它），5 個根本測不到，3 個是死條目。
>
> **「把 34 個都宣告掉」會讓兩條護欄的數字同時下降，而系統一點都沒變。** 那不是落實這條判準，是拿這條判準當藉口——**把缺陷洗成設計，然後讓護欄替它背書**。
>
> 所以宣告需要門檻：理由只有兩個值（`declarative`／`consumed-by-parent`）且**不得增加**——第三個值就是在替「還沒做」找一個體面的名字。

同一個形狀的其他實例：

- 「靜默降級反模式」——多層 fallback 都用同一個預設值 `'x'`，於是資料遺失和正常路徑長得一樣
- `try { ... } catch (_e) { /* ignore */ }`——`block-registrar.ts` 有 6 個，正好吞掉「欄位名不對」這個已知會發生的錯誤
- 被 skip 的測試——「墓碑的正確後果」（`#define` 已否決）和「缺陷」混在一起，除非強制標分類

### 二、債務搬到沒人稽核的地方，就會看起來像清掉了

`src/` 裡 `TODO|FIXME|HACK|XXX` **一個都沒有**——技術債全部堆在測試檔的 `it.todo` 與 `skip` 裡。所以 `src/` 看起來乾淨。

更深一層：**缺陷會被記在「被它擋住的那個東西」上，而不是「有問題的那個東西」上**。10 個 string fuzz 測試因為 `print` 的 lift 只吃淺運算元而全部停用，而那句診斷是**一個被停用測試檔裡的註解**——稽核 `print` 會通過，稽核 `string` 看起來有覆蓋，沒有任何一條路徑會走到那句話。

> **記錄比修復便宜，而且記錄完看起來像處理過了。**

## 執行機構自己也可能是殼（2026-08-06，由 P0 的實作發現）

本檔原本的主張是「規範沒有檢查就是殼」。實作四條護欄時撞到它的**下一層**：

> **檢查本身也會安靜地量錯，而錯誤的數字比沒有數字更糟——它給你假的安全感。**

兩個實例（`specs/049-audit-guardrails`）：

| 量測 | 錯在哪 | 產出 |
|---|---|---|
| 完備性護欄第一版 | 用了需要 `program` 外殼、只處理 statement 的入口 | **84 個假的 missing**——數字很大、很像真的 |
| 兩組態比對第一版 | 比 verdict（粒度太粗），而差異其實在**產生的文字** | 「無差異」——真實是 35 個元件不同 |

**兩次都不是靠檢查程式碼抓到的，是靠結果不合理**：`render` 全過卻 `extract` 全缺，那個組合不可能；而「無差異」那次，救命的是報表裡自己預先寫的一句「**若這裡是空的，多半是護欄沒接對**」。

### 因此：每個量測工具都要帶一句自我否證提示

> 「**如果結果長成 ○○，代表工具壞了，不是世界長這樣。**」

量測工具是最容易變成殼的東西——**它產出數字，而數字天生看起來像證據**。這條是本概念的自我應用：執行機構是規範的執行機構，那**誰是執行機構的執行機構**？答案不是再加一層檢查（無限後退），而是**讓工具自己聲明它的失效樣態**。

同一形狀的第二個實例，也在 P0 裡：完備性護欄的報表固定印出「**本護欄不檢測條件性正確**」（FR-025）。那不是免責，是**劃出工具的能力邊界**——一條只抓得到「殼」的護欄若被誤讀成完備性保證，會比沒有護欄更危險。

### 數字是 0 的護欄，健康與全瞎長得一樣（2026-08-06）

在它之前的護欄基線都是非零的（20 檔、92 個殼、85 筆停用、8 個歧義群組）。非零有一個附帶的好處：**它證明量測真的量到了東西**。有一支測試就叫「數字不為零——零代表沒有真的量到東西」。

第六條不同。它量的三種違規在它裝上去之前就已經被同一個功能修完了，所以基線是 **0／0／0**。而這時候「數字不為零」那招**反過來會逼你造假**。

一條回報零違規的健康護欄，與一條**什麼都沒量到**的護欄，產出完全相同。

**解法是注入，不是斷言數字**：餵一個**故意壞掉**的實作進掃描器，確認它報得出來。三支：

| 注入 | 釘住什麼 |
|---|---|
| 會丟欄位的實作 | 報得出來，**而且理由是「存入後讀回為 undefined」** |
| 會竄改值的實作 | 理由必須是「變成了什麼」——「丟了」與「被改了」是兩種病 |
| **正確的實作** | **必須零違規**——沒有這支，一個「什麼都報」的掃描器也能通過前兩支 |

第三支是不可省的：前兩支只證明「會報」，第三支才證明「不亂報」。**兩個方向都釘，才是量得準。**

### 錨點要挑「這個功能不會修好的東西」（2026-08-06）

自我否證聲明本身也會過期。

分類護欄的第一版錨在 `static_cast`：「已知它是壞的（實測輸出 0）——它若通過，代表這支測試沒有真的在跑。」

**同一個功能的下一個 Story 就把 `static_cast` 修好了。** 那句聲明於是變成「叫未來的讀者不要相信一個正確的結果」——比沒有聲明更糟。

**判準**：錨點要挑**這個功能明確不打算修的**東西。改成物件導向那十個（直譯器不支援 OOP，本功能也不實作它）之後才穩。

> 一句會過期的自我否證聲明，過期之後看起來與有效的完全一樣——**這條概念的自我應用又多了一層**。

### 數字下降有兩種，混在一起就變成刷分的入口

同一輪還撞到一個更軟的失效方式：**宣告會讓「殼」的數字下降，而系統一點都沒變。**

| 下降原因 | 意義 |
|---|---|
| 因為**實作**了 | 系統多會做一件事 |
| 因為**宣告**了 | 系統沒有變，只是我們終於說清楚它本來就不做 |

實測那一輪：92 個殼降到 76，但**只有 4 個是真的修好**（四個轉型），另外 12 個只是說清楚了。

兩者混在同一個數字裡的話，**用宣告刷數字看起來會像進步**，而護欄會替它背書。所以報表分三欄（實作／已宣告不提供／殼），棘輪只看殼與缺，而且每個宣告都要列出**理由**——宣告要可複查，不是一次性的。

配套的失效樣態聲明：

> ⚠️ **「已宣告」的數字上升不是進步。** 實測 34 個候選裡只有 12 個站得住；**若哪天它逼近 34，那是判準壞了，不是我們變好了。**

## 記錄本身也會存殼——「已採用」是意圖，不是證據（2026-08-06，由 P1 發現）

再下一層：**知識庫自己也會存殼**。

`history/005`（2026-03-09）決定 pattern 歧義用偏序仲裁，狀態欄寫「✅ 已採用」。四個月後 P1 第一次量它，發現三種情況裡**只有一種真的實作了**——情況二（交叉歧義報註冊錯誤）從未存在，實測 18 對規則落在那裡卻無人報錯。

這比程式碼裡的殼更難抓，因為**記錄是後續決策唯一的依據**。引用一條標著「已採用」的舊決定時，沒有人會去驗證它。

### 為什麼這一類特別容易空著

因為 P3 這種規範的形式是「**新增 X 不得改變既有 Y**」——它守的不是「現在是對的」，而是「未來的變更不會破壞現在」。

**這類規範沒實作時，症狀恆為零。** 靠登記順序決勝負的規則現在幾乎都是對的（否則專案早就不能用了），所以它不會出現在任何失敗測試、任何 bug 報告裡。它只在有人動它的時候咬人——而那時已經很貴了。

**零症狀不是健康，是這類規範的正常表現。**

### 因此：兩種護欄要分開講

| 護欄 | 量什麼 | 數字下降代表 |
|---|---|---|
| 就近性／中立性／完備性／缺陷帳 | **有多少東西壞了** | 修好了 bug |
| 辨識歧義那條 | **有多少東西靠運氣** | 移除了一個未來會咬人的機會 |

把兩者混進同一個「品質分數」，會讓人以為靠運氣的那部分是安全的。**它不是安全，它是還沒被觸發。**

### 護欄常常只問了一個方向（2026-08-06，由 055 發現兩次）

護欄是照著「我們怕什麼」寫的，而怕的通常是**已經被咬過**的那一種。沒被咬過的方向就沒人想到。

| 護欄問了 | 沒問的那一半 | 後果 |
|---|---|---|
| 已宣告的概念，五條路都有實作嗎 | **有實作的東西，有被宣告嗎** | 4 個概念完全隱形，身上 8 個缺口跟著隱形 |
| 核心層有沒有提到語言專屬的概念名 | **核心層有沒有 import 語言套件** | 一個核心檔可以一個概念名都不提，卻直接引用整包 |

第二列尤其刺眼：**P9 的原文就是「無 `languages/cpp/` import」**——那是這條原則自己寫下的檢查，而兩個月來沒有人做過它。

### 可操作的做法：把主詞與受詞對調再讀一次

> 「**宣告**的有沒有**實作**」→「**實作**的有沒有**宣告**」
> 「核心**提到**語言概念」→「核心**引用**語言套件」

對調之後**讀起來仍然成立**的，就是漏掉的那一半。

## 剪枝力：它排除什麼

對任何一條規範性陳述（原則、成功標準、契約、註解裡的保證）問一句：

> **「如果有人違反它，什麼東西會變紅？」**

- 答得出 → 這條規範有執行機構
- **答不出 → 它是裝飾**，不論措辭多強（「MUST」「0 容忍」「零 todo」都不算）

反過來也剪：**不是每條規範都值得執行機構**。判準是知識庫既有的那條——「砍了 AI 會不會默默跳過？會 → 留；不會 → 砍」。答不出「什麼會變紅」而且**跳過也沒人在意**的，該砍的是那條規範本身，不是補檢查。

## 推論：新增規範時，同時交付它的執行機構

不然它從第一天就是殼。這條適用於：

- **新原則** → 交一條測試，或明說「這條靠人 review，沒有機械檢查」
- **新契約**（序列化格式、膠囊格式、埠協定）→ 交驗證器；版本欄位要**被 branch on**，不是只存在
- **新的「不准」**（不准雙重真相、不准跨層 import）→ 交 audit 測試

這正是 [元件膠囊重構](../draft/2026-08-05-元件膠囊重構.md) 的 P0 在做的事：**它不加任何新規範，只是讓三條已經寫下的原則第一次真的被檢查。**

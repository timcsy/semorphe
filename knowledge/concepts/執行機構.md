# 執行機構（Enforcement）

**一條規範沒有機械化的檢查，它本身就是殼——而殼看起來像完成。**

這兩句是同一件事的兩面：**宣稱存在、檢查不存在**。原則、版本欄位、空 stub、被歸檔的缺陷，全是同一個形狀——它們都通過了「看一眼」，因為看一眼檢查的是**存在**，不是**作用**。

**三視角投影：**

- **原則**：P2「0 容忍」與 P9「四項獨立性」都是規範，兩條都**沒有任何測試在檢查**
- **願景**：每個階段的成功標準都寫「所有測試通過」，但沒有東西檢查**完備性**——通過的是已經寫出來的測試，不是該有的測試
- **經驗**：殼的六種樣態、64 個被歸檔的缺陷、`version` 欄位、`src/` 裡零個 TODO

|---|---|---|
| P2「缺任一條路徑 = 架構缺陷（**0 容忍**）」 | **無** | 15/17 個 `std/*/lifters.ts` 是空 stub，沒人發現 |
| P9「拔掉 C++…**無 `languages/cpp/` import**」 | **無** | 12 個 kernel／app 檔硬編 C++ conceptId |

**五次都不是疏忽，是同一個結構性缺口。** 而最後一列是最乾淨的標本——`version` 欄位存在、名字對、看起來就是版本控制，**但沒有任何東西 branch on 它**。

### 第六列：**符合性**（2026-08-10 補上，來自 spec 104）

| 宣稱 | 檢查 | 後果 |
|---|---|---|
| 「**每個形態的接腳集合 == 語義接腳**」（[元件](元件.md):346「投影忠實度不變式」） | **無** | `cpp:vector_declare` 宣告了 `values`／`source` 兩個接點，而積木形態的 `args0` 只有兩個 **field**、**一個 input 都沒有**——積木在結構上表達不出帶初始值的 vector |

**後果使用者看得到**：`vector<int> v = {3, 1, 4}` 走一次 render → extract 就變成
`vector<int> v;`，而任何一次工作區重新序列化（切語言、切風格、存檔重載）都會走那條路。

**它與前五列的差別**：前五列是「原則寫了、沒人查」。這一列是
**同一個缺陷在五路裡修了三路，剩下兩路沒有人回頭掃**——
generate 與 execute 都修過並在程式碼裡留下註解
（「少了它的話，來回轉換會靜靜地把 `{3,1,4}` 變成 `v;`」），
而那兩段註解**都沒有提到 render／extract**。

> **修一條路的時候，要問「同一個缺陷在別的路上長什麼樣」。**
> 五路是同一顆元件的五個投影——一個語義上的東西掉了，通常不會只掉一路。

#### 七筆確定違規，其中兩筆比原本發現的那筆更嚴重

```
原:  [](int a, int b) { return a + b; }   →  回:  []() { return a + b; }
原:  C(int a) {}                          →  回:  C() {}
原:  vector<int> v = {3, 1, 4};           →  回:  vector<int> v;
```

`lambda`／`constructor`／`method_virtual`／`method_virtual_pure`／`method_override`／
`template_function` 六顆的 `params` 全部走不過投影，加上 `vector_declare`。
**而 `func_def` 是好的**——所以這不是「參數這件事沒做」，是**函式族的六個變體漏了**。

⚠️ 收**棘輪**不收硬性零：規範成立（留一筆就會靜默丟資料），但**每一筆都要驗行為**
（給積木加參數插槽是真的功能改動）——`build-guardrail` 6.8 的兩個問題分開答。

#### ✅ 六筆已還（2026-08-10，spec 105），**7 → 1**

新增宣告式映射 `childrenAsField`（子節點列表 ↔ 一個文字欄位），
六顆各加四行 JSON、**零行程式碼**。

⚠️ 否決了「照 `u_func_def` 複製 82 行 Blockly 動態積木 × 6」
——**那是這階段在治的碎裂本身**。六顆今天就有 `PARAMS` 文字欄位，
使用者已經在那裡打字，所以不重設計積木。

**這個取捨與既有教訓「需要 parse 回結構才能用的字串，就不該是字串」有張力**，
處置是把張力寫成可執行的東西：字串只存在於**形態層**，語義層永遠是結構化的
`param_decl`；並定下**三個升級訊號**（打錯字缺陷出現第二次／需要逐項操作／
含分隔符的型別變成課程內容），任一出現就改成結構化插槽。

> **一個取捨若沒有退出條件，它會永遠留著。**

剩下的一筆 `cpp:vector_declare` 形狀不同（變長初始值要動態積木），另案。

完整的轉變記錄見 [history/035](../history/035-符合性從無機制到七筆還六筆.md)。

## 為什麼「看一眼」永遠抓不到

因為殼的定義就是「**存在但不作用**」，而看一眼檢查的是存在。

需要的檢查隨病加深而升級：

| 病 | 症狀 | 檢查形式 |
|---|---|---|
| **碎裂** | 東西散在太多地方 | **靜態計數** —— 數它出現在幾個檔 |
| **殼** | 東西在該在的地方，但是空的 | **執行式** —— 跑一次，看它吐什麼 |
| **條件性正確** | 在、不空，**單獨測都過，組合才壞** | **組合式** —— 隨機生成真實程式（fuzz）**＋一個外部 oracle** |

**每一階都抓不到下一階。** 靜態計數會把空 stub 算成覆蓋；執行式的最小樣本，就是那個會過的 case。

### ⚠️ 第三階的處方**有兩半，而專案長期只做了一半**（2026-08-10 更正）

第三階原本只寫「fuzz」。實測 18 個 fuzz 檔（`specs/109` 收尾時查）：

```
用參照編譯器對答案        2 檔   ← 而兩邊都是 g++（來回保義，不是模擬保真）
斷言執行輸出              6 檔   ← **人手寫的預期字串**
只比產出的碼             12 檔   ← 根本沒有執行
```

最刺的一筆是 `fuzz-cpp-oop.test.ts`：檔頭寫著
「Tests lift → generate → **execution** roundtrip for OOP programs:
classes, **constructors**, destructors」，而斷言是
`expect(gen).toContain('class Counter')`——**比的是碼**。
它涵蓋的正是「建構子不被執行」那個缺陷，而**它一直是綠的**。

> **fuzz 把輸入生成做對了，oracle 卻是凍結的。**
> 隨機生成真實組合只解決了「找得到那個 case」；
> **「知道答案該是什麼」是另一半，而它需要一個能重新問的外部權威。**

所以第三十二條護欄加的不是 fuzz，是**fuzz 一直缺的那半邊**——
而 14 筆條件性正確缺陷在 18 個 fuzz 檔下活了幾個月，就是那半邊缺席的代價。

**這是同一形狀的第三個實例**：

| | 宣稱 | 實際比的 |
|---|---|---|
| 標籤說謊 | `stack`／`queue` 的 push 說明作用位置 | 兩者逐字相同 |
| 凍結的讀數 | 27 個檔「與 `g++` 對過答案」 | 人工量一次寫死 |
| **fuzz 的 oracle** | 檔頭說「測執行來回」 | **產出的字串** |

## 兩條可操作的判準

### 一、沉默的正確和沉默的缺失撞在一起時，讓正確的那個說話

有些「空」是對的（`cpp_include` 這種宣告性概念本來就不執行），有些是缺。**兩者長得一模一樣**，所以偵測不了。

解法不是更聰明的偵測，是把**推斷**改成**宣告**：

```
execute: "noop"        ← 顯式宣告：這個概念本來就不執行
（缺這個欄位）          ← 缺失
```

缺失於是自動變成可偵測的。

> **這條判準在 2026-08-06 第一次真的被落實**（`specs/053-declare-noop-execute`）。而落實的過程本身推翻了一個直覺：
>
> 核心直譯器有一份寫死的 34 個「無執行行為」概念清單。原本以為工作是「把 34 個改成宣告」——**實測只有 12 個配得上**。其餘 14 個跑起來結果是錯的（十個是物件導向，直譯器不支援它），5 個根本測不到，3 個是死條目。
>
> ⚠️ **「直譯器不支援物件導向」這句話已於 2026-08-10 過期**——`specs/071`／`072`／`073` 在那之後實作了它，`unimplemented.ts` 的 `OOP_NOT_IMPLEMENTED` 現在是**空陣列**。而 2026-08-10 規劃 `specs/109` 時**我把這句話當成現況引用**，整份 spec 圍繞「新增一個『已知不支援』宣告值」設計，直到查證才推翻。
> **一句寫在知識庫裡的論斷，會被當成現況引用，而它記的是寫下當天的世界。**（見 [history/038](../history/038-過期的論斷被當成現況引用.md)）
>
> **「把 34 個都宣告掉」會讓兩條護欄的數字同時下降，而系統一點都沒變。** 那不是落實這條判準，是拿這條判準當藉口——**把缺陷洗成設計，然後讓護欄替它背書**。
>
> 所以宣告需要門檻：理由只有兩個值（`declarative`／`consumed-by-parent`）且**不得增加**——第三個值就是在替「還沒做」找一個體面的名字。

同一個形狀的其他實例：

- 「靜默降級反模式」——多層 fallback 都用同一個預設值 `'x'`，於是資料遺失和正常路徑長得一樣
- `try { ... } catch (_e) { /* ignore */ }`——`block-registrar.ts` 有 6 個，正好吞掉「欄位名不對」這個已知會發生的錯誤
- 被 skip 的測試——「墓碑的正確後果」（`#define` 已否決）和「缺陷」混在一起，除非強制標分類

### 二、債務搬到沒人稽核的地方，就會看起來像清掉了

`src/` 裡 `TODO|FIXME|HACK|XXX` **一個都沒有**——技術債全部堆在測試檔的 `it.todo` 與 `skip` 裡。所以 `src/` 看起來乾淨。

更深一層：**缺陷會被記在「被它擋住的那個東西」上，而不是「有問題的那個東西」上**。10 個 string fuzz 測試因為 `print` 的 lift 只吃淺運算元而全部停用，而那句診斷是**一個被停用測試檔裡的註解**——稽核 `print` 會通過，稽核 `string` 看起來有覆蓋，沒有任何一條路徑會走到那句話。

> **記錄比修復便宜，而且記錄完看起來像處理過了。**

## 執行機構自己也可能是殼（2026-08-06，由 P0 的實作發現）

本檔原本的主張是「規範沒有檢查就是殼」。實作四條護欄時撞到它的**下一層**：

> **檢查本身也會安靜地量錯，而錯誤的數字比沒有數字更糟——它給你假的安全感。**

兩個實例（`specs/049-audit-guardrails`）：

| 量測 | 錯在哪 | 產出 |
|---|---|---|
| 完備性護欄第一版 | 用了需要 `program` 外殼、只處理 statement 的入口 | **84 個假的 missing**——數字很大、很像真的 |
| 兩組態比對第一版 | 比 verdict（粒度太粗），而差異其實在**產生的文字** | 「無差異」——真實是 35 個元件不同 |

**兩次都不是靠檢查程式碼抓到的，是靠結果不合理**：`render` 全過卻 `extract` 全缺，那個組合不可能；而「無差異」那次，救命的是報表裡自己預先寫的一句「**若這裡是空的，多半是護欄沒接對**」。

### 因此：每個量測工具都要帶一句自我否證提示

> 「**如果結果長成 ○○，代表工具壞了，不是世界長這樣。**」

量測工具是最容易變成殼的東西——**它產出數字，而數字天生看起來像證據**。這條是本概念的自我應用：執行機構是規範的執行機構，那**誰是執行機構的執行機構**？答案不是再加一層檢查（無限後退），而是**讓工具自己聲明它的失效樣態**。

同一形狀的第二個實例，也在 P0 裡：完備性護欄的報表固定印出「**本護欄不檢測條件性正確**」（FR-025）。那不是免責，是**劃出工具的能力邊界**——一條只抓得到「殼」的護欄若被誤讀成完備性保證，會比沒有護欄更危險。

### 數字是 0 的護欄，健康與全瞎長得一樣（2026-08-06）

在它之前的護欄基線都是非零的（20 檔、92 個殼、85 筆停用、8 個歧義群組）。非零有一個附帶的好處：**它證明量測真的量到了東西**。有一支測試就叫「數字不為零——零代表沒有真的量到東西」。

第六條不同。它量的三種違規在它裝上去之前就已經被同一個功能修完了，所以基線是 **0／0／0**。而這時候「數字不為零」那招**反過來會逼你造假**。

一條回報零違規的健康護欄，與一條**什麼都沒量到**的護欄，產出完全相同。

**解法是注入，不是斷言數字**：餵一個**故意壞掉**的實作進掃描器，確認它報得出來。三支：

| 注入 | 釘住什麼 |
|---|---|
| 會丟欄位的實作 | 報得出來，**而且理由是「存入後讀回為 undefined」** |
| 會竄改值的實作 | 理由必須是「變成了什麼」——「丟了」與「被改了」是兩種病 |
| **正確的實作** | **必須零違規**——沒有這支，一個「什麼都報」的掃描器也能通過前兩支 |

第三支是不可省的：前兩支只證明「會報」，第三支才證明「不亂報」。**兩個方向都釘，才是量得準。**

#### ⚠️ 而注入釘不住「輸入有沒有進來」（2026-08-10）

第七條護欄「執行器重複註冊」自 2026-08-06 起**量的是一個空的註冊表**
（量測前沒有載入語言套件），基線的 `0 / 0` 四天以來一直是假的——真實是 **4**。

**而它的三支注入一直是綠的**：注入手動註冊同一個名字兩次再確認被數到，
它證明的是「**計數器會數**」。**計數器會數 ≠ 註冊表裡有東西。**

更糟的是它的自我否證聲明**把讀者指向注入**（「判斷依據是『★ 注入』那支測試」）
——而注入正是看不到這個缺口的那一支。
**一句錯誤的自我否證提示，比沒有提示更糟：它讓人停止懷疑。**

| | 釘住什麼 | 漏掉什麼 |
|---|---|---|
| 注入 | 判定邏輯**會不會報** | 真實輸入**有沒有進來** |
| **入口條件** | 真實輸入**有沒有進來** | 判定邏輯對不對 |

→ 每條護欄都要有一支**入口條件**斷言：掃了幾個檔／載入了幾條規則／
註冊表裡有幾個概念／語料幾段。見 [history/042](../history/042-護欄自己量了四天的空註冊表.md)。

#### 而「錨點會爛」這件事本身也機械化了（2026-08-10，第三十五條護欄）

第 2 步那個「錨在缺陷還在不在上」的錯**犯了八次**，判準寫成語法簽名之後
還是犯了第八次——而**那次是全套測試在同一輪抓到的，不是被人看出來的**。

於是它變成一條護欄：掃 `audit-*.test.ts` 的注入與健康檢查，
報出「**期望值裡出現真實元件身分**」的行。硬性零。

⚠️ 它**不判對錯**——第 6 步要求的「已知答案樣本」本來就用真實身分，
判準是身分出現在**期望值**裡（錨在缺陷上）還是**查表的鍵**上（錨在事實上）。

⚠️ 而它第一次跑是**綠**的，因為那八次都已經被修掉了。
這正是本節上面那條「數字是 0 的護欄，健康與全瞎長得一樣」的情況
——**靠注入，不靠第一次的紅**。

#### 第十一列：**投影的名字必須從真實導出**（2026-08-11，第三十六條護欄）

量：專案宣告的積木裡，`blockDef.type` 不等於 `deriveBlockType(conceptId, form)`
的筆數。**硬性零**——留一筆，「一個名字」那句話就是假的，護欄會變成在替
第二份命名背書。

第一次跑 **153 筆**（只差前綴 67、主體不同 86）。而「主體不同」那 86 筆不是隨機：

> **積木型別是命名整理那次改名的化石層**——身分停在 G 之後（`peek`），
> 積木型別停在 G 之前（`top`）。**兩個時間層疊在一起。**

⚠️ **這一條與前十列的差別**：前面十列量的是「機制在不在」「宣告全不全」，
這一條量的是**兩個命名系統之間的關係**。它能收硬性零，是因為其中一邊
（身分）已經被 G 項收乾淨了——**一條護欄能不能收硬性零，取決於它的參照物有多硬。**

見 `specs/116-block-type-derive/`、[history/048](../history/048-積木型別導出與四類描述過去的東西.md)。

### 釘住一個不存在的缺陷，比不釘更糟（2026-08-06）

`it.fails` 用來釘住已知缺陷：缺陷還在＝綠且出聲，修好了＝紅且提醒拔釘子。機制是對的。

但有一次釘住的東西**根本不存在**——測試傳了一個假的風格物件，產生器因此走了非預期的分支。那個假象被當成缺陷釘住，還附上「修法會動到跨風格行為，因此擱置」的完整分析。

**釘子看起來像盡責，而它讓後續每一個讀到的人相信系統壞了。**

判準：**釘之前先確認缺陷是真的**——用真實環境跑一次，不是用測試裡隨手造的物件。

### 錨點要挑「這個功能不會修好的東西」（2026-08-06）

自我否證聲明本身也會過期。

分類護欄的第一版錨在 `static_cast`：「已知它是壞的（實測輸出 0）——它若通過，代表這支測試沒有真的在跑。」

**同一個功能的下一個 Story 就把 `static_cast` 修好了。** 那句聲明於是變成「叫未來的讀者不要相信一個正確的結果」——比沒有聲明更糟。

> 一句會過期的自我否證聲明，過期之後看起來與有效的完全一樣——**這條概念的自我應用又多了一層**。

**判準（2026-08-06 加強，原本是「挑這個功能不打算修的東西」）**：**根本別錨在真實狀態上，錨在餵給判定函式的合成輸入上。**

原本的判準同一天又失效兩次——辨識歧義護欄錨在「`declaration` 那 8 條」（下一個功能把那群修好了）、雙重真相護欄斷言「兩處都有定義 > 10」（而**消滅雙重真相正是那條護欄存在的目的**）。兩次都符合「這個功能不打算修」，兩次都爛了。

> **護欄修好了它要量的東西，就是它的錨點爛掉的時候。**

一條護欄的目的就是讓它量的數字下降。錨在那個數字上的自我否證聲明**註定過期**——不是意外，是設計上的必然。合成輸入不會。

轉移見 [history/022](../history/022-護欄的自我否證不得錨在真實狀態.md)。

### 名字比對忘了詞界——一天之內四次（2026-08-06）

護欄的判定十之八九是「這個名字有沒有出現在那裡」。而**名字會互相包含**：

| 要找的 | 被誤判的原因 |
|---|---|
| 概念身分 `comment` | 也是語法樹節點型別、列舉成員、UI 提示文字 |
| C++ 的 `endl` | `'u_endl'`（積木型別）裡含它 |
| 剝除註解的正則 | 寫在正則字面裡，只掃字串字面的話看不到 |
| `children.init` | 是 `children.initializer` 的**子字串** |

四次的後果**不一樣**，而這一點很重要：

- 前兩次是**多報**——數字虛高，看起來像還有很多要修
- 後兩次是**漏報**——數字虛低，而 **0 與健康的 0 長得一模一樣**

**漏報那一種更危險，因為它讓護欄在最需要出聲的時候安靜。** 第四次那個護欄的
第一版回報「0 個問題」，而它要抓的那一筆正好被自己的子字串遮掉。

**可操作的做法**：任何以名字為基礎的比對，**先寫一支專門釘詞界的注入測試**
——「一個更長的名字包含了它，不得算它出現過」。這支測試比報表上的數字更能
說明護欄有沒有壞。

### 一條規範被機械化時，選了哪一維會消失在數字裡（2026-08-06，由 059 發現）

前面幾節講的都是**工具的第一版會實作錯**——入口用錯、粒度太粗、判準對而自動化錯。修法是修工具。

這一節不一樣：**判定邏輯完全正確，錯的是它量的那一維不是規範的全部。**

中立性護欄的檔頭寫著「數字是幾，就是離語言獨立性還有多遠」。它精準地數出核心層有多少**元件身分字串**。而核心層寫死**語法符號**（`//`、`/* */`）的六個地方，它一個字都看不到——那些位置一個身分都沒有。

> P9 說「拔掉 C++，核心無 `languages/cpp/` import」。**那句話自己也只寫了一個維度**——import 是耦合的一種形式，身分是另一種，語法是第三種。

**判準**：一條護欄要能回答「這條規範有幾種違反形式，我量的是哪一種」。答不出來的話，那個數字看起來像完整的答案，而它不是。

**這條會重演。** 就近性數檔案數、缺陷帳數停用測試、完備性跑五路——每一條都在自己選定的那一維上正確，而每一條都可能有一整類違規落在維度外面。

**可操作的做法**：每條護欄的「本護欄不檢測什麼」要寫**維度**，不只寫範圍。「不檢測執行期才成立的耦合」是範圍；「**不檢測語法層級的耦合——本護欄找的是元件身分**」是維度。

轉移見 [history/021](../history/021-中立性的數字只量身分那一維.md)。

**第四種形式：型別名（2026-08-07，由 095 發現）。** 核心層寫死 `'istringstream'` 判斷 `>>` 是讀值還是位移——中立性找身分、語法耦合找符號，**兩條都數不到**。叫的是**就近性**，而它量的是「一個元件散在幾個檔」，根本不是語言耦合。

> **如果把那條規則寫進一個已經提到那些概念的既有檔，三條護欄會全綠。**
> 一筆耦合能不能被發現，取決於它被寫在哪個檔案——而那與它是不是耦合毫無關係。

所以更強的版本是：**「有護欄叫了」不代表「那條護欄涵蓋了這個問題」。** 見 [history/024](../history/024-耦合的第四種形式是型別名.md)。

### 延後也要留機制——一句「之後再處理」本身就是殼

一個問題被正確診斷、正確地切出本次範圍，然後寫成「記在此供後續期別處理」——**那一刻它從問題變成記錄，而記錄看起來像處理過了**。

實例：呼叫編譯器的測試逾時不足，診斷完全正確，躺了四天；期間「已知的載入敏感 flake」被用來帶過紅燈至少四次。修好之後全套第一次真正全綠。

這比「機制有了，沒人接上」更極端——**機制連建都沒建**。

**判準**：延後的東西要落在一支 `it.fails`、一條護欄的基線、或一個帶驗收標準的路線圖項目上。三者都會在該叫的時候叫，**一句話不會**。見 [history/025](../history/025-那個-flake-從真實變數改為診斷過但沒人接上.md)。

### 數字下降有兩種，混在一起就變成刷分的入口

同一輪還撞到一個更軟的失效方式：**宣告會讓「殼」的數字下降，而系統一點都沒變。**

| 下降原因 | 意義 |
|---|---|
| 因為**實作**了 | 系統多會做一件事 |
| 因為**宣告**了 | 系統沒有變，只是我們終於說清楚它本來就不做 |

實測那一輪：92 個殼降到 76，但**只有 4 個是真的修好**（四個轉型），另外 12 個只是說清楚了。

兩者混在同一個數字裡的話，**用宣告刷數字看起來會像進步**，而護欄會替它背書。所以報表分三欄（實作／已宣告不提供／殼），棘輪只看殼與缺，而且每個宣告都要列出**理由**——宣告要可複查，不是一次性的。

配套的失效樣態聲明：

> ⚠️ **「已宣告」的數字上升不是進步。** 實測 34 個候選裡只有 12 個站得住；**若哪天它逼近 34，那是判準壞了，不是我們變好了。**

轉移的完整經過見 [history/018](../history/018-清償從搬檔案改為把清單換成宣告.md)——那份記著這條判準的來源，以及「拿判準當藉口，把缺陷洗成設計」的原話。**059 的三步順序（修量測 → 搬投影 → 才改分層）整個建立在它上面**：改分層讓四筆違規消失，形狀與刷數字一模一樣，唯一的分別是搬移已經先做完了。

## 記錄本身也會存殼——「已採用」是意圖，不是證據（2026-08-06，由 P1 發現）

再下一層：**知識庫自己也會存殼**。

`history/005`（2026-03-09）決定 pattern 歧義用偏序仲裁，狀態欄寫「✅ 已採用」。四個月後 P1 第一次量它，發現三種情況裡**只有一種真的實作了**——情況二（交叉歧義報註冊錯誤）從未存在，實測 18 對規則落在那裡卻無人報錯。

這比程式碼裡的殼更難抓，因為**記錄是後續決策唯一的依據**。引用一條標著「已採用」的舊決定時，沒有人會去驗證它。

### 為什麼這一類特別容易空著

因為 P3 這種規範的形式是「**新增 X 不得改變既有 Y**」——它守的不是「現在是對的」，而是「未來的變更不會破壞現在」。

**這類規範沒實作時，症狀恆為零。** 靠登記順序決勝負的規則現在幾乎都是對的（否則專案早就不能用了），所以它不會出現在任何失敗測試、任何 bug 報告裡。它只在有人動它的時候咬人——而那時已經很貴了。

**零症狀不是健康，是這類規範的正常表現。**

### 因此：兩種護欄要分開講

| 護欄 | 量什麼 | 數字下降代表 |
|---|---|---|
| 就近性／中立性／完備性／缺陷帳 | **有多少東西壞了** | 修好了 bug |
| 辨識歧義那條 | **有多少東西靠運氣** | 移除了一個未來會咬人的機會 |

把兩者混進同一個「品質分數」，會讓人以為靠運氣的那部分是安全的。**它不是安全，它是還沒被觸發。**

### 護欄常常只問了一個方向（2026-08-06，由 055 發現兩次）

護欄是照著「我們怕什麼」寫的，而怕的通常是**已經被咬過**的那一種。沒被咬過的方向就沒人想到。

| 護欄問了 | 沒問的那一半 | 後果 |
|---|---|---|
| 已宣告的概念，五條路都有實作嗎 | **有實作的東西，有被宣告嗎** | 4 個概念完全隱形，身上 8 個缺口跟著隱形 |
| 核心層有沒有提到語言專屬的概念名 | **核心層有沒有 import 語言套件** | 一個核心檔可以一個概念名都不提，卻直接引用整包 |

第二列尤其刺眼：**P9 的原文就是「無 `languages/cpp/` import」**——那是這條原則自己寫下的檢查，而兩個月來沒有人做過它。

### 可操作的做法：把主詞與受詞對調再讀一次

> 「**宣告**的有沒有**實作**」→「**實作**的有沒有**宣告**」
> 「核心**提到**語言概念」→「核心**引用**語言套件」

對調之後**讀起來仍然成立**的，就是漏掉的那一半。

### 機制有了，沒人接上——「殼」的近親（2026-08-06 起，**十個實例**）

本概念的原型是「**規範沒有機械化的檢查，它本身就是殼**」。十次撞到它的近親
（前八次列在下表，第九、十個各換了一個軸，見本節末）：

> **建一個機制不等於它在運作。**

| 機制 | 發現時的採用率 |
|---|---|
| `skipPaths`（宣告刻意不提供） | **0 / 175** |
| `abstractConcept`（語言中立父概念） | **33 / 131 指得到** |
| `block-input-names`（插槽名唯一真相） | **7 / 77** |
| `introduces_scope`（這個概念引入作用域） | **0 / 4**（宣告者四個，讀的人零個） |
| 辨識脈絡的作用域／型別追蹤 | **0 呼叫者**（`declare`／`getType`／`pushScope`／`lookup` 四個方法全空） |

三個的檔頭都寫著它解決了什麼。那是**設計意圖**，不是**現況描述**——而讀的人分不出來。

**為什麼**：建機制是創造性的工作，遷移既有呼叫點是機械性的。前者做完有成就感、會寫註解、會關議題；後者沒有終點感，而且**不做也不會有任何症狀**——舊寫法照樣運作。

**因此**：建一個唯一真相的機制時，同時交付**遷移**與**一條量採用率的護欄**。既有的護欄問的都是「東西對不對」，沒有一條問過「**機制有沒有人用**」。

#### 第九個實例：**被呼叫過一次，然後結果被凍成常數**（2026-08-10，`specs/108`）

前八個是「機制沒人呼叫」或「呼叫了但接到別的地方」。第九個換了一個軸：
**機制被呼叫過，而且結果是對的——只是它只跑了一次。**

```
tests/ 裡提到 g++ 的檔                29
真的 shell out 去編譯的                2   ← 而那 2 個比的是 g++ vs g++（來回保義）
自動比較「直譯器 vs g++」的            0
```

那 27 個檔的答案長這樣（`declare-family-semantics.test.ts:61`）：

```ts
it('★ g++ 說是 123（不是 111）', …)
```

**有人真的去量過**——那個 123 是量出來的，不是猜的。而它被寫成常數之後，
`g++` 這顆參照元件就從量測變成了宣告。

> **檢查存在，但它不會重跑。** 而不重跑的檢查與不存在的檢查，
> 在「有沒有人在守這件事」上是一樣的——只差在它更難發現，
> 因為檔案裡到處都是 `g++` 這個字。

⚠️ **它的偵測方式與前八個不同**：前八個問「有沒有人呼叫」（grep 得到），
這一個要問「**呼叫發生在什麼時候**」——著作期還是執行期。
grep `g++` 會得到 29，而正確答案是 0。

#### 第八個實例：**脈絡有了、接不上**（2026-08-08，`specs/102`）

前七個實例是「機制沒人呼叫」。第八個換了一層：**東西被呼叫了，只是接到別的地方去。**

完備性護欄的 `SAMPLE_CONTEXT` 給 `cpp_string_*` 提供前置宣告 `string x;`，
變數名寫死成 `'x'`——因為合成器當時給 `obj` 這類屬性的值就是 `'x'`。
參數規格化之後合成器改讀宣告的預設值（`'str'`），名字對不上，型別查不到，
三顆概念一起被判成假的「殼」。

⚠️ 這份檔案的註解**自己記著這個陷阱**（「脈絡宣告的變數名必須與合成節點用的
那個一致」，寫於第三個實例時），而它仍然斷了——因為那句話記的是**當下的對法**，
不是**對法本身**。

> **治法不是把 `'x'` 改成 `'str'`，是讓脈絡跟著合成節點走。**
> 一份「記得要對齊」的註解擋不住下一次不對齊；一個從來源讀出對齊值的函式可以。

#### 第五個實例：**註解把「沒插電」寫成了「做不到」**

前四個實例的症狀是「沒人用」或「有人繞過」。第五個多一層：**有人替它寫了一句
解釋，而那句解釋是錯的。**

辨識層有一段註解寫著：

> 「共用的方法名一律用通用容器概念，**為了避免型別消歧問題**。」

讀起來像「型別消歧做不到，所以只好降級」。而辨識脈絡**有一整套作用域與型別
追蹤**——`declare` / `getType` / `pushScope` / `lookup`，四個方法**零呼叫者**。
消歧的工具一直都在，只是沒有人接上。

> 一句解釋為什麼「只能這樣」的註解，**會讓那個限制看起來是本質的**。
> 而它其實只是「還沒接上」。

**這比沒有註解更難發現**：沒有註解的話，下一個人會去查為什麼；有了那句話，
他會接受它。

**可操作的做法**：任何「因為做不到所以降級」的註解，要能指出**哪一個機制不
存在**。指不出來的話，先去查那個機制是不是已經存在而沒有接上。

**同一天第二個實例，而標籤更強**：測試檔裡有兩處標著 `ARCHITECTURAL` 與
`architectural`——「辨識器沒有型別資訊」「辨識器產出的是運算式版」。
兩句都不是架構上的必然：前者的機制零呼叫者，後者只要看語法樹的父節點就知道。

> **一個大寫的標籤會讓下一個人停止追問。** 「架構上如此」比「因為做不到」
> 更難挑戰——它聽起來像已經有人想過了。

→ 判準：`ARCHITECTURAL` 這類標籤要附**哪一條設計決定**（指向 history／
concepts 的某一節）。指不出來的話，它只是一句沒有依據的斷言。

#### 「沒人讀」有三種，而它們的處置完全不同

抓到零讀取點之後，**不要一律歸成「待辦」**。先問它是哪一種：

| 種類 | 怎麼認 | 處置 |
|---|---|---|
| **被取代的殘留** | 有一筆決策紀錄說它被取代了 | **刪掉**——留著只會繼續漂移 |
| **建了沒接上** | 沒有紀錄說取代，也沒有路線圖項目在等它 | 接上或刪掉，二擇一 |
| **消費者還沒到** | 路線圖上有一個項目寫著會消費它 | 留著，**理由要指名那個項目** |

實例：`cognitive_level` 是第一種——決策紀錄明說線性層級已被主題層級樹取代，而且兩份來源**已經漂移**（一個概念的標註說 2、層級樹說 1）。`control_flow` 是第三種。

> **兩者混成一類的話，第一種會被「這是為了未來」擋著不刪，然後繼續漂移。**

⚠️ **第三種是刷數字最方便的入口**——貼一句「這是為了未來」就能讓任何東西合法化。所以理由**不是自由文字**：它必須指名一個路線圖裡**搜得到**的項目，而護欄要真的去搜。這條紀律來自 [history/018](../history/018-清償從搬檔案改為把清單換成宣告.md)：「理由只有固定幾個值且不得增加——第三個值就是在替『還沒做』找一個體面的名字。」

**而那條檢查本身也要驗**：注入一個不存在的項目，它必須變紅。沒驗的話它就只是另一個裝飾——**一條檢查宣告的機制，自己也可能是殼**。

#### 第七個實例（最大的一個）：**護欄自己沒有執行機構（2026-08-08）**

前六個各漏掉**一個**機制。第七個漏掉的是**全部**：

```
護欄 22 條｜測試 226 檔／3633 個｜自動執行它們的機制  ← 零
```

`.github/workflows/deploy.yml` 只有 `npm ci` → `npm run build` → 部署。
**沒有 `npm test`**，也沒有 pre-commit hook。它們只在有人手動打指令時跑。

> 本概念的原型是「**一條規範沒有機械化的檢查，它本身就是殼**」。
> 這一個是**上一層的同一句話**：檢查有了，而沒有機械化的東西去跑那些檢查。

**為什麼它躲了那麼久**：CI 每一次都是綠的——因為它只 build。
**一個只驗建置的 CI，與一個驗全部的 CI，綠燈長得一模一樣。**

**接上之後第一次跑就抓到東西**（與每一條新護欄相同的形狀）：
`syntax-tokens.test.ts` 用 `git show 35e96d8:…` 讀歷史檔，而
`actions/checkout` 預設淺複製——**那是一支只在本機通得過的測試**。

→ 判準：**「測試在誰的機器上跑得過」與「它是不是真的在跑」是兩件事。**
→ 驗收也照這個概念的紀律做：**先推一個故意紅的 commit**，確認 CI 紅且不部署，
  才算接上。設定完就宣告完成，正是本概念在講的殼。

#### 第六個實例：**有人替它寫了測試——而那份實作沒有人用（2026-08-07）**

前五個實例的症狀是「沒人用」。第六個把方向反過來：**唯一的使用者是它的測試。**

`buildIoCategoryContents` 與 `buildIoContents` 是同一段邏輯的兩份拷貝。產品程式碼
只走後者（`isIoCategory` 的預設路徑）；前者**只有它自己的單元測試在叫**，
綠了三個月——而**兩份有一模一樣的缺陷**。

這比前五個更難發現：

| | 症狀 | 誰會抱怨 |
|---|---|---|
| 前五個（沒人用） | 功能沒發生 | 遲早有人 |
| 第六個（只有測試在用） | **信心是假的** | **沒有人**——它是綠的 |

**測試覆蓋率會把它算成已覆蓋。** 而它覆蓋的是一段不會執行的程式碼。

**判準**：寫測試時問一句「**產品程式碼從哪裡進到這個函式？**」——答不出路徑就先答
這個，再寫斷言。**兩份重複實作最容易掉進這裡**：其中一份被接上，另一份留著測試。

**護欄缺口（已知，未補）**：`audit-orphan-implementations` 量的是
「已註冊執行器的概念」減「概念定義檔宣告的概念」，看不到「匯出了但只有測試在叫的
函式」。這是十九條護欄外面的一格。

**已量出規模（2026-08-07）**：`src/` 匯出 178 個函式，其中 **26 個產品程式碼零引用、
只有測試在叫**。最大一叢是 `core/semantic-tree.ts` 的 **11 個**樹操作輔助函式。

⚠️ **而量它的過程本身就是一課。** 掃描器把 `generateCode` 報成「只有測試在叫」，
我判定掃描器壞了——**錯的是我，不是掃描器**：production 走的是
`generateCodeWithMapping`，`generateCode` 真的零呼叫者，而它有 **384 次測試引用**。

> 「已知答案的樣本」只有在**那個答案是查過的**時候才有效。
> 用**記得的**答案去驗掃描器，驗的是記憶不是工具——而我差點因此丟掉一個正確的結果。

**而 `generateCode` 正是第六個實例的放大版**：它與 `generateCodeWithMapping` 是
**同一段 setup 的兩份拷貝**（各七行相同），一份production 在跑、一份 384 支測試在跑。
兩份一旦分歧，整套測試會在驗證一條沒有人執行的路徑，**而全套仍然是綠的**。

**第六個實例的續集（同一天，隔三個 commit）**：`src/blocks/universal.ts` 建成
「蓋 owner 章的唯一入口」之後，**只有測試路徑改過去**，`app.ts` 與 `module.ts`
仍 import 原始 JSON。每個 `(universal)` 段落在正式路徑上回傳零筆——
**通用積木整批從工具箱消失，而全套 222 檔全綠**，使用者截圖才發現。

> **建了「唯一入口」之後，第一件事是搜尋舊入口還有誰在用**，不是改測試。
> 留一個舊入口在那裡，等於宣告「唯一」的那句話是假的。

而修法不是把 import 改對（那是再賭一次沒有人會忘記），是讓**組裝只剩一份**
——測試與 production 用同一個函式，分歧**無法被表達**。

→ **並非 26 個都是問題。** 危險的子集是**重複實作**（`generateCode`、
`buildIoCategoryContents`）；純粹放錯地方的測試輔助函式是另一種、較輕的病。
補護欄之前要先切開這兩類——否則它會報 26 筆噪音，然後被忽略（第 11 步）。

#### 第四個實例不一樣：前三個是「沒人用」，這個是「**有人繞過它自己做了**」

`introduces_scope` 有四個宣告者。其中兩個（迴圈、函式定義）**各自在自己的執行器裡寫死了建子作用域的邏輯**，另外兩個（兩種分支）什麼都沒做。

所以那個標註從頭到尾是裝飾——**而且它藏著一個真的語義錯誤**：分支裡宣告的變數會外洩到外層，跑得出結果、印得出東西、而它是錯的。

> 前三個實例的症狀是「數字難看」（採用率低）。**這個的症狀是「程式跑錯」**，而沒有人發現，因為外洩只在特定寫法下才看得出來。

**新的判準**：一個機制的採用率不只要看「有幾個宣告者」，還要看「**有沒有人繞過它自己實作了同一件事**」。繞過的那些是最危險的——它們讓機制看起來被驗證過（那兩個概念的作用域確實是對的），而實際上機制本身從未執行。

見 [history/023](../history/023-機制被繞過比沒人用更危險.md)。

見 [history/020](../history/020-建一個機制不等於它在運作.md)。

#### 第十個實例：**機制在跑，而使用它的人有動機繞過它**（2026-08-12）

前九個都是「**沒有人呼叫**」（零呼叫者、空樁、只跑一次）——那些 grep 得到。
第十個是另一回事：

> **機制接上了、每天都在跑，而使用它的人有動機繞過它。**

實例是漸進揭露。使用者（一位真的在教的老師）的原話：

> 「還要手動把那些東西打勾，然後我實際在運作的時候
> **我會乾脆叫學生把全部都打勾，那有沒有這個漸進揭露是沒用的**」

兩個機制疊在一起：

| | 症狀 | 老師的**理性**反應 |
|---|---|---|
| **收益不可見** | 打勾的好處看不到，成本（設定）看得到 | 「反正都給他們用」 |
| **選項太多** | **9 個節點 = 512 種組合**，而沒有依據 | 找一條不用想的規則 |

> **一個機制如果它的成本由 A 付、收益由 B 得，A 就會找到繞過它的路
> ——而那不是 A 的錯。**

⚠️ **它比前九個難發現**：那九個是零呼叫者，工具看得到；
這一個**每天都在執行，只是永遠全開**。
**程式碼看起來完全健康，四十條護欄一條都不會紅。**

→ 偵測它需要的不是 grep，是**問使用的人怎麼用**。
而處置也不同：前九個是「補接線」，這一個是**讓收益可見**
（見 [draft](../draft/2026-08-12-漸進揭露把選項轉嫁給了老師.md)：
教材讓打勾從「限制」變成「選課」）。

## ⚠️ 反方向：機制升級了，而指著它的說明書沒跟上（2026-08-13）

上面十個實例都是**機制是殼／沒人接上**。這一類是它的**鏡像**：

> **機制是好的、每天都在跑，而描述它的文件停在上一個版本。**

實例：F 步把 177 顆元件全部搬進膠囊（`notEncapsulated: 0`），
而 `component-generate`／`refactor`／`pipeline`／`encapsulate` **四份 skill**
仍教「把五路分別加進五個共用檔」。`refactor` 的第一步是 `cat …/concepts.json`
——**而那個檔已經不存在**。詳見 [history/054](../history/054-元件skill的世界觀落後了一個階段.md)。

### 為什麼它比「沒人接上」難抓

| | 症狀 | 工具看得到嗎 |
|---|---|---|
| 前十個 | 零呼叫者、空樁、永遠全開 | ✅ grep／護欄／問使用者 |
| **這一個** | **文件的每一句話單獨看都合文法，指的檔案大多還在** | ❌ |

⚠️ 而「檢查路徑還在不在」**是無效的判準**——那次九支 skill 全綠，四份是壞的。
有效的是問：**它對今天的結構特徵提及幾次**（`src/components/`、`component.json`…）。
`component-generate` 的答案是 **0 次**。

> **路徑活著不代表做法還對。
> 一份指著存在檔案的過時說明書，比指著不存在檔案的更難發現。**

### ⚠️ 而它有一個容易誤信的緩衝

照著過時的 skill 做，`npm test`（那批護欄）會擋下——所以代價是**浪費一輪**，
不是靜默錯誤。**但那個緩衝是別人蓋的護欄，不是這份文件自己的健康度。**
🔴 護欄少一條，同一份文件就從「浪費一輪」變成「靜默錯誤」。

### 處置與前十個不同

前十個是**補接線**。這一個是**對帳**：
每次一個階段完成（F 步這種），**把指著那個階段的文件全部 grep 出來讀一遍**。
而 ⚠️ **它今天沒有機械化的檢查**——本檔的第十一個實例，就是這個機制自己的殼。

## 剪枝力：它排除什麼

對任何一條規範性陳述（原則、成功標準、契約、註解裡的保證）問一句：

> **「如果有人違反它，什麼東西會變紅？」**

- 答得出 → 這條規範有執行機構
- **答不出 → 它是裝飾**，不論措辭多強（「MUST」「0 容忍」「零 todo」都不算）

反過來也剪：**不是每條規範都值得執行機構**。判準是知識庫既有的那條——「砍了 AI 會不會默默跳過？會 → 留；不會 → 砍」。答不出「什麼會變紅」而且**跳過也沒人在意**的，該砍的是那條規範本身，不是補檢查。

## 推論：新增規範時，同時交付它的執行機構

不然它從第一天就是殼。這條適用於：

- **新原則** → 交一條測試，或明說「這條靠人 review，沒有機械檢查」
- **新契約**（序列化格式、膠囊格式、埠協定）→ 交驗證器；版本欄位要**被 branch on**，不是只存在
- **新的「不准」**（不准雙重真相、不准跨層 import）→ 交 audit 測試

這正是 [元件膠囊重構](../draft/retired/2026-08-05-元件膠囊重構.md) 的 P0 在做的事：**它不加任何新規範，只是讓三條已經寫下的原則第一次真的被檢查。**

## 落實

- **[階段 6.5](../vision.md) 的 P0 四條護欄已實作**（2026-08-06，`specs/049-audit-guardrails`）——就近性（P3）／中立性（P9）／完備性（P2）／缺陷帳（使用者明示指令）。四條規範第一次真的被檢查，實測基線：中立性 20 檔／完備性 🈳92 ❌5／缺陷帳 85 筆／就近性平均 8.5 檔
- **P1 第五條護欄：辨識歧義**（2026-08-06，`specs/051-lift-claim-arbitration`）——P3「歧義在註冊時仲裁」第一次有執行機構。基線：8 個同優先權群組／10 對確定會撞／18 對無法確定／11 處重複登記。判定保守，**判不出來一律歸「無法確定」且不計入安全**
- **052 存檔完整性護欄**（`specs/052-storage-integrity-gate`）——`version` 那一列的執行機構。基線 0／0／0，健康檢查靠**注入**不靠數字
- **053 執行器重複註冊護欄**（`specs/053-declare-noop-execute`）——「同一概念的執行器被註冊幾次」，此前完全沒有東西在看。它咬過一次：四個轉型概念各被註冊三次，最後贏的是空操作
- **第一條判準（讓正確的那個說話）也在 053 落實**——但實測 34 個候選裡只有 12 個配得上宣告，見上方
- **054／055 執行路搬進膠囊**——模組本來就有四路，執行那一路住在核心層。補上之後核心的語言耦合從 216 降到 55 筆
- **第八條護欄：有實作卻沒宣告**（`specs/055-finish-executor-move`）——見下方「護欄常常只問了一個方向」
- **P9 的 import 檢查**（同一輪）——P9 原文寫的是「核心無 `languages/cpp/` import」，而中立性護欄從第一天起數的是**概念身分字串**。**那條原則自己寫下的檢查，兩個月來沒被做過**
- **第九條護欄：抽象層完整性**（`specs/056-abstract-concept-integrity`）——131 個父概念宣告裡 98 個指向不存在的概念，而查詢函式對「沒宣告」與「指不到」**回傳同一個值**。見 [history/019](../history/019-跨語言抽象層從假定可用到實測七成五是破的.md)
- **第十條「雙重真相」與第十一條「欄位寫入」**（`specs/057-single-source-input-names`）——插槽名的唯一真相採用率 9% → 100%；15 個靜默 catch 從沉默變成可量測
- **棘輪改為雙向**（`assertRatchet`）——**單向的棘輪不會自己收緊**。改善訊息印在 stdout 上沒有人會去改檔案，只有紅色會
- `tests/baselines/*.json` ＋ `tests/integration/audit-*.test.ts`——基線與棘輪。**明確否決 vitest snapshot**：`-u` 會靜默更新，等於「跑一下就自動接受惡化」，那本身就是本概念在講的殼
- [`/over-justify`](../skills/over-justify/SKILL.md)——上游的價值判斷：這條規範／抽象賺不賺得起位置
- `/component-refactor`——「偵測四路完備性缺口、死概念」的能力**早就寫好了，只是沒有人在 CI 裡跑它**（這件事本身就是本概念的又一個實例）

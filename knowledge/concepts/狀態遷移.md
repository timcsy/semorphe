# 狀態遷移（State Migration）

一樣東西的**形狀變了**，而你手上還有一份**按舊形狀做出來的東西**——
那份東西怎麼過來？這個問題每次出現，答案都是同一個形狀：

> **按鑰匙配對，配得上的搬過去，配不上的【必須有明確處置】。**

而三個字裡最容易被丟掉的是最後那個：**明確**。

## 三視角

- **原則**：P6 誠實降級（「不確定時保留原始資訊，**禁止**給出一個看起來合理的結構」）
  ——配不上而靜靜丟掉，就是給了一個看起來合理的結構
- **願景**：hot-fix（執行中改結構）、外接執行器、存檔改版，三條路**共用這一個機制**
- **經驗**：「一個被重畫過的視圖，它的復原歷史描述的是另一份真相」——付過學費的那一次

## 四個不相干的世界，收斂到同一招

| 世界 | 機制 | 配不上的怎麼辦 |
|---|---|---|
| **Erlang/OTP** | `code_change(OldVsn, State, Extra)` | 你自己寫，而**它是具名的回呼**——不寫就不給你熱更新 |
| **CLOS** | `update-instance-for-redefined-class` | 被丟棄的槽**捕捉成一份 plist 交給你** |
| **PyTorch** | `load_state_dict(strict=False)` | 回傳 `missing_keys` / `unexpected_keys` |
| **Semorphe** | `core/flow/layout-key.ts` 三把鑰匙（內容／行號／路徑） | 有**配對率門檻**，低於它就退回自動排版 |

⚠️ **而 JVM HotSwap 是第五種答案：不准變形狀。** 那也是一個合法的處置
——它只是把「明確」推到極致：**形狀變了就重啟**。

> **沒有一個系統允許「隨意改形狀 ＋ 隱式修好狀態」。
> 允許改形狀的，都要求你【說出狀態怎麼遷移】；不想說的，就禁止改形狀。**

## 🔴 這個概念的剪枝力在哪

它會擋掉三種提案，而三種都很吸引人：

```
① 「配不上的就用預設值」          → 那是靜默降級，P6 明文禁止
② 「配對器夠聰明就不用處置」       → 啟發式沒有「夠聰明」這個狀態，只有「錯的時候你知不知道」
③ 「先做，配不上的情況之後再說」   → 那個「之後」不會來：它不報錯，所以沒有人會回來
```

而 `strict=False` 那個旗標是最好的反例教材：**它有回傳值，而多數人不看**。
一個「有出聲但沒有人聽」的機制，與靜默是同一件事。

> **明確處置 ＝ 讓配不上這件事【擋住流程】或【出現在畫面上】，
> 而不是出現在一個回傳值裡。**

## 這個專案裡它出現過的地方

| 場景 | 舊形狀 → 新形狀 | 鑰匙 | 配不上時 |
|---|---|---|---|
| 流程佈局還原 | 上次的樹 → 這次的樹 | 內容／行號／路徑 | 低於配對率門檻 → 退回自動排版 |
| 存檔改版 | v(N-1) → vN | 欄位名（`SAVED_STATE_FIELDS` ＋ `satisfies`） | 認不得的 ID **回退到預設**，不崩潰也不留空白 |
| 🔴 Blockly 的復原 | 重畫前的工作區 → 重畫後 | **沒有鑰匙——它存的是命令** | **沒有處置**：一顆 `int x;` 憑空長回來 |

最後一列是這個概念的**反例**，而它是實際發生過的缺陷：

> 「那顆積木屬於**重畫之前的那個工作區**。重放它等於把一個已經不存在的過去
> 接回現在的畫布上」——`ui/panels/blockly-panel.ts`

**根因用這個概念一句話講得完**：它存的是**命令**（「把積木移到這裡」），
而命令的意思取決於它作用的那個世界；**事實**（「節點 X 的 name 從 a 變成 b」）才有鑰匙。

## 判準（拿來測一個設計）

1. **鑰匙是什麼？** 答不出來 ⟹ 你存的是命令不是事實，遷移不可能對
2. **鑰匙會不會隨無關的編輯而變？** 會 ⟹ 它報的不是遷移失敗，是 diff
   （實測：用 `檔案:行號` 當鑰匙，一次正確的清償讓整片被判成「新增違規」）
3. **配不上的時候，使用者看得到嗎？** 看不到 ⟹ 它是靜默降級
4. **配對是啟發式的嗎？** 是 ⟹ **把結論寫成事實**，否則重放時會再猜一次而給出不同答案

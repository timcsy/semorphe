# 元件（Component）

**元件是語義真實在系統裡的單位**——有身分、有埠、有參數，並向外投影出形態與行為。「一個積木」「一顆零件」「一個 UI 按鈕」是同一個東西在三個域的名字。

這個概念的用途不是當口號（「一切都是元件」泛到能裝任何東西 = 沒有剪枝力的假母概念），而是當**一張五槽模板**：填得出就白拿整套機器（登錄／投影／分步播放／符合性／跨域組裝），填不出就代表那個域不是元件，剪掉。

**三視角投影：**

- **原則**：根公理直接推論——語義結構是唯一真實，元件是那個結構的節點；投影是開放集合
- **願景**：跨域合流（軟體／硬體／UI）的整合契約，讓工具蓋一次 N 域通用
- **經驗**：碎裂與雙重真相的根因，是「同一個元件的槽散在按機制組織的檔案裡」

## 五槽

一個元件由五個槽組成。前三槽是**真實**（不是投影），後兩槽是**投影**：

| 槽 | 內容 | 是真實還是投影 |
|---|---|---|
| **身分** | `componentId` = **`<scope>:<name>`**——登錄表的鍵，跨域唯一 | 真實 |
| **接點** | 具名的對外掛接處，帶域標籤與**關係律** | 真實 |
| **參數** | 型別側宣告（`ParamSpec`）＋ 實例側存值 | 真實 |
| **形態** | 積木／文字／2D／3D／URDF——「長什麼樣」 | 投影 |
| **行為** | 直譯執行／電氣傳播／物理模擬——「做什麼」 | 投影 |

> **身分的格式已落地**（2026-08-08，`specs/103`）：`<scope>:<name>`，`scope` 表示
> **所有權**不是分類也不是位置——域已經是宣告裡的欄位，把它再編進 id 就是雙重真相，
> 而且是最糟的那種（**id 進了存檔改不動**）。
>
> 現行 scope：`lang`（跨語言軟體元件，32 顆）、`cpp`（145 顆）。
> 未落地：`hw`（硬體）、`@<user>`（第三方）。白名單是**明列的**——沒有它，
> `cop:foo` 這種錯字會被當成一個合法的新命名空間。
>
> **沒有裸名，沒有例外。** 不留「沒有冒號就是核心」的解析特例——
> 特例是偵測，統一格式是**消除**。
>
> `參數` 的規格化見 `specs/102`（`ParamSpec`：`kind`／`values`／`default`／`required`）。

## 命名（2026-08-09 定案的骨架）

### 名字有三層，而它們的可撤回性不同

這一層一層分開，是因為**「這個名字能不能自由改」有一個機械判準**：
它是 **bound** 還是 **free**——也就是**引用它的人，是不是都在你看得見的範圍內**。

α 轉換之所以免費，正是因為 bound 變數的所有出現都在 binder 的身體裡，你看得完。

| 層 | 是什麼 | 改名的代價 |
|---|---|---|
| **套件內部名** | **bound**——所有引用都在套件裡 | **α 轉換，免費** |
| **對外 id**（`cpp:string_size`） | **free**——存檔、其他套件、轉換規範在指它 | 要版本 ＋ 遷移表 |
| **顯示名** | 不是變數，是**投影** | 隨時可換（i18n 已在做） |

> **存檔是一個你看不見的引用**——在使用者的磁碟上、在明年。
> 所以任何進了存檔的 id，永遠是自由變數。這就是「id 進了存檔改不動」的根據。

**套件是 binder**；`cpp:` 是從 binder 外面指進去的合格參照；**裸名是自由變數**
（意義由誰載入了什麼決定）——這才是「核心不用裸名，沒有例外」的根本理由，
比「特例是偵測，統一格式是消除」更底層。scope 前綴同時在做 **capture avoidance**。

⚠️ **不採 `id ＝ 位置`**（Go／Modelica、de Bruijn 索引）。那是同一個老取捨：
名字對「重新組織」穩定、對改名脆弱；位置反過來。這個系統裡搬家是持續發生的
（F 就是把 177 顆全部搬進各自的目錄），改名是罕見且刻意的。

> **版本 = binder。** 存檔記 `套件@版本 ＋ 名字`，舊名字就綁在那個版本上，
> 而版本隨附的轉換表說它在下一版叫什麼。**版本化把自由變數重新綁起來**，
> 於是改名從不可撤回的決定變成「α 轉換 ＋ 一條版本邊」。

### 跨域的命名規則（少數，而且都導得出來）

**① 名字不記投影。** 任何「怎麼呈現／怎麼製造」的東西都不進名字。

| 域 | 錯 | 為什麼 |
|---|---|---|
| C++ | `string_length`（記 `.length()` 的拼法） | 拼法在 `codeTemplate` 裡 |
| 硬體 | `led_0805`（記封裝） | 0805 是封裝，是投影 |

KiCad 早就這樣分（symbol 與 footprint 分家）。

**② 名字不記會變的東西——那些各有自己的槽。**

| 進名字是錯的 | 該進哪個槽 |
|---|---|
| 尺寸／數量（`resistor_10k`、`array_2d`） | **參數** |
| 封裝／樣式／位置 | **形態** |
| 「跟誰接得上」 | **接點** |
| 「哪個語言／哪塊板子」 | **scope**（或實例屬性） |

**③ 主體在前，限定在後。** 不是美感——**排序即分群**，而登錄表／工具箱／目錄
（F 之後每顆元件一個資料夾）都吃這個順序。形式是「屬 ＋ 種差」：
`hw:led`（只有屬）、`hw:led_rgb`（屬 ＋ 種差）。

**④ 縮寫的判準是「新手需不需要展開」。** `strlen` → 要展開；
`LED`／`I2C`／`PWM` → 那**就是**它的名字，保留。

**⑤ 分隔符統一 `_`。** 不借 npm 的 `-`——那個慣例的理由（出現在 URL 與 shell）
在這裡不成立，我們的 id 出現在字串字面與目錄名。

**⑥ 對外 id 不得編碼套件的內部組織。** 重新組織正是套件會做的事。
`cpp:string_size` 的 `string` 是**主體**（過關）；`cpp:cmath_pow` 就會是錯的
（`cmath` 是標頭檔，是組織）。

### 各域自己的：封閉詞彙表，而加字是顯式動作

跨域規則只管**形狀**；用哪些字是各域的事（軟體的動詞與硬體的名詞根本不同）。

每個域帶兩份清單：**主體詞彙**（`string`／`led`）與**操作詞彙**
（`size`／`at`／`append`／`clear`／`find`）。而**同一個操作在任何主體上用同一個字**。

⚠️ **詞彙表必須是白名單，加一個新字是顯式動作。**
免費加字的話詞彙表會爆炸，三年後回到雜亂無章；必須改一份明列清單的話，
**有人會在寫 `length` 的時候看到清單上已經有 `size`**。

這與 scope 白名單是同一個機制（「明列清單，不是任何冒號前的東西」），往下一層套用。

### ⚠️ scope 是**套件擁有者**，不是語言（2026-08-09 修正）

我們一路把 `cpp:` 讀成「C++ 這個語言」。**不對**——它是「**第一方的 C++ 套件**」。

第一方的情況下兩者剛好重合（`cpp:` 的東西都針對 C++），所以區別看不見。
**第三方一出現就分開了**：

有人發佈 20 顆 Boost 的元件，語義上是 C++ 的，但擁有者不是第一方，
所以它們是 `@someone:*`。而一支 C++ 程式可以自由混用 `cpp:` 與 `@someone:` 的元件。

| 講過的 | 更準的 |
|---|---|
| 各**語言**自理 | 各**套件**自理 |
| scope 表示語言 | scope 表示**擁有者**；「針對哪個語言」是**欄位** |

這其實才符合 D 自己的決定——「scope ＝ 所有權，不是分類、也不是位置」。
把它讀成語言，是因為當時只有第一方。

**連帶的好處**：`@someone:boost_vector` 宣告一條轉換邊到 `cpp:vector_declare`，
就**自動進了同一個抽象元件**、出現在同一個圖鑑條目底下——
不需要第一方批准，不需要改 `cpp:` 一個字。

> **「方便大家擴充」的實際樣子不是給人一個地方塞東西，
> 是讓他塞進去的東西自己接得上既有的意義。**

### 名字撞不了，而 `@` 的重載只在人機介面

`cpp` 撞不了：`@` 是第三方標記，第一方 scope 是白名單。
（npm 同一個模型：`react` 是裸名，`@babel/core` 是有主的。）

`@` 確實被用了兩次——`@timcsy:x` 的 scope 標記與 `x@3` 的版本。
但**版本不進 id**，資料裡是 key-value（`packages: { cpp: 1 }`），
`@` 只出現在它原本的意思上。

剩下的只有**文件與 CLI 怎麼寫**。npm 靠位置消歧（`@babel/core@7.0.0`）活得下去，
照抄即可——它不會傳染到任何持久化的東西。

### 開放生態系的誠實限制

第一方（`lang:`／`cpp:`／`hw:`）可以在 CI 強制；`@someone:` 管不到。
第三方靠**誘因**：照著詞彙命名 → 排在對的地方、被對的搜尋找到、
轉換規範好寫、共用實作的槽對得起來。

→ 詞彙表該是**一份公開、可提案擴充的清單**，而不只是規則。
第三方需要新動詞就提出來——那同時是「有人在用」的訊號。

### `name` 的階層——`.` 是真實，`/` 與 `_` 是投影

> **狀態：規則已定，尚未實作**（2026-08-13 三輪討論）。
> 今天 177 顆全是扁平的 `cpp:*`，**帶 `.` 的身分 0 顆**——語法位置空著。
> 改動清單與未決項見 [draft/Python 的 package 怎麼收](../draft/2026-08-13-Python的package怎麼收.md)。

Python 進來時 `numpy` 該住哪，逼出三條規則。

#### ① `numpy` 在 `python` 底下，而那是「scope ＝ 擁有者」的直接推論

`cpp:` 不是「C++ 這個語言」，是「**第一方的 C++ 套件**」（見上一節）。
同理 `python:` ＝ 第一方的 Python 套件，**而我們寫的 numpy 支援住在裡面**：

```
python:numpy.linalg.solve
```

⚠️ **而「讓 numpy 自己當 scope」是錯的**——它把「針對哪個語言」丟掉了，
於是同名 package 跨語言就會撞：

```
python:json.loads   ⎫ 不同 scope，永遠不撞
js:json.parse       ⎭
json:loads          ← 若 scope ＝ package，這兩個語言的 json 撞在一起
```

**同名 package 是常態**（`json`／`random`／`math`／`time`／`socket`…），不是邊角。

而 NumPy 團隊哪天自己發佈膠囊，那是 `@numpy:array`——**第三方是另一條路，不是替代**。

#### ② 階層只能來自**語言的語義**，不准表達我們的分類

| 階層的來源 | 准嗎 | 為什麼 |
|---|---|---|
| package 名（`numpy`）、子模組（`linalg`、`os.path`） | ✅ | **不是我們的決定，我們改主意它也不會變** |
| **我們發明的分類**（`containers`、`math`） | ❌ | **分類會變，而變了就是搬家** |

第二種正是 [history/047](../history/047-模組是搬家的中途站不是終點.md) 記過的坑
（「模組是搬家的中途站，不是終點」——`<cmath>` 的五面牆全空，
而那個組織方式五個月前才剛被稱為完成）。

⚠️ 而分類**已經有地方住**：`forms/blocks.json` 的 `category` ＋ 工具箱的有序來源。
再寫進路徑一次就是兩份真相，**而路徑那份會贏**（它決定檔案在哪），於是 `category` 變裝飾。

> **分類也是形態——它不該決定位置。**

#### ③ `.` 是真實，其餘兩個是投影

```
真實    componentId       python:numpy.linalg.solve
投影    目錄            components/python/numpy/linalg/solve/      "." → "/"
投影    Blockly type    python_numpy_linalg_solve                  "." → "_"
```

**選 `.` 而不是 `/` 的決定性理由是核心純淨性**：`idToDir` 住在
`src/core/component/types.ts`，而中立性護欄的 `NEUTRAL_DIRS` 第一項就是 `src/core`。
**所以分隔符不能跟語言走**（那需要核心知道這顆是哪個語言的）——
必須統一，那就該選最語義的那個。

兩個次要理由：

- `/` 會讓 `idToDir` 退化成字串拼接，而
  **一個不需要轉換的映射，會讓人忘記那是兩個東西**——你們剛把「位置不是身分」拆開
- `from numpy.linalg import solve`——**學生寫的就是 `.`**

❌ **`_` 不行**（雖然零改動且 Blockly 安全）：`numpy_linalg_solve` 是
`numpy.linalg.solve` 還是 `numpy.linalg_solve`？**`_` 今天已經是詞之間的分隔**
（`vector_declare` ＝ vector ＋ declare），而目錄映射需要知道邊界。

#### ⚠️ 代價，而它已經有機制接著

`deriveBlockType` 多換一次會開一個撞名：`numpy.linalg_solve` 與
`numpy.linalg.solve` 導出同名。**`assertDerivedNamesUnique()` 已經在擋**，
而它的檔頭逐字：「**代價要有機制接著，不能只有註解**」。

那條機制擋的正是最可怕的症狀：「後登錄的蓋掉先登錄的，於是
**一顆積木從工具箱消失而沒有任何錯誤**」。

#### C++ 不跟進——而不一致是刻意的

`<vector>` 其實就是 package，所以 `cpp:vector.declare` 更一致。
**而它要付 177 顆改名 ＋ 一次性存檔轉換**（`history/026`：P8 不做向後相容
**不管語義詞彙本身**），收益只是目錄好看一點——
而 `requires: ["<vector>"]` **已經記了那個資訊**。

> **階層是選用的，不是強制的。一致性不值那個價。**


**組裝**（哪些實例經哪些接點相接）也是真實，但它不屬於單一元件，屬於元件之間。

接點是語義的一部分、與檢視無關——這是判斷一個東西該進哪一槽的試金石：**換一個檢視它會變嗎？會變就是投影，不會就是真實。**

### 接點的關係律：三種，不是一種

**接點不都是埠。** 決定「兩個接點接起來會發生什麼」的，是**關係**：

| 關係 | 結構 | 律 | 是埠嗎 |
|---|---|---|---|
| **組合**（composition） | 樹 | 父擁有子；恰好一個父；刪父連子一起死 | ✗ |
| **守恆**（conserved） | 約束網 | 不可自由複製；全網求解（見下方兩種律） | ✓ |
| **資訊**（information） | 有向邊 | 一源 fan-out 多讀者，可複製、無基質 | ✓ |

**埠 = 關係為守恆或資訊的接點**——對等、可 Link、雙方獨立存活。組合接點（積木的 `body` 槽、UI 的 `slots`）是**擁有**不是**連接**，不是埠。

**`relation` 屬於「邊」，不屬於「接點」。** 接點宣告的是「我能參與哪些關係」（`accepts`）。硬體是退化情形——兩端都是電氣接腳，邊必然守恆，看起來像接點自己的性質；軟體是一般情形——同一個語法接點，關係由流過的**型別**決定：

```rust
let b = a;      // a: i32    → 複製，資訊
let b = a;      // a: String → move，守恆
let r = &a;     // 共享借用 → 守恆基質的非消耗性投影，可 fan-out
let r = &mut a; // 獨佔借用 → 取得驅動權，不可 fan-out
```

### 守恆＝有基質；其上的邏輯是基質的投影

**守恆接點常常同時載著資訊**——一條 GPIO 線既是電壓（守恆）又是邏輯位階（資訊）。單值 `relation` 看似裝不下，解法是不要把它當第二條關係：

> **守恆 = 有守恆基質；其上的邏輯／命令是該基質的投影。**
> **資訊 = 沒有基質的純資料流**，可自由 fan-out。

於是 GPIO 的關係是**守恆**，邏輯位階是它的投影。這和本檔另外兩個判決（「行為軌跡是投影不是真實」）是同一把刀——**同一個論證形狀成立三次。**

推論：**adapter 邊界被釘在型別上**。資訊↔資訊直接接；一端有守恆基質就要 adapter。Arduino API 就是這層的既有實證——`digitalWrite`/`analogWrite` 是資訊→守恆，`digitalRead`/`analogRead`/`pulseIn` 是守恆→資訊的投影，`pinMode` 宣告的正是「這個接點在網裡是 driver 還是 reader」。

### 守恆的兩種律

| `law` | 律 | 域 |
|---|---|---|
| `balance` | across 相等、through 相加為零（克希荷夫／力平衡） | 電氣 ✅ 已驗；機械、未來熱／流體＝**設計意圖，未驗**（見下） |
| `exclusive` | 資源不可自由複製，合法性需要一份帳 | Rust ownership、`unique_ptr`、`shared_ptr`、mutex、file handle |

兩律**可證不同**，這是分律賺得起位置的理由：**open-drain／I2C 的多 driver 在 `balance` 下合法，在 `exclusive` 下非法**。

**為什麼是兩律**——差異的根不在「守不守恆」，在**有沒有可以退回去的連續基質**：

| | `balance`（物理模型） | `balance`（理想化模型） | `exclusive` |
|---|---|---|---|
| 律本身 | **永遠可滿足**（短路也有解，只是電流很大） | **借來可滿足性違反** | **只有可滿足性** |
| 違反長什麼樣 | 解出來的值比**額定**（過流、超出 SOA） | 方程不一致，無解 | 二值，沒有「違反多少」 |
| 需要的機器 | 求解器 ＋ 門檻 | 可滿足性檢查 | 可滿足性檢查 |

**KCL 從不禁止任何東西；禁止的是額定。** 借用檢查沒有「額定」——它直接說有沒有合法指派。

**理想化是可滿足性違反的來源，跨域同形**（ArduinoCAD 回送）：

| | 理想化 | 後果 | 去掉理想化 |
|---|---|---|---|
| 電氣 | 理想源（0Ω 推挽） | 5V 與 0V 短接 → KVL 方程不一致、**無解** | 有限輸出阻抗 → 解存在＋過流（額定違反） |
| 機械 | 剛體（無順應） | 兩馬達不同轉速同軸 → **無合法角度指派** | 有扭轉順應 → 軸扭轉＋強度違反 |

所以 `CONFLICT` 和運動學鎖死是**同一個現象**——都是理想化的產物。

### 這條讓 `law` 塌回基質

於是兩律的差別**塌回本節自己的核心論題**：

- **有連續基質** → 退得回去 → 物理模型可滿足、違反是額定 → `balance`
- **沒有連續基質** → 退無可退 → 只有可滿足性 → `exclusive`

`law` 不是第二條獨立的軸，**它是「有沒有連續基質」的推論**。「守恆＝有基質」這個判準在本節第四次成立。

> **可測後果（未驗，標為預測）**：若 `law` 可從基質推導，它就該是**衍生欄位而非宣告欄位**。而且這預測**軟體域最終也會有 `balance`**——速率限制／頻寬／token 預算有連續基質，超用是降級（額定違反）而非失敗。目前無證據。

> **機械域的誠實標記**（ArduinoCAD 查證）：他們的 `coupleKinematics` 目前是**單向剛性導出**（driver→driven，1:1），不是全網平衡求解；兩端同 role 直接略過、不產生 CONFLICT；無額定檢查；只跑開放運動鏈。**「機械是 `balance`」是設計意圖，不是已實作驗證的現實**——上面那些表**只有電氣列被驗過**。要等機械長出閉環或多驅動（兩馬達一軸、四連桿）才會同時取得額定面與可滿足性面。

> ⚠️ **一句被否決的過度宣稱**：本檔原版寫「Rust 的 aliasing XOR mutability 就是麵包板的『一個 driver、多個 reader』」。**不成立**——電氣的 `CONFLICT` 不是「不只一個 driver」，是「不只一個**不一致**的 driver」：兩個推挽都 HIGH 不衝突；open-drain／I2C 多 driver 合法且正常（那是 I2C 仲裁的整個基礎）。而 Rust 不管一不一致，第二個 mutator 就是錯。
>
> **正解**：數位推挽的「一線一 driver」是**施加在 `balance` 基質上的 DRC 慣例**，不是物理律——`balance` 律結構上不可能禁止它。這也解釋了為何 `CONFLICT`／`FLOATING` 是「求解的定性」而非電壓讀數：**數位 `NetLevel` 模型把 DRC 慣例烘進了模型本身**；類比模型裡沒有 `CONFLICT`，只有分壓出來的一個電壓。
>
> 教育後果：初學者被教的「一線一 driver」是慣例非定律，**工具該講對，否則學生一碰 I2C 就困惑**。

仍然成立的對應（弱一點，但足夠）：

| | 電氣 net | Rust ownership |
|---|---|---|
| 無驅動／未定 | `FLOATING` | use of moved / uninitialized value |
| 非消耗性讀取可 fan-out | `digitalRead` ×N | `&T` ×N |
| 取得驅動權 vs 讀取 | `pinMode(OUTPUT)` vs `INPUT` | `&mut` vs `&` |

**`&T` 之於 ownership，就是 `digitalRead` 之於電壓**——非消耗性的投影。這條沒被推翻，它正是「守恆＝有基質、其上是投影」在第二種 law 下的實例。

**不加第四個 `relation` 值**——那會把「兩者都是不可複製＋全網求解」這個深層相同點藏起來。

> **未解**：`exclusive` 底下其實有兩條不變式——**銷毀恰好一次**（`unique_ptr`／`shared_ptr`／Rust drop）與**同時至多一個可變存取**（`&mut`／mutex）。兩者的關係未證。
>
> 一個**賭注級**的收斂方向（來自 ArduinoCAD）：真正的不變式是「恰好一次銷毀／無 UAF／無 double-free」，而 **static borrow-check 與 dynamic refcount 是同一不變式的兩種執行**。若成立，`shared_ptr` 仍是 `exclusive`、只是動態強制。
>
> mutex 看似不合（它跟銷毀無關），但有個更好的歸宿：**Rust 的 `Mutex<T>` 是「動態產生 `&mut` 的東西」**（`lock()` 的 guard deref 成 `&mut T`）——不是第四類，是 `exclusive` 邊的動態產生器。**當方向、別當結論。**

### 第三層：角色

律**之內**還有角色，它是邊在該律內的進一步定性：

```
關係 relation    composition | conserved | information
  └ 律 law       （conserved 才有）balance | exclusive
      └ 角色 role  driver / reader   ·   &mut / &
```

`pinMode` 改的是**角色**，不是 relation（relation 固定為守恆-balance）。這正對映 Rust 的 `&mut`／`&`——`exclusive` 律內的兩個角色。**「角色在律內變、律本身不變」兩域一致**，這反過來加固「relation 屬於邊、接點宣告 `accepts`」的框架。

### 這條戳破了膠囊格式的一個假設

守恆的兩種律都需要**全樹流敏感約束求解**——電氣傳播（誰在驅動、驅動到哪、有沒有衝突）與 borrow check（第 3 行的 move 殺掉第 5 行的 use）是**同一類機器**。

（**收窄**：同一類、不同終局判定——照上面那張表，`balance` 是求解器＋門檻、`exclusive` 是可滿足性檢查。共用的是**遍歷與傳播骨架**，不是判定邏輯。）

[語義診斷系統](../draft/2026-08-05-語義診斷系統.md) 的三層（節點 constraint／parent-sibling 關係／語言特有規則）**裝不下它**——第 2 層是局部結構檢查，借用檢查是流敏感的。

所以：**per-元件的膠囊裝不下全樹約束**。那是 kernel 的一條新脊椎，不是元件的第六個槽。加 Rust 之前必須先有這個位置。

兩件事跟著這條走：

- **關係律跟著「資源」走，不跟著「域」走。** 電氣 net 與機械連接結構長得一樣，因為它們是**兩個域的同一種東西**（`balance` 守恆網）。所以該共用的是**守恆求解器**，不是把電氣接腳和機械埠併成一個陣列。（**注意**：類比訊號驅動**不是**資訊——net 上的電壓當然守恆。它是基質本身，數位位階才是它的投影。這一格 ArduinoCAD 前後兩封改過分類，第二封才對。）
- **接點的儲存要加法式、域專屬。** 電氣接點帶電氣能力（2 欄）、機械接點帶運動框（9 欄），形狀不相交、也沒有消費者統一遍歷它們——硬合成判別聯集是**反壓縮**。統一發生在**接縫投影**上：接點 `{name, kind, accepts}`、邊 `{relation, law?, role?}`。

`kind`（電氣／機械／結構／資料）是**域標籤，協定不需要理解它**，照「跨域機器需不需要理解」那條判準，它是不透明酬載；`relation`／`law`／`role` 才是協定的心臟，因為它們決定連接律。加一個新域＝加一個 `kind` 值，協定不動。

> **來源與修訂**：本節是 2026-08-05 與 ArduinoCAD 五封往返協商的產物，被推翻過三次：
>
> 1. **原版**主張「三個平行埠陣列合併成一個 `ports` 帶 `kind`」＋「`children` 是 containment 型的埠」。**ArduinoCAD 推翻**：合併不相交型別是反壓縮，過不了 over-justify（**而 over-justify 不是成本測試，「不計成本」豁免不到它**）；組合不是連接，把 containment 塞進埠是類別錯誤。
> 2. **本側第二版**用單值 `relation`。**ArduinoCAD 推翻**：電氣接點同時是守恆又載資訊，單值裝不下 → 解法是「守恆＝有基質，其上的邏輯是投影」。
> 3. **本側第三版**寫「aliasing XOR mutability 就是麵包板規則」。**ArduinoCAD 推翻**：那是 DRC 慣例不是物理律（見上方警語）——而**這個更正反而救了分律**，因為它提供了兩律可證不同的實例。
>
> 本側的貢獻是：接點／埠拆兩詞、`kind`／`relation` 分家、composition 收進 `relation`、`relation` 屬於邊、`law` 二分、「永遠可滿足 vs 約束圖形狀」那條根。既有實證：Modelica 的 physical／signal connector、bond graph 的 effort／flow、Arduino API 就是 adapter 層。
>
> **完整現場**（五封的往返、每一次被推翻的當下、以及為什麼敵對協商做得出兩邊單獨做不出的東西）：[episodes/2026-08-05-跨專案敵對協商](../episodes/2026-08-05-跨專案敵對協商.md)

## 真實與投影：兩族並列

根公理已經列出三種投影：

```
「x++;」              ← 文字投影
[變數 x 加1（++）]     ← 視覺投影
 x: 0→1               ← 行為投影
```

前兩者是**形態**，第三者是**行為**。**這兩族並列，不互相包含。**

一個常見的誤推是「行為也是投影，所以行為屬於『表示』」——不成立。「投影」是兩族的**上位詞**（公理層），不是其中任一族的欄位名。若讓形態那一槽吃掉行為，它就退化成「所有非身分的東西」的雜物袋，失去剪枝力。

反過來，這也解釋了為何 `representations` 這個欄位名不好：它只涵蓋形態，卻佔著一個看起來像上位詞的位置。**上位詞是「投影」，形態那一槽就老實叫形態。**

## 否決：行為軌跡不是真實

一個誘人但錯誤的提案是：把「訊號／狀態隨時間的行為軌跡」當成共享的真實，而程式碼／硬體／模擬／執行是「產生它／承載它／算出它／實現它」的四個角色。

**否決，理由與 [墓碑](../history/014-墓碑目錄.md) 否決 λ-core 完全同構：**

以軌跡為真實，`count_loop` 和手寫 `while` ＋ 計數器會塌成同一個東西——它們產生**相同的軌跡**，卻是**不同的概念**。真實變成軌跡 → 區別消失 → 可逆性從 R0 掉到 R1 → 摧毀語義意圖。這就是 lowering，只是換上物理學的外衣。

**正解：行為軌跡是行為投影吐出來的東西，不是真實。** 那四個角色不是「四者對真實的角色」，而是**同一個元件的四個投影去向**。真實始終是元件。

## 為何是「元件」不是「概念」

`concept` 曾是首選（它連著根公理的「元件節點」），四條理由推翻它：

1. **`concept` 是 C++20 的關鍵字**（`template<typename T> concept Integral = …`）。Semorphe 主要是 C++ 工具，同一畫面上會出現兩個 concept——這是教育 telos 上的實傷。
2. **「概念」聽起來在腦子裡**，但它是系統裡最真實的東西。
3. **它不蘊含埠與可組裝**，`component` 天生蘊含。
4. **三域通用性**——電子元件／軟體元件／UI component 是唯一一個三個域都通用的詞。學習遷移（一個心智模型教一次通吃）只有它兌現得了。

**代價，要誠實記**：`concept` 帶著一個 `component` 給不了的意思——**「發現而非發明」**。那句話是承重的，它是墓碑否決 λ-core 的核心論據。

**解法是分工，但只有一個進資料結構**：

- **元件** = 系統裡的單位。有 `componentId`、進登錄表、被實例化、有埠有參數有投影。**唯一的技術名詞。**
- **概念** = 一個元件**所承載的意義**。只活在原則、墓碑、教學語言裡，**不是欄位、不是 id、不是型別**。句子長這樣：「這顆元件承載 `count_loop` 這個概念」。

這樣墓碑的論據原封不動（真實是語義概念），資料結構拿到三域通用的名字。這個分工本身就是根公理的形狀——**概念是意義，元件是它在系統裡的身分**。

**⚠️ 而「分工」不等於「概念被廢掉」**（2026-08-20 由人補充）：

```
                    元件（跨域的父概念）
                   ╱                  ╲
      語言域 → 概念                    硬體域 → 零件／器件
   （if、print、變數宣告）            （電阻、LED、腳位）
```

在語言域，人們本來就把一顆元件叫做「概念」——而那**不與上面的分工衝突**，
因為語言域的元件所承載的**正是意義**。硬體域沒有這個習慣：一顆電阻不是一個概念。

所以判準是**單向**的：**「元件」剪得掉硬體讀不通的用法，「概念」剪不掉**
——這正是父概念要有的剪枝力，也是為什麼進資料結構的只有一個。

> **推論**：`knowledge/concepts/` 這個資料夾**不改名**。它裝的是「這個專案的概念」（知識層），
> 不是「程式的元件」（產品層）——同一個詞在兩層各有各的正確用法。

其餘死掉的候選與死因：`Entity`（軟體界一律指實例，撞「實例」）、`Unit`（無剪枝力，撞 unit test）、`Archetype`（已被參數化 CAD 佔用）、`Category`（撞範疇論＋toolbox category）、`Module`（撞 std 模組）、`Noumenon`（哲學正確但過重）、`Sememe`（語言學上是 morpheme 的對偶、正好對上 σῆμα＋μορφή，但它指「**最小**意義單位」而概念可分解，語義錯了——etymology 誘人但不是論證）。造新詞一律否。

## 元件住在哪：域／語言／layer 三軸正交

「元件是三域同一抽象」有一個直接推論——**域必須是一條獨立的軸**。三個軸不能疊：

| 軸 | 是什麼 | 值 |
|---|---|---|
| **域** | 決定有哪些接點與**關係律** | software / hardware / UI |
| **語言** | **只在 software 域內有意義** | cpp / rust / python |
| **layer** | **語言內部**的依賴序（Layer 2 依賴 Layer 1） | universal / lang-core / lang-library |

`layer` 是語言內部的階；**硬體不是「更深的 layer」，它沒有 lang-core 可以依賴**。把硬體塞進 layer 序列或塞進 `languages/` 底下，兩種都是類別錯誤。

**判準**：一個元件的家由「域 →（若是 software）語言 → layer」三段決定；機制不看這三段中的任何一段（`kind` 是不透明酬載）。

推論出兩條可測的不變式：

- **就近性**——一個元件的實作應該只出現在它自己的資料夾
- **中立性**——kernel／app／render 的檔案**不准提到任何具體 componentId**

第二條就是**多語言／硬體就緒度的量化指標**，而且**不必等第二語言就測得出來**。（本專案 2026-08-05 的基線：12 個 kernel／app／interpreter 檔硬編 C++ 專屬 componentId——那 12 個就是 Rust 或硬體進來時會爆的地方。落地計畫見 [元件膠囊重構](../draft/retired/2026-08-05-元件膠囊重構.md)。）

## 判準：哪些名詞必須統一

整合契約必須**薄**——只標窄接縫，域內部當不透明酬載。厚協定要罩住硬體＋軟體＋UI，會薄弱到近乎空。

**這條的命名推論——一個名詞要不要跨域統一，看兩件事：**

1. **跨域機器需不需要「理解」它的語義？**（登錄表／圖鑑／分步播放／符合性／跨域接線）
2. **學習者會不會跨域碰到它？**（教育 telos——學習遷移靠的是同一個心智模型搬到所有域）

任一為真 → 統一。兩者皆否 → 域內俗名，統一反而是厚協定。

注意判準問的是「**需不需要理解**」，不是「讀不讀」。反例：`role: 'statement' | 'expression'` 被登錄表**讀**著，但硬體域根本沒有這個分野——登錄表可以原封不動搬運它而不理解它（不透明酬載）。用「讀不讀」當判準會產生偽陽性，用「理解不理解」才剪得對。

於是「零件 vs 積木 vs 按鈕」的爭論消失——那是域內俗名。真正要統一的只有上面那張表。

## 剪枝力：填不出就不是元件

母概念的價值在它**排除**什麼。對一個新的域，逐槽填：

**身分？接點＋每個接點的關係律？形態＋符合性不變式？行為＋時鐘？組裝？**

- 填得出 → 學到具體東西，且白拿整套機器
- 填不出 → **這個域不是元件**，別硬套

用 UI 域驗證（三域中業界最成熟的一域）：

| 槽 | UI 域 | |
|---|---|---|
| 身分 | `Button` 這個型別 | ✓ |
| 接點 | props（入）／events（出）／slots | ✓ |
| 關係律 | props/events ＝ **資訊**；slots ＝ **組合**；**沒有守恆** | ✓ 而且它**解釋了**為何 UI 最好教 |
| 形態 | 渲染的 DOM ／ JSX 文字 | ✓ |
| 行為 | state ＋ 生命週期 | ✓ |
| 組裝 | 組合樹（slots 嵌套）＋ 資訊流（event→state→prop） | ✓ |
| 符合性 | props 名 == 語義接點名 | ✓ |

七格全填得出，且**填的過程學到了新東西**：UI 是三個域裡**唯一沒有守恆關係**的——沒有過流、沒有反推、一份 state 可以餵無限多個讀者。這正是它最乾淨好教的原因，也是它的埠可以無腦 fan-out 而硬體不行的原因。這才是剪枝力兌現的樣子，不是口號。

三域擺在一起，關係律的分佈本身就是一張地圖：

| 域 | 組合 | 資訊埠 | 守恆埠 |
|---|---|---|---|
| 軟體（Semorphe） | `children` ✓ | 待補（積木輸出→輸入） | **Rust 之後 ✓**（`exclusive`） |
| 硬體（ArduinoCAD） | 擺放／持有 | **可能為零**（待對方確認） | ✓ 電氣 net、機械連接（`balance`） |
| UI | slots ✓ | props／events ✓ | ✗ |

三件事從這張表落出來：

- **`balance` 律只出現在硬體**——預測未來加熱學／流體域會重用同一張平衡網。
- **UI 是唯一完全沒有守恆的域**，這正是它最乾淨好教的原因，也是它的埠可以無腦 fan-out 而硬體不行的原因。
- **硬體的資訊埠是零**（ArduinoCAD 已查證確認：`src/model/` 只有電氣 `Net` 與機械 `mechanicalLinks` 兩種連接，都是守恆；訊號線的顏色、`DynamicBinding`、感測值／`distance` attr 三個疑似反例都不是元件間的可連接埠）。

**這解釋了為何硬體最難教**：初學者把一條線想成「送一個 1」（資訊），它其實是「驅一個電壓」（守恆）——**floating、contention、電流上限，就是守恆基質從資訊抽象底下漏出來**。這把「硬體難教」從模糊感覺變成型別層的必然。

## 組裝：三種關係邊，樹是其中一種的形狀

根公理已經寫死了「邊」：

> 程式是由「元件節點」和「關係邊」組成的語義結構：**在檔案內是樹，在檔案間是圖，在系統間是超圖**。

所以「組裝有邊」不是新決定，是**還原根公理**——現行 `SemanticNode` 只有 `children`、沒有具名的邊，是實作欠公理的債。

但**還這筆債不等於把 `children` 改叫埠**。三種關係各有結構：

```
組合  父─┬─子   樹。擁有、獨佔、生死與共。       ← children 在這裡
資訊  源──▶讀者  有向、可 fan-out、可複製。
守恆  ●───●───●  平衡網。across 相等、through 歸零。
```

`children: Record<string, Instance[]>` 是**組合關係**。要還的債是**把資訊關係補上**（積木輸出→另一積木輸入→硬體 pin），那是一條**新增的軸**，加法式，不是把 `children` 重新詮釋成埠。

**一個要標清楚的細節**：Blockly 的 value input（`arithmetic` 的運算元）在樹裡是組合，語義上卻帶資訊流向。這不是矛盾——**運算式樹是 DAG 在「無共享」時的無損編碼**。它變成真問題只在兩種情況：同一子運算式要餵兩處（共享），或跨元件接線（積木輸出→硬體 pin）。在那之前，用組合編碼資訊流是誠實且無損的。

**檢查它不違反墓碑**：`count_loop` 還是 `count_loop`，condition／body 還是具名組合接點，**沒有任何語義意圖被降級**。Sc2／Sc3 不破，可逆性不變。通過。

> ⚠️ ArduinoCAD 的經驗「**加法式併行通道 >> 加寬共享型別**」不只是 blast radius。原文的判準是「先問這是**加法**還是**改寫**」——那是語義問題，不是成本問題（原文：「數位 HIGH/LOW 本是類比電壓的量化讀數，兩者本就分層」；程式碼註解：「機械埠是**電氣之外的語義域**」）。本檔原版用「不計成本」豁免它，**豁免錯了層**。這條教訓對地基決定同樣適用。

## 現況落差（採用此表要改什麼）

| 名詞表 | 現行碼 |
|---|---|
| `componentId` | `SemanticNode.concept`（欄位名與型別 `ConceptId` 就已不一致） |
| `Instance` | `SemanticNode` |
| `params` / `ParamSpec` | `properties` 型別側 `string[]`（**只有名字，沒有型別、範圍、預設值**）／實例側 `Record` |
| `attachments` ＋ `relation` | `children`（全是組合關係，無 `relation` 欄位；**資訊軸尚不存在**——這是要加的那條，不是要改的那條） |
| `forms` | `blockDef` ／ `codeTemplate` ／ `astPattern` 分屬三個機制 |
| `ComponentRegistry` | `BlockSpecRegistry`（**以投影命名登錄表**，且有 `byConceptId`／`byBlockType` 雙索引） |
| `conformance` | 無名，只有零星 guard test |

`params` 那一列不只是改名——型別側只有名字清單，**沒有型別、沒有範圍、沒有預設值**，正是「複合型別字串解析」那條技術債的根因，也是 [元件膠囊重構](../draft/retired/2026-08-05-元件膠囊重構.md) 說的「結構化 property」增量。**改名時應連結構一起借過來。**

# 紀錄的腐壞（Record Rot）

**一份紀錄與現實的落差，不會自己出聲。**

它與 [執行機構](執行機構.md) 是姊妹，而**方向相反**：

```
執行機構   規範說了，而【沒有東西在執行它】       → 宣稱存在、檢查不存在
紀錄的腐壞  紀錄說了，而【它說的已經不是現實了】  → 檢查存在、【它守著一個過期的事實】
```

🔴 而後者更難發現：**測試是綠的**。那份紀錄裡的數字、理由、判定，
在寫下的那一刻全部正確——它們是後來才錯的，而**沒有人約好要回來看**。

**三視角投影：**

- **原則**：一條原則自己標記的缺口（P8 的「編譯器就是驗證器**假設所有程式碼都是你的**」），
  在那個假設失效之後**不會自己更新**
- **願景**：路線圖上的每一筆都是「當時看起來要做的事」——而其中有些
  **早就完成了**、有些**與別處的判斷打架**、有些**指的東西已經退場**
- **經驗**：底下那張表的每一列都是實測，而它們都是**綠著發生的**

## 一天之內量到的**九**種樣態（2026-09-06）

⚠️ 原本是七種——⑧⑨ 是**同一天稍後**又量到的兩種。
🔴 而那件事本身是這個概念最有力的證據：**一份「我們量到七種」的紀錄，
在兩小時之後就過期了。**

那天逐筆去清 vision 的「未清的債」，做法是**先驗再決定**。
八筆裡有**五筆**的紀錄與現實不符——而它們沒有一筆是「寫錯了」，
全部是「**寫的時候對，而後來變了**」。

| # | 樣態 | 標本 | 為什麼沒人發現 |
|---|---|---|---|
| ① | **這筆債從來不存在** | `structured_binding_declarator` 被列為缺陷，而量它的範例用了 `pair t{1,2}`——掉的是**初值列** | 報表上那一列寫著 X 的名字 |
| ② | **早就完成了** | 型別註解寫「⚠️ 過渡中：純名字清單（**124 顆**）」，而實測 **0 顆** | 那個數字自交付日就沒再量過 |
| ③ | **兩份宣告打架** | `FIELD_OWNERSHIP` 說 `blocklyState`「可以丟」，`REQUIRED_FIELDS` 說它**必填** | 執行的是驗證那一份，而寫另一份的人以為自己說了算 |
| ④ | **只在一個宿主成立** | 「重開後在原位」打了勾，而 `flowLayout` 在 IDE 那側**零筆** | 開發在瀏覽器裡進行 |
| ⑤ | **重開條件沒人量** | 一個決定附著「什麼時候重開」，而**沒有人去量它成立了沒** | 它與「永遠不重開」是同一件事 |
| ⑥ | **理由是猜測** | 「那些名字**幾乎沒有人會重新宣告**」——去做那件事，它照樣壞 | 那是關於**使用者**的猜測，不是關於**機制**的保證 |
| ⑦ | **指的東西退場了** | 「活動列＋檔案總管要由 `profile.features` 擋」——**活動列本身退場了** | 它留在清單上，看起來像一件還沒做的事 |
| ⑧ | **把幾條當成一條** | 「上面**三條**未做的驗收共用同一個前置：真的檔案，卡在 FSA 驗不到」——而其中一條走的是 `<a download>`，**根本不碰 FSA** | 它們**寫在一起**，而那個前置對其中兩條是真的 |
| ⑨ | **宣告了而沒有產物長成它** | `FIELD_OWNERSHIP` 宣告了四種歸屬，而匯出的檔案仍然把 13 個欄位混在同一層 | 一份打算**不會腐壞**——沒有東西會與它牴觸 |

⚠️ 而 ①～⑦ **沒有一個是「有人偷懶」**。每一筆都有完整的理由、
清楚的措辭、當時正確的數字。

> **一份紀錄的正確性有兩個時間點：寫下的時候，與被讀的時候
> ——而只有前者有人檢查。**

## 它們共同的根：**紀錄裡的每一個現況描述都是一個到期日**

看那七種樣態各自寫了什麼：

```
「純名字清單 124 顆」          一個【數字】
「它是 lift-pattern.json 的     一個【它現在長什麼樣】
  純資料樣式」
「那些名字幾乎沒有人會重宣告」  一個【關於使用者的猜測】
「活動列要由 features 擋」      一個【對現存事物的指涉】
```

**四種都是現況描述**，而現況會變。

🔴 而「理由」那一格最危險：一個**建立在現況上的理由**，
在現況變了之後**仍然讀起來很有道理**——它不會變成一句明顯的錯話，
它會變成一句**看起來仍然成立的錯話**。

> **一個判定的理由如果描述的是「它現在長什麼樣」，
> 那它會在那個樣子變了的那天變成一句錯話——而判定本身照樣通過。**

## 判準：什麼樣的句子會腐壞

寫一句紀錄的時候問：**這句話明年還會是真的嗎**。

| 會腐壞 | 不會 |
|---|---|
| 「今天有 124 顆」 | 「數量由 `<那條護欄>` 的基線說了算」 |
| 「它是一份純資料樣式」 | 「它**沒有** lift 路，理由是 ⟨那次翻車⟩」 |
| 「幾乎沒有人會這樣做」 | 「做了會怎樣：⟨量過的結果⟩」 |
| 「等 X 出現再做」 | 「等 X 出現再做，而 **X 是**⟨可以 grep 的東西⟩」 |
| 「這幾條共用同一個前置」 | 「這**一**條的前置是 X」——⚠️ **逐條寫，逐條驗** |
| 「我們把它分成四類了」 | 「⟨這個產物⟩長成那四類的樣子」 |

🟢 右欄的共同點：**它們錨在一個會自己說話的東西上**
（一條護欄、一次翻車、一份量測、一個 grep 得到的字串）。

> **一個錨在「事實」上的句子會腐壞；
> 一個錨在「證據在哪」上的句子不會——因為證據會自己更新。**

## 🟢 唯一有效的機制：**讓那個數字住在護欄的基線裡**

這個 repo 的棘輪基線（`tests/baselines/*.json`）就是這個概念的實作：

```
註解裡的「124 顆」    沒有人回來量  → 一年後它是錯的，而它讀起來很正常
基線裡的「124 顆」    每次跑測試都量 → 變了就紅，而它報得出變成多少
```

⚠️ 所以判準不是「要不要寫下那個數字」，是「**那個數字住在哪**」。

> **註解裡的每一個數字都是一個到期日；
> 而基線裡的每一個數字都是一份契約。**

🔴 **而它擋不到「理由」與「判定」**——那兩種沒有辦法住進基線
（它們是散文）。對那兩種，唯一的機制是**定期去量**，
而「定期」在實務上等於「**下一次有人碰到它的時候**」。

⚠️ 所以第二條判準：**碰到一筆帶理由的舊決定時，先問那個理由今天還成立嗎**
——那正是 2026-09-06 那一天做對的唯一一件事。

## ⚠️ 這個概念自己也會腐壞

上面那張表寫著「2026-09-06 量到七種」。**那個日期與那個數字，
就是這一份自己的到期日**。

🟢 而它的錨：`history/207`～`212` 六份轉變記錄。
表上每一列都指得到一份，而那些是**發生過的事**——它們不會變。

> **一份談腐壞的紀錄，要把自己錨在「發生過的事」上，
> 而不是「現在有幾種」。**

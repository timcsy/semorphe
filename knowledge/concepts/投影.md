# 投影（Projection）

語義結構的任何一種表示都是投影。這是整個系統唯一的擴充機制——新增功能等於新增一種投影，不等於修改核心。

**三視角投影：**

- **原則**：P1 投影定理——`view = project(structure, scope, viewType, viewParams)`
- **願景**：所有未來視圖（流程圖、資料流、接線、模擬、敘事）都是同一管線的新 viewType，不需改語言套件
- **經驗**：R0 雙射是設計目標而非工程現實——第三方 UI 框架有狀態，只能保證語義層等價

## 投影管線

```
view = project(structure, scope, viewType, viewParams)
其中 viewParams = { language, ...viewTypeSpecificParams }
```

**正交性**：Language 是基底參數，決定其他參數的**可用空間**。同一 viewType 內的參數彼此獨立；不同 viewType 的參數互不影響。

### 架構維度（開放集合）

```
┌─ Scope ───────────── 觀察範圍（開放序數：S0 語句 → S1 函式 → ...）────┐
├─ View Type ───────── 投影種類（開放集合：文字/視覺/行為/分析/...）────┤
├─ View Params ─────── 投影參數（每種 viewType 各自的參數空間）─────────┤
├─ Topic ───────────── 主題（同語言不同情境的層級樹和積木覆蓋）─────────┤
├─ Concept Layer ───── 元件代數（開放有序集：universal → lang-core → ...）┤
├─ Language Layer ──── 語言專屬（型別、語法、慣例）─────────────────────┤
├─ Locale ──────────── 自然語言（zh-TW / en / ...）────────────────────┤
├─ User Context ────── 使用者模型（慣性快取 + 角色意圖）────────────────┤
└─ ... ─────────────── 框架允許追加新維度 ─────────────────────────────┘
```

每一層獨立可配置、獨立可擴充。**維度集合本身也是開放的**——發現現有維度無法覆蓋的正交配置需求時，可追加新維度。

User Context 不直接影響投影結果，而是作為 View Params 的**推導來源**——使用者沒明確指定時，系統從慣性快取和角色意圖推導預設值（見 [漸進揭露](漸進揭露.md)）。

```
viewType    viewParams 範例
─────────   ────────────────────────────────────────────
code        { language, codeStyle: { indent, brace, naming, ... } }
blocks      { language, locale, blockStyle: { renderer, density, ... } }
flowchart   { language, layout, detailLevel, orientation }
execution   { language, strategy, backend, provider }
narrative   { language, audience, verbosity }
```

目前已實現：`code`、`blocks`、`execution`（直譯器），加上反向的 `parse` + `lift`。

## 可逆性分級（R0-R4）

設 `T` 為原始語義結構，`R = lift(project(T))`：

| 等級 | 名稱 | 定義 | 意義 |
|------|------|------|------|
| **R0** | 雙射 | `lift(project(T)) ≡ T` | 完全可逆，零損失 |
| **R1** | 語義保留 | `structured_info(R) ≡ structured_info(T)` | 語義不丟，呈現可丟 |
| **R2** | 結構可逆 | 主要拓撲可恢復，細粒度語義損失 | 骨架在，血肉缺 |
| **R3** | 片段可逆 | 部分語義片段可提取，整體不可恢復 | 能撿回碎片 |
| **R4** | 單向 | 無有意義的逆映射 | 只能觀察，不能反推 |

**關鍵洞察**：R0-R1 是**可編輯視圖**；R2-R4 是**唯讀視圖**（用於觀察、分析、溝通）。

```
R0 雙射 ──────── code:same_lang, blocks, semantic_package, share_link
R1 語義保留 ──── code:restyle, scaffolded:LN, syntax_highlight, braille,
                  high_contrast, embed_snippet, flowchart(簡單情況)
R2 結構可逆 ──── ast_tree, pseudocode, state_machine, data_flow,
                  screen_reader, flowchart(複雜情況), execution_trace
R3 片段可逆 ──── code:cross_lang, doc:structured, diff, call_graph,
                  dependency_graph, class_diagram, sequence_diagram, outline,
                  type_info, symbol_index, test_suite, api_surface,
                  protocol_schema, comparison, system_topology
R4 單向 ──────── narrative, error_report, execution, animation, benchmark,
                  complexity_metrics, coverage, lint, sonification,
                  worked_example, hint, assessment, memory_layout, minimap
```

投影族群共七類：文字、視覺結構、行為、分析、教育、可及性、分發。**這是開放集合**——需要新視圖時追加，不需要改核心。

**跨語言投影的組合性**：`code:cross_lang` 不是獨立 viewType，而是 lift + project 的組合：`project(lift(parse(codeA), langA), scope, code, { language: langB })`。可逆性取決於兩種語言間的語義阻抗（見 [元件代數](元件代數.md)）。

## 已實現的兩種 View Params

### Code Style（`code` viewType）

```
Preset 範例：
  APCS 考試:    cout/cin, camelCase*, K&R, 4-space, using namespace std
  競賽:         printf/scanf, snake_case*, K&R, 4-space, bits/stdc++.h
  Google Style: cout/cin, snake_case*, K&R, 2-space, 不用 using namespace

* naming convention 僅影響新建變數的預設名稱格式（見下方「變數命名的邊界」）
```

三大功能：(1) 選 preset → **積木不動**，重新生成程式碼 (2) 自動偵測：貼入程式碼 → 匹配最接近的 preset (3) 風格互轉：`Code(A) → Parser → 積木 → Generator(B) → Code(B)`。

Code Style 也影響工具箱：APCS 顯示 cout 積木、競賽顯示 printf 積木。

### Block Style（`blocks` viewType）

| 面向 | 選項 | 影響 |
|------|------|------|
| Renderer | zelos / geras | 圓角 vs 方角 |
| Density | compact / normal / spacious | 間距 |
| Colour scheme | scratch / classic / custom | 配色 |
| Inputs inline | true / false / auto | 水平或垂直 |
| Orientation | horizontal / vertical | 多值積木延伸方向 |

**Block Style 不影響**：語義樹結構、積木文字（Locale 控制）、程式碼生成（Code Style 控制）、可用積木集合（Language + P4 控制）。

> Block Style 切換會走 serialize → deserialize，這正是 PatternRenderer 自動推導的 input mapping 錯誤唯一會暴露的時機——見 [積木投影管線](積木投影管線.md)。

## 執行也是投影

「執行」不是生成文字或圖形，而是生成**行為**。每個語義節點有對應的 `execute()` 語義，語義直譯器直接走訪語義結構執行。

**策略（何時用）和後端（用什麼）是兩個獨立維度：**

```
view = project(structure, scope, execution, {
  executionStrategy: 'interpret' | 'compiled' | 'hybrid',
  backend: 'js' | 'wasm' | 'remote' | 'webgpu' | ...,
  provider: '@stdlib' | '@optimized' | ...,
})
```

| | interpret | js native | wasm | remote | webgpu |
|---|---|---|---|---|---|
| **速度** | 最慢 | 快（零 bridge） | 快（大量運算最佳） | 視網路延遲 | 快（GPU 平行） |
| **透明度** | 全透明 | 半透明 | 黑箱 | 黑箱 | 黑箱 |
| **時空旅行** | 無限回溯 | 關鍵點回溯 | pure 可重新執行 | 不可 | 不可 |
| **適用場景** | 教學/debug | 輕量運算 | 計算密集 | OS API | 矩陣/ML |

**外延等價**：每個執行體只需滿足 ∀ 合法輸入，`A(input) ≡ B(input)`，不要求內部結構相同。後端選擇是效能/透明度的取捨，**不影響語義正確性**。系統可用測試輸入自動驗證。

> ⚠️ **那個 `∀ 合法輸入` 是未加索引的形式。** 對所有輸入量化在一般情況下
> 不可判定，而「系統可用測試輸入自動驗證」這句話裡的**測試輸入就是觀察集**
> ——它決定了「相同」的解析度，而它會長大。
> 完整的形式要帶三樣東西：觀察集、容差、回饋週期。見
> [等價與觀察集](等價與觀察集.md)。

**預設策略：**

```
已知元件且有語義直譯器  → interpret
raw_code 且有執行體     → compiled（自動選最適後端）
raw_code 且無執行體     → 不可執行（汙染下游）
使用者手動切換          → 任何節點都可在 interpret ↔ compiled 間切換
```

**時空旅行除錯**：直譯器每步生成語義狀態快照，回溯 = 用歷史快照重新投影（viewParams 多一個 `timeStep`）。點擊輸出值可反向追蹤哪些節點「貢獻」了這個值。教學模式下所有 I/O 經由 Virtual I/O Layer 代理，回溯時只顯示對應時間步的輸出。

**編譯執行的狀態盲區**：直譯器看不到編譯執行節點的內部狀態，解法是節點宣告透明度等級——`pure: true`（重新呼叫即重現）/ `stateful: { getState(), setState() }`（快照介面）/ `opaque: true`（不透明屏障，只能從前面重新執行）。

執行透明度與 P4 的對應見 [認知鷹架](認知鷹架.md)。

## 語義結構的分層（Scope）

```
Scope 0 語句 → 節點          Scope 3 模組 → 語義子圖
Scope 1 函式 → 子樹          Scope 4 專案 → 語義圖
Scope 2 檔案 → 語義樹        Scope 5 系統 → 語義超圖
```

**Scope 0-2 是樹**（已實現），**Scope 3-5 是圖**（未來擴展）。每一層是前一層的**組合**，不是替換。

```
結構關係（樹邊，Scope 0-2）：parent-child — 語法巢狀
引用關係（圖邊，Scope 3+）： calls / imports / uses_type / extends / depends_on
```

**架構原則**：Scope 0-2 的語義樹不需要改變。Scope 3+ 的圖邊是從多棵語義樹**衍生**的索引結構——任何一棵樹改了，重建相關圖邊即可。

高 Scope 沒有 R0-R1 投影——這不是缺陷而是本質：跨檔案結構過於複雜，無法在單一視圖中無損編輯，必須回到子 Scope 修改。

## AST ≠ 語義樹

```
printf("hello");     // AST: call_expression(function="printf")
cout << "hello";     // AST: shift_expression(operator="<<")
                     // 語義樹: print(values: ["hello"])
```

AST 是語法層產物，語義樹是意圖層產物。`lift()` 是兩者之間的橋。

**`lift()` 是語法慣用語（syntactic idiom）的結構化辨識器**——用 pattern matching 和上下文查表辨識已知寫法。這是確定性、可驗證的過程，**不涉及意圖推斷**（「為什麼在這裡寫這個」）。真正的意圖推斷是機率性的，由 LLM 層處理。（這個定位是一次轉移的結果——原本 `lift()` 被當成「語用分析」，見 [history/002](../history/002-lift-從語用推斷改為慣用語辨識器.md)。）

| 語法結構 | 語用推斷 | 推斷依據 |
|---------|---------|---------|
| `for(int i=0;i<n;i++)` | `count_loop` | 慣用語辨識：init + cond + update 模式 |
| `cout << x << endl` | `print` | 身份辨識：`cout` 是什麼東西 |
| `printf("%d", x)` | `print` | 名稱辨識：`printf` 的已知語義 |
| `i++`（迴圈末尾） | 迴圈步進 | 位置上下文 |
| `i++`（獨立語句） | `cpp_increment` | 位置上下文 |

慣用語辨識解釋了四件設計決策：為什麼 lift() 需要符號表和作用域棧、為什麼 Pattern Engine 有多層、為什麼降級存在、為什麼高 Scope 比低 Scope 難。

**lift() 的狀態模型**：在**單次調用內**維護作用域棧 + 局部符號表；**跨次調用不共享狀態**。Style 切換不影響符號表——確保 lift() 與 Style 不耦合。

## 資訊分類學：什麼該保留、什麼可以丟

| | 語義 | 呈現 | 元資訊 | 語法偏好 |
|---|---|---|---|---|
| **定義** | 改行為 | 改外觀 | 不改行為有資訊價值 | 不改行為但使用者有意識的選擇 |
| **程式碼側** | 變數名、型別、邏輯 | 縮排、空行、命名風格 | 註解、pragma | `+=` vs `= x+1` |
| **積木側** | 連接關係、field 值 | 位置、顏色、tooltip | block comment | — |
| **儲存** | 語義樹節點 | metadata | annotation | metadata.syntaxPreference |
| **round-trip** | 必須保留 | 可丟失 | best-effort | best-effort |

**第五類——結構性依賴宣告**：`#include <iostream>`、`using namespace std;`、`import numpy as np` 不屬於上述任何一類。它是 **Scope 3 的圖邊投影到 Scope 2 程式碼中的產物**（跨 Scope 衍生投影），特徵是**可從語義樹的元件使用集合中確定性地推導**。因此 round-trip 規則是 best-effort：lift() 時可忽略（可重新推導），project() 時由 DependencyResolver 自動生成。使用者手動加的依賴記錄在 metadata 中避免丟失。

**註解模型**：行尾註解跟著宿主節點走（`position: 'inline'`）；獨立註解是**無操作的平級節點**（避免「最近節點」啟發式導致註解漂移）；表達式內部的註解附著在子節點上。annotation 可附著在任何層級的節點上。

## 投影可逆性 ≠ 語義樹完整性

```
投影可逆性（R0-R4）：投影管線本身的數學性質，與輸入無關。
  code 投影永遠是 R0，不管語義樹多殘缺。

語義樹完整性：lift() 能從 AST 恢復多少語義結構。
  受巨集、動態特性、框架 DSL 影響。完整性 = structured_nodes / total_nodes
```

R0 投影作用在不完整的語義樹上，roundtrip 仍然成立——raw_code 節點也能 roundtrip。所以「巨集導致大面積降級」**不是投影管線從 R0 退化到 R4**，而是語義樹完整性下降。**根公理不動搖**——它說「程式是語義結構」，不說「所有文字都能被語義化」。

## 推論：語義 Diff 是投影不變量

如果 `semanticDiff(T1, T2) = ∅`，則無論用什麼 viewParams 投影，語義層差異永遠為零——即使文字表示不同（Code Style 切換導致縮排、命名變化）。反之 `codeDiff ≠ ∅` 不代表 `semanticDiff ≠ ∅`。

**這是未來語義版本控制的理論基礎：style 變更 = semantic diff 0。** 挑戰在於序列化格式需要穩定（節點 ID 不隨重新 lift 改變）、merge 演算法需要理解樹結構而非行結構。

## 🔴 「積木好不好懂」的判準是**可逆性**，不是像不像原始語言

2026-08-17 使用者問：「有些套件我希望積木是方便理解的，但是這樣可能會和
純粹的 C++ 積木有點不一樣，例如某個套件的一連串功能等等。」

**而答案不是「不行」。** 積木本來就不必長得像 C++——這件事已經在做：

```
cout << x << endl        →  一顆「輸出 x 換行」積木        三個語法元素，一顆元件
vector<int> v = {1,2,3}  →  一顆「建立 int 動態陣列」積木
Serial.print / println   →  一顆元件，用「並換行／不換行」旗標區分
```

而標籤規範**明文禁止**把語法當標籤（「`.method()` 不可出現，用動詞描述」）。

### 而 [墓碑](../history/014-墓碑目錄.md#在程式碼之上疊一層積木)管的是另一件事

> 「以程式碼為真實，積木作為一層可視化包裝……⚰️ 已否決……
> **為什麼不選**：這使積木→程式碼**單向不可逆（R4）**，失去雙向 round-trip。」

🔴 **它否決的不是「積木長得不像 C++」，是「積木不是語義樹的投影」。**

> **判準只有一條：轉得回去嗎。**

### 三條合法的路 ＋ 一個反模式

| 路 | 什麼時候 | 條件 |
|---|---|---|
| **一顆元件，投影成多行** | 它**真的是一個語義行為**（`setCursor` ＋ `print` ＝「在第 1 行印 x」） | ⚠️ 使用者寫變體時**要能退回多顆元件**——lift 樣式加約束、不匹配就降級 |
| **同一身分的另一個形態** | 差別**只在呈現** | `form: {axis, value}`（已有）。🟢 語義樹一個字不動 |
| **函式** | 真的是「好幾個行為常一起用」 | 🟢 C++ 自己的答案，轉得回去，而且學到的東西可遷移 |

**🔴 反模式**：一顆積木展開成 N 行，**而那 N 行的變體它表達不出來**。
那不是投影，是**程式碼片段產生器**——**而它一旦進來，「積木→程式碼」就變回單向**。

### ⚠️ 而「不好懂」有兩種，成本差很多

```
名字不好懂   lcd.setCursor(0,1) → 「把游標移到第 1 行第 0 格」   ⚪ 便宜——那只是標籤
結構不好懂   三行才做完一件事                                    🟡 貴——要判斷它是不是【一個】行為
```

**預設走前者**（一個呼叫一顆元件 ＋ 好懂的標籤）；
只有在「學生看了三顆積木還是不知道發生什麼事」時才動第一條路。

> **一組總是一起出現的呼叫，才有資格被合成一顆元件；
> 而「總是」是一個可以數的東西。**

⚠️ 而**工具箱裡的預組積木是【另一個問題】**，它完全不碰語義樹——
見 [draft/套件積木的粒度與預組](../draft/2026-08-17-套件積木的粒度與預組.md)。

## 實用判定法

- 寫完一個新的 R0/R1 投影 → 跑 roundtrip，語義不能變
- R2-R4 投影不需要 roundtrip → 但需驗證投影**完整性**（不遺漏應投影的節點）
- 兩種視圖不一致了 → 回到根公理：所有視圖都是同一棵樹的投影
- 「轉不了」→ 不存在轉不了，只有降級程度（見 [降級與認知邊界](降級與認知邊界.md)）

## 🔴 雙重真相來源：同一顆積木有兩份定義，而它們會分岔

一顆積木的形狀有**兩個可能的來源**：

```
膠囊的 forms/blocks.json    宣告式，投影管線讀它
src/ui/block-registrar.ts   手寫的 Blockly 定義，動態積木（可增減的輸入）需要它
```

⚠️ **絕大多數積木只有前者**。而**需要動態輸入的**（引數個數會變的）
兩邊都要有——`cpp_func_call` 是這樣，而 `cpp_method_call` **只有前者**。

### 症狀：**兩側各自的測試都是綠的**

2026-08-18 使用者在 Arduino IDE 實測到 `Serial.write(cmd)` 的積木是
「對 Serial 執行 write（ ▯ ）」——括號裡是空的。

```
語義樹   children.args = [var_ref cmd]     ✅
產生器   Serial.write(cmd);                ✅
積木     inputs: {}                        🔴 引數不在上面
```

lift 的測試綠、generate 的測試綠、文字→文字的 round-trip 也綠
——**因為那條路徑根本沒有經過積木**。而使用者按一次「積木→程式碼」，`cmd` 就不見了。

> **一個資料只在【某一條投影】上丟失時，
> 任何不經過那條投影的測試都會是綠的。**

### 🔴 而根因有兩層，只修一層等於沒修

```
① renderMapping 把 `ARGS` 當成【欄位】對到 `args` 這個【接點】
   —— 接點是節點陣列，一個文字欄位裝不下它
② 修完①之後產出的 `ARG_0`【沒有插槽可接】
   —— 那是雙重真相來源本身：JSON 那一份改了，UI 那一份沒有
```

### 判準

**加一顆有「引數個數會變」的積木時，問兩件事**：

```
① renderMapping 用的是 `dynamicRules` 還是 `fields`？
   接點（節點陣列）**只能**走 dynamicRules
② `block-registrar.ts` 有沒有這顆的動態定義？
   沒有的話，產出的 `ARG_{i}` 沒有插槽可接
```

⚠️ 而**測試要渲染成積木狀態再斷言**——只驗語義樹與輸出字串抓不到它。
護欄在 `tests/integration/method-call-args.test.ts`。

⚠️ 同一族 2026-08-18 出現**三次**（液晶的建構參數、方法呼叫的引數、
以及液晶那顆在瀏覽器裡才看見）——**三次都是眼睛看到的，沒有一次是測試先報的**。

## 🔴 可逆性是一個**約束**，不只是一個功能

[願景](../vision.md)的比較表把雙向記成「我們多會一件事」
（「Blockly/Scratch：積木 → 程式碼（單向，不可逆）｜我們：程式碼 ↔ 積木」）。

⚠️ **而它同時是一個約束：它禁止了一整類設計。**

2026-08-18 查競品時撞到最清楚的一次——Mind+ 的擴充**一顆宣告積木都沒有**，
物件從動作積木自己長出來：

```ts
export function println(parameter, block) {
  Generator.addObject(`myoled`, `OLED_12864`, `myoled;`);   // 每個方法都發一次
  Generator.addSetup(`myoled.begin`, `myoled.begin();`);     // 靠鍵去重
  Generator.addCode(`myoled.printLine(${str});`);
}
```

那個設計**很好**：學生少拉一顆積木，而且**不可能忘記宣告**。

**而我們用不了它。** `OLED_12864 myoled;` 從程式碼回來時沒有任何積木對應
——一次同步就散了。

> **單向的工具可以讓一個東西「只存在於產出裡」；
> 雙向的工具裡沒有這種位置——每一行程式碼都必須有一顆積木認領它。**

### 兩個用途

🟢 **正面**：當一個設計「看起來比我們的簡潔」時，先問**它是不是靠單向省下來的**。
是的話，那不是我們該追的簡潔——⚠️ 而追它的代價會在**第二次同步**時才出現。

🟢 **反面**：我們推出的結論如果沒有競品做，**先問是不是這個約束造成的**。
「零件不是身分，是參數」（見 [元件代數](元件代數.md)）四家競品沒有一家這樣做
——**不是他們沒想到，是他們不必面對這個約束**。

### ⚠️ 而它與 R0–R4 是不同的東西

上面那節（可逆性分級）問的是「**這一次投影還原得了多少**」；
這一節問的是「**可逆這個要求，讓哪些設計不可用**」。
前者是量測，後者是**設計空間的邊界**。

## 🔴 一個視圖的歷史，屬於它當時投影的那份真相

2026-08-19，使用者在 Arduino IDE 實測：在 `setup()` 裡寫 `int x = 1;`，
按兩次 Cmd+Z，得到兩顆掉在最外層的 `int x;`（`= 1` 不見了）。

成因不在任何一次投影上——**四路走完一字不差**。它在**歷史**上：

```
① 使用者曾經親手拉過積木  → Blockly 的復原堆疊有項目
② 從程式碼重畫工作區      → 復原堆疊【沒有人清它】
③ Cmd+Z                   → 重放【重畫之前】的事件
④ 自動同步                → 把長回來的孤兒積木寫進檔案
```

> **一個被重畫過的視圖，它的復原歷史描述的是另一份真相；
> 重放那份歷史不是「還原」，是【把兩個世界混在一起】。**

這是「唯一真實，各式投影」的一個推論：投影**本身**是無狀態的，
而**復原堆疊是投影自己攢下來的狀態**——它一旦與真實脫節，就成為第二個真相來源。

判準：**這個視圖手上有沒有「不是從真實推導出來的」東西？**
有 → 真實一變，它就必須被丟掉，不能留著等人重放。

### 代價要說出來

清掉之後，面板上的 Cmd+Z 不再能還原更早的積木編輯。這是**刻意的取捨**：
自動模式下重畫很頻繁，而文件那側的復原才是使用者真正在用的
——用「少一段拿不回來的積木歷史」換「檔案不會被寫壞」。

## ⚠️ 一個沒在做事的守衛，與一個壞掉的守衛讀起來一模一樣

同一輪查出來的**副產品**：`busUpdateInProgress` 這個旗標從蓋好起就沒有為真過
——Blockly 走 `requestAnimationFrame → setTimeout(0)` 發事件，而旗標是同步開關的。

```
同步窗口結束時，聽到的事件數：0
一個 tick 之後：            2   ← 兩則都看到旗標是 false
```

🟢 而它一直沒出事，是因為**真正在擋的是別人**（`setState` 裡的 `Events.disable()`）。

> **一個宣告了保護、而保護由別人提供的守衛，
> 差別要到「真正在擋的那個被拿掉」的那天才看得出來。**

處置：讓守衛**跟著事件走**（事件群組），不押在時序上。
⚠️ **而它不是上面那個 bug 的成因**——把副產品當成成因，會結案在錯的地方。

## 排版屬於投影，不屬於真實

2026-08-19 使用者拍板：**空行是排版**。程式碼投影記住使用者的垂直留白，
重寫時對回去；積木那側看不到、也加不出空行。

判準是問「**它換一個投影還存在嗎**」：

```
`int x = 1;` 的那個 1      → 換成積木仍然在   → 真實
`}` 前面的那個空行          → 積木上沒有位置   → 排版
註解                       → 積木上有一顆     → 真實（而它確實是一顆膠囊）
```

🔴 推論一件要說清楚的事：**使用者在積木那側加不出空行**。
那不是缺陷，是這個決定的直接後果——**空行不是語義，所以語義的編輯器裡沒有它。**

⚠️ 而這條界線**不是靠直覺畫的**：註解看起來也像排版，而它是真實
——因為它換一個投影仍然要在。判準是投影不變性，不是「看起來重不重要」。

### 一個空行是「位置」還是「分隔」，看它下一行站在哪一層

使用者逐字（2026-08-19）：「setup 那邊原本的空行**被新東西覆蓋**感覺比較自然」
——Arduino 樣板那個空行是「在這裡寫你的程式」的**位置**，填進去了它就該消失。

⚠️ 而「新行吃掉後面的空行」這條**太寬**：

```
foo();          加了 baz() 之後，
                bar() 前面那個【分隔用】的空行
bar();          不該被吃掉
```

判準是**縮排**：`}` 比新行淺（＝區塊的結尾），而 `bar()` 與新行同層（＝分隔）。

> **同一個字元（一個空行），意思由它的鄰居決定——
> 而「鄰居」在這裡是【縮排層級】，不是【前後順序】。**

### 一個「重寫成一樣的內容」的寫入，不是沒有後果的

還原空行之後，沒有語義變動時結果與原檔**逐字相同** → 最小編輯算出「沒有差異」
→ **整個寫入不會發生**。

⚠️ 在此之前，**每一次同步都在重寫檔案**。沒有人把它當成缺陷，因為
「內容一樣」看起來無害——而它是前一週那一整串同步災難的燃料
（每一次重寫都是編輯器裡的一個復原項）。

> **一個沒有改變內容的寫入，仍然改變了歷史。**
